## Description

<!-- Please only use this template for submitting enhancement requests -->

**What would you like to be added**:
This is a request to add 2 metrics:
* Age of pending workloads, by clusterqueue. Gauge metric, presentable as a time series.
* Time from decision to preempt a workload till the time the preemption completes (latency of preemption), by clusterqueue. 

**Why is this needed**:
We are facing issues in production where some jobs remain pending for a long time. So, we want the average/max times that jobs are waiting in each clusterqueue. The `kueue_admission_wait_time_seconds` gives a somewhat similar metric but only for admitted workloads, not pending ones. Also, it is a histogram, not a time series. To make things simpler, this could be the time till job admission from either job creation or eviction. 

Secondly, another issue we have seen is that, once Kueue decides to preempt a workload, it may take a while for the workload to terminate. That's because it may have finalizers, long pod grace period, volume unmount issues, etc.  It would be good to measure the 'preemption latency', i.e., the time from the decision to preempt to the time preemption completes (i.e., the other workload is gone). 


**Completion requirements**:
Have the metrics visible in Prometheus.

### Comment by [@mimowo](https://github.com/mimowo) — 2026-05-04T16:21:08Z

@ns-sundar @amy thank you for the discussion 👍

First of all, I can certainly see some use case as mentioned in https://github.com/kubernetes-sigs/kueue/issues/10124#issuecomment-4356267672 for capturing workloads which cannot get admitted for a long time for alerting.

At the same time the metric has some cons:
1. it is not very idiomatic for k8s metrics, as metrics are usually updated in event-based fashion rather than by time. In this case updating the metric in event-driven fashion would be too costly, and unnecessarily too costly. Having said that there is some precedent in the core k8s. For example the apiserver_current_inflight_requests also seems to be [flushed periodically](https://github.com/kubernetes/kubernetes/blob/master/staging/src/k8s.io/apiserver/pkg/server/filters/maxinflight.go#L42C2-L42C33), but this is an exception rather than a rule, so it makes me wonder twice.
2. the metric has some potentially unexpected property, for example the "mean" or "median" may drop suddently if you create 100 low priority workloads. The workloads are waiting very shortly, so the metric goes down, but in fact nothing has changed for the biggest workloads.

Also,  I think there might be multiple reasons for long-pending workloads to occur:
1. they are misconfigured - wrong resource, wrong LQ, etc
2. they are very big and need to wait long for resources / preemptions
3. bug in Kueue ? For example "stuck" preemptions etc.

I think:
* for (1.) the better and more direct approach would be to do https://github.com/kubernetes-sigs/kueue/issues/10852. 
* for (3.) the better metric would be to focus on "guarantee violations" which would indicate a bug, similarly as proposed in https://github.com/kubernetes-sigs/kueue/pull/10485
* for (2.) the waiting time for workloads of similar size could be approximated pretty well retrospecively, by workloads in the same priority. The kueue_admission_wait_time_seconds metric is a histogram, so you could use promQL in Grafana to compute the diff in the last 1h to see the distribution of waiting times for workloads with XYZ priorities (similar workloads). With the new feature https://github.com/kubernetes-sigs/kueue/issues/7066 you can also add custom labels to workloads to put the workloads into dedicated buckets, even within the same priority.

So, I'm not sure we have a clear use case for the metric. Maybe it makes sense to first try with https://github.com/kubernetes-sigs/kueue/issues/10852 and re-evaluate if we still need the workload, wdyt @ns-sundar ?
