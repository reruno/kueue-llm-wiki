### Comment by [@ivnovakov](https://github.com/ivnovakov) — 2026-05-14T13:15:34Z

Yes, @mimowo. I looked through ci log, tested locally, and created a PR with related fixes.

The kuberay operator image pull failed with a **filesystem layer verification** error (content-integrity check on the downloaded layer — not image signing). That triggered the foreground `errexit` while `kind create cluster` was still running in a background subshell. Prow's CI cleanup then started shutting down docker-in-docker; after the 30-second `terminationGracePeriod`, it stopped the docker daemon, which SIGKILL'd the kind containers (kubeadm inside surfaced as `exit status 137`).

So in the log we see the layer-verification failure first, then the EXIT trap collecting artifacts against a half-built cluster (producing a cascade of `no context exists` / `unknown cluster` / `connection refused`), then `make: *** Error 1`, and then a deferred kind log dump from the background subshell. The dump is a bit messy because `cluster_create` didn't stop after kind failed — the `|| { echo; cat; }` let it continue past kind, and it only stopped at `kubectl config use-context` which returned a proper non-zero exit code.

Note: increasing `kind create cluster --wait` (e.g. from `1m` to `3m`) does not change failure behavior — kind's `--wait` is best-effort: on timeout it prints `WARNING: Timed out waiting for Ready` and exits 0, so the script proceeds regardless. The real readiness gate is the `kubectl wait --for=Ready node ... --timeout=5m` step immediately after. When that times out, `kubectl` exits 1, and `set -o errexit` stops the script.

This PR fixes the error-handling path in `cluster_create` and removes unnecessary error logs during `cleanup` in `cluster_collect_artifacts`: https://github.com/kubernetes-sigs/kueue/pull/11190

Since the actual trigger of the CI failure was a `docker pull`, how should we mitigate it? Adding a retry?
