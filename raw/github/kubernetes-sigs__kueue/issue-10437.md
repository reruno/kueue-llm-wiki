## Description


**What happened**:
In a MultiKueue environment, when a workload is executed on a worker cluster, 
the workload.status.accumulatedPastExecutionTimeSeconds field is not being populated/updated on the Workload object. This field remains unset or at its initial value (0 or nil) even after the workload has completed execution on the worker cluster.

**What you expected to happen**:
The workload.status.accumulatedPastExecutionTimeSeconds field should be updated with the actual execution time when a workload completes on a worker cluster in a MultiKueue setup. This field is critical for tracking workload re-execution and implementing features based on past execution history.

**How to reproduce it (as minimally and precisely as possible)**:
1. Set up a MultiKueue environment with a manager cluster and at least one worker cluster
2. Create a workload that gets admitted to the worker cluster
3. Wait for the workload to complete execution on the worker cluster
4. Check the workload status on the manager cluster:
$ kubectl get workload <workload-name> -n <namespace> -o jsonpath='{.status.accumulatedPastExecutionTimeSeconds}'
5. Observe that the field is not populated (returns empty, 0, or nil)

**Environment**:
- Kubernetes version (use `kubectl version`): v1.31.14
- Kueue version (use `git describe --tags --dirty --always`): v0.16.4
- Cloud provider or hardware configuration: HP A100 GPU Server 
- OS (e.g: `cat /etc/os-release`): Ubuntu 24.04.3
- Kernel (e.g. `uname -a`): Linux 6.8.0-90-generic
- Install tools: Helm

### Comment by [@kshalot](https://github.com/kshalot) — 2026-04-24T15:13:44Z

As mentioned in the [PR review](https://github.com/kubernetes-sigs/kueue/pull/10725#pullrequestreview-4170997478) (@MatteoFari thanks for working on that), I think this is working as intended.

`AccumulatedPastExecutionTimeSeconds` is only updated upon workload eviction, which I don't see in the reproduction steps. We can verify that MultiKueue indeed accumulates the admitted time since there are some subtleties to how MultiKueue handles evictions, but from what I can see in the code the local workload on the manager should correctly accumulate the time (and trigger a manager-level eviction when the defined max time is reached).

Regardless, we could use an e2e test case for that behavior in MultiKueue.

### Comment by [@kshalot](https://github.com/kshalot) — 2026-04-24T15:19:24Z

### Comment by [@alison-lim](https://github.com/alison-lim) — 2026-04-28T07:45:01Z

Following your explanation, the accumulatedPastExecutionTimeSeconds field is updated only when the remote cluster's workload is evicted, not during normal completion or while the workload is running? If that's the case, no code modification is needed. I previously assumed this field would synchronize all running time accumulated up to the current point.

### Comment by [@kshalot](https://github.com/kshalot) — 2026-04-28T10:06:07Z

Yes. This field is mostly used to be able to enforce `MaximumExecutionTimeSeconds` across evictions. [Documentation](https://kueue.sigs.k8s.io/docs/reference/kueue.v1beta2/#kueue-x-k8s-io-v1beta2-WorkloadStatus) for full context:
> accumulatedPastExecutionTimeSeconds holds the total time, in seconds, the workload spent in Admitted state, in the **previous** Admit - Evict cycles.

In MultiKueue, `accumulatedPastExecutionTimeSeconds` should be tallied up in the manager cluster's workload.

IIUC we can close the issue.
