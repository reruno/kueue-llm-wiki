 **What happened**:

In a Kueue + DRA setup, when `deviceClassMappings` is removed from the Kueue configuration (e.g., via the Kueue CR in OpenShift), Kueue loses all awareness of DRA-managed GPU resources. However, it continues to admit workloads that reference DRA `ResourceClaimTemplates` and unsuspends Jobs as if everything is properly configured.

This means:
  - DRA workloads are admitted and Jobs unsuspended without any warning that `deviceClassMappings` is not configured
  - The `ResourceClaim` is allocated directly by the Kubernetes DRA scheduler, bypassing Kueue's quota entirely
  - The ClusterQueue's GPU resource usage remains at `0` despite a physical GPU being consumed
  - Since Kueue always sees DRA resource usage as `0`, it will admit an unlimited number of DRA workloads regardless of the `nominalQuota` value.

**What you expected to happen**:
When a DRA workload references a `DeviceClass` that has no corresponding `deviceClassMapping` configured, Kueue could either:
  - Reject admission with a message like: `"Workload references DeviceClass 'gpu.nvidia.com' but no deviceClassMapping is configured"`
  - Or set a warning condition on the Workload indicating the DRA resource is not being quota-managed

**How to reproduce it (as minimally and precisely as possible)**:

  1. Remove `deviceClassMappings` from the Kueue configuration and wait for reconciliation
  2. Verify that `deviceClassMapping` was removed from the kueue-manager-config ConfigMap
  3. Create Kueue resources with a GPU-related `coveredResource` (ResourceFlavor, ClusterQueue, Namespace, and LocalQueue)
  4. Submit a DRA workload referencing a `ResourceClaimTemplate`
  5. Observe the workload is admitted, the Job is unsuspended, and the GPU is consumed outside Kueue's control via DRA
  6. Check `kubectl describe clusterqueue` — GPU usage shows `0` despite physical GPU being consumed through DRA

**Anything else we need to know?**:

This silently bypasses quota enforcement. Since Kueue never accounts for DRA resource usage, it will admit an unlimited number of DRA workloads regardless of `nominalQuota`. There is no error, warning, or condition indicating the misconfiguration — making it easy to over-commit physical GPUs without any visibility.

### Comment by [@sohankunkerkar](https://github.com/sohankunkerkar) — 2026-05-05T20:52:22Z

The bug is real for `ResourceClaimTemplate/ResourceClaim` workloads and needs fixing. Extended resources like `nvidia.com/gpu: 2` in container requests are not affected though, they're still quota-accounted through PodRequests() under their literal resource name regardless of gate state. The DRA replacement branch is gated and skipped when DRA is off, but the base `PodRequests()` call always picks them up. The quota hole is specifically about workloads whose DRA usage lives in pod-level resourceClaims since those are caught by `HasDRA()` but skipped by `NeedsDRAReconcile()` when the gate is off.
   
I don't think we need a new DRA gate for this though. We already handle the same pattern without a gate today. When DRA is enabled and a DeviceClass is not in deviceClassMappings, the workload gets marked `WorkloadInadmissible`. The DRA-disabled case can follow the same path. `HasDRA()` is already ungated so the check is just `!features.Enabled(DRA) && HasDRA(wl)` in Reconcile plus the event handler skips at the same sites where `NeedsDRAReconcile` is already checked. The existing recovery pattern already handles this: mark inadmissible now, clear the condition and admit after config fix and restart. Same flow as the unmapped DeviceClass test.

### Comment by [@sohankunkerkar](https://github.com/sohankunkerkar) — 2026-05-06T20:12:45Z

With https://github.com/kubernetes-sigs/kueue/pull/10996, the existing code already handles the following cases:
  - Workload with RCTs and a mapped DeviceClass: DRA processing runs, quota is tracked, workload admitted normally.                                                          
  - Workload with RCTs and an unmapped DeviceClass: workload is marked WorkloadInadmissible with a clear message                                                                                                                                             
  - GB200 ComputeDomain: the admin maps the ComputeDomain DeviceClass in deviceClassMappings alongside the GPU DeviceClass. Both get processed, `nvidia.com/gpu` quota is tracked, workload admitted. If ComputeDomain is not mapped, the workload is rejected with a clear error telling the admin exactly what to configure. This is the same contract as any other DRA DeviceClass.                                                                                                    
  - dra-cpu-driver and dranet: same pattern. Map the DeviceClass and quota is tracked. Don't map it and the admin gets a clear error pointing them to the fix.
                                                                                                                                                                                                                                
The only remaining scenario is when an admin explicitly disables DRA after beta promotion. But at that point they're making a conscious choice to opt out of DRA support. If DRA workloads are still submitted, that's a configuration decision they own, not a bug Kueue needs to work around.
