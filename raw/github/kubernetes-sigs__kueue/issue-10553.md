**What would you like to be added**:

I would like to revisit the architectural problem we encountered and discussed here: https://github.com/kubernetes-sigs/kueue/pull/10496#discussion_r3087674111

There are some ideas here. Let me add another possiblity worth exploring which is to externalize the visbility server to a dedicated Pod/Deployment (as KueueViz or kueue-populator). This is something that @Nilsachy @dkaluza may need to consider for their use case anyway. This would allow the "core" Kueue to stop using leaderAwareReconciler model.

**Why is this needed**:

To make clarify on the long term cache management for the project.

### Comment by [@dkaluza](https://github.com/dkaluza) — 2026-04-29T12:04:35Z

I think due to discussions in the various subgroups we are lacking some communication here which can cause misunderstandings. I will try to add some information to make sure everybody is up to date.
  
Generally the problem we are facing right now is a firewall issue, if Kueue is run in an isolated secure subnetwork  it may be not possible to register an APIService targeting it.

The first idea that we had was that maybe a separation of visibility to a distinct pod (with less privilages, e.g. not allowing it to update resources) will allow us to run it outside of the secure subnetwork and thereby have the APIService targeting it. 

As mentioned by @mwielgus it has downsides like larger memory usage, and visibility getting out of sync even in small clusters that would right now require only one pod.

During discussions with @mimowo I have suggested that maybe this can be handled by a CRD's representing **list of pending workloads** that can be updated periodically, e.g. X minutes. But we have reached a conclusion that as resources are limited to 1.5 Mi and this would require updating thousands of resources this will not work well and can lead to performance problems. Generally this would also be a regression from the current visibility functionalities.

Yesterday I had a sync with @mwielgus on which he has suggested **other** CRD based approach, which in principal works as follows: 
1. Users create new custom resources which symbolize a **"visibility API request".**
2. New controller fulfills those requests by just running current visibility API code. Then it  inserts outcomes to appropriate field of the resources and updates its status to done.
3. User can fetch the results from the resource. Resources are deleted manually by the user when he no longer need them or  after X time by the controller. 
With pagination and some automatic cleanup of resources this will avoid APIService registration and let us use majority of the existing visibility code.
