**What would you like to be added**:
A mechanism of ordering MultiKueue Manager Workloads. The aim is to provide users with an accurate and informative estimate of when each Manager Workload will be admitted in the context of a specific MultiKueue Manager Cluster Queue.

**Why is this needed**:
The Pending Workload Ordering in the cluster queue in the Management Cluster is a limited source of information - users have no way of tracking the relative order of Manager Workloads once they get the quota on the Manager and start Dispatching.
The reported Workload position in queue in the Management Cluster must reflect the true state derived from remote clusters.

# Overview
We extend the Visibility API with a new subresource to track the order of Manager Workloads of a specific Manager Cluster Queue. The ordering happens in three stages:
First the workloads of the Manager Cluster Queue are gathered and processed. We determine which workloads should be ordered, then which require data from the Workers to do so.
Then we gather the data from the Workers finding Remote Workloads which are most likely to be admitted first for each Manager Workload.
Finally, using the gathered remotes and information sourced from Manager Workloads themselves we order them and provide users with a result: a list of Manager Workloads estimating the order in which said workloads will be admitted on one of the Worker Clusters.

# Ordering Scheme Proposal
When ordering workloads we will utilize the following types of timestamps:
* **Quota Reserved Timestamp** – the timestamp of when the workload has last received a quota reservation,
* **Create Timestamp** – the timestamp of when the workload was first created (in its cluster).
* **Timeout Timestamp** – the timestamp of when the workload has last been put into timeout (it became inactive or inadmissible).
All timestamps will be ordered from Oldest to Latest. 

To identify and order relevant Workloads (both Manager and Remote Workloads), we define three Workload Tiers:
* **Tier [1]** – QuotaReserved – Workloads that received QuotaReservation on their cluster (Manager for Manager Workloads, Worker for Remote Workloads), but have not yet been Admitted,
* **Tier [2]** – Pending – Workloads that are queued for receiving quota.
* **Tier [3]** – Other, NOT Admitted – other workloads, that are a step behind Pending (inactive, inadmissible, etc.).

Tier [1] Workloads will be considered closer to being admitted than Tier [2] Workloads, both closer than Tier [3] Workloads (Tier [1] < Tier [2] < Tier [3]). Workloads that are already admitted will be ignored. Workloads that are not admitted but do not fit either of those tiers will be considered Tier [3].

Tier [3] Manager Workloads will be ordered by their Create Timestamp.

Tier [2] Manager Workloads will be ordered increasingly based on their Manager Cluster Queue Position.

Ordering Tier [1] Manager Workloads requires finding their **Best Chance Remote (BCR)** - a Remote Workload considered to be closest to being admitted on their Worker Cluster.
To identify the BCR, we split all Remote Workloads of the specific Manager Workloads into the same two tiers. Since Tier 1 Manager Workloads are not yet Admitted, no remotes that are Admitted or Finished should exist. Remote Workloads that fit neither of the two tiers (are inactive, inadmissible or otherwise considered to be too far from being Admitted to be considered in the ordering) will be ignored.

The BCR will be chosen by gathering all Remote Workloads of a given MW that fit tiers 1 and 2, then checking the following conditions:
1. If any Tier 1 Remotes exist, we will choose one with the oldest Quota Reserved Timestamp.
1. Else, if any Tier 2 Remotes exist, we will choose one with the lowest Workload Score, then one with the oldest Create Timestamp.
1. If no Tier 1 or Tier 2 Remotes exist, the BCR will be set to nil.
**Workload Score** will be calculated as the position of the Remote Workload within their Worker Cluster Queue.
Tier 3 Remotes will be ignored here, as they are considered “too far behind on the road to being admitted” at this point in time.

When comparing two Tier 1 Manager Workloads, we will order them based on the following criteria:
* Workloads with BCR will be ordered before workloads without BCR (i.e. with BCR == nil).
* If both workloads have non-nil BCR:
    * If their BCR are of different tiers, one with Tier 1 BCR will be ordered before the one with Tier 2 BCR,
    * If both BCR are of Tier 1, the MWs will be ordered based on BCR’s Quota Reserved Timestamp.
    * If both BCR are of Tier 2, the MWs will be ordered based on BCR’s Workload Score, then its Create Timestamp.
* If BCR of both workloads are equal (including both being nil), we will order these Manager Workloads based on their Quota Reserved Timestamp.

# Alternative workload score

**Full Queue Cycles Until Admission Attempt Parameter**

Instead of using a simple Workload Score - the position in the Worker Cluster Queue - we could consider a more complex parameter. Specifically one that expresses the state of the Workload more accurately and includes the context of the Workload’s Cluster Queue and its configuration.

Full Queue Cycles Until Admission Attempt would be a composite value calculated based on:
A: Total cluster queue resource availability
Q: The amount of resource requested by the workload
P: Total resource amount requested by preceding workloads
R: The amount of the resource that is currently reserved

For each resource we want to estimate how much of the resource has to be processed by the queue, meaning reserved then used-and-released. Then we can consider how much it is in “full queue capacity”, effectively getting a number denoting how much resources (in full queue capacity units) must be reserved (and potentially released) before the subject workload gets a chance to be admitted (get quota reservation).

This value would be calculated as: (Q + P + R) / A — (our request + preceding requests + currently reserved) / queues capacity for given resource. The parameter would be calculated per resource managed by the queue for each workload in it.

We can then compare this value within the scopes of each workload between each resource managed by the queue, with MAX representing the aggregated value (as we will have to wait until the most demanding resource receives its reservation) to represent the workload in question. In case a workload has partial reservations, we just need to account that the Q should be adjusted as it is already included in R.

# Visibility API and Client
## Extending Visibility API
The ordered Manager Workloads list will be exposed to the users via Visibility API. Specifically, we will collect the result ordered list into visibilityv1beta2.PendingWorkloadsSummary. Each Manager Workload will be represented by a PendingWorkload, with local and cluster queue positions determined by the MW’s position in the resulting list.

To expose the MultiKueue PendingWorkloadsSummary, we will extend the Visibility Server with a new subresource: multikueueworkloads, populated via multiKueueGlobalSummaryREST:
```go
func NewStorage(mgr *qcache.Manager) map[string]rest.Storage {
 return map[string]rest.Storage{
   "clusterqueues":                  NewCqREST(),
   "clusterqueues/pendingworkloads": NewPendingWorkloadsInCqREST(mgr),
   "clusterqueues/multikueueworkloads": NewMultiKueueGlobalSummaryREST(mgr),
   "localqueues":                    NewLqREST(),
   "localqueues/pendingworkloads":   NewPendingWorkloadsInLqREST(mgr),
 }
}
```

"clusterqueues/multikueueworkloads" will be added to storage only if the MultiKueueGlobalSummary feature is enabled. The class will implement the rest.Storage, rest.Getter and rest.Scoperinterfaces. The core logic will be implemented inside the Get method of the rest.Getter interface:

```go
func (m *multiKueueGlobalSummaryREST) Get(ctx context.Context, name string, opts runtime.Object) (runtime.Object, error)
```

## Complete design
We would implement a Caching mechanism populated by the MultiKueue Workloads Reconciler:

```go
type MultiKueueCache struct {
	// Tier 1 Remote Workloads identified as Best Chance Remotes for the referenced T1 Manager Workload.
	t1Bcr map[workload.Reference]Tier1RemoteWorkloadInfo
// Tier 2 Remote Workloads of the referenced T1 Manager Workloads that do not have any Tier 1 Remotes. Recorded to identify the Best Chance Remote when compared with a list of Pending Workloads from Worker Cluster Queues.
	t2Remotes map[workload.Reference]sets.Set[Tier2RemoteWorkloadInfo]
}

// Tier 1 Remote
type Tier1RemoteWorkloadInfo struct {
quotaReservedTime v1.Time
}

// Tier 2 Remote
type Tier2RemoteWorkloadInfo struct {
pendingTime 		v1.Time
	// Required to identify Workload Score
workerName 		string
workerClusterQueue 	string
}
```

**WARNING:** this caching strategy must be implemented with Leader Awareness in mind. For context see: https://github.com/kubernetes-sigs/kueue/issues/11163.

The population of this cache in the MK Workload Reconciler would proceed as follows:
1. Check if the Manager Workload is of Tier 1.
1. If not - ignore, else proceed.
1. Assign an appropriate tier to each Remote.
1. If Tier 1 remotes exist, find the BCR and save it to cache.
1. If no Tier 1 remotes exist - save the Tier 2 Remotes to the cache.

The GET method will calculate the ordered list of Manager Workload by:
1. Identify if the Cluster Queue is a Manager Cluster Queue by checking if it possesses the MultiKueue Admission Check.
1. If not, return an error stating the Cluster Queue of the given name is not a MultiKueue Queue.
1. If yes, list all Manager Workloads (of the specific Manager Cluster Queue) via the qcache.Manager.
1. Identify and label Tier 1-3 Manager Workloads, discard the rest.
1. Identify the Best Chance Remotes (BCR) for all Tier 1 Manager Workloads.
1. Order Workloads in all tiers, then collect them into a joint list (ordered as tier 1, tier 2 then tier 3 at the end).
1. Assign each workload a position based on their index in this ordered list. Local queue position will be calculated the same way, once the list is filtered to only contain Workloads from the specific LQ.

BCR will be identified as follows:
1. Collect all Tier 1 Manager Workloads.
1. If a T1MW has `t1Bcr` not nil in the MultiKueueCache, use it as the BCR for that T1MW.
Else use the following steps to determine the BCR for that T1MW.
1. Get all Tier 2 Remote Workloads of the gathered T1 MWs from MultiKueueCache.
1. If no Remote Workloads exist, set BCR to nil. Else proceed.
1. Calculate T2RW’s Workload Scores and find the BCR:
    1. identify all Workers and Worker Cluster Queues containing any of the Tier 2 Remotes (using the CQ Names saved in the cache),
    1. query each worker per identified cluster queue for the Cluster Queue’s Pending Workloads (via remoteClients[worker].visibility.{...}),
    1. search these results for each of the Tier 2 Remotes’ Worker Cluster Queue Position,
    1. remotes with the lowest position (oldest timestamp, if positions are equal) will be chosen as BCR for their respective Manager Workloads.
