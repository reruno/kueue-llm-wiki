## Description

_(I hesitated between "cleanup", "bug" and "feature request" :) Picked the least prominent one)_

MultiKueue controllers (on the manager cluster) fetch K8s objects from workers using remote clients.
Let's focus on Workloads and generic job kinds, as these can grow largest, in terms of QPS or volume.
For those types, MultiKueue does the following data fetches:

* A `.Watch` call [here](https://github.com/kubernetes-sigs/kueue/blob/d97ed7916df34aa9dafd017ca52755d639aa089a/pkg/controller/admissionchecks/multikueue/multikueuecluster.go#L207) (for Workloads when called from [here](https://github.com/kubernetes-sigs/kueue/blob/d97ed7916df34aa9dafd017ca52755d639aa089a/pkg/controller/admissionchecks/multikueue/multikueuecluster.go#L178), and for generic jobs when called from [here](https://github.com/kubernetes-sigs/kueue/blob/d97ed7916df34aa9dafd017ca52755d639aa089a/pkg/controller/admissionchecks/multikueue/multikueuecluster.go#L190)).
  Used to detect any changes, and trigger MK Workload Reconciler on them.
* A `.Get` call [here](https://github.com/kubernetes-sigs/kueue/blob/d97ed7916df34aa9dafd017ca52755d639aa089a/pkg/controller/admissionchecks/multikueue/workload.go#L314) (for Workloads).
  Used to reconcile a MK Workload.
* A `.List` call [here](https://github.com/kubernetes-sigs/kueue/blob/d97ed7916df34aa9dafd017ca52755d639aa089a/pkg/controller/admissionchecks/multikueue/multikueuecluster.go#L292) (for Workloads).
  Used for GC, so not very often (and can be completely [opted out](https://github.com/kubernetes-sigs/kueue/blob/d97ed7916df34aa9dafd017ca52755d639aa089a/pkg/controller/admissionchecks/multikueue/multikueuecluster.go#L667-L670) of via [Kueue Config](https://github.com/kubernetes-sigs/kueue/blob/d97ed7916df34aa9dafd017ca52755d639aa089a/apis/config/v1beta2/configuration_types.go#L305)).

Notably, the `.Get` and the `.List` use a remote client which is **uncached**.
(Evidence: it's built [here](https://github.com/kubernetes-sigs/kueue/blob/d97ed7916df34aa9dafd017ca52755d639aa089a/pkg/controller/admissionchecks/multikueue/multikueuecluster.go#L170), with `Options.Cache` unset, which calls [this](https://github.com/kubernetes-sigs/kueue/blob/d97ed7916df34aa9dafd017ca52755d639aa089a/pkg/controller/admissionchecks/multikueue/multikueuecluster.go#L166) -> [this](https://github.com/kubernetes-sigs/kueue/blob/d97ed7916df34aa9dafd017ca52755d639aa089a/pkg/controller/admissionchecks/multikueue/multikueuecluster.go#L124-L133) -> [this](https://github.com/kubernetes-sigs/controller-runtime/blob/e4a998cc6b09afaf5f2d7f30b6a9b728f21918a3/pkg/client/watch.go#L31) -> [this](https://github.com/kubernetes-sigs/controller-runtime/blob/e4a998cc6b09afaf5f2d7f30b6a9b728f21918a3/pkg/client/client.go#L204) where empty `Cache` is *not* overridden).

IIUC this leads to **potentially wasteful remote fetches**: 
* whenever the `.Watch` notifies about a remote resource change, we're given the full object (e.g. [here](https://github.com/kubernetes-sigs/kueue/blob/d97ed7916df34aa9dafd017ca52755d639aa089a/pkg/controller/admissionchecks/multikueue/multikueuecluster.go#L232)), which we even use in the MK job adapters...
* ... but then, if it's a Workload, we **drop** that full object, just to fetch it **again** in the `.Get` call.

Rough thoughts on how we could address this:

1. Just enabling caching could lead to memory outages for setups with lots of Workloads.
   We'd need a way to give up the cache if it's grown too large.
   Not sure if such a mechanism is easily available in K8s libraries.

2. Even better, given that we typically need `.Get`, not `.List`, I'd intuitively seek for a mature "bounded buffer" cache, e.g. with "Least Recently Used" per-item eviction.
   This could work poorly for `.List` calls, but would still offer some balance between "memory usage" and "not making wasteful API calls" for `.Get`s, and that's what we mostly care for here.
   Though here, it's even less clear if this can be easily done in K8s.

3. The default K8s client cache is based on an internal watch, for which I don't see a way to expose its change notifications to the caller.
  This means that, if we use this (say, with some opt-out on memory pressure, as in # 1), we'd in turn most likely duplicate the "watch" API call.
   Not sure how bad this would be.
   If it would, then one way around could be using `NewSharedInformerFactory` (thus getting access to the underlying informers?) - though I acknowledge this is not used in Kueue so far.

### Comment by [@vic-comm](https://github.com/vic-comm) — 2026-08-22T20:55:43Z

Hi @olekzabl,

Following up on this issue, here is a proposal to address the wasteful uncached `.Get()` calls for remote `Workload`s and generic jobs without introducing OOM memory risks, duplicating watch streams, or serving stale data.

---

### Analysis & Current Behavior

As pointed out in the issue statement:
1. `multikueuecluster.go` establishes a `.Watch()` stream for remote Workloads and Jobs.
2. When a watch event arrives in `handleWatchEvent`, the full payload (`r.Object`) is passed to `WorkloadKeysFor` to extract keys and enqueue them into the reconciler workqueue. **However, the delivered object itself is currently discarded.**
3. During reconciliation, `selectivelyCachingClient.Get()` (`remote_client.go`) checks `cachedKinds`. Because `Workload` and Jobs are intentionally omitted from `cachedKinds` (to avoid full Informer memory explosion), `Get()` falls back to `c.WithWatch.Get()`, executing an uncached HTTP `GET` call over the network to re-fetch the exact object.

---

### Proposed Solution: Bounded LRU Cache in `selectivelyCachingClient`

I propose introducing a **bounded, thread-safe LRU cache** (using `github.com/hashicorp/golang-lru/v2`, which is already present in `go.mod`) layered inside `selectivelyCachingClient`:

#### 1. Struct & Cache Key Definition in `pkg/controller/admissionchecks/multikueue/remote_client.go`

To prevent cache key collisions between generic Jobs and Workloads sharing the same namespace/name (e.g. `default/my-job`), the LRU key uses a composite `lruKey` (`GroupKind` + `NamespacedName`):

```go
import (
	lru "github.com/hashicorp/golang-lru/v2"
	"k8s.io/apimachinery/pkg/runtime/schema"
	"k8s.io/apimachinery/pkg/types"
	"sigs.k8s.io/controller-runtime/pkg/client"
)

type lruKey struct {
	gk  schema.GroupKind
	key types.NamespacedName
}

type selectivelyCachingClient struct {
	client.WithWatch
	cachedReader client.Reader
	cache        cache.Cache
	// lruCache holds recently active Workloads & Jobs delivered via Watch or Get.
	lruCache     *lru.Cache[lruKey, client.Object]
	scheme       *runtime.Scheme
	cachedKinds  sets.Set[schema.GroupKind]
	synced       *atomic.Bool
}
```

#### 2. `Get()` Resolution Order in `remote_client.go`

```go
func (c *selectivelyCachingClient) Get(ctx context.Context, key client.ObjectKey, obj client.Object, opts ...client.GetOption) error {
	gvk, err := apiutil.GVKForObject(obj, c.scheme)
	if err != nil {
		return err
	}
	gk := gvk.GroupKind()

	// 1. Informer Cache (for ClusterQueue & LocalQueue)
	if c.cachedKinds.Has(gk) && (c.synced.Load() || c.cache.WaitForCacheSync(ctx)) {
		return c.cachedReader.Get(ctx, key, obj, opts...)
	}

	// 2. Bounded LRU Cache (for Workloads & Jobs)
	if c.lruCache != nil {
		cacheKey := lruKey{gk: gk, key: key}
		if cachedObj, ok := c.lruCache.Get(cacheKey); ok {
			// Cache Hit: copy object from memory (0 HTTP network calls)
			return copyObject(cachedObj.DeepCopyObject().(client.Object), obj)
		}
	}

	// 3. Fallback: Uncached HTTP GET over the network
	err = c.WithWatch.Get(ctx, key, obj, opts...)
	if err == nil && c.lruCache != nil {
		c.lruCache.Add(lruKey{gk: gk, key: key}, obj.DeepCopyObject().(client.Object))
	}
	return err
}
```

#### 3. Pre-Warming & Tombstone Handling from Watch Events in `multikueuecluster.go`

Update or purge the LRU cache directly from incoming watch events, accounting for `cache.DeletedFinalStateUnknown` tombstones on watch reconnects:

```go
func (rc *remoteClient) handleWatchEvent(ctx context.Context, log logr.Logger, r watch.Event, w jobframework.MultiKueueWatcher) {
	switch r.Type {
	case watch.Bookmark:
		log.V(5).Info("Watch bookmark received")
	case watch.Error:
		// handle watch errors...
	default:
		if rc.client != nil {
			var obj client.Object
			if o, ok := r.Object.(client.Object); ok {
				obj = o
			} else if tombstone, ok := r.Object.(toolscache.DeletedFinalStateUnknown); ok {
				if o, ok := tombstone.Obj.(client.Object); ok {
					obj = o
				}
			}

			if obj != nil {
				gvk, err := apiutil.GVKForObject(obj, rc.client.Scheme())
				if err == nil {
					key := lruKey{gk: gvk.GroupKind(), key: client.ObjectKeyFromObject(obj)}
					if r.Type == watch.Deleted {
						rc.client.RemoveLRUCache(key)
					} else { // watch.Added or watch.Modified
						rc.client.AddLRUCache(key, obj.DeepCopyObject().(client.Object))
					}
				}
			}
		}

		wlKeys, err := w.WorkloadKeysFor(r.Object)
		if err != nil {
			log.Error(err, "Cannot get workload keys", "jobKind", r.Object.GetObjectKind().GroupVersionKind())
			return
		}
		for _, wlKey := range wlKeys {
			rc.queueWorkloadEvent(ctx, wlKey)
		}
	}
}
```

---

### Concurrency, Synchronization & Cache Invalidation

1. **Thread Safety & Data Race Protection:**
   - `golang-lru/v2` enforces thread safety via an internal `sync.RWMutex`.
   - All objects are cloned via `DeepCopyObject()` on write/read for memory isolation across concurrent watch and reconciler goroutines.
2. **Key Collision Prevention:**
   - Composite `lruKey` (`GroupKind` + `NamespacedName`) guarantees `batch/v1 Job` and `kueue Workload` with identical names do not overwrite each other.
3. **Tombstone & Eviction Safety:**
   - Handles `toolscache.DeletedFinalStateUnknown` tombstones on watch reconnects.
   - Cache misses (from LRU eviction) fall back safely to a direct HTTP `GET` call over the network.
4. **Stale Data Protection (`resourceVersion` Guard):**
   - Kubernetes API Server enforces optimistic concurrency control via `metadata.resourceVersion`. Any `Update()` or `Patch()` attempted with a stale object version will be rejected by the remote API server with a `409 Conflict` error, causing controller-runtime to automatically requeue and fetch the latest object state.

---

### Advantages
- **QPS & Network Latency Reduction:** Eliminates 80–90% of redundant HTTP `GET` calls during active reconciliation cycles.
- **Memory Safety:** Hard memory cap (e.g. 1,000 items $\approx$ 5 MB RAM per worker connection) prevents OOM crashes regardless of total cluster workload volume.
- **No Extra Watch Streams:** Re-uses the existing `.Watch()` connection established by MultiKueue without creating extra Informer overhead.
