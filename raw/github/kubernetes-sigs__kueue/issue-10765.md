## Description

**What would you like to be added**:

A mechanism to designate a WorkloadPriorityClass as the cluster-wide default, so that workloads without an explicit `kueue.x-k8s.io/priority-class` label automatically receive its priority value instead of falling through to the Kubernetes `scheduling.k8s.io/v1` PriorityClass chain.

This could take the form of a `globalDefault` boolean field on WorkloadPriorityClass (mirroring the Kubernetes PriorityClass API), or a configuration option in the Kueue Configuration API. The behaviour should be opt-in and preserve the current fall back mechanism.

**Why is this needed**:

In clusters where only a subset of workloads are managed by Kueue, admins need a way to assign a `default` WorkloadPriorityClass to Kueue-managed workloads without requiring job authors to explicitly set the `kueue.x-k8s.io/priority-class` label on every job.

Today, if a Kueue-managed job omits that label, `ExtractPriority()` falls through to the Kubernetes `scheduling.k8s.io/v1 PriorityClass` chain — either from the PodSpec, the `globalDefault` PriorityClass, or a hardcoded 0. This conflates pod scheduling priority with queueing priority, which are intentionally separate concerns in clusters that use WorkloadPriorityClass.

The only workarounds are:

1. Require every job author to set the label — which is fragile and hard to enforce across teams.
2. Deploy a custom mutating webhook — which adds operational overhead just to inject a default value that Kueue could handle natively.

A default WorkloadPriorityClass would let Kueue set the priority automatically at admission time for workloads that don't specify one, keeping all Kueue-managed workloads in a consistent priority domain without burdening users or requiring external mutation infrastructure.
