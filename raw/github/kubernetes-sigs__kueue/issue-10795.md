## Description

When RayService that uses Redis deleted, the RayCluster creates the Redis cleanup job. I observed that the Redis cleanup job was able to create a Redis cleanup pod, but then it was removed and the job was stuck in suspended state and was not able to execute.

The job stuck in suspended state because it could not find the RayService kueue workload. 
Since the RayCluster has ray.io/gcs-ft-redis-cleanup-finalizer it stuck in suspended state as well.

### Comment by [@yaroslava-serdiuk](https://github.com/yaroslava-serdiuk) — 2026-04-27T09:13:59Z

There are multiple ways to fix the issue:
1. Add finalizers to the RayService, so the Redis Cleanup Job will find its workloads and will be able to run. 
However if the [foreground deletion policy](https://kubernetes.io/docs/concepts/architecture/garbage-collection/#foreground-deletion) is chosen, the workload of the RayService will be removed anyway. 
2. Change the ownership of Redis Cleanup Job to the Redis service.

### Comment by [@anniejili](https://github.com/anniejili) — 2026-04-27T17:41:56Z

Hi @mimowo  and @yaroslava-serdiuk, 

One additional observation from our investigation: this issue can be triggered even when ray.io/rayservice is not enabled in the frameworks configuration. isKnownOwner checks all registered integrations, not just enabled ones. So having the RayService controller compiled into the binary is enough to make the walk traverse to RayService. This means the issue can't be worked around through configuration alone.

Just FYI We've been working on a fix that handles apierrors.IsNotFound as a graceful stop condition rather than a hard error:

  ```
if err := c.Get(ctx, client.ObjectKey{Name: owner.Name, Namespace: jobObj.GetNamespace()}, parentObj); err !=
  nil {
      if apierrors.IsNotFound(err) {
          log.V(3).Info("stop walking up as the owner object was deleted",
              "currentObj", klog.KObj(currentObj),
              "owner", klog.KRef(jobObj.GetNamespace(), owner.Name),
          )
          return topLevelJob, nil
      }
      return nil, errors.Join(ErrWorkloadOwnerNotFound, err)
  }
```
This is consistent with how the function already handles unknown owners https://github.com/kubernetes-sigs/kueue/blob/46e45cb22a27080726a13c2c00cf1071f34be55d/pkg/controller/jobframework/reconciler.go#L806 (line 806-813) — stopping the walk rather than failing. It also generalizes to other integrations with multi-level ownership chains during cascade deletion.

Happy to open a PR if this approach aligns with what you think.

Thank you!

### Comment by [@mimowo](https://github.com/mimowo) — 2026-04-27T18:04:24Z

> (line 806-813) — stopping the walk rather than failing. It also generalizes to other integrations with multi-level ownership chains during cascade deletion.

I think this approach might be problematic in cases of creating new chains. So, while RayService is created first, then RayCluster, there is no k8s level guarantee that Kueue will know about the events of creations in the same order. I think the creation event for RayCluster might be received first before the event for RayService. The same for Job, JobSet etc. This should be incredibly rare, but possible.

To fix it, I think we would probably need to also add a check that the "current object" is being deleted.  Even then we need a feature gate, as I'm not sure this is universally correct due to the possible unlikely scenario. 

I'm also wondering if this approach could fix more generically this problem https://github.com/kubernetes-sigs/kueue/pull/10009, cc @iaalm

Finally, we need a feature gate as this is meant to be only a quick workaround until the proper fix is implemented as suggested in https://github.com/kubernetes-sigs/kueue/issues/10795#issuecomment-4325690542.
