We are seeing a TAS admission/preemption issue with Kueue Fair Sharing across two ClusterQueues in the same cohort. A high-priority workload in gec-kueue requires a full 16-node nvidia.com/gpu.clique slice (64 GPUs total), while unified-queue is borrowing well beyond its nominal quota from the shared gb200 ResourceFlavor. Even with reclaimWithinCohort: Any enabled, the workload remains pending with quota-shortage and sometimes topology-fit errors, which suggests Kueue is not selecting or executing a cross-queue preemption set that frees a topology domain that actually fits the TAS workload.

1. Kueue Preemption came up with a plan to preempt some resources from `unified-queue`. But it does not care about topology or TAS. so the free-up resources will be scattered across different cliques.
2. Topology: I'd like some resources on the same clique, your plan does not fit, so reject it.
3. Kueue Preemtion: since Topology rejects it, i will do nothing.

**What happened**:

We have two `ClusterQueue`s in the same cohort:

- `unified-queue`
- `gec-kueue`

Both use Fair Sharing and:

```yaml
preemption:
  withinClusterQueue: LowerOrNewerEqualPriority
  reclaimWithinCohort: Any
  borrowWithinCohort:
    policy: Never
    maxPriorityThreshold: 100
```

The pending workload is in `gec-kueue`  is requesting some requests on the same clique:
```
topologyRequest:
  podSetSliceRequiredTopology: nvidia.com/gpu.clique
  podSetSliceSize: 16
```

Currently `unified-queue` is borrowing some resources from `gec-kueue` clusterqueue. So theoretically, it should preempt some pods from `unified-queue`.

But the workload remains pending with:

```text
couldn't assign flavors to pod set main: insufficient unused quota for nvidia.com/gpu in flavor gb200, 52 more needed
```

During earlier observations of the same pending wave, we also saw:

```text
couldn't assign flavors to pod set main: topology "nvl72" doesn't allow to fit any of 1 slice(s)
```

This suggests the preemption can happen, but since they are not in the same clique, it's rejected by topology.


**What you expected to happen**:

Because:

- `unified-queue` is borrowing beyond nominal quota
- `gec-kueue` is in the same cohort
- `reclaimWithinCohort: Any` is enabled
- Fair Sharing is enabled
- the pending workload has high priority

we expected Kueue to reclaim enough borrowed capacity from `unified-queue` to make the `gec-kueue` TAS workload admissible.

More specifically, we expected Kueue to preempt a victim set that frees a topology slice that actually fits the pending workload, not only improve scalar quota accounting.


**How to reproduce it (as minimally and precisely as possible)**:

Minimal shape of the setup:

1. Create two `ClusterQueue`s in the same cohort, both using `admissionMode: UsageBasedAdmissionFairSharing`.
2. Enable:
   - `reclaimWithinCohort: Any`
   - Fair Sharing with `preemptionStrategies: [LessThanOrEqualToFinalShare, LessThanInitialShare]`
3. Make both queues consume from the same TAS-enabled `ResourceFlavor` with:
   - `topologyName: nvl72`
   - underlying topology domain `nvidia.com/gpu.clique`
4. Give one queue (`unified-queue`) nominal quota `432` GPUs and the other (`gec-kueue`) nominal quota `288` GPUs.
5. Admit enough workloads into `unified-queue` so it borrows well above nominal quota and fragments the shared topology domains.
6. Submit a TAS workload into `gec-kueue` with:
   - `16` pods
   - `4` GPUs per pod
   - `podSetSliceRequiredTopology: nvidia.com/gpu.clique`
   - `podSetSliceSize: 16`
7. Observe that the workload remains pending with quota-shortage and/or topology-fit errors even though another queue in the cohort is borrowing the required quota.

In our live cluster, the pending workload is:

- `job-lbt-gec-3b-broad-decay-sweep190-b3f5cbe4-56a05`

### Comment by [@edmund-shi-arm](https://github.com/edmund-shi-arm) — 2026-05-05T17:19:29Z

Quick summary is that:
1. both `unified-queue` and `gec-kueue` are fully-occupied. 
2. `gec-kueue`  is lending some capacity for the jobs of `unified-queue` 
3. new jobs of  `gec-kueue`  come in and try to preempt some jobs from borrowed capacity.
4. new jobs has the topology on `kueue.x-k8s.io/podset-slice-required-topology: nvidia.com/gpu.clique`, required to be land on the same clique.
5. kueue is generating a preemption plan. But the plan only cares about preemption and giving back capacity, it does not care about topology requirement that put all nodes on the same clique.
6. So the plan was rejected, and got stuck. The plan might keep changing, and after hours, finally comes up with a good plan acceptable by the topology
