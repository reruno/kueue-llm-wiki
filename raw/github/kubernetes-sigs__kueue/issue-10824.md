## Description

### Summary

When a ClusterQueue has two TAS-enabled `ResourceFlavor`s and `flavorFungibility.whenCanPreempt: TryNextFlavor`, a workload that requires preemption in the first flavor and selects the second flavor by `TryNextFlavor` can be left Pending indefinitely if the second flavor's `nominalQuota` exceeds its TAS-reachable capacity (e.g. a node carrying that flavor's selector label is cordoned / unschedulable). The scheduler accepts the second flavor at the quota level, then fails at the TAS placement step, and **does not retry the first flavor with preemption**, even when there are ample preemptable lower-priority workloads there.


### What you expected to happen

Kueue picks the first flavor, preempts a lower-priority workload there, and admits the higher-priority workload within seconds.

### What actually happens
The higher-priority workload stays Pending indefinitely with:

```
couldn't assign flavors to pod set <name>: topology "<topology>" doesn't allow to fit any of N pod(s).
Total nodes: M; excluded: resource "<X>": M
```

This is the same error class we observed on our production cluster (`Total nodes: 15; excluded: resource "nvidia.com/gpu": 15`) when there were preemptable workloads in the first ResourceFlavor

The lower-priority workloads in the first flavor continue running. The scheduler logs no preemption attempt against the first flavor after the TAS failure on the second.

### Mechanism
With flavor order `[flavor-a, flavor-b]`, `flavorFungibility.whenCanPreempt: TryNextFlavor`, and the workload requesting `kueue.x-k8s.io/podset-required-topology`:

1. `assignFlavors` evaluates **flavor-a**: quota saturated → would need preemption → `TryNextFlavor` defers to flavor-b.
2. `assignFlavors` evaluates **flavor-b**: `nominalQuota` shows free room → `Fit` mode → flavor-b selected.
3. `updateAssignmentForTAS` runs TAS on flavor-b: the only reachable topology domain cannot fit the PodSet (no schedulable nodes, or schedulable nodes don't have enough free resource), records the TAS error on the `PodSetAssignment`.
4. There is no path that re-enters `findFlavorForPodSets` to retry flavor-a with preemption. The decision from step 2 is final.

The "ghost room" in step 2 comes from `nominalQuota` being a static spec value while TAS reachability is dynamic (excludes cordoned / NotReady nodes). The bug is independent of how the gap is created: `nominalQuota` higher than labelled-node count, a labelled node being unschedulable, and so on all hit the same scheduler path.

### Workaround we are using 
Collapse the two RFs into a single flavor matching all nodes, with a two-level topolgy. Drop `flavorFungibility` (single flavor, nothing to defer to). 

This works as a config workaround but loses per-flavor quota accounting and the ability to express per-pod hardware differentiation.

### Suggested fix direction

We don't have a strong opinion on the right shape and would welcome maintainer guidance. Two options we considered:

1. **Move TAS feasibility into the flavor loop** in `findFlavorForPodSets`, so `TryNextFlavor` honours TAS failures the same way it honours quota failures. 
2. **Add a TAS-failure fallback** after `updateAssignmentForTAS` records a failure, that re-invokes `findFlavorForPodSets` with the failed flavor marked ineligible. 


### Related

- **#10270**: feature request for ClusterQueue quota auto-derived from node selectors. Would mitigate this bug at the source by eliminating the `nominalQuota` vs. capacity gap, but the scheduler-level fallback would still be desirable for any case where quota and capacity diverge for legitimate reasons.


### Reproduction

#### Cluster prerequisites

- Two worker nodes available for testing.
- Kueue v0.17.1+ installed with TAS feature gate enabled (default since 0.14).
- `kubectl` access with permission to label and cordon nodes, create namespaces, and apply Kueue / batch CRs.

Substitute `<node-a>` and `<node-b>` with two real node names from your cluster. Adjust the CPU numbers if your nodes have less than 2 schedulable CPUs each (the workloads request 1 CPU each).

#### 1. Prepare nodes

```bash
kubectl create namespace kueue-test

kubectl label node <node-a> topology.example.com/pod=pod-a cluster-queue-member=true
kubectl label node <node-b> topology.example.com/pod=pod-b cluster-queue-member=true

# Cordon node-b but keep its labels. This creates the "ghost quota":
# flavor-b's nominalQuota will reflect node-b's CPU, but TAS will not
# place anything on a SchedulingDisabled node.
kubectl cordon <node-b>
```

#### 2. Apply Kueue config and workloads (one manifest)

#### 3. Observe

After ~10 seconds:

```bash
kubectl get workload -n kueue-test
# expect: filler workload Admitted=True, test workload Admitted=False

WL=$(kubectl get workload -n kueue-test -o name | grep '/job-test')
kubectl get -n kueue-test $WL -o jsonpath='{.status.conditions[?(@.type=="QuotaReserved")].message}'; echo
# expect: ...no topology domains at level: topology.example.com/pod
```

The filler keeps running. The test workload stays Pending forever, even though the filler is a valid preemption candidate on flavor-a.

#### 4. Sanity check

```bash
kubectl uncordon <node-b>
# Within seconds, the test workload should be Admitted on node-b.
# (Re-cordon node-b to put the cluster back into the failing state.)
```

This confirms the scheduler picked flavor-b at step 2 above. The only thing keeping the test workload Pending is the absence of a fallback to flavor-a with preemption.

## Discussion

### Comment by [@PBundyra](https://github.com/PBundyra) — 2026-04-29T15:08:21Z

Hi @ananth1996 thanks for reporting this issue. The description makes sense, and it's seems like there's indeed a bug in flavorassigner code.

We should always take into consideration TAS when setting Fit/Preempt/NoFit mode, and only after that we can select the best assignment. I believe we should run TAS code earlier, although not necessarily in `findFlavorForPodSets` function. This is because `findFlavorForPodSets` is called per resource and if we added TAS there we would impact the performance significantly.

 Would you be able to try an approach where the bestAssignment includes TAS, but at the same time TAS is not run per resource?

### Comment by [@ananth1996](https://github.com/ananth1996) — 2026-05-06T08:30:05Z

Thanks @PBundyra. Understood that TAS needs to factor into the Fit/Preempt/NoFit decision but can't run per-resource. I'll coordinate with a colleague and come back with a solution that doesn't hurt performance.
