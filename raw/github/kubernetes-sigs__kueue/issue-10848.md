Use the flake debugger skill here:

 I have investigated the flake reported in https://github.com/kubernetes-sigs/kueue/issues/10848 (https://github.com/kubernetes-sigs/kueue/issues/10848) and identified the root cause.

  Summary of Findings

  The failing test MultiKueue Sequential when MultiKueueOrchestratedPreemption is enabled [It] should not trigger concurrent preemptions fails because it incorrectly assumes that a high-priority workload will only be created in one of the worker
  clusters. However, given the current configuration and MultiKueue's dispatching logic, the workload is correctly synchronized to both worker clusters, causing the test's assertion to fail.

  1. Incorrect Test Assertion
  The failure occurs at test/e2e/multikueuesequential/e2e_test.go:828:

   1 g.Expect(worker1Error == nil).NotTo(gomega.Equal(worker2Error == nil))
  This line expects that exactly one of the worker clusters will have the workload (worker1Error == nil XOR worker2Error == nil). If the workload is present in both clusters, both conditions are true, and the NotTo(Equal(true)) assertion fails with:
  Expected <bool>: true not to equal <bool>: true (as seen in build-log.txt:119354 (https://gcsweb.k8s.io/gcs/kubernetes-ci-logs/pr-logs/pull/kubernetes-sigs_kueue/10844/pull-kueue-test-e2e-multikueue-sequential-main/2049759299504181248/build-log.txt)).

  2. Dispatcher Mode Behavior
  The E2E suite defaults to MultiKueueDispatcherModeIncremental (manager log
  (https://gcsweb.k8s.io/gcs/kubernetes-ci-logs/pr-logs/pull/kubernetes-sigs_kueue/10844/pull-kueue-test-e2e-multikueue-sequential-main/2049759299504181248/artifacts/run-test-e2e-multikueue-sequential-1.35.0/kind-manager-worker/pods/kueue-system_kueue-co
  ntroller-manager-55cf9b7d4-45ntp_318bf678-5c8d-491c-a965-c562e835f0cf/manager/0.log)).
  In Incremental mode, the dispatcher nominates clusters in batches of up to 3 (incrementaldispatcher.go:181 (pkg/controller/workloaddispatcher/incrementaldispatcher.go)).
  Since the test environment only has 2 worker clusters, they are both nominated in the first round. Consequently, the MultiKueue workload controller synchronizes the workload to both worker clusters (workload.go:789
  (pkg/controller/admissionchecks/multikueue/workload.go)).

  3. Orchestrated Preemption is Working Correctly
  The MultiKueue manager leader logs show that while the workload was synced to both clusters, the preemption orchestration logic correctly identified both as needing preemption but only evaluated them sequentially for ungating. However, because the test
  fails as soon as it detects the workload's presence in both clusters, it doesn't wait to see that only one cluster actually proceeds with preemption.

  Recommendations

   1. Fix the Test Assertion: The test should be updated to allow the workload to exist in multiple worker clusters but assert that only one cluster admits (or is ungated for) the workload. Line 828 should be removed or relaxed.
   2. Verify Sequential Dispatching: If the intent is to test truly sequential dispatching (one cluster at a time), the Incremental dispatcher's batch size should be made configurable and set to 1 for this test, or a new Sequential dispatcher mode should
      be implemented.
   3. Update Integration Tests: The corresponding integration test in test/integration/multikueue/scheduler/scheduler_test.go has the same assertion and may also be prone to similar issues or pass only due to different timing/concurrency characteristics
      of the integration environment.

### Comment by [@mimowo](https://github.com/mimowo) — 2026-05-08T18:48:03Z

Then followed up with the question

 > how does it happen the test is passing most of the time?                                                                                                                                                                                                   

✦ The test should not trigger concurrent preemptions is prone to flaking because it contains a "race-condition-friendly" assertion that expects a workload to exist in exactly one worker cluster at a specific point in time.

  The reason it passes most of the time, but fails occasionally, is likely due to the following dynamics:

  1. The "Race" that usually results in a Pass
  The test uses the Incremental dispatcher (in the failing run's configuration), which nominates clusters in batches. In a 2-worker setup, both are nominated in the first round. The MultiKueue manager then attempts to synchronize (create) the workload in
  both clusters near-simultaneously.

  In Go, map iteration is randomized, but even with sorted keys, the Create calls are separate network requests to different clusters. Usually:
   1. The manager successfully creates the workload on Worker 1.
   2. The test's Eventually block (polling at a 100ms interval) catches this state.
   3. Crucially, if the workload is also Admitted on Worker 1 quickly enough (because it fits or preemption completes), the Eventually block succeeds and exits immediately.
   4. The manager might not have finished creating the workload on Worker 2 yet, or the test's Get call to Worker 2 still returns a NotFound error.

  In this scenario, worker1Error == nil (true) and worker2Error == nil (false) satisfies the NotTo(Equal) assertion, and the test proceeds.

  2. Why it Fails (The Flake)
  The failure occurs when the synchronization to both clusters happens faster than the test can finish its first successful poll, or when both clusters are synced but neither is admitted yet.

  In the failing run (build-log.txt:119354 (https://gcsweb.k8s.io/gcs/kubernetes-ci-logs/pr-logs/pull/kubernetes-sigs_kueue/10844/pull-kueue-test-e2e-multikueue-sequential-main/2049759299504181248/build-log.txt)), we see:
  Expected <bool>: true not to equal <bool>: true

  This means the test polled and found the workload already existed in both clusters. This is actually the correct and intended behavior of MultiKueue when both clusters are nominated. The test's assertion:

   1 g.Expect(worker1Error == nil).NotTo(gomega.Equal(worker2Error == nil))
  is logically flawed for any dispatcher that nominates more than one cluster at a time (which both AllAtOnce and Incremental do in this setup).

  3. Contributing Factors to the Flake
   * Throttling: In the failed run, the logs show client-side throttling and Waited before sending request (manager log
     (https://gcsweb.k8s.io/gcs/kubernetes-ci-logs/pr-logs/pull/kubernetes-sigs_kueue/10844/pull-kueue-test-e2e-multikueue-sequential-main/2049759299504181248/artifacts/run-test-e2e-multikueue-sequential-1.35.0/kind-manager-worker/pods/kueue-system_kueue
     -controller-manager-788dcc5f9b-2zzjq_b14dda75-d1b1-4e3e-9013-7ece3d76f506/manager/0.log)). This suggests the environment was under load, which can alter the timing of synchronization vs. polling, making it more likely for the test to see the "fully
     synced" state rather than the "partially synced" state it relies on.
   * Dispatcher Defaults: If the test suite recently switched the default dispatcher or changed its batch size, a previously "safe" race might have become "unsafe."

  Conclusion
  The test is essentially asserting on a transient, race-dependent state. To fix the flake, the test should be refactored to assert that at most one cluster has the workload in an Admitted state (which is what OrchestratedPreemption guarantees), rather
  than asserting that the workload object exists in only one cluster.

### Comment by [@kshalot](https://github.com/kshalot) — 2026-05-11T08:21:49Z

By glancing at it, I think the analysis is flawed. First of all, this test is not using the `Incremental` dispatching mode, but `AllAtOnce` ([link](https://github.com/kubernetes-sigs/kueue/blob/main/test/e2e/config/multikueue/sequential/controller_manager_config.yaml)). There is one test case which sets it to incremental and then switches back and the LLM picked the logs for that one (you can see that `MultiKueueOrchestratedPreemption` is disabled in that one).

The goal in the failing assertion is to wait until the workload is fully admitted on the manager, which means that it is only present on of the workers (the one that won the admission race). Adding a sleep would make the test **less** flaky in my opinion, because it means there is more time for the workloads to pass through the scheduling cycle. The LLM is mistaken when saying:
> the "partially synced" state it relies on

because we are relying on the full state. It misunderstood the test IMO.

One race unrelated to this flake that is theoretically possible is:
1. Workload is admitted on worker A.
2. Workload wasn't even created yet in worker B.

This would pass the expectations. I don't think this case is relevant here though, because we only care about the admitted one, and it would be removed on worker B anyway. We could add a check whether the workload is also admitted on the manager to make it robust, but I don't think this would ever cause flakiness.

From my perspective, we could try to increase the timeout in the failing block to `MediumTimeout`, which would give it 35 more seconds to go through the admission, removal etc. I'd also propose adding logging of those workloads for the future, so we can see what state they are in.
