## Description

**What would you like to be added**:
Currently we have two metrics for monitoring pending workloads related to local and cluster queues: `kueue_pending_workloads` and `kueue_local_queue_pending_workloads` (see [metrics documentation](https://kueue.sigs.k8s.io/docs/reference/metrics/)). Both of them use one of 2 values of `status` label: `active` or `inadmissible`.

There are two problems with this:
1. Workloads with missing/non-existing local queue defined in `kueue.x-k8s.io/local-queue-name` label are not counted in `status=inadmissible` label.
2. `Reason`s defined in workloads' `.Status.Conditions` are kind of misleading compared to `status=inadmissible` label defined in the mentioned metrics. In [API](https://github.com/kubernetes-sigs/kueue/blob/9a434bf1e825875a5af480515288385dfff3a511/apis/kueue/v1beta2/workload_types.go#L1004) we have `Inadmissible` defined as "LocalQueue or ClusterQueue doesn't exist or inactive" which relates to the problem no. 1.

It would be beneficial for Kueue users to define alerting based on metrics in case of wrong configuration of the workload itself so manual checking of each workload would not be necessary.

Examples for alerts:
- A workload points to a non-existing `LocalQueue` in `kueue.x-k8s.io/local-queue-name` label
- A workload points to correct `LocalQueue` name but that `LocalQueue` points to non-existing `ClusterQueue`
- A workload is defined with incorrect tolerations, meaning no `ResourceFlavor` can match it.

Initially, I considered simply counting such misconfigured workloads under `status=inadmissible`. However, this isn't very helpful because `status=inadmissible` would become a massive, general group of 'not runnable' workloads, making further investigation difficult.

Furthermore, including workloads that were not initially counted changes the existing behavior of the metric. Despite it sounding natural to count these as `status=inadmissible`, the drawbacks led me to my current proposal.

I'm leaning towards another solution which would be a new set of metrics:
- `kueue_queued_workloads`
- `kueue_local_queue_queued_workloads`

Both of these would use `reason` label and the reason label would map 1:1 to the `Reason` field of `.Status.Conditions` of a workload. The only problem I currently see with this approach is that workloads that are not admitted due to flavor mismatch are  currently given `Pending` reason - the same as workloads that are waiting for resources / cannot fit.

If possible we could change the `Reason` for flavor mismatch scenario to `FlavorMismatch` to not mix them up with `Pending` workloads.

I've found the following `Reason`s are currently used in Kueue for workloads that are waiting for admission:
- "Pending"
- "Inadmissible"
- "Waiting"

These metrics would be "extensible"; if we were to add a new `Reason`, we would simply count them using a new label.

Also, presence of two sets of "similar" metrics might be confusing for users but I think we could simply describe them well OR deprecate the old ones.

Alternatives:
- As previously mentioned, counting misconfigured workloads as `status=inadmissible`.
- Adding a second label to the already existing metrics, but this sounds confusing and complicated to me.

I'm open to discussion; let me know what you think.

**Why is this needed**:

Improve observability of misconfigured workloads.

### Comment by [@j-skiba](https://github.com/j-skiba) — 2026-05-04T13:30:57Z

I feel like the `QuotaReserved` is not necessarily good place for reflecting configuration issues and these two maybe should not be mixed here.

In order to decouple configuration validity from quota reservation we could introduce new `Condition` type. Let's say working name `Queueable`.

Workload with condition:
```yaml
Type: Queueable
Status: True
Reason: Active
```
would be considered a workload that is structurally valid and actively competing for quota.

and workloads with condition:
```yaml
Type: Queueable
Status: False
Reason: LocalQueueNotFound | ClusterQueueNotFound | FlavorMismatch # or some any other reason that could be introduced later
```
would be considered a workload that is structurally invalid.

The previously mentioned metrics could feature two labels `status` and `reason` for easy mapping to `Queueable` condition.

### Comment by [@j-skiba](https://github.com/j-skiba) — 2026-05-08T10:28:21Z

Here are my thoughts on the alternative approaches discussed during the last Batch WG:
1. Using `DueTo...` reasons
I think it would be good to have this in the first place but I think it doesn't solve the problem entirely as changing the existing `Reason` from `Pending` to `PendingDueTo...` is still a breaking change.
2. Using events instead of conditions for mapping reason of inadmissibility
I haven't found any events being generated in any of the scenarios (local/cluster queue misconfiguration, flavor mismatch) but that's something we could potentially add. The problem with this approach is that the events are not connected to the workload (as `.Status.Conditions` via a separate field in the object) so reporting of the proposed metric as gauge would be problematic as we would have to keep the reasons of inadmissibility in some other place than the workload itself which feels  counter-intuitive.
3. Migration to a new condition type
Basically it solves all of the problems listed in the issue, the only issue is that it would be the biggest effort from all of the proposals to design and implement this solution, apart from that I think it would work. It also comes with deprecation of the current `QuotaReserved` condition type. Also it's worth to mention it's not exactly like https://github.com/kubernetes-sigs/kueue/issues/10852#issuecomment-4371454307 this proposal, here I wasn't thinking about making `Queueable` replace the `QuotaReserved` but more like additional condition.

### Comment by [@j-skiba](https://github.com/j-skiba) — 2026-05-08T10:43:09Z

Re: 3
There were some concerns about scenarios where a workload is inadmissible due to both a permanent cause (like misconfiguration) and a temporary one (like insufficient quota) at the same time. 

In such cases, I think we should treat the permanent reason as having precedence, since it's a blocker that will prevent the workload from running regardless of temporary reasons. If there are multiple permanent reasons, we can simply keep the most recent one. 

Any additional detailed information can still be made available in the `Message` field.

edit: the same applies to any other new condition/reason proposal

### Comment by [@j-skiba](https://github.com/j-skiba) — 2026-05-13T09:51:10Z

Another remark: the term `inadmissible` is overloaded not just as a label name in the metrics, but also within its own definition in the [API](https://github.com/kubernetes-sigs/kueue/blob/9a434bf1e825875a5af480515288385dfff3a511/apis/kueue/v1beta2/workload_types.go#L1004). 

Currently, the `Reason` is set to `Inadmissible` both when a local/cluster queue doesn't exist (a structural misconfiguration) and when a local/cluster queue has a `StopPolicy` set. While the immediate outcome in both scenarios is identical (`QuotaReserved` is set to `false`), the root causes are fundamentally different: setting a `StopPolicy` is an intentional administrative action, whereas a misspelled queue name is an error. Despite this difference, they currently fall under the exact same reason.

### Comment by [@j-skiba](https://github.com/j-skiba) — 2026-05-13T10:56:02Z

After mentioning `StopPolicy` I think that we could categorize workloads into 4 general categories:
- `Queued` - the workload has been submitted and is actively positioned in the queue, simply awaiting its cycle for scheduler capacity evaluation
- `PendingCapacity` - the workload fits all physical and flavor constraints, but the cluster currently lacks sufficient unreserved resources. It's practically in backoff queue
- `Misconfigured` - a permanent structural conflict prevents the workload from ever being admitted (local/cluster queue not found etc.)
- `Suspended` - the workload is structurally valid, but admission is intentionally halted by an administrative state. This strictly covers: local/cluster queue has `StopPolicy` set (or is terminating but I'm not sure it's necessary to set this in such situation)

and there are also 2 reasons that are currently used in `QuotaReserved` condition for special scenarios:
- `Waiting` - when waiting for pods of a previous workload to be ready before scheduling - also I noticed `Waiting` is not documented in any way as `Inadmissible` or `AdmissionGated` is (see 
https://github.com/kubernetes-sigs/kueue/blob/cd26df2848bf23bf78078387bc823335efa402c3/pkg/scheduler/scheduler.go#L524
https://github.com/kubernetes-sigs/kueue/blob/cd26df2848bf23bf78078387bc823335efa402c3/apis/kueue/v1beta2/workload_types.go#L1008)
- `AdmissionGated` - the workload is gated by external component
