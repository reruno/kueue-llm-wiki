## Description



**What happened**:

Workloads corresponding to JobSets got marked finished immediately after creation.

We observe in the logs that
1. the JobReconciler created a Workload for a JobSet
2. within the same millisecond the workload_controller marked the Workload as finished with the reason OwnerNotFound

This is because the cache inside Kueue for the JobReconciler already saw the owner JobSet, but the cache for the Workload_controller still didn't see the JobSet.

**Additionally**, we observed that the workload which was marked as finished was requeued via `Manager.RequeueWorkload `. this is not the root cause, but we should strenghten the check manager.go to do not requeue Finished workloads (use !workload.IsAdmissible(&w) ), because the workload which was requeued kept winning the fair sharing tournament in the consecutive scheduling cycles, thus blocking other workloads from making progress. If it was not requeued it would at least not cause problems to other workloads.

**What you expected to happen**:

Workloads should not be marked as Finished if the owner still exists, as in this case. 

**How to reproduce it (as minimally and precisely as possible)**:

This is very hard to repro, but we observed that on a busy large scale cluster.

**Anything else we need to know?**:

This makes the fix for Requeue of evicted Deployment workloads buggy https://github.com/kubernetes-sigs/kueue/pull/10274.

So we need search for a better fix, some options to consider:
1. mark the workloads as finished from within JobReconciler rather than workload_controller, but this would still leave some window open for the workload controller to put such a workload in the queue
2. (preferred) add an additional check in the workload_controller to skip adding a workload which has no owner onto the heap. Once the workload has the owner then it will be put back onto the heap.

### Comment by [@mimowo](https://github.com/mimowo) — 2026-05-08T11:45:00Z

I think the root cause for the issue is that in the workload controller we use [PartialObjectMetadata](https://github.com/kubernetes-sigs/kueue/blob/main/pkg/controller/core/workload_controller.go#L1340-L1345) which has its own informer in the API server, separate from the "structured" informers per-kind, see [informersByType](https://github.com/kubernetes-sigs/controller-runtime/blob/a76332c07f5751d9bf861548804d6f73946e5fed/pkg/cache/internal/informers.go#L354-L363)

Moreover, it does not even look like a bug in controller-runtime, the PartialObjectMetadata looks like a structure watched separately from the "real" jobs, see for example [here](https://github.com/kubernetes-sigs/controller-runtime/blob/a76332c07f5751d9bf861548804d6f73946e5fed/pkg/client/watch.go#L42-L51)

The delays are possible, that the JobSet is already in its Structured informer, but not yet in the Metadata informer.

So, one way of fixing would be to do what jobframwrok is doing, and instead of querying by PartialObjectMetadata query by the actual object. We may try reusing FindAncestorJobManagedByKueue. Another alternative is to move finishing the worklaods from workload_controller to job reconciler. 

I'm not yet sure which one is better, posting what I've established so far.
