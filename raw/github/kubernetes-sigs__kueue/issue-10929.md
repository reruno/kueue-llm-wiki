## Description

### What happened

When Topology-Aware Scheduling (TAS) is enabled and a higher-priority workload needs to preempt a lower-priority workload, preemption is skipped if:
1. The lower-priority workload occupies **all nodes** in the topology domain, AND
2. The workloads are backed by **Deployments** rather than native Kubernetes Jobs.

The higher-priority workload stays pending indefinitely with `insufficient unused quota` — the preemption evaluator is never invoked.

**Native batch/v1 Jobs preempt correctly under the same conditions.** The difference is that batch Jobs use Kueue's suspend/unsuspend mechanism with TAS scheduling gates, while Deployment-backed workloads create pods directly without scheduling gates.

Preemption also works correctly for Deployment-backed workloads when there are spare (unoccupied) nodes in the topology domain.

### What did you expect to happen

The higher-priority workload should preempt the lower-priority workload regardless of how many spare nodes exist in the topology domain. The preemption evaluator should consider that evicting the incumbent would free both quota **and** topology capacity.

### Reproduction

Tested on Kueue v0.12.0. The bug is likely present on `main` based on code review (see analysis below).

#### Setup

```yaml
# Topology CRD (single-level, zone-id)
apiVersion: kueue.x-k8s.io/v1beta2
kind: Topology
metadata:
  name: test-topology
spec:
  levels:
    - nodeLabel: topology.k8s.aws/zone-id
---
# ResourceFlavor with TAS enabled
apiVersion: kueue.x-k8s.io/v1beta1
kind: ResourceFlavor
metadata:
  name: gpu-flavor
spec:
  nodeLabels:
    node.kubernetes.io/instance-type: <any-gpu-instance>
  topologyName: test-topology
---
# ClusterQueue with preemption enabled
apiVersion: kueue.x-k8s.io/v1beta1
kind: ClusterQueue
metadata:
  name: test-cq
spec:
  preemption:
    withinClusterQueue: LowerPriority
    reclaimWithinCohort: LowerPriority
  namespaceSelector:
    matchLabels:
      kubernetes.io/metadata.name: test-ns
  resourceGroups:
    - coveredResources: ["cpu", "memory", "nvidia.com/gpu"]
      flavors:
        - name: gpu-flavor
          resources:
            - name: cpu
              nominalQuota: 16
            - name: memory
              nominalQuota: 64Gi
            - name: "nvidia.com/gpu"
              nominalQuota: 2    # exactly matches available nodes
---
# Two priority classes
apiVersion: kueue.x-k8s.io/v1beta1
kind: WorkloadPriorityClass
metadata:
  name: low-priority
value: 1
---
apiVersion: kueue.x-k8s.io/v1beta1
kind: WorkloadPriorityClass
metadata:
  name: high-priority
value: 100
```

#### Steps

**Cluster:** 2 nodes with 1 GPU each, both in the same topology domain (same `topology.k8s.aws/zone-id` value). `TopologyAwareScheduling` feature gate enabled.

1. Submit a low-priority **Deployment-backed** workload with 2 replicas, each requesting 1 GPU (the workload's CRD must create a Deployment, not a native Job). Label it with `kueue.x-k8s.io/priority-class: low-priority`. Wait for it to be admitted — it fills the entire 2-GPU quota.

2. Submit a high-priority **Deployment-backed** workload with 2 replicas, each requesting 1 GPU. Label it with `kueue.x-k8s.io/priority-class: high-priority`.

**Expected:** Low-priority workload is preempted. High-priority workload is admitted.

**Actual:** High-priority workload stays pending with:
```
couldn't assign flavors to pod set <name>: insufficient unused quota for
nvidia.com/gpu in flavor gpu-flavor, 2 more needed
```
No `Preempted` event is generated. The preemption evaluator is never invoked.

#### Control: same setup with spare nodes

Repeat the same test with **10 nodes** (instead of 2) in the same topology domain, keeping `nominalQuota: 2`. Everything else identical.

**Result:** Preemption works correctly. The scheduler log shows:
```
insufficient unused quota for nvidia.com/gpu in flavor gpu-flavor, 2 more needed.
Pending the preemption of 1 workload(s)
```

Note the `Pending the preemption of 1 workload(s)` suffix — this is absent in the failing case.

#### Additional control: batch/v1 Jobs under same tight conditions

Repeat the 2-node test with plain `batch/v1` Jobs (with `suspend: true`) instead of Deployment-backed workloads. Everything else identical.

**Result:** Preemption works correctly. Batch Jobs use Kueue's scheduling gates, so their pods don't consume node-level capacity in the TAS snapshot the same way Deployment-created pods do.

### Analysis — root cause in the code

The bug is a combination of two issues:

1. **Scheduling gate difference:** Batch Jobs use Kueue's native suspend/unsuspend mechanism — pods are created with TAS scheduling gates and don't consume node-level capacity in the TAS snapshot until ungated. Deployment-backed workloads create pods directly without scheduling gates, consuming real node capacity immediately. The non-gated pods are classified as "non-TAS" by the snapshot builder ([`addNonTASUsage()`](https://github.com/kubernetes-sigs/kueue/blob/main/pkg/cache/scheduler/tas_flavor_snapshot.go#:~:text=func%20(s%20*TASFlavorSnapshot)%20addNonTASUsage)) and their usage is permanently subtracted from [`freeCapacity`](https://github.com/kubernetes-sigs/kueue/blob/main/pkg/cache/scheduler/tas_flavor_snapshot.go#:~:text=freeCapacity%20represents). But the same capacity is also tracked in [`tasUsage`](https://github.com/kubernetes-sigs/kueue/blob/main/pkg/cache/scheduler/tas_flavor_snapshot.go#:~:text=tasUsage%20represents) via the Kueue Workload — **double-counted**.

2. **Circular dependency in preemption evaluation:** When TAS evaluates topology with [`WithSimulateEmpty=true`](https://github.com/kubernetes-sigs/kueue/blob/main/pkg/cache/scheduler/tas_flavor_snapshot.go#:~:text=func%20WithSimulateEmpty) in [`updateAssignmentForTAS()`](https://github.com/kubernetes-sigs/kueue/blob/main/pkg/scheduler/scheduler.go#:~:text=func%20updateAssignmentForTAS), it clears workload-level TAS usage but not the `freeCapacity` deduction from non-gated pods. This causes TAS to return `NoFit` for Deployment-backed workloads, which prevents the preemption evaluator from ever running.

The circular dependency in [`pkg/scheduler/scheduler.go`](https://github.com/kubernetes-sigs/kueue/blob/main/pkg/scheduler/scheduler.go):

1. **[`getInitialAssignments()`](https://github.com/kubernetes-sigs/kueue/blob/main/pkg/scheduler/scheduler.go#:~:text=func%20(s%20*Scheduler)%20getInitialAssignments)** — the flavor assigner checks quota and returns a mode:
   - `Fit` — enough free quota
   - `Preempt` — not enough free quota, but preemption could work
   - `NoFit` — cannot fit

   With quota full, this correctly returns `Preempt`.

2. **[`updateAssignmentForTAS()`](https://github.com/kubernetes-sigs/kueue/blob/main/pkg/scheduler/scheduler.go#:~:text=func%20updateAssignmentForTAS)** — runs after step 1. When mode is `Preempt`, it checks whether TAS can find a valid topology placement:

   ```go
   if len(targets) > 0 {
       // Simulate removing preemption targets, then check topology
       revertUsage := snapshot.SimulateWorkloadRemoval(targetWorkloads)
       tasResult = cq.FindTopologyAssignmentsForWorkload(tasRequests)
       revertUsage()
   } else {
       // No targets — check topology against current state
       tasResult = cq.FindTopologyAssignmentsForWorkload(tasRequests,
           schdcache.WithSimulateEmpty(true))
   }
   assignment.UpdateForTASResult(cq, tasResult)
   ```

   At this point, `targets` is empty — [`GetTargets()`](https://github.com/kubernetes-sigs/kueue/blob/main/pkg/scheduler/scheduler.go#:~:text=faPreemptionTargets%20%3A%3D%20s.preemptor.GetTargets) hasn't been called yet (it only runs when mode is `Preempt`, which hasn't been downgraded yet). So TAS takes the `else` branch and evaluates topology against the **current** snapshot, where the incumbent workload occupies all nodes.

   Inside the snapshot, [`fillInCounts()`](https://github.com/kubernetes-sigs/kueue/blob/main/pkg/cache/scheduler/tas_flavor_snapshot.go#:~:text=remainingCapacity%20%3A%3D%20leaf.freeCapacity.Clone) computes:
   ```go
   remainingCapacity := leaf.freeCapacity.Clone()   // Already 0 (deducted by addNonTASUsage)
   if !requirements.simulateEmpty {                 // simulateEmpty=true → skipped
       remainingCapacity.Sub(leaf.tasUsage)
   }
   // remainingCapacity is STILL 0 — simulateEmpty only skips tasUsage,
   // not the freeCapacity deduction from Deployment pods
   ```

   - **With spare nodes:** TAS finds free capacity in the domain → mode stays `Preempt`
   - **Without spare nodes:** TAS finds zero free capacity → `UpdateForTASResult` downgrades mode to `NoFit`

3. **[`processEntry()`](https://github.com/kubernetes-sigs/kueue/blob/main/pkg/scheduler/scheduler.go#:~:text=Skipping%20workload%20as%20FlavorAssigner%20assigned%20NoFit)** — sees the final mode:

   ```go
   if mode == flavorassigner.NoFit {
       log.V(3).Info("Skipping workload as FlavorAssigner assigned NoFit mode")
       return  // preemption evaluator never runs
   }
   ```

#### The circular dependency

```
TAS needs preemption targets to simulate their removal from the topology snapshot
    ↓
But preemption targets come from GetTargets()
    ↓
But GetTargets() only runs when mode = Preempt
    ↓
But TAS just set mode = NoFit (because it evaluated topology without simulating removal)
    ↓
→ Deadlock — neither step can proceed without the other
```

### Root cause confirmation — manual label fix

We confirmed the double-counting is the **sole** root cause by manually labeling the incumbent Deployment pods with `kueue.x-k8s.io/tas=true` after they were running.

In v0.12, `TASFlavorCache.snapshot()` queries non-TAS pods using:
```go
r, err := labels.NewRequirement(kueuealpha.TASLabel, selection.DoesNotExist, nil)
```

Adding the `kueue.x-k8s.io/tas` label to the Deployment pods excluded them from this query → `addNonTASUsage()` was never called → `freeCapacity` stayed intact → `simulateEmpty=true` correctly freed `tasUsage` → `Preempt` mode → preemption executed.

**Before labeling:** high-priority workload stuck with "insufficient unused quota" (no preemption suffix).

**After labeling:** high-priority workload admitted, low-priority workload preempted. Events showed:
```
Preempted    lowpri   "Preempted to accommodate a workload..."
Admitted     hipri    "Admitted by ClusterQueue test-cq"
```

This proves the double-counting is the sole cause — no secondary issues.

### Where the classification happens (code pointers)

**v0.12:** [`pkg/cache/tas_flavor.go` — `snapshot()`](https://github.com/kubernetes-sigs/kueue/blob/v0.12.0/pkg/cache/tas_flavor.go) — queries pods where `kueue.x-k8s.io/tas` label does not exist, passes all of them to `addNonTASUsage()`.

**main/v0.16+:** [`pkg/controller/tas/non_tas_usage_controller.go` — `belongsToNonTASCache()`](https://github.com/kubernetes-sigs/kueue/blob/main/pkg/controller/tas/non_tas_usage_controller.go#:~:text=func%20belongsToNonTASCache) — checks `IsTAS(pod)` via [`pkg/util/tas/tas.go`](https://github.com/kubernetes-sigs/kueue/blob/main/pkg/util/tas/tas.go#:~:text=func%20IsTAS) which looks for TAS annotations. Deployment pods lack these annotations → classified as non-TAS → added to `nonTasUsageCache` → deducted from `freeCapacity`.

Both versions have the same structural bug — only the classification gate differs (label in v0.12, annotation in main).

### Possible fix directions

1. **Fix the pod classification** — make the non-TAS pod filter aware of TAS-admitted workloads' Deployment pods. When classifying a pod, trace its ownership chain (Pod → ReplicaSet → Deployment → parent CRD → Kueue Workload) and skip pods that belong to a TAS-admitted Workload. This is the most targeted fix — it only changes classification for pods that are genuinely TAS-managed but lack the label/annotation due to the Deployment intermediary. System pods (DaemonSets, CoreDNS, etc.) remain correctly classified as non-TAS since they have no Kueue Workload owner.
   - v0.12: [`pkg/cache/tas_flavor.go` — `snapshot()`](https://github.com/kubernetes-sigs/kueue/blob/v0.12.0/pkg/cache/tas_flavor.go) — the label selector query
   - main: [`pkg/controller/tas/non_tas_usage_controller.go` — `belongsToNonTASCache()`](https://github.com/kubernetes-sigs/kueue/blob/main/pkg/controller/tas/non_tas_usage_controller.go#:~:text=func%20belongsToNonTASCache) and [`pkg/util/tas/tas.go` — `IsTAS()`](https://github.com/kubernetes-sigs/kueue/blob/main/pkg/util/tas/tas.go#:~:text=func%20IsTAS)

2. **Make `WithSimulateEmpty` also restore `freeCapacity`** deducted by `addNonTASUsage()` for pods belonging to TAS-admitted workloads. This fixes the preemption simulation without changing the classification. Less targeted — the double-counting still exists in the snapshot, but the preemption evaluator would see through it.
   - [`pkg/cache/scheduler/tas_flavor_snapshot.go` — `fillInCounts()`](https://github.com/kubernetes-sigs/kueue/blob/main/pkg/cache/scheduler/tas_flavor_snapshot.go#:~:text=remainingCapacity%20%3A%3D%20leaf.freeCapacity.Clone)

3. **Add scheduling gates to Deployment-backed workloads** so they follow the same pod lifecycle as batch Jobs. This aligns all workload types with Kueue's expected TAS flow. Requires changes in the job framework integration, not in the scheduler.

4. **Run `GetTargets()` speculatively before TAS evaluation.** When the initial quota-level mode is `Preempt`, identify preemption candidates first, then pass them to `updateAssignmentForTAS()` so it can simulate their removal via `SimulateWorkloadRemoval`. This breaks the circular dependency regardless of pod gating behavior.

### Environment

- Kueue version: v0.12.0 (also reviewed `main` branch — same code structure)
- Kubernetes version: v1.33.5
- Feature gates: `TopologyAwareScheduling: true`
- Topology: single-level (`zone-id`), all nodes in one domain
- Workload types tested:
  - **Deployment-backed** (any Kueue-integrated CRD that creates Deployments instead of Jobs): preemption FAILS under tight capacity
  - **batch/v1 Job** (native Kueue suspend/unsuspend): preemption WORKS under same tight capacity
