## Description

<!-- Please only use this template for submitting enhancement requests -->

**What would you like to be added**:

Add **first-class “workload/job dependencies”** support to Kueue so users can express *“B must not be admitted until A finishes (Succeeded/Completed)”* as a built-in capability, instead of implementing bespoke external controllers.

Concretely, introduce a **built-in dependency gate** integrated with Kueue’s admission flow, so dependent workloads remain queued but **not admitted** until their prerequisites are satisfied.

Possible scope for the built-in feature (community can pick the exact shape during design):

- A standardized way to declare dependencies (e.g., via `Workload`-level fields or well-defined annotations).
- A built-in “Dependency” admission check (or equivalent mechanism) that:
  - Evaluates prerequisite completion (Succeeded/Finished).
  - Provides clear status/messages on the blocked workload (`Pending` / `Retry` / `Rejected`).
  - Supports basic patterns: 1→1 dependency, fan-in, optionally cross-namespace policy.
  - Avoids deadlocks and minimizes extra reconcile churn.

**Why is this needed**:

Many batch/ML pipelines have strict ordering constraints (ETL → training → evaluation, preprocessing → simulation → aggregation). Today Kueue users typically solve this with external workflow engines (Argo/Tekton) or by writing their own `AdmissionCheck` controller, but that has drawbacks:

- **Common need, repeated re-implementation**: dependency gating is a frequent ask; every organization ends up building a similar controller with slightly different semantics and bugs.
- **Harder for users to get right**: a custom check controller must handle watch patterns, reconcile triggers, failure modes, backoff, race conditions (objects created out of order), and consistent status reporting—non-trivial for new users.
- **Inconsistent UX & operability**: different implementations produce different statuses/events/metrics, making debugging “why isn’t my workload running?” harder across clusters.
- **Tight integration benefits**: Kueue can implement this more reliably by integrating with its existing queuing model, admission checks state machine, and workload lifecycle (finished/evicted/deactivated), and by defining supported semantics.
- **Lower adoption friction**: a built-in solution reduces the barrier for users who want Kueue *without* adopting a full workflow system.
- **Community-maintained correctness**: when dependency gating is built-in, the community can ensure correctness across features like preemption, fair-sharing, stop policies, and future changes to Workload lifecycle.

(Users can still build custom controllers for advanced DAG logic, but a built-in “simple dependency gating” covers the 80% case and provides a standard foundation.)

**Completion requirements**:

- Define the **supported dependency semantics**:
  - What qualifies as “completed” (Succeeded only? Finished? handling failures?).
  - Behavior on missing prerequisites (Pending vs Rejected).
  - Behavior on prerequisite deletion/recreation.
  - Namespace boundaries and RBAC expectations.
  - Interaction with Kueue features (preemption, fair-sharing, stopPolicy, eviction, deactivation).
- Provide a clear **API/UX** for users to declare dependencies.
- Implement a controller/logic that updates `Workload.status.admissionChecks` (or equivalent) with:
  - Deterministic state transitions
  - Useful messages and events
  - Reasonable requeue/backoff to avoid hot loops
- Add tests (unit + integration) and documentation with examples.

This enhancement requires the following artifacts:

- [ ] Design doc
- [ ] API change
- [ ] Docs update

### Comment by [@gyliu513](https://github.com/gyliu513) — 2026-05-07T18:59:55Z

Thanks for the feedback, @kannon92. Let me clarify the scope and address your concerns.

**This is not a workflow engine.** The proposal is specifically for a bounded AdmissionCheck that gates workload admission based on prerequisite completion status, no DAG scheduling, no data flow, no retry orchestration. Kueue already has the AdmissionCheck extensibility point for exactly this pattern.

Regarding #74: that issue is about integrating Kueue with Argo/Tekton as full workflow systems. These are not mutually exclusive. Many users need simple sequential ordering (A then B) without deploying an entire workflow system. They're already using Kueue and just want admission ordering. Telling them to adopt Argo/Tekton for this use case adds significant operational overhead.

On the JobSet precedent: you mentioned "JobSet did add some simple dependOn policy for ML workloads." This is exactly the pattern I'm proposing at the Workload level. If JobSet found it appropriate to add simple dependency semantics, I'd argue a Workload-level dependency gate is in scope for Kueue, especially since Kueue owns the admission lifecycle.

On adoption friction: I understand you disagree, but this is based on direct user feedback. The alternative today is to write a custom AdmissionCheck controller, non-trivial work involving watch patterns, reconcile triggers, backoff, and race
conditions. A built-in implementation gives the community one correct, tested implementation instead of N slightly-different ones across organizations. Thoughts?

### Comment by [@gyliu513](https://github.com/gyliu513) — 2026-05-07T21:57:10Z

Thanks @mimowo — that's exactly the use case this is targeting. The "manager must be admitted before workers" pattern within a multi-Workload JobSet is a perfect concrete example of what a dependency AdmissionCheck would solve cleanly.

@kannon92 — point taken on Workload being an implementation detail. To clarify, the dependency declaration doesn't have to live on the Workload spec itself. One clean approach:

- The dependency is expressed on the **Job-level object** (e.g., an annotation on the BatchJob, JobSet ReplicatedJob, or a separate lightweight CRD).
- Kueue's integration layer (or a built-in AdmissionCheck controller) reads that declaration and sets the corresponding `admissionChecks` condition on the Workload, keeping Workload as an internal object.

This maps well to how existing AdmissionChecks work today — the user-facing contract is on the job object or AC config, not on Workload directly.
