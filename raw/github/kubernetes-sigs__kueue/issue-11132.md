## Description

**What would you like to be added**:
Multikueue would need a set of new metrics at various levels: cluster connectivity and status, dispatch performance and errors, evictions/preemptions across clusters, etc. (There are probably more, but these seem to be the most obvious ones.)

  * Cluster connectivity and status:
       * Cluster status: Reachable/active, disconnected, retrying. 
       * Last Reachable time by cluster: when was the cluster last reachable?
       * Sync_errors by cluster by reason: Kube API server returned 4xx/5xx, API server not reachable,  etc.
  * Dispatch performance:
       * Number of workloads dispatched to a cluster as candidate
       * Number of workloads admitted by the cluster? (This may be available in the worker cluster, but not sure if the mgmt cluster can provide more info.)
       * Admission latency by cluster (worker clusters' admission latency metric is not the same)
       * Number of dispatch rounds before admission
       * Number of clusters tried per admission 
       * Number of workloads pending that are eligible for a given cluster
  * Dispatch errors:
       * Number of dispatch rejections, faiilure to submit, etc. by cluster and by reason
  * Cross-cluster evictions:
       * Number of evictions for the same workload across clusters 

**Why is this needed**:
For MultiKueue to move from beta to production readiness, observability is important. Cross-cluster metrics will provide a global visibility.

## Update

Based on the discussion and feedback from the meeting, I reviewed the metrics again and removed some of them .

I think this is the list that we currently need (it is also open for discussion), and now I am struggling to determine the next step.


**1. Name:** `multikueue_cluster_last_reachable_time_seconds`

* **What it measures (Type):** A *Gauge* storing the Unix timestamp of the last successful ping/connection to a worker API.
* **Why implement it:** It instantly answers the most critical operational question: *"Is this specific worker cluster down?"* By using this metric, operators can write a simple alert that triggers if the timestamp gets too old.

**2. Name:** `multikueue_workloads_dispatched_total`

* **What it measures (Type):** A *Counter* tracking the total number of workloads the manager has attempted to send to a worker.
* **Why implement it:** It provides visibility into load balancing. It shows the operator if the manager is utilizing all worker clusters evenly, or if it is unfairly flooding one specific cluster with requests.

**3. Name:** `multikueue_workloads_admitted_total`

* **What it measures (Type):** A *Counter* tracking how many workloads were actually accepted and started by the worker.
* **Why implement it:** When you divide this metric by the "dispatched" metric, you get the **Admission Success Rate**. It tells you if a specific worker is constantly rejecting the jobs sent to it.

**4. Name:** `multikueue_pending_workloads`

* **What it measures (Type):** A live *Gauge* showing how many workloads have been sent to a worker but are currently stuck waiting in its queue.
* **Why implement it:** MultiKueue has an invisible "middle state" where a job is approved by the manager but still pending on the worker. This metric exposes that blind spot and tells the operator exactly which worker cluster is currently acting as a bottleneck.

**5. Name:** `multikueue_workload_admission_latency_seconds`

* **What it measures (Type):** A *Histogram* measuring the end-to-end time it takes from the manager dispatching the workload to the worker returning a "Ready/Admitted" status.
* **Why implement it:** It measures the actual speed of the system. It proves to operators which worker clusters are responding fast, and which ones are suffering from performance degradation.


**6. Name:** `multikueue_evictions_total`

* **What it measures (Type):** A *Counter* tracking how many times a running workload was preempted (kicked out) by a worker cluster.
* **Why implement it:** While the standard Kueue manager tracks evictions, it does *not* know which remote cluster did the evicting.  telling the manager exactly which worker is aggressively kicking out jobs due to quota or resource issues.
