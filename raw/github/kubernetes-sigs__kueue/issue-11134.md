**What happened**:
When enabling Admission Fair Sharing without explicitly setting usageHalfLifeTime, the field defaults to 0s. With a half-life of 0s, LocalQueue usage is effectively always zero, so there is no meaningful usage data to compare — fair sharing ordering has no effect.

This is particularly impactful when an operator (e.g., the Kueue operator) offers a Default configuration for admissionFairSharing. The Default configuration produces usageHalfLifeTime: 0s and usageSamplingInterval: 0s in the ConfigMap, though upstream Kueue internally defaults usageSamplingInterval to 5m0s. However, usageHalfLifeTime remains at 0s, which means users who enable admission fair sharing with the Default preset get no actual fair sharing behavior.

**What you expected to happen**:
When admissionFairSharing is enabled, a reasonable non-zero default for usageHalfLifeTime should be applied (similar to how usageSamplingInterval defaults to 5m0s), so that fair sharing ordering works out of the box.

**How to reproduce it (as minimally and precisely as possible)**:
  1. Configure Kueue with admissionFairSharing enabled using default values (e.g., admissionFairSharing: {} or via an operator's Default configuration)
  2. Create a ResourceFlavor, a ClusterQueue with 2 CPU quota, and two LocalQueues (A and B) in a namespace
  3. Submit job1 and job2 (1 CPU each) on LocalQueueA — ClusterQueue is now saturated (2/2 CPU)
  4. Submit job3 on LocalQueueA and job4 on LocalQueueB
  5. Delete job1 to free 1 CPU
  6. Observe which job is admitted next

**Actual behavior**:
job3 (LocalQueueA, high usage) is admitted. The consumedResources field on LocalQueues is never populated, and lastUpdate is never meaningfully updated.
Fair sharing ordering is not applied — admission falls back to other comparison criteria (ref).

Resulting config when using Default configuration:
```
  admissionFairSharing:
    usageHalfLifeTime: 0s
    usageSamplingInterval: 0s
```

LocalQueue status shows empty consumed resources:
```
  Fair Sharing:
    Admission Fair Sharing Status:
      Consumed Resources:
      Last Update: 2026-04-30T13:59:01Z
    Weighted Share: 0
```

**Expected behavior**:
job4 (LocalQueueB, zero usage) should be admitted over job3 (LocalQueueA, high usage), because fair sharing should prioritize the queue with lower  resource consumption.

With explicit non-zero values (e.g., usageHalfLifeTime: 1s, usageSamplingInterval: 1s), consumedResources is populated correctly and job4 is admitted as expected.

Setting halfLife to 0 effectively disables the feature, so I don't think it's necessarily wrong behavior. The value of halfLife should depend on the length of jobs - if jobs run for longer it makes sense to increase the halfLife, so their impact is well reflected; and admin's intention. This varies from cluster to cluster so we haven't introduced any specific default. We can however require this field (and add some exemplary values) so admins need to make more conscious decisions, wdyt?
