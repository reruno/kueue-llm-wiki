## Description

<!-- Please only use this template for submitting enhancement requests -->

**What would you like to be added**:
Currently all MK Controllers are running only in the leader instance of Kueue. 
We want to introduce a mechanism to allow some MultiKueue Controllers to run with custom logic in follower binaries, not just the leader instance.

This would be modeled after the leader-aware reconciliation strategies implemented by Core Controllers.

**Why is this needed**:
As part of the initiative of extending the Visibility API with MK-specific endpoints we will require certain data to be cached by the MultiKueue Controllers to make said API calls possible and efficient.
Since MK Controllers are not created in follower binaries of Kueue, these caches would not be available to the API Server nested within these binaries.

By providing a leader-aware solution for MK Controllers to utilize, we can define custom, limited logic populating the necessary data in the caches for Visibility API to use regardless whether the Kueue instance is a leader or a follower.

**Issues depending on implementing this mechanism:**
* https://github.com/kubernetes-sigs/kueue/issues/10105
* https://github.com/kubernetes-sigs/kueue/issues/10614

## Proposal 1: Interface + Wrapper

We define an interface to mark Reconciler of Controllers to implement the follower-aware logic:
```go
type ReconcilerWithFollowerObserver interface {
  TypedReconciler[Request]
  Observe(context.Context, Request) (Result, error)
}
```

Reconcilers implementing it will provide the follower Observe method, where the follower logic will be implemented.

The Reconcilers will then be wrapped by a dedicated leader-aware reconciler wrapper:
* the wrapper will invoke the wrapped reconciler's Reconcile method in the leader instance,
* the wrapper will invoke the Observe method in the follower instance.

```go
type LeaderAwareReconcilerWrapper struct {
    elected   <-chan struct{}
    reconcilerWithFollowerObserver   ReconcilerWithFollowerObserver
}

func (larw *LeaderAwareReconcilerWrapper) Reconcile(ctx context.Context, req reconcile.Request) (reconcile.Result, error) {
    select {
    case <-larw.elected:
        return larw.reconcilerWithFollowerObserve.Reconcile(ctx, req)
    default:
        return larw.reconcilerWithFollowerObserve.Observe(ctx, req)
    }
}
```

## Proposal 2: Injection

We define a leader-aware reconciler, with parametrized leader and follower reconcile strategies.
```go
type LeaderAwareReconcile struct {
    elected           <-chan struct{}
    leaderReconcile   func(ctx context.Context, req reconcile.Request) (reconcile.Result, error)
    followerReconcile func(ctx context.Context, req reconcile.Request) (reconcile.Result, error)
}

func (lar *LeaderAwareReconcile) Reconcile(ctx context.Context, req reconcile.Request) (reconcile.Result, error) {
    select {
    case <-lar.elected:
        return lar.leaderReconcile(ctx, req)
    default:
        return lar.followerReconcile(ctx, req)
    }
}
```

This reconciler is then injected and set up for chosen reconcilers, for example - when setting up wlReconciler, we rename its Reconcile method to LReconcile (leader-specific reconciler) and define a new method: FReconcile (follower-specific reconcile). We inject the LAR:

```go
type wlReconciler struct {
    LeaderAwareReconcile
    ...
}
```

then set the injected Reconciler as follows:

```go
wlReconciler.LeaderAwareReconcile = LeaderAwareReconcile {
    elected: mgr.Elected(),
    leaderReconcile: wlReconciler.LReconcile,    // the logic previously implemented by wlReconciler.Reconcile
    followerReconcile: wlReconciler.FReconcile,  // the new, follower specific logic implemented for wlReconciler
}
```

### Comment by [@olekzabl](https://github.com/olekzabl) — 2026-05-13T22:22:50Z

Thank you @Singularity23x0 for summarizing this.

A few more thoughts from me:

1. If we choose Option 2, I'd like `LReconcile` and `FReconcile` renamed.
   Say, to `LeaderReconciler` and `FollowerReconcile`. Feels much more self-explaining.

2. I personally prefer Option 1, mostly for 2 reasons:   
   - it's more in line with the `leaderAwareReconciler` already existing in Kueue, which is also a wrapper
   - it keeps `Reconcile()` method not renamed, which I think is what every reader (familiar with K8s code concepts but less familiar with specific MK files) would expect.

   However, I think Options 1 & 2 mostly differ on the "syntactic sugar level".

   So below I'm going to "speak Option 1 language" but it should translate well to the other one.

3. Down the code, I'd like to minimize code duplication between `Reconcile` and `Observe`.
   At least for #10105, I'd do it as follows:
   - move the current `Reconcile` into an internal helper, `doReconcile`, taking a param telling which "mode" it is
   - if the param says "observe", just skip most of reconcile logic (e.g. for the MK Workload Reconciler - just return early)
   - implement new `Reconcile` and `Observe` methods just as tiny wrappers around that shared `doReconcile`

   An alternative would be to try being more compositional (i.e. split `Reconcile()` into `Observe(); DoTheRest()`).
   However, I imagine this could be cumbersome in practice, e.g. `DoTheRest()` would naturally depend on some inner state of `Observe()`; also some functions in MK Cluster Reconciler have the observing and mutating code "shuffled".

4. We intend to treat this issue as a "shared input point" for KEPs for both #10105 and #10614.
   So that the plan for treating this can be aligned on here, not making the 2 KEPs depend on each other.
   (And not writing a separate KEP for this issue, which seems a bit too small and too internal to have its own KEP).
