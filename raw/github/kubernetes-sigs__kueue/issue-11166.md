## Description

## What happened?

The tiebreaker in the `slices.SortFunc` comparator at [`pkg/workloadslicing/workloadslicing.go#L124-L129`](https://github.com/kubernetes-sigs/kueue/blob/main/pkg/workloadslicing/workloadslicing.go#L124-L129) only checks one direction of the replacement relationship and falls through to `return 1` unconditionally:

```go
func() int {
    if b.Annotations[WorkloadSliceReplacementFor] == string(workload.Key(&a)) {
        return -1
    }
    return 1   // ← violates antisymmetry when neither replaces the other
},
```

When two workloads have identical `CreationTimestamp` and neither's `WorkloadSliceReplacementFor` annotation points to the other, both `cmp(a,b)` and `cmp(b,a)` return `1`. This violates Go's [strict weak ordering contract](https://pkg.go.dev/slices#SortFunc) for `slices.SortFunc`.

## How to reproduce

1. Enable `ElasticJobsViaWorkloadSlices`.
2. Create an elastic Job, admit it (`workload-v1`), scale up (`workload-v2` replaces v1), scale up again quickly (`workload-v3` replaces v2).
3. If `workload-v2` gets finished but `workload-v1` does not (transient `Finish` failure), `FindNotFinishedWorkloads` returns `[v1, v3]`.
4. `v1` has no replacement annotation; `v3` points to `v2` (not `v1`) → the tiebreaker returns `1` in both directions.
5. `EnsureWorkloadSlices` `case 2:` (line 215-216) assumes `workloads[0]=old, workloads[1]=new` — nondeterministic sort can swap them.

**Note:** Existing test `TwoActiveWorkloads_TimestampCollision` doesn't cover this — both test workloads have annotations where one directly points to the other.

## Impact

- Wrong workload finished → **quota leak** (stale slice holds quota, active slice is killed)
- Invalid comparator can cause **undefined pdqsort behavior**

## Suggested fix

```go
func() int {
    if b.Annotations[WorkloadSliceReplacementFor] == string(workload.Key(&a)) {
        return -1
    }
    if a.Annotations[WorkloadSliceReplacementFor] == string(workload.Key(&b)) {
        return 1
    }
    return 0
},
```
