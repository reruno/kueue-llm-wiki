## Description

## Summary

Kueue currently tracks preemptions at the **ClusterQueue level** via `kueue_preempted_workloads_total` (a Counter). There is no way to track how many times a specific workload has been preempted.

This makes it impossible to detect and alert on workloads that are repeatedly preempted — a pattern that indicates starvation or misconfigured priority/quota.

## Current State

Existing preemption metrics:

| Metric | Type | Labels | Granularity |
|---|---|---|---|
| `kueue_preempted_workloads_total` | Counter | `preempting_cluster_queue`, `reason`, `replica_role` | ClusterQueue |
| `kueue_admission_cycle_preemption_skips` | Gauge | `cluster_queue` | ClusterQueue |

Neither metric carries workload identity (`namespace`, `name`).

## Problem with `_total` Counter for Sparse Events

`kueue_preempted_workloads_total` requires `rate()` or `increase()` in PromQL to be useful for alerting. This works well for high-frequency events, but workload preemptions can be very sparse — days or weeks apart. For sparse events:

- `rate()` over any practical window (e.g. `[1h]`, `[24h]`) will return `0` or a near-zero float even when a workload has been preempted multiple times.
- Threshold-based alerts (`> N`) are not expressible with a counter alone.

## Request

Add a new **Gauge** metric tracking cumulative preemption count per workload:

```
kueue_workload_preemptions_count
```

- **Type:** Gauge
- **Labels:** `namespace`, `workload` (workload name), `cluster_queue`, `reason`
- **Semantics:** incremented each time the workload is preempted; deleted (with matching labels) when the workload completes or is deleted
- **Measurement point:** inside `metrics.ReportPreemption()` or equivalent, where the target workload is known

This enables straightforward alerting:

```promql
# Alert: workload preempted more than 3 times
kueue_workload_preemptions_count > 3
```

which is not achievable with the current counter-based metric.
