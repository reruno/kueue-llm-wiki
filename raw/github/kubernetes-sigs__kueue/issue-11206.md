## Description

## What happens

When one MultiKueue remote cluster's watch hangs, all other clusters become unusable for dispatch too — not just the affected one.

The `multikueuecluster` controller has one worker goroutine. It sets up each remote serially, opening watches with `client.Watch()` and not marking the cluster ready until all watches return. If one cluster's `client.Watch()` hangs (for example, when the remote apiserver is behind a proxy that buffers empty chunked responses), the worker is stuck on that cluster and never moves on to the rest. The remaining clusters stay in the "still connecting" state forever; the dispatcher then excludes them from the active set and admission for every queue stops, even for queues that point at completely different clusters.

## How we hit it

kueue v0.13.3 with one remote behind Cloudflare Tunnel. Cloudflare buffers chunked HTTP responses with no payload, so an empty watch (label selector matched zero objects) never streams a single event back. `client.Watch()` never returns. The reconciler's worker is stuck. Other clusters never get their watches set up, and admission cluster-wide stops.

Roughly 90 minutes of zero-admission across all our queues before we reverted the offending change.

## Proposed fix

Add a 60s bound on the `client.Watch()` *establishment* phase only. On timeout, propagate an error to the existing `failedConnAttempts` / `retryAfter()` backoff. The successful-watch stream lifetime is unchanged.

PR: #11207.

This is defense in depth on top of #9968 (which fixed the specific Cloudflare-empty-watch trigger by enabling watch bookmarks). Any other future condition that hangs `client.Watch()` would hit the same head-of-line blocking.

Adjacent: #10428.
