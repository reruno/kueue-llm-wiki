## Description

**What happened**:

The `GroupKindConcurrency` knob is wired up for the `MultiKueueCluster` controller, but setting it above 1 does not actually buy you parallelism. Any one slow or hung remote stalls reconciles for every other MultiKueueCluster.

The reason: `Reconcile` calls `clustersReconciler.setRemoteClientConfig`, which takes the controller wide write lock `clustersReconciler.lock` ([`pkg/controller/admissionchecks/multikueue/multikueuecluster.go:394`](https://github.com/kubernetes-sigs/kueue/blob/main/pkg/controller/admissionchecks/multikueue/multikueuecluster.go#L394)) and holds it through the entire synchronous `setConfig` → `startWatcher` → `establishWatch` → `client.Watch()` chain ([line 460](https://github.com/kubernetes-sigs/kueue/blob/main/pkg/controller/admissionchecks/multikueue/multikueuecluster.go#L460)). While one worker is parked inside `client.Watch()`, every other reconcile that wants to do anything with a different cluster blocks on the same lock.

So concurrency=N collapses back to 1 whenever any remote is slow or hung.

**What you expected to happen**:

Setting `controller.groupKindConcurrency["MultiKueueCluster.kueue.x-k8s.io"]` to N should give up to N reconciles running in parallel. When one cluster's reconcile is slow or hung, the other N-1 workers should keep going on other clusters.

**How to reproduce it (as minimally and precisely as possible)**:

1. Run Kueue with `controller.groupKindConcurrency["MultiKueueCluster.kueue.x-k8s.io"]` set to something greater than 1 (e.g. 5).
2. Add two or more `MultiKueueCluster` objects, with one of them pointing at an unreachable or unresponsive remote apiserver.
3. Watch the healthy clusters: they also stall (no `Active=True`, no status updates) for as long as the unhealthy one is hung inside watch establishment.

With #11207 merged this stall is bounded to 10 minutes per cycle instead of indefinite, but the head of line blocking across clusters still happens during that window.

**Anything else we need to know?**:

Surfaced during review of #11207. Mimowo flagged it as "this renders `GroupKindConcurrency` useless for `MultiKueueCluster` due to very technical reasons which can be considered a bug by a user" ([PR thread](https://github.com/kubernetes-sigs/kueue/pull/11207#discussion_r3248735173)).

The 10 minute timeout from #11207 only addresses the worst case (indefinite block). The underlying serialization is still there.

Filing this to track the lock refactor.

**Environment**:

N/A. Architectural bug, reproducible on `main` at the time of #11207.
