## Description

**What happened**:

PR #11207 set `defaultWatchEstablishTimeout` to a static 10 minutes. That covers the apiserver cold cache plus conversion webhook scenario from kubernetes/kubernetes#136950 (about 8 min at 50k Workloads), but it also means a truly hung remote keeps a reconciler worker parked for 10 full minutes before the timeout fires.

**What you expected to happen**:

A tight initial timeout (around 1 minute) so hung remotes fail fast, growing on consecutive failures so a slow but recovering remote still gets the time it needs.

**Proposal**:

Drive the timeout off the existing `rc.failedConnAttempts` counter.

Schedule: 1m, 2m, 4m, 8m, 10m, 10m, ...

`failedConnAttempts` already resets to zero on a successful establishment and resets on config change, so there is no new state to manage. It stacks naturally with the `retryAfter(rc.failedConnAttempts)` reconnect backoff from #10990: both grow together when the same remote keeps failing.

**Anything else**:

Committed to in PR #11207 (https://github.com/kubernetes-sigs/kueue/pull/11207#discussion_r3260697405).

Today's Kueue (v1beta2 served = stored) does not actually hit the slow apiserver cold cache path, so practical impact is limited until version skew returns. Filing this so the design discussion can happen on its own thread.
