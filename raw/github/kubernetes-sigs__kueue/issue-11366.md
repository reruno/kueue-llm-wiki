## Description

**What would you like to be added**:

Enable wait for Pods ready by default as a safety net.

The main consideration I think is backwards compatibility, but maybe with a suffiently large timeout this would be acceptable. This is still a beta feature, I think this could go by default:

```yaml
waitForPodsReady:
  timeout: 1h
  recoveryTimeout: 1h
  blockAdmission: false
  requeuingStrategy:
    backoffBaseSeconds: 60
    backoffMaxSeconds: 3600
    backoffLimitCount: null // endless
    timestamp: Eviction
```
This is our recommendation basically with an extended timeout.

I wanted to post it long time ago, but the KEP DRA was the main trigger: https://github.com/kubernetes-sigs/kueue/pull/10283/changes#diff-9992bde183489d9f804057ec1cebd8b81b2470c8a9430abffee5ad8db5278e93R321

**Why is this needed**:

We have multiple incidents where waitForPodsReady could have mitigated the issue, and so we now always recommend it to all users, but sometimes only after an incident.

### Comment by [@tenzen-y](https://github.com/tenzen-y) — 2026-06-25T14:30:13Z

I discussed with @mimowo about this offline. As a result, I almost agree with enabling this by default. Because disabling waitForPodsReady is indeed not effective in the Production Kueue cluster. In my experience, waitForPodsReady is a must-have feature for almost every cluster.

But, API governance PoV, I requested to check if k/k previously has changed default values in the core API without API version upgrades.
If they have experience, we can directly enable it by default. Otherwise, we will have some mitigation way like introducing a dedicated feature gate. The reason that we can change the default in either situation is that waitForPodsReady is the Kueue Configuration API, and I am thinking the Configuration API has a more flexible compatibility policy (e.g., we didn't apply the same API convention rules to the Configuration API while we apply those to the Kueue core APIs) than the Kueue core APIs like ClusterQueue, and Workload.
