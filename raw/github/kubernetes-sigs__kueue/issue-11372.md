## Description

**What happened**:
A pod with `kueue.x-k8s.io/managed` label was admitted by the Pod mutating webhook (status was `SchedulingGated`), but the workload creation failed due to timeout:
```
"caller":"jobframework/reconciler.go:481","msg":"Handling job with no workload","controller":"v1_pod",
...
Internal error occurred: failed calling webhook \"mworkload.kb.io\": failed to call webhook: Post ...: context deadline exceeded".
```
and related, also:
```
"caller":"controller/controller.go:474","msg":"Reconciler error","controller":"v1_pod",
...
Internal error occurred: failed calling webhook \"mworkload.kb.io\": failed to call webhook: Post...
```

The pod remained gated indefinitely with no Workload object until the Kueue controller process was manually restarted 1h 52min later. I also didn't see repeat logs of above, which means the retry on reconcile was not kicking in. Once I restarted Kueue, I believed this triggered fresh reinformer list to re-enqueue every pod, and so the workload create succeeded on that orphaned pod, and the pod was unblocked.

**What you expected to happen**:
A managed pod should not be orphaned indefinitely. Either:
1. Reconciler retries until workload is created successfully or
2. There is some way to re-enqueue such orphaned pods without corresponding workloads.

**How to reproduce it (as minimally and precisely as possible)**:
I haven't been able to manually reproduce consistently in my production or development environment. I have tried to update the webhook mutatingwebhookconfiguration to point at a bad URL, and while I saw similar error logs, I noticed the reconciler was able to do retry-with-backoff for that case. I was not able to reproduce a unit test that would drop the retry on the floor like I observed in production. 

**Anything else we need to know?**:
- Other pods were able to be processed by the some Kueue controller process during that 1h 52m time window, which makes me believe this error condition only happened to a few pods.
- Pod informer watch looked healthy during this time window
- No leader election switchover happened during the affected time window, until I manually restarted Kueue.
- We run Kueue as an out-of-cluster controller.
- `failurePolicy` for `mworkload.kb.io` is currently set to `Fail `
- I tried tracing the code, and my understanding is that if reconciler returns `(ctrl.Reuslt{}, nil)`, then the [retry](https://github.com/kubernetes-sigs/kueue/blob/v0.14.4/pkg/controller/jobframework/reconciler.go#L484) could be dropped. I looked at:
  - 1. jws Skip() - [code](https://github.com/kubernetes-sigs/kueue/blob/v0.14.4/pkg/controller/jobframework/reconciler.go#L268-L272) - probably not relevant for my situation
  - 2. dropFinalizers() - [code](https://github.com/kubernetes-sigs/kueue/blob/v0.14.4/pkg/controller/jobframework/reconciler.go#L274-L305) - probably not relevant for my situation
  - 3. client.IgnoreNotFound(err) - [code](https://github.com/kubernetes-sigs/kueue/blob/v0.14.4/pkg/controller/jobframework/reconciler.go#L308-L310) - I know that the pod did exist during the time of the orphaning, but curious if there is some race here that might result in apiserver not found error.
  - 4. Namespace-selector mismatch - [code](https://github.com/kubernetes-sigs/kueue/blob/v0.14.4/pkg/controller/jobframework/reconciler.go#L312-L322) - I don't use this feature.
  - 5. Missing queue name - [code](https://github.com/kubernetes-sigs/kueue/blob/v0.14.4/pkg/controller/jobframework/reconciler.go#L345-L356) - my pod did have the queue-name label.
  - 6. not top-level job - [code](https://github.com/kubernetes-sigs/kueue/blob/v0.14.4/pkg/controller/jobframework/reconciler.go#L359) - IIUC this is not relevant since I use Kueue for pods

Regardless of the root cause, I would like to propose some opt-in sweeper than periodically checks for orphaned pods and creates the corresponding workload for the gated pod. Would like to hear your thoughts! Let me know if any other information would useful. Thanks.

### Comment by [@kevin85421](https://github.com/kevin85421) — 2026-06-22T02:03:13Z

I take a look at the issue. One possible theory is that:
* The user creates a Pod.
* The reconciler fails to create the workload CR in the first reconciliation.
* The informer cache is still not up to date, so `shouldFinalize` is set to true because the Pod is not found.
* `ReconcileGenericJob` returns `ctrl.Result{}, nil` because `shouldFinalize` is true, so the resource is not re-enqueue into the work queue.

However, I don't know how to explain why the Pod doesn't exist in the informer cache. The reconciler watches both Pod and `Workload`. Because the `Workload` is failed to create, the reconciliation is only possible to be triggered by the Pod's event. However, client-go will put the Pod into the informer cache before putting into the work queue ([code](https://github.com/kubernetes/client-go/blob/d04ac3067ff145b15e6740d07ef5043eb1d2206f/tools/cache/controller.go#L639)). Therefore, the above theory still doesn't fully hold.
