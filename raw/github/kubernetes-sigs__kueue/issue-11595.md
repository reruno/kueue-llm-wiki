**What happened**:
When using plain pod integration with pod-group-fast-admission: "true", the waitForPodsReady timeout never triggers even when some pods in the group (e.g., Spark executors) remain permanently Pending/Unschedulable. The workload stays admitted indefinitely with PodsReady=True, and quota is never reclaimed.
```
# k get po 
NAME                               READY   STATUS    RESTARTS   AGE
pythonpi-d179a69e5d78028b-exec-1   0/1     Pending   0          7h2m
pythonpi-d179a69e5d78028b-exec-2   0/1     Pending   0          7h2m
spark-gang-requeue-driver          1/1     Running   0          7h2m
```
**What you expected to happen**:
The workload should be evicted after the configured waitForPodsReady.timeout because not all pods in the group are Ready.
**How to reproduce it (as minimally and precisely as possible)**:
1. Create a pod group with pod-group-fast-admission: "true" and pod-group-total-count: "3" (1 driver + 2 executors)
2. Driver and executors have different PodSpecs (different containers, args, resources — as is normal for Spark)
3. Driver pod is schedulable and becomes Running/Ready
4. Executor pods have unsatisfiable nodeSelector, remaining Pending forever
5. Observe: the Workload's PodsReady condition is set to True (only driver was checked)
6. waitForPodsReady timeout never fires; workload is never evicted
