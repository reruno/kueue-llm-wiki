**What happened**:
Kueue assigned a flavor to a Workload with ProvisioningRequest as an AdmissionCheck. After the Workload was evicted e.g. by higher priority Workload, or deactivation, the ProvisioningRequest is kept which is a bad design pattern

**What you expected to happen**:
ProvisioningRequest to be cleaned-up after Workload is evicted

### Comment by [@k-ngs](https://github.com/k-ngs) — 2026-06-20T10:51:03Z

I also encountered what appears to be this issue in the past.

Before fixing this issue, I think it would be analyzing the behavior for each eviction scenario and agreeing on the intended spec first — for example, whether a workload should be requeued or deactivated after being evicted.

In the case of a simple preemption-based eviction, the ProvisioningRequest temporarily remains but appears to be resolved when the workload is requeued, so I don't think it is critical in that scenario. However, I suspect there may be more serious consequences in other cases.

### Comment by [@MatteoFari](https://github.com/MatteoFari) — 2026-06-23T08:58:10Z

I think the intended ProvisioningRequest behavior should be explicit.

My idea is:

| Scenario | ProvisioningRequest behavior |
|---|---|
| `Finished=True` | Delete owned ProvisioningRequests |
| `Evicted=True` with reason other than `AdmissionCheck` | Delete owned ProvisioningRequests |
| `Evicted=True` with reason `AdmissionCheck` | Preserve ProvisioningRequest state, because this is used for retry/backoff |
| Quota reservation lost without finish/eviction | Preserve existing behavior |

Regarding preemption, yes it may fix itself later, but deleting it while the Workload is evicted avoids keeping an old capacity request that no longer matches an active reservation.
