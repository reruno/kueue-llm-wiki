**What happened**:
`kueue_admission_cycle_preemption_skips` as a gauge is not a good historical signal. It reflects the last reported cycle with skips and can disappear with cleanup/resync. Scrape timing can also easily miss or misrepresent short-lived skip behavior. It should probably be a counter

As an example, over a span of 4 hours, I got 0 preemption skips from the metrics. But saw several indictions in the logs that preemption skips happened. 

I think whats happening is this: 
It latches at the last cycle's skip count and stays there until the next cycle that has skips overwrites it.

**What you expected to happen**:
Instead of gauge, you probably want to change this from a gauge to a counter and need to add a reason label. 
We probably want a new metric `kueue_admission_cycle_preemption_skips_total` added so as not to break backwards compatibility. But I'm curious if people are successfully using `kueue_admission_cycle_preemption_skips` in dashboards.

### Comment by [@mimowo](https://github.com/mimowo) — 2026-06-15T05:57:04Z

The new metric looks reasonable, and was my instinct too. I can certainly see why the "guage" metric is missing some of the skips  from the admin perspective - because it reports them to the user only relying on the fixed scrape time, every 15s by default. 

However now I looked at the PR (https://github.com/kubernetes-sigs/kueue/pull/2919) which introduced the guage as a metric and it reports these two points:
- "I also considered using a counter, instead of a gauge, but, because admission cycles are not capped, the number could grow too fast.". Here are actually two thoughts folded under this sentence:
- the rapid increase of the metric could maybe loop around the counter? Let's assume 10 skips per cycle, 10ms each, this is 
1000skips per second, so in a year this is "354*24*60*60*1000=30585600000". That may exceed int32 but is nowhere near float 64 (2^53) which is used by metrics, so I think we are ok here.

However, the other problem I see is: "how will user interpret the metric" since the scheduling cycles don't really have a fixed delay, they start with 1ms and grow to 100ms if no admissions. This could be difficult to interpret looking at the numbers. **For example an admin can observe a reduced growth rate just because the scheduling cycles are less often.**. This interpretability issue makes me wonder if the approach is even correct to measure stuff per cycle. 

I don't have a strong view here, we could consider the metric as alpha, but I'm wondering if we run out of other ideas. cc @amy @andrewseif @tenzen-y

IIUC the primary objective for the guage metric done in https://github.com/kubernetes-sigs/kueue/pull/2919 was to provide observability for cases when the "skips" are stuck for a prolonged time. The skips are alartiming  only if there are many of them for a long time, I think the guage metric provides that observability.
