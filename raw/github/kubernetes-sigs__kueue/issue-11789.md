**What would you like to be added**:

Invstigate how / if possible without regression to optimize the number of Pods marked as Failed by the Node Hot Swap.

This was originally found by flaking tests, https://github.com/kubernetes-sigs/kueue/issues/11617.

However, the initial attempt to improve the situation turned out has a bug as raised in the thread: https://github.com/kubernetes-sigs/kueue/pull/11621#discussion_r3304301729

**Why is this needed**:

To minimize the impact of the Node Hot Swap on production workloads.

### Comment by [@j-skiba](https://github.com/j-skiba) — 2026-06-01T09:57:24Z

as discussed here https://github.com/kubernetes-sigs/kueue/pull/11621#discussion_r3322614063

I think that one of possible solutions is to react on workload's assignment change and only then mark stray pods as failed. Reacting on pod changes allows us just to find the stray pods but it doesn't give us any guarantee that when we mark the pod as failed then the pod will not be recreated with a nodeSelector pointing to the same unhealthy node and such pod would have to be mark as failed again. Such approach results in artificial increment of backoff counter of a job.

By reacting on workload's assignment change we know that any new pods recreated after marking stray pods as failed will have nodeSelectors set properly to healthy nodes from the new assignment
