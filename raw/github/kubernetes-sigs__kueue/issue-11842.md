## Description

**What would you like to be added?**

  When the TAS scheduler cannot find a topology placement for a Workload, the QuotaReserved=False condition is set with a message string such as:

```
  - topology "<topology-name>" doesn't allow to fit any of <N> pod(s).
  - topology "<topology-name>" allows to fit only <X> out of <Y> pod(s).
```

  (Source: pkg/cache/scheduler/tas_flavor_snapshot.go#L1788 (https://github.com/kubernetes-sigs/kueue/blob/0d1a4ddd7e3aebf626d52776aa6315d776158bea/pkg/cache/scheduler/tas_flavor_snapshot.go#L1788))

  However, the reason field on the same condition is set to the same generic value (e.g. Pending / Inadmissible) that's used for ordinary quota-exhaustion misses. As a result, anything consuming the condition programmatically — controllers, dashboards, KSM CustomResourceStateMetrics scrapers — has no structured way to identify
  topology placement failures separately from quota-exhaustion failures.

  We'd like Kueue to set a distinct reason value on the QuotaReserved=False condition whenever TAS is the cause of the rejection. A suggested value:

  - TopologyPlacementFailed (or NoTopologyFit / TASFitFailed — open to whatever the maintainers prefer)

  Ideally this reason would be applied for both the "no pods fit" and "only some pods fit" cases, since both represent the same underlying signal: quota is available but topology constraints prevent admission.

  **Why is this needed?**

  This is for first-class observability into "tasks blocked by topology placement". Today our options are all bad:

  1. Substring-match the message field in our control plane / dashboards. Brittle (any wording change in Kueue silently breaks it) and not portable across Kueue versions. We currently do this and it's exactly what we'd like to delete.
  2. Expose the full message as a metric label via kube-state-metrics CustomResourceStateMetrics. Unbounded label cardinality — message includes the topology name and (<N>, <X>, <Y>) per-pod counts, which can explode time-series counts in Prometheus.
  3. Track admission-attempt counters at the namespace/cluster level. Doesn't tell us which workloads are stuck, just that something is.

  A distinct reason value would let us do all of the following cleanly:

  - kube-state-metrics CRS can expose kueue_workload_quota_reserved{reason="TopologyPlacementFailed"} directly from the condition path, with bounded label cardinality. Operators can then alert/dashboard on count by (cluster_queue, namespace) (kueue_workload_quota_reserved{status="False", reason="TopologyPlacementFailed"}).
  - External controllers that want to surface a user-facing "your workload is queued because no topology fits right now" message can do so by reading a structured field rather than parsing English.
  - Alerts can fire specifically on topology starvation (which often signals a cluster-wide capacity layout issue) without false positives from quota saturation (which is a project-level capacity issue).

  **Alternatives considered**

  - A separate condition type (e.g. TopologyPlacementFailed) rather than a new reason on QuotaReserved. Cleaner in some ways but more invasive — adds a new condition to the public Workload API and would need stronger consensus. Happy to go this route if maintainers prefer it.
  - A structured field on Workload.status capturing TAS diagnostics (e.g. tasSchedulingResult with requestedTopology, fitFailureReason, podsFitted, podsRequested). Most expressive, but largest API surface change.
  - No-op, rely on message. What we do today; downsides above.

  We'd be happy with the smallest of these (a new reason value) and can adopt larger changes if the project lands them later.
