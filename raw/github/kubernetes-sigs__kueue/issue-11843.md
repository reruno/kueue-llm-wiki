## Description

   **What would you like to be added?**

  Today, kueue_pending_workloads (https://kueue.sigs.k8s.io/docs/reference/metrics/) is documented as:

  ```
 kueue_pending_workloads | Gauge | The number of pending workloads, per 'cluster_queue' and 'status'.
   'status' can have the following values:
   - "active" means that the workloads are in the admission queue.
   - "inadmissible" means there was a failed admission attempt for these workloads and they won't be retried until cluster conditions, which could make this workload admissible, change.
  
  
 Labels: cluster_queue, status, replica_role
```

  We'd like to extend this metric (and its local-queue counterpart kueue_local_queue_pending_workloads) with an additional `reason` label that explains why a workload is pending / inadmissible. The current status="inadmissible" value collapses several distinct root causes into one bucket; a structured reason would let operators alert on and dashboard the underlying causes.


  Suggested initial enum (analogous to the existing reason enum on kueue_evicted_workloads_total (https://kueue.sigs.k8s.io/docs/reference/metrics/) — a nice precedent in the same metrics surface):

  - "InsufficientQuota" — no quota currently available in the cluster queue (or cohort) to fit the workload.
  - "BorrowingLimitReached" — borrowing limit prevents admission even though some shared quota exists.
  - "TopologyPlacementFailed" — TAS could not find a placement that satisfies the requested topology (see also #).
  - "PreemptionPending" — the workload is waiting for in-flight preemption to release resources.
  - "AdmissionCheckPending" — a configured AdmissionCheck has not yet transitioned to True.
  - "Blocked" — administrative state prevents admission (e.g. ClusterQueue/LocalQueue stopped, spec.active=false).
  - "Unknown" — fallback for any reason not yet enumerated, so the metric remains complete during version skew.


  For status="active" the reason would typically be empty (or a single "Pending" value), since those workloads are simply waiting their turn — but emitting a consistent default keeps the time-series shape stable.

  **Why is this needed?**
  
  The pending-workload backlog is one of the highest-signal numbers we watch for capacity planning, alerting, and user-facing diagnostics. Today, when kueue_pending_workloads{status="inadmissible"} ticks up, we can't programmatically distinguish between fundamentally different operator actions.
  
  Each warrants a different page, dashboard panel, and runbook. With only status="inadmissible", we either build coarse alerts that page on the wrong cause or roll our own scrapers/controllers to extract Workload.status.conditions — which is expensive and brittle (we end up parsing condition message strings to distinguish e.g. TAS failures from quota-exhaustion failures).

  Adding reason mirrors what kueue_evicted_workloads_total already does for evictions, and would let us write:

```
  # How many workloads are blocked by TAS placement, by cluster queue?
  sum by (cluster_queue) (
    kueue_pending_workloads{status="inadmissible", reason="TopologyPlacementFailed"}
  )
```
  …directly out of Kueue's own metrics, with no controller-side enrichment.

  **Alternatives considered**
  
  - A separate kueue_pending_workloads_by_reason metric. Keeps the current metric shape stable but doubles the metrics surface and creates two sources of truth that can drift. Extending the existing metric with an extra label is cleaner; PromQL aggregation (sum without (reason)) preserves the old query shape exactly.
  - Encode the reason inside the status label (e.g. status="inadmissible:TopologyPlacementFailed"). Unidiomatic and harder to query.

  **Anything else we need to know?**

  - We'd want the same change on kueue_local_queue_pending_workloads.
  - Cardinality impact is bounded: reason is a small fixed enum (~6 values), multiplicative with the existing (cluster_queue, status, replica_role) tuple. In practice the inadmissible status sees most of the new fan-out.
