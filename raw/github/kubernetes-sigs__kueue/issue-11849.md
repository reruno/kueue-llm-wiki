## Description

**What happened**:

In a MultiKueue environment, I observed that the existing worker-local Jobs will be deleted when a Job is created on the manager cluster and a Job with the same NamespacedName already exists on the worker clusters. 
This occurs regardless of whether the existing worker-local Jobs are managed by kueue.

Before `wlReconciler` on manager cluster create remote workload onto worker clusters, 
it seems to delete all Jobs with same NamespacedName by `DeleteRemoteObject()` in `RemoveRemoteObjects()`:

https://github.com/kubernetes-sigs/kueue/blob/563f449618940b39805dcdec289c8a4d6e522d26/pkg/controller/admissionchecks/multikueue/workload.go#L132-L138

Is that intentional?

**How to reproduce it**
- Setup [MultiKueue](https://kueue.sigs.k8s.io/docs/tasks/manage/setup_multikueue/), and manager and worker cluster
- Create a job named `sample-job-a` on worker cluster.(call this job `Job(a)`)
- Create a job which has the same name of worker's(`sample-job-a`) on manager cluster specifying `kueue.x-k8s.io/queue-name` so that it is dispatched to worker cluster.(call this job `Job(b)`)

After `Job(b)` is created, `Job(a)` will be deleted and remote job `Job(b)` is created on worker cluster.
You can check this by comparing uid of Job object on worker cluster.

**Anything else we need to know?**:
This change seems to have been introduced in https://github.com/kubernetes-sigs/kueue/pull/9201, but this problem might not been considered.

**Environment**:
- Kubernetes version: v1.35.1
- Kueue version: v0.18.0

### Comment by [@mochizuki875](https://github.com/mochizuki875) — 2026-06-01T13:08:11Z

@mszadkow 
Thank you for your comment.

By my research, [this change](https://github.com/kubernetes-sigs/kueue/pull/9201) was introduced in [v0.17.0](https://github.com/kubernetes-sigs/kueue/releases/tag/v0.17.0) and cherry-picked in [v0.16.2](https://github.com/kubernetes-sigs/kueue/releases/tag/v0.16.2) and [v0.15.5](https://github.com/kubernetes-sigs/kueue/releases/tag/v0.15.5).
Before that, the existing worker-local Jobs with same NamespacedName will not be deleted and mistakenly identified as remote Job by the Manager cluster.
So the Job on Manager cluster will not actually dispatched to Worker cluster.(The situation might be more terrible...)

For example, this is the `RemoveRemoteObjects()` in v0.16.1 before this change was introduced:

https://github.com/kubernetes-sigs/kueue/blob/5d4944e6b782a95a0858b858c082f2a869f4012a/pkg/controller/admissionchecks/multikueue/workload.go#L128-L149

In this case, `RemoveRemoteObjects()` will return nil before delete the Jobs if `remWl == nil`.

### Comment by [@mszadkow](https://github.com/mszadkow) — 2026-06-01T18:14:06Z

Yes, you are 100% correct, it was introduced to fix GC race.
Now, one way to fix this is to `Get` the remote object and verify it carries the expected `kueue.MultiKueueOriginLabel` before issuing the `Delete.`
