## Description

### What happened

When a TAS-admitted Workload undergoes a second-pass admission that rewrites `Workload.Status.Admission.PodSetAssignments[*].TopologyAssignment`, for example after a node-failure-driven eviction and re-scheduling, pods that were ungated against the *previous* `TopologyAssignment` can be left pinned (via `pod.spec.nodeSelector`) to topology domains that are no longer present in the *current* `TopologyAssignment`. This is timing-dependent, it only fires when the ungater observes the replacement pod before the TA rewrite.

In our setup the topology's lowest level is `kubernetes.io/hostname`, so each leaf domain corresponds to a single node and "pinned to a domain" is literally "pinned to a hostname". When the failed host is removed from the TA, an already-ungated pod that targeted it remains nailed to that exact hostname.

Once the underlying host recovers, such a pod runs on a domain no longer tracked by Kueue. It consumes capacity invisible to TAS's per-domain accounting, distorting subsequent scheduling decisions for other Workloads on that ClusterQueue/Cohort. If the host does not recover, the pod stays unschedulable until `PodReadyTimeout` fires,  which is recoverable, but still a stranded slot.

### What you expected to happen

Every ungated, non-terminated pod belonging to a `PodSetAssignment` *P* with `P.TopologyAssignment != nil` should be pinned to a domain that is in `P.TopologyAssignment.Domains`. If a `TopologyAssignment` is rewritten in a way that strands previously-ungated pods, the ungater should reconcile the invariant, e.g., by deleting the orphans so the owner controller (Job/JobSet/LWS/...) recreates them, after which the ungater will pin them against the fresh TA.

### How to reproduce

> **Note on reproducibility:** this is **not deterministic** in a simple cluster. The bug depends on the order in which the ungater processes two events: the newly-created replacement pod and the Workload TA update. If the TA update is reconciled *first* and the replacement pod *second*, the pod is gated by the webhook and the (now-current) TA is used to pin it: no orphan, no bug. The orphan only persists when the replacement pod is reconciled (and ungated) *before* the TA update is observed, so the pod ends up pinned against the stale TA and is never revisited. Note that this race can't be eliminated by event ordering alone, because Pods and Workloads are watched independently. In production this fires often enough to leak hosts; in a small cluster you may need to script the failure injection and retry, or instrument the ungater to delay one of the two informer paths.

1. Submit a TAS-enabled Workload (e.g., a JobSet with a `kueue.x-k8s.io/podset-required-topology` annotation) sized to span multiple topology domains, with `kubernetes.io/hostname` as the lowest level.
2. Wait until all pods are ungated and pinned by the topology ungater (`pod.spec.nodeSelector` contains the assigned hostname).
3. Mark one of the assigned nodes as unhealthy/unschedulable so its pods are evicted (e.g., cordon + drain, or simulate a TAS node-failure event).
4. Kueue performs a second-pass admission and rewrites the affected `PodSetAssignment.TopologyAssignment` to swap the failed domain for a replacement.
5. **If** the ungater observes the new pod before the TA update, the new pod is ungated against the stale TA and pinned to the failed hostname. Otherwise the case resolves correctly (retry until the race fires).
6. Observe that any pod ungated in step 5 remains pinned to the failed hostname even after the TA no longer contains that domain.
7. Bring the failed node back. The orphaned pod now schedules on a hostname Kueue no longer accounts for.

### Anything else we need to know

**Root cause (from reading the code):**

[topology_ungater](https://github.com/kubernetes-sigs/kueue/blob/main/pkg/controller/tas/topology_ungater.go) watches both Pods and Workloads, so it does react to the TA rewrite. However, its current logic is designed around two paths:

- The **greedy / rank-assignment path** (`assignGatedPodsToDomainsGreedy`, `Reconcile` grouping block) operates only on *gated* pods. It computes how many slots per domain remain after subtracting *already-ungated* pods, then assigns the gated pods. This implicitly assumes already-ungated pods are pinned to domains that exist in the current TA; mismatches *within* the assigned set are expected and tolerated (e.g., across `PodIndexOffset` changes).
- There is no path that enforces the converse, that the *set* of domains occupied by ungated pods is a subset of the *set* of domains in the current TA. So when a TA rewrite removes a domain that previously held ungated pods, those pods are silently dropped from the ungater's view.

In other words, the invariant *"every ungated pod is pinned to a domain in its PodSet's current TopologyAssignment"* is assumed but never enforced.

**Proposed fix:**

Add a membership check to `topology_ungater.Reconcile` (running before the existing grouping / greedy assignment block). For each `PodSetAssignment` *P* with `P.TopologyAssignment != nil` and each non-terminated, ungated pod *q* belonging to *P*: if `q`'s nodeSelector does not resolve to a domain in `P.TopologyAssignment.Domains`, treat `q` as an orphan and delete it. Use the expectations store to swallow the resulting pod-delete event, emit per-pod + per-workload events for observability, and bail out of the reconcile so the next round sees a clean state (the owner controller recreates the pod gated, and the normal greedy/rank path pins it against the current TA).

Happy to send a PR. Open questions for the TAS maintainers before I do:

1. **Feature-gate or not?** This changes ungater semantics for TAS workloads. Would you prefer it behind an alpha `TASEvictOrphanPods` gate for a release, or land it as a straight bug fix?
2. **Eviction vs. relabel?** I went with delete-and-let-the-owner-recreate because it composes cleanly with all owner integrations (Job/JobSet/LWS/Pod-group) and avoids inventing a "re-pin in place" path. Any preference?
3. **Observability surface:** I'd add a `kueue_tas_orphan_pods_evicted_total{podset}` counter and a `TopologyEnforced` workload condition with reason `OrphanPodEvicted` when at least one orphan is evicted. Any naming preferences?

### Environment
- Kueue version: v0.16.1
- Kubernetes: AKS with unmanaged GPU nodes
- Cluster Size: 1000s of GB200/300 nodes with 100s of NVL72 racks
- Topology: 2 levels (nvidia.com/gpu.clique → kubernetes.io/hostname)

### Comment by [@j-skiba](https://github.com/j-skiba) — 2026-06-01T11:38:23Z

there was a bugfix in v0.16.4 https://github.com/kubernetes-sigs/kueue/pull/9615 that was trying to fix this issue. The node controller watches for pods that are "bound" to a node via `nodeSelector` but cannot run and marks these as `Failed` so the job controller can recreate these pods and Kueue has a chance to assign the up to date `nodeSelectors` to these new pods. 

But it doesn't handle situation when the node becomes healthy again unfortunately.

Note: I think would be nice to add a condition too if we were to terminate the pods, similar like here https://github.com/kubernetes-sigs/kueue/blob/a4f53d21d1ba45580a0f9a827cb48c30be4ddff2/pkg/controller/tas/node_controller.go#L611
