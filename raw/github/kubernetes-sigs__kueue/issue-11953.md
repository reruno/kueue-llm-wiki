## Description

**What would you like to be added**:

Relax the two constraints that TAS PodSet grouping (`kueue.x-k8s.io/podset-group-name`) currently enforces in `ValidatePodSetGroupingTopology` ([`pkg/controller/jobframework/tas_validation.go:214-264`](https://github.com/kubernetes-sigs/kueue/blob/main/pkg/controller/jobframework/tas_validation.go#L214)):

1. A group must contain **exactly 2 PodSets** — otherwise: `"can only define groups of exactly 2 pod sets, got: N pod set(s)"`.
2. At least one of the 2 PodSets must have **count == 1** — otherwise: `"can only define groups where at least one pod set has only 1 replica"`.

We would like to relax **both** so that a PodSet group with a **required** topology constraint can:
- contain **more than 2 PodSets**, and
- contain PodSets that **all have count > 1** (no required single-replica "leader").

Placement semantics: all PodSets sharing a `podset-group-name` with a required topology should be co-located within the same topology domain (e.g., the same spine).

Scope this to the **required** topology case (`podset-required-topology`). The **preferred** case is a harder optimization problem (best-effort balancing across domains, fallback when the whole group doesn't fit) and is left as future work.

The 2-PodSet / leader-worker assumption is also baked into the scheduler and ungater, which would need to be generalized:
- `findLeaderAndWorkers` ([`pkg/cache/scheduler/tas_flavor_snapshot.go:614-627`](https://github.com/kubernetes-sigs/kueue/blob/main/pkg/cache/scheduler/tas_flavor_snapshot.go#L614)) — only reads `trs[0]` and `trs[1]`; a 3rd+ PodSet in a group is ignored during placement.
- topology ungater rank assignment ([`pkg/controller/tas/topology_ungater.go:201-221`](https://github.com/kubernetes-sigs/kueue/blob/main/pkg/controller/tas/topology_ungater.go#L201)) — handles a group only as a 2-element (smaller=leader, larger=workers) pair.

**Why is this needed**:

We have a reinforcement learning (RL) use case where **inference and training pods need to be placed on the same spine** for performance. These are distinct roles with different pod templates, modeled as separate PodSets, each with multiple replicas — and none is a singleton "leader". The current grouping model can't express this, since it violates both the "exactly 2 PodSets" and the "one must be <=1 replica" rules.

Related: #6242 (Add validation for PodSet Grouping)

### Comment by [@phoenix1712](https://github.com/phoenix1712) — 2026-06-05T17:39:53Z

We run large-scale asynchronous off-policy RL post-training. A single logical job is several cooperating roles, each its own PodSet:

- a distributed **trainer** (MPIJob / PyTorchJob) — N workers
- a fleet of **inference / rollout generators** (vLLM-style, StatefulSet) — M replicas
- **supporting services** (weight-sync server, replay buffer, messaging bus)

The trainer and generator fleet have to land in the **same network topology domain (same spine)**. Generator rollouts feed the trainer, and updated weights are pushed back to every generator many times per run via NCCL collectives / P2P RDMA over a high-bandwidth fabric (EFA / InfiniBand-class). If the two fleets split across spines, weight-transfer bandwidth collapses, the refit step dominates step time, and expensive accelerators sit idle. 

Today these run as **separate workloads** on a single spine resource flavor. We plan to combine them into a single workload using either **AppWrapper** or **RayJob**, so the trainer and inference roles are submitted and gang-scheduled together on a multi-spine resource flavor (this allows us to aggregate capacity and improve occupancy and utilization).
