## Description

### What happened

With the `ElasticJobsViaWorkloadSlices` feature gate enabled, an elastic
autoscaling RayCluster scaled its workers **up past its ClusterQueue's nominal
quota**, and the surplus worker pods were **ungated and Running** — while the
ClusterQueue's accounted usage stayed flat at the admitted amount. The
replacement WorkloadSlice for the larger worker count was still `Pending`
(correctly held back by quota), yet its pods had already been started.

The net effect is that the `ElasticJobUngater` lets an elastic job exceed its
ClusterQueue quota during scale-up: quota enforcement is silently bypassed for
the extra replicas.

### Environment

- Kueue **v0.18.0** (also reproduces on `main` / `release-0.18` — see below)
- KubeRay v1.6.0, Ray 2.51.1
- Feature gate: `ElasticJobsViaWorkloadSlices=true`
- An elastic RayCluster (`kueue.x-k8s.io/elastic-job: "true"`,
  `enableInTreeAutoscaling: true`) whose `worker` replicas exceed the quota
  granted to the admitted slice.

### Expected

When a scale-up mints a new WorkloadSlice whose worker count does not fit the
ClusterQueue quota, that slice stays `Pending` and its **surplus** worker pods
stay `SchedulingGated` until the replacement slice is admitted. Only the
replicas actually granted quota should ever be ungated.

### Actual

All gated pods carrying the elastic job's (chain-root) workload name are ungated
the moment **any** slice in the chain is admitted/has a quota reservation — with
no cap to the granted replica count. The surplus workers run outside quota.

### Root cause

`pkg/controller/elasticjobs/elastic_job_ungater.go`. `Reconcile` ungates **every**
pod returned by `listGatedPods`, and `listGatedPods` is uncapped:

```go
func (r *elasticJobUngater) listGatedPods(ctx context.Context, wl *kueue.Workload) ([]*corev1.Pod, error) {
	sliceName := workloadslicing.SliceName(wl)
	var podList corev1.PodList
	if err := r.client.List(ctx, &podList,
		client.InNamespace(wl.Namespace),
		client.MatchingFields{indexer.WorkloadSliceNameKey: sliceName},
	); err != nil {
		return nil, fmt.Errorf("listing pods for workload slice: %w", err)
	}

	var gated []*corev1.Pod
	for i := range podList.Items {
		if utilpod.HasGate(&podList.Items[i], kueue.ElasticJobSchedulingGate) &&
			podList.Items[i].Annotations[kueue.WorkloadAnnotation] == wl.Name {
			gated = append(gated, &podList.Items[i])
		}
	}
	return gated, nil
}
```

The list is keyed by the **chain-root** slice name (`SliceName(wl)` returns the
chain root via the `kueue.x-k8s.io/workload-slice-name` annotation, falling back
to `wl.Name`). Every pod of an elastic job — including the scale-up workers
belonging to the *replacement* slice — carries that same chain-root name in its
`kueue.x-k8s.io/workload` annotation. So when the **already-admitted root** slice
reconciles (`shouldUngate` is true for it: it's admitted), `listGatedPods`
returns *all* gated pods in the chain, and `Reconcile` ungates the entire set —
including the surplus workers whose own replacement slice is still `Pending` and
over quota.

There is nothing bounding the ungated count to the replicas the ClusterQueue
actually granted. The reconcile of the admitted slice ungates pods that belong,
quota-wise, to a slice that has not been admitted.

### Reproduction

1. Enable `ElasticJobsViaWorkloadSlices`.
2. Create a ClusterQueue + LocalQueue with quota for, say, head + **1** worker.
3. Create an elastic, in-tree-autoscaling RayCluster against that queue; it is
   admitted at 1 worker.
4. Drive load so the Ray autoscaler raises `worker.replicas` (e.g. to 3). Kueue
   mints a replacement WorkloadSlice for the larger count; it does **not** fit
   quota and stays `Pending`.
5. Observe: the surplus worker pods are **Running** (ungated), but the
   ClusterQueue's admitted usage is unchanged — the job is over quota.

   Expected: the surplus workers stay `SchedulingGated` until the replacement
   slice is admitted.

### Affected versions

The ungater source is byte-identical across releases — the same blob
(`ee4ac3f2…`) is on `main`, `release-0.18`, and the `v0.18.0` tag — so this is a
live bug on `main`, not only on the release.

### Proposed fix

Cap ungating, per PodSet, to the replicas actually **granted quota** across the
slice chain (the largest count among quota-reserved slices sharing the chain
root), counting already-ungated pods against the cap. Surplus pods stay gated
until their replacement slice is admitted. Sketch:

```go
// In listGatedPods, after the List:
granted, err := r.grantedPodSetCounts(ctx, wl) // max Count per podSet over quota-reserved slices in the chain
if err != nil {
	return nil, err
}

ungatedPerPodSet := make(map[string]int32)
gatedPerPodSet := make(map[string][]*corev1.Pod)
for i := range podList.Items {
	p := &podList.Items[i]
	if p.Annotations[kueue.WorkloadAnnotation] != wl.Name {
		continue
	}
	ps := p.Labels[constants.PodSetLabel]
	if utilpod.HasGate(p, kueue.ElasticJobSchedulingGate) {
		gatedPerPodSet[ps] = append(gatedPerPodSet[ps], p)
	} else {
		ungatedPerPodSet[ps]++ // already-ungated pods consume quota too
	}
}

var gated []*corev1.Pod
for ps, pods := range gatedPerPodSet {
	slices.SortFunc(pods, func(a, b *corev1.Pod) int { return strings.Compare(a.Name, b.Name) })
	room := granted[ps] - ungatedPerPodSet[ps]
	if room <= 0 {
		continue
	}
	if int32(len(pods)) > room {
		pods = pods[:room]
	}
	gated = append(gated, pods...)
}
return gated, nil
```

`grantedPodSetCounts` walks the slice chain (siblings sharing the parent job's
`OwnerReference` UID, matched to the same `SliceName`) and takes, per PodSet, the
max `Count` among slices that `HasQuotaReservation`. We have this fix running on
our cluster; with it, scale-up surplus workers stay `SchedulingGated` until the
replacement slice is admitted, and the ClusterQueue quota is respected. Happy to
open a PR.
