## Description

**What would you like to be added**:
When using the time-sharing fairness mechanism through `kueue-priority-booster`, I would like the queue ordering to be based on a criterion other than `creationTimestamp`.

If this proposal sounds reasonable, I'd be happy to work on an implementation and submit a PR.

**Why is this needed**:
The current behavior of `kueue-priority-booster` is as follows
```
job-sample-job-st6g6-f7381 - create - running
job-sample-job-h9446-f9845 - create - running
job-sample-job-87dhp-fc903 - create - suspend
job-sample-job-r4hkr-a3e27 - create - suspend
job-sample-job-87dhp-fc903 preempt job-sample-job-st6g6-f7381
job-sample-job-st6g6-f7381 clear booster annotation
job-sample-job-st6g6-f7381 preempt job-sample-job-h9446-f9845
job-sample-job-h9446-f9845 clear booster annotation
job-sample-job-h9446-f9845 preempt job-sample-job-87dhp-fc903
```
However, with this approach, `job-sample-job-r4hkr-a3e27` remains suspended and cannot preempt any workload. 
This seems inconsistent with the intended goals of a time-sharing fairness mechanism.

Therefore, I suggest adopting a new queue-ordering strategy that operates as follows:
```
job-sample-job-st6g6-f7381 - create - running
job-sample-job-h9446-f9845 - create - running
job-sample-job-87dhp-fc903 - create - suspend
job-sample-job-r4hkr-a3e27 - create - suspend
job-sample-job-87dhp-fc903 preempt job-sample-job-st6g6-f7381
job-sample-job-st6g6-f7381 clear booster annotation
job-sample-job-r4hkr-a3e27 preempt job-sample-job-h9446-f9845
job-sample-job-h9446-f9845 clear booster annotation
job-sample-job-st6g6-f7381 preempt job-sample-job-87dhp-fc903
```


**Completion requirements**:
- Introduce a new queue-ordering strategy that does not rely solely on `creationTimestamp`.
- Ensure the behavior works consistently with workloads preempted by kueue-priority-booster.

### Comment by [@dddwsd](https://github.com/dddwsd) — 2026-06-17T11:16:41Z

I see your point. As you mentioned, the new approach could potentially be unfair to the oldest job.

One mixed approach I would like to suggest is slightly modifying the FIFO comparison logic.

Currently, we only compare workloads based on `creationTimestamp`. 

Instead, we could introduce an additional condition when comparing workloads with the same priority:
* If the gap between the two workloads' `creationTimestamp` values is greater than **N seconds**, the older workload would win.
* If the gap is smaller than **N seconds**, we could use `lastTransitionTime` as the tie-breaker and compare the older and newer workloads based on that value.

I think this could preserve the FIFO behavior for workloads with a significant age difference, while allowing workloads with similar creation times to be ordered more fairly based on their latest transition time.

I really like the idea of a time-boundary-based RoundRobin approach and fully agree with it.

One of my concerns with a purely timestamp-based approach was that it could introduce various edge cases. A time boundary seems like a much cleaner way to balance fairness and FIFO semantics.

I have one question. When a new (or requeued) workload is pushed into the queue, would the RoundRobin logic be triggered to apply to both the existing pending workloads within the time boundary and this newly arrived workload?

The reason I ask is that, for a preempted workload that has already been pushed back into the CQ, changing its position later would likely require some form of priority boost. If that's the case, I wonder whether we would need a separate feature gate for that behavior.
