## Description

<!-- Please only use this template for submitting enhancement requests -->

**What would you like to be added**:
When using the time-sharing fairness mechanism through `kueue-priority-booster`, I would like the queue ordering to be based on a criterion other than `creationTimestamp`.

If this proposal sounds reasonable, I'd be happy to work on an implementation and submit a PR.

**Why is this needed**:
The current behavior of `kueue-priority-booster` is as follows
```
job-sample-job-st6g6-f7381 - create - running
job-sample-job-h9446-f9845 - create - running
job-sample-job-87dhp-fc903 - create - suspend
job-sample-job-r4hkr-a3e27 - create - suspend
job-sample-job-87dhp-fc903 preempt job-sample-job-st6g6-f7381
job-sample-job-st6g6-f7381 clear booster annotation
job-sample-job-st6g6-f7381 preempt job-sample-job-h9446-f9845
job-sample-job-h9446-f9845 clear booster annotation
job-sample-job-h9446-f9845 preempt job-sample-job-87dhp-fc903
```
However, with this approach, `job-sample-job-r4hkr-a3e27` remains suspended and cannot preempt any workload. 
This seems inconsistent with the intended goals of a time-sharing fairness mechanism.

Therefore, I suggest adopting a new queue-ordering strategy that operates as follows:
```
job-sample-job-st6g6-f7381 - create - running
job-sample-job-h9446-f9845 - create - running
job-sample-job-87dhp-fc903 - create - suspend
job-sample-job-r4hkr-a3e27 - create - suspend
job-sample-job-87dhp-fc903 preempt job-sample-job-st6g6-f7381
job-sample-job-st6g6-f7381 clear booster annotation
job-sample-job-r4hkr-a3e27 preempt job-sample-job-h9446-f9845
job-sample-job-h9446-f9845 clear booster annotation
job-sample-job-st6g6-f7381 preempt job-sample-job-87dhp-fc903
```


**Completion requirements**:
- Introduce a new queue-ordering strategy that does not rely solely on `creationTimestamp`.
- Ensure the behavior works consistently with workloads preempted by kueue-priority-booster.


This enhancement requires the following artifacts:

- [v] Design doc
- [v] API change
- [v] Docs update

The artifacts should be linked in subsequent comments.

### Comment by [@dddwsd](https://github.com/dddwsd) — 2026-06-17T11:16:41Z

I see your point. As you mentioned, the new approach could potentially be unfair to the oldest job.

One mixed approach I would like to suggest is slightly modifying the FIFO comparison logic.

Currently, we only compare workloads based on `creationTimestamp`. 

Instead, we could introduce an additional condition when comparing workloads with the same priority:
* If the gap between the two workloads' `creationTimestamp` values is greater than **N seconds**, the older workload would win.
* If the gap is smaller than **N seconds**, we could use `lastTransitionTime` as the tie-breaker and compare the older and newer workloads based on that value.

I think this could preserve the FIFO behavior for workloads with a significant age difference, while allowing workloads with similar creation times to be ordered more fairly based on their latest transition time.

### Comment by [@dddwsd](https://github.com/dddwsd) — 2026-07-19T00:54:36Z

In #12653 I proposed adding `ClusterQueue.spec.ordering` with a `RoundRobin` mode
(Option 1 below). While iterating on it, I came up with three alternative designs
(Options 2–4). All four share the same idea — for a bounded period (a "round-robin
window"), a preempted workload is ordered *behind* already-pending same-priority
workloads, then falls back to creation-time FIFO — but they differ in where the knob
lives and what triggers the reordering. I'd love to hear which direction fits Kueue best
before continuing with the KEP.

---

### Option 1 — `ClusterQueue.spec.ordering` with a `RoundRobin` mode (the current #12653 design)

A dedicated per-CQ ordering field (`mode: FIFO | RoundRobin` + `roundRobinWindow`).
`RoundRobin` orders same-priority workloads by the latest `lastTransitionTime` across all
`status.conditions`; the window is measured from workload *creation*.

- **Pros**: per-ClusterQueue and discoverable; a separate field, so it composes with
  either queueing strategy; the latest-condition key generically covers any requeue cause.
- **Cons**: *any* condition transition (reactivation, admission-check changes, PodsReady
  flips) reorders the workload — surprising orderings unrelated to preemption; new CRD
  surface (field, webhook, conversion, per-CQ plumbing); the creation-anchored window
  means a long-pending/long-running victim can age out before it is ever preempted and
  immediately return to the head.

### Option 2 — New `ClusterQueue.spec.queueingStrategy` value (e.g. `RoundRobinFIFO`)

A third strategy alongside `StrictFIFO`/`BestEffortFIFO`: like `BestEffortFIFO`, but a
workload requeued after a preemption eviction is placed at the back of its priority band
for the window (eviction-anchored, preemption-only trigger).

- **Pros**: per-ClusterQueue and discoverable; reorders only on preemption, with the
  window anchored to the eviction.
- **Cons**: same behavior as Option 3 but strictly more API — new enum value, webhook
  validation, conversion, per-CQ plumbing, plus an extra `roundRobinWindow` field since a
  duration can't live in an enum; bundles two orthogonal axes (`queueingStrategy` today
  governs head-blocking/requeue placement, not the sort key), and as a sibling enum it is
  mutually exclusive with the existing strategies — "StrictFIFO + round-robin" becomes
  inexpressible.

### Option 3 — Eviction-timestamp requeuing via the per-CQ heap ordering (Configuration-level)

For a workload evicted with reason `Preempted`, the pending-heap comparator uses the
eviction's `lastTransitionTime` instead of `creationTimestamp` (still after effective
priority, as a tie-breaker) — generalizing the existing
`waitForPodsReady.requeuingStrategy.timestamp: Eviction` precedent:

```yaml
preemption:
  requeuingStrategy:
    timestamp: Eviction   # default Creation (current behavior)
    window: 30m           # optional; measured from the eviction
```

- **Pros**: no CRD change, purely additive and easy to feature-gate; precise scope
  (tie-breaker only — preemption policies, cross-CQ ordering, fair sharing untouched);
  the victim goes behind already-pending peers but stays ahead of later arrivals;
  composes with both `StrictFIFO` and `BestEffortFIFO`; eviction-anchored window covers
  long-running victims.
- **Cons**: global (per-Configuration), not per-ClusterQueue; with `window` set, each CQ
  keeps a small auxiliary expiry index to re-fix expired heap entries.

### Option 4 — Keep the priority-boost annotation for the window (external controller only)

The booster keeps the negative `kueue.x-k8s.io/priority-boost` on the victim for the
window instead of clearing it at eviction, so the victim sorts behind peers via effective
priority.

- **Pros**: no Kueue core change — ships as a booster-side change on top of the existing
  `PriorityBoost` gate; naturally per-workload and per-controller-policy.
- **Cons**: encodes queue position into effective priority, leaking into preemption
  policy checks (`LowerPriority`, `LowerOrNewerEqualPriority`) and cross-priority-tier
  ordering; re-admission race — a workload admitted with a stale negative boost runs as
  artificially low priority and is immediately preemptable; over-penalizes the victim —
  since priority is compared *before* the timestamp tie-breaker, even workloads created
  *after* the eviction get ahead of the victim for the whole window.

---

To summarize, the options are really combinations of two axes (where the knob lives ×
what triggers the reordering):

| | Trigger: any condition transition, window from creation | Trigger: preemption eviction only, window from eviction |
|---|---|---|
| **Per-CQ CRD** | Option 1 (`spec.ordering`, separate field) | Option 2 (`queueingStrategy` enum) |
| **Configuration (global)** | — | Option 3 |
| **External controller** | — | Option 4 (via effective priority) |

I'm still weighing these and haven't settled on one — I'd really appreciate the
community's opinion on which direction fits Kueue best (or any other approach I might
have missed). Once there's a rough consensus, I'm happy to rework #12653 toward that
direction.
