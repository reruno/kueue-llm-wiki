### Comment by [@apullo777](https://github.com/apullo777) — 2026-06-08T12:59:19Z

Hi, I'd like to work on this :)
  
I looked at a recent run (21 specs, ~328s) and the heaviest part is the Spark setup (apache/spark + spark-operator) are by far the largest images, while the rest of the suite is lighter. So my initial thought is to isolate Spark into its own shard by feature label, so the other shard can skip those image pulls:
- shard-0: feature:spark
- shard-1: the rest (managejobswithoutqueuename, workloadidentifierannotations)

Most of the job time is actually setup rather than test exec, so I'll confirm the wall-clock balance and adjust the split if needed. Does this direction sound reasonable?

/assign

### Comment by [@mimowo](https://github.com/mimowo) — 2026-06-08T13:33:47Z

Hi @apullo777 this makes sense to me, I would just suggest making spark `shard-1` so that we don't need to rename the other ones if we delete the shard for spark one day. This is possible because:
1. if we graduate it to beta then we will not need to change configuration and we can just run it as part of regular singlecluster build
2. we may externalize it to a subproject for external integrations (I will work on the issue)

I think (2.) ,might be more likely, cc @everpeace 

Also, I think we could move some tests for the core Job from `managejobswithoutqueuename_test.go` to the sequential baseline suite.
