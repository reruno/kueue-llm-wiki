## Description

**What would you like to be added**:

Mirror the existing `borrowWithinCohort.maxPriorityThreshold` field on `withinClusterQueue`: when set, `LowerPriority` / `LowerOrNewerEqualPriority` only target Workloads whose priority is at or below the threshold.

```yaml
preemption:
  withinClusterQueue:
    policy: LowerPriority
    maxPriorityThreshold: 100   # only preempt workloads with priority <= 100
```

**Why is this needed**:

A common pattern is opportunistic / best-effort Workloads at a dedicated scavenger priority class sharing a ClusterQueue with production tiers. Operators want preemption to be strictly tiered:

- production at high should preempt scavenger
- production at high should **not** preempt production at medium in the same CQ

Today `withinClusterQueue: LowerPriority` is all-or-nothing — enabling it also lets high preempt medium within the production tier, which most users explicitly don't want. `withinClusterQueue: Never` leaves scavenger Workloads non-preemptable.

The cohort workaround (move scavenger to its own CQ + `reclaimWithinCohort: LowerPriority`) doesn't compose cleanly when other CQs already borrow from the production CQ via cohort (e.g. CPU CQ borrowing CPU/memory from a GPU CQ to fill stranded compute) — enabling reclaim there reclaims all lower-priority cohort borrowers, not just the scavenger tier.

A `maxPriorityThreshold` on `withinClusterQueue` solves this on the same-CQ axis directly, mirroring the field that already exists for `borrowWithinCohort`.

### Comment by [@andrewseif](https://github.com/andrewseif) — 2026-06-18T13:41:45Z

Before I open a PR I want to confirm the API shape, because a literal mirror of `borrowWithinCohort` runs into a backwards-compatibility wall.

`borrowWithinCohort` carries its threshold inside a struct:

```go
type BorrowWithinCohort struct {
    Policy               BorrowWithinCohortPolicy
    MaxPriorityThreshold *int32
}
```
but `withinClusterQueue` is a bare scalar enum in both served versions (`v1beta1`, deprecated + served; `v1beta2`, storage):

```go
WithinClusterQueue PreemptionPolicy `json:"withinClusterQueue,omitempty"`
```

So nesting the threshold the way the issue's YAML suggests:

```yaml
withinClusterQueue:
  policy: LowerPriority
  maxPriorityThreshold: 100
```

changes that field's wire format from `string` → `object`. That breaks every existing manifest/stored object setting `withinClusterQueue: LowerPriority` and would require a new API version + hand-written conversion, which seems disproportionate for an additive feature.

Proposed alternative:  an additive sibling field on `ClusterQueuePreemption` (no version bump, fully backward-compatible):

```yaml
preemption:
  withinClusterQueue: LowerPriority
  withinClusterQueueMaxPriorityThreshold: 100   # only preempt same-CQ workloads with priority <= 100
```

```go
WithinClusterQueueMaxPriorityThreshold *int32 `json:"withinClusterQueueMaxPriorityThreshold,omitempty"`
```

Semantics identical to `borrowWithinCohort.maxPriorityThreshold` (victim priority ≤ threshold; unset → no restriction), gated behind a new alpha feature gate, enforced for same-CQ candidates in both the classical and Fair Sharing paths. The only trade-off is cosmetic asymmetry, the cohort axis nests the threshold, the same-CQ axis hangs it as a sibling.

would the sibling field be acceptable, or do you specifically want the nested-struct shape (accepting a new API version + conversion)? One detail either way, the new field would live only in `v1beta2`, IIUC.

WDYT?
