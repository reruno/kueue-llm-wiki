### Comment by [@vladikkuzn](https://github.com/vladikkuzn) — 2026-06-12T12:53:59Z

I also applied longer timeout, but was thinking if we need to:
1. Shorten scrape interval in e2e Prometheus config — recommended structural fix
Change: Patch the ServiceMonitor (or Prometheus CR) in the e2e overlay, e.g.:
```
spec:
  endpoints:
    - path: /metrics
      port: https
      interval: 5s   # e2e only
```
Why it works: Shrinks worst-case scrape delay from ~30s to ~5s, making PromQL checks much more deterministic without changing production defaults.
Pros: Fixes the race at the source for tests; faster feedback on pass.
Cons: Slightly more scrape load in e2e clusters (negligible for one target).

2. Two-phase assertion: direct `/metrics` first, then PromQL — recommended robust fix
Change: After admission:
Confirm kueue_admitted_workloads_total exists on Kueue `/metrics` (curl helper or shared util).
Then poll PromQL with a timeout of roughly one scrape interval + buffer (e.g. 40s if interval stays 30s, or 15s if interval is 5s).
Why it works: Separates “Kueue emitted the metric” from “Prometheus ingested it”. Failures become actionable instead of one opaque 90s timeout.
