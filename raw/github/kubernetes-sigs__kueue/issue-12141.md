## Description

**What would you like to be added**:

An opt-in sidecar layout for the KueueViz chart, so the chart installs **1 Deployment with 2 containers + 1 ClusterIP Service**, instead of today's 2 Deployments + 2 Services + 2 Ingresses:

- Keep the current 2-Deployment layout as the default for backward compatibility (no breaking change).
- Add a `kueueViz.sidecar.enabled` chart value (default `false`). When it's set, the install becomes:
  - **1 Deployment** with 2 containers:
    - `frontend` container running nginx, serving the React static build and forwarding `/ws` to `127.0.0.1:8090`
    - `backend` container running the existing Go server on `127.0.0.1:8090` — **no changes to `cmd/kueueviz/backend`**
  - **1 ClusterIP Service** (`kueueviz`) targeting the frontend container's port
  - **0 ConfigMaps** for `env.js` URL injection — the React code points at relative `/ws` instead of an external URL
  - **0 Ingress objects** by default; users wire one Ingress / HTTPRoute / `kubectl expose --type LoadBalancer` themselves

**Why is this needed**:

The current 2-Deployment + 2-Service + 2-Ingress layout makes installation more complicated than it needs to be. When deploying the chart with the default Ingress objects (or trying alternatives like raw `type: LoadBalancer` Services or Gateway API), I keep hitting the same difficulties:

1. **Two user-facing addresses** (`frontend.kueueviz.local`, `backend.kueueviz.local`) — both must be reachable from the browser, so the user needs two rules in the LoadBalancer and two DNS records.
2. **`env.js` ConfigMap must be patched at install time** with the backend endpoint, then the frontend pod restarted to pick it up. This is a chicken-and-egg problem if the backend address (e.g. a LoadBalancer IP) isn't known until install completes.
3. **CORS configuration** (`KUEUEVIZ_ALLOWED_ORIGINS`) must be set on the backend to match the frontend's origin.
4. **WebSocket from the browser directly to the backend Service** — the browser itself opens the connection directly to `kueueviz-backend`. The frontend pod isn't on the data path. This is what forces issues 1, 2, and 3.
5. **Path-based routing helps, but isn't the chart's default.** A single path-routed `Ingress` / `HTTPRoute` (with `/` → frontend, `/ws` → backend) gives you 1 address and removes CORS — but the chart ships 2 host-based Ingresses, so you'd have to override the defaults to get it.

I went through the previous conversations to make sure this hasn't already been discussed:

- **Issue #940** discussed *what* the dashboard should be and *whether* metrics + Grafana would be enough, but didn't get into pod / Service topology, container packaging, or how the browser would talk to the backend.
- **PR #3727** (the "Initial commit") adopted @akram's [`kueue-viz`](https://github.com/akram/kueue-viz) project. The 2-Deployment layout came in with that contribution. I couldn't find a thread explaining *why* it's two Deployments vs one pod with two containers.

It looks like this wasn't discussed, or did I miss something?
