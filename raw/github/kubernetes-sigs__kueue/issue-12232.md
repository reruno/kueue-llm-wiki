## Description

**What happened**:

When a Kueue-managed StatefulSet is scaled down to `spec.replicas=0`, the old Workload may remain in the cluster and continue to consume ClusterQueue quota.

In the problematic case we observed:

1. the StatefulSet was scaled down to `0`
2. the corresponding Workload no longer had the StatefulSet ownerReference
3. the Workload still had:
   - `QuotaReserved=True`
   - `Admitted=True`
   - `status.admission != nil`
   - `spec.active=true`
4. the Workload was also marked `Evicted=True` with reason `PodsReadyTimeout`
5. the ClusterQueue still counted the Workload usage

As a result, the workload was logically retired, but its quota reservation was still active and continued blocking queue capacity.

Additionally, scaling the StatefulSet from `0` back to `>0` can be blocked by the webhook with:

```text
workload from previous scale-down is still being deleted
```

So the old Workload can both:

1. keep consuming quota, and
2. prevent the StatefulSet from scaling up again.

**What you expected to happen**:

When a Kueue-managed StatefulSet is explicitly scaled down to `spec.replicas=0`, the previous admitted Workload should not keep consuming ClusterQueue quota indefinitely.

At minimum, one of the following should happen automatically:

1. the old Workload should release its quota reservation and clear `status.admission`, or
2. the old Workload should be driven to a terminal cleanup state that no longer counts against ClusterQueue usage.

In other words, `replicas=0` should not leave behind an admitted/reserved Workload that remains active in quota accounting.

**How to reproduce it (as minimally and precisely as possible)**:

1. Create a Kueue-managed StatefulSet with `replicas=1` and a queue label so it gets a Workload.
2. Let the Workload become admitted and reserve quota in a ClusterQueue.
3. Make the Workload hit a `PodsReadyTimeout` path, or otherwise keep it in a state where `Evicted=True` is set while the old reservation still exists.
4. Scale the StatefulSet down to `spec.replicas=0`.
5. Observe the old Workload:
   - ownerReference may be removed
   - but `QuotaReserved=True` and `status.admission` may remain
6. Observe the ClusterQueue usage:
   - the old Workload can still be counted as active reserved usage
7. Try scaling the StatefulSet back from `0` to `>0`
   - the webhook may reject it with:
     `workload from previous scale-down is still being deleted`

**Anything else we need to know?**:

This looks like a semantic mismatch across multiple parts of the StatefulSet / Workload lifecycle:

1. In `pkg/controller/jobs/statefulset/statefulset_reconciler.go`, when `replicas == 0`, the reconciler removes the StatefulSet ownerReference from the Workload, but does not release quota reservation.
2. In `pkg/controller/core/workload_controller.go`, the `PodsReadyTimeout` eviction path calls `workload.Evict(...)`, but does not clear `status.admission` or unset the quota reservation.
3. In `pkg/workload/workload.go`, `HasActiveQuotaReservation(...)` still treats the Workload as active quota usage as long as:
   - it has quota reservation
   - it is not finished
   - it is active
4. In `pkg/controller/jobs/statefulset/statefulset_webhook.go`, scaling from `0` to `>0` may be rejected if the old Workload still exists:
   - `workload from previous scale-down is still being deleted`

So even though `replicas=0` looks like an explicit owner retirement event, the old Workload can remain both:

1. quota-consuming, and
2. scale-up-blocking

This does not look like a normal delayed cleanup window. It can leave the system in a long-lived residual state that requires manual intervention.
