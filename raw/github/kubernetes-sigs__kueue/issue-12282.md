## Description

<!-- Please only use this template for submitting enhancement requests -->

**What would you like to be added**:

`kueue_cluster_queue_lendable_resources` - Instantaneous amount of quota a ClusterQueue can lend to peers now, for one flavor-resource pair.
`kueue_cohort_lendable_resources` - Total instantaneous lendable capacity available in a cohort for each flavor-resource.

Introduce a new metric that help to understand current amount of resource quota that this ClusterQueue can expose to peers in its Cohort right now.
Another metric that aggregates the amount of sharable resource quota of all CLusterQueues in the given Cohort.
This should represent shareable slack, not static limits.

Pending/terminating/stopped ClusterQueues should not be treated as lenders. If state gating is imperfect, the metric can report shareable quota that is not actually borrowable.

**Why is this needed**:

Existing metrics give static limits and usage, but not real-time exportable capacity.
This directly answers: how much can others borrow from this ClusterQueue now.
It aligns with cohort borrowing and fair-sharing behavior better than nominal, lending limit, or usage alone.

**Risks/Open questions**:

1. Ambiguity due to reservation phase:
If we base it on reservation (which is correct for safety), users may think capacity is “missing” while workloads are only quota-reserved, not yet admitted/running. 
If we base it on admitted usage, you risk over-promising shareable capacity.
We must explicitly define whether it is reservation-based or admitted-usage-based.

2. ClusterQueue/Cohort state updates are event-driven and concurrent. The metric can oscillate quickly during bursts, preemption, or admission retries, producing noisy alerts and dashboard confusion.

### Comment by [@mszadkow](https://github.com/mszadkow) — 2026-08-04T12:23:20Z

Considerations:
1. Lendable calculation formula - Use reservation-based (resourceNode.Usage) — the same source the scheduler itself uses for admission. 
Why reservation-based:
* Consistent with how available() and admission decisions work in the scheduler
* Aligns with Kubernetes-wide convention (kube-scheduler, cluster-autoscaler, YARN all use requests/reservations)
* Safe: avoids double-booking during the reservation→admission transition window
* The metric description will explicitly call this out so users understand why capacity may appear consumed before pods are running

```
// What this CQ can lend right now
kueue_cluster_queue_lendable_resources = max(0, min(nominal, lendingLimit) - resourceNode.Usage[fr])
```
```
// Total lendable pool available to any borrower in the cohort
kueue_cohort_lendable_resources  = max(0, cohort.resourceNode.SubtreeQuota[fr] - cohort.resourceNode.Usage[fr])
```
2.  Report 0 for inactive/pending/terminating CQs, delete on CQ removal — consistent with how all other resource metrics behave.
```
active CQ → reports real value
pending/terminating/stopped CQ → reports 0
deleted CQ → series removed entirely
```
The cohort lendable metric should follow the same delete-when-zero pattern as CohortSubtreeQuota and CohortSubtreeResourceReservations.

3. The metric should aggregate only direct children (both CQs and immediate child cohorts treated as nodes), following the same level-scoped pattern as CohortSubtreeQuota.
Why:
 * Consistent with kueue_cluster_queue_lendable_resources — the cohort metric is a direct aggregate of the CQ metrics
 * Avoids double-counting in hierarchical scenarios — sub-cohorts contribute their own separate metric series
 * Each cohort node is independently interpretable without needing to understand the full tree depth
 * Aligns with how CohortSubtreeQuota / CohortSubtreeResourceReservations work — each cohort reports its own level's aggregation

4. Update trigger 
Since the lendable computation is purely additive to existing call sites with no extra lookups, the combination of both triggers makes sense:

Spec-change path — add lendable reporting inside reportResourceMetrics (CQ) and applyCohortMetricPoint (cohort). Zero extra cost — already executing.

Workload-event path — add a call to reportResourceMetrics at the end of updateWorkloadUsage. This is the only new plumbing needed, and it mirrors what reportActiveWorkloads already does in the same function. For cohorts, RecordCohortMetrics is already called from the cohort controller on CQ changes — workload-level cohort updates can piggyback the same path by triggering it from updateWorkloadUsage when the CQ has a parent.

This gives the metric both freshness (updates with every workload change) and correctness (stays in sync with spec changes), at a cost that's negligible since the underlying data is already computed and maintained.
