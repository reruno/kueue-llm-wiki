### Comment by [@apullo777](https://github.com/apullo777) — 2026-06-16T14:48:45Z

Hi @mimowo while working on this, I found that direct removal is blocked by the feature-gate lifecycle tooling:

`MultiKueueAllowInsecureKubeconfigs` is `Deprecated`, but its last spec is not `LockToDefault: true`, so `make verify` rejects removing it.

Would you prefer this PR to do the required intermediate step instead?

* keep the gate recognized;
* set `LockToDefault: true` with default `false`;
* make the secure kubeconfig validation path unconditional, so the insecure path is no longer reachable;
* leave full removal for a follow-up release/PR.

I also noticed that the MultiKueue dev setup still relies on this gate because it generates kubeconfigs with `insecure-skip-tls-verify: true`. Should this PR also update that workflow to generate a CA-based kubeconfig using `certificate-authority-data`, so the documented Kind setup keeps working after the gate is locked?
