With the additional periodic runs after this issue was closed, I think this now looks more like a separate deterministic config break.

At the time, the outer symptom was very similar to a normal kind/bootstrap flake: `wait-control-plane` / ClusterRoleBinding / `connection refused`. But the later repeated failures point to kube-apiserver never starting because the WAS kind config still enables `GangScheduling`, which was removed upstream in kubernetes/kubernetes#139520 and consolidated into `GenericWorkload` per KEP-4671.

Kueue still sets it here:
https://github.com/kubernetes-sigs/kueue/blob/main/hack/testing/e2e-common.sh#L487

kind propagates that gate to the control-plane components, which now fail with `unrecognized feature gate: GangScheduling`.

The timing also matches the upstream change: the last green periodic was Jun 17 00:43 UTC, kubernetes/kubernetes#139520 merged Jun 17 07:03 UTC, and every run since Jun 17 12:18 UTC has failed the same way.

So I think #12338's retry is still the right safeguard for genuinely transient bootstrap failures; it just cannot recover this case because the feature-gate config is deterministically invalid and every attempt fails the same way.

Proposed fix direction: drop `GangScheduling` from the WAS patch and keep `GenericWorkload=true`. I will confirm whether the suite needs any successor gates, such as `CompositePodGroup` / `TopologyAwareWorkloadScheduling`, before sending the PR.
