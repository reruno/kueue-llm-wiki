## Description

**What happened**:

Elastic jobs (with `ElasticJobsViaWorkloadSlices` enabled) admitted to a ResourceFlavor with `nodeLabels` never receive those labels on their pods. The pods keep only the nodeSelector set by the workload owner. If the owner strips the nodepool selector (to let Kueue pick the flavor), pods land on any node matching the accelerator label, including nodes outside the target pool.

The standard path injects nodeLabels via `startJob` -> `RunWithPodSetsInfo` -> `podset.Merge`, which calls `podset.FromAssignment` to collect labels from each assigned flavor. The elastic path bypasses `startJob`. The job is never suspended, so step 7 of `ReconcileGenericJob` skips it. The `ElasticJobUngater` then removes the scheduling gate from pods but never injects nodeLabels or tolerations from the assigned ResourceFlavor.

This is the same class of bug as #10167 (missing tolerations) and #11977 (ungater bypasses quota). The ungater touches pods but does not apply the full PodSetInfo that `podset.Merge` applies on the standard path.

**What you expected to happen**:

Pods admitted to a ResourceFlavor should receive that flavor's `nodeLabels` and `tolerations`, whether the job uses the standard path or the elastic path. The elastic ungater should call `podset.FromAssignment` and merge the result into each pod before removing the scheduling gate.

**How to reproduce it (as minimally and precisely as possible)**:

1. Enable `ElasticJobsViaWorkloadSlices`.
2. Create a ResourceFlavor with two `nodeLabels`: `cloud.google.com/gke-accelerator` and `cloud.google.com/gke-nodepool`.
3. Create a RayCluster with `kueue.x-k8s.io/elastic-job: "true"` and a worker pod template whose `nodeSelector` has only `cloud.google.com/gke-accelerator` (the nodepool label omitted, to let Kueue place it).
4. Submit the RayCluster to a ClusterQueue that uses that flavor, so Kueue admits it.
5. The pods are ungated and scheduled. Their `nodeSelector` lacks the `gke-nodepool` label from the ResourceFlavor. They land on any node pool with the matching accelerator, not just the reserved one.

**Anything else we need to know?**:

- Reproduces on v0.16.9, v0.17.5, and v0.18.1. The `ElasticJobUngater` is unchanged in all three.
- If the client sets the nodepool label on the pod template directly, RayCluster workers are unaffected: the label survives pod creation. The bug bites only when the owner omits the nodepool label and relies on Kueue to inject it.
- Related issues: #10167 (elastic jobs missing tolerations from ResourceFlavor), #11977 (ungater bypasses quota by ungating all pods in the slice chain). Both stem from the ungater doing less than `podset.Merge` does on the standard path.

**Environment**:
- Kubernetes version: GKE 1.33
- Kueue version: v0.16.9 (also confirmed on v0.18.1 source)
- Cloud provider: GKE
- Others: KubeRay v1.6.0, `ElasticJobsViaWorkloadSlices=true`
