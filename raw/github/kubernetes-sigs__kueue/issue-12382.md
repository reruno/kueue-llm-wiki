## Description

<!-- Please only use this template for submitting enhancement requests -->

**What would you like to be added**:

A mechanism which will express dynamic quota orchestration, which manages the quotas in reaction to the available capacity.

**Why is this needed**:

There are features which need some kind of automated quota orchestration:
1. MultiKueue quota aggregation from the worker clusters: https://github.com/kubernetes-sigs/kueue/issues/9988 
2. Node-based quota  (and also probably DRA): https://github.com/kubernetes-sigs/kueue/issues/10270  
3. UberClusterQueues: https://github.com/kubernetes-sigs/kueue/issues/8826 
4. TemporaryQuotaOverrides: https://github.com/kubernetes-sigs/kueue/issues/8654 

I would like to have a consistent API for managing quotas in such cases.

Initial high-level [design doc](https://docs.google.com/document/d/1hNLLHU3vssn1RlxX-iWCusZESiC5UmjiwgTONTpZqh0)

### Comment by [@amy](https://github.com/amy) — 2026-06-23T17:25:55Z

@mimowo Talked to my llm for a bit. If these ring true, maybe add it to the issue description for full context. 

```
The four scenarios

1. MultiKueue aggregation (#9988)
- Enforced quota should be: sum(worker CQ nominal quotas), recomputed whenever any worker changes.
- Why not just spec.nominalQuota: the number is controller-computed and moves on its own as workers come and go. An admin can't hand-maintain it. So a controller needs a place to publish it.
- Source of the number: other Kueue objects on the worker clusters.

2. Node-based / DRA quota (#10270)
- Enforced quota should be: the actual hardware present, discovered live — node counts, or for DRA the device counts from ResourceSlice.Spec.Devices and counter totals from ResourceSlice.Spec.SharedCounters (exactly what Sohan pointed at).
- Why not just spec.nominalQuota: capacity changes continuously with autoscaling, node failures, hardware being added. Admin can't keep retyping it. Controller discovers it from cluster state and publishes it.
- Source of the number: observed infrastructure (Nodes, ResourceSlices).

3. UberClusterQueue / hero workloads (#8826)
- Enforced quota should be: temporarily shrink other CQs below their nominal so a hero workload can grab >50% (recall nominal quota is preemption-protected, which is what normally blocks this), then restore everyone afterward.
- Why not just spec.nominalQuota: the in-force number must differ from the admin's nominal for a window — and the admin's real nominal has to survive so it can be put back.
- Source of the number: a controller orchestrating the hero event.

4. TemporaryQuotaOverrides (#8654)
- Enforced quota should be: a time-bounded adjustment (a burst, a drain, a maintenance window) that expires back to normal.
- Why not just spec.nominalQuota: same as UberQueue — the override is explicitly temporary, and the standing value must survive to be restored.
- Source of the number: whoever/whatever sets the override.
```

### Comment by [@mimowo](https://github.com/mimowo) — 2026-06-23T18:31:20Z

Hi @amy this sounds like a fair summary. Actually, the cases seem to split corresponding to different stages of the process. 

I consider that we have 2 phases:
1. capacity discover [considers 1 and/or 2]
2. capacity distribution (setting quotas) [considers 3 and/or 4]

I'm thinking that we could have something like:

```yaml
dynamicQuotaOrchestrator:
   spec:
      clusterQueueName: // root capacity node, mutually exclusive with cohortName
      cohortName: // root capacity node, mutually exclusive with clusterQueueName
      managedResources:
      - flavorName: flavor1
        resourceName: cpu
      - flavorName: flavor2
        resourceName: gpu
      capacityDiscovery:
      - kueue.x-k8s.io/capacity-discovery-multiKueue
      - kueue.x-k8s.io/capacity-discovery-nodes
     capacityDistribution:
        uberClusterQueue: 
          name: "some-uber-cluster-queue" // indicates the management at this level
          // other potential configuration
        temporaryOverrides:
          override:
          - clusterQueueName: CQ1
            flavorName: flavor1
            resourceName: cpu
            from:  2026-12-23
            until: 2026-12-24
```
This orchestrator would push the results under `CQ,status.quotaOverride` or `Cohort,status.quotaOverride`.

Now, the fields `CQ,status.quotaOverride` or `Cohort,status.quotaOverride` could also be populated by external controllers if someone wants to write an external controller replacing dynamicQuotaOrchestrator. 

For example what I'm less sure about is if the configuraiton for the capacityDiscovery should be inside dynamicQuotaOrchestrator or de-coupled.

Ofc, this is just to illustrate the direction I'm currently thinking about. Publishing the thoughts to collect early feedback

If we come to speak about "capacity distribution", maybe the target ref (CQ / Cohort) should be allowed in multiple occurrences inside that part?

Motivating story: 
"Here's our capacity, defined by nodes / MultiKueue workers / whatever.
Now, let's assign 50% of that capacity to `cq1`, 40% to `cq2`, and 10% to the Cohort above both of them (as shared borrowable quota).
[Plus optionally some story about hero workloads]"

This would most naturally express like

```yaml
capacityDiscovery:
// ...
capacityDistribution:
  targets:
  - clusterQueue: cq1
    percentShare: 50
  - clusterQueue: cq2
    percentShare: 40
  - cohort: cohort1
    percentShare: 10
```

You could say it's over-done; your language could express it as well, just by duplicating `capacityDiscovery` separately for each target.
However, one gain here is that we could validate that the percents add up to <= 100%.

WDYT?

### Comment by [@olekzabl](https://github.com/olekzabl) — 2026-07-03T21:56:31Z

> Is the purpose different from preemption fair sharing weights?

I agree the spirit is similar; however, technically it's not exactly the same.
FS weights play any role only within the _borrowable / lendable buffer_, and are softer in their nature.
(Each CQ will "trend towards" the FS-specified usage, as our docs describe it).

OTOH, the percentages discussed here would apply to CQs' _total quotas_, possibly outside the _borrowable / lendable buffer_.
For an easy example, if nothing is borrowable, `cq1` would be _guaranteed_ to have 50% of total capacity.

---

That said, @mimowo has clarified to me offline how he envisions it: once CapacityDistribution is applied to a Cohort, it would distribute capacity among _all_ vertices in the Cohort/CQ hierarchy, _proportionally_ to the current values of `NominalQuota`.

So, my example [above](https://github.com/kubernetes-sigs/kueue/issues/12382#issuecomment-4784884709) would be expressible simply as

```yaml
spec:
  cohortName: cohort1
  // ...
```

assuming that the `NominalQuota` values of `cq1` / `cq2` / `cohort1` are respectively set to 5X, 4X, X for some positive number X.
(Where the specific value of X is quite irrelevant. The original quotas may be just the source of _proportions_).

---

BTW this example also shows why it's essential in @mimowo 's proposal that DQO does not replace original `NominalQuota` values but places its output somewhere else.
