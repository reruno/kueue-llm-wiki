**What would you like to be added**:

Kueue currently implements its own pod group concept via labels and annotations
(`kueue.x-k8s.io/pod-group-name`, `kueue.x-k8s.io/pod-group-total-count`) to support
gang admission of plain Pods. Kubernetes 1.35/1.36 introduced Workload Aware Scheduling
(WAS), a suite of in-tree feature gates that add first-class `PodGroup` and `Workload`
objects in `scheduling.k8s.io/v1alpha2`, enabling native gang scheduling, workload-aware
preemption, and topology constraints inside kube-scheduler.

This enhancement proposes integrating Kueue with WAS so that:

1. Kueue creates and owns `scheduling.k8s.io/v1alpha2/PodGroup` objects derived from
   its pod group label/annotation concept, rather than relying solely on labels.
2. Pods are annotated with `spec.schedulingGroup.podGroupName` to hand gang placement
   enforcement to kube-scheduler's native Permit phase.
3. Kueue's `constructGroupPodSets()` / roleHash fingerprinting logic is replaced with
   structured role definitions from `Workload.spec.podGroupTemplates`.
4. Kueue-specific pod group labels/annotations are deprecated once `GangScheduling`
   reaches GA and workload integrations are available with gangs.

The integration is proposed in three phases:

**Phase 1** — Kueue creates WAS `PodGroup` objects at admission time and sets
`pod.spec.schedulingGroup.podGroupName`. Kueue's scheduling gate remains the outer
quota gate; kube-scheduler's Permit phase handles inner gang placement.

**Phase 2** — Replace `constructGroupPodSets()` / `constructGroupPodSetsFast()` with
PodGroup-driven PodSet construction, eliminating the roleHash heuristic.

**Phase 3** — Deprecate `kueue.x-k8s.io/pod-group-name`, `pod-group-total-count`, and
`pod-group-fast-admission` once `GangScheduling` is Beta. Provide webhook-based
auto-migration to `spec.schedulingGroup`.

**Why is this needed**:

- Kueue's current label/annotation pod group model is bespoke and duplicates logic
  that is now being standardised in-tree in kube-scheduler.
- WAS provides richer semantics: `disruptionMode: PodGroup` for atomic preemption,
  topology constraints (`schedulingConstraints.topology`), and DRA shared resource
  claims across a pod group — none of which are available in Kueue's current model.
- Aligning with the in-tree standard reduces long-term maintenance burden and makes
  Kueue's pod group behaviour consistent with what kube-scheduler natively understands.

**Challenges and Risks**:

1. **Feature gate dependency**: `GenericWorkload` / `GangScheduling` are Alpha in
   1.35/1.36. A Kueue feature gate (`features.WASPodGroups`) is needed to guard the
   new path for backward compatibility with older clusters.

2. **Cluster version skew**: `spec.schedulingGroup` is silently ignored on clusters
   without `GenericWorkload` enabled, losing the gang guarantee without warning.

3. **Workload object name collision**: WAS `Workload` (`scheduling.k8s.io/v1alpha2`)
   and Kueue `Workload` (`kueue.x-k8s.io/v1beta1`) share the same kind name —
   documentation and code must clearly distinguish the two.

4. **Two-level admission coordination**: Kueue's scheduling gate (quota) and
   kube-scheduler's Permit gate (gang minCount) must be carefully coordinated to
   avoid Kueue considering a workload admitted while the scheduler's Permit phase
   blocks indefinitely.

5. **StatefulSet / LWS controller changes**: Both controllers currently call into
   Kueue's pod group labeling logic and would need updating to create WAS
   `Workload` / `PodGroup` objects.

6. **In-flight LWS WAS integration**: There is existing ongoing work to add WAS
   support directly into LeaderWorkerSet (LWS), which would have LWS create and
   manage its own `PodGroup` objects natively. Kueue must detect when an upstream
   controller has already established gang semantics via WAS and avoid creating
   conflicting `PodGroup` objects or double-managing the scheduling gate. A mechanism
   (e.g. a feature flag, annotation, or ownership check on the `PodGroup`) will be
   needed so Kueue can step back when appropriate. https://github.com/kubernetes-sigs/lws/pull/844

### Comment by [@sohankunkerkar](https://github.com/sohankunkerkar) — 2026-06-23T20:28:22Z

I think the three things in this issue are actually independent enough to track separately.

- For controller-managed workloads, to @kannon92's question about whether Kueue should also have a PodGroup when LWS already does, I'd lean toward no. KEP-6089 [puts](https://github.com/kubernetes/enhancements/blob/master/keps/sig-scheduling/6089-was-controller-apis/README.md#core-principles--assumptions) the Workload object on the root controller, and [lws#844](https://github.com/kubernetes-sigs/lws/pull/844) is already designing one PodGroup per replica with an escape hatch for external owners. IMO, the right model is Kueue consuming those objects to derive scheduling shape rather than creating its own. The harder question is @mimowo's though: how does a Kueue workload with multiple PodSets map onto WAS PodGroups? That needs to be answered before we can design the consuming side cleanly.
- For bare Pods there's no controller above Kueue, so synthesizing WAS objects there might make sense as a separate opt-in path.
- scheduler-library is orthogonal to all of this, it's algorithm reuse for pre-admission feasibility. Doesn't conflict with whatever we decide on WAS object ownership.

I'd also keep the label/annotation model long-term. It's more flexible in some areas and we need a supported path for clusters without WAS gates.
