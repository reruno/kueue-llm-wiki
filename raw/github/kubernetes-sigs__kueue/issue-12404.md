## Description

**What happened**:
Assume this situation:
Manager cluster has two worker cluster, and a job resource will be created on manager cluster and dispatched to each cluster.

- worker-1: there is a job resource with same NamespacedName
- worker-2: empty

In current implementation, remote workload will be dispatched each worker cluster following with [dispatching algorithm](https://kueue.sigs.k8s.io/docs/concepts/multikueue/#workload-dispatching), and the first admitted workload will be selected.

Then, there is a possibility that worker-1 will be selected.
As the same NamespacedName job resource already exists on worker-1, remote job will not be synced by the change introduced in #11877 .
However remote workload will reserve quota and be admitted on worker-1 even though remote job will not be executed.

**What you expected to happen**:
The manager cluster will select worker clusters where the job resource with same NamespacedName does not exist on.

In our use case, some job resources sometimes created on worker cluster directly.
I understand that we can mitigate this issue by adding prefix to job resource based on cluster.
However, it will become difficult to integrate it by increasing the number of workers.
IMO, this condition should be treated appropriately by Kueue itself in the first place.

**How to reproduce it (as minimally and precisely as possible)**:
- Setup [MultiKueue](https://kueue.sigs.k8s.io/docs/tasks/manage/setup_multikueue/), and manager and two worker clusters
- Create a job named `sample-job-a` on worker-1.(call this job `Job(a)`)
- Create a job which has the same name of worker-1's(`sample-job-a`) on manager cluster specifying `kueue.x-k8s.io/queue-name`
- If workload on worker-1 is admitted at first, it will remain as QuotaReserved and Admitted, and syncing remote job will fail

**Anything else we need to know?**:
Follow up issue of [#11877](https://github.com/kubernetes-sigs/kueue/pull/11877#issuecomment-4750401167)

**Environment**:
- Kubernetes version: v1.35.1
- Kueue version: After #11877 merged (may be v0.18.2)

In addition, we may need to consider a TOCTOU issue like the following:

- The manager cluster creates `nominatedWorkers`, avoiding remote workers where the same NamespacedName job resource already exists.
- Before remote workload will be dispatched), the same NamespacedName job resource is created on the worker cluster which has already been selected as `nominatedWorkers`.
- As a result, the remote workload will be dispatched onto the inappropriate worker cluster.
