## Description

Suspected bug, based on my static reading of the code (and initial consulting with AI).
Not observed in practice.

In [`handleElasticWorkload`](https://github.com/kubernetes-sigs/kueue/blob/38c962f6af181667c8a0440733ed0f83d98448f7/pkg/cache/scheduler/tas_elastic_workloads.go#L35):

* In the [scale-up case](https://github.com/kubernetes-sigs/kueue/blob/38c962f6af181667c8a0440733ed0f83d98448f7/pkg/cache/scheduler/tas_elastic_workloads.go#L58), we [do account](https://github.com/kubernetes-sigs/kueue/blob/38c962f6af181667c8a0440733ed0f83d98448f7/pkg/cache/scheduler/tas_elastic_workloads.go#L98-L101) for the leader (if it exists), both in `assumedUsage` and in the returned topology assignment.
* However, in the [scale-down](https://github.com/kubernetes-sigs/kueue/blob/38c962f6af181667c8a0440733ed0f83d98448f7/pkg/cache/scheduler/tas_elastic_workloads.go#L60) and [no-change](https://github.com/kubernetes-sigs/kueue/blob/38c962f6af181667c8a0440733ed0f83d98448f7/pkg/cache/scheduler/tas_elastic_workloads.go#L64) cases, the leader is completely ignored.

This seems to be an omission, potentially leading to:
- getting an unrelated Pod stuck because it was assigned leader's capacity falsely assumed to be free
- getting the leader itself stuck, in case it needed a restart and a new placement (which will be missing)
