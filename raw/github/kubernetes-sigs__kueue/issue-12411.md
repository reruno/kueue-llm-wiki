## Description

<!-- Please only use this template for submitting enhancement requests -->

**What would you like to be added**:

I would like to revisit the OOTB QPS and concurrency for Kueue.

In particular, currently we use QPS=50, Burst=100, which is very constraining for users.

For QPS the load can be rate-limited currently at the API -server layer with P&F.

Similarly, the current concurrency level for workload (5), LQ (1), CQ (1) seems constraining.

I propose:
- QPS: 300, Burst=500
- Workload concurrency: 10, LQ and CQ: 5.

**Why is this needed**:

Currently, the 300 - 500 pods/ second scheduling seems like the standard. However, Kueue becomes a bottleneck when TAS is used, because we need to remove scheduling gate from every pod with TopologyUngater. So, users get only 50 pods / second scheduling rate.

### Comment by [@tenzen-y](https://github.com/tenzen-y) — 2026-06-23T16:00:49Z

I discussed this internally with @mimowo 
Indeed, client-side QPS and Burst control is not the recommended way today. The recommended ways are disabling client-side control (`qps=-1`) and introducing APF to customer clusters. But, I understand that every customer can not introduce APF in their cluster by historical or other political reasons.

So, I agree with increasing QPS and Burst to a large number. If they want to have a more fine-grained API budget mechanism instead of a large fixed client-side API budget control, they should delegate to APF.


Also, I agree with increasing controller concurrencies because the current concurrencies are not realistic parameters in production environments. I believe that almost Kueue users (even in a middle or small cluster) have already increased such controller concurrency parameters.
