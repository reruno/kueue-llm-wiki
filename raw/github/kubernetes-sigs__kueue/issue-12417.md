## Description

**What happened**:
I have a CQ that only manages one type of precious resources (machines with those in the cluster are homogeneous), e.g. GPUs.
I have a topology specified for the flavor used in this CQ.
I tried to create LWS job and deploy it to the queue.

As leader does not require the precious resources I have not specified appropriate request for it.
Workers do require the resource so I have added appropriate entry.

LWS job never got admitted, although nodes with appropriate resources were idle all the time.
My investigation showed that it fails admission because of this condition:
https://github.com/kubernetes-sigs/kueue/blob/release-0.18/pkg/scheduler/flavorassigner/tas_flavorassigner.go#L156

which in combination with recent [fix](https://github.com/kubernetes-sigs/kueue/pull/12055
) results in workload treated as invalid. 

If additional resource exists on the list of resources managed by CQ validation succeeds (e.g. cpu). 
If "0" resources are requested explicitly by the leader podset the validation succeeds.

**What you expected to happen**:
Workload getting properly admitted.

**How to reproduce it (as minimally and precisely as possible)**:

0. Deploy Kueue with LWS integration enabled.
1. Have a cluster queue with TAS enabled flavor and just one resource managed.
2. Create a LWS workload with one of the podsets not requesting the managed resource (for example with empty resource requests).

**Anything else we need to know?**:
Reproduced on different environments v0.17.5 and v0.18.1

**Environment**:
I believe not connected to particular environment as specific line of code and PR that introduce the regression have bin pinned - omitting to minimize the distraction.

### Comment by [@mszadkow](https://github.com/mszadkow) — 2026-06-25T14:20:52Z

There are at least 3 options how to fix the issue:
1. Treat missing as zero in TAS validation
Admits a podset that doesn't request a TAS-managed resource by inferring the flavor from a same-group peer and filling zero-request resources.
Risks: 
A naive "missing = 0" could over-admit by hiding genuinely invalid assignments; the group-scoped variant mitigates this but won't admit standalone non-consuming podsets that have no peer.

2. Special-case non-consuming podsets
Keeps strict validation in general but explicitly allows podsets not expected to consume TAS-managed resources.
Risks: 
"Not expected to consume" is hard to define robustly and tends to grow fragile across future workload types, adding complexity that may still miss legitimate sparse-request patterns.

3. Normalize requests earlier (inject zero quantities)
Builds a normalized request map with all CQ-managed resources defaulted to 0 before TAS validation runs.
Risks: 
Broad behavioral impact that can erase the "unset vs explicit zero" distinction other callers rely on, requiring a careful audit of every consumer of those sparse maps.

I think `option 1` is the way to go.
 - Matches the intended semantics: a non-consuming leader in an LWS-like formation is admitted as expected, instead of being wrongly rejected.
- Group-scoped inference preserves strict validation everywhere else — it only fills flavors when a same-group TAS peer makes the flavor unambiguous.
- No user-facing workaround required
