Lets use this github issue as a high level planning for doc improvements. Feel free to close this whenever if someone wants to own this domain and has a different idea to organize it.

I would prefer for a product manager and a technical writer to pick up this task. Its because our docs read like code instead of the intended human audience. Engineers (myself included) tend to come up with more programatic writing styles that aren't intuitive to end users.

**What would you like to be documented or improved**:
Overall... Kueue documentation is hard for users to parse and reads more programatic than human readable. Areas of the documentation that are confusing:

- In QuickStart, we need basic preemption and queueing scenarios with more than 1 CQ. (Basic borrowing, Basic preemption, basic queueing due to quota saturation)
- Resource Flavors: specific to "Brands and models", provide an example of how to mix flavor types with TAS turned on. Example should include workload taints and tolerations. Brand and Models bc this is mostly what I see people using for resource flavors in training use case. The language for FlavorFungibility can also still be improved. Previously the project has made attempts, but... it still takes some mental gymnastics.
- Preemption Fairsharing: overall... needs a revamp with pictures. The language is very mathy and difficult to parse. For instance, an image that would be helpful is, for preemption fairsharing, your fairshare value is effectively some proportion of the burst capacity at the given scheduling snapshot. 
- Overall, spell out invariances / things that are always true. People encounter unexpected behavior a lot. 
- Should concurrent admission be a section under resourceflavor? 

General doc themes not specific to the above areas:
- Less programmatic language
- More diagrams
- More examples 
- More use cases
