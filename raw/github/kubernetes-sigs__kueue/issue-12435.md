**What happened**:

periodic-kueue-test-e2e-k8s-main-was has failed on every run since Jun 17 ~12:18 UTC.

Job history:
https://prow.k8s.io/job-history/gs/kubernetes-ci-logs/logs/periodic-kueue-test-e2e-k8s-main-was

The kind cluster never finishes bootstrapping. kubeadm waits in wait-control-plane and eventually fails with unable to create ClusterRoleBinding: ... connection refused, because kube-apiserver never starts.

The root cause appears to be that the WAS kind config still enables the removed GangScheduling feature gate:

https://github.com/kubernetes-sigs/kueue/blob/main/hack/testing/e2e-common.sh#L487

That gate was removed upstream in kubernetes/kubernetes#139520 and consolidated into GenericWorkload per KEP-4671. kind propagates the gate to the control-plane components, which now reject it on k8s-main with unrecognized feature gate: GangScheduling.

This is not a transient flake: it fails deterministically on every run and every retry attempt. I am splitting this out from #12307, which tracked a transient bootstrap flake with the same surface symptom.

**What you expected to happen**:

WAS e2e against k8s-main should build the kind cluster successfully and run the suite.

**How to reproduce it (as minimally and precisely as possible)**:

Run the WAS e2e against k8s-main, for example:

WAS_ENABLED=true make test-e2e-k8s-main-was

Or inspect any recent periodic run, for example:
https://prow.k8s.io/view/gs/kubernetes-ci-logs/logs/periodic-kueue-test-e2e-k8s-main-was/2069211073285722112

Each run rebuilds k8s-main, so it picks up the upstream feature-gate removal.

**Anything else we need to know?**:

The timing lines up with the upstream merge:
|Time (UTC) | Build | Result|
|-- | -- | --|
|Jun 17 00:43 | 2067036… | last green|
|Jun 17 07:03 | — | kubernetes/kubernetes#139520 merged|
|Jun 17 12:18 | 2067217… | first red|
|Jun 18–23 | …2069211… | consistently red|

Proposed fix: drop GangScheduling from the WAS patch and keep GenericWorkload=true. I will confirm whether the suite needs any successor gates, such as CompositePodGroup / TopologyAwareWorkloadScheduling, before sending the PR.
