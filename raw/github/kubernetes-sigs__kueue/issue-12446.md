## Description


**What happened**:
We have a working setup with Kueue and a few resource flavours created. We want to route new types of jobs through Kueue and add new resource flavours for them to be admitted to. These resource flavours will match on additional labels to the previously existing resource flavours.

We found that within a single resource group, a workload's required node affinity is filtered against the union of all flavors' label keys, but then matched against each flavor individually. So an affinity term on key K that some other flavor in the group declares will cause a flavor that doesn't declare K to be rejected for a given workload even though K is irrelevant to that flavor. 

This has caused some issues on our end and resulted in a need for a complicated unnecessary workaround to be able to add new resource flavors that have specific labels that don't exist on previously existing resource flavors.

Is there a reason things are this way or can it change to do the comparison per resource flavor's label?

**What you expected to happen**:

We have flavors declaring certain labels and flavors that don't. When a job that has that label declared comes in and is tested for admission against a flavor that doesn't have that label declared, it shouldn't be rejected. Currently it is rejected because the current code builds LabelKeys as the union of labels on all resource flavors here: https://github.com/kubernetes-sigs/kueue/blob/fefb31a40508e4447d509ed77598e1fb15e92e4b/pkg/cache/scheduler/clusterqueue.go#L390

**How to reproduce it**:
Create 2 resource flavours on a resource group. Flavor A declares a label X =a ,  flavor B declares that label X= b and another additional label Y = k.
Create a job that has label X=a, Y=g.
The job will be stuck in pending forever instead of being admitted to flavor A


**Environment**:
- Kubernetes version : v1.33.12-eks-0247562
- Kueue version : v0.17.2
