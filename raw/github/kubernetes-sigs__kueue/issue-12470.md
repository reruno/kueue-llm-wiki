## Description

**What would you like to be added**:

[Concurrent Admission](https://github.com/kubernetes-sigs/kueue/tree/main/keps/8691-concurrent-admission) was added recently, but how it plays with MultiKueue was never verified. While in principle, enabling it on the worker cluster should somewhat work, there are a few rough edges that we need to verify/polish:

1. It probably makes no sense to enable `ConcurrentAdmission` on the manager cluster. This should be documented/validated, as it might yield confusing results. For example, even if the `OwnerReferenceUID` is copied to the worker cluster by the manager, the GC on the worker cluster will remove the copied Workload as the UIDs won't match between the manager and worker. Moreover, it does not make sense to have multiple flavors on the manager cluster, which beats the purpose of `ConcurrentAdmission`.
2. When `MultiKueueOrchestratedPreemption` is enabled we have the following problems:
    a) MultiKueue manager is blind to variant preemption signals, as the relevant condition is not bubbled up from the variants to the parent workload.
    b) The `kueue.x-k8s.io/multikueue` preemption gate is not copied to the variants. It's only set on the owner workload. So in practice, currently `MultiKueueOrchestratedPreemption` is likely a no-op when `ConcurrentAdmission` is enabled on the worker.

**Why is this needed**:

We should properly document the interactions between those two important features. Moreover, it would be good to make sure that this interaction behaves in a way that does not surprise the user.
