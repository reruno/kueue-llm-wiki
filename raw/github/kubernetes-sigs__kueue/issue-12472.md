## Description

<!-- Please only use this template for submitting enhancement requests -->

**What would you like to be added**:

Add a CI on-demand job to verify links on webpage PRs before merging

**Why is this needed**:

We sometimes miss missing links so it would be good to verify them before merging. Currently we only verify after merging. In case of complex PRs like https://github.com/kubernetes-sigs/kueue/pull/12412 it is hard to check them all manually.

One relatively idea is to just point the checker to the preview generated, for example [https://deploy-preview-12412--kubernetes-sigs-kueue.netlify.app/](https://deploy-preview-12412--kubernetes-sigs-kueue.netlify.app/).

### Comment by [@apullo777](https://github.com/apullo777) — 2026-06-24T16:39:38Z

Hi  I looked into this a bit.

My understanding is that the current link check runs as the periodic `periodic-kueue-verify-website-links-main` job in `kubernetes/test-infra`, calling `make verify-website-links` against the production site.

The Kueue-side change would be to make the link checker accept a configurable base URL, so the presubmit job can run it against the PR's Netlify deploy preview.

Before anyone implements this, I think a few details are worth aligning on to avoid a flaky presubmit:

1. Should “on-demand” mean purely manual via `/test`, rather than `always_run` or `run_if_changed`?
2. Should this be optional/non-blocking, since the Netlify preview is external and async?
3. If the preview is not ready or does not exist, should the job retry for a bounded time and then skip/pass instead of failing?

If this direction sounds right, I may be able to help move this forward :)

### Comment by [@mimowo](https://github.com/mimowo) — 2026-06-24T16:50:22Z

Yeah, the main problem is that the preview may not exist yet for new PRs. Or it may exist but still be stale. This is why I thought we could start by on-demand only. The makefile goal would read the comment with the preview link with GH API and execute the checks on the preview.

If this is to run on every PR then we need to be careful so that this is not confusing. For that we may need to wait for the preview and ensure it is generated based on the same commit. If the preview does not show up then we probably accept (success), because not every PR needs to ganerate the preview (IIRC). 

So, because of that complications I thought it makes sense to start with on-demand. We could add a comment to the makefile goal
about the limitations of the system. I think it would still be useful.

### Comment by [@apullo777](https://github.com/apullo777) — 2026-06-24T17:14:46Z

Thanks @mimowo, that makes sense. I agree the stale-preview case is the key issue here.

Given that, I’ll start with the on-demand approach as you suggested. We can keep the `always_run` idea as a possible follow-up once the fresh preview for the PR head commit check is reliable.

Proposed first step:

* add an on-demand, optional/non-blocking presubmit;
* add a preview-oriented Makefile target with a comment documenting the limitations;
* in preview mode, skip/pass quickly if the PR does not touch `site/`;
* otherwise, resolve a deploy preview for the PR head commit, wait for it with a bounded timeout, and skip/pass if no matching preview is available;
* once a matching preview is found, run the link checker against it. Actual broken-link failures should still fail the optional job.

For resolving the preview URL, I will first check if the Netlify commit status on the PR head SHA gives us the exact deploy preview URL. If that is not reliable, I will use the comment-based approach you suggested and document the limitation.
