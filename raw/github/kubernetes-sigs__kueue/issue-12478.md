## Description

**What would you like to be added**:
For GB series GPUs (GB200, GB300, etc), we want certain jobs to have `kueue.x-k8s.io/podset-slice-required-topology` set to the rack label and `kueue.x-k8s.io/podset-slice-size` to the number of available nodes on each rack to ensure maximum training efficiency. The TAS scheduler won't consider preempting jobs from other cluster queues/cohorts if they are within the guaranteed quota. We want certain important jobs to have the ability to force themselves onto the desired topology and place the jobs in their way onto other racks. The important jobs can only evict other jobs to other racks if it is within the guaranteed quota (it can preempt jobs within the same CQ given they have lower priority).


To achieve the desired behaviour, we could add a new annotation `kueue.x-k8s.io/podset-force-required-topology` on top of the existing APIs (see [link](https://kueue.sigs.k8s.io/docs/concepts/topology_aware_scheduling/#user-facing-apis). The algorithm will consider preemption candidates in the order of first to last:
1. workloads with lower priority in the same cluster queue
1. workloads with lower priority in the same cohort
1. workloads which are borrowing
1. workloads from other CQ/cohorts with lower priority

The cluster we use has fair sharing and a hierarchical cohort enabled.

I am not tied to a specific implementation, so any suggestion is much appreciated.

**Why is this needed**:
When having a job using a large number of GPUs, the speed is largely limited by the smallest number of nodes on a rack. This is also in parity with Slurm's --segment.

### Comment by [@shaq918](https://github.com/shaq918) — 2026-07-26T07:26:28Z

I work with large GPU training clusters where this exact problem (clearing a full rack/NVLink domain for a high-priority job) comes up regularly, and I'd like to drive this feature. I've gone through the TAS + preemption code and want to propose a design direction that hopefully addresses @Huang-Wei's concern about workload-annotation-shaped APIs.

### Where the gap lives in code

Categories 1–3 from the issue exist today via `ClusterQueue.spec.preemption` (`withinClusterQueue`, `reclaimWithinCohort`/`borrowWithinCohort`). The two missing pieces are enforced in the classical preemption path:

- Within-nominal CQs/cohort subtrees are pruned from candidate collection (`hierarchical_preemption.go` skips `IsWithinNominalInResources` subtrees and CQs), and `candidateIsValid` re-drops cross-CQ candidates once their CQ path is within nominal.
- Cross-CQ policy only exists as *reclaim* (`classifyPreemptionVariant` → `ReclaimWithinCohort`), so there is no policy that can reach lower-priority workloads in non-exceeding CQs.

Notably, the flavorassigner's second pass (`WithSimulateEmpty`) already marks these workloads `Preempt` — it promises a preemptibility that the preemption phase can't deliver, so the workload just stays pending. The trial-removal machinery (`workloadFits` re-running full TAS placement per removed candidate) needs no structural change for phase 1.

### Proposed API: CQ-level authority + per-PodSet opt-in

Rather than a pure workload annotation, pair two knobs where **the ClusterQueue policy is the sole authority**:

1. **Admin-side** — extend `ClusterQueue.spec.preemption` with an advanced knob (naming TBD):

```yaml
preemption:
  forcedTopologyPreemption:
    policy: LowerPriority        # Never (default) | LowerPriority
    minPriorityThreshold: 1000   # only preemptors at/above this priority may force
```

Semantics: workloads admitted to this CQ that carry a required-topology request and the per-PodSet opt-in may preempt **strictly lower-priority** workloads in other CQs of the cohort **even when those CQs are within nominal quota** — provided the preemptor itself stays within its own nominal quota (the helper for that check already exists).

2. **User-side** — `kueue.x-k8s.io/podset-force-required-topology` mapping to a `forceRequired` field on `PodSetTopologyRequest`, valid only alongside `required`. The annotation alone grants nothing; without the CQ knob it's inert. This keeps tenant escalation impossible (annotations are user-settable, the CQ policy is admin-owned) while still letting only the jobs that need force-fit pay its disruption cost.

Feature gate: `TASForcedTopologyPreemption`, alpha default-off, classical preemption only (FairSharing excluded in alpha — its candidate path is separate and gated on `cqIsBorrowing`; the `FairSharingPreemptWithinNominal` precedent suggests how to extend it later).

### Algorithm (phase 1)

Add a fourth candidate class ("forced topology") in the candidate generator: collected without the within-nominal pruning, restricted to strictly-lower-priority victims that use the flavor-resources needing preemption, and ordered **after** the existing hierarchy/priority/same-queue classes — so the issue's candidate ordering falls out of the existing iterator concatenation. `workloadFits` already validates that removing the chosen victims actually frees a conforming domain. New preemption variant/reason for observability. Strict lower-priority requirement prevents A↔B force-fit loops.

Phase 2 (separate discussion, overlaps with the defragmentation roadmap): topology-targeted victim selection — rank required-level domains by cost-to-clear using the per-workload per-domain usage already tracked in the TAS flavor cache, instead of global-priority trial removal.

### Open questions before I write this up as a KEP

1. Does the CQ-knob + inert-podset-opt-in pairing address the "advanced preemption knobs, not workload annotation" concern — or would you prefer no per-workload opt-in at all?
2. Scope: candidates only within the preemptor's cohort tree (recommend yes — cross-root preemption has no quota relationship; UberCQ exists to create one)?
3. Is eviction+requeue acceptable as the "move victims to other racks" mechanism (best-effort), or is stronger re-admission ordering for victims expected?
4. Standalone KEP referencing KEP-2724, or folded into the upcoming defragmentation work mimowo mentioned?

If this direction sounds right I'm happy to write the KEP and take the implementation. I have access to multi-rack A100/H100 IB clusters for realistic testing (topology-labeled nodes, rack-scale domains), and GB200-shaped topologies are easy to model in integration tests with fake nodes.
