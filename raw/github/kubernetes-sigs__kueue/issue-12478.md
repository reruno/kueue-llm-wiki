## Description

**What would you like to be added**:
For GB series GPUs (GB200, GB300, etc), we want certain jobs to have `kueue.x-k8s.io/podset-slice-required-topology` set to the rack label and `kueue.x-k8s.io/podset-slice-size` to the number of available nodes on each rack to ensure maximum training efficiency. The TAS scheduler won't consider preempting jobs from other cluster queues/cohorts if they are within the guaranteed quota. We want certain important jobs to have the ability to force themselves onto the desired topology and place the jobs in their way onto other racks. The important jobs can only evict other jobs to other racks if it is within the guaranteed quota (it can preempt jobs within the same CQ given they have lower priority).


To achieve the desired behaviour, we could add a new annotation `kueue.x-k8s.io/podset-force-required-topology` on top of the existing APIs (see [link](https://kueue.sigs.k8s.io/docs/concepts/topology_aware_scheduling/#user-facing-apis). The algorithm will consider preemption candidates in the order of first to last:
1. workloads with lower priority in the same cluster queue
1. workloads with lower priority in the same cohort
1. workloads which are borrowing
1. workloads from other CQ/cohorts with lower priority

The cluster we use has fair sharing and a hierarchical cohort enabled.

I am not tied to a specific implementation, so any suggestion is much appreciated.

**Why is this needed**:
When having a job using a large number of GPUs, the speed is largely limited by the smallest number of nodes on a rack. This is also in parity with Slurm's --segment.
