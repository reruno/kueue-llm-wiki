# Design: NetworkPolicies for Kueue

Implementation is up in https://github.com/kubernetes-sigs/kueue/pull/14142.

## Summary

Ship NetworkPolicies for the Kueue components through both Helm and Kustomize, restricting ingress to the ports each component actually serves. Egress restriction is a separate opt-in because it interacts with MultiKueue.

## Motivation

Kueue ships no NetworkPolicy today. There is no `networking.k8s.io/v1` NetworkPolicy anywhere in `config/` or `charts/`, so every Kueue pod is reachable on every port from every pod in the cluster.

Kueue is a privileged controller with broad watch permissions that also sits in the admission path, so limiting its reachable surface is worthwhile defense in depth. This is OWASP Kubernetes Top Ten 2025 K05.

### Goals

- Ship policies through both install paths, from one source, so they can't drift.
- Restrict ingress to the ports each component serves.
- Give operators a way to narrow rules to specific peers.
- Don't break anything on upgrade.

### Non-Goals

- Restricting traffic between the workloads Kueue schedules. Kueue doesn't own those pods.
- Solving egress for MultiKueue's dynamic destinations.
- Segmentation for `hostNetwork` deployments, which NetworkPolicy can't do.
- Adding a policy-enforcing CNI to CI.

## Traffic map

From `apis/config/v1beta2/defaults.go:36-54` and the manager Deployment:

| Component | Port | Purpose | Initiated by |
| --- | --- | --- | --- |
| ControllerManager | 9443 | Admission webhooks | kube-apiserver |
| ControllerManager | 8082 | Aggregated visibility API | kube-apiserver aggregator |
| ControllerManager | 8443 | Metrics | Prometheus |
| ControllerManager | 8081 | Health/readiness probes | kubelet |
| ControllerManager | 8083 | pprof, off by default | operator, via port-forward |
| KueueViz backend | 8080 | Dashboard API and websocket | ingress controller |
| KueueViz frontend | 8080 | Dashboard assets | ingress controller |

Two things here shaped the design.

The peers can't be expressed as selectors. The apiserver and the kubelet normally run on the host network, and the metrics scraper and ingress controller live wherever the operator put them.

The KueueViz frontend never dials the backend. The websocket URL is baked into a ConfigMap pointing at the backend's Ingress host (`charts/kueue/templates/kueueviz/frontend-configmap.yaml`), so the path is browser → ingress controller → backend. A frontend-to-backend pod rule would have been wrong.

Note also that 8081 is a real listener but isn't in the container's `ports:` list, so it has to be allowed explicitly or the pods go NotReady.

## Design

Policies are authored under `config/components/networkpolicy/` and the Helm templates are generated from them by the existing yaml-processor pipeline (`hack/processing-plan.yaml`, `make update-helm`). Kustomize users opt in through a thin `config/networkpolicy` overlay, the same way prometheus and visibility-apf are handled. Helm users set `networkPolicy.enabled=true`.

Each policy denies by default and allows only the ports above, from any source. Operators who want real peer restriction append rules through `networkPolicy.extraIngress`, for example limiting 8443 to a monitoring namespace.

```yaml
networkPolicy:
  enabled: false
  extraIngress: []
  egress:
    enabled: false
    extraEgress: []
```

The manager policy selects on `control-plane: controller-manager`. The KueueViz policies select on `app: kueueviz-backend` and `app: kueueviz-frontend`, since those pods carry no `app.kubernetes.io/*` labels.

## Risks

**MultiKueue and egress.** MultiKueue is Beta and default-on, and dials remote cluster API servers whose addresses come from Secrets and ClusterProfiles at runtime (`pkg/controller/admissionchecks/multikueue/multikueuecluster.go`). Validation constrains the auth mechanism but not the destination address, so the chart can't enumerate egress destinations. Egress is therefore a separate opt-in; when enabled it allows DNS plus 443/6443 to any address, and the limitation is documented rather than hidden.

**hostNetwork makes policies a no-op.** Most CNI plugins don't apply NetworkPolicy to host-network pods. Rather than render something ineffective, combining `networkPolicy.enabled` with `controllerManager.hostNetwork` fails the render with an explanation.

**CI can't catch a wrong rule.** kind's default CNI doesn't enforce NetworkPolicy, so every existing e2e lane stays green whether or not these policies are correct. I checked enforcement by hand against `kube-network-policies` — with the manager policy applied, 8443 connects, 9999 is blocked, and 9999 on a pod without the selector label still connects, which rules out a general network fault. The dataplane logged `"Pod is not allowed to be connected on port" src-port=9999`. A policy-enforcing e2e lane would be worth adding, but it felt like too much for this PR. Happy to file a follow-up.

## Test plan

helm-unittest in `charts/kueue/tests/networkpolicy_test.yaml`: gating in both directions for each toggle, the exact port allowlist, the extra-rule append behaviour, the pod selectors, and the hostNetwork failure. A `--set networkPolicy.enabled=true --set networkPolicy.egress.enabled=true --set enableKueueViz=true` line in `_helm_verify_recipe`.

Enforcement, which CI can't cover, verified by hand as described above.

## Alternatives considered

Hand-writing the chart templates and maintaining the Kustomize copies separately. There's precedent, since `manager.yaml` is maintained in both trees, and it would allow richer per-rule templating. Rejected because Helm/Kustomize parity is the point of this issue and generation enforces it mechanically.

Defaulting peer restriction to node and control-plane CIDRs. Rejected because those vary per cluster and a wrong guess breaks admission.

A single toggle for ingress and egress together. Rejected because it forces every MultiKueue user to override CIDRs or lose the feature.

A namespace-wide default-deny in `kueue-system`. Rejected because it would also govern components Kueue doesn't own that operators may have installed there.

## Open question: should these be on by default?

The issue says policies should be deployed by default. I've made them opt-in (`networkPolicy.enabled: false`) and I want to be upfront about why rather than have it slip past review.

The manager's webhook is reached by the kube-apiserver. On most distributions the apiserver runs on the host network, so its traffic arrives with a node IP and matches no pod or namespace selector. There is no way for the chart to know the right `ipBlock` for a given cluster. If that rule is wrong on a cluster running Calico or Cilium, the webhook becomes unreachable and every Job creation in the cluster starts failing — on upgrade, without the admin having asked for anything.

That is also why the rules are scoped by port instead of by peer. Port scoping still closes every other port and all lateral access, and it can't be wrong in a way that breaks admission.

So either:

1. Land it opt-in now, let it soak a release, then flip the default with an ACTION REQUIRED note.
2. Flip it to default-on in this PR. It's a one-line values change, and I'm happy to do it if you'd rather take the risk in one step.

Given CI can't catch a wrong rule, I'd lean towards the first, but it's your call.
