## Description

**What would you like to be cleaned**:

While reviewing a recent bugfix #12436, I had impression that the code overall might benefit from some de-duping (which would be no-op, or close to no-op, hence out of scope of that bugfix).

Specific ideas:

1. [infeasible?] `addAssumedUsage` is currently called in a few places, while _essentially_ it seems maybe it could be called just in one place, once we know the result of an iteration of [this](https://github.com/kubernetes-sigs/kueue/blob/8b18b7ec3d9c8a9dc4c3079eed2c333ae662263c/pkg/cache/scheduler/tas_flavor_snapshot.go#L588) `for` loop.
   * Caveat, though: error handling like [here](https://github.com/kubernetes-sigs/kueue/blob/8b18b7ec3d9c8a9dc4c3079eed2c333ae662263c/pkg/cache/scheduler/tas_flavor_snapshot.go#L616) could make that not entirely true. So this requires careful double-checking).
   * EDIT: I'm now seeing it's more tricky. In `handleScaleUp`, [here](https://github.com/kubernetes-sigs/kueue/blob/63a0db725d2d341e306285adf3c9afd51a10c938/pkg/cache/scheduler/tas_elastic_workloads.go#L82-L85), we only want to compute placement for the delta ("new Pods"), thus need to first `addAssumedUsage` for the old ones, then for the new ones.
   So this probably defeats the idea of commonizing.

2. While #12436 introduced `finalizeElasticAssignment` for handling scale-down and no-change cases, couldn't it be also reused for scale-ups?
   (Just like in point "1" above - it seems it _essentially_ could, but error handling cases require special attention).

**Why is this needed**:

To clean the code from an unnecessary layer of mental complexity.
