## Description

_Note: This issue was initially flagged by an automated AI security scan and has been manually triaged by a human_

### Impact
Critically breaks the Elastic Scale-Up feature for AI/ML workloads (like RayClusters) that use TopologyAwareScheduling. Because the leader's TopologyAssignment is arbitrarily modified during a worker scale-up, the job controller will terminate and restart the running leader/head pod, destroying the cluster's state and aborting any running jobs. Additionally, double-subtracting capacity in the scheduler can cause valid scale-up requests to be rejected due to artificial capacity exhaustion.

### Data Flow
- **pkg/cache/scheduler/tas_flavor_snapshot.go:567**: When an elastic workload (e.g. RayCluster) scales up, `handleElasticWorkload` is called with both `workers` and `leader` PodSet requests.
- **pkg/cache/scheduler/tas_elastic_workloads.go:43**: `handleElasticWorkload` delegates to `handleScaleUp` because `workers.Count > previousCount`.
- **pkg/cache/scheduler/tas_elastic_workloads.go:94**: `handleScaleUp` passes the `leader` to `findTopologyAssignment` to ensure delta workers are co-located with the leader.
- **pkg/cache/scheduler/tas_flavor_snapshot.go:823**: `findTopologyAssignment` completely ignores the leader's `PreviousAssignment` and calculates a new placement for 1 leader pod.
- **pkg/cache/scheduler/tas_elastic_workloads.go:105**: `handleScaleUp` unconditionally overwrites the leader's `TopologyAssignment` with this newly calculated placement, causing the Workload's admission to update with a new NodeAffinity for the running head/leader pod.

### Reproduction
**Preconditions**: 1. Kueue running with feature gates `TopologyAwareScheduling`, `ElasticJobsViaWorkloadSlices`, and `ElasticJobsViaWorkloadSlicesWithTAS` enabled.
2. A RayCluster or a Workload with two PodSets (head/leader and workers) admitted and running under a TAS-enabled ClusterQueue.
**Steps**:
1. 1. Submit a RayCluster that requests TAS (TopologyAwareScheduling) with 1 head pod and 2 worker pods.
2. 2. Wait for the Workload to be admitted and the pods to start running. Note the NodeAffinity/TopologyAssignment of the head pod.
3. 3. Scale up the RayCluster by increasing the number of workers to 4.
4. 4. Kueue's scheduler evaluates the scale-up and invokes `handleScaleUp`.
5. 5. Observe that the Workload's `PodSetAssignments` for the head pod gets updated with a newly calculated `TopologyAssignment`, which likely points to a different node.

### Vulnerable Code
```
	if leader != nil {
		result[leader.PodSet.Name] = tasPodSetAssignmentResult{TopologyAssignment: deltaAssignments[leader.PodSet.Name]}
		addAssumedUsage(assumedUsage, deltaAssignments[leader.PodSet.Name], leader)
	}
```

### Remediation
Preserve the leader's existing TopologyAssignment during scale-up instead of overwriting it with a new placement.

Suggested Fix:
```
In `handleScaleUp`, if the leader has a previous assignment, merge it or keep it intact instead of directly applying `deltaAssignments[leader.PodSet.Name]`. Alternatively, avoid calculating a new placement for the leader entirely and only enforce co-location constraints for the delta workers.
```
