## Description

_Note: This issue was initially flagged by an automated AI security scan and has been manually triaged by a human_

### Impact
A low-privileged user or tenant who is only authorized to read visibility metrics and submit standard batch workloads can intentionally trigger a data race. This leads to a persistent DoS (Denial of Service) via continuous controller panics, disrupting batch scheduling for the entire Kubernetes cluster.

### Data Flow
- **pkg/cache/queue/manager.go:793**: The PendingWorkloadsInfo method calls cq.Snapshot() WITHOUT holding Manager's Lock() or ClusterQueue's rwm.Lock() during the sorting phase.
- **pkg/cache/queue/cluster_queue.go:375**: ClusterQueue.Snapshot() calls snapshotSort(elements) without any locks.
- **pkg/cache/queue/cluster_queue.go:763**: The sorting function baseCompareFunc reads the multi-word string field c.sw.workloadName via the matches() method.
- **pkg/cache/queue/cluster_queue.go:738**: Concurrently, a scheduler preemption triggers RequeueIfNotPresent (holding Manager's Lock, but NOT ClusterQueue's rwm.Lock), which performs an unsynchronized write to the multi-word string c.sw.workloadName.

### Reproduction
**Preconditions**:
1. Kueue must be deployed with a BestEffortFIFO ClusterQueue and the Visibility API enabled.
2. The attacker needs permissions to create/delete jobs/workloads and view the pending workloads via the Visibility API.

**Steps**:
1. Start a background script that repeatedly queries the Visibility API: `watch -n 0.1 kubectl get --raw /apis/visibility.kueue.x-k8s.io/v1beta2/clusterqueues/<cq-name>/pendingworkloads`
2. Create a low-priority workload that fully consumes the ClusterQueue's quota.
3. Create a high-priority workload targeting the same ClusterQueue.
4. The scheduler will trigger a preemption, causing `RequeueIfNotPresent` to be called with `RequeueReasonPendingPreemption`.
5. The concurrent read/write to the `c.sw.workloadName` string field will trigger a data race (torn read), crashing the controller.

### Vulnerable Code
```
c.sw.set(workload.Key(wInfo.Obj))
```

### Remediation
Synchronize access to the `stickyWorkload` string field by protecting it with `ClusterQueue`'s `rwm` lock during both reads and writes.

Suggested Fix:
```
Modify `RequeueIfNotPresent` to hold `c.rwm.Lock()` before modifying `c.sw`. Update `Snapshot()` so that `c.snapshotSort` is called while holding `c.rwm.RLock()`, or precompute the `stickyWorkload` matches inside `totalElements` so the sorting function operates on a safe, immutable snapshot.
```
