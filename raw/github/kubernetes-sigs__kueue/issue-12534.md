## Description

_Note: This issue was initially flagged by an automated AI security scan and has been manually triaged by a human_

### Impact
When the visibility API is accessed, the controller attempts to generate a snapshot. The invalid sorting function causes a runtime panic, which blocks workload visibility and could disrupt internal scheduling if invoked elsewhere, leading to Denial of Service.

### Data Flow
- **pkg/cache/queue/cluster_queue.go:616**: The function `buildSnapshotSort` creates a custom sort function for fair-sharing that relies on a `usageCache` map.
- **pkg/cache/queue/cluster_queue.go:672**: Not all LocalQueues are added to `usageCache` (e.g., if `afsConsumedResources.Peek(lqKey)` returns nil or `getLQWeight(lqKey)` fails).
- **pkg/cache/queue/cluster_queue.go:680**: If one item is in the cache but the other is not, the code falls back to `baseCmp(a, b)`.
- **pkg/cache/queue/cluster_queue.go:675**: This fallback conditionally violates the strict weak ordering requirement (transitivity). For elements A, B in the cache where A < B, and element C outside the cache, it's possible to create a cycle where A < B, B < C, and C < A. Go's `slices.SortFunc` detects this cycle and panics, crashing the Kueue controller.

### Reproduction
**Preconditions**: Fair sharing must be enabled. The Kueue controller must be managing workloads.
**Steps**:
1. Create LocalQueue A and submit a high-priority workload to establish a usage value (e.g. usage = 20).
2. Create LocalQueue B and submit a low-priority workload to establish a lower usage value (e.g. usage = 10).
3. Create LocalQueue C and submit a medium-priority workload, but ensure the queue has NO consumed resources (so it is omitted from `usageCache`).
4. When `ClusterQueue.Snapshot()` is called (e.g., via the visibility API `PendingWorkloadsInfo`), the `slices.SortFunc` attempts to sort the workloads from A, B, and C.
5. The non-transitive relationship triggers the runtime `panic("slices.SortFunc: comparison function is not a strict weak ordering")`.

### Vulnerable Code
```
if okA && okB {
        if cmpResult := cmp.Compare(usageA, usageB); cmpResult != 0 {
                return cmpResult
        }
}
return baseCmp(a, b)
```

### Remediation
Ensure the comparison function implements a consistent strict weak ordering by explicitly handling the presence and absence of elements in the `usageCache`.

Suggested Fix:
```
if okA && okB {
    if cmpResult := cmp.Compare(usageA, usageB); cmpResult != 0 {
        return cmpResult
    }
}
// Give precedence to items missing from the cache, or treat them as having 0 usage.
if okA && !okB {
    return 1 // or -1 based on desired ordering
}
if !okA && okB {
    return -1 // or 1 based on desired ordering
}
return baseCmp(a, b)
```
