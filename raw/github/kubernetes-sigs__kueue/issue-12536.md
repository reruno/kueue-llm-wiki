## Description

_Note: This issue was initially flagged by an automated AI security scan and has been manually triaged by a human_

### Impact
An unauthenticated attacker can crash the KueueViz backend (Denial of Service via OOM) by overflowing the unbounded cache map. Concurrently, the attacker can overwhelm the Kubernetes API server with `TokenReview` requests, degrading cluster-wide control plane performance.

### Data Flow
- **cmd/kueueviz/backend/middleware/auth.go:85**: An arbitrary 'token' is extracted from the user's Authorization header.
- **cmd/kueueviz/backend/middleware/auth.go:91**: The token is hashed and used as a cache key.
- **cmd/kueueviz/backend/middleware/auth.go:104**: If the token is not cached, reviewToken() synchronously invokes the Kubernetes API server.
- **cmd/kueueviz/backend/middleware/auth.go:114**: The result is stored in an unbounded map (tokenReviewCache), causing memory exhaustion over time.

### Reproduction
**Preconditions**: KueueViz backend is running with `KUEUEVIZ_AUTH_MODE=TokenReview` enabled.
**Steps**:
1. Send a high volume of HTTP requests to a KueueViz API endpoint.
2. For each request, provide a unique, randomly generated bearer token in the `Authorization` header.
3. Observe the memory usage of the KueueViz backend container increase rapidly. Simultaneously, observe high CPU/memory utilization on the Kubernetes API Server due to the flood of `TokenReview` requests.

### Vulnerable Code
```
		a.cache.Set(key, cacheEntry{
			authenticated: authenticated,
			username:      username,
			expiresAt:     now.Add(ttl),
		})
```

### Remediation
Implement an upper bound on the cache size and rate-limit authentication failures.

Suggested Fix:
```
Replace the unbounded `map[string]cacheEntry` in `tokenReviewCache` with an LRU cache (e.g., using `golang-lru`) with a fixed maximum capacity. Additionally, implement rate limiting on the `/auth` middleware for unknown tokens to prevent flooding the Kubernetes API Server with `TokenReview` requests.
```
