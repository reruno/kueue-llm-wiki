## Description

_Note: This issue was initially flagged by an automated AI security scan and has been manually triaged by a human_

### Impact
A malicious tenant can exploit this bug to bypass preemption capacity checks and forcefully evict innocent workloads belonging to other tenants in the same Cohort, causing an availability denial of service. The malicious scale-up workload does not even need to be successfully admitted to trigger the unwarranted evictions.

### Data Flow
- **pkg/scheduler/scheduler.go:241**: The old workload slice is added to `preemptionTargets` via `workloadslicing.ReplacedWorkloadSlice`.
- **pkg/scheduler/scheduler.go:252**: `s.preemptor.GetTargets` considers the old workload slice as a preemption candidate and may return it inside `faPreemptionTargets`.
- **pkg/scheduler/scheduler.go:254**: `faPreemptionTargets` is directly appended to `preemptionTargets`, causing the old workload slice to appear twice in the returned slice.
- **pkg/scheduler/scheduler.go:578**: In `fits()`, `newTargets` (which contains the duplicated targets) is iteratively appended to the `workloads` slice.
- **pkg/scheduler/scheduler.go:581**: `snapshot.SimulateWorkloadRemoval(workloads)` is called, iterating over `workloads` and subtracting the usage of the duplicated workload twice from the ClusterQueue snapshot, artificially inflating available capacity.

### Reproduction
**Preconditions**: Kueue controller must be running with `ElasticJobsViaWorkloadSlices` feature enabled.
**Steps**:
1. Create a ClusterQueue and Cohort with a strict maximum resource limit (e.g., 10 CPUs total).
2. Submit 'Workload A' requesting 5 CPUs and 'Workload B' requesting 5 CPUs. Wait for both to be admitted.
3. Submit a scale-up slice 'Workload A2' that targets 'Workload A' for replacement, but requests 15 CPUs (a delta of 10 CPUs).
4. The scheduler evaluates A2. It sees a 10 CPU delta. It evaluates preemption targets and selects both A (5 CPUs) and B (5 CPUs) to satisfy the 10 CPU delta.
5. The targets slice returned will contain `[A, A, B]` due to the un-deduplicated slice append.
6. The `fits()` capacity check simulates removing the targets. It subtracts A's usage TWICE (10 CPUs) and B's usage ONCE (5 CPUs), summing to 15 phantom freed CPUs.
7. The capacity check incorrectly succeeds (15 phantom free CPUs > 10 CPU delta), and Workload B is forcefully preempted (evicted).

### Vulnerable Code
```
return fullAssignment, append(preemptionTargets, faPreemptionTargets...)
```

### Remediation
Deduplicate preemption targets before returning them from `getInitialAssignments`, or modify `SimulateWorkloadRemoval()` to ensure each workload's usage is only removed once.

Suggested Fix:
```
Modify `getInitialAssignments` in `pkg/scheduler/scheduler.go` to filter out targets that already exist:

```go
		if arm == flavorassigner.Preempt {
			faPreemptionTargets := s.preemptor.GetTargets(log, *wl, fullAssignment, snap)
			if len(faPreemptionTargets) > 0 {
				for _, target := range faPreemptionTargets {
					alreadyAdded := false
					for _, existing := range preemptionTargets {
						if workload.Key(existing.WorkloadInfo.Obj) == workload.Key(target.WorkloadInfo.Obj) {
							alreadyAdded = true
							break
						}
					}
					if !alreadyAdded {
						preemptionTargets = append(preemptionTargets, target)
					}
				}
				return fullAssignment, preemptionTargets
			}
		}
```
