## Description

_Note: This issue was initially flagged by an automated AI security scan and has been manually triaged by a human_

### Impact
A malicious or misconfigured tenant can submit an external framework custom job with an invalid ownerReference. This causes the multikueue worker adapter to enter a rapid, infinite Create-Delete-Reconcile loop. This severely degrades the performance of the local Kueue controller and the remote API server, leading to a Denial of Service (DoS) for all multikueue operations.

### Data Flow
- **pkg/controller/admissionchecks/multikueue/externalframeworks/adapter.go:63**: Local custom job containing an untrusted ownerReference is fetched into localObj
- **pkg/controller/admissionchecks/multikueue/externalframeworks/adapter.go:77**: localObj is deep copied into remoteObj, retaining the malicious ownerReference and local UID
- **pkg/controller/admissionchecks/multikueue/externalframeworks/adapter.go:78**: Only ResourceVersion is cleared. The ownerReferences and other sensitive metadata fields remain intact
- **pkg/controller/admissionchecks/multikueue/externalframeworks/adapter.go:90**: remoteClient.Create is called, pushing the object to the remote cluster where its garbage collector will immediately delete it due to the invalid ownerReference

### Reproduction
**Preconditions**:
1. MultiKueue is configured with `MultiKueueAdaptersForCustomJobs` enabled.
2. At least one external framework custom job CRD is configured.
3. A remote worker cluster is linked.

**Steps**:
1. Create an external framework Custom Job with an `ownerReferences` block pointing to a random, non-existent UID.
2. Submit the custom job to a LocalQueue managed by Kueue.
3. Observe the logs of the Kueue controller manager. It will be stuck in a rapid, infinite loop constantly logging 'Creating remote object'.

### Vulnerable Code
```
	// Create a copy of the local object for the remote cluster
	remoteObj := localObj.DeepCopy()
	remoteObj.SetResourceVersion("")
```

### Remediation
When duplicating the local unstructured object for the remote cluster, explicitly strip `metadata.ownerReferences`, `metadata.uid`, `metadata.finalizers`, `metadata.managedFields`, and the `status` block. This mirrors the safe behavior of `api.CloneObjectMetaForCreation` used by built-in job adapters.

Suggested Fix:
```
	// Create a copy of the local object for the remote cluster
	remoteObj := localObj.DeepCopy()
	
	// Strip fields that shouldn't be copied to the remote cluster
	unstructured.RemoveNestedField(remoteObj.Object, "metadata", "resourceVersion")
	unstructured.RemoveNestedField(remoteObj.Object, "metadata", "uid")
	unstructured.RemoveNestedField(remoteObj.Object, "metadata", "ownerReferences")
	unstructured.RemoveNestedField(remoteObj.Object, "metadata", "finalizers")
	unstructured.RemoveNestedField(remoteObj.Object, "metadata", "managedFields")
	unstructured.RemoveNestedField(remoteObj.Object, "status")
```

I checked the external-framework path and the issue looks valid. `createRemoteObject` builds the remote object from `localObj.DeepCopy()` and only clears `resourceVersion`, so source-cluster metadata such as `ownerReferences` can be carried to the worker.

This appears to be the outlier among the MultiKueue remote-object creation paths: the concrete adapters build remote objects with `api.CloneObjectMetaForCreation`, which only carries Name/Namespace/Labels/Annotations and drops creation-unsafe metadata by construction. The unstructured external-framework path is the only one that starts from `DeepCopy()` and then clears fields selectively.

One small framing note: this does not seem to require a malicious ownerReference; a normal local ownerReference can also become unresolved on the worker cluster.

Plan: add an integration test for an external-framework custom job with an `ownerReference`, then update the unstructured create path to follow the same whitelist-style creation semantics. 

I plan to start with a small helper near the unstructured create path mirroring `CloneObjectMetaForCreation` semantics, but happy to keep it inline or move it to a shared utility if maintainers prefer.
