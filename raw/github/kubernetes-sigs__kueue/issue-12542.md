## Description

_Note: This issue was initially flagged by an automated AI security scan and has been manually triaged by a human_

### Impact
A user with permissions to create Workloads can cause a Denial of Service (DoS) against the Kubernetes API server and the Kueue controller. By simply creating a workload with a long name, the Kueue controller enters an uncontrolled infinite loop of creating and deleting ProvisioningRequest objects, consuming significant API server resources, controller CPU, and preventing the workload from ever being scheduled.

### Data Flow
- **pkg/controller/admissionchecks/provisioning/controller.go:267**: syncOwnedProvisionRequest creates a ProvisioningRequest name using ProvisioningRequestName, passing the attempt number.
- **pkg/controller/admissionchecks/provisioning/provisioning.go:57**: ProvisioningRequestName appends the attempt number and passes the result to limitObjectName.
- **pkg/controller/admissionchecks/provisioning/controller.go:848**: If the length exceeds 247 chars, limitObjectName hashes the entire string (including the attempt number) and truncates it, appending the hash.
- **pkg/controller/admissionchecks/provisioning/provisioning.go:82**: Later, getAttemptRegex generates a regex using a prefix that does NOT include the attempt number, creating a different hash.
- **pkg/controller/admissionchecks/provisioning/provisioning.go:73**: matchesWorkloadAndCheck fails to match the ProvisioningRequest because the regex expects the prefix's hash, but the PR name has the full name's hash.
- **pkg/controller/admissionchecks/provisioning/controller.go:207**: deleteUnusedProvisioningRequests deletes the unmatched PR, and syncOwnedProvisionRequest recreates it, causing an infinite loop.

### Reproduction
**Preconditions**:
1. Kueue installed and running.
2. The ProvisioningRequest admission check controller is active.
3. A ClusterQueue configured with an AdmissionCheck that uses a ProvisioningRequestConfig.
4. A LocalQueue targeting the ClusterQueue.

**Steps**:
1. Identify a valid queue name that routes to the ProvisioningRequest-enabled ClusterQueue.
2. Create a Workload targeting this queue where the combined length of the workload name and admission check name exceeds 247 characters.
3. Observe the Kueue controller manager logs and the API server events.
4. The Workload becomes stuck and the controller rapidly creates and deletes ProvisioningRequests in an infinite loop.

### Vulnerable Code
```
func ProvisioningRequestName(workloadName string, checkName kueue.AdmissionCheckReference, attempt int32) string {
	fullName := fmt.Sprintf("%s-%s-%d", workloadName, checkName, int(attempt))
	return limitObjectName(fullName)
}
```

### Remediation
Ensure the attempt number is appended to the name after truncation, so the prefix remains stable and matching succeeds.

Suggested Fix:
```
Modify ProvisioningRequestName to append the attempt number after limiting the object name: 
`prefix := limitObjectName(fmt.Sprintf("%s-%s-", workloadName, checkName))`
`return fmt.Sprintf("%s%d", prefix, attempt)`.
Update length constraints to account for the appended attempt number so the final string does not exceed 253 characters.
```
