## Description

_Note: This issue was initially flagged by an automated AI security scan and has been manually triaged by a human_

### Impact
A low-privileged tenant can induce a severe Denial of Service (DoS) against the Kueue control plane and the underlying Kubernetes API server. Because the Reconcile function successfully completes without returning an error after re-creating the remote workload, the controller-runtime's internal backoff rate limit is bypassed. The controller will infinitely delete and recreate the remote workload, consuming its own API Priority and Fairness (APF) quota, starving other legitimate reconciliations, and flooding the API server/etcd with write operations.

### Data Flow
- **pkg/controller/admissionchecks/multikueue/workload.go:537**: User-supplied WorkloadSpec is passed as `local`, containing populated `PreemptionGates`.
- **pkg/controller/admissionchecks/multikueue/workload.go:538**: The function nullifies `remote.PreemptionGates` to ignore them during comparison, but fails to nullify `local.PreemptionGates`.
- **pkg/controller/admissionchecks/multikueue/workload.go:539**: `equality.Semantic.DeepEqual(local, remote)` evaluates to false because `local` still contains PreemptionGates while `remote` does not, causing the function to always return true.
- **pkg/controller/admissionchecks/multikueue/workload.go:303**: Because the specs are falsely identified as out-of-sync, the controller deletes the remote Workload.
- **pkg/controller/admissionchecks/multikueue/workload.go:343**: The controller then immediately recreates the remote Workload in the same reconciliation pass, generating new API events that instantly trigger the loop again.

### Reproduction
**Preconditions**:
1. Kueue must be installed and configured with a MultiKueue AdmissionCheck and an active remote worker cluster.
2. The attacker needs RBAC permissions to create Workloads that route to the MultiKueue ClusterQueue.

**Steps**:
1. Create a Workload definition that explicitly defines `spec.preemptionGates` (e.g., a dummy gate).
2. Submit the Workload to a LocalQueue/ClusterQueue that utilizes the MultiKueue AdmissionCheck.
3. Monitor the Kueue controller manager logs and observe the tight infinite loop of deletions and creations.

### Vulnerable Code
```
func isRemoteSpecOutOfSync(local, remote kueue.WorkloadSpec) bool {
	remote.PreemptionGates = nil
	return !equality.Semantic.DeepEqual(local, remote)
}
```

### Remediation
Ensure that `PreemptionGates` are nullified on both the `local` and `remote` WorkloadSpec copies before performing the DeepEqual comparison.

Suggested Fix:
```
func isRemoteSpecOutOfSync(local, remote kueue.WorkloadSpec) bool {
	local.PreemptionGates = nil
	remote.PreemptionGates = nil
	return !equality.Semantic.DeepEqual(local, remote)
}
```

### Comment by [@kshalot](https://github.com/kshalot) — 2026-06-26T15:14:20Z

Yes, I originally triaged this issue when it was first reported by the security scan. This is only a problem when the local workload in MK has a preemption gate. We don't have this case right now, because the only other preemption gate (Concurrent Admission) makes no sense on the manager cluster in MK (see https://github.com/kubernetes-sigs/kueue/issues/12470). So this is low-ish priority.

The AI suggested fix makes sense, but there's also another side to this - all the gates pre-existing on the manager WL are currently copied to the remote:
https://github.com/kubernetes-sigs/kueue/blob/8ba64c9ee1f90c747757a009c5b015b8af2420eb/pkg/controller/admissionchecks/multikueue/workload.go#L1179

I suppose this will not always make sense. For example a preemption gate might be tied to a controller which only runs on the manager cluster. So I think for now we should treat the preemption gates independently on the remote and local.

Since I already spent time writing this out, I'll just open a PR with this change 🤷 We can discuss there if necessary.
