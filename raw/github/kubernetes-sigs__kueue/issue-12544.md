## Description

_Note: This issue was initially flagged by an automated AI security scan and has been manually triaged by a human_

### Impact
Cross-PodSet configuration contamination. An AdmissionCheck (like MultiKueue or ProvisioningRequest) might restrict sensitive PodSets to specific isolated topology domains. Because of this bug, TAS scheduling will apply the topology constraints of the LAST processed PodSet to ALL PodSets in the Workload. This completely bypasses placement enforcement, potentially causing pods to be scheduled on incorrect, non-compliant, or unauthorized nodes.

### Data Flow
- **pkg/scheduler/flavorassigner/tas_flavorassigner.go:118**: The inner loop iterates over `ac.PodSetUpdates` using the value variable `psUpdate`.
- **pkg/scheduler/flavorassigner/tas_flavorassigner.go:120**: The address `&psUpdate` is appended to `podSetUpdates`. Since Kueue uses `go 1.19` semantics, this captures the address of the loop variable itself, not the slice element.
- **pkg/scheduler/flavorassigner/tas_flavorassigner.go:120**: After the loop concludes, all appended pointers reference the last element processed in `ac.PodSetUpdates`, overwriting the intended updates.

### Reproduction
**Preconditions**:
Kueue must be compiled with Go 1.19 loop variable semantics (as specified in its go.mod). The Workload must contain multiple PodSets and an AdmissionCheck must provide `PodSetUpdates` for them.

**Steps**:
1. Create a Workload with two PodSets (e.g., `worker` and `driver`).
2. Add an AdmissionCheck to the Workload in the `Ready` state.
3. Within the AdmissionCheck, provide a `PodSetUpdate` for both `worker` (e.g., `NodeSelector: {type: gpu}`) and `driver` (e.g., `NodeSelector: {type: cpu}`).
4. Observe that TAS scheduling assigns the `worker` PodSet the constraints intended for the `driver` PodSet, effectively bypassing the intended topology placement.

### Vulnerable Code
```
podSetUpdates = append(podSetUpdates, &psUpdate)
```

### Remediation
Avoid capturing the address of the loop variable by indexing the slice directly.

Suggested Fix:
```
for j := range ac.PodSetUpdates {
    if ac.PodSetUpdates[j].Name == podSet.Name {
        podSetUpdates = append(podSetUpdates, &ac.PodSetUpdates[j])
    }
}
```

### Comment by [@ArangoGutierrez](https://github.com/ArangoGutierrez) — 2026-07-11T12:57:00Z

I looked at this before picking it up, and I do not think it reproduces on main. Flagging before we spend a fix on it.

The report hinges on `go 1.19` loop variable semantics. Our go.mod moved past that a long time ago: it is `go 1.26.0` today, and it was already `go 1.24.0` when this exact line landed in May 2025 (blame: 3117559223d). With the Go 1.22 loop variable change, `psUpdate` is a fresh variable each iteration, so `&psUpdate` at pkg/scheduler/flavorassigner/tas_flavorassigner.go:120 takes a distinct address every iteration. A later non-matching iteration cannot clobber a pointer captured earlier.

There is also a name filter right above it, `if psUpdate.Name == podSet.Name` at line 119. `podSetTopologyRequest` runs once per PodSet, so only updates matching the current PodSet get appended. The "worker inherits the driver NodeSelector" scenario needs a matching entry followed by a non-matching one in the same slice, and it only bites under pre-1.22 semantics, which we do not compile under.

I confirmed with a minimal repro of the same pattern: built under `go 1.19` the worker PodSet resolves to the driver selector, built under `go 1.22` it resolves correctly. So the code is correct as compiled on main.

Proposed next step: close as not reproducible on Go >= 1.22. If we want the index form for defensiveness we can do it as a small cleanup, but it is not a correctness fix and I would not keep the kind/bug label. If anyone can show it firing under our actual go directive, please reopen with the go.mod version and I will take another look.

### Comment by [@aburan28](https://github.com/aburan28) — 2026-07-18T20:36:20Z

I checked this against current main and the premise no longer holds: `go.mod` declares `go 1.26.0`, and since Go 1.22 the loop variable is a fresh variable per iteration, so `&psUpdate` in `tas_flavorassigner.go` captures a distinct address each time — the appended pointers do not alias each other. The described cross-PodSet contamination is therefore not reachable with the current toolchain (it would only apply if the module were built with pre-1.22 semantics, which `go.mod` rules out).

I'd suggest closing this one, optionally after a trivial clarity cleanup to index the slice (`&ac.PodSetUpdates[j]`) so the code doesn't rely on reader knowledge of loop-variable semantics.

### Comment by [@alien1403](https://github.com/alien1403) — 2026-08-20T13:45:03Z

This issue is not reproducible on Go >= 1.22.

Since Go 1.22, each iteration of a `for` loop creates a new [variable](https://go.dev/doc/go1.22#:~:text=Previously%2C%20the%20variables,in%20Go%201.21.). Because Kueue compiles with `go 1.26.0`, `&psUpdate` will capture a distinct memory address on every iteration and cannot overwrite earlier pointers.
