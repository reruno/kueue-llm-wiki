## Description

_Note: This issue was initially flagged by an automated AI security scan and has been manually triaged by a human_
### Impact
A malicious tenant can exploit this data race to evade AdmissionFairSharing penalties. By spamming the creation/updating of Workloads to force concurrent RMW operations, they can cause the Kueue scheduler to 'lose' their penalties, keeping their LocalQueue artificially prioritized and monopolizing cluster resources (Denial of Service to other tenants).

### Data Flow
- **pkg/scheduler/scheduler.go:812**: Scheduler goroutine calls s.updateEntryPenalty(..., add) when assuming a Workload, which calls AfsEntryPenalties.Push().
- **pkg/controller/core/workload_controller.go:1175**: Informer listener goroutine concurrently calls WorkloadReconciler.Update() -> updateAfsConsumedUsage() -> AfsEntryPenalties.Sub() for another Workload in the same LocalQueue.
- **pkg/cache/queue/afs/entry_penalties.go:36**: Both goroutines perform m.Peek(lqKey) simultaneously, reading the same stale penalty value.
- **pkg/cache/queue/afs/entry_penalties.go:36**: Both goroutines compute MergeResourceListKeepSum based on the stale value.
- **pkg/cache/queue/afs/entry_penalties.go:36**: Both goroutines call m.penalties.Add() sequentially. The second Add overwrites the first, silently discarding the other goroutine's penalty addition or subtraction (SINK).

### Reproduction
**Preconditions**:
AdmissionFairSharing must be enabled. A tenant must have permissions to create Workloads in a LocalQueue.

**Steps**:
1. Tenant creates a Workload (W1) that is immediately admissible (no admission checks).
2. At the exact same time, the tenant creates a second Workload (W2) in the same LocalQueue.
3. The Scheduler goroutine assumes W2 and calls AfsEntryPenalties.Push().
4. Simultaneously, the Informer listener goroutine processes W1's transition to Admitted and calls AfsEntryPenalties.Sub().
5. Due to the data race, the Push from the Scheduler is overwritten by the Sub from the Informer.
6. W2 is successfully scheduled but its fair-sharing penalty is permanently lost, allowing the tenant to bypass fair-sharing limits.

### Vulnerable Code
```
m.penalties.Add(lqKey, resource.MergeResourceListKeepSum(m.Peek(lqKey), penalty))
```

### Remediation
Introduce a mutex to protect Read-Modify-Write operations on the Fair Sharing caches, or use a compute/update function that locks the specific entry.
