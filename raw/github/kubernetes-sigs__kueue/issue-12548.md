## Description

_Note: This issue was initially flagged by an automated AI security scan and has been manually triaged by a human_

### Impact
An attacker with Workload creation permissions can act as a confused deputy to delete arbitrary remote running Jobs within their namespace across all worker clusters configured in a MultiKueue setup. This bypasses RBAC restrictions (e.g., if the user lacks Job deletion permissions) and causes severe denial-of-service for batch/ML workloads.

### Data Flow
- **pkg/controller/admissionchecks/multikueue/workload.go:277**: Attacker creates a Workload. w.adapter() blindly trusts the 'kueue.x-k8s.io/job-owner-name' annotation, fabricating an OwnerReference to the victim's Job.
- **pkg/controller/admissionchecks/multikueue/workload.go:300**: adapter.IsJobManagedByKueue() validates that the victim's Job is managed by MultiKueue (which it is).
- **pkg/controller/admissionchecks/multikueue/workload.go:309**: readGroup populates grp.controllerKey with the victim's Job name.
- **pkg/controller/admissionchecks/multikueue/workload.go:330**: Because the new spoofed Workload has no quota reservation yet, reconcileGroup triggers the deletion path.
- **pkg/controller/admissionchecks/multikueue/workload.go:134**: RemoveRemoteObjects calls jobAdapter.DeleteRemoteObject() using the victim's controllerKey.
- **pkg/controller/jobs/job/job_multikueue_adapter.go:115**: The worker cluster client forcefully deletes the victim's running Job on the remote worker cluster.

### Reproduction
**Preconditions**:
A multi-cluster MultiKueue environment must be set up with at least one worker cluster. The attacker needs RBAC permissions to create `Workloads` in a namespace, but does not need any permissions on the worker clusters or permission to delete `Jobs`.

**Steps**:
1. Identify a target Job managed by MultiKueue in the same namespace (e.g., 'victim-job').
2. Create a fake Workload in the same namespace with the 'kueue.x-k8s.io/job-owner-gvk' and 'kueue.x-k8s.io/job-owner-name' annotations pointing to the victim job.
3. Ensure the fake Workload references a MultiKueue AdmissionCheck.
4. Observe that the victim's Job on the remote worker cluster is immediately deleted by the MultiKueue controller.

### Vulnerable Code
```
if err := group.RemoveRemoteObjects(ctx, rem); err != nil {
```

### Remediation
Ensure that the Workload actually belongs to the Job before trusting the owner annotations, and validate that the Workload is the authentic primary workload for the targeted Job.

Suggested Fix:
```
In `pkg/controller/admissionchecks/multikueue/workload.go`, modify the `adapter` function or the reconciliation logic to verify that the Workload is a genuine child of the referenced `Job`. Specifically, enforce that the `Job` references the `Workload` (e.g., via `kueue.x-k8s.io/prebuilt-workload-name`) and drop the request if there is a mismatch. Do not allow arbitrary Workloads to hijack a Job's remote lifecycle.
```
