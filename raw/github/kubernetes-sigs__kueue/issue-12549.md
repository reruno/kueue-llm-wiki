## Description

_Note: This issue was initially flagged by an automated AI security scan and has been manually triaged by a human_

### Impact
Denial of Service (DoS). A malicious user can remotely crash the backend application, rendering the visualization dashboard and all its features completely unavailable until the pod restarts.

### Data Flow
- **cmd/kueueviz/backend/handlers/websocket_handler.go:49**: An attacker establishes a WebSocket connection to any configured WS endpoint.
- **cmd/kueueviz/backend/handlers/websocket_handler.go:68**: A goroutine spins up and continually calls `conn.ReadMessage()` to process incoming WebSocket frames.
- **cmd/kueueviz/backend/handlers/websocket_handler.go:69**: Because `conn.SetReadLimit()` is not configured, `gorilla/websocket` will unbounded-ly allocate memory to read arbitrarily large frames sent by the attacker, leading to an immediate Out-Of-Memory (OOM) panic.

### Reproduction
**Preconditions**:
1. KueueViz server is running.
2. The attacker can reach any WebSocket endpoint (e.g., `/ws/workloads`). If Auth is enabled, the attacker must have a valid token.

**Steps**:
1. Open a WebSocket connection to the server.
2. Send a single, continuous WebSocket frame containing several gigabytes of junk data.
3. Observe the KueueViz backend process memory usage spike rapidly until the OS kills the process or Go panics with out-of-memory.

### Vulnerable Code
```
		go func() {
			defer cancel()
			for {
				if _, _, err := conn.ReadMessage(); err != nil {
					return
				}
			}
		}()
```

### Remediation
Enforce a strict maximum read limit on the WebSocket connection.

Suggested Fix:
```
Call `conn.SetReadLimit(maxMessageSize)` immediately after the WebSocket connection is upgraded. For example, `conn.SetReadLimit(8192)` is sufficient since the client only receives data and does not send large payloads.
```
