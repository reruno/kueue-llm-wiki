## Description

_Note: This issue was initially flagged by an automated AI security scan and has been manually triaged by a human_

### Impact
A data race on the `client.WithWatch` interface causes a runtime panic, leading to a Denial of Service (controller crash loop). This can be triggered intentionally by a privileged user or occur accidentally during normal operations (e.g., network blips causing automatic reconnection while the GC runs).

### Data Flow
- **pkg/controller/admissionchecks/multikueue/multikueuecluster.go:679**: A background goroutine running `c.runGC` calls `getRemoteClients()`, which locks `c.lock`, returns a copy of the clients slice, and releases `c.lock`.
- **pkg/controller/admissionchecks/multikueue/multikueuecluster.go:292**: The background goroutine iterates the slice and calls `rc.runGC()`, which directly reads the `rc.client` interface to call `.List(ctx, wls, ...)`.
- **pkg/controller/admissionchecks/multikueue/multikueuecluster.go:175**: Concurrently, a Reconcile loop (triggered by a kubeconfig change or network watch reconnect) calls `rc.setConfig()`, which directly writes to `rc.client` without synchronization on `rc`.

### Reproduction
**Preconditions**:
Kueue controller is running with a configured MultiKueueCluster pointing to a remote cluster.

**Steps**:
1. Configure a MultiKueueCluster object pointing to a valid kubeconfig Secret.
2. Configure Kueue's GCInterval to a very small value to increase the race window, or populate many Workloads so `runGC` takes longer.
3. Continuously update the kubeconfig Secret or simulate network disconnects to trigger `rc.setConfig` via the reconciler.
4. Observe the controller manager crash with a Go runtime panic (data race or invalid memory address) when reading the `rc.client` interface.

### Vulnerable Code
```
rc.client = remoteClient
```

### Remediation
Introduce a mutex in `remoteClient` to protect read/write access to `rc.client` and other configuration state.

Suggested Fix:
```
Add a `sync.RWMutex` to the `remoteClient` struct. Acquire `rc.lock.Lock()` in `setConfig` when assigning `rc.client`, and acquire `rc.lock.RLock()` in `runGC` when reading `rc.client`.
```

I would like to pick this up.

I traced the race and agree it looks real. `setConfig` swaps `rc.client`, while several async readers still access `remoteClient.client` without the same synchronization; this includes the GC / queue event paths and additional workload / clusterqueue readers.

I will keep the fix minimal: reuse the existing `remoteClient.mu`, snapshot the client through a small `getClient()` accessor for all direct readers, avoid holding the mutex across remote API calls, and add `go test -race` coverage for the concurrent `setConfig` path.

Please let me know if you would prefer a different synchronization approach.
