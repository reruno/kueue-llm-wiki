## Description

_Note: This issue was initially flagged by an automated AI security scan and has been manually triaged by a human_
### Impact
If a user's access is revoked or their token expires, they will continue to receive real-time, sensitive cluster data via their pre-existing WebSocket connection indefinitely.

### Data Flow
- **cmd/kueueviz/backend/middleware/auth.go:73**: HTTP request is initially authenticated by auth.Middleware()
- **cmd/kueueviz/backend/handlers/websocket_handler.go:48**: Connection is upgraded to a WebSocket. The HTTP context and middleware checks are finalized.
- **cmd/kueueviz/backend/handlers/websocket_handler.go:179**: An infinite loop streams Kubernetes informer updates to the client without ever re-verifying the user's token or enforcing session expiration.

### Reproduction
**Preconditions**:
1. kueueviz server is running with TokenReview auth enabled.
2. You have a valid Kubernetes Bearer token that is about to expire or can be manually revoked.
3. `websocat` tool is installed.

**Steps**:
1. Export your valid token as VALID_TOKEN.
2. Run the reproduction script to establish a WebSocket connection.
3. Once connected, manually revoke the ServiceAccount or wait for the token to expire.
4. Create a new Workload in the Kubernetes cluster.

### Vulnerable Code
```
case <-updateChan:
	if err := h.sendData(ctx, conn, dataFetcher); err != nil {
```

### Remediation
Implement periodic token re-evaluation for open WebSocket connections or enforce a maximum connection lifetime.

Suggested Fix:
```
Add a ticker inside the `handleInformerUpdates` select loop that periodically triggers a re-authentication check using the original token. If the TokenReview fails, close the WebSocket connection.
```
