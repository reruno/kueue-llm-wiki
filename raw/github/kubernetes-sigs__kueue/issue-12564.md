## Description

_Note: This issue was initially flagged by an automated AI security scan and has been manually triaged by a human_

### Impact
Unlike a panic in a core reconciler loop, a panic in the webhook's HTTP handler goroutine does not bring down the entire Kueue controller process because `net/http` automatically recovers from handler panics. However, because the webhook is configured with `failurePolicy: Fail`, the panic drops the request, blocking the creation of the malicious resource. While this is primarily an input-rejection bug, an attacker who rapidly and continuously streams this invalid payload can consume webhook processing threads and generate noisy stack traces, resulting in a localized Denial of Service and degradation of webhook responsiveness.

### Data Flow
- **pkg/controller/jobs/mpijob/mpijob_webhook.go:124**: A user submits an `MPIJob` resource where the `ReplicaSpec` mapping (e.g., `Launcher`) points to a literal `null`. The creation is intercepted by the Kueue validating/mutating webhook for MPIJobs.
- **pkg/controller/jobs/mpijob/mpijob_webhook.go:161**: The webhook executes `w.validateCommon`, which cascades down to extract PodSets from the Job configuration via `jobframework.JobPodSets(ctx, mpiJob)`.
- **pkg/controller/jobs/mpijob/mpijob_controller.go:221**: `orderedReplicaTypes` parses the map keys. Because `map[kfmpi.MPIReplicaTypeLauncher]` exists (despite the value being `nil`), the launcher replica type is included.
- **pkg/controller/jobs/mpijob/mpijob_controller.go:118**: When iterating over the replica types, the code blindly assumes `MPIReplicaSpecs[mpiReplicaType]` is non-nil and accesses its `.Template` property, resulting in a nil pointer dereference panic.

### Reproduction
**Preconditions**:
The Kueue webhook must be deployed, actively intercepting `MPIJob` requests (`vmpijob.kb.io` / `mmpijob.kb.io`), and the environment must have the Kubeflow MPI operator CRDs registered.

**Steps**:
1. Create a `kubeflow.org/v2beta1` `MPIJob` definition.
2. Provide the `mpiReplicaSpecs` object, but set one of the inner replica types (such as `Launcher` or `Worker`) explicitly to `null`.
3. Apply the resource to the cluster.
4. The request triggers Kueue's mutating/validating webhook, which immediately panics when processing the null pointer.

### Vulnerable Code
```
Template: *j.Spec.MPIReplicaSpecs[mpiReplicaType].Template.DeepCopy(),
```

### Remediation
Check that the pointer to `ReplicaSpec` is not nil before attempting to process it or construct a `PodSet`.

Suggested Fix:
In `pkg/controller/jobs/mpijob/mpijob_controller.go`:

```go
func orderedReplicaTypes(jobSpec *kfmpi.MPIJobSpec) []kfmpi.MPIReplicaType {
	var result []kfmpi.MPIReplicaType
	if spec, ok := jobSpec.MPIReplicaSpecs[kfmpi.MPIReplicaTypeLauncher]; ok && spec != nil {
		result = append(result, kfmpi.MPIReplicaTypeLauncher)
	}
	if spec, ok := jobSpec.MPIReplicaSpecs[kfmpi.MPIReplicaTypeWorker]; ok && spec != nil {
		result = append(result, kfmpi.MPIReplicaTypeWorker)
	}
	return result
}
```

### Comment by [@kannon92](https://github.com/kannon92) — 2026-06-26T18:22:04Z

> **AI Disclosure:** This analysis was performed with the assistance of an AI coding agent (Claude). The investigation steps, commands, and conclusions were reviewed by a human.

## Investigation: Bug is not reproducible in a real Kubernetes environment

I investigated whether `Launcher: null` (or `Worker: null`) in an MPIJob `mpiReplicaSpecs` can actually reach the Kueue webhook and trigger the nil pointer dereference.

### What I found

**1. Go-level: the nil dereference is real in isolation**

`json.Unmarshal` of `"Launcher": null` into `map[MPIReplicaType]*ReplicaSpec` does create a map entry with key `"Launcher"` and value `nil`. A direct call to `PodSets()` with such a map panics at line 118 of `mpijob_controller.go`. This is reproducible in a unit test.

**2. CRD schema prevents null values from reaching the webhook**

The MPIJob CRD schema defines `mpiReplicaSpecs.additionalProperties` as `type: object` **without** `nullable: true`. This means the Kubernetes API server applies [structural schema pruning](https://kubernetes.io/docs/tasks/extend-kubernetes/custom-resources/custom-resource-definitions/#field-pruning) — null map values are silently removed before the object reaches any admission webhook.

```
$ kubectl get crd mpijobs.kubeflow.org -o json | \
    jq '.spec.versions[0].schema.openAPIV3Schema.properties.spec.properties.mpiReplicaSpecs.additionalProperties | {type, nullable}'
{
  "type": "object",
  "nullable": null   # not set — null values are pruned
}
```

**3. End-to-end test confirms no panic**

I tested on a kind cluster with the MPIJob CRD installed and Kueue webhooks active:

```yaml
apiVersion: kubeflow.org/v2beta1
kind: MPIJob
metadata:
  name: test-nil-launcher
spec:
  mpiReplicaSpecs:
    Launcher: null
    Worker:
      replicas: 1
      template:
        spec:
          containers:
          - name: worker
            image: busybox
```

Result:
- **No panic** in the Kueue controller logs
- The stored object has `Launcher` completely absent (pruned)
- Also tested with both `Launcher: null` and `Worker: null` — same result, no panic

### Conclusion

The Kubernetes API server's structural schema pruning removes null map values **before** dispatching to mutating/validating webhooks. The nil pointer dereference is only reachable in unit tests that bypass the API server, not in any real deployment. The described DoS scenario is **not exploitable**.

A defensive nil check in `orderedReplicaTypes()` would still be reasonable as defense-in-depth, but this is not an exploitable vulnerability.
