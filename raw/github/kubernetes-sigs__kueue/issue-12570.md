## Description

_Note: This issue was initially flagged by an automated AI security scan and has been manually triaged by a human_

### Impact
Attackers or misconfigured tenants with permission to create/update ClusterQueues can bypass all Kueue admission validations. This allows for injecting negative quotas, exceeding lending limits, or configuring borrowing limits without a cohort. This can result in scheduling disruptions, resource overallocation, or starvation of other queues.

### Data Flow
- **pkg/webhooks/clusterqueue_webhook.go:282**: User submits a ClusterQueue with `flavorQuotas.Resources` containing more items than `CoveredResources`.
- **pkg/webhooks/clusterqueue_webhook.go:284**: The validation loop prematurely `break`s when `i >= len(coveredResources)`, silently skipping validation for any trailing resources.
- **pkg/cache/scheduler/resource.go:57**: The Kueue scheduler (`createResourceQuotas`) iterates over all items in `flavorQuotas.Resources`, injecting the unvalidated items (which can contain negative quotas, unauthorized borrowing limits, or lending limits exceeding nominal quota) into the active scheduler cache.

### Reproduction
**Preconditions**:
Kueue must be installed in the cluster and the validating webhook must be active.

**Steps**:
1. Create a YAML payload for a ClusterQueue where the `resources` array inside a flavor has more elements than the `coveredResources` array.
2. Add a duplicate resource name in the trailing elements, but configure it with invalid limits (e.g., `lendingLimit` greater than `nominalQuota`, which violates validation rules).
3. Apply the YAML using `kubectl apply`.

### Vulnerable Code
```go
if i >= len(coveredResources) {
	break
}
```

### Remediation
Ensure the webhook rejects configurations where the length of `flavorQuotas.Resources` exceeds `coveredResources` instead of silently ignoring the extra items.

Suggested Fix:
Change the `break` statement to emit a validation error instead:

```go
if i >= len(coveredResources) {
	allErrs = append(allErrs, field.Invalid(path.Child("resources").Index(i), rq.Name, "too many resources in flavor, must match coveredResources"))
	continue
}
```

### Analysis: Not Exploitable — CEL Validation Prevents the Attack

The precondition for this attack **cannot be met** because of a CEL (Common Expression Language) validation rule on the `ResourceGroup` type, enforced by the Kubernetes API server before any webhook runs.

Both `v1beta1` and `v1beta2` have this rule on `ResourceGroup`:

```go
// +kubebuilder:validation:XValidation:rule="self.flavors.all(x, size(x.resources) == size(self.coveredResources))", message="flavors must have the same number of resources as the coveredResources"
```

([v1beta2 source](https://github.com/kubernetes-sigs/kueue/blob/main/apis/kueue/v1beta2/clusterqueue_types.go#L254), [v1beta1 source](https://github.com/kubernetes-sigs/kueue/blob/main/apis/kueue/v1beta1/clusterqueue_types.go#L178))

This rule requires that every flavor's `resources` array has **exactly the same length** as `coveredResources`. The API server evaluates this before the object is persisted and before the validating webhook fires. It cannot be bypassed by a client.

**Implications:**

1. The reproduction step — *"Create a YAML payload where the `resources` array inside a flavor has more elements than the `coveredResources` array"* — will be rejected by the API server with: `"flavors must have the same number of resources as the coveredResources"`.
2. The `break` at `clusterqueue_webhook.go:336` is dead code for this scenario — it's a defensive fallback that can never trigger in practice.
3. `createResourceQuotas` in `resource.go` will never see extra unvalidated resources because they can never make it into etcd.

The `break` could be changed to emit a validation error for defense-in-depth, but this is not a security vulnerability. This appears to be an AI security scan false positive that did not account for the CEL schema validation.
