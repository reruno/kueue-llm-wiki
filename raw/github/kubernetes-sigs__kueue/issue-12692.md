## Description

<!-- Please use this template for documentation-related issues -->

**What would you like to be documented or improved**:

Many integrations can exist but we need to draw the line on what goes into Kueue core versus what should be done via an external integration.

I think Kueue should manage integrations in kubernetes and kubernetes-sigs. And integrations outside of that (minus the ones we have already) should be done as an external framework owned by that community.

**Why**
#12620 

#11273 

Some projects are not keeping up with k8s dependencies and that puts burden on Kueue maintainers during release time.
**Location** (URL, file path, or section if applicable):

Not sure where we should put this but we should document this for community when we get new integration requests.

### Comment by [@kannon92](https://github.com/kannon92) — 2026-08-26T16:45:18Z

https://github.com/kubernetes-sigs/kueue/issues/14722

This came up internally for us and we realize that one benefit of external frameworks is that could handle breaking API changes more gracefully. Kueue right now verifies 1-to-1 mapping between the controllers api we vendor and what we test. We don't really guarantee anything like skew (ie Trainer 2.1 runs on Kueue 0.19).

This becomes a pain point for enterprise customers where they may not update all the dependencies that Kueue uses. I think we have been okay for a while since many of the APIs have not had any breaking changes.
