## Description

TAS workloads already have node hot swap support: when a node fails, Kueue can use the TAS topology assignment to find affected workloads, replace the failed node when possible, or evict/requeue the workload when replacement is not possible.

For non-TAS workloads, there is no TAS topology assignment to update, so TAS-style node hot swap is not expected. However, Kueue should still be able to react to node failures for admitted workloads.

One possible approach is to make the node controller generic and branch the behavior:

- TAS workloads: keep the existing TAS assignment-based hot swap behavior.
- Non-TAS workloads: if an admitted workload has pods scheduled to or bound to a failed node and the workload cannot make progress, evict/requeue the workload to release admission instead of waiting for `waitForPodsReady.recoveryTimeout`.

After the affected workload is requeued, the normal Kueue admission and preemption logic should be able to reconsider it. For example, if the requeued LWS workload has higher priority than an already admitted RayJob, Kueue should be able to admit the LWS workload by preempting the RayJob, according to the configured priority and preemption policies.

**Why is this needed**:

This scenario is common in GPU clusters that intentionally use spare failure-buffer GPUs for opportunistic RayJob workloads to improve overall GPU utilization; when a node fails, higher-priority serving workloads such as LWS may need to reclaim capacity quickly.

Consider a small k8s cluster with two worker nodes:

- Node A is running a RayJob.
- Node B is running an LWS workload.
- Both workloads are already admitted by Kueue.
- Node B goes down.
- The LWS pods become Pending and cannot recover quickly.

Because both workloads are already admitted, the affected LWS workload may continue holding admission even though it cannot make progress. In this state, Kueue may not promptly reconsider admission/preemption decisions, and recovery can be delayed.

Relying only on `waitForPodsReady.recoveryTimeout` can be too slow for node failure scenarios. Since node failure is an explicit cluster event, Kueue should be able to react more directly for non-TAS workloads as well.

The expectation is that Kueue should provide a generic node-failure recovery path for admitted workloads, while keeping topology-assignment replacement logic specific to TAS.

### Comment by [@lkhun9311](https://github.com/lkhun9311) — 2026-11-16T09:20:29Z


I tested this on kind using two batch/v1 Jobs named “serving” and “batch”, with simulated `example.com/gpu` resources. I did not test LWS or RayJob. Script, manifests and raw timelines: https://gist.github.com/lkhun9311/58825f2721d878f75f363e8b8a88d88c

- Kueue v0.20.6, Kubernetes v1.36.1. One ResourceFlavor without topology, one ClusterQueue with no Cohort, `withinClusterQueue: LowerPriority`. GPU-token quota 4, with 2 advertised by each worker. Each Job requests 2 tokens. WorkloadPriorityClass values are 1000 for serving and 100 for batch; both Pod priorities are 0.
- Node loss left `nominalQuota` at 4 in this setup.
- After `docker stop` of serving’s worker, its Workload changed to `PodsReady=False/WaitForRecovery` and retained its two-token reservation. With the shipped v1beta2 configuration’s 30-minute recovery timeout, Kueue evicted it about 31 minutes after the stop.
- After the 60-second backoff, Kueue re-admitted it without preempting batch. Replacement Pods stayed Pending through the end of the 40-minute run. A shorter run recorded four timeout evictions in 15 minutes with `recoveryTimeout: 90s`, `timeout: 3m`, and backoff base/max of 30s/300s. The first eviction used the recovery timeout; later ones used the startup timeout.
- An untolerated NoExecute taint on the live worker also left the Workload admitted during a five-minute run. Stopping the worker and deleting its Node two minutes later left it admitted through a ten-minute run. Neither run reached the default recovery timeout.
- With the shorter timeout settings, manually reducing quota from 4 to 2 caused no immediate eviction. After serving timed out and requeued, Kueue preempted batch, and serving’s replacement Pods ran on the surviving worker.
- With Pod priorities also set to 1000/100, kube-scheduler preempted batch’s Pods after serving’s 300-second unreachable-taint toleration expired. Serving recovered at about 349 seconds; batch’s Workload remained admitted through the ten-minute run.
- With the same quota and priorities plus hostname-level TAS, serving’s replacement Pods were Ready at about six minutes. After taint eviction, Kueue evicted serving with `NodeFailures` when replacement failed, then preempted batch because the surviving node lacked free capacity.

In the non-TAS runs with equal Pod priorities, shortening the timeout did not restore serving: its request fit the unchanged quota again, so Kueue re-admitted it without preempting batch. Reducing quota or using TAS changed that admission decision.
