### Comment by [@reruno](https://github.com/reruno) — 2026-07-16T15:42:31Z


I calculate the new avg cpu for the as you have suggested, I use this formula to calculate new avg cpu
```
new avg cpu = avg cpu usage * build duration / target build duration (7min)
```
We calculate it for every build for e.g. calculate new avg cpu for every 400 builds. Then we have 400 numbers of new avg cpu, with that we can draw distribution (dist_mean_new_cpu.png) and from that distribution we pick p95 as a target cpu.

The main problem is that we pick CPU request based on average which is not ideal for job that has burst cpu usage patterns (like e2e jobs), because if we don't account for peaks the peaks will throttle and it could lead to higher than expected durations for these type of jobs. We assign type (burst, stable) for a job based on its median **crest factor**. In our case `crest factor = p95 / p50 (cpu)` for a build, we calculate crest factor for each build, calculate distribution and if median crest factor is lower than `2.0` then we label job as stable, otherwise burst type. 

To pick a job that is quicker than 7 min, we take the p95 of duration.

So to determine for what jobs we can cut corners I propose these **requirements**: 
1. Job MUST be stable (crest factor < 2.0)
2. Job p95 duration MUST be less than 7 min

If everything checks out the target cpu recommendation formula:
``` 
target cpu recommendation = round_up(p95 from new avg cpu distribution, cpu resolution)
# cpu resolution - how many digits after floating point, in our case it is 0.1 ie 100m 
```

I think it is because `new avg cpu` calculations are too simple for burst type jobs. It doesn't account for throttling. I have an idea how we can calculate the cpu cores for these type of job

1. Calculate `new avg cpu` as usual
2. For build metrics filter out every data point where cpu usage is less than `new avg cpu`, every data point where cpu usage is lower than new avg cpu is **low cpu usage** 
3. Peak duration = Build duration - Low cpu usage duration, with peak duration we know how much time job runs with "high" cpu usage
4. Peak target duration = Target duration - Low cpu usage duration, it is target duration for peak cpu usage
5. `new peak avg cpu = peak avg cpu * peak duration / peak target duration`, the same formula but for slice of job with peak cpu usage, 
6. calculate new peak avg cpu for every build
7. Calculate distribution, take p95 of new peak avg cpu as a recommendation for cpu core request/limit

### Comment by [@reruno](https://github.com/reruno) — 2026-07-21T13:02:22Z

> I don't follow the details exactly, maybe formalizing the steps would help and formulas.

We calculate recommendation cpu for each build, and take p95 as a cpu request for ci job. 

To understand the rec cpu algorithm here pseudocode of how we calculate the thing. 
```
MINUTES_CUTOFF = 1.0 # 1 minute
# samples - metric data, in our case cpu usage measurements every 30s for one build
# duration_minutes - duration of the build in minutes
# target_duration_minutes - target duration, in our case 10min
# iterations - how much iterations should we run the for loop, right now it in the python scripts it is set to 5
# returns the cpu recommendation for a build 
func calc_rec_cpu(samples []float, duration_minutes float, target_duration_minutes float, iterations int) float
    target_cpu = 0
    for i in range(iterations)
        # high_cpu contains samples where cpu usage is higher than target_cpu
        # the same but oposite for below_cpu 
        high_cpu = only_higher(samples, target_cpu) 
        below_cpu = only_lower_equal(samples, target_cpu)
        # On first iteration we don't have any below_cpu because target_cpu is not calculated here
        if i == 0
            high_cpu = samples
            below_cpu = [] 

        # calculate how much time build runs at below cpu
        below_cpu_duration_minutes = len(below_cpu) / len(samples) * duration_minutes
        target_time_remaining = target_duration_minutes - below_cpu_duration_minutes

        # If remaining time is less than constant MINUTES_CUTOFF we break and return what we got in target_cpu 
        if target_time_remaining < MINUTES_CUTOFF 
            break
        avg_cpu = avg_cpu(high_cpu)
        # duration_minutes - below_cpu_duration_minutes is because we are working on slice of job with high cpu usage here
        # on first iter below_cpu_duration_minutes=0 
        target_cpu = avg_cpu * (duration_minutes - below_cpu_duration_minutes) / target_time_remaining
    return target_cpu
```

The basic idea is first iteration is approximation, second iteration we taking into account the peaks, and the next iterations we take into account "the peaks of the peaks", until the `target_time_remaining` is less than a minute or `target_cpu` converges to one value
