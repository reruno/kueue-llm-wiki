## Description

**What would you like to be added**

Pluggable OpenTelemetry tracing for the Kueue controller, following the Kubernetes system-component tracing pattern (kubelet, kube-apiserver): OTLP over gRPC exported to an OpenTelemetry Collector, opt-in via config + feature gate.

**Why is this needed**

Kueue admits workloads through async reconcile loops (scheduling, quota reservation, admission checks). Latency and stalls in that pipeline are hard to diagnose from metrics/logs alone. Traces would show where a workload spends time between submission and admission.

**Proposed shape**

- Config: `Tracing *TracingConfiguration` on the Kueue `Configuration`, reusing `k8s.io/component-base/tracing/api/v1` (same type/UX as kubelet — `endpoint`, `samplingRatePerMillion`).
- Feature gate: `KueueTracing` (alpha, off by default).
- Provider bootstrapped via `component-base/tracing`; kube-apiserver client wrapped for span + context propagation.
- Spans on the admission path: scheduling cycle, quota reservation, admission checks, workload reconcile.

**Open design question**

A workload's admission journey spans multiple reconciles, so lifecycle traces require persisting span context on the Workload (annotation). Two phases:

1. MVP: per-reconcile / per-cycle spans (no persistence).
2. Full: workload-lifecycle traces via span-context annotations.

**Completion requirements**

- [ ] KEP
- [ ] API change
- [ ] Docs update

Related: #8848 (OTLP metrics export) — complementary transport (push metrics vs. traces); same OTLP→Collector direction.

Prior art in Kueue: @vladikkuzn already has a draft tracing experiment in #10818 — this issue aims to build on that direction toward a KEP.
