## Description

<!-- Please only use this template for submitting clean up requests -->

**What would you like to be cleaned**:

In the MultiKueue admission-check controller
(`pkg/controller/admissionchecks/multikueue/workload.go`), when a reserving remote
workload is deleted in step 5 for drifting out of sync with the manager spec, step 6a
now reports the generic admission-check message
`Reserving remote no longer exists or is not admitted` instead of a more specific
`Remote workload out of sync`.

An earlier attempt tracked this with an `outOfSyncDeleted` side map, but it was dropped
from #12999 to keep that bugfix focused (see
https://github.com/kubernetes-sigs/kueue/pull/12999#discussion_r3589317420). As suggested
there, a cleaner approach is to encapsulate the "deleted / out-of-sync" state inside the
referenced per-remote structure instead of setting `group.remotes[rem] = nil` and tracking
deletion in a separate map, similar to how `connectionState` encapsulates connection state
in that PR. Step 6a could then surface a precise message without a side map.

**Why is this needed**:

A precise "out of sync" message helps operators understand why a workload was reset for
re-dispatch, and encapsulating the per-remote state avoids splitting related information
across `group.remotes` and an ad-hoc map, improving readability and reducing the chance of
the two drifting.
