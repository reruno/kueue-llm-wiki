## Description

**What would you like to be added**:

A brainstorm issue for incorporating "good taste" into `cmd/experimental/skills/reviewer/`.

Today the reviewer skills are largely *enumerators*: each fires on a pattern and emits a finding. They cover style, security CWEs, and convention drift well.

They cannot make the judgment calls a human reviewer makes. Ie whether the problem even needs solving, whether the solution is proportionate to it, what alternatives and tradeoffs were on the table, when duplication is correct, when an abstraction is premature, when a nit should be swallowed so the real bug is visible, and when the right review is simply "LGTM".

Summary: elevate more abstract code review skills and quantify "good taste"

This github issue is a place to brainstorm what good taste means from a human reviewer and how we train llms to pick up the same skillsets.

Some dimensions may become new guidance inside existing skill files, some may adjust `code-eval` scoring, some may need something else entirely.

This matters empirically: studies of industrial code review show its realized value is dominated by understanding, knowledge transfer, and team awareness rather than raw defect counts ([Bacchelli & Bird, ICSE'13](https://sback.it/publications/icse2013.pdf); [Google's study of 9M reviewed changes](https://dl.acm.org/doi/10.1145/3183519.3183525)), while LLM reviewers do well on surface checks but miss business logic, cross-system impact, and end-to-end behavior, and systematically fail to abstain ([empirical study](https://arxiv.org/html/2505.16339v1), [AbstentionBench](https://arxiv.org/pdf/2506.09038)).

**What "taste" means here:** taste has two halves. The **discernment** half is positive judgment — recognizing the right problem, the better structure, the alternative not taken, the tradeoff weighed correctly (Axes 0–2 below). The **restraint** half is knowing what not to say — abstaining, swallowing nits, respecting incumbent structure (Axis 3 and the restraint clauses). Both are required; agents are weakest at the restraint half, so this issue mandates it structurally: every "flag X" rule ships with a restraint clause saying when NOT to fire. Additionally, some dimensions below are *harness* concerns (scoring, severity weighting, caps) rather than prompt text — taste that cannot be prompted must be enforced by scoring.

## Taxonomy: four axes of review taste

```
Taste
├── Axis 0: judgment about the problem   (dimensions P1–P3)
├── Axis 1: judgment about the code      (clusters A, B; dimensions D1–D4)
├── Axis 2: judgment about risk          (dimensions D5–D6)
└── Axis 3: judgment about the review    (cluster C; dimensions D7–D10; meta-layer)
```

Axis 0 is the deepest form of taste — whether the change should exist at all is upstream of every code-level judgment, and it is the hardest to encode. Axis 3 is purely behavioral and therefore the most encodable. Everything code-level (Axes 1–2) sits in between.

---

## Axis 0 — Judgment about the problem

The reviewer's first duty is not to judge the code but to judge the change: is this the right problem, and is this the right amount of solution? Reviewing the code quality of a change that shouldn't exist is a category error — "there is nothing so useless as doing efficiently that which should not be done at all" ([Drucker, "Managing for Business Effectiveness", HBR 1963](https://hbr.org/1963/05/managing-for-business-effectiveness)). Effectiveness (the right thing) precedes efficiency (the thing done right).

### P1. Should this exist at all?

- **Signal:** a PR whose underlying problem is unclear, self-inflicted, better solved by configuration/documentation, already solved by an existing mechanism, or not worth its ongoing cost.
- **Judgment:** "the best code is no code at all" — every new line is a liability that must be debugged, read, understood, and supported; capabilities are the asset, code is the cost ([Atwood](https://blog.codinghorror.com/the-best-code-is-no-code-at-all/)).
- **Restraint:** the bar is a genuine question ("what breaks today without this?"), not reflexive rejection. A confirmed user-facing bug or an accepted KEP clears it instantly.
- **Kueue shape:** does this need a new API field, or does an existing knob / AdmissionCheck / feature gate / label already cover it? Is this fixing a symptom in Kueue that belongs upstream (controller-runtime, the job framework's CRD)?

### P2. Is the solution proportionate to the problem?

- **Signal:** solution complexity out of scale with problem severity — a new controller for a rare edge case, a config surface for a one-line fix, machinery whose maintenance cost exceeds the cost of the bug it prevents.
- **Judgment:** prefer the simplest thing that could possibly work; complexity must be paid for by the problem, not by the pattern — complexity is the liability, and "no" is a legitimate design tool ([The Grug Brained Developer](https://grugbrain.dev/)). A cure more complex than the disease is a net loss even when it works.
- **Restraint:** some problems are genuinely hard; don't flag necessary complexity (this is the flip side of `avoidable-complexity`). Judge against the *problem's* size, not against an absolute simplicity ideal.

### P3. Alternatives and tradeoffs

- **Signal:** a non-trivial design choice presented with no visible consideration of alternatives — no "why not X" for the obvious X, no acknowledgment of what the chosen path costs.
- **Judgment:** every non-trivial choice is a tradeoff; there are no solutions, only trade-offs. Google design docs make "alternatives considered" a fixed section precisely because it forces the author to justify the pick against reuse, buying, or doing nothing ([Design Docs at Google](https://www.industrialempathy.com/posts/design-docs-at-google/)); ADRs require documenting consequences including the cost side — lock-in, ops burden, narrowed future choices ([Fowler on ADRs](https://martinfowler.com/bliki/ArchitectureDecisionRecord.html)). A tasteful review names the strongest alternative and asks how the tradeoff was weighed — including "do nothing".
- **Restraint:** demand this in proportion to reversibility (see D5). A one-way-door change (new CRD field, RBAC grant) warrants an explicit alternatives discussion; an internal refactor does not need an ADR.
- **Kueue shape:** the reviewer's question is "what is the strongest alternative, including doing nothing?" The project's own KEP corpus (~35 `## Alternatives` sections) shows the recurring shapes: *do nothing or less* (don't build it, document it, let the ecosystem or the user handle it); *reuse or adopt instead of build* (an existing mechanism, project, or upstream feature — judged on maintenance health, not just fit); *move the responsibility* (webhook vs reconciler, Kueue core vs standalone component vs external controller vs upstream — really the question of who bears the complexity); *change the commitment level* (annotation before API field, feature gate before config surface, defer to Beta — the KEP template's "Reasons for discarding/deferring" treats most alternatives as deferred, not dead); *change the granularity* (which tier — global, ClusterQueue, LocalQueue, Workload — owns the knob); and *same feature, different API shape* (minimal vs extensible, reuse vs new type). The tradeoffs that most often decide: backwards compatibility, new failure modes (stuck states, held quota, degraded admission), drift vs consistency-by-construction, and consistency with existing precedent as the tiebreaker.

## Axis 1 — Judgment about the code

### Cluster A — Abstraction Discipline (*don't add structure you don't need yet*)

- **A1 Avoid Hasty Abstractions** — flag *premature* extraction (≤2 callers, param-heavy "mode" flags) AND genuine 3+ site duplication. Default lenient at 2. *"Prefer duplication over the wrong abstraction"* (Sandi Metz, via [AHA Programming](https://kentcdodds.com/blog/aha-programming)). The existing `duplicated-logic` skill already flags one-caller helpers; this makes the rule explicitly bidirectional.
- **A2 YAGNI** — unused config/exports/extension points are permanent cost; on a CRD, permanent API surface. Restraint: distinguish speculative generality from load-bearing extensibility shipped in the same PR. Ties to the existing `visibility-exports` and `api-field-comments` skills.
- **A3 Boring Solutions** — cleverness spends an [innovation token](https://mcfunley.com/choose-boring-technology); boring code has well-understood failure modes, which is the whole game on the admission hot path. Restraint: never flag boring-but-verbose code for verbosity.

### Cluster B — Locality & Modularity (*where code lives, what it hides*)

- **B1 Deep Modules** — flag shallow modules (wide interface, thin behavior) that leak internal state to callers ([Ousterhout](https://softengbook.org/articles/deep-modules)). Restraint: don't demand every helper be "deep". The existing `push-guards-to-callees` skill is one instance of this principle.
- **B2 Locality of Behavior** — flag avoidable "spooky action at a distance" ([Carson Gross / htmx](https://htmx.org/essays/locality-of-behaviour/)). Restraint: controller-runtime is event-driven *by design* — never flag the framework; only avoidable non-locality (e.g., an annotation whose only reader is three packages away with no doc pointer).
- **B3 Vertical Slices** — **advisory, greenfield packages only.** Kueue is already layer- and integration-organized (`pkg/controller/jobs/<framework>/`); flagging existing structure would itself be the taste failure this issue exists to prevent.

### D1. Intent alignment (review the "why", not the diff)

- **Signal:** diff does not match the PR description / linked issue — scope beyond the ticket, a "bugfix" that adds API surface, a refactor bundled silently.
- **Judgment:** understanding change intent is the central bottleneck of review ([Bacchelli & Bird](https://sback.it/publications/icse2013.pdf)); the first review pass is description-vs-diff, before any code judgment.
- **Restraint:** small mechanical drift (typo fix in passing) is not scope creep.

### D2. Chesterton's fence / tacit knowledge

- **Signal:** the diff removes or bypasses existing code whose purpose is not obvious.
- **Judgment:** understand why code exists before agreeing it should go — `git log -L`, linked issues, upgrade paths. Fences are often undocumented ([Chesterton's fence in SE](https://medium.com/@mesw1/understanding-chestertons-fence-a-guiding-principle-in-software-engineering-7459e1fb7bf1)). Generalizes the existing `deleted-backwards-compatibility-code` hard blocker: any removal requires archaeology before a finding — in either direction.
- **Restraint:** archaeology that finds a clear, obsolete reason clears the removal — the rule requires *checking*, not *keeping*.

### D3. Special-case elimination (Torvalds' "good taste")

- **Signal:** the diff adds an `if special-case` branch where restructuring would make the special case the normal case ([linked-list example](https://github.com/mkirchner/linked-list-good-taste)).
- **Judgment:** "rewrite it so that a special case goes away and becomes the normal case." Note the inversion: agents flag *missing* edge-case handling; taste also flags edge-case handling that shouldn't need to exist.
- **Restraint:** only when the restructure is local and obvious; never demand whole-function rewrites (see C2).

### D4. Hyrum's law — implicit interfaces

- **Signal:** the diff changes observable behavior outside the declared API: event message formats, condition ordering, metric names/text, log formats, default orderings, requeue timing.
- **Judgment:** with enough users, all observable behavior is depended on ([Hyrum's law](https://www.hyrumslaw.com/)). Treat observable-output changes as API change candidates. Concrete in-repo proof: the `kueue-who-preempted` skill *parses the Preempted event message format* — that string is load-bearing.
- **Restraint:** not every log line is an interface; weight by how discoverable and how documented the behavior is.

## Axis 2 — Judgment about risk

### D5. Risk-weighted scrutiny (blast radius × reversibility)

- **Judgment:** review attention should scale with blast radius and reversibility ([one-way vs two-way doors](https://thoughtbot.com/blog/one-way-vs-two-way-door-decisions)). Humans do this instinctively; agents give uniform scrutiny to a test comment and a CRD field.
- **Direction:** some notion of per-path risk tiering — `apis/` + webhooks + RBAC are one-way doors deserving max scrutiny; scheduler/cache hot path is high blast radius; `test/`, docs, `site/` are two-way doors. Finding severity/weight should reflect the tier (harness concern, likely `code-eval`).

### D6. Runtime grounding (simulate the flow)

- **Judgment:** incident-causing bugs often only appear following an end-to-end flow; static reading both misses them and produces plausible-but-not-exploitable false positives ([empirical study](https://arxiv.org/html/2505.16339v1)). Humans mentally execute: rolling upgrade, concurrent reconciles, webhook down, cache cold.
- **Direction:** high-severity findings should state a concrete failure scenario (input/state, then wrong outcome) and confirm no upstream webhook/validation already blocks it. No scenario = downgrade to a question.

## Axis 3 — Judgment about the review itself

### Cluster C — Review posture

- **C1 Pragmatic Focus** — logic over style, three ordered questions mapped to Kueue:
  1. *Happy path* — right requirement? correct quota/priority/borrowing math? right objects mutated? no clobbered conditions?
  2. *Sad path* — nil/empty optional CR fields (panic in scheduler cache or webhook wedges the loop → high); MultiKueue timeouts; adversarial input; races (overlaps `nil-safety`, `input-validation`, `race-conditions` — reuse them).
  3. *Boundaries* — leaky abstractions, coupling, dependency direction, terminology-as-boundary (existing `terminology-semantics`).
- **C2 Bounded Cleanup (Boy Scout Rule)** — clean what you touch, not the whole file. Applies to the *reviewer* too: no demanding whole-file refactors (ties to `scope-creep`).

### D7. Code-health trajectory, not perfection

- **Judgment:** Google's senior rule — approve once the change *definitely improves overall code health*, even if imperfect; "there is no perfect code, only better code" ([eng-practices standard](https://google.github.io/eng-practices/review/reviewer/standard.html)).
- **Direction:** reviews should end with an explicit verdict — net improvement yes/no, and which findings (if any) actually block.

### D8. Calibrated abstention — "LGTM" is a valid output

- **Judgment:** the deepest human/agent gap. No current model achieves calibrated abstention; LLM reviewers systematically underabstain and manufacture findings ([AbstentionBench](https://arxiv.org/pdf/2506.09038), [abstention survey](https://direct.mit.edu/tacl/article/doi/10.1162/tacl_a_00754/131566/Know-Your-Limits-A-Survey-of-Abstention-in-Large), [LLM-as-reviewer](https://arxiv.org/pdf/2605.25415)).
- **Direction:** "an empty findings list is a successful review" belongs in the skill guidance; evaluation should include clean diffs that must produce zero findings, and scoring should penalize unverified findings rather than only rewarding found ones.

### D9. Signal-to-noise discipline (severity labels, nit budget)

- **Judgment:** five nits plus one critical makes the critical look unimportant ([Dan Lew](https://blog.danlew.net/2021/02/23/stop-nitpicking-in-code-reviews/)). [Conventional Comments](https://conventionalcomments.org/) labels (`issue`/`suggestion`/`question`/`nit`, `blocking`/`non-blocking`) make intent machine-checkable; anything a linter can catch should be automated away ([Google on comments](https://google.github.io/eng-practices/review/reviewer/comments.html)).
- **Direction:** findings carry a label and a blocking bit; some cap on nit volume per review; linter-catchable findings suppressed.

### D10. Review as knowledge transfer

- **Judgment:** the top realized value of review is knowledge transfer and team awareness, not defect count ([Bacchelli & Bird](https://sback.it/publications/icse2013.pdf), [Google study](https://dl.acm.org/doi/10.1145/3183519.3183525)). A tasteful comment teaches: names the principle, links repo precedent, shows before/after.
- **Direction:** findings should name the principle and point at repo precedent (e.g., `scheduler_tas_test.go` as the split-test-file pattern) — existing skills half-do this; make it consistent.

## Meta-layer: the behavioral contract

Agents already *know* these principles; the gap is *behavior*. Four mechanisms that should apply across the reviewer skills, however the dimensions above are incorporated:

1. **Two-sided rules only** — no taste rule without a restraint clause.
2. **Proportionality** — mandatory severity + domain weight; a bug always outranks a nit (extends the existing `code-eval` weighting).
3. **Confidence threshold + propose-don't-mandate** — taste findings are phrased as questions and suppressed below a confidence bar (unlike asserted security CWEs). Axis 0 findings are *always* questions — "should this exist" is a conversation with the author, never an assertion.
4. **Respect incumbent structure** — check package conventions before flagging; consistency with the existing codebase beats the textbook ideal.

**Completion requirements**:

Deliberately loose — contributors should propose the packaging per dimension. Roughly:

- [ ] Agree on the two-sided (signal + restraint) format for taste guidance
- [ ] Incorporate Axis 0 dimensions (P1–P3): problem-worth, proportionality, alternatives/tradeoffs
- [ ] Incorporate Axis 1 dimensions (A, B, D1–D4) into the relevant existing skills
- [ ] Incorporate Axis 2 dimensions (D5–D6): risk tiering and failure-scenario requirements
- [ ] Incorporate Axis 3 dimensions (C, D7–D10): verdicts, abstention, severity labels, nit discipline
- [ ] Apply the meta-layer contract across the reviewer skills and `code-eval` scoring
- [ ] Validate against recent merged PRs, including clean diffs that must produce zero findings
