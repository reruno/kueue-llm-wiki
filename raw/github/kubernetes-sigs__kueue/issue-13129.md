## Description

## Summary

Evaluate and implement a short-lived **positive-only** cache for KueueViz WebSocket bearer-token revalidation.

The current `Authenticator.ValidateToken` implementation deliberately bypasses the shared TokenReview cache so every periodic WebSocket re-check observes current token revocation state. This prioritizes authorization freshness, but requires a Kubernetes TokenReview for each active authenticated WebSocket connection on every revalidation interval.

## Rationale

A very short positive cache lifetime (discussed as approximately 2 seconds) may reduce TokenReview/API-server load for concurrent WebSocket connections while retaining a tightly bounded window before revocation or expiry is observed.

This is an optimization follow-up, not a change required for the initial WebSocket token revalidation feature.

## Affected areas

- `cmd/kueueviz/backend/middleware/auth.go`
  - `Authenticator.ValidateToken`
  - TokenReview caching behavior
- `cmd/kueueviz/backend/handlers/websocket_handler.go`
  - Periodic WebSocket token revalidation caller

## Acceptance criteria

- Introduce an explicitly configured, short-lived positive cache for successful WebSocket revalidation results (or document why an alternative design is preferable).
- Do not cache TokenReview errors or invalid/unauthenticated results through this new cache.
- Preserve the existing normal request-authentication cache semantics.
- Ensure revocation/expiry is detected no later than the selected positive-cache TTL plus the existing revalidation cadence.
- Add backend unit tests covering cache hits, cache expiry, and invalid/revoked token behavior after expiry.
- Document the performance/freshness trade-off and the chosen default TTL.
