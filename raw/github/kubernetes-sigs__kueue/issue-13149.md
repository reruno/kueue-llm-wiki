## Description

<!-- Please only use this template for submitting enhancement requests -->

**What would you like to be added:**
Integrate the [Scheduler Library](https://github.com/kubernetes-sigs/scheduler-library/tree/main) into Kueue's admission controller to perform high-fidelity, in-memory scheduling simulations instead of using Kueue's proprietary node filtering logic. Kueue should leverage the library's SchedulingSimulator to maintain a ClusterState and create frozen, non-destructive ClusterSnapshot instances. These snapshots will be used to evaluate workload feasibility (via SchedulePods or CanSchedulePod) and complex preemption sets using the actual upstream Kubernetes scheduler codebase.

This change corresponds to _Strategic Track 1: Common Scheduling Primitives_ from the [WAS and Kueue integration strategy](https://docs.google.com/document/d/13I3bMY-abBtsWmDhCl4RdDHKchHeB3G8zMSTpplmxHA/edit?usp=sharing) document.

**Why is this needed:**
Currently, Kueue maintains its own simplified implementation of node filtering logic (e.g., node selectors, taints/tolerations). This leads to technical debt, duplicate maintenance effort, and divergence from standard Kubernetes scheduling behavior. It is especially difficult to keep up with complex, evolving features like Dynamic Resource Allocation (DRA) or inter-pod affinity.

By adopting the Scheduler Library, Kueue avoids "split-brain" admission decisions. Workloads admitted in Kueue's in-memory simulation will be aligned with the placement decisions of the live kube-scheduler. Furthermore, the library's built-in feature gate emulation and version skew compatibility ensure consistent simulation results across different Kubernetes versions without Kueue needing to implement heavy custom compatibility logic.

**Completion requirements:**

- Refactor Kueue's admission controller to integrate with the scheduler-library.
- Maintain ClusterState within Kueue and utilize SchedulingSimulator to spawn ClusterSnapshots for simulation batches.
- Replace Kueue's internal simplified predicate logic with library feasibility calls (SchedulePods / CanSchedulePod).
- Leverage Transaction Support (Commit/Revert) to simulate and branch complex admission and preemption permutations safely without mutating cluster state.
- Configure Feature Gate emulation to align the simulation behavior with the target cluster's Kubernetes version.
- Add integration tests verifying that Kueue's admission decisions align perfectly with upstream kube-scheduler behavior (including DRA and topology constraints).

### Comment by [@sohankunkerkar](https://github.com/sohankunkerkar) — 2026-08-06T04:56:57Z

While tracing the code paths that #13700, #13702, and #13709 will touch, I noticed a shared design constraint that might be worth considering upfront.
Kueue tracks node occupancy in two places that are updated independently:
1. Per-domain resource counters (tasUsage, assumedUsage) — updated during admission and preemption simulation.
2. The scheduler-library ClusterSnapshot — constructed once per scheduling cycle from tracked pods, immutable after that.

These two don't talk to each other. A few places where this shows up:
- When a workload is admitted mid-cycle, assumed usage is added to the Kueue-side counters but the `ClusterSnapshot` doesn't change. Virtual pods (#13700) would need to update both systems to keep them consistent.
- During preemption simulation (#13702), removing a candidate subtracts from Kueue-side counters, but the `ClusterSnapshot` still has that workload's pods. The `SimulateEmpty` pre-check has the same issue — it zeroes Kueue-side state while the WAS feasibility check runs on the unchanged snapshot.
- Replacing Kueue arithmetic with `SchedulePodsByTemplate` (#13709) makes the `ClusterSnapshot` the capacity source. Until assumed usage is migrated into the snapshot as virtual pods, the library calls will over-count.

Two additional things from the DRA side:
- Virtual pods with `ResourceClaimTemplateName` would fail the dynamicresources plugin PreFilter bc the actual claim doesn't exist yet, and the plugin resolves template references through `pod.Status.ResourceClaimStatuses`. Building virtual pods for DRA workloads would need to synthesize that status or convert to direct claim references.   
- The pod reconciler only tracks pods with a NodeName set. Admitted non-TAS workloads whose pods haven't scheduled are invisible to both systems as no virtual pod mechanism exists for them since there's no topology assignment to derive placement from.

Flagging this since the dual-state boundary is something each issue will hit, and picking a resolution strategy once might save rework.
