## Description

<!-- Please only use this template for submitting enhancement requests -->

**What would you like to be added:**
Enable Kueue to natively parse and respect standard WAS Workload/PodGroup/CompositePodGroup APIs (and corresponding workload-level priority and topology fields) for configuration, moving away from exclusive reliance on proprietary Kueue labels and annotations.

This change corresponds to _Strategic Track 2: Integration of Kueue with WAS APIs_ from the [WAS and Kueue integration strategy](https://docs.google.com/document/d/13I3bMY-abBtsWmDhCl4RdDHKchHeB3G8zMSTpplmxHA/edit?usp=sharing) document.

**Why is this needed:**
Users currently configure gang scheduling and Topology Aware Scheduling (TAS) in Kueue using proprietary markers (e.g., kueue.x-k8s.io/pod-group-name, kueue.x-k8s.io/podset-required-topology). The Workload Aware-Scheduler (WAS) introduces standard, core Kubernetes APIs to express these. Continuing to rely on proprietary labels leads to configuration drift, forces redundant "translation" controllers, and can cause kube-scheduler to reject Kueue admission decisions if they conflict with underlying standard API specs.

**Completion requirements:**

- Enable Kueue to derive Gang Definitions (member pods and total size) directly from standard Workload/PodGroup/CompositePodGroup API fields instead of custom labels.
- Enable Kueue to read Topology Constraints natively from the standard APIs instead of podset-required-topology annotations.
- Integrate standard Workload Level Scheduling Priority into Kueue's internal queue ordering and preemption evaluation logic.
- Ensure backwards compatibility with legacy Kueue labels via appropriate deprecation cycles.

### Comment by [@kannon92](https://github.com/kannon92) — 2026-07-29T19:25:28Z

> Enable Kueue to derive Gang Definitions (member pods and total size) directly from standard Workload/PodGroup/CompositePodGroup API fields instead of custom labels.

I discussed this with @44past4 and @kshalot. 
The idea would be that if a user has a podGroup specified on their pod spec, we can read the podgroup on the podspec. This allows one to surmise the shape of the Kueue workload and avoid having to use Kueue annotations to enforce podgroups.

This supports the use case of "Bring your own podgroup" similar to the idea in https://github.com/kannon92/kubecon-eu-2025-demo/blob/main/examples/bring-your-own-pod-group/README.md#bring-your-own-podgroup.
