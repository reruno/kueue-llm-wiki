## Description

 **What would you like to be added**:
Expose estimated wait time for pending workloads via new Prometheus metrics and an optional Workload status condition, so users can answer "how long will my workload wait?" and operators can detect ClusterQueue saturation.

  **Why is this needed**:
Users see "Pending" with no way to know if admission is minutes or hours away. The Visibility API (KEP-168-2) gives queue position but explicitly excluded ETA: "we don't have the means to estimate wait time at the moment" (#1657). Existing `kueue_admission_wait_time_seconds` is retrospective (recorded after admission), not predictive. #10614 proposed an admission estimation formula for MultiKueue, demonstrating user interest in forward-looking scheduling signals.

  **Completion requirements**:

  This enhancement requires the following artifacts:

  - [ ] Design doc
  - [ ] API change
  - [ ] Docs update

Are we going to introduce a persistent storage of information with historical runs now?

### Comment by [@sohankunkerkar](https://github.com/sohankunkerkar) — 2026-07-17T20:32:13Z

I don't think we need any new persistent storage for this. We already have established patterns in Kueue that we can build on.
1. **In-memory EMA** — same pattern as AFS half-life decay (`calculateAlphaRate`). One float64 per ClusterQueue, optionally persisted to CQ status. Sufficient for Phase 1 (wait time estimation from admission throughput).
2.  **Decaying histogram** — same pattern as VPA recommender. Sparse bucket weights checkpointed to a CRD. VPA has used this for years without any external database. Useful for richer estimates later (runtime distributions for backfill).

Either way: no external database, no time-series store, no new storage mechanism. I will cover more in the design document.

### Comment by [@sohankunkerkar](https://github.com/sohankunkerkar) — 2026-07-20T03:34:58Z

That's a good point. I think [KEP-7029](https://github.com/kubernetes-sigs/kueue/pull/10596) is valuable on its own from a cluster hygiene perspective.

For wait time estimation, though, I don't think we need max execution time as an input. For the first phase, admission throughput together with queue depth should be enough to produce a reasonable estimate, without relying on per-workload runtime information.

If we decide to improve backfilling later, I think observed runtime distributions per ClusterQueue will likely be a better signal than declared time limits anyway. That's a separate discussion though, and I'd rather cover those tradeoffs in the design doc.

### Comment by [@sohankunkerkar](https://github.com/sohankunkerkar) — 2026-07-20T16:26:48Z

In that case the throughput EMA would drop to near zero, so the estimate would correctly surface as unbounded, which is the right signal for the operator. `MaximumExecutionTimeSeconds` wouldn't help here either as long-running Deployments don't set max execution time, and even the `admitted_active_workloads` metric would just show the serving workload sitting there. The value of the estimate in this scenario is surfacing that the CQ has stalled and the operator can then decide whether to adjust priorities, configure preemption, or add quota. Happy to dig into edge cases like this more in the design doc.
