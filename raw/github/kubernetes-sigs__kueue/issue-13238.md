**What would you like to be cleaned**:

MultiKueue currently handles an unavailable worker cluster differently depending on *why* it is
unavailable, and the difference is an implementation accident rather than a design decision
(it comes down to whether `setRemoteClientConfig` is reached in
`clustersReconciler.Reconcile`, see
https://github.com/kubernetes-sigs/kueue/pull/13188#discussion_r3614148249):

1. **Network loss** (kubeconfig is valid but the worker's API server is unreachable): the remote
   client exists and records `disconnectedSince`, so the worker-lost grace
   (`workerLostTimeout`) runs and the admitted workloads are eventually **retried/evicted**.
2. **Configuration error** (missing kubeconfig secret / `BadKubeConfig`): `loadClientConfig`
   fails before the remote client is (re)created. If the manager restarts during the outage the
   worker never enters `remoteClients`, `reconcileGroup` step 6a has no loss time to anchor on,
   and the workloads **requeue forever** and are never retried.

We should decide the long-term behavior and make the two paths consistent. Points raised in the
discussion:

- Eviction after the timeout is arguably the sane default for both causes, with case-by-case
  distinctions where mass eviction is clearly wrong (e.g. an expired token that the admin can
  refresh).
- Whether Kueue was restarted during the outage should be irrelevant to the outcome. Today the
  loss time is tracked in memory only, so a restart re-anchors the grace, and in the
  configuration-error case a restart changes the behavior entirely (grace → requeue-forever).
- Ideally admin misconfiguration would be rejected earlier by a validation webhook or a
  validation stage at the beginning of `Reconcile` (compare e.g.
  https://github.com/ray-project/kuberay/blob/19af0a5e2442cd63a55dc1a3fba83cf8e5f46668/ray-operator/controllers/ray/raycluster_controller.go#L159-L185),
  which would shrink the configuration-error path to transient races. Mass eviction is a heavy
  penalty for a misconfiguration the admin may be about to fix.

**Why is this needed**:

Consistent behavior for unavailable workers is easier to understand and maintain, and the
current requeue-forever outcome after a restart during a configuration error means genuinely
lost workers are never cleaned up.
