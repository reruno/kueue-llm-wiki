## Description

> WDYT about the comment from coderabbit?
> 
> pkg/controller/jobs/pod/pod_controller.go (1) 782-805: 🩺 Stability & Availability | 🔴 Critical | 🏗️ Heavy lift
> 
> Infinite reconciliation loop with heterogeneous pods in fast admission.
> 
> constructGroupPodSetsFast assumes all pods belong to the same role and uses the first pod's roleHash to construct a single PodSet for the Workload. However, it does not verify that subsequent pods actually share this roleHash.
> 
> If a user enables fast admission but submits pods with different roleHashes (e.g., differing resource requests that don't trigger the podExceedsRequests limit, or natively different specs), constructGroupPodSetsFast will successfully create a single-role Workload. In the next sync cycle, FindMatchingWorkloads (which uses strict getRoleHash matching to partition active pods) will discover that the actual pods do not map exactly to the single-role Workload. It will reject and delete the Workload, which constructGroupPodSetsFast will immediately recreate, causing an infinite churn loop.
> 
> To ensure proper controller behavior and availability as per path instructions, verify that all pods have identical roleHashes during fast admission and return an unretryable error if they diverge.

Oh, I think this is a good point that we should investigate. It would be great to prepare an integration test to verify this case before starting to fix it.

### Comment by [@sanskar-singh-2403](https://github.com/sanskar-singh-2403) — 2026-07-23T16:22:42Z

@vladikkuzn @mbobrovskyi @rphillips

I went ahead and built the step-1 integration test to reproduce this before touching the fix, and I want to share what I found because it changes the picture a bit.

I added a spec that submits a fast-admission pod group with two members whose role hashes diverge (different resource requests that don't trip podExceedsRequests). The test passes i.e. it does not reproduce the create → reject → recreate churn.

Tracing why: after constructGroupPodSetsFast builds the single-role Workload from the first pod, on the next sync keptPods partitions down to just that first pod, so jobPodSets is [role-a, count=1]. In equivalentToWorkload ([kueue/pkg/controller/jobs/pod/pod_controller.go at main · kubernetes-sigs/kueue · GitHub](https://github.com/kubernetes-sigs/kueue/blob/main/pkg/controller/jobs/pod/pod_controller.go#L1357)) the count comparison is:

`
if !workloadFinished && wl.Spec.PodSets[j].Count < jobPodSets[i].Count {
    return false
}`

That's a <, not a != so 2 < 1 is false, the Workload is judged equivalent, and it is not deleted. No churn. The observable effect for the plain two-role case is instead a silently un-admitted role-b pod, not an infinite reconciliation loop.

To actually drive delete → recreate churn you'd need keptPods to yield a role that's absent from the Workload (hitting the j == len(wl.Spec.PodSets) early-return at L1353), or a count moving the other way not simply "two pods, two roles."

So before I write the constructGroupPodSetsFast fix: could you confirm the exact conditions you were seeing the loop under? If it's the absent-role scenario I'll extend the repro to that; if the concern is really the silently-gated pod, the fix shape is a bit different. Happy to push the test spec as-is so you can see the reproduction attempt.
