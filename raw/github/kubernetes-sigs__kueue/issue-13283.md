## Description

**What would you like to be added**:
We added the `scheduler-library`-based `SchedulingSimulator` in https://github.com/kubernetes-sigs/kueue/pull/13261, although without granular exclusion tracking.

The `scheduler-library` currently returns `fwk.Diagnosis`, which contains the exclusion strings. We need to either:
1. Delegate exposing this information in a parsed manner to the library.
2. Parse this ourselves.
3. Drop `ExclusionStats` in favor of returning the strings from `fwk.Diagnosis`.

Preferrable - 1.

**Why is this needed**:
To surface proper exclusion reasons for the user.

### Comment by [@andrewseif](https://github.com/andrewseif) — 2026-07-31T12:03:20Z

**Update:** I analyzed the three approaches (exploration done with AI assistance, per the [AI tool usage policy](https://www.kubernetes.dev/docs/guide/pull-requests/#ai-guidance)). Findings from the current integration:

1. `CanSchedulePod` already returns a `*framework.Diagnosis` -> the current WAS checker discards it and records only the lump `SchedulerLibraryNoFit` count (`pkg/cache/scheduler/was/scheduling_simulator.go`).
2. `Diagnosis.NodeToStatus` carries a per-node `*Status` whose `Plugin()` field is typed, so per-plugin attribution requires no string parsing at all.
3. The human-readable reason strings are both unstable and less informative than they once were: `TaintToleration` now returns the generic `"node(s) had untolerated taint(s)"` (the specific taint is only logged at V(4)), and `NodeAffinity` merges nodeSelector and affinity mismatches into a single reason. So full parity with the default checker's granularity (per-taint keys, selector-vs-affinity split) is not recoverable from `Diagnosis` regardless of who parses it ,per-plugin counts are the practical ceiling short of duplicating plugin logic or changing upstream plugins to emit structured reasons.

**Proposal a hybrid of options 1 + 2:**

- **Short term (Kueue, option 2 scoped down):** consume the `Diagnosis` and attribute rejected nodes to exclusion buckets keyed by `Status.Plugin()` only (no message-text parsing), e.g. taints / node affinity counts, plus a catch-all keyed by plugin name for anything unrecognized, replacing the `schedulerLibraryNoFit` lump. The existing `TODO(#13283)` stays as the deferred-removal marker.
- **Long term (option 1, the stated preference):** file a design issue in `kubernetes-sigs/scheduler-library` proposing a typed per-node exclusion API, and switch Kueue to it once available. I'll open that issue and cross-link it here.

One question worth settling in the library design: do we need per-taint detail back (which requires re-running plugin-equivalent checks somewhere), or are per-plugin counts sufficient for the debugging use case?

If this direction sounds right, I'll start with the Kueue-side PR, open an issue in `kubernetes-sigs/scheduler-library` (maybe contribute it myself), and link it here. 

WDYT?
