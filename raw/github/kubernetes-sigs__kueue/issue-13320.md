## Description


## What happened

In a busy multi-tenant cluster with a hierarchical cohort setup, a large-request workload got pinned to the *last* position of every fair-sharing tournament cycle for ~12 hours, even though its ClusterQueue had enough own-nominal quota to accommodate the request without borrowing. Being last then triggered the intra-cycle "overlapping preemption targets" skip — the workload's preemption target set overlapped with every earlier candidate's set, so it was skipped every cycle and never actually issued any preemptions on its behalf.

## Root cause

Kueue's fair-sharing tournament runs recursively: comparisons happen at each level of the cohort tree (leaf ClusterQueue → parent cohort → root cohort). The `FairSharingPrioritizeNonBorrowing` tiebreaker uses the **subtree's aggregated borrowing state at the current tournament level** as its criterion.

The problem: at higher tournament levels the subtree aggregates usage across all descendant ClusterQueues. A workload whose *own leaf ClusterQueue* fits entirely within its nominal quota can still be flagged as "borrowing" at a higher tournament level because a **sibling ClusterQueue** under the same parent cohort is over-consuming. The tiebreaker penalizes the workload for its sibling's borrowing, even though its own admission would require no borrowing at all.

"Fits entirely within own-CQ nominal" is arguably the strongest possible non-borrowing signal — the admission won't trigger reclamation, won't need cross-cohort preemption, and won't add cohort-wide pressure. Yet the current tiebreaker gives it no more weight than a workload that *would* borrow.

## Expected behavior

A workload whose leaf ClusterQueue has sufficient own-nominal quota (post-admission) should be treated as "non-borrowing" at *every* tournament level, not only at the leaf level. Equivalently: the tiebreaker should consider the full descendant path down to the leaf CQ, not only the subtree at the current level.

## Reproducer (generic topology)

```
root-cohort 
  parent-cohort-A  (total subtree nominal = 3000)
       CQ-hero      (own nominal 3000, currently used 500)
       CQ-noisy     (own nominal  0, currently used 2500)
  parent-cohort-B  (total subtree nominal = 50)
       CQ-tiny      (own nominal   50, currently used 60)
```

Both subtrees are currently over their allocated share at root (both "borrowing" at the root tournament level). Submit two workloads simultaneously:
(Assume both have similar Fair Share Weights)

* **Workload H** — 2048 units to `CQ-hero`. Post-admission `CQ-hero` usage: 2548 / 3000. **Leaf CQ is not borrowing** — H fits entirely within `CQ-hero`'s own guarantee. However, Parent-cohort-A is trying to borrow 2048 share at root (its subtree still reports as borrowing), making the post admission parent-cohort-A usage to be 5048/3000
* **Workload T** — 8 units to `CQ-tiny` (a small reclaimer). Post-admission `CQ-tiny` usage: 68 / 50 — the leaf CQ and parent-cohort-B are in borrowing territory, but are borrowing much less as compared to Workload H.

**Expected:** H should win. H fits entirely within `CQ-hero`'s own guaranteed nominal quota; T's admission piles onto an already borrowing leaf CQ as well as parent cohot. The workload that stays within its own guarantee is genuinely the "least borrowing" candidate on the descendant path.

**Actual:** T wins. Both subtrees look "borrowing" at the root tournament, so the non-borrowing tiebreaker is a tie and the comparison falls through to DRF (step 2). Because T is a much smaller request than H (8 vs 2048), T's post-admission subtree DRS is far lower than H's — so DRF picks T. H's leaf-CQ non-borrowing state is never considered anywhere along the way: not at step 1 (the tiebreaker only looks at the subtree at each tournament level), and not at step 2 (DRF ranks by post-admission subtree share, which the large request inflates). A workload that would use only its own guaranteed quota loses to a workload that deepens an existing borrow — purely because it's larger.

## Suggested fix (overview)

Extend the non-borrowing tiebreaker to consider the descendant path from the current tournament level down to the workload's leaf ClusterQueue, rather than only the subtree at the current level.

* **Preferred:** consider a workload "non-borrowing at level L" only if it is non-borrowing at every level from L down to its leaf CQ. A workload that is genuinely fits-within-own-nominal is then preferred at every tournament level, matching the tiebreaker's stated intent.
* **Simpler variant:** at any level, additionally consult the workload's leaf-CQ-level borrowing state, and treat "leaf CQ non-borrowing" as a positive signal at every level.

Either variant reuses the per-level DRS values that are already computed and cached during the tournament. The change is in how the tiebreaker *consumes* those values, not about new computation.

## Workaround used

Temporarily bumping fair-share weight on the ClusterQueue *and* on its parent cohort overpowered DRF at both tournament levels and let the workload win.

## Related

* **Prior fix —** [**kubernetes-sigs/kueue#10149**](https://github.com/kubernetes-sigs/kueue/pull/10149) (merged, present in v0.17.6). Addressed issue #10126 by moving the tiebreaker from a workload-level "requires borrowing" boolean to a per-flavor, per-level subtree check. This issue reports a **further gap**: the per-level check still ignores descendant / leaf-CQ non-borrowing state, so a workload whose leaf CQ has ample nominal is still deprioritized when a sibling CQ is over-share.

### Comment by [@pajakd](https://github.com/pajakd) — 2026-07-24T11:27:53Z

We talked about this with @mimowo and @mwielgus and we have a new idea how to solve this. In your example `parent-cohort-A` is currently within its nominal quota, so the only workload that might preempt workloads from `CQ-noisy` would be the hero workload. The problem is that we stick to the preemption targets that were originally found even if some of them may have already been preempted during this scheduling cycle.

So, actually instead of changing the order in fair sharing (which might just cover this case but would not generalize and might lead to subtle bugs). We propose to reevalute the preemption targets during the scheduling cycle if such overlap is detected. Basically, update the cache and find new targets knowing what is already "taken". This will definitely work as the targets from `CQ-noisy` cannot be preempted by workloads from other cohorts.

In more detail, the main problem in this issue is that the hero workload has overlapping preemption targets with some other workloads considered in this scheduling cycle. Such workload is then skipped https://github.com/kubernetes-sigs/kueue/blob/63618be512856cfa6af895ca7264671e39d87b26/pkg/scheduler/scheduler.go#L447 and reconsidered in the next cycle. This is overly restrictive because

* After preempting targets for the previous workloads, the considered workload might actually fit without requiring further preemptions.
* There may be other targets that the considered workload can preempt.

# Long-term solution
We have the following idea for the fix.

It will consist of 2 PRs:

1. If overlap is detected in the scheduler, remove the already preempted workloads from the snapshot and check if now the workload now fits.
```
victimsOfOtherPreemptions := slices.Collect(maps.Values(preemptedWorkloads))
revertUsage := snapshot.SimulateWorkloadRemoval(victimsOfOtherPreemptions)
(check if workload fits)
revertUsage()
```
2. If the workload does not fit, recompute the candidates for preemption
```
newAssignment, newTargets := s.getAssignments(ctx, &e.Info, snapshot)
```
One important requirement here is to keep flavors as in the original assignment (changing to a different flavor would result in a change in DRS, which should change the order in which the workload is considered).

This change is similar in nature to the following fix in TAS (https://github.com/kubernetes-sigs/kueue/pull/12419), where we recomputed TAS assignment in case of overlaps in assigned nodes between multiple workloads.

I claim that 1 and 2 will fix the customer issue, because since hero workloads wants to use the nominal quota of its CQ, it will have candidates for reclaim in its cohort. And these candidates will not be preempted by other workloads as they are guarded by nominal quota of the cohort. They will only be preempted by the hero workload. But the initial assignment of targets might contain other targets that become invalid during scheduling cycle.

This is a change in a rather complex part of the codebase and needs extensive testing. Each 1. and 2. will be guarded by a separate feature gate.

We plan to deliver the fix in the next patch release (in ~2 weeks).

# Temporary mitigation
If such an issue happens again we recommend possible mitigations. It requires editing the cohorts. I checked (in tests) that both of them work:

1. [recommended] For the cohort that is parent of the hero CQ (`parent-cohort-A`) set the Borrowing Limit to 0. If the issue persists also set the Lending Limit to 0.
2. For the cohort that is parent of the hero CQ set its parent to nil (disconnect this cohort from the rest of the hierarchy).

This works because the hero workload will have no other possible candidates other than the ones in the cohort.

### Comment by [@amy](https://github.com/amy) — 2026-07-28T05:55:12Z

@pajakd @mimowo The long term solution feels similar to something I tried solving last year. Worth it to point out why I gave up (besides the code just not being good at all haha). See if this is useful to you. Has some of Gabe's old comments too 🥲❤️ 

The same approach last year (#6488, #6541, KEP #6776) and closed it after scope exploded. 
- #6488: "Optimize overlapping preemption problem" (issue)
- #6541: "Refresh assignments during scheduling cycle when there's overlapping preemption targets" (implementation PR)
- #6776: "KEP refreshAssignmentsDuringSchedulingCycle" (KEP PR)
- #6581: "Allow 2 preemptors point to the same preemption target in Preempt mode" (issue, referenced in lesson 3)

A few lessons that still apply:

1. "Fits after removing already-preempted workloads" doesn't mean admissible. The freed capacity isn't real until the victims' evictions complete, so admitting on a post-removal fit overcommits quota (https://github.com/kubernetes-sigs/kueue/pull/6541#discussion_r2273264645). If PR 1's fit check passes, I'd suggest requeueing rather than admitting. The workload admits cleanly next cycle once the evictions land.
2. For PR 2, exclude the claimed victims from findCandidates rather than removing them from the snapshot before recompute. Removing them leaks the same phantom capacity into flavor assignment and can produce a false Fit mode with zero targets.
3. Exclusion-based recompute doesn't generalize past this issue's scenario. When an earlier preemptor claims a victim larger than its request, the leftover capacity has no representation, so exclusion either over-preempts an extra victim or returns PreemptionNoCandidates. Solving that generally requires letting preemptors share a victim with fractional claim tracking (#6581), that's what blew up my PR. It's avoidable here because the hero's victims are guarded by its cohort's nominal quota, so its recomputed target set is disjoint; worth stating that boundary explicitly in the design.
4. One latent bug PR 1 will activate: fits() passes both preemptedWorkloads and the entry's own targets to SimulateWorkloadRemoval, which doesn't dedup, an overlapping target gets subtracted twice. Harmless today only because the overlap check early-returns before the result is used.
