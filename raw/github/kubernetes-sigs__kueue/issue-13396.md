This will be achievable by adding appropriate selector in the config to not preempt from particular workloads - which might not be the best UX, as it may require to edit multiple strategies.

### Comment by [@OhDuck47](https://github.com/OhDuck47) — 2026-08-04T13:54:38Z

Hi @dkaluza, thanks for picking this up — an umbrella redesign of preemption config is very welcome.

I'd like to add a use case that I don't think either of the linked initiatives covers, in case it's useful while the API is still being shaped.

We run a 4-tier GPU pool for ML training (p0–p3 at 80k/60k/40k/20k). We want preemption only when the gap exceeds one tier: p0 → p2/p3, p1 → p3, adjacent tiers coexist. The motivation is thrash — near-peer interruptions cost us more in lost training progress than the queueing delay saves.

This can't be encoded in priority values at all. p0 not preempting p1 requires `f(p0) ≤ f(p1)`; p1 not preempting p2 requires `f(p1) ≤ f(p2)`; so `f(p0) ≤ f(p2)`, which contradicts p0 preempting p2.

So: could the new configuration express predicates that are *relative* between preemptor and preemptee, not just each against a constant? #9596 and #8826 are both absolute/categorical in shape, so this may not surface from them — but `preemptor.priority - preemptee.priority > X` would cover us, and it fits the argument in #8869 for general primitives over special-case modes.

Is the design doc that was presented on wg-batch available anywhere?

### Comment by [@dkaluza](https://github.com/dkaluza) — 2026-08-05T06:56:43Z

Hi @OhDuck47,

Thanks for this use case.

I'm not sure if the original presentation from wg-batch is available. We have also refined the design after the presentation - simplified the API while still maintaining same express-ability. 
Nevertheless, you can find my current state of the KEP [here](https://github.com/dkaluza/kueue/tree/configurable-preemptions/keps/13396-configurable-preemptions#proposed-api-preemptionstrategy)
Keep in mind it is still WIP and some parts are still missing this is why I even haven't created draft PR yet.

Coming back to your use case, it is somehow addressed in the design, but not by a priority difference. In the design apart from just relation between priorities(greater equal vs greater etc  ) we also provide priority selectors for both preemptor and preemptee.
This will probably require multiple rules, one for each pair like (p0, p2) in the config, but you should be able to express your use case in the currently planned solution.

Having said that, I'm open for discussion if this is enough of we should replace relation between the priorities with "required difference" or something else, but it will be probably easier to do this when KEP is available as a PR.

### Comment by [@OhDuck47](https://github.com/OhDuck47) — 2026-08-05T08:43:35Z

Thanks for the pointer — I've read through the KEP and it covers our case well.

The `PreemptingWorkloadPrioritySelector` / `CandidateWorkloadPrioritySelector` pair lets us express the per-tier matrix directly, without needing one ClusterQueue per tier. And `minTriggerRequiredDurationSeconds` actually gives us something better than the hard ban we were asking for: adjacent tiers can become preemptable only after a starvation delay, with priority ordering keeping them a last resort rather than a first choice.

Two things I'd like to understand while the design is still open:

1. **Trigger clock and flapping.** The trigger conditions are cleared when the trigger is no longer true. If `InsufficientQuota` oscillates — quota briefly appears but the workload still isn't admitted — does `minTriggerRequiredDurationSeconds` restart from zero? For delays on the order of an hour on a busy cluster, a single transient clear could mean the threshold never elapses. Is any debounce or hysteresis intended here?

2. **Phasing.** Step 0 identifies the minimal subfields needed to migrate existing rules, and Step 4 covers the remaining selectors. The priority selector pair isn't needed to migrate today's `LowerPriority` / `maxPriorityThreshold` behavior, so I assume it would fall into Step 4 — is that right?

Looking forward to the draft PR either way.

### Comment by [@dkaluza](https://github.com/dkaluza) — 2026-08-05T14:48:48Z

Glad to hear this!

Ad 1. Good point, the one solution that I see is to not clear them at all, until admission - which actually makes some sense from specific point of view - because when the workload isn't admitted there has to be some reason for it.  

But on the other hand this can lead to incorrect preemptions - for example if insufficient topology only occurred for a moment and then it was always available (and workload was blocked because of strict FIFO CQ or lack of quota), so clearing still seems like a better solution right now.
Although maybe we can come up with some efficient "debounce or hysteresis" - I do not have an efficient solution in mind here yet.

Ad 2.  I'm still looking into this, but generally the maxPriorityThreshold is not covered by the `RelativeConstraint` so I guess we will need to consider it for the Step 1 (but I cannot promise anything here yet - I'm still discussing the steps with the team, I think we may need to rearrange them)
