## Description

**What would you like to be added**:

For measuring performance and debugging, we often need to specify a set topology (eg/ say I need 8 nodes, I want exactly 1 node in the first rack, 3 nodes on the second rack, and 4 nodes on the third rack). Unfortunately, this feature currently isn't supported by kueue:
- `kueue.x-k8s.io/podset-slice-required-topology-constraints` can only be used to specify different topology layer, but not exact number of nodes on racks
- `kueue.x-k8s.io/podset-slice-size=n` will guarantee a minimum of multiple of n nodes per rack, which means that you could end up with n, n\*2, n, n\*3 (because they are all multiples of n). Also, this doesn't give a way to specify an uneven number (eg/ I want 1, 3, 4 nodes on 3 racks respectively).


**Why is this needed**:

To rightsize the TAS required topology's podset slices, we want the precise number of nodes on different racks to see how it impacts performance. Also, we want to see how an uneven number of nodes on different racks when using TAS preferred topology impacts performance. In some cases, we were able to reproduce hanging given a specific number of nodes on different racks.

This enhancement requires the following artifacts:

### Comment by [@sanskar-singh-2403](https://github.com/sanskar-singh-2403) — 2026-07-23T16:57:39Z

Took a pass through the TAS code to scope what a "precise topology" would actually touch. Sharing a design sketch to get direction before writing a KEP, since this needs an API change.

## Problem restatement

Today a PodSet can express *shape* but not an *exact, uneven distribution*:

- `podset-slice-required-topology` picks the layer a slice must fit in.
- `podset-slice-size=n` forces each slice to a multiple of `n`, so counts land on multiples (n, 2n, 3n) and there is no way to say "1 here, 3 there, 4 there".

The placement itself is decided by `findTopologyAssignment` in `pkg/cache/scheduler/tas_flavor_snapshot.go`: Phase 2 sorts domains by the fill strategy and selects consecutive fitting domains. There is no input path for a caller-supplied per-domain count, so this is genuinely not expressible with the current API.

## Proposed approach

Add an explicit per-domain count request, evaluated as a *required* pin (fail admission if it cannot be satisfied, rather than falling back to the greedy strategy).

Two options for the API surface:

**Option A - counts list (positional)**
A new annotation carrying an ordered list of counts at the requested level, e.g.:

    kueue.x-k8s.io/podset-required-topology: cloud.provider.com/topology-rack
    kueue.x-k8s.io/podset-domain-counts: "1,3,4"

Kueue picks any N domains at that level (N = list length) and pins the counts to them. Good for the perf/debug use case in the description where the user cares about *distribution*, not *which physical rack*. Sum must equal PodSet count.

**Option B - explicit domain-value bindings**
Bind counts to specific domain values, for cases where the exact rack matters (reproducing the hang):

    kueue.x-k8s.io/podset-domain-counts: |
      rack-a: 1
      rack-b: 3
      rack-c: 4

More precise, but couples the workload to physical topology labels and needs richer validation.

I would lean toward starting with Option A (covers the stated motivation, less coupling) and leaving B as a follow-up if there is demand.

## Implementation surface (rough)

- API: new field on `PodSetTopologyRequest` in `apis/kueue/v1beta1/topology_types.go` plus the annotation constant and generated deepcopy/applyconfiguration.
- Validation: `pkg/controller/jobframework/tas_validation.go` - counts sum to PodSet count, list length <= domains available at the level, mutually exclusive with `podset-slice-size`, non-negative.
- Scheduling: `findTopologyAssignment` in `pkg/cache/scheduler/tas_flavor_snapshot.go` - short-circuit Phase 2's strategy sort when explicit counts are present and instead try to satisfy the requested multiset of counts against domain free capacity (this is a bin-fit against available domains; infeasible -> admission failure with a clear reason).
- No change expected in the ungater (`pkg/controller/tas/topology_ungater.go`) since it consumes the resulting `TopologyAssignment` the same way.

## Open questions

1. Required-only, or should there be a "preferred" variant that falls back to the normal strategy when the exact split will not fit?
2. Interaction with slices - is `podset-domain-counts` mutually exclusive with `podset-slice-size`, or should counts be expressed in slices rather than pods?
3. Does this belong under the slice API family or as a top-level PodSet topology request?

Happy to write the KEP if there is agreement on Option A and the required-only semantics. I can also prototype the scheduler change behind the existing TAS feature gate to validate feasibility.

### Comment by [@apullo777](https://github.com/apullo777) — 2026-07-24T02:40:11Z

I took a closer look at the current multi-layer topology-constraints path with this use case in mind. Thanks @sanskar-singh-2403 for the initial scoping. The notes around findTopologyAssignment and matching the requested counts against available domains were helpful.

Building on @mimowo’s suggestion to extend podset-slice-required-topology-constraints with a sizes field, I think there are two semantics worth pinning down before implementation:

1. What does each entry in sizes bind to? Is [1,3,4] intended as an unordered multiset, with TAS still choosing which domains receive those counts, or is each value positionally or explicitly associated with a particular domain? I think this overlaps with the Option A vs. Option B distinction @sanskar-singh-2403 raised above, and the interpretations seem to imply fairly different API and placement semantics.
2. How should heterogeneous sizes compose with multi-layer constraints? The current constraints rely on divisibility between levels. For example, if an outer block constraint has size: 8 and the rack-level distribution is [1,3,4], should sizes only be allowed at the innermost constrained level, or should nesting be supported more generally?

One thing worth flagging is that the implementation scope seems to depend heavily on (1). If the sizes are bound to particular domains, this looks relatively close to validation plus per-domain feasibility checks. If they are an unordered multiset, the current placement path’s model of fungible, equal-sized slices may not generalize directly, particularly if multiple requested groups can share a domain. That may require a different feasibility or packing formulation, and the same uniform-within-a-level assumption appears in related paths such as leader placement and incomplete-slice node replacement.

I have a couple of in-flight items to bring to a stable point first, but I’m very interested in helping shape and prototype this :)

### Comment by [@sanskar-singh-2403](https://github.com/sanskar-singh-2403) — 2026-07-24T08:34:57Z

Thanks @apullo777, this is the right pair of questions to pin down and I think (1) is the fork that determines almost all of the implementation cost. A few things I confirmed re-reading the placement path that might help frame it:

The current multi-layer model is fundamentally single-scalar-per-level. `buildSliceSizeAtLevel` stores a `map[int]int32` (one `Size` per level) and enforces a strict divisibility invariant between layers (`prevSize % layer.Size != 0` is rejected, and every intermediate level is filled with the same uniform `layer.Size`). A `sizes: [1,3,4]` has no single scalar to divide the parent by, so it does not compose with the existing nesting rules as-is. That is the crux of your question (2): I think `sizes` can only be well-defined at the innermost constrained level, with the constraint that `sum(sizes)` equals the count admitted into the parent domain. Allowing heterogeneous `sizes` at multiple nested levels multiplies the feasibility space and I would keep it out of scope for a first cut.

On (1): the placement loop (`updateCountsToMinimumGeneric`) is built on a single `remainingPrimary = count / sliceSize` and greedily fills domains sorted by free capacity (`sortedDomains`, BestFit/LeastFreeCapacity). Slices are treated as fully fungible and equal-sized, and domain selection is a capacity heuristic, not a requested-count match. So:

- Unordered multiset (TAS still picks the domains): this is the smaller delta. You would replace the single scalar with a requested multiset and turn the greedy fill into a bin-fit of the requested counts against domain free capacity, with infeasible -> admission failure. It reuses the existing capacity model but changes the fill from "consume in order" to "match a multiset."
- Positional / explicit domain binding: this couples the workload to physical topology values and needs the assignment to pin specific `levelValues`, which is a heavier lift and, as you note, does not reuse the fungible model at all.

I would argue the multiset interpretation covers the motivating perf/debug use case in the issue (they care about the distribution, not which physical rack), and explicit domain binding is arguably a separable follow-up feature rather than the same one. Worth calling out that the fungibility assumption also shows up in the leader path and in `findIncompleteSliceDomain` (the incomplete-slice replacement keys off `% sliceSize`), so whichever semantic we pick, those paths need to agree on how a heterogeneous split is represented.

You are the owner here, so this is just to save you some digging. Happy to pair on a prototype behind the TAS feature gate to sanity-check the multiset bin-fit if that would help.
