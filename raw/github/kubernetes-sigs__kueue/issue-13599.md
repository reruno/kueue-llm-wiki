## Description

> **Current normative Alpha contract: #13601.** What follows is the original statement of the
> problem and is historical in its design. The Alpha in the KEP requires every alternative of
> one top-level request to map to a single logical resource rather than a charge vector over
> disjoint ones, refuses a charge no active representation can hold exactly rather than
> saturating it, and adds the composition restrictions the KEP documents. Where the two
> disagree, the KEP is the contract.

**TL;DR**

Kueue currently rejects DRA `firstAvailable` requests because the selected subrequest is not known when quota is reserved. For count-based `ResourceClaimTemplate` accounting, Kueue can safely admit them by

1. mapping every subrequest to its Kueue logical quota resource,
2. representing each alternative as a non-negative resource-charge vector, and
3. charging the component-wise maximum over the alternatives of each top-level `DeviceRequest`.

This is the smallest fixed conservative envelope that stays safe without binding the kube-scheduler's eventual choice.

## Current behavior

`pkg/dra/claims.go` counts `Exactly` requests but rejects a request whose `FirstAvailable` field is set:

```text
FirstAvailable device selection is not supported
```

The Workload is marked inadmissible and the owning Job stays suspended.

KEP-2941 lists quota-aware handling of prioritized DRA requests as unsupported, and sketches charging all the mentioned DeviceClasses.

Core Kubernetes `ResourceQuota` accounts at DeviceClass granularity (it charges per-DeviceClass quota resources). Kueue has an extra lever: its DRA configuration can intentionally map several DeviceClasses to one logical quota resource, so Kueue can take the maximum *after* that mapping. That collapses mutually exclusive alternatives that consume the same logical quota instead of summing them.

## Proposed accounting rule

Let `A_q` be the alternatives of a top-level `DeviceRequest` `q`. After resolving a subrequest's DeviceClass through Kueue's DRA configuration, let `charge(q, a)[r]` be the non-negative charge of alternative `a` against logical quota resource `r`.

For each `FirstAvailable` request:

```text
envelope(q)[r] = max over a in A_q of charge(q, a)[r]
```

The per-Pod DRA request becomes:

```text
existing Exactly charges
+ sum over FirstAvailable requests of envelope(q)
```

Existing PodSet scaling is unchanged: Kueue multiplies this per-Pod charge by the effective PodSet count.

The maximum must be computed **after** DeviceClass-to-logical-resource mapping. Taking a maximum per DeviceClass and then summing the mapped classes would still overcharge when several classes map to the same logical resource.

### Safety argument

The kube-scheduler selects exactly one subrequest from each `FirstAvailable`. For every logical resource `r`, the selected alternative's charge is therefore no greater than the component-wise maximum for that request. Summing this inequality over all top-level requests shows the realized charge cannot exceed the admitted envelope.

This assumes every alternative resolves to a complete, non-negative charge vector. Unmapped, unsupported, or unknown request forms must fail closed.

## Examples

Two DeviceClasses mapped to one logical GPU resource:

```text
prefer H100: {example.com/gpu: 1}
else A100:   {example.com/gpu: 1}

envelope:    {example.com/gpu: 1}
map-and-sum: {example.com/gpu: 2}
```

Different counts, same resource:

```text
one H100:  {example.com/gpu: 1}
two A100s: {example.com/gpu: 2}

envelope:  {example.com/gpu: 2}
```

Disjoint alternatives:

```text
GPU alternative: {example.com/gpu: 1}
CPU alternative: {cpu: 8}

envelope:        {example.com/gpu: 1, cpu: 8}
```

The disjoint case stays conservative and can substantially over-reserve quota. This proposal improves overlapping alternatives; it is not a complete fix for over-reservation across disjoint resources. Multiple top-level `FirstAvailable` requests are additive: Kueue sums each request's envelope rather than taking one global maximum.

## Initial implementation scope

To keep the first cut safe and reviewable:

* `ResourceClaimTemplate` references only; direct `ResourceClaim` references and the extended-resource auto-claim path are unchanged.
* `ExactCount` subrequests only; `All` and unknown allocation modes stay rejected.
* Every subrequest must resolve to a logical quota resource, otherwise the request is rejected.
* Count-based `deviceClassMappings` only. A `FirstAvailable` that references a counter-backed or consumable-capacity-backed DeviceClass is rejected initially, because the counter accounting path (`counters.go`) currently processes only `Exactly` requests, so a source-backed alternative cannot be charged correctly yet.
* An Alpha, default-off feature gate; with it disabled, the current rejection behavior is preserved.
* Saturating arithmetic is kept when the envelopes of multiple top-level requests are summed (device counts can approach `MaxInt64`).

Counter-backed and capacity-backed alternatives can be added later by evaluating each alternative through its existing accounting path and taking the component-wise maximum of the resulting charge vectors.

## Selector validation

CEL selectors in every subrequest should at least be compiled and syntax-checked. The existing `Exactly`-oriented device-cardinality validation cannot be reused by treating each alternative as mandatory, since only one alternative has to be satisfiable. For the first cut I propose to compile the CEL deterministically but skip the cluster-cardinality check for `FirstAvailable`, document the limitation, and rely on kube-scheduler plus `WaitForPodsReady`. Silently skipping all selector processing, or requiring every alternative to be satisfiable, would both be wrong.

## Expected tradeoffs

For alternatives that map to disjoint quota resources, the envelope reserves every dimension even though only one alternative will run. This can affect admission eligibility, cohort borrowing, preemption, Admission Fair Sharing usage, workload ordering, and overall quota utilization. These effects are conservative rather than unsafe, but they belong in the KEP as explicit policy tradeoffs.

Post-allocation reconciliation (shrinking the reservation to the realized alternative) is not part of this proposal. It would need its own design for observing the generated ResourceClaims, handling per-Pod choices, and safely updating admitted usage, cache, fair-sharing, borrowing, and preemption state.

## Relationship to #12422

Related to, but not blocked by, #12422. That issue concerns admission-time scheduling feasibility against real nodes and devices; this one only defines a safe quota envelope while the scheduler's eventual choice is unknown. Scheduler-library feasibility can improve admission accuracy later, but it does not by itself bind the eventual `FirstAvailable` selection.

## Test coverage

At minimum:

* two classes mapped to the same logical resource, equal counts;
* two classes mapped to the same resource, different counts;
* alternatives mapped to disjoint resources;
* multiple top-level `FirstAvailable` requests;
* mixed `Exactly` and `FirstAvailable`;
* multiple ResourceClaimTemplates in one PodSet;
* PodSet count greater than one;
* unmapped alternatives;
* `All` and unknown allocation modes;
* counter-backed and capacity-backed alternatives rejected in the initial scope;
* invalid CEL in any subrequest;
* feature gate disabled;
* saturation when summed counts approach `MaxInt64`;
* an integration test where different Pods pick different alternatives while the admitted envelope stays an upper bound.

## Prototype

A proof of concept on `v0.18.3` demonstrated the count-based case: two classes mapped to one `gpu` resource charged `gpu: 1` instead of `gpu: 2`; disjoint alternatives charged both logical resources; the previously rejected Job was admitted and ran to completion. Before an implementation PR I will rebase it onto `main` and handle the counter/capacity paths above, and attach a reproducible branch, manifests, versions, Kueue config, and the observed `Workload.status.admission.podSetAssignments[].resourceUsage`.

Per the discussion below, I will fold this into a KEP-2941 update and rebase the prototype onto `main`. The main open question I would value input on: should the quota path and the feasibility path (#10548) gate on the same count-based subset initially, so they agree on which claims are supported?

The Alpha scope settled narrower than this issue describes, so recording it here before anyone implements from the older text.

Every alternative of one top-level `firstAvailable` request has to map to the same logical resource. A request whose alternatives map to more than one is rejected while the claim is read, rather than charged a multi-dimensional envelope. So the component-wise maximum over a vector reduces to the largest count on one resource, and the disjoint-resource examples above are future work.

Arithmetic that cannot be represented exactly makes the workload inadmissible instead of saturating near `MaxInt64`, and exact means milli scale for `cpu` and scale zero otherwise, since `Quantity.Value()` rounds as well as overflows.

### Comment by [@thc1006](https://github.com/thc1006) — 2026-08-08T13:58:29Z

Correcting one thing in my note above and adding what the scope picked up since.

I wrote that arithmetic which cannot be represented exactly makes the workload inadmissible "instead of saturating near `MaxInt64`", which reads as though `MaxInt64` itself were a finite charge. It is not. `resources.Amount` keeps that value as its `Unlimited` sentinel, and `Info.ResourceUsage` folds the PodSets together through the saturating `Amount.AddInt64`, so a total of `MaxInt64 - 10` on one PodSet plus `10` on another is exact, does not overflow, and still comes out of the fold as unlimited. The finite range is `0` up to `MaxInt64` exclusive.

Four more things settled after that note:

Preprocessing has to keep the logical-resource names a `firstAvailable` request reached, alongside the merged charge. One `ResourceList` per PodSet cannot say which key an envelope is on, and the checked accounting is scoped to those keys, so without that set it would either take in every DRA dimension or miss the shared boundaries. The scope is their union across the workload, not the set for one PodSet.

`excludeResourcePrefixes` is applied before the DRA merge, so a mapping name an excluded prefix covers is charged anyway. Alpha refuses a `firstAvailable` request whose logical resource an excluded prefix covers, and leaves the older question alone for the `Exactly` path.

The non-negative premise is checked at the merge rather than by requiring `WorkloadValidateResourcesAreNonNegative`, since that gate is Beta and an administrator can turn it off.

Two more prerequisites: #14004, where a DRA-backed extended resource is replaced by deleting its whole key, so overhead or a transformation output on that name goes with it, and #14007, where `excludeResourcePrefixes` removing a multiplier leaves `multiplyBy` computing as though it were one.

The reasoning for all of it is in #13601.

Update: #13601 narrowed the Alpha contract after I went through flavor assignment and the accounting path, and two things above are superseded by it. Leaving them here unmarked means anyone reading both sees two designs that contradict each other.

The disjoint alternatives example, `{example.com/gpu: 1, cpu: 8}`, and the matching test case are out. Alpha requires every alternative of one top-level request to map to the same logical resource and rejects a request whose alternatives map to more than one. The reason is flavor assignment rather than the envelope: `Flavors` is keyed by resource, so an envelope reaching two logical resources takes two flavors, and `podset.FromAssignment` copies the node labels of both into one PodSet. That selects a node satisfying every branch at once, while the request asks for any one of them. Cross-resource fallback needs an alternative bound to a flavor, and that is a Beta criterion.

"Saturating arithmetic is kept when the envelopes of multiple top-level requests are summed" is out as well. `math.MaxInt64` is the `Unlimited` sentinel in `resources.Amount`, so clamping there does not report a conservative bound, it reports an unbounded one. The contract is now exact or reject at each step that can produce an unrepresentable charge.

The prototype branch mentioned at the end predates both and should be read as a proof of concept rather than the implementation contract.

### Comment by [@thc1006](https://github.com/thc1006) — 2026-09-02T15:27:21Z

Update: #13601 carries the current design, and the proposal in this issue predates several decisions it makes. Keeping this here as the history rather than the contract.

What changed since:

- Every alternative of one `firstAvailable` request has to map to the same logical resource. Alternatives on different resources are refused rather than charged, because once the claim has been read there is nothing left to say two logical resources were alternatives rather than both needed, and a PodSet assigned two flavors merges their node labels.
- A charge that does not fit the range the queue can represent makes the Workload inadmissible instead of being saturated and admitted. A saturated total no longer stands for the number it replaced, so it cannot carry the bound.
- An explicit `capacity` on a subrequest is charged its declared device count under a source-less mapping, rather than refused. A mapping that configures a counter or capacity source is still refused, since those paths read `Exactly` requests only.
- `excludeResourcePrefixes` applies to the Pod's own requests, and a logical resource an explicit `deviceClassMappings` entry synthesizes stays chargeable, which is what the `Exactly` path already does.
