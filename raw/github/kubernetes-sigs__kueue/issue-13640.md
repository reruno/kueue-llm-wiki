## Description

<!-- Please only use this template for submitting enhancement requests -->

**What would you like to be added**:
Add support for required and preferred Topology-Aware Scheduling (TAS) modes for Elastic Jobs. Currently, the job webhook explicitly rejects `kueue.x-k8s.io/podset-required-topology` and `kueue.x-k8s.io/podset-preferred-topology` annotations for elastic workloads (referencing the TODO in `pkg/controller/jobs/job/job_webhook.go`).

**Why is this needed**:
Topology-Aware Scheduling is critical for optimizing performance in distributed ML/HPC workloads by ensuring pods are co-located. Enabling this for Elastic Jobs unlocks significant performance improvements for flexible slice-based workloads that can scale dynamically.

### Comment by [@sohankunkerkar](https://github.com/sohankunkerkar) — 2026-07-30T12:54:13Z

> cc/ [@sohankunkerkar](https://github.com/sohankunkerkar) since you wrote [#8580](https://github.com/kubernetes-sigs/kueue/pull/8580) -> do you have any gotchas you want to point out that should be kept in mind when implementing? ^

I think @mimowo already covered things but a few gotchas from #8580:
**Preferred:** This is fairly straightforward. For scale-down, we use `TruncateAssignment`, which preserves a valid prefix of the existing assignment. For scale-up, we use `mergeTopologyAssignments` to combine the previous assignment with the delta assignment. Falling back to the greedy algorithm on rank overflow is acceptable for the preferred policy.

**Required:** This is where things get more complicated. During scale-up, we free the previously allocated capacity and compute a new assignment from scratch, so there's no guarantee the new assignment will be a superset of the existing one. As a result, the additional pods may end up on different topology domains than the existing pods. On top of that, the ungater currently falls back to the greedy algorithm on rank overflow, which breaks the required semantics.
