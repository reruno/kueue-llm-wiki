## Description

**What happened**:

On a large cluster with TAS, we released a top-of-the-hour burst of single-Pod workloads (roughly 1-5 per node), each pinned to a target node via labels. Workloads were admitted, but Pods stayed `SchedulingGated` far too long, and we had to bypass Kueue for this pattern (mentioned in https://github.com/kubernetes-sigs/kueue/issues/13148#issuecomment-5013727425).

The `TopologyUngater` algorithm itself is linear and cheap. The limits are in process-level tuning, for which ungating (one Pod patch per Pod) is the highest-volume consumer at scale:

1. **Shared rate limiter:** All patches go through the controller-manager's single client-side rate limiter, shared with the scheduler's own status updates. At the pre-#12440 defaults (QPS 25 / burst 35) the whole process drains at most 25 requests/second; for example, a 10k-Pod burst would take ~7 minutes even if ungating got every token. #12440 raised the defaults to 300/500.
2. **Blocked reconcile workers:** Patches block reconcile workers while waiting for tokens (`MaxConcurrentReconciles` from `groupKindConcurrency`, previously defaulting to 5, now 10 since #12440), so the two limits compound rather than add.
3. **Patch parallelism cap:** Per-workload patch parallelism is hardcoded at 8 (`pkg/util/parallelize`), which becomes the next ceiling for a single large PodSet now that default QPS is 300. For comparison, kube-controller-manager uses slow-start batching that ramps to 500 parallel Pod creations.
4. **Backoff amplification:** While the ungater waits for its patches to be confirmed via the informer, `Reconcile` reports that waiting state as an error (`errPendingUngateOps`). The workqueue treats each occurrence as a failure and doubles the workload's retry delay, so the longer patches sit behind the rate limiter, the larger the accumulated backoff penalty. Any follow-up work for that workload (a failed patch retry, a replacement Pod arriving gated) then waits out that penalty even after the system has recovered.

The scheduler side also contributes for this workload shape: even node-pinned single-Pod workloads pay a full O(domains) TAS evaluation per scheduling attempt. `fillInCounts` resets state across all domains and node matching scans all leaves regardless of how constrained the selector is, and the #13110 node-match cache is keyed per workload so it does not help across many distinct workloads. There is no fast path for fully-constrained PodSets.

There is currently no way to catch this before production: upstream has scale coverage for TAS *assignment* (#13148 + `BenchmarkSchedulerTAS`) but none for the *ungate* path. The TAS performance framework (#8917) creates zero Pods, so the ungater sits idle for the entire run, and the effect of QPS/concurrency settings on end-to-end admitted-to-running latency is untested and undocumented.

**What you expected to happen**:

Documented tuning that ungates bursts of thousands of Pods within seconds of admission, and CI scale coverage so throughput regressions and tuning interactions are caught before release.

**Anything else we need to know?**:

Proposed next steps:
- [ ] add Kwok to Kueue CI
- [ ] Extend the TAS performance framework (#8917) to create real gated Pods, with thresholds on admitted-to-ungated latency (both many-small-workloads and one-large-workload shapes), so tuning defaults are validated at scale in CI.
- [ ] Document the scaling relationship between `clientConnection.qps/burst`, `groupKindConcurrency`, and ungate throughput for large-cluster operators.
- [ ] Make the per-workload patch parallelism cap configurable or adaptive. It is hardcoded at 8 for all bulk-Pod call sites (`pkg/util/parallelize`, also used by the pod-group, LeaderWorkerSet, and StatefulSet reconcilers); for comparison, kube-controller-manager uses slow-start batching that ramps to 500 parallel Pod creations per sync (`SlowStartInitialBatchSize`, `MaxPodCreateDeletePerSync`), throttled only by client QPS.
- [ ] Requeue without error when ungate expectations are pending, to avoid backoff amplification under rate-limiter pressure.
- [ ] Add a `BenchmarkTopologyUngater` mirroring the `BenchmarkSchedulerTAS` approach.
- [ ] Consider a scheduler fast path for fully-constrained PodSets (e.g. short-circuit the TAS evaluation when the node selector resolves to a single node), so bursts of node-pinned single-Pod workloads avoid the per-workload O(domains) scan.

Related: #13148, #12411 / #12440, #12434, #8917, #9992, #8277.
