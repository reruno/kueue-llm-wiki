## Description

**What would you like to be added**:

Context: This is a part of #13149 .
In #13555, Kueue tracks existing Pods and passes them to the scheduling library's ClusterSnapshot.

However, in the current (non-WAS) TAS implementation, all fit checks in Kueue also take into account any anticipated Pod placements resulting from already-made TAS decisions. This includes:

1. Workloads with quota reserved but not yet admitted (e.g. due to pending AdmissionChecks)
2. Workloads which have been admitted but their Pods don't yet exist (too short after ungating)
3. Workloads whose Pods already exist but have not yet been placed on the Kueue-selected nodes.

(Cases 2 & 3 are typically very short-lived but still exist. Case 1 may last long).

We should have such tracking also in the WAS integration.

**Why is this needed**:

Without this, Kueue can easily over-admit workloads to conflicting topology domains.

**Ideas on fixing**:

1. **Short-term:** Create "virtual Pods" representing what Kueue anticipates to happen based on its placement decisions, and inject them into the scheduling library's snapshot object.
 
   Caveats / questions:

   * How exactly should this "injecting" happen? There are at least two ways:
     * [A] As of #13555, a ClusterSnapshot is constructed based on a given slice of (real) `pods`. We could just expand that slice with virtual ones.
     * [B] OTOH, AFAIU from [here](https://docs.google.com/document/d/1MASczp_dvKXjrbhExePxMZfasZN8ukaHopP7y_bNom4/edit?tab=t.rw5qbtt3f021#heading=h.kdxt53wc4gie), it may be more desirable to keep _constructing_ the ClusterSnapshot based only on the real Pods, and _then_ call `SchedulePod()` on all the fake ones. 
   * Some of virtual Pods may have already realized - we'll need careful deduplication.
   * In Case 3 (a Pod exists but has no K8s-scheduler node placement yet) - we may want to prioritize the virtual Pod over the real one, for better simulation fidelity.
     In variant [B] of injecting, this would likely mean preempting the real Pod and scheduling the virtual one.

2. **Long-term:** Once Kueue-WAS integration reaches the level of scheduler workloads, PodGroups or so (cf. #13151), we'll likely want to rely on this, instead of hand-crafting the virtual Pods.
   This will naturally make this issue obsolete for Cases 2 & 3; possibly also for Case 1.

### Comment by [@olekzabl](https://github.com/olekzabl) — 2026-07-31T13:43:09Z

Additional caveat: 

As long as we're dealing with virtual Pods, we may need to add some of them during the scheduling cycle.
My proposal is to follow how resource usage is currently tracked in TAS cache.
AFAICS, in scheduler code, this happens in two places:

* In `processEntry` (the standard path for admitting a workload), [here](https://github.com/kubernetes-sigs/kueue/blob/e88c9b054f10f4a47fe45a3d7d7eb3c81ea61630/pkg/scheduler/scheduler.go#L463)
* Also in [this edge case](https://github.com/kubernetes-sigs/kueue/blob/e88c9b054f10f4a47fe45a3d7d7eb3c81ea61630/pkg/scheduler/scheduler.go#L517)

Why do we need this? A single scheduling cycle may admit up to 1 workload in each ClusterQueue.
It may turn out e.g. that admitting `wl1` in `cq1` has ruled out a possibility of admitting another `wl2` in `cq2` on the same node.
Without adding virtual Pod(s) representing `wl1`, Kueue will not notice this.

(CQs can be freely configured to target overlapping nodes. Or even if disjoint - there can be borrowing).

### Comment by [@tomsen02](https://github.com/tomsen02) — 2026-08-19T04:07:12Z

@olekzabl I'd like to work on this issue and would like to confirm the intended scope before starting the implementation.

My current understanding after #14308 is:

1. Build the cycle-wide simulator snapshot from real scheduled Pods.
2. Derive virtual Pods from quota-reserved TAS Workloads and their TopologyAssignments.
3. Generate virtual Pods only for replicas not already represented by scheduled, non-terminated real Pods.
4. When a new Workload gets a placement during the current scheduling cycle, immediately add its virtual Pods to the same simulator snapshot before evaluating the next entry.
5. Rebuild this derived state every scheduling cycle rather than maintaining a persistent virtual-Pod ledger.

I am leaning toward option B from the issue description: construct the snapshot from real Pods first, then use scheduler-library scheduling operations to place and commit the virtual Pods within their assigned topology domains. This should also work for topology domains above the hostname level.

Proposed scope boundaries:

- preemption snapshot mutations remain in #13702;
- cumulative leader/worker and multi-Pod matching remain in #13709;
- failure-aware invalidation after real kube-scheduler placement failures would remain a separate follow-up, with the existing PodsReady eviction acting as the current recovery mechanism.

Does this match the intended direction? In particular, should #13700 introduce the snapshot mutation API that #13702 can later reuse?
