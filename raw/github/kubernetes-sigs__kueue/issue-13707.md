**What would you like to be added**:

As projects adopt scheduling apis in the workload controllers, kueue needs to figure out how to read these apis to build the right kueue workload.

At a high level, the goal should be that the kueue workload, podgroup and workload should match.

**Why is this needed**:

gangs can be simple but features like partial disruption, topology awareness, DRA for PodGroups and hiearchial gangs tend to require an API. We need a plan to build Kueue Workloads from this controller apis.

I expect each of these can be done as separate PRs once the APIs are added.

### Comment by [@thc1006](https://github.com/thc1006) — 2026-08-11T20:15:26Z

Could we track a DRA accounting profile under this issue as well?

A controller-provided PodGroup can carry ResourceClaims or ResourceClaimTemplates whose allocation scope is the group rather than the individual Pods, so the read path can't derive their quota by treating the claim as part of a per-Pod PodSet request and multiplying by `PodSet.Count`. I left the arithmetic and a counterexample on #14201.

What the read path would have to work out:

- which runtime PodGroups a Kueue Workload covers;
- how many claim instances those groups generate;
- which Workload accounts for each instance;
- how Pod-scoped and group-scoped claims sit side by side without either one being charged twice or hidden.

I'm planning a focused child issue for the exact-once quota invariant, starting with a one Workload to one PodGroup profile. It should stay separate from the allocation-feasibility work in #10548 and from the per-claim `firstAvailable` valuation in #13599 and #13601.

_Disclosure: I used an AI coding assistant while drafting this. I verified the accounting path myself._
