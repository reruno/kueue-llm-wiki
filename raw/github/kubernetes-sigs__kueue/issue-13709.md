## Description

**What would you like to be added**:

Context: This is a part of #13149.
Currently (after #13261, under appropriate FG), given a TAS workload (potentially consisting of one leader and multiple workers):

1. Kueue can use the WAS library to determine the feasible nodes **for the worker PodTemplate**.
   (Depending on FGs, this can happen [here](https://github.com/kubernetes-sigs/kueue/blob/e88c9b054f10f4a47fe45a3d7d7eb3c81ea61630/pkg/cache/scheduler/tas_flavor_snapshot.go#L1762) or [here](https://github.com/kubernetes-sigs/kueue/blob/e88c9b054f10f4a47fe45a3d7d7eb3c81ea61630/pkg/cache/scheduler/tas_flavor_snapshot.go#L1807); the Kueue-WAS mechanics in both cases are the same). 

2. However, then, for every matching node, Kueue uses **its own logic** to answer additional questions:

   A. How many workers can fit on the node? ([code](https://github.com/kubernetes-sigs/kueue/blob/e88c9b054f10f4a47fe45a3d7d7eb3c81ea61630/pkg/cache/scheduler/tas_flavor_snapshot.go#L1853))
   B. Does the leader fit on the node? ([code](https://github.com/kubernetes-sigs/kueue/blob/e88c9b054f10f4a47fe45a3d7d7eb3c81ea61630/pkg/cache/scheduler/tas_flavor_snapshot.go#L1862))
   C. How many workers can fit on the node alongside the leader? ([code](https://github.com/kubernetes-sigs/kueue/blob/e88c9b054f10f4a47fe45a3d7d7eb3c81ea61630/pkg/cache/scheduler/tas_flavor_snapshot.go#L1867))

   Currently, they're all resolved just by Kueue-side resource arithmetics (usage against node capacity).

WAS integration, when enabled, should become responsible for answering these questions [A-C].
(In particular, this involves enabling the `NodeResourceFit` plugin in our scheduling library config).

**Why is this needed**:

1. Without this, Kueue can't fully integrate with WAS, as it will miss e.g. the following scenarios:

   * The leader is not schedulable on a node, in a way only recognizable by WAS logic (e.g. port conflict; cf. #13555).
   * Inter-pod affinity or topology spread restrict the number of workers that can fit on a node, independently from resource constraints.

   In particular, fixing this issue should unblock enabling the `InterPodAffinity` and `PodTopologySpread` plugins.

2. Even if we disregard the above functional gains and consider just "plain resource arithmetics" - dealing with this will ultimately belong to the responsibility scope of WAS (and not of Kueue).
   Then, reorganizing the code to reflect that improves its health (by reducing duplication of logic, preventing future divergence  etc.)

**Completion requirements**:

This enhancement requires the following artifacts:

- [ ] Design doc
- [ ] API change
- [ ] Docs update

The artifacts should be linked in subsequent comments.

### Comment by [@olekzabl](https://github.com/olekzabl) — 2026-07-31T16:51:42Z

Remarks on implementation
(following my earlier sync with @brejman):

* All questions [A, B, C] are just **simulations** - the final number of Pods scheduled may be well below the outcoming answer.
  This poses a problem on how to deal with this in the scheduling library.
  Theoretically, we could happily schedule and revert; however, that would require another level of Transactions nested inside the simulation transactions required for #13702.
  The scheduling library currently does **not** support transaction nesting.

* [A] can be done with [`SchedulePodsByTemplate`](https://github.com/kubernetes-sigs/kueue/blob/e88c9b054f10f4a47fe45a3d7d7eb3c81ea61630/vendor/sigs.k8s.io/scheduler-library/pkg/upstreamsync/snapshot/snapshot.go#L176), necessarily in a dry-run mode which can be requested [here](https://github.com/kubernetes-sigs/kueue/blob/e88c9b054f10f4a47fe45a3d7d7eb3c81ea61630/vendor/sigs.k8s.io/scheduler-library/pkg/upstreamsync/snapshot/types.go#L39).

* [B+C] require scheduling a non-homogeneous group of Pods (leader + workers).
  For this, we need [`SchedulePods`](https://github.com/kubernetes-sigs/kueue/blob/e88c9b054f10f4a47fe45a3d7d7eb3c81ea61630/vendor/sigs.k8s.io/scheduler-library/pkg/upstreamsync/snapshot/snapshot.go#L170) for a collection of leader & virtual workers spawned from the template (whose number can be limited by what we obtained from [A]). Here, options should specify both dry-run and `StopOnFailure`.
  
* @brejman raised concern that the above strategy is suboptimal in performance.
  Ideally, we would schedule the leader first, fill with as many workers as possible, then unschedule the leader, then fill up with workers again.
  However, doing so would require additional support from the scheduling library.
  (@brejman suggested that WAS could add a `TryUnschedule` operation which would either unschedule the leader or fail in harder cases; on failure, to be able to gracefully recover, we'd also need backup/restore operation on snapshots to be able to fall back to the original slow path).
  Anyway, this follow-up direction is blocked on WAS side support.

### Comment by [@olekzabl](https://github.com/olekzabl) — 2026-07-31T16:58:53Z

**Likely blockers:**

Just replacing current Kueue resource arithmetics [A, B, C] with scheduling library calls is not going to work fully correctly, unless #13700 and #13702 are addressed.

Interestingly, this is quite analogous to the situation from #13555 where we agreed that such inexactness does not prevent the PR from being merged; after all, this is all hidden behind a "WAS integration" alpha FG.

Yet, I'd doubt that the same reasoning may be applied in this case.
In #13555, the impact of merging despite #13700 and #13702 remaining unresolved feels minor; port conflicts feel like rare events, and co-occurrences / preemptions around them feel like edge cases.
Here, the story is different. Doing "usage vs. capacity" calculations ignoring in-flight workloads and preemption assumptions is a guarantee of making wrong admission decisions nearly every time (as long as any resource on the cluster is well utilized).

Therefore, I'd lean towards treating #13700 and #13702 as blockers for this.
