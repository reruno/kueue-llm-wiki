**What would you like to be added**:

A KEP defining when and how Kueue should express gang-scheduling intent on the Jobs it manages through spec.scheduling.schedulingPolicy, introduced by KEP-5547.

When a Job has not specified a scheduling policy, Kueue could default it to `gang: {}` behind a Kueue feature gate. An explicit `basic: {}` would act as an opt-out, and Kueue would never overwrite a value set by the user.

This covers the write side of the Job × WAS integration. It complements #13707, which tracks the read side: building the corresponding Kueue Workload from controller-provided WAS APIs.

This follows the discussion in #13533, where @mimowo asked for this to be settled in a KEP and @kannon92 suggested I drive the Kueue side.

The KEP should define:

- which Jobs are eligible for gang defaulting and what value Kueue injects;
- an explicit opt-out and the rule that user-provided values are preserved;
- a root-Job-only guard, so child Jobs owned by another Kueue-managed controller are skipped;
- the Kueue feature gate and the behavior when the upstream `WorkloadWithJob` gate is disabled or the WAS API is otherwise unavailable;
- the suspend and resume lifecycle; and
- interactions with partial admission, workload slices, elastic Jobs, and `waitForPodsReady`.

For Jobs, Kueue would only express scheduling intent through the Job API. The Job controller would remain responsible for creating or compiling the corresponding WAS objects.

**Open design questions**

- Should Kueue default all managed Jobs to gang scheduling, or only Jobs with properties such as `completions == parallelism` and `completionMode: Indexed`? The gang-satisfaction policy for replacement Pods is still being discussed upstream in kubernetes/kubernetes#136334.
- How should defaulting interact with the read path? Once Kueue defaults `gang`, the Job controller can produce a Workload whose `minCount` is derived from `parallelism`. If partial admission then lowers `parallelism` at admission time, #13150 may read that value back, creating a feedback loop across controllers. If a user sets an explicit `minCount`, upstream validation also rejects lowering `parallelism` below it, which would block partial admission for that Job entirely.
- Should the policy be controlled only by a feature gate, or also by a Kueue configuration option?
- Should the initial alpha scope cover only `Job`, while documenting how other integrations could adopt the same mechanism later?


**Why is this needed**:

Under KEP-5547, a Job that omits spec.scheduling uses the Basic policy. Without integration in Kueue, users would therefore need to opt into gang scheduling on every Job manually.

Many queued batch and AI workloads benefit from all-or-nothing placement, so Kueue should have a defined and predictable way to express that intent for the Jobs it manages while preserving explicit user choices.

The design can proceed now, while implementation would depend on the upstream APIs targeted for Kubernetes 1.37.

Happy to adjust the boundary if any of this overlaps with work already planned elsewhere.
