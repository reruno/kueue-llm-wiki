## Description

**What would you like to be cleaned**:

#13674 added integration tests for hierarchical cohort scheduling (reparenting, mid-tree deletion, lendingLimit, borrowingLimit, burst queues). All of those scenarios exercise capacity in the grow direction: a workload that could not be admitted becomes admissible after a topology or quota change.

The shrink direction has no coverage: what happens to already-admitted workloads when a hierarchy change reduces the capacity available to their ClusterQueue below current usage. The invariant under test is the same across all scenarios: capacity reduction never evicts admitted workloads, and only new admission attempts see the reduced capacity.

Proposed integration tests (in `test/integration/singlecluster/scheduler/scheduler_test.go`, reusing the fixtures introduced in #13674):

| # | Scenario | What It Validates |
|---|----------|-------------------|
| S1 | Reparent child cohort to a smaller root while subtree usage exceeds the new subtree quota | Admitted workloads survive the reparent; new workloads stay pending |
| S2 | Reduce nominal quota on an ancestor Cohort below current subtree usage | Same invariant with a quota edit instead of a topology change |
| S3 | Tighten `lendingLimit` on a lender Cohort while a sibling holds admitted borrowed workloads | Borrowed workloads survive; new borrowing is capped at the new limit |
| S4 | Set `borrowingLimit: 0` on a Cohort whose ClusterQueue is actively borrowing | Borrowing workloads survive; no new borrowing |
| S5 | Reparent the lender subtree away so the borrower's capacity source leaves the tree | Complements the mid-tree deletion test from #13674 with a reparent trigger |
| S6 (stretch) | Shrink with `reclaimWithinCohort` enabled | Reclaim happens only through normal preemption on subsequent admission attempts, never as a spontaneous eviction |

**Why is this needed**:

A wrong implementation of any shrink path could evict or panic, and the grow-direction tests from #13674 would not catch it. Quota reduction and reparenting are routine admin operations in multi-tenant hierarchies (KEP-79), so the no-eviction guarantee deserves explicit regression coverage.
