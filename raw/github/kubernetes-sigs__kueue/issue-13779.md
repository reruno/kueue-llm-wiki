## Description

**What would you like to be added**:

A way for a Job blocked on a missing `WorkloadPriorityClass` to be reconciled promptly once that class is created, rather than waiting for the next retry.

**Why is this needed**:

A Job whose `kueue.x-k8s.io/priority-class` label names a class that does not exist cannot have its Workload built, so reconciliation returns an error. #13775 reports that on the Job as a Warning event, and an integration test there covers that the Workload does appear once the class is created.

What it appears on is the timing. The job controller is set up as `For(job).Owns(&kueue.Workload{})`, so nothing enqueues the Jobs that reference a class when that class is created. `WorkloadPriorityClassReconciler` does react to the class, but it lists existing Workloads to update their priority, and in this case no Workload exists yet.

So recovery comes from the reconcile retry alone. With controller-runtime's default rate limiter the exponential backoff tops out at 1000s, so a Job that has been failing long enough to reach the ceiling can sit for up to about 16 minutes after the class is created before anything happens. Creating the class is the obvious remedy for the misconfiguration, and it looking like it did nothing is a poor experience.

A shape that would work is a field index on the priority-class label plus a watch on `WorkloadPriorityClass` that enqueues the Jobs referencing the created class. Worth weighing before anyone builds it:

- the index would be needed per integration, since every job kind carries the same label, so the memory cost lands on every Kueue deployment for a recovery path that only misconfigured Jobs use;
- `WorkloadPriorityClassReconciler` already watches the class, so the enqueue could live alongside what is there rather than as a new controller;
- whether the same treatment is wanted for a class that is deleted and recreated;
- whether the backoff ceiling is better addressed for this error class generally, which would be smaller than an index.

I have not measured the delay on a real cluster; the numbers above come from reading the setup and the controller-runtime default.
