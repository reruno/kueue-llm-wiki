## Description

**What would you like to be added**:

A decision on what should happen when the `kueue.x-k8s.io/priority-class` label is added to a Job whose Workload already takes its priority from a Pod `PriorityClass`. Today the label is accepted and has no effect.

**Why is this needed**:

`UpdateWorkloadPriority` re-resolves the label only when the Workload has no priority or already carries a `WorkloadPriorityClass`:

```go
if (workload.HasNoPriority(wl) || workload.IsWorkloadPriorityClass(wl)) && jobPriorityClassName != wlPriorityClassName {
```

A Workload backed by a Pod `PriorityClass` satisfies neither, so no lookup happens. `ValidateUpdateForWorkloadPriorityClassName` only blocks adding the label to a running Job and blocks removing it, so adding it to a suspended Job is admitted. The result is a label that is stored, shown in `kubectl get job -o yaml`, and does nothing.

The exclusion itself looks deliberate: it was asked for during the review of #8480, so this is not a request to drop it. What seems worth revisiting is only the silence around it.

It is narrower than it first looks. With no Pod `PriorityClass` and no cluster-wide default, `getDefaultPriority` returns a nil `PriorityClassRef`, so `HasNoPriority` holds and the label is resolved normally. The gap applies to Workloads that really do carry a Pod `PriorityClass` reference, whether from the pod template or from a global default.

Roughly three ways out, in increasing cost:

1. reject the change in the Job webhook, so the label cannot be added where it will be ignored;
2. report it, in the same shape as the missing-class event in #13775;
3. support the transition, which would need the Job controller, the Workload controller and validation to agree on it.

### Comment by [@vic-comm](https://github.com/vic-comm) — 2026-10-10T17:44:02Z

Looking at the three options, Option 1 (rejecting the change in the webhook) seems like the most robust path. 

Allowing a `kueue.x-k8s.io/priority-class` label to be admitted when the Workload already derives priority from a Pod `PriorityClass` introduces ambiguous configuration intent. Failing closed in the validation webhook prevents this conflicting state from ever entering etcd, which avoids the silent ignore behavior entirely.

If there is consensus on Option 1, I could implement this by updating the validation logic (e.g., `ValidateUpdateForWorkloadPriorityClassName`) to block the label addition when a Pod PriorityClass is already present.

### Comment by [@thc1006](https://github.com/thc1006) — 2026-10-10T18:39:53Z

Thanks for looking into this and offering to take it on, @vic-comm.

There's one case option 1 would miss: a Workload can also get its Pod PriorityClass from the cluster's default PriorityClass, which never appears on the Job. `ValidateUpdateForWorkloadPriorityClassName` only receives the old and new Job, so the webhook would need to look up the default class itself to catch it. Option 1 would also reject an update that works today, so it would probably need an ACTION REQUIRED release note.

Option 2 (an event) has neither problem. Still, Kueue deliberately doesn't update the priority of a Workload that uses a Pod PriorityClass (`Updates to Pod Priority are not supported` in `PriorityChanged`), so I'd leave the call to @mbobrovskyi and @mimowo.
