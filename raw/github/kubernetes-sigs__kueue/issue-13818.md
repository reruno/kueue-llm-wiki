**What happened**:

Follow-up to https://github.com/kubernetes-sigs/kueue/pull/13764 (discussion: https://github.com/kubernetes-sigs/kueue/pull/13764#discussion_r3708832253).

With #13764, the TAS non-TAS usage cache updates when a pod's spec resources change (in-place resize). Spec-based accounting frees capacity as soon as the spec changes, but kube-scheduler keeps charging the old value until the kubelet actually completes the resize. So a requeued TAS workload can land on a node kube-scheduler still considers full, leaving its pods Pending. For CPU that window is seconds, but for a memory limit decrease the kubelet waits for usage to drop below the new limit.

**What you expected to happen**:

Kueue accounts non-TAS pods the way kube-scheduler does, using `resourcehelpers.PodRequests(pod, PodResourcesOptions{UseStatusResources: true})` on the full pod. Capacity then frees exactly when kube-scheduler frees it, and the requeue only fires for capacity that actually exists.

This changes the cache's accounting contract (`resources.NewRequestsFromPodSpec` is spec-only throughout), and the Update predicate must also fire on `status.containerStatuses[].resources` changes, since freeing becomes status-driven.

**How to reproduce it (as minimally and precisely as possible)**:

1. On a TAS-relevant node, run a non-TAS pod whose memory limit is then decreased in place while its usage is above the new limit.
2. Kueue (with #13764) frees the capacity immediately based on spec and requeues TAS workloads.
3. kube-scheduler still charges the old value until the kubelet completes d TAS workload's pods stay Pending.

### Comment by [@sohankunkerkar](https://github.com/sohankunkerkar) — 2026-08-04T16:27:48Z

The question is whether the TAS scheduler hits that window in practice. The batched drain runs every 10s, so for CPU resize-down: spec changes → cache updates immediately → requeue fires → TAS workload tries to schedule → but kubelet finishes the resize in seconds anyway, so by the time the scheduler cycle runs the capacity is real. The race is more theoretical than practical for CPU.

For memory: it's real. If a pod's memory usage stays high, the kubelet won't actuate the resize, and the cache would show freed capacity that doesn't exist. But this requires someone doing in-place memory resize-down on a TAS node while a TAS workload is waiting —> that's a narrow scenario.
So: CPU → ~0% chance of hitting the race window. Memory → possible but requires a specific sequence. Not 0%, but unlikely without deliberate setup.
