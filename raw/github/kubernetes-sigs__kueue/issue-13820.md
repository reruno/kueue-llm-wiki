## Description

**What happened**:

`UpdateWorkloadPriority` resolves the WorkloadPriorityClass separately for every Workload it is given, so a reconcile that updates more than one Workload performs more than one lookup. Each lookup can observe a different value of the same class, and the resulting Workloads keep whatever value their own lookup returned.

## Where the lookups come from

`UpdateWorkloadPriority` calls `PrepareWorkloadPriority`, which calls `ExtractPriority`, which does the `Get`. Nothing is carried between calls, so N Workloads means N reads of the same class in one reconcile.

The LeaderWorkerSet reconciler is the sharpest case, because the calls are concurrent rather than sequential:

```go
eg.Go(func() error {
	return parallelize.Until(ctx, len(toUpdate), func(i int) error {
		return r.updateWorkload(ctx, lws, toUpdate[i])
	})
})
```

`updateWorkload` calls `jobframework.UpdateWorkloadPriority`, so a LeaderWorkerSet with N component Workloads to update fans out into N goroutines that each resolve the class independently. If the class value changes while that fan-out is in flight, the components can be written with different values of the same class.

The same shape exists sequentially in the generic path. #13780 adds a second one, where a scale-up keeps a quota-reserved slice alongside its pending replacement and both are updated in one reconcile.

## Why it does not settle on its own

`WorkloadPriorityClassReconciler` lists by class name:

```go
client.MatchingFields{indexer.WorkloadPriorityClassKey: wpc.Name}
```

After a divergence every affected Workload already names the same class, so the next value update for that class does list them all and bring them back together. There is no guarantee of such an update, though, and until one happens the Workloads of a single owner are ordered against each other during preemption using different values.

**What you expected to happen**:

One reconcile resolves the class once and applies the same reference and value to every Workload it updates.

**How to reproduce it (as minimally and precisely as possible)**:

I have not reproduced this on a cluster; the window is small and I have no way to drive it reliably. It is visible in the code:

1. `pkg/controller/jobs/leaderworkerset/leaderworkerset_reconciler.go:233-235` fans `updateWorkload` out through `parallelize.Until`.
2. `leaderworkerset_reconciler.go:447` calls `UpdateWorkloadPriority` from inside that fan-out.
3. `pkg/controller/jobframework/reconciler.go:1198` reaches `PrepareWorkloadPriority`, and `ExtractPriority` performs a fresh `Get` of the class on every call.

**Anything else we need to know?**:

## Scope

Seven call sites reach these two helpers today:

- `pkg/controller/jobframework/reconciler.go:955, 1124, 1198, 1596`
- `pkg/controller/jobs/leaderworkerset/leaderworkerset_reconciler.go:311, 447`
- `pkg/controller/jobs/statefulset/statefulset_reconciler.go:319`

Because the helpers are shared, a fix belongs to them rather than to any one caller. I raised this on #13780 and deliberately did not change it there: that PR fixes a slicing bug, and narrowing a shared helper's behaviour from inside it would have addressed the smaller of the two instances while leaving the LeaderWorkerSet fan-out untouched.

## A shape that would work

Separate resolving the class from applying it. `PrepareWorkloadPriority` currently does both; if the resolved reference and value could be passed in, a caller with several Workloads could resolve once and apply the same pair to each. That also makes a missing class fail before the first write rather than partway through.

One detail needs deciding first: `ExtractPriority` takes the Workload's PodSets, because the fallback path reads `priorityClassName` from the pod template. Callers with several Workloads would have to say which PodSets the single resolution uses, or the split would have to apply only to the label path.

## What this is not

This is not about a class being renamed on the Job, which is handled, nor about `PodPriorityClass`-backed Workloads, which are excluded on purpose (#8480, #13781).

### Comment by [@thc1006](https://github.com/thc1006) — 2026-08-06T07:41:05Z

Still present on main. `updateWorkload` calls `UpdateWorkloadPriority` from inside `parallelize.Until`, so a LeaderWorkerSet with N component Workloads to update fans out into N goroutines that each resolve the class.

I have the update half of this on a branch. The helper that #13780 added already resolves once for a batch and applies the same reference and value to each, so the caller can hand it the whole set after the per-component work instead of calling it per component. A test that counts `WorkloadPriorityClass` reads through an interceptor goes from 2 to 1 for two components, and fails again if the per-component call is put back.

Two things worth saying before that becomes a PR.

The create path is the other half and is not covered by it. `createWorkload` calls `PrepareWorkloadPriority` per component as well, but it constructs the Workload inside that function, so resolving once there means splitting construction from creation. That is a larger change and I would rather not fold it in.

The batch resolves the class using one workload's PodSets, which is what #13780 settled on. That only matters where the object carries no priority-class label and the value falls back to a pod template, and a LeaderWorkerSet can have different leader and worker templates. Applying one value to the whole set is what this issue asks for, but it is a behaviour change and should be stated in the PR.

I am holding the PR until #13775 merges, since it wraps the same call sites to report a missing class from inside the worker, and moving the call changes where that error surfaces.
