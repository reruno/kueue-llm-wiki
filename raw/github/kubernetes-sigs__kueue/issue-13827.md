## Description

**What happened**:

A StatefulSet whose Workload already exists keeps its old priority when the `kueue.x-k8s.io/priority-class` label is changed. The webhook accepts the change and nothing applies it.

## Where the two halves disagree

`reconcileWorkload` handles the case where the Workload exists. It syncs the owner reference, the queue name, the `AdmissionGatedBy` annotation and the scale-to-zero hold state, and calls neither `UpdateWorkloadPriority` nor `PrepareWorkloadPriority`. Priority is resolved in one place only, `createPrebuiltWorkload`, which runs when there is no Workload yet.

The webhook, meanwhile, decides whether the StatefulSet counts as suspended from its replica status:

```go
isSuspended := oldStatefulSet.Status.ReadyReplicas == 0
```

and then applies the shared `ValidateUpdateForWorkloadPriorityClassName`, which refuses only two things: adding the label to a running workload, and removing it. Changing one class name for another is allowed, and so is adding the label while `ReadyReplicas == 0`.

So the label update is admitted, stored, and visible in `kubectl get statefulset -o yaml`, while the Workload keeps whatever priority it was created with.

**What you expected to happen**:

Either the change is applied to the existing Workload, the way the generic Job path applies it, or it is refused at admission. What should not happen is that it is accepted and ignored.

**How to reproduce it (as minimally and precisely as possible)**:

1. Create a StatefulSet managed by Kueue with `kueue.x-k8s.io/priority-class: low`, and let its Workload be created.
2. Scale it to zero, so `status.readyReplicas` is 0.
3. Change the label to `high`.
4. The update is admitted. The Workload still carries `low`.

Pointing the label at a class that does not exist behaves the same way, and reports nothing, since the lookup that would fail is never reached.

**Anything else we need to know?**:

## Relation to the other silent boundaries

This is the same shape as two issues already open, where the API accepts a priority-class label change that the controller then does not apply:

- #13778, the compatible workload-slice path, which returns before the priority sync;
- #13781, a Workload whose priority came from a Pod `PriorityClass`, which is excluded on purpose.

This one differs from #13781 in that nothing appears to have decided it. The generic path gained `none -> WorkloadPriorityClass` and `old -> new` handling in #8480, and the StatefulSet reconciler was simply never given the same call.

## Deciding it

Applying the change looks like the smaller answer, since the generic path already defines the transition rules and the StatefulSet reconciler already batches its Workload mutations behind one `shouldUpdate` flag, so the priority could join that update rather than issuing a second one. Refusing it at admission is the other option, but it would have to explain why the same change is allowed on a Job.
