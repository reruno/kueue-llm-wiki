## Description

# kueue.x-k8s.io/managed finalizer not reliably removed during Workload eviction, leaving pods stuck and driving owning controllers into a create/delete thrash loop

## What happened

During a full Workload eviction (`Stop()`), the `kueue.x-k8s.io/managed` finalizer is
sometimes not removed from one or more pods even though their containers have already
terminated. The pod is left with `deletionTimestamp` set indefinitely.

For a StatefulSet-owned pod, this blocks the StatefulSet controller from ever creating a
replacement with the same ordinal name — the tenant never recovers.

For Deployment-owned pods, the stuck pod appears to desynchronize Kueue's own excess-pod
accounting for that role: the controller repeatedly creates a replacement pod and almost
immediately deletes it as excess (`ExcessPodDeleted`), in a tight loop that produced
thousands of create/delete events within a few minutes in our testing, until we manually
stripped the finalizer from the stuck pod(s).

## Reproduction (4 independent trigger paths, same symptom every time)

We use plain-Pod group integration (`kueue.x-k8s.io/pod-group-name` +
`pod-group-total-count` + `pod-group-serving: "true"`) to join pods from 3 Deployments and
1 StatefulSet into a single Workload, with:

```yaml
waitForPodsReady:
  enable: true
  timeout: 10m
  recoveryTimeout: 90s
  blockAdmission: false
  requeuingStrategy:
    timestamp: Eviction
    backoffBaseSeconds: 60
    backoffMaxSeconds: 600
```

Every one of the following triggered the same finalizer-stuck / thrash-loop symptom:

1. Manually scaling the StatefulSet replica to 0 and back to 1.
2. Toggling `Workload.spec.active` false → true on Kueue v0.17.2.
3. Toggling `Workload.spec.active` false → true on Kueue v0.19.0 (latest stable at time of
   testing — confirmed not fixed by the version bump).
4. A real kube-scheduler priority preemption of two of the four group members (not a manual
   Kueue-side action at all) — same result: the two preempted pods terminated cleanly, but
   after `recoveryTimeout` evicted the whole group, one StatefulSet pod and one Deployment
   pod were left with `deletionTimestamp` set and `kueue.x-k8s.io/managed` still present,
   containers already in `terminated`/`Completed` state, and the Deployment(s) whose pods
   were affected went into the create/delete thrash loop described above.

In all four cases, `kubectl patch pod <name> --type=merge -p '{"metadata":{"finalizers":[]}}'`
on the stuck pod(s) immediately stopped the thrash loop and let the group recover normally.

## Environment

- Kueue: reproduced on both v0.17.2 and v0.19.0
- Kubernetes: v1.35 (kubeadm/kubespray-managed cluster, containerd)
- Integration: plain-Pod group (`pod`), `waitForPodsReady` enabled, no cohort, no ClusterQueue
  preemption configured (arbitration between tenants is handled entirely by
  PriorityClass + default-scheduler, outside Kueue)

## Expected behavior

The `kueue.x-k8s.io/managed` finalizer should always be removed once a pod's containers have
terminated and Kueue's own bookkeeping for that pod's deletion is complete, regardless of
what triggered the eviction (manual scale, `spec.active` toggle, or scheduler preemption).

## Root cause (from reading pkg/controller/jobs/pod/pod_controller.go on main @ 047967bb, same on v0.19.0)

`Stop()` (pod_controller.go:510, :502 on v0.19.0) deletes group member pods via `c.Delete()`
for any `stopReason`, but only calls `p.Finalize()` — which unconditionally strips the
`kueue.x-k8s.io/managed` finalizer from every pod in the group — when
`stopReason == StopReasonWorkloadDeleted`. For a `recoveryTimeout` eviction the reconciler
calls `stopJob` with `StopReasonWorkloadEvicted` (reconciler.go:574), so `Finalize()` is never
called; finalizer removal for these pods is left entirely to the ordinary per-pod
reconciliation via `FindMatchingWorkloads`/`ConstructComposableWorkload`. Two independent gaps
in that path account for the two symptoms we saw:

**StatefulSet member (structural deadlock).** In `FindMatchingWorkloads`, a role's inactive
pods only get finalized once `finalizeablePodsCount = min(len(roleInactivePods),
len(roleInactivePods)+len(roleActivePods)-int(ps.Count))` is positive (pod_controller.go:1290,
:1282 on v0.19.0) — i.e., only once a *new* active pod for that role already exists alongside
the old one. For a StatefulSet-owned pod, the API server refuses to create a replacement with
the same ordinal name while the old pod object still exists in etcd (even mid-deletion), and
it can't be removed from etcd without the finalizer being gone first. New active pod is
required to unblock the finalizer; the finalizer is required to allow the new active pod to
exist. Neither side moves without external intervention.

**Deployment member (misclassification, not a deadlock, but same outcome).**
`isPodRunnableOrSucceeded` (pod_controller.go:896, :888 on v0.19.0) only treats a pod with
`deletionTimestamp` set as "inactive" when its `NodeName` is *also* still empty:

```go
func isPodRunnableOrSucceeded(p *corev1.Pod) bool {
	if !p.DeletionTimestamp.IsZero() && len(p.Spec.NodeName) == 0 {
		return false
	}
	return p.Status.Phase != corev1.PodFailed
}
```

A pod that already ran, terminated cleanly (`Phase: Succeeded`), and is now stuck with
`deletionTimestamp` set (our stuck-finalizer case) keeps its `NodeName`, so the special case
is skipped and it's classified as **active** purely because `Succeeded != Failed`.
`sortActivePods` (pod_controller.go:951, :943 on v0.19.0) then prefers to keep non-gated pods
over gated ones when deciding which "excess" active pods to remove — and the fresh legitimate
replacement pod is still `SchedulingGated` (waiting for the group to be re-admitted) while the
misclassified stuck pod is not gated (it already ran). So the *new* pod is the one picked as
excess, finalized, and deleted — and the owning ReplicaSet immediately creates another
replacement to satisfy its desired replica count, which is gated again and again picked as
excess against the same permanently-present stuck pod. This is the create/delete thrash loop
we observed (thousands of `ExcessPodDeleted` events within a few minutes), and it never
resolves on its own because the actually-stuck pod is never even considered by
`finalizePods`/`removeExcessPods` — it's misclassified as active the whole time.

Neither of these paths is reached by anything that unconditionally clears the finalizer once
a pod's containers have terminated, regardless of `stopReason`, which is why we haven't found
a lever (Kueue version, `spec.active` vs. scheduler preemption) that avoids it.

## Possible fix directions (not proposing a specific patch, just what we see from the outside)

- Have `isPodRunnableOrSucceeded` also treat a pod with a non-zero `deletionTimestamp` as
  inactive once its containers have actually terminated (e.g. check `ContainersReady`/phase
  independent of `NodeName`), not only when `NodeName` is empty.
- Have `Stop()` remove the finalizer directly on the pods it deletes, for every `stopReason`,
  the same way it already does unconditionally for `StopReasonWorkloadDeleted` via
  `Finalize()` — rather than relying on a later reconcile pass that depends on a replacement
  pod already existing.

## Impact

This blocks a legitimate all-or-nothing "gang" recovery pattern built on top of
`waitForPodsReady.recoveryTimeout`: the teardown half works reliably every time, but the
self-heal-once-capacity-returns half does not, and can additionally destabilize the control
plane via the thrash loop. We currently mitigate with a Prometheus alert
(`kube_pod_deletion_timestamp` age > 15m) and a documented manual finalizer-strip runbook, but
this requires a human to intervene within minutes to avoid sustained API server load.

Happy to provide full pod/Workload YAML dumps, controller logs around the race window, and
timestamps from all four reproductions if useful.
