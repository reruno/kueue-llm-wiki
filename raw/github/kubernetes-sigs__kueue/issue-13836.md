## Description

**What happened**:

An elastic Job accepts a change to its `AdmissionGatedBy` annotation, or to its maximum execution time, and the change never reaches the existing Workload.

`ensureOneWorkload` returns as soon as the slice is judged compatible:

```go
wl, compatible, err := workloadslicing.EnsureWorkloadSlices(ctx, r.client, r.clock, podSets, object, job.GVK())
if err != nil {
	return nil, err
}
if compatible {
	if err := r.syncWorkloadSlicePriority(ctx, job, object, wl); err != nil {
		return nil, err
	}
	return wl, nil
}
```

The ordinary path runs past that point and applies more than the priority class:

```go
if match != nil {
	if features.Enabled(features.AdmissionGatedBy) {
		if err := UpdateAdmissionGatedBy(ctx, r.client, r.record, job.Object(), match); err != nil {
			return nil, err
		}
	}

	if err := UpdateWorkloadPriority(ctx, r.client, r.record, job.Object(), match, getCustomPriorityClassFuncFromJob(job)); err != nil {
		return nil, err
	}
}
```

Compatibility is decided on the pod set shape alone, `HasSamePodSetKeys` plus the counts, so an edit that changes neither reaches the early return with nothing applied.

Maximum execution time arrives by a different route, and the two probably want different fixes. `AdmissionGatedBy` is patched onto a matched Workload by the call above. Maximum execution time is not patched at all: `EquivalentToWorkload` compares `Spec.MaximumExecutionTimeSeconds`, so a change makes the existing Workload a non-match, and `updateWorkloadToMatchJob` rewrites its spec from the job. Slice compatibility never looks at that field, so on this path the slice stays a match and keeps the old value. The annotation wants the call the early return skips.

The timeout wants the same thing, not what this issue first suggested. Making it part of the compatibility decision would be wrong, and the consequence is worse than a missed update: an incompatible slice falls through to the generic path, where `EquivalentToWorkload` compares the timeout as well, so `match` is nil. `ensureOneWorkload` then suspends a running job with `StopReasonNoMatchingWorkload` and deletes the Workloads it did not match. Editing the timeout on a running elastic job would tear it down. The field is owner-wide and mutable, so it belongs in the same in-place sync as the annotation.

**What you expected to happen**:

The compatible slice path applies the same mutable Workload fields the ordinary path applies, or the change is refused at admission rather than accepted and dropped.

**How to reproduce it (as minimally and precisely as possible)**:

1. Create an elastic Job that Kueue manages, and let its Workload be created.
2. Change the `AdmissionGatedBy` annotation, or the maximum execution time, without touching parallelism.
3. The Job shows the new value. The Workload keeps the old one, and nothing is reported.

**Anything else we need to know?**:

This is the same shape as three issues already open, where the API accepts a priority-class or annotation change that the controller then ignores: #13778 for the priority class on this same path, #13781 for Pod `PriorityClass`-backed Workloads, and #13827 for StatefulSet. #13780 fixes only the priority class and deliberately leaves these, so they are tracked here rather than folded in quietly.

I’d like to work on this if nobody is already implementing it.

My proposed direction is to keep workload-slice compatibility limited to pod-set shape and counts, propagate `AdmissionGatedBy` through the existing live-slice synchronization path, and update `maximumExecutionTimeSeconds` in place for non-admitted slices.

Before coding, could you confirm the intended behavior when a retained slice is already `Admitted=True`? The Workload API and KEP currently make `maximumExecutionTimeSeconds` immutable in that state, so an unconditional all-slice patch would be rejected. The choices appear to be deferring/rejecting that owner mutation, handling it through slice replacement, or deliberately changing the existing API contract.

Open PR #10479 also adds ClusterQueue-derived maximum-execution-time defaults, so the synchronization should use the effective desired value rather than treating an absent Job label as an instruction to clear the field.

### Comment by [@thc1006](https://github.com/thc1006) — 2026-08-11T10:08:57Z

TLDR: please do, nobody is working on it and I am not either. On your question, the API only freezes `maximumExecutionTimeSeconds` while the Workload is `Admitted` on both sides of the update, so the non-admitted half of your plan is allowed as written. Sorry for the slow reply.

The rule is in `apis/kueue/v1beta2/workload_types.go`:

```
((has(oldSelf.status) && oldSelf.status.conditions.exists(c, c.type == 'Admitted' && c.status == 'True'))
 && (has(self.status) && self.status.conditions.exists(c, c.type == 'Admitted' && c.status == 'True')))
? ((has(oldSelf.spec.maximumExecutionTimeSeconds) ? oldSelf.spec.maximumExecutionTimeSeconds : 0)
   == (has(self.spec.maximumExecutionTimeSeconds) ? self.spec.maximumExecutionTimeSeconds : 0))
: true
```

So it is conditional rather than absolute. Updating it in place on a slice that is not admitted passes.

For a retained slice that is already `Admitted=True`, the API refuses the in-place change, so the behaviour has to be one of two things. Either the retained slice keeps the value it was admitted with and the new one takes effect on the next slice that is not yet admitted, or a change to that field counts as incompatible and a new slice is created rather than the old one retained. I lean towards the first, since the second turns a field the user can edit freely before admission into a reason to recreate, but that is a preference rather than something the API decides for us. Worth getting a maintainer to confirm which one they want before you build around it.

One edge that falls out of the rule: it only bites when both sides are `Admitted=True`, so an update that also drops the condition in the same write is accepted. I would not build on that, but it explains any test that seems to get away with the change.

While reading it I noticed the message on that rule says `maximumExecutionTimeSeconds is immutable while workload quota reserved`, and the rule checks the `Admitted` condition. The neighbouring rules for `priorityClassRef` and `queueName` do check `QuotaReserved`, so the wording looks copied. Small thing, and I am happy to send a one line fix for the message separately so it does not get tangled with your change.

On the rest of your direction, keeping compatibility to pod set shape and counts reads right to me, and the `AdmissionGatedBy` propagation sounds plausible, though I have only checked the immutability rule above rather than that path, so take that part as an opinion rather than a verified answer. Happy to review whenever you have something.
