## Description

**What would you like to be cleaned**:

`workloadslicing.EnsureWorkloadSlices` decides and writes in the same pass, and its caller in `ensureOneWorkload` then reads the chain again to finish the job. Having it return the decision, and letting the caller carry out the writes, would take care of three rough edges at once.

**Why is this needed**:

The count and the priority class are not written atomically. `EnsureWorkloadSlices` persists a changed pod set count, and the priority class is resolved after it returns, so a class that cannot be resolved leaves the new count next to the old priority until the class exists. This is not a regression: before priority was synced on this path at all, the count was written and the priority was ignored permanently and silently. It is still a state worth removing.

The chain is listed twice. `syncWorkloadSlicePriority` calls `FindLatestActiveWorkload`, which lists through the cache again, so the slice the caller is holding and the slice that list returns are not guaranteed to describe the same moment, and `EnsureWorkloadSlices` may have finished some members in between.

`FindLatestActiveWorkload` skips finished slices and selects on quota reservation, but does not exclude evicted ones:

```go
for i := range slices.Backward(workloads) {
	if workload.HasQuotaReservation(&workloads[i]) {
		return &workloads[i], nil
	}
}
```

so it can return a slice that is on its way out while it still holds quota.

None of these is a permanent failure by itself; a later reconcile converges. They do make the compatible path hard to reason about, and the cost grows as more fields are synced there, which is what the sibling issue is about.

A decision type returned from one normalization pass, something along the lines of the selected slice, the retained quota-reserved slice, and whether the shape is compatible, would let the caller apply count and priority together and would remove the second list.

Context: #13780 is what surfaced this, and its description records the same reasoning; this issue exists so it is not recorded only there.

### Comment by [@thc1006](https://github.com/thc1006) — 2026-08-05T00:39:33Z

One qualification on the convergence statement here: a later reconcile only repairs the partial state while at least one live slice still carries a different class name.

If a previous write leaves `high/100 + low/10` and the class value then changes to 200, the pre-#13780 helper produces `high/100 + high/200`, which is a fixed point because both names then match, so nothing resolves the class again. #13780 closes that retry hole by reconciling the full ref/value rather than the class name; this issue can keep tracking the decision/write split, the second cached List, and the evicted retained-slice selection.

### Comment by [@thc1006](https://github.com/thc1006) — 2026-08-06T10:01:05Z

Three constraints on how this can be done, from reading the current code.

The ordering tie-break is already there. `FindNotFinishedWorkloads` sorts oldest-first and breaks same-second ties on UID, which #12931 added for the elastic stress-job flake. Nothing to do on that front.

`FindLatestActiveWorkload` is not only used by the slicing path. The elastic job ungater calls it from `activeSlice`, and the comment there says it does so to reuse the same slice ordering as the rest of the slicing code. So this helper is a contract between two callers, and folding it into `ensureOneWorkload` or narrowing what it counts as active would change which pods get ungated. Whatever this cleanup does to it needs an ungater regression alongside the slicing one.

One question worth settling before touching it: it selects on `HasQuotaReservation`, which stays true from the moment a slice is marked evicted until the workload controller unsets the reservation. During that window the helper can return a slice whose capacity is being released as the one whose granted counts define the admitted capacity. There is a stricter `HasActiveQuotaReservation`, but it adds only not-finished and active, so it does not close that window either. I have not reproduced a wrong outcome from it, so it is a question rather than a finding, but it is the kind of thing this cleanup would otherwise lock in.

### Comment by [@thc1006](https://github.com/thc1006) — 2026-08-06T10:21:33Z

One more read, verified: the compatible slice path lists the chain three times in a reconcile, not twice.

`EnsureWorkloadSlices` lists it, `syncWorkloadSlicePriority` lists it again through `FindLatestActiveWorkload`, and on the create path `prepareWorkloadSlice` lists it a third time at `reconciler.go:1506`. The third one is the most exposed, because the first pass may have just finished a surplus slice through a status patch that the cache has not caught up with, and `prepareWorkloadSlice` returns an error when it sees a count it does not expect.

So whatever carries the decision forward has to carry the creation link too, rather than letting the creation path look the chain up again.
