## Description

**What would you like to be added**:

Kueue computes a workload's DRA quota charge once, while the workload is `Pending`, by reading the `ResourceClaimTemplate` by name and summing its device counts (`getClaimSpec` / `countDevicesPerClass` in `pkg/dra/claims.go`, driven from `pkg/controller/core/workload_controller.go` where the DRA path runs only for `Status == Pending`). Nothing ties that charge to the `ResourceClaim` the workload actually runs with. I'd like the charge pinned to the template it was computed from — for example by recording the template UID and a hash of the quota-affecting spec on the Workload, and rejecting (or re-charging) if the generated `ResourceClaim` was created from a different spec.

**Why is this needed**:

A `ResourceClaimTemplate` spec is immutable in place, but nothing stops deleting a template and recreating one under the same name with a different spec. On the scheduler side, the resource-claim controller resolves the template by name at `ResourceClaim` generation time and copies its then-current spec, which happens after Kueue has already charged and admitted. So this sequence under-accounts quota:

1. template `gpu` has count 1
2. Kueue reads it while the workload is `Pending`, reserves `gpu: 1`, and admits
3. the user deletes `gpu` and recreates it under the same name with count 8
4. the pod is created; the resource-claim controller generates a `ResourceClaim` of 8 from the current template
5. the pod schedules and runs at 8 while the ClusterQueue still accounts for 1

`WaitForPodsReady` does not catch this: the pod is schedulable and runs fine. The impact is quota under-accounting / over-subscription — a tenant needs create/delete on templates in its own namespace — not a cross-tenant escalation.

This is not specific to prioritized-list. It lives in the existing `Exactly` path today and applies to all Kueue DRA charging, which is why it belongs in its own issue rather than inside KEP-2941 (#13601). That KEP now records template-spec stability as an assumption of the envelope upper bound and points here.

### Comment by [@thc1006](https://github.com/thc1006) — 2026-10-17T16:13:31Z

Dear @sohankunkerkar, I have a fix for the pending case locally: a ResourceClaimTemplate watch that requeues the pending workloads that reference the template, so a recreated template is charged before admission. That's right for Jobs, whose Pods are created after admission. Plain Pods, alone or in a pod group, are different: they exist while the workload is pending, and the resource-claim controller has already created their ResourceClaims from the old template, because it doesn't wait for the scheduling gate. Recomputing those workloads' charge from the new template would charge a count their Pods won't use, and a smaller template would get them admitted on less quota than they use. Should the fix skip workloads whose Pods already exist, or should their charge come from their Pods' ResourceClaims, as this issue proposes for admitted workloads?
