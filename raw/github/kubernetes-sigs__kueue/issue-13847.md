## Description

**What would you like to be added**:

An optional, configurable retention period (TTL) for remote objects (the remote Workload and its mirrored Job/JobSet) after the workload finishes, before MultiKueue deletes them from the worker cluster. Today, as soon as the local workload is finished, the MultiKueue workload reconciler deletes the remote objects on every worker cluster immediately and unconditionally

**Why is this needed**:

In deployments where the worker cluster is observed directly by end users e.g. multi-tenant or cross-project setups where each worker is a user's own cluster/project, the remote Job/JobSet on the worker is the object those users inspect (in the cloud console / dashboards) to see their completed run. Because MultiKueue deletes it immediately on completion, the run disappears from the worker cluster after it finishes, breaking post-completion visibility.

### Comment by [@YQ-Wang](https://github.com/YQ-Wang) — 2026-08-10T08:45:23Z

Hi @olekzabl, I’m interested in working on this issue, but I’d like to confirm the intended configuration and lifecycle semantics before starting.

Would it be acceptable to reuse the existing `objectRetentionPolicies.workloads.afterFinished` setting for MultiKueue remote objects?

My proposed behavior is:

- For a positive duration, perform the final status sync and then retain the remote Workload and its mirrored controller object until the manager Workload’s `Finished.LastTransitionTime + duration`.
- To preserve backward compatibility, an unset/`nil` value or `0s` would keep the current immediate remote cleanup behavior. This means `nil` would still disable automatic deletion of local Workloads while leaving MultiKueue remote cleanup immediate. Is that distinction acceptable?
- Explicit manager Job/Workload deletion, quota loss, eviction or out-of-sync recovery, and cleanup of non-selected workers would remain immediate.
- The behavior would apply to all registered MultiKueue adapters, rather than only Job and JobSet.

Reusing the existing setting would also mean that users who already configure a positive `afterFinished` value would begin retaining remote objects after upgrading. Is that intended? If a separate setting is preferred, should it be global under the MultiKueue component configuration or per `MultiKueueConfig`?

There is also a same-name reuse case to clarify. If a new run finds a retained remote object with the same namespace, name, and MultiKueue origin, but a different prebuilt Workload name, should MultiKueue delete the old object and requeue the new run, or block the new run until the retention period expires?

I would document that the setting controls only MultiKueue-initiated deletion; worker-side TTL policies or manual deletion could remove the objects earlier.

If this direction is acceptable, I can add deterministic unit tests, Job and JobSet integration coverage, and the documentation update.

I'd vote on `MultiKueue` field of the `Configuration` object (global).
My main reason here is that `Configuration` is static for the whole lifetime of a Kueue binary, as opposed to `MultiKueueConfig` which can change for a given ClusterQueue (by either updating the MKC or reassigning another MKC to a CQ). So supporting that would be more cumbersome.

### Comment by [@YQ-Wang](https://github.com/YQ-Wang) — 2026-08-25T08:32:53Z

Hi @olekzabl, thanks for the answers.

I’ll use a dedicated field on the global MultiKueue Configuration: multiKueue.objectRetentionPolicies.remoteObjects.afterFinished, behind an Alpha feature gate. nil or 0 keeps today’s immediate cleanup. That stays separate from the manager-side workloads.afterFinished, where nil means “never delete”.

Retention applies only after the local Workload Succeeded or Failed. Eviction, quota loss, out-of-sync recovery, local deletion, and cleanup of non-selected workers stay immediate.

If a new run finds a retained remote object from an earlier run of the same name, we delete that leftover and continue. We cannot reuse a finished batch/Job in place because its spec is immutable, so the reconciler deletes it and retries shortly so the new object can be created. That retry is only the MultiKueue reconcile loop, not a ClusterQueue requeue.

I’ll open a PR with tests and docs.
