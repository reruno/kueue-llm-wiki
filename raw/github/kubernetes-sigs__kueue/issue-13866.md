## Description

**What happened**:

A `WorkloadPriorityClass` value change can be lost permanently if it is reconciled before the Workloads that will reference the class have switched to it.

`WorkloadPriorityClassReconciler` watches `WorkloadPriorityClass` only. On an event it lists the Workloads that reference that class through the `WorkloadPriorityClassKey` index and rewrites their `spec.priority`. It has no watch on Workloads, and its RBAC reflects that:

```go
// +kubebuilder:rbac:groups=kueue.x-k8s.io,resources=workloadpriorityclasses,verbs=get;list;watch
// +kubebuilder:rbac:groups=kueue.x-k8s.io,resources=workloads,verbs=get;list;update
```

The Job side does not re-resolve either. `UpdateWorkloadPriority` only resolves the class when the Workload's class name still has to change:

```go
if (workload.HasNoPriority(wl) || workload.IsWorkloadPriorityClass(wl)) && jobPriorityClassName != wlPriorityClassName {
	// resolve and write
}
```

Once the name matches, no later reconcile looks at the numeric value again. So neither side owns the repair:

1. the Job reconcile resolves `high` and reads value 100;
2. an administrator changes `high` to 200;
3. `WorkloadPriorityClassReconciler` handles that update. The Workload still references `low`, so the indexed list returns nothing and the event is consumed;
4. the Job reconcile writes the Workload as `high` / 100;
5. every later reconcile sees the name already matching and returns.

The Workload stays on 100 while the class says 200, until the class is edited again, deleted and recreated, or the manager restarts, where the informer's initial list arrives as create events and the create predicate returns true.

A periodic resync is not a fallback here: it delivers update events whose value is unchanged, and the update predicate filters exactly those out.

```go
if e.ObjectOld.Value == e.ObjectNew.Value {
	return false
}
```

**What you expected to happen**:

A Workload that references a `WorkloadPriorityClass` ends up on that class's current value, whichever order the two reconciles run in.

**How to reproduce it (as minimally and precisely as possible)**:

1. Create `WorkloadPriorityClass` `high` with value 100 and a Job labelled `kueue.x-k8s.io/priority-class: low`.
2. Change the Job label to `high` and, in the same window, change `high` to 200 so the class reconcile runs while the Workload still references `low`.
3. The Workload settles on `high` / 100 and stays there.

**Anything else we need to know?**:

This is not specific to elastic Jobs: it reproduces with a single Workload on the ordinary path, so it predates #13780. That PR resolves the class once per batch, which stops one batch from writing two different values, but it cannot close this ordering, because the repair it added still needs one Workload whose class name has not caught up yet as the trigger to re-resolve.

Making the class reconciliation level-triggered would close it: a filtered Workload watch that enqueues the newly referenced class on create, and on an update where `priorityClassRef` identity changes, while ignoring numeric-only and status-only updates so the controller does not re-trigger on its own writes or take ownership of the otherwise-mutable `spec.priority`. That needs `watch` added to the Workload RBAC above.

Priority feeds ClusterQueue ordering, preemption and borrowing, so a stale value is a scheduling difference rather than only a cosmetic one.

**Environment**:
- Kueue version (use `git describe --tags --dirty --always`): main
