## Description

<!-- Please only use this template for submitting clean up requests -->

**What would you like to be cleaned**:

Remove the synthesized zero-usage value that `LocalQueueReconciler` passes into its status assembly when the referenced ClusterQueue no longer exists, and serve the LocalQueue status usage from the scheduler cache in that path as well.

Today, `pkg/controller/core/localqueue_controller.go:202` calls:

```go
err = r.updateStatusIfChanged(ctx, &queueObj, &schdcache.LocalQueueUsageStats{}, metav1.ConditionFalse, "ClusterQueueDoesNotExist", clusterQueueIsInactiveMsg)
```

The explicit `&schdcache.LocalQueueUsageStats{}` bypasses `Cache.LocalQueueUsage` and makes `updateStatusIfChanged` (`localqueue_controller.go:652`) accept a caller-supplied override, checked at `localqueue_controller.go:672`. The goal of this cleanup is to remove that override parameter so the usage always comes from one place.

**Why is this needed**:

This came out of review on #13708, which fixed a real bug: the `Active` condition is derived from a live ClusterQueue API read while the usage counters come from the scheduler cache, whose entry is torn down asynchronously by `ClusterQueueReconciler.Delete` (`clusterqueue_controller.go:364`). A LocalQueue reconcile landing between those two events published a status that simultaneously reported `ClusterQueueDoesNotExist` and non-zero reserved and admitted quota, and that status was not self-correcting.

Passing zeroed usage in that branch fixes the user-visible defect, but as noted in review it leaves the reconciler serving a value it synthesized rather than one it read. That is fine today and is not a bug, but it is error prone for future evolution: a later change to how usage is derived would have to remember that one branch does not go through the cache at all.

To be explicit about what this issue is not: there is no cache leak. The ClusterQueue cache entry is removed on the delete event, and the LocalQueue entries are dropped with it because `localQueues` is a field on the cached ClusterQueue struct. This was verified against both `main` and the `release-0.19` tree where the original flake was observed, with identical results:

```
BEFORE delete: clusterQueues=1  localQueues=1  workloads=1
AFTER  delete: clusterQueues=0  ClusterQueue("cq")=<nil>
LocalQueueUsage after delete: reserving=0 admitted=0 reserved=[] used=[]
```

So this is tech debt.

**Options considered**
The first two were recommended by @mimowo, the other 2 were recommended by LLM. 
1. Have the LocalQueue reconcile delete the cache entry when the ClusterQueue does not exist.

   Concern: this makes the LocalQueue reconciler mutate ClusterQueue-scoped cache state, which is owned by the ClusterQueue reconciler, and the cached entry covers every LocalQueue in that ClusterQueue plus its cohort linkage. It also introduces a recreation hazard: if the ClusterQueue is deleted and recreated quickly, a LocalQueue reconcile still holding the stale not-found observation could delete the fresh cache entry that the ClusterQueue reconciler just added, dropping live quota accounting for a ClusterQueue that does exist. That failure mode is worse than the one #13708 fixed. Guarding it would need a UID or resourceVersion check that the cache does not currently track.

2. Have the code that cleans the cache trigger another LocalQueue reconcile.

   This converges and there is precedent for cross-controller notification (`NotifyWorkloadUpdate`, `notifyWatchers`). On its own it does not stop the contradictory status from being written and observed first, it only guarantees a later correction. Note `qCQHandler.Delete` already enqueues the LocalQueues on ClusterQueue deletion; this would be a second enqueue issued after cleanup completes.

3. Requeue while the two sources disagree, instead of publishing anything (LLM recommended)

   In the not-found branch, if the cache still holds the ClusterQueue, requeue without writing status. This never serves a synthesized value and never publishes a contradictory one. Costs: the correct `Active` condition is published later than today, and the reconcile could spin if a cleanup is ever missed. The cache query here is read only, so it does not have option 1's layering problem.

4. Make the cache the single source of truth for ClusterQueue existence as well as usage. (LLM recommended)

   Genuinely one source, so the two halves cannot disagree. The tradeoff is a worse lag in the opposite direction: the LocalQueue would keep reporting `Active=True` after the ClusterQueue is deleted from the API until the cache catches up, and reporting that everything is fine is arguably more misleading to operators than reporting stale numbers. It also needs the cache to expose the ClusterQueue's API conditions, which it does not today.

**Suggested direction**

Options 2 and 3 combined look like the best fit for the concern raised: option 3 removes the synthesized value and the contradictory publish, and option 2 bounds how long the requeue loop lasts. Worth confirming before implementation, since option 3 alone changes when the `Active` condition becomes visible.

**Acceptance criteria**

- `updateStatusIfChanged` no longer takes a caller-supplied usage override; usage has a single derivation path.
- A LocalQueue never reports `ClusterQueueDoesNotExist` together with non-zero `status.reservingWorkloads`, `status.admittedWorkloads`, `status.flavorsReservation`, or `status.flavorsUsage`, at any observation.
- The result does not depend on whether the scheduler cache has been cleaned when the LocalQueue reconcile runs.
- The integration test `Queue controller Should update status when ClusterQueue are forcefully deleted` (`test/integration/singlecluster/controller/core/localqueue_controller_test.go`) keeps passing without its assertion being weakened or its timeout lengthened.
- The unit case `cluster queue deleted while its scheduler cache entry is still present` in `pkg/controller/core/localqueue_controller_test.go` is updated rather than deleted. Under option 3 it would assert a requeue instead of an immediate status write, so it needs re-expressing, but the scenario it covers must stay covered.
