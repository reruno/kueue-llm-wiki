**What would you like to be cleaned**:

Follow-up to https://github.com/kubernetes-sigs/kueue/pull/13785#discussion_r3721900452 which suggested exploring creation expectations for ProvisioningRequests.

The provisioning controller currently handles the informer-cache delay after creation by retrying when another `Create` returns `AlreadyExists` while the object is still missing from the cache.

An alternative would be to record an expectation after a successful create and avoid issuing another create until the ProvisioningRequest is observed by the event handler. Kueue already uses this pattern for other time-sensitive operations through `pkg/util/expectations`.

**Why is this needed**:

This could prevent the duplicate create at the source rather than recovering from it afterward.

This is not a regression or a high-priority change: #13785 already handles the transient conflict and stale-message issue. The goal is to explore whether expectations can simplify the flow without introducing too much bookkeeping.

The current expectations store has no expiry, so the design should ensure that a missed observation cannot block creation indefinitely. Keeping the existing recovery-based behavior is also a valid outcome if the expectations approach becomes too complex.
