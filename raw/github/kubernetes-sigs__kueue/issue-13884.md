**What happened**:

At the beginning of a scheduling cycle, `Manager.Heads` removes one workload from every active, non-empty ClusterQueue, together with all ready second-pass workloads.

If `cache.Snapshot()` then fails, the scheduler returns without restoring those workloads.

For a regular ClusterQueue head, the workload has already been removed from the heap and LocalQueue items and remains tracked as `inflight`. It is no longer available for scheduling, and updates arriving before the stale `inflight` entry is cleared are ignored by `ClusterQueue.PushOrUpdate`.

Nothing in a later cycle automatically re-adds it. It returns only after a later update happens once the stale entry has been cleared, or after the queue manager restarts and repopulates its queues.

Second-pass workloads are also removed from their queue and not restored, which can leave workloads that already reserved quota waiting for further processing.

A single snapshot failure can therefore park one workload from every active, non-empty ClusterQueue.

**What you expected to happen**:

When snapshot construction fails, all workloads returned by `Manager.Heads` should be restored to their respective queues and retried in the next scheduling cycle.

**How to reproduce it (as minimally and precisely as possible)**:

One reproducible path is a non-NotFound error while resolving LocalQueue fair-sharing usage during snapshot construction:

1. Add an admitted workload and a pending workload to a ClusterQueue using usage-based AdmissionFairSharing.
2. Make the LocalQueue `Get` performed by `cache.Snapshot()` fail for one scheduling cycle.
3. Run another cycle after the lookup succeeds again.

The pending workload is absent from `queueManager.Dump()` after the failed cycle and is not admitted in the following cycle.

The proposed regression test, `TestScheduleSnapshotErrorRequeuesHeads`, reproduces this on main and verifies that the workload is restored and admitted after the fix.

**Anything else we need to know?**:

Found while splitting an independent correctness fix from #13729. The bug does not depend on the FairSharingRefill feature.

Errors while building TAS flavor snapshots appear to reach the same early-return path, although the regression test covers the AdmissionFairSharing path.
