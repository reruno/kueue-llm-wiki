**What would you like to be added**:

Context: follow-up from #13223 ([review comment](https://github.com/kubernetes-sigs/kueue/pull/13223#discussion_r3615694104)).

When a pod's rank has no domain in the `TopologyAssignment`, `TopologyUngater` gives up on rank-based ordering for the whole PodSet and places every pod greedily. It should skip only the out-of-range pods and keep rank-based ordering for the rest.

Two checks in `topology_ungater.go` lead to the greedy fallback:

1. `readRanksForLabels` returns an error when a rank is `>= *psa.Count`, or when the pod index label is not below `maxRank` ([code](https://github.com/kubernetes-sigs/kueue/blob/d37078a750971c165674a1a9dd0e0b37887912dc/pkg/controller/tas/topology_ungater.go#L515-L539)).
2. `readRanksIfAvailable` returns `(nil, false)` when `rank >= len(rankToDomainID)`, added in #13223 to prevent an out-of-range panic ([code](https://github.com/kubernetes-sigs/kueue/blob/d37078a750971c165674a1a9dd0e0b37887912dc/pkg/controller/tas/topology_ungater.go#L469-L480)).

Proposed behavior: drop the out-of-range ranks from the `rankToPod` map, ungate the remaining pods by rank, and leave the out-of-range pods gated. `TruncateAssignment` removes domains from the end ([code](https://github.com/kubernetes-sigs/kueue/blob/d37078a750971c165674a1a9dd0e0b37887912dc/pkg/util/tas/tas_assignment.go#L527-L556)), so the out-of-range ranks are the highest ones, which are the pods the job controller is about to delete anyway. The domain mismatch check for already running pods in `readRanksIfAvailable` bails out for the whole PodSet too, so it needs the same narrowing.

**Why is this needed**:

With `ElasticJobsViaWorkloadSlicesWithTAS`, a user can create a job of size 1000 and scale it down to 900 before all pods get ungated. The assignment is truncated to 900 pods while pods with completion index 900 to 999 still exist and are still gated. All 900 remaining pods then lose rank-based ordering and are placed greedily, so pods with consecutive ranks are no longer placed in the same topology domain. That is what TAS rank-aware packing is for (story 4 in KEP-2724). I have not reproduced this on a cluster; the sequence above comes from reading `TopologyUngater` and `TruncateAssignment`, and which of the two checks fires first depends on when the `PodSetAssignment` count is updated relative to the `TopologyUngater` reconcile.

The same fallback triggers without elastic jobs, when a PodSet slice size does not evenly divide the PodSet count, so the assignment covers fewer pods than `*psa.Count`. #13223 stopped the panic in that case, but greedy placement there is a workaround, not the intended placement.

KEP-77 lists this as a Beta graduation criterion for `ElasticJobsViaWorkloadSlicesWithTAS`: "Correct handling of rank-based ordering for scale-downs".

**Completion requirements**:

1. Keep rank ordering for the in-range pods, drop only the out-of-range ranks, and leave those pods gated. Same narrowing for the domain mismatch check.
2. Unit tests in `pkg/controller/tas/topology_ungater_test.go`, next to the existing `ranks: TopologyAssignment shorter than the PodSet count falls back to greedy assignment` case.
3. Integration test for an elastic scale-down with TAS in `test/integration/singlecluster/tas/tas_test.go`, where the elastic and TAS specs cover scale-up only today.
4. Tick the Beta criterion in `keps/77-dynamically-sized-jobs/README.md`.

### Comment by [@ivnovakov](https://github.com/ivnovakov) — 2026-10-16T11:06:09Z

#16771 covers requirements 1, 2 and 4. With ElasticJobsViaWorkloadSlicesWithTAS enabled, the ungater keeps rank-based ordering when some ranks have no domain in the assignment. When it lends free capacity, it skips the domain-mismatch check.

Three things are left for this issue.

- An integration spec for an elastic scale-down that fails without #16771. The two specs in #16771 also pass on the old code, so they are smoke tests. In envtest the ungater lists pods from the informer cache in random order, so with two or more gated pods a spec fails on the old code only some of the time. A reliable spec needs exactly one gated pod whose own domain is free while an earlier domain in the assignment is also free.
- The slice-size case with TASPartialSlices disabled. When the slice size doesn't divide the PodSet count, the assignment covers fewer pods than the count. The ungater then falls back to greedy assignment for the whole PodSet, as it did before #16771.
- Pods left above the count after a scale-down. In an Indexed Job with completions above parallelism, pods above the count are expected, and the ungater lends them free domains. After a scale-down, the pods left above the new count look the same to the ungater, because it only sees the Workload. So such a pod can take free capacity before the Job controller deletes it.
