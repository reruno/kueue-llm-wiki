## Description

**What happened**:

A Workload rejected by DRA validation is stamped `Requeued=False` with reason `Inadmissible`. Nothing in the codebase ever sets that condition back to `True`, and while it is `False` the Workload is excluded from **both** paths into the scheduling heap — including `queueInadmissibleWorkloads`, the sweep that exists specifically to retry inadmissible Workloads.

The result is a permanently unschedulable Workload. The mechanism meant to retry inadmissible work is disabled by the very condition that marks it inadmissible. Fixing the underlying misconfiguration does not release it; only deleting and recreating the Workload does.

We hit this after upgrading v0.17.6 → v0.18.4 on a GB200 cluster where `resources.deviceClassMappings` was not configured. `KueueDRAIntegration` is beta / default `true` in v0.18 (in v0.17 DRA was gated by `DynamicResourceAllocation`, alpha / default `false`), so the upgrade switched DRA validation on implicitly. Every Workload carrying an IMEX compute-domain resource claim failed the DeviceClass lookup and was stamped:

```
QuotaReserved = False / Pending
Requeued      = False / Inadmissible
  spec.podSets[0].template.spec.resourceClaims[0].resourceClaimTemplateName: Not found:
  "DeviceClass <class>.nvidia.com is not mapped in DRA configuration for podset <hash>"
```

16 Workloads sat pending for over 5 days in a ClusterQueue that was lightly utilised and admitting other Workloads in ~26 ms.

**Two facts combine into a closed loop.**

**Fact 1 — nothing ever clears reason `Inadmissible`.** In v0.18.4 there are exactly **four** writers that set `Requeued=True`, and none covers it:

| Writer | Reason set | Recovers `Inadmissible`? |
|---|---|---|
| `workload_controller.go:534` | `Reactivated` | No — switch case is `WorkloadDeactivated` |
| `workload_controller.go:547` | `BackoffFinished` | No — cases are `EvictedByPodsReadyTimeout`, `EvictedByAdmissionCheck` |
| `workload_controller.go:633` | `LocalQueueRestarted` | No — gated on `EvictedByLocalQueueStopped` |
| `workload_controller.go:653` | `ClusterQueueRestarted` | No — gated on `EvictedByClusterQueueStopped` |

The recovery switch (`workload_controller.go:531-537`) dispatches on the reason and has no `Inadmissible` case:

```go
if cond := apimeta.FindStatusCondition(wl.Status.Conditions, kueue.WorkloadRequeued); cond != nil && cond.Status == metav1.ConditionFalse {
	switch cond.Reason {
	case kueue.WorkloadDeactivated:
		workload.SetRequeuedCondition(wl, kueue.WorkloadReactivated, "The workload was reactivated", true)
	case kueue.WorkloadEvictedByPodsReadyTimeout, kueue.WorkloadEvictedByAdmissionCheck:
		...
	}   // ← no case for kueue.WorkloadInadmissible
}
```

The two queue-restart writers are likewise reason-gated via `isDisabledRequeuedByReason` (`workload_controller.go:811`), so stopping and starting the queue cannot help either.

`Inadmissible` is therefore the **only** `Requeued=False` reason with neither a backoff timer nor a guaranteed writer. Every other reason is transient by construction; this one is terminal.

The one place that does clear it is `workload_controller.go:456-462`:

```go
if requeuedCond != nil && requeuedCond.Status == metav1.ConditionFalse {
	apimeta.RemoveStatusCondition(&wl.Status.Conditions, kueue.WorkloadRequeued)
	conditionsCleared = true
}
```

But that sits **inside** the block gated by `dra.NeedsDRAReconcile()` (`workload_controller.go:337`). With DRA disabled that returns `false` (`pkg/dra/extended_resources.go:44`), so the block is skipped and the condition persists forever. Disabling `KueueDRAIntegration` — the natural response to "DRA is misconfigured" — is precisely what makes the state permanent.

**Fact 2 — while `Requeued=False`, the Workload cannot enter the heap at all.** `pkg/cache/queue/cluster_queue.go:421-434`:

```go
// backoffWaitingTimeExpired returns true if the current time is after the requeueAt
// and Requeued condition not present or equal True.
func (c *ClusterQueue) backoffWaitingTimeExpired(wInfo *workload.Info) bool {
	if apimeta.IsStatusConditionFalse(wInfo.Obj.Status.Conditions, kueue.WorkloadRequeued) {
		return false          // ← no timer, no expiry, no reason check
	}
	if wInfo.Obj.Status.RequeueState == nil || wInfo.Obj.Status.RequeueState.RequeueAt == nil {
		return true
	}
	return c.clock.Now().After(wInfo.Obj.Status.RequeueState.RequeueAt.Time) ||
		c.clock.Now().Equal(wInfo.Obj.Status.RequeueState.RequeueAt.Time)
}
```

Both callers consult it, so neither path can admit the Workload:

- `PushOrUpdate` → `cluster_queue.go:376` → `insertInadmissible`
- `queueInadmissibleWorkloads` → `inadmissible_workloads.go:184` → re-inserted into `newInadmissibleWorkloads`:

```go
for key, wInfo := range c.inadmissibleWorkloads {
	ns := corev1.Namespace{}
	err := client.Get(ctx, types.NamespacedName{Name: wInfo.Obj.Namespace}, &ns)
	if err != nil || !c.namespaceSelector.Matches(labels.Set(ns.Labels)) || !c.backoffWaitingTimeExpired(wInfo) {
		newInadmissibleWorkloads.insert(key, wInfo)   // ← always taken; never reaches the heap
	} else if c.heap.PushIfNotPresent(wInfo) {
		moved++
	}
}
```

The sweep runs correctly and does nothing. We logged `"Resetting the head of the ClusterQueue"` **14 times in 95 minutes** for the affected ClusterQueue, each time moving **0** of the 16, producing `Obtained ClusterQueue heads count=0`. Across the entire 5-day lifetime of these Workloads there is **not one `logger=scheduler` line** mentioning any of them — they are never evaluated for admission. Consequently their `QuotaReserved` message is stale output from the single original evaluation, never recomputed, which reads as a quota problem when quota is fine. That misled our own investigation for days.

**Observed non-remedies.** None of these release the Workload:

- **Deactivate/reactivate.** After toggling `spec.active`, `Evicted=True/Deactivated` was stamped with a current timestamp while `Requeued=False/Inadmissible` kept its original one. No matching switch case, so no patch.
- **Stop/start the ClusterQueue or LocalQueue.** Reason-gated, as above.
- **Restart the controller.** All replicas restarted; the block is re-derived from the persisted condition.
- **Fix the configuration.** The clearing code is unreachable while DRA is disabled.

**Silent failure mode.** These Workloads count toward `status.pendingWorkloads` while generating zero scheduler activity, no event, and no metric distinguishing a *wedged* Workload from an ordinary *waiting* one. Nothing surfaces the difference.

**What you expected to happen**:

A Workload should not become permanently unschedulable because of a **fixable configuration error**. Specifically:

1. **Reason `Inadmissible` should have a recovery path**, as every other `Requeued=False` reason does — a timer, a case in the recovery switch, or eligibility for the inadmissible sweep.

2. **`queueInadmissibleWorkloads` should be able to requeue an inadmissible Workload.** This is documented as the intended recovery path. v0.17.6 carried this comment on `NeedsDRAReconcile` (`pkg/dra/extended_resources.go:41-42`):

   > *"Note: there is no DeviceClass watcher. If a DeviceClass is created after a workload was marked inadmissible, requeuing depends on the next `QueueInadmissibleWorkloads` event."*

   That is exactly the behaviour we expected — and it is **not what the code does**, because the `Requeued` latch makes the sweep skip the Workload unconditionally. The comment was **removed in v0.18.x** (present in v0.17.6; absent in v0.18.4, v0.19.0, `main`) with no corresponding fix to the behaviour it described.

3. **Disabling `KueueDRAIntegration` should not strand Workloads rejected while it was enabled.** Nesting the condition-clearing inside the DRA-gated block makes the disable path a one-way door.

**How to reproduce it (as minimally and precisely as possible)**:

The DRA misconfiguration is only the *trigger*; the bug is that the resulting state is unrecoverable.

1. Run Kueue **v0.18.x** with `KueueDRAIntegration` at its default (`true`) and **no** `resources.deviceClassMappings` in the Configuration. (`PopulateFromConfiguration` returns early when `mappings == nil` — `pkg/dra/mapper.go:66-68` — so an absent mapping is indistinguishable from a deliberate one, and `ResourceMapper.Lookup()` fails for every DeviceClass.)

2. Create a `DeviceClass` and a `ResourceClaimTemplate` referencing it:

```yaml
apiVersion: resource.k8s.io/v1
kind: DeviceClass
metadata:
  name: my-device-class.example.com
---
apiVersion: resource.k8s.io/v1
kind: ResourceClaimTemplate
metadata:
  name: my-claim
  namespace: default
spec:
  spec:
    devices:
      requests:
      - name: channel
        exactly:
          deviceClassName: my-device-class.example.com
          allocationMode: ExactCount
          count: 1
```

3. Submit a Job into a LocalQueue that has ample quota for every other resource, with the podSet referencing the template:

```yaml
spec:
  template:
    spec:
      resourceClaims:
      - name: my-channel
        resourceClaimTemplateName: my-claim
```

4. Observe the Workload rejected, with both conditions `False`:

```console
$ kubectl get workload <wl> -o jsonpath='{range .status.conditions[*]}{.type}={.status}/{.reason}{"\n"}{end}'
QuotaReserved=False/Pending
Requeued=False/Inadmissible

$ kubectl get workload <wl> -o jsonpath='{.status.conditions[?(@.type=="Requeued")].message}{"\n"}'
spec.podSets[0].template.spec.resourceClaims[0].resourceClaimTemplateName: Not found:
"DeviceClass my-device-class.example.com is not mapped in DRA configuration for podset main"
```

5. **Now fix the root cause** — add the correct `deviceClassMappings` to the Configuration and restart the controller (required: config is read once at startup, per #13727).

6. **Attempt every available recovery.** None admits the Workload:

```console
# a) deactivate / reactivate
$ kubectl patch workload <wl> --type=merge -p '{"spec":{"active":false}}'
$ kubectl patch workload <wl> --type=merge -p '{"spec":{"active":true}}'

# b) stop / start the ClusterQueue
$ kubectl patch clusterqueue <cq> --type=merge -p '{"spec":{"stopPolicy":"Hold"}}'
$ kubectl patch clusterqueue <cq> --type=merge -p '{"spec":{"stopPolicy":"None"}}'

# c) restart the controller
$ kubectl rollout restart deployment/kueue-controller-manager -n kueue-system
```

Confirm the condition never moves — its `lastTransitionTime` stays at the original rejection:

```console
$ kubectl get workload <wl> -o jsonpath='{.status.conditions[?(@.type=="Requeued")].lastTransitionTime}{"\n"}'
```

7. **Confirm it is invisible to the scheduler.** The sweep fires for the ClusterQueue but moves nothing:

```console
$ kubectl logs -n kueue-system -l control-plane=controller-manager --tail=-1 \
    | grep "Resetting the head of the ClusterQueue"     # fires repeatedly
$ kubectl logs -n kueue-system -l control-plane=controller-manager --tail=-1 \
    | grep <wl> | grep '"logger":"scheduler"'           # → empty, always
```

8. **Confirm a new Workload is fine.** Submit an identical Job; it admits in milliseconds. A fresh Workload carries no `Requeued` condition, so `backoffWaitingTimeExpired` returns `true`. Only the already-stamped Workloads are wedged — which is what makes this easy to miss: the queue looks perfectly healthy.

**Anything else we need to know?**:

*The latch is old; the exposure is new.* `backoffWaitingTimeExpired`'s `Requeued` check is present and byte-identical in **v0.15.0, v0.16.9, v0.17.6, v0.18.4, v0.19.0, and `main`** (it dates to #2362, Jun 2024). Both DRA call sites that pair `SetRequeuedCondition` with reason `Inadmissible` already exist in v0.16.0. So this is **not a v0.18 regression** in the latch itself.

What v0.18 changed is **who is exposed**, via two beta-default-`true` gates that did not exist in v0.17.6:

| | v0.17.6 | v0.18.x |
|---|---|---|
| Gate | `DynamicResourceAllocation` — alpha, default **`false`** | `KueueDRAIntegration` — beta, default **`true`** |
| `NeedsDRAReconcile` when gate off | `return false` — unconditional | `return features.Enabled(KueueDRARejectWorkloadsWhenDRADisabled) && workload.HasDRA(wl)` |
| Reject-when-disabled gate | does not exist | `KueueDRARejectWorkloadsWhenDRADisabled` — beta, default **`true`** (from #10964) |

Two consequences for anyone upgrading v0.17 → v0.18 without configuring DRA:

1. DRA validation begins running implicitly, so every claim-bearing Workload is rejected and wedged.
2. Setting `KueueDRAIntegration=false` **does not** restore the v0.17.6 no-op, because the disabled branch is now itself gated. Both gates must be set to `false`. In v0.17.6 the disabled path was an unconditional `return false`; in v0.18.x it is not.

*Secondary observation — the condition-clearing is never persisted.* The `RemoveStatusCondition` calls at `workload_controller.go:456-462` mutate the local object only. Unlike every other condition write in that file, they are not wrapped in `PatchAdmissionStatus`, and no patch follows before the queue/cache update. The cleared copy is passed to `AddOrUpdateWorkload`, so the Workload *can* be admitted in that process — but the API object keeps `Requeued=False/Inadmissible` while the log line reports `"Cleared previous inadmissible conditions after successful DRA processing"`.

We see this in production after re-enabling DRA: Workloads with `QuotaReserved=True` and a current admission timestamp still carrying a `Requeued=False/Inadmissible` condition stamped days earlier. It does not block admission, but it makes `kubectl` report a condition the controller believes it deleted. A reviewer raised the same point on #13549 (asking that the stale conditions be removed via `PatchAdmissionStatus` before the queue update); the code in v0.19.0 and `main` is unchanged. Happy to split this into its own issue if preferred.

*Related work.* #13727 (merged, docs) documents that `deviceClassMappings` is read once at manager startup and that an unmapped DeviceClass produces exactly this message; its commit trail — *"docs: not admitted, and not terminal either"* and *"docs: drop a recovery claim I could not verify"* — suggests the author looked for a recovery path and could not find one. We believe that is because none exists. #13549 (merged, v0.20) refactors this code into `handleDRA` / `markDRAInadmissible`; it is **not** in v0.18.4 or v0.19.0 and, being cleanup-only, appears to keep the condition-clearing inside the DRA-gated block. #8095 covers inadmissible-requeue rate limiting — adjacent, but different.

*Verified:* once `KueueDRAIntegration` is re-enabled **with** correct `deviceClassMappings`, newly submitted DRA Workloads admit normally, their ResourceClaims allocate, and the pods start and complete. Only Workloads already stamped `Inadmissible` remain stuck.

**Three possible directions**, narrowest first:

1. **Add an `Inadmissible` case to the recovery switch** at `workload_controller.go:531`, so deactivate/reactivate becomes a documented operator remedy instead of a no-op.
2. **Make the latch reason-aware.** Have `backoffWaitingTimeExpired` block heap entry only for `Requeued=False` reasons that have a writer guaranteed to flip them (the backoff/eviction reasons), so `Inadmissible` no longer excludes a Workload from the sweep. This restores the behaviour the removed v0.17.6 comment described.
3. **Hoist the condition-clearing out of the DRA-gated block** (and persist it via `PatchAdmissionStatus`), so disabling `KueueDRAIntegration` releases Workloads it previously rejected. Optionally emit an event or metric for Workloads in a non-self-clearing `Requeued=False` state, so they are distinguishable from ordinary pending ones.

Happy to open a PR for whichever direction maintainers prefer.

**Environment**:

- Kubernetes version (use `kubectl version`): v1.34
- Kueue version (use `git describe --tags --dirty --always`): **v0.18.4**, upgraded from v0.17.6 the day before the Workloads wedged
- Feature gates: `KueueDRAIntegration` at the v0.18 default (`true`) when the Workloads were rejected, later set to `false`, which made the state unrecoverable; `KueueDRARejectWorkloadsWhenDRADisabled=false`. No `resources.deviceClassMappings` in the Configuration.
- Cloud provider or hardware configuration: GKE, NVIDIA GB200 (arm64), IMEX compute-domain channels requested via DRA `ResourceClaimTemplate`s
- Others: `queueingStrategy: BestEffortFIFO`, fair sharing enabled, TAS enabled — none implicated. The affected ClusterQueue was actively borrowing and admitting non-DRA Workloads throughout, on a lightly-utilised cluster.

### Comment by [@sohankunkerkar](https://github.com/sohankunkerkar) — 2026-08-08T21:15:43Z

Thanks for reporting this. This seems like a legit bug. The latch in `backoffWaitingTimeExpired` blocks all `Requeued=False` without checking the reason, and Inadmissible is the only reason that has no recovery writer anywhere. Every other reason has either a timer or a case in the recovery switch.

One thing worth noting: if the operator fixes the config and restarts with DRA still enabled, `handleDRA` clears the conditions locally and passes a clean copy to the queue, so the workload does recover. The permanent stuck state only happens when they disable `KueueDRAIntegration` first, which is the natural thing to do when DRA is misconfigured. The clearing code sits inside the DRA-gated block, so disabling the  gate is a one-way door.

For the fix, I think adding Inadmissible to the recovery switch is the right cherry-pick for 0.18/0.19 since it's one case and gives operators deactivate/reactivate as a remedy. For main, should we make backoffWaitingTimeExpired reason-aware? cc @mimowo @mbobrovskyi 


The latch was designed in #2362 for eviction backoff where every reason has a guaranteed writer and Inadmissible broke that assumption without anyone noticing. Curious what you think about making it an allowlist of reasons to block vs the current blanket check. Also, the condition clearing in `handleDRA` isn't persisted to the API server, so kubectl shows a stale `Requeued=False/Inadmissible` even after the workload is admitted. Same thing was flagged on #13549. Should that be a separate fix?
