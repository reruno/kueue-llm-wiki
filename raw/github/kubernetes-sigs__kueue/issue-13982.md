## Description

The `WorkloadPriorityClass` controller reconciles a class by listing every Workload that references it and writing them one at a time, in one `Reconcile` call, without consulting the context between items. That was a bounded amount of work while the label had to be set by hand. Since v0.20 it is not, because a single class can now cover the whole cluster.

**What happened**:

`pkg/controller/core/workloadpriorityclass_controller.go` lists the class's whole membership and walks it serially:

```go
var workloads kueue.WorkloadList
if err := r.client.List(ctx, &workloads,
	client.MatchingFields{indexer.WorkloadPriorityClassKey: wpc.Name}); err != nil {
	return ctrl.Result{}, err
}

var updateErrors []error
for i := range workloads.Items {
	wl := &workloads.Items[i]
	if wl.Spec.Priority != nil && *wl.Spec.Priority == wpc.Value {
		continue
	}
	wl.Spec.Priority = new(wpc.Value)
	if err := r.client.Update(ctx, wl); err != nil {
		if !apierrors.IsNotFound(err) {
			updateErrors = append(updateErrors, err)
		}
		continue
	}
}
return ctrl.Result{}, errors.Join(updateErrors...)
```

Three properties follow from that shape. The `List` is unpaginated, so one reconcile holds every Workload referencing the class in memory. The writes are serial, so a single worker walks the entire membership before the reconcile returns. And `ctx` reaches each `Update` but is never read by the loop, so on shutdown the loop still runs to the end; the remaining writes fail locally rather than reaching the API server, and each one is appended, so the returned `errors.Join` carries an entry per remaining Workload.

**What you expected to happen**:

The writes bounded and cancellable, the way the same job is done elsewhere in the tree. `pkg/util/parallelize`'s `Until` caps concurrency, checks `ctx.Done()` before each item, and keeps one error rather than accumulating one per item. The LeaderWorkerSet reconciler writes its Workloads through it, and the Pod controller its groups.

**How to reproduce it (as minimally and precisely as possible)**:

1. Run with `WorkloadPriorityClassDefaulting` at its v0.20 default, so Workloads without an explicit label reference the class named `default`.
2. Admit enough Workloads for that class to have a large membership.
3. Change `default`'s `value`, which is what the update predicate fires on.
4. One `Reconcile` lists every one of them and updates them in sequence.

Cancelling the manager during step 4 shows the second half: the loop finishes walking the list and the reconcile returns a joined error naming every Workload it did not get to.

**Anything else we need to know?**:

This mattered less before v0.20. The gate that changed it:

> Enable defaulting of WorkloadPriorityClass to a WorkloadPriorityClass named "default" when no explicit priority class label is set.

```go
WorkloadPriorityClassDefaulting: {
	{Version: version.MustParse("0.18"), Default: false, PreRelease: featuregate.Alpha},
	{Version: version.MustParse("0.20"), Default: true, PreRelease: featuregate.Beta},
},
```

With that on, the membership of `default` is every Workload that does not name a class of its own, so the cost of one class-value change scales with the cluster rather than with how many users opted in.

This is about the shape of the write, not about which Workloads are eligible for it. #13929 covers the other half of the same loop, that it writes Workloads MultiKueue created here whose priority the manager owns.

**Environment**:

Read from `main` at `4c6dc1a35f334305a774c4c10ea4e94ef91ff0e6`; the controller has this shape in the released branches that carry the v0.20 gate default. Not observed on a cluster, so the scale numbers above are the ones the code implies rather than ones I measured.

### Comment by [@thc1006](https://github.com/thc1006) — 2026-08-13T13:53:50Z

One more property of the membership this walks: it is not filtered for terminal Workloads. `WorkloadPriorityClassKey` indexes every Workload that references the class, so an installation retaining finished ones walks and writes them too, and the value written can no longer affect anything. A finished Workload has already left the scheduler cache, since the Workload controller deletes it there on the `StatusFinished` branch.

The rest of the project guards on this already. `workloadfinish.IsFinished` gates the concurrent-admission controller, the MultiKueue workload group, the provisioning controller, the incremental dispatcher, the pod and statefulset reconcilers, the elastic-job ungater, and both the TAS indexer and node controller. The priority path is the one place that does not ask.

I would rather it landed here than as a separate change, because the guard belongs in one place for both writers. A Workload-keyed writer wants the same question asked on the reference side, where it would take the direct reads at manager startup down by however many terminal Workloads an installation keeps.
