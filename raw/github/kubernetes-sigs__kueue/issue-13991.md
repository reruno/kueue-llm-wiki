## Description

### What happened:

`validatePodSet` checks init containers, containers, and pod-level `spec.resources`, but not `spec.overhead`:

```go
	// validate pod-level resources
	if ps.Template.Spec.Resources != nil {
		resPath := path.Child("template", "spec", "resources")
		allErrs = append(allErrs, validateResourceList(ps.Template.Spec.Resources.Requests, resPath.Child("requests"))...)
```

Overhead is part of the charge. `totalRequestsFromPodSets` calls `resourcehelpers.PodRequests` with a zero-valued options struct, so `ExcludeOverhead` is false and `component-helpers` adds it:

```go
	if !opts.ExcludeOverhead && pod.Spec.Overhead != nil {
		addResourceList(reqs, pod.Spec.Overhead)
	}
```

So a Workload carrying a negative overhead passes validation with `WorkloadValidateResourcesAreNonNegative` enabled, and the negative value is added into the request that quota is taken from.

**What you expected to happen**:

Overhead is validated with the rest of the PodSet's quantities when that gate is on.

**How to reproduce it (as minimally and precisely as possible)**:

A PodSet whose container requests `example.com/gpu: 1` and whose `template.spec.overhead` is `example.com/gpu: -1`:

```
container requests 1, overhead -1, PodRequests = 0
```

The Workload is admitted holding a device it was not charged for. `Requests.FloorToZero` then makes a larger negative overhead look like a clean zero rather than a mistake.

**Anything else we need to know?**:

This matters beyond the direct case: it is the remaining way a negative operand reaches the merge in the DRA accounting path, where a logical resource charge shares a name with an ordinary request. I found it while checking that premise for KEP-2941 and have corrected the KEP, which said Pod resource requests cannot be negative.
