## Description

**What happened**:

When an extended resource is backed by a DeviceClass, the workload builder deletes the whole resource key from the PodSet's requests and adds back only the charge `ResolveExtendedResourceQuota` rebuilt from container requests. Anything else that landed on that same key is deleted with it, and nothing puts it back.

Two ways a PodSet gets a second contribution on the key:

- `spec.overhead`. `PodRequests` adds it, `ResolveExtendedResourceQuota` only walks containers.
- a resource transformation output naming that resource. Transformations run before the deletion.

There is also a third, where the rebuilt charge is simply the wrong number. `AggregateContainerRequests` adds a restartable init container's requests to the running total, since a sidecar keeps its resources for the life of the Pod. `ResolveExtendedResourceQuota` aggregates every entry in `initContainers` with max. A sidecar asking for the resource is summed by one and maxed by the other, and the deletion then removes the summed value.

**What you expected to happen**:

A charge on the key that did not come from the DRA-backed request survives the replacement, and the replacement removes what it actually replaces.

**How to reproduce it (as minimally and precisely as possible)**:

`KueueDRAIntegration` and `KueueDRAIntegrationExtendedResource` on, a DeviceClass with `spec.extendedResourceName: example.com/gpu`, and a PodSet asking for `example.com/gpu`.

Sidecar. One container asking for 1 and one restartable init container asking for 1:

```
PodRequests[example.com/gpu]                 2
ResolveExtendedResourceQuota                 1   max(init)=1, sum(regular)=1, max=1
TotalRequests[example.com/gpu]               1
```

Two devices are requested and one is charged.

Overhead. One container asking for 1, `spec.overhead` of 1 on the same key:

```
PodRequests[example.com/gpu]                 2
TotalRequests[example.com/gpu]               1
```

Transformation. One container asking for 1 for the device and 1 for `example.com/credit`, with a `Replace` transformation from `example.com/credit` to `example.com/gpu: 1`. Over 200 runs the total is 1 every time, where the device and the transformation are one each.

**Anything else we need to know?**:

The order is in `totalRequestsFromPodSets`: `PodRequests`, then `dropExcludedResources`, then `applyResourceTransformations`, then `delete` for each name in `replacedExtendedResources`, then the preprocessed DRA resources are added. The delete takes a resource name, so it cannot tell one contribution on that name from another.

Not a duplicate of #13990. That one is about which of two contributions survives `applyResourceTransformations`; here both survive it and are then deleted together, which is why the transformation case above is stable rather than order-dependent.

The sidecar half is the aggregation rule rather than the deletion, and would still be wrong if the deletion knew what it was removing.
