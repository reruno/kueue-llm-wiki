## Description

**What happened**:

`WorkloadPriorityClassReconciler` lists the workloads on a class from the cache and skips the ones whose `spec.priority` already equals the class value. When the cache has not caught up with the last write to a workload, that skip can be taken against a value the API server no longer holds, and there is no event left to come back on.

The class predicate only fires on a value change, so a sweep that skipped everything has spent the only event that change produced.

**What you expected to happen**:

The class value and the priority on every workload referencing it agree once the writes settle.

**How to reproduce it (as minimally and precisely as possible)**:

A class `high` at 100 and a workload referencing it at 100.

1. `high` is edited to 200. The sweep lists the workload at 100, writes 200 to the API server.
2. `high` is edited back to 100 before the workload informer has seen that write.
3. The sweep runs again. The cache still says 100, which is the class value, so it skips.
4. The informer catches up to 200.

The API server is left with `high` at 100 and the workload at 200, and nothing is queued: the class has no further change and the workload update is a `spec.priority` change the class controller does not watch.

Driven with a split client, reads served by a store the test advances by hand and writes sent to a second store standing in for the API server, this terminates every run.

**Anything else we need to know?**:

It rests there rather than staying wrong forever. Both controllers take a Create event for everything they watch when the manager starts, and the cache is current by then, so a restart or a leader failover repairs it. Measured on the same harness: resting state class 200 and workload 100, and after the restart both 200. That bounds the damage without making it benign, since the workload sits at the wrong preemption priority for as long as the process lives.

Editing a value back to one it held before is what makes the single-writer case reachable, but any second writer of `spec.priority` gets there without that. `jobframework.UpdateWorkloadPriority` is one, and #13920 adds another.

Verifying each candidate live before accepting the skip closes it, but the create predicate returns true unconditionally, so every class gets a sweep at startup where every workload looks up to date, and that would be one uncached read per workload per class on every start and every failover.

Whichever way it is closed, the fix has to carry the guard from #13929 with it. The sweep has no ownership check at all: it lists by index and writes. A Workload MultiKueue created here whose cached priority happens to equal this cluster's class value is skipped today, and that accidental skip is the only thing standing between it and an overwrite. Verifying live and finding a different value on the API server turns that skip into a write of the local class value over one the manager resolved, so the repair would make #13929 easier to reach rather than leaving it where it is.

Having one writer keyed on the workload, fed by both the reference events and the class events, and reading both objects live, avoids that. It would also fold in #13982 and #13929, so it is worth deciding rather than patching the skip in place.
