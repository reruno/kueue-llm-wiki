## Description

**What happened**:

`multiplyBy` reads the multiplier out of the resource list the transformations run over, and that list has already had `excludeResourcePrefixes` applied to it:

```go
effectiveRequests := dropExcludedResources(specRequests, info.excludedResourcePrefixes)
effectiveRequests = applyResourceTransformations(effectiveRequests, info.resourceTransformations)
```

```go
if mapping.MultiplyBy != "" {
    if q, ok := input[mapping.MultiplyBy]; ok {
        inputQuantity = multiplyResourceQuantities(inputQuantity, q)
    }
}
```

If the multiplier was excluded, the lookup misses and the input is carried through unmultiplied. That is a multiplier of one, and nothing says so: no error at startup, no error on the workload, no log line.

**What you expected to happen**:

Excluding a resource from quota does not silently change what another resource is charged. Either the multiplier still reads the request, or the configuration is refused.

**How to reproduce it (as minimally and precisely as possible)**:

```yaml
resources:
  excludeResourcePrefixes:
  - example.com/
  transformations:
  - input: other.com/gpumem
    strategy: Retain
    multiplyBy: example.com/gpu
    outputs:
      other.com/total-gpumem: "1"
```

A PodSet requesting `other.com/gpumem: 1024` and `example.com/gpu: 8`:

```
without excludeResourcePrefixes    other.com/total-gpumem = 8192
with the prefix above              other.com/total-gpumem = 1024
```

Eight times under-charged, from two settings that are each valid on their own.

**Anything else we need to know?**:

The API comment says the multiplier is the quantity of that resource the workload requests. It does not say the exclusion list is applied first, and an operator has no reason to read one field as changing the other.

Any missing multiplier behaves this way, not only an excluded one, but a name the workload never requests is at least a configuration the operator can see is wrong. Here the workload does request it and Kueue removes it first.

**`pods` is the second trigger, and nothing the operator writes can fix it**

```yaml
resources:
  transformations:
  - input: example.com/gpumem
    strategy: Retain
    multiplyBy: pods
    outputs:
      example.com/total: "1"
```

A PodSet of four asking for `1024` is charged `1024` per Pod, not `4096`. `pods` is not a container resource, so it is not in the list transformations run over; flavor assignment writes it from the PodSet count long afterwards. Unlike the excluded case there is no configuration that makes this one work, since the name is never present at that stage.

That widens the third option below. Refusing `multiplyBy` where it overlaps `excludeResourcePrefixes` does not reach this one; refusing a `multiplyBy` that cannot resolve at all, which covers both, does.

Three ways out, in rough order of how much they surprise:

1. refuse a `multiplyBy` that names a resource `excludeResourcePrefixes` covers, at configuration validation. Fails fast and does not change what exclusion means.
2. read the multiplier from the unfiltered requests and keep the outputs on the filtered ones.
3. document the identity fallback and cover it with a test.
