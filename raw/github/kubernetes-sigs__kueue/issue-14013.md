## Description

**What happened**:

The StatefulSet reconcile patches the queue label onto the Pods, and only then starts the two independent branches:

```go
if err := r.syncQueueLabel(ctx, sts, podList.Items); err != nil {
    return ctrl.Result{}, err
}

eg, ctx := errgroup.WithContext(ctx)

eg.Go(func() error {
    return r.finalizePods(ctx, sts, podList.Items)
})

eg.Go(func() error {
    return r.reconcileWorkload(ctx, sts)
})
```

So a Pod patch that keeps failing keeps `reconcileWorkload` from ever running. The Workload is a different object with a different reason to fail, and it does not need the label to have landed on the Pods.

**What you expected to happen**:

Work on the Pods and work on the Workload each make what progress they can. One failing does not stop the other from starting.

**How to reproduce it (as minimally and precisely as possible)**:

Any persistent failure from `syncQueueLabel`, a conflicting patch on one Pod or a webhook refusing it, leaves the Workload unreconciled for as long as it lasts, however healthy the Workload path is.

**Anything else we need to know?**:

This is the same shape as #13902, one piece of work suppressing another that does not depend on it, and the other half of it. #13921 fixes the half below this line, where a branch error cancelled its sibling through the errgroup context; the branches still do not start.

Moving it into the Pod branch keeps the Pod work sequential without holding the Workload back:

```go
eg.Go(func() error {
    if err := r.syncQueueLabel(ctx, sts, pods); err != nil {
        return err
    }
    return r.finalizePods(ctx, sts, pods)
})

eg.Go(func() error {
    return r.reconcileWorkload(ctx, sts)
})
```
