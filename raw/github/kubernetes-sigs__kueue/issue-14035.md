## Description

`handleDRA` currently both preprocesses DRA resources and queues the workload via `AddOrUpdateWorkload`, then returns done=false letting the reconciler continue to other code paths that call `AddOrUpdateWorkload`  again. The last call wins and silently overwrites earlier work.

This already caused #13930 (DRA resources lost on backoff requeue) and interacts with #13969 (condition clearing not persisted, restored by subsequent PatchAdmissionStatus). As DRA grows (counter sources,    capacity sources, TAS+DRA, WAS), each new preprocessing step that queues internally creates the same overwrite risk.

**Proposal**: separate preprocessing from queueing in the reconciler.
1. `handleDRA` becomes a pure preprocessing step. It computes DRA resources, clears stale conditions (persisted via `PatchAdmissionStatus`), and returns `InfoOptions`. It does not call `AddOrUpdateWorkload`.
2. The reconciler accumulates options from all preprocessing steps and calls `AddOrUpdateWorkload` once at the end.
3. New features add preprocessing logic, not new queueing points.

Depends on:
  - #13969 (backoffWaitingTimeExpired reason-aware, condition-clearing persistence)

### Comment by [@thc1006](https://github.com/thc1006) — 2026-08-11T20:16:23Z

This looks like a prerequisite for PodGroup-scoped DRA accounting too.

A WAS read path has to add a second class of DRA contribution whose multiplicity comes from the number of runtime PodGroups rather than from `PodSet.Count`, and that scope has to survive until after the per-Pod scaling. If it can be lost to an overwrite between the preprocessing and the queue update, it will be, and the failure is quiet: the charge just reverts to being multiplied by the Pod count. Keeping all of it as pure preprocessing ahead of a single queue update removes that whole class of bug rather than adding another place to guard. I opened #14235 for the accounting side.

Happy to review, or to help with tests that carry both the per-Pod and the per-PodGroup contributions through a requeue.

### Comment by [@thc1006](https://github.com/thc1006) — 2026-08-12T02:34:53Z

I went and counted the other call sites while checking something else, in case the number is useful here.

`workload_controller.go` on current `main` has seven `queues.AddOrUpdateWorkload` calls. Only the one inside `handleDRA` passes `queueOptions`:

```
215   AddOrUpdateWorkload(log, wl.DeepCopy(), queueOptions...)   <- the only one carrying DRA preprocessing
561   AddOrUpdateWorkload(log, wl.DeepCopy())
1253  AddOrUpdateWorkload(log, wlCopy)
1362  AddOrUpdateWorkload(log, wlCopy)
1401  AddOrUpdateWorkloadWithoutLock(log, wlCopy)
1655  AddOrUpdateWorkload(log, wlCopy)
1863  AddOrUpdateWorkload(log, wlCopy)
```

So it is six other entry points, not one. That is worth knowing because #13967 threads the options through the backoff path, which fixes the one that was reported, and leaves the other five reachable the same way. It also gets worse rather than better as more preprocessing metadata appears, since each new piece has to be threaded through every one of them.

Happy to help with tests once the shape is agreed.
