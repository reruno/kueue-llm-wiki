## Description

#### What happened:

Kueue keeps pending workloads in two different places.

```
   CQ-1's own queue                    second-pass queue
   waiting for a first attempt         has quota, waiting for one more pass
   ┌─────────────────┐                 ┌─────────────────┐
   │   B    D    E   │                 │   A             │
   └─────────────────┘                 └─────────────────┘
```

A already had its first attempt. There are two ways it can end up in the second-pass queue:

```
   deferred placement:   CQ queue ──► scheduled, quota reserved ──► placement deferred ──► second-pass queue
   node replacement:     admitted and RUNNING ──► a node it uses dies or gets tainted ──► second-pass queue
```

Either way, a workload is only ever in one of the two places at a time. A is waiting on its second pass; B has not had its first attempt yet.

Each scheduling cycle collects candidates from both places: everything ready in the second-pass queue, then the next workload from each ClusterQueue's own queue.

```
                       ┌── all of the second-pass queue ──►  A  (CQ-1)
   scheduling cycle ───┤
                       └── one from each CQ's queue     ──►  B  (CQ-1)
                                                             C  (CQ-2)

   candidates:  [  A(CQ-1)   B(CQ-1)   C(CQ-2)  ]
                     └───────┬──────┘
                     both belong to CQ-1
```

With Fair Sharing on, the iterator holds one slot per ClusterQueue. Two candidates from the same ClusterQueue means the later one overwrites the earlier one, and since second-pass workloads are added first, the overwritten one is always the second-pass workload.

```
   CQ-1 slot:   A   ──overwritten by──►   B
   CQ-2 slot:   C

   considered:      B, C
   never looked at: A
```

A is never scheduled. Its status is still the default one, which is what makes the end-of-cycle cleanup loop pick it up and send it back to the second-pass queue with the retry count bumped. It also fires a `SecondPassFailed` warning event, usually with an empty message, since nothing ever evaluated it.

CQ-1's queue still holds D and E, so the next cycles look the same:

```
   cycle 1:   A  vs  B   →   B considered,  A dropped,  retry in 1s
   cycle 2:   A  vs  D   →   D considered,  A dropped,  retry in 2s
   cycle 3:   A  vs  E   →   E considered,  A dropped,  retry in 4s
                                                        8s, 16s, then 30s forever
```

Due to backoff A comes back less and less often, settling at once every 30 seconds, and loses the slot again every time. As long as CQ-1 keeps a schedulable workload in its queue, this does not end on its own. A holds its quota reservation the whole time and runs nothing.

It is not limited to one victim per ClusterQueue. Second-pass workloads from the same ClusterQueue also overwrite each other, and a node failure or taint typically hits several workloads at once:

```
   candidates:  [ A1(CQ-1)  A2(CQ-1)  A3(CQ-1)  B(CQ-1) ]

   CQ-1 slot:   A1 → A2 → A3 → B       last write wins
   considered:  B only
   dropped:     A1, A2, A3             all backoff, all SecondPassFailed
```

With a busy queue, every second-pass workload in the ClusterQueue is dropped every cycle. Even with an empty queue, they recover at most one per cycle, in no particular order.

There is an ironic escape. If CQ-1's own candidate cannot be scheduled, it goes on a separate list and never enters the slot map, so no collision happens. The second-pass workload gets through exactly when its ClusterQueue is failing to schedule, and is starved when the ClusterQueue is healthy.

This is Fair Sharing only. The classical iterator walks every candidate, and its ordering comment says it puts quota-reserved workloads first precisely so they can take a second pass.

#### What you expected to happen:

A workload taken into a cycle for a second pass should be evaluated in that cycle, whether or not its ClusterQueue also contributed a candidate of its own, and whichever iterator is running.

#### How to reproduce it (as minimally and precisely as possible):

1. Turn on Fair Sharing.
2. Get a workload into the second-pass queue. Easiest is a deferred topology placement: admission checks all passed, topology assignment still pending, workload not yet admitted.
3. Keep schedulable pending work in the same ClusterQueue, so it contributes a candidate of its own every cycle.
4. The second-pass workload is never processed. `SecondPassFailed` warning events pile up on it, with the gap between them doubling.

#### Anything else we need to know?:

Found while reviewing #13729. (That PR does not cause this.)

Confirmed with two unit tests.

The first isolates the iterator. It builds a snapshot with one ClusterQueue, hands the same pair of entries to each iterator (one standing in for a second-pass workload, one for the ClusterQueue's own candidate, both pointing at that ClusterQueue), drains it, and records what came out. The classical iterator returns both. The fair-sharing one returns only the ClusterQueue's own candidate:

```
--- PASS: TestIteratorSameClusterQueueEntries/classical_iterator
--- FAIL: TestIteratorSameClusterQueueEntries/fair_sharing_iterator
        considered entries (-want +got):
          []string{
                "head",
        -       "second-pass",
          }
```

The scheduler's own log confirms only one workload ever leaves the iterator for that ClusterQueue:

```
fair_sharing_iterator.go:73  "Returning workload from ClusterQueue without Cohort"
                             clusterQueue={"name":"cq"}  workload={"name":"head","namespace":"ns"}
```

The second reproduces the starvation through `Scheduler.schedule` with Fair Sharing on. A ClusterQueue holds one workload waiting on a deferred topology placement (quota reserved, admission check ready, not admitted). The control arm leaves the ClusterQueue otherwise empty. The other gives it one pending workload per cycle, which is what a busy queue looks like. Quota is sized so the pending workload and the second-pass workload both fit, so the failure below is the slot collision, not quota contention. Three cycles run in both:

```
--- PASS: TestSecondPassStarvedByClusterQueueBacklog/empty_ClusterQueue
--- FAIL: TestSecondPassStarvedByClusterQueueBacklog/steady_backlog
        second pass completed = false after 3 cycles, want true (delayed request state [Pending])
```

With an empty ClusterQueue the second pass completes and the workload gets its topology assignment. With a backlog it is still `Pending` after three cycles, holding its quota reservation and running nothing.

The growing retry gap is read from the backoff constants rather than asserted.

#### Environment:
- Kubernetes version: main
- Kueue version: v0.20.0-devel, commit f9afdfa3f
- Others: Fair Sharing enabled
