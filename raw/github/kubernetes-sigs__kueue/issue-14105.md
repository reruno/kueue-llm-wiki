## Description

**What happened**:

`Amount` reserves `math.MaxInt64` as the sentinel for unlimited, and says what that costs:

```go
// math.MaxInt64 is the sentinel for "unlimited"; bounded amounts must never
// equal math.MaxInt64 (AmountFromQuantity enforces this at the quota boundary).
```

```go
func (a Amount) isUnlimited() bool { return a.value == math.MaxInt64 }
```

The quota boundary is guarded, as the comment says. The workload usage boundary is the other way in, and it is not. `Info.ResourceUsage` turns a PodSet's `int64` request into the `Amount` the quota tree counts:

```go
ru.Assigned[fr] = ru.Assigned[fr].AddInt64(q)
```

`AddInt64` saturates, so a `q` of `math.MaxInt64` gives a bounded usage that nothing downstream can tell apart from unlimited.

Reaching that `q` does not take an unrepresentable number. `totalRequestsFromPodSets` ends with

```go
setRes.Requests.Mul(int64(count))
```

and `Mul` saturates. Four pods asking for 2^62 of a countable resource is a product past `int64`, and saturation puts it exactly on the sentinel. Measured on `cead7dee`:

```
4 pods x 2^62 as a total request -> 9223372036854775807   isMaxInt64 = true
```

From there the ClusterQueue's usage for that flavor and resource reads as unlimited, and `Amount` arithmetic is no longer symmetric. `AddInt64` returns early on an unlimited receiver, so another workload's usage is never counted, while removing that workload still subtracts. Measured through the cache, with a ClusterQueue holding one such workload and one ordinary workload of 7:

```
usage after the saturating workload      9223372036854775807
usage after the 7-unit workload joins    9223372036854775807
usage after the saturating workload goes 0
usage after the 7-unit workload goes     -7
```

The second line is the ordinary workload's 7 units going uncounted, and the last is the same 7 being taken off a total that never carried them. The queue is left believing 7 units less are in use than ever were, so its available capacity is that much larger than it should be, until the process restarts and the cache is rebuilt.

**What you expected to happen**:

A workload's usage is a bounded quantity, however large, and is never mistaken for the sentinel that means no limit. Adding a workload and then removing it leaves the accounting where it started.

**How to reproduce it (as minimally and precisely as possible)**:

A PodSet with `count: 4` requesting `4611686018427387904` of any countable resource, admitted against a flavor. Neither number is past `int64` on its own.

**Anything else we need to know?**:

Two things this is not, since both are the first guesses.

It is not a permanent wedge. `Sub` answers bounded zero when both sides are unlimited, so the saturating workload's own removal clears the sentinel. What survives is the difference the swallowed additions left behind.

It is not caused by the saturating arithmetic that has been added recently. `Mul` has saturated for as long as this sentinel has existed, so the value that collides is already reachable. #14100 gives `Add` and `Sub` the same behaviour, and #14042 would give it to `ResourceValue`, so both widen the entry, and neither opens it.

What I have not established is whether the scheduler admits such a workload in the first place. The reproduction above hands an already admitted Workload to the cache, which is what a resync does and is the path `AddOrUpdateWorkload` takes without rechecking quota. Whether an admission decision can be reached in band, most plausibly against a ClusterQueue whose own quota is unlimited, is worth answering before deciding how much this matters.

On the fix, the shape I would expect is that bounded arithmetic in `Amount` stops one short of the sentinel, the way a reserved value is normally handled, so `AddInt64` cannot produce it and the invariant in the comment holds on both boundaries rather than one. Guarding the usage call site instead would leave every other caller of `AddInt64` to know the same thing. I have not sent a patch because which of those is right is a decision about what a bounded maximum means for this type, including what it reports through metrics, and that belongs with whoever owns it. Happy to write whichever is preferred.

### Comment by [@thc1006](https://github.com/thc1006) — 2026-08-11T16:14:13Z

A third way onto the sentinel turned up while I was bounding the DRA charges in #14130, and it changes what the fix has to cover, so it's worth adding here rather than filing separately.

`Mul` and `AddInt64` land on `math.MaxInt64` by saturating. The conversion into `Requests` gets there by aiming at it:

```go
func SafeValue(q resource.Quantity) int64 {
	if q.Cmp(maxValue) > 0 {
		return stdmath.MaxInt64
	}
```

DRA charges are accumulated with `MergeResourceListKeepSum`, which is `Quantity.Add` and arbitrary precision, so the total can pass `int64` without any one term doing so. Three ResourceClaimTemplates on one PodSet, each charging `MaxInt64-1` to the same logical resource, measured on `3b38ac65d`:

```
true sum                              27670116110564327418
Quantity.Value()                       9223372036854775802
NewRequestsFromResourceList (SafeValue)  9223372036854775807   sentinel
Amount(0).AddInt64(that).String()      <unlimited>
```

The middle line is worth its own note. `Value()` wraps there and hands back a positive number below the sentinel, so a bound written on `Value()` reads an unbounded charge as an ordinary one. That's the bug I had in #14130 until this week, and `SafeValue` is the fix for it, which is how I ended up here: the accessor that stops the wrap is also the one that manufactures the reserved value.

What this means for the shape you propose. Stopping `Amount`'s bounded arithmetic one short of `math.MaxInt64` closes `Mul` and `AddInt64`, but `SafeValue` and `SafeMilliValue` would still convert into the sentinel one step earlier, so the collision would move rather than go. If the invariant is that no bounded amount equals `math.MaxInt64`, then the clamp target belongs in the same change, and `AmountFromQuantity` is already the precedent for a conversion that enforces it at a boundary.

Two things I haven't established. Whether the scheduler admits such a Workload is the same open question you raised, and I haven't answered it either. And a `deviceClassMappings[].name` can be any resource name, including one a Pod also requests, in which case `totalRequestsFromPodSets` adds the two, so the DRA charge doesn't have to reach the sentinel on its own. I haven't measured how close an ordinary cluster can get that way.

### Comment by [@thc1006](https://github.com/thc1006) — 2026-08-15T20:08:57Z

TL;DR: the `MaxInt64-1` clamp I sketched isn't enough, even once `SafeValue` is folded in as I noted above. It stops the collision but not the accounting drift, so this wants a recoverable usage representation or a recompute-on-remove, not a clamp.

I pushed the clamp as #14519 (Amount `Add`/`AddInt64` stop one below the sentinel) before I looked at the remove side. It does close the collision, a bounded usage is no longer read as Unlimited, but the accounting still isn't symmetric. The sequence from this issue, run against that build:

```
usage = 0
add saturating wl  -> MaxInt64-1
add ordinary 7     -> MaxInt64-1   (the 7 is swallowed, now by saturation instead of the Unlimited short-circuit)
remove saturating  -> 0            (the 7 wl is still admitted; usage should read 7)
remove ordinary 7  -> -7
```

So the swallow just moves from `AddInt64`'s `isUnlimited` early-return to saturation at the ceiling, and the add/remove asymmetry this issue is about is still there. Flooring the subtraction doesn't save it: once the saturating wl leaves, the remaining 7 reads as 0.

Together with the `SafeValue`/`SafeMilliValue` step above, and that clamping `Amount` also nudges the quota-side contract #14100 deliberately left alone, I don't think a clamp can close this. A clamp on `Amount` only touches the assigned usage path anyway: the unassigned branch of `Info.ResourceUsage` and `FlattenFlavors` still add raw int64 with plain `+=`, so those wrap sites stay open. A real fix looks like either a recoverable usage type (int64 fast path, arbitrary precision once an aggregate leaves the bounded range) or saturation metadata plus a recompute from the remaining Workloads when a saturated key changes. Both reach into resourceNode / ClusterQueue / LocalQueue usage, cohort aggregation and snapshots.

That is a lot of change on the accounting hot path, and I have still only reached this at ~10^18-scale requests, never on a normal cluster. So before I build any of it: is it worth a recoverable-usage change, a smaller defensive hardening, or writing it down as a known limitation? Happy to take whichever you prefer, and I'll hold #14519 until then.
