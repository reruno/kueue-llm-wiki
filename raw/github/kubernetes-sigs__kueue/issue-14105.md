## Description

**What happened**:

`Amount` reserves `math.MaxInt64` as the sentinel for unlimited, and says what that costs:

```go
// math.MaxInt64 is the sentinel for "unlimited"; bounded amounts must never
// equal math.MaxInt64 (AmountFromQuantity enforces this at the quota boundary).
```

```go
func (a Amount) isUnlimited() bool { return a.value == math.MaxInt64 }
```

The quota boundary is guarded, as the comment says. The workload usage boundary is the other way in, and it is not. `Info.ResourceUsage` turns a PodSet's `int64` request into the `Amount` the quota tree counts:

```go
ru.Assigned[fr] = ru.Assigned[fr].AddInt64(q)
```

`AddInt64` saturates, so a `q` of `math.MaxInt64` gives a bounded usage that nothing downstream can tell apart from unlimited.

Reaching that `q` does not take an unrepresentable number. `totalRequestsFromPodSets` ends with

```go
setRes.Requests.Mul(int64(count))
```

and `Mul` saturates. Four pods asking for 2^62 of a countable resource is a product past `int64`, and saturation puts it exactly on the sentinel. Measured on `cead7dee`:

```
4 pods x 2^62 as a total request -> 9223372036854775807   isMaxInt64 = true
```

From there the ClusterQueue's usage for that flavor and resource reads as unlimited, and `Amount` arithmetic is no longer symmetric. `AddInt64` returns early on an unlimited receiver, so another workload's usage is never counted, while removing that workload still subtracts. Measured through the cache, with a ClusterQueue holding one such workload and one ordinary workload of 7:

```
usage after the saturating workload      9223372036854775807
usage after the 7-unit workload joins    9223372036854775807
usage after the saturating workload goes 0
usage after the 7-unit workload goes     -7
```

The second line is the ordinary workload's 7 units going uncounted, and the last is the same 7 being taken off a total that never carried them. The queue is left believing 7 units less are in use than ever were, so its available capacity is that much larger than it should be, until the process restarts and the cache is rebuilt.

**What you expected to happen**:

A workload's usage is a bounded quantity, however large, and is never mistaken for the sentinel that means no limit. Adding a workload and then removing it leaves the accounting where it started.

**How to reproduce it (as minimally and precisely as possible)**:

A PodSet with `count: 4` requesting `4611686018427387904` of any countable resource, admitted against a flavor. Neither number is past `int64` on its own.

**Anything else we need to know?**:

Two things this is not, since both are the first guesses.

It is not a permanent wedge. `Sub` answers bounded zero when both sides are unlimited, so the saturating workload's own removal clears the sentinel. What survives is the difference the swallowed additions left behind.

It is not caused by the saturating arithmetic that has been added recently. `Mul` has saturated for as long as this sentinel has existed, so the value that collides is already reachable. #14100 gives `Add` and `Sub` the same behaviour, and #14042 would give it to `ResourceValue`, so both widen the entry, and neither opens it.

What I have not established is whether the scheduler admits such a workload in the first place. The reproduction above hands an already admitted Workload to the cache, which is what a resync does and is the path `AddOrUpdateWorkload` takes without rechecking quota. Whether an admission decision can be reached in band, most plausibly against a ClusterQueue whose own quota is unlimited, is worth answering before deciding how much this matters.

On the fix, the shape I would expect is that bounded arithmetic in `Amount` stops one short of the sentinel, the way a reserved value is normally handled, so `AddInt64` cannot produce it and the invariant in the comment holds on both boundaries rather than one. Guarding the usage call site instead would leave every other caller of `AddInt64` to know the same thing. I have not sent a patch because which of those is right is a decision about what a bounded maximum means for this type, including what it reports through metrics, and that belongs with whoever owns it. Happy to write whichever is preferred.

A third way onto the sentinel turned up while I was bounding the DRA charges in #14130, and it changes what the fix has to cover, so it's worth adding here rather than filing separately.

`Mul` and `AddInt64` land on `math.MaxInt64` by saturating. The conversion into `Requests` gets there by aiming at it:

```go
func SafeValue(q resource.Quantity) int64 {
	if q.Cmp(maxValue) > 0 {
		return stdmath.MaxInt64
	}
```

DRA charges are accumulated with `MergeResourceListKeepSum`, which is `Quantity.Add` and arbitrary precision, so the total can pass `int64` without any one term doing so. Three ResourceClaimTemplates on one PodSet, each charging `MaxInt64-1` to the same logical resource, measured on `3b38ac65d`:

```
true sum                              27670116110564327418
Quantity.Value()                       9223372036854775802
NewRequestsFromResourceList (SafeValue)  9223372036854775807   sentinel
Amount(0).AddInt64(that).String()      <unlimited>
```

The middle line is worth its own note. `Value()` wraps there and hands back a positive number below the sentinel, so a bound written on `Value()` reads an unbounded charge as an ordinary one. That's the bug I had in #14130 until this week, and `SafeValue` is the fix for it, which is how I ended up here: the accessor that stops the wrap is also the one that manufactures the reserved value.

What this means for the shape you propose. Stopping `Amount`'s bounded arithmetic one short of `math.MaxInt64` closes `Mul` and `AddInt64`, but `SafeValue` and `SafeMilliValue` would still convert into the sentinel one step earlier, so the collision would move rather than go. If the invariant is that no bounded amount equals `math.MaxInt64`, then the clamp target belongs in the same change, and `AmountFromQuantity` is already the precedent for a conversion that enforces it at a boundary.

Two things I haven't established. Whether the scheduler admits such a Workload is the same open question you raised, and I haven't answered it either. And a `deviceClassMappings[].name` can be any resource name, including one a Pod also requests, in which case `totalRequestsFromPodSets` adds the two, so the DRA charge doesn't have to reach the sentinel on its own. I haven't measured how close an ordinary cluster can get that way.

```
usage = 0
add saturating wl  -> MaxInt64-1
add ordinary 7     -> MaxInt64-1   (the 7 is swallowed, now by saturation instead of the Unlimited short-circuit)
remove saturating  -> 0            (the 7 wl is still admitted; usage should read 7)
remove ordinary 7  -> -7
```

So the swallow just moves from `AddInt64`'s `isUnlimited` early-return to saturation at the ceiling, and the add/remove asymmetry this issue is about is still there. Flooring the subtraction doesn't save it: once the saturating wl leaves, the remaining 7 reads as 0.

Together with the `SafeValue`/`SafeMilliValue` step above, and that clamping `Amount` also nudges the quota-side contract #14100 deliberately left alone, I don't think a clamp can close this. A real fix looks like either a recoverable usage type (int64 fast path, arbitrary precision once an aggregate leaves the bounded range) or saturation metadata plus a recompute from the remaining Workloads when a saturated key changes. Both reach into resourceNode / ClusterQueue / LocalQueue usage, cohort aggregation and snapshots.

That is a lot of change on the accounting hot path, and I have still only reached this at ~10^18-scale requests, never on a normal cluster. On `Unlimited`. The reason a big-integer `Amount` alone is not enough is that `NewAmount(math.MaxInt64)` and `Unlimited` are currently the same value, so a finite amount that reaches the ceiling is read as the sentinel. That is what produces the `0` and then the `-7` in your paste: both operands read as unlimited, and `Sub(Unlimited, Unlimited)` is defined as bounded zero. So finite values need to be able to hold `math.MaxInt64` and beyond, which means the unlimited state needs somewhere else to live.

The tagged form was your own suggestion in #9843:

```go
type Amount struct {
    unlimited bool
    value     int64
}
```

and collapsing it to `math.MaxInt64` during the #11156 review made sense at the time, since `Amount` then only carried quotas and those all arrive through the guarded `AmountFromQuantity`. Usage came in later through `AddInt64`, which has no equivalent guard, and that is where the two meanings started to overlap. I would like to bring the explicit state back rather than pick a different sentinel, but it is your and @mszadkow's call, so please say if you would rather keep the numeric form and solve it another way.

On the decision I cannot make alone. `AmountFromQuantity` maps a large but finite quantity to `Unlimited` today because its milliCPU form does not fit `int64`, which is the `1E` CPU behaviour from #9843. Once finite arithmetic is arbitrary precision, keeping that rule makes the result depend on how an operator splits the quota: `5P + 5P` would be a finite `10^19` while a single `10P` entry stays `Unlimited`. My preference is that every finite quantity becomes a finite exact amount, and `Unlimited` is only ever set on purpose, but that changes what `1E` CPU means today and its `+Inf` metric, so I did not want to decide it quietly.

On casting to `int64` when exposing in the API, one detail I ran into while measuring. CPU amounts are stored in milliCPU, so saturating to `int64` first drops magnitude the `Quantity` can still carry. `10P` of CPU is `10^19` milliCPU, past `int64`, but `10P` is an ordinary quantity; capping in milliCPU reports it as `9223372036854775807m`, roughly `9.2P`. Applying the resource scale first and capping only if the resulting `Quantity` cannot hold the value avoids that. The ceiling there is not `int64` either: `resource.Quantity` stores `10E` fine, but `resource.ParseQuantity("1000E").String()` returns `1`, so the helper needs to check that what it emits parses back. Metrics can stay an approximate `float64`.

Scope I would suggest: the ledger only. `Requests` still saturates on its own after #14100, so a workload whose true magnitude was already lost stays lost, and #14371 and #14520 track that part. The two raw `int64` sites I mentioned on 15 Aug, the unassigned branch of `Info.ResourceUsage` and `FlattenFlavors`, are still there and I would fold them in, since `FlattenFlavors` wraps to a negative rather than saturating.

Happy to go either way on both questions. If you would like to see it in code first instead, I can put up a draft and we can split it from there, the way you suggested in #11156.

### Comment by [@thc1006](https://github.com/thc1006) — 2026-09-02T08:09:57Z

Thank you, and thank you for the #9843 link. That settles the representation question for me: I will treat the `math.MaxInt64` encoding as an implementation detail of `Amount` rather than something to preserve.

**Is the CPU case a bug on main, or one that would be introduced?** Introduced. On main `Amount` cannot hold a finite value above `int64` at all: `AmountFromQuantity` turns a CPU quota whose milliCPU form does not fit into `Unlimited` (`pkg/resources/amount.go:79`), so there is no finite `10^19` milliCPU today to lose. It becomes a bug only if the arbitrary-precision `Amount` lands while the API path keeps its current order, `used.Int64()` first and `NewMilliQuantity` after. `10P` of CPU is `10^19` milliCPU but only `10^16` cores, so narrowing first would emit `9223372036854775807m`, about `9.223P`, for a quantity that is an ordinary `10P`. The rule I mean is just that the resource scale is applied before any narrowing or capping.

**Does `math/big` versus `resource.Quantity` change that?** Only if the `Quantity` holds the resource-scaled value rather than the canonical integer. Today `Amount` is resource-agnostic: `NewAmount` and `AddInt64` take a bare `int64` that is milliCPU for CPU and whole units otherwise, and the resource name appears only at the boundaries. A `Quantity` used as an arbitrary-precision integer in that same contract has the same problem. Making it carry real units would mean threading the resource name or scale through the constructors and arithmetic call sites across the scheduler, which is a much larger change than swapping the integer. So I lean toward keeping the integer contract, with an `int64` fast path and an immutable `big.Int` slow path.

**I should also withdraw the `1000E` part of my last comment.** It mixed in a separate upstream problem. We pin `apimachinery v0.36.4`, whose `Quantity` doc says no quantity may represent a number greater than `2^63-1` in magnitude, so `1000E` was outside the documented range and not a good example for a Kueue boundary. What I actually hit there is an upstream serialization bug: `CanonicalizeBytes` discards the success result of `constructBytes`, so a DecimalSI value past `E` loses its suffix and `1000E` prints as `1`. Upstream fixed that in kubernetes/apimachinery `357557a670d84c30ef3b5355f02c11d8aba5a941`. It is not something this fix should work around, and a parse-back check is not part of what I am proposing. Applying the CPU scale first and capping only if the resulting `Quantity` is out of range is enough, and `10P` and `1E` make the point on their own since both are well under `2^63-1` in cores.

**Metrics.** The path is:

```
AmountFromQuantity(cpu, "1E")            pkg/resources/amount.go:79   -> Unlimited
Amount.AsApproximateFloat64(cpu)         pkg/resources/amount.go:104  -> math.Inf(1)
clusterQueue.reportResourceMetrics       pkg/cache/scheduler/clusterqueue.go:562
metrics.ReportClusterQueueQuotas         pkg/cache/scheduler/clusterqueue.go:573
```

Reservations and usage on the same lines go through the same conversion, and cohort subtree quota reaches it at `pkg/cache/scheduler/cohort_metrics.go:134`. With exact finite amounts, `1E` CPU would report `1e18` and `10P` would report `1e16` instead of `+Inf`. Worth noting that the `+Inf` for an absent borrowing or lending limit does not come through `Amount` at all; `clusterqueue.go:564` and `:570` set `math.Inf(1)` from the nil pointer, so that stays as it is.

I agree this is not a substantial operational difference and should not hold up the accounting fix. It is an observable change to those gauges plus the tests that pin them, and I will call it out in the PR description.

One more thing I checked while looking at that. Outside `pkg/resources`, `resources.Unlimited` appears only in tests. The production sources of the value are `AmountFromQuantity` on an oversized finite quantity and the saturating arithmetic, and both of those go away once finite amounts are exact. An absent borrowing or lending limit is already a nil pointer rather than an infinity. So rather than keeping an `unlimited` tag that may have no producer left, I will first try the simpler shape where `Amount` is only an exact finite integer, and bring the tag back as an explicit field if the full conversion turns up a path that genuinely needs infinity. Either way `math.MaxInt64` stops doubling as the sentinel.

I will put up a draft with the `int64` fast path and immutable `big.Int` slow path, no sentinel, the internal `Amount -> int64 -> Amount` round trips removed, resource-aware conversion at the API boundary, and exact arithmetic through the cache, LocalQueue, cohort propagation and fair sharing, with the add/remove sequence from this issue plus API, metrics and snapshot-aliasing tests. `Requests` stays out of scope, so a workload whose magnitude was already lost there stays lost.
