## Description

### What happened

A Workload created for a sliced job is named from the owner's generation at the moment the slice is created. The owner's generation then keeps moving while that Workload keeps its name, so a MultiKueue adapter that rebuilds the name from the owner's current generation stops identifying it.

`EnsureWorkloadSlices` is where the two come apart. A scale-down applies the new counts to the existing Workload and updates it in place:

```go
if !workload.HasQuotaReservation(wl) || ScaledDown(wlPodSetsCounts, jobPodSetsCounts) {
	workload.ApplyPodSetCounts(wl, jobPodSetsCounts)
	if err := clnt.Update(ctx, wl); err != nil {
		...
	}
	return wl, true, nil
}
```

Only a scale-up on an already admitted slice asks for a new one. So each scale-down advances the owner's `metadata.generation` without producing a Workload that carries it:

```
created        owner gen N     Workload named from gen N
scaled down    owner gen N+1   Workload still named from gen N
scaled down    owner gen N+2   Workload still named from gen N
```

The distance between the two has no upper bound, since a user can scale down as many times as they like.

### What you expected to happen

MultiKueue should be able to tell whether a Workload belongs to a given job for the lifetime of that job, including after repeated scale-downs.

### Anything else we need to know

This surfaced while reviewing #13213, which replaces prefix matching in the MultiKueue ownership check with exact matching. Prefix matching tolerated any generation, so the divergence above did not show; exact matching makes it visible. @Vaishnav88sk added a `gen` and `gen-1` key pair in that PR to cover it, which closes the window for one scale-down. The point of this issue is that the window cannot be closed by widening it, because the distance is unbounded, and `WorkloadKeysFor` receives only the job object and has no way to see which Workload exists.

`ElasticJobsViaWorkloadSlices` has been Beta and on by default since 0.18, so this is not limited to an opt-in path.

Some directions, all of which need a decision rather than a bigger constant:

- resolve the Workload rather than reconstruct its name, which would mean giving the ownership check a reader
- identify ownership from the Workload's owner reference or labels instead of its name
- keep a deliberately tolerant match for sliced jobs, and be explicit that it is tolerant and why

Filed separately from #13213 so the MultiKueue ownership fix can be reviewed on its own. Happy to pick this up if nobody else is on it.

### Update: the name is not always built from the generation either

Found while re-reading #13213. `newWorkloadName` asks the job type before falling back to the generation:

```go
if elasticWorkloadNameProvider, ok := job.(ElasticWorkloadNameProvider); ok {
	extra = elasticWorkloadNameProvider.GetWorkloadNameExtraPart()
} else {
	extra = strconv.FormatInt(object.GetGeneration(), 10)
}
```

`RayJob` and `RayService` implement `ElasticWorkloadNameProvider`, and for them it resolves to a composite:

```go
extra := strconv.FormatInt(objectMeta.GetGeneration(), 10)
rayClusterGeneration := objectMeta.GetAnnotations()[RayClusterGenerationAnnotation]
if rayClusterGeneration != "" {
	extra += "_" + rayClusterGeneration
}
```

So a Workload for those two kinds can be named from `<gen>_<rayClusterGen>` while any generation-based reconstruction produces `<gen>`. Unlike the scale-down window, this is not a distance that can be widened, since the two names are shaped differently. RayCluster has no override and falls through to the plain generation.

I have not established how often `RayClusterGenerationAnnotation` is populated in practice, only that `RayJob.GetCustomAnnotations` goes through `raycluster.GetWorkloadslicingRayClusterCustomAnnotations`.

This makes the general point sharper rather than adding a second issue: the Workload name belongs to the job type, and anything that rebuilds it from outside has to reproduce every naming rule and keep up with them as they change.

### Problem Analysis
As pointed out, rebuilding the Workload name from the Job's current `metadata.generation` is fundamentally mismatched with Workload Slicing because:
1. **Unbounded Scale-Down Drift:** `EnsureWorkloadSlices` updates existing slices in-place during scale-down without renaming them. A job scaling down $N$ times causes its `generation` to drift $N$ steps ahead of the Workload's creation generation. A static window like `[gen, gen-1]` cannot close an unbounded gap.
2. **Framework-Specific Name Providers:** Frameworks implementing `ElasticWorkloadNameProvider` (e.g., `RayJob`, `RayService`) incorporate annotations such as `RayClusterGenerationAnnotation` into `extra` (`<gen>_<rayClusterGen>`), so generation-only reconstruction diverges even at generation 1.

### Proposed Solution (Hybrid of Direction 3 & Direction 2)

Rather than trying to synthesize generation-based hashes in the adapter or modifying the `MultiKueueWatcher` interface to pass a reader, we propose handling this via a **two-tier verification in `verifyWorkloadOwnership`**:

1. **Tier 1 (Strict Exact Matching):**
   - For standard (non-sliced) jobs, continue enforcing exact name matching via `isWorkloadOwnedByKeys(wl.Name, wl.Namespace, keys)`. This preserves the Confused Deputy protection introduced in #13213.

2. **Tier 2 (Tolerant Sliced Matching):**
   - If exact matching fails, check if the object is an elastic job (`workloadslicing.Enabled(jobObj)`).
   - If slicing is enabled, verify genuine ownership using the two invariants that never change across scale-downs or custom naming rules:
     - **Deterministic Prefix:** `strings.HasPrefix(wl.Name, jobframework.GenerateWorkloadNamePrefix(jobObj.GetName(), jobObj.GetUID(), adapter.GVK()) + "-")`
     - **Immutable Identity:** `owner.UID == jobObj.GetUID()`
     - **Namespace:** `wl.Namespace == jobObj.GetNamespace()`

3. **Cleanup:**
   - Remove the `[gen, gen-1]` heuristic from `job_multikueue_adapter.go` (and avoid introducing similar heuristics in Ray adapters).

### Why This Works
- **Surgical & Minimal:** Confines the logic to `verifyWorkloadOwnership` without altering the `MultiKueueWatcher` interface signatures or requiring extra cache listings.
- **Robust Against Scale-Downs:** Tolerates arbitrary scale-downs ($N \ge 1$) because the prefix and owner UID are invariant.
- **Framework-Agnostic:** Covers `RayJob` and `RayService` composite naming automatically without custom adapter logic.
- **Maintains Confused Deputy Defense:** An attacker attempting to inject an arbitrary workload (e.g., `spoofed-wl`) fails both the prefix check and the owner UID verification.

If this direction looks good to maintainers, I can prepare a PR with accompanying unit and integration tests.
