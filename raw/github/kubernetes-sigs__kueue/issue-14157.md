## Description

**What would you like to be added**:

Nothing right now. This issue records a known scheduling-throughput tradeoff so that future "scheduling is slow" investigations have a documented lead. Not meant to be solved unless a concrete production requirement shows up.

Two mechanisms recompute a workload's flavor assignment within the scheduling cycle:

- `TASRecomputeAssignmentWithinSchedulingCycle`: recompute when the TAS assignment no longer fits mid-cycle.
- `RecomputeAssignmentUponPreemptionTargetsOverlap` (#13863): recompute when preemption targets overlap an earlier workload's claimed victims.

Each recomputes at most once per entry per cycle, so the worst case is 2x full assignment computations per cycle (TAS placement search being the expensive part), plus snapshot remove/re-add churn over the cycle's accumulated victim list for the overlap case (cheap: usage arithmetic, not assignment search). There is no cost explosion, but in contended cohorts the overlap trigger fires routinely, so the 2x bound is hit often rather than rarely. 

**Why is this needed**:

If a user ever needs to speed up scheduling cycles, this is a documented inefficiency to rule in or out before profiling from scratch.
