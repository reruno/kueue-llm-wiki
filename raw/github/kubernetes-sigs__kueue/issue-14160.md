## Description

### What happened:

The DRA extended-resource charge is merged into a PodSet's requests after `excludeResourcePrefixes` and after `resources.transformations` have run, so it takes part in neither. When a transformation names the same extended resource, the one request is charged twice.

Two shapes reach this, and configuration validation accepts both.

**A `Replace` whose input is a DRA-backed extended resource.** The transformation consumes the request and emits its own output. The DRA path then adds the device charge for a request that is no longer there to be replaced, so the same three devices are charged as three credits and as three `gpu`.

**A transformation output that lands on the logical quota name.** `deviceClassMappings[].name` and a transformation output name are separate configuration surfaces with no cross-check, so both can write `gpu`. A request for three devices is charged as six.

Measured on `5f42184cb73e589a1d321dabc7d73f5ee097ef84` with a PodSet whose single container requests `example.com/gpu: 3`, a DeviceClass carrying `spec.extendedResourceName: example.com/gpu`, and `deviceClassMappings` mapping it to the logical name `gpu`:

| `resources.transformations` | charged |
| --- | --- |
| none | `gpu=3` |
| `Replace` `example.com/gpu` → `example.com/credit: 1` | `example.com/credit=3` **and** `gpu=3` |
| `Replace` `example.com/gpu` → `gpu: 1` | `gpu=6` |

### What you expected to happen:

One request charged once. Either the two mechanisms compose so that a transformation on a DRA-backed extended resource still charges the underlying devices exactly once, or the configuration is rejected at validation so an operator finds out before a Workload is admitted against the wrong number.

### How can we reproduce it (as minimally and precisely as possible):

`pkg/workload/workload.go` builds a PodSet's requests in this order:

```go
specRequests := resourcehelpers.PodRequests(&corev1.Pod{Spec: ps.Template.Spec}, resourcehelpers.PodResourcesOptions{})
effectiveRequests := dropExcludedResources(specRequests, info.excludedResourcePrefixes)
effectiveRequests = applyResourceTransformations(effectiveRequests, info.resourceTransformations)
if features.Enabled(features.KueueDRAIntegration) && info.preprocessedDRAResources != nil {
	// remove the replaced extended resources, then add the DRA logical resources
}
```

Exclusion and transformation are applied to `specRequests` only. The charge is merged afterwards, so it is neither excluded nor transformed, and the removal step cannot reach an amount a transformation has already moved to another name.

A self-contained reproducer, as `pkg/workload/zz_repro_test.go` on main:

```go
func TestZZRepro(t *testing.T) {
	features.SetFeatureGateDuringTest(t, features.KueueDRAIntegration, true)
	wl := &kueue.Workload{
		ObjectMeta: metav1.ObjectMeta{Name: "w"},
		Spec: kueue.WorkloadSpec{PodSets: []kueue.PodSet{{
			Name: "a", Count: 1,
			Template: corev1.PodTemplateSpec{Spec: corev1.PodSpec{
				Containers: []corev1.Container{{Resources: corev1.ResourceRequirements{
					Requests: corev1.ResourceList{"example.com/gpu": resource.MustParse("3")},
				}}},
			}},
		}}},
	}
	info := NewInfo(wl,
		WithResourceTransformations([]config.ResourceTransformation{{
			Input:    "example.com/gpu",
			Strategy: new(config.Replace),
			Outputs:  corev1.ResourceList{"gpu": resource.MustParse("1")},
		}}),
		WithPreprocessedDRAResources(
			map[kueue.PodSetReference]corev1.ResourceList{"a": {"gpu": resource.MustParse("3")}},
			map[kueue.PodSetReference]sets.Set[corev1.ResourceName]{"a": sets.New[corev1.ResourceName]("example.com/gpu")},
		))
	fmt.Println(info.TotalRequests[0].Requests.ToResourceList(nil))
	// map[gpu:{{6 0} {<nil>}  DecimalSI}]
}
```

Swapping the output name for `example.com/credit` gives `map[example.com/credit:3 gpu:3]` from the same single request.

### Anything else we need to know?:

Nothing rejects either configuration. `validateResourceTransformations` checks that the strategy is `Retain` or `Replace` and that inputs are unique, and stops there. `validateDeviceClassMappings` never looks at `Transformations`. The two functions are independent, and an operator gets no signal that a transformation input or output collides with a DRA-backed name.

Same root cause and worth deciding alongside it, though it is arguably intended: `excludeResourcePrefixes` does not reach the charge either. With `excludeResourcePrefixes: ["gpu"]` and the mapping above, the Workload is still charged `gpu=3`.

This is separate from #14004. That one is about the removal step taking more off the key than the charge stands for, and its fix subtracts the containers' request instead of deleting the entry. None of the numbers above change under it, because the amount has already moved to a different name by the time the subtraction runs.
