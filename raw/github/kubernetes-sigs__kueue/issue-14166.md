## Description

**What would you like to be added**:

Extend the MultiKueue manager→worker sync mechanism (the `RemoteSpecSyncer` interface plus the local-job watch introduced in #14036) to also forward selected manager-side **metadata** changes — labels/annotations — to the worker copy after admission, in particular the workload **priority label**.

Today the local-job watch (`localJobHandler.Update`) keys on `metadata.generation`, which bumps only on spec changes. Metadata-only edits (labels, annotations) therefore never trigger a sync and are not forwarded (see the `TODO` in `localJobHandler.Update` in `pkg/controller/admissionchecks/multikueue/workload.go`).

**Why is this needed**:

Some manager-side changes that operators expect to take effect on the worker are metadata-only. The priority label is the motivating example: changing it on the manager should propagate to the running worker copy, but with the current generation-only filter it is silently dropped after admission. Forwarding an allowlisted set of labels/annotations would let these changes reach the worker.

### Comment by [@kevin85421](https://github.com/kevin85421) — 2026-08-14T07:56:54Z

After digging into this, the motivating use case here — the workload priority (`kueue.x-k8s.io/priority-class`) label — already propagates from the manager to the worker end-to-end, so this issue does not need the metadata-forwarding mechanism for priority.

To be precise about what does and does not get updated on the worker cluster when the priority-class label is changed on an admitted manager job:

- **The worker `Workload` CR is updated.** Changing the label re-prioritizes the manager `Workload` (jobframework's `UpdateWorkloadPriority`), and MultiKueue forwards that priority to the worker `Workload` in place (the `PriorityChanged` path in `reconcileGroup`, `pkg/controller/admissionchecks/multikueue/workload.go`). The worker's own job reconciler does not revert it: the remote job is a prebuilt workload, and `ensureOneWorkload` returns prebuilt workloads before reaching `UpdateWorkloadPriority`, so the worker never re-derives priority from the worker job label.
- **The worker job CR is NOT updated.** Its `kueue.x-k8s.io/priority-class` label stays at the value it had at creation (metadata is not re-synced manager→worker), so it goes stale relative to the manager job.
- **This does not matter.** The worker's scheduling priority comes from the worker `Workload`'s `Spec.Priority`, not from the worker job CR's label. Since the worker `Workload` is updated correctly, the change takes effect; the stale job-CR label is cosmetic.

This is already covered by an e2e test — `Should keep workload priority event if job reconcile` in `test/e2e/multikueue/baseline/e2e_test.go` — which changes the priority-class label after admission, asserts the worker `Workload` is updated, actively triggers a worker-side job reconcile (pod failure), and `Consistently` asserts the worker priority is not reverted.

So the only thing the generic metadata-forwarding mechanism (`RemoteSpecSyncer` + local-job watch) would add here is keeping the worker **job CR's** own labels/annotations in sync — which, for priority, has no functional effect.

Priority is the only concrete use case named in this issue, and it already works today, so there's no priority-driven need for the generic metadata-forwarding mechanism right now. Leaving this open as a placeholder: if a concrete non-priority label/annotation that must reach the worker **job CR** comes up, that would be the driver to build the allowlisted forwarding described above.
