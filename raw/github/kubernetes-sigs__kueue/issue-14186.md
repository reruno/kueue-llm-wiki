### Comment by [@Singularity23x0](https://github.com/Singularity23x0) — 2026-11-20T14:10:14Z

Hi @nsega 

1. This metric is a gauge like `kueue_admitted_active_workloads` and should behave the same. Note that when interacting with the `CustomLabels` storage object, we need to ensure it won't be corrupted by multiple metrics using it. Things like adding, updating and deleting labels must be synchronized across the metrics so that we do not corrupt them.

2. To my knowledge `kueue_admitted_active_workloads` keeps no entries until a workload is admitted, so I propose using the same approach here. In short then: YES, it is okay for the metric to have no entries until a workload is admitted.

3. The implementation here should be analogous to what we did for `kueue_admitted_active_workloads`. `labelValsSet` is used as a storage unit and key-type in the CustomLabels object. Any usage outside of that object is meant to be read-only. WIth that in mind - we should never put CQ labels into `labelValsSet` objects, rather extract the values from `labelValsSet` into a separate obejct to sotre them alongside CQ labels. We want to keep `labelValsSet` as small as possible so as not to burden the CL object with larger memory allocation. 6 -> 8 would be a ~33% increase which seems like a lot.
