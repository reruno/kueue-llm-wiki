## Description

## Summary

Improve TAS failed-node replacement behavior when preemptions are already in flight.

When `TASFailedNodeReplacementFailFast` is enabled, a workload that needs a node replacement can be evicted immediately if its assignment mode is not `Fit`. This can evict the workload even when an in-flight preemption is expected to free a suitable node shortly.

## Required change

Investigate and implement a scheduler path that identifies capacity expected from in-flight preemptions for failed-node replacements. Defer the fail-fast eviction when that capacity can satisfy the replacement. Preserve fail-fast eviction when no pending preemption can provide a suitable placement.

The solution may require scheduler state that remains available across scheduling cycles. Do not assume that changing only the current `mode != flavorassigner.Fit` condition is sufficient.

## Rationale

Waiting for a relevant in-flight preemption avoids evicting a gang workload unnecessarily. The workload can then complete its node replacement after the target workload is removed.

## Affected areas

- `pkg/scheduler/scheduler.go`
  - `Scheduler.processEntry`
  - `Scheduler.handleFailedTASReplacement`
  - assignment recomputation and preemption state handling
- TAS failed-node replacement scheduling behavior
- Scheduler tests for in-flight preemption and failed-node replacement

## Acceptance criteria

- If a pending preemption can free a suitable topology placement, the scheduler does not evict the failed-node replacement workload solely because it currently does not fit.
- If no pending preemption can provide a suitable placement, `TASFailedNodeReplacementFailFast` retains its current fail-fast behavior.
- The behavior is correct across scheduling cycles.
- Tests cover both the defer and fail-fast cases.
