## Description

## Summary

Improve TAS failed-node replacement behavior when preemptions are already in flight.

When `TASFailedNodeReplacementFailFast` is enabled, a workload that needs a node replacement can be evicted immediately if its assignment mode is not `Fit`. This can evict the workload even when an in-flight preemption is expected to free a suitable node shortly.

## Required change

Investigate and implement a scheduler path that identifies capacity expected from in-flight preemptions for failed-node replacements. Defer the fail-fast eviction when that capacity can satisfy the replacement. Preserve fail-fast eviction when no pending preemption can provide a suitable placement.

The solution may require scheduler state that remains available across scheduling cycles. Do not assume that changing only the current `mode != flavorassigner.Fit` condition is sufficient.

## Rationale

Waiting for a relevant in-flight preemption avoids evicting a gang workload unnecessarily. The workload can then complete its node replacement after the target workload is removed.

## Affected areas

- `pkg/scheduler/scheduler.go`
  - `Scheduler.processEntry`
  - `Scheduler.handleFailedTASReplacement`
  - assignment recomputation and preemption state handling
- TAS failed-node replacement scheduling behavior
- Scheduler tests for in-flight preemption and failed-node replacement

## Acceptance criteria

- If a pending preemption can free a suitable topology placement, the scheduler does not evict the failed-node replacement workload solely because it currently does not fit.
- If no pending preemption can provide a suitable placement, `TASFailedNodeReplacementFailFast` retains its current fail-fast behavior.
- The behavior is correct across scheduling cycles.
- Tests cover both the defer and fail-fast cases.

Hi @pajakd @amy! I'd like to pick this up — I'm the same contributor, previously on account 3900563672 (no longer available), now on hdgd337.

I agree with @amy's analysis in the #13863 review comment that spawned this issue, and verified the mechanics: replacement workloads carry no preemption targets — `updateAssignmentForTAS` skips the TAS preemption branch when the workload has a topology assignment with unhealthy nodes (`scheduler.go:960-975`), and KEP-2724 limits replacement to cases where no preemption/reclamation is needed. Since `preemptedWorkloads` only covers the current cycle (`scheduler.go:357`), the DeferredFit path never runs for them, and fail-fast (`scheduler.go:444`) evicts on `mode != Fit` even when an in-flight preemption will free a suitable domain shortly.

Plan: before the fail-fast eviction, check whether in-flight evictions can free a placement that fits the replacement's domain. If so, simulate their removal (reusing `Snapshot.SimulateWorkloadRemoval`, as the overlap recompute does at `scheduler.go:746`), recompute the assignment, and defer using the same semantics as the DeferredFit branch (`scheduler.go:474`): the `PendingPreemption` requeue reason and the `WaitingForPreemptedWorkloads` quota-reserved reason. Otherwise, fail-fast stays unchanged.

For the cross-cycle "capacity is coming" signal, I plan to derive it from the snapshot: workloads with the `Evicted` condition that still hold usage (evicted workloads keep their quota until their pods terminate, so they stay in the snapshot). This covers the full in-flight window — the `preemptionExpectations` store only covers the short "issued but not yet observed" window and is lost on leader switch — and it adds no new scheduler state. The check re-runs every cycle, so it picks up the freed capacity as soon as the eviction completes. One question: if a victim's pods get stuck terminating, the deferral has no natural bound — would you prefer it tied to the victim's pod termination, or is an unbounded wait acceptable (it would match how preemptors wait today)? Happy to switch to the store-based approach if you prefer it.

I'll start with two tests: the negative regression (no suitable pending preemption, including evictions that free the wrong domain, still evicted) and the defer case. Also, the issue is still assigned to my old account — could it be reassigned to hdgd337? Thanks!
