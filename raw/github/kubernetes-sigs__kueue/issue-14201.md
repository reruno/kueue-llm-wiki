## Description

**Actors on the stage:**

 * On the Kueue side:
   * `Workload` - a **gang admission & preemption unit** (well, unless we do "partial" or "elastic").
     * _May specify_: topology, priority.
   * `PodSet` - a group of **homogeneous** Pods in a `Workload`.
     * _May specify_: topology.

* On the WAS side:
  * `Workload` - a bag for `[Composite]PodGroup`s. (TBH I'm not sure what role it actually plays).
  * `PodGroup` - a group of Pods, possibly **heterogeneous**.
    * _May specify_: gang, topology, priority, preemption policy.
    * May be bundled together in `CompositePodGroup`s.
  * **gang scheduling units** - specified by WAS API but...
    * They're indirect, and orthogonal to WAS resource kinds. A gang scheduling unit could be:
      - a single `PodGroup` (in case it's `gang`, and has no `gang` parent)
      - *less* than a `PodGroup` (in case it's `basic`; then the units are single Pods)
      - *more* than a `PodGroup` (in case it has a `gang` CompositePodGroup as a parent)
    - They can be partial/elastic too, by specifying partial `minCount`s.
      (Even worse, could be hierarchically partial. That clearly doesn't translate to Kueue internals at all).
  * **gang preemption units** - may align with scheduling units or not, depending on disruption policies.

**Fundamental question:**

How should these objects map to each other? 

The Kueue -> WAS mapping is hopefully easy, but at least 2 scenarios are hard:

* **Scenario 1.** WAS objects exist, Kueue objects should be created -> but what objects?
  * 1.1. What should a Kueue Workloads correspond to?
    * **1.1A:** To a WAS Workload.
      * Intuitively nice, but makes "gang admission" diverge from "gang scheduling" - *does that make sense?*
        * _Example:_ A WAS Workload consists of 3 independent PodGroups, each of them gang (count = minCount = 10).
          If we let Kueue treat it as a single Workload, it will be a gang admission unit of size 30.
          So if the cluster has free space for 20 Pods, Kueue won't let anything run. Even though WAS would do.
    * **1.1B:** To a WAS gang scheduling unit.
    * **1.1C:** To the larger of: WAS gang scheduling unit, WAS gang preemption unit.
  * 1.2. What should a Kueue PodSet correspond to?
    * **1.2A:** To a WAS PodGroup, if it's homogeneous. Otherwise - claim a failure.
    * **1.2B:** To a maximal homogeneous subset of a WAS PodGroup.
* **Scenario 2.** WAS & Kueue objects both exist -> questions:
  * 2.1. How should we try matching them against each other?
    * **2.1A:** Rearrange Kueue objects following WAS objects (according to some strategy for Scenario **1**).
    * **2.1B:** Expect Kueue objects to match WAS objects (according to some strategy for Scenario **1**). Otherwise - claim a failure.
    * **2.1C:** Be a bit more flexible than in **2.1B**, e.g. tolerate 1:many relationships between the sides as long as it's obvious how to aggregate one of the sides to match the other one.
      * _Just an example:_ If a Kueue Workload with 1 PodSet corresponds to a WAS Workload with 3 PodGroups, we may add up the PodGroup sizes and put it on the PodSet.
  * 2.2. What if matching fails?
    * **2.2A:** Kueue ignores the existence of WAS objects, and proceeds according to its own specs.
    * **2.2B:** Kueue deactivates the "conflicting" Workload(s), preventing them from running.
    * **2.2C:** ~Kueue "yields to WAS", stepping back from controlling the "conflicting" Pods.~
      * Likely a no-go; it would let Kueue users unexpectedly bypass quota checks by creating "conflicting" WAS specs.
        Still, I'm mentioning it for a full picture.
    * **2.2D:** Kueue attempts approximating from the *stricter* side.
      * _Example:_ Given a gang (count = 5, minCount = 4) of gang PodGroups (each having count = 10, minCount = 8), Kueue approximates that all as a single Workload (= single admission gang) of size 5 * 10 = 50.
        Then, admissibility should imply schedulability (@), but not vice versa.

        (@) Well, typically (e.g. assuming no interfering cluster state changes between admission and scheduling).
        And assuming that Kueue can faithfully use WAS for schedulability predictions (= [#13149](https://github.com/kubernetes-sigs/kueue/issues/13149)).

    * **2.2E:** Kueue attempts approximating from the *looser* side.
      * _Example:_ Given a gang (count = 5, minCount = 4) of gang PodGroups (each having count = minCount = 10), Kueue approximates that all as 5 Workloads, each of them an independent "admission gang", of size 10.
        Then, schedulability should imply admissibility (@@), but not vice versa.

        (@@) Again, typically (assuming no interfering changes etc.).
        Also, I deliberately simplified this example to avoid a case of Kueue naively relying on `minCount`, which feels dangerous (see [here](https://github.com/kubernetes-sigs/kueue/pull/13643#discussion_r3745454840)).

At first, I assumed the answer has been set. Yet, I can't find it, despite having looked through sources like:
- the main WAS [KEP-4671](https://github.com/kubernetes/enhancements/tree/master/keps/sig-scheduling/4671-gang-scheduling)
- the [integration strategy](https://docs.google.com/document/d/13I3bMY-abBtsWmDhCl4RdDHKchHeB3G8zMSTpplmxHA/edit#heading=h.vt4px4s7if1y) doc
- #13150 
- #12385
- #13707
- #13598 
- #13643 

Maybe I'm overlooking sth - then happy to be educated - but I feel there's a need to open this issue and discuss.

**Why is the answer needed:**

* [#13643](https://github.com/kubernetes-sigs/kueue/pull/13643) is likely going to need answers in Scenario **1**.
* [#13707](https://github.com/kubernetes-sigs/kueue/issues/13707) is likely going to need answers in Scenario **2** (and hence likely also in Scenario **1**).

etc.

**Case studies:**

[#13707](https://github.com/kubernetes-sigs/kueue/issues/13707) provides a nice table of existing & planned integrations (both Kueue & WAS).

I gave that table to AI and asked about compatibility with the above strategies.
The response in a nutshell was that:
_(disclaimer: I haven't yet validated it myself)_

* LWS won't work with **1.1A**.
  (1 LWS -> 1 WAS Workload, N Kueue Workloads).
* JobSet won't work with **1.1B** or **1.1C**.
  (1 JobSet -> potentially 1 WAS Workload with N gang PodGroups, 1 Kueue Workload).
* LWS, TrainJob, JobSet et al. won't work with **1.2A**.
  (WAS integrations may involve heterogeneous PodGroups).
* Then, **2.1C** feels unavoidable to keep all Kueue & WAS integrations working together.

### Comment by [@thc1006](https://github.com/thc1006) — 2026-08-11T20:15:15Z

DRA brings a second cardinality into this mapping, and I don't think `PodSet.Count` can carry it.

A ResourceClaimTemplate referenced by a Pod generates one claim per Pod. Referenced by a PodGroup, KEP-5729 generates it once for the whole group: "A ResourceClaimTemplate referenced by a PodGroup will cause a ResourceClaim to be generated once for that PodGroup". Every Pod in the group then consumes that one allocation, and a second PodGroup using the same template gets its own separate claim, so the replication unit is the PodGroup rather than the Pod.

Kueue's accounting currently assumes the other shape. `pkg/workload/workload.go` merges the preprocessed DRA logical resources into a PodSet's effective per-Pod requests, and then the whole thing is scaled:

```go
setRes.Requests = resources.NewRequestsFromResourceList(effectiveRequests)
setRes.Requests.FloorToZero()
setRes.Requests.Mul(int64(count))
```

For a claim whose mapped charge is `example.com/gpu: 8`, that gives:

| shape | claim instances | correct charge |
| --- | ---: | ---: |
| 64 Pods, Pod-level template | 64 | 512 |
| one 64-Pod PodGroup sharing one generated claim | 1 | 8 |
| four 64-Pod PodGroups on the same template | 4 | 32 |

Reading a PodGroup's claim and feeding it into the existing preprocessing would charge the middle row 512 instead of 8, so a single group could exhaust a quota 64 times its real footprint.

The scaling in the other direction has the same problem. When reclaimable Pods bring the count down, `Info.Requests` is rescaled proportionally (`Divide(oldCount)` then `Mul(newCount)`), which would shrink a shared claim that hasn't changed at all: 64 Pods dropping to 32 would take a group's 8 GPUs down to 4 while the claim still holds 8.

So a Kueue to WAS projection needs to keep at least three things that a flat ResourceList loses:

- the claim scope, Pod or PodGroup;
- the number of claim instances the envelope covers;
- which runtime PodGroup produced each group-scoped charge, by UID rather than name, so a delete and recreate isn't silently deduplicated.

The invariant I'd want to hold is that every runtime ResourceClaim allocation instance is charged by exactly one admission envelope, exactly once.

This is separate from what one claim spec is worth. #13599 and #13601 cover the per-claim valuation; this is about how many instances the WAS graph produces. I'm happy to write up a DRA mapping profile starting from the exact one Workload to one PodGroup case, and leave JobSet and LWS as follow-up profiles once the basic contract is settled.

_Disclosure: I used an AI coding assistant while drafting this. I checked the KEP wording and the Kueue accounting path myself._

### Comment by [@44past4](https://github.com/44past4) — 2026-08-19T14:36:51Z

My take on those questions:
- Scenario 1.
  - 1.1. What should a Kueue Workloads correspond to?

    I believe that we should go with "1.1B: To a WAS gang scheduling unit." option taking the top most gang scheduling unit from the WAS CompositePodGroup/PodGroup tree. So for instance if we have both CompositePodGroup and its children marked with Gang policy we should map CompositePodGroup to Kueue Workload. As mentioned in the issue description option 1.1A will not work for workloads like LWS where Kueue already maps a single true workload to multiple Kueue Workloads / Kueue Pod Groups. When it comes to option 1.1C as WAS gang preemption unit cannot be larger than WAS gang scheduling unit this option is basically the same as 1.1B.

   - 1.2. What should a Kueue PodSet correspond to?

     Implementing 1.2B might be problematic because it will require quite complex logic to group pods. Besides the actual use cases for WAS heterogeneous PodGroups for true workloads are quite limited and are currently mostly about LWS. From the kube-scheduler perspective heterogeneity of the PodGroups limit some potential scheduling optimizations so with the CompositePodGroup introduction it is not clear for me if we shouldn't try to have all standard workloads mappins to use homogeneous PodGroups only. Because of this I would probably suggest to go with 1.2A first.

- Scenario 2.
  
  I am not sure if I agree with the whole question being a valid one because it is not clear for me what "Kueue objects exist" in this context really means. My understanding is that in normal circumstances Kueue objects like Kueue Workload are created based on some true workload resources like Job or JobSet which are supported by Kueue. So it is not like that we have some existing Kueue and WAS objects which already exist but rather we can have some WAS objects and we can have some Kueue objects which Kueue would create for a given workload and there may be some misalignment between those.

  In such case I believe that we should distinguish two situation: 

  A. Kueue uses some default logic for creating Kueue objects.

  B. User provides some explicit Kueue config for a workload to force some specific mapping like for instance mapping each Job in JobSet to separate Kueue workload or using some specific TAS constraint.

  With those two situations in A. WAS config should be a primary source of information and there it should override Kueue default mapping basically following "2.1A: Rearrange Kueue objects following WAS objects (according to some strategy for Scenario 1)." option. In B. Kueue should block such workloads from running basically following "2.2B: Kueue deactivates the "conflicting" Workload(s), preventing them from running." option to avoid situations where creation of WAS resources breaks existing Kueue features.
