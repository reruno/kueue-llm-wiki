## Description

**What happened**:

Exclusions are applied to the PodSet's requests, and the transformations then run over whatever is left:

```go
effectiveRequests := dropExcludedResources(specRequests, info.excludedResourcePrefixes)
effectiveRequests = applyResourceTransformations(effectiveRequests, info.resourceTransformations)
```

`applyResourceTransformations` walks the list it's handed, so an input the filter removed isn't there to match:

```go
for inputName, inputQuantity := range input {
	mapping, ok := transforms[inputName]
```

The transformation never fires and its outputs are never generated. Nothing says so: no error at startup, no condition on the Workload, no log line. The outputs can sit under a prefix nobody excluded and they still disappear.

KEP-2937 describes this and says it should be caught:

> We should implement additional verification to flag overlaps between `resources.excludeResourcePrefixes` and `resources.transformations`. The implementation applies the exclusions before the transformations, so if a resource both matches an exclusion prefix and is an input resource to a transformation the transformation will never apply. This could be detected when validating the configuration and reported as a configuration error.

That paragraph is under `### Graduation Criteria`, and the same KEP's Implementation History records `2025-09-08: Promoted to GA`, so it graduated without the check. `validateResourceTransformations` today only rejects an unknown strategy and a duplicate input.

**What you expected to happen**:

Keeping a vendor prefix out of quota doesn't delete a resource I asked Kueue to charge under a different name. Either the transformation still sees its input, or something tells me the pair does nothing.

**How to reproduce it (as minimally and precisely as possible)**:

An admin converting a vendor resource into their own credits, who separately keeps the vendor prefix out of quota:

```yaml
resources:
  excludeResourcePrefixes:
  - nvidia.com/
  transformations:
  - input: nvidia.com/gpu
    strategy: Replace
    outputs:
      team.io/credits: 5
```

A PodSet requesting `nvidia.com/gpu: 2`, run through `workload.NewInfo`:

```
excludeResourcePrefixes=[]             TotalRequests = map[team.io/credits:10]
excludeResourcePrefixes=[nvidia.com/]  TotalRequests = map[]
```

`team.io/credits` isn't covered by any prefix in that configuration.

**Anything else we need to know?**:

The detection the KEP asks for would refuse a configuration the documentation shows. `administer_cluster_quotas.md` sets `excludeResourcePrefixes: ["example.com"]` under "Exclude arbitrary resources in the quota management", and the next section gives a transformation with `input: example.com/gpu-type1`. `dropExcludedResources` matches with `strings.HasPrefix`, so an admin who followed both sections would be refused. A configuration error is fatal, `cmd/kueue/main.go` calls `os.Exit(1)` on it, so implementing the criterion as written turns a running cluster into one that won't start after an upgrade. That seems worth settling before writing the check.

This isn't the same thing as #14007. There the transformation still fires and `multiplyBy` quietly becomes one, because the multiplier is read out of the already filtered list. Here the transformation doesn't fire at all, and the field involved is `input`.

The field's own comment reads wider than what it does, which may be part of why the pair looks safe:

```go
// ExcludedResourcePrefixes defines which resources should be ignored by Kueue
ExcludeResourcePrefixes []string `json:"excludeResourcePrefixes,omitempty"`
```

What it filters is the Pod's requests. Names Kueue synthesises afterwards, transformation outputs and DRA logical resources, are added after the filter and aren't affected by it either way.

I haven't sent a patch. Validating the overlap, running the transformations before the filter, and leaving the behaviour but documenting it are three different answers to what `excludeResourcePrefixes` means, and picking one belongs with whoever owns that field. Happy to write whichever is preferred.
