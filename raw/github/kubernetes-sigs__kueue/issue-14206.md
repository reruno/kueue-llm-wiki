## Description

**What happened**:

A claim naming a DeviceClass that `deviceClassMappings` doesn't cover marks the Workload inadmissible through `field.NotFound`, with the whole explanation passed where the missing value goes (`pkg/dra/claims.go:218-221`):

```go
allErrs = append(allErrs, field.NotFound(
	field.NewPath("spec", "podSets").Index(i).Child("template", "spec", "resourceClaims").Index(j).Child("resourceClaimTemplateName"),
	fmt.Sprintf("DeviceClass %s is not mapped in DRA configuration for podset %s", dc, ps.Name),
))
```

The helper's second parameter is the value that wasn't found, and it becomes `BadValue`:

```go
// NotFound returns a *Error indicating "value not found".  This is
// used to report failure to find a requested value (e.g. looking up an ID).
func NotFound(field *Path, value interface{}) *Error {
	return &Error{
		Type:     ErrorTypeNotFound,
		Field:    field.String(),
		BadValue: value,
	}
}
```

So the condition an operator reads carries a sentence where a name belongs:

```
spec.podSets[0].template.spec.resourceClaims[0].resourceClaimTemplateName: Not found: "DeviceClass gpu.example.com is not mapped in DRA configuration for podset main"
```

The path has the same problem from the other side. It names `resourceClaimTemplateName`, and that field was found. What wasn't found is the DeviceClass, which the mapping is keyed on.

**What you expected to happen**:

The not-found value is the DeviceClass name, the path names a field that has something wrong with it, and the explanation goes in the detail, the way the rest of the package does it. That reads as:

```
...resourceClaims[0].resourceClaimTemplateName.deviceClassName: Not found: "gpu.example.com"
```

**How to reproduce it (as minimally and precisely as possible)**:

Submit a Workload whose ResourceClaimTemplate names a DeviceClass absent from `resources.deviceClassMappings`, with `KueueDRAIntegration` on, and read the resulting condition message. `TestReconcileDRA` already pins the string, at `pkg/controller/core/workload_controller_dra_test.go:295` and `:307`.

**Anything else we need to know?**:

This is cosmetic and I'd understand it being closed as such. I'm raising it because the message isn't only internal: `site/content/en/docs/tasks/manage/setup_dra.md` quotes it word for word ("marks the Workload inadmissible, with `DeviceClass <class> is not mapped in DRA configuration for podset <podset>`"), so whoever changes the call has three places to keep in step, and it's cheaper to know that up front than to find out from a docs build.

There's a second reason it's worth settling now rather than later. My open #14130 adds a `firstAvailable` path that hits the same condition, and it reports it the way the helper reads, with the class as the value and the path on `deviceClassName`. Whichever form is preferred, the two paths should agree, and I'm happy to move mine to match this one instead if that's the call.
