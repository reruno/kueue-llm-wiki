## Description

## Summary

`SchedulingEquivalenceHashing` can group `ElasticJobsViaWorkloadSlices` Workloads that have different replacement state into the same scheduling equivalence class.

A representative failure can then defer a replacement Workload that is schedulable.

## Required changes

Update the scheduling equivalence shape or the class-wide deferral logic so that replacement state cannot cause an unsafe equivalence decision.

Choose one of these approaches:

- Include the scheduling-relevant replacement state in the equivalence shape.
- Exclude affected `ElasticJobsViaWorkloadSlices` Workloads or outcomes from class-wide handling.

## Rationale

The KEP lists this as an open scheduling-shape gap. The current behavior can repeatedly defer a schedulable replacement Workload.

## Affected areas

- `SchedulingEquivalenceHashing` implementation
- `ElasticJobsViaWorkloadSlices` scheduling path
- `keps/9694-scheduling-equivalence-hashing/README.md`

## Acceptance criteria

- A replacement Workload is not bulk-deferred based on a non-equivalent representative.
- Tests cover the replacement-state scenario.
- The KEP risk status and mitigation are updated when the implementation resolves the gap.
