## Description

### What would you like to be added:

Define how Kueue accounts for DRA ResourceClaims whose allocation scope is a WAS PodGroup rather than an individual Pod.

A ResourceClaimTemplate referenced by a Pod generates one claim per Pod. Referenced by a PodGroup, KEP-5729 generates it once for that group and every Pod in the group consumes the same allocation. Two PodGroups on the same template get two separate claims. So the replication unit is the PodGroup.

Kueue's DRA preprocessing produces a logical resource request per PodSet. The request builder merges it into the PodSet's effective per-Pod requests and then scales the result by `PodSet.Count`. That is right for a Pod-scoped template and cannot express a group-scoped one.

For a claim whose logical charge is `example.com/gpu: 8`:

| shape | claim instances | correct charge |
| --- | ---: | ---: |
| 64 Pods, each generating its own claim | 64 | 512 |
| one 64-Pod PodGroup sharing one generated claim | 1 | 8 |
| four 64-Pod PodGroups on the same template | 4 | 32 |

The middle row is the one that matters. This is not a bug anyone can hit today, since Kueue does not ingest PodGroup-scoped claims yet. It is a trap waiting for the read path: reusing today's per-Pod preprocessing unchanged is the natural thing to do, and it charges the middle row 512 for a footprint of 8.

### Why is this needed:

A flat `map[PodSetReference]ResourceList` has already lost the distinction by the time the count is applied, so the projection needs to keep:

1. the claim scope, `Pod` or `PodGroup`;
2. how many claim allocation instances the Kueue Workload covers;
3. a stable identity for each group-scoped instance. A finalizer already keeps a PodGroup from being deleted while its Pods are running, so the name is not as fragile as I first assumed, but the identity still has to carry the claim entry, and whether it also needs the UID is part of the design;
4. which Workload and PodSet hold the corresponding charge.

The charge would then be the per-Pod part scaled by the effective Pod count, plus one contribution per distinct PodGroup claim entry. Not per PodGroup: `spec.resourceClaims` holds up to four entries, so one group can generate several claims and each of them is charged once. The Go shape isn't the point of this issue, but the scope has to survive until after PodSet scaling rather than being flattened before it.

Flattening early also breaks the other direction. When reclaimable Pods lower the count, `Info` rescales the whole request proportionally, so 64 Pods dropping to 32 would take a shared 8-GPU claim down to 4 while the claim itself is unchanged. That is why the first version should reject partial admission, reclaimable Pods and WorkloadSlices rather than pretend the scaling generalizes.

Invariants worth pinning:

- within one cluster and quota-accounting domain, every runtime ResourceClaim allocation instance is charged by exactly one admission envelope, exactly once;
- a group-scoped claim is charged once for the group no matter how many Pods reference it;
- two PodGroups sharing a template are charged twice;
- adding Pods inside an existing PodGroup does not multiply a group-scoped charge, and adding a PodGroup cannot lower the total;
- reconciling again, or observing the same objects in a different order, gives the same charge;
- if Kueue can't establish the scope, the group identity or a single accounting owner, the Workload is inadmissible rather than falling back to per-Pod multiplication.

### Completion requirements:

Initial scope, deliberately narrow so the accounting representation can be reviewed on its own:

- one Kueue Workload matching exactly one runtime PodGroup, one homogeneous PodSet;
- template-generated claims only. A direct ResourceClaim can be shared by more than one PodGroup, which is one allocation against several reservations, and counting PodGroups would double charge it;
- scope decided by the upstream exact-match rule on `name`, `resourceClaimName` and `resourceClaimTemplateName`, since matching template names alone does not make a Pod's claim group-scoped;
- count-based `deviceClassMappings`, static membership;
- gated consistently with the parent WAS read path rather than behind a gate of its own, since letting an admin enable group claims while disabling correct accounting would only create a wrong fallback. The exact boundary belongs with the parent design;
- ambiguous or unsupported mappings produce a specific condition and event.

- [ ] claim scope and multiplicity design agreed
- [ ] the exact one Workload to one PodGroup profile
- [ ] unit tests, plus property tests for permutation invariance, idempotence and exact-once
- [ ] integration test covering the 64-Pod group charging 8 rather than 512, a Pod-scoped and a group-scoped claim coexisting, and two groups on one template charging twice
- [ ] an explicit inadmissible condition for ambiguous mappings
- [ ] the unsupported Alpha cases written down

One-to-many mappings, heterogeneous groups across several PodSets, JobSet and LWS replicas, CompositePodGroup hierarchies and elastic scaling should follow once the reference profile holds.

Not in scope, since each already has an owner:

- what one ResourceClaimSpec is worth, including `firstAvailable` valuation: #13599, #13601
- binding the admitted charge to the spec the runtime claim was actually generated from: #13842
- node and device allocation feasibility: #10548, #13534
- separating DRA preprocessing from queueing: #14035
- the general Kueue to WAS resource mapping: #14201, and the controller-provided read path: #13707

### Comment by [@thc1006](https://github.com/thc1006) — 2026-11-18T15:17:07Z

I wrote in the description that nobody can hit this today. That was wrong. Kubernetes 1.36 already lets the Pods of a PodGroup [share one claim](https://github.com/kubernetes/kubernetes/blob/v1.36.0/staging/src/k8s.io/api/core/v1/types.go#L4509-L4515), and 1.37 lets a Job ask for that through `spec.scheduling.resourceClaims`. Both are behind feature gates that are off by default. Kueue still [charges such a claim once per Pod](https://github.com/kubernetes-sigs/kueue/blob/c2a63ce12470a699bdabebacac9b5101db5cad02/pkg/workload/workload.go#L822-L830).

On kind with v1.37.0 and Kueue main, a 4-Pod Job ran on one device and was charged `gpu: 4`. A second Job of the same shape stayed pending, with 7 of the 8 devices free.
