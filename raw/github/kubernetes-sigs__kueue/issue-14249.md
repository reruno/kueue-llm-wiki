## Description

**What happened**:

A source-backed device class is charged nothing at all when the ResourceSlice API is absent, rather than the Workload being held back.

The claim-template path leaves the device count to the counter and capacity paths when a mapping has sources:

https://github.com/kubernetes-sigs/kueue/blob/707286041a26da6580f8ab43cbc5e893cbece792/pkg/dra/claims.go#L224-L229

Those paths only run when the ResourceSlice API is there:

https://github.com/kubernetes-sigs/kueue/blob/707286041a26da6580f8ab43cbc5e893cbece792/pkg/controller/core/workload_controller.go#L175

https://github.com/kubernetes-sigs/kueue/blob/707286041a26da6580f8ab43cbc5e893cbece792/pkg/controller/core/workload_controller.go#L184

and the option that turns them off says so plainly:

> When false, the KueueDRAIntegrationPartitionableDevices and KueueDRAIntegrationConsumableCapacity code paths are skipped to avoid reconciliation errors on clusters without ResourceSlice API.

So with the gate on, a mapping carrying `sources`, and `resource.k8s.io/v1` unavailable, the first branch declines to charge the device count because something else will, and the something else never runs. The request contributes zero.

The skip itself was a deliberate choice in #13629, to keep the manager from crashlooping on a cluster without the API. What it did not settle is what should happen to a Workload whose quota cannot be computed as a result. Skipping the reconcile path and admitting the Workload for free are different things.

This is not confined to a claim that is entirely source-backed. A PodSet holding one ordinary count-based request and one source-backed one is charged for the first and not the second, so nothing about the Workload looks unusual from the outside.

**What you expected to happen**:

A Workload whose charge depends on a source that cannot be read is not admitted on the strength of a charge that was never computed. Failing it closed, or refusing the configuration at startup when `sources` are set and the API is absent, both seem preferable to a silent zero.

Falling back to the device count is not right either: a counter or capacity charge is denominated in the source's own units, not in devices, so the two are not interchangeable.

**How to reproduce it (as minimally and precisely as possible)**:

Read from the code rather than run on a cluster, so I would not want to claim more than that.

1. `KueueDRAIntegration` and `KueueDRAIntegrationPartitionableDevices` on, against an apiserver without `resource.k8s.io/v1`.
2. A mapping with a counter source:

```yaml
deviceClassMappings:
- name: example.com/gpu-memory
  deviceClassNames:
  - mig.example.com
  sources:
  - counter:
      name: memory
      driver: mig.example.com
      deviceSelector:
        cel:
          expression: "true"
```

3. A ResourceClaimTemplate with an `exactly` request naming `mig.example.com`.
4. The Workload is admitted with no `example.com/gpu-memory` charge.

`KueueDRAIntegrationConsumableCapacity` with a `capacity` source is the same shape.

**Anything else we need to know?**:

Both halves are on `main` and predate the prioritized-list work in #14130; that PR does not touch `workload_controller.go`. I came across it while re-reading the claim-template path for something else.

I have not sent a patch because the choice is not mine to make: refusing the Workload, refusing the configuration at startup, or passing availability into the claim-template path so it can charge the device count instead are three different contracts. Happy to write whichever you would prefer.

Adding the measurement here, since I ran it separately and then went and filed the same thing again as #14262. Closing that one; this is the earlier issue and it has the provenance already.

The part worth keeping is the control. Charging nothing is only interesting if the counter path would have charged something, so I ran both halves against a slice carrying a counter set:

```
claim-template path       ->  example.com/gpu = 0      errs = 0
counter path (API up)     ->  example.com/gpu = 10Gi   errs = <nil>
```

`errs = 0` on the first row is the bit that makes it silent rather than fail-closed: the path doesn't refuse the request, it just contributes nothing and leaves the rest to a path that may not run.

The second row took two tries. My first slice had one device against a request for eight, and the counter path returned `insufficient matching devices for counter driver: 1 device(s) match but 8 requested` and charged zero. Read alone that would have said "the counter path charges nothing either, so it makes no difference", which is the opposite of what's happening. Worth mentioning in case anyone writes the regression from the same starting point.

One thing I didn't do: I never built a `WorkloadReconciler` with `resourceSliceAPIAvailable` false and ran `handleDRA` end to end. Both contributions above come from the real functions, composed the way `handleDRA` composes them, so the final step is read rather than executed.
