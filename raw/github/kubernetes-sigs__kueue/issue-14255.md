## Description

**What happened**:

A Workload written directly can carry a pod-level request smaller than the containers it covers, and Kueue charges the smaller one.

The apiserver refuses that shape on a Pod. `validatePodResourceConsistency` compares the aggregate against each pod-level entry:

https://github.com/kubernetes/kubernetes/blob/v1.37.0/pkg/apis/core/validation/validation.go#L4948-L4960

> must be greater than or equal to aggregate container requests of %s

A Workload is not a Pod, so nothing runs that check on `podSets[].template.spec`. The Workload webhook validates each container's list and the pod-level lists separately, but never compares the two levels.

The charge then follows `resourcehelpers.PodRequests`, which lets a pod-level entry replace the container total rather than add to it, so:

```yaml
podSets:
- name: main
  count: 1
  template:
    spec:
      containers:
      - resources:
          requests:
            cpu: "8"
      resources:
        requests:
          cpu: "0"
```

reserves zero CPU for a PodSet whose container asks for eight.

**What you expected to happen**:

Either the Workload is refused the way the Pod would be, or the charge is the larger of the pod-level request and the aggregate the containers ask for. Both leave every valid PodSpec alone, since a valid one already satisfies the invariant.

**How to reproduce it (as minimally and precisely as possible)**:

1. Enable `PodLevelResources`.
2. Create the Workload above directly, without a Job on top of it.
3. Read `status.admission` or the ClusterQueue usage: the reservation is zero CPU.

A unit-level version is quicker: hand `workload.NewInfo` a PodSet with one container requesting `cpu: 8` and `spec.resources.requests.cpu: 0`, and read `TotalRequests`.

**Anything else we need to know?**:

This is not about negative quantities. Both numbers here are valid on their own, and each passes the per-list validation Kueue already does; it is only the relationship between the two levels that is wrong, and that is the part nobody checks.

I noticed it while writing a test for #14047 and, for a while, wrote the shape down as legitimate. It is worth saying that the reservation is what a Workload asked for rather than what its Pods will use, so the gap costs quota rather than causing an admission failure.

I have not sent a patch because the two fixes have different blast radii: refusing it in the webhook is the honest answer but needs the same ratcheting the overhead work in #13995 is adding for existing objects, while charging the maximum is quieter and needs none. Happy to write whichever you prefer.
