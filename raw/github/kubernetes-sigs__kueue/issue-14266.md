## Description

**What happened**:

The StatefulSet webhook lets the queue name change while the Workload still holds a quota reservation, and the reconcile that follows can never apply it.

The webhook decides a StatefulSet is quiescent from its Ready count:

https://github.com/kubernetes-sigs/kueue/blob/756b8b9bb64211be5165984f021924ccc79c8591/pkg/controller/jobs/statefulset/statefulset_webhook.go#L167-L172

```go
// Prevents updating the queue-name if at least one Pod is not suspended
// or if the queue-name has been deleted.
isSuspended := oldStatefulSet.Status.ReadyReplicas == 0
if !isSuspended || newQueueName == "" {
    allErrs = append(allErrs, apivalidation.ValidateImmutableField(newQueueName, oldQueueName, queueNameLabelPath)...)
}
```

`ReadyReplicas == 0` is not the same as "no reservation". The Workload CRD forbids the change on a different condition, `QuotaReserved`:

```
((has(oldSelf.status) && ... oldSelf.status.conditions.exists(c, c.type == 'QuotaReserved' && c.status == 'True'))
 && (has(self.status) && ... self.status.conditions.exists(c, c.type == 'QuotaReserved' && c.status == 'True')))
  ? ((has(oldSelf.spec.queueName) == has(self.spec.queueName)) && (!has(oldSelf.spec.queueName) || oldSelf.spec.queueName == self.spec.queueName))
  : true
```

and the reconciler writes the new name with nothing standing between:

https://github.com/kubernetes-sigs/kueue/blob/756b8b9bb64211be5165984f021924ccc79c8591/pkg/controller/jobs/statefulset/statefulset_reconciler.go#L273-L276

```go
if replicas > 0 && wl.Spec.QueueName != queueName {
    wl.Spec.QueueName = queueName
    shouldUpdate = true
}
```

So a StatefulSet whose Workload is reserved but whose Pods are not Ready accepts the rename, the Pods are relabelled to the new queue, and every attempt to move the Workload is refused by the apiserver.

**What you expected to happen**:

Either the webhook refuses the rename while the Workload is reserved, or the transition releases the reservation first. What should not happen is the StatefulSet and its Pods naming one queue while the Workload names another and the reconcile fails on every pass.

**How to reproduce it (as minimally and precisely as possible)**:

Traced through the code rather than run, so the ordering below is what I expect rather than what I watched.

1. A StatefulSet with `replicas: 3` on `old-lq`, whose Workload has `QuotaReserved=True`.
2. Keep the Pods from becoming Ready. An image that cannot be pulled is enough, and so is a node shortage; the point is only that `status.readyReplicas` stays at `0`.
3. Change the StatefulSet's `kueue.x-k8s.io/queue-name` label to `new-lq`. The webhook accepts it.
4. Watch the Pods pick up `new-lq`, and the StatefulSet reconcile fail on the Workload update, repeatedly.

**Anything else we need to know?**:

This is worth separating from the ordinary case where the reservation is released when a StatefulSet scales to zero. `shouldReleaseReservation` is gated on `replicas == 0`, so a StatefulSet sitting at three replicas and no Ready Pods keeps its reservation indefinitely. That makes the window a state rather than a race: a StatefulSet whose Pods are crashlooping or unschedulable can stay there for as long as the operator leaves it.

I came across it while reading the same path for #14117, which moves the queue-label write into the Pod branch. That PR does not introduce this: the old code also wrote the Pod labels before reaching the Workload, so the two could already disagree.

The webhook comment says "if at least one Pod is not suspended", which reads like the intent was closer to the reservation than to readiness. Whether the right test is `QuotaReserved`, `status.admission`, or something that also covers the eviction window is not obvious to me from outside, which is why I have not sent a patch.
