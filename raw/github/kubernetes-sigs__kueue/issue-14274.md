## Description

### What happened:

A Workload naming a `runtimeClassName` and carrying its own overhead is charged the overhead it carries, and the RuntimeClass is never read.

`handlePodOverhead` only reads the class when the overhead is empty:

```go
podSpec.Overhead = resources.ChargeableOverhead(podSpec.Overhead)
if podSpec.RuntimeClassName != nil && len(podSpec.Overhead) == 0 {
	var runtimeClass nodev1.RuntimeClass
	...
	podSpec.Overhead = runtimeClass.Overhead.PodFixed
}
```

On a Pod that is safe, because the apiserver will not let the two disagree. Measured against v1.36.3 with a server-side dry run, against a RuntimeClass defining `cpu: 250m`:

```
overhead, no runtimeClassName        rejected: Pod Overhead set without corresponding RuntimeClass defined Overhead
overhead, runtimeClass not found     rejected: RuntimeClass "nosuchclass" not found
overhead 250m, class 250m            accepted
overhead 1m,   class 250m            rejected: Pod's Overhead doesn't match RuntimeClass's defined Overhead
```

Only the matching shape survives, so skipping the lookup for a Pod charges the same number either way.

A Workload is not a Pod, and nothing runs that check on `podSets[].template.spec`. One written directly, or a prebuilt Workload for a Job, can name a class defining `cpu: 250m` while carrying `overhead: {cpu: 1m}`. Kueue charges `1m`. The Pods the Job actually creates go through the admission controller and get `250m`, so the reservation is short by the difference on every Pod.

### What you expected to happen:

Either the overhead a Workload carries is checked against the class it names, the way the apiserver checks a Pod, or the class is read regardless and its value is the one charged.

### How to reproduce it (as minimally and precisely as possible):

A RuntimeClass with `overhead.podFixed.cpu: 250m`, and a Workload whose PodSet template names it and sets `overhead.cpu: 1m`. The Workload reserves `1m` of overhead per Pod.

### Anything else we need to know?:

Not introduced by #13995, which is about overhead that is invalid rather than inconsistent. That PR removes negative and `pods` entries before this check, so an overhead that was only invalid now empties out and the class is read after all. What is left is an overhead that is valid on its own and disagrees with the class.

#9030 covers the lookup returning an error and being logged rather than surfaced, which is a different step.

One thing I should have checked before filing, since it decides whether the prebuilt path is reachable at all: the equivalence check a prebuilt Workload is held to does not look at overhead.

`comparePodTemplate` in `pkg/util/equality/podset.go` compares init containers and containers and stops there:

```go
if !equality.Semantic.DeepEqual(a.InitContainers, b.InitContainers) {
	return false
}
return equality.Semantic.DeepEqual(a.Containers, b.Containers)
```

So a prebuilt Workload can carry an overhead its Job's Pod template does not have, and nothing rejects the pair. That is what leaves the gap open rather than making it theoretical.

What I have not done is drive it end to end: build that Workload, admit it, and read the charge back. The steps above are the apiserver behaviour measured directly, the Kueue code path read, and this comparison read. ### Comment by [@thc1006](https://github.com/thc1006) — 2026-08-12T09:50:39Z

Correcting myself: I named the wrong field above.

`comparePodTemplate` not looking at `overhead` is not the gap, and it should not look at it. A Job template never passes through the RuntimeClass admission that writes the overhead, so a Job and a prebuilt Workload legitimately differ there.

The field it needs is `runtimeClassName`, which it also does not compare:

```go
if !opts.ignoreTolerations && !equality.Semantic.DeepEqual(a.Tolerations, b.Tolerations) {
	return false
}
if !equality.Semantic.DeepEqual(a.InitContainers, b.InitContainers) {
	return false
}
return equality.Semantic.DeepEqual(a.Containers, b.Containers)
```

That matters because it decides which class the fix resolves. Making the lookup authoritative resolves the class the *Workload* names, and nothing required that to be the class the *Job* names, so a prebuilt Workload could point at a cheaper class, or at none, and still be taken as standing for a Job pointing at an expensive one. The overhead would then be read correctly off the wrong class.

Both halves are in #14289.
