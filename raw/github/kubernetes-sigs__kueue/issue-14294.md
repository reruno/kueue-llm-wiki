## Description

### What happened:

Kueue reads the overhead a RuntimeClass defines and ignores the scheduling constraints it defines, so a flavor can be assigned that the Pods will never be placeable on.

`RuntimeClass` carries both:

```go
Overhead   *Overhead   `json:"overhead,omitempty"`
Scheduling *Scheduling `json:"scheduling,omitempty"`
```

and `Scheduling` is the class's `nodeSelector` and `tolerations`. The RuntimeClass admission controller merges those into the Pod it admits, the same way it writes the overhead.

Kueue reads the overhead in `handlePodOverhead`, and `.Scheduling` appears nowhere in `pkg/workload/resources.go`. The only other use of the type is the watch in `workload_controller.go`.

That matters because flavor assignment is decided from the PodSet template, which doesn't carry them. `flavorassigner.go` reads exactly the two fields the class would have added:

```go
taint, untolerated := corev1helpers.FindMatchingUntoleratedTaint(log, flavor.Spec.NodeTaints, append(podSpec.Tolerations, flavor.Spec.Tolerations...), ...)
```

```go
if len(spec.NodeSelector) != 0 {
```

So a Workload naming a class whose `scheduling.nodeSelector` pins its Pods to one pool can be assigned a flavor backed by another. Kueue reserves the quota, and the Pods are then created carrying a selector that the assigned flavor's nodes don't satisfy.

### What you expected to happen:

The constraints the class will add are taken into account when the flavor is chosen, the same way its overhead is taken into account when the charge is computed. Either the template is resolved against the class before assignment, or a Workload naming a class with `scheduling` set is refused rather than assigned a flavor that may not hold it.

### How to reproduce it (as minimally and precisely as possible):

A RuntimeClass with `scheduling.nodeSelector` naming a label only some nodes carry, two ResourceFlavors whose nodes differ by that label, and a Workload naming the class with no selector of its own. The flavor is chosen without the selector, and the Pods are created with it.

### Anything else we need to know?:

I haven't driven this to a Pod that fails to schedule. What is above is the two fields the assigner reads, the absence of `.Scheduling` from the accounting path, and the upstream field that the admission controller merges. The consequence follows from those but I haven't watched it happen, so please read it as that.

Found while making the class authoritative for overhead in #14289, which doesn't change this: it resolves the class for the charge and still leaves the constraints out of the assignment.
