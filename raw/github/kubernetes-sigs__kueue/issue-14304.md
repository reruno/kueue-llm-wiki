## Description

Title: [TAS] Node replacement fails when kubernetes.io/hostname differs from the Node name

**What happened**:

For a TAS topology whose lowest level is `kubernetes.io/hostname`, the
`TopologyAssignment` stores the value of that label. However, the node failure
controller receives Node events keyed by `Node.metadata.name` and uses that
value to look up Workloads assigned to the node.

Kubernetes allows these two values to differ. For example:

```yaml
apiVersion: v1
kind: Node
metadata:
  name: node-x1
  labels:
    kubernetes.io/hostname: x1
```

In this case, a TAS assignment refers to the node as `x1`, while the Node
reconcile request refers to it as `node-x1`. The admitted Workload index is
populated from the topology assignment, so looking it up with `node-x1` does
not find the Workload.

As a result, when `node-x1` becomes NotReady for longer than the node failure
delay, the controller logs that it is marking the node as failed, but the
affected Workload's `status.unhealthyNodes` remains empty and replacement does
not start.

The same identity mismatch also affects adjacent paths:

- a pending TAS Pod event enqueues its hostname node selector value as though
  it were a Node name, so an existing healthy Node can be treated as deleted;
- replacement compares `status.unhealthyNodes[].name` (the Node name) with the
  hostname value in the topology assignment, so the stale domain is not
  removed;
- the topology ungater performs the same comparison, so a replacement Pod can
  still be ungated onto the unhealthy hostname domain.

**What you expected to happen**:

TAS node failure handling should correlate the Kubernetes Node name with the
hostname topology value and consistently identify the same Node throughout
failure detection, replacement, and Pod ungating.

A NotReady Node should mark all affected Workloads and allow their topology
assignments to be replaced, regardless of whether `Node.metadata.name` equals
the value of the Node's `kubernetes.io/hostname` label.

**How to reproduce it (as minimally and precisely as possible)**:

I reproduced this against the current `main` branch with local unit tests using:

```text
Node.metadata.name: node-x1
Node label kubernetes.io/hostname: x1
TopologyAssignment lowest-level value: x1
```

The following four regression scenarios fail:

1. Reconcile a NotReady `node-x1` after the failure delay. Expected
   `status.unhealthyNodes: [{name: node-x1}]`; got an empty list.
2. Reconcile `x1` as queued by a pending Pod with
   `nodeSelector[kubernetes.io/hostname]=x1`, while the Ready Node is named
   `node-x1`. Expected no unhealthy node; got `{name: x1}` because `GET Node
   x1` returned NotFound.
3. Run replacement with `unhealthyNodes: [{name: node-x1}]` and an existing
   assignment for `x1`. Expected assignment to move to a healthy node; got
   `Cannot replace the node, because the existing topologyAssignment is
   invalid, as it contains the stale domain x1`.
4. Reconcile a gated replacement Pod for an assignment on `x1` with
   `unhealthyNodes: [{name: node-x1}]`. Expected the Pod to remain gated; it was
   ungated with `nodeSelector[kubernetes.io/hostname]=x1`.

I can submit the regression tests separately once the intended representation
or mapping between these two identifiers is agreed on.

**Anything else we need to know?**:

The Kubernetes documentation explicitly notes that the value of
`kubernetes.io/hostname` can differ from the Node name in some environments:
https://kubernetes.io/docs/reference/node/node-labels/

This is related to the unhealthy-node protection added by #14099 for #14092,
but it is a distinct edge case: that protection currently works when the
hostname topology value and Node name are equal.

A possible direction is to represent or carry both identifiers explicitly,
rather than treating the hostname topology value as a Node name. Tests where
the two values differ would be useful across the node controller, scheduler
replacement, and topology ungater paths.

### Comment by [@tomsen02](https://github.com/tomsen02) — 2026-08-13T05:44:28Z

I traced the history of the two identifiers and added a focused deletion-path regression test locally.

- #3677 intentionally changed `TopologyAssignment` to store only the `kubernetes.io/hostname` label value when hostname is the lowest level, in order to reduce the Workload object size.
- #5184 later introduced the node-failure controller and compared the Node reconcile key (`Node.metadata.name`) directly with that assignment value. Its tests used the same string for both identifiers, so the mismatch was not covered.
- During the API discussion in #6648, `UnhealthyNodes[].name` was explicitly intended to contain the actual Node name. The struct form was preferred partly to leave room for additional node information in the future.

I also tested this sequence using the same reconciler instance:

1. Create and reconcile a healthy Node with `metadata.name=node-x1` and `kubernetes.io/hostname=x1`.
2. Use `x1` in an admitted Workload's hostname-level `TopologyAssignment`.
3. Delete the Node.
4. Reconcile `node-x1` again.

The controller logs `Node not found. Marking as failed immediately`, but the Workload's `status.unhealthyNodes` remains empty. This confirms that the mapping is not retained even if the controller observed the Node before deletion. The Node delete event still carries the old object and its labels, but `TypedEnqueueRequestForObject` reduces it to a reconcile request containing only `node-x1`.

Would it make sense to keep the two identities explicit in `UnhealthyNode`, for example by adding an optional hostname/topology-domain value alongside `name`?

```go
type UnhealthyNode struct {
    Name                string // Node.metadata.name
    TopologyDomainValue string // hostname value used by TopologyAssignment
}
```

The node controller and Pod lookups would continue using `Name`, while Workload indexing, assignment replacement, and ungating comparisons would use the topology-domain value. Existing objects without the new field could fall back to `Name`, preserving the current equal-name behavior.

If this representation is acceptable, I can prepare the API/conversion changes and regression coverage for the node controller, scheduler replacement, and topology ungater. I have not started an implementation because this changes a public Workload status type and I wanted to confirm the intended model first.
