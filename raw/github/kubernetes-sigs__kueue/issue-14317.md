## Description

### What happened:

The overhead Kueue records for a Workload can stop matching the overhead its Pods actually carry, in two ways that want different answers. Both come from the same place: a RuntimeClass writes the overhead onto a Pod when the apiserver creates it, and the class is free to change between then and now, since only `handler` is immutable.

Found while reading the same path for #14274, so this is neither a regression from that nor blocked on it.

**A RuntimeClass edited after a Workload reserves quota is never picked up.**

The handler that reacts to a class change lists pending Workloads only:

```go
func (h *resourceUpdatesHandler) queueReconcileForPending(ctx context.Context, q ..., opts ...client.ListOption) {
	lst := kueue.WorkloadList{}
	opts = append(opts, client.MatchingFields{indexer.WorkloadQuotaReservedKey: string(metav1.ConditionFalse)})
	err := h.r.client.List(ctx, &lst, opts...)
```

So a Workload that has reserved quota and is waiting on an AdmissionCheck is not revisited. If the class overhead changes during that wait, the Job is unsuspended afterwards and its Pods are created with the new value, while `status.admission.podSetAssignments[].resourceUsage` still holds the old one. The ClusterQueue accounts one figure and the nodes carry another, in whichever direction the class moved.

**A fast-admission Pod group cannot express two generations at once.**

`constructGroupPodSetsFast` builds one PodSet from a single Pod that already exists, then widens the count to the whole group:

```go
podSets, err := constructPodSets(&podInGroup)
podSets[0].Name = kueue.NewPodSetReference(roleHash)
podSets[0].Count = int32(groupTotalCount)
```

That PodSet stands for the seed Pod, which was admitted under the class as it was, and for the Pods not created yet, which will get the class as it will be. If the class changes in between there is no single value the PodSet could hold that is right for both.

These are not the same problem. The first is a refresh gap and could be answered by revisiting reserved Workloads, or by recomputing at admission. The second is a representation gap, and refreshing cannot fix it, because one number has to stand for two populations.

### What you expected to happen:

For the first, either the recorded usage tracks the class the Pods will actually be created under, or the class stops being editable underneath a reservation.

For the second, no strong view. Refusing fast admission when the seed Pod's class no longer matches, or not widening the count past what has been observed, both seem plausible, and both have costs I am not well placed to weigh.

### How to reproduce it (as minimally and precisely as possible):

For the first, with a class defining `cpu: 250m`:

1. Submit a Job naming that class into a ClusterQueue with an AdmissionCheck that does not complete immediately.
2. Wait for `QuotaReserved=True`. The recorded usage includes `250m` a Pod.
3. Edit the class to `cpu: 1m`.
4. Let the AdmissionCheck pass. The Job is unsuspended and its Pods are created carrying `1m`.
5. `status.admission` still records `250m` a Pod.

Reverse the edit to get the over-committed direction.

For the second, with the same class and `kueue.x-k8s.io/pod-group-fast-admission`:

1. Create the first Pod of a group whose total count is greater than one. It is admitted with `250m`.
2. Before the rest are created, edit the class to `1m`.
3. The PodSet built from the first Pod is charged `250m` for every member, while every member created after the edit carries `1m`.

I have read these from the source rather than run them, and have said so rather than implying otherwise.

### Anything else we need to know?:

Related but separate: #14274 is about a Workload whose overhead never matched its class at all, and #14294 is about the class's scheduling constraints rather than its overhead.

I have not opened these as two issues because the harm is one thing and splitting the report seemed likely to lose the contrast between them. Happy to split if you would rather track them apart.
