## Description

**What happened**:

`resources.Amount` treats `math.MaxInt64` as the `Unlimited` sentinel, and the arithmetic on it is written around that: `Add`, `AddInt64`, `Sub`, `SubInt64` and `Cmp` all check `isUnlimited()` first, and `Requests.Mul` saturates through `SaturatingMul` so an overflowing product becomes the sentinel rather than wrapping.

`Divide` is the one operation that does not know about it. Both backends divide the raw value:

```go
// pkg/resources/requests.go
func (r MapRequests) Divide(f int64) {
	for k := range r {
		...
		r[k] /= f
	}
}

// pkg/resources/slice_requests.go
func (sr *SliceRequests) Divide(f int64) {
	for i := range *sr {
		...
		(*sr)[i].value /= f
	}
}
```

So once a total has saturated to `Unlimited`, dividing it produces an ordinary finite number that no longer represents anything. `PodSetResources.ScaledTo` divides by the old count and multiplies by the new one, which turns "this workload wants more than can be represented" into "this workload wants a third of MaxInt64", and that smaller number is what gets recorded as usage.

Three non-test paths divide, and all three are on the admitted-usage path:

- `PodSetResources.ScaledTo` (`pkg/workload/workload.go:334`), reached from `Assignment.TotalRequestsFor`, which builds the usage charged to the ClusterQueue, and from the partial-admission branch of the flavor assigner that scales `TotalRequests` down to the counts it is about to admit.
- `PodSetResources.SinglePodRequests` (`pkg/workload/workload.go:294`, through `Requests.ScaledDown`), which is what the admitted-resources builder hands to the TAS topology domain requests.
- the reclaimable-Pod scale-down at `pkg/workload/workload.go:762`, which divides by the admitted count and multiplies by the count after reclaim.

**What you expected to happen**:

Dividing `Unlimited` stays `Unlimited`, the same way subtracting from it does. A request that could not be represented before scaling should not become representable because it was scaled down.

**How to reproduce it (as minimally and precisely as possible)**:

No DRA, no feature gates, one PodSet. Drop this in `pkg/workload` and run it:

```go
func TestScaledToDividesTheSentinel(t *testing.T) {
	half := resource.NewQuantity(math.MaxInt64/2, resource.DecimalSI)
	wl := utiltestingapi.MakeWorkload("w", "ns").
		PodSets(*utiltestingapi.MakePodSet("main", 3).
			Request("example.com/gpu", half.String()).Obj()).
		Obj()

	total := NewInfo(wl).TotalRequests[0]
	agg := total.Requests.ResourceValue("example.com/gpu")
	t.Logf("one Pod asks             %d", math.MaxInt64/2)
	t.Logf("aggregate over 3 Pods    %d  (Unlimited sentinel = %v)", agg, agg == math.MaxInt64)

	scaled := total.ScaledTo(1)
	got := scaled.Requests.ResourceValue("example.com/gpu")
	t.Logf("ScaledTo(1) returns      %d", got)
	t.Logf("undercharge              %d", int64(math.MaxInt64/2)-got)

	if got != math.MaxInt64/2 {
		t.Errorf("ScaledTo(1) = %d, want %d", got, math.MaxInt64/2)
	}
}
```

Three Pods asking `MaxInt64/2` each saturate to the sentinel, and scaling back to one Pod returns a third of MaxInt64 instead of the `MaxInt64/2` that one Pod actually asks for.

The same thing at the `PodSetResources` level, without going through `NewInfo`:

```
before ScaledTo: count=3 value=9223372036854775807 (MaxInt64)
after  ScaledTo(1): value=3074457345618258602  unlimited=false
```

**Anything else we need to know?**:

Reaching the sentinel takes a request in the 10^18 region, so this is not something an ordinary cluster runs into. I am filing it because the repository already decided to defend against exactly this: #14045 made `Add` and `Sub` saturate across both `Requests` backends, `Amount` carries the sentinel through comparison, and #14130 refuses a DRA charge that reaches `Unlimited` rather than clamping it, on the grounds that clamping there reports no limit rather than a conservative one. `Divide` is the remaining operation that silently undoes that, and it does so on the path that writes ClusterQueue usage.

Two things worth deciding rather than assuming:

- whether `Divide` should propagate the sentinel, or whether the callers should refuse to scale a saturated request at all. Propagating keeps the arithmetic uniform; refusing gives a clearer signal, since a workload whose total cannot be represented is not one whose per-Pod share is meaningful either.
- if it propagates, what `SinglePodRequests` should then hand to TAS, since `Unlimited` per Pod is not a topology-domain request anyone can satisfy.

Happy to send the fix either way once the shape is settled.

### Comment by [@thc1006](https://github.com/thc1006) — 2026-10-06T15:32:48Z

#14520 and #16479 fixed part of this. A pending PodSet is now scaled from its per-Pod request, and `Requests` no longer saturates, so `ScaledTo(1)` in the reproducer above returns MaxInt64/2 on main.

The admitted case is still wrong, and it's the capped `resourceUsage` from #16486. Kueue writes each admitted PodSet's total into `status.admission` as a Quantity, capped at MaxInt64, and the cache reads that cap back as the usage. For example, 7 Pods of 2e18 `example.com/gpu` can be admitted by borrowing from a second ClusterQueue in the cohort, each with a nominal quota of MaxInt64. The ClusterQueue is then charged 9.2e18 instead of 1.4e19, and after four Pods are reclaimed the three left are charged about 3.95e18 where they need 6e18. Seven works because it divides MaxInt64. With a count that doesn't, the webhook refuses the capped value and the admission never lands. CPU only hits this past MaxInt64 cores.

#16486 asks for a total that can't be stored to fail admission with a condition. Once it does, new admissions only store exact totals and the reclaim path divides those exactly, so I'll keep this open until then.
