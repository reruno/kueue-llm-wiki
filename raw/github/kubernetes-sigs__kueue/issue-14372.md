## Description

**What happened**:

Kueue compiles DRA device selectors with an empty feature set, in both places it builds a compiler:

```go
// pkg/dra/claims.go:43
var celCache = dracel.NewCache(256, dracel.Features{})

// pkg/config/validation.go:570
celCache := dracel.NewCache(len(mapping.Sources), dracel.Features{})
```

The vendored compiler at `k8s.io/dynamic-resource-allocation v0.36.3` uses that struct to decide what the CEL environment contains:

```go
type Features struct {
	EnableConsumableCapacity bool
	EnableListTypeAttributes bool
}
```

`EnableConsumableCapacity` picks which type the `device` variable gets, `deviceTypeV134ConsumableCapacity` or `deviceTypeV131`. `EnableListTypeAttributes` adds the 1.36 `includes` declaration and stops list-valued attributes from being typed as `any`.

Passing the zero value hardcodes both to off, whatever the cluster's apiserver has enabled. Where the apiserver's environment is wider, a selector it accepted on write is refused by Kueue on read, and the Workload is inadmissible for a reason the user cannot see in their own object.

**What you expected to happen**:

Kueue's selector compiler matches the environment the apiserver validated the selector against, or is deliberately a superset of it, so a stored `DeviceSelector` cannot become uncompilable by being read here.

**How to reproduce it (as minimally and precisely as possible)**:

In `pkg/dra`:

```go
func TestCELCacheFeatureEnvironment(t *testing.T) {
	sets := []struct {
		name string
		f    dracel.Features
	}{
		{"Features{} (what Kueue uses)", dracel.Features{}},
		{"EnableConsumableCapacity", dracel.Features{EnableConsumableCapacity: true}},
		{"EnableListTypeAttributes", dracel.Features{EnableListTypeAttributes: true}},
	}
	exprs := []string{
		`device.allowMultipleAllocations == true`,
		`device.attributes["x.com"].list.includes("a")`,
		`device.attributes["x.com"].list.exists(v, v == "a")`,
	}
	for _, e := range exprs {
		for _, s := range sets {
			r := dracel.NewCache(8, s.f).GetOrCompile(e)
			verdict := "compiles"
			if r.Error != nil {
				verdict = "REFUSED"
			}
			t.Logf("%-46s | %-30s | %s", e, s.name, verdict)
		}
	}
}
```

**Anything else we need to know?**:

I want to be precise about how far the evidence goes, because it is narrower than it first looks.

The proven divergence is list-type attributes. A comprehension over a list attribute compiles only with `EnableListTypeAttributes`, and `DRAListTypeAttributes` is alpha and off by default in 1.36, so a default cluster's apiserver refuses it too. The gap opens when an operator enables that alpha gate: the apiserver then accepts the selector and Kueue still refuses it.

`DRAConsumableCapacity` is different. It is beta and on by default in 1.36, so on a stock cluster the apiserver already compiles `device` as `deviceTypeV134ConsumableCapacity` while Kueue compiles it as `deviceTypeV131`. That difference is real today, but I could not find an expression where it changes accept or reject: `device.allowMultipleAllocations == true` compiles under the empty feature set as well. So I am reporting a type mismatch that is live by default and a compile mismatch that needs an alpha gate, not one thing that is both.

On the fix, reading the runtime feature gates from a package-level initializer would be wrong here, since `pkg/dra`'s `celCache` is initialized before the CLI and Configuration gates are applied. Injecting the environment after feature initialization, or compiling against a superset of what the supported API allows, both avoid that ordering problem. Which one is the right shape is a question for whoever owns the DRA integration; I am happy to send it once that is decided.

## Discussion

### Comment by [@thc1006](https://github.com/thc1006) — 2026-10-15T07:52:49Z

Fixed since v0.20.0 by the Kubernetes 1.37 bump in #15448. From `k8s.io/dynamic-resource-allocation` v0.37 on, the `device` type for each feature combination is a versioned option, and the stored-expressions environment that `GetOrCompile` uses takes the newest one whatever `Features` says. With v0.37.0 (in v0.20.0) and v0.37.1 (on main), the three expressions above compile under `Features{}`, and they evaluate on a device that has a list attribute. Kueue 0.19 still uses v0.36.2. That version refuses `exists()` over a list attribute and fails to evaluate any selector on a device that has one. But ResourceSlices only get list attributes while the apiserver has the alpha `DRAListTypeAttributes` gate on, so I am not proposing a backport.
