## Description

**What happened**:

`WorkloadValidateResourcesAreNonNegative` has been Beta and on by default since v0.18.5 and v0.19.1. The webhook it runs in is registered for `workloads/status` as well as `workloads`, and the update path revalidates the whole object rather than what changed:

- [registration](https://github.com/kubernetes-sigs/kueue/blob/6368db3b02b8541b37048ffcf650ef998b5ec684/pkg/webhooks/workload_webhook.go#L79) covers `workloads;workloads/status`, `verbs=create;update`, `failurePolicy=fail`
- [`ValidateUpdate`](https://github.com/kubernetes-sigs/kueue/blob/6368db3b02b8541b37048ffcf650ef998b5ec684/pkg/webhooks/workload_webhook.go#L91-L100) calls `ValidateWorkloadUpdate`, which walks every PodSet again
- [`validateResourceList`](https://github.com/kubernetes-sigs/kueue/blob/6368db3b02b8541b37048ffcf650ef998b5ec684/pkg/webhooks/workload_webhook.go#L199-L211) has no old-vs-new comparison

So a quantity that was already there when the check arrived is refused again on every update, including the ones Kueue makes itself. Running the validation against a Workload whose container asks for `example.com/gpu: -3`:

```
write an Evicted condition   spec.podSets[0].template.spec.containers[0].resources.requests[example.com/gpu]: Invalid value: "-3": must be greater than or equal to 0
deactivate                   spec.podSets[0].template.spec.containers[0].resources.requests[example.com/gpu]: Invalid value: "-3": must be greater than or equal to 0
remove the finalizer         spec.podSets[0].template.spec.containers[0].resources.requests[example.com/gpu]: Invalid value: "-3": must be greater than or equal to 0
```

The last row is the one that lasts. [`RemoveFinalizer`](https://github.com/kubernetes-sigs/kueue/blob/6368db3b02b8541b37048ffcf650ef998b5ec684/pkg/workload/workload.go#L1481-L1486) takes `kueue.x-k8s.io/resource-in-use` off with `client.Update`, the webhook has no `deletionTimestamp` exemption, and the [deletion branch](https://github.com/kubernetes-sigs/kueue/blob/6368db3b02b8541b37048ffcf650ef998b5ec684/pkg/controller/jobframework/reconciler.go#L465-L474) has nothing else to try, so the Workload stays in Terminating.

**What you expected to happen**:

An update that does not touch the invalid value goes through, so a Workload written before the check existed can still reserve quota, be deactivated, and be deleted. A new or changed invalid value is still refused.

#13995 proposes that shape for `spec.overhead`. The container, init-container and pod-level request and limit lists do not have it yet.

**How to reproduce it (as minimally and precisely as possible)**:

In a cluster: run with `WorkloadValidateResourcesAreNonNegative=false`, or on v0.19.0, where the gate did not exist yet. Create a Workload whose container requests a negative quantity. Turn the gate on, or upgrade. Then `kubectl delete workload/<name>`: it stays in Terminating.

The three rows above came from calling the validation directly, which needs no cluster. In `pkg/webhooks`:

```go
func TestLegacyNegativeCannotBeDeleted(t *testing.T) {
	features.SetFeatureGateDuringTest(t, features.WorkloadValidateResourcesAreNonNegative, true)

	legacy := utiltestingapi.MakeWorkload("legacy", "ns").
		PodSets(*utiltestingapi.MakePodSet("a", 1).
			Request(corev1.ResourceCPU, "8").
			Request("example.com/gpu", "-3").Obj()).
		Obj()

	finalizerless := legacy.DeepCopy()
	finalizerless.Finalizers = nil

	t.Log(ValidateWorkloadUpdate(finalizerless, legacy).ToAggregate())
}
```

**Anything else we need to know?**:

I came at this from the accounting side, in #14015 and #13991, which are about what such a Workload is charged. This is the lifecycle side and is separate from both: those assume the Workload can still be written to at all.

I have not checked what MultiKueue does when it copies such a Workload to a worker where the gate is on, since that is a create with no old object to compare against. That may want a look of its own.

**Environment**:
- Kueue version: `main` at `6368db3b02b8541b37048ffcf650ef998b5ec684`
- Kubernetes version, provider, OS: not relevant here. The three results above come from the validation functions, with no apiserver involved.

### Comment by [@thc1006](https://github.com/thc1006) — 2026-08-16T01:04:02Z

Linking #14367, which closes the resolver half of the accounting side: a negative extended-resource request is dropped per container before the aggregation, so it can no longer offset a positive charge under the same quota key.

It does not help here, and I want to be explicit about why rather than leave the two looking like the same fix. #14367 changes what a Workload is charged the next time its requests are computed. This issue is about the object no longer being writable at all, so the controller cannot record an eviction, deactivate it, or drop the finalizer regardless of what the charge would have been.

One thing I noticed while reading that path, which makes the lifecycle side a little worse than the description above: `rebuildTotalRequests` takes the requests from `status.admission` once `Status.Admission` is set, rather than recomputing them from the PodSets. So for a Workload that already holds a reservation, the recorded usage stays as it was admitted, and the ordinary way to get it recomputed is to release and rebuild that reservation, which is one of the writes the webhook refuses.
