## Description

Update 2026-10-15: for Pod groups, #13382 now keeps a Pod gated when it requests more than its PodSet reserves, behind `PodIntegrationVerifyRoleRequests` (Beta and on by default on main). The adoption check itself still compares only names and counts, and HARSHRAJ2789's #15239 proposes comparing per-Pod requests there. The two workload-slice paths still skip the template.

/kind bug

**What happened**:

Three paths that bind a Job or a Pod group to an existing Workload accept it without reading the PodSet template. A prebuilt Workload can therefore state resources its Pods will not request, and quota is charged from the Workload.

The generic path reads part of it. `equality.comparePodTemplate` (now `ComparePodTemplate`) compares `InitContainers` and `Containers`, and `Tolerations` unless the Workload is already admitted, so a prebuilt Workload for an ordinary Job cannot understate its containers. It does not compare `RuntimeClassName`, which I had wrong when filing, as HARSHRAJ2789 pointed out below. Pod-level `spec.resources` and `spec.resourceClaims` were not compared when this was filed; #14436 added both. The three paths below read none of it. `ensurePrebuiltWorkloadInSync` (`pkg/controller/jobframework/reconciler.go:1358`) reaches it through `EquivalentToWorkload`, which ends in `equality.ComparePodSetSlices`. The three paths below never arrive there.

## Pod groups compare names and counts

`(*Pod).EquivalentToWorkload` splits on group membership (`pkg/controller/jobs/pod/pod_controller.go:1484`):

```go
// For single job using base EquivalentToWorkload method.
if !p.isGroup {
	return jobframework.EquivalentToWorkload(ctx, c, p, wl)
}

podSets, err := p.constructGroupPodSets()
if err != nil {
	return false, err
}

return p.equivalentToWorkload(wl, podSets), nil
```

`(*Pod).equivalentToWorkload` (`:1339`) compares the Workload name, the PodSet names, and the counts. It reads no field of the template.

## The workload-slice path promises more than it checks

`ensureOneWorkload` says what the rule is meant to be (`pkg/controller/jobframework/reconciler.go:1046`):

> ```go
> // Workload slices allow modifications only to PodSet.Count.
> // Any other changes will result in the slice being marked as incompatible,
> ```

`EnsureWorkloadSlices` (`pkg/workloadslicing/workloadslicing.go:172`) decides compatibility from `HasSamePodSetKeys` and the counts, so the second sentence is not implemented. The template stays reachable while it matters: the webhook only freezes PodSets once the *old* Workload holds a quota reservation (`pkg/webhooks/workload_webhook.go:366`), so a pending Workload's template can still be updated after its slice was accepted.

## Scaled-up prebuilt Workloads skip the check entirely

`ensurePrebuiltWorkload` returns before the in-sync comparison (`pkg/controller/jobframework/reconciler.go:1013`):

```go
if workloadslicing.Enabled(object) && workloadslicing.ScaledUp(wl) {
	log.V(3).Info("WorkloadSlice: skip in-sync check in ensurePrebuiltWorkload")
	return wl, nil
}
```

`ScaledUp` is `ReplacementForKey(workload) != nil` (`pkg/workloadslicing/workloadslicing.go:162`), which reads the `workload-slice-replacement-for` annotation and nothing else.

**What you expected to happen**:

A Workload accepted for a Job or a Pod group states what those Pods will request, at least as far as the generic comparison already requires.

**How to reproduce it (as minimally and precisely as possible)**:

In `pkg/controller/jobs/pod`:

## Why this is not a patch on #14289

#14289 would have added `RuntimeClassName` to the template comparison so that a prebuilt Workload could not name a cheaper RuntimeClass than its Job. I closed it without merging on 2026-10-11. Adding that one field to these three paths would read as a guarantee they cannot give: the reproducer above understates the CPU request by a factor of a hundred through the same hole, and a check on one field suggests the rest are covered. The scope of the comparison is the question, so it belongs here rather than in a change about overhead.

## Two things worth deciding rather than assuming

Whether a Pod group should compare per Pod or per aggregated PodSet. `getRoleHash` (`:670`) returns the existing `kueue.x-k8s.io/role-hash` annotation when there is one rather than recomputing it, and `constructGroupPodSets` (`:792`) builds a PodSet from the first Pod of a role while later Pods of the same role only raise its count. Two Pods with different templates can therefore share a role, and a comparison against the aggregate would not see the second one.

Whether the two slice paths should share the generic comparison or a narrower one. Scale-up wants the counts to differ for a while, so `ComparePodSetSlices` wholesale is not right; the caller comment above already describes the intended rule.

## Discussion

### Comment by [@HARSHRAJ2789](https://github.com/HARSHRAJ2789) — 2026-09-05T14:18:59Z

I traced the three paths on current `main` and prototyped the group-path fix to see what the comparison scope has to be. The core holds: the pod-group and slice paths accept a Workload from its names and counts alone, while the generic path reads the template. One premise has shifted since filing, and the prototype turned up a concrete constraint on the fix.

**The generic comparator now reads more than the report describes.** `comparePodTemplate` compares pod-level resources and resource claims, not only the containers: `pkg/util/equality/podset.go:60-63` runs `DeepEqual` on `PodSpec.Resources` and hands `PodSpec.ResourceClaims` to `compareResourceClaims`. So on the generic path a prebuilt Workload can no longer understate the container or the pod-level requests for an ordinary Job. `RuntimeClassName` is compared nowhere in that file, so the RuntimeClass half of the reproducer passes even on the generic path today; the container-request half (cpu 1 against cpu 100) is what the group path lets through, because it never reaches `comparePodTemplate`.

**What each path reads:**

- Group: `(*Pod).equivalentToWorkload` (`pkg/controller/jobs/pod/pod_controller.go:1402`) checks the Workload name, the PodSet names, and `wl.Spec.PodSets[j].Count < jobPodSets[i].Count`. No template field.
- Slice: `EnsureWorkloadSlices` (`pkg/workloadslicing/workloadslicing.go:225-227`) gates on `HasSamePodSetKeys` and then the counts. No template field.
- Generic: `EquivalentToWorkload` ends in `ComparePodSets` to `comparePodTemplate`, reading tolerations, init containers, containers, pod resources, and resource claims.

**A full-template compare on the group path is not a drop-in, and a prototype showed why.** I added an ignore-counts option to `ComparePodSets` (the group count must stay free to grow past the seed Pod) and had `equivalentToWorkload` compare the constructed PodSet template against the Workload's, mirroring the admitted-tolerations and topology handling of the generic path. A focused unit test for the understated-cpu case passed, but two existing pod-group integration specs then failed: "Should ungate pods with prebuilt workload" and "Should finish the group ... retriable-in-group: false". I dumped the diff the comparison tripped on, and it is API defaulting: the group builds its PodSets from the live Pods through `constructGroupPodSets`, and the live Pod is defaulted, so its template carries `TerminationMessagePath: /dev/termination-log`, `TerminationMessagePolicy: File`, `ImagePullPolicy: IfNotPresent`, `TerminationGracePeriodSeconds: 30`, and a `DNSPolicy`, while the stored Workload template has those empty. A whole-template `DeepEqual` rejects the controller's own group over defaults and stalls unsuspension. The generic path sidesteps this by comparing against `expectedRunningPodSets` with a suspended-spec fallback, machinery the group path does not have.

**So the scope question is really which fields, and the diff answers it.** The resource requests were in the identical part of that diff; only the defaulted scalar fields diverged. So the resource shape the charge is taken from, the container and pod-level requests and the resource claims, is stable across defaulting, while the rest of the template is not. Comparing that subset closes the understatement the report is about without rejecting a Workload over `imagePullPolicy`, and it is what `PodRequests` actually sums into the quota charge. A whole-template comparison on these paths would need the running-vs-suspended normalization the generic path carries, which is a larger change than the report needs.

**On per-Pod versus per-aggregated-PodSet.** The aggregate cannot see two Pods of one role with different templates: `constructGroupPodSets` builds the PodSet from the first Pod of a role and only raises the count for the rest, and `getRoleHash` returns the stored `role-hash` annotation and does not recompute it per Pod. That is the representation limit described in #14317 and is orthogonal to this hole; comparing the aggregate closes the reported case, where every Pod of a role shares one template, and the mixed-template case is better tracked with #14317 than folded in, since closing it means changing how roles are keyed.

I have the prototype and the two failing specs locally if that is useful. Happy to open a PR once the field scope is settled, on the resource subset unless you would rather thread the running-vs-suspended comparison through these paths.
