## Description

/kind cleanup

**What happened**:

Every controller in `pkg/controller/core` opts out of leader election and is wrapped so that non-leaders discard what they are given:

```go
WithOptions(controller.Options{
	NeedLeaderElection: new(false),
	...
}).
Complete(WithLeadingManager(mgr, r, &kueue.Workload{}, cfg))
```

`admissioncheck`, `clusterqueue`, `cohort`, `localqueue`, `resourceflavor`, `resourceslice`, `workload` and `workloadpriorityclass` all do this. On a non-leading replica the wrapper does a cached `Get` and returns `RequeueAfter: leaseDuration`, so each key it has ever seen keeps cycling.

With the default 15s lease that is one cached read per eligible object per 15s per follower, indefinitely, and for the Workload-keyed controllers the object count is the cluster's Workload count.

Two further effects follow from where the delay is applied rather than from the loop itself:

- A key keeps cycling after it stops matching the controller's predicate. `RequeueAfter` goes through the workqueue's delaying queue, not back through the source, so the predicate never sees it again. A Workload that gains the MultiKueue origin label, or moves to a Pod `PriorityClass`, keeps its slot until it is deleted or the replica wins the lease.
- A replica that requeued a batch just before winning the lease still waits out the delay. Closing `mgr.Elected()` does not wake items already scheduled with `AddAfter`, so work the new leader could do immediately can sit for up to a lease duration.

**What you expected to happen**:

Followers hold whatever a fast failover needs, and no more.

**Anything else we need to know?**:

## What the wrapper says it is for

```go
// Starting controllers in non-leading replicas is needed for these that update the data
// served by the visibility extension API server.
//
// This enables to:
//   - Keep the scheduling decisions under the responsibility of the leading replica alone,
//     to prevent any concurrency issues.
//   - Consume requests from the watch event queues, to prevent them from growing indefinitely
//     in the non-leading replicas.
//   - Transition to actually reconciling requests in the replica that may acquire
//     the leader election lease, in case the previously leading replica failed to renew it.
```

The first reason is specific: visibility-extension data. The second is self-referential, since a leader-only controller has no queue on a follower to drain. The third, being ready to take over, is the one that applies to all eight.

## controller-runtime has an option for exactly the third reason

`controller.Options` in the vendored v0.24.1 carries:

```go
// EnableWarmup specifies whether the controller should start its sources when the manager is not
// the leader. This is useful for cases where sources take a long time to start, as it allows
// for the controller to warm up its caches even before it is elected as the leader. This
// improves leadership failover time, as the caches will be prepopulated before the controller
// transitions to be leader.
//
// Setting EnableWarmup to true and NeedLeaderElection to true means the controller will start its
// sources without waiting to become leader.
```

Sources run and the queue fills on followers; workers start at election. That is the failover readiness the third bullet asks for, without a reconcile per object per lease period, without keys that outlive their predicate, and without a batch that has to wait out a delay the new leader did not choose.

Nothing in the repository uses it today, and it is marked beta upstream, which is why this is an issue rather than a patch: it is a choice about the package, and about taking a beta option, rather than something to change under one controller.

## What would need answering first

- whether any of the eight genuinely needs follower-side reconciliation, rather than a warm queue. The visibility path is the one the comment names, so that is where to look.
- whether beta is acceptable here, given the option changes when work starts rather than what it does.
- what to keep `WithLeadingManager` for afterwards, if the answer is that none of them need it.

I came to this from #13920, which adds another Workload-keyed controller in this package and therefore a second such loop on every follower. That PR follows the existing shape rather than departing from it, and states the cost in its description; this is the part that is not one PR's to decide.
