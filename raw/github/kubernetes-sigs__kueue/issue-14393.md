## Description

/kind bug
/area dra

**What happened**:

`NeedsDRAReconcile` decides whether a Workload needs DRA preprocessing by reading each container's `Resources.Requests` (`pkg/dra/extended_resources.go:60`). Every caller asks it about a Workload that has not been through `AdjustResources`, and `AdjustResources` is where a request can first appear.

`handlePodLimitRange` applies a LimitRange's `defaultRequest`, and `handleLimitsToRequests` copies a limit onto a request that was not set (`pkg/workload/resources.go:149-152`). A Workload whose only mention of a DRA-backed extended resource is a limit therefore answers no to a question asked before either of those runs.

Measured on current main, with `example.com/gpu` in the extended-resource cache and one container carrying only `limits`:

```
as it arrives, limits only:              NeedsDRAReconcile=false
requests after AdjustResources:          map[example.com/gpu:1]
the copy the controller actually queues: NeedsDRAReconcile=true
```

Three call sites read it that way:

- `workload_controller.go:1244` deep-copies, adjusts the copy, then asks about `e.Object` and queues the copy;
- `:1359` does the same with `e.ObjectNew`;
- `Reconcile` at `:523` asks about the Workload it read, and that answer is what gates the call to `handleDRA`, which is where `AdjustResources` runs at `:133`.

So the resource reaches quota under its raw name as an ordinary extended resource, with no DeviceClass resolution and no logical charge behind it.

**What you expected to happen**:

Whether a Workload needs DRA preprocessing is decided from the same requests its accounting will be built from.

**How to reproduce it (as minimally and precisely as possible)**:

```go
cache := dra.NewExtendedResourceCache()
cache.Add("example.com/gpu", "gpu.example.com")

wl := utiltestingapi.MakeWorkload("limits-only", "ns").
    PodSets(*utiltestingapi.MakePodSet("a", 1).Obj()).Obj()
wl.Spec.PodSets[0].Template.Spec.Containers[0].Resources = corev1.ResourceRequirements{
    Limits: corev1.ResourceList{"example.com/gpu": resource.MustParse("1")},
}

dra.NeedsDRAReconcile(wl, cache)        // false

adjusted := wl.DeepCopy()
workload.AdjustResources(ctx, cl, adjusted)
dra.NeedsDRAReconcile(adjusted, cache)  // true
```

With `KueueDRAIntegration` and `KueueDRAIntegrationExtendedResource` enabled.

**Anything else we need to know?**:

Reading `Limits` as well as `Requests` would close only half of it: a LimitRange `defaultRequest` names neither field on the Workload. The decision has to be taken on a Workload that has already been through `AdjustResources`, which is the copy each of these call sites has to hand anyway.

**Environment**:
- Kueue version (use `git describe --tags --dirty --always`): `v0.20.0-devel` on current main
- Others: reproduced against `pkg/dra` and `pkg/workload` directly

## Discussion

### Comment by [@bolubo](https://github.com/bolubo) — 2026-09-23T23:58:55Z

I re-ran the reproducer from the report against current main (both DRA gates enabled), and it now behaves as expected.

A Workload whose only GPU entry is under `limits` — and one that gets its request from a LimitRange `defaultRequest` — both make `NeedsDRAReconcile` return true: the decision is now taken on the same effective view the accounting uses (`wi.PodSpec(i)` → `EffectivePodSpecs`, with defaults resolved in `NewInfoFromClient`). `TestDRADetectionAndQuotaUseEffectiveRequests` in `pkg/dra` pins exactly those two inputs — detection, charging under the mapped resource, and the `replaced` marker — and it is green on current main.

Looks like #15284 closed this gap as part of #14964. Unless there's a corner you wanted to keep this open for, it looks ready to close.
