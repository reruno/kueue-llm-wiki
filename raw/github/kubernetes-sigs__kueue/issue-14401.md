## Description

**What would you like to be added**:

A decision, and then the accounting to match it, for what Kueue charges when a DRA device supplies a resource that is normally part of a node's allocatable.

KEP-5517 (`keps/sig-scheduling/5517-dra-node-allocatable-resources`) adds that path, and the API is already in the `k8s.io/api` this repo builds against, `v0.36.3`. A ResourceSlice device declares the translation:

```go
// NodeAllocatableResourceMappings defines the mapping of node resources
// +featureGate=DRANodeAllocatableResources
NodeAllocatableResourceMappings map[v1.ResourceName]NodeAllocatableResourceMapping
```

and what a Pod ends up holding lands in its status:

```go
// NodeAllocatableResourceClaimStatuses contains the status of node-allocatable resources
// that were allocated for this pod through DRA claims. This includes resources currently
// reported in v1.Node `status.allocatable` that are not extended resources.
// Examples include "cpu", "memory", "ephemeral-storage", and hugepages.
// +featureGate=DRANodeAllocatableResources
NodeAllocatableResourceClaimStatuses []NodeAllocatableResourceClaimStatus
```

So `cpu` and `memory` can reach a Pod through a claim rather than through a container's `requests`, and the figure is only known once the claim is allocated.

Kueue computes what a Workload costs from the PodSet templates alone. `totalRequestsFromPodSets` (`pkg/workload/workload.go:684`) walks `wl.Spec.PodSets` and nothing else, and the tree has no reference to `NodeAllocatableResourceClaimStatuses` outside `vendor/`. A Workload whose Pods draw cpu or memory from a device is therefore charged for what its containers declare, not for what its Pods will hold.

**Why is this needed**:

Because there are at least three defensible answers and they are not equivalent, so whichever one Kueue ends up with should be chosen rather than inherited:

1. Charge it. Cpu a device supplies is cpu the node cannot give to anything else, so a ClusterQueue that ignores it admits more than its nominal quota describes. The difficulty is that admission happens before the claim is allocated, so the figure is not available when it is needed.
2. Do not charge it, and document that. Treat device-supplied cpu the way a node's system reserve is treated: real, but outside the quota model. The cost is that the same `cpu` string then means two things depending on where it came from.
3. Charge the device rather than the resource it supplies. Kueue already counts DRA devices through `deviceClassMappings`, so a device supplying 4 cpu charged as one device keeps the accounting internally consistent and leaves the sizing to whoever writes the mapping.

On timing: the gate is alpha and off by default, so nothing is broken for anyone today. `kep.yaml` targets beta at v1.38, which is when it would be on unless an operator turns it off. Milestones in `kep.yaml` are plans and do slip, so that is what the file says rather than a prediction. Choosing the answer before the flag flips seems easier than after.
