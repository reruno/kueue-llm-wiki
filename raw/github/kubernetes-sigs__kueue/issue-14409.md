## Description

/kind bug

**What happened**:

When a PodSet is admitted, `FromAssignment` builds the Pod's `nodeSelector` by walking every flavor the assignment picked and copying that flavor's `spec.nodeLabels` in (`pkg/podset/podset.go:78-90`):

```go
for _, flvRef := range assignment.Flavors {
    if processedFlvs.Has(flvRef) {
        continue
    }
    ...
    utilmaps.Copy(&info.NodeSelector, flv.Spec.NodeLabels)
    ...
    processedFlvs.Insert(flvRef)
}
```

`assignment.Flavors` is a `map[corev1.ResourceName]ResourceFlavorReference` (`apis/kueue/v1beta2/workload_types.go:299`), the dedup set is keyed by the flavor reference rather than by label key, and `utilmaps.Copy` is last-writer-wins with no conflict check (`pkg/util/maps/maps.go`). So if one PodSet has resources that resolve to two different flavors, and those flavors set the same node-label key to different values, the value that ends up on the Pod is whichever flavor the map happened to visit last.

The same package already treats this kind of collision as an error on the admission-check side: `PodSetInfo.Merge` runs `utilmaps.HaveConflict` on `NodeSelector` before copying (`pkg/podset/podset.go:126`) and returns `BadPodSetsUpdateError`. The flavor merge doesn't, so the conflict passes silently and resolves by iteration order.

Measured on current main, driving the real `FromAssignment` with one PodSet whose two resources resolve to `flavor-a` (`topology.kubernetes.io/zone=zone-a`) and `flavor-b` (`...=zone-b`), 3000 times:

```
distinct nodeSelector["topology.kubernetes.io/zone"] values over 3000 runs: map[zone-a:361 zone-b:2639]
```

Both values occur, so the selector that reaches the job's Pods is not reproducible across reconciles.

**What you expected to happen**:

Either a deterministic result, or an explicit refusal, the way `Merge` already rejects a conflicting `nodeSelector`. Two flavors disagreeing on the same node-label key is a real contradiction (a Pod cannot be pinned to two zones at once), so silently keeping one of them by map order can place the Pod somewhere neither the operator nor the assignment intended, or leave it unschedulable, and the outcome can differ the next time the same Workload is reconciled.

**How to reproduce it (as minimally and precisely as possible)**:

Two ResourceFlavors in different resource groups that reuse one node-label key with different values, and a single PodSet whose requests span both groups so both flavors are assigned to it. The following unit test against `pkg/podset` fails intermittently today (it counts how often each value wins over many runs):

```go
func TestFlavorNodeLabelConflictIsNondeterministic(t *testing.T) {
    const key = "topology.kubernetes.io/zone"
    scheme := runtime.NewScheme()
    _ = kueue.AddToScheme(scheme)
    flv := func(name, val string) *kueue.ResourceFlavor {
        return &kueue.ResourceFlavor{
            ObjectMeta: metav1.ObjectMeta{Name: name},
            Spec:       kueue.ResourceFlavorSpec{NodeLabels: map[string]string{key: val}},
        }
    }
    cl := fake.NewClientBuilder().WithScheme(scheme).
        WithObjects(flv("flavor-a", "zone-a"), flv("flavor-b", "zone-b")).Build()
    assignment := &kueue.PodSetAssignment{
        Name: "main",
        Flavors: map[corev1.ResourceName]kueue.ResourceFlavorReference{
            corev1.ResourceCPU:            "flavor-a",
            corev1.ResourceName("gpu.io"): "flavor-b",
        },
    }
    podSet := &kueue.PodSet{Name: "main", Count: 1}
    seen := map[string]int{}
    for i := 0; i < 3000; i++ {
        info, _ := FromAssignment(context.Background(), cl, assignment, podSet)
        seen[info.NodeSelector[key]]++
    }
    t.Logf("%v", seen) // both zone-a and zone-b appear
}
```

**Anything else we need to know?**:

The flavor assigner validates each flavor's labels against the PodSet's own affinity (`pkg/scheduler/flavorassigner/flavorassigner.go`), but nothing compares two assigned flavors against each other, so this isn't caught earlier. The trigger is narrow, it needs a single PodSet assigned across two flavors that reuse a key, which is an unusual and arguably mis-configured layout, so I'd treat it as low priority rather than urgent. Reusing `Merge`'s `HaveConflict` check on the flavor-label copy, so a real conflict surfaces as an admission error instead of a coin flip, looks like the smallest fix.
