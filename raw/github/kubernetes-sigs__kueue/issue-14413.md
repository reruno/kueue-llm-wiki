## Description

**What would you like to be added**:

A design note (or KEP) settling how Kueue's `WorkloadPriorityClass` coexists with the priority and preemption semantics that upstream Workload-Aware Scheduling gives a `PodGroup` (KEP-5710), once Kueue starts expressing gang intent through the WAS APIs behind `GenericWorkload` (Beta in 1.37).

This is the row #13715's relationship table already calls out as a *"Separate follow-up KEP based on upstream KEP-5710"*, covering "`disruptionMode: all`, eviction and preemption semantics, and workload-priority mapping". It has no tracking issue yet. It is the counterpart to #13150: that one covers reading standard workload-level priority *into* Kueue's ordering, whereas this one is about the two priority/preemption models diverging, which #13150's scope does not cover.

Two things need a decision.

**1. Priority divergence between the Workload and its PodGroup.**
`WorkloadPriorityClass` sets a Kueue-only priority on the `Workload`, decoupled from any pod `PriorityClass`: the `kueue.x-k8s.io/priority-class` label (`pkg/controller/constants/constants.go:48`) is resolved by `GetPriorityFromWorkloadPriorityClass` (`pkg/util/priority/priority.go:108`) straight from `wpc.Value`. On a live cluster (v0.19.1), a Job labelled with a `WorkloadPriorityClass` of value `9000` produces a Workload with

```
spec.priority: 9000
spec.priorityClassRef.kind: WorkloadPriorityClass
```

while the pod template carries no `priorityClassName` at all (pod priority stays the default). KEP-5710 requires the opposite for a `PodGroup`:

> when scheduling or preempting a pod that is part of a Pod Group, the priority defined in the `PodGroup` object will be used (and priority defined in the `Pod` itself will be ignored…)

and for Beta/GA it is stricter:

> For Beta and GA, we will disallow the divergence between the priority of the `Pod` and the `PodGroup`. This will be done by the scheduler, which will fail scheduling of the `PodGroup`, once it observes such divergence.

So the moment Kueue emits a PodGroup for a Workload that carries a `WorkloadPriorityClass`, we have to decide what priority the PodGroup gets and whether the WorkloadPriorityClass value is projected onto the pods, or the scheduler rejects the group outright.

**2. Scheduler-owned preemption of an already-admitted Workload.**
KEP-5710 lets the scheduler pick victims across groups:

> all running pod groups with (preemption) priority lower than preemptor priority

so kube-scheduler can evict the pods of a Workload that Kueue has already admitted and reserved quota for. Kueue did not make that decision and gets no signal to release the reservation, and the scheduler's PodGroup-priority ordering need not match Kueue's `WorkloadPriorityClass` ordering. We should define who owns the preemption decision at the seam, and how a Kueue reservation is reconciled when the scheduler removes the pods underneath it.

**Why is this needed**:

`GenericWorkload` is Beta in 1.37 but still off by default, and #13715 proposes defaulting Kueue-managed Jobs to gang scheduling on top of it. Once that lands and a cluster turns on `GenericWorkload` and serves `scheduling.k8s.io/v1beta1`, both cases above become reachable: a `WorkloadPriorityClass` whose value differs from the pods' priority trips the Beta divergence check, and a scheduler-driven cross-group preemption silently strands a Kueue quota reservation. Deciding this before the integration ships keeps `WorkloadPriorityClass` meaningful under WAS and stops the two systems from disagreeing about who preempts whom.

The KEP side is quoted above; the Kueue side is checked against the code and a live cluster. What I could not reproduce end to end is the cross-preemption itself. That needs the WAS integration (`GenericWorkload` plus Kueue-emitted PodGroups) that #13715 and #13150 are still building, so this is a design question rather than a bug.

Happy to fold it into #13715 instead if you'd rather keep the follow-up inline; opening it separately only because #13715's own table points to a separate issue.
