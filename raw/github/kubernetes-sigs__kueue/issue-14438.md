## Description

**What happened**:

With `TASRespectNodeAffinityPreferred` on, a leaf's preferred affinity score comes out twice its real value the first time a PodSet is evaluated, and zero every time after that. Same snapshot, same PodSet, same terms.

The score lives in per-snapshot state, and the candidate handed to the simulator is a view onto it:

```go
func (c *leafCandidate) SetAffinityScore(score int64) {
	c.s.domainStates[c.leaf.idx].affinityScore = score
}

func (c *leafCandidate) GetAffinityScore() int64 {
	return c.s.domainStates[c.leaf.idx].affinityScore
}
```

The default checker writes the score there, and then `fillInCounts` adds it to the same field:

```go
matchingLeaves, stats, err := s.getMatchingLeaves(ctx, requirements)
...
for _, ml := range matchingLeaves {
	leaf := s.leaves[ml.GetID()]
	s.domainStateOf(&leaf.domain).affinityScore += ml.GetAffinityScore()
```

So a cold evaluation doubles it. A warm one loses it instead, because `fillInCounts` opens with `clear(s.domainStates)` and a cache hit returns the stored candidates without running the checker again, so `GetAffinityScore` reads the field it just cleared.

`matchingLeavesCacheEntry` holds `leaves` and `stats`, and neither carries the score.

**What you expected to happen**:

The same PodSet against the same snapshot ranks domains the same way whether or not something warmed the cache first, and a single term of weight 10 produces a score of 10.

**How to reproduce it (as minimally and precisely as possible)**:

In `pkg/cache/scheduler`, against `01c45cacf`. Two nodes in one rack, one of them matching a single preferred term of weight 10:

Cold, `n1` outranks `n2` on a score twice what the term asked for. Warm, the two tie and the preference is gone.

**Anything else we need to know?**:

`affinityScore` is the first thing `compareDomains` and `compareDomainsWithParents` look at, and `fillInCountsHelper` sums it up the tree, so this decides which domain a PodSet lands in whenever the tie is otherwise close. `TASCacheNodeMatchResults` is Beta and on since 0.19, which is what makes both the cold and warm paths reachable in one process: a PodSet evaluated during preemption and again during admission takes different branches.

`TASRespectNodeAffinityPreferred` is still Alpha and off by default, so this doesn't reach anyone who hasn't opted in. It does mean the feature does not do what it says for anyone who has.

The WAS checker reads the field before writing it back, so the same clearing affects it:

```go
newAffinityScore := leaf.GetAffinityScore() + requirements.PreferredSchedulingTerms.Score(leaf.GetNode())
leaf.SetAffinityScore(newAffinityScore)
```

I think the cache entry wants to hold the leaf IDs with their scores as plain values, and `fillInCounts` wants to assign rather than accumulate, so that neither path depends on scratch state that gets cleared between runs. Happy to send that if it sounds right.
