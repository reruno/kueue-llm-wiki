## Description

<!-- Please only use this template for submitting enhancement requests -->

**What would you like to be added**:
 An opt-in, per-(ClusterQueue, FlavorResource) reclaim backoff. After a ClusterQueue's borrowed resource is reclaimed by cohort preemption (InCohortReclamation / InCohortReclaimWhileBorrowing), the scheduler applies an exponentially growing cooldown during which it defers only the flavor assignments that would borrow that same resource again. Assignments within nominal quota and assignments of other resources are unaffected.

Proposed configuration (config.kueue.x-k8s.io/v1beta2, following the waitForPodsReady.requeuingStrategy precedent):
 ```
    reclaimBackoff:
        enable: true
        backoffBaseSeconds: 60    # cooldown for the n-th consecutive reclaim ≈ b*2^(n-1)+jitter
        backoffMaxSeconds: 3600
        backoffResetSeconds: 600  # quiet period after which the counter resets
```
**Why is this needed**:
 When several ClusterQueues in a cohort contend for shared capacity, a ClusterQueue whose borrowed quota is reclaimed by preemption can be re-admitted in the very next scheduling cycle by borrowing the same resource again — only to be reclaimed again shortly after. This admit → reclaim → re-admit spin loop causes repeated workload evictions, floods the API server with events, and degrades scheduling cycle latency for the whole cohort.
