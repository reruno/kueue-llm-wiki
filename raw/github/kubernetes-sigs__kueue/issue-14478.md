## Description

**Update 2026-10-19:** KEP-7066 says a custom label value change on a ClusterQueue, LocalQueue or Cohort deletes its counters and histograms. The Cohort path, which keeps its counter, is the one that differs from the KEP. #17413 proposes keeping them only when every custom label of that kind has `trackedValues`. I'll rewrite this issue once that settles.

**What happened**:

Changing a custom metric label value on a ClusterQueue deletes that ClusterQueue's counter and histogram series, not just its gauges. The accumulated history is gone; nothing re-records it, because counters and histograms cannot be resynced from cache state the way gauges can.

Doing the same thing on a Cohort keeps the counters. That contract is written down in the tree:

```go
// ClearCohortMetrics only clears gauges (CohortInfo), not counters (AdmittedWorkloadsTotal).
util.ExpectCohortSubtreeAdmittedWorkloadsTotalMetric(kueue.CohortReference(cohort.Name), "", 1, "data-eng")
```

`test/integration/singlecluster/controller/core/custom_labels_test.go:928`. The ClusterQueue side has no equivalent case, and does the opposite.

The path: `ClusterQueueReconciler.Update` calls `CQStore`, and when the extracted custom values changed it calls `resyncClusterQueueGaugeMetrics` (`pkg/controller/core/clusterqueue_controller.go:410`). That function opens with `ClearClusterQueueMetrics` (`:434`), which deletes every ClusterQueue-scoped series including the cumulative ones:

```go
QuotaReservedWorkloadsTotal.DeletePartialMatch(prometheus.Labels{"cluster_queue": cqName})
FinishedWorkloadsTotal.DeletePartialMatch(prometheus.Labels{"cluster_queue": cqName})
AdmittedWorkloadsTotal.DeletePartialMatch(prometheus.Labels{"cluster_queue": cqName})
EvictedWorkloadsTotal.DeletePartialMatch(prometheus.Labels{"cluster_queue": cqName})
// Histogram vec, not cleared by gauge cleanup above.
WorkloadEvictionLatencySeconds.DeletePartialMatch(prometheus.Labels{"cluster_queue": cqName})
PodSchedulingGateRemovalSeconds.DeletePartialMatch(prometheus.Labels{"cluster_queue": cqName})
```

`pkg/metrics/metrics.go:1217`.

`ClearClusterQueueMetrics` was written for ClusterQueue deletion, where deleting everything is right, and `pkg/cache/queue/metrics.go:147` still calls it for that. The second caller arrived with #10552, which was scoped to unifying gauge cleanup and resync; the function it added is called `resyncClusterQueueGaugeMetrics` and takes the counters and histograms with it.

**What you expected to happen**:

A label change re-labels the ClusterQueue's gauges and leaves its counters and histograms alone, as the Cohort path already does. The old series keeps the history it accumulated under the old label value, which is what actually happened, and new observations land under the new one.

**How to reproduce it (as minimally and precisely as possible)**:

With `CustomMetricLabels` enabled and a ClusterQueue-sourced label configured:

1. Create a ClusterQueue labelled `team: infra` and admit one Workload through it.
2. Read `kueue_admitted_workloads_total{cluster_queue="cq", custom_team="infra"}`. It is 1.
3. Patch the ClusterQueue's label to `team: platform`.
4. Wait for `kueue_cluster_queue_status` to appear under `custom_team="platform"`, which is how you know the resync ran.
5. Read `kueue_admitted_workloads_total{cluster_queue="cq", custom_team="infra"}` again.

It is 0. As an integration spec in `test/integration/singlecluster/controller/core/custom_labels_test.go`, mirroring the cohort case above:

```go
util.ExpectAdmittedWorkloadsTotalMetric(cq, "", 1, "infra")     // before the change

// ... patch the label to platform ...

util.ExpectClusterQueueStatusMetric(cq, metrics.CQStatusActive, "platform")  // resync landed
util.ExpectAdmittedWorkloadsTotalMetric(cq, "", 1, "infra")     // fails
```

```
[FAILED] Timed out after 10.000s.
The function passed to Eventually failed at test/util/metrics.go:286 with:
Expected
    <int>: 0
to equal
    <int>: 1
```

Step 4 matters. Without waiting for the gauge to move, the counter read races the clear and can pass, which is how I first talked myself out of this.

**Anything else we need to know?**:

Two things worth separating from the main report.

The counters at least reset to zero and start again. `PodSchedulingGateRemovalSeconds` and `WorkloadEvictionLatencySeconds` are histograms, so `_sum` and `_count` reset too; `rate()` handles that as a counter reset, but any recording rule or dashboard reading `_sum` directly sees it drop.

There is also a narrow window where the clear can be undone. A reporter resolves its label values with `CQGet` and then calls `WithLabelValues(...).Observe(...)` a moment later. If the update handler stores the new values and clears the old series in between, the reporter recreates a series under the old values, after the cleanup that was meant to remove it. The window is small and the result is one stale sample rather than anything broken, so it is not worth chasing on its own. It disappears if the cumulative metrics stop being cleared here, which is the fix this issue is asking for anyway.

I found this while working on #14419, which touches `PodSchedulingGateRemovalSeconds`. It is not caused by that PR and does not block it: this behavior predates it and applies to every cumulative ClusterQueue metric.

Hi @Andrushika, thanks for taking this one too! It's still there on main after #16653 and #17046. I reproduced it in the core integration suite: once a ClusterQueue's custom label changes and its status gauge moves to the new value, `kueue_admitted_workloads_total` under the old value reads 0 instead of 1.

#15010 tried to fix this in September, but it has stalled: the CLA isn't signed, and sohankunkerkar's question there on September 10 got no reply. It also conflicts with main now, because #16653 removed `ClearClusterQueueMetricsOnLabelChange`, which it edits, so starting from main will be simpler than reusing its commits. iacker left the fix to #15010 above and offered to pick it back up if it stalled. Since you've assigned yourself, I think it's fine for you to go ahead.

The cause is that `resyncClusterQueueGaugeMetrics` in `pkg/controller/core/clusterqueue_controller.go` starts with `metrics.ClearClusterQueueMetrics`, the same clear that runs when a ClusterQueue is deleted, so it drops the counters and histograms too. What worked for me was a `ClearClusterQueueGaugeMetrics` in `pkg/metrics/metrics.go` that only calls `clearScopedGaugeMetrics(gaugeCleanupScopeClusterQueue, ...)`, used in that resync instead.

For the test, `shouldn't clear cohort counter metrics on label changed` in `test/integration/singlecluster/controller/core/custom_labels_test.go` checks the same thing for a Cohort. A ClusterQueue version of it fails on main and passes with that change, and the rest of that file still passes. mimowo asked for an integration test on #15010, so it's worth including. The other question there, about `gaugeCleanupScopeClusterQueueLabelChange`, no longer applies: #16653 removed that scope and moved the weighted share gauge into the resource scope, which the resync already clears.

LocalQueue has the same problem, and a LocalQueue version of the spec fails on main too. It needs two changes, because `resyncLocalQueueGaugeMetrics` calls `clearLocalQueueMetrics` and so does the `else if oldMetricsExposed` branch in `LocalQueueReconciler.Update`. That branch also runs when the queue's labels stop matching `localQueueSelector`, and there the full clear should stay, so only the custom-label case should switch to a gauge-only clear. It can go in this PR, or in a follow-up if the first PR says `Part of: #14478` so this issue stays open. Please cc me on the PR and I'll review it.
