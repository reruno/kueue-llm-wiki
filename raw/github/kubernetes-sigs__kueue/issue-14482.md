## Description

**What happened**:

A Workload that has reserved quota cannot change its `priorityClassRef` in most of the ways the priority reconciliation wants to. The classifier that decides which Workloads to write skips one of those cases and walks into the rest, and because the unit tests use a fake client, which does not run CEL, none of them notice.

The Workload CRD carries four rules, all conditioned on `QuotaReserved` being true (`apis/kueue/v1beta2/workload_types.go:1193-1196`):

```
priorityClassRef is immutable while workload quota reserved
priorityClassRef.group is immutable while workload quota reserved
priorityClassRef.kind is immutable while workload quota reserved
priorityClassRef.name is immutable for scheduling.k8s.io/priorityclass while workload quota reserved
```

The first is about presence: a ref cannot be added and cannot be removed. `classifyWorkloadsForPriorityUpdate` (`pkg/controller/jobframework/reconciler.go:1355`) skips exactly the addition half:

```go
if workload.HasQuotaReservation(wl) && workload.HasNoPriority(wl) {
	continue
}
```

What is left reachable:

- A quota-reserved Workload referencing a WorkloadPriorityClass, whose owner drops the label and falls back to a Pod PriorityClass. `kueue.x-k8s.io/WorkloadPriorityClass` to `scheduling.k8s.io/PriorityClass` changes both group and kind, so rules 2 and 3 reject it.
- The same Workload where the fallback resolves to nothing at all. That is a removal, so rule 1 rejects it.
- A quota-reserved Workload already on a Pod PriorityClass whose name changes. Rule 4 rejects it.

Each is a write the reconciler will keep retrying and the API server will keep refusing, for as long as the reservation is held.

**What you expected to happen**:

Either the classifier skips a transition the API server cannot accept, the way it already skips the addition, or the reconciler records why the Workload cannot follow its owner instead of retrying a write that cannot land.

**How to reproduce it (as minimally and precisely as possible)**:

Against a real API server, since the fake client does not evaluate CEL:

1. Create a ClusterQueue and LocalQueue with quota.
2. Create a Job labelled `kueue.x-k8s.io/priority-class` naming a WorkloadPriorityClass, and let its Workload reserve quota.
3. Remove that label from the Job, leaving a Pod PriorityClass on the pod template.
4. Watch the Workload reconcile.

The update is rejected with `priorityClassRef.group is immutable while workload quota reserved`.

**Anything else we need to know?**:

The reason this is worth separating from the batching work is what it does to a set. #13904 hands the components of a LeaderWorkerSet to one write path, and a batch is not all-or-nothing: the components that have not reserved yet take the transition and the ones that have keep being refused. The set is then split across two classes with nothing to bring it back, and the split is invisible in unit tests for the reason above.

I have not tried to fix this in #13904. It predates that PR and applies equally to the ordinary Job path, so it wants its own change and an envtest that actually runs the CEL rules; every existing test in this area builds its client with `utiltesting.NewClientBuilder`.

### Comment by [@gangadhar-res](https://github.com/gangadhar-res) — 2026-08-16T06:45:06Z

I'd like to take this one if nobody else is on it.

One thing worth flagging first. I think the third case in the description is already covered. #13780 added the `!HasNoPriority(wl) && !IsWorkloadPriorityClass(wl)` skip to the classifier, so a workload already sitting on a Pod PriorityClass never reaches the write and rule 4 can't be hit through this path. The other two look reachable exactly as you describe: a workload holding a WorkloadPriorityClass ref passes both guards, and the resolved target can be either a Pod PriorityClass, which changes group and kind and trips rules 2 and 3, or nothing at all, which is a removal and trips rule 1.

On the fix, I don't think the classifier can be the place for it. It only gets the class name, not the resolved ref, so at that point it can't tell a forbidden transition from an allowed one. The target ref only exists after `ExtractPriority`. So I'd put the check in the write loop in `UpdateWorkloadPriority`, next to the existing `priorityStateEqual` skip: if the workload has quota reserved and the resolved ref differs from the current one by presence, group, kind, or by name when it's a Pod PriorityClass, skip it and log why instead of issuing a write the API server is going to refuse.

That also keeps the batch behaviour you mention sane, since the components that can take the transition still get written and the reserved ones are left alone deliberately rather than failing the whole reconcile on the first rejection.

Plus an envtest that actually runs the CEL rules, since as you say everything in this area currently builds its client with `utiltesting.NewClientBuilder` and won't see any of this.

Two things I'd want a steer on before I write it. Whether a V(2) log is enough, matching the existing skip, or you'd rather have an event on the owner so it's visible to users. And whether silently skipping is right at all, versus surfacing somewhere that the workload can't follow its owner while it holds a reservation.
