## Description

## Summary

Evaluate and correct the ordering of simulator snapshot capture in `Cache.Snapshot`.

The current implementation captures `c.schedulingSimulator.Snapshot(ctx, c.tasCache.nodesCache.getAllNodes())` before the TAS flavor snapshot construction loop. The TAS cache node state can change while later snapshot construction runs. This can cause `SimulatorSnapshot` to represent an older node state than the TAS flavor snapshots that use it.

## Rationale

The cluster-scoped simulator snapshot must be consistent with the TAS snapshot construction for a scheduling cycle. A stale simulator snapshot can produce feasibility results that do not match the related TAS state.

## Affected area

- `pkg/cache/scheduler/snapshot.go`
- `Cache.Snapshot`
- TAS flavor snapshot construction and simulator snapshot capture ordering

## Required work

- Investigate the consistency requirements between the simulator snapshot and TAS flavor snapshots.
- Evaluate moving simulator snapshot capture after the TAS flavor cache iteration, or use another design that preserves snapshot consistency.
- Measure and document any time or memory cost of the selected approach.
- Add or update tests that cover the selected consistency behavior.

## Acceptance criteria

- The simulator snapshot and TAS flavor snapshots use a consistent view of TAS node state for one `Cache.Snapshot` call.
- The implementation documents or tests the intended ordering and consistency guarantee.
- Tests cover the condition that motivated this follow-up.
