## Description

/kind bug
/area dra

**What happened**:

`deviceClassHandler` reacts to DeviceClass create, update and delete by requeuing the Workloads that request the affected extended resource. It only ever finds the ones that have not reserved quota yet:

```go
lst := kueue.WorkloadList{}
err := h.r.client.List(ctx, &lst,
	client.MatchingFields{
		indexer.WorkloadExtendedResourceKey: name,
		indexer.WorkloadQuotaReservedKey:    string(metav1.ConditionFalse),
	},
)
```
(`pkg/controller/core/workload_controller.go`, `deviceClassHandler.reconcileWorkloads`)

`IndexWorkloadQuotaReserved` indexes a missing condition as `False` and otherwise as the condition's own status, so a Workload holding a reservation is indexed under `True` and sits outside that List:

```go
cond := apimeta.FindStatusCondition(wl.Status.Conditions, kueue.WorkloadQuotaReserved)
if cond == nil {
	return []string{string(metav1.ConditionFalse)}
}
return []string{string(cond.Status)}
```
(`pkg/controller/core/indexer/indexer.go`)

A Workload keeps the quota key that was resolved when its quota was reserved. If a DeviceClass declaring the same `extendedResourceName` is created after that point, `resolveContainerExtendedResources` would now pick that class, and a different logical name if the two classes have different `deviceClassMappings` entries, but nothing re-runs for the Workload that already reserved.

## Why this is a code gap rather than a new risk

The KEP already names the failure mode. From `keps/2941-DRA/README.md`, under Risks and Mitigations:

> **Quota drift**: the scheduler allocates from a different DeviceClass than Kueue charged quota against, but the pod runs successfully. `waitForPodsReady` does not catch this.

and among the mitigations listed right below it:

> - Post-scheduling quota reconciliation will be evaluated for Beta.

So the behaviour is written down and the direction is agreed. I couldn't find anything tracking the code side of it, which is what I'm filing this for. The `QuotaReserved=False` term is the concrete reason a reserved Workload is never revisited, and it seems like the right place to start.

**What you expected to happen**:

At minimum, that skipping a reserved Workload is a deliberate decision with a test and a comment behind it. Beyond that, something along the lines of the KEP's post-scheduling reconciliation: compare the class that was charged against the class the scheduler actually allocated from, and either correct the charge or surface the divergence.

**How to reproduce it (as minimally and precisely as possible)**:

Drop this in `pkg/controller/core/` and run it. Two Workloads request the same extended resource, one pending and one with `QuotaReserved=True`, and a DeviceClass event is delivered for that resource.

```go
import (
	"testing"
	"time"

	corev1 "k8s.io/api/core/v1"
	metav1 "k8s.io/apimachinery/pkg/apis/meta/v1"
	"k8s.io/client-go/util/workqueue"
	"sigs.k8s.io/controller-runtime/pkg/reconcile"

	kueue "sigs.k8s.io/kueue/apis/kueue/v1beta2"
	qcache "sigs.k8s.io/kueue/pkg/cache/queue"
	schdcache "sigs.k8s.io/kueue/pkg/cache/scheduler"
	"sigs.k8s.io/kueue/pkg/controller/core/indexer"
	utiltesting "sigs.k8s.io/kueue/pkg/util/testing"
	utiltestingapi "sigs.k8s.io/kueue/pkg/util/testing/v1beta2"
)

type recordingQueue struct {
	workqueue.TypedRateLimitingInterface[reconcile.Request]
	added []string
}

func (q *recordingQueue) AddAfter(item reconcile.Request, _ time.Duration) {
	q.added = append(q.added, item.Name)
}

func TestDeviceClassHandlerSkipsReservedWorkloads(t *testing.T) {
	const extResource = "example.com/gpu"

	pending := utiltestingapi.MakeWorkload("wl-pending", "ns").
		Queue("lq").
		Request(corev1.ResourceName(extResource), "1").
		Obj()
	reserved := utiltestingapi.MakeWorkload("wl-reserved", "ns").
		Queue("lq").
		Request(corev1.ResourceName(extResource), "1").
		Condition(metav1.Condition{
			Type:    kueue.WorkloadQuotaReserved,
			Status:  metav1.ConditionTrue,
			Reason:  "Admitted",
			Message: "Quota reserved in ClusterQueue cq",
		}).
		Obj()

	t.Logf("index(pending)  quotaReserved=%v extendedResources=%v",
		indexer.IndexWorkloadQuotaReserved(pending), indexer.IndexWorkloadExtendedResources(pending))
	t.Logf("index(reserved) quotaReserved=%v extendedResources=%v",
		indexer.IndexWorkloadQuotaReserved(reserved), indexer.IndexWorkloadExtendedResources(reserved))

	cl := utiltesting.NewClientBuilder().
		WithIndex(&kueue.Workload{}, indexer.WorkloadQuotaReservedKey, indexer.IndexWorkloadQuotaReserved).
		WithIndex(&kueue.Workload{}, indexer.WorkloadExtendedResourceKey, indexer.IndexWorkloadExtendedResources).
		WithObjects(pending, reserved).
		Build()

	cqCache := schdcache.New(cl)
	qManager := qcache.NewManagerForUnitTests(cl, cqCache)
	r := NewWorkloadReconciler(cl, qManager, cqCache, &utiltesting.EventRecorder{})
	h := &deviceClassHandler{r: r}

	ctx, _ := utiltesting.ContextWithLog(t)
	q := &recordingQueue{TypedRateLimitingInterface: workqueue.NewTypedRateLimitingQueue(
		workqueue.DefaultTypedControllerRateLimiter[reconcile.Request]())}

	h.reconcileWorkloads(ctx, q, extResource)

	t.Logf("workloads requeued by the DeviceClass handler: %v", q.added)
	for _, name := range q.added {
		if name == "wl-reserved" {
			return
		}
	}
	t.Errorf("quota-reserved workload was not requeued; handler only saw %v", q.added)
}
```

**Anything else we need to know?**:

It doesn't show a cluster ending up mischarged, which also needs kube-scheduler to allocate from the newer class while the Workload keeps the older key. ### Comment by [@PannagaRao](https://github.com/PannagaRao) — 2026-08-27T00:58:47Z

I reviewed this issue and feel that the behavior is by design and not a bug.

Kueue treats .status.admission as a point-in-time snapshot of a valid charge at admission. To maintain consistency across all resource types, Kueue explicitly avoids rewriting admission records. A workload with reserved quota is meant to hold its reservation for its entire lifecycle. Post-admission modifications or deletions of a DeviceClass are cluster management events, and Kueue shouldn't retroactively modify existing admission state to accommodate them.

The KEP requirement can be re-titled to explicitly state it but I don't think we need a fix.
