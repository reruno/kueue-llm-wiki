## Description

**What happened**:

A StatefulSet-backed Workload can bypass the normal `PodsReadyTimeout` eviction completion when the PodGroup has no remaining Pods at the time the Workload update is reconciled.

The relevant control flow is:

1. The workload controller sets:

   ```yaml
   type: Evicted
   status: "True"
   reason: PodsReadyTimeout
   ```

2. Because the Workload has:

   ```yaml
   metadata:
     annotations:
       kueue.x-k8s.io/is-group-workload: "true"
   ```

   the Workload event handler enqueues a PodGroup reconcile request.

3. `(*Pod).Load()` lists the group members. When the list is empty, it returns `shouldFinalize=true`:

   https://github.com/kubernetes-sigs/kueue/blob/456c96f88ca70bcdac2cdf5f488b13aa711c466c/pkg/controller/jobs/pod/pod_controller.go#L686-L732

4. `ReconcileGenericJob()` handles `shouldFinalize` before reaching the normal eviction branch:

   https://github.com/kubernetes-sigs/kueue/blob/456c96f88ca70bcdac2cdf5f488b13aa711c466c/pkg/controller/jobframework/reconciler.go#L310-L335

5. Consequently, the normal eviction completion is skipped:

   https://github.com/kubernetes-sigs/kueue/blob/456c96f88ca70bcdac2cdf5f488b13aa711c466c/pkg/controller/jobframework/reconciler.go#L592-L630

That branch would normally stop the job, clear `status.admission`, set `QuotaReserved=False`, and allow the Workload to follow its configured requeue and backoff policy.

The externally visible result depends on the `FinishOrphanedWorkloads` feature gate.

With `FinishOrphanedWorkloads=false`, as in the environment where this was observed, the Workload finalizer is removed, but eviction completion is skipped. The Workload can remain in this state:

```yaml
spec:
  active: true
status:
  admission: <still present>
  conditions:
  - type: QuotaReserved
    status: "True"
  - type: Admitted
    status: "True"
  - type: Evicted
    status: "True"
    reason: PodsReadyTimeout
```

The Workload continues consuming ClusterQueue quota even though no matching Pod exists.

With `FinishOrphanedWorkloads=true`, which is the default on current `main`, the same empty-group finalization path may instead mark the Workload as:

```yaml
- type: Finished
  status: "True"
  reason: OwnerNotFound
```

This can happen even though the Workload still has an existing StatefulSet as its controller owner.

The relevant finalization code is:

https://github.com/kubernetes-sigs/kueue/blob/456c96f88ca70bcdac2cdf5f488b13aa711c466c/pkg/workload/workload.go#L1455-L1478

An empty child Pod list does not prove that an external controller owner is gone. A transiently empty StatefulSet PodGroup must not be terminally finished as `OwnerNotFound`.

In one observed v0.19-based deployment:

- the Workload was admitted at `2026-08-17T10:53:23Z`;
- `Evicted=True, Reason=PodsReadyTimeout` was set at `2026-08-17T10:58:23Z`;
- no matching Pod existed;
- `QuotaReserved=True`, `Admitted=True`, and `status.admission` remained until `2026-08-17T19:22:37Z`;
- quota was released only when a later StatefulSet scale-to-zero reconciliation set `QuotaReserved=False, Reason=OnHold`.

The relevant fork code was compared with upstream v0.19.0. The `Pod.Load`, JobFramework finalization/eviction, and StatefulSet lifecycle paths are upstream-equivalent. The fork does not introduce this control flow.

**What you expected to happen**:

An empty PodGroup should not bypass eviction completion, and it should not by itself prove that an external controller owner is gone.

For a StatefulSet with `spec.replicas > 0`, the expected lifecycle is:

1. `PodsReadyTimeout` sets `Evicted=True`.
2. Existing non-gated Pods are stopped or deleted, if any.
3. Once no active Pods remain, Kueue clears `status.admission` and sets `QuotaReserved=False`.
4. The Workload is requeued according to `waitForPodsReady.requeuingStrategy`.
5. Replacement Pods remain scheduling-gated until the Workload is admitted again.
6. Once `backoffLimitCount` is reached, Kueue deactivates the Workload according to the existing WaitForPodsReady policy.

For a StatefulSet with `spec.replicas == 0`, the expected lifecycle is:

1. quota is released;
2. the Workload is placed on hold with `QuotaReserved=False, Reason=OnHold`;
3. the Workload is not requeued while the StatefulSet remains at zero;
4. scaling the StatefulSet above zero clears `OnHold` and resumes normal admission.

In neither case should an existing StatefulSet-owned Workload be marked `Finished/OwnerNotFound` solely because the PodGroup currently contains zero Pods.

This is consistent with the documented WaitForPodsReady behavior:

https://kueue.sigs.k8s.io/docs/tasks/manage/setup_wait_for_pods_ready/

**How to reproduce it (as minimally and precisely as possible)**:

A deterministic controller-level reproduction is:

1. Enable the StatefulSet and Pod integrations.
2. Create a StatefulSet.
3. Create or obtain its group Workload with:

   ```yaml
   metadata:
     annotations:
       kueue.x-k8s.io/is-group-workload: "true"
     ownerReferences:
     - apiVersion: apps/v1
       kind: StatefulSet
       name: test-sts
       controller: true
   ```

4. Give the Workload a quota reservation and the following conditions:

   ```yaml
   status:
     admission:
       clusterQueue: test-cq
     conditions:
     - type: QuotaReserved
       status: "True"
     - type: Admitted
       status: "True"
     - type: Evicted
       status: "True"
       reason: PodsReadyTimeout
   ```

5. Ensure that the StatefulSet owner still exists.
6. Ensure that no Pod exists with this Workload's PodGroup name.
7. Reconcile the group request:

   ```text
   {Name: <workload-name>, Namespace: "group/<namespace>"}
   ```

8. With `FinishOrphanedWorkloads=false`, observe that `status.admission` and `QuotaReserved=True` can remain.
9. Repeat with `FinishOrphanedWorkloads=true`.
10. Observe that the Workload can be marked `Finished=True, Reason=OwnerNotFound`, even though the StatefulSet owner still exists.

The regression test should cover both feature-gate values.

**Anything else we need to know?**:

This is related to, but not fixed by:

- https://github.com/kubernetes-sigs/kueue/issues/12232
- https://github.com/kubernetes-sigs/kueue/pull/12233

Those changes implement the StatefulSet scale-to-zero `OnHold` behavior. They do not cover the empty-PodGroup fast path that runs before normal eviction handling.

It is also adjacent to:

- https://github.com/kubernetes-sigs/kueue/pull/13960

That PR documents the same early finalization path and prevents it from finalizing a foreign Workload that merely shares the PodGroup name.

A StatefulSet Workload is a legitimate group Workload carrying `is-group-workload=true`, so it remains outside that guard.

A possible fix direction is to make missing-member handling owner-aware:

- a verified missing controller owner may continue using the existing `OwnerNotFound` finalization;
- an existing external owner must not be inferred missing from an empty child Pod list;
- an evicted Workload with no active members should complete the normal eviction status transition without calling `Stop()` on nonexistent Pods;
- StatefulSet scale-to-zero should continue using the existing `OnHold` semantics;
- the regular eviction status mutation should be extracted and reused rather than duplicated.
