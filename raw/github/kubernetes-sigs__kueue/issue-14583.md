## Description

/kind bug
/area tas

## What happened

A Job can adopt a prebuilt Workload whose `PodSet.TopologyRequest` contradicts the topology requested by the Job's Pod template.

`Job.PodSets` builds a structured `TopologyRequest` from the Pod template's TAS annotations. The generic prebuilt-Workload path reaches `equality.ComparePodSetSlices`, but `ComparePodSets` (`pkg/util/equality/podset.go`) compares only `Count`, `MinCount`, and selected `PodSpec` fields. It never reads `TopologyRequest`.

For example, these are considered equivalent when their count, containers, and requests match:

```text
Job:      required topology = kubernetes.io/hostname
Workload: required topology = topology.kubernetes.io/zone
```

That changes the placement contract from "all Pods in one node domain" to "all Pods in one zone domain."

## Controller-level reproduction

I added a case to the existing Job reconciler test on current `main` (`22aefdeca`):

- an unsuspended Job references a prebuilt Workload;
- the Job Pod template has `podset-required-topology=kubernetes.io/hostname`;
- the Workload template and `TopologyRequest.Required` use `topology.kubernetes.io/zone`;
- count, resources, and containers match;
- the expected behavior is the same as the existing non-equivalent-prebuilt case: preserve the Job and finish the Workload with `Reason=OutOfSync`.

The test fails for both values of `WorkloadRequestUseMergePatch`. The reconciler instead:

1. returns success rather than `ErrPrebuiltWorkloadNotFound`;
2. attaches the Workload to the Job without an `OutOfSync` condition;
3. while stopping the unadmitted Job, restores the zone annotation from the accepted Workload over the Job's hostname annotation.

The relevant diff from the executed test is:

```diff
- kueue.x-k8s.io/podset-required-topology: kubernetes.io/hostname
+ kueue.x-k8s.io/podset-required-topology: topology.kubernetes.io/zone
```

## Expected behavior

Topology requests that affect TAS placement must participate in Job/Workload equivalence. A conflicting prebuilt Workload should be marked `OutOfSync`; it must not replace the Job's topology request or be scheduled on the Job's behalf.

## Impact and recovery

A weaker Workload request can spread Pods more broadly than the Job requested. The reverse mismatch can make admission unnecessarily restrictive. There is no automatic correction: scheduling follows the accepted Workload, and in the unsuspended-Job path the restore operation can make the Job template agree with that Workload, hiding the original mismatch from later reconciles.

## Fix direction tested

Comparing `TopologyRequest` whenever either side contains an effective TAS placement constraint makes the controller regression pass. A completely unconditional deep comparison is too strict for existing non-TAS Workloads: when TAS is enabled, some Job integrations can construct a request containing only derived indexing information such as `PodIndexLabel`, while older or manually constructed non-TAS Workloads have `nil`.

The tested compatibility shape was:

- if neither side has a placement constraint, retain current compatibility;
- if either side has one, compare the complete `TopologyRequest`.

With that change, the regression and the existing tests pass:

```text
go test ./pkg/util/equality ./pkg/controller/jobs/job -count=1
ok sigs.k8s.io/kueue/pkg/util/equality
ok sigs.k8s.io/kueue/pkg/controller/jobs/job
```
