**What would you like to be added**:

Define a bounded Scheduling Cycle Refill mechanism. After a ClusterQueue successfully admits a Workload, the scheduler may consider its next Workload in the same scheduling cycle rather than waiting for the next one.

The Alpha proposal applies this to Fair Sharing behind the disabled-by-default FairSharingRefill feature gate, using the existing fair-sharing ordering and a per-cycle bound on additional work. The accompanying KEP records the remaining policy questions for Beta, including budget allocation, budget exhaustion, and the insertion rule for a future classic-scheduling variant.

Prototype: #13729
Benchmark: #13730
Motivating bug: #9345
Umbrella: #13695 (work item 1)

**Why is this needed**:

Today a ClusterQueue can contribute only one candidate per scheduling cycle. After an under-share ClusterQueue admits that candidate, its successor cannot compete until the next cycle. This can allow remaining capacity to go to a ClusterQueue with a higher share and adds repeated cycle overhead.

The prototype shows that refill can address this, but it also changes cycle-level candidate semantics and introduces policy tradeoffs that should be documented separately from the implementation.

**Completion requirements**:

- Agree on the Alpha refill semantics and the policy questions that remain open for Beta.
- Implement the Alpha behavior behind the disabled-by-default `FairSharingRefill` feature gate.
- Validate the motivating scenario and the cycle-work and latency tradeoffs with the companion benchmark.
