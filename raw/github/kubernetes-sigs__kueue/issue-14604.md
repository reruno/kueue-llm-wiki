## Description

<!-- Please only use this template for submitting clean up requests -->

**What would you like to be cleaned**:

`Manager.RequeueWorkload` re-reads the Workload and calls `workload.Info.Update`, which recomputes its scheduling equivalence hash:

```text
Manager.RequeueWorkload
  └─ Info.Update
       └─ Info.UpdateSchedulingHash
            └─ computeSchedulingHash
```

`computeSchedulingHash` rebuilds the scheduling shape, marshals it through `encoding/json`, and hashes the result even when the relevant workload shape has not changed.

This showed up while profiling the `contended` fixture in #13730 (context: #13729), but the cost is not refill-specific. Refill just makes an existing requeue cost easier to see.

On the `contended` fixture, where refill repeatedly pops and requeues a successor that cannot be admitted:

- the requeue path accounts for about **56%** of the extra allocations;
- `computeSchedulingHash` is the largest single item on that path;
- about **81%** of its allocations come from `encoding/json.Marshal`;
- for the one-PodSet / one-container workload in the benchmark, that is roughly **80 allocations per hash**.

There seem to be two independent places worth looking at:

1. avoid recomputing the hash when the relevant workload shape has not changed;
2. make computing the hash cheaper when it is needed, potentially without building and JSON-marshalling the intermediate shape.

For (2), changing how the hash is produced may change the hash values themselves, so we should first confirm whether anything depends on the exact value rather than equivalence within the running process.

**Why is this needed**:

Requeueing is a scheduler hot path, and this cost is paid by workloads that are popped and then returned to the queue. Reducing it would lower allocation and CPU overhead independently of fair-sharing refill.
