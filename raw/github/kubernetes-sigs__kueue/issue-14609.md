## Description

**What happened**:

A JobSet restarted replicas that had succeeded before. The Workload's `status.reclaimablePods` did not reset. Kueue then under-counts the workload's usage for the rest of its admission.

Observed instance (one replicated job, `replicas: 3`, 16 CPUs per pod):

1. Kueue admits the Workload: `resourceUsage cpu: 48, pods: 3`.
2. 2 replicas succeed. `reclaimablePods` becomes `count: 2`. Kueue now counts the workload as `cpu: 16, pods: 1`. Correct.
3. The last replica stalls. `PodsReady=False (WaitForRecovery)`, then `Evicted=True (PodsReadyTimeout)`. The workload is not requeued. `QuotaReserved` stays `True`.
4. The JobSet restarts all 3 replicas. 3 pods run and request 48 CPUs.
5. `reclaimablePods` stays at 2. Kueue counts 16 CPUs. The 32-CPU gap is permanent.

Verification: sum all admitted Workloads on the ClusterQueue as `resourceUsage − (resourceUsage / count) × reclaimablePods`. The sum equals `ClusterQueue.status.flavorsUsage` exactly. The sum without the subtraction is over by exactly the reclaimed amounts. Thus the live ledger counts this workload at 16 CPUs while its pods request 48.

The API field is documented as non-decreasing while quota is reserved, so each component behaves as specified. But no component corrects the count when succeeded replicas run again in the same admission. The ClusterQueue then admits new workloads into capacity that pods already use.

**What you expected to happen**:

`reclaimablePods` returns to match reality when previously-succeeded replicas are recreated in the same admission — reset by the JobSet integration or by Kueue core. If the ratchet is intentional across owner restarts, document the over-admission risk.

**How to reproduce it (as minimally and precisely as possible)**:

1. Kueue with the JobSet integration. A ClusterQueue with a CPU quota. `waitForPodsReady` with recovery enabled.
2. Create a JobSet: one replicated job, `replicas: 3`, 16 CPUs per pod.
3. Let 2 replicas succeed. Observe `reclaimablePods: 2` and `flavorsUsage` drop by 32 CPUs.
4. Make the JobSet restart its replicas without a requeue (our trigger: last replica stalls → `Evicted=True (PodsReadyTimeout)` → JobSet recreates all child Jobs while `QuotaReserved` stays `True`. A `failurePolicy` restart should also work).
5. Observe: 3 pods `Running` (48 CPUs requested), `reclaimablePods` still 2, `flavorsUsage` still counts 16 CPUs.
6. Impact: fill the queue to nominal. Kueue admits a new workload into the 32 CPUs that running pods already use.

**Anything else we need to know?**:

- The gap scales with `reclaimablePods × per-pod request`. Every JobSet that restarts after a partial success is exposed.
- Possible separate issue: after `Evicted=True (PodsReadyTimeout)` the workload kept `QuotaReserved=True` and its pods kept running. This state makes the ratchet permanent. We can file it separately.
- Sanitized Workload/ClusterQueue YAML available on request.

**Environment**:

### Comment by [@tjcuddihy](https://github.com/tjcuddihy) — 2026-08-19T22:52:05Z

**Follow-up: the same workload was requeued, and the divergence now runs in the opposite direction.**

The workload from the report was later evicted fully and requeued. Kueue re-admitted it. Its conditions now read `Requeued=True`, `Evicted=False`, `PodsReady=True`. All 3 pods run.

New observation: `status.reclaimablePods` **still reads `count: 2`** — the requeue did not clear it. But Kueue's ledger now counts the workload at **full usage** (48 CPUs, 3 pods).

Verification, same method as the report, after the requeue:

- Σ over the ClusterQueue of raw `podSetAssignments.resourceUsage` == `flavorsUsage` **exactly**.
- Σ with the reclaim subtraction is short by exactly 32 CPUs and 2 pods — the stale field's amount.

Before the requeue, the opposite held: the subtraction matched the ledger exactly, and the raw sum was over.

So the field and the ledger disagree in both directions across one evict/requeue cycle:

1. **Before requeue:** the ledger honors a stale `reclaimablePods` → Kueue under-counts running pods (the report's over-admission risk).
2. **After requeue:** the ledger ignores the still-present field → the field is stale metadata with no marker that says so.

Impact for API consumers: `resourceUsage − (resourceUsage/count) × reclaimablePods` (the `workload.Info` rule) matches the ledger before the requeue and diverges by the stale amount after it. **No API-visible signal says which regime applies** — the admission history that decides it is not on the object.

A single fix covers both directions: **clear `reclaimablePods` on eviction/requeue** (or at re-admission). The integration then re-reports real completions for the new attempt.

### Comment by [@mimowo](https://github.com/mimowo) — 2026-09-16T07:17:28Z


Imagine you have a Job with 10 pods, embarrassingly parallel. It processed 5 and got evicted. In that case I think we shouldn't repeat the computations for the 5 already finished Pods, and so we only need quota to run the remaining 5 Pods.

I totally understand that in the ML use case the Job will need all 10 pods to make progress.

So, I think this should a configuration option - probably per workload. I would be ok with a FG to determine the behavior for ReclaimablePods for now, say ReclaimablePodsResetOnEviction. However, long term I would like to have API (probably annotation) which gives users choice per Workload.

Let me know if I'm missing something.
