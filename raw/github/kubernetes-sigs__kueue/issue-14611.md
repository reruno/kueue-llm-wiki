## Description

**What happened**:

The Pod Importer selects the first ResourceFlavor listed for a requested resource, without checking that the flavor is compatible with the Pod's node selector, required node affinity, or taints.

For example, when a ClusterQueue resource group lists `rf-gpu` first and `rf-cpu` second, the importer maps `cpu` to `rf-gpu` even when the imported Pod has `nodeSelector: {accelerator: cpu}` and `rf-gpu` has `nodeLabels: {accelerator: gpu}`. The importer then uses that mapping when constructing the Workload admission. The import path marks the Workload as both quota-reserved and admitted.

The relevant implementation is [`flavorsByResourceFrom`](https://github.com/kubernetes-sigs/kueue/blob/f7b7f3c7e90d541b3dfddc044e18bb91406e0d0e/cmd/importer/cache/cache.go#L136-L146), which assigns `rg.Flavors[0]` for each resource. The resulting mapping is consumed by [`flavorAssignmentsForRequests`](https://github.com/kubernetes-sigs/kueue/blob/f7b7f3c7e90d541b3dfddc044e18bb91406e0d0e/cmd/importer/pod/check.go#L155-L184), while the import path writes the admission and `Admitted=True` condition in [`import.go`](https://github.com/kubernetes-sigs/kueue/blob/f7b7f3c7e90d541b3dfddc044e18bb91406e0d0e/cmd/importer/pod/import.go#L203-L229).

**What you expected to happen**:

The importer should choose the first **feasible** flavor in the resource group. In the example above, it should select `rf-cpu`. If no listed flavor matches the Pod's node selector, required node affinity, taints, topology requirements, and quota constraints, the importer should reject the Pod during validation instead of creating an admitted Workload with an incompatible assignment.

This is consistent with the ResourceFlavor API documentation, which says that `nodeLabels` must match the PodSet's node selector and node affinity. The normal scheduler performs this check in [`checkFlavorForPodSets`](https://github.com/kubernetes-sigs/kueue/blob/f7b7f3c7e90d541b3dfddc044e18bb91406e0d0e/pkg/scheduler/flavorassigner/flavorassigner.go#L1177-L1225), but the importer does not use the same feasibility logic.

**How to reproduce it (as minimally and precisely as possible)**:

1. Create two ResourceFlavors:

```yaml
apiVersion: kueue.x-k8s.io/v1beta2
kind: ResourceFlavor
metadata:
  name: rf-gpu
spec:
  nodeLabels:
    accelerator: gpu
---
apiVersion: kueue.x-k8s.io/v1beta2
kind: ResourceFlavor
metadata:
  name: rf-cpu
spec:
  nodeLabels:
    accelerator: cpu
```

1. Configure a ClusterQueue with the flavors in this order, both covering CPU:

```yaml
apiVersion: kueue.x-k8s.io/v1beta2
kind: ClusterQueue
metadata:
  name: cq
spec:
  resourceGroups:
  - coveredResources: [cpu]
    flavors:
    - name: rf-gpu
      resources:
      - name: cpu
        nominalQuota: "10"
    - name: rf-cpu
      resources:
      - name: cpu
        nominalQuota: "10"
```

1. Create a Pod requesting CPU and requiring CPU nodes:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: cpu-pod
  namespace: default
  labels:
    kueue.x-k8s.io/queue-name: local-queue
spec:
  nodeSelector:
    accelerator: cpu
  restartPolicy: Never
  containers:
  - name: main
    image: busybox
    command: ["sh", "-c", "sleep 3600"]
    resources:
      requests:
        cpu: "1"
```

1. Run the Pod Importer against the LocalQueue that points to `cq` with `--dry-run=false`.

The importer computes the admission flavor as:

```
cpu -> rf-gpu
```

and proceeds through its direct-admission path, despite `rf-gpu` being incompatible with the Pod's `accelerator: cpu` selector. `rf-cpu` is never considered.

I also reproduced the same first-flavor behavior with a first flavor containing an untolerated `NoSchedule` taint and a second clean flavor.

Validation performed at commit [`f7b7f3c7e90d541b3dfddc044e18bb91406e0d0e`](https://github.com/kubernetes-sigs/kueue/tree/f7b7f3c7e90d541b3dfddc044e18bb91406e0d0e):


**Anything else we need to know?**:

The repeated test is a temporary repository-native regression probe; it was removed after validation. The behavior is deterministic because the importer precomputes a single resource-to-flavor mapping using the first flavor in each resource group.

The normal scheduler checks node affinity and taints before assigning a ResourceFlavor, including the failure case `flavor %s doesn't match node affinity`. The importer bypasses those checks and also bypasses normal quota-feasibility evaluation. This can charge accounting to the wrong flavor or leave an admitted Workload whose assignment cannot be applied consistently to the Pod.

This appears distinct from [PR #12924](https://github.com/kubernetes-sigs/kueue/pull/12924), which made Pod Importer flavor mapping deterministic per requested resource but did not add flavor compatibility checks. A targeted search of existing Kueue issues for importer, first-flavor, node-affinity, node-label, ResourceFlavor, and toleration combinations found no report of this specific behavior.

A possible fix is to reuse the scheduler's flavor-assignment feasibility logic in a read-only importer path, or to add equivalent checks for node labels/affinity, taints, topology, and quota before selecting a flavor. A regression test should verify that with `rf-gpu` first and `rf-cpu` second, a Pod selecting `accelerator: cpu` receives `rf-cpu`.
