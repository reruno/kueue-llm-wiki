## Description

**What would you like to be added**:

A KEP documenting the compatibility constraints between elastic Jobs `ElasticJobsViaWorkloadSlices` and Kueue's `ProvisioningRequest` admission-check integration, specifically:

1. Which `provisioningClassName`s are verified safe to combine with elastic Job scale-up/scale-down today:
- `queued-provisioning.gke.io`
- `best-effort-atomic-scale-up.autoscaling.x-k8s.io`
- `check-capacity.autoscaling.x-k8s.io` 

vs. which are out of scope and unverified:

- TPU multi-host queued provisioning
- non-GKE queued/reservation classes
- elastic + MultiKueue
- concurrent overlapping scale-ups

2. The per-pod vs. per-template lifetime rule for `ProvisioningRequest` identity annotations `consume-provisioning-request`, `provisioning-class-name` that keeps the long-lived elastic job template free of stale per-request identity, so GKE's nodeSelector injection behavior for `queued-provisioning.gke.io` stays correctly scoped across every scale-up.

**Why is this needed**:

Raised during review of #14316 elastic Job scale-up/scale-down support: it was correctly observed that if a pod is admitted without the correct, current `consume-provisioning-request` annotation, GKE's webhook won't inject the nodeSelector scoping it to the right node, risking scheduling onto arbitrary capacity. This is currently only documented implicitly in code `podset.go`, `elastic_job_ungater.go`; 
A KEP gives it a durable, reviewable home and a scope boundary for future `provisioningClassName`/elastic-job work to extend.
