## Description

## Summary

Add dedicated metrics for the time that a workload spends waiting to recover after a `WaitForPodsReady` failure.

## Rationale

PR #14626 prevents recovery transitions from re-emitting the initial readiness wait-time metrics. The recovery duration is still useful operational data. It should be exposed through separate metrics so that recovery behavior does not change the meaning of initial readiness metrics.

## Scope

- Define a workload-level recovery duration metric. A candidate name is `kueue_workload_recovery_time_seconds`.
- Define the metric lifecycle and labels. The metric must measure the interval from the start of `WaitForPodsReady` recovery to the successful recovery transition.
- Consider matching LocalQueue-scoped recovery metrics if the existing readiness metrics require the same visibility.
- Update the metric documentation and add unit and end-to-end coverage.

## Acceptance criteria

- A successful `WaitForPodsReady` recovery emits dedicated recovery-duration metric data.
- Initial readiness wait-time metrics remain limited to the initial `WorkloadStarted` transition.
- The metric name, type, labels, and timing boundaries are documented.
- Tests cover recovery and verify that the recovery metrics do not alter initial readiness metric counts.
