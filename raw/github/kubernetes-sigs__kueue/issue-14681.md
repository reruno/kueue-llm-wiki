## Description

## Summary

Ensure that preemptor state remains consistent between the queue state and the ClusterQueue scheduling snapshot.

## Rationale

The current implementation has two related follow-up concerns:

1. `pkg/cache/queue/manager.go` calculates `cq.IsPreemptor` before it takes the ClusterQueue snapshot. Concurrent state changes can make the calculated value and the snapshot state differ for one scheduling cycle.
2. `pkg/cache/queue/second_pass_queue.go` can lose `IsPreemptor` state when it stores queued workload data. The implementation needs a durable representation or a correct recomputation point.

## Affected areas

- `pkg/cache/queue/manager.go`
- `pkg/cache/queue/second_pass_queue.go`
- Preemptor-state propagation in queue snapshots and second-pass scheduling

## Acceptance criteria

- Preemptor state and the ClusterQueue snapshot use a consistent view of queue state.
- The second-pass queue preserves or correctly recomputes preemptor state.
- Tests cover concurrent queue-state changes and second-pass scheduling behavior.
- The change does not regress sticky pending-preemption scheduling.
