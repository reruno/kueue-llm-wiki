**What happened**:

Restarting the kueue controller or leader election will reconcile all the workloadpriorityclass' priority. Say we have modified the .spec.priority earlier, the reconciliation of workloadpriorityclass in the workloadpriorityclass_controller.go when the kueue controller restarts would override the .spec.priority back to workloadpriorityclass' priority.

**What you expected to happen**:

I expect that restarting the kueue controller keeps the original .spec.priority

**How to reproduce it (as minimally and precisely as possible)**:

1. Create a new WorkloadPriorityClass
```
apiVersion: kueue.x-k8s.io/v1beta2
kind: WorkloadPriorityClass
metadata:
  name: sample-priority
value: 100
```
2. Create a job
```
apiVersion: batch/v1
kind: Job
metadata:
  name: sample-job
  labels:
    kueue.x-k8s.io/queue-name: user-queue
    kueue.x-k8s.io/priority-class: sample-priority
spec:
...
```
3. Find the corresponding workload to the Job and modifies its `.spec.priority` from 100 to 1.
4. Restart the kueue controller (eg/ `kubectl rollout restart deployment kueue-controller-manager -n kueue`)
5. Check the `.spec.priority` on the workload and you should see it getting reverted back to 100.

### Comment by [@jessicaxiejw](https://github.com/jessicaxiejw) — 2026-08-20T18:44:09Z

I think the `pkg/controller/core/workloadpriorityclass_controller.go` assumes that any changes to .value should be reflected to all the exiting workloads. We can enable a new beta flag that `NoWorkloadPriorityClassValuePropogation` or something similar that only applies the level to existing workload when the flag is enabled. Otherwise, we don't need to run the WorkloadPriorityClassReconciler.

Another workaround is adding a predicate
```
func (r *WorkloadPriorityClassReconciler) Create(e event.TypedCreateEvent[*kueue.WorkloadPriorityClass]) bool {
	log := r.logger().WithValues("workloadPriorityClass", klog.KObj(e.Object))
	// Create events from the informer's initial list carry no information about
	// whether the value changed, so propagating them would overwrite priorities
	// that were set directly on the Workload.
	if e.IsInInitialList {
		log.V(3).Info("Skipping initial list event")
		return false
	}
	// Covering the case when the WorkloadPriorityClass was re-created with a different priority,
	// but the Workload is still referencing it.
	return true
}
```
The downside with the second option is that if someone edits a WorkloadPriorityClass value while Kueue is down, the new value is never propagated.

### Comment by [@mimowo](https://github.com/mimowo) — 2026-08-31T17:30:43Z

Actually, mutating manually workload .spec.priority is not well supported. Controller restart is just one corner case, but generally speaking the value in Workload's spec.priority should follow what is in Job. The fact that you can even mutate it could be considered a bug.

I would suggest using the priority-boost feature  (annotation) for that. 

Alternatively, you can change the priority on the Job itself via the workload-priority label.
