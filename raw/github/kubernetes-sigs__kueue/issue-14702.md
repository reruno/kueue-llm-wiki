## Description

Hi Kueue team, I am designing an **idle-termination** feature for KubeRay:

when a RayCluster has been idle for some period, the Ray autoscaler either **suspends** or **deletes** the RayCluster. Since Kueue treats `RayCluster.spec.suspend` as its own admission actuator, we would like to agree on the right signal before we settle the API.

We may want to support the suspend feature for idle termination, so I want to discuss this behavior with kueue team.

## Background: what Kueue does with `spec.suspend` today:

**For regular RayClusters**: `spec.suspend` is the actuator Kueue writes to start/stop the RayCluster, and Kueue is its sole writer:

- When the Workload is admitted and the job is still suspended, the reconciler unsuspends it unconditionally.
- When a RayCluster is admitted by Kueue, Kueue will unsuspend it by setting `spec.suspend` to `false`, regardless of its previous value.

**For **elastic** RayClusters**:  Kueue no longer uses `spec.suspend` as the throttling mechanism. Instead, new Ray Pods are created with a Kueue scheduling gate and remain unscheduled until the workload is admitted. For an already running RayCluster, Kueue does not re-suspend it just because a new Workload slice is not admitted.


## Which RayClusters are affected, and where the idle decision lives

The ownership conflict above applies to **both**  RayClusters and elastic Elastic RayCluster. 

| | RayCluster | Elastic RayCluster (`kueue.x-k8s.io/elastic-job: "true"`) |
|---|---|---|
| Who writes `spec.suspend` | Kueue only; it **is** the start/stop actuator | Kueue only, but it is **not** the throttle (pod scheduling gates are) |
| `enableInTreeAutoscaling: true` | rejected by Kueue's webhook, on create **and** update | allowed — the only supported combination |
| Effect of an external `suspend=true` | Kueue flips it back on the next reconcile; quota is never released | same with RayCluster |
Quota returned by idle termination | Entire cluster | Entire cluster


## Question

1. Let the Ray autoscaler update `spec.suspend`
Since this feature only applies to elastic RayClusters (regular RayClusters are rejected by the admission webhook), I wonder if it would be okay to let the Ray autoscaler patch `spec.suspend`.

2. If not, introduce a new, separate signal on the RayCluster
If `spec.suspend` should remain exclusively controlled by Kueue, should we introduce a separate field for RayCluster for the Ray autoscaler to use?

### Comment by [@win5923](https://github.com/win5923) — 2026-08-21T19:50:04Z

Hi @kannon92, thanks!

Looks like the KEP only supports gating at **creation** time. That doesn't reach our case, for two reasons:
- our signal is necessarily post-admission. The Ray autoscaler runs as a sidecar container in the head pod, so it only exists *after* Kueue has set `spec.suspend=false`. The KEP does not support gating an already-admitted workload.
- The gate prevents a Workload from being admitted before it reserves quota. Idle termination requires the opposite: release quota that has already been reserved, while keeping the Workload around so it can be re-admitted when it wakes up.


I think the “Gating the admission of Jobs past their creation time” alternative would be fit for our use case. 

> One possible implementation would allow users to interact directly with a managed Job object (where Job is a CR that Kueue manages like batch/v1.Job, PyTorchJob, Deployment, etc.) to declare their intent that Kueue should "deactivate" or "activate" the associated Workload.
> 
> Users would do this by setting annotations on the Job:
> 
> - kueue.x-k8s.io/activate=true: Instructs Kueue to make the Workload eligible for admission. The Workload will flow through the normal Kueue admission checks and scheduling decisions.
> - kueue.x-k8s.io/deactivate=true: Instructs Kueue to mark the Workload as ineligible for admission. Kueue will not consider this Workload for admission until it is activated.


When the autoscaler detects that the RayCluster is idle, it could set `kueue.x-k8s.io/deactivate=true` to the kueue-managed RayCluster, allowing Kueue to deactivate the associated Workload and release its reserved quota.

### Comment by [@win5923](https://github.com/win5923) — 2026-08-24T06:41:30Z

From the Kueue side, the suggested workflow may be:

1. Users enable `idleTermination` in the RayCluster CR spec.
2. Autoscaler detects no driver for the timeout duration.
3. Autoscaler patches the RayCluster with an annotation marking it as idle (e.g. `kueue.x-k8s.io/idle-terminated: "true"`). It does not touch `spec.suspend`, which stays owned by Kueue.
4. Kueue sees the annotation and runs its existing eviction path for the RayCluster's Workload: `.spec.active` is set to `false`, the Workload gets `Evicted=True` with reason `Deactivated`, and Kueue sets `spec.suspend` to `true` while restoring the pod templates it had mutated at admission time.
5. KubeRay will delete the underlying resources while preserving the RayCluster custom resource.
6. Once no Pods remain, Kueue releases the quota reservation back to the ClusterQueue, and other queued workloads can use it. Because the Workload is inactive, Kueue will not try to unsuspend the RayCluster on its own.
7. Users remove the annotation to resume their workspaces when they need. Kueue marks the Workload active, it re-enters the queue like any other pending workload, and once quota is available Kueue admits it and sets `spec.suspend` back to `false` so KubeRay recreates the head and worker Pods.

### Comment by [@mimowo](https://github.com/mimowo) — 2026-08-31T17:51:15Z

@win5923 Indeed, updating `spec.suspend` by the Ray autoscaler will not fly with Kueue, because Kueue will try to re-admit the workload and set `spec.suspend=false` soon after that (and will not release the quota as you say). 

Setting the Workload's `.spec.active=false` will work, but may not be the cleanest, because it requires you to mutate the Kueue's Workload is which rather an internal state tracking CRD. 

I think a cleaner solution would be if KubeRay could communicate that the RayJob / RayCluster is doomed to be idle-terminated. Then, Kueue-specific integration code could observe the situation and set OnHold or Deactivate it. 

We already use OnHold when the RayJob / RayCluster has the ValidationFailed condition, but we could have a dedicated condition here, say "IdleTermination".
