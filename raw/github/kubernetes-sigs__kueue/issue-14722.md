**What happened**:

A Kueue-managed TrainJob created against Kubeflow Trainer v2.1 is never admitted on Kueue 0.17+. The Workload stays Pending and the Kueue controller logs `"error":"kueue runtime patch not found"`.

**What you expected to happen**:

Kueue manages TrainJobs from both v2.1 and v2.2+ Trainer.

**How to reproduce it (as minimally and precisely as possible)**:

- Kueue v0.18, Kubeflow Trainer v2.1
- Create a kueue-managed TrainJob

**Anything else we need to know?**:

Root cause is a breaking Trainer API change adopted by Kueue in #9831. Trainer v2.2 (kubeflow/trainer#3309) replaced `spec.podTemplateOverrides` with `spec.runtimePatches` with a schema change. The current version of Kueue targets the v2.2+ shape exclusively.

We support customers on KFT v2.1 under agreements running ~18 more months, so upgrading them to v2.2+ isn't an option. Upgrading Kueue is fine. We need Kueue to keep supporting podTemplateOverrides for v2.1 Trainer, detected at runtime (e.g. from the TrainJob CRD schema). NB: there was a similar breaking change in Trainer v2.0->v.2.1, but we don't need support for KFT v2.0.

This is related to https://github.com/kubernetes-sigs/kueue/issues/11931 but not the same - we want support for KFT v2.1 and 2.2+ in Kueue.

I'm happy to write the patch -- can you confirm you'd accept that approach before I start?

### Comment by [@robert-bell](https://github.com/robert-bell) — 2026-08-26T19:14:23Z

Thanks for the update. I appreciate that it doesn’t make sense for Kueue to take on the maintenance burden of supporting both API shapes. @andreyvelich unfortunately, we’re not able to run a legacy version of Kueue, nor upgrade to 2.2+ due to separate support commitments.

I’ve dug into this a little more, and I think I can work around the problem in our downstream fork. However, I’d need Kueue to patch the TrainJob rather than perform a full Update. That way, Kueue only needs to update `spec.runtimePatches` and `spec.suspend`, and can remain agnostic to the other fields.

FYI, this is the approach I’m working towards in our fork:
* Add `runtimePatches` to the KFT 2.1 CRD alongside the existing `podTemplateOverrides field.
Have the Trainer controller translate any `runtimePatches` into the equivalent `podTemplateOverrides` in memory during reconciliation.
* Kueue needs to use a patch in the update otherwise it will remove any existing `podTemplateOverrides` contents. Since Kueue vendors the TrainJob type, a full Update will silently drop that field.

I’m not sure how this would work with multikueue, but I don’t think we need to support that in our case.

I’m testing this approach now, but I’d be interested to hear if you can immediately spot any issues. If it works, would you be happy to accept a PR to have Kueue use patches?
