## Description


**What happened**:

`Describe("Job controller with CustomMetricLabels")` in `test/integration/singlecluster/controller/jobs/job/job_controller_test.go` starts a manager configured with two ClusterQueue custom labels, which rebuilds the shared metric vectors to `3 + 2 = 5` labels through `metrics.InitMetricVectors`. Its teardown only stops the manager:

```go
ginkgo.AfterEach(func() {
	gomega.Expect(util.DeleteNamespace(ctx, k8sClient, ns)).To(gomega.Succeed())
	fwk.StopManager(ctx)
})
```

There is no `metrics.InitMetricVectors(nil)`, so the widened vectors outlive the block. Every sibling custom-label suite does reset: `controller/core/custom_labels_test.go` resets in each `When`, and the pod/elastic custom-label suites reset in `AfterAll`.

A later spec that starts a manager with no custom labels does not reset them either, because `NewCustomLabels` returns early for an empty config and never touches the vectors:

```go
func NewCustomLabels(entries []configapi.ControllerMetricsCustomLabel) *CustomLabels {
	if !features.Enabled(features.CustomMetricLabels) || len(entries) == 0 {
		return nil
	}
	...
	InitMetricVectors(cl)
}
```

So when `Describe("Interacting with scheduler")` creates its ClusterQueue `"cq"` with a nil config, `AddClusterQueue` reports `PendingWorkloads` with the three fixed values against the still-five-label vector and panics the manager:

```
panic: inconsistent label cardinality: expected 5 label values but got 3 in []string{"cq", "active", "standalone"}
  sigs.k8s.io/kueue/pkg/metrics.ReportPendingWorkloads
  sigs.k8s.io/kueue/pkg/cache/queue.(*Manager).AddClusterQueue
```

It is order-dependent, so it stays latent until the specs are redistributed across the parallel processes. Adding a second custom-label suite to the same package makes it deterministic on `pull-kueue-test-integration-shard-2-main`.

**What you expected to happen**:

The block resets the shared vectors after itself, like every other custom-label suite, so no later spec inherits the widened cardinality.

**How to reproduce it (as minimally and precisely as possible)**:

The widen-without-reset is enough on its own:

```go
features.SetFeatureGateDuringTest(t, features.CustomMetricLabels, true)
cl := metrics.NewCustomLabels([]config.ControllerMetricsCustomLabel{{Name: "a"}, {Name: "b"}})
metrics.InitMetricVectors(cl) // PendingWorkloads now has 5 labels
metrics.PendingWorkloads.WithLabelValues("cq", "active", "standalone").Set(1) // panics: expected 5, got 3
```

`metrics.InitMetricVectors(nil)` afterwards makes the same call safe again.

**Anything else we need to know?**:

Same class as #12555 / #12881 (LocalQueue custom labels) and the sequential-isolation move in #13294. This one is the missing reset in the Job suite's block.
