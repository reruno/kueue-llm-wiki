## Description

## Summary

Gate the rejection of the reserved resource name `pods` behind a new alpha feature gate that defaults to disabled on the `release-0.18` and `release-0.19` branches.

Keep the rejection unconditional on `main`.

## Rationale

Before the cherry-pick in #14756, the following configurations are valid on these release branches:

- A resource transformation with `multiplyBy: pods`.
- A resource transformation with `input: pods`.
- A resource transformation with `outputs: {pods: 1}`.
- A DRA device-class mapping with `deviceClassMappings[].name: pods`.

After the change, validation rejects these configurations. Validation failure calls `os.Exit`, so an upgrade from a 0.18.z or 0.19.z release can cause `kueue-controller-manager` to crashloop. The DRA device-class mapping case is active by default because `KueueDRAIntegration` defaults to enabled since 0.18.

## Required changes

- Add an alpha feature gate for this validation behavior on `release-0.18` and `release-0.19`.
- Default the feature gate to disabled.
- Apply the validation only when the feature gate is enabled on these release branches.
- Keep the validation unconditional on `main`.
- Document the upgrade behavior and feature-gate setting.

## Acceptance criteria

- Existing affected configuration does not prevent `kueue-controller-manager` from starting after a 0.18.z or 0.19.z upgrade when the new feature gate remains disabled.
- Administrators can enable the feature gate to reject reserved `pods` usage.
- The `main` branch continues to reject this configuration without a feature gate.

### Comment by [@thc1006](https://github.com/thc1006) — 2026-08-24T16:32:17Z

Thanks, I will carry on with the two branch PRs then.

On moving forward with `main`: there is a wrinkle I would like @sohankunkerkar to weigh in on, because it decides the shape of the `main` change.

The acceptance criteria here say `main` keeps refusing the name without a gate, which I agree with. The problem is the gate name itself. If `ReservedResourceNameValidation` exists only on `release-0.18` and `release-0.19`, an operator who follows the mitigation and sets it in `featureGates` or `--feature-gates` carries that setting into their 0.20 upgrade. `SetFromMap` and `Set` return `unrecognized feature gate` for a name that is not registered, and `cmd/kueue/main.go` exits on it:

```go
// cmd/kueue/main.go
if err := config.LoadAndValidateFeatureGates(featureGates, cfg.FeatureGates).ToAggregate(); err != nil {
	setupLog.Error(err, "conflicting feature gates detected")
	os.Exit(1)
}
```

That is the same crashlooping manager this issue exists to prevent, moved one release later and now triggered by the mitigation itself.

Two ways out that I can see:

1. Register the name on `main` as well, deprecated and defaulted on, so the refusal stays unconditional and the leftover setting is accepted with a warning instead of exiting. There is precedent for the shape: `TASReplaceNodeDueToNotReadyOverFixedTime` sits in `defaultVersionedFeatureGates` as `{Version: 0.19, Default: false, PreRelease: featuregate.Deprecated}` rather than being deleted.
2. Leave `main` alone and put an `ACTION REQUIRED` in both branch release notes telling operators to remove the setting before upgrading to 0.20.

I lean towards the first, since the second depends on every operator reading a release note for a flag they set months earlier, but the first does add a gate to `main` that the criteria above deliberately avoid. Happy to do either.
