## Description

### Problem

MultiKueue must observe a remote object's terminal status before the object disappears from the worker cluster. If an integration propagates a TTL, self-deletion, or cleanup policy to the remote object, the worker-side controller might delete the object before MultiKueue synchronizes its terminal status back to the manager cluster. MultiKueue can then treat the missing remote object as needing dispatch again.

Batch Jobs demonstrated this with `spec.ttlSecondsAfterFinished`; PR #14734 stops propagating that field to newly created remote Jobs.

This issue tracks whether any other MultiKueue integration has an equivalent lifecycle or self-cleanup policy that can cause the same problem. It follows up on [this review comment](https://github.com/kubernetes-sigs/kueue/pull/14734#issuecomment-5394592197).

### Investigation checklist

For each integration:

1. Identify TTL, self-deletion, garbage-collection, or cleanup-policy fields and controller behavior.
2. Determine whether MultiKueue copies those settings to the remote object.
3. Verify whether the remote object can disappear before its terminal status is synchronized to the manager.
4. If affected, define the desired manager/worker ownership semantics and add regression coverage.

#### Kubernetes and workload APIs

- [x] Batch Job — `spec.ttlSecondsAfterFinished` addressed by #14734
- [x] Pod — no TTL or self-deletion field was found; `activeDeadlineSeconds` terminates execution but does not delete the Pod object.
- [x] StatefulSet — no TTL or self-deletion field was found; its PVC retention policy affects PVCs rather than deleting the StatefulSet object.
- [ ] JobSet — `spec.ttlSecondsAfterFinished` causes the JobSet controller to delete the completed JobSet. MultiKueue currently deep-copies the spec to the remote JobSet, so this has the same risk as Batch Job. (https://github.com/kubernetes-sigs/kueue/pull/14734#issuecomment-5399089985, thanks @kannon92)
- [ ] AppWrapper — no self-deletion policy was found on the AppWrapper itself. An embedded component can still define its own cleanup policy, but that does not directly delete the AppWrapper CR. (AI, pending verification)
- [ ] LeaderWorkerSet — no TTL or self-deletion policy was found on the LeaderWorkerSet itself; observed cleanup behavior targets child resources. (AI, pending verification)

#### Kubeflow and training integrations

- [ ] MPIJob — `runPolicy.ttlSecondsAfterFinished` is copied to the child launcher Kubernetes Job, rather than deleting the MPIJob CR itself. This does not appear to cause the exact missing-remote-object redispatch behavior, although early child cleanup may need separate status-sync validation. (AI, pending verification)
- [ ] PyTorchJob — shared `runPolicy.ttlSecondsAfterFinished` cleanup deletes the PyTorchJob CR, and MultiKueue currently deep-copies this field to the remote object. Potentially affected. (AI, pending verification)
- [ ] TFJob — shared `runPolicy.ttlSecondsAfterFinished` cleanup deletes the TFJob CR, and MultiKueue currently deep-copies this field to the remote object. Potentially affected. (AI, pending verification)
- [ ] XGBoostJob — shared `runPolicy.ttlSecondsAfterFinished` cleanup deletes the XGBoostJob CR, and MultiKueue currently deep-copies this field to the remote object. Potentially affected. (AI, pending verification)
- [ ] PaddleJob — shared `runPolicy.ttlSecondsAfterFinished` cleanup deletes the PaddleJob CR, and MultiKueue currently deep-copies this field to the remote object. Potentially affected. (AI, pending verification)
- [ ] JAXJob — shared `runPolicy.ttlSecondsAfterFinished` cleanup deletes the JAXJob CR, and MultiKueue currently deep-copies this field to the remote object. Potentially affected. (AI, pending verification)
- [ ] TrainJob — no TTL or self-deletion field was found on the TrainJob spec. Its generated runtime resources may independently use Job or JobSet cleanup policies, but those do not directly delete the TrainJob CR. (AI, pending verification)

#### Ray integrations

- [ ] RayJob — `DeletionStrategy` supports `DeleteSelf` through legacy `onSuccess`/`onFailure` policies and `deletionRules`. The KubeRay controller deletes the RayJob CR when this policy executes, while MultiKueue currently deep-copies the strategy to the remote RayJob. Affected.
- [x] RayCluster — no self-deletion behavior
- [x] RayService — no self-deletion behavior

### Completion criteria

- Every integration above has a documented investigation result.
- Affected integrations have follow-up issues or PRs linked from this checklist.
- Regression coverage verifies that terminal status reaches the manager before worker-side cleanup can remove the remote object.
