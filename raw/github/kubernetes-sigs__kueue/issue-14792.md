## Description

**What happened**:
An elastic Workload initially admitted on a GPU ResourceFlavor can switch to a CPU ResourceFlavor after all of its Pods become reclaimable and the Workload is evicted and re-admitted.

The reproducer has one PodSet with `count: 1` requesting `cpu: 1` and `nvidia.com/gpu: 1`. Its ClusterQueue has two flavors, in this order:

- `on-demand`: CPU quota `100`, GPU quota `0`
- `gpu`: CPU quota `100`, GPU quota `8`

The first admission correctly uses `gpu` for both resources:

```text
assignments: [{
  "name":"main",
  "flavors":{"cpu":"gpu","nvidia.com/gpu":"gpu"},
  "resourceUsage":{"cpu":"1","nvidia.com/gpu":"1"},
  "count":1
}]
```

After the only Pod is marked reclaimable, the ClusterQueue is drained, the eviction is completed, and the ClusterQueue is resumed. Kueue re-admits the Workload at `count: 0`, but changes both assignments to the first flavor:

```text
assignments: [{
  "name":"main",
  "flavors":{"cpu":"on-demand","nvidia.com/gpu":"on-demand"},
  "resourceUsage":{"cpu":"0","nvidia.com/gpu":"0"},
  "count":0
}]
```

The `on-demand` flavor has zero GPU quota. Its node labels are then part of the persisted admission used by the elastic workload lifecycle. When the workload grows again, those labels can make the GPU Pod impossible to place.

**What you expected to happen**:

Re-admission at an outstanding count of zero should not persist a flavor assignment that cannot support the PodSet's non-zero per-Pod resource shape when the workload grows again.

I am not sure which behavior Kueue intends here. Preserving the previous flavor, evaluating zero-count flavor feasibility using the per-Pod shape, or deferring flavor assignment until the count becomes positive would all avoid the incompatible persisted admission.

**Anything else we need to know?**:

The apparent code path is:

1. `podSetsCountsAfterReclaim` subtracts the reclaimable count, leaving the PodSet with a current count of zero.
2. `totalRequestsFromPodSets` multiplies every per-Pod request by that count, producing zero CPU and GPU usage.
3. The flavor assigner still evaluates the managed resource keys and calls `findFlavorForPodSets`.
4. The first flavor passes the static label and taint checks. Its zero GPU quota is sufficient for the zero-valued GPU request, so it is persisted for `nvidia.com/gpu`.

This is close to the zero-resource edge cases in #8079 and #13932, but the failure is different: Kueue admits the Workload and persists a different flavor rather than rejecting it or entering a retry loop. It is also distinct from #14611, where the Pod Importer bypasses normal flavor feasibility checks; this reproducer goes through the scheduler and the initial positive-count admission is correct.

A configuration workaround is to put a mutually exclusive hardware label on CPU and GPU ResourceFlavors. For example, adding `accelerator=cpu` to the CPU flavor causes the test Pod's `accelerator=required` selector to reject that flavor, and the focused test passes. That avoids the bad assignment for this configuration, but it does not address zero-count re-admission when flavors differ on other label keys.

I can send the failing integration test and implementation as a pull request once the intended zero-count flavor semantics are settled. This issue was drafted with AI assistance, and I reviewed the report before filing.

### Comment by [@prash2512](https://github.com/prash2512) — 2026-09-10T22:45:15Z

I was able to reproduce this issue. 

**Note:** this issue is not limited to drain and evicted jobs alone as stated in the issue. Any elasticJob with count-0 parallelism and scaled up later can be assigned wrong resourceFlavor and stays poisoned.

Setup: two flavors, `on-demand` (`nvidia.com/gpu: 0`) listed **first** in the ClusterQueue, then `gpu` (`nvidia.com/gpu: 16`). Elastic Job requesting 1 GPU/pod. Kueue built from master; same on v0.19.2.

| path | result |
|---|---|
| create at `parallelism: 0` → patch to 2 | admitted on **on-demand**, scale-up slice never admitted |
| admit at 2 (correctly on `gpu`) → 0 → drain/undrain → patch to 2 | flips to **on-demand**, same terminal state |

The count-0 admission stamps `on-demand`'s `nodeLabels` into the **Job's pod template**, so the scale-up slice is rejected on node affinity rather than quota:

```
couldn't assign flavors to pod set main: flavor gpu doesn't match node affinity,
insufficient quota for nvidia.com/gpu in flavor on-demand, previously considered
podsets requests (0) + current podset request (2) > maximum capacity (0)
```

### Comment by [@prash2512](https://github.com/prash2512) — 2026-09-10T22:57:13Z

On the fix, of the four options:

| option | why not |
|---|---|
| retain the previous slice's flavor | nothing to inherit when the job is created at 0 replicas |
| defer assignment until count > 0 | a RayCluster head is `Count: 1` while a worker group is legitimately 0, so the object still unsuspends and the deferred group gets neither nodeSelector nor tolerations |
| don't admit a workload whose PodSets are all 0 | fixes it, but reverses `#13975`. Fine if that's up for revisiting, but it's a behaviour change rather than a bug fix |
| **per-pod feasibility check** | works for both paths |

So: when a PodSet's count is 0, ask whether the flavor could hold one pod rather than zero.
