## Description

**What would you like to be added**:
I would like a supported handoff between an external controller that chooses an elastic Job's target size and Kueue, which owns quota admission and the WorkloadSlice transition.

In our use case, an external controller reads ClusterQueue capacity and Workload admission state, chooses a target, and patches only `batch/v1.Job.spec.parallelism`. Kueue otherwise owns that lifecycle and may also patch `parallelism` during preemption.

This mostly works, but the controller has to infer whether a replacement, admission, or preemption is in flight and stop writing until Kueue settles. A `resourceVersion` precondition prevents concurrent writes from overwriting each other, but it does not provide an accepted, rejected, or in-progress resize state.

The scale-down sequence also creates a temporary accounting gap:

```text
Initial:
  Job parallelism=N
  Workload count=N
  non-terminal Pods=N

External controller patches:
  Job parallelism=N -> M

Current transition:
  Kueue lowers the Workload count and releases quota to M
  The Job controller asynchronously deletes N-M Pods

Temporary state:
  accounted quota=M
  non-terminal Pods>M
```

For scale-up, the inverse handoff is the concern. Patching `parallelism` starts a replacement-slice transition, but the external controller has no explicit result saying that the requested target is met/unmet/in-progress. Instead the state must be derived from the current and replacement Workloads, admission conditions, preemption state, and scheduling-gated Pods.

Would Kueue support an integration model where an external controller proposes the target size, while Kueue serializes the transition and exposes its result? The result would be a clear ownership boundary around applying that target.

**Why is this needed**:
During scale-down, another Workload can observe released quota while the old Pods still occupy the corresponding physical capacity. During scale-up or preemption, an external controller can avoid conflicting writes only by recognizing several intermediate WorkloadSlice states that are internal to Kueue.

The PartialScaleUp proposal #14310 looks complementary as it changes how much of a requested scale-up Kueue may admit, but it does not appear to define the external-controller handoff.
