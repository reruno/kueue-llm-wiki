## Description

### What happened

`kueue.x-k8s.io/role-hash` is client-settable, becomes the PodSet name, and PodSets are sorted by it. Flavor assignment is positional first-fit, so a client-chosen string decides flavor assignment and can decide the `RepresentativeMode`.

Chain, on `main` at `9a21d06`:

1. [`getRoleHash`](https://github.com/kubernetes-sigs/kueue/blob/9a21d069490c56832bee45b15263e6e980aee96a/pkg/controller/jobs/pod/pod_controller.go#L685-L690) returns the annotation verbatim when set, so the value is opaque to Kueue.
2. [`constructGroupPodSets`](https://github.com/kubernetes-sigs/kueue/blob/9a21d069490c56832bee45b15263e6e980aee96a/pkg/controller/jobs/pod/pod_controller.go#L834-L842) assigns it as `PodSet.Name` and sorts `resultPodSets` by that name.
3. `assignFlavors` iterates PodSets by index and accumulates `assumedUsage`, surfaced in [`fitsResourceQuota`](https://github.com/kubernetes-sigs/kueue/blob/9a21d069490c56832bee45b15263e6e980aee96a/pkg/scheduler/flavorassigner/flavorassigner.go#L1354) as `previously considered podsets requests (%s) + current podset request (%s) > maximum capacity (%s)`.

Two pod groups with identical PodSet shapes but different annotations sort differently, so they get different flavors, and under `FlavorFungibility` `TryNextFlavor` on a saturated CQ one can be `Fit` while the other is `NoFit`.

### Reproduce

ClusterQueue, one ResourceGroup, two flavors, no borrowing:

```yaml
- name: on-demand
  resources: [{name: "nvidia.com/gpu", nominalQuota: 4}]
- name: spot
  resources: [{name: "nvidia.com/gpu", nominalQuota: 2}]
```

`flavorFungibility: {whenCanBorrow: TryNextFlavor, whenCanPreempt: TryNextFlavor}`

Two pod groups, same `pod-group-total-count: 2`, same shapes, `leader` requests 1 GPU and `worker` requests 4 GPU. Only the annotations differ:

| group | leader role-hash | worker role-hash | sorted PodSets | result |
|---|---|---|---|---|
| A | `aaaa1111` | `ffff9999` | `[leader, worker]` | leader takes `on-demand` (4 to 3), worker needs 4, `on-demand` 3 and `spot` 2 both too small, **NoFit** |
| B | `ffff9999` | `aaaa1111` | `[worker, leader]` | worker takes `on-demand` (4 to 0), leader takes `spot`, **Fit** |

Group A stays pending with `insufficient quota for nvidia.com/gpu in flavor on-demand, previously considered podsets requests (1) + current podset request (4) > maximum capacity (4)`. Group B admits.

Omitting the annotation makes this deterministic: the webhook derives the name from `SpecShape`, so identical roles produce identical names and a stable order across Workloads.

### Why this is a bug

`PodSet.Name` is identity, not a scheduling input, but it selects the first-fit order. Two Workloads with the same scheduling shape get different verdicts, and nothing in the flavor assigner diagnostics points at sort order.

Scope: needs 2+ distinct role-hashes in one group, so multi-role integrations (Ray head plus workers, MPIJob, PyTorchJob, JobSet, LeaderWorkerSet) and pod groups that set the annotation per Workload.

Not fixed by #14784, which only removes the name from the equivalence hash. The shape stays positional.

### Possible directions

- Sort `resultPodSets` on a shape-derived key instead of `PodSet.Name`.
- Or document that `role-hash` must be a function of pod shape and validate it.
