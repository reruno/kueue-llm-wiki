### Comment by [@mszadkow](https://github.com/mszadkow) — 2026-08-26T17:00:50Z

@yaroslava-serdiuk 
[Scenario D of KEP](https://github.com/kubernetes-sigs/kueue/pull/14310/changes#diff-08831fa0dd775022f542799aef25b58b456f12555b94d47e4660326a6dc20aa0R311) shows that when PodSets are tied to independent resource flavors, the sequential `Phase-1` reduction can over-reduce a PodSet whose own flavor still had slack (e.g. fully draining ps2 even though rf2 was never the bottleneck), and only a separate restore pass fixes that. 
This restore pass is algorithmically distinct from `Phase 1` — it operates per-PodSet rather than over a single global scalar — and it isn't actually specific to the order-based strategy: the existing proportional reducer used by PartialAdmission could just as easily over-reduce a PodSet under the same multi-flavor conditions, yet has no restore step today.

Question: 
Should the `Phase 2` (optimization) be wired into both the existing proportional reducer and the new order-based one as a shared, strategy-agnostic post-processing step, or is it intended as a concern specific to order-based only — leaving the proportional/PartialAdmission path's existing behavior (no restore pass) untouched?

Why I ask: 
It decides how we structure the code. If `Phase 2` should apply to both reducers, we can build `PodSetReducer` as a shared, reusable struct — one binary-search skeleton with a pluggable "how to distribute the cut" strategy (proportional or order-based), plus a common restore step both can call. 
If Phase 2 is order-based only, we can write it as a fully separate, self-contained type, with no changes to the existing proportional reducer.
