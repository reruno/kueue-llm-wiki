## Description

**What happened**:

`kueuectl delete workload` resolves associated resources by API version, kind, and name, but drops the UID from the Workload owner reference before issuing the delete. If the original owner is deleted and another object is created with the same name, deleting the stale Workload can delete the replacement object.

**What you expected to happen**:

Deletion of an associated resource should be conditional on its UID still matching the Workload owner reference.

**How to reproduce it (as minimally and precisely as possible)**:

1. Create a Job managed by Kueue and record the generated Workload.
2. Delete the Job while retaining a stale copy of the Workload owner reference.
3. Create another Job with the same namespace and name but a different UID.
4. Run `kueuectl delete workload <workload-name> --yes`.
5. Observe that the replacement Job is deleted despite not owning the Workload.

**Anything else we need to know?**:

Kubernetes `DeleteOptions.Preconditions.UID` can prevent the name-reuse race.
