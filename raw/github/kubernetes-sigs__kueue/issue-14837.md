## Description

## Summary

MultiKueue `SyncJob` implementations can drop fields that are not modeled by the vendored API types.

The current pattern copies the remote job specification from `*localJob.Spec.DeepCopy()` and then creates the remote job. Kubernetes removes fields that the typed client does not model during decoding. The created remote job therefore does not contain those fields.

The merge-patch change in #14836 preserves unknown fields when Kueue updates an existing TrainJob. It cannot preserve fields that are already absent when MultiKueue creates the remote job.

## Required changes

Review the built-in MultiKueue job adapters that construct remote jobs from typed `Spec.DeepCopy()` results.

Define and implement a field-preservation approach for remote-job creation. The approach must preserve valid fields that exist in the source job specification but are unknown to Kueue's vendored API version.

Use the existing unstructured-spec-copy pattern, where applicable, as a reference. Keep the existing typed behavior for Kueue-managed fields.

## Rationale

New fields can be accepted and stored by a workload CRD before Kueue upgrades its vendored API dependency. MultiKueue must not silently omit those fields when it creates the corresponding remote job.

## Affected area

- MultiKueue `SyncJob` implementations in built-in job adapters.
- Remote job creation paths that copy typed job specifications.

## Acceptance criteria

- [ ] Remote-job creation preserves source `spec` fields that are not modeled by Kueue's vendored API types.
- [ ] The implementation does not regress Kueue-managed fields or existing MultiKueue synchronization behavior.
- [ ] Tests verify that an unmodeled source `spec` field is present on the created remote job.
- [ ] The implementation documents any adapter-specific limitations that cannot use the common approach.
