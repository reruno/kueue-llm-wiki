**What happened**:

`variantReconciler.Reconcile (pkg/controller/concurrentadmission/controller.go:209`) has an unimplemented
TODO:

```
go
// TODO: If ConcurrentAdmission is no longer enabled for this CQ, delete parent and variants.
```
`getFamilyAndClusterQueue` fetches the `ClusterQueue` but never checks whether `cq.Spec.ConcurrentAdmissionPolicy` is still non-nil before proceeding. If a user removes `concurrentAdmissionPolicy` from a `ClusterQueue` that still has parent/variant Workloads left from when the feature was enabled, the reconciler continues treating them as active — running `createVariants/deleteStaleVariants/syncVariantEvictionStatus` against a policy that no longer exists.

**What you expected to happen**:

When a Workload is a `ConcurrentAdmission` parent and its `ClusterQueue` no longer has `concurrentAdmissionPolicy` set, the reconciler should detect this and clean up rather than continuing to manage variants for a disabled feature.

**Design question for maintainers:**
Variants are already owned by their parent via `ctrl.SetControllerReference` (line 318), so deleting the parent Workload would cascade-delete all variants through normal Kubernetes garbage collection — no separate variant-deletion logic should be needed.

The open question is what "delete parent" should actually mean for the underlying Job: does the parent Workload get deleted outright (losing its current admission/quota reservation entirely, requiring the Job to be re-queued from scratch), or should it first be converted back into a normal, non-gated Workload so the Job doesn't lose admission just because the feature was toggled off?

**How to reproduce it (as minimally and precisely as possible)**:

1. Create a `ClusterQueue` with `concurrentAdmissionPolicy` set and admit a Workload that creates parent + variant Workloads.
2. Edit the `ClusterQueue` to remove concurrentAdmissionPolicy.
3. Observe: the parent/variant Workloads remain and continue being reconciled by `variantReconciler` as if the policy were still active.

### Comment by [@NasitSony](https://github.com/NasitSony) — 2026-08-31T19:24:33Z

Following up on the design question above — I traced the existing primitives in this file, and I think the safer/less-disruptive option (convert back to normal rather than delete outright) is also the one that needs the least new code, since it reuses machinery already used elsewhere here:

**Where the check goes:** right at the existing TODO (line 209), before `createVariants/deleteStaleVariants`/etc. run — those already assume `cq.Spec.ConcurrentAdmissionPolicy` and `cq.Spec.ResourceGroups[0]`.Flavors are meaningful, so the check needs to short-circuit before them.

**For variants:** reuse `deactivateVariant` (line 449) as-is on each one. It already deactivates (`Spec.Active = false`) and, once eviction is observed, clears admission via `clearWorkloadAdmission` — no new logic needed here.

**For the parent:** a different operation than variants, since `deactivateVariant/deactivateWl` would set `Spec.Active = false` and strand it permanently. Instead:

- Call `clearWorkloadAdmission` alone (unset quota reservation, mark `Requeued`) so it drops back to `Pending` and re-enters normal scheduling — without deactivating it.
- Remove `ConcurrentAdmissionParentLabelKey` from its labels (the same way `createVariants` already strips this label when copying the parent into a variant, line 370), so `IsParent()` returns false afterward and this reconciler stops touching it.

This keeps the underlying Job's chance at admission intact (nothing gets deleted), and only touches code paths that already exist and are already exercised elsewhere in this file. Happy to open a PR along these lines unless there's a reason to prefer outright deletion instead.
