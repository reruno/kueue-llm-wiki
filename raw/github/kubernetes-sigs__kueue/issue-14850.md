## Description

### What would you like to be added:

  An option to use the `LeastFreeCapacity` placement algorithm for PodSets that use `kueue.x-k8s.io/podset-required-topology`, rather than being forced onto `BestFit`.

  Ideally exposed as configuration (TAS algorithm selection per ResourceFlavor/Topology or in the Kueue Configuration API) rather than as a feature gate — i.e. the work described in #4570 and in the KEP's Stable graduation criteria ("introduce
  configuration for setting TAS profiles/algorithms").

  Today, per the algorithm-selection table in KEP-2724, `required` maps to `BestFit` under every remaining profile. The only way to get `LeastFreeCapacity` for `required` requests was the `TASProfileLeastFreeCapacity` gate, which was removed in v0.17 by
  #9298 (replaced by `TASProfileMixed`, which uses `LeastFreeCapacity` only for `unconstrained`).

  ### Why is this needed:

  `LeastFreeCapacity` optimizes for fragmentation, and that goal is orthogonal to the `required` constraint. The `required` annotation is a *feasibility* guarantee — the PodSet must fit entirely within one domain at the annotated level. It says nothing
  about *which* eligible domain should be chosen, or how pods should be spread over sub-domains inside it. So we can honor the required constraint and still minimize fragmentation.

  Example: topology levels are `rack` and `hostname`, with 20 hosts per rack, and a PodSet annotated `podset-required-topology: rack`.

  - **Choosing the rack:** `BestFit` starts from the rack with the most free capacity, so it breaks into an empty (or near-empty) rack while partially-used racks that could also host the workload stay partially used. `LeastFreeCapacity` picks the most-utilized rack that still fits, preserving whole free racks for future workloads that need an entire rack.
  - **Choosing hosts within the rack:** likewise, `LeastFreeCapacity` packs onto already-partially-used hosts, keeping whole hosts free, instead of spreading over the emptiest ones.

  Both effects reduce fragmentation without ever violating the required constraint - the candidate domains considered are exactly the same set either way.

  This is the same rationale the KEP already gives for making `LeastFreeCapacity` the default for `unconstrained` requests ("Kueue should prioritize minimizing fragmentation which is provided by the `LeastFreeCapacity` algorithm"). For clusters where most workloads carry a `required` annotation, `TASProfileMixed` leaves no way to apply it, and fragmentation accumulates.

  ### Completion requirements:

  - [ ] Design: where the algorithm choice lives (Configuration API, ResourceFlavor, Topology, or per-PodSet annotation) and its interaction with the existing `TASProfile*` gates and `TASBalancedPlacement`
  - [ ] API change
  - [ ] Docs update

## Discussion

### Comment by [@kavix](https://github.com/kavix) — 2026-08-28T09:05:43Z

This is a great proposal and aligns perfectly with the KEP-2724 graduation criteria to replace hardcoded TAS feature gates with actual configuration.

  Here is a high-level plan to implement this 
  1. API Addition: Introduce a setting to select the algorithm (BestFit or LeastFreeCapacity).
  (Should this live globally in the Kueue Configuration API, or more granularly in the Topology CRD?)

  2. Refactoring: Update pkg/cache/scheduler/tas_flavor_snapshot.go. Currently, useLeastFreeCapacityAlgorithm()
  forces BestFit unless the request is unconstrained. We'll update this to respect the new API configuration instead.

  3. Deprecation: Begin deprecating the TASProfileMixed feature gate since the new API supersedes it.
  4. Docs & Tests: Add integration tests for the new behavior and update the docs using the excellent rack/host
  fragmentation example provided in the description.

  Happy to open a PR for this once we decide on where the configuration should live!
