## Description

## What happened

When a node in an admitted Workload's `topologyAssignment` gets a taint the Workload does not tolerate, the TAS node controller terminates the Pods pinned to it (`PodTerminatedByKueue`; condition `TerminatedByKueue`, reason `UnschedulableOnAssignedNode`).

When those Pods are recreated, the ungater stamps them with the same `kubernetes.io/hostname` from the unchanged `topologyAssignment`. They cannot be scheduled, so they are terminated again. The assignment is never recomputed and the Workload is never evicted, so the loop ends only when the Pod owner stops recreating. This happens especially when another or previous pod of the workload is still making progress or not yet terminated, on the same node.

Observed: 21 replacement Pods for one Workload in about 5 minutes, each `Admitted` -> `FailedScheduling` -> `PodTerminatedByKueue`, with one admission for the whole window and no eviction.

## Expected

Kueue records the node in `Status.UnhealthyNodes` and either recomputes the assignment or evicts the Workload, instead of terminating replacements indefinitely against a stale assignment.

## Cause

`checkPodsOnNode` reports the Workload healthy whenever another Pod of the same Workload is still progressing on the node, even when the node has untolerated taints and unschedulable Pods are pinned to it. The healthy path then clears `Status.UnhealthyNodes`, which disables both `TASFailedNodeReplacementFailFast` and the ungater's unhealthy-node guard.

A `NoSchedule` taint does not evict Pods already bound to the node, so the progressing Pods never terminate and the loop has no exit.

## Second variant

The same symptom appeared on a single-Pod Workload whose Pod was already `Failed` before the first replacement, where the unhealthy path should have run. Possibly a separate bug.

## Repro

1. Enable TAS with `TASReplaceNodeOnNodeTaints` and `TASReplaceNodeOnPodTermination`.
2. Admit a multi-Pod Workload assigned to a single node.
3. With a Pod running on that node, add a `NoSchedule` taint the Workload does not tolerate.
4. Delete a Pod and let its owner recreate it.

The replacement is ungated back onto the tainted node and terminated, indefinitely.

## Suggested fix

Report the Workload unhealthy when the node has untolerated taints and Pods are pinned to it awaiting scheduling, before checking whether other Pods are progressing. Terminate the doomed Pods as today, but record the node so the replacement path can run.

Separately: the node controller's per-Workload health decision is only logged at V(3)/V(4), which makes this failure mode hard to diagnose in production.

## Previous related fix:
The previous #14099 fix stops gated Pods being ungated onto a node recorded in Status.UnhealthyNodes, but the guard never engages in the above case because checkPodsOnNode reports the Workload healthy and clears the node from that field.

## Environment

* Kueue v0.19.1
* Kubernetes: v1.35.6
* Integration: Pod groups
* Enabled: `TopologyAwareScheduling`, `TASFailedNodeReplacement`, `TASReplaceNodeOnPodTermination`, `TASReplaceNodeOnNodeTaints`
