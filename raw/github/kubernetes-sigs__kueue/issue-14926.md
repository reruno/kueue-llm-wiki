## Description

**What happened**:

`kueuectl create clusterqueue` validates whether resource groups overlap by joining each group's resource names with `.` and comparing the resulting strings with `strings.Contains`.

This makes validation order-dependent. For example, these quota arguments are accepted by client-side validation even though `cpu` appears in both resource groups:

```text
--nominal-quota alpha:cpu=1
--nominal-quota beta:cpu=1;memory=1
```

The generated ClusterQueue is rejected later by the validating webhook. With `--dry-run=client`, kueuectl prints an invalid manifest. The string comparison can also reject distinct resource names when one serialized group happens to be a substring of another.

**What you expected to happen**:

Resource-group overlap validation should compare exact resource names, reject intersections regardless of argument order, and allow distinct resource names regardless of substrings in their spelling.

**How to reproduce it (as minimally and precisely as possible)**:

Run:

```text
kueuectl create clusterqueue test \
  --nominal-quota alpha:cpu=1 \
  --nominal-quota 'beta:cpu=1;memory=1' \
  --dry-run=client -o yaml
```

Observe that kueuectl emits a ClusterQueue containing `cpu` in two resource groups instead of returning `invalid resource group`. Reversing the two quota arguments returns the error, demonstrating that the result depends on input order.

**Anything else we need to know?**:

The relevant code is `isResourceGroupValid` in `cmd/kueuectl/app/create/create_clusterqueue.go`. The webhook already performs exact duplicate-resource validation using a set, so the CLI can use the same semantics. A focused table-driven unit test can cover both argument orders and similarly named but distinct resources; no cluster is required.
