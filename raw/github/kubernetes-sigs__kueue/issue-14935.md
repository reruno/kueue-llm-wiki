## Description

### What happened

With the `pod` integration under MultiKueue, a dispatched plain Pod never ran. Its manager-side Workload went `QuotaReserved` → `Admitted` → `Finished`, and the Pod was left `Pending` **with its Kueue scheduling gates still attached**, forever:

```
schedulingGates: [kueue.x-k8s.io/admission, kueue.x-k8s.io/topology]
```

Manager Workload conditions:

```
QuotaReserved  True   QuotaReserved   Quota reserved in ClusterQueue <cq>
Admitted       True   Admitted        The workload is admitted
Finished       True   OwnerNotFound   The workload's owner no longer exists
admissionChecks: [{multikueue, Ready, "The workload got reservation on \"<worker>\""}]
```

The `OwnerNotFound` verdict is wrong: the owner Pod existed at that moment and still existed days later, and the Workload's `ownerReferences[0].uid` still matched that live Pod's UID exactly.

### Worker-side origin, and the race

Two reconcilers on the **worker** collide on the same Pod, 11 ms apart (offsets from the worker's first reconcile of the mirrored Pod):

```
T+0ms    v1_pod               Reconciling Job                 <- remote Pod exists
T+40ms   v1_pod               Job admitted, unsuspending      <- starts removing the gates
T+51ms   workload-reconciler  Workload is orphaned, finishing to release quota
T+149ms  v1_pod               Unsuspending job  ERROR:
         Operation cannot be fulfilled on pods "<pod>": the object has been modified;
         please apply your changes to the latest version and try again
T+267ms  events               Workload '<ns>/<wl>' is declared finished   (x4)
T+9.0s   workload-reconciler  Workload delete event
```

The workload reconciler resolves the owner while the Pod reconciler is mid-patch on that very Pod, decides it is orphaned, and finishes the Workload. The ungate patch then loses on a resource-version conflict, and by the time it retries the Workload is `Finished`, so the retry is a no-op. The gates are never removed.

### Manager-side consequence

The MultiKueue workload sync copies the remote `Finished` condition onto the local Workload verbatim, so a worker-side sync failure is treated as a job completion:

- **Terminal.** The local Workload is `Finished`, so it is never re-dispatched and never fails.
- **Unschedulable.** Ungating only happens for an admitted, non-finished Workload, so the manager Pod keeps both gates permanently. Anything awaiting the Pod hangs indefinitely.
- **Silent.** No event or condition on the manager explains that this was a sync failure rather than a completion.

Quota is correctly released, so this is not a quota leak — the cost is a permanently stranded Pod.

### Why #13047 does not cover it

This is the same shape as #13046, fixed by #13047 (milestone v0.19), but that fix is guarded on the reason:

```go
if remoteFinishedCond.Reason == kueue.WorkloadFinishedReasonOutOfSync && !group.IsElasticWorkload() {
```

`OwnerNotFound` therefore still falls through to the verbatim Finish. It is equally a sync failure rather than a completion, and arguably any remote finish reason that is *not* a genuine job outcome should reset the admission check to `Retry` rather than finishing the local Workload. Possibly related: #14736.

### Expected

A remote `OwnerNotFound` finish should not finish the manager Workload; it should reset for re-dispatch (as #13047 does for `OutOfSync`), or at minimum surface a warning event and leave the Workload eligible for re-dispatch instead of silently stranding a gated Pod.

### Environment

- Kueue **v0.17.1**, same version on manager and workers
- `pod` integration, single plain Pods (not pod groups), created by a controller of ours; MultiKueue with two worker clusters; Topology Aware Scheduling enabled (hence the second gate)
- Observed twice in ~11 days on one worker; roughly 0.5% of dispatches. Rare and timing-dependent, so I don't have a deterministic reproducer — the 11 ms gap between `Job admitted, unsuspending` and `Workload is orphaned` suggests the owner lookup racing the ungate patch.
