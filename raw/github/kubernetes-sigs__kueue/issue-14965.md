## What happened

A Workload rejected at admission for exceeding a LimitRange `max` stays
inadmissible forever after an administrator raises that `max` (or deletes the
LimitRange), until an unrelated cluster event happens to requeue the whole
ClusterQueue.

The wake-up chain exists but its last link never fires:

1. The scheduler rejects the Workload via `workload.ValidateAdmissibility` →
   `ValidateLimitRange` (`pkg/scheduler/scheduler.go:705`) with
   `"resources didn't satisfy LimitRange constraints"`. The requeue reason is
   left at `RequeueReasonGeneric`, so under BestEffortFIFO the Workload is
   parked in `inadmissibleWorkloads`.
2. The workload controller does watch LimitRange
   (`pkg/controller/core/workload_controller.go:1612`); on any event it lists
   the namespace's pending Workloads, recomputes them with
   `workload.AdjustResources`, and calls `AddOrUpdateWorkload`
   (`workload_controller.go:1703-1736`).
3. `AdjustResources` → `handlePodLimitRange` (`pkg/workload/resources.go:76-113`)
   only consumes `Default`/`DefaultRequest`. It never reads `Max`/`Min`, so a
   constraint-only change recomputes a byte-identical spec.
4. `PushOrUpdate` (`pkg/cache/queue/cluster_queue.go:393-412`) sees an
   unchanged spec on a parked Workload and returns it to
   `inadmissibleWorkloads` without waking it.

A `defaultRequest` change does alter the adjusted spec and wakes the Workload
(the asymmetry is covered by the existing "LimitRanges are defined and change"
integration spec), which suggests the constraint case was an oversight rather
than a design choice.

Deletion of the LimitRange sometimes appears to work, but only by accident:
while the LimitRange exists, `mergeResourceList` materializes empty
`ResourceList{}` maps onto containers that had `nil` (`pkg/util/resource/resource.go:31-34`),
and after deletion the recomputed spec keeps `nil`, so the spurious
nil-vs-empty diff defeats the `PushOrUpdate` guard. A Workload whose
containers set explicit limits gets no such diff and stays stuck even after
the LimitRange is deleted.

## Reproduction

Three integration specs on current `main` (`9c85f631f`), BestEffortFIFO,
ClusterQueue quota 10 CPU, container LimitRange with `max: cpu=2`, Workload
requesting `cpu=3`:

- Raise `max` to 8 → the Workload is never admitted (fails).
- Delete the LimitRange, Workload with requests only → admitted, but only via
  the nil-vs-empty-map accident above.
- Delete the LimitRange, Workload with explicit limits → never admitted (fails).

I can share the specs in a PR.

## Expected

Raising `max` (or lowering `min`, or deleting the LimitRange) requeues the
pending Workloads of that namespace so they are re-evaluated, the same way a
`defaultRequest` change already does.

## Suggested fix

On a LimitRange event whose constraint fields changed (or on deletion), requeue
the namespace's pending Workloads unconditionally — e.g. route them through
`QueueInadmissibleWorkloads` for their ClusterQueues instead of relying on the
spec-diff guard in `PushOrUpdate`. The occasional extra scheduling cycle seems
acceptable against Workloads being stuck indefinitely.

StrictFIFO is unaffected (`RequeueReasonGeneric` requeues immediately there,
`pkg/cache/queue/cluster_queue.go:836-848`).

### Comment by [@tomsen02](https://github.com/tomsen02) — 2026-09-01T07:07:23Z

@mimowo Yes, related — #14965 actually hands your point 1 a fresh exhibit.
The only reason a LimitRange *deletion* sometimes wakes pending workloads
today is an AdjustResources artifact: while the LimitRange exists,
`mergeResourceList` materializes empty `ResourceList{}` maps onto containers
that had `nil`; once it is deleted the recomputed spec keeps `nil`, and that
spurious nil-vs-empty diff is what defeats the `PushOrUpdate` "spec unchanged"
guard. A wake-up that only works by accident of spec mutation is exactly the
kind of behavior your refactor would eliminate.

That said, I don't think the refactor alone can close #14965, and it would in
fact make it slightly worse: `max`/`min` are only consumed at admission time by
`ValidateAdmissibility` and never leave a trace in the effective resources —
wherever those are stored, a constraint-only change produces nothing to diff.
And once the accidental nil-vs-empty wake-up is gone, no LimitRange relaxation
would ever requeue anything. So the missing piece is an explicit signal, the
same shape as the ResourceFlavor scheduling-fields requeue: on a LimitRange
constraint-field change (or deletion), retry the inadmissible workloads of the
affected ClusterQueues. I'm preparing a PR along those lines with the three
integration specs from the issue — it doesn't touch the AdjustResources path,
so it should compose cleanly with your refactor and remain the single wake-up
source after it lands.
