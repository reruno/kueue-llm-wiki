## Description

Follow-up to: #14794
Required for: #13702

**What would you like to be cleaned**:
kueue.WorkloadAnnotation should be populated for all Pods created by jobs managed by Kueue.

As part of this task we need to:
- [ ] Create a test verifying if the annotation is populated for all Pods created by any job at the time of being passed to the SchedulerSimulator (TrackPod).
- [ ] Fix the logic populating the annotation for failing test cases.

**Why is this needed**:
To ensure WAS Simulator can map the Pods to workloads representing them. This in turn is needed to allow time-efficient identification of pods to be preempted in the WAS Snapshot Simulator when simulating a workload preemption.

### Comment by [@NasitSony](https://github.com/NasitSony) — 2026-11-04T21:35:41Z

Bumping this — the open question is still whether the cross-job-type test should be integration or unit level.

One thing that's become relevant since: #18192 describes a case where the annotation is present but points at the wrong workload. When ConcurrentAdmission is enabled, pods are stamped with the parent's name (the Variant never goes through `startJob`, so `getPodSetsInfoFromStatus` only ever sees the parent), while the scheduler cache and preemption operate on Variant keys. I verified both halves of that on the issue.

So "the annotation is populated" and "the simulator can map the pod to the workload it needs" aren't the same property. If the goal here is the latter — and the issue says it's to let WAS map pods to the workloads representing them — then a test asserting presence at `TrackPod` wouldn't catch the ConcurrentAdmission case.

Worth deciding whether this task should assert presence, or assert that the annotation resolves to the workload the simulator is reasoning about. The second is a stronger guarantee and would have caught #18192.
