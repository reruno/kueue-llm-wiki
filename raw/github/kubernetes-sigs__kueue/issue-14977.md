## Description

<!-- Please only use this template for submitting enhancement requests -->

**What would you like to be added**:

A DRA capacity provider for DQO (#12382): a controller that derives `(ResourceFlavor, resource)` capacity from `ResourceSlice` objects and publishes it as a `CapacityProvider`, so GPU quota can track the devices actually present in the cluster.

**Why is this needed**:

Today an admin sets GPU quota by hand and keeps it in sync with the device pool. DQO gives us the distribution half; this is the discovery half for DRA.

Filing separately from #10270 because that one is specifically about node selectors and node allocatable. A DRA provider is a different derivation: it reads `ResourceSlice` objects, applies `deviceClassMappings`, and produces a different unit depending on whether the mapping is device-count, counter-based, or consumable capacity. Bundling them would be one KEP doing two unrelated things.

Some notes so the design starts from the right place:

- The quota resource name and unit for a `DeviceClass` already live in `pkg/dra/mapper.go`, which Kueue populates from `deviceClassMappings` for the workload side. Capacity and consumption have to be denominated identically or quota is wrong in a way nobody can see, so the provider should share that mapper rather than re-derive it from a copy of the config.
- Only one of `devices` and `sharedCounters` can be set on a `ResourceSlice`, so a counter dimension and a device dimension must not be summed across both.
- `ResourceSlice` objects describe total capacity, not fr wants; usage is tracked separately.

### Comment by [@NasitSony](https://github.com/NasitSony) — 2026-09-02T21:00:02Z

Read through the merged `CapacityProvider` type (#14557) and `pkg/dra/mapper.go` to get a feel for how this would fit together.

The `CapacityProvider` shape seems to fit well: `spec.controllerName` matches the standard Kubernetes controller-ownership pattern (like `IngressClass`), so a DRA-specific controller would watch for `CapacityProvider` objects naming it and publish into `status.capacity.flavors[].resources` for whichever flavors it's assigned via `orchestratedFlavors. spec.parameters` looks like the natural place for DRA-specific config (e.g., which `deviceClassMappings` or `ResourceSlice` selection criteria apply).

One concrete implementation question worth resolving early, since it affects how cleanly the "share the mapper" goal (from the issue description) can actually be achieved: `pkg/dra.ResourceMapper`'s public surface (`Lookup`, `CounterBasedResourceNames`, `CapacityBasedResourceNames`, `PopulateFromConfiguration`) tells you which logical resource name and which dimension (counter vs. capacity) a `DeviceClass` maps to, but the actual `deviceSelector/counterName` details needed to match devices within a real `ResourceSlice` against that class live in unexported structs (`deviceClassCounterConfig`, `deviceClassCapacityConfig`) only usable within `pkg/dra` itself. So a capacity provider living in a different package would either need the mapper's public API extended with something like a `SelectorsForDeviceClass(dc)`-shaped method, or would need to live inside `pkg/dra` itself to get direct access — otherwise it'd end up re-deriving selector logic from a copy of the config, which is exactly what the issue says to avoid.

Happy to dig further into whichever direction seems right, though given the design-doc requirement I expect this needs alignment first — let me know if a rough sketch of the mapper API extension would be useful to see written out.

### Comment by [@sohankunkerkar](https://github.com/sohankunkerkar) — 2026-10-28T19:51:12Z

Ok, I spent some time understanding how this would fit with DQO and DRA, so sharing where I landed. The provider itself is simple: read the `ResourceSlice` objects, publish "flavor X has N GPUs" in a `CapacityProvider`, and let DQO split it across the ClusterQueues. What needs discussion is which flavor a device belongs to, and what we actually count.

Here's a small example. The `a100` flavor has two nodes with 8 GPUs each. The `h100` flavor has one node with 8 GPUs, and one of them is split with MIG, so the driver lists it as 4 devices. There's also a fabric pool: 2 GPUs that aren't in any node, and any node can attach them over the network.

```
   flavor a100                    flavor h100
 ┌────────────┐ ┌────────────┐   ┌───────────────────────────┐
 │ a1: 8 GPU  │ │ a2: 8 GPU  │   │ h1: 7 GPU + 1 MIG GPU     │
 └─────┬──────┘ └─────┬──────┘   │     (listed as 4 devices) │
       │              │          └─────────────┬─────────────┘
       └──────────────┴────────┬───────────────┘
                               │ any node can attach
                     ┌─────────┴─────────┐
                     │ fabric: 2 GPU     │
                     └───────────────────┘

 real GPUs:            16 + 8 + 2              = 26
 naive count:  a100 = 16 + 2 fabric            = 18
               h100 =  7 + 4 MIG + 2 fabric    = 13   → 31
```

So if we just count the devices each flavor's nodes can reach, we get 31 instead of 26. The MIG GPU counts as 4 instead of 1. And both flavors can reach the 2 fabric GPUs, so both count them. DQO doesn't check for overlap, so it would hand out quota for 5 GPUs that don't exist.

What I have in mind for alpha is to follow what KEP-10270 (#16088) does for nodes. A device belongs to a flavor only through its node's labels, since that's where Kueue puts the pods anyway. If a node matches two orchestrated flavors, the provider goes `Misconfigured`. Devices that aren't tied to one node, like the fabric GPUs, we skip and report in the condition, rather than fail the whole provider. And we count in the same unit `deviceClassMappings` already uses on the workload side, so capacity matches usage. With a counter-based mapping, each physical GPU counts once, MIG or not. With that, the example comes out to 16 for `a100` and 8 for `h100`, and the 2 fabric GPUs show up as skipped.

@PannagaRao what do you think, does this work as a base for the design? I'd also like to see where the overlap discussion on #16088 lands before we lock this in.
