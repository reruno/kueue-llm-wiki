## Description

## Summary

Expose feature-gate enablement through a metric or another observable mechanism.

## Rationale

Operators need to determine whether feature gates are enabled. This should work consistently for all feature gates. It should not add feature-specific admission behavior for `DisableWaitForPodsReady`.

The discussion started during the Workload-level `WaitForPodsReady` KEP review. When an administrator enables `DisableWaitForPodsReady` as an incident escape hatch, workloads that set a pods-ready timeout should continue admission using the existing fallback behavior. Observability of gate usage should be addressed separately.

## Affected areas

- Feature-gate configuration and observability code.
- Metrics documentation and tests.
- `DisableWaitForPodsReady` and other Kueue feature gates.

## Acceptance criteria

- Operators can observe the enabled or disabled state of Kueue feature gates.
- The mechanism covers feature gates consistently and does not special-case `DisableWaitForPodsReady`.
- Metrics documentation and tests describe and validate the behavior.
