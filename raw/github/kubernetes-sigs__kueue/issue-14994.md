**What would you like to be added**:

Scheduler performance tests for DRA as a new config in https://github.com/kubernetes-sigs/kueue/tree/main/test/performance/scheduler/configs.

**Why is this needed**:

Such tests proven to be very useful for Kueue TAS. They allow to track regressions, but more importantly to easily generate pprof charts before / after a change. They use API server with key controllers so they allow to test performance in a more realistic setup than unit tests.

### Comment by [@sohankunkerkar](https://github.com/sohankunkerkar) — 2026-09-01T20:18:38Z

Yeah, quota-only wouldn't show much as DRA resources get preprocessed once in the workload controller and attached to the Info, so by the time the scheduler sees the workload it's just a PodSet with a logical resource name going through the normal flavor assignment. Same path as any extended resource.

IIUC, the DRA cost is in the workload controller (ResourceSlice listing, CEL evaluation, device matching). minimalkueue does start those controllers via core.SetupControllers, but it builds them with an empty Configuration and no DRA mapper, so exercising that path would mean wiring the mapper and ResourceSlice availability into the harness first.

### Comment by [@mimowo](https://github.com/mimowo) — 2026-09-01T20:32:30Z

i see, in that case I agree it does not make much sense to do the perf tests. The intention of the current framework is to test scheduler, and this is no different for DRA and regular quota-only.

We may get a little bit of signal for quota only DRA when other controllers are considered, but for that kwok will be a better fit.

So the rule of the thumb for performane testing:
1. use the current framework for benchmarking scheduling (quota only and tas is already) covered
2. use the coming kwok tests (still maturing) for benchamarking scenarios involving wiring complex set of controllers

So I think based on that rule we can close the currently open issue or re-purpose for TAS+DRA or TAS +WAS.
