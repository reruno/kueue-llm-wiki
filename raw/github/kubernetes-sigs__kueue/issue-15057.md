## Description

<!-- Please only use this template for submitting enhancement requests -->

**What would you like to be added**:

Add TAS support for LWS's affinity and anti-affinity config

**Why is this needed**:

Currently TAS only support affinity-like topology placement but not anti-affinity placement. Anti-affinity is crucial for serve workload HA.

**Completion requirements**:

For LWS, if we put the below annotation:

```
leaderworkerset.sigs.k8s.io/exclusive-topology: kubernetes.io/hostname
```

The pod generated by LWS will have these labels and affinity/anti-affinity settings, which means all pods within one replica should stick together (in the same node), and all different replicas are spread out to different nodes.

```
#labels
    leaderworkerset.sigs.k8s.io/group-index: "0"
    leaderworkerset.sigs.k8s.io/group-key: c8f058e7ff29f9bca86fac6bac4f3fdd602e1768
    leaderworkerset.sigs.k8s.io/template-revision-hash: 5d76c979b
    leaderworkerset.sigs.k8s.io/worker-index: "0"
```

```
  affinity:
    podAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchExpressions:
          - key: leaderworkerset.sigs.k8s.io/group-key
            operator: In
            values:
            - c8f058e7ff29f9bca86fac6bac4f3fdd602e1768
        topologyKey: kubernetes.io/hostname
    podAntiAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchExpressions:
          - key: leaderworkerset.sigs.k8s.io/group-key
            operator: Exists
          - key: leaderworkerset.sigs.k8s.io/group-key
            operator: NotIn
            values:
            - c8f058e7ff29f9bca86fac6bac4f3fdd602e1768
        topologyKey: kubernetes.io/hostname
```

However, if the workload goes through TAS, even with unconstraint TAS policy, TAS will select the node and add the `nodeSelector` to the pod template. This will limit the pod's node candidates to only one node, which violate the anti-affinity rule, resulting in the pods pending forever.

In order to support serve HA, we should make TAS support this use case. Maybe this can be generalized to other k8s resources as well, like statefulset and deployment with affinity and anti-affinity.  


This enhancement requires the following artifacts:

- [ ] Design doc
- [ ] API change
- [ ] Docs update

The artifacts should be linked in subsequent comments.

### Comment by [@NasitSony](https://github.com/NasitSony) — 2026-09-02T23:46:36Z

Traced the write site — `podset.go:226-227` sets `spec.NodeSelector` directly from TAS's computed domain assignment, pinning the pod to one specific node. TAS's domain-selection algorithm (`tas_flavor_snapshot.go`'s `sortedDomains`/topology-tree capacity accounting) has no visibility into `podAntiAffinity` at all — it picks nodes purely on topology capacity, so it can legitimately assign a node that's already occupied by another replica's pod, directly conflicting with the anti-affinity rule LWS itself set. Two independent scheduling primitives, neither aware of the other, and the pod becomes permanently unschedulable when they disagree.

One design question worth raising: TAS already has a mechanism for excluding some nodes from consideration (e.g. unhealthy-node exclusion, `deleteDomain` in the replacement-assignment path). Would extending that same exclusion concept to also account for "nodes already claimed by an anti-affinity-conflicting pod from this workload's other PodSets" be a viable direction, or does that require something structurally different, given it's cross-PodSet (excluding based on sibling pods' placements, not node health)? That distinction seems like it'd meaningfully affect scope.

Agreed this seems bigger than just LWS — any workload type using standard K8s anti-affinity alongside TAS unconstrained placement would hit the same conflict.
