## Description

<!-- Please only use this template for submitting clean up requests -->

**What would you like to be cleaned**:

`LocalQueue` currently exposes admitted and reserved usage as `corev1.ResourceList`, even though the cache keeps the underlying usage in Kueue's internal resource types.

It would be cleaner to keep the LocalQueue accounting path in the internal resource representation and convert at the API boundary. Changing only `GetAdmittedUsage` or `GetReservedUsage` would mostly move the conversion, since the AFS decay and usage ledger currently use `ResourceList` as well.

One design point is how to represent decayed history. AFS applies fractional decay, while the existing internal request representation is integer-valued, so this is more than a mechanical type replacement.

Follow-up from https://github.com/kubernetes-sigs/kueue/pull/15000#discussion_r3912916322.

**Why is this needed**:

This would avoid repeated flattening and formatting in the accounting path and make resource representation more consistent within the scheduler cache.

Traced this — confirmed the tension is real, not just surface-level. `GetAdmittedUsage` (`localqueue.go:49`) does store internally as `resources.FlavorResourceQuantities` (a `map[FlavorResource]Amount`), converting to `corev1.ResourceList` only at the very end via `.FlattenFlavors().ToResourceList(...)`. But `resources.Amount` is a hard `int64` (explicitly documented: "Keep usage values... as int64"), while `CalculateDecayedConsumed` (`admission_fair_sharing.go:108`) computes decayed usage via float64-driven exponential half-life decay on `corev1.ResourceList` — genuinely fractional output, not just an integer type that happens to be formatted as a `Quantity`.

So this seems like two related but distinct questions: (1) moving `GetAdmittedUsage/GetReservedUsage` themselves onto the internal type — straightforward, since the underlying storage already is that type; and (2) what AFS decay's fractional values should do once they need to interact with that same internal representation — extend `Amount` with a fractional variant (bigger, more invasive change touching quota-comparison semantics elsewhere), or keep AFS decay deliberately on `float64/ResourceList` as a separate "soft fairness signal" representation distinct from "hard quota consumption," only converging at whatever boundary actually needs both. The second question feels like the one that actually needs design alignment; the first seems close to mechanical.

Happy to help however's useful once there's a direction on (2).

**The plan**

Thanks @NasitSony for splitting this into (1) moving the getters onto the internal type and (2) what to do with the fractional decayed values — I agree (2) is the one that needs alignment first. Reading your two options, the axis seems to be "one representation or two", and I lean toward your second: keep the soft fairness signal and the hard quota consumption separate, converging only where something actually needs both. The one thing I'd like to discuss is what carries the soft signal — would moving it from `ResourceList` to an AFS-internal decimal type still fit what you had in mind?

I ask because I'm not sure I've read your second option correctly: did you mean the principle of keeping the two representations separate, or literally keeping AFS on `ResourceList`? The issue notes that moving only the getters "would mostly move the conversion", so my guess is that the "repeated flattening and formatting in the accounting path" refers to `ResourceList` in the ledger — but that's only my reading, and I'd like to hear your view on it.

On extending `Amount`: you mentioned it would touch quota-comparison semantics, and that matches what I found — the cost is fairly concrete. Switching its unit to 10⁻⁹ would drop the `int64` fast path from 9.2×10¹⁸ units to 9.2×10⁹ (memory above ~8.6 GiB would keep taking the `big.Int` path), and adding a scale field would make `Add`/`Sub`/`Cmp`/`Equal` scale-aware. AFS needs neither, but quota comparisons would carry both, so I'd rather leave it alone.

Concretely, what I have in mind is an AFS-internal type (working name `Decimal`) holding an integer count of 10⁻⁹ base units, structured like `Amount` from #15026 — `int64` fast path, `*big.Int` when it doesn't fit, exact add/sub, narrowed only at the boundary. Decay and entry penalties move to it, and `corev1.ResourceList` stays only in the two places where it really is the API: writing the status and seeding from it on restart. The shared `int64` + `big.Int` core can be factored out so there aren't two copies of it.

I did consider reusing `Amount` as it stands, but it holds whole base units, so fractional decayed history disappears: a GPU history that should decay to 0.75 ends up as 1 or 0.

**The #13621 semantics**

I was pointed at #13621, which I'm grateful for since I'd missed it. Reading it, two details have to match `MulByFloat` exactly or the ledger stops matching main ([[resource.go#L95-L116](https://github.com/kubernetes-sigs/kueue/blob/7a617ed3d0f1ce982f8399a0b61363df280d9089/pkg/util/resource/resource.go#L95-L116)](https://github.com/kubernetes-sigs/kueue/blob/7a617ed3d0f1ce982f8399a0b61363df280d9089/pkg/util/resource/resource.go#L95-L116), [[admission_fair_sharing.go#L108-L114](https://github.com/kubernetes-sigs/kueue/blob/7a617ed3d0f1ce982f8399a0b61363df280d9089/pkg/util/admissionfairsharing/admission_fair_sharing.go#L108-L114)](https://github.com/kubernetes-sigs/kueue/blob/7a617ed3d0f1ce982f8399a0b61363df280d9089/pkg/util/admissionfairsharing/admission_fair_sharing.go#L108-L114)).

First, the two products are each rounded down to 9 decimals before they're summed. With old = 0.001031291 and usage = 3, per-term rounding gives 0.002062227, while rounding the combined sum gives 0.002062228. Second, `alpha` and `1-alpha` are each converted with `strconv.FormatFloat(f, 'f', -1, 64)`; round alpha to 9 decimals first and 3 × alpha goes from 0.001031291 to 0.001031292.

For tests I plan to port the #13621 tests onto `Decimal` unchanged, plus a randomized differential test comparing `Decimal` against `MulByFloat` digit for digit. If I've misread any of those semantics, please do correct me.

**Where I'm stuck: `Decimal` → `float64`**

The ledger value is an integer `U` meaning `U × 10⁻⁹`, and the sort score needs a `float64` ([[cluster_queue.go#L792](https://github.com/kubernetes-sigs/kueue/blob/7a617ed3d0f1ce982f8399a0b61363df280d9089/pkg/cache/queue/cluster_queue.go#L792)](https://github.com/kubernetes-sigs/kueue/blob/7a617ed3d0f1ce982f8399a0b61363df280d9089/pkg/cache/queue/cluster_queue.go#L792), [[workload.go#L657](https://github.com/kubernetes-sigs/kueue/blob/7a617ed3d0f1ce982f8399a0b61363df280d9089/pkg/workload/workload.go#L657)](https://github.com/kubernetes-sigs/kueue/blob/7a617ed3d0f1ce982f8399a0b61363df280d9089/pkg/workload/workload.go#L657), plus the `LocalQueueAdmissionFairSharingUsage` metric). Two options:

- **A**: replicate `Quantity.AsApproximateFloat64`, i.e. `float64(U) * math.Pow10(-9)`, which rounds twice.
- **B**: one correctly rounded conversion — the nearest `float64` to the true value.

Take U = 687527 (true value 0.000687527). The adjacent `float64`s are a = 0.00068752699999999995154… and b = 0.00068752700000000005996…, with midpoint 0.00068752700000000000575…. The true value is below the midpoint, so B gives a. A rounds not the true value but the product 687527 × `Pow10(-9)` = 0.00068752700000000004282… (`Pow10(-9)` is slightly larger than 10⁻⁹), which lands above the midpoint, so it gives b. Over 1,000,000 random values, A is not the nearest `float64` about 41% of the time, always in the last place.

I assumed A was the safe "no behavior change" option, but digging in turned up two things.

**A isn't bit-identical to main in every case either.** `AsApproximateFloat64` computes from the Quantity's internal (unscaled, exponent) pair rather than from the value. Everything `MulByFloat` writes is `Dec` at scale 9, and there A matches main exactly — but the restart seed parses the status string ([[localqueue_controller.go#L369-L377](https://github.com/kubernetes-sigs/kueue/blob/7a617ed3d0f1ce982f8399a0b61363df280d9089/pkg/controller/core/localqueue_controller.go#L369-L377)](https://github.com/kubernetes-sigs/kueue/blob/7a617ed3d0f1ce982f8399a0b61363df280d9089/pkg/controller/core/localqueue_controller.go#L369-L377)), so the exponent comes from the serialized suffix. A ledger value of 946635135000 is written as `946635135u` and read back as (946635135, −6); main then returns 946.63513499999999 where before the restart it returned 946.6351350000001. `Decimal` has a single representation and can't reproduce both. The window is: after a restart until that LocalQueue's next sampling tick or settlement, and only for resources with no pending penalty.

**The performance worry about B is fixable.** Following the shape of #15026 (guarded fast path, `big.Rat` otherwise) works, but memory ledger values almost always exceed 2⁵³ (~8.6 MiB when the unit is bytes), so the common case lands in `big.Rat` at ~570 ns and 9 allocs. If that's too much, splitting integer and fractional parts avoids it:

```go
if -(1<<53) <= u && u <= 1<<53 {
    return float64(u) / 1e9
}
q, rem := u/1e9, u%1e9
return float64(q) + float64(rem)/1e9
```

Neither hazard that `PerThousandOf`'s fast path guards against applies here: there's no multiplication that can overflow (the divisor is the constant `1e9`; in Go only `MinInt64 / -1` overflows), and the remainder is added back rather than dropped, so no value is lost. `|q| ≤ 9,223,372,036` and `|rem| ≤ 999,999,999` are both well inside 2⁵³ — the condition #15026's guard checks — here guaranteed by the division itself. If there's a case those guards were meant to cover that I've missed, I'd be glad to hear it.

The correctness argument: in this branch `|U| > 2⁵³`, so the result exceeds 9,007,199, adjacent `float64`s are at least 2⁻²⁹ apart, and rounding boundaries lie on a grid no finer than 2⁻³⁰. Writing a boundary as `m/2ᵗ` with `t ≤ 30`, the distance is `|U·2ᵗ − m·10⁹| / (10⁹·2ᵗ)`, whose numerator is an integer divisible by 2⁹ (since `10⁹ = 2⁹·5⁹`), so when non-zero it is at least `2⁹/(10⁹·2³⁰) ≈ 2⁻⁵¹`. For an `int64` `U` it is never zero: landing exactly on a boundary would need `|U| ≥ 2⁴⁴·10⁹ ≈ 1.8×10²²`, past `MaxInt64`. Since `float64(rem)/1e9` has rounding error at most 2⁻⁵⁴, that first rounding can't cross a boundary, and the final sum rounds to the same `float64` as the exact value. On the `big.Int` path a value can sit exactly on a boundary, but there `rem/1e9` is a dyadic fraction `float64` holds exactly, so no first rounding happens.

What I checked, all compared against `big.Rat`:

- 20M random `U` in (2⁵³, 2⁶³), including negatives — 0 mismatches
- 10M `U` placed next to `float64` midpoints — 0 mismatches
- 200k `U` sitting exactly on a rounding boundary (`big.Int` path, with ±1 and negatives) — 0 mismatches
- edge values `MinInt64`, `MaxInt64`, ±2⁵³, ±10⁹ — all match
- speed: 2.8 ns, 0 allocs for `int64` above 2⁵³, and 127 ns, 2 allocs on the `big.Int` path (A is 2.8 ns, 0 allocs and 114 ns, 2 allocs)

One aside: `Quantity.AsFloat64Slow` can't stand in for B — it rounds twice (about 240 per 1,000,000 values aren't the nearest `float64`) and costs ~550 ns.

**What B would actually change**: the score can differ in the last place, so ordering can only differ when two LocalQueues' scores are within one ulp of each other. Over 200,000 pairs, comparisons differed only when the two differed by 1 nano-unit at a ~1e9-byte memory history (8,484 of 200,000); at 1 micro-unit or more, none. The metric shifts in its last digit, and quotas are untouched.
