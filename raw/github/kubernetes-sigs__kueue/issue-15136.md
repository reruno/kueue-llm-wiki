## Description

Kueue performs flavor matching for incoming workloads primarily by using the `.spec.nodeLabels` field. This is advertised and documented in e.g. [ResourceFlavor tolerations for automatic scheduling](https://kueue.sigs.k8s.io/docs/concepts/resource_flavor/#resourceflavor-tolerations-for-automatic-scheduling) in the Kueue documentation, which states:

> To associate a `ResourceFlavor` with a subset of nodes of your cluster, you can configure the `.spec.nodeLabels` field with matching node labels that uniquely identify the nodes. If you are using [cluster autoscaler](https://github.com/kubernetes/autoscaler/tree/master/cluster-autoscaler) (or equivalent controllers), make sure that the controller is configured to add those labels when adding new nodes.
To guarantee that the Pods in the [`Workload`](https://kueue.sigs.k8s.io/docs/concepts/workload/) run on the nodes associated to the flavor that Kueue selected, Kueue performs the following steps:
> 
> 1. When admitting a Workload, Kueue evaluates the [`.nodeSelector`](https://kubernetes.io/docs/concepts/scheduling-eviction/assign-pod-node/#nodeselector) [...]

This directly links to the k8s documentation on node selectors:

> `nodeSelector` is the simplest recommended form of node selection constraint. You can add the `nodeSelector` field to your Pod specification and specify the [node labels](https://kubernetes.io/docs/concepts/scheduling-eviction/assign-pod-node/#built-in-node-labels) you want the target node to have. **Kubernetes only schedules the Pod onto nodes that have each of the labels you specify.**

Emphasis mine. Notice that, as per the description above, node selectors in k8s are _onto_ ([technical definition](https://www.geeksforgeeks.org/maths/onto-functions/)): the node that is the recipient of the pod must match all of the labels specified on the pod.

So for example, a pod with node selector labels `X=a, Y=g` is _onto_ (and can schedule on) a node with labels `X=a, Y=g`, but is not _onto_ (and cannot schedule on) a node with just the label `X=b`, or one with just the label `Y=g`. Both labels need to be present for admission to proceed.

Until recently, resource flavor admission in Kueue worked the same way. This was changed, seemingly on purpose, in https://github.com/kubernetes-sigs/kueue/pull/12487 et al, which links back to https://github.com/kubernetes-sigs/kueue/issues/12446, which calls this property a bug:

> Create 2 resource flavours on a resource group. Flavor A declares a label X =a , flavor B declares that label X= b and another additional label Y = k.
> Create a job that has label X=a, Y=g.
> The job will be stuck in pending forever instead of being admitted to flavor A

There are several problems with this:

* **This strategy diverges from the k8s node selector specification**. Kueue links directly to the node selector specification but has introduced its own divergent behavior. This divergent behavior is not documented in the corresponding documentation page ([ResourceFlavor tolerations for automatic scheduling](https://kueue.sigs.k8s.io/docs/concepts/resource_flavor/#resourceflavor-tolerations-for-automatic-scheduling)), which links the reader to the k8s documentation (which Kueue is no longer consistent with) rendering it very difficult to discover.
* **This is a backwards-incompatible change released in a patch version of Kueue**. We were relying on the property of _ontoness_ in our production deployment of Kueue. Upgrading our release past [`0.18.2`](https://github.com/kubernetes-sigs/kueue/releases/tag/v0.18.2) caused our workloads to be scheduled onto the wrong resource type, which led to scheduling failures. Re-applying the upgrade would require reworking our resource labeling strategy.

----

To illustrate the backwards incompatibility. In our specific case we had a model `Workload` which set:

```yaml
nodeSelector:
  cloud.google.com/gke-accelerator: nvidia-l4
  ray.gazette.reddit.com/flexible: 'true'
```

This was unexpectedly admitted onto the `nvidia-l4-flavor` `ResourceFlavor` (for GPU):

```yaml
admission:
  clusterQueue: ray-anti-evil-nonprod-cq
  podSetAssignments:
  - count: 1
    flavors:
      cpu: default-flavor
      memory: default-flavor
    name: head
    resourceUsage:
      cpu: 4100m
      memory: 15488Mi
  - count: 1
    flavors:
      cpu: default-flavor
      memory: default-flavor
      nvidia.com/gpu: nvidia-l4-flavor
    name: gpu-1xl4-standard
    resourceUsage:
      cpu: 8100m
      memory: 34944Mi
      nvidia.com/gpu: '1'
```

Which is this resource flavor:

```yaml
spec:
  nodeLabels:
    cloud.google.com/gke-accelerator: nvidia-l4
    ray.gazette.reddit.com/on-demand: "true"
```

We expected it to reject scheduling onto this flavor and schedule instead onto the `nvidia-l4-flexible-reserved-flavor` `ResourceFlavor`, which has set:

```yaml
spec:
  nodeLabels:
    cloud.google.com/gke-accelerator: nvidia-l4
    ray.gazette.reddit.com/flexible: 'true'
```

Our system _did_ have this behavior prior to the `0.18.2` upgrade, after the `0.18.2` it did not.

The end effect is that this (and other) workloads were incorrectly routed onto the wrong class of resource.

### Comment by [@NasitSony](https://github.com/NasitSony) — 2026-09-03T23:59:34Z

Traced this — confirmed `precisely. checkPodSetAndFlavorMatchForFlavor`'s flavorLabelKeys (`flavorassigner.go`:1231) is deliberately scoped to only this flavor's own label keys, per the comment there: "not the union across all flavors in the resource group." `flavorSelector` (line 1282) then filters the pod's `NodeSelector` down to just those keys before matching (line 1288-1294) — so any selector key the current flavor doesn't declare is silently dropped, rather than enforced. That reproduces the reported bug exactly: a pod selector requiring `{A, B}` gets treated as if it only required `{A}` when evaluated against a flavor that only declares `A`, wrongly admitting it even though the flavor doesn't satisfy `B` at all.

This looks like a real, narrower gap in the fix for #12446, not a full revert candidate — #12446's actual problem was a selector key belonging to a different flavor in the same resource group (so a workload could get stuck forever if evaluated strictly). But the current fix drops any unrecognized key, not just ones a sibling flavor declares. A key that no flavor in the resource group declares at all is a different situation — that's a real, meaningful constraint the workload cares about, not one aimed at a different flavor, and dropping it silently causes exactly this issue.

A possible fix: only ignore a selector key if some other flavor in the same resource group actually declares it (implying it's plausibly meant for that flavor instead); otherwise enforce it normally. This looks implementable at this exact call site without new plumbing — `rg.Flavors` (already a parameter here) gives the sibling flavor names, and `a.resourceFlavors` (already used two lines above) can resolve each to its NodeLabels keys.

Given the backwards-compatibility and correctness stakes here, this seems worth prioritizing — happy to help with a PR once there's agreement on the right resolution direction.

Thank you for opening the issue. 

For now I can see three semantics worth considering here for defining what "matching the Workload's PodTemplate to a RF" means:
1. the RF satisfies the entire node selector (as Node would)
2. the RF nodeLabels don't contradict the nodeSelector (current)
3. the RF nodeLabels don't contradict the nodeSelector, and additionally if the Workload's nodeSelector falls in the union of keys, then require full match of the value (before https://github.com/kubernetes-sigs/kueue/issues/12446 and https://github.com/kubernetes-sigs/kueue/pull/12449)

While (1.) is compatible with k8s it makes the model in Kueue too restrictive - it does not allow users to say a specific nodeSelector which binds the Pod to a specific node in the RF.

As for (3.) I can see it useful here. I considered it a bug in the past because: 
a) the user raised it as a bug, 
b) there was no test to support it, 
c) there was no documentation to support it, 
d) the semantics is risky - adding a new flavor might be disruptive because it extends the union 
e) it is tricky tricky, because setting `ray.gazette.reddit.com/flexible: partial` on the Workload would also match on-demand (IIUC).

Re-introducing (3.) would also mean regression for the other user who reported #12446.

So a potentially vital path forward I see:
A. re-introduce (3.) behind a feature gate to allow users to migrate to 0.18 easily
B. consider a cleaner and more expressive API, for example a new spec field in the flavor like `spec.requiredLabelKeys`

Actually B can be already expressed with TAS as the Topology keys are exactly that - set of label keys which need to be present on the Workload.

If you @ResidentMario already mitigated the issue then maybe we should skip A and re-evaluate cleaner options for B.

### Comment by [@mimowo](https://github.com/mimowo) — 2026-09-11T21:33:36Z

I'm ok backporting the old behavior, but I think the claim that the previous logic was handling RF nodes like isn't accurate.

In particular: there is no logic difference in handling before / after when single RF in CQ is considered - the only semantic difference happens by considering multiple RFs in CQ as before we would union their keys.

1. Single flavor behaviors

Pod selector: `{pool: gpu, hostname: node-1}`. 

| Flavor’s nodeLabels | Before #12449: union matching | After #12449: per-flavor matching | Full match against RF labels (k8s-like) |
|---|---|---|---|
| `{pool: gpu}` | Accept: hostname is outside the union | Accept: hostname is outside this flavor’s keys | Reject: missing hostname |
| `{pool: gpu, hostname: node-1}` | Accept | Accept | Accept |
| `{}` | Accept: no keys checked | Accept: no keys checked | Reject: requested keys are missing |

2. Effect of adding sibling flavors

Pod selector: `{x: a, y: g}`. Evaluate flavor A with `{x: a}`.

| Flavors in the resource group | Before #12449: union matching | After #12449: per-flavor matching | Full match against A’s labels (k8s-like) |
|---|---|---|---|
| A only | Accept A | Accept A | Reject A: missing `y` |
| A and B `{x: b}` | Accept A | Accept A | Reject A: missing `y` |
| A and B `{x: b, y: k}` | Reject A: `y` is now in the union | Accept A | Reject A: missing `y` |

So just adding a new flavor to CQ could change evaluation of the pre-existing flavors. 

Other semantic difference with core k8s pod selector is that RF injects the missing node labels into the pod selector.

### Comment by [@mimowo](https://github.com/mimowo) — 2026-09-14T07:57:55Z

@ResidentMario there is another option, which is not that intuitive and will require you PodTemplate updates on Workloads, but does not require the FG, or any other code changes inside Kueue.

```yaml
apiVersion: kueue.x-k8s.io/v1beta1
kind: ResourceFlavor
metadata:
  name: l4-on-demand
spec:
  nodeLabels:
    cloud.google.com/gke-accelerator: nvidia-l4
    ray.gazette.reddit.com/on-demand: "true"       // keep it to inject the label to the workloads once matched
  nodeTaints:
  - key: ray.gazette.reddit.com/on-demand
    value: "true"
    effect: NoSchedule
---
apiVersion: kueue.x-k8s.io/v1beta1
kind: ResourceFlavor
metadata:
  name: l4-flexible
spec:
  nodeLabels:
    cloud.google.com/gke-accelerator: nvidia-l4
    ray.gazette.reddit.com/flexible: "true"               // keep it to inject the label to the workloads once matched
  nodeTaints:
  - key: ray.gazette.reddit.com/flexible
    value: "true"
    effect: NoSchedule
```

Then in your workloads you just need to inject the toleration which will determine the flavor affinity. 

```yaml
spec:
  template:
    spec:
      nodeSelector:
        cloud.google.com/gke-accelerator: nvidia-l4
      tolerations:
      - key: ray.gazette.reddit.com/flexible
        operator: Equal
        value: "true"
        effect: NoSchedule
```

Please let us know if this satisfies your requirements.
