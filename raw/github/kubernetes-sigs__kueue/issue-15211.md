## Description

**What would you like to be added**:

When Kueue preempts some Workloads to fit a new one, these preemptions may take multiple scheduling cycles to complete.
In the meantime, another scheduling cycle may plan preemptions again.

I propose introducing a **general rule** that every preemption planning should rely on the fact that some Workloads may be already in an Evicted state, *to the maximal possible extent*.

**Context: How it looks in Kueue today**:

* In **fair preemptions**, existing evictees come first in each CQ.
  However, in the first place, [CQs are ordered](https://github.com/kubernetes-sigs/kueue/blob/6d77545cadffb5350341b432d7c37826eef0d7e5/pkg/scheduler/preemption/preemption.go#L397) based [on DRS](https://github.com/kubernetes-sigs/kueue/blob/8a6a7750f7da0d7ea0a73af53158a37b5dec715f/pkg/scheduler/preemption/fairsharing/ordering.go#L138-L144).
  So the rule is not strictly followed.

* In **classical preemptions**, existing evictees are fully prioritized:
  
  https://github.com/kubernetes-sigs/kueue/blob/6d77545cadffb5350341b432d7c37826eef0d7e5/pkg/scheduler/preemption/classical/candidate_generator.go#L101-L104

  However, the structure of the code makes this a relatively unstable implementation detail.

* In the **[Configurable Preemptions KEP](https://github.com/kubernetes-sigs/kueue/pull/14554)** (currently in review), this topic seems either overlooked or omitted as an implementation detail.
  (The proposed default ordering ignores existing evictions, and taking them into account seems not supported).
  I've [commented](https://github.com/kubernetes-sigs/kueue/pull/14554#discussion_r3934782525) on that KEP about this, to make sure we're aligned.

**Why is this needed**:

Consider a Cohort of 3 ClusterQueues, `cqA` (running `wl1`), `cqB` (running `wl2`, `wl3`), `cqC` (running `wl4`, `wl5`).
All CQs have quotas 5 CPU. All workloads so far (`wl1`-`wl5`) take 3 CPU. 
So, right now, `cqB` & `cqC` are borrowing 1 CPU each from `cqA`.
Fair sharing preemptions are enabled.

* Before scheduling cycle 1, a `wl6` requesting just 2 CPU arrives at `cqA`.
   So that `wl1` + `wl6` would fit in `cqA`'s quota - but we need to reclaim what was borrowed.
* In scheduling cycle 1, we plan preempting `wl2` from `cqB`.
  `wl6` must wait for this preemption to complete, so it's Pending for now.
* Between scheduling cycles 1 and 2, `wl3` has completed.
  As a result, `cqB` is no longer borrowing from `cqA`.
* In scheduling cycle 2, `wl6` gets nominated again.
  The only borrower now is `cqC`, so we plan preempting `wl4` from it.

In most cases (assuming preemptions complete reasonably fast), the decision to preempt `wl4` is **completely unnecessary** - we already evicted `wl2`, and it should be enough to just wait for it to be gone.
So, by not following the proposed rule, we're unnecessarily disruptive for more workloads.

**Completion requirements**:

I imagine 3 action items here, 1 main fix & 2 potential follow-up:

* **AI 1. The main fix:** reorganize `fairPreemptions` to first find *all* Evicted workloads (regardless of DRS etc.) and ensure they're all considered before any other Workloads. Only then proceed with considering the other workloads according to the current algorithm.

* **AI 2. Make that universal**: move the "go through Evicted first" code (from AI 1) higher up in the code (e.g. `Preemptor.getTargets()`), so that it's utilized also in `classicalPreemptions`.
  (And also usable in the implementation of the Configurable Preemptions KEP).
  _This could be done as follow-up to AI 1 or right away together with it. I've no strong opinion._

* **AI 3. Minor optimizations**: in the logic of preemption planning, the already-evicted candidates can be treated specially to save some time.
  For example: if we have 5 preemption candidates A B C D E, where A B C are already Evicted, then there's no point in doing fit checks like "what if we preempted just A". Because A B C are all going to be preempted soon, so we can take this as a baseline. 
  Specifically:
  * In the forward pass ("for each candidate, remove it from snapshot, then do fit check") - we can fast-forward to the state where all evictees are removed.
  * In the backward pass (`fillBackWorkloads`) - we can skip considering bringing back the evictees. This won't happen anyway.
  * _(An alternative approach would be to remove all evictees from the snapshot at the very start; however, this could change Kueue behavior in an unexpected way, by switching the assignment mode from `Preempt` to `Fit` in some cases. So that's sth I wouldn't recommend)_
