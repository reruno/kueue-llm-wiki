**What happened**:

AdmissionFairSharing can settle more than one entry penalty for the same Workload and LocalQueue.

Pending penalties are already tracked per Workload, so a re-push replaces the existing pending record. Once a penalty is settled, however, it is folded into the aggregate consumed history and the Workload identity is dropped. If the same Workload later reaches the accounting anchor again, another penalty can be settled.

For example, with the admitted anchor:

    Admitted -> evicted -> Admitted

settles an entry penalty on both admissions.

**What you expected to happen**:

A Workload should not be charged multiple settled entry penalties for the same LocalQueue solely because it leaves and re-enters the accounting anchor

**How to reproduce it (as minimally and precisely as possible)**:

1. Create a ClusterQueue using `UsageBasedAdmissionFairSharing` and a LocalQueue under it.
2. Admit a Workload so its entry penalty is settled.
3. Evict it and let it be admitted again.
4. Observe that another entry penalty is settled for the same Workload and LocalQueue.

**Anything else we need to know?**:

This predates #15000 and is orthogonal to the accounting-anchor change. Moving the anchor to quota reservation only makes the same issue reachable before admission as well, for example when a Workload loses and reacquires a reservation.

Since #14153, pending penalties already have per-Workload tracking. The missing piece is retaining enough identity after settlement to distinguish a repeated charge from a new Workload/LocalQueue entry.

Discussed in https://github.com/kubernetes-sigs/kueue/pull/15000#discussion_r3927134072.

### Comment by [@apullo777](https://github.com/apullo777) — 2026-09-06T21:28:49Z

One scope detail I noticed while looking at #15236: #15221 as I filed it does not say how long the deduplication should last.

#15000 currently documents repeated reservations as separately chargeable, while #15236 keeps a settled marker for the Workload/LocalQueue lifetime. Those are different semantics, so I wanted to make that distinction explicit. One input for the choice: consumed history decays, so a lifetime-scoped marker can outlive the penalty it suppresses.

@mimowo whenever convenient, do you see repeated reservations as remaining separately chargeable, or is the intent lifetime deduplication per Workload and LocalQueue? No urgency since this is a low-priority follow-up :)

### Comment by [@apullo777](https://github.com/apullo777) — 2026-09-23T03:00:55Z

Another case for the scope question above, from https://github.com/kubernetes-sigs/kueue/pull/15000#discussion_r4078201470: with AdmissionCheck retries, the same Workload can lose and reacquire its quota reservation repeatedly before admission. At the quota-reservation anchor, lifetime dedup would charge this once, while per-reservation accounting would charge each retry.

### Comment by [@mimowo](https://github.com/mimowo) — 2026-09-23T09:48:54Z
