**What would you like to be added**:

E2E coverage for partial replica scale-up of elastic jobs (KEP-12100), plus manual verification results attached to this issue as a comment.

Scenarios, following the KEP's "Two-Step Scale Up under Quota Constraints" example:

* A scale-up exceeding available quota is admitted partially rather than rejected.
* The remainder is admitted opportunistically once quota frees up, via the scale-up probe.
* A further scale-up while the probe is pending updates that probe rather than creating another workload.
* A scale-down after a partial scale-up.
* RayJob, RayCluster and RayService, all three being in Alpha scope.

Manual results should record the Kubernetes, KubeRay and Ray image versions, the quota used, and the observed pod counts per step.

**Why is this needed**:

The integration suites run under envtest with no KubeRay operator, so a RayCluster or RayJob produces no pods. 
They assert `status.admission.podSetAssignments[*].Count` — the KEP's authoritative record — but cannot verify that exactly N of M gated worker pods are ungated and running while the rest stay gated. 
That ungating path is the user-visible half of the feature and the KEP's Test Plan asks for it explicitly.

Two things only a real cluster exercises: 
* the Ray autoscaler actually driving the replica changes (integration tests stand in for KubeRay by editing .replicas directly)
* the recycling drawback the KEP documents — gated pods reclaimed by the autoscaler after RAY_AUTOSCALER_RECONCILE_ALLOCATE_STATUS_TIMEOUT_S, which bears directly on whether opportunistic scale-up delivers Story 2.
