## Description

**What happened**:
When a LocalQueue is put on Hold, its Admission Fair Sharing (AFS) usage history stops updating even though admitted workloads keep running. If those workloads finish before the queue resumes, their usage during Hold is missed.

I reproduced this with two Jobs on Kind. Both requested 1 CPU and ran `sleep 180`. After putting one queue on Hold, letting both Jobs finish, and resuming it, `consumedResources.cpu` was roughly 469m for the active queue and 7m for the queue put on Hold. 

This could let new work from the resumed queue go ahead of work from other queues.

**What you expected to happen**:
Both queues ran the same work, so they should have similar usage histories after resume.

**How to reproduce it (as minimally and precisely as possible)**:
With AdmissionFairSharing enabled:

1. Set the following in the configuration (`managerConfig.controllerManagerConfigYaml`):

   ```yaml
   admissionFairSharing:
     usageHalfLifeTime: 30s
     usageSamplingInterval: 2s
   ```

    (The short configuration settings help the test finish in a few minutes)

2. Create two LocalQueues, `open` and `held`, both with weight 1, under one ClusterQueue. Set `spec.admissionScope.admissionMode: UsageBasedAdmissionFairSharing` and give it 4 CPUs of quota.
3. Submit one Job to each queue, each requesting 1 CPU and running `sleep 180`.
4. Wait 30 seconds after both jobs are admitted, then set `held`'s `spec.stopPolicy` to `Hold`.
5. Let both Jobs finish, wait another 30 seconds, then set `held`'s stop policy to `None`.
6. Compare `consumedResources.cpu` and `lastUpdate` for each LocalQueue's `status.fairSharing.admissionFairSharingStatus`.

During Hold, the queue's `consumedResources.cpu` and `lastUpdate` stayed frozen while its Job kept running. After the Job finished, resuming the queue dropped its `consumedResources.cpu` to **7m**, compared with **469m** for the active queue. Kueue decayed the old history as though the entire pause had been idle.


**Anything else we need to know?**:
In [`LocalQueueReconciler.Reconcile`](https://github.com/kubernetes-sigs/kueue/blob/730f57dd18194b6f0825e6231301ac9d3e9b7d77/pkg/controller/core/localqueue_controller.go), a stopped queue causes an early return before `reconcileConsumedUsage` updates AFS history.

If you agree that usage should still count during Hold, I’d be happy to work on a fix.

**Environment**:
- Kubernetes: v1.36.1 on Kind, linux/arm64
- Kueue: v0.20.0-devel-586-g730f57dd1, locally built and installed with Helm
- Full commit: 730f57dd18194b6f0825e6231301ac9d3e9b7d77
