**What happened**:

With the `SchedulerLibraryIntegration` feature gate enabled, TAS scheduling simulation ignores two sets of pod constraints that Kueue applies to the real pods it admits:

- `ResourceFlavor.spec.tolerations`
- `nodeSelector` and `tolerations` set through `PodSetUpdates` by admission checks, for example a ProvisioningRequest targeting newly provisioned nodes

As a result, a TAS workload whose only toleration for a node taint comes from the ResourceFlavor is never admitted, and a workload with a ProvisioningRequest nodeSelector can be placed on a node the selector excludes. The same workloads behave correctly with the gate disabled.

**What you expected to happen**:

The scheduler-library simulation sees the same tolerations and nodeSelector that Kueue injects into the admitted pods, so its `TaintToleration` and `NodeAffinity` filters make the same decision the kube-scheduler will make once the pods exist.

**How to reproduce it (as minimally and precisely as possible)**:

Unit, in `pkg/scheduler`, with the gate default temporarily flipped to `true`:

```
go test ./pkg/scheduler/ -run 'TestScheduleForTAS/scheduling_workload_on_a_tainted_node_when_the_toleration_is_on_ResourceFlavor' -count=1
```

The workload lands in the inadmissible set with `topology "tas-single-level" doesn't allow to fit any of 1 pod(s)`.

Integration, once the WAS simulator is wired into the `tas` suite (part of the item (2) work for #14969), two specs fail with the gate on:

- `Topology Aware Scheduling when Updating TAS ResourceFlavor tolerations should apply updates, requeue pending workloads, and preserve admitted usage` times out waiting for admission after the flavor toleration is added.
- `Topology Aware Scheduling when Single TAS Resource Flavor when ProvisioningRequest is used should admit workload targeting the dedicated newly provisioned nodes` gets the wrong node in its TopologyAssignment.

Manually: enable the gate, create a Topology and a TAS ResourceFlavor with a toleration for a taint that is present on the only matching node, and submit a Job with a TAS annotation and no toleration of its own. The Workload stays pending.

**Anything else we need to know?**:

`TASFlavorSnapshot.findTopologyAssignment` builds the pod requirements in two forms. The field form (`PodRequirements.Tolerations`, `Selector`, `AffinitySelector`) is computed from the PodSet info merged with `PodSetUpdates`, plus the flavor's tolerations, and the default simulator reads it. The pod form (`PodRequirements.PodTemplate`) is a plain deep copy of the PodSet template, and the WAS simulator builds its dummy pod from that alone, so anything merged into the field form after the template is lost.

Proposed fix, verified locally with the gate on against the `pkg/scheduler` and `pkg/cache/scheduler` unit packages and the full `tas` integration suite (132 of 132 passing): after the template is deep-copied, overwrite `PodTemplate.Spec.Tolerations` with the merged tolerations and `PodTemplate.Spec.NodeSelector` with the merged nodeSelector. I will open a PR.

Related: #14969 item (2) depends on this, since wiring the WAS simulator into the `tas` integration suite exposes the two specs above under a gate-on run.
