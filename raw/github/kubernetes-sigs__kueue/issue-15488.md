## Description


**What happened**:

We have done static code analysis here https://github.com/kubernetes-sigs/kueue/pull/12849/changes/BASE..30f021d4f6e78ad5508395093f663003c5685d5a#r3988633544 which suggests there might be a bug that prevents cleaning worker clusters in case ` --cascade=orphan` is used on the management cluster.

**What you expected to happen**:

Worker cluster workloads are cleaned up when the Job on the manager is deleted with ` --cascade=orphan` 

**How to reproduce it (as minimally and precisely as possible)**:

Execute ` --cascade=orphan`  on a running job on the management cluster.

**Anything else we need to know?**:

This was only observed by static code analysis. I would suggest starting with an integration test to first confirm the problem.

### Comment by [@JanKaczmarski](https://github.com/JanKaczmarski) — 2026-11-06T15:38:44Z

I wrote an integration [test](https://github.com/kubernetes-sigs/kueue/pull/18445/changes/e086379d1cfd46b5e100e88c9bcd56bbcf3d120a) that reproduces the bug

Why this happens when a manager Job is deleted with `--cascade=orphan`:
1. Kubernetes GC removes `ownerReferences` from the manager Workload before deleting the manager Job.
2. MultiKueue sees that the manager Workload has no owner (`w.adapter(wl)` returns `nil`) and sets the AdmissionCheck state to `CheckStateRejected`.
3. Because the check is `Rejected`, later reconciles exit early and never reach the cleanup logic. Even after the orphaned manager Workload is marked `Finished` (or later deleted). MultiKueue GC also skips it while the local Workload exists.
