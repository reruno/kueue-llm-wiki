## Description

# TAS: reservation loss via the scheduler's stale release write, then the reservation-free re-admission commits flavors-only (vacuous replacement loop)

**Affected:** v0.19.1, v0.19.2, and main (the vacuous commit reproduces on main, and `requeueAndUpdate` / the second-pass queue are unchanged from v0.19.2). Gates: `TopologyAwareScheduling`, `TASReplaceNodeOnNodeTaints`.

*All code references are pinned to tag `v0.19.2`.*

## What happened

1. A TAS workload has a node marked unhealthy (`tas-node-reconciler` → `status.unhealthyNodes`), so it
   needs a second pass. `QueueSecondPassIfNeeded` and `secondPassQueue` store the **workload object
   captured at request time** ([`queue/manager.go:991`](https://github.com/kubernetes-sigs/kueue/blob/v0.19.2/pkg/cache/queue/manager.go#L991),
   [`second_pass_queue.go`](https://github.com/kubernetes-sigs/kueue/blob/v0.19.2/pkg/cache/queue/second_pass_queue.go));
   nothing re-reads the object before it is used.
2. When a second-pass attempt fails while another retry is already scheduled, `QueueSecondPassIfNeeded`
   returns false and the scheduler runs its release path
   ([`scheduler.go:1149 requeueAndUpdate`](https://github.com/kubernetes-sigs/kueue/blob/v0.19.2/pkg/scheduler/scheduler.go#L1149)).
   `prepareWorkloadPatch` builds the apply payload from that stale copy: it unconditionally re-sends the
   copy's `UnhealthyNodes` ([`patching.go:136`](https://github.com/kubernetes-sigs/kueue/blob/v0.19.2/pkg/workload/patching/patching.go#L136)),
   the nine admission-managed conditions, and its `Status.AdmissionChecks`. The loose apply carries no
   resourceVersion, so the release **unsets the live reservation while re-sending the stale status**:
   the object flips `admitted → pending` with the marks attached (logged:
   [`workload_controller.go:1451 "Workload transitioned back to pending"`](https://github.com/kubernetes-sigs/kueue/blob/v0.19.2/pkg/controller/core/workload_controller.go#L1451),
   `prevStatus=admitted`, `unhealthyNodes=[<node>]`). No eviction is required for this, and eviction
   itself is not the marks' source ([`evict.go:209 resetUnhealthyNodes`](https://github.com/kubernetes-sigs/kueue/blob/v0.19.2/pkg/workload/evict/evict.go#L209)
   already clears them).
3. Seconds later the workload is evaluated **fresh** (no `status.admission` anymore). The Fit branch
   *does* run TAS ([`flavorassigner.go:862`](https://github.com/kubernetes-sigs/kueue/blob/v0.19.2/pkg/scheduler/flavorassigner/flavorassigner.go#L862)),
   but the marked-workload loop in `FindTopologyAssignmentsForWorkload` does
   [`psa == nil || psa.TopologyAssignment == nil → continue`](https://github.com/kubernetes-sigs/kueue/blob/v0.19.2/pkg/cache/scheduler/tas_flavor_snapshot.go#L608):
   no prior assignment to replace, nothing computed, and
   [`result.Failure()`](https://github.com/kubernetes-sigs/kueue/blob/v0.19.2/pkg/cache/scheduler/tas_flavor_snapshot.go#L411)
   iterates an empty map ⇒ **nil** (vacuous success) ⇒ `UpdateForTASResult` no-ops ⇒ **TA:nil,
   flavors-only commit on a TAS-only ClusterQueue**.
4. The commit clears the marks, so the object afterwards shows no trace of the cause. (If the fresh
   cycle lands Preempt-mode instead, it produces the same flavors-only outcome via the guard at
   [`flavorassigner.go:875`](https://github.com/kubernetes-sigs/kueue/blob/v0.19.2/pkg/scheduler/flavorassigner/flavorassigner.go#L875),
   the adjacent, already-filed issue.)

Production (a large GPU cluster, v0.19.2, level-4 logging): 11 formations in a single 20-hour window,
all with this skeleton. Canonical trace (31-pod worker workload, 2026-09-10): marks written onto the
admitted workload at 13:05:02 and 13:05:40; four `SecondPassFailed` events between 13:05:10 and
13:05:42; at 13:05:47.741 cycle 534525 evaluates the entry (carrying a full, valid 31-domain
TopologyAssignment), then `scheduler.go:1165 "Workload re-queued"`, a `Pending` event with an empty
reason at .771, and the `admitted → pending` flip at .773 with `unhealthyNodes` attached; at
13:05:49.615 cycle 534526 logs `successfully admitted and assigned flavors` with flavors but no
`topologyAssignment`. No eviction fired for this workload that day (no
`Start the eviction ... PodsReady timeout` line, no victim/preemption event). The same release payload
was also observed re-asserting an ~18-hour-old `Evicted=True` with no evicting actor on record, which
then persisted until the next fresh admit: the write transports whichever status snapshot its copy
holds, in both directions. As @bolubo detailed in the comments, the identical payload also re-asserts
`status.admissionChecks` (undoing the "Reset to Pending after eviction" reset, which can pass a
ProvisioningRequest gate without the underlying work being redone); the same fix layer covers it.

## What you expected to happen

A marked, reservation-free workload on a TAS-only CQ must get a freshly computed TA, or fail with a
reason: it must never commit flavors-only. And the scheduler must never drop a live reservation from a
stale copy.

## How to reproduce it (unit sketch)

`pkg/scheduler/flavorassigner` (or snapshot test): TAS flavor + CQ; workload Info with
`status.UnhealthyNodes=[x1]` and **nil Status.Admission**; ask → Fit. Assert: the resulting assignment
has `TopologyAssignment != nil` (or an explicit failure reason). Today it is nil, with no error
anywhere. Scheduler-side: enqueue a second-pass head while the workload is marked, heal the live
object (marks cleared) before the pass fires, and assert the head is evaluated on a fresh read and
skipped with no status write.

## Anything else

- Not #14572/#14647: those are accounting-side fixes guarding *computed* replacements
  (verified in our tree and running in production while this class forms daily). This defect never
  computes an assignment, so per-domain accounting never engages.
- Fix direction, in two layers:
  (i) commit path: when a marked podset has no prior TA, fall through to fresh placement instead of
  skipping (equivalently: do not consult `unhealthyNodes` when `status.admission == nil`), and make
  `Failure()` non-vacuous for a TAS-required podset that got nothing;
  (ii) freshness: second-pass requeue queues by key and re-reads the object at fire/pop time before
  building the scheduling entry, plus a freshness re-check in `requeueAndUpdate` before it unsets a
  reservation. (ii) covers every transported field: `unhealthyNodes`, the managed conditions
  (`Evicted` pruned or resurrected depending on copy age), and `admissionChecks`.
- Tripwire: an admission-time invariant "TAS-only CQ ⇒ topologyAssignment present"
  (reject/warn/event) catches this class and the sibling guard together.

## Environment

EKS 1.32-era; Kueue v0.19.1/v0.19.2; large homogeneous 8-GPU B200-class clusters; hostname-only
topology; fair-sharing on; feature gates `TopologyAwareScheduling`, `TASReplaceNodeOnNodeTaints`.

### Comment by [@bolubo](https://github.com/bolubo) — 2026-09-12T04:08:27Z

@anguszzzz thanks for the detailed write-up, the end state matches what I see on a TAS-only ClusterQueue in v0.19.2.

The vacuous commit part reproduces (also on main): with status.unhealthyNodes set and no admission, the assignment comes back as Fit, flavors assigned, topologyAssignment nil, and FindTopologyAssignmentsForWorkload reports no failure at all (one request in the snapshot, empty result, nil Failure()), so UpdateForTASResult is a no-op and the flavors-only admission commits.

One part I could not reproduce as written is step 2. In v0.19.1/v0.19.2 (and on main) the eviction path (workloadevict.Evict and prepareForEviction in pkg/workload/evict/evict.go) does clear the marks, and in a local kind run the eviction apply drops status.unhealthyNodes from the object (field manager kueue-admission). What I can reproduce instead is the marks coming back in the same write that drops the reservation: the admission status apply always copies status.unhealthyNodes from the writer's copy (admissionStatusPatch, pkg/workload/patching/patching.go:136), so a release applied from a pre-eviction copy re-asserts the stale marks. In the kind run, a pre-eviction copy with the loose apply that the scheduler release path uses puts the marks back in the same write that clears the admission (kueue-admission ends up owning both fields). A fresh copy leaves them cleared, and the same stale copy with the default strict apply is rejected with a 409.

As far as I can tell, the most likely holder of a pre-eviction copy is the second pass queue: it stores the object captured when the second pass was requested, and an eviction update does not purge it (QueueSecondPassIfNeeded only deletes an entry once the retry iteration is above 0). One nuance if you go looking for the writer: the scheduler release path (requeueAndUpdate) does not normally run for an entry whose copy still points at a marked node; it re-queues it for another second pass instead, and it releases from such a copy when a retry for the same workload is already scheduled, or when the copy no longer needs a second pass. This is consistent with the payload in your 13:05:47.775 line still carrying unhealthyNodes.

If that is the path, two notes for the fix list. First, item (ii) looks already satisfied on the eviction side; the remaining gap is the write that later drops the reservation and re-asserts the marks, for example not carrying status.unhealthyNodes in that apply, or re-checking the copy's freshness before releasing. Second, a quick check on your side: if the pending transition came from a pre-eviction copy, the same write should also drop the Evicted condition, since that copy does not declare it. Does that show up in your logs?

### Comment by [@bolubo](https://github.com/bolubo) — 2026-09-12T04:48:20Z

One more field travels in the same release payload as the marks, and this one sits on the admission path itself.

`prepareWorkloadPatch` appends `admissionChecksStatusPatch` to every `PatchAdmissionStatus` payload (`pkg/workload/patching/patching.go`, default SSA path; same construction on main). So the loose release from the pre-eviction copy also re-asserts `status.admissionChecks`. Replaying that sequence against a real apiserver (kind, v0.19.2): the workload is admitted with a check in `Ready`, then eviction resets non-pending checks to `Pending` with the "Reset to Pending after eviction" message (`prepareForEviction`, `pkg/workload/evict/evict.go`). The stale release then writes the old copy back, so the check returns to `Ready` with its pre-eviction message, in the same apply that clears the admission and removes the `Evicted` condition.

A fresh copy keeps the check `Pending`, and a strict apply is rejected with a 409.

This is the part I would weigh most: the reset to `Pending` is what tells the check controller the check has to be re-evaluated. For a ProvisioningRequest, the controller skips its sync while the check is `Ready` (`pkg/controller/admissionchecks/provisioning/controller.go`). If the state is restored, that re-evaluation never happens, and the workload can pass the admission gate again without the underlying work being redone.

If the fix is scoped to not carry `unhealthyNodes` in the release payload, this field would still come back the same way, since it is the same stale copy and the same apply. A fix that re-checks the copy's freshness before releasing, or stops re-sending the copied status snapshot, covers both. Not claiming anything here; just flagging a second acceptance case. Happy to open a separate issue if you would rather track this apart from the marks.
