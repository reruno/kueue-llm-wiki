## Description

/kind bug

**What happened**:

The controller-manager builds a single `rest.Config` in `cmd/kueue/main.go`, installs one `flowcontrol` token-bucket limiter on it from `clientConnection.qps` / `clientConnection.burst` (https://github.com/kubernetes-sigs/kueue/blob/f89a9d41027589b85402cdab6eb4b62d8802db9e/cmd/kueue/main.go#L244-L259, introduced by #2462 so that all API-type clients share one limiter), and passes it to `ctrl.NewManager` (https://github.com/kubernetes-sigs/kueue/blob/f89a9d41027589b85402cdab6eb4b62d8802db9e/cmd/kueue/main.go#L278).

`pkg/config/config.go` `addLeaderElectionTo` (https://github.com/kubernetes-sigs/kueue/blob/f89a9d41027589b85402cdab6eb4b62d8802db9e/pkg/config/config.go#L128-L167) copies `leaderElection.*` (lease duration, renew deadline, retry period, lock/namespace/name) into `ctrl.Options`, but never sets `ctrl.Options.LeaderElectionConfig`. controller-runtime v0.25.0 then falls back to `rest.CopyConfig(config)` for the lease client (https://github.com/kubernetes-sigs/controller-runtime/blob/v0.25.0/pkg/manager/manager.go#L382-L386), and `rest.CopyConfig` copies the `RateLimiter` pointer (https://github.com/kubernetes/client-go/blob/v0.37.0/rest/config.go#L649). The result is that Lease `get`/`update` requests from the leader-election loop draw tokens from the exact same bucket as every Workload/Job/Pod reconcile.

Under load this starves lease renewal. Observed on v0.18.2 with the default `clientConnection` of that release (`qps: 20`, `burst: 30`) and a few hundred retained finished Workloads: every controller start replays a create event per Workload (`WorkloadReconciler.Create` -> `queues.AddFinishedWorkload`) plus Job/Pod/Node reconciles, the burst is consumed immediately, the lease renewal request waits behind the reconciles, `client rate limiter Wait returned an error` is logged, `renewDeadline` (10s) is exceeded, and the process exits with `leader election lost`. The replacement pod repeats the same sequence, so the deployment crash-loops for hours while no new Workloads are admitted. It recovered only after raising `clientConnection.qps/burst`, lengthening `leaderElection.leaseDuration/renewDeadline`, and setting `objectRetentionPolicies.workloads.afterFinished` to drain the replay.

#12440 / #15206 raised the default to `1000/1000`, which makes this much less likely with defaults, but the coupling is still present on `main`: any administrator who lowers `clientConnection.qps` to protect the API server (the stated purpose of #2423 / #2462), or any cluster whose startup replay saturates the limiter, gets the same failure mode. Lease renewals are a handful of tiny requests per `retryPeriod` and should never queue behind reconcile traffic.

**What you expected to happen**:

Leader-election lease requests use a dedicated `rest.Config` / rate limiter so that a reconcile burst cannot delay renewal past `renewDeadline`. controller-runtime exposes `manager.Options.LeaderElectionConfig` for exactly this purpose (https://github.com/kubernetes-sigs/controller-runtime/blob/v0.25.0/pkg/manager/manager.go#L199-L201); today no caller in this repository sets it, so the option's fallback (a copy of the manager config sharing the same limiter) is always taken.

**How to reproduce it (as minimally and precisely as possible)**:

Unit-level (no cluster needed), in `pkg/config/config_test.go`:

1. Load a `Configuration` with `clientConnection: {qps: 20, burst: 30}` and `leaderElection.leaderElect: true` via `config.Load` (the existing `TestLoad` fixtures already do this).
2. Assert `options.LeaderElectionConfig != nil`, and that it is a distinct `*rest.Config` from the manager config whose `RateLimiter` is not the same object.
3. Today this fails: `LeaderElectionConfig` is `nil`, so controller-runtime reuses the manager `rest.Config` (and its shared token bucket).

Behavioural reproduction on a cluster: set `clientConnection.qps: 5`, `burst: 5`, keep `leaderElection` defaults, retain a few hundred finished Workloads (no `objectRetentionPolicies.workloads.afterFinished`), restart the controller-manager, and watch for `client rate limiter Wait returned an error` followed by `leader election lost` and a restart.

**Anything else we need to know?**:

Proposed fix (roughly 20-30 lines plus test, no API change):

- Where the manager `rest.Config` is built in `cmd/kueue/main.go` (or in `addLeaderElectionTo`), when leader election is enabled: `leCfg := rest.CopyConfig(kubeConfig); leCfg.RateLimiter = nil; leCfg.QPS = <small dedicated value>; leCfg.Burst = <small dedicated value>; options.LeaderElectionConfig = leCfg`. With `RateLimiter` nil, client-go allocates a separate limiter from `QPS/Burst` for the lease client, so renewals are unaffected by reconcile traffic. Optionally `rest.AddUserAgent(leCfg, "leader-election")` so lease traffic is distinguishable in API-server audit logs.
- Add the unit test above to `pkg/config/config_test.go`.
- Note in the configuration reference (`site/content/en/docs/reference/kueue-config.v1beta2.md`, `clientConnection`) that leader-election traffic is not subject to `clientConnection.qps/burst`.

Workarounds today: raise `clientConnection.qps/burst` (or set `qps: -1` to disable client-side limiting per #6300), lengthen `leaderElection.leaseDuration/renewDeadline`, and set `objectRetentionPolicies.workloads.afterFinished` to bound the startup replay.

Related: #2423 / #2462 (single shared limiter), #6256 / #6300 (disable client-side limiting), #12440 / #15206 (default QPS raised to 1000).
