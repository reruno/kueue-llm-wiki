**What happened**:

`firstCandidateVariant` picks which ConcurrentAdmission Variant may have its preemption gate opened ([code](https://github.com/kubernetes-sigs/kueue/blob/4a91e9c26b5652a6043f1cf66d5115e453d459fd/pkg/controller/concurrentadmission/controller.go#L776-L798)). For a Variant with no `BlockedOnPreemptionGates` condition it has to tell two cases apart: the scheduler evaluated this Variant and it needs no preemption (skip it, keep scanning), and the scheduler has not evaluated it yet (stop and wait, so a less favorable flavor does not win by arriving first).

#14272 made that call on the *presence* of a `WorkloadQuotaReserved` condition ([code](https://github.com/kubernetes-sigs/kueue/blob/4a91e9c26b5652a6043f1cf66d5115e453d459fd/pkg/controller/concurrentadmission/controller.go#L786-L792)):

```go
quotaReserved := apimeta.FindStatusCondition(wl.Status.Conditions, kueue.WorkloadQuotaReserved)
if quotaReserved == nil {
    wlLog.Info("Variant has not been evaluated for admission yet")
    return nil
}
wlLog.Info("Variant does not require preemption")
continue
```

A `WorkloadQuotaReserved` condition with reason `PendingEvaluation` ([constant](https://github.com/kubernetes-sigs/kueue/blob/4a91e9c26b5652a6043f1cf66d5115e453d459fd/apis/kueue/v1beta2/workload_types.go#L977)) carries no scheduler decision — it means the opposite, that the Variant is still awaiting one. The condition is present, so the guard does not fire, the loop keeps scanning, and the controller opens the preemption gate of a less favorable Variant that happened to be evaluated first.

The choice is then pinned. `latestOpenGateTime` refuses to ungate any other Variant until `preemptionTimeout` elapses ([code](https://github.com/kubernetes-sigs/kueue/blob/4a91e9c26b5652a6043f1cf66d5115e453d459fd/pkg/controller/concurrentadmission/controller.go#L765-L773)), which is 5 minutes ([code](https://github.com/kubernetes-sigs/kueue/blob/4a91e9c26b5652a6043f1cf66d5115e453d459fd/pkg/controller/concurrentadmission/controller.go#L68)). The concurrentadmission controller only ever opens gates, never closes them; the one path that closes a gate is eviction, through `closeAllPreemptionGates` ([code](https://github.com/kubernetes-sigs/kueue/blob/4a91e9c26b5652a6043f1cf66d5115e453d459fd/pkg/workload/evict/evict.go#L265-L270)). So the preferred Variant stays locked out for the full 5 minutes, and the observable symptom is a `PreemptionUngatedVariant` event ([code](https://github.com/kubernetes-sigs/kueue/blob/4a91e9c26b5652a6043f1cf66d5115e453d459fd/pkg/controller/concurrentadmission/controller.go#L840)) naming the wrong Variant.

Two sites stamp `PendingEvaluation` on a Variant that is awaiting evaluation and reaches `firstCandidateVariant`:

| Site | Gating |
|---|---|
| `clearWorkloadAdmission`, after eviction ([code](https://github.com/kubernetes-sigs/kueue/blob/4a91e9c26b5652a6043f1cf66d5115e453d459fd/pkg/controller/concurrentadmission/controller.go#L435-L441)) | via `UnadmittedWorkloadReasonWithFallback` |
| `resolveGranularUnadmittedQuotaReservedCondition`, on first reconciliation ([code](https://github.com/kubernetes-sigs/kueue/blob/4a91e9c26b5652a6043f1cf66d5115e453d459fd/pkg/controller/core/workload_controller.go#L2161-L2166)) | `UnadmittedWorkloadsExplicitStatus`, for the condition-absent case only |

Both go through `UnadmittedWorkloadReasonWithFallback`, which returns the granular reason when `UnadmittedWorkloadsObservability` is enabled ([code](https://github.com/kubernetes-sigs/kueue/blob/4a91e9c26b5652a6043f1cf66d5115e453d459fd/pkg/workload/workload.go#L1766-L1771)). That gate is Beta and defaults to **true** ([code](https://github.com/kubernetes-sigs/kueue/blob/4a91e9c26b5652a6043f1cf66d5115e453d459fd/pkg/features/kube_features.go#L920-L922)), so the post-eviction route needs nothing flipped beyond `ConcurrentAdmission` itself. The first-reconciliation route additionally needs `UnadmittedWorkloadsExplicitStatus`, which is off by default ([code](https://github.com/kubernetes-sigs/kueue/blob/4a91e9c26b5652a6043f1cf66d5115e453d459fd/pkg/features/kube_features.go#L928-L930)).

The scheduler sets the same reason on Variants it *has* evaluated — a more favorable sibling was admitted, migration was refused, admission checks were rejected. I have not found a path where those reach `firstCandidateVariant`: `deactivateVariants` deactivates the migration-refused set earlier in the same reconcile, and `IsAdmissible` then drops inactive Variants. This issue is about the two sites above.

**What you expected to happen**:

`firstCandidateVariant` waits for the more preferred Variant instead of ungating a less favorable one, i.e. it treats reason `PendingEvaluation` the same as a missing `WorkloadQuotaReserved` condition:

```go
if quotaReserved == nil || quotaReserved.Reason == kueue.WorkloadQuotaReservedReasonPendingEvaluation {
    wlLog.Info("Variant has not been evaluated for admission yet")
    return nil
}
```

**How to reproduce it (as minimally and precisely as possible)**:

I have not reproduced this on a cluster; the sequence above comes from reading `firstCandidateVariant` and the sites that stamp `PendingEvaluation`. At the unit level it is deterministic, as a case in `TestFirstCandidateVariant` ([code](https://github.com/kubernetes-sigs/kueue/blob/4a91e9c26b5652a6043f1cf66d5115e453d459fd/pkg/controller/concurrentadmission/controller_test.go#L2288)):

1. `first`: a preferred Variant carrying `WorkloadQuotaReserved=False` with reason `PendingEvaluation` and no `BlockedOnPreemptionGates` condition — that is, the existing `skips a preferred variant with an existing quota reservation condition` case with the reason swapped from the legacy `Pending` to `PendingEvaluation`.
2. The less favorable Variant is the `blocked` fixture the other cases already use, carrying `BlockedOnPreemptionGates=True`.
3. `want`: `nil` — wait for the preferred Variant.

Actual: `firstCandidateVariant` returns `blocked`, which `selectVariantToOpenPreemptionGate` then ungates.

On a cluster the same shape is reachable by enabling `ConcurrentAdmission`, letting a parent Workload fan out into Variants across ordered flavors, and having the preferred Variant evicted (so `clearWorkloadAdmission` stamps `PendingEvaluation`) while a less favorable sibling already carries `BlockedOnPreemptionGates=True`.

**Anything else we need to know?**:

- This is unreleased. #14272 merged as [3e8402c95](https://github.com/kubernetes-sigs/kueue/commit/3e8402c956b3ddd117b62effc8b89a7211f3f896) on 2026-08-12 and is not contained in any tag, including `v0.20.0`, so only `main` is affected and no released version needs a patch.
- `ConcurrentAdmission` is Alpha and defaults to false ([code](https://github.com/kubernetes-sigs/kueue/blob/4a91e9c26b5652a6043f1cf66d5115e453d459fd/pkg/features/kube_features.go#L885-L887)), so this needs an opt-in.
- The existing case `skips a preferred variant with an existing quota reservation condition` ([code](https://github.com/kubernetes-sigs/kueue/blob/4a91e9c26b5652a6043f1cf66d5115e453d459fd/pkg/controller/concurrentadmission/controller_test.go#L2306-L2313)) feeds `evaluatedForAdmissionCondition`, whose reason is `kueue.WorkloadPending` ([code](https://github.com/kubernetes-sigs/kueue/blob/4a91e9c26b5652a6043f1cf66d5115e453d459fd/pkg/controller/concurrentadmission/controller_test.go#L76-L84)). The suite therefore already treats reason `Pending` as "evaluated", which is one of the two meanings this issue is about separating.
- Matching `PendingEvaluation` does not cover a deployment that disables `UnadmittedWorkloadsObservability`. With that gate off, `UnadmittedWorkloadReasonWithFallback` returns the legacy `kueue.WorkloadPending` and `requeueAndUpdate` collapses every reason to the same literal ([code](https://github.com/kubernetes-sigs/kueue/blob/4a91e9c26b5652a6043f1cf66d5115e453d459fd/pkg/scheduler/scheduler.go#L1226-L1228)), so "not evaluated" and "evaluated, needs no preemption" become the same string and no discriminator exists. Widening the check to `Pending` would make `firstCandidateVariant` return `nil` unconditionally and never ungate anything. Closing that properly is a feature-gate-dependency question — there is precedent in `defaultFeatureGateDependencies` ([code](https://github.com/kubernetes-sigs/kueue/blob/4a91e9c26b5652a6043f1cf66d5115e453d459fd/pkg/features/kube_features.go#L672)) — and I would rather handle it separately than fold it in here.
