`@mimowo`, the root cause is a failed pull from Quay. This is not a Kueue test failure and is unrelated to PR `#15551`, which changes only `.coderabbit.yaml`.

## Root cause

The Prometheus StatefulSet Pod, `monitoring/prometheus-prometheus-0`, scheduled successfully on `kind-worker2`.

Its `init-config-reloader` container completed. Its `config-reloader` container also became ready.

The main `prometheus` container could not pull:

```text
quay.io/prometheus/prometheus:v3.9.1
```

The exported node diagnostics show these failures:

```text
failed to pull and unpack image "quay.io/prometheus/prometheus:v3.9.1":
read tcp 172.18.0.4:49716->18.116.224.38:443: read: connection reset by peer
```

A later retry also failed:

```text
dial tcp 3.14.204.72:443: i/o timeout
```

Kubelet then put the container into `ErrImagePull` and `ImagePullBackOff`. The Pod could not become ready. Therefore, the StatefulSet kept `readyReplicas: 0`.

`WaitForPrometheusAvailability` then timed out after 90 seconds while it waited for one ready replica.

## Impact

All four Ginkgo processes report the same `BeforeSuite` failure because they use the same Kind cluster and the same unavailable Prometheus StatefulSet. No test spec ran.

## Recommended action

Treat this as a CI infrastructure or external registry flake.

To reduce recurrence, preload `quay.io/prometheus/prometheus:v3.9.1` into the Kind nodes during test setup, as the job already does for Prometheus Operator images. This removes the runtime dependency on Quay during suite startup.

Separately, improve `test/util/e2e.go` so that a Prometheus readiness timeout prints the StatefulSet and Pod status, Events, and container waiting reasons. That diagnostic would have exposed `ImagePullBackOff` directly instead of only reporting `0 != 1`.

`@mimowo`, you are correct.

The retry mechanism exists in `hack/testing/e2e-common.sh`. `e2e_docker_pull_if_needed` retries `docker pull` seven times.

The Prometheus setup omits the main Prometheus image:

- `prepare_docker_images` pre-pulls `PROMETHEUS_OPERATOR_IMAGE`.
- `prepare_docker_images` pre-pulls `PROMETHEUS_CONFIG_RELOADER_IMAGE`.
- `install_prometheus_operator` loads those same two images into the Kind nodes.
- Neither path pre-pulls or loads `quay.io/prometheus/prometheus:v3.9.1`.

The Prometheus Operator later creates the StatefulSet from the Prometheus custom resource. At that point, the Kind node must pull the main Prometheus image directly from Quay. That direct pull caused the failure.

The fix should add the main Prometheus image to both operations:

1. Pre-pull it through `e2e_docker_pull_if_needed`.
2. Load it into every Kind node through `cluster_kind_load_image`.

This will apply the existing retry policy before the suite starts. It will also prevent the Prometheus StatefulSet from depending on Quay at runtime.
