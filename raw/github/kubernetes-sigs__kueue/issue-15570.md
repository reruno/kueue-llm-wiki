## Description

**What would you like to be added**:

An opt-in relaxation of the pod-template shape comparison the LWS integration's validating webhook performs on updates, so that field classes that cannot change quota requirements can be updated in place on an already-managed LeaderWorkerSet.

Two candidate field classes, in priority order:

1. Tolerations (add, remove, replace). Tolerations enter the shape today and feed flavor selection at admission. They cannot change quota accounting, and a fleet-wide taint change (our case: a new taint rolled out for topology-aware scheduling) currently forces recreating every LWS rather than rolling template updates.
2. Init containers with unchanged effective-request envelope and port set. The kubelet's effective pod request is `max` over init containers and `sum` over app containers; the current positional-list comparison rejects even a zero-resource init-container addition. A name-keyed envelope comparison (per-resource max, port set union) admits exactly the quota-neutral set.

The shape comparison itself should stay the default. One opt-in workaround we are considering: a `matchConditions` entry on `vleaderworkerset.kb.io` that skips the validator when the object has equal producer-computed shape-hash annotations on both sides of an update (hash input is the shape minus the relaxed classes). 

**Why is this needed**:

Serving operators need to change LWS pod templates on live traffic without disruptive recreate cycles. Our specific incidents, both verified on a quota-backed v0.19.3 deployment today:

- A fleet-wide taint addition required a matching toleration on serving workloads. Kueue-managed LWS updates to add it are rejected with `field is immutable`, so the only in-band path is delete-and-recreate, a multi-hour disruption per fleet rollout.
- Pre-existing workloads whose templates predate a toleration become un-restartable in effect: replacement pods after crash/preemption re-enter admission against Workload PodSets frozen with the pre-change shape and sit scheduling-gated indefinitely.

We verified the current behavior against `v0.19.3` (files `pkg/controller/jobs/leaderworkerset/leaderworkerset_webhook.go`, `pkg/util/pod/pod.go`) with a live A/B: the same tolerations patch is rejected when the LWS has the queue label and accepted when it does not.

**Completion requirements**:

This enhancement requires the following artifacts:

- [ ] Design doc
- [ ] API change (flag or field on the LWS integration choosing the relaxed comparison)
- [ ] Docs update

Upstream questions we would like input on:

1. Is the shape comparison's primary purpose quota-invariant protection, and if so, should tolerations belong to a separate relaxation class?
2. For init containers, is name-keyed envelope comparison (per-resource max, port union) acceptable as the default for the LWS integration?
3. Is a per-update opt-in (annotation, flag, or admission-level policy) acceptable to own the relaxation?

### Comment by [@anguszzzz](https://github.com/anguszzzz) — 2026-09-18T06:12:09Z

   We ran the reproduction and the requeue check for this issue on a production v0.19.3 cluster, using a real queue-managed serve endpoint from our online-serving platform (LWS, 2 groups, live traffic through the
 ingress). Our serving control plane renders the LWS templates for these jobs.

   1. Adding a toleration to `workerTemplate.spec.tolerations` is rejected by `vleaderworkerset.kb.io`: `spec.leaderWorkerTemplate.workerTemplate.spec.tolerations: Invalid value: [...]: field is immutable`.
   2. Adding an initContainer with no resource requests is rejected the same way. The error payload shows the comparison list directly (`[{"ports":null,"resources":{"requests":null}},
 {"ports":null,"resources":{"requests":{"cpu":"xxx","memory":"xxx"}}}, ...]`), so position decides the outcome, not quota effect.
   3. One input for the init-container envelope rule: our platform-rendered templates already include an init container whose requests match the app container. The comparator has to handle
 init containers with real requests, not only zero-resource additions.

   On whether a rebuilt Workload can roll without interrupting the running LWS:

   4. I deleted one group's Workload while the endpoint was serving. The controller recreated it within a second and re-admitted it in 1–2 seconds (`QuotaReserved` and `Admitted` both true at +2s). The replacement
 pod stayed scheduling-gated until admission, then started normally. The sibling group was never touched, and 120/120 requests returned 200 during the window. So per-group delete/recreate works as a base for rolling re-admission in the quota-neutral case. 

   Follow up on the open questions: (1) I think keeping tolerations as a separate relaxation class matches what we see, and I can send the PR behind an LWS-scoped feature gate, same pattern as `LWSImmutableGroupSize`
 (#13279). (2) The name-keyed envelope comparison works for us, I can add the comparator matrix tests with it. (3) Waiting Kueue maintainer's input on this
