## Description

<!-- Please only use this template for submitting enhancement requests -->

**What would you like to be added**:

When Kueue cannot admit a RayCluster worker group because of insufficient quota,
Kueue should signal that to the Ray Autoscaler by adding a scaling gate to that
worker group's `scaleStrategy.scaleGate` in the RayCluster spec, and remove the
gate once the group becomes admissible again.

1. Kueue should support partial admission when the Ray Autoscaler requests multiple nodes for a worker group but there isn't enough quota for all of them. 
2. Kueue should only add a scale gate to the worker group when the remaining quota isn't even sufficient for a single node.
3. When scale down is detected, Kueue removes gate from corresponding workergroup.

KubeRay added the field for exactly this purpose in
[ray-project/kuberay#5094](https://github.com/ray-project/kuberay/pull/5094)
(design discussion in [ray-project/kuberay#5233](https://github.com/ray-project/kuberay/issues/5233)):

```go
// ScaleStrategy controls scaling of a worker group.
type ScaleStrategy struct {
    WorkersToDelete []string `json:"workersToDelete,omitempty"`

    // ScaleGate is a signal written by an external controller to indicate that
    // this worker group cannot currently be scaled up. KubeRay preserves the
    // field across reconciles but never reads or writes it; the Ray Autoscaler
    // consumes it and falls back to another worker group while it is non-empty.
    // +optional
    // +listType=map
    // +listMapKey=type
    ScaleGate []ScaleGate `json:"scaleGate,omitempty"`
}

// ScaleGate marks a worker group as not currently scalable. type is the merge
// key, so a gate is added and removed by exactly one controller.
type ScaleGate struct {
    Type string `json:"type"`
}
```

On the wire:

```yaml
spec:
  workerGroupSpecs:
  - groupName: gpu-worker-group
    scaleStrategy:
      scaleGate:
      - name: kueue.x-k8s.io/quota-exceeded
```

**Why is this needed**:

Kueue enforces quota through Pod scheduling gates. When a worker group exceeds
its quota, the Pods are created but stay gated on `kueue.x-k8s.io/admission`,
and the `Workload` carries `QuotaReserved=False` (`Reason: Pending`).

From the Ray Autoscaler's point of view a gated Pod is indistinguishable from a
slow-starting one: the node request transitions to `ALLOCATED` and the
autoscaler waits for `RAY_AUTOSCALER_RECONCILE_ALLOCATE_STATUS_TIMEOUT_S`
(default 3600s) before declaring failure and falling back to a lower-priority
worker group.

Kueue is the component that knows the difference, and it is the only scheduler
that is already aware of the RayCluster CRD. Writing the gate turns an hour-long
stall into a single reconcile cycle.

### Comment by [@NasitSony](https://github.com/NasitSony) — 2026-09-15T20:48:34Z

The KubeRay side looks well specified — the merge-key design means Kueue can own exactly one gate name without fighting other controllers.

The part I'd want pinned down before a design doc is where the two signals come from. Writing the gate needs "this worker group cannot currently be admitted," and removing it needs the inverse, promptly enough that a group doesn't stay gated after quota frees up.

`QuotaReserved=False` on the Workload is per-Workload, not per-worker-group, so for a RayCluster with several groups it doesn't say which group is the problem. Is the intent to derive this per pod set from the flavor assignment result, or to gate every worker group whenever the whole Workload can't be admitted? Those give quite different autoscaler behaviour — the second would stop the autoscaler falling back within the same cluster, which seems like the opposite of the goal.

Also worth deciding whether removal is driven by admission succeeding or by a periodic re-evaluation, since quota can free up without any event on this Workload.

### Comment by [@NasitSony](https://github.com/NasitSony) — 2026-09-20T04:58:04Z

Followed up on where the per-pod-set information lives, since it decides how big this is.

The scheduler does compute it: `flavorassigner.PodSetAssignment` is per pod set, with empty `.Flavors` meaning NoFit for that pod set, `.Status` carrying the reasons, and `FlavorAssignmentAttempts` recording what was tried. So inside a scheduling cycle, "worker group B doesn't fit" is known precisely.

But it doesn't survive the cycle. The `Assignment` lives on the in-memory `entry` in `scheduler.go` and is discarded at the end. What gets written to the Workload on failure is `QuotaReserved=False` with a single prose `inadmissibleMsg`, plus the same string as an event — workload-level, not per-pod-set.

So a controller that wants to gate one worker group can't currently derive which group to gate. Either the per-pod-set assignment result needs persisting somewhere readable (a status field, presumably), or the gate has to be written from inside the scheduling cycle, which is a bigger layering change than it sounds.

Worth deciding which before a design doc, since it's most of the work.

### Comment by [@kvnloo](https://github.com/kvnloo) — 2026-09-20T20:57:50Z

AI-assisted: I used an AI assistant to trace the ScaleGate lifecycle and Kueue's inadmissible-workload requeue behavior; I reviewed the relevant discussion/code paths myself.

One more lifecycle invariant seems worth defining here in addition to the per-worker-group signal and SSA ownership discussion: should the Kueue-owned gate be treated as derived, level-triggered state rather than something removed only on particular transition events?

The normal scheduler requeue path should help when quota changes and the Workload gets evaluated again. I'm more concerned about the persisted "RayCluster.spec...scaleGate" surviving cases such as:

- Kueue restarting while its gate is already present;
- the corresponding Workload being deleted/replaced;
- the worker group scaling down or disappearing;
- the integration/feature being disabled;
- current state no longer justifying the old gate before the transition that would have cleared it was observed.

In those cases reality can become:

"worker group is admissible / no longer requested"

while the RayCluster still says:

"kueue.../quota-exceeded"

and the autoscaler will continue treating the preferred group as unavailable.

Would it make sense to define the desired state as:

«for every worker group, Kueue's ScaleGate entry exists iff the current Kueue state says that group cannot admit even its minimum useful increment»

and make reconciliation converge the persisted RayCluster field toward that state?

A restart/resync regression test seems particularly useful: begin with a stale Kueue-owned gate already persisted on the RayCluster, start/reconcile Kueue with state in which the group is now admissible (or no longer requested), and verify the gate is removed without depending on replaying the original transition that would normally clear it.

That would make the ScaleGate behave more like ordinary controller-owned desired state and less like an edge-triggered cleanup obligation.

### Comment by [@NasitSony](https://github.com/NasitSony) — 2026-09-28T02:18:22Z

+1 on level-triggered — and I think it makes the persistence question sharper rather than orthogonal to it.

A reconciler converging toward "gate exists iff this group can't admit its minimum increment" has to be able to evaluate that predicate at any time, without having observed the transition that would have set or cleared it. That's exactly what isn't possible today: the per-pod-set fit result lives on the in-memory `entry` in `scheduler.go` and is discarded when the cycle ends, so outside a scheduling cycle there's nothing to recompute from beyond `QuotaReserved=False` and a prose message.

An edge-triggered design could at least write the gate at the moment the scheduler knew. A level-triggered one can't, unless either the assignment result is persisted where a controller can read it, or the reconciliation runs inside the scheduling cycle.

The restart/resync test you describe is the right one to write first, since it fails under any design that depends on replaying a transition.
