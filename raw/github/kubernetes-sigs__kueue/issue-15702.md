## Description

**What happened**:

Kueue can overestimate a pending Workload's CPU request when the Pod template has a pod-level CPU limit, no explicit pod-level CPU request, and a smaller aggregate container request.

For one Pod with a container request of `1` CPU and a pod-level limit of `4` CPU:

- Kubernetes v1.37.0 creates the Pod with a pod-level request of `1` CPU.
- Kueue defaults the pod-level request to `4` CPU and calculates `4000m` in `Info.TotalRequests`.

This is a pre-existing issue in `UseLimitsAsMissingRequestsInPod`, reproduced both on the base commit and on #15284. The migration in that PR preserves this behavior.

**What you expected to happen**:

Kueue's effective resource requests should match those of the Pod created by the Kubernetes API server. For the example above, the effective request should be `1` CPU.

Explicit pod-level requests must remain unchanged, and a pod-level limit should still supply the default where appropriate when no container request contributes to it.

**How to reproduce it (as minimally and precisely as possible)**:

Use this Pod spec, with no LimitRanges or RuntimeClass involved:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: pod-level-request-defaulting
spec:
  resources:
    limits:
      cpu: "4"
  containers:
  - name: main
    image: registry.k8s.io/pause:3.10
    resources:
      requests:
        cpu: "1"
```

1. Create the Pod using a Kubernetes v1.37.0 API server with default feature gates and inspect `spec.resources.requests.cpu`. The API server returns `1`.
2. Put the same un-defaulted Pod spec into a Workload with one PodSet and `count: 1`.
3. On base commit `8e6c6dee5e63b652ab151c8b9b3e04c7589bf35c`, run `AdjustResources` followed by `NewInfo`. On PR #15284 head `7bec2a85b37160ab2ff31cb73815bd974b706fc4`, use `NewInfoFromClient` instead.
4. Observe an effective pod-level request of `4` and `TotalRequests[0].Requests.ResourceValue(corev1.ResourceCPU) == 4000` on both versions.

The defaulting mismatch can also be isolated by passing this PodSpec to `workload.UseLimitsAsMissingRequestsInPod`: it copies the pod-level limit into the missing request without considering aggregate container requests.

The following cases were verified against actual Pod creation through a Kubernetes v1.37.0 API server started with envtest, as well as Kueue resource accounting on both commits:

| Input | API server pod-level CPU request | Kueue base and PR CPU request |
| --- | --- | --- |
| Container request `1`, pod limit `4` | `1` | `4` |
| Container limit `1`, pod limit `4` | `1` | `4` |
| No container request/limit, pod limit `4` | `4` | `4` |
| Explicit pod request `2`, container request `1`, pod limit `4` | `2` | `2` |
| Container requests `1` + `2`, pod limit `8` | `3` | `8` |
| Init container request `2`, regular container request `1`, pod limit `4` | `2` | `4` |

Each Workload had one Pod, and Kueue's `TotalRequests` matched its effective requests shown above. This verifies an accounting mismatch; the probe did not run a complete Kueue admission/scheduling cycle.

**Anything else we need to know?**:

- Filed as a follow-up requested in [the review of #15284](https://github.com/kubernetes-sigs/kueue/pull/15284#issuecomment-5711505162), rather than as a prerequisite fix for that migration.
- [The verification reply](https://github.com/kubernetes-sigs/kueue/pull/15284#discussion_r4032460395) establishes that the behavior also exists on the base branch.
- [Affected helper at the tested base commit](https://github.com/kubernetes-sigs/kueue/blob/8e6c6dee5e63b652ab151c8b9b3e04c7589bf35c/pkg/workload/resources.go).
- Resource-lookup error propagation is a separate issue tracked by #9030 / #13681 and is outside this report's scope.
- Regression coverage should compare against API-server defaulting, including the explicit-request and no-container-request controls above. Calling only `SetDefaults_Pod` is insufficient as an API-server reference for the v1.37 defaulting path.
