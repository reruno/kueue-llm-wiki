## Description

**What would you like to be added**:

Two opt-in mechanisms for the LWS integration:

1. **Relax the template-update validation for quota-neutral field classes.**
   The update check compares old and new pod templates over `SpecShape`
   (placement + per-container `resources.requests`/`ports`, init containers
   positional), so even a toleration add or a zero-resource init container add
   is rejected with `field is immutable`. We would like to exclude tolerations,
   container ports, and init containers that leave the effective request
   envelope unchanged (per-resource max across init containers, sorted port
   union: the kubelet's own effective-request model).

2. **Support quota-bearing edits per group with rolling updates.**
   For `resources.requests` and container membership changes, delete the
   group's Workload inside the window where the roll has already drained that
   group, so it is recreated from the current template (`createWorkload` /
   `constructWorkload`) and re-admitted.
   `maxUnavailable: 1` then bounds disruption to one group at a time, and a
   group whose fresh admission does not fit stalls the roll at reduced
   capacity instead of reverting the accepted update.

Both behind feature gates; default behavior unchanged.

**Why is this needed**:

- Verified on v0.19.3: managed-LWS updates adding a toleration or an init
  container are rejected (`field is immutable` on
  `spec.leaderWorkerTemplate.workerTemplate.spec`), so a fleet-wide taint
  rollout forces delete-and-recreate of every LeaderWorkerSet. With a fleet of 
   many thousands of replicas of online applications running on LWS, rolling out 
   new tolerations or initContainers as part of critical cluster-wide
  upgrades is difficult.
- Verified on the same deployment: Workloads are never recomputed in place.
  PodSets are built only at creation and pinned once admitted
  (`ValidateWorkloadUpdate`); eviction paths clear `status.admission` and
  never touch `spec.podSets`. Deleting a Workload by hand gets it recreated
  from the current template and re-admitted; an admitted
  template edit rolls pods with no eviction or re-admission of the Workload,
  so the reservation silently stays one generation behind.
- Role naming is already static per role (`kueue.x-k8s.io/role-hash` =
  `main`/`leader`/`worker`), so replacement pods match their PodSets by name
  regardless of template edits. That makes mechanism 2 safe to build.

**Question for maintainers**:

Is this worth a KEP? In particular:

1. Is the quota-neutral/quota-bearing split of relaxable field classes
   acceptable, with the envelope rule for init containers?
2. For a rebuilt group that cannot be admitted, is "roll stalls at reduced
   capacity, `waitForPodsReady` requeues" the right contract?
3. Is roll-window delete/recreate acceptable, or is a Workload-level
   "recompute PodSets when unadmitted" transition preferable?

### Comment by [@mbobrovskyi](https://github.com/mbobrovskyi) — 2026-09-18T08:08:35Z

I investigated the complications I previously encountered with `nodeSelector`.

**Test scenario:**

1. Updated the LWS `nodeSelector` to a non-existent label. The StatefulSet started a rolling update from the last group, but the pods became stuck in `Pending` because no matching node was available. The rolling update stalled because the StatefulSet waits for each pod to become `Ready` before proceeding to the next group.
2. Updated the `nodeSelector` back to a valid value. The previously stuck `Pending` pods were not automatically recreated or updated. The StatefulSet did not apply the new template to those existing pods.
3. Manually deleted the stuck pods one by one, starting from the last group. Each pod was recreated using the updated template with the correct `nodeSelector`, became `Ready`, and the rolling update then proceeded group by group successfully.

The root cause appears to be the standard StatefulSet rolling update behavior rather than anything specific to Kueue or LWS.

Based on this, the delete-Workload-in-roll-window approach should work as expected as long as the `nodeSelector` is valid and a matching node is available. If a user configures an invalid `nodeSelector` and the pods become stuck in `Pending`, manual pod deletion in ordinal order (last to first) is required to recover the rollout.

This behavior is a Kubernetes StatefulSet limitation and appears to be outside the scope of the Kueue or LWS integration.
