### Comment by [@Huangpinhan](https://github.com/Huangpinhan) — 2026-09-19T18:23:41Z

Hi @mbobrovskyi, I'd like to work on this if you're not planning to do it yourself alongside #15711.

My plan is to follow the same structure as #15711:
1. Add a composite action `.github/actions/create-devel-tag/action.yml` that derives the devel tag from the release version (e.g. `v0.20.0` -> `v0.21.0-devel`), creates an unannotated tag on `main`, and pushes it.
2. Wire up `/create-devel-tag` in `release-utils.yml` (trigger, command parsing, and a job that reports via `report-result`).
3. Only allow `vX.Y.0` versions, and treat an already-existing tag as success so the command can be re-run safely.
4. Require the release branch (e.g. `release-0.20`) to exist, and refuse to tag if `main` HEAD is still reachable from it. Otherwise release-branch builds would pick up the devel tag via `git describe`.
5. Update `NEW_RELEASE.md` to use `/create-devel-tag` instead of the manual step.

With the check in (4), tagging the current `main` HEAD when the command runs should be enough, instead of locating the exact first commit after branching. Does that sound OK?

I'll test it end-to-end in my fork and include the results in the PR.
