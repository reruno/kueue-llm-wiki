**What happened**:
When a ResourceFlavor is removed from a ClusterQueue with `concurrentAdmissionPolicy`, the parent Workload is evicted even though it is running and a replacement variant is created in the same reconcile.

Within one `Reconcile` pass:

1. `deleteStaleVariants` deletes the admitted variant, because its flavor is no longer in `flavorOrder`.
2. `createVariants` creates a variant for the new flavor. It has not been through the scheduler, so it is not admitted.
3. `syncAdmissionStatus` calls `getAdmittedVariant`, which returns nil, hits the `admittedVariant == nil && workload.IsAdmitted(parent)` branch, and writes `Evicted` / `ConcurrentAdmission` / "No variant is running" onto the parent.

The parent's own admission is still valid at that point — only the object that was tracking it has been replaced.

**What you expected to happen**:

The parent keeps its admission while a replacement variant is created and scheduled. Eviction should happen when the workload genuinely has nothing running, not when variants are being churned by a ClusterQueue edit.

**How to reproduce it (as minimally and precisely as possible)**:
Unit test against `TestReconcile` in `pkg/controller/concurrentadmission/controller_test.go`:

- ClusterQueue with `ConcurrentAdmissionPolicy` and flavor `spot` only
- parent Workload labelled `ConcurrentAdmissionParentLabelKey`, admitted on `spot`
- one variant on `on-demand`

The parent comes back with an `Evicted` condition.

**Anything else we need to know?**:
Found while adding coverage for a related case in #14954. The eviction branch in `syncAdmissionStatus` has no guard for "variants are mid-replacement" — it only distinguishes finished parents. One option is to skip the eviction when variants were created in the same pass; another is to require the parent to have been without an admitted variant across more than one reconcile.

Note `syncVariantEvictionStatus` already handles the case where an admitted variant is *evicted* — it propagates that to the parent with reason `VariantEvicted`, which is correct, since the admission genuinely went away. The gap is that a variant being *deleted* during flavor churn is treated the same way by `syncAdmissionStatus`, even though the parent's admission is still valid and a replacement variant is being created in the same pass.

**Environment**:
- Kubernetes version (use `kubectl version`): 1.36
- Kueue version (use `git describe --tags --dirty --always`): v0.20.0-rc.1-12-ge27680c3a
