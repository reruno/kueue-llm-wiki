## Description

**What would you like to be cleaned**:

Replace the comment-based leader-capacity contract in `pkg/cache/scheduler/tas_flavor_snapshot.go` with a dedicated `leaderDomainState` owned by `domainState`.

**Why is this needed**:

This makes leader-only capacity fields explicit and prevents leaderless placement from depending on `podCountWithLeader`, `sliceCountWithLeader`, or `leaderCount`.

Requested by @tenzen-y in https://github.com/kubernetes-sigs/kueue/pull/15861#discussion_r4069967952. Related PR: https://github.com/kubernetes-sigs/kueue/pull/15861.

### Comment by [@pajakd](https://github.com/pajakd) — 2026-09-23T05:45:07Z

Yeah, now that we decoupled the computations, we could decouple the structs. In general the direction looks good. I'm just thinking that simply separating a struct might not scale. For example, now that I'm adding the tail handling (#15640) I need extra fields `WithTail`, including `WithLeaderAndTail` (since a domain might hold both). So, the features are not orthogonal and we'll not be able to separate them into structs. 

I don't know if we will have more such "special" cases but I was thinking of refactoring all the `SliceCount` fields into an array

```
type obligationMask uint8
const (
	obligationNone   obligationMask = 0
	obligationLeader obligationMask = 1 << 0
	obligationTail   obligationMask = 1 << 1
)

type domainState struct {
	podCount   int32
    leaderCount int32
	// sliceCap[mask] is the whole-slice capacity while also hosting `mask` (nothing, leader, tail or both)
	sliceCount   [4]int32
	...
}
```
