**What happened**:

Eight single-GPU jobs were submitted to a manager `ClusterQueue` whose only flavor was one keyed on a node label naming our largest accelerator. The manager admitted all eight against that flavor and charged its quota accordingly. Across the workers, two ran on one accelerator type, four on a second, and two on the flavor the manager had charged.

Inspecting a mirrored `Workload` on the worker showed it carrying a node selector for an accelerator the manager never chose. Kueue injects the flavor's node labels as a node selector on admission, but it does so to the manager's local copy, which is not what is mirrored.

```
manager   job-0   admitted against   <largest-accelerator flavor>
worker    job-0   admitted against   <smallest-accelerator flavor>
```

Nothing surfaced this as an error. Every job succeeded.

**What you expected to happen**:

We expected the flavor the manager admitted a `Workload` against, and charged quota for, to be the
flavor the work ran on, so that manager-side per-flavor totals describe the fleet.

We read per-flavor quota on the manager as a description of the fleet, and our capacity planning rests on it. If a manager-side flavor total can disagree with what actually ran, then it is an admission gate rather than a description, and we should stop reading it the way we do.

**How to reproduce it (as minimally and precisely as possible)**:

This is what we ran rather than a reduced case. We are glad to build a minimal reproduction if that would help.

1. Configure a manager cluster and at least two worker clusters with `MultiKueueConfig` and `MultiKueueCluster` objects, and an admission check using the `kueue.x-k8s.io/multikueue` controller.
2. On the manager, define a `ClusterQueue` whose resource group provides a GPU resource through a single `ResourceFlavor` keyed on a node label naming one accelerator type.
3. On the workers, define `ResourceFlavor`s keyed on their own node labels, such that they do not correspond one-to-one with the manager's flavor. At least one worker should offer a different accelerator type from the one the manager's flavor names.
4. Submit several jobs requesting one GPU each, with no node selector on the pod template, so that placement is unconstrained.
5. Compare `Status.Admission.PodSetAssignments` on the manager's `Workload` with the same field on the mirrored `Workload` on the worker that ran it, and with where the pod actually landed.

The manager names its own flavor for every job. The worker need not agree.

**Anything else we need to know?**:

A `ClusterQueue` resource group may hold several `ResourceFlavor`s providing the same resource name. That is the ordinary way to express "the same resource, on differently labelled or tainted nodes", and it means a `Workload` requesting that resource without constraining placement is satisfiable by any flavor in the group. The manager picks one and charges that flavor's `nominalQuota`.

The chosen flavor is recorded in `Status.Admission.PodSetAssignments` ([`workload_types.go#L639`](https://github.com/kubernetes-sigs/kueue/blob/v0.18.8/apis/kueue/v1beta2/workload_types.go#L639)), which is status rather than spec. When MultiKueue creates the `Workload` on a worker,
`cloneForCreate` ([`multikueue/workload.go#L1331`](https://github.com/kubernetes-sigs/kueue/blob/v0.18.8/pkg/controller/admissionchecks/multikueue/workload.go#L1331)) copies `ObjectMeta` and `Spec` only:

```go
remoteWl.ObjectMeta = api.CloneObjectMetaForCreation(&orig.ObjectMeta)
...
orig.Spec.DeepCopyInto(&remoteWl.Spec)
```

So the remote `Workload` arrives with no admission, and the worker's `ClusterQueue` runs its own flavor assignment from scratch against the worker's own flavors.

Where the worker's flavors do not correspond one-to-one with the manager's, and the pod template does not constrain placement, the worker's choice need not match what the manager charged. Nothing surfaces that as an error. The job runs and succeeds, and the manager's per-flavor accounting describes a flavor that did not run it.

Our own flavors are keyed on node labels, and jobs submitted through our launcher set a matching node selector, which constrains the worker to the same choice the manager made. Those are unaffected. The divergence above came from hand-submitted work, which carries no such constraint, so what protects the common path is a convention in our launcher rather than anything Kueue guarantees.

What would help is knowing which of these is intended:

* The manager's assignment is meant to be authoritative, in which case not copying it is a bug and we can put together a minimal reproduction.
* The worker's assignment is authoritative by design, and manager-side per-flavor quota is a local admission gate rather than a statement about where work ran.

If it is the second, a sentence saying so in the MultiKueue documentation would have saved us the investigation. The current text describes how quota is consumed on the manager without saying whether the flavor dimension of it survives dispatch, and we read it the first way.

A third possibility we would understand: that keeping a manager-side assignment meaningful across heterogeneous workers is not something MultiKueue can promise, since the worker's flavors are defined independently and need not have counterparts. If that is the reasoning, it is worth recording, because it explains the design rather than just the behavior.

### Comment by [@HasonoCell](https://github.com/HasonoCell) — 2026-09-23T06:07:16Z

I spent some time tracing the current MultiKueue code path. The manager records its flavor choice in the Workload's status.admission, but cloneForCreate copies only metadata and spec to the worker. The worker then makes its own flavor assignment, and the chosen flavor's node labels are applied to the Job's Pod template when it starts. syncAdmittingRemoteState marks the manager's admission check Ready and records the worker cluster, but does not copy the worker's flavor assignment back to the manager.

It would be helpful to clarify whether independent flavor assignment is the intended MultiKueue behavior. If so, I think the documentation should explicitly say that manager-side per-flavor quota controls dispatch eligibility and does not necessarily reflect the flavor used on workers. If the assignments are expected to match, we would need to define how flavors map across workers with different configurations.
