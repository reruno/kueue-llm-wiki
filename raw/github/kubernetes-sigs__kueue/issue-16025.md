## Description

**What would you like to be added**:

A counter for excess pods that Kueue deletes from a pod group, e.g. `kueue_excess_pods_deleted_total`, incremented where `removeExcessPods` emits the `ExcessPodDeleted` event.

The [Metrics section of KEP-976](https://github.com/kubernetes-sigs/kueue/tree/main/keps/976-plain-pods#metrics) lists three counters that were never implemented. I propose adding only this one:

- `pods_gated_total`: the gate is added in the mutating webhook, so a counter there would also count dry-run requests and creations the API server later rejects.
- `pods_ungated_total`: already covered by `kueue_pod_scheduling_gate_removal_seconds_count{name="kueue.x-k8s.io/admission"}`.
- `pods_rejected_total`: Kueue deletes excess pods rather than rejecting them, so the name should say "deleted".

Open question: which labels to use. One deletion path runs before the Workload exists and the other can run before admission, so `cluster_queue` is not always known.

**Why is this needed**:

Excess-pod deletions are only visible as `ExcessPodDeleted` events, which expire and cannot be aggregated or alerted on. A counter lets operators see how often pod groups are over-created.
