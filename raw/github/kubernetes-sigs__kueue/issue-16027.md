## Description

**What would you like to be cleaned**:

Revisit and document the contract of `jobframework.GenericJob.IsActive`, then audit every built-in job integration against that contract.

The interface currently says that `IsActive` returns true when there are running Pods, but the generic reconciler uses it in multiple lifecycle contexts, including:

- deciding whether a suspended job with no matching Workload is safe to recreate;
- deciding whether an evicted Workload can release its quota;
- handling the interval between requesting suspension and the integration controller completing it.

The audit should define expected behavior for at least these states:

- a newly created job that is suspended before its controller initializes status;
- an unsuspended job that is starting but not ready;
- a running job;
- a job whose suspension was requested but whose Pods are still terminating;
- a job whose suspension has completed;
- a resumed job with stale suspended status.

For integrations backed by third-party controllers, document the minimum compatible controller version and whether the implementation relies on status counters, state fields, or conditions.

Related investigation: https://github.com/kubernetes-sigs/kueue/pull/15980

**Why is this needed**:

The current implementations use different proxies for activity: active replica counters, readiness, phases, conditions, and controller-specific states. These signals do not necessarily have the same semantics as "has running Pods."

In particular, treating every RayCluster state other than `Suspended` as active prevents Kueue from creating a Workload for an initially suspended RayCluster whose status has not been initialized. Conversely, treating every non-`Ready` state as inactive can release quota before KubeRay finishes deleting Pods. This exposes an ambiguity in the shared `IsActive` contract rather than only a RayCluster-specific bug.

### Comment by [@phoenix1712](https://github.com/phoenix1712) — 2026-10-07T20:24:05Z

Input for the Kubeflow v1 rows (PyTorchJob, TFJob, JAXJob, PaddleJob, XGBoostJob). These share `KubeflowJob.IsActive()`, which is true only if some `status.replicaStatuses[].active != 0` ([kubeflowjob_controller.go#L134-L141](https://github.com/kubernetes-sigs/kueue/blob/v0.19.0/pkg/controller/jobs/kubeflow/kubeflowjob/kubeflowjob_controller.go#L134-L141)). In the training-operator, `active` counts only `Running` Pods without a `deletionTimestamp` ([status.go#L34-L50](https://github.com/kubeflow/trainer/blob/v1.9.4/pkg/core/status.go#L34-L50)); `Pending` Pods have been excluded on purpose since kubeflow/trainer#578. This differs from `batch/v1` Job, whose `status.active` includes `Pending` Pods.

How the states listed here map for a v1 Kubeflow job:

| State | `replicaStatuses[].active` | `JobSuspended` condition | `IsActive()` |
|---|---|---|---|
| new, suspended, status not initialized | absent | absent | false (correct: the Workload gets created) |
| unsuspended, starting but not ready (gated, unscheduled, pulling images, or created in the operator's current reconcile) | 0 | `False`, or absent if the operator never saw the job suspended | **false** |
| running | number of `Running` Pods | `False` or absent | true |
| suspend requested, operator hasn't reconciled yet | last written value | unchanged | **false unless a Pod was `Running` at the operator's last status write** |
| suspend handled, Pods still `Terminating` | 0, zeroed in the same status write that sets `JobSuspended=True`, right after the deletes are issued ([job.go#L146-L166](https://github.com/kubeflow/trainer/blob/v1.9.4/pkg/controller.v1/common/job.go#L146-L166)) | `True` | **false** |
| suspension completed, Pods gone | 0 | `True` | false (correct) |
| resumed, status still says suspended | 0 | `True` until the operator's next status write | false |

The second and fourth rows matter for "deciding whether an evicted Workload can release its quota". With preemption and a training-operator that lags behind (default `--controller-threads=1`), Kueue clears the reservation in the same pass as the suspend patch. It can then re-admit the Workload elsewhere and set `suspend=false` before the operator ever sees the suspend, and the old Pods are never deleted. We see this in production with TAS; the details and a repro are in #16867.

Two constraints for the contract:

- `active` can't simply be widened to include `Pending` Pods. `UpdateJobStatus` derives `JobRunning` from `active > 0` ([pytorchjob_controller.go#L376-L424](https://github.com/kubeflow/trainer/blob/v1.9.4/pkg/controller.v1/pytorch/pytorchjob_controller.go#L376-L424); same pattern in the other v1 controllers), and `KubeflowJob.PodsReady()` reads `JobRunning`.
- The only "operator saw the stop" signal is `JobSuspended=True`. It is written once the deletes are issued, not when the Pods are gone. It is absent on jobs the operator never observed suspended, and it can be stale after an unprocessed resume; v1 `JobStatus` has no `observedGeneration`. Because a row-1 job (no status) must stay inactive so its Workload still gets created, "wait for `JobSuspended=True`" has to tell a never-admitted job from an admitted one. The alternative is to check for owned Pods with a context-taking check, as #14486 suggests; KEP-10076 already plans `IsActive(ctx, strategy)`.
