## Description

**What would you like to be added**:

Provide explicit opt-outs for metrics authentication and TLS for trusted pod-local scrapers, while preserving authenticated HTTPS by default:

- `--metrics-authentication`, default `true`: when disabled, omit controller-runtime's authentication/authorization filter so metrics requests do not require bearer tokens, TokenReview, or SubjectAccessReview.
- `--metrics-secure`, default `true`: when disabled, serve metrics over HTTP. HTTP requires `--metrics-authentication=false`; reject authenticated HTTP at startup when metrics are enabled.

Whenever metrics are enabled and authentication is disabled, require `metrics.bindAddress` to contain an explicit IPv4 or IPv6 loopback IP and numeric port (for example, `127.0.0.1:8443` or `[::1]:8443`). Reject wildcard, non-loopback, hostname-based, and malformed addresses before serving. Preserve the existing `"0"` value for disabling metrics.

HTTPS retains existing certificate loading and rotation. HTTP skips metrics certificate loading and watching, including with `internalCertManagement.enable: false`; webhook TLS and its certificate requirements remain unchanged. Preserve authenticated HTTPS defaults and upstream RBAC manifests.

Design proposal: [KEP-16029 — Metrics access for pod-local scrapers (#16535)](https://github.com/kubernetes-sigs/kueue/pull/16535). Implementation prototype: #16035.

The KEP is provisional. Optional HTTP is a separate design decision for maintainer review; the authentication opt-out can be accepted independently while retaining HTTPS. This expands the original HTTPS-only issue scope and explicitly revisits KEP-4377's earlier exclusion of disabling TLS.

**Why is this needed**:

**Urgent: this is currently blocking Kueue integration at Stripe.** We need a supported way for a trusted pod-local scraper to collect metrics without bearer-token authentication, with an additional option to avoid metrics serving-certificate dependencies for loopback scraping.

Some deployments authenticate the controller to Kubernetes using client certificates but do not provision a supported bearer token for the metrics sidecar. The controller's API client credentials and the scraper's incoming request credentials serve different purposes. Supplying serving certificates or granting review-API RBAC does not satisfy the metrics filter's bearer-token requirement.

In v0.19.5 (`8e60d76a91bb9a45754218e569de1088f862ac75`), `cmd/kueue/main.go` unconditionally sets both `SecureServing: true` and `FilterProvider: filters.WithAuthenticationAndAuthorization`. With internal certificate management disabled, the manager also requires metrics certificates at `/etc/kueue/metrics/certs/tls.crt` and `tls.key`. Optional loopback HTTP would remove that metrics certificate-provisioning, mounting, rotation, and scraper TLS-configuration dependency.

A service-registry-only DNS certificate does not automatically validate against `127.0.0.1`, but a trusted CA and certificate-matching TLS server name can support verified HTTPS over loopback. Missing loopback SANs alone do not require HTTP. Disabling TLS verification is not the proposed solution.

Related historical discussions: #663 (older auth-proxy configuration) and #4841 (HTTP and alternative authentication). The KEP discusses these alternatives and the security tradeoffs.

**Completion requirements**:

- Default and explicit `true` values preserve authenticated HTTPS.
- Authentication disabled permits HTTPS scraping without a bearer token and without either review API call.
- If accepted, HTTP requires both flags disabled and an explicit loopback bind address, serves metrics without review API calls or metrics certificate files, and rejects authentication-enabled configurations.
- Tests cover IPv4/IPv6 loopback, unsafe/malformed addresses, startup rejection, disabled metrics, HTTPS certificate loading/rotation and verified TLS connections, plus the optional HTTP path.
- Document that all containers in the pod can access loopback; it is a pod-level boundary, not container isolation. Host-networked pods share the node network namespace. The KEP must cover forwarding risks and an opt-out startup warning.
- Preserve separate webhook certificate handling and all webhook behavior.
- Document HTTPS scraper CA trust and certificate-matching TLS server-name configuration, and HTTP scraper scheme selection. Scraper wiring and removal of unused metrics-auth RBAC in downstream deployments are separate changes.
