## Description

**What happened**:

`kueuectl list workload --for` can hang.

When `--for` is set, the command first lists Workloads with a `kueue.x-k8s.io/job-uid` label selector, and if that returns nothing it is supposed to retry once without that label and match the Job by owner reference.

The retry check uses `strings.Contains` on the whole selector. If `-l` already contains that job-uid requirement (with another label in front of it), the selector after the retry still matches, the list is still empty, and the command loops forever.

**What you expected to happen**:

The owner-reference fallback should run once. The command should print matching Workloads, or "No resources found", and exit.

**How to reproduce it (as minimally and precisely as possible)**:

Have a Job whose Workload is only tied by owner reference (no `kueue.x-k8s.io/job-uid` label), then:

```shell
kueuectl list workload --for job/my-job -l "app=foo,kueue.x-k8s.io/job-uid=<job uid>"
```

The process does not return.

**Anything else we need to know?**:

The check is in `cmd/kueuectl/app/list/list_workload.go` (`strings.Contains(opts.LabelSelector, jobUIDLabelSelector)`). `jobUIDLabelSelector` is prefixed with a comma when `-l` is also set, so a user selector like `app=foo,kueue.x-k8s.io/job-uid=<uid>` still contains it after the fallback.
