## Description

**What happened**:

For a Kueue-managed StatefulSet, `reconcileWorkload` releases the Workload admission and sets `QuotaReserved=False` with reason `OnHold` as soon as `spec.replicas` becomes 0. The decision checks the StatefulSet replica count and Workload state but not whether an owned Pod is still active. During graceful termination or delayed Pod removal, a Running Pod can therefore continue consuming resources after its Workload reservation has been released. The freed quota can be assigned to another Workload too early.

This is separate from #14574 and PR #14578, which address eviction completion for a PodGroup with no member Pods.

**What you expected to happen**:

Scale-to-zero should keep the quota reservation while a Pod owned by that StatefulSet is still active under the Pod integration's activity semantics. Once no matching active Pod remains, the Workload should converge to `QuotaReserved=False` with reason `OnHold`, preventing immediate re-admission until scale-up. A same-name Pod owned by a different StatefulSet UID must not delay this transition.

If `FastQuotaReleaseInPodIntegration` is enabled, a terminating Pod may be treated as inactive immediately, consistently with the Pod integration. With the gate disabled, a Running Pod remains active until its deletion grace period expires, its phase changes, or it is deleted.

**How to reproduce it (as minimally and precisely as possible)**:

1. Enable the StatefulSet and Pod integrations, and admit a Kueue-managed StatefulSet Workload with one replica.
2. Keep an owned Pod in `Running`, for example while it is in its termination grace period.
3. Set the StatefulSet's `spec.replicas` to 0 and reconcile it before the Pod becomes inactive.
4. Observe that the Workload's quota reservation is released and marked `OnHold` while the Pod is still active.

**Anything else we need to know?**:

The fix should watch or retry Pod transitions so delayed Pod deletion, a phase change, or grace-period expiry eventually releases the reservation. It should also handle the ordering in which empty-PodGroup eviction has already cleared the reservation to `PendingEvaluation` before the StatefulSet reconciles at zero replicas: that Workload still needs to converge to `OnHold`. Regression tests should cover a Running Pod, no Pods, completion or deletion, an owner UID mismatch, both `FastQuotaReleaseInPodIntegration` settings, and the eviction-cleanup ordering.

**Environment**:
- Kubernetes version (use `kubectl version`): envtest v1.37.0; not reproduced on a live cluster.
- Kueue version (use `git describe --tags --dirty --always`): upstream `main` at `c448d4edc9f6ca026918e7ab911675d5e7dc11b9`; regression branch based on `7dd4a577592ecefbd9f08770e0118baa6f9190b0`.
- Cloud provider or hardware configuration: Not hardware-specific.
- OS (e.g: `cat /etc/os-release`): Linux/amd64 for envtest.
- Kernel (e.g. `uname -a`): Not kernel-specific.
- Install tools: Kueue StatefulSet and Pod integrations enabled.
- Others: The race is most visible when Pod termination is delayed after scale-to-zero.
