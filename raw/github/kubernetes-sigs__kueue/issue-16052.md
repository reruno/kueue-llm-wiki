## Description

**What happened**:

For an elastic job using `elastic-job-scale-up-strategy: partial`
(`ElasticJobsViaWorkloadSlicesWithPartialReplicaScaleUp`, alpha, KEP-12100), a scale-up
probe's `MinCount` is frozen at creation time to whatever count its immediate predecessor
slice was granted. If that predecessor is later evicted (ClusterQueue drain, preemption,
...) and finished, nothing in the codebase ever revisits or lowers the probe's `MinCount`
afterward.

As a result, once the ClusterQueue's available quota drops below that frozen floor - even
to a level the exact same job already ran at successfully earlier in its own history -
the probe stays `Pending` forever. The scheduler can only ever try admitting the probe
somewhere in `[MinCount, Count]`; it has no way to fall back below `MinCount`, so the job
never recovers even though a strictly smaller, previously-proven admission would be valid.

**What you expected to happen**:

Once quota is enough to cover a worker count the job has already been granted before (in
this case, its very first, pre-scale-up count), the job should be re-admitted there,
rather than staying `Pending` indefinitely.

**How to reproduce it (as minimally and precisely as possible)**:

Using a `ClusterQueue` with a 7-pod quota (`RequestWorkerGroup` requesting 1 CPU each,
"pods" as the binding resource):

1. Create a RayCluster with `elastic-job-scale-up-strategy: partial`, requesting 5 worker
   replicas. It admits in full: 1 head + 5 workers = 6 pods.
2. Scale the worker group to 10 replicas. A new slice is admitted **partially** at 6
   workers (1 head + 6 = 7 pods, the whole quota), with `MinCount=5` (the previous
   baseline). The original slice is finished.
3. A scale-up probe is created for the full 10 workers, with `MinCount=6` (the count just
   granted to the partially-admitted slice in step 2). It stays `Pending` - the quota is
   already fully used.
4. Evict the partially-admitted slice from step 2 (e.g. `ClusterQueue.spec.stopPolicy:
   HoldAndDrain`, or preemption by a higher-priority workload). It gets finished. The
   probe from step 3 survives, still `Pending`.
5. Restore/resume the ClusterQueue with just **6 pods** of quota - exactly enough for 1
   head + 5 workers, the count the job was successfully running at in step 1.

Expected: the probe (or a replacement) is admitted at 5 workers.
Actual: the probe stays `Pending` forever. The scheduler logs
`ExceedsMaxQuota: ... previously considered podsets requests (1) + current podset
request (10) > maximum capacity (6)` - it only ever tries the probe's frozen floor of 6
workers (7 pods) or its full request of 10, never the 5 workers that fits and that the
job has already proven it can run at.

A failing integration test reproducing this exact sequence will be added to
`test/integration/singlecluster/controller/jobs/raycluster/raycluster_controller_partial_scaleup_test.go`,
spec name: `"Should recover at a worker count the job already ran at, even below the
probe's frozen floor"` ([PR](https://github.com/kubernetes-sigs/kueue/pull/16056)).

**Anything else we need to know?**:

- This is a gap adjacent to, but distinct from, #15399: that issue covered a probe whose
  floor became unreachable and was never revisited *at all* (fixed by #15776's
  `mustGrow`-aware `PodSetReducer`, which lets a probe fall back to exactly its own frozen
  floor once its predecessor is gone). This issue is about what happens when even that
  frozen floor stops fitting - `mustGrow` only decides whether landing on `MinCount`
  counts as a fit; it can't lower `MinCount` itself.
- Root cause is in `prepareWorkloadSliceForScaleUp`
  (`pkg/controller/jobframework/reconciler.go`), which sets a probe's `MinCount` once, at
  creation, from `FindLatestActiveWorkload`'s current grant - and nowhere else in the
  codebase ever updates it afterward.
- Feature-gated behind `ElasticJobsViaWorkloadSlicesWithPartialReplicaScaleUp`, which is
  alpha and disabled by default (KEP-12100). Filing this now to track fixing it before
  Beta graduation.

### Comment by [@mszadkow](https://github.com/mszadkow) — 2026-09-23T17:17:18Z

Let's revisit options that we have:
1. Patch the probe's `baseline` down to evicted wl's minCount.
2. Fallback to Job's declared minimum `minReplicas`, this appears to be problematic, because the field is not optional.
Also how do we treat 0 (default value).
3. Finish probe and recreate both workloads. The problematic part is probe name collision and necessity to pass minCount to next workloads to overcome GC retention configuration.

Out of 3 alternatives I would go with option 1.
