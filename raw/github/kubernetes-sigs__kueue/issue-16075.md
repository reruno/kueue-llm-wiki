## Description

**What happened**:

With `FastQuotaReleaseInPodIntegration=false` (the default), a Running Pod in a PodGroup can keep its Workload quota reserved for one extra deletion grace period after the Pod's actual deletion deadline has passed. The Pod integration's `Pod.IsActive()` checks `now > pod.DeletionTimestamp + pod.DeletionGracePeriodSeconds`. For a graceful Pod deletion, the API server has already set `deletionTimestamp` to the deletion request time **plus** the grace period.

For example, a deletion requested at 12:00:00 with a 30-second grace period yields `deletionTimestamp=12:00:30`. If the Pod remains present and Running after that deadline (for example, due to a lost node), Kueue currently considers it active until after 12:01:00. A Pod that exits normally before the deadline is handled by the usual object/status events, so this discrepancy is most visible for lingering terminating Pods.

**What you expected to happen**:

Once the API server's `deletionTimestamp` has passed, a terminating Pod with an explicit deletion grace period should no longer be considered active for PodGroup quota retention. The grace period must not be added to that timestamp again. The fast-release feature gate's immediate-release behavior should remain unchanged.

**How to reproduce it (as minimally and precisely as possible)**:

1. Keep `FastQuotaReleaseInPodIntegration` disabled and create a PodGroup containing a Running Pod.
2. Gracefully delete the Pod with `gracePeriodSeconds=30`, leaving the Pod object present and `status.phase=Running` after the deadline (a finalizer or a failed/unreachable node can make this state observable).
3. Inspect the Pod's `metadata.deletionTimestamp` and `metadata.deletionGracePeriodSeconds`; the former is already approximately deletion-request-time + 30 seconds.
4. After `deletionTimestamp` but before `deletionTimestamp + 30 seconds`, trigger a PodGroup reconciliation. Observe that `Pod.IsActive()` still returns true and the PodGroup can retain quota.

The behavior is also reproducible in a unit test with a Running Pod whose `deletionTimestamp` is 10 seconds in the past and `deletionGracePeriodSeconds=90`: it is still treated as active today, although the API server's deletion deadline has passed.

**Anything else we need to know?**:

The API server sets the initial graceful-deletion timestamp to `now + gracePeriodSeconds` in [`BeforeDelete`](https://github.com/kubernetes/apiserver/blob/master/pkg/registry/rest/delete.go#L894-L898). [`ObjectMeta.DeletionTimestamp`](https://github.com/kubernetes/apimachinery/blob/master/pkg/apis/meta/v1/types.go#L2541-L2559) is the expected deletion time, not the start of the grace period. This Kueue calculation predates the current StatefulSet work and originated in [#6872](https://github.com/kubernetes-sigs/kueue/pull/6872), whose stated goal was to avoid retaining quota after the grace period expires.

Related: [#16044](https://github.com/kubernetes-sigs/kueue/pull/16044) reuses the Pod activity semantics for StatefulSet scale-down and currently computes its timed recheck with the same extra addition. Its deadline calculation should be aligned when the two changes are integrated, regardless of merge order.

This issue concerns the activity decision **when reconciliation runs**; it does not imply that PodGroup reconciliation is automatically scheduled at the deletion deadline. Releasing quota for an API-visible Running Pod after its expected deletion time is the existing intent of #6872, but it does not prove the underlying process has stopped on a partitioned node.
