## Description

**What happened**:

#15444 fixed #14792: zero-count PodSets had zero total requests, so they could receive a flavor unable to fit even one pod. We preserved processed per-pod requests and added a capacity probe, while keeping actual quota usage at zero.

We also applied the probe to mixed-count TAS groups, checking the leader's actual requests plus one hypothetical worker. The intent was to choose a shared flavor that could support later worker scale-up.

Before this change, the leader's actual requests drove flavor selection. Now, a zero-count worker can cause a flavor that fits the leader to be skipped. The leader can remain pending if the chosen flavor has enough configured quota but no available topology capacity. This happens on first admission too.

**What you expected to happen**:

I expected the leader to remain admissible on a flavor that fits the group's actual requests, as before #15444. In the example below, it should be admitted on `small`, with worker count and quota usage staying zero.

**How to reproduce it (as minimally and precisely as possible)**:

1. Configure two TAS flavors in the same ClusterQueue: `small` has 1 CPU quota and an available 1-CPU node; `large` has 2 CPUs quota but no nodes.
2. Submit a new Workload with grouped leader/worker PodSets, each requesting 1 CPU per pod, with counts 1 and 0 and preferred hostname topology.
3. Observe that the leader stays pending: the probe asks for 2 CPUs, selects `large`, and topology assignment fails, although the leader could run on `small`.

**Anything else we need to know?**:

I'd like maintainer input on the intended behavior: should a mixed-count group prioritize admitting its current pods, or prefer capacity for future workers even when that delays the leader? I see two directions:

- **Keep mixed-count probing and account for its inputs in the scheduling hash.** The probe uses one worker's processed requests, but the hash currently omits those saved per-pod requests. Including them would make scheduling equivalence reflect the probe inputs. This would keep the new behavior where future-worker requirements can delay the leader; the hash change alone would not fix that delay.
- **Limit probing to groups where every count is zero.** This retains the original fix while restoring previous mixed-count behavior: actual requests drive the leader's flavor choice. A future worker might not fit that flavor, as before #15444. Hash consistency for the remaining all-zero probes would still need checking.

The first-admission test fails with the merged code and passes with the second approach. I am leaning toward preserving existing leader admission behavior, but would appreciate maintainer guidance on which behavior we want.

### Comment by [@sohankunkerkar](https://github.com/sohankunkerkar) — 2026-09-24T17:51:47Z

Thanks for raising this issue. I’d lean toward the second option and only probe a group when every PodSet in it has a count of 0.

TAS placement is only checked after the flavor is chosen. So if the probe skips a flavor the leader fits on, the assigner never comes back to it. An all-zero group can't hit this, because TAS skips count 0 PodSets and there's nothing to place. A mixed group gives up an admission we can make now for a worker that may never come. Admitting the pods we have is the right default.

I checked this on main. A `TestScheduleForTAS` case with your setup (small with 1 CPU and a node, large with 2 CPU and no nodes, leader 1 and worker 0 in one group) leaves the leader pending with no topology domains at `level: kubernetes.io/hostname`. With the probe limited to all-zero groups, it's admitted on small. The other flavorassigner cases from #15444 still pass. Only the five mixed-count cases fail, and that's expected: they test the behavior we're removing.

On the hash: it's built from the effective pod specs, and those already include each container's requests. So I don't think the probe needs its own hash input, and either way it's separate from this fix.
