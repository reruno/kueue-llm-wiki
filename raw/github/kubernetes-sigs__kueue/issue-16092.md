**What happened**:

When `waitForPodsReady` is enabled and a Deployment doesn't reach readiness within the Timeout specified, the workload is evicted and a new workload gets created. This wipes the status field consequently the retry counter resets every time.

The `kueue_evicted_workloads_once_total`  keeps increasing in every eviction while a new workload gets created.

**What you expected to happen**:
Shouldn't the same workload remain there so we could track retry counter?

**How to reproduce it (as minimally and precisely as possible)**:
- Set the waitForPodsReady on the config Map to a timeout applicable to you.
- Create a Deployment that is never ready, for example with a nodeSelector of a node that doesn't exist.

### Comment by [@bolubo](https://github.com/bolubo) — 2026-09-25T00:09:14Z

Thanks for the pointer. I reproduced this on a local branch first, so the questions below come with evidence. cc @mimowo @sohankunkerkar @tenzen-y

With waitForPodsReady + Deployment (unschedulable pod), the loop I reproduce is: evict, Pod deleted, Workload finished on the orphan path (`Workload is orphaned; finishing to release quota`, pkg/workload/workload.go), Deployment recreates the Pod, new Workload with a fresh status.

Three findings from the repro:

- The Workload's only ownerRef is the Pod, and the live-owner keep-alive branch added in #14578 skips Pod owners. Once the Pod is gone, nothing holds the Workload, and the retry counter goes with it.
- An owner that outlives the Pod fixes the survival half: with the Deployment as a plain, non-controller ownerRef at construction time, the Workload stays and admission is released instead of being finished.
- Surviving is not enough. The replacement Pod has a new name and UID, and the single-Pod lookup matches by Pod name, so it does not adopt the kept Workload: a second one is created for the same Deployment and the counter still starts from zero. So keeping the same Workload needs both halves: a surviving owner, and a way for the replacement Pod to find and adopt it. The job-uid label (DeploymentJobUIDLabel) looks like the natural handle for the second half, though matching needs more thought with replicas > 1.

What I'd like a call on:

1. Direction: keep the Workload across evictions and let the replacement Pod adopt it, or keep one Workload per Pod and carry the retry counter over? The first sounds consistent with the update-in-place direction from #15503, but I don't want to assume.
2. If we keep it, what releases it when no Pod comes back (rollout to a new ReplicaSet, scale-down, Deployment deleted)? It needs a terminator, otherwise an old copy just lingers.
3. Before settling the ownerRef layout: my understanding is that we cannot keep a Workload without changing its owners, since the Pod is the only one and GC collects an object once all owners are gone. If that holds, how should the Pod ownerRef look in the final layout (leave it, drop it, move the controller ref to the Deployment)? Hard to settle with unit tests; I can verify with envtest once we know which behavior the design relies on.

No need to settle all three at once; even a lean on (1) would unblock the rest. For triage: this looks like a real bug in the pod integration rather than user error. I'm assigned here; once the direction is settled I can put up a first cut and share the repro test.
