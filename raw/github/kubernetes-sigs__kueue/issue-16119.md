**What happened**:

With `ElasticJobsViaWorkloadSlicesWithTAS` (Alpha, off by default), admitting a workload-slice replacement leaves the replaced slice's topology usage in the scheduling-cycle snapshot in addition to the replacement's own usage.

A replacement is a new Workload whose own `Status.Admission` is nil, so its full TAS assignment is added without removing the topology usage of the slice it replaces.

The observed impact is conservative: a workload that should fit is deferred to the next scheduling cycle and succeeds once the replaced slice leaves the cache.

**What you expected to happen**:

Once a replacement is admitted, the scheduling-cycle snapshot should reflect the replacement's topology usage without also counting the slice it replaces.

**How to reproduce it (as minimally and precisely as possible)**:

To observe the stale topology usage within the same scheduling cycle, enable `FairSharingRefill` so that succ is nominated after the replacement has been booked.

Scheduler unit level with:

- `ElasticJobsViaWorkloadSlices`
- `ElasticJobsViaWorkloadSlicesWithTAS`
- `FairSharingRefill`

enabled.

Use a single-level `kubernetes.io/hostname` topology with one 4-CPU node. ClusterQueue quota is deliberately non-binding, so topology placement is the only constraint. Elastic workloads may only use unconstrained topology, so every PodSet here is unconstrained.

- `old`: admitted elastic slice using 2 pods × 1 CPU;
- `grow`: replacement using 3 pods × 1 CPU;
- `succ`: 1-pod workload behind it.

`grow` is admitted, so the real usage is 3/4 CPU. `succ` then enters the same cycle through refill and should use the remaining CPU.

Instead, nomination effectively sees:

```
old 2 + grow 3 + succ 1 = 6
```

and defers `succ` as a topology no-fit.

Control: replace `grow` with an ordinary 1-pod workload. `succ` is then admitted on the 4-CPU node.

Sweeping other replacement shapes shows that the extra apparent topology usage is always the replaced slice in full:

| replacement | true capacity needed | observed threshold | extra |
|---|---|---|---|
| 2 → 3 | 4 | 6 | 2 |
| 2 → 4 | 5 | 7 | 2 |
| 3 → 2 | 3 | 6 | 3 |
| 2 → 2 | 3 | 5 | 2 |

**Anything else we need to know?**:

- The underlying bookkeeping path is also present on `release-0.18` and `release-0.19`; the user-visible reproduction above is specific to main/0.20 because refill provides the mid-cycle reader.
- This is the topology-side counterpart of #16118: the two expose inconsistent views of the same workload-slice replacement transition.
