**What happened**:

`GetTargets` sizes preemption from `Assignment.TotalRequestsFor`, but that request can differ from the assignment being admitted in two ways:

1. `pods` is missing. When `pods` is the binding resource, target selection can stop after an insufficient victim because the Pod quota is never checked.
2. Partial-admission count is ignored for workload-slice replacements. The request uses the spec count rather than the count selected by `ElasticJobsViaWorkloadSlicesWithPartialReplicaScaleUp`.

In both cases, a workload that could fit after preempting lower-priority workloads can remain pending instead.

**What you expected to happen**:

Preemption target selection should use the same resources and counts as the assignment it is trying to admit.

For the partial scale-up case below, `victim` should be preempted; a replacement with 1 head + 6 workers then fits within the 7 CPU quota.

**How to reproduce it (as minimally and precisely as possible)**:

Scheduler unit level, one ClusterQueue with `withinClusterQueue: LowerPriority`.

| Case | Setup | Result |
|---|---|---|
| missing `pods` | quota: 7 pods, CPU non-binding; `va`=4 and `vb`=3 pods admitted at priority -1; `new`=7 pods at priority 0 | no workload is preempted and `new` stays pending |
| partial count ignored | quota: 7 CPU; `victim`=4 CPU at priority -1; elastic slice uses 1 head + 2 workers; replacement scales workers to 10 with partial scale-up (`MinCount: 2`) | no workload is preempted |

Control for the first case: making CPU the binding quota instead causes both victims to be preempted.

I have scheduler unit tests for both cases and the control.

**Anything else we need to know?**:

- The missing-`pods` path is also present on `release-0.18` and `release-0.19` by code inspection; I haven't reproduced it on those branches.
- The partial-admission case requires `ElasticJobsViaWorkloadSlicesWithPartialReplicaScaleUp`, which is new in 0.20 and Alpha/off by default.
- Found while investigating #16125 after the existing RayCluster partial scale-up integration test with preemption failed with that change. The failure is reproducible locally; the focused cases above isolate the two request-sizing mismatches. [Prow failure](https://prow.k8s.io/view/gs/kubernetes-ci-logs/pr-logs/pull/kubernetes-sigs_kueue/16125/pull-kueue-test-integration-shard-1-main/2103046022182735872)
- This is different from #16052, which concerns a frozen `MinCount` in the scale-up probe.
