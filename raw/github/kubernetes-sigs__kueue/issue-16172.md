## Description

**What happened**:

When a MultiKueue worker watch disconnects and reconnects, the replacement watch begins at the time it is established and does not replay events that occurred during the disconnect.

Workloads whose state changed during the gap, such as `Admitted`, `Finished`, or `Evicted`, are not immediately re-enqueued after the watch reconnects. The manager eventually re-reads each remote workload during reconciliation, but admitted workloads normally rely on the `workerLostTimeout` requeue for this refresh.

As a result, terminal states, evictions, and admission transitions can remain stale until the next periodic reconciliation, even after the worker connection has recovered.

The relevant code paths are `establishWatch` and `establishWatcher` in `pkg/controller/admissionchecks/multikueue/multikueuecluster.go`. The replacement watch does not use a `ResourceVersion`, and reconnect handling does not relist or resynchronize affected workloads.

**What you expected to happen**:

After a worker watch reconnects, MultiKueue should resynchronize workloads assigned to that worker without waiting for the next `workerLostTimeout`-based reconciliation.

Remote terminal states and admission transitions should be propagated promptly after the connection is restored.

**How to reproduce it (as minimally and precisely as possible)**:

1. Configure a manager cluster with MultiKueue and one worker cluster.
2. Submit a managed workload and wait until it is admitted on the worker.
3. Temporarily disrupt the worker API connection so the workload watch disconnects.
4. While the watch is disconnected, finish or evict the remote workload.
5. Restore the worker connection before `workerLostTimeout` expires.
6. Verify that the manager workload does not immediately reflect the remote state transition.
7. Verify that the manager typically reflects the transition only after the next `workerLostTimeout`-based reconciliation.

A regression test should simulate a watch disconnect, update the remote workload while disconnected, reconnect the worker, and verify that the manager workload is reconciled immediately.

**Anything else we need to know?**:

The manager does perform a direct remote `Get` during `readGroup`, so the state is eventually self-healing. The issue is the missing immediate resynchronization after reconnect, not guaranteed permanent status loss or duplicate execution.

A possible fix is to list remote workloads after reconnect using the `kueue.x-k8s.io/multikueue-origin` label and enqueue the corresponding manager workloads. This would be additive to the existing reconnect path and bounded by the number of workloads assigned to that worker.

**Environment**:

- Kueue version: Unreleased `main`, commit `2a7667170`
- OS: macOS
- Others: MultiKueue manager and worker cluster setup
