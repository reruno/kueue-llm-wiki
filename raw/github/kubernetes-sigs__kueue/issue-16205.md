## Description

**Which test is flaking?**:

`Cohorts when creating, modifying and removing [It] should clear metrics for the implicit root Cohort after switching to another root Cohort` in `test/integration/singlecluster/scheduler/fairsharing/metrics_test.go`.

**Link to failed CI job or steps to reproduce locally**:

[pull-kueue-test-integration-shard-3-main, PR #16202](https://prow.k8s.io/view/gs/kubernetes-ci-logs/pr-logs/pull/kubernetes-sigs_kueue/16202/pull-kueue-test-integration-shard-3-main/2103450578498621440).

**Failure message or logs**:
```
metrics_test.go:1086: ExpectCohortSubtreeAdmittedActiveWorkloadsGaugeMetric("root1", 3)
Timed out after 10.001s: expected 3, observed 0
```

**Anything else we need to know?**:

The failure occurs during the initial admission metrics check, before `ch1` changes parents. Investigate why the implicit root Cohort gauge stays at 0 while the test expects 3 admitted workloads. Ensure the test and metric update behave reliably on reruns. This test is unrelated to the RBAC change in [PR #16202](https://github.com/kubernetes-sigs/kueue/pull/16202).

### Comment by [@apullo777](https://github.com/apullo777) — 2026-09-27T15:27:18Z

I was able to reproduce this on main, and @Narwhal-fish's diagnosis matches what I'm seeing: the same-parent resync recreates the implicit root with a zeroed `admittedWorkloadsCount`. That also accounts for the `root1 = 0` gauge while the Total counter still reaches 3.

One thing I noticed while reproducing it is that the issue may be broader than the same-parent resync. `admittedWorkloadsCount` is maintained incrementally, but unlike `Usage`, it isn't rebuilt when the hierarchy changes. I can reproduce similar drift with reparenting, deleting a Cohort with children, and workload changes while the hierarchy contains a cycle.

I tried recomputing the count from children in `updateCohortResourceNode`, which fixes those repros locally. There may also be one follow-up needed for the metric itself: hierarchy changes don't currently re-report this gauge, so the exposed value can remain stale until another workload event.

@mimowo, one thing I'm not sure about is the intended semantics after reparenting: when `ch1` moves from `root1` to `root2`, should `root2`'s subtree gauge become 5 immediately? The existing test expects 2, but that seems to depend on the count not following `ch1`.

@Narwhal-fish, are you planning to pick this up? I have a minimal repro and a few broader cases locally, happy to share anything useful :)
