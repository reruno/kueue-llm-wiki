**What happened**:
With `ElasticJobsViaWorkloadSlicesWithTAS` on, a replacement slice that scales grouped workers from 0 to 1, with the leader at 1, crashes kueue-controller-manager with a nil pointer dereference.

`findLeaderAndWorkers` picks roles by count, so on a tie it takes the workers PodSet as the leader. That PodSet had no previous topology assignment, and `finalizeElasticAssignment` dereferences it.

```sh
panic: runtime error: invalid memory address or nil pointer dereference [recovered, repanicked]
pkg/util/tas.ComputeUsagePerDomain
pkg/cache/scheduler.addAssumedUsage
pkg/cache/scheduler.(*TASFlavorSnapshot).finalizeElasticAssignment
pkg/cache/scheduler.(*TASFlavorSnapshot).handleElasticWorkload
```
**What you expected to happen**:
The replacement slice is admitted, or stays pending, with the leader keeping its placement. No crash.

**How to reproduce it (as minimally and precisely as possible)**:
1. Enable ElasticJobsViaWorkloadSlices and ElasticJobsViaWorkloadSlicesWithTAS.
2. Admit an elastic Workload with grouped PodSets: leader (count 1, listed first) and workers (count 0).
3. Create a replacement slice with leader 1 and workers 1.

**Anything else we need to know?**:
I found this while testing #16174, but it reproduces without it. It's also on release-0.19 and release-0.18.
