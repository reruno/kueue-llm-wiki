**What would you like to be cleaned**:

Use consistently PodSetCounts structure rather than []int32 for PodSet counts: https://github.com/kubernetes-sigs/kueue/blob/47e69465d1befa762860f33095c42223afd33b0e/pkg/workload/podsetscounts.go#L34

For example in PodSet reducer we should use the more robust structure: https://github.com/kubernetes-sigs/kueue/blob/main/pkg/scheduler/flavorassigner/podset_reducer.go

Also, we may need to extend the structure to keep the ordering. 

**Why is this needed**:

To prevent some tricky bugs due to operating on low-level strutures like arrays.

Here is example: https://github.com/kubernetes-sigs/kueue/issues/16239

### Comment by [@apullo777](https://github.com/apullo777) — 2026-10-13T08:33:50Z

@mimowo! Thanks! I went through the ordering-dependent paths across the scheduler and controllers (catalog below).

The main finding is that there isn't one order to preserve. The reducer uses spec position, TAS uses group order, pod groups derive their own spec order, and `TotalRequests` can follow either spec or admission order. The #16266 bugs came from pairing across these orders by index.

## The orders

| Order | Where it comes from | Notes |
|---|---|---|
| Spec | `wl.Spec.PodSets` (= the job's `PodSets()`), `workload.Info.EffectivePodSpecs` | |
| Admission | `flavorassigner.AssignFlavors` groups requests by `tas.GroupKeyForPodSet` in first-appearance order → `Assignment.PodSets` → `Assignment.ToAPI` → `Admission.PodSetAssignments` | differs from spec only when group members are not adjacent; persisted |
| Mixed | `workload.Info.TotalRequests`: spec order while pending, admission order once admitted (`rebuildTotalRequests`) | `WithPreserveTotalRequests` keeps whichever order it had |
| Pod group (canonical) | `pod.constructGroupPodSets` sorts by role hash (by shape hash, count, name with `PodGroupSchedulingShapeOrdering`); `reorderPodSets` follows an existing Workload | this becomes the spec order for pod groups |

Pod groups use a hash to *produce* an order; `workload.computeSchedulingHash` *consumes* spec order.

The API lists (`spec.podSets`, `status.admission.podSetAssignments`, `status.resourceRequests`, `status.reclaimablePods`) are `+listType=map` keyed by `name`, but they are slices in Go.

## Index pairing of two per-PodSet lists

Example of a non-adjacent group: spec `[leader(g), other, worker(g)]`, admission `[leader, worker, other]`.

| Site | Pairs | Note |
|---|---|---|
| `jobframework.getPodSetsInfoFromStatus`, `deferAdmissionCheckNodeSelectorsToPods` | `PodSetAssignments[i]` ↔ `Spec.PodSets[i]` | fixed by #17052 (reordered by name first) |
| `RunWithPodSetsInfo` in JobSet, Kubeflow, MPIJob, RayCluster / RayService / RayJob, Spark, AppWrapper | `podSetsInfo[i]` ↔ own replica `i` | positional interface; receives spec order |
| `podset.FromAssignment` | an assignment ↔ a PodSet | no name check |
| `workload.computeSchedulingHash` | `Spec.PodSets[i]` ↔ `TotalRequests[i]` | the two may be in different orders once admitted |
| `flavorassigner.AssignFlavors` (second pass) | `requests[i]` ↔ `Admission.PodSetAssignments[i]` | relies on `TotalRequests` being rebuilt from the admission |
| `flavorassigner.AssignFlavors` | `podset.SpecIndexes` result | falls back to `i` if a name is missing |
| `jobframework.EquivalentToWorkload` → `equality.ComparePodSetSlices` | job `PodSets()` ↔ `wl.Spec.PodSets` | needs a stable `PodSets()` order across Kueue versions |
| `workload.PropagateResourceRequests`, `workload.sameHashedRequests`, `queue.draRequestsChanged` | old ↔ new `TotalRequests` | a reorder counts as a change |
| webhooks `validateImmutablePodSets`, `validateAdmissionUpdate`, `validateImmutablePodSetUpdates` | old ↔ new | a reorder counts as a change |

## Order-sensitive behavior

The reducer policy is documented and tested; the others rely on position as the code stands.

- Partial-admission reducer (`distributeOrderBased`, `giveBack`): shrinks from the last PodSet, gives back from the first.
- `workload.computeTopologySpreading`: the first annotated PodSet in a group is used.
- `jobframework.extractPriorityFromPodSets`: the first PodSet with a priority class is used.
- Provisioning `mergePodSets` / `podSetUpdates`: the first PodSet is the merge representative.
- `AssignFlavors` and TAS `FindTopologyAssignmentsForFlavor`: earlier groups, and earlier members within a group, claim capacity first.
- Leader vs. workers: TAS `findLeaderAndWorkers` and `topology_ungater` each fall back to position, with different tie-breaks.
- `Assignment.Message`, flavor-attempt events and NoFit reasons follow admission order; the first error wins.
- `flavorassigner.WorkloadsTopologyRequests` builds TAS requests in spec order while the quota pass runs in admission order.

## Grouping implementations

| Where | Key |
|---|---|
| `flavorassigner.AssignFlavors` (`orderedgroups`) | `tas.GroupKeyForPodSet` (prefixed) |
| TAS `FindTopologyAssignmentsForFlavor` (hand-rolled loop) | `tas.GroupKeyForPodSet` |
| `workload.computeTopologySpreading` | `tas.GroupKeyForPodSet` |
| webhook `validateSpreadingGroups` | raw `PodSetGroupName` |
| `jobframework.ValidatePodSetGroupingTopology` | raw `PodSetGroupName`, members `[0]` / `[1]` |
| `topology_ungater` | raw `PodSetGroupName`, or the admission index as a string for ungrouped PodSets |

## Indexed by spec position

- `workload`: `Info.PodSpec(i)`, `EffectivePodSpecs[i]`, `FlavorScanState.TriedFlavors[i]`, validation field paths.
- `scheduler/flavorassigner`: `Assignment.append(psIdx)`, `findFlavorForPodSets` / `resolvePodSetFlavors` (via the carried spec index), reducer counts, TAS `podSetTopologyRequest`.

## Looked up by name

- Helpers (linear scans): `podset.FindPodSetByName`, `workload.Info.PodSpecByName`, `flavorassigner.podSetResourcesByName`, `Assignment.podSetAssignmentByName`, TAS `findPSA`, multikueue `findPodSetAssignment`.
- Maps: `workload.PodSetsCounts` and friends, `PodSetNameToTopologyRequest`, `ReclaimableCounts`, `TASAssignmentsResult`, DRA `WithPreprocessedDRAResources`.
- Callers include the TAS node controller, provisioning, pod groups, workload slicing / elastic jobs, and the PodSetUpdates / ReclaimablePods webhooks.

## Test coverage

Test wrappers (`MakeAdmission`, `ReserveQuota`) build admissions in spec order in practice, so most tests only cover spec order == admission order.
