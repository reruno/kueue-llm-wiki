**What happened**:

A valid Workload can contain a PodSet group whose members are not adjacent, for example `[leader(group=g), other, worker(group=g)]`.

The flavor assigner lists the PodSets as `[leader, worker, other]`, and that order is persisted in the admission. Some consumers then pair this group-ordered data with the Workload's PodSets by position, so they associate state with the wrong PodSet.

In the preemption path this makes kueue-controller-manager panic:

```
panic: runtime error: invalid memory address or nil pointer dereference [recovered, repanicked]
sigs.k8s.io/kueue/pkg/scheduler/flavorassigner.(*Assignment).TotalRequestsFor.func1(...)
	/workspace/pkg/scheduler/flavorassigner/flavorassigner.go:300
```

With other resource layouts it doesn't panic, but the preemptor is sized wrong, nothing is preempted, and the Workload stays pending.


**What you expected to happen**:

The Workload preempts the lower-priority workload and is admitted, as it is when the two group members are adjacent.

**How to reproduce it (as minimally and precisely as possible)**:

I reproduced this end to end on kind with a JobSet on main. Setup: TAS enabled, each node has 1 `example.com/gpu`, and a ClusterQueue with `cpu: 100` and `example.com/gpu: 3` on a TAS flavor with `withinClusterQueue: LowerPriority`. The ClusterQueue is filled by a lower-priority JobSet using 3 GPUs.

The high-priority JobSet below has three ReplicatedJobs: `leader` (group `g`, 1 GPU), `other` (no group, CPU only) and `worker` (group `g`, 2 GPUs). The JobSet is accepted, and the generated Workload has PodSets `[leader, other, worker]`. kueue-controller-manager then panics as above, and it restarted twice during the test while the Workload stayed pending.

**Anything else we need to know?**:

The same positional assumption also appears in:

- preemption request sizing (`TotalRequestsFor`)
- flavor-scan resumption (`LastTriedFlavorIndexes`)
- the TAS second pass
- workload-slice replacement lookup
- the job reconciler when it applies topology-related admission state

The first is reproduced end to end above; I have unit or scheduler-level reproducers for the others.

The common invariant is that per-PodSet state from differently ordered representations must be matched by PodSet name, not assumed to share an index.

The group ordering comes from #5878. I reproduced the scheduler failure on main, release-0.18 and release-0.19.

I used Claude Code to help investigate and reproduce this, and verified the results myself.
