## Description

**What happened**:

On the KueueViz Workloads page, the "Preempted" column always shows "No" and "Preemption Reason" always shows "N/A", even for workloads with a `Preempted=True` condition.

`Workloads.jsx` reads `workload.preemption?.preempted` and `workload.preemption?.reason` for each item. The `/ws/workloads` handler (`fetchWorkloads` in `cmd/kueueviz/backend/handlers/workloads.go`) returns the raw `WorkloadList`, and a Workload has no `preemption` field. So the columns never get data.

**What you expected to happen**:

Either the list response carries preemption state per workload, or the frontend reads it from `status.conditions` (type `Preempted`), the same way the details handler does.

**How to reproduce it (as minimally and precisely as possible)**:

1. Run KueueViz against a cluster where a workload gets preempted.
2. Open the Workloads page. The row shows "No" and "N/A".

**Anything else we need to know?**:

Reading the condition in the frontend looks like the smaller change, since it keeps the list payload unchanged. Happy to send a PR for whichever approach the maintainers prefer.

**Environment**:
- Kueue version: main at 9e9112f94

### Comment by [@onkar717](https://github.com/onkar717) — 2026-09-29T13:46:25Z

Proposal for the fix:

Read the preemption state in the frontend from the Workload's own `status.conditions`, the same data `fetchWorkloadDetails` uses on the backend. No backend or payload change needed.

In `cmd/kueueviz/frontend/src/Workloads.jsx`:

```jsx
const preempted = workload.status?.conditions?.find((c) => c.type === 'Preempted');

<TableCell>{preempted?.status === 'True' ? 'Yes' : 'No'}</TableCell>
<TableCell>{preempted?.reason || 'N/A'}</TableCell>
```

Plus vitest cases for a workload with `Preempted=True` and one without the condition.

The alternative is to wrap each list item on the backend like `fetchWorkloadDetails` does. That changes the `/ws/workloads` payload shape, so the frontend change looks smaller and safer.

If this approach is fine, I will send a PR once #16277 to #16279 are reviewed.
