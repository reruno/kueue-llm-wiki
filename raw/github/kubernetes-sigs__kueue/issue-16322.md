**What happened**:
NewWorkload copies labels named in `integrations.labelKeysToCopy`, and with `CustomMetricLabels` NewWorkload copies labels from integrations.labelKeysToCopy, plus annotations from Workload-scoped custom metric sources (with CustomMetricLabels on), from the Job or Pod onto its Workload. Some of those keys control Kueue decisions, so if the config names one, whoever creates the Job can set it:

- multikueue-origin: MultiKueue treats the Workload as its own.
- priority-boost: users can boost their own jobs.
- job-owner-gvk / job-owner-name: trusted over the owner reference (#12548).

**What you expected to happen**:
Control metadata is never inherited from the Job or Pod, whatever the copy configuration says.

**Anything else we need to know?**:
- It needs an admin to configure copying of one of these keys. The label path needs no feature gate; the annotation path needs CustomMetricLabels (alpha).
- #14227 fixes it. It has two parts that could land separately: filtering the keys when building the Workload (not breaking), and refusing such keys in labelKeysToCopy at startup (breaking for existing configs).
- This becomes reachable by default once PriorityBoost or CustomMetricLabels goes beta (#12927).
