**What happened**:

A second-pass admission write can remove Workload status that another controller wrote after the second pass took its snapshot.

I reproduced two concrete outcomes with the real scheduler, workload controller and TAS node controller:

- Default gates: while a failed-node replacement write was in flight, a second node failure set `Evicted=True (NodeFailures)`. The second-pass apply removed `Evicted`, leaving the Workload `Admitted`. It was still in that state 5 seconds later.
- `TASReplaceMultipleFailedNodes` enabled: the node controller added N2 to `status.unhealthyNodes`. The second-pass apply removed N2, even though the resulting TopologyAssignment still contained N2. It was still missing 5 seconds later and came back only after a new node event for N2.

The second-pass write is a server-side apply with `WithLooseOnApply()`, so it has no `resourceVersion` precondition. The node controller and eviction paths write the same admission-managed status through the same field manager, with `ForceOwnership`. Under server-side apply, list-map entries and conditions that this manager owns but that are absent from the applied object are removed. As a result, entries added after the snapshot are dropped by the stale apply instead of producing a conflict.

The write mode was discussed in #12344. It was made strict at one point to protect `unhealthyNodes`, then switched back to loose during review, with the generic concurrent second-pass race left for a separate fix (https://github.com/kubernetes-sigs/kueue/pull/12344#discussion_r4102976321). This issue records the concrete impact of that race and adds the integration-level evidence asked about there (https://github.com/kubernetes-sigs/kueue/pull/12344#discussion_r4102980177).

Two comments still assume that the write cannot drop concurrent failures: `scheduler.go` ("A retry on conflict may observe additional failures…") and `tas_flavor_snapshot.go` ("the admission patch preserves failures added after the recorded head"). Neither holds on the loose SSA path: it does not conflict, and `WithRetryOnConflict` is only consulted on the merge-patch branch.

**What you expected to happen**:

A second-pass admission write based on a stale Workload should not remove status added by another controller. It should fail against the newer object and be retried from the current state.

**How to reproduce it (as minimally and precisely as possible)**:

1. Run the TAS controllers and scheduler against envtest.
2. Admit a Workload on x1..x3, then make x1 unhealthy so that a replacement second pass starts.
3. Delay that second pass's admission apply without modifying its payload. In the test, the scheduler's client is wrapped; production code is unchanged.
4. While it is delayed, fail x2 so that the node controller updates the Workload.
5. Release the original apply and observe the resulting conditions and `status.unhealthyNodes`.

The artificial delay only makes the interleaving deterministic. The natural window runs from the fire-time informer read, through the scheduling cycle, to the admission apply. On an idle envtest, the scheduling cycle itself took about a millisecond. This demonstrates reachability, not frequency.

**Anything else we need to know?**:

- #15761 (open) implements the strict `resourceVersion` write proposed as option (1) in its discussion (https://github.com/kubernetes-sigs/kueue/pull/15761#issuecomment-5759017861). In a separate envtest probe that calls `PatchAdmissionStatus` directly, a strict apply returned a conflict and preserved both an `Evicted` condition and N2.
- Replays in #15658 already covered a stale second pass racing an eviction (https://github.com/kubernetes-sigs/kueue/issues/15658#issuecomment-5793891110). This issue reproduces the API-level outcome with the real node controller.
- Reproduced on main (`31cc6c2da`). release-0.19 uses the same admission-write options, but I have not reproduced this there.
