## Description

**What happened**:

With `WorkloadPriorityClassDefaulting` (on by default in v0.20), the Deployment, StatefulSet, and LeaderWorkerSet mutating webhooks add `kueue.x-k8s.io/priority-class: default` on update, not only on create. They do this even for objects without a queue-name that Kueue does not manage.

If the object already has ready replicas, the validating webhook then rejects the update:

```
admission webhook "vstatefulset.kb.io" denied the request: metadata.labels[kueue.x-k8s.io/priority-class]: Invalid value: "default": WorkloadPriorityClass cannot be added to a non-suspended workload
```

So after a WorkloadPriorityClass named `default` is created, any Ready Deployment, StatefulSet, or LeaderWorkerSet that existed before it can no longer be updated, even if it is unrelated to Kueue.

**What you expected to happen**:

The update succeeds. The default WorkloadPriorityClass is applied only on create.

**How to reproduce it (as minimally and precisely as possible)**:

1. Run Kueue from main with the default configuration.
2. Create a StatefulSet without the `kueue.x-k8s.io/queue-name` label and wait until it is Ready.
3. Create a WorkloadPriorityClass named `default`.
4. Update the StatefulSet, for example `kubectl annotate statefulset <name> example.com/touched=true`. The update is rejected with the error above.

Deployment and LeaderWorkerSet behave the same.

**Anything else we need to know?**:

Only these three integrations run their mutating webhook on update, so batch Job and the other integrations are not affected. Reproduced on main (418f08128) with an envtest integration test.
