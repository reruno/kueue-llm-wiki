## Description

**What happened**:

When a TAS Workload becomes inactive while one of its Pods remains bound and nonterminal, Kueue removes the Workload's TAS reservation. The Pod still occupies resources on its node, but TAS capacity snapshots no longer account for those resources. A subsequent Workload can therefore be admitted against capacity that is physically occupied.

The same accounting gap can occur when a Workload is marked Finished before its terminating Pod has actually left the node. This is related to #10076, which reports the Finished/Terminating case. This issue isolates the inactive-Workload case and the required reservation-to-physical-usage transition; it does not ask Kueue to delete the remaining Pod.

**What you expected to happen**:

Once the Workload's TAS reservation is released, any Pod that remains bound and nonterminal should continue to count against its node's TAS capacity until the Pod terminates or is deleted. Normally admitted Pods should not be counted twice while their Workload still holds an active TAS reservation.

**How to reproduce it (as minimally and precisely as possible)**:

1. Configure a TAS ResourceFlavor with one eligible node allocatable for 1 CPU, and a ClusterQueue with sufficient quota.
2. Admit a Workload requesting 1 CPU and create its TAS Pod bound to that node with a 1 CPU request.
3. Set `workload.spec.active=false`, leaving the Pod bound and nonterminal. Wait until the ClusterQueue reports that the old Workload no longer reserves quota.
4. Create another TAS Workload requesting 1 CPU on the same node.

Without accounting for the residual Pod, the second Workload can be admitted before the first Pod leaves the node. It should remain Pending until that Pod terminates or is deleted. The in-repository single-cluster TAS integration regression exercises this sequence, as well as the related Finished/Terminating transition.

**Anything else we need to know?**:

- Related: #10076. The previous draft implementation, #10820, was closed without being merged; this report is not a request to reopen it.
- The proposed fix is scoped to Pods whose Workload no longer has an active TAS reservation. A distinguishable old owner or PodGroup Pod UID is also checked when a same-named Workload is recreated, to avoid hiding an unrelated old Pod. Full accounting for excess or relocated Pods, fully reclaimed PodSets, or ambiguous ownership while a reservation is still active is outside this issue.
