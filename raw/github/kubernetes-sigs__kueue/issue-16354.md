## Description

TAS currently drops capacity accounting for bound Pods after their Workload stops holding an active quota reservation.

When a TAS Workload is deactivated or finished, the scheduler cache removes the Workload's TAS reservation. If one of the Workload's Pods is still bound to a node and non-terminal, that Pod still consumes physical node resources. However, because the Pod has TAS annotations, the Pod usage controller excludes it from the non-TAS pod usage cache. As a result, TAS snapshots account for the resource in neither Workload TAS usage nor pod usage, and a subsequent TAS Workload can be admitted onto already occupied capacity.

To reproduce the issue, please run the unit tests: https://github.com/kubernetes-sigs/kueue/pull/16355/changes#diff-95ef2b4868044a4fbcc96fcda6df858f3b79548d2e4548fafcd9280114928dfc

Beyond the basic case, these check how counting the residual Pod interacts with preemption, requeue, and slice replacement. In rows 1–2, main avoids the extra eviction only because it ignores the residual Pod and admits onto the occupied node:

Case | main (56d0e2b54) | #16339 (a3586e262) | #16355 (6322d415c)
-- | -- | -- | --
Preempted victim's Pod still bound after its quota is released | 1 victim | 1 victim, preemptor waits | a second workload is evicted
Requeued Workload whose own old Pod is still bound | readmitted | waits | evicts another workload
Elastic slice replacement, old Pod still bound | other workload admitted | admitted | stays pending
Two victims release quota at different times | no extra eviction | a third workload is evicted | a third workload is evicted

Both fix the basic undercounting case (#16355's own test passes locally, #16339's in CI). Both also update Pod usage from Pod events; the difference is that on Workload changes, #16339 updates its cached state without listing Pods, while #16355 lists the Workload's Pods to reclassify them.
