## Description

**What happened**:

`SparkApplication.Finished()` treats `SUBMISSION_FAILED` as terminal, so Kueue marks the Workload Finished and releases its quota.

For the Spark operator, `SUBMISSION_FAILED` is not terminal. With `restartPolicy.type: Always`, or `OnFailure` with `onSubmissionFailureRetries` left, the operator resubmits the app after the retry interval and it goes to `RUNNING`. Kueue never stops it because the Workload is already Finished, so the driver and executors run outside quota, preemption, and `waitForPodsReady`.

When no retries are left, the operator itself moves the app to `FAILED`, so Kueue does not need to treat `SUBMISSION_FAILED` as finished.

**What you expected to happen**:

The Workload stays admitted while the operator can still retry the submission, and finishes only when the app reaches `COMPLETED` or `FAILED`.

**How to reproduce it (as minimally and precisely as possible)**:

1. Create a SparkApplication with a queue-name, `restartPolicy: {type: OnFailure, onSubmissionFailureRetries: 3, onSubmissionFailureRetryInterval: 30}`, and `spec.driver.serviceAccount` set to a ServiceAccount that does not exist.
2. Wait until the app is `SUBMISSION_FAILED` and the Workload is Finished.
3. Create the ServiceAccount. The operator resubmits, the app runs, and the ClusterQueue does not count its usage.

**Anything else we need to know?**:

Found by reading the code; not reproduced on a cluster yet. The Kueue side is `pkg/controller/jobs/sparkapplication/sparkapplication_controller.go` (`Finished()`); the operator side is `IsTerminated` and `ShouldRetry` in `pkg/util/sparkapplication.go`. No existing test covers `SUBMISSION_FAILED` or a non-default `restartPolicy`.
