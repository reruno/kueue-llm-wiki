### Comment by [@Ce11an](https://github.com/Ce11an) — 2026-11-02T21:22:37Z

Hey 👋🏻 

We (Isomorphic Labs) have run TAS in production since October on one training cluster: implicit TAS, plus `preferred` topology annotations set by our job launcher. Before enabling it we replayed our production queue configuration and load through the scheduler performance harness on v0.18.6, and TAS added about 12% scheduler time per admission compared with the gate off. That is acceptable for us, though it sets the order in which we enable it on our other clusters.

A few questions about how GA will handle things we rely on today:

1. **Rollback once the gate is locked.** Today the feature gate is our cluster-wide kill switch. Per flavor there is already no way back other than replacing the ResourceFlavor, since `topologyName` is immutable. After GA, is that replacement (documented in #17999) the intended way to stop TAS on a flavor, or is a supported per-flavor off switch planned, for example allowing `topologyName` to be unset the way `nodeLabels` and `tolerations` were relaxed? Either way, it would help if the graduation notes linked the supported path.
2. **Release notes for users who toggle the gate.** Jobs admitted through TAS keep the `kueue.x-k8s.io/topology` scheduling gate in their Pod template, so Pods recreated after TAS is turned off stay gated until waitForPodsReady evicts the workload. If GA locks the gate like other graduated Kueue features, that path goes away along with the gate as a rollback. Will the release notes say that the gate can no longer be set to `false`, for anyone using it that way?
3. **Test coverage.** While writing #17838 I found a couple documented TAS behaviours where the testing could be improved and opened #18220. Are there other areas you would want tested before GA? We are happy to help.

Thanks 🚀
