## Description

**What happened**:

The fix for [#14792](https://github.com/kubernetes-sigs/kueue/issues/14792) added a one-pod capacity probe so zero-count PodSets could select a flavor suitable for later scale-up, while keeping their quota usage at zero.

That suitable choice can be lost when admission needs a retry. A zero-count PodSet finds a flavor, but another PodSet cannot get quota, so the Workload waits. Once quota becomes available, the saved search position makes the zero-count PodSet continue after the flavor it previously selected. It can then fall back to a flavor with no GPU capacity, even though the earlier flavor still fits and the requests have not changed.

When that PodSet scales from zero to one, the elastic job retains the unsuitable flavor and cannot get quota. Reproduced with an integration test: scale-up stays pending even though the suitable flavor has a free GPU.

**What you expected to happen**:

An elastic job should not receive an unsuitable flavor for future pods merely because admission needed a retry. In the example below, both PodSets should select `large`, allowing A to scale from zero to one later.

**How to reproduce it (as minimally and precisely as possible)**:

Configure a ClusterQueue with two flavors, in this order, using distinct node labels:

- `large`: GPU quota **2**.
- `empty`: GPU quota **0**.

Create an elastic RayCluster with these two worker groups, in this order. Its head does not request a GPU. Each worker group becomes a separate PodSet:

| PodSet | Pod count | GPU request per pod |
| --- | ---: | ---: |
| A | 0 | 1 |
| B | 1 | 1 |

1. First admit another job that occupies both GPUs in `large`, then create the elastic RayCluster.
2. On its first scheduling attempt, A's one-pod capacity probe selects `large`. B needs an actual GPU now, so the whole Workload waits; neither assignment is admitted.
3. Complete the blocking job before the immediate next scheduling attempt, freeing both GPUs. Keep the RayCluster's counts and requests unchanged.
4. On retry, A's saved search position makes it continue **after `large`**. It checks `empty` and falls back to it. B exhausted its search on the first attempt, so it starts again and selects `large`. The Workload is admitted.
5. Increase A's replicas from zero to one. Its replacement Workload stays pending: A retains `empty`, which has zero GPU quota. Meanwhile, `large` has one free GPU after accounting for B.

With flavor-search progress preservation disabled, the same test selects **A → `large`, B → `large`**, and the scale-up is admitted.

**Anything else we need to know?**:

- Reproduced with an integration test using the RayCluster controller and scheduler, including the scale-up request.
- The test pauses between the first failed attempt and its retry so the blocking job can finish at that point. It does not modify scheduling decisions or saved search progress. This is a timing-dependent failure, not every admission retry.

**Environment**:

Local envtest with race detection; elastic Workload slicing and flavor-search progress preservation enabled. Validates admission, without running GPU pods.
