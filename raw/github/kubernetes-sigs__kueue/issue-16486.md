## Description

***What happened***:
An admitted PodSet total is stored in `PodSetAssignment.resourceUsage` as a `Quantity`. For a non-CPU resource, a total past `MaxInt64` is written back as `9223372036854775807`. The cache then rebuilds usage from that capped value.

`AssignFlavors` keeps the total in the `PodSetAssignment`, and `toAPI` copies it into `resourceUsage`. The workload webhook requires `resourceUsage` to be divisible by `PodSetAssignment.count`. `MaxInt64` is odd, so an even Pod count fails that check. The scheduler retries the admission and never sets a condition.

This is already the behavior on `main`. It showed up while reviewing the change that keeps the quota check exact.

***What you expected to happen***:
The recorded usage should be the total that was admitted, and a total that cannot be stored should fail once with a condition instead of being retried.

***How to reproduce it (as minimally and precisely as possible)***:
Cohort of two ClusterQueues, each with nominal quota `5E` of an extended resource, borrowing enabled.

1. Seven Pods requesting `1.4E` each (`9.8E` total) are admitted. `resourceUsage` is `9223372036854775807` rather than `9.8E`.
2. Two Pods requesting `5E` each (`10E` total) produce `resourceUsage` `9223372036854775807`, which is not a multiple of 2. The webhook rejects the admission. In one run the scheduler retried it more than 1,800 times in about ten seconds and never set a condition.

***Anything else we need to know?***:
A `Quantity` cannot hold a non-CPU magnitude past `MaxInt64`, so the status field itself cannot store the exact total. The quota check and this status write are separate: the check can see a total the API field then caps.
Found while reviewing the Requests-to-Amount quota fix.
