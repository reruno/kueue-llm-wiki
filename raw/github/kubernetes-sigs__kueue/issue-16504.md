## Description

We are testing MultiKueue with Plain Pods across multiple OpenShift clusters.

The basic dispatch works correctly: the Pod is created on the worker cluster and its status is synced back.

The problem is that the dispatched Pod may reference resources that only exist on the manager cluster, for example:

- Secrets
- ConfigMaps
- ServiceAccounts / imagePullSecrets
- PVCs
- other namespace-scoped dependencies

MultiKueue copies the workload/Pod spec, but does not provision these referenced resources on the selected worker cluster.

This means that real workloads often fail after dispatch unless all dependencies are pre-created on every worker cluster.

We also noticed that some cluster-specific Pod mutations from the manager cluster can be propagated to the worker, which may not be valid there.

Is there a recommended pattern for handling this today?

Would the expected approach be:

- an external syncer/controller,
- a hook or extension point around worker selection/dispatch,
- or something that MultiKueue may support directly in the future?

For reference, https://github.com/openshift-pipelines/syncer-service appears to solve a similar problem for Tekton workloads by syncing required resources after MultiKueue selects a worker.

Any guidance on the intended architecture here would be very helpful.

Environment:

- Kueue v0.19.7
- OpenShift 4.22
- MultiKueue Plain Pods https://kueue.sigs.k8s.io/docs/tasks/run/multikueue/plain_pods/

### Comment by [@sohankunkerkar](https://github.com/sohankunkerkar) — 2026-10-05T20:15:35Z

Dependency sync is a KEP-693 non-goal, and there's no hook between a worker admitting and the Pod being created, since both happen in the same reconcile pass. The place to hook in is earlier: configure MultiKueue to use an external dispatcher instead of a built-in one, and it will dispatch to whichever clusters your controller nominates. So your syncer picks the cluster, creates the deps there, then nominates it, one cluster at a time so nomination is selection.

Your second point is a real bug though. Plain Pods are the only integration where we copy an already-admitted object instead of a template, so the image pull secrets the manager's ServiceAccount admission injected (and the SCC-assigned user ID on OpenShift) ride along. @coderabbitai could you open an issue for that with the label kind/bug and don't assign to anyone?

### Comment by [@jangel97](https://github.com/jangel97) — 2026-10-05T22:58:27Z

@sohankunkerkar We could use an external dispatcher, but that would move cluster selection into our controller. One of the main reasons we are interested in MultiKueue is precisely to let the worker clusters determine where the workload can actually be admitted, based on their local queue/quota/capacity state.

Is there a supported way to gate admission of the remote Workload on each worker while we sync its dependencies, for example using an AdmissionCheck, and only allow it to become admitted once those dependencies are ready?

Ideally we would like to preserve the AllAtOnce model: fan out Workload → sync dependencies on each candidate → worker admission race → first admitted worker wins

That would let MultiKueue remain responsible for cluster selection while an external controller handles dependency synchronization.

### Comment by [@sohankunkerkar](https://github.com/sohankunkerkar) — 2026-10-06T04:35:42Z

Yes, and `AllAtOnce` works as-is. Put your own `AdmissionCheck` on each worker's CQ. `MultiKueue` only creates the Pod once a remote Workload is Admitted, so the first worker to be admitted wins (see the `ProvisioningRequest` test in `test/integration/multikueue`).
On deps your controller creates (not ones already on the worker), set an owner reference to the remote Workload, so the losers' copies get cleaned up when `MultiKueue` deletes their Workloads. Your controller must mark its `AdmissionCheck` Active, or the worker CQ goes inactive. Every candidate also holds quota while its check is pending.

### Comment by [@mimowo](https://github.com/mimowo) — 2026-10-06T15:34:14Z

### Comment by [@kevin85421](https://github.com/kevin85421) — 2026-10-06T16:19:18Z

We have similar issues. For example, we want to use a container registry in the same cloud and region to avoid egress fees when pulling images. However, MultiKueue doesn’t provide a way to modify the images in the CR spec based on the target worker cluster. 

Currently, our worker clusters have clearly defined roles (e.g., some are dedicated to training, while others handle data processing), so most jobs can only be scheduled on specific worker clusters. This makes the limitation acceptable for us. We also rely heavily on https://github.com/kubernetes-sigs/kueue/pull/14539 in our internal fork. We let a coding agent select worker clusters based on application logic (e.g., which region the input data is stored in).

For image pulling, another workaround is to deploy Dragonfly or Spegel so that egress fees are incurred only once per image, but this doesn’t address the Secrets and ConfigMaps issues you mentioned.

For the resources you mentioned, we try to keep their names—including image pull Secrets, NFS PVs, and ConfigMaps—consistent across worker clusters. Definitely, this is not the best UX.

Ideally, MultiKueue should support semantics like: “I want to submit these job variants (e.g., using different image registries) to these worker clusters; please get one of them admitted.”

In addition, populating resources in worker clusters seems to overlap significantly with GitOps tools like Argo CD. We should consider carefully whether this belongs within MultiKueue’s scope.
