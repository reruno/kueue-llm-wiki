## Description


**What would you like to be added**:
When a pod is admitted by kueue, reflect on the pod(s) the selected resource-to-ResourceFlavor name mapping as readable metadata/annotation on the pod before the workload is ungated.

Something like so on the pod:
[kueue.x-k8s.io/resource-flavors](http://kueue.x-k8s.io/resource-flavors): '{"cpu":"flavor-a","memory":"flavor-b"}'

**Why is this needed**:
Today the exact assignment is available only in `Workload.status.admission.podSetAssignments[].flavors`. A Pod-level consumer must therefore discover and watch the corresponding Workload and join the two objects.  We have some use cases that require us to know which Resource Flavor(s) a pod was admitted by, while only reading the pod itself.

**Completion requirements**:
We would like to be able to retrieve which resource flavour a pod was admitted into (or a list if multiple were selected) from the pod (via annotation metadata perhaps). The annotation should not impact pod placement (cannot be a label)
- The Pod exposes the complete resource-to-ResourceFlavor mapping selected for its PodSet upon admission.
- It is informational only and introduces no scheduling constraint; an annotation is ideal.

## Discussion

### Comment by [@sohankunkerkar](https://github.com/sohankunkerkar) — 2026-10-05T20:08:08Z

Thanks for raising this! I think there is a way today. An AdmissionCheck can set `podSetUpdates[].annotations`, and whatever it puts there lands on the pod just before Kueue starts it. The flavor assignment is already on the Workload by then, so the check can just copy it across. Kueue's own ProvisioningRequest check works this way.

Longer term I think Kueue should write it itself, as one annotation holding the whole resource-to-flavor map. One catch here: elastic jobs reuse the same pod template across slices, so the new key has to be allowed to overwrite an older value.

### Comment by [@reemmadkour](https://github.com/reemmadkour) — 2026-10-09T21:50:01Z

Thanks, good to know the AdmissionCheck path works today as an interim option.

 We'd strongly prefer Kueue writing the annotation natively though, for a few reasons:

 1. **Operational overhead.** Every adopter who wants this has to build, deploy, and maintain a custom controller, plus configure every ClusterQueue to require the check. That's a lot of per-cluster setup for what is really just copying data that Kueue already has.
 3. **Correctness by default.** If a ClusterQueue is missing the check, Pods silently get no annotation. Native support means every admitted Pod gets the mapping without opt-in configuration.

 Would you be open to tracking native support as a feature? Happy to contribute if that helps move it forward.

### Comment by [@sohankunkerkar](https://github.com/sohankunkerkar) — 2026-10-10T05:23:37Z

Yeah, I agree Kueue should write this itself. Reading the node selector isn't reliable, since two flavors can set the same label (#14409). If you'd like it in v0.21, could you put up a short KEP soon covering the annotation format, the gate and elastic jobs?
