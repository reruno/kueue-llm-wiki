## Description


## What would you like to be added?

An explicit opt-in mechanism allowing Kueue's Pod integration to manage a Pod even when its owner chain contains a resource type known to Kueue.

For example:

```yaml
metadata:
  annotations:
    kueue.x-k8s.io/manage-as-standalone-pod: "true"
```

Today, the Pod integration excludes Pods whose ancestor belongs to another Kueue job integration. This prevents using the plain-Pod integration as an intentional execution boundary for workloads whose higher-level controllers should remain outside Kueue's management.

This proposal is related to #4106, but our motivation is specifically MultiKueue cross-cluster execution.

## Why is this needed?

We are experimenting with a multi-cluster GPU-as-a-Service architecture:

```text
Source cluster
──────────────
RHOAI / workload-specific controllers
        ↓
TrainJob / RayJob / etc.
        ↓
JobSet / Job / ...
        ↓
Pods
        │
        │ MultiKueue plain-Pod dispatch
        ▼
Shared GPU execution cluster
────────────────────────────
Kueue
GPU Operator
GPU nodes
```

The source clusters may run different versions of RHOAI and its workload-specific controllers, including development/nightly builds.

The shared GPU execution cluster should remain stable and should ideally not require the corresponding Training Operator, KubeRay, RHOAI CRDs, etc.

For that reason, we would like to experiment with using the Kubernetes Pod as the cross-cluster execution boundary.

MultiKueue already supports plain-Pod dispatch and Pod groups, making it potentially suitable for this model.

However, Pods produced by these higher-level controllers commonly have owner chains such as:

```text
TrainJob
  └── JobSet
       └── Job
            └── Pod
```

The Pod integration detects the known ancestor and does not manage the Pod as a plain Pod.

As a result, there is currently no way for us to explicitly say:

> I know this Pod belongs to another workload API, but I intentionally want this Pod to be the Kueue/MultiKueue management boundary.

## Why not dispatch the parent resource?

For our use case, dispatching the higher-level resource introduces coupling between the source and execution clusters.

For example, dispatching a TrainJob requires the execution cluster to understand and reconcile TrainJob and its associated controller stack.

That becomes problematic when multiple source clusters run different versions of those APIs/controllers.

Our desired separation is:

```text
Source cluster:
  workload-specific APIs/controllers
  version under test
          ↓
        Pods
          │
──────────┼────────── execution boundary
          │
          ▼
Execution cluster:
  generic Kubernetes execution
  Kueue quota/admission
  GPU infrastructure
```

We are not proposing that Pod-level dispatch should replace the existing higher-level integrations. We would like an explicit opt-in for users who intentionally want this boundary.

## Pod groups

This is particularly interesting together with Kueue Pod groups.

For distributed workloads, the generated Pods could explicitly carry the existing Pod-group metadata so that they are represented as a single Kueue Workload and dispatched through MultiKueue together.

For example:

```yaml
metadata:
  labels:
    kueue.x-k8s.io/queue-name: gpu
    kueue.x-k8s.io/pod-group-name: training-123
  annotations:
    kueue.x-k8s.io/pod-group-total-count: "4"
```

This could allow the higher-level controller to remain on the source cluster while Kueue handles admission and MultiKueue placement at the execution-Pod level.

We are currently validating the complete semantics of this model, including Services and other dependencies required by distributed workloads.

## Proposed API

One possibility would be an explicit annotation:

```yaml
metadata:
  annotations:
    kueue.x-k8s.io/manage-as-standalone-pod: "true"
```

When present, the Pod integration would be allowed to manage the Pod despite a known ancestor.

Another possibility could be a PodIntegrationOptions configuration field or selector if a cluster-level opt-in is preferred.

The exact API is not important to us; the important capability is having an explicit and safe way to select the Pod as the management boundary.

## Avoiding double management

The main concern appears to be avoiding a situation where both the parent integration and the Pod integration manage the same execution.

Could the opt-in be accepted only when Kueue can determine that the relevant ancestor is not actively managed by another enabled integration?

Alternatively, if determining that safely is difficult, the opt-in could be considered an advanced configuration where Kueue validates as much as possible and documents the requirement that the parent workload must not also be managed by Kueue.

Existing ownerReference/UID and Workload ownership validation should remain unchanged.

## Relationship to #4106

#4106 proposed a `kueue.x-k8s.io/standalone` annotation for allowing known-owned Pods to participate in the Pod integration.

That issue was primarily motivated by workload flexibility such as Spark and dynamically-sized workloads.

Our motivation is different but closely related:

**using plain Pods as an explicit MultiKueue cross-cluster execution boundary.**

The target cluster may intentionally not have the CRDs/controllers associated with the source workload.

We would like to understand whether maintainers would consider revisiting an explicit opt-in mechanism in the context of MultiKueue, or whether there is another supported mechanism we should use to achieve this execution model.
