## Description

<!-- Please only use this template for submitting clean up requests -->

**What would you like to be cleaned**:

At present, the plain yaml manifests are used as the "source of truth", and the helm chart templates are "subservient" to them. That is, when the plain manifests chain, the helm charts must be mutated to accommodate. This relationship should be reversed. This is relatively simple to do by creating a "canonical" values.yaml file that, when run through `helm template` recovers the desired example manifests. If no such values file is possible, the templates are corrected to allow for it.

I am happy to contribute this if approved.

**Why is this needed**:

[This file](https://github.com/kubernetes-sigs/kueue/blob/main/hack/processing-plan.yaml).

No. Absolutely not. This is nonsensical. This is not okay. There is no universe in which this is part of a correct solution, least of all ours. It should have been obvious something was wrong when this file reached a triple-digit line count, and it is within tasting distance of quadruple. I recognize that this is likely out of a desire to stay in line with the outputs of kubebuilder/controller-gen, but having myself given up on doing so for the dozen or so operators I maintain at my current place of employment, I can say its not worth it. If that is still a hard requirement, then a CI action can be used to confirm that the canonical template output matches the kubebuilder output.

Having made 3 PRs related to helm charts, this state of affairs requires an unnecessary templating step, and adds extra unnecessary engineering effort to first reverse engineer the actual desired change and convert it into this second order templating language. This issue is only going to magnify as more features are added to the chart.

Apologies for the delay on this. Figures that life gets busy the day after I offer to do something like this, but that's always how it goes, huh?

I've pushed a draft PR with an proof of concept of at least detecting drift between kubebuilder Kustomize and helm outputs for a given config/values pair. It first validates that there are the same set of objects being output, and then identifies which have differences, through a combination of sorting and pretty-printing. This has actually turned up a number of places where the default values are out of sync with the default Kustomize config, some of which I have addressed, while others will need a bit more thought, namely, the ConfigMap in the helm chart vs Configuration in the manifests.

Having had a chance to grapple with the kubebuilder side of things, I think I better understand the challenge here, and that is really the desire (as I perceive it) to offer many different configurations and options for deployment with the base manifests. It seems evident to me that Kueue is at a level of complexity where, despite all its numerous faults, helm becomes the undisputed best way to offer an all-inclusive packaging for a k8s-deployed product. This is also the reason, as far as I can tell, that most other large projects offer a set of "example" manifests for tire-kicking (and the laggards who insist on doing things by hand or have some sort of personal grudge against helm), and a helm chart for doing things the easy way.

Kueue being a Kubernetes SIG project, and Kustomize being the "official" Kubernetes management tool, and Helm being "only" a CNCF project, I understand the desire to offer Kustomize, but I don't think it will be particularly productive in the long run. Kueue may very well have started at a point where Kustomize was sufficient as a way to distribute it, but it seems to me that it passed that point a long time ago.

### Comment by [@meln5674](https://github.com/meln5674) — 2026-10-12T23:09:12Z

As far as I can tell, the current workflow goes like this:
1. Kubebuilder generates *some* resources from the Go source (CRDs, etc)
2. Developers edit *some* plain manifests to augment them (kueueviz, etc) in the ./config/ directory
3. Developers edit *some* helm chart templates directly
4. Developers edit *some* helm chart templates via yaml-processor file
5. Makefile applies yaml-processor to *some* helm chart templates.
6. Developer manually inspects outputs of step 5.

My proposed workflow would instead look like:
1. Kubebuilder generates some resources from the Go source (CRDs, etc)
2. Makefile compares manifested rendered by helm chart with "canonical" values file against manifests from step 1 to ensure no drift
3. Makefile renders helm chart with one or more sets of "canonical" value files to obtain all plain yaml manifests other than those from step 1 (i.e. that would be manually edited from step 2 of the original workflow)

In other words, the helm chart becomes the source of truth for all manifests which are not dynamically generated, and intrinsically tied to, elements of the Go source code (api types, etc). All changes to anything but the "core operator" manifests would be required to be done through the chart, and the plain yaml manifests would be obtained by re-rendering the chart.
