**What happened**:

When a Workload is deleted after its LocalQueue was deleted, Kueue does not request a requeue of the inadmissible
Workloads in the cohort, even though the deletion frees quota. A Workload that was waiting for that quota in another
queue of the cohort stays pending until some unrelated event triggers a requeue (scenario 1). This happens with and
without `SchedulingEquivalenceHashing`.

With `SchedulingEquivalenceHashing` (Beta, on by default), the same lost requeue also leaves a stale entry in the
ClusterQueue's `hashToBulkMoveReason`. A new Workload with the same shape is then put straight into the inadmissible
list. It has no `QuotaReserved` condition and no message, and it is never tried, even when the cohort is empty
(scenario 2, typical of namespace deletion, which deletes LocalQueues and Workloads in no fixed order).

We found scenario 2 in a benchmark that deletes and recreates a namespace between repetitions. In 2 of the 5 resets
that followed a preemption, Kueue processed the LocalQueue deletion first. The same-shape repetitions after that stayed
stuck (5 of 20 repetitions in total) until an unrelated requeue happened. In the other 3 resets the Workload deletion
was processed first, a requeue followed about 1 s later, and the next repetition was admitted normally.

In a busy cohort another event probably triggers a requeue soon and hides the problem; in a quiet cohort the Workload
stays pending.

**What you expected to happen**:

Scenario 1: when the quota is freed, the waiting Workload is retried and admitted.
Scenario 2: the new Workload is evaluated and admitted, because the cohort has enough unused quota.

**How to reproduce it (as minimally and precisely as possible)**:

Two ClusterQueues in one cohort, 400m CPU each, `reclaimWithinCohort: Any`, default `BestEffortFIFO`. Jobs run
`registry.k8s.io/pause:3.10` with `cpu: 100m` per pod. A single-node kind cluster is enough.

Common start: apply `setup.yaml` and `localqueues.yaml`; apply `train-a.yaml` (admitted by borrowing team-b's 400m);
apply `train-b.yaml` (it reclaims; `train-a` is preempted and goes back to pending as NoFit).

**Scenario 1, LocalQueue only:**

1. `kubectl delete localqueue team-b -n demo`. `train-b` stays admitted and keeps running.
2. `kubectl delete job train-b -n demo`. This frees 400m; team-a's LocalQueue still exists.
3. Result: `train-a` is not admitted within 60 s. After an unrelated 1-pod job in team-a is admitted and deleted,
   `train-a` is admitted.

**Anything else we need to know?**:

What we think happens (line numbers at v0.20.0):

- A Workload delete event requests the cohort requeue through `QueueAssociatedInadmissibleWorkloadsAfter`
  (`handleDelete`, [workload_controller.go#L1350-L1371](https://github.com/kubernetes-sigs/kueue/blob/v0.20.0/pkg/controller/core/workload_controller.go#L1350-L1371);
  [manager.go#L891-L912](https://github.com/kubernetes-sigs/kueue/blob/v0.20.0/pkg/cache/queue/manager.go#L891-L912)).
  The ClusterQueue is found through `workloadAssignedQueues` (Workload → LocalQueue) and then `localQueues`; if the
  LocalQueue is already gone, the function returns without requesting anything.
- `DeleteLocalQueue` removes the LocalQueue's pending Workloads from the ClusterQueue but does not request a requeue
  ([manager.go#L596-L618](https://github.com/kubernetes-sigs/kueue/blob/v0.20.0/pkg/cache/queue/manager.go#L596-L618),
  [localqueue_controller.go#L262-L280](https://github.com/kubernetes-sigs/kueue/blob/v0.20.0/pkg/controller/core/localqueue_controller.go#L262-L280)).
  Admitted Workloads are not affected and keep running, so they can outlive their LocalQueue (scenario 1).
- For scenario 2: on NoFit, `handleInadmissibleHash` records the hash
  ([cluster_queue.go#L622-L635](https://github.com/kubernetes-sigs/kueue/blob/v0.20.0/pkg/cache/queue/cluster_queue.go#L622-L635)),
  and `PushOrUpdate` parks new Workloads with a recorded hash
  ([cluster_queue.go#L416-L423](https://github.com/kubernetes-sigs/kueue/blob/v0.20.0/pkg/cache/queue/cluster_queue.go#L416-L423)).
  The map has no per-entry removal; it is only reset in `queueInadmissibleWorkloads`
  ([inadmissible_workloads.go#L152-L158](https://github.com/kubernetes-sigs/kueue/blob/v0.20.0/pkg/cache/queue/inadmissible_workloads.go#L152-L158)),
  i.e. only by the requeue that was skipped. The deleted Workloads themselves are removed from the queues on both
  paths; only the map entry is left behind.
- Not tested: the Finished path in the Workload update handler calls the same function, so an admitted Workload that
  finishes after its LocalQueue was deleted probably loses the requeue in the same way.

Possible directions (not tried):

1. Request the requeue in `DeleteLocalQueue`, which already has the ClusterQueue and holds the manager lock. This should
   cover scenario 2, but not scenario 1 on its own, because there the quota is freed later.
2. When the LocalQueue is gone, find the ClusterQueue another way, for example from `status.admission.clusterQueue` of
   the deleted or finished Workload. This covers admitted Workloads (scenario 1).
3. For the hash map: park a new Workload by hash only while an inadmissible Workload with the same hash still exists.
   v0.20.0 already keeps per-hash counts of pending Workloads (`schedulingHashCounts`, scheduling_hash_counts.go).
