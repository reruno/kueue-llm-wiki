## Description

**What happened**:

A ClusterQueue with a positive fair sharing weight that borrows only resources its Cohort has nothing lendable for gets a weighted share of 0. Its status shows `borrowed: "4"` for cpu next to `weightedShare: 0`, and `CompareDRS` treats its share as equal to that of a ClusterQueue that does not borrow.

**What you expected to happen**:

A weighted share above 0 while the ClusterQueue borrows, since the `weightedShare` API documentation says that 0 means the usage is below the nominal quota. I'm not sure which value fits when nothing is lendable. With #16488, a weight of 0 gets the maximum share in this state.

**How to reproduce it (as minimally and precisely as possible)**:

1. Enable fair sharing, and create a Cohort with one ClusterQueue that has `fairSharing.weight: 1` and a nominal quota of 4 CPU. Nothing else in the Cohort has CPU quota.
2. Admit a workload that requests 4 CPU in that ClusterQueue.
3. Change the nominal CPU quota of the ClusterQueue to 0. The workload stays admitted.
4. Once the `Active` condition of the ClusterQueue has the new `observedGeneration`, its status has:

```yaml
status:
  flavorsUsage:
  - name: default
    resources:
    - name: cpu
      total: "4"
      borrowed: "4"
  fairSharing:
    weightedShare: 0
```

**Anything else we need to know?**:

`dominantResourceShare` only takes the ratio for resources the Cohort can lend (https://github.com/kubernetes-sigs/kueue/blob/5cb82c5a4159007df57ebb7649160da5c4dc5c66/pkg/cache/scheduler/fair_sharing.go#L175), so the ratio stays 0 while `borrowing` is true. #16488 changes this for a weight of 0 and leaves the positive-weight case as it is, which its `TestDominantResourceShare` keeps as the "positive weight borrowing only a resource with nothing lendable" case.

The statement that 0 means the usage is below the nominal quota is in the `weightedShare` documentation of `FairSharingStatus` in v1beta1 and v1beta2 and of `LocalQueueFairSharingStatus` in v1beta2, and in the help text of `kueue_cluster_queue_weighted_share` and `kueue_cohort_weighted_share`.

Related: #16477

Hi @LindaSummer, welcome, and thanks for picking this up! Sure, go ahead. You can comment `/assign` to take it.

The ratio comes from `dominantResourceShare` in `pkg/cache/scheduler/fair_sharing.go`. It skips any resource the Cohort has nothing lendable for, which is why the share stays at 0 here. #16488 fixed the same state for a weight of 0, so that one is worth reading first.

The part we still need to agree on is the value. With nothing lendable the ratio is basically borrowed / 0, so I'd lean towards +Inf (MaxInt64 in the status, same as a zero-weight borrower). That does change which ClusterQueue gets preempted first though, so @mimowo, does +Inf sound ok to you?
