### Comment by [@yuluo-yx](https://github.com/yuluo-yx) — 2026-10-02T09:57:00Z

I analyzed the current situation: Regarding this issue: the MultiKueue integration tests run in parallel with `-procs=3`, and Ginkgo's `BeforeSuite` is executed in every process. Each process creates 3 envtest clusters—one manager and two workers. This results in a total of 9 kube-apiserver and 9 etcd instances. During the test run, an `INTERNAL_ERROR` occurred in one of the apiservers, causing the Workload to time out.

Based on the above analysis, there are two solutions:

1. Change the `ctx` used for teardown to an independent `context.Background` context pattern. This prevents the context from being canceled after a test failure, which would cause the manager to enter apiserver teardown before it is fully cleaned up.
2. Refactor the `envtest` lifecycle. Keep the parallel mode with `-procs=3`, but prevent each process from independently creating a manager and two workers. Share the control plane using `SynchronizedBeforeSuite`, and then clean everything up uniformly at the end using `SynchronizedAfterSuite`.

The first solution here cannot guarantee the elimination of the APIServer's `INTERNAL_ERROR` issue; it can only solve the teardown lifecycle problem.

What are your thoughts on this? @mimowo @mbobrovskyi. 👀

Evidence:

- [Full build log](https://storage.googleapis.com/kubernetes-ci-logs/pr-logs/pull/kubernetes-sigs_kueue/16532/pull-kueue-test-integration-multikueue-main/2105875436348116992/build-log.txt)
- [Pod metadata](https://storage.googleapis.com/kubernetes-ci-logs/pr-logs/pull/kubernetes-sigs_kueue/16532/pull-kueue-test-integration-multikueue-main/2105875436348116992/podinfo.json)
- The `test` container had a `12 GiB` memory limit and reached `12,871,102,464` bytes (`11.987 GiB`, about `99.89%` of the limit).
- `container_oom_events_total` stayed at `0`, and the container terminated with reason `Error`, not `OOMKilled`.
- The first explicit failure was `timeout waiting for process kube-apiserver to stop` during `[AfterSuite]`. The later `http2: client connection lost` / `INTERNAL_ERROR` was observed while another parallel process was still accessing an envtest API server.

Conclusion:

This is an envtest control-plane lifecycle flake under heavy parallel resource pressure. With `-procs=3`, each Ginkgo process creates a manager cluster and two worker clusters, which can result in up to nine envtest control planes in the same test container. The memory pressure is a highly plausible contributing factor, but we cannot claim that this build was directly caused by an OOM kill. The exact apiserver-side failure remains unconfirmed because `API_LOG_LEVEL=0` and no apiserver/etcd logs were captured.

The long-term direction is to keep `-procs=3` while sharing the control planes through `SynchronizedBeforeSuite` and performing uniform cleanup through `SynchronizedAfterSuite`.

The Prow metrics helper also had a stale datasource/metric configuration; it is addressed separately in [PR #16582](https://github.com/kubernetes-sigs/kueue/pull/16582).
