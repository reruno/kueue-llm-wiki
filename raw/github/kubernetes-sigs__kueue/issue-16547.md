## Description

**What would you like to be cleaned**:

Follow up on the remaining review comments in [PR #16479](https://github.com/kubernetes-sigs/kueue/pull/16479):

- [ ] In `pkg/resources/factory.go`, build `SliceRequests` directly from the input map in `NewRequestsFromMap` when `VectorizedResourceRequests` is enabled. Avoid the intermediate `MapRequests`. Preserve sorted entries, exact values, empty-input behavior, and independence from the caller's map. Test both feature-gate settings and compare construction allocations and `BenchmarkSchedulerTAS`. [Review discussion](https://github.com/kubernetes-sigs/kueue/pull/16479#discussion_r4160460978).
- [ ] In `pkg/resources/resource_formatter.go`, append `m` to the exact CPU fallback in `ResourceFormatter.ExactAmountString`. The internal amount is milli-CPU, not cores. Add tests beyond the Quantity limit, including negative amounts; preserve existing in-range and non-CPU output. [Review comment](https://github.com/kubernetes-sigs/kueue/pull/16479#discussion_r4162310775).

**Why is this needed**:

The vectorized constructor makes an unnecessary map allocation on the scheduling path. The reported direct-construction benchmark reduced allocations, but the follow-up should verify the result.

The CPU fallback currently renders two times `MaxInt64` cores as `18446744073709551614000` without a unit. It should render `18446744073709551614000m` so quota messages do not present milli-CPU as cores.

Admission encoding and webhook retries are already tracked in #16486. The integration flake is tracked in #16498.
