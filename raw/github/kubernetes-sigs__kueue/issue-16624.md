## Description

**What happened**:

During a Kueue rollout, a freshly started replica became leader and began scheduling while its cache was still loading ClusterQueues. The ClusterQueues not yet loaded were missing from the cache along with their admitted Workloads, so TAS counted those Workloads' nodes as free and placed new Workloads on nodes that running pods already filled.

From the new leader's logs (UTC, names anonymized, 8 GPUs per node):

| Time | Log |
|---|---|
| 20:28:10.306 | `Starting manager` |
| 20:28:23.918 | first `ClusterQueue create event` |
| 20:28:25.884 | cycle 5: `wl-victim-1` (cq-a, one 8-GPU pod) admitted to `[node-1]` |
| 20:28:27.088 | `ClusterQueue create event` for cq-b, which holds `wl-occupant-1` |
| 20:28:30.527 | cycle 9: `wl-victim-3` (cq-a, one 8-GPU pod) admitted to `[node-3]` |
| 20:28:30.571 | `ClusterQueue create event` for cq-e, which holds `wl-occupant-3` |
| 20:28:30.945 | last of 588 `ClusterQueue create event` lines |

`wl-occupant-1` (admitted 18:46:19 by the previous leader) and `wl-occupant-3` (64 pods, admitted 19:40:16) each had an 8-GPU pod Running on node-1 or node-3, inside their topology assignments, the whole time. Kueue logs "admitted" after the API write, which follows the cycle's snapshot, so both snapshots predate the occupant's ClusterQueue load.

Before the last ClusterQueue loaded, 25 admissions were written (cycles 2 to 9). Seven landed on nodes already full of running pods. Their pods stayed Pending on those nodes until `waitForPodsReady` (45m) evicted them about 40 minutes later. Until 20:28:32 the log also shows 961 `ClusterQueue for workload didn't exist; ignored for now` lines.

**What you expected to happen**:

The scheduler admits nothing until its cache reflects the existing ClusterQueues, Cohorts, ResourceFlavors, Topologies, and their admitted Workloads. kube-scheduler already waits for all event handlers to sync at startup.

**How to reproduce it (as minimally and precisely as possible)**:

I reproduced it locally with kind, KWOK, and the Kueue v0.19.5 default manifests (one replica). The setup has 20 fake 8-CPU nodes, a Topology with the `kubernetes.io/hostname` level, and a ResourceFlavor for those nodes. An occupant Job from its own ClusterQueue and LocalQueue fills each node. Seven victim Jobs of the same shape wait in another ClusterQueue, and 500 empty ClusterQueues pad the list. Each Job runs one `pause` pod requesting `cpu: 8` with `kueue.x-k8s.io/podset-required-topology: kubernetes.io/hostname`. KWOK runs its "fast" stages without `pod-complete`, so pods stay Running. Then restart Kueue with `kubectl -n kueue-system delete pod -l control-plane=controller-manager`; with `LeaderElectionReleaseOnCancel` the new pod takes the lease at once.

Three settings made the window reachable on a laptop:

- One ClusterQueue per occupant. Initial create events don't arrive in name order, so the victims' ClusterQueue is processed at a random position, and every occupant ClusterQueue processed after it leaves its node looking free.
- A 200m CPU limit on the manager. It stretches the ClusterQueue load from about 20 ms to 0.6 to 2.8 s (7 s in production).
- `failurePolicy: Ignore` on the `vworkload.kb.io` webhook. With one replica the new pod's webhook isn't serving yet, so admission writes fail (`failed calling webhook "vworkload.kb.io": ... connection refused`) even though the logs show the victims assumed onto full nodes. In production, other replicas served the webhook.

Two of three restarts reproduced it. In the first, the victims' ClusterQueue loaded at 21:01:00.809 and cycles 1 to 7 assumed all seven victims by 21:01:00.910. The ClusterQueues of those nodes' occupants loaded later, between 21:01:01.012 and 03.239. The victim pods stay Pending with `0/21 nodes are available: 1 Insufficient cpu, 20 node(s) didn't match Pod's node affinity/selector`. I can share the scripts.

**Anything else we need to know?**:

Code at v0.19.5, unchanged on main at 36c42c8:

- The scheduling loop starts as soon as the manager starts leader-election runnables: [`setupScheduler`](https://github.com/kubernetes-sigs/kueue/blob/8e60d76a91bb9a45754218e569de1088f862ac75/cmd/kueue/main.go#L663-L690), [`Scheduler.Start`](https://github.com/kubernetes-sigs/kueue/blob/8e60d76a91bb9a45754218e569de1088f862ac75/pkg/scheduler/scheduler.go#L222-L233) (main: [main.go](https://github.com/kubernetes-sigs/kueue/blob/36c42c8dfc10abcf90b15fa9c7cba6e28038b471/cmd/kueue/main.go#L697-L724), [scheduler.go](https://github.com/kubernetes-sigs/kueue/blob/36c42c8dfc10abcf90b15fa9c7cba6e28038b471/pkg/scheduler/scheduler.go#L236-L247)).
- A ClusterQueue and its admitted Workloads enter the cache only when its create event is processed: [`ClusterQueueReconciler.Create`](https://github.com/kubernetes-sigs/kueue/blob/8e60d76a91bb9a45754218e569de1088f862ac75/pkg/controller/core/clusterqueue_controller.go#L332-L351) calls [`Cache.AddClusterQueue`](https://github.com/kubernetes-sigs/kueue/blob/8e60d76a91bb9a45754218e569de1088f862ac75/pkg/cache/scheduler/cache.go#L437-L490), which backfills the Workloads.
- [`WorkloadReconciler.Create`](https://github.com/kubernetes-sigs/kueue/blob/8e60d76a91bb9a45754218e569de1088f862ac75/pkg/controller/core/workload_controller.go#L1336-L1365) drops a Workload whose ClusterQueue isn't cached yet.

Nothing makes the first scheduling cycle wait for those initial events.

In #5221 (closed), mimowo noted "there's always potential for the controllers and the scheduler racing against each other during boot time". Waiting for handler sync was the preferred fix, but controller-runtime didn't support it then, and #5276 replaced the PR. As I read #5276, it holds back only a ClusterQueue whose own TAS cache isn't initialized. Here the victims' ClusterQueue was ready, and the occupants' ClusterQueues hadn't been added. controller-runtime v0.25.1 (used by main) now waits for the handler registration's `HasSynced` in `Kind.WaitForSync`, which may remove that blocker.

The core controllers also run on followers (#14386), so a long-running follower that takes over should already have a warm cache. We have seen this only when a freshly started replica became leader, as in a rollout or a single-replica restart. Cohort quota accounting is probably affected too; I only checked TAS.

### Comment by [@dundysm](https://github.com/dundysm) — 2026-10-03T11:34:36Z

hi @anguszzzz and @mimowo, taking this. after a cold leader start the scheduler can admit a workload before every clusterqueue is in its cache, so topology aware scheduling treats occupied nodes as free. the change is a startup gate in scheduler.start: do not schedule until two successive lists of clusterqueues, cohorts, resourceflavors, and topologies are present in the kueue cache and every workload with an active quota reservation is recorded. the tas math stays as it is.
