## Description

## What happened?

In an isolated test cluster running Kueue v0.16.9 and JobSet v0.10.1, we observed increasing Kueue controller-manager memory while two-stage JobSets repeatedly went through readiness timeout, eviction, and re-admission.

Each JobSet contains two replicated jobs, with one replica each:

- `stage-a` runs a sleeping loop and does not complete.
- `stage-b` depends on `stage-a` reaching `Complete`.

Consequently, the second stage cannot start, and the JobSet does not satisfy the overall PodsReady condition. With `waitForPodsReady` enabled and no explicit requeue-count limit, the workload repeatedly enters the timeout/requeue cycle.

The readiness/dependency interaction has already been discussed in [#6796](https://github.com/kubernetes-sigs/kueue/issues/6796), but remains unresolved as of October 3, 2026. The attempted fix in #7889 was reverted by [#8294](https://github.com/kubernetes-sigs/kueue/pull/8294), and #6796 remains open. This report adds memory observations under sustained workload arrivals and repeated control processing.

## Environment and configuration

| Setting | Value |
|---|---|
| Kueue / JobSet controller | v0.16.9 / v0.10.1 |
| Kueue manager | One Pod; CPU request/limit: 3; memory request/limit: 512Mi |
| `waitForPodsReady.timeout` / `recoveryTimeout` | 5m / 5m |
| `blockAdmission` | false |
| `requeuingStrategy.backoffLimitCount` | Unset |
| `backoffBaseSeconds` / `backoffMaxSeconds` | 5 / 5 |
| Ordinary Jobs | 30/s; one Pod running `sleep 1`; finished-job TTL: 10s |
| JobSet arrivals | 100 independent submitters, each at 0.003/s, uniformly staggered; aggregate: 0.3/s |
| Placement | Ordinary Jobs and JobSets use separate worker groups but share the control plane and ClusterQueue |

The aggregate ordinary-Job-to-JobSet arrival ratio is **100:1**, not 10000:1. The latter describes the ordinary Job stream relative to one JobSet submitter.

## Observed memory usage

In the diagnostic run started on **2026-09-21 at 15:35 UTC**, memory increased over approximately 80 minutes:

| Measurement | Value |
|---|---:|
| Sampled heap `inuse_space` immediately before workload arrivals | 56.23 MiB |
| Later sampled heap `inuse_space` | 237.96 MiB |
| Nearby Go `HeapAlloc` | 364.80 MiB |
| Nearby container working set | 489.51 MiB |

These metrics have different definitions and were collected at nearby, rather than identical, timestamps; they must not be added together.

In the later heap profile, mutually exclusive classification by allocation stack attributed approximately **54.45%** of sampled in-use bytes to API Watch decoding and **11.57%** to informer callbacks. Workload copies and admission/reconciliation processing were also visible.

These are allocation origins, not proof of which cache or queue retains every object. We are **not claiming a confirmed memory leak or permanent storage of every requeue event**. Continued arrivals also increase the inventory of unfinished JobSets, and ordinary Job objects share the same manager. We have not separately isolated inventory growth from the effect of repeated updates.

## Reproduction outline

1. Configure the versions, resource budget, and readiness/requeue settings above in an isolated cluster.
2. Submit two-stage JobSets with the dependency described above, alongside short-lived ordinary Jobs at the stated rates.
3. Track readiness-timeout/requeue transitions, object inventory, manager memory, and heap profiles over time.

This describes the measured workload; it has not yet been reduced to a minimal reproducer with the same memory growth.

## Expected behavior / questions

We would appreciate guidance on whether the observed memory footprint is expected for the retained object inventory, or whether repeated readiness-timeout/requeue processing introduces avoidable allocations or retention.

Which additional measurements would best distinguish current-object cache occupancy from pending notifications and transient processing data? Is there an existing issue or fix covering this specific path?

We believe that the same readiness-timeout/requeue cycle may also occur in the latest Kueue release, although we have not experimentally verified this.

We can provide heap profiles, timestamped memory statistics, and object-inventory summaries after redaction.
