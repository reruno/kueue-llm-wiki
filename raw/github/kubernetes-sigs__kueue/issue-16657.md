**What happened**:

When an elastic Workload's replacement slice shrinks one PodSet and grows another, whether it is admitted depends on the PodSet order.

If the shrinking PodSet comes first, the replacement is admitted. If the growing PodSet comes first, the same replacement stays pending with `insufficient unused quota … N more needed`, even when it fits within the quota the predecessor already holds. Meanwhile the predecessor keeps its full quota reservation.

This happens with the default feature gates (`ElasticJobsViaWorkloadSlices` only). It is not limited to partial replica scale-up.

**What you expected to happen**:

The replacement is admitted regardless of PodSet order, since the shrink frees more than the grow needs.

**How to reproduce it (as minimally and precisely as possible)**:

ClusterQueue with `pods: 7`. Elastic RayCluster (`kueue.x-k8s.io/elastic-job: "true"`) with head 1 and two worker groups: `workers-b` (2 replicas), then `workers-a` (4 replicas). It gets admitted using all 7 pods.

Then either:
1. In one update, set `workers-a` to 1 and `workers-b` to 5 (7 pods in total); or
2. Set `workers-b` to 5 first (the replacement waits for quota), then set `workers-a` to 1.

In both cases the replacement (`head=1, workers-b=5, workers-a=1`) stays pending with `couldn't assign flavors to pod set workers-b: insufficient unused quota for pods in flavor default, 3 more needed`. With the worker groups listed as `workers-a, workers-b`, both cases are admitted.

I reproduced this in the RayCluster integration suite (envtest) on main, and as `TestSchedule` cases in `pkg/scheduler`.

**Anything else we need to know?**:

- This predates #16371; I found it while testing that PR.
- For a RayCluster, the PodSet order is the worker group order in the user's spec.
- Case 2 is the shape you would expect from the Ray autoscaler on a full ClusterQueue: a scale-up waits for quota, then an idle group is scaled down to make room.
- The existing shrink/grow integration tests (from #16289 and #16371) list the shrinking group first.
- It looks like the per-PodSet quota check in `pkg/scheduler/flavorassigner` credits a shrinking PodSet's freed quota only to PodSets checked after it. I have not confirmed this beyond the cases above.

AI assistance was used to run these cases and draft this issue.

**Environment**:
- Kueue version: main at `02bd8807f` (#16371 head). The same quota-check code is on release-0.19 and 0.20, but I did not run it there.
- Not reproduced on a live cluster with KubeRay or the Ray autoscaler.
