**What happened**:

When fair-share preemption is configured and there are multiple ResourceFlavors, a ClusterQueue that is initially borrowing on a contented ResourceFlavor can have its Workloads preempted even when the ClusterQueue would still be within quota with some of those Workloads still admitted, as long as the ClusterQueue is borrowing on an unrelated ResourceFlavor.

**What you expected to happen**:

When Kueue is preparing a list of Workloads to preempt, each incremental Workload is only a preemption candidate if its ClusterQueue would still be borrowing on that Workload's ResourceFlavor(s) after preempting the previous preemption candidates.

**How to reproduce it (as minimally and precisely as possible)**:

```
┌──────────────────────────────────────┬────────────────┬──────────────┬─────────────────────────────────────────────────────────────────────────────────┐
│             ClusterQueue             │ default flavor │ other flavor │                                    Admitted                                     │
├──────────────────────────────────────┼────────────────┼──────────────┼─────────────────────────────────────────────────────────────────────────────────┤
│ preemptor (reclaimWithinCohort: Any) │ 4 CPU          │ none         │ nothing                                                                         │
├──────────────────────────────────────┼────────────────┼──────────────┼─────────────────────────────────────────────────────────────────────────────────┤
│ victim                               │ 2 CPU          │ 2 CPU        │ w1, w2, w3 on default (3 used, borrowing 1); w0 (10 CPU) on other (borrowing 8) │
├──────────────────────────────────────┼────────────────┼──────────────┼─────────────────────────────────────────────────────────────────────────────────┤
│ lender                               │ none           │ 8 CPU        │ nothing                                                                         │
└──────────────────────────────────────┴────────────────┴──────────────┴─────────────────────────────────────────────────────────────────────────────────┘
```

Incoming workload `wi` in `preemptor` CQ requesting 5 `default` quota.  The workload can fit only if 2 out of `w1`, `w2`, and `w3` are preempted, but after the first of those is preempted `victim` is no longer borrowing.

Expected behavior: No workloads are preempted and `wi` remains pending.

Actual behavior: `w1` and `w2` are preempted and `wi` is admitted.

**Anything else we need to know?**:

The bug is most like in https://github.com/kubernetes-sigs/kueue/blob/main/pkg/scheduler/preemption/fairsharing/ordering.go#L156.  Specifically, `nextTarget` checks if remaining CQs are borrowing on any flavor, but should instead check that they are borrowing only on the contended flavors.  The initial set of candidate CQs is filtered to those borrowing on the contended flavors.

**Environment**:
- Kubernetes version: v1.34.11
- Kueue version: v0.19.0
