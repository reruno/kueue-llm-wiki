**What happened**:

With fair-share enabled, hierarchical cohorts, and multiple resource flavors, Kueue can enter an infinite preemption and readmission loop.  This occurs when the fair-share preemption ordering based on DRS disagrees with the admission tournament re-admission ordering.  Specifically, fair-share preemption can choose a cohort as preemption victim when it is not borrowing on the contested flavor, as long as it is sufficiently borrowing on a separate flavor.  Readmission ordering then favors the preempted workload over the preemptor since it only considers the contested flavor.

**What you expected to happen**:

Kueue should make forward progress, whether that is towards fair-share ordering or admission ordering.

**How to reproduce it (as minimally and precisely as possible)**:

This example was generated by AI tools as a simplification of an observed preemption loop:
```
The root has two cohorts, two GPU types (gpu-x and gpu-y), 24 GPUs in total, and every queue uses reclaimWithinCohort: Any.

┌────────┬─────────┬─────────────┬─────────────┬──────────────────────────────────────────────┐
│ Cohort │  Queue  │ gpu-x quota │ gpu-y quota │                   Running                    │
├────────┼─────────┼─────────────┼─────────────┼──────────────────────────────────────────────┤
│ A      │ a-train │ 8           │ 8           │ A1: 8 gpu-x                                  │
├────────┼─────────┼─────────────┼─────────────┼──────────────────────────────────────────────┤
│ B      │ b-owner │ 8           │ 0           │ Y1: 6 gpu-y (borrowed from A)                │
├────────┼─────────┼─────────────┼─────────────┼──────────────────────────────────────────────┤
│ B      │ b-inf   │ 0           │ 0           │ I1, I2: 4 gpu-x each (borrowed from b-owner) │
└────────┴─────────┴─────────────┴─────────────┴──────────────────────────────────────────────┘
```

P (4 gpu-x) arrives in a-train.

1. The score check runs. With P, a-train would use 12 against its 8 quota, so the within-quota shortcut doesn't apply.
2. The preemption passes on a strict score difference. A with P scores 4/24 = 0.17. B after losing I1 scores 6/24 = 0.25 from its gpu-y borrowing. 0.17 < 0.25, so I1 is evicted.
3. The admission order reverses it with its first rule. B with I1 back uses 8 of its 8 gpu-x, so it isn't borrowing on what I1 requests. A with P would be borrowing gpu-x. I1 goes first because B isn't borrowing; scores and priority are never compared.
4. I1 is readmitted and P is skipped. The state is back where it started, and the loop repeats.

**Anything else we need to know?**:

This appears to be distinct from another preemption infinite loop issue: https://github.com/kubernetes-sigs/kueue/issues/14543.

**Environment**:
- Kubernetes version: v1.34.11
- Kueue version: v0.19.0
