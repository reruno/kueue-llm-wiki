**What happened**:

With the MultiKueue Incremental dispatcher, every scale-up of an elastic job makes the dispatcher try to nominate worker clusters for the new Workload slice. The new slice already has `status.clusterName`, because the scheduler copies it from the slice it replaces so that the job stays on the same worker cluster. The API server rejects the update:


```
ERROR	multikueue_incremental_dispatcher	workloaddispatcher/incrementaldispatcher.go:160	Failed to patch nominated clusters	{"namespace": "multikueue-7xlrx", "name": "job-job-209b2", "error": "Workload.kueue.x-k8s.io \"job-job-209b2\" is invalid: status: Invalid value: clusterName and nominatedClusterNames are mutually exclusive"}
```
controller-runtime also logs a "Reconciler error" for each attempt, and the request is retried with backoff until the slice's MultiKueue admission check is Ready. The slice still reaches its worker cluster, because the MultiKueue workload reconciler syncs it to the assigned cluster, so the impact is error logs, rejected API requests and retries on every scale-up.

**What you expected to happen**:

The Incremental dispatcher does not nominate clusters for a Workload that already has a cluster, and scaling up an elastic job logs no errors. This is how it behaved up to v0.17.

**How to reproduce it (as minimally and precisely as possible)**:

1. Configure MultiKueue with `dispatcherName: kueue.x-k8s.io/multikueue-dispatcher-incremental`.
2. Run an elastic job through MultiKueue, for example a batch/v1 Job with the annotation `kueue.x-k8s.io/elastic-job: "true"`, and wait until it runs on a worker cluster.
3. Scale it up, for example by increasing `spec.parallelism`.
4. The manager logs "Failed to patch nominated clusters" with the error above for the new slice, several times.
The integration tests show it too. In `test/integration/multikueue/elasticjob_test.go`, pass `MultiKueueDispatcherModeIncremental` instead of `MultiKueueDispatcherModeAllAtOnce` to `managerAndMultiKueueSetup` and run the "MultiKueue ElasticJob" specs. They pass, but the log has 36 rejection lines: each of the 3 new slices (two Jobs and one RayCluster) is rejected 6 times, and each rejection is logged twice. With the default AllAtOnce dispatcher the same specs log none.

**Anything else we need to know?**:

This is a regression from #11598 , first released in v0.18.0. Before it, the Incremental dispatcher skipped any Workload with a cluster name. #11598 replaced that check with the shared `workload.ShouldSkipClusterNomination`, which deliberately does not skip elastic Workloads that have a cluster name, because the MultiKueue workload reconciler still has to sync such a slice to its cluster. The dispatcher does not handle that case, so it goes on to nominate clusters, and the CRD rule on Workload status forbids `clusterName` and `nominatedClusterNames` together.
ElasticJobsViaWorkloadSlices is Beta and enabled by default since v0.18, so v0.18, v0.19 and v0.20 are affected. The default AllAtOnce dispatcher is not.
A fix is to skip nomination in the Incremental dispatcher again whenever the Workload already has a cluster name. I have it ready with a regression test and will open a PR. I found this while working on #10937.
