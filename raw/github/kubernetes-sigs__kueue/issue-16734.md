## Description

**What happened**:

`Workload` CRs scheduled and admitted onto a DWS `ResourceFlavor` ([backing a `RayJob` CR, as documented here in GKE documentation](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/provisioningrequest#create-provisioningrequest))) fail to progress due to an implementation error in the [concurrent admission](https://kueue.sigs.k8s.io/docs/concepts/concurrent_admission/) feature.

These CRs optionally schedule onto node pools using GKE's [Dynamic Workload Scheduler](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/provisioningrequest). When a `RayJob` CR (`Workload` CR) in a `ClusterQueue` CR with concurrent admission enabled is scheduled onto a DWS node pool, a `ProvisioningRequest` is created and the job is admitted, but the pods assigned to the Ray cluster fail are reported to be unscheduleable by Kubernetes. **As a result the job never progresses.**

This occurs because the _variant_ `Workload` sets the correct `autoscaling.x-k8s.io/consume-provisioning-request` and `autoscaling.x-k8s.io/provisioning-class-name` pod annotations, as expected by the GKE autoscaler, in the admission check's `podSetUpdates` value. However, this `podSetUpdate` doesn't get copied to the parent `Workload`, and the parent `Workload` is authoritative for the `RunWithPodSetsInfo` operation that actually stands up the job.

**What you expected to happen**:

`Workload` schedules in the expected way.

**How to reproduce it (as minimally and precisely as possible)**:

Create a `ClusterQueue` CR that has concurrent admission enabled and includes a DWS resource flavor in a GKE cluster. Attempt to schedule a `Workload`.

**Anything else we need to know?**:

This is blocking for adoption of concurrent admission feature for our use cases.
