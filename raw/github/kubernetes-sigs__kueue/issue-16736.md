**What happened**:
A Job using `kueue.x-k8s.io/prebuilt-workload-name` is deleted while its Workload survives in a finished state. A new Job is then created with the same prebuilt-workload name. The new Job adopts the predecessor's finished Workload, is immediately declared finished, and stops being managed by Kueue — it runs unsuspended and outside quota accounting.

In one reconcile:

1. `ensureOneWorkload` fetches the Workload by the prebuilt name. Its controller check only rejects when a *different* controller already owns it (`controlledBy != nil && controlledBy.UID != object.GetUID()`), so a Workload with no controller reference falls through.
2. `EnsurePrebuiltWorkloadOwnership` claims it unconditionally — sets a controller reference to the new Job and rewrites `JobUIDLabel` to the new UID. Nothing checks whether the Workload is already finished.
3. `ReconcileGenericJob` reaches the `wl != nil && workloadfinish.IsFinished(wl)` branch, calls `finalizeJob`, emits `FinishedWorkload`, and removes the Workload's finalizer.

The Job is left running with `suspend: false`, holding no quota reservation, with an event stating its work is finished.

**What you expected to happen**:

Unclear, which is partly why I'm asking rather than asserting a bug. Reusing a prebuilt Workload may be intentional in some scenarios. But adopting one that is already *finished* seems different: the new Job can never be admitted, since Kueue believes the work is done, and it escapes quota management silently.

**How to reproduce it (as minimally and precisely as possible)**:
Table test case in `pkg/controller/jobs/job/job_controller_test.go`:

- a Job with `PrebuiltWorkloadLabel("prebuilt-workload")`, `UID("new-uid")`, `Suspend(false)`
- a Workload named `prebuilt-workload` with no controller reference, carrying `WorkloadFinished` / `Succeeded`

After reconcile, the Workload comes back with a controller reference to the new Job and `JobUIDLabel: new-uid`, and the Job emits `FinishedWorkload`. Happy to attach the test case or open a PR with it if useful.


**Anything else we need to know?**:
Found while working on #14672, where the owner's finish timestamp is copied from the Workload — in this scenario a new Job would inherit its predecessor's finish time. But the adoption itself looks independent of that work.

Is this intended behaviour for prebuilt workloads, or should `ensureOneWorkload` refuse to adopt a Workload that is already finished?
