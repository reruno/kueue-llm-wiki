## Description

**What happened**:

When a Job references a `ResourceClaimTemplate` whose `deviceClassName` is not present in Kueue's `deviceClassMappings` configuration, the resulting Workload gets stuck in pending state without any status condition, event, or log message explaining why it can't be admitted.

The `TotalRequests()` call in `pkg/dra/claims.go` returns a `field.NotFound` error when `mapper.Lookup(dc)` fails ([claims.go around L302-308](https://github.com/kubernetes-sigs/kueue/blob/main/pkg/dra/claims.go)), but this error is swallowed during workload preprocessing. The workload never reaches the scheduler, and the user has no way to tell what's wrong without reading controller-manager debug logs.

**What you expected to happen**:

The Workload should get a visible status condition (e.g. `QuotaReserved=False` with a reason like `UnmappedDeviceClass`) or at least an Event on the Workload object, so users can quickly see the misconfiguration and fix their `deviceClassMappings`.

This is different from #15953 which covers DRA-specific reasons during the *quota reservation reconciliation path*. This bug is about the *preprocessing stage* — the workload never even gets queued for admission.

**How to reproduce it (as minimally and precisely as possible)**:

1. Deploy Kueue with DRA enabled (`KueueDRAIntegration` feature gate on).
2. Create a `ClusterQueue` / `LocalQueue` setup. Do NOT add a mapping for a device class called, say, `example.com/unmapped-gpu` in the Kueue configuration's `deviceClassMappings`.
3. Submit a Job with a `ResourceClaimTemplate` that references `deviceClassName: example.com/unmapped-gpu`:

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: test-dra-unmapped
  labels:
    kueue.x-k8s.io/queue-name: my-queue
spec:
  template:
    spec:
      containers:
      - name: worker
        image: busybox
        command: ["sleep", "10"]
      resourceClaims:
      - name: gpu-claim
        resourceClaimTemplateName: gpu-template
      restartPolicy: Never
---
apiVersion: resource.k8s.io/v1
kind: ResourceClaimTemplate
metadata:
  name: gpu-template
spec:
  spec:
    devices:
      requests:
      - name: gpu
        exactly:
          deviceClassName: example.com/unmapped-gpu
          count: 1
```

4. Observe the Workload stays pending. `kubectl describe workload <name>` shows no conditions explaining why.

**Anything else we need to know?**:

Looking at the code, `chargesForClaimSpec` in `pkg/dra/claims.go` correctly returns `field.NotFound` when the device class isn't in the mapper. And `TotalRequests` propagates this error. But the caller that preprocesses workloads before queueing doesn't surface the error back as a Workload condition or Kubernetes Event. It just drops the workload from the scheduling cycle silently.

A fix could:
- Set `QuotaReserved=False` with a new reason like `UnmappedDeviceClass` and a message naming the missing class.
- Or emit a Warning event on the Workload so it shows up in `kubectl describe`.

Related: #15953 (DRA-specific reasons for `WorkloadQuotaReserved=False`, but covers the reconciliation path, not preprocessing).
