## Description

**What happened**:

Kueue preempted a PyTorchJob whose Pod was bound to a node but still `Pending` (pulling its image). In the same reconcile that set `spec.runPolicy.suspend=true`, it cleared the Workload's quota reservation. About 4.4 s later it re-admitted the Workload onto a **different** node and set `suspend=false` again. The training-operator didn't reconcile the job until `suspend` was already back to `false`, so it never deleted the old Pod. That Pod went on to run on its original node, while the Workload's `TopologyAssignment` pointed at the new one.

Sequence from the kube-apiserver audit log and the training-operator log:

| t | actor | action |
|---|---|---|
| 0 | Kueue | Workload evicted (`Preempted`); job patched to `runPolicy.suspend=true` |
| +12 ms | Kueue | quota reservation cleared, in the same reconcile |
| +4.4 s | Kueue | Workload re-admitted with a `TopologyAssignment` on a different node; job patched to `suspend=false` |
| +7.9 s | training-operator | first reconcile of the job since the eviction: `suspend=false`, Pod `Pending` with no `deletionTimestamp`, so the Pod is kept |

The operator never deleted that Pod; it stayed until we removed it by hand hours later. When the operator did reach the job, its status had `JobSuspended=False` (reason `PyTorchJobResumed`), written about a minute earlier when the operator handled the previous admission. The operator never observed the second suspend.

Code path (Kueue v0.19.0; same logic in v0.19.7, v0.20.0 and `main`):

1. In the eviction branch, `stopJob` is followed in the same pass by `if !job.IsActive() { ...UnsetQuotaReservationWithCondition... }` ([reconciler.go#L558-L597](https://github.com/kubernetes-sigs/kueue/blob/v0.19.0/pkg/controller/jobframework/reconciler.go#L558-L597); on `main` the clear is `clearAdmissionAfterEviction`, [L661-L675](https://github.com/kubernetes-sigs/kueue/blob/97d2acbe237e28762e2354cfc9e3422dfbf3b55f/pkg/controller/jobframework/reconciler.go#L661-L675)).
2. `KubeflowJob` implements neither `JobWithCustomStop` nor `ComposableJob` ([kubeflowjob_controller.go#L41-L44](https://github.com/kubernetes-sigs/kueue/blob/v0.19.0/pkg/controller/jobs/kubeflow/kubeflowjob/kubeflowjob_controller.go#L41-L44)), so `stopJob` only patches `suspend` (and restores the PodSet info).
3. `KubeflowJob.IsActive()` returns true only if some `status.replicaStatuses[].active != 0` ([kubeflowjob_controller.go#L134-L141](https://github.com/kubernetes-sigs/kueue/blob/v0.19.0/pkg/controller/jobs/kubeflow/kubeflowjob/kubeflowjob_controller.go#L134-L141)).
4. In the v1 training-operator, `active` is documented as "The number of actively running pods" ([common_types.go#L77-L78](https://github.com/kubeflow/trainer/blob/v1.9.4/pkg/apis/kubeflow.org/v1/common_types.go#L77-L78)). `UpdateJobReplicaStatuses` increments it only for `PodRunning` with no `deletionTimestamp` ([status.go#L34-L50](https://github.com/kubeflow/trainer/blob/v1.9.4/pkg/core/status.go#L34-L50)). This has been intentional since kubeflow/trainer#578. A Pod that is bound but `Pending` adds 0, so `IsActive()` is already false before the operator has done anything.
5. The operator deletes Pods only in the `IsJobSuspended(runPolicy)` branch of `ReconcileJobs` (`CleanUpResources`, [job.go#L146-L166](https://github.com/kubeflow/trainer/blob/v1.9.4/pkg/controller.v1/common/job.go#L146-L166)). If `suspend` is already `false` again on its next pass, that branch doesn't run. The resume branch (L167-L173) runs only when `JobSuspended=True`, so it doesn't run either, and `ReconcilePods` keeps the existing Pod. With the default `--controller-threads=1` and a large job ahead of this one in its queue, the operator took about 8 s to get there.

Impact with TAS (hostname is the lowest level, one full-node Pod per GPU node): TAS usage for TAS Pods comes only from Workload `TopologyAssignment`s ([tas_flavor.go#L157-L168](https://github.com/kubernetes-sigs/kueue/blob/v0.19.0/pkg/cache/scheduler/tas_flavor.go#L157-L168)), and TAS Pods are excluded from per-node usage (`belongsToNonTASCache` returns false for `utiltas.IsTAS(pod)`, [non_tas_usage_controller.go#L82-L88](https://github.com/kubernetes-sigs/kueue/blob/v0.19.0/pkg/controller/tas/non_tas_usage_controller.go#L82-L88)). After the re-admission:

- The old node runs the Pod but looks free to TAS. Kueue pins a worker of the next gang there, and that Pod stays `Pending` with `1 Insufficient nvidia.com/gpu, N-1 node(s) didn't match Pod's node affinity/selector`. The gang hits `PodsReadyTimeout`, is requeued, and is often placed on the same node again. In the case above, Kueue pinned 31 Pods from 23 different jobs to the occupied node before we cleaned it up.
- The newly assigned node is reserved for a Pod that never arrives.

So each orphan costs two nodes until the old Pod is deleted for some other reason: one is reserved but empty, and the other is occupied but keeps attracting Pods that can't run there.

Scale, on one large production cluster with heavy preemption:

- On the days we sampled over the last two months, we confirmed between 8 and 66 of these orphans per day, rising over that period; the two most recent full days had 53 and 66. These are lower bounds, because our logs drop lines. Most orphans were gone within 20 minutes; a few per day lasted longer, some for many hours.
- In one busy hour, we counted about 200 cases (across about 80 PyTorchJobs) where Kueue patched a job twice within 20 s, suspending and then resuming it, with no training-operator write to the job in between. Each one opens this race; not every one leaves an orphan.

**What you expected to happen**:

For an integration whose stop is carried out by another controller, Kueue should keep an evicted Workload's quota reservation, and so block its re-admission, until that controller has acted on the suspend. At minimum, it should not release the quota in the same reconcile that submits the suspend, based on a status read before the suspend was written.

This is more than a question of how soon quota is released. As we read KEP-10076, even the default `OnQuotaReleased` strategy assumes the integration's controller still carries out the stop. Here it never does, so the Pods outlive the admission until something else deletes them.

**How to reproduce it (as minimally and precisely as possible)**:

We reproduced this on a small dev cluster (CPU-only is enough):

1. Kueue with the Kubeflow PyTorchJob integration, priority-based preemption, and a TAS flavor whose lowest level is `kubernetes.io/hostname`. Size the ClusterQueue so that jobs A and B below don't fit together, but A and C do.
2. Admit a low-priority PyTorchJob A (one replica). Make its Pod stay `Pending` after binding, e.g. with an init container that sleeps.
3. Stall the training-operator. We held its leader-election `Lease`; scaling its Deployment to 0 should also work.
4. Submit a high-priority job B that preempts A. Then cordon A's node and delete B, so A is re-admitted onto a different node.
5. Un-stall the operator. It reconciles A with `suspend=false` and keeps the old Pod: no `delete pods` call for it appears in the audit log.
6. A's Pod is still on the original node, while A's Workload `TopologyAssignment` names the new node. Uncordon the original node and submit job C sized to it. Kueue pins C's Pod there, and it fails with `0/N nodes are available: 1 Insufficient cpu, N-1 node(s) didn't match Pod's node affinity/selector`.

**Anything else we need to know?**:

Variants we also observed:

- **Eviction during the operator's pod-creation loop.** For a 40-worker job, the eviction landed about 1.2 s into the operator's reconcile that was creating the Pods. The job was re-admitted and resumed about 1.5 s later, while that same reconcile was still creating the remaining Pods. The operator writes the resume (`JobSuspended=False`) only in the status write at the end of that reconcile ([job.go#L339](https://github.com/kubeflow/trainer/blob/v1.9.4/pkg/controller.v1/common/job.go#L339) `ReconcilePods`, then [L361](https://github.com/kubeflow/trainer/blob/v1.9.4/pkg/controller.v1/common/job.go#L361)). So in this window the API can still show `JobSuspended=True` from before the admission, and the new Pods aren't counted in `active` either. The 11 Pods that had already been ungated against the previous assignment kept running outside the new `TopologyAssignment` for more than a day.
- **Quota released while Pods are still `Terminating`.** The suspend branch zeroes `active` and sets `JobSuspended=True` in the status write right after it *issues* the deletes. This is #10076; the KEP-10076 table already notes it for PyTorchJob.

Related work, and why none of it covers this path today:

- #14441 (draft) adds `JobWithStopAcknowledgement`, with a `KubeflowJob.StopAcknowledged()` that reads `JobSuspended`. However, `stopSettled` is used only for the prebuilt `OutOfSync` finish. The PR description says "Admission and eviction keep using `IsActive()` unchanged", and the eviction hunk only changes `if err := r.stopJob(` to `if _, err := r.stopJob(`. #14486 tracks the remaining integrations, but only for that `OutOfSync` path.
- Applied to eviction, that gate would have held the quota in the main sequence above, because `JobSuspended` was `False`. Three cases would still be open:
  - A missing condition is treated as acknowledged, and a job the operator never saw suspended has no `JobSuspended` condition.
  - A stale `JobSuspended=True` from before an unprocessed resume also counts as acknowledged. This is the pod-creation variant above; the PR notes the same limitation. Kubeflow v1 `JobStatus` has no `observedGeneration`.
  - `Terminating` Pods (#10076).
- KEP-10076 plans Kubeflow support for `OnTerminal` in Beta as "Evaluates operator replica statuses". Those statuses never count bound-but-`Pending` Pods or Pods created in the current reconcile, and they are zeroed while Pods are still `Terminating`, so a replica-status check would miss all of the cases above. It would need to look at the Pods, or at a stop acknowledgement.
- #15980 (WIP) makes RayCluster stay active until KubeRay reports suspended. #16027 is auditing `IsActive` semantics; its "deciding whether an evicted Workload can release its quota" and "an unsuspended job that is starting but not ready" are exactly the cases in this report.
- Changing the training-operator to count `Pending` Pods as `active` isn't a clean fix. `UpdateJobStatus` sets `JobRunning=True` from `active > 0` ([pytorchjob_controller.go#L376-L424](https://github.com/kubeflow/trainer/blob/v1.9.4/pkg/controller.v1/pytorch/pytorchjob_controller.go#L376-L424)), and `KubeflowJob.PodsReady()` reads `JobRunning` ([L143-L150](https://github.com/kubernetes-sigs/kueue/blob/v0.19.0/pkg/controller/jobs/kubeflow/kubeflowjob/kubeflowjob_controller.go#L143-L150)), so gangs would look ready early.
- On the TAS side, #11858 describes the same end state reached through node-failure reassignment: an ungated Pod pinned to a domain outside the current `TopologyAssignment`. #16339 lists "excess or relocated Pods ... while an active reservation still covers the Pod" as out of scope.
