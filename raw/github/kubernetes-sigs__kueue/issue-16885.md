## Description

<!-- Please only use this template for submitting enhancement requests -->

  **What would you like to be added**:

A first-class way to pace workload admission so Kueue does not release more work to the downstream scheduler than it can bind — specifically, a configurable cap on the number of admitted-but-not-yet-scheduled pods (or workloads) "in flight".

Proposed as a narrow building block, not a general rate limiter. Rough shape (open for discussion):

- A limit (e.g. `maxInFlightPods` / `admissionConcurrency`) on `ClusterQueue` and/or the Kueue `Configuration`.
- Semantics: Kueue holds an otherwise quota-fitting Workload in a not-yet-admitted state while `inFlightPods + workloadPodCount > N`, where "in flight" = pods Kueue has ungated but the scheduler has not yet bound (`spec.nodeName == ""` / `PodScheduled != True`), and releases more as the backlog drains.
- Accompanying metrics (current in-flight count, workloads held, time held) so operators can see the throttle working.

Open questions I'd like maintainer input on:
  - Unit: pods vs. workloads (pods preferred for this use case; workloads simpler).
  - Scope: per-ClusterQueue, per-cohort, and/or global.
  - How it composes with quota, preemption, FairSharing, `waitForPodsReady`, and TAS.
  - Is this better as a core primitive, or does the project prefer it stay an out-of-tree AdmissionCheck? That's the key thing to settle before any KEP.

  **Why is this needed**:

  Kueue admits based on quota (nominal + borrowable), not physical schedulability. When a ClusterQueue's quota is large, a batch ungates hundreds–thousands of pods at once. In front of a throughput-limited scheduler this is a self-inflicted flood: the pods all arrive simultaneously, can't be placed fast enough, sit admitted-but-unschedulable, and the scheduler spins.

Motivating environment: a single, throughput-limited scheduler sustaining roughly ~3–5 pod binds/sec, far below the rate at which Kueue can ungate work. We want admission rate to track bind rate — "never dump more into the scheduler than it can drain" — while still letting many pods eventually run.

Existing mechanisms don't cover rate / in-flight pacing:

  - Quota caps total concurrency (pending + running), not ingress rate. Lowering quota to N throttles steady-state throughput to N, which is not what we want.
  - `waitForPodsReady` + `blockAdmission` serializes to ~one Workload at a time cluster-wide, releases a Workload's entire pod set at once (no pod cap — a single large job, e.g. one with hundreds of pods, still floods), and causes cluster-wide head-of-line blocking if a workload never becomes Ready.
  - `SchedulerLongRequeueInterval` (#9799) paces re-evaluation of inadmissible workloads, not admission volume.
  - ProvisioningRequest AdmissionCheck requires a Cluster Autoscaler / ProvisioningRequest handler and assumes kube-scheduler capacity semantics — unusable for a custom scheduler or a cluster with no autoscaler (the check stays Pending forever and wedges the queue). scheduler or a cluster with no autoscaler (the check stays Pending forever and wedges the queue).

Current workaround: a custom AdmissionCheck controller acting as a pod semaphore (hold workloads in `Pending`, flip `Pending → Ready` only while in-flight pods stay under N). This works, but every operator reinvents it, correct in-flight accounting is subtle, and there are no shared metrics or consistent interaction with quota/preemption — which is why a core primitive would help.

There is adjacent appetite for this class of control: scheduler-pressure tuning via`SchedulerLongRequeueInterval` (#9799), preemption rate-limiting in the KEP-13396 `FUTURE_WORK.md`, and external admission hooks via `AdmissionGatedBy` (KEP-6915). This proposes the admission-side counterpart.

### Comment by [@sohankunkerkar](https://github.com/sohankunkerkar) — 2026-10-11T19:47:21Z

I think this belongs in core: before admitting, Kueue counts the pods of admitted Workloads that aren't fully scheduled yet, and skips the Workload for that cycle if the count would go over the limit (always admitting when the count is 0, so a Workload larger than the limit isn't starved).
[KEP-13502](https://github.com/kubernetes-sigs/kueue/tree/main/keps/13502-unscheduled-pods-timeout) already tracks which admitted Workloads have unscheduled pods, so this can build on it, but today it runs only behind an Alpha gate with `unscheduledTimeout` set. I wouldn't extend [`blockAdmission`](https://github.com/kubernetes-sigs/kueue/tree/main/keps/349-all-or-nothing), because it waits and stops the whole scheduler.
Also, [#14089](https://github.com/kubernetes-sigs/kueue/pull/14089) removed `SchedulerLongRequeueInterval`, so it doesn't apply here.

### Comment by [@kaushik229](https://github.com/kaushik229) — 2026-10-19T22:33:44Z

Thanks @sohankunkerkar, that's a fair ask! I think the specific numbers from one setup matter less than the ratio that drives this: how fast Kueue releases Pods versus how fast they can actually be bound. Whenever the scheduler is slow, binding only a single-digit number of Pods per second, a single Job can still release its entire parallelism at once. That can be thousands of Pods, and on its own it becomes the whole backlog.

On `AdmissionGatedBy`: a gate plus a small controller would work much like the AdmissionCheck-based workaround described in the issue, and for many small Workloads that's probably enough. But it means running and owning another controller in production just for this: deploying, upgrading and keeping it highly available, granting it cluster-wide Pod watch RBAC, and keeping its accounting in sync with Kueue's across versions. Every operator with this problem ends up rebuilding the same thing. It also leaves three gaps, which are the real motivation:

1. **A single large Workload.** The gate is per Workload, so a Job with parallelism in the thousands (e.g., 10,000 Pods) is released all at once. No Workload-level cap can pace that, in-tree or out-of-tree. For Workloads that don't need gang semantics, pacing needs to happen at Pod level after admission, releasing Pods as the backlog drains, similar to how TAS releases Pods through per-Pod scheduling gates.
2. **Capacity that arrives slowly.** With an autoscaler and constrained capacity (e.g., spot instances in a region or account), the effective bind rate is the node arrival rate, which can be minutes rather than seconds. Thousands of unschedulable Pods keep the scheduler and autoscaler busy the whole time. Timeout-based eviction (`unscheduledTimeout`) makes this worse, not better: it evicts and requeues the whole Job, which then floods again when it's re-admitted.
3. **Isolation between tenants.** In a multi-tenant cluster, one ClusterQueue shouldn't be able to slow down the others. Today, whichever ClusterQueue releases the most Pods at once, whether from one large Job or many smaller ones, fills the shared scheduler, and other ClusterQueues wait longer for their Pods to be scheduled even though they're well within their own quota. Quota and FairSharing act at admission, so they don't prevent this, and a single global limit wouldn't either, since one ClusterQueue could still use most of it.

So I'd frame the KEP around Pod-level pacing for non-gang Workloads, decoupled from eviction, with the Workload-level cap as the fallback for gangs. I'd start with a single global limit, since the bottleneck is one scheduler, and extend it to ClusterQueue and Cohort level later, which is where the fairness concern above gets fully addressed. Does that seem like a reasonable scope to you?
