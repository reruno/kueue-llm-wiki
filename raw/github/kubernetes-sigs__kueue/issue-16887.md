## Description

**What happened**:

A MultiKueue manager leaves a Workload stuck at the `multikueue` AdmissionCheck in state `Pending` (no `status.clusterName`, no remote Workload created) when the Workload is reconciled during the short window in which its only worker cluster is marked disconnected because its watches are being re-established. The Workload is never retried on its own; it stays `Pending` until some unrelated update event (for example `kubectl annotate workload ...`) triggers another reconcile, after which it dispatches normally.

Timeline from the manager logs (v0.20.0, `--zap-log-level=2`), single-cluster MultiKueueConfig, dispatcher `AllAtOnce`:

```
01:24:44.994  scheduler: Workload successfully admitted and assigned flavors   (QuotaReserved)
01:24:45.012  multikueuecluster.go:511 Watch ended            clusterName=worker-b   (all 7 watch kinds end, watch stream idle timeout)
01:24:45.012  multikueuecluster.go:514 Queue reconcile for reconnect  cluster=worker-b
01:24:45.055  multikueue/workload.go:930 Failed to patch nominated clusters  op=nominateAndSynchronizeWorkers  error="Operation cannot be fulfilled ... the object has been modified"
01:24:45.055  controller.go:497 Reconciler error  (requeued)
01:24:45.055  multikueue/workload.go:189 Reconcile Workload     <- runs while worker-b is still disconnected; no further log line, no error, no requeue
01:24:45.211  multikueuecluster.go:509 Starting watch          clusterName=worker-b   (x7, cluster connected again)
...                                                              nothing touches the Workload
01:25:58.087  multikueue/workload.go:189 Reconcile Workload     <- triggered by a manual annotation; remote Workload created, admitted, job runs
```

Reading `pkg/controller/admissionchecks/multikueue/workload.go` at v0.20.0:

- `remoteClientsForAC` only returns clients whose `connState.isConnected()` is true, so during a reconnect (`markDisconnected` on the first `Watch ended`, `markConnected` only after every watch is re-established) the worker lands in `group.unavailableClusters` and `group.remotes` is empty.
- In `nominateAndSynchronizeWorkers`, the `AllAtOnce` branch builds `nominatedWorkers` from `group.remotes`, so it nominates an empty list, creates nothing, and returns `reconcile.Result{}` with `errors.Join(nil)`: no error and no `RequeueAfter`.
- The `RequeueAfter: workerLostTimeout` handling for `unavailableClusters` exists on the cleanup path and on the already-admitted path, but not on this first-dispatch path.
- Nothing re-enqueues pending Workloads when the cluster reconnects: `queueWatchEndedEvent` only reconciles the `MultiKueueCluster`, and `queueEventsForCQ` is gated behind `MultiKueueManagerQuotaAutomation`.

The window is short (0.2 to 1.9 s per reconnect in our setup, depending on round trip to the worker), but every watch stream end opens it. Watch streams end periodically on most clouds (load balancer idle timeouts), so any manager with a MultiKueueConfig that lists a single cluster can hit this. We saw it on the first day of use.

**What you expected to happen**:

When the Workload's admission check has pending clusters that are currently unavailable and nothing was dispatched, the reconciler should return a short `RequeueAfter` (or the reconnect should re-enqueue pending Workloads for that cluster) so dispatch happens as soon as the worker is connected again.

**How to reproduce it (as minimally and precisely as possible)**:

1. Manager with one MultiKueueCluster and a MultiKueueConfig listing only that cluster, default dispatcher.
2. Make the worker's watch streams end periodically (any L4/L7 proxy with an idle read timeout in front of the worker API works; we used nginx with `proxy_read_timeout 180s`, so every kind-watch ends and is re-established every 3 minutes).
3. Submit Jobs continuously to a LocalQueue backed by that MultiKueueConfig. Any Job whose Workload gets `QuotaReserved` while the worker is between `Watch ended` and the last `Starting watch` stays at `multikueue` check `Pending` with `status.nominatedClusterNames` empty and no remote Workload.
4. `kubectl annotate workload <name> x=y --overwrite` on the manager immediately dispatches it.

**Anything else we need to know?**:

The conflict error just before the stuck reconcile (`Failed to patch nominated clusters`) is incidental: it causes the controller-runtime requeue that lands inside the disconnected window. Any reconcile inside the window has the same outcome.

**Environment**:
- Kubernetes version (use `kubectl version`): manager v1.35 (EKS), worker v1.37
- Kueue version (use `git describe --tags --dirty --always`): v0.20.0 (manager and worker, Helm chart 0.20.0)
- Cloud provider or hardware configuration: manager on AWS EKS, worker on a non-AWS managed Kubernetes reached over the public internet through a reverse proxy
- OS (e.g: `cat /etc/os-release`): n/a
- Kernel (e.g. `uname -a`): n/a
