## Description

**What would you like to be added**:

[KEP-15423](https://github.com/kubernetes-sigs/kueue/blob/main/keps/15423-wait-for-pods-ready-max-not-ready/README.md) introduced `kueue.x-k8s.io/pod-group-max-not-ready-count`, which allows a Pod group to remain `PodsReady=True` within its configured not-ready budget, preventing eviction through `waitForPodsReady.recoveryTimeout`. With `TASFailedNodeReplacementFailFast` disabled, failed-node replacement continues retrying until it succeeds or until that recovery timeout. Given that `TASFailedNodeReplacementFailFast` provides an earlier eviction path for the same replacement process, it seems reasonable for it to also take the workload’s configured readiness tolerance into account.

Essentially, what I want to be able to tell Kueue is that hey, it's okay if we're still within our not ready budget, we can wait indefinitely for a replacement. But once we go above that, we do still want the fail-fast behavior as it is today.

Right now, Kueue will fail fast when a replacement cannot be found, even though maybe say my training job is able to tolerate this and keep making progress.

https://github.com/kubernetes-sigs/kueue/blob/f7b3f8c28c0688e419448eb01383753de0371b6a/pkg/scheduler/scheduler.go#L601-L605

https://github.com/kubernetes-sigs/kueue/blob/ee183e84e7bb8a524027123ec9ee71e0bb0dbaa9/pkg/workload/workload.go#L1589-L1604

**Why is this needed**:

Consider an 18 pod training workload running on GB200/GB300s, placed within one NVL72 clique/rack, with one pod per node. The job needs 16 pods for training and uses two as standbys (it is common to reserve two spare nodes per rack to tolerate node/GPU failures). So each pod has:

```
metadata:
  annotations:
    kueue.x-k8s.io/pod-group-total-count: "18"
    kueue.x-k8s.io/pod-group-max-not-ready-count: "2"
```

Since the workload already occupies all 18 nodes in the clique, losing one leaves no capacity for a replacement until that node recovers. `TASFailedNodeReplacementFailFast` can therefore evict the entire workload, even though the remaining 17 ready pods are sufficient to continue training.

Disabling fail-fast globally avoids this eviction, but also disables it for workloads that genuinely cannot make progress.

An alternative we considered is setting `pod-group-total-count: "16"`, leaving two nodes initially available for replacement. However, this means (1) paying the pod startup cost during recovery, and (2) leaving those nodes available to other 1-2 node workloads (which technically is good for overall cluster utilization, but we may not always want), since our job’s admission only reserves capacity for 16 pods. If other jobs consume that capacity, we can encounter the same replacement failure.

**Completion requirements**:

- Keep the workload admitted and continue replacement attempts while it satisfies its configured readiness requirement.
- Preserve existing fail-fast behavior when that requirement is no longer satisfied and a replacement cannot be found.
- Add tests covering both cases and transitions between them.
- Document the interaction between `TASFailedNodeReplacementFailFast` and `WaitForPodsReadyMaxNotReady`.

This enhancement requires the following artifacts:

- [x] Design doc
- [ ] API change
- [x] Docs update

Happy to start by drafting a change to [KEP-15423](https://github.com/kubernetes-sigs/kueue/blob/main/keps/15423-wait-for-pods-ready-max-not-ready/README.md) and/or [KEP-2724](https://github.com/kubernetes-sigs/kueue/tree/main/keps/2724-topology-aware-scheduling) if this makes sense!

**Out of scope**:

For multi-clique workloads, the budget may need to apply per clique. For example, with 36 pods across two 18-node cliques, training may require at least 16 ready pods **per clique**. A global `max-not-ready-count: "4"` would allow both `16 + 16` and `14 + 18`, but only the first works. This would require a per-clique budget, which likely needs a new API.
