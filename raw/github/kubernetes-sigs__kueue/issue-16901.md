## Description

### What happened:

**Background — #12980 (fixes #12735)**

#12980 introduced `SkipReassignmentForPodOwnedWorkloads` (Alpha in v0.17/v0.18, **Beta / on by default since v0.19**). When a Workload that is `OwnedBySinglePod` is evicted by preemption or node failure, the reconciler sets `Requeued=False` instead of `True`, so the Workload is not re-assigned to a new placement that the (already running) Pod can never consume:

https://github.com/kubernetes-sigs/kueue/blob/v0.19.2/pkg/controller/jobframework/reconciler.go#L590-L597

```go
setRequeued := (evCond.Reason == kueue.WorkloadEvictedByPreemption) || (evCond.Reason == kueue.WorkloadEvictedDueToNodeFailures)
// A pod-owned Workload dies with its pod; requeuing it would
// recompute an assignment nothing can consume (placement drift).
if features.Enabled(features.SkipReassignmentForPodOwnedWorkloads) && workload.OwnedBySinglePod(wl) {
    setRequeued = false
}
```

The documented recovery path is: the Workload is parked, it finishes together with its Pod, and the owning controller's (e.g. ReplicaSet's) replacement Pod arrives as a brand-new Workload. That is correct for the scenario in #12735 (a Pod that was already running and is being terminated with a long grace period).

**The problem — the recovery path assumes the Pod is deleted, but gated Pods are never deleted**

`Pod.Stop()` skips Pods that are "suspended", and for the Pod integration "suspended" includes "still has the Kueue admission scheduling gate":

- https://github.com/kubernetes-sigs/kueue/blob/v0.19.2/pkg/controller/jobs/pod/pod_controller.go#L234-L236
  ```go
  func podSuspended(p *corev1.Pod) bool {
      return utilpod.IsTerminated(p) || isGated(p)
  }
  ```
- https://github.com/kubernetes-sigs/kueue/blob/v0.19.2/pkg/controller/jobs/pod/pod_controller.go#L523-L527 (Stop skips `podSuspended` pods)

So if a pod-owned Workload is preempted **after it got QuotaReserved but before it was Admitted** (i.e. the Pod is still gated, typically because an AdmissionCheck is still pending), we get a deadlock:

1. Workload gets `QuotaReserved=True`; an AdmissionCheck (e.g. ProvisioningRequest) is still `Pending`, so the Workload is not `Admitted` and the Pod keeps its scheduling gate.
2. A higher-priority / reclaiming Workload preempts it (`EvictedByPreemption`, e.g. `InCohortReclamation`).
3. `Stop()` skips the Pod because it is gated → **the Pod is not deleted**.
4. The reconciler sets `Requeued=False` because of `SkipReassignmentForPodOwnedWorkloads`.
5. The queue manager never retries it: `backoffWaitingTimeExpired` returns `false` while `Requeued=False`
   https://github.com/kubernetes-sigs/kueue/blob/v0.19.2/pkg/cache/queue/cluster_queue.go#L492-L495
6. Nothing flips `Requeued` back to `True` for this case — the workload controller only does that for the Deactivated / PodsReadyTimeout / AdmissionCheck eviction reasons (`pkg/controller/core/workload_controller.go`, ~L642-L660 in v0.19.2).
7. The Pod never runs and is never deleted, so the ReplicaSet never creates a replacement. The Deployment is stuck at 0 available replicas **forever**.

Additionally, the visibility API (`pendingworkloads`) still lists the Workload as pending (we saw it at position 0), which is misleading because it will never be considered.

**Why this is common in our setup**

- TAS + ProvisioningRequest AdmissionCheck (`best-effort-atomic-scale-up`), as recommended in the TAS docs for autoscaled node pools. Topology assignment is delayed until the AC is Ready (`DelayedTopologyRequest=Pending`, `pkg/cache/scheduler/tas_flavorassigner.go` ~L103-L108), so the window "QuotaReserved but still gated" lasts as long as node provisioning (minutes).
- Several ClusterQueues are borrow-only (nominal quota 0) inside a cohort; the quota-owning ClusterQueues use `reclaimWithinCohort: Any`, and their nominal quota is changed on a schedule (peak / off-peak). When nominal is raised, borrowers are reclaimed.
- The preemption candidate ordering prefers the most recently reserved Workloads (by QuotaReserved time), i.e. exactly the ones that are most likely still gated.

Observed: 9 Deployment-owned Pods were preempted between 8 seconds and ~12 minutes after creation, all while still gated; all stayed stuck with `Requeued=False`, one of them for more than 5 days, until the Pods were deleted manually.

Example Workload status (sanitized):

```yaml
conditions:
- type: QuotaReserved
  status: "False"
  reason: Pending
  message: 'Preempted to accommodate a workload (UID: ..., JobUID: ...) ...'
- type: Evicted
  status: "True"
  reason: Preempted
  message: 'Preempted to accommodate a workload (UID: ..., JobUID: ...) ...'
- type: Preempted
  status: "True"
  reason: InCohortReclamation
- type: Requeued
  status: "False"
  reason: Preempted
- type: PodsReady
  status: "False"
  reason: WaitForStart
```

(At the time of preemption the ProvisioningRequest AdmissionCheck was still `Pending`; after eviction the Workload's `admissionChecks` list is empty.)

The Pod still has the `kueue.x-k8s.io/admission` scheduling gate and is `Pending`.

### What you expected to happen:

A Workload whose Pod has never started (still has the Kueue admission gate) should not be parked. There is no "placement drift" risk because nothing has been placed yet, so it should be requeued (`Requeued=True`) as before #12980 — or, alternatively, the Pod should be deleted so that the owner controller's replacement takes over, as the docs describe.

### How to reproduce it (as minimally and precisely as possible):

Kueue v0.19.x with default feature gates (`SkipReassignmentForPodOwnedWorkloads` on), Pod integration enabled (e.g. via the `deployment` integration).

1. Create a cohort with two ClusterQueues sharing one ResourceFlavor:
   - `cq-borrower`: `nominalQuota: 0`, `borrowingLimit` unset, with an AdmissionCheck that stays `Pending` for a while (a ProvisioningRequest AC, or any custom AC controller that you keep `Pending`).
   - `cq-owner`: `nominalQuota: N`, `preemption.reclaimWithinCohort: Any`.
2. Create a 1-replica Deployment in a namespace whose LocalQueue points at `cq-borrower`, requesting ≤ N.
   → Workload gets `QuotaReserved=True` (borrowing), AC `Pending`, Pod is gated.
3. Before the AC becomes `Ready`, submit a Workload to `cq-owner` that needs the quota.
   → The borrower Workload is preempted (`InCohortReclamation`).
4. Observe:
   - Borrower Workload: `Evicted=True`, `Requeued=False`, `QuotaReserved=False`.
   - The Pod is still gated and is **not** deleted.
   - After the `cq-owner` Workload finishes and quota is free again, the borrower Workload is **never** re-admitted, and the ReplicaSet never creates a new Pod.

Deleting the Pod manually recovers it (the orphaned Workload is finalized and the ReplicaSet creates a new Pod / Workload).

### Anything else we need to know?:

**Test gap.** The existing feature-gate-on test in `pod_controller_test.go` admits (ungates) the Workload before evicting it, and only asserts that `Requeued` stays `False`. The "evicted while still gated" path is not covered.

**Suggested fix.** In the reconciler, only park when the job has actually started, e.g.:

```go
if features.Enabled(features.SkipReassignmentForPodOwnedWorkloads) &&
    workload.OwnedBySinglePod(wl) && !jobNeverStarted(job) {
    setRequeued = false
}
```

where, for the Pod integration, "never started" means "still has the Kueue admission scheduling gate" (`isGated`).

Notes on this choice:
- We intentionally do **not** suggest `job.IsSuspended()`: for Pods it is `IsTerminated || isGated`, and with `FastQuotaReleaseInPodIntegration` the eviction branch can run after the Pod is no longer running, which would re-enable exactly the requeue that #12980 prevents.
- If the admission gate was already removed but the TAS topology gate is still present, `Stop()` does delete the Pod (it is not `isGated`), so parking is fine in that case and the documented recovery works.

**Alternative fix.** When parking a single-Pod Workload, have `Stop()` delete the Pod even if it is gated, so the owner controller recreates it. Downside: bare Pods (no owner controller) would be lost, so we prefer the reconciler-side fix above.

**Requests.**
- An integration test for "preempted while QuotaReserved but not yet Admitted (Pod still gated)".
- A cherry-pick to `release-0.19` (and later), since this is a regression introduced when the gate became on by default in v0.19.

**Workarounds** (for others hitting this):
- Delete the stuck gated Pod manually (or with a periodic job that finds Workloads with `Evicted=True`, `Requeued=False`, `OwnedBySinglePod`, Pod still gated).
- Disable the feature gate: `featureGates: {SkipReassignmentForPodOwnedWorkloads: false}` in the Kueue Configuration (this gives up the #12735 protection).
- Use a workload type that is not `OwnedBySinglePod` (e.g. LeaderWorkerSet / StatefulSet) instead of a Deployment.
