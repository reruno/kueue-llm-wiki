### Comment by [@yuluo-yx](https://github.com/yuluo-yx) — 2026-10-08T08:45:06Z

my thinks:

1. **Prebuild CI tools into a versioned base image.** I previously used this approach in VSR: we packaged the tools required by CI into a base image, and the pipelines used it instead of installing tools on every run. A similar approach could reduce tool setup time here.

   reference: https://github.com/vllm-project/semantic-router/pkgs/container/semantic-router%2Fprecommit

2. **Run checks selectively based on changed files and module dependencies.** Apache Shenyu uses a script to resolve which modules need CI checks. We would need a conservative fallback to full verification for changes affecting shared APIs, dependencies, generators, or CI configuration.

   reference: https://github.com/apache/shenyu/blob/master/.github/scripts/resolve-ci-modules.sh

3. **Reuse Go module, build, and golangci-lint caches across runs.** VSR uses GitHub Actions caching. Since Kueue uses Prow, i don`t known prow cache impl. If we are going to use it, we need to explore it in advance.

   references: 
      https://github.com/vllm-project/semantic-router/actions/caches  
      https://github.com/actions/cache

I would start with the prebuilt tool image and cache reuse, since these can reduce repeated work while preserving the existing verification coverage. 👀

Within `verify-artifacts`, the four-platform CLI build/package command accounts for **8m 46s / 11m 44s**. Within runner verification, the race-test command accounts for **8m 42s / 11m 51s**, whereas actual test execution reported by gotestsum takes only **~1.9s / ~2.1s**.

The initial window also contains substantial overlapping work: golangci-lint installation takes **68s / 97s**, Helm installation **79s / 114s**, genref installation **79s / 112s**, API reference generation **77s / 104s**, and building the CLI documentation generator **83s / 114s**. These times are not additive either.

**Overlap and contribution to completion time:** full-module lint, four-platform CLI builds, and runner race tests run simultaneously for **8m 11s / 11m 16s**. Runner verification finishes last in both builds. In the typical run, lint finishes 31s before completion and CLI builds finish 20s before completion. Accelerating only the runner would therefore save at most about 20s if the other timings remained unchanged.

**Timing limitations:** the logs report recipe-command durations, not complete per-target traces. Successful commands below the default one-second reporting threshold may be omitted. There are no individual timings for each CLI platform, each lint module, or compilation versus linking versus test execution. Some short generation/update commands and the final Git diff/untracked-file checks also lack individual records. Estimates are marked above; missing records should not be interpreted as zero runtime. These two builds use different commits, so this is a descriptive comparison, not a controlled benchmark.

### Comment by [@yuluo-yx](https://github.com/yuluo-yx) — 2026-10-08T11:01:01Z

Judging from the aggregated results, the following three should yield the greatest gains:

1. Reusing GOCACHE;
2. Merging runner tests into the existing race unit job to reuse precompiled race dependencies, reducing redundant compilation in verify while freeing up resources;
3. Running the cross-platform CLI build independently to reduce resource contention between the four compilation sets and lint/race tests within verify, while retaining cross-platform verification;

- Follow-up adjustments include adapting to prow resource concurrency;
- Packaging and building a base image to reduce tool installation time.
