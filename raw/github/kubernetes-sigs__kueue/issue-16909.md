## Description

**What happened**:

A workload admitted on worker `dc-a` lost its manager→worker connection. After `workerLostTimeout` the manager evicted and requeued it; it was dispatched to worker `dc-b` and admitted there (`status.clusterName: dc-b`). Meanwhile the copy on `dc-a` kept running, since the manager could not reach it. When the connection came back, MultiKueue deleted the **new** copy on `dc-b` about one second after reconnecting, and kept the **stale** copy on `dc-a`:

- the manager workload kept `status.clusterName: dc-b`, which no longer runs anything
- the stale copy on `dc-a` kept running; we watched for 5 minutes and it was not removed
- the manager then tried to sync the `dc-a` Job's status into the manager Job and failed repeatedly for ~6 minutes, because `status.startTime` cannot change on a Job that is not suspended

Evicting the manager workload once more (setting our admission check to `Retry`) removed the stale copy within ~6 s; after re-dispatching to `dc-b`, one copy ran and the errors stopped.

Seen twice, with the same outcome both times.

**What you expected to happen**:

After the worker reconnects, the remote copy that does not match the manager workload's current placement (the stale one on `dc-a`) is removed, and the copy on `status.clusterName` (`dc-b`) is kept. Or, at least, the manager's record stays consistent with what runs (no remote copy left running that the manager does not account for).

**How to reproduce it (as minimally and precisely as possible)**:

1. A manager cluster and two workers (`dc-a`, `dc-b`), `batch/job` integration, `multiKueue.workerLostTimeout: 2m`, `gcInterval: 30s`. We used an external dispatcher (`multiKueue.dispatcherName` set to our controller, which writes `status.nominatedClusterNames`, with the `clear-nominated-cluster-names` MutatingAdmissionPolicy from the release) and our own AdmissionCheck on the MultiKueue ClusterQueue as the go signal.
2. Submit a Job (`spec.managedBy: kueue.x-k8s.io/multikueue`), dispatch it to `dc-a`, and wait until it runs there.
3. Block the manager's route to `dc-a`'s API server only (iptables on the manager node; `dc-a` itself keeps working).
4. MultiKueue marks `dc-a` inactive (`ClientConnectionFailed`) after ~76–83 s; the manager workload is evicted (`Evicted: True(AdmissionCheck)`) and requeued after ~166–174 s. The `dc-a` copy is still running.
5. Dispatch to `dc-b`; it is admitted and runs there. Two copies now run.
6. Restore the route. MultiKueue reconnects to `dc-a` after ~43–45 s.
7. Observe: ~1 s after reconnecting, the `dc-b` copy is deleted; the `dc-a` copy stays; `status.clusterName` stays `dc-b`; the status sync error repeats.

**Anything else we need to know?**:

Reading the code (v0.20.0, and unchanged on `main` as of today), we think this is the cause:

- [`bestMatchByCondition`](https://github.com/kubernetes-sigs/kueue/blob/v0.20.0/pkg/controller/admissionchecks/multikueue/workload.go#L141-L156) picks, among the remote copies with `Admitted=True`, the one whose condition has the **oldest** `lastTransitionTime`.
- In `reconcileGroup` step [6b](https://github.com/kubernetes-sigs/kueue/blob/v0.20.0/pkg/controller/admissionchecks/multikueue/workload.go#L582-L593), all other remotes are deleted. Nothing compares the chosen remote with the manager workload's `status.clusterName`.
- After the reconnect, both remotes are admitted, and the stale copy on `dc-a` was admitted earlier. So it wins, and the current copy on `dc-b` is deleted.
- The [per-cluster GC](https://github.com/kubernetes-sigs/kueue/blob/v0.20.0/pkg/controller/admissionchecks/multikueue/multikueuecluster.go#L739-L797) only removes remote workloads whose manager workload is gone, so it does not remove the stale copy either.

A possible fix: when the manager workload has `status.clusterName` set and that remote is admitted, converge onto it and treat admitted copies on other clusters as stale. We have not written or tested a patch. We're glad to try one if this direction is right.

Related: #16172 (no resync after a watch reconnect). There the state heals and nothing runs twice; here the wrong copy is deleted and the record stays wrong.

What avoids it for us, also tested on the same setup:

- Remove the unreachable worker from the MultiKueueConfig's `spec.clusters`. The workload admitted there is requeued at once ("Admitting remote no longer exists", step 6a), without waiting for `workerLostTimeout`.
- While the worker is out of the config, its reconnecting does not touch the new copy elsewhere. The stale copy keeps running there, and the GC does not remove it.
- Deleting the stale copy (its Job, its pod and its Workload) before adding the worker back kept a single copy, the current one.
