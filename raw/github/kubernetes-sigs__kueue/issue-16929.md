## Description

_Credits to CodeRabbit for flagging this in review of #16904. Then I noticed we have this already._

**What happened**:

Kueue has at least 3 sanitizers of compound object names which may produce strings containing a `.-` substring (which is incorrect per the standard Kubernetes object naming rules):

- [`GenerateWorkloadNameWithExtra`](https://github.com/kubernetes-sigs/kueue/blob/90e8f5849eb33c75e5b7d5d4d7bc213396eab4e8/pkg/controller/jobframework/workload_names.go#L85)
- [`limitObjectNameWithReservedSuffix`](https://github.com/kubernetes-sigs/kueue/blob/90e8f5849eb33c75e5b7d5d4d7bc213396eab4e8/pkg/controller/admissionchecks/provisioning/controller.go#L1006) - used for naming ProvisioningRequests
- [`virtualPodName`](https://github.com/kubernetes-sigs/kueue/blob/90e8f5849eb33c75e5b7d5d4d7bc213396eab4e8/pkg/cache/scheduler/was/virtual_pods.go#L46)

In the first two cases, a resulting name with `.-` would be then rejected by the API server validation (HTTP 422 `Unprocessable Entity`).

In the third case (as well as in the incoming case in [#16904](https://github.com/kubernetes-sigs/kueue/pull/16904)), the problem is probably not-really-existing, as "virtual Pods" are purely in-memory objects never intended to reach etcd. 
Still, it feels a bit healthier to use valid names also in this case.

**What you expected to happen**:

1. When taking a name prefix, we should strip any trailing `.` and `-` chars, and only then add `-$suffix`.

2. By the way, I think the variety of our name sanitizers deserves a cleanup - commonizing the code.

   * Thinking naively, we could just have `shortenName(compoundName)`, computing the hash of everything, then taking `$prefix-$hash`.
   * This is, however, not sufficient for Kueue code; we need 2 additional mechanisms:
     - Keeping some info (think: slice index) visible at the end (used [for ProvisioningRequests](https://github.com/kubernetes-sigs/kueue/blob/90e8f5849eb33c75e5b7d5d4d7bc213396eab4e8/pkg/controller/admissionchecks/provisioning/provisioning.go#L57) for managing retries; also [for virtual Pods](https://github.com/kubernetes-sigs/kueue/blob/90e8f5849eb33c75e5b7d5d4d7bc213396eab4e8/pkg/cache/scheduler/was/virtual_pods.go#L49) for better visibility)
     - seeding into the hash some data which shall be omitted in the "human-displayed" object name (this is the "extra" [for Workloads](https://github.com/kubernetes-sigs/kueue/blob/90e8f5849eb33c75e5b7d5d4d7bc213396eab4e8/pkg/controller/jobframework/workload_names.go#L85))
   * Still, it seems like a single, unified helper taking args `fullName, maxLen, finalIndex, extras` would do. \
     (Here `extras` could be a `[]string`, or even a `string` into which multiple extras are pre-concatenated)

### Comment by [@olekzabl](https://github.com/olekzabl) — 2026-10-08T13:16:58Z

BTW [this CodeRabbit finding](https://github.com/kubernetes-sigs/kueue/pull/16904#discussion_r4217935043) is also quite convincing to me.

Short story in my words: Consider a large cluster with 100k Pods. Of course, they typically differ by prefix, so suppose we have 10k distinct prefixes and `prefix-0`, `prefix-1`, ..., `prefix-9` for each of them. And prefixes are so long that we need sanitizing.

Then, if we use 5-char hex hashes (i.e. 20 bits), the chance for a hash collision for _a single prefix_ is
```
1 - 2^20 * (2^20-1) * ... * (2^20-9) / 2^200 ~= 0.0042915%
```
Then, however, the chance for at least one collision _anywhere_ (i.e. within _some_ prefix group) is
```
1 - (1 - 0.0042915%)^10k ~= 34.894%
```

Using 8 chars instead brings this down to ~0.01%.

Another option is to use base-36 instead of hex; then we get 0.74% for 5 chars, 0.02% for 6 chars.
