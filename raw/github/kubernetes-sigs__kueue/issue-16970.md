## Description

**What happened**:

`ParseAnnotation` in `pkg/util/waitforpodsready/waitforpodsready.go` converts
`timeoutSeconds` and `recoveryTimeoutSeconds` from the
`kueue.x-k8s.io/wait-for-pods-ready` annotation with a bare multiplication
and no overflow check:

    Timeout: time.Duration(raw.TimeoutSeconds) * time.Second

A value such as `36028797018963969` (2^55+1) wraps around to exactly `1s`.
That value is positive and below `maxTimeoutOnWorkload` (2h by default), so
the webhook accepts it, and the workload gets a 1-second timeout instead of
the enormous one the user wrote. Other values wrap to a negative duration
(`9223372036854775807` becomes `-1s`) and are rejected with the misleading
message "timeoutSeconds must be greater than 0".

**What you expected to happen**:

Oversized values should saturate at the maximum `time.Duration` instead of
wrapping, so the existing `maxTimeoutOnWorkload` check rejects them with
"timeoutSeconds must be less than or equal to N seconds" rather than
accepting them as a tiny duration.

**How to reproduce it (as minimally and precisely as possible)**:

Annotate a Job (with the `WorkloadLevelWaitForPodsReady` feature gate enabled) with:

    kueue.x-k8s.io/wait-for-pods-ready: '{"timeoutSeconds": 36028797018963969}'

The same applies to `recoveryTimeoutSeconds`. At the unit level, a
`TestParseAnnotation` case with `{"timeoutSeconds":36028797018963969}` returns
a `1s` timeout on unfixed code.

**Anything else we need to know?**:

No existing test used a value large enough to trigger the wraparound.
I reproduced this with unit tests of `ParseAnnotation` and of
`ValidateJobOnCreate`; I did not reproduce it on a live cluster.

I have a fix ready that saturates the conversion using the existing
`SaturatingMul` helper from `pkg/util/math`.
