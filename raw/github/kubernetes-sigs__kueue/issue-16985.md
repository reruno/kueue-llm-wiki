## Description

### What happened?

Kueue releases all ClusterQueue quota when a managed RayJob's `JobDeploymentStatus` becomes `Complete` or `Failed`.

KubeRay can keep the RayCluster and all of its head and worker Pods running after that transition when `shutdownAfterJobFinishes: true` is combined with a nonzero `ttlSecondsAfterFinished`.

During that retention window, Kueue can admit another Workload using quota that is still physically occupied by the retained Ray Pods.

This behavior was initially discussed in #3994, but that issue was closed as not planned. The gap remains reproducible with Kueue v0.19.6 and KubeRay v1.7.0.

### Reproduction

Create a ClusterQueue with 500m CPU quota.

Submit a fixed-size RayJob requesting:

- head: 100m
- two workers: 100m each
- aggregate: 300m

Configure:

```yaml
shutdownAfterJobFinishes: true
ttlSecondsAfterFinished: 7200
```

After the RayJob reaches `SUCCEEDED`:

- its Workload has `Finished=True`;
- ClusterQueue CPU usage becomes zero;
- the RayCluster remains Ready;
- the head and both worker Pods remain Running and Ready;
- those Pods still request 300m CPU in total.

Submit another 300m Workload to the same ClusterQueue.

Observed:

- the second Workload is admitted;
- 600m of Kueue-admitted Pod requests remain running;
- the ClusterQueue reports only 300m usage against its 500m quota.

Whether the second Workload runs or remains Pending depends on physical node capacity. In either case, ClusterQueue quota has been assigned while the Pods that previously held it are still running.

### Expected behavior

Kueue should continue accounting for the completed RayJob's reservation while its RayCluster and Pods remain active during the configured retention period.

Quota should be released only after KubeRay has completed the full RayCluster cleanup.

### Proposed direction

Separate Ray application completion from Kueue Workload completion:

1. KubeRay may report that the Ray application has completed.
2. Kueue keeps the Workload admitted and retains its quota while the owned RayCluster or its Pods still exist.
3. KubeRay performs cleanup according to `shutdownAfterJobFinishes` and `ttlSecondsAfterFinished`.
4. After cleanup is confirmed, Kueue marks the Workload `Finished` and releases its quota.

This likely requires an explicit cleanup-complete signal or acknowledgment between the KubeRay and Kueue controllers. Ray application success alone is not sufficient because it precedes asynchronous RayCluster deletion.

### Out of scope

This issue covers the case where the full RayCluster, head and workers, is retained during `ttlSecondsAfterFinished`.

It does not cover deletion policies that remove workers while retaining the head Pod. That case may require partial accounting through Dynamic Reclaim and should be designed separately.

### Comment by [@kevin85421](https://github.com/kevin85421) — 2026-11-09T04:38:38Z

Here is the plan I promised. It is a short-term mitigation until KubeRay exposes the status API tracked in kuberay-project/kuberay#5455.

### Scope

RayJobs with `shutdownAfterJobFinishes: true` and `ttlSecondsAfterFinished > 0`, in both single-cluster and MultiKueue setups. #17646 currently covers only the single-cluster case: on the MultiKueue manager there is no RayCluster to check, so the manager Workload still finishes early and the remote RayJob is deleted before the TTL expires. `deletionRules` is out of scope, because KubeRay currently rejects it together with `shutdownAfterJobFinishes: true`. Supporting `deletionRules` for Kueue-managed RayJobs is tracked in #18504.

### Proposal

Keep the change inside the RayJob integration, behind a new alpha feature gate. No job framework changes.

In `RayJob.Finished()`, do not report the job as finished until KubeRay's shutdown deadline has passed:

```go
finished = j.Status.JobDeploymentStatus == rayv1.JobDeploymentStatusFailed ||
	j.Status.JobDeploymentStatus == rayv1.JobDeploymentStatusComplete
if finished && features.Enabled(features.<NewGate>) &&
	j.Spec.ShutdownAfterJobFinishes && j.Spec.TTLSecondsAfterFinished > 0 && j.Status.EndTime != nil {
	shutdownTime := j.Status.EndTime.Add(time.Duration(j.Spec.TTLSecondsAfterFinished) * time.Second)
	if time.Now().Before(shutdownTime.Add(-clockSkewTolerance)) {
		finished = false // the RayCluster is still retained, keep the quota reserved
	}
}
```

- KubeRay deletes the RayCluster at `status.endTime + ttlSecondsAfterFinished`, so Kueue can compute the same deadline from the RayJob alone. `Finished()` has no client, and it does not need one.
- KubeRay does not update the RayJob status when it deletes the cluster. However, the RayJob integration already watches RayClusters owned by RayJobs. The deletion enqueues the RayJob, and at that point `Finished()` returns true.
- `clockSkewTolerance` (for example 30s) covers clock skew between kuberay-operator and kueue-controller-manager. Without it, a Kueue clock that lags behind KubeRay could leave the Workload admitted after the cluster is gone, with no further event to finish it. Releasing quota a few seconds early is in the same range as the Pod termination grace period after cluster deletion.

### MultiKueue

This works without MultiKueue-specific code, as long as the gate is enabled on the worker clusters:

- On the worker, the Workload stays admitted until the deadline, and the RayCluster deletion finishes it.
- On the manager, the RayJob status is copied from the worker. The same check keeps the manager Workload admitted, so MultiKueue does not delete the remote RayJob early. The manager then finishes when the remote Workload reports `Finished`.

This is a behavior change for MultiKueue. Today the manager finishes as soon as the RayJob completes, and MultiKueue deletes the remote RayJob, which cuts `ttlSecondsAfterFinished` short on the worker. With this change, the TTL is honored and both clusters keep the quota until it expires.

Once the KubeRay status API from kuberay-project/kuberay#5455 lands, we can replace the deadline check with it and remove the gate.

### Comment by [@win5923](https://github.com/win5923) — 2026-11-18T02:29:41Z

KubeRay APIs:

```
type RayJobStatus struct {
    // ... existing status

    // PodCounts reports, for each group of Pods of this
    // RayJob, how many Pods are active or terminating.
    // It stays current after Complete or Failed.
    // KubeRay sets this field when the RayJobPodCounts
    // feature gate is enabled.
    // +listType=map
    // +listMapKey=role
    // +listMapKey=name
    // +optional
    PodCounts []RayJobPodCount `json:"podCounts,omitempty"`
}

// +kubebuilder:validation:Enum=Head;Worker;Submitter
type RayJobPodRole string

const (
    RayJobPodRoleHead      RayJobPodRole = "Head"
    RayJobPodRoleWorker    RayJobPodRole = "Worker"
    RayJobPodRoleSubmitter RayJobPodRole = "Submitter"
)

type RayJobPodCount struct {
    // Role is the role of this group of Pods.
    // +required
    Role RayJobPodRole `json:"role"`

    // Name is "head", the groupName of a worker group,
    // or "submitter".
    // +kubebuilder:validation:MinLength=1
    // +required
    Name string `json:"name"`

    // Active is the number of pending and running Pods
    // which are not terminating (without a
    // deletionTimestamp).
    // +kubebuilder:validation:Minimum=0
    // +required
    Active *int32 `json:"active,omitempty"`

    // Terminating is the number of Pods which are
    // terminating (in phase Pending or Running and have
    // a deletionTimestamp).
    // +kubebuilder:validation:Minimum=0
    // +required
    Terminating *int32 `json:"terminating,omitempty"`
}
```

Here is an example below shows the status of a RayJob that has succeeded and is waiting for `ttlSecondsAfterFinished` to expire.
```
status:
  jobDeploymentStatus: Complete
  jobStatus: SUCCEEDED
  podCounts:
  - role: Head
    name: head
    active: 1
    terminating: 0
  - role: Worker
    name: gpu-workers
    active: 4
    terminating: 0
  - role: Submitter
    name: submitter
    active: 0
    terminating: 0
```
