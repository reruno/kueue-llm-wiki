**What happened**:
With fair sharing and default feature gates, workload `p` is within its ClusterQueue's nominal quota on cpu but has to borrow memory. It preempts workload `w1`, which is borrowing `p`'s cpu. As soon as `w1`'s eviction completes, the fair-sharing admission ordering puts `w1` ahead of `p`, so `w1` is admitted again. `p` then preempts `w1` again, and so on.

**What you expected to happen**:

Kueue makes progress. Either of these would be fine:
- `p` is entitled to its nominal cpu, as documented for `FairSharingPreemptWithinNominal`. Then, once `w1`'s eviction completes, `p` is admitted and `w1` stays pending.
- `p` is not entitled, because it also borrows memory. This is the definition the fair-sharing admission ordering uses. Then `p` does not preempt `w1` at all.
Preempting `w1` and then re-admitting it ahead of `p` should not happen.

**How to reproduce it (as minimally and precisely as possible)**:


One Cohort, one ResourceFlavor `default`, fair sharing enabled, default feature gates:
| ClusterQueue | cpu quota | memory quota | Workloads |
|---|---|---|---|
| `cq-p` (`reclaimWithinCohort: Any`) | 4 | 2Gi | `p` (pending): cpu 4, memory 6Gi |
| `cq-w` | 0 | 0 | `w1` (admitted): cpu 4, borrowed from `cq-p` |
| `cq-y` | 20 | 0 | `y1` (admitted): cpu 20  (just to make cpus cheap from the DRS perspective)|
| `cq-l` | 0 | 10Gi | none |

1. `p` preempts `w1` ("reclamation within the cohort"), because `cq-p` is within its nominal cpu.
2. When `w1`'s eviction completes, `w1` is admitted again, ahead of `p`.
3. `p` preempts `w1` again....

[Repro code](https://github.com/pajakd/kueue/blob/ff311089d0988f2ae2e61960ee2dacc2283e2f91/test/integration/singlecluster/scheduler/fairsharing/fair_sharing_test.go#L420-L534) 

The root cause is that preemption and admission define "within nominal" differently:
- **Preemption** (`FairSharingPreemptWithinNominal`, Beta, on by default since v0.17):
  - `queueWithinNominalInResourcesNeedingPreemption` checks only the flavor-resources that need preemption (cpu), and only for the preemptor's ClusterQueue.
  - `cq-p` is within nominal on cpu, so `p` preempts `w1` without the DRS-based fair-sharing check.
  - `FairSharingVerifyFinalTargets` skips within-nominal reclamation, so it doesn't catch this.
- **Admission** (`FairSharingPrioritizeNonBorrowing`, Beta, on by default since v0.17):
  - The fair-sharing tournament checks whether the subtree is borrowing on any of the workload's requested flavor-resources.
  - `p` borrows memory, so it gets no precedence over `w1`. Both count as borrowing, so DRS decides.
  - `w1` borrows 4 of 24 lendable cpu (≈ 0.17); `p` borrows 4Gi of 12Gi lendable memory (≈ 0.33). So `w1` goes first.


**Anything else we need to know?**:
Its not fixed by #16738 (or #16886).

In other words, `p` bypasses the DRS check during preemption because it is within the nominal quota in resources needing preemption. But its not within nominal in the other resource so it does not bypass the DRS during scheduling.

I think the fix should be on the preemption side.
