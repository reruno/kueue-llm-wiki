**What happened**:

Scheduler.admit (pkg/scheduler/scheduler.go) assumes a workload into the scheduler cache synchronously, then patches its admission status in a goroutine. On any error from that patch, the error path rolls back the cache assumption (_ = s.cache.DeleteWorkload(...)) and requeues, implicitly assuming the write did not persist.

But the apiserver can commit the write while the client only observes a timeout/connection reset (e.g. under apiserver overload). The result is a cache↔API divergence: the Workload is QuotaReserved/Admitted in the API while the scheduler cache has forgotten it, so the cache under-counts the ClusterQueue's usage. Compounding this: cache membership for an admitted workload is populated only by edge-triggered event handlers (e.g. the Pending → QuotaReserved transition in workload_controller.go and the create handler); there is no level-triggered step that repairs membership from API state. So once the error path deletes the entry, nothing re-adds it until the workload's next update event — any update re-adds it via the generic update handler, so recovery is tied to event timing rather than guaranteed.

**What you expected to happen**:

A client error on the admission status patch should not cause the scheduler to forget a workload the apiserver actually admitted. Cache and API should converge, and the ClusterQueue's nominal quota should not be exceeded.

**How to reproduce it (as minimally and precisely as possible)**:

Deterministic (unit level), which pinpoints the logic:
1. Create one ClusterQueue and one queued Workload that fits its quota.
2. Intercept the Workload status patch so it applies the write for real and then returns an error (simulating commit-then-timeout).
3. Run one scheduling cycle and wait for the async admit goroutine to finish.
4. Observe the divergence: the API shows the Workload QuotaReserved while the scheduler cache no longer contains it.
5. In isolation (frozen state, no reconciler running), a follow-on cycle then admits a second workload past the quota — demonstrating the over-admission consequence. A self-contained Go test that seeds this divergence and verifies the reconciler re-adds the Workload will be included in the fix PR.

Live cluster (kind, fault-injected build): the divergence reproduces reliably — the scheduler logs Could not admit Workload and forgets the committed workload. The downstream over-admission, however, was not observed across repeated runs: the edge-triggered re-adds repopulate the cache before a competing workload's scheduling cycle lands. The case that persists is a quiet single commit-then-timeout with no follow-on events, where nothing re-adds the forgotten entry until a later update.

**Anything else we need to know?**:

This is a latent correctness / hardening issue, not a frequently-hit one: the divergence is real but largely self-correcting, and the over-admission window is narrow.
Preferred fix: have the WorkloadReconciler converge cache membership from API state — if a workload is reserved/admitted in the API but missing from the scheduler cache, add it. This is level-triggered, covers this and other divergence sources, and does not depend on read freshness. An earlier approach of re-Get-ing in the scheduler error path and keeping the assumption was considered but is best-effort: under the overload premise the informer-cached read lags the committed write (and even an uncached read can time out), so the error path can't be made reliably accurate.
