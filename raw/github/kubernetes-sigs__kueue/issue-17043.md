## Description

**What would you like to be cleaned**:

Follow up on https://github.com/kubernetes-sigs/kueue/pull/16778 by using `Workload.status.replaces` to determine committed workload slice replacements in the single-cluster reconciliation path as well as MultiKueue.

- Make the job reconciler the sole place responsible for finishing replaced slices in both setups. Deprecate/remove the scheduler's `replaceWorkloadSlice` completion path; the scheduler should continue recording `status.replaces` atomically with quota reservation.
- Use the shared `workloadslicing.Manager.FinishReplacedWorkloadSlices` logic in the single-cluster path, and simplify replacement handling in `EnsureWorkloadSlices`/`normalizeActiveSlices` to use the committed status record instead of inferring successful replacement from annotations and current admission state. Preserve the remaining slice selection, scale-up, scale-down, and pending-slice behavior.
- Only finish referenced predecessors present in the workloads supplied for the job/slice chain. Do not fetch absent predecessors by name, to avoid finishing an unrelated same-name slice.
- Cover single-cluster and MultiKueue replacement completion, including a successor whose admission has been cleared or that has finished, and ensure that a pending replacement without `status.replaces` does not cause predecessor completion. Preserve replacement events and metrics without duplicate reporting.

**Why is this needed**:

PR #16778 introduces a durable replacement record but intentionally leaves the single-cluster completion and normalization paths unchanged. The scheduler still finishes predecessors after successful admission, while the prebuilt job reconciliation path uses `status.replaces` for recovery.

Using the committed record in both paths removes duplicated completion logic and avoids relying on transient admission state to determine whether a replacement succeeded. It also makes the job reconciler's ownership of replacement completion explicit.
