That PR removed all three presubmits and periodics; it did not repair Kueue code. The baseline status later became successful with `Context retired without replacement.` Both extended shard statuses still show failure at inspection time.

A [comment on #17033](https://github.com/kubernetes-sigs/kueue/issues/17033#issuecomment-6086026754) suspects #16766. This is a hypothesis, not a confirmed cause. PR #17014 changes only CLI verification/build recipes and their regression test; `pull-kueue-verify-main` passed.

- Fix the confirmed scheduler, test, or configuration cause and add regression coverage.
- Determine why only the baseline status was retired. Coordinate CI restoration with #16832; do not treat retired statuses as passing tests.

Completion criteria: document a reproducible cause or supported classification, provide passing evidence for all three targets before restoring jobs, and explain how obsolete failed contexts on #17014 should be handled.

The immediate CI impact has been mitigated by kubernetes/test-infra#38028, which removed all three deep-TAS jobs. New commits, including the latest revision of #16895, pass without those checks. This does not demonstrate that deep-TAS functionality has been fixed.

Local scheduler tests traced the admission failure to the planner introduced in #16801. With SchedulerLibraryDeepIntegration enabled, a fitting TAS workload hits was planner unable to process assignment. The same cases pass with deep integration disabled. The failure reproduces both before and after #16766, so reverting #16766 would not address this cause.

Related implementation work is already underway in #16482 and #16483. All three deep-TAS E2E targets still need validation before the jobs are restored; my local reproduction did not run those full suites. The obsolete failed statuses are a separate CI reconciliation concern.
