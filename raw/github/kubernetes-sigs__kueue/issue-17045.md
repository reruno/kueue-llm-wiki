## Description

**What happened**:

A PodSet requested two one-GPU Pods with:

```yaml
kueue.x-k8s.io/podset-required-topology: kubernetes.io/hostname
```

The cluster had two eligible hosts with one free GPU each. Aggregate capacity was sufficient, but no single hostname domain could fit both Pods.

Kueue correctly kept the Workload pending, but reported only:

```text
topology "default-topology" allows to fit only 1 out of 2 pod(s)
```

The message does not explain that `1 out of 2` is the capacity of the best single hostname domain, or that required topology forces all Pods into one such domain. A user who sees two free GPUs across the cluster can therefore interpret this as an aggregate-capacity failure.

**What you expected to happen**:

The message should identify the required topology level and explain the single-domain constraint. For example:

```text
topology "default-topology" cannot place all 2 pods in one "kubernetes.io/hostname" domain; the largest eligible domain fits 1
```

The exact wording is open to maintainer feedback.

This extra context should apply only to required-topology failures. Preferred, unconstrained, implied, and multi-layer placement have different semantics and should retain diagnostics appropriate to those paths.

**How to reproduce it (as minimally and precisely as possible)**:

1. Create two eligible nodes with one allocatable GPU each.
2. Configure a TAS `Topology` containing `kubernetes.io/hostname`.
3. Create a `ClusterQueue` with quota for two GPUs and a matching `LocalQueue`.
4. Submit a two-Pod Job requesting one GPU per Pod and annotate its Pod template with:

   ```yaml
   kueue.x-k8s.io/podset-required-topology: kubernetes.io/hostname
   ```

5. Observe that the Workload remains pending because no hostname can fit both Pods, while the condition message omits the co-location constraint.
6. Remove the required-topology annotation and observe that the same two Pods can be admitted across the two nodes.

**Anything else we need to know?**:

This is a diagnostic issue, not an admission correctness issue. Required topology is working as designed.

The message is produced by `TASFlavorSnapshot.notFitMessage` in `pkg/cache/scheduler/tas_flavor_snapshot.go`. The placement path already carries whether topology is required and the requested topology level, so this should not require an API or scheduling-algorithm change.

Issue #11842 is related but complementary: it tracks a structured condition reason for TAS placement failures. This report concerns the human-readable explanation of the specific constraint that prevented placement.

This issue was investigated and drafted with AI assistance. I reviewed the reproduction, source path, proposed wording, and scope.
