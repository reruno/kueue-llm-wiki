## Description

**What happened**:

A MultiKueue `batch/Job` (Indexed, 4 pods) was running on a worker cluster when one of its pods was killed by a gke node failure. The worker's Kueue evicted the workload (`EvictedDueToNodeFailures`, no replacement node available), and the manager reset the MultiKueue AdmissionCheck and re-dispatched it. Before the eviction, the manager Job's status had been synced with `status.failed: 1`.

On re-dispatch, a new Job is created on the worker with `status.failed: 0`. All of its pods start and become ready there (`failed: 0`, `ready: 4`), but the manager Job stays at `failed: 1`, `ready: 0`. The manager Workload never gets `PodsReady=True` and is evicted with `Exceeded the PodsReady timeout` exactly `waitForPodsReady.timeout` after admission (the default 30m in our case, since the manager config does not set `waitForPodsReady`). This repeated on both re-dispatches we observed; the only way out was deleting and recreating the Job.

The cause appears to be that the MultiKueue Job adapter replaces the manager Job's status wholesale with the worker Job's status (`localJob.Status = *statusUpdate` in `SyncJob`, `pkg/controller/jobs/job/job_multikueue_adapter.go`). With the strengthened Job status validation for `managedBy` Jobs, the API server always sets `RejectDecreasingFailedCounter: true` (`pkg/registry/batch/job/strategy.go`), so the update is rejected with `status.failed: Invalid value: 0: cannot decrease the failed counter` and the manager Job status is never refreshed after the re-dispatch. The same applies to `status.succeeded` for Jobs where decreasing it is rejected.

**Expected behavior**:

After a re-dispatch, the worker Job's status is synced to the manager Job, the manager Workload becomes `PodsReady`, and the Job keeps running.

**How to reproduce it (as minimally and precisely as possible)**:

These are the steps we expect to reproduce it in a minimal setup; we hit it in production and have not yet run them in isolation.

1. MultiKueue with one manager and one worker cluster on Kubernetes 1.35, `waitForPodsReady` enabled on the manager (a short timeout such as 2m makes it quicker to observe).
2. Create a `batch/Job` with `restartPolicy: Never`, `backoffLimit: 1`, `parallelism: 2` in a MultiKueue-enabled LocalQueue and wait until it runs on the worker.
3. On the worker, delete one of the Job's pods so the worker Job reports `status.failed: 1`, and wait until the manager Job also shows `status.failed: 1`.
4. Force a re-dispatch, e.g. by deleting the remote Workload on the worker cluster.
5. Observe that the new worker Job runs with `failed: 0`, the manager Job stays at `failed: 1` / `ready: 0`, the manager logs a rejected status update, and the manager Workload is evicted with `Exceeded the PodsReady timeout`, after which the cycle repeats.

**Anything else we need to know?**:

The manager Job is managed by MultiKueue, so its counters are informational there; `backoffLimit` is enforced by the Job controller on the worker. A possible fix is to keep `failed` and `succeeded` at `max(local, remote)` when syncing the remote status to the local Job, so a re-dispatched remote Job (whose counters restart at zero) can still be synced.

The same code is present on `main` and in v0.20.1. The version we originally encountered this is v0.19.1.

**Environment**:
- Kubernetes version: manager v1.35.8-gke.1380001, worker v1.35.6-gke.1250001 (GKE)
- Kueue version: v0.19.1 on both manager and worker
- Cloud provider or hardware configuration: GKE; MultiKueue via ClusterProfile (`MultiKueueClusterProfile` feature gate); Topology Aware Scheduling on the worker
- Others: worker `waitForPodsReady` with `blockAdmission: true`, `timeout: 25m`; manager `waitForPodsReady` not configured (defaulted to 30m)
