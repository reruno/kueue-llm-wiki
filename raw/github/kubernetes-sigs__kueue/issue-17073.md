## Description

**What happened**:

KueueViz registers the `/ws/namespaces` websocket route without wrapping it in `middleware.RequireAuthorization`.

The endpoint derives namespace data from `LocalQueue` objects and is updated through the `LocalQueue` informer. Other websocket endpoints in KueueViz require RBAC authorization for the resources they list/watch, but `/ws/namespaces` appears to allow an authenticated user to open the stream without first proving `list`/`watch` access to LocalQueues.

AI-assisted review was used to identify this issue.

**What you expected to happen**:

`/ws/namespaces` should enforce RBAC authorization consistent with the data source and streaming behavior, likely requiring `list` and `watch` access to LocalQueues before opening the websocket stream.

Alternatively, the endpoint should avoid using a live LocalQueue-backed stream for users who do not have the corresponding watch permission.

**How to reproduce it (as minimally and precisely as possible)**:

1. Run KueueViz with `TokenReview` authentication enabled.
2. Use a Kubernetes user/service account that can authenticate to KueueViz but does not have `watch` permission on `localqueues.kueue.x-k8s.io`.
3. Open a websocket connection to `/ws/namespaces`.
4. Observe that the route is not guarded by `middleware.RequireAuthorization` in `cmd/kueueviz/backend/handlers/handlers.go`, unlike other websocket routes.

Code pointer:

- `cmd/kueueviz/backend/handlers/handlers.go`: `/ws/namespaces` is registered directly with `h.NamespacesWebSocketHandler()`.
- `cmd/kueueviz/backend/handlers/namespaces.go`: the handler derives namespace data from LocalQueues and watches `LocalQueuesGVK()`.

**Anything else we need to know?**:

This is an RBAC consistency issue and may expose namespace/LocalQueue presence or update timing metadata in multi-tenant deployments. The impact depends on how broadly KueueViz is exposed and whether namespace names or queue existence are considered sensitive in the cluster.

A possible fix is to wrap `/ws/namespaces` with `middleware.RequireAuthorization` and require `list`/`watch` access to LocalQueues, similar to the other websocket endpoints.
