## Description

**What would you like to be added**:

Support in-place updates and zero-downtime upgrades for MultiKueue-managed RayServices. Add zero-downtime upgrade support after https://github.com/kubernetes-sigs/kueue/pull/11264 is merged, including worker-side autoscaling of pending RayClusters.

The implementation in https://github.com/kubernetes-sigs/kueue/pull/16259 currently reads only `status.activeServiceStatus.rayClusterName` in `fetchActiveRayClusterWorkerState`. This follow-up should handle the pending phase and the transition from pending to active, including periods when both RayClusters exist.

For in-place updates, support propagating changes to `serveConfigV2` from the manager RayService to the worker RayService without replacing the active RayCluster, while keeping worker-side autoscaling and workload-slice accounting consistent.

Related tracking issue: https://github.com/kubernetes-sigs/kueue/issues/11102.

**Why is this needed**:

When only a pending RayCluster exists, the current helper does not reflect its runtime worker counts to the manager. When active and pending RayClusters coexist during an upgrade, it reflects only the active cluster's counts. Supporting upgrades requires coordinating resource accounting and workload slices for both clusters, rather than simply switching the source of replica counts to the pending cluster.

In-place Serve configuration updates also need to reach the worker RayService so that the running application reflects the manager-side configuration and any resulting changes in resource demand are accounted for.

**Completion requirements**:

- Propagate in-place `serveConfigV2` updates from the manager to the worker RayService without unnecessarily replacing the active RayCluster.
- Verify that worker-side autoscaling and workload-slice accounting remain correct after an in-place update, and add test coverage.
- Define how active and pending RayClusters map to workload slices across manager and worker clusters.
- Reflect the relevant worker-side autoscaling changes throughout an upgrade without losing resource accounting for the still-running active cluster.
- Handle promotion of the pending RayCluster and retirement of the old active RayCluster.
- Add coverage for the pending phase, coexistence, and promotion, and update the documented support and limitations.
