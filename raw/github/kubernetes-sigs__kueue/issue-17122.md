## Description

**What happened**:

`jobframework.UpdateWorkloadPriority` resolves the WorkloadPriorityClass once for a set of Workloads (#13780) and then writes them one by one: first the Workloads that already name the class but hold another value, then the ones that move to it. If the class value changes after the lookup, and the class reconcile runs before a write lands, the reconcile skips a Workload that still holds the new value, and the write then lands the value from before the change.

For a Workload whose reference does not change in that write, nothing triggers again. The class controller acts on class events only, and the job reconcilers resolve the class only while a class name still has to change. The Workload keeps the old value until the class is reconciled again.

Workload slices on main reach this path: the Job reconciler passes the replacement slice together with the quota-reserved slice it waits behind. LeaderWorkerSet components reach it with #13904, which passes all existing components in one call. With #17100, a Workload whose reference changes in that write is repaired, so the components can end up with different values.

**What you expected to happen**:

A Workload that references a WorkloadPriorityClass ends up on the class value, whichever order the writes and the class reconcile run in.

**How to reproduce it (as minimally and precisely as possible)**:

With the fake client, on main at 4f8aa9cc7:

1. WorkloadPriorityClass `high` at 200 and `low` at 10; Workload `w0` on `high` with priority 100, Workload `w1` on `low` with priority 10; a Job labelled `kueue.x-k8s.io/priority-class: high` as the owner.
2. Call `UpdateWorkloadPriority(ctx, c, recorder, job, nil, w0, w1)`. An Update interceptor, on the write of `w0` with 200, first changes `high` to 100 and runs `WorkloadPriorityClassReconciler.Reconcile` for `high`. That reconcile skips `w0`, which still holds 100 in the store, and `w1`, which still references `low`.
3. The writes go through.

Result on main: `high` is 100, and both `w0` and `w1` are on `high` with 200. With #17100 applied as well (I ran it with #13904 and #16459 merged too), its reconciler repairs `w1` to 100 because its reference changed, and `w0` stays at 200.

**Anything else we need to know?**:

Two ways to close it:

- After its writes, `UpdateWorkloadPriority` reads the class again and, if the value changed, writes the new value to the Workloads it wrote, the way #17100 does for one Workload. That second write should be a merge patch of `spec.priority`: an Update that conflicts would leave the same-class Workloads with no class-name mismatch for the next reconcile to act on.
- After a value change, the class controller reconciles the class once more after a delay. That would also catch writes from other components, at the cost of a timer.

I'd go with the first: it closes the window without a timer and follows #17100. #16459 doesn't close it either: after a class change it writes the Workloads the cache shows as current, and that write is a no-op when the cache is up to date, so a write still in flight goes through.
