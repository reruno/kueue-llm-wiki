### Comment by [@kannon92](https://github.com/kannon92) — 2026-10-13T14:10:55Z

A local trial of promoting `MultiKueueClusterProfile` to beta/default-on in v0.21 identified the following work:

### Confirmed implementation and test work

- [x] **Preserve startup without the optional ClusterProfile CRD.**  
  `ConfigureClusterProfileCache` skips cache configuration when the CRD is missing, but the controller still registers a ClusterProfile watch when the gate is enabled. A local envtest reproduction starts successfully with the gate disabled but fails cache synchronization with it enabled. Watch registration should account for CRD availability, with regression coverage ensuring kubeconfig-based MultiKueue remains operational.

- [ ] **Explicitly disable the gate in gate-off tests.**  
  The disabled-feature cases in the MultiKueue unit and integration tests currently rely on the alpha default and fail after promotion.

- [ ] **Update documentation and generated feature-gate data.**  
  Update the setup guide’s alpha/manual-enablement instructions and regenerate the compatibility reference and site data with `make generate-featuregates`.

### Graduation criteria and dependency questions

The feature-gate declaration in `pkg/features/kube_features.go` points to **Kueue KEP-693: MultiKueue**. That KEP describes ClusterProfile authentication, but does not explicitly mention `MultiKueueClusterProfile`, list it in `kep.yaml`, or provide integration-specific graduation criteria. Its existing beta criteria concern the original MultiKueue feature.

**Recommendation:** update KEP-693 to record the gate and clarify its beta expectations, including adoption/feedback evidence, testing, default-on safety, and compatibility commitments. This is a recommendation, not an existing explicit requirement.

Upstream **Cluster Inventory KEP-4322 remains alpha/provisional**. Credential-plugin KEP-5339 was merged into it, with the base API and access-related fields expected to graduate together. Should Kueue wait for upstream beta, or promote its integration independently with explicit compatibility expectations? Kueue KEP-693 currently specifies neither requirement.

Automatic cluster generation (issue 7716) and standardized plugin distribution (issue 8042) appear to be follow-ups rather than documented beta prerequisites.

### Local validation

Race-enabled features/configuration unit tests and MultiKueue webhook integrations passed. MultiKueue unit tests had one implicit gate-off failure; ClusterProfile integrations had **5 passes and 1 implicit gate-off failure**. A separate startup probe confirmed the missing-CRD blocker. A full e2e run was not performed.

### Comment by [@yindia](https://github.com/yindia) — 2026-10-14T14:56:16Z

Picking this up. I traced the alpha→beta work and want to confirm scope before PR, especially the graduation questions.

**Implementation items that are clearly needed regardless of timing:**

1. *Startup without the ClusterProfile CRD.* `ConfigureClusterProfileCache` correctly skips the informer cache when the CRD is absent, but `clustersReconciler.setupWithManager` still registers the `ClusterProfile` watch off the feature gate alone. Gate-on + CRD-absent then syncs a watch with no cache entry and the manager exits. I'd thread the CRD-presence result from `ConfigureClusterProfileCache` into the controller setup so the watch is only registered when the CRD exists, with regression coverage that kubeconfig-based MultiKueue still starts. This is a real bug today and I'm happy to send it as a standalone PR ahead of the promotion.

2. *Explicitly disable the gate in the gate-off unit/integration cases* so they don't depend on the alpha default.

3. *Docs + generated data:* update the setup guide's manual-enablement section and regenerate with `make generate-featuregates`.

**Graduation questions I'd like a maintainer decision on before flipping the default:**

- KEP-693 records the gate but doesn't list `MultiKueueClusterProfile` in `kep.yaml` or give integration-specific beta criteria. Should we update the KEP (adoption/feedback, testing, default-on safety, compatibility) as part of this, and who owns that?
- Cluster Inventory KEP-4322 / credential KEP-5339 are still alpha/provisional upstream. Do we wait for upstream beta, or promote Kueue's integration independently with explicit compatibility expectations?

If the preference is to land the CRD-startup fix first independently of the promotion decision, I can open that PR now. Let me know how you'd like to split it.
