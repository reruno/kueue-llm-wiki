## Description

**What would you like to be added**:

A new option on `ProvisioningRequestConfig`:

```yaml
spec:
  provisioningClassName: best-effort-atomic-scale-up.autoscaling.x-k8s.io
  admitWhen: PodSetsSchedulable   # default: Provisioned (current behaviour)
```

Today the check turns Ready when the ProvisioningRequest reports `Provisioned=True`. The autoscaler sets that condition when the scale-up call succeeds. The new nodes may not have registered or become Ready yet. Kueue admits anyway, and the pods wait Pending.

With `admitWhen: PodSetsSchedulable`, the check stays Pending a little longer. It turns Ready when the new nodes are Ready and the Workload's pod sets fit on them. Fit means the node selectors, tolerations and resource requests are satisfied. The Workload is then admitted and its pods start at once.

While the check waits, its `message` says which step it is on: provisioning, node registration, node readiness, or pod fit.

If `BookingExpired` arrives during the wait, the existing `retryStrategy` handles it. That is already how Kueue treats an unadmitted Workload today.

The option does nothing for `check-capacity`, which never scales up. The default stays `Provisioned`. The option is opt-in per config, behind a feature gate.

**Why is this needed**:

Some providers take minutes to boot a node. Cluster API clusters and bare-metal GPU clouds are examples. There, Kueue admits before any node exists. The pods sit Pending for the whole provisioning time with no reason shown. The autoscaler's 10-minute booking can lapse while the nodes are still booting. With Topology Aware Scheduling this becomes a hard failure, because TAS assigns over nodes that do not exist yet.

Today's workarounds are a very high `backoffLimitCount`, or an external AdmissionCheck that waits for Ready nodes. The autoscaler's `Provisioned` condition is shared by every consumer. Kueue is the consumer that decides what "admitted" means to users. That makes Kueue the narrower place for this choice.

**Completion requirements**:

This enhancement requires the following artifacts:

- [x] Design doc, as an update to KEP-1136
- [x] API change, feature-gated
- [x] Docs update

### Comment by [@yindia](https://github.com/yindia) — 2026-10-14T14:26:41Z

I'd like to pick this up, and want to align on direction first since the thread has two competing views (fix in Kueue vs. fix in CAS/CapacityBuffer).

Grounding the problem in the code: `isProvisioned()` in `pkg/controller/admissionchecks/provisioning/provisioning.go` flips the check to Ready the moment the ProvisioningRequest reports `Provisioned=True`. CAS sets that when the scale-up call is accepted, not when nodes have registered and gone Ready — so on slow providers (Cluster API, bare-metal GPU) the Workload is admitted over nodes that don't exist yet, pods stay Pending with no surfaced reason, and with TAS it's a hard failure.

On the Kueue-vs-CAS question: I agree long-term the autoscaler is the right owner (CapacityBuffer / [autoscaler#10127](https://github.com/kubernetes/autoscaler/issues/10127)), but that's not available today, and the current behavior already contradicts our own ProvisioningRequest docs ("when nodes are ready"). An opt-in, feature-gated, default-off option on `ProvisioningRequestConfig` seems like a reasonable bridge that doesn't change any existing behavior.

Proposed minimal shape:
- `ProvisioningRequestConfigSpec.admitWhen: Provisioned | PodSetsSchedulable`, default `Provisioned`, behind a feature gate.
- When `PodSetsSchedulable`, after `Provisioned=True` the check stays Pending until provisioned nodes are registered + Ready and the pod sets fit (node selectors, tolerations, resource requests), with the current sub-state shown in the check `message`. `BookingExpired` continues to be handled by the existing `retryStrategy`.
- No change for `check-capacity`.

Questions for maintainers before I start:
1. Is a Kueue-side opt-in acceptable as an interim solution, or do you want to wait for the CAS/CapacityBuffer path?
2. Does this need a full KEP-1136 update (the completion requirements say yes) — and who should own/approve that?
3. Any preference on the field name/enum and whether "pod set fit" should reuse existing scheduler fit logic vs. a lightweight check here?
