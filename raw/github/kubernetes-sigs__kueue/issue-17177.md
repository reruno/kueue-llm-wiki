## Description

**What happened**:

Multi-resource WebSocket handlers register secondary informers without checking the user's `watch` permission. Changes to resources the user cannot watch can trigger live updates.

Affected files under `cmd/kueueviz/backend/handlers/`:
- `workloads_dashboard.go`: `/ws/workloads/dashboard` registers `PodsGVK()`, `ClusterQueuesGVK()`, `LocalQueuesGVK()`, and `ResourceFlavorsGVK()`.
- `cohorts.go`: `/ws/cohorts` and `/ws/cohort/:cohort_name` register `ClusterQueuesGVK()`.
- `cluster_queues.go`: `/ws/cluster-queue/:cluster_queue_name` registers `LocalQueuesGVK()`.
- `resource_flavors.go`: `/ws/resource-flavor/:flavor_name` registers `ClusterQueuesGVK()` and `NodesGVK()`.

**What you expected to happen**:

Before passing each secondary GVK to `GenericWebSocketHandler`, check its corresponding GVR with `authorizer.Authorize(ctx, identity, middleware.ResourceAccess("watch", gvr, "", ""))`. Follow the `/ws/namespaces` pattern in PR #17088.

Acceptance criteria:
- Denied secondary resources have no registered informer event handlers.
- Allowed secondary resources retain live updates.
- Initial snapshots retain existing list authorization checks.
- Authorization errors fail closed with the existing WebSocket-aware service-unavailable response.
- Preserve behavior when no authorizer is configured.
- Add regression tests for allowed, denied, and error cases.

**How to reproduce it (as minimally and precisely as possible)**:

Connect to an affected endpoint with access to its primary resource but without cluster-wide `watch` access to a secondary resource. Change that secondary resource and observe that its informer can trigger an update.
