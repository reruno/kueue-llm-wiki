## Description

Variant `Workload` CRs maintain a list of resource flavors they are allowed to admit jobs to. In the current implementation of concurrent admission one variant `Workload` is created for each resource flavor, and the list consists of a single entry: that resource flavor.

This design is incompatible with jobs (in our case, `RayJob` CRs) consisting of multiple pods which are a mix of different types.

It is extremely common for our managed `RayJob` CRs to consist of a single CPU head node and one or more GPU worker nodes; this promotes separation of concern by siloing cluster management tasks to the head node while the GPU worker nodes do all of the meaningful work. This prevents a class of issues we have seen in the past where cluster performance degrades or the cluster fails due to competition for resources between the processes responsible for managing the cluster and the processes responsible for executing the actual user workload.

We furthermore also support heterogeneous clusters consisting of a CPU head node, one or more CPU worker nodes, and one or more GPU worker nodes.

Neither of these designs is compatible with concurrent admission as implemented due to the “one variant Workload, one resource flavor” restriction.

In order to work around this issue we patched our version of Kueue to add the special `default-flavor` to the list of allowed resource flavors variant `Workload` CRs are allowed to admit to. This resource flavor is used for admission for all CPU pods in our specific configuration, but this fix is not portable across Kueue use cases.

I am not sure what a portable fix would be. At a minimum, as a starting point, this limitation should be outlined clearly in the [Concurrent Admission](https://kueue.sigs.k8s.io/docs/concepts/concurrent_admission/) documentation.

Hi, I read through this and the Concurrent Admission page. Agree the limitation should be written down.

I'm opening a small docs PR that adds it to the Constraints list and to the "Parent and Variant Workloads" section: each Variant is pinned to one ResourceFlavor, so a Workload whose pod sets need different flavors at the same time (e.g. a RayJob with a CPU head and GPU workers) can't be admitted.

One question for maintainer @ResidentMario, should the page also mention the workaround of adding a shared default flavor to each variant's allowed list, or keep it as a plain constraint? I left it out for now.
