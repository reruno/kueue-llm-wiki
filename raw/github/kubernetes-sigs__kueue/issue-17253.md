**What would you like to be added**:

Part of https://github.com/kubernetes-sigs/kueue/issues/12763

Currently the release process takes pretty long since LGTM to finalize.

Stage | v0.19.8 | v0.20.1 | What consumes the time
-- | -- | -- | --
Preparation PR opened → merged | 13m52s | 15m17s | CI, review, merge queue
Draft-release job | 14m01s | 16m24s | Artifact build/upload, followed by SBOM/OpenVEX
Promotion PR opened → merged | 17m27s | 4m34s | Review, checks, merge queue
Promotion merged → production images confirmed | 7m33s | 3m27s | Registry propagation, command setup and checking
Preparation PR opened → published | 77m56s | 78m41s | Includes the stages above and handoffs

Some ideas:
1. Skip the test matrix for metadata-only preparation PRs, keep the verify probably
2. Run draft generation and image promotion concurrently

/wait-for-images and creation of the draft release are sequential, but they don't need to be. Only promotion of imags needs to wait for images. Release publication needs to wait for both steps.

3. Automate remaining PR creation and handoffs.

Add automation (locally run scripts etc) which will execute the steps without waiting for a human. Human remains needed for lgtm/approach

- Opens the preparation PR
- Opens the promotion PR immediately when all staging digests exist.
- Starts production checks after promotion merges.
- Opens the main-update PR after publication and requests the website cherry-pick after merge.

**Why is this needed**:

To optimize the process getting below 1h.

### Release publication flow

The release team executes the steps of the **New Release** issue template.
The diagram shows a patch release (`v$MAJ.$MIN.$PATCH`, `$PATCH` > 0).
An arrow means "must finish before". Steps without an arrow between them can run in parallel.

```mermaid
flowchart TD
    classDef chatops fill:#e8f0fe,stroke:#4285f4,color:#000
    classDef script fill:#fef7e0,stroke:#f9ab00,color:#000
    classDef wait fill:#fce8e6,stroke:#d93025,color:#000
    classDef manual fill:#e6f4ea,stroke:#188038,color:#000

    sync["/sync-release-notes"]:::chatops
    lgtm["OWNERS LGTM<br/>(1 owner)"]:::manual
    prepRel["prepare_pull.sh --target release"]:::script
    prepRelMerge["Wait: release PR merged<br/>⏱ ~14-15 min"]:::wait
    tag["/tag-release<br/>⏱ ~1.2 min"]:::chatops

    draft["/create-draft-release<br/>(artifacts, openvex, SBOM)<br/>⏱ ~14-16 min"]:::chatops
    waitImg["/wait-for-images<br/>(Prow builds staging image)"]:::wait
    promote["promote_pull.sh"]:::script
    promoteMerge["Wait: k8s.io PR merged<br/>⏱ ~5-17 min"]:::wait
    waitProd["/wait-for-prod-images<br/>⏱ ~3-8 min"]:::wait

    publish["/publish-release<br/>⏱ ~1.3 min"]:::chatops

    krew["/update-krew-index<br/>(latest published release only)"]:::chatops
    prepMain["prepare_pull.sh --target main<br/>(+ snapshot-docs.py)"]:::script
    prepMainMerge["Wait: main PR merged"]:::wait
    cherry["Cherry-pick to website"]:::manual
    announce["Announcement email"]:::manual

    sync --> lgtm --> prepRel --> prepRelMerge --> tag

    tag --> draft
    tag --> waitImg --> promote --> promoteMerge --> waitProd
    draft --> publish
    waitProd --> publish

    publish --> krew
    publish --> prepMain --> prepMainMerge --> cherry
    publish --> announce
```

Legend: blue is a ChatOps command, yellow is a local script that opens a PR,
red is a wait on CI or a PR merge, green is a manual step.

What can run in parallel:

- After `/tag-release`: `/create-draft-release` and the image promotion chain
  (`/wait-for-images` through `/wait-for-prod-images`).
- After `/publish-release`: the krew update, the `main` update, and the announcement.

What cannot run in parallel: everything up to `/tag-release` is a strict chain,
and `/publish-release` needs both the draft release and the promoted images.

### Comment by [@mbobrovskyi](https://github.com/mbobrovskyi) — 2026-11-05T09:04:54Z

Thanks @mimowo. Two items from the issue description:

**1. Skip the test matrix for metadata-only preparation PRs.**
I don't think we can do this safely. A preparation PR isn't metadata-only. For example, #17965 changes:
  - cmd/kueueviz/frontend/package.json / package-lock.json and test/e2e/kueueviz/package.json / package-lock.json. These feed the KueueViz build and tests, so the KueueViz jobs have to run. Go e2e and integration tests may not be needed for these files, but the KueueViz ones are.
  - Makefile. In practice only RELEASE_VERSION changes, but every test target is driven by the Makefile, and path-based Prow rules can't tell a version bump from a change to the build or test logic. A Makefile change has to rerun the full matrix.

So the time the preparation PR spends in CI stays for now.

**2. Run draft generation and image promotion concurrently.**
This is already solved by changing the order of steps. We now run `/wait-for-images` first, then start `/create-draft-release` and do the image promotion while the draft is being built. In practice this removes the waiting, and the release goes more smoothly.
