## Description

<!-- Please only use this template for submitting clean up requests -->

**What would you like to be cleaned**:
I would like us to have a test wrapper for the SchedulerSimulator. The wrapper should be a centralized way of testing basic aspects of an implementation of the interface.
Ideally we would:
* take an implementation under test,
* wrap it with the wrapper,
* allow the tests to run.
The wrappers method should ensure the basic contract of the interface is kept by the wrapped impl.
Example case here is that for SchedulerWorkload, the pods in the result always match the list of the pods in the input (ObjectKey-wise).

**Why is this needed**:
We want to have a clean and easy way of testing the core aspects of each implementation.

### Comment by [@yindia](https://github.com/yindia) — 2026-10-15T12:54:00Z

I'd like to take this one. Proposed approach:

Add a `SchedulerSimulator` contract harness under `pkg/cache/scheduler/simulator/testing`:

- `WrapForTest(t, impl) SchedulerSimulator` — decorates an impl so every call asserts the interface invariants inline, letting existing per-impl tests opt in by wrapping their simulator.
- `RunContractSuite(t, factory)` — a shared, impl-agnostic suite any implementation can call.

Invariants enforced initially:
- `ScheduleWorkload`: result placement keys exactly match input pod ObjectKeys; success ⟺ `Node != ""`, no `Error`, no `Reasons` (and failure ⟹ empty `Node`).
- `FindFeasibleNodes`: returned candidates are a subset of inputs.
- `Simulate`/`PreemptWorkload`: snapshot state is reverted after the call.

Two questions before I start:
1. Prefer the `WrapForTest` wrapper, the `RunContractSuite` table, or both?
2. OK to put it in a `simulator/testing` subpackage, or would you rather keep it in-package?
