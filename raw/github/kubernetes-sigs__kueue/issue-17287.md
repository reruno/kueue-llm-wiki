## Description

**What would you like to investigate**:

When a ResourceFlavor is removed from a ClusterQueue, admitted workloads keep running on it.
The ClusterQueue only stops admitting new workloads on that flavor.

With ConcurrentAdmission the same change evicts a running parent.
Since #12501, the variant reconciler deletes the variant whose flavor is no longer in the ClusterQueue, in `deleteStaleVariants`.
If that variant was the admitted one, the controller evicts the parent with reason `ConcurrentAdmission` and message "No variant is running".
#17144 extends this to the case when another variant is already admitted at that moment.

So, the same ClusterQueue update stops a running concurrent-admission workload, but leaves a regular workload running.

The question is whether concurrent admission should keep this behavior, or follow the regular semantics and keep the parent running on the removed flavor until it finishes.
If we change it, we need to decide:
- whether the admitted variant is kept, instead of deleted, while its flavor is not in the ClusterQueue;
- how it interacts with `TryPreferredFlavors`, since the parent can still migrate to a more preferred flavor later;
- what KEP-8691 should say. Today it only says that the controller creates and deletes variants when the flavor list changes, and that the parent is evicted when its admitted variant is evicted.

**Why is this needed**:

@mimowo raised it in https://github.com/kubernetes-sigs/kueue/pull/17144#discussion_r4272216093.
Removing a flavor from a ClusterQueue is a normal admin operation, for example when retiring a reservation or a node pool.
Today it restarts running concurrent-admission workloads, which users may not expect.
Neither KEP-8691 nor the concurrent admission docs describe this behavior.
