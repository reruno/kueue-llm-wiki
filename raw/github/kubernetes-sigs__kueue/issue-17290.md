## Description

**What would you like to be added:**

Investigate compatibility between WAS configuration and Kueue features, starting with batch Job and considering implications for JobSet and other frameworks.

Cover topology constraints, TAS Node Hot Swap, partial admission, elastic Jobs, preemption, and eviction/readmission.

Produce a compatibility matrix distinguishing supported, conditional, incompatible, and unverified combinations, with concrete examples and supporting evidence. Build on the analysis and PoC associated with #14091.

**Why is this needed:**

Establish a shared understanding of the interactions before choosing implementation changes. The findings should guide validation of unsupported combinations, safe defaulting, and documentation updates.

**Completion requirements:**
- [ ] Document the initial compatibility matrix and evidence gaps.
- [ ] Identify necessary tests, documentation updates, validations or defaulting opportunities.
- [ ] Recommend a small, actionable first set of changes.

### Comment by [@apullo777](https://github.com/apullo777) — 2026-11-04T16:27:40Z

@mimowo @kannon92 I've pulled together the initial Job compatibility findings (Kubernetes v1.37.0, Kueue v0.20.1; exceptions are noted in the doc):
- [Compatibility report](https://docs.google.com/document/d/1XqzVXqy6jViBhOJKVmoVF2KfQs0pL-wKrSANN-mcsk0/edit?usp=sharing): §1 summary, §2 KEP-13715 reassessment, §4 open questions and gaps, §6 suggested first changes
- [Repros and snapshots](https://gist.github.com/apullo777/535e8024b2e8e452053de954495e9a1b)

Ｏn areas raised in #14091 (numbers in parentheses are test cases in Appendix A):
- **TAS in the WAS API:** same-key placement works (6b). With a WAS key that is not a TAS level, Kueue TAS can pick an infeasible rack even when another rack satisfies both constraints (6c-2).
- **TAS Node Hot Swap:** works before completion; after completion, recovery works with #17375 (verified on v0.20.4).
- **Elastic Jobs:** WAS scaling works with `gang: {}` (2), though Kueue scale-down accounting remains unverified.

For defaulting, the tested `gang: {}` path (the same policy the KEP would inject) can hang after partial completion with `PodsReady=True` under partial admission (1a). An explicit `minCount` above the admitted count also blocks unsuspend (1b).

I'd start with regression tests for 1a/1b and a Kueue-side guard for 1b (§6), leaving topology and scheduler preemption for WG alignment (§4). Does that sound like a reasonable starting point, or would you put another area first?
