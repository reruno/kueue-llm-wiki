## Description

## What would you like to be added

An opt-in fail-fast policy for the plain Pod integration, including workloads dispatched through MultiKueue.

The initial scope could be standalone batch Pods with `restartPolicy: Never` and no per-container restart overrides. When a regular container selected by the policy terminates with a non-zero exit code, Kueue could cancel the unsuccessful attempt even if another container is still Waiting and the Pod phase has not reached Failed.

The policy should:

1. Be disabled by default, preserving existing behavior.
2. Have clearly defined container selection and restart-policy semantics; native restartable sidecars should not accidentally trigger it.
3. Stop/cancel the remaining Pod execution through the normal cleanup path before releasing quota, honoring the configured termination grace period.
4. Expose a clear Workload condition/event identifying the failed container and exit code.
5. Propagate the outcome to the manager in MultiKueue and allow both manager and worker quota accounting to converge.

This is a request for earlier failure handling, not for automatic retries or dependency synchronization. Retrying the application can remain the submitting workflow controller's responsibility. The API shape and which controller should own this policy are open for discussion.

## Why is this needed

In a MultiKueue deployment, a standalone Pod with three regular containers gets stuck in the following state:

- The Pod has `restartPolicy: Never`.
- The main container cannot start because an `envFrom.secretRef` refers to a missing Secret on the worker cluster.
- Two helper containers start, time out waiting for initialization normally performed by the main container, and terminate with exit code 1.
- `kubectl get pods` displays `Error`, but the actual `.status.phase` remains `Pending` because the main container is still `Waiting`.
- Both the manager and worker Workloads retain `QuotaReserved=True` and `Admitted=True`, with no `Finished` condition. Quota remained reserved more than 10 minutes after admission during observation.

The two failed helper containers are regular entries in `spec.containers`, **not** native sidecars in `spec.initContainers` with `restartPolicy: Always`.

I compared the complete `Pod.status` on the manager and worker; they were identical. This does **not** appear to be a MultiKueue Pod status synchronization failure.

The worker has `DisableWaitForPodsReady=true`, so there is no PodsReady timeout to evict this workload. I understand that this disables timeout-based recovery; the question here is about recognizing an already-unsuccessful attempt before the Pod phase becomes terminal.

### Observed state, with identifying information removed

Both manager and worker Pods report the equivalent of:

```yaml
spec:
  restartPolicy: Never
status:
  phase: Pending
  containerStatuses:
    - name: main
      state:
        waiting:
          reason: CreateContainerConfigError
          message: 'secret "required-runtime-config" not found'
    - name: helper-a
      state:
        terminated:
          reason: Error
          exitCode: 1
    - name: helper-b
      state:
        terminated:
          reason: Error
          exitCode: 1
```

Both corresponding Workloads have:

```yaml
status:
  conditions:
    - type: QuotaReserved
      status: "True"
    - type: Admitted
      status: "True"
  # No Finished condition.
```

The worker Pod events repeatedly report the missing Secret. The helper container logs report a timeout waiting for the initialization file. The workload continues to hold its CPU, memory, and vGPU quota despite the failed containers.

### Why phase-based completion alone is insufficient for this case

With `restartPolicy: Never` and non-zero exits from regular containers, the current Pod attempt cannot eventually become `Succeeded`. Creating the missing Secret later would not restart those failed containers.

The attempt continues to reserve quota even though the failed containers will not restart. With multiple such attempts, useful queued workloads can be blocked by these reservations.

An **opt-in fail-fast policy** for plain batch Pods could be one possible solution. It would need to stop/cancel the remaining Pod execution before releasing quota. I am **not** proposing simply marking the Workload `Finished` while a remaining container could still start or run outside quota accounting.

Enabling a worker-side PodsReady timeout can provide a time-based fallback, but does not express this failure-based policy. The proposed behavior should be opt-in because some applications may want remaining containers to finish cleanup or persist results after another container fails.

### Proposed reduced reproduction

**The reduced example below is proposed and has not yet been executed independently.** The state and synchronization observations above were verified in the existing deployment. This example removes the application, GPU, and Volcano dependencies to isolate the plain Pod lifecycle behavior.

### Prerequisites

In an existing MultiKueue test setup:

- Enable the `pod` integration on the manager and worker.
- Enable `DisableWaitForPodsReady=true` on the worker, matching the observed setup. Keep the manager from independently evicting the reproduction via a PodsReady timeout as well.
- Create the same namespace, `multikueue-repro`, and LocalQueue, `user-queue`, on both clusters.
- Configure the manager queue with a valid MultiKueue AdmissionCheck targeting the worker.
- Ensure both queues have enough CPU/memory quota for this Pod: at least `300m` CPU and `192Mi` memory.
- Ensure `intentionally-missing-secret` does not exist in `multikueue-repro` on the worker.

Save the following as `repro-pod.yaml`:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: quota-retention-repro
  namespace: multikueue-repro
  labels:
    kueue.x-k8s.io/queue-name: user-queue
spec:
  restartPolicy: Never
  containers:
    - name: main
      image: busybox:1.37
      command: ["sh", "-c", "sleep 300"]
      envFrom:
        - secretRef:
            name: intentionally-missing-secret
      resources:
        requests:
          cpu: 100m
          memory: 64Mi
        limits:
          cpu: 100m
          memory: 64Mi
    - name: helper-a
      image: busybox:1.37
      command: ["sh", "-c", "sleep 5; exit 1"]
      resources:
        requests:
          cpu: 100m
          memory: 64Mi
        limits:
          cpu: 100m
          memory: 64Mi
    - name: helper-b
      image: busybox:1.37
      command: ["sh", "-c", "sleep 5; exit 1"]
      resources:
        requests:
          cpu: 100m
          memory: 64Mi
        limits:
          cpu: 100m
          memory: 64Mi
```

Submit to the manager, replacing the example context names with the test cluster contexts:

```bash
kubectl --context manager apply -f repro-pod.yaml
```

After the helper containers exit, inspect the actual Pod phase and container states instead of relying only on the `kubectl get pods` STATUS column:

```bash
kubectl --context worker -n multikueue-repro get pod quota-retention-repro \
  -o jsonpath='{.status.phase}{"\n"}{range .status.containerStatuses[*]}{.name}{"\t"}{.state}{"\n"}{end}'

kubectl --context manager -n multikueue-repro get pod quota-retention-repro \
  -o jsonpath='{.status.phase}{"\n"}{range .status.containerStatuses[*]}{.name}{"\t"}{.state}{"\n"}{end}'

kubectl --context worker -n multikueue-repro get workloads -o yaml
kubectl --context manager -n multikueue-repro get workloads -o yaml
```

Check whether the workload remains quota-reserved without `Finished=True` while `main` is Waiting and both helpers have non-zero exit codes under `restartPolicy: Never`.

### Current implementation

In the v0.19.0 upstream source:

- [`Pod.Finished`](https://github.com/kubernetes-sigs/kueue/blob/v0.19.0/pkg/controller/jobs/pod/pod_controller.go) delegates the single-Pod completion check to `utilpod.IsTerminated`.
- [`utilpod.IsTerminated`](https://github.com/kubernetes-sigs/kueue/blob/v0.19.0/pkg/util/pod/pod.go) returns true only for `PodFailed` or `PodSucceeded`.
- The [MultiKueue Pod adapter](https://github.com/kubernetes-sigs/kueue/blob/v0.19.0/pkg/controller/jobs/pod/pod_multikueue_adapter.go) copies worker Pod status to the manager, consistent with the identical statuses observed here.

This explains the current result, but it leaves a failed attempt holding quota while Kubernetes still considers the Pod non-terminal. I have not verified the reduced example in a single-cluster setup or on other Kueue versions, and I am not assuming that every non-zero container exit should trigger unconditional cancellation.

### Related discussions

I found the following related issues when searching on 2026-10-15, but did not find an exact match for the container-failure/Waiting/quota-retention combination described here:

- [#16504 — MultiKueue does not sync Pod dependencies to worker clusters](https://github.com/kubernetes-sigs/kueue/issues/16504) (open, support): maintainers explain that dependency synchronization is outside the current MultiKueue scope. A [worker-side AdmissionCheck can gate admission until dependencies are ready](https://github.com/kubernetes-sigs/kueue/issues/16504#issuecomment-6009415925). This report is not requesting automatic Secret synchronization; the missing Secret is the trigger for the non-terminal failed-attempt scenario.
- [#16732 — MultiKueue Plain Pods inherit manager admission mutations](https://github.com/kubernetes-sigs/kueue/issues/16732) (open, bug): concerns manager-injected imagePullSecrets and security settings propagating to workers. Our failing Secret reference is explicitly declared in `envFrom`, and this report concerns lifecycle convergence and quota retention after container failures.
- [#6149 — Plain Pods cannot delete before completion](https://github.com/kubernetes-sigs/kueue/issues/6149) (closed, support): concerns PodGroup deletion/finalizer behavior, with discussion of higher-level Job APIs for finer failure handling. Our case is a single multi-container Pod with no deletion requested, not a PodGroup stuck terminating.

### Environment

- Kueue image tag: `v0.19.0`, served from a private registry.
- Kueue deployment: Helm, MultiKueue manager plus worker clusters.
- Kubernetes manager: `v1.36.2`.
- Kubernetes affected worker: `v1.35.2`.
- Platform: Alibaba Cloud ACK, `linux/amd64`.
- Workload type: standalone `v1/Pod`, three regular containers, `restartPolicy: Never`.
- Relevant observed worker feature gates: `PriorityBoost=true,DisableWaitForPodsReady=true`.
- Worker Workload retention: `afterFinished: 30m`, `afterDeactivatedByKueue: 30m`. These policies do not apply while the Workload is neither finished nor deactivated.
