### Comment by [@Hsinweilin](https://github.com/Hsinweilin) — 2026-11-03T05:15:05Z

@Singularity23x0 
Hi, before starting I checked what the move involves, and I think it hits an import cycle.

Today:
- `assignment/planner.go` imports `preemption`, only for `Plan.PreemptionTargets []*preemption.Target` (line 45).
- `preemption` imports `flavorassigner` and reads `flavorassigner.Assignment` (`preemption.go` lines 172, 212, 232, 530).
- `flavorassigner` imports neither, so there's no cycle today.

After moving `Assignment` into `assignment`, `preemption` has to import `assignment` (and so does `flavorassigner`). Together with the existing `assignment → preemption` edge, that's a cycle. I checked with the compiler in a scratch checkout by adding only the `preemption → assignment` import:

    package sigs.k8s.io/kueue/pkg/scheduler/preemption
      imports sigs.k8s.io/kueue/pkg/scheduler/assignment from zz_probe.go
      imports sigs.k8s.io/kueue/pkg/scheduler/preemption from planner.go: import cycle not allowed

Proposed fix: `preemption.Target` is an alias of `policy.Target`, and `preemption/policy` doesn't import any scheduler package. If `Plan.PreemptionTargets` is `[]*policy.Target`, the same probe builds cleanly (`go build ./pkg/scheduler/...`), and the type is identical so callers don't change. I haven't done the full move with the real `Assignment` yet, so there may be further edges I haven't seen.

Questions:
1. Is using `policy.Target` in `Plan` acceptable?
2. For the unexported `Assignment` methods that `FlavorAssigner` calls (e.g., `append`, `psError`, `updateMode`), which should be exported and which should be restructured?

I'll wait for your guidance before opening a PR.
