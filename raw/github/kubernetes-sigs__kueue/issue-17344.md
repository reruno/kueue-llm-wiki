## Description

**What happened**:

Consider workload where PodSet `A` needs preemption for quota and PodSet `B` fits quota.
If `B` then fails TAS placement even on an empty cluster (`WithSimulateEmpty`), the workload becomes `NoFit` with an empty reason, so the QuotaReserved condition shows `Pending`, and the message lists only `A`'s quota reasons. This happens because `AssignTopology` sets `B`'s flavors to `NoFit` but leaves `B.Status` empty, so `ResolveNoFitReason` and `Message()` treat `B` as `Fit` and skip it.

**What you expected to happen**:

The workload reports `TopologyPlacementFailed` as its QuotaReserved reason, and the message includes `B`'s topology failure.

**How to reproduce it (as minimally and precisely as possible)**:

With `TopologyAwareScheduling` and `UnadmittedWorkloadsObservability` enabled, use a ClusterQueue with one TAS flavor whose cpu quota is fully used by lower-priority workloads and whose memory quota is larger than any node's memory. Submit a workload with two PodSets that both require a hostname topology: one requests cpu (needs preemption) and one requests more memory than any node has (fits quota). The workload stays `NoFit` with reason `Pending`.

**Anything else we need to know?**:

Workloads with a single PodSet aren't affected. A fix is proposed in <PR link>, which records the failure with `ResolvePodSetFailure` and `TopologyPlacementFailed`. This issue was analyzed with AI assistance (Gemini) and verified by me.
