## Description

**What happened**:

A NoExecute `DeviceTaintRule` on the device a running TAS pod holds evicts the pod. The new pod is pinned to the same node and stays Pending ("cannot allocate all claims"). The Workload stays Admitted and `unhealthyNodes` stays empty, because the node itself is Ready and untainted.

After the WaitForPodsReady timeout (30m by default), Kueue evicts and requeues. With the DRA feasibility gates off, it readmits onto the same tainted device and gets stuck again.

**What you expected to happen**:

Kueue should treat it like an untolerated NoExecute node taint and replace the node. With a node taint, this works in about 12s on the same cluster.

**How to reproduce it (as minimally and precisely as possible)**:

1. kind, Kubernetes v1.37.0, two workers, dra-example-driver v0.5.0 with one device per worker. Kueue main with DRA, TAS and the TAS node replacement gates on.
2. A TAS Job (`podset-required-topology: kubernetes.io/hostname`) with one claim for `gpu.example.com`.
3. When it runs, apply a NoExecute `DeviceTaintRule` on the pod's device:

```yaml
apiVersion: resource.k8s.io/v1
kind: DeviceTaintRule
metadata:
  name: bad-gpu
spec:
  deviceSelector:
    driver: gpu.example.com
    pool: <node of the pod>
    device: gpu-0
  taint:
    key: example.com/unhealthy
    value: "true"
    effect: NoExecute
```

Same result with `KueueDRADeviceFeasibility` and `KueueDRAIntegrationDeviceTaints` on or off.

**Anything else we need to know?**:

#16081 fixed the admission side. This is the running-workload side. It also happens with the Kueue DRA gates off. Fixing it covers the `KueueDRAIntegrationDeviceTaints` Beta criterion "decide how Kueue handles an admitted Workload whose Pods a `NoExecute` rule evicts".

I reran this without TAS, and the replacement pod skipped the tainted device and was Running on the other worker in about 10s, same as a plain Job without Kueue. So the stall comes from TAS pinning the new pod to the old node with the hostname nodeSelector.
