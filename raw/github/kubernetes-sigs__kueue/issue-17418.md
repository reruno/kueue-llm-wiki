**What happened**: 

With the Pod integration and MultiKueue, the manager cluster copies the worker Pod status onto the gated manager Pod. When the workload is evicted on the worker cluster (for example, preempted), the manager workload loses its quota reservation and is requeued, and the remote workload and Pod are deleted. The manager Pod, however, keeps the status copied from the worker Pod. It still reports `phase: Running`, a Pod IP, container statuses, and `PodScheduled=True`, while it is gated and no worker Pod exists. It keeps this status until the workload is dispatched again.

**What you expected to happen**: 

After the requeue, the manager Pod should look like a gated Pod again: `phase: Pending` with `PodScheduled=False`, `reason=SchedulingGated`, and no Pod IP or container statuses.

**How to reproduce it (as minimally and precisely as possible)**:

1. Set up a MultiKueue manager with one worker cluster and the Pod integration enabled.
2. Create a single Pod on the manager with a `kueue.x-k8s.io/queue-name` label, and wait until it runs on the worker. The manager Pod then shows Running.
3. Evict the workload on the worker, for example by having a higher-priority workload preempt it.
4. Check that the manager workload is requeued: it no longer has `QuotaReserved`, and `status.clusterName` is unset.
5. Check the manager Pod. It is still gated but reports `phase: Running`, along with the Pod IP and container statuses from the deleted worker Pod.

**Anything else we need to know?**: 

Tools that read Pod status on the manager, such as dashboards, workflow engines and `kubectl get pods`, report the Pod as running while it is actually queued. I have a fix with unit and integration tests and can open a PR.

**Environment**:
- Kueue version: `v0.20.1`
- Install tools: `Helm`
