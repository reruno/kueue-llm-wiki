## Description

**What happened**:

With `SchedulerLibraryIntegration` and `SchedulerLibraryDeepIntegration` enabled, a Job with `kueue.x-k8s.io/podset-preferred-topology` is accepted. Its Kueue Workload creation repeatedly fails validation. The Job stays suspended without a Warning event; the error appears only in controller logs. Direct Workloads are rejected as expected.

Reported by @apullo777 in [this comment](https://github.com/kubernetes-sigs/kueue/pull/17419#issuecomment-6272474539).

**What you expected to happen**:

Users receive an actionable explanation that preferred topology is unsupported with `SchedulerLibraryDeepIntegration`, rather than an unexplained suspended Job.

Acceptance criteria:
- Surface the unsupported request through earlier Job-level validation or a user-visible reconciliation error, such as a Warning event. Leave the solution open.
- Identify the unsupported preferred topology request and feature gate.
- If Job-level validation is added, allow unchanged annotations on existing Jobs after the gate is enabled. Check new or changed requests without blocking unrelated updates.
- Preserve gate-disabled behavior and supported topology requests.
- Add regression coverage for the chosen behavior and gate-transition compatibility.

**How to reproduce it (as minimally and precisely as possible)**:

1. Use a kind cluster with the Workload validation from #17419. Enable `TopologyAwareScheduling`, `SchedulerLibraryIntegration`, and `SchedulerLibraryDeepIntegration` in Kueue.
2. Configure a TAS-enabled ClusterQueue and a LocalQueue named `tas-queue` in `default`. Include `kubernetes.io/hostname` in the configured Topology.
3. Submit this minimal Job:
   ```yaml
   apiVersion: batch/v1
   kind: Job
   metadata:
     name: preferred-topology-repro
     namespace: default
     labels:
       kueue.x-k8s.io/queue-name: tas-queue
   spec:
     suspend: true
     parallelism: 2
     completions: 2
     template:
       metadata:
         annotations:
           kueue.x-k8s.io/podset-preferred-topology: kubernetes.io/hostname
       spec:
         restartPolicy: Never
         containers:
         - name: worker
           image: busybox:1.36
           command: ["sh", "-c", "sleep 60"]
           resources:
             requests:
               cpu: 100m
               memory: 32Mi
   ```
4. Inspect the Job, its events, Workloads, and Kueue controller logs:
   ```sh
   kubectl get job preferred-topology-repro -n default -o yaml
   kubectl describe job preferred-topology-repro -n default
   kubectl get workloads -n default
   kubectl logs -n kueue-system deployment/kueue-controller-manager --all-containers=true --since=5m
   ```
   The reported result is an accepted, suspended Job, failed Workload creation, and no Warning event explaining the failure. Adjust the controller namespace/name for the installation.

**Anything else we need to know?**:

Track this separately from [#17419](https://github.com/kubernetes-sigs/kueue/pull/17419). Related WAS compatibility investigation: [#17290](https://github.com/kubernetes-sigs/kueue/issues/17290).

Affected areas: Job validation in `pkg/controller/jobs/job/job_webhook.go`, Job reconciliation/Workload creation error reporting, and Workload validation in `pkg/webhooks/workload_webhook.go`.
