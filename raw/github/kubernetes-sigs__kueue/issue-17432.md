## Description

**What would you like to be added**:

An opt-in way for remote HTTPS metrics scrapers to authenticate to Kueue with an existing X.509 client certificate, while retaining Kubernetes authorization for `GET /metrics` and compatibility with bearer-only scrapers.

The proposed authenticated follow-up mode, `metrics.accessControlMode: ClientCertificateOrBearer`, and its `metrics.clientCAFile` setting would identify an administrator-provided public client-CA bundle. Kueue would validate presented client certificates, derive their Kubernetes identities, and perform SubjectAccessReview before serving metrics. A certificate holder would not automatically receive metrics access. Certificate-authenticated requests would not require a bearer token or TokenReview.

This includes the metrics listener's TLS and request-authentication configuration, not just a CA mount or an API field. No certificate issuer, anonymous access, HTTP listener, or change to serving-certificate management is proposed.

**Why is this needed**:

Some monitoring platforms already issue and rotate client certificates for their collectors, including for authenticated infrastructure metrics endpoints. They would like to reuse those identities rather than distribute an additional bearer credential accepted by TokenReview.

Kueue's current metrics filter uses bearer-token authentication and exposes no client-CA option. Supplying serving certificates or configuring a scraper's client certificate alone does not enable incoming X.509 authentication.

This is the authenticated alternative discussed in https://github.com/kubernetes-sigs/kueue/issues/4841 and the Alternatives section of KEP-16029. That KEP's loopback-only authentication opt-out serves trusted pod-local scrapers; it does not cover remote certificate-authenticated scraping. Server CA/SAN verification by the scraper remains a separate responsibility. An API-server client CA could be reused if it signs the scraper's certificate, but would not be automatically trusted.

Proposed design: [KEP-16029 amendment PR #17433](https://github.com/kubernetes-sigs/kueue/pull/17433), reworked per maintainer feedback rather than introducing a standalone KEP. Its authenticated follow-up does not expand the current loopback-only implementation in #16035. Feedback is welcome on the mode/API, credential selection, authorization, CA reload/rotation, and gate/delivery staging.

**Completion requirements**:

- Preserve the current bearer-authenticated HTTPS default and bearer-only compatibility.
- Authenticate trusted client certificates and authorize their identities through SubjectAccessReview for non-resource `GET /metrics`.
- Reject missing/invalid credentials and unauthorized identities; do not let an invalid or denied certificate silently fall back to a more privileged token identity.
- Define feature-gate, startup validation, CA reload/rotation, disabled-metrics, and rollback behavior without anonymous or trust-all fallbacks.
- Cover real TLS, certificate identity/RBAC, credential precedence, bearer compatibility, leaf/CA rotation, and serving-TLS compatibility in tests.
- Document public client-CA versus serving-CA trust, existing certificate reuse, least-privilege bindings, and the remaining API-server authorization dependency.

This enhancement requires the following artifacts:

- [ ] Design doc — proposed as an authenticated follow-up in KEP-16029 amendment PR #17433, pending maintainer agreement.
- [ ] API change — proposed; not implemented by the KEP PR.
- [ ] Docs update — implementation and deployment documentation to follow acceptance.

The artifacts should be linked in subsequent comments.
