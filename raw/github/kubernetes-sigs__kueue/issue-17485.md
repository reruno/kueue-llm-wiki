**What happened**:

With the Pod integration and MultiKueue, the manager cluster copies the worker Pod status onto the gated manager Pods. When the workload of a Pod group is evicted on the worker cluster (for example, preempted), the manager workload gets `Evicted=True`, but it never releases its quota reservation and is never requeued.

The job reconciler releases the quota only once `IsActive()` returns false. For a Pod group, `Stop` leaves the gated manager Pods in place, and `IsActive()` counts every Pod in the group whose phase is `Running`, including the gated manager Pods whose `Running` phase was copied from the worker. The worker Pods are deleted, so nothing updates the copied phase again. The workload keeps `QuotaReserved=True`, holds its ClusterQueue usage, and is not dispatched again.

Single Pods are not affected: `IsActive()` only checks the Pods of a group, so the quota of an evicted single Pod is released regardless of its phase.

**What you expected to happen**:

After the eviction, the manager workload should release its quota and be requeued, and the manager Pods should go back to gated `Pending`.

**How to reproduce it (as minimally and precisely as possible)**:

1. Set up a MultiKueue manager with one worker cluster and the Pod integration enabled.
2. Create a Pod group on the manager. For example, create 2 Pods with the same `kueue.x-k8s.io/pod-group-name` label, the `kueue.x-k8s.io/pod-group-total-count: "2"` annotation, and a `kueue.x-k8s.io/queue-name` label. Wait until the group runs on the worker. The manager Pods then show Running.
3. Evict the workload on the worker, for example by having a higher-priority workload preempt it.
4. Check the manager workload. It has `Evicted=True` but keeps `QuotaReserved=True`, and the ClusterQueue usage is not released.
5. Check the manager Pods. They are still gated but report `phase: Running`, and they stay that way.

**Anything else we need to know?**:

Related to #17418, which covers the stale status of single Pods and is fixed in #17420. That fix resets the manager Pod status after the quota is released, so it never runs for Pod groups.

Possible approaches:

1. Don't count gated Pods as active in `IsActive()`. A gated Pod can't run in the cluster where it is gated, so a `Running` phase on it can only be copied from a worker. The status reset from #17420 could then also cover Pod groups.
2. Reset the manager Pod status when the workload is evicted, before the quota is released, after the remote objects are deleted, so the status sync doesn't copy `Running` back.

**Environment**:
Kueue version: `main` (also `v0.20.1`)
Install tools: `Helm`

Since a gated Pod cannot physically run on the manager cluster, filtering out gated Pods in `IsActive()` directly patches the root cause without having to perfectly time a status reset during the remote deletion phase.
