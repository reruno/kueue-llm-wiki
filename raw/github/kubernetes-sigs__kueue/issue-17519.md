## Description

**What happened:**

A long-running serving Workload (LeaderWorkerSet group) was deactivated by `backoffLimitCount` even though it had been continuously Ready for weeks before deactivation.

Timeline of one replica's group Workload (Kueue v0.20.0, `waitForPodsReady.timeout=45m`,`requeuingStrategy.backoffLimitCount=75`):

- Created Aug 7, served 4/4 Ready within ~2 days.
- Aug 20–25:  ~69 PodsReadyTimeout evictions in 115h under the 45m timeout + capped 60m backoff.
- Aug 25 → Oct 1: **36.5 days continuously 4/4 Ready**, serving, with normal preemption churn (13 preemptions, 2 node-failure evictions over the Workload's life — none of which increment the counter).
- Oct 2: 6 more failed start cycles → `count` reached 76 → deactivated (`DeactivatedDueToRequeuingLimitExceeded`). Stuck `SchedulingGated` since, because for an LWS group the Workload is only ever recreated on scale-in below its index, and nothing reactivates it.

**Why:**

`requeueState.count` is lifetime-cumulative. Only PodsReadyTimeout evictions increment it (`workload.UpdateRequeueState`, sole call site `pkg/controller/core/workload_controller.go` in the PodsReadyTimeout eviction path); preemption, node-failure and queue-stopped evictions do not. It is cleared only when the Workload is deactivated. Reaching `PodsReady=True` does not reset it (also true on current main).

For batch Workloads this is invisible: a Workload that becomes Ready finishes and is deleted, so cumulative == consecutive. Long-lived Workloads (LWS/StatefulSet/serving pod groups) live for months, so any finite `backoffLimitCount` is a countdown to deactivation for workloads that are otherwise healthy — every fully-recovered incident stays on the clock forever.

Notably, the original design discussion described the semantics as the PodsReady timeout being "exceeded %v times in a row" (#2175) — consecutive was the intent; lifetime-cumulative is an artifact of the batch lifecycle assumption.

**What you would like to be added:**

Reset `requeueState.count` once the Workload has been continuously `PodsReady=True` for a sustained period — e.g. at least `waitForPodsReady.timeout` (or a dedicated knob). A Workload that cannot hold readiness for a single timeout window still accumulates and is deactivated as today; a Workload that recovers and serves is not eventually killed by history.

- For batch Workloads this is a no-op in practice (Ready → Finished → deleted).
- The sustained-ready requirement answers the flapping concern: a Workload that oscillates mReady/timeout faster than the timeout window still counts every timeout.
- Alternative or complement: exempt serving pod groups from the count-based limit, leaving deactivation to the time-based proposal in #15278.

**Anything else we should know:**

Related but separate from #15255 / #15278 / #16023: those add a resettable *time-based* limit (`backoffLimitTimeout`); this asks that the existing *count-based* limit match its documented "in a row" semantics for long-lived Workloads. The two compose independently.

A secondary effect worth noting: KEDA counts a deactivated replica toward `minReplicaCount`, so the deactivation silently reduces serving capacity while dashboards stay green — consumers of serving integrations need either this fix or external reactivation logic.
