### What would you like to be added?

Currently, Kueue's deployment admission webhook (`pkg/controller/jobs/deployment/deployment_webhook.go`) enforces strict immutability on `kueue.x-k8s.io/queue-name` whenever the Deployment has ready replicas:

```go
// Prevents updating the queue-name if at least one Pod is not suspended
// or if the queue-name has been deleted.
isSuspended := oldDeployment.Status.ReadyReplicas == 0
if !isSuspended || newQueueName == "" {
    allErrs = append(allErrs, apivalidation.ValidateImmutableField(newQueueName, oldQueueName, queueNameLabelPath)...)
}
```

We propose relaxing this restriction to **allow `queue-name` updates while `ReadyReplicas > 0`**, while keeping the check that `queue-name` cannot be removed (`newQueueName == ""`).

### Why is this needed?

In serving / continuous workloads (e.g. inference endpoints, model serving, background services), changing a Deployment's queue—such as migrating from a dev queue to a production queue, shifting between priority tiers, or migrating between node flavor pools—is a common operational need.

Today, because of the `oldDeployment.Status.ReadyReplicas == 0` check, the only way to change a Deployment's queue is:
1. Scale the Deployment down to 0 replicas.
2. Wait for all existing pods to terminate (causing 100% service outage / downtime).
3. Update `kueue.x-k8s.io/queue-name`.
4. Scale back up to N replicas.

### Why is this safe for Deployments?

Unlike batch jobs (`batch/v1 Job`, RayJob, JobSet) where all pods belong to a single monolithic gang `Workload` CRD that cannot be split across queues mid-run, Deployments are managed via the plain Pod integration, where each pod replica is admitted as an independent Workload.

When a Deployment's `queue-name` label is updated:
1. Kueue's mutating webhook updates `spec.template.metadata.labels[kueue.x-k8s.io/queue-name]`.
2. The standard Kubernetes Deployment controller initiates a standard `RollingUpdateDeployment`.
3. New pods created under the new ReplicaSet queue for admission in the **new queue**.
4. Old pods under the old ReplicaSet continue running and serving traffic under their original quota in the **old queue**.
5. As new pods become ready in the new queue, old pods are progressively terminated, smoothly relinquishing quota back to the old queue without any downtime.

Retaining `if newQueueName == "" { ... ValidateImmutableField ... }` guarantees that a Deployment cannot silently remove its queue and bypass Kueue admission control while running.
