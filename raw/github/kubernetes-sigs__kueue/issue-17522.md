## Description


## What happened?

The DynamicQuotaOrchestrator (DQO) controller can accept capacity published for an older `CapacityProvider` specification as synchronized with its current specification.

In `reconcileDiscovery`, the controller checks whether the provider reports `CapacitySynchronized=True`, but does not validate the condition's `ObservedGeneration` against the current `CapacityProvider.metadata.generation`.

After a provider's spec is updated, Kubernetes increments its generation without automatically removing previously published status conditions or capacity data.

During the interval before the provider controller publishes updated status, DQO can combine the **new `spec.orchestratedFlavors` with previous-generation `status.capacity`**.

When capacity distribution is enabled, this potentially inconsistent capacity can influence the effective quotas written to ClusterQueues and Cohorts.

### Verification status

The missing generation validation is directly observable in the current code path.

## Root cause analysis

### 1. CapacityProvider exposes generation-aware status

**Source:**

[capacityprovider_types.go](https://github.com/kubernetes-sigs/kueue/blob/7f64dc9ef2e476a6f7232af2e19d4a549c82f2fa/apis/kueue/v1alpha1/capacityprovider_types.go)

A CapacityProvider contains:

- `spec.orchestratedFlavors`: flavors managed by the provider.
- `spec.parameters`: optional controller-specific configuration.
- `status.capacity`: normalized reported capacity.
- `status.conditions`: synchronization state.

The synchronization condition uses Kubernetes `metav1.Condition`, which exposes `ObservedGeneration`.

This field allows consumers to distinguish between status computed for the current configuration and status from an earlier configuration.

### 2. DQO does not validate synchronization freshness

**Source:**

[discovery.go — reconcileDiscovery](https://github.com/kubernetes-sigs/kueue/blob/7f64dc9ef2e476a6f7232af2e19d4a549c82f2fa/pkg/controller/core/dqo/discovery.go#L41-L99)

The relevant check is:

```go
if !apimeta.IsStatusConditionTrue(
    capacityProvider.Status.Conditions,
    kueuealpha.CapacityProviderCapacitySynchronized,
) {
    // Provider is not ready.
}
```

This validates only the condition's boolean status.

It does not establish the following generation-consistency invariant:

```go
condition.Status == metav1.ConditionTrue &&
condition.ObservedGeneration == capacityProvider.Generation
```

Therefore, `CapacitySynchronized=True` can be accepted even when the condition belongs to a previous generation.

### 3. New specification can be combined with old capacity

**Source:**

[discovery.go — aggregateProviderCapacity](https://github.com/kubernetes-sigs/kueue/blob/7f64dc9ef2e476a6f7232af2e19d4a549c82f2fa/pkg/controller/core/dqo/discovery.go#L102-L138)

The aggregation function uses:

- Current `capacityProvider.Spec.OrchestratedFlavors`.
- Previously published `capacityProvider.Status.Capacity`, which may not have been synchronized for that spec.

This can lead to a mixed-generation aggregation.

For a synchronized report, interpreting missing capacity for an orchestrated flavor as zero is intentional.

However, if the status predates a spec update introducing a flavor, the missing capacity could instead indicate that the provider has not processed the updated configuration.

### 4. Impact on effective quota distribution

**Sources:**

- [DQO reconciler](https://github.com/kubernetes-sigs/kueue/blob/7f64dc9ef2e476a6f7232af2e19d4a549c82f2fa/pkg/controller/core/dqo/reconciler.go#L195-L247)
- [Quota distribution](https://github.com/kubernetes-sigs/kueue/blob/7f64dc9ef2e476a6f7232af2e19d4a549c82f2fa/pkg/controller/core/dqo/distribution.go#L42-L85)
- [Effective quota updates](https://github.com/kubernetes-sigs/kueue/blob/7f64dc9ef2e476a6f7232af2e19d4a549c82f2fa/pkg/controller/core/dqo/distribution.go#L244-L291)

DQO performs two phases:

1. **Capacity discovery:** aggregate normalized capacity from referenced providers.
2. **Quota distribution:** calculate allocations and update `status.effectiveQuotas` on participating ClusterQueues and Cohorts.

If discovery accepts a stale provider condition, the subsequent distribution can use inconsistent input.

Potential consequences include:

- Temporary capacity underestimation.
- Temporary capacity overestimation.
- Incorrect effective quotas propagated to multiple queues.
- Scheduling or admission decisions based on stale allocations.

The precise impact depends on the provider implementation and configuration changes.

## What you expected to happen

A CapacityProvider should be considered freshly synchronized for its current specification only when its synchronization condition corresponds to the current metadata generation.

Expected behavior:

1. A synchronized condition with the current observed generation is accepted.
2. A synchronized condition with an older observed generation is treated as not ready.
3. DQO does not calculate new effective capacity from inconsistent spec/status generations.
4. DQO reports a useful diagnostic identifying the affected provider.
5. When the provider publishes current-generation status, DQO automatically resumes discovery and distribution.
6. Existing effective quota retention behavior remains unchanged unless a separate policy change is explicitly agreed upon.

This issue concerns **preventing new mixed-generation calculations**, not automatically deleting previously written effective quotas.

**Location:**

`pkg/controller/core/dqo/reconciler_test.go`

The existing `TestDynamicQuotaOrchestratorReconcile` table-driven test is a suitable starting point.

### Step 1: Create a stale synchronized provider

Construct the following test fixture:

```go
cp := utiltestingalpha.MakeCapacityProvider("cp").
    OrchestratedFlavors("gpu-a", "gpu-b").
    Condition(metav1.Condition{
        Type: kueuealpha.CapacityProviderCapacitySynchronized,
        Status: metav1.ConditionTrue,
        Reason: kueuealpha.CapacityProviderReasonSynchronized,
        ObservedGeneration: 1,
    }).
    Capacity(
        utiltestingalpha.MakeNormalizedCapacity().
            Flavors(
                utiltestingalpha.MakeNormalizedCapacityFlavor("gpu-a").
                    Resource(corev1.ResourceCPU, "16").
                    Obj(),
            ).
            Obj(),
    ).
    Obj()

cp.Generation = 2
```

This is an illustrative fixture, not a complete standalone test.

Here:

- The current specification is generation 2.
- The synchronization condition reports generation 1.
- The old capacity report contains only `gpu-a`.
- The current specification also orchestrates `gpu-b`.

### Step 2: Create a referencing DQO

Configure a DynamicQuotaOrchestrator with a discovery provider referencing `cp`.

Enable the `DynamicQuotaOrchestration` feature gate.

### Step 3: Reconcile

Invoke the existing DQO reconciliation test path.

**Behavior expected from the current implementation:**

The stale `CapacitySynchronized=True` condition passes the readiness check.

DQO can report `EffectiveCapacityComputed=True` while aggregating previous-generation capacity with current-generation flavor configuration.

### Step 4: Verify the correct behavior

Expected condition:

```text

Reason=ProviderNotReady
```

Suggested diagnostic:

```text

observedGeneration=1, currentGeneration=2
```

No new mixed-generation effective capacity should be committed.

### Step 5: Verify recovery

Update the provider to publish fresh capacity with:

```text

```

Reconcile again.

Expected:

```text

Reason=Computed
```

The effective capacity should now reflect the updated provider report.

## Proposed fix

The fix should be localized to provider readiness validation in:

`pkg/controller/core/dqo/discovery.go`

A conceptual generation-aware predicate is:

```go
condition := apimeta.FindStatusCondition(
    capacityProvider.Status.Conditions,
    kueuealpha.CapacityProviderCapacitySynchronized,
)

ready := condition != nil &&
    condition.Status == metav1.ConditionTrue &&
    condition.ObservedGeneration == capacityProvider.Generation
```

When `ready` is false:

- Mark discovery as not ready.
- Include the provider name and generation mismatch in the diagnostic.
- Avoid new aggregation using inconsistent provider data.

The existing `ProviderNotReady` reason may be sufficient; maintainers can decide whether a dedicated reason is preferable.

### Backward compatibility

Several existing tests construct synchronization conditions without explicitly setting `ObservedGeneration`.

A strict generation check would require updating these fixtures and clarifying the expected contract for external CapacityProvider controllers.

Before implementing the change:

1. Confirm how zero-valued `ObservedGeneration` should be handled.
2. Document the generation contract.
3. Update affected tests.
4. Verify compatibility with provider implementations.
5. Avoid silently treating stale generations as current.
