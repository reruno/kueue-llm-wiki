## Description

**What happened**:

Stopping a LocalQueue resets its counters, and deleting it while it is stopped leaves stale ones:

1. On `Hold`, the LocalQueue's counter and histogram series disappear. After a resume, the next admission sets `kueue_local_queue_admitted_workloads_total` to 1 instead of 2. A ClusterQueue on `Hold` keeps its counters. @tomsen02 found this one (comment below).
2. Counters recorded while the LocalQueue is stopped stay after it is deleted: the `LocalQueueStopped` eviction from `HoldAndDrain` in `kueue_local_queue_evicted_workloads_total`, or a Workload that finished under `Hold` in `kueue_local_queue_finished_workloads_total`. A LocalQueue created again with the same name and namespace starts from those values.

**What you expected to happen**:

Stopping a LocalQueue keeps its counters and histograms, as stopping a ClusterQueue does. Deleting a LocalQueue removes its series, stopped or not.

**How to reproduce it (as minimally and precisely as possible)**:

The reset:

1. Admit a Workload through a LocalQueue. `kueue_local_queue_admitted_workloads_total` is 1.
2. Set `spec.stopPolicy: Hold`. The series is gone.
3. Set `spec.stopPolicy: None` and admit a second Workload. The series is 1.

The stale counters:

1. Admit a Workload through a LocalQueue.
2. Set `spec.stopPolicy: HoldAndDrain`. The Workload is evicted and `kueue_local_queue_evicted_workloads_total{reason="LocalQueueStopped"}` is 1.
3. Delete the LocalQueue. The series is still 1, and creating the LocalQueue again keeps it at 1.

Resuming before the delete removes the series. The spec below covers both. On main (7f64dc9ef), "HoldAndDrain, resumed before the delete" passes and the other three cases fail. The Hold case reports `Expected <int>: 1 to equal <int>: 2`, and a delete case reports the series it left:

**Anything else we need to know?**:

Both come from the stop path:

- Stopping a LocalQueue [calls `Manager.DeleteLocalQueue`](https://github.com/kubernetes-sigs/kueue/blob/7f64dc9ef2e476a6f7232af2e19d4a549c82f2fa/pkg/controller/core/localqueue_controller.go#L325-L326), which [clears the LocalQueue's counters and histograms](https://github.com/kubernetes-sigs/kueue/blob/7f64dc9ef2e476a6f7232af2e19d4a549c82f2fa/pkg/cache/queue/manager.go#L617-L619). The stop has used that function since #2173, and #3673 added the clear there later. [KEP-1833](https://github.com/kubernetes-sigs/kueue/blob/main/keps/1833-metrics-for-local-queue/README.md#integration-tests) only asks for the metrics to be removed on delete.
- A stopped LocalQueue is no longer in the queue manager, so on delete `Manager.DeleteLocalQueue` [returns early](https://github.com/kubernetes-sigs/kueue/blob/7f64dc9ef2e476a6f7232af2e19d4a549c82f2fa/pkg/cache/queue/manager.go#L607-L610) and the counters recorded after the stop stay.

Keeping the counters on stop fixes the reset but not the stale counters. A sketch that clears only the LocalQueue's gauges on stop, and the rest in `LocalQueueReconciler.Delete` [next to `ClearLocalQueueResourceMetrics`](https://github.com/kubernetes-sigs/kueue/blob/7f64dc9ef2e476a6f7232af2e19d4a549c82f2fa/pkg/controller/core/localqueue_controller.go#L263-L265), makes all four cases pass, and the core controller suite still passes. release-0.20 and release-0.19 have the same code; I only ran the spec on main.

Related: #16840

### Comment by [@thc1006](https://github.com/thc1006) — 2026-10-21T03:49:14Z

Thanks for catching this. It reproduces on main: after a resume from `Hold`, the next admission sets `kueue_local_queue_admitted_workloads_total` to 1 instead of 2. I don't think it's intended: the stop has used `DeleteLocalQueue` since #2173, and #3673 added the clear there later.

Keeping the counters on stop fixes the reset but not the leak, because a stopped LocalQueue isn't in the queue manager and `DeleteLocalQueue` returns early when it's deleted. Clearing them on delete as well fixes both in my run. I've updated the title and description to match.
