**What happened**:

With `ElasticJobsViaWorkloadSlicesWithTAS` enabled, an elastic replacement can be skipped even though a valid topology placement exists, depending on PodSet order.

Reproduced with two nodes (`x1`: 4 CPU, `x2`: 2 CPU), each pod requesting 1 CPU:

| PodSet | Previous | Replacement |
|---|---|---|
| `a` | 1 on `x1` | 4 |
| `b` | 3 on `x1` | 1 |

When `a` comes before `b`, the scheduler on main (4a2bb59f9) skips the replacement with `Workload no longer fits after processing another workload` and requeues it. With the PodSet order reversed, the replacement is admitted.

It also happens when the later PodSet keeps its count (`a`: 2→3, `b`: 2→2).

**What you expected to happen**:

A feasible replacement is admitted regardless of PodSet order, keeping the placement of the pods that stay running and respecting node capacity. For the case above, `a`: 3 on `x1` + 1 on `x2`, `b`: 1 on `x1` is one valid placement, not the only one.

**How to reproduce it (as minimally and precisely as possible)**:

Using `runScheduleForTASCases` in `pkg/scheduler`, with:
- Two nodes: `x1` (4 CPU), `x2` (2 CPU)
- Initial admitted slice: `a`=1, `b`=3, all on `x1`
- Replacement: `a`=4, `b`=1, in that order
- `ElasticJobsViaWorkloadSlices` and `ElasticJobsViaWorkloadSlicesWithTAS` enabled

On main the replacement is skipped and requeued. A regression test should check admission, the kept pods' placement and node capacity, rather than one exact assignment.

**Anything else we need to know?**:

The replaced slice's topology usage is released before placement. Kept pods of a later PodSet are added to the assumed usage only when that PodSet is processed, so an earlier PodSet can take their capacity. This holds whether the later PodSet shrinks, keeps its count, or grows.

Before #14443, this placement was admitted with 5 CPU on the 4-CPU `x1` (originally reproduced at 1849ee987). #14443 makes the final fit check catch it, so the replacement is skipped instead. The check was backported in v0.19.10 (#17335) and v0.20.3 (#17327); The check was backported in v0.19.10 (#17335) and v0.20.3 (#17327). On v0.20.2, the invalid placement was admitted; on v0.20.3, the replacement was skipped and requeued.
