**What happened**:

With `ElasticJobsViaWorkloadSlicesWithTAS` enabled, an elastic replacement can be admitted with a topology assignment that exceeds node capacity when a growing PodSet comes before a shrinking one.

Reproduced with two nodes (`x1`: 4 CPU, `x2`: 2 CPU), each pod requesting 1 CPU:

| PodSet | Previous | Replacement |
|---|---|---|
| `a` | 1 on `x1` | 4 |
| `b` | 3 on `x1` | 1 |

Observed (grow first): `a`: 4 on `x1`, `b`: 1 on `x1`. That is 5 CPU assigned to a 4-CPU node.

With the PodSet order reversed, the placement is valid: `a`: 3 on `x1` + 1 on `x2`, `b`: 1 on `x1`.

**What you expected to happen**:

The replacement respects node capacity regardless of PodSet order, and keeps the placement of the pods that stay running.

**How to reproduce it (as minimally and precisely as possible)**:

Using `runScheduleForTASCases` in `pkg/scheduler`, with:
- Two nodes: `x1` (4 CPU), `x2` (2 CPU)
- Initial admitted slice: `a`=1, `b`=3, all on `x1`
- Replacement: `a`=4, `b`=1, in that order
- `ElasticJobsViaWorkloadSlices` and `ElasticJobsViaWorkloadSlicesWithTAS` enabled


The replacement is admitted with 5 CPU assigned to `x1`.

**Anything else we need to know?**:

The replaced slice's topology usage is released before placement. A growing PodSet can then use capacity that the kept pods of a later PodSet still need, and those kept pods get their previous assignment back without another capacity check.

This reproduces on main (1849ee987) with a 50-CPU ClusterQueue quota. With the quota set to 6 CPU, main leaves the replacement pending because of #16657, while #16662 admits it with the same invalid placement. So this is a pre-existing TAS placement issue that #16662 exposes in more cases, not a regression from that PR.

Verified at the scheduler level only, no end-to-end cluster reproduction yet.
