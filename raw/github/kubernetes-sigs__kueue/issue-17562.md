## Description

<!-- Please use this template while reporting a bug and provide as much info as possible. -->

**What happened**:
When a MultiKueue `batch/Job` with multiple completions (e.g. an Indexed Job or any Job with `spec.completions > 1`) has partially succeeded pods (`status.succeeded >= 1`) before being evicted on the worker cluster (e.g. due to node failure or preemption), the manager resets the AdmissionCheck and re-dispatches the Job.

On re-dispatch, a new worker Job is created on the worker cluster starting with `status.succeeded: 0`. When the MultiKueue Job adapter syncs the worker Job status to the manager Job, the manager API server rejects the update with HTTP 422:
> `status.succeeded: Invalid value: 0: cannot decrease the succeeded counter`

Because this status patch is repeatedly rejected, the manager Job's status is never updated with the new worker Job's active and ready pods (`status.ready`). Consequently, the manager Workload never attains `PodsReady=True` and is eventually evicted once `waitForPodsReady.timeout` expires.

**What you expected to happen**:
The manager Job should successfully sync status (active, ready, conditions) from the re-dispatched worker Job without being rejected by the Kubernetes API server for decreasing `status.succeeded`.

**How to reproduce it (as minimally and precisely as possible)**:
1. Submit an Indexed Job with `completions: 4, parallelism: 2` managed by MultiKueue.
2. Let pod 0 finish successfully (`status.succeeded: 1` synced to manager).
3. Simulate node failure or eviction on worker 1 so the workload is evicted and re-dispatched.
4. On the newly created worker Job, pods start running with `status.succeeded: 0, status.ready: 2`.
5. Observe that the manager Job adapter fails to update the manager Job status due to `status.succeeded` decreasing from 1 to 0.

**Anything else we need to know?**:
This is the same monotonicity issue as with `status.failed` (see PR #17059). In Kubernetes core (`k8s.io/kubernetes/pkg/apis/batch/validation/validation.go`), `ValidateJobStatusUpdate` enforces `RejectDecreasingSucceededCounter`:
```go
if opts.RejectDecreasingSucceededCounter && job.Status.Succeeded < oldJob.Status.Succeeded {
    allErrs = append(allErrs, field.Invalid(statusFld.Child("succeeded"), job.Status.Succeeded, "cannot decrease the succeeded counter"))
}

okay soo,, following up on the discussion in PR #17059 with @mimowo :

In Kubernetes 1.35+, `ValidateJobStatusUpdate` also enforces `RejectDecreasingSucceededCounter`, so re-dispatched Jobs with partial completions face the exact same API rejection when worker status resets to `succeeded=0`.

However, unlike `failed`, `succeeded` has extra considerations due to `completionMode: Indexed` and dynamic scaling (`ElasticIndexedJob` shrinking),,,heree are two possible approaches which im thinking around right noww :

Candidate 1 is  (Scalar Clamping + CompletedIndexes Union):
Clamp `merged.Succeeded = max(local.Succeeded, remote.Succeeded)` to satisfy the API server validation, and for Indexed Jobs, compute the union of `local.CompletedIndexes` and `remote.CompletedIndexes`.

Candidate 2 (Progressive Succeeded Sync):
For non-indexed Jobs, use `max(local, remote)`. For Indexed Jobs, keep the manager's `local.Succeeded` and `local.CompletedIndexes` until the new worker reaches or exceeds the previous progress (`remote.Succeeded >= local.Succeeded`), then switch to remote.
