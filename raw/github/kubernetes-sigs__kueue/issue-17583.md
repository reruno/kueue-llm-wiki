## Description

**What would you like to be cleaned?**

Make the quota-mapping-related `ResourceSlice` retry notifications driver-aware. Currently, a `ResourceSlice` event belonging to one configured DRA driver can notify ClusterQueues that only cover resources associated with entirely different drivers.

This is a code-backed **unnecessary scheduling retry / scalability concern**, not a claim of incorrect quota accounting or a measured production incident.

### Current behavior and code references

In [`pkg/controller/core/resourceslice_controller.go`](https://github.com/kubernetes-sigs/kueue/blob/2ebbf83c63e4d050e30ff7f3de1b79f785b615af/pkg/controller/core/resourceslice_controller.go):

1. `NewResourceSliceReconciler` builds a `drivers` set and a separate `quotaResources` set. `quotaResources` is the union of the logical resource names from **all** configured `deviceClassMappings` sources with a driver.
2. The `Create`, `Update`, and `Delete` predicates accept a `ResourceSlice` if its `Spec.Driver` belongs to that global `drivers` set.
3. `Reconcile` always passes the **entire** global `quotaResources` set to `r.cache.ClusterQueuesForResources(...)`, then calls `qcache.NotifyRetryInadmissible(...)`.

The relevant reconciler code is:

```go
if cqNames := r.cache.ClusterQueuesForResources(r.quotaResources); cqNames.Len() > 0 {
    qcache.NotifyRetryInadmissible(r.qManager, cqNames)
}
```

[`ClusterQueuesForResources`](https://github.com/kubernetes-sigs/kueue/blob/2ebbf83c63e4d050e30ff7f3de1b79f785b615af/pkg/cache/scheduler/cache.go) intentionally selects ClusterQueues covering **any** supplied resource. The problem is that this caller supplies the union for every configured driver, even when the event concerns only one.

[`NotifyRetryInadmissible`](https://github.com/kubernetes-sigs/kueue/blob/2ebbf83c63e4d050e30ff7f3de1b79f785b615af/pkg/cache/queue/inadmissible_workloads.go) can move eligible inadmissible Workloads back into the active scheduling heap, so the redundant notification may cause actual rescheduling work rather than only a no-op callback.

**Why is this needed?**

### Minimal two-driver scenario

Configure two independent DRA mappings:

| ResourceSlice driver | Logical quota resource | ClusterQueue |
| --- | --- | --- |
| `driver-a.example.com` | `example.com/a-capacity` | `cq-a` |
| `driver-b.example.com` | `example.com/b-capacity` | `cq-b` |

Place eligible inadmissible Workloads in both ClusterQueues, with namespace selectors and queue state allowing retries.

1. Create/update a `ResourceSlice` belonging to **driver A only**.
2. Follow the `ResourceSliceReconciler` notification targets or test against the inadmissible requeuer.

**Actual behavior inferred from the current implementation:** Both `cq-a` and `cq-b` can receive notifications because `Reconcile` queries `{example.com/a-capacity, example.com/b-capacity}`.

**Expected behavior:** The quota-mapping-related retry should include `cq-a` but not `cq-b`, provided the resources are disjoint and no independent DRA-feasibility change requires `cq-b` to be retried. A ClusterQueue covering both resources should still be included.

### Suggested approach

Preserve the relation between each configured driver and the logical quota resources it can affect, e.g. conceptually:

```go
// Design sketch only; not a tested patch.
quotaResourcesByDriver map[string]sets.Set[corev1.ResourceName]
```

Resolve the affected driver's resource set when scheduling mapping-related retries instead of unconditionally passing the union across drivers.

**Important lifecycle constraint:** The current reconciliation request is keyed by `ResourceSlice` **name**, not driver. Simply looking up the object during `Reconcile` is insufficient when it has been deleted. A solution must handle create/update/delete, informer coalescing, and delete/recreate races without silently dropping a required notification. A conservative fallback is preferable where the affected driver cannot safely be determined.

Please keep **DRA device-feasibility** notification requirements separate: events involving unmapped drivers may still require re-evaluation under that mechanism.

### Suggested regression coverage

- [ ] A driver-A slice event does not trigger the mapping-related retry for a disjoint driver-B-only ClusterQueue.
- [ ] A driver-B event retries the driver-B ClusterQueue normally.
- [ ] Multiple drivers mapping to one logical resource correctly notify ClusterQueues covering that shared resource.
- [ ] A ClusterQueue covering resources from both drivers is included for either relevant event.
- [ ] An unconfigured driver does not trigger unrelated mapping-based retries.
- [ ] Deletion of a configured driver's ResourceSlice preserves the necessary notification.
- [ ] Rapid update and delete/recreate sequences do not lose required retries.
- [ ] Changes needed by DRA device feasibility still trigger the appropriate pending Workload retries.

### Related work / duplicate distinction

- **PR [#13639](https://github.com/kubernetes-sigs/kueue/pull/13639)** narrowed ResourceSlice notifications from *all ClusterQueues* to queues covering *any DRA-mapped resource*. This request proposes the next, distinct narrowing: from *all configured drivers' resources* to *the changed driver's resources*.
- **Issue [#15769](https://github.com/kubernetes-sigs/kueue/issues/15769)** concerns ensuring that **DRA feasibility** re-evaluation can react to ResourceSlice changes, even for drivers without configured `deviceClassMappings`. The proposed mapping-aware filtering must not regress that behavior.
