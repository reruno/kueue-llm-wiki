## Description

**What would you like to be added**:

Support zero-downtime upgrades for elastic jobs when the per-Pod resource requests of an existing PodSet change while the PodSet name remains stable.

For an admitted workload slice, changing a PodSet's resource requests should create a replacement slice that represents the new resource shape. Kueue should keep the new Pods scheduling-gated until the replacement is admitted, account for both the running old Pods and the replacement Pods during the handover, and retire the old slice only after ownership has transferred safely.

The initial motivating case is a RayService zero-downtime upgrade where, for example, a worker PodSet changes from 1 CPU to 2 CPUs without changing its replica count. The behavior should be defined in the generic workload-slicing machinery so integrations do not need to treat a resource-only update as a replica-count change.

This issue is limited to resource updates for an existing PodSet identity. Adding or removing PodSets can be handled separately because that also changes the workload structure and PodSet-to-admission mapping.

**Why is this needed**:

`EnsureWorkloadSlices` currently derives compatibility and change detection from PodSet names and counts. When a PodSet keeps the same name and count but changes its resource requests, the existing slice is returned unchanged. Its old resource requests remain in quota accounting, no replacement admission is performed for the new shape, and an integration performing a zero-downtime rollout cannot safely release the new Pods.

#14374 tracks the underlying correctness problem that workload-slice paths do not compare PodSet templates. Rejecting a mismatched template or falling back to the non-slicing path prevents stale accounting, but it does not provide a zero-downtime upgrade path for an intentional resource change. This enhancement tracks that handover behavior.

RayService zero-downtime accounting is also being developed in #11264 and is a concrete consumer of this capability.

**Completion requirements**:

- Workload slicing detects changes to the resource requests represented by a stable PodSet name, even when its count is unchanged.
- An intentional resource update on an admitted elastic workload creates a replacement slice with the new resource requests instead of reusing or mutating the admitted slice in place.
- Quota accounting covers both the old running Pods and the new replacement Pods for the duration of the zero-downtime handover.
- Replacement Pods remain scheduling-gated until the replacement slice is admitted.
- The predecessor slice is finished only after the replacement can take ownership safely.
- Unit and integration coverage includes a resource-only update with an unchanged PodSet count and verifies that quota is not understated.
- The interaction with resource changes combined with replica scale-up or scale-down is defined and tested.
