## Description

**What happened**:

The RayService validating webhook accepts zero-downtime upgrade updates that change the shape or per-Pod resource requests of the RayService's PodSets. In particular, it allows:

- adding a worker group, which adds a PodSet;
- removing a worker group, which removes a PodSet; and
- changing quota-relevant resource requests for the head or an existing worker-group PodSet.

Elastic workload slicing currently supports changes to `PodSet.Count`, but its compatibility path does not provide a safe zero-downtime handover for these structural or resource-shape changes. Accepting such an update can cause stale quota accounting, fallback to disruptive non-slicing reconciliation, a mismatch between the replacement Workload and the RayService, or replacement Pods remaining scheduling-gated.

**What you expected to happen**:

Until workload slicing supports these transitions, the RayService validating webhook should reject them when zero-downtime upgrades are enabled.

For an update where the effective upgrade strategy is not `None`, validation should compare the old and new PodSets and reject:

- changes to the set of PodSet names; and
- changes to the quota-relevant per-Pod resource requests of a PodSet with the same name.

Changing only a PodSet's replica count should remain allowed. Updates using upgrade strategy `None` should not be subject to this zero-downtime-specific restriction. Validation errors should identify the corresponding `spec.rayClusterConfig` field or worker group clearly.

**How to reproduce it (as minimally and precisely as possible)**:

1. Enable elastic workload slicing and create an admitted RayService using the workload-slicing annotation and the default zero-downtime upgrade strategy.
2. Update the RayService using any one of the following changes:
   - add a worker group;
   - remove a worker group; or
   - change a container CPU request from `1` to `2` without changing its replica count.
3. Observe that the validating webhook accepts the update even though workload slicing cannot safely represent the transition as a count-only replacement.

**Anything else we need to know?**:

#17586 tracks native zero-downtime support for updating the resources of an existing PodSet. The resource-update validation proposed here can be relaxed when that support is implemented.

#11264 is adding RayService zero-downtime accounting based on workload slicing and is the motivating integration.

Suggested coverage:

- webhook unit tests for added, removed, reordered, resource-modified, and count-only-changed PodSets;
- default and explicitly configured zero-downtime upgrade strategies;
- upgrade strategy `None`; and
- an API-server integration test confirming rejected updates return an invalid/forbidden response.
