## Description

**What happened**:

A JobSet that uses `spec.volumeClaimPolicies` never gets a ProvisioningRequest when its ClusterQueue has a ProvisioningRequest admission check. The admission check stays `Pending` with:

```
Error creating PodTemplate "ppt-jobset-<name>-<hash>-<check>-1-<replicatedJob>": PodTemplate "..." is invalid: template.spec.containers[0].volumeMounts[0].name: Not found: "state"
```

With `volumeClaimPolicies`, the container only declares the `volumeMount`; the JobSet controller adds the matching `volume` (PVC `<claim>-<jobset>`) when it creates the child Job (`addVolumes` in `pkg/controllers/volume_claim_policy.go` in JobSet). The JobSet webhook also rejects a ReplicatedJob that declares a volume with that name, so it can't be added to the spec by hand.

Kueue's JobSet integration builds the PodSets from the ReplicatedJob templates, so the PodSet has the mount but not the volume. `buildPodTemplate` in `pkg/controller/admissionchecks/provisioning/controller.go` copies the PodSet template as is, and the API server rejects the PodTemplate.

**What you expected to happen**:

The ProvisioningRequest is created, and the workload is admitted once the capacity is provisioned.

**How to reproduce it (as minimally and precisely as possible)**:

1. A ClusterQueue with an AdmissionCheck for `kueue.x-k8s.io/provisioning-request` (any `provisioningClassName`; the PodTemplate is rejected before the provisioner is involved).
2. Submit:
   ```yaml
   apiVersion: jobset.x-k8s.io/v1alpha2
   kind: JobSet
   metadata:
     name: provreq-vcp
     labels:
       kueue.x-k8s.io/queue-name: <local-queue>
   spec:
     volumeClaimPolicies:
     - templates:
       - metadata:
           name: state
         spec:
           accessModes: ["ReadWriteOnce"]
           resources:
             requests:
               storage: 10Gi
     replicatedJobs:
     - name: test
       replicas: 1
       template:
         spec:
           template:
             spec:
               restartPolicy: Never
               containers:
               - name: test
                 image: busybox:1.36
                 command: ["sleep", "60"]
                 resources:
                   requests: {nvidia.com/gpu: "1"}
                   limits: {nvidia.com/gpu: "1"}
                 volumeMounts:
                 - name: state
                   mountPath: /state
   ```
3. The workload's admission check shows the error above; no ProvisioningRequest is created.

**Anything else we need to know?**:

Possible fixes:
- In the JobSet integration, add the `volumeClaimPolicies` volumes to the PodSet templates the same way the JobSet controller adds them to the Job, so the PodSet matches the real pods.
- Or, in the provisioning controller, add a placeholder volume (e.g. `emptyDir`) for each volumeMount without a volume (or drop such mounts) when building the PodTemplate, since it is only used to size the capacity.

A mutating admission policy that adds an `emptyDir` for such mounts on PodTemplates labelled `kueue.x-k8s.io/managed=true` works around it.

Related (docs): on GKE, a queued-provisioning node pool with GPUs also carries the `nvidia.com/gpu` taint. That toleration is added to Pods automatically, but not to PodTemplates, so the ProvisioningRequest is reported as not schedulable in the node pool unless the ResourceFlavor tolerates `nvidia.com/gpu`. The ProvisioningRequest/DWS examples could mention this.

**Environment**:
- Kubernetes version: v1.35 (GKE)
- Kueue version: v0.20.2 (same code path on `main`)
- JobSet version: v0.13.0
- Cloud provider or hardware configuration: GKE, `queued-provisioning.gke.io`
- Others: also reproduced with MultiKueue, where the admission check runs on the worker cluster

The PodSet copies the ReplicatedJob template as is, so it never gets the volumes that the JobSet controller adds from `volumeClaimPolicies`.

Of the two fixes you list, I lean towards the provisioning-controller side: when building the PodTemplate, add a placeholder volume for each `volumeMount` that has no matching volume, since the template is only used to size capacity.
