## Description

<!-- Please only use this template for submitting enhancement requests -->

**What would you like to be added**:

A Fair Sharing configuration option that keeps share-based admission ordering, but limits cross-ClusterQueue preemption to reclaiming nominal quota, at both the ClusterQueue and the Cohort level.

In other words:

- Admission ordering: unchanged. Heads are ordered by dominant resource share and weights.
- Preemption: allowed only when the preemptor's ClusterQueue or Cohort is within its nominal quota and reclaims from borrowers (scenario S1 in [KEP-1714](https://github.com/kubernetes-sigs/kueue/blob/504213adc39d83f709f0c45420ff4830f90c86a7/keps/1714-fair-sharing/README.md?plain=1#L261-L275)). There is no share-based preemption between ClusterQueues that are both borrowing (scenario S2).

**Why is this needed**:

Workload churn in our environment is high. Borrowed capacity frees up quickly, so share-based admission ordering is enough to converge on fairness over time. Enforcing fairness strictly by preempting running workloads mostly adds evictions and wasted work. We still need nominal quota to be guaranteed through reclaim.

Today this combination can't be configured:

- Enabling Fair Sharing always enables share-based preemption between borrowing ClusterQueues.
preemptionStrategies is required and has no "none" value ([PR #7948](https://github.com/kubernetes-sigs/kueue/pull/7948)).
- `reclaimWithinCohort: Never` disables reclaim as well.

Related Issues:

- https://github.com/kubernetes-sigs/kueue/issues/17612
  - I'm essentially proposing supporting a `within-nominal` only preemption mode. 
- https://github.com/kubernetes-sigs/kueue/issues/9466
  - Cohort-nominal should be supported in addition to cq-nominal preemptions.

### Comment by [@pajakd](https://github.com/pajakd) — 2026-10-23T07:50:56Z

Yeah, I definitely think it makes sense. Looking at kep https://github.com/kubernetes-sigs/kueue/tree/main/keps/1714-fair-sharing#choosing-clusterqueues-to-preempt-from we mention there scenarios S1 and S2. In the current implementation we have two strategies that cover the S2 "general preemption": `LessThanOrEqualToFinalShare` implements Rule S2-a and `LessThanInitialShare` implements rule S2-b" But we don't allow to only have the S1 ("only reclaim").

We could consider adding a third strategy ("ReclaimOnly" or sth). 

In general I don't think its risky because we are limiting the number of preemptions so it should not introduce any infinite preemption loops (and the preemptor will be protected by the nominal quota).

But, one tricky place that I see is in the hierarchical case as always  :-).  Since in the (unchanged) admission part the workloads are ordered based on the DRS at the AlmostLCA, we should do the same for the preemption here. So, the S1 scenario between preemptor and candidate should be evaluated at the AlmostLCA between them. 

In a case like this
```
root
├── cohort-c   (no quota)
│   ├── a      10 GPU   P: 10 (pending)
│   └── s       0 GPU   S: 4  (admitted)
└── t           0 GPU   T: 6  (admitted) 
```

P should be able to reclaim the nominal quota. But if we would consider candidate for preemption `t` before `s`, we would not see that this is just a reclaim. An idea to deal with this would be to order the candidates starting from the closest to the preemptor CQ and update the usage after considering each candidate.
