## Description

**What happened**:

During ConcurrentAdmission teardown, a ClusterQueue can retain its `resource-in-use` finalizer after its scheduler cache is empty. A deleted LocalQueue prevents the Workload deletion notification from identifying the ClusterQueue.

**What you expected to happen**:

ClusterQueue deletion completes after its cached Workloads are removed, even if the LocalQueue was deleted first.

**How to reproduce it (as minimally and precisely as possible)**:

The reported race requires this sequence:
1. The scheduler assumes a recreated Variant in its cache before admission reaches the API.
2. The LocalQueue is deleted.
3. The Variant is deleted, and its deletion handler removes the cached assumption.
4. The notification cannot identify the ClusterQueue: the API Workload has no admission, and the LocalQueue is gone.
5. The ClusterQueue retains its finalizer despite its empty cache.

**Anything else we need to know?**:

Follow-up to https://github.com/kubernetes-sigs/kueue/pull/17629. Deleting the ClusterQueue first mitigates the test flake but does not fix the production race.

Required changes:
- In `pkg/controller/core/workload_controller.go`, preserve the removed cached Workload in `WorkloadReconciler.handleDelete` and use its admission information to notify ClusterQueue watchers. Extend the cache deletion API if needed.
- Update teardown in `test/integration/singlecluster/controller/concurrentadmission/concurrent_admission_test.go` to delete the ClusterQueue before the LocalQueue.
- Add regression coverage for an assumed Variant with no API admission whose LocalQueue is already deleted. Verify that the ClusterQueue receives a cleanup notification and deletion completes.

Details and proposed approach: https://github.com/kubernetes-sigs/kueue/pull/17629#issuecomment-6345910753.
