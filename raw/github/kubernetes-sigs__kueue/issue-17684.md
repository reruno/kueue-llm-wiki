## Description

Please document the intended end-to-end setup for shared license quotas with standard Kubernetes Jobs.
We have several types of licenses whose usage we need to track and limit independently of the nodes or ResourceFlavors on which the workloads run. A Job may require zero, one, or multiple license types.
We want license usage to be accounted for independently of the per-flavor compute quotas, with a shared license pool across all compute ResourceFlavors. For example, a limit of 10 render licenses should allow at most 10 admitted Jobs requiring one render license each, regardless of their compute flavor.
With the standard Job integration, it appears that we need to declare each license requirement as an extended resource request/limit in the Job’s Pod template. This also makes the license a resource requirement for the actual Pods. Since our nodes do not advertise license resources, those Pods would remain unschedulable.
Is there a supported way to declare these requirements only on the Kueue Workload, without adding them to the Job’s Pod template or propagating them to the resulting Pods as resource requests or node selectors?
An end-to-end example would help clarify:
- How Jobs declare their license requirements.
- How Kueue enforces shared, flavor-independent license quotas alongside per-flavor CPU and memory quotas.
- How the resulting Pods remain schedulable without advertising license resources on individual nodes.
- When license quota is reserved and released.
- Whether this requires a custom integration or AdmissionCheck controller.
