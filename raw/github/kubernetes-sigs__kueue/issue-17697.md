## Description

**What happened**:

DQO discovery adds up capacity from all CapacityProviders per flavor. Each provider can report up to 64 resources for a flavor, but the sum can go over 64. `status.effectiveCapacity.flavors[].resources` only allows 64, so the status update is rejected:

```
DynamicQuotaOrchestrator.kueue.x-k8s.io "res-limit-dqo" is invalid: status.effectiveCapacity.flavors[0].resources: Invalid value: resource capacity must have at most 64 entries
```

The reconciler keeps retrying, and the DQO keeps the old `effectiveCapacity` with `EffectiveCapacityComputed=True`. So it looks fine, but the capacity is stale.

**What you expected to happen**:

Same as the flavor limit in #16356 / #16767: `EffectiveCapacityComputed=False` with reason `AggregationFailed`, and `status.effectiveCapacity` cleared.

**How to reproduce it (as minimally and precisely as possible)**:

1. CapacityProvider A orchestrates flavor `f1` and reports 64 resources (`example.com/r-00` to `example.com/r-63`).
2. CapacityProvider B orchestrates `f1` and reports `example.com/r-00`. A DQO using both computes fine with 64 resources.
3. Change B to report `example.com/extra` instead. Now `f1` has 65 resources and the status update fails as above.

**Anything else we need to know?**:

The KEP mentions `TooManyResourcesInAggregatedCapacity` for this case. I'd use `AggregationFailed` to match #16767, but can switch if you prefer the KEP name. I have a fix ready and will open a PR.

**Environment**:
- Kueue version: main (5dae9b322)
- Reproduced with an envtest integration test
