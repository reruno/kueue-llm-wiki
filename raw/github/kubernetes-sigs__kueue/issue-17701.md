## Description

**What would you like to be added**:

An opt-in way for MultiKueue to avoid duplicate scale-ups for the same workload.

When a workload is nominated to several workers, each worker creates its own ProvisioningRequest for it. With a class that scales up as soon as the request is accepted, such as `best-effort-atomic-scale-up`, every one of these duplicate requests starts adding nodes, even though only one worker will run the workload.

With the option enabled, only one worker at a time would create a ProvisioningRequest for the workload. If that worker's scale-up fails, the next worker would get a turn. Workers that already have free capacity would still compete as they do today, so a workload that fits somewhere right away isn't delayed.

It should be opt-in because racing helps with queued classes such as Dynamic Workload Scheduler. There, requests wait until capacity is available, and the duplicates are cancelled before any nodes exist. Those setups should keep today's behaviour.

The mechanism is open. Mainly looking for opinions on whether this is worth solving.

**Why is this needed**:

MultiKueue keeps every worker's copy until one copy is Admitted, and each copy's ProvisioningRequest acts on its own. So every nominated worker scales up, one runs the workload, and the rest sit idle until scale-down removes them.

Roughly, each losing worker wastes a node boot plus about 14 minutes of idle time, and holds pool room and quota in the meantime. With 4 workers and an 8-node job, that's about 12 node-hours per cold start.

Today there's no way to offer a workload to all workers while letting only one of them scale up at a time. A custom External dispatcher, or Incremental with `stepSize: 1`, can limit scale-ups, but only by offering the workload to fewer workers. That gives up the race on capacity that already exists.

Related: KEP-8303 solves the same kind of problem for preemption, by letting one worker preempt at a time. kubernetes/autoscaler#10430 would make `Provisioned=True` mean the nodes are Ready, so a failed scale-up is noticed sooner.
