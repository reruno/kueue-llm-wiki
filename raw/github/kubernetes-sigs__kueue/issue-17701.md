## Description

**What would you like to be added**:

When a workload is nominated to several MultiKueue workers and its ProvisioningRequest class starts a scale-up as soon as the request is accepted (such as `best-effort-atomic-scale-up`), we'd like this behaviour:

- Only one worker at a time starts a scale-up for the workload.
- Workers that can admit it on existing capacity still compete, as today. The first to admit wins.
- If that worker's scale-up fails, another worker may start one.
- Queued classes (for example Dynamic Workload Scheduler) behave as today.
- It is opt-in, and it works with the built-in dispatchers. No custom dispatcher is needed.

Exact mechanism is undecided, just wanted opinion if the issue is worth solving.

**Why is this needed**:

Take a MultiKueue setup with several worker clusters (for example in different zones or regions), each with autoscaled GPU node pools behind `best-effort-atomic-scale-up`. Every nominated worker keeps its copy until one copy is Admitted. With this class, each copy's ProvisioningRequest starts a scale-up within seconds. So every worker starts nodes, one runs the workload, and the rest sit idle until scale-down.

As a rough estimate, each losing worker costs the boot time (5 to 16 min) plus about 14 min idle. With 4 workers and an 8-node job, that is about 12 node-hours per cold start. Those nodes also hold pool room and quota in workers that never run the workload.

What exists today falls short:

- A custom External dispatcher can nominate one worker. But dispatch stops while it is down or being upgraded, it can't run alongside the built-in dispatcher, and it needs the field-manager workaround for `nominatedClusterNames` (#8607). When it can't score capacity, the natural fallback is to nominate every worker, which brings the problem back.
- Incremental with `stepSize: 1` offers the workload to one worker per 5-minute round. It gives up the race on existing capacity, and its fixed clock adds another worker during a normal boot.
- Cancelling the scale-up when the request is deleted doesn't help. Once the provider is creating nodes, they come anyway.

How quickly a failed attempt is noticed depends on the provisioning signal. Today `Provisioned=True` is set when the provider accepts the scale-up, which can be long before nodes exist. kubernetes/autoscaler#10430 (`waitForNodesReady`) would make that signal reliable.

Related:

- [KEP-8303](https://github.com/kubernetes-sigs/kueue/tree/main/keps/8303-multikueue-orchestrated-preemption) (MultiKueue orchestrated preemption) does the same for preemption: one worker preempts at a time, and another gets a turn after a timeout. Its non-goals leave other MultiKueue inefficiencies out of scope.
- [KEP-8691](https://github.com/kubernetes-sigs/kueue/tree/main/keps/8691-concurrent-admission) (Concurrent Admission) reuses the KEP-8303 gates.
- [KEP-693](https://github.com/kubernetes-sigs/kueue/tree/main/keps/693-multikueue) (MultiKueue) defines the dispatcher API and `nominatedClusterNames`.
- [KEP-9270](https://github.com/kubernetes-sigs/kueue/tree/main/keps/9270-multikueue-incremental-step-size) adds `stepSize` to the Incremental dispatcher.
- #8585 / #8592: copies are kept until one is Admitted, so workers can look for capacity in parallel.
