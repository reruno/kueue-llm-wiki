## Description

**What would you like to be cleaned**:

The e2e setup in `hack/testing/e2e-test.sh` / `hack/testing/e2e-common.sh` does not log how long each step takes, so CI logs cannot tell where e2e setup time goes.

In CI, `make-timed-shell.sh` times each Makefile recipe line, so the whole `e2e-test.sh` invocation shows up as a single entry. Example from `pull-kueue-test-e2e-tas-baseline-main` on #17059 ([build 2112917289836744704](https://prow.k8s.io/view/gs/kubernetes-ci-logs/pr-logs/pull/kubernetes-sigs_kueue/17059/pull-kueue-test-e2e-tas-baseline-main/2112917289836744704)):

- `make-timing: ... duration=340s command=... ./hack/testing/e2e-test.sh`
- Ginkgo: `Ran 19 of 19 Specs in 161.602 seconds`

That leaves ~178s with no breakdown. The time is spent somewhere in kind node image build, cluster creation, image pulls, `kind_load` (image load plus every `install_*` operator) and `kueue_deploy` (apply plus waiting for the controller/webhook), but nothing in the log says which. `e2e-common.sh` has no timing today.

**Why is this needed**:

The setup cost is paid by every e2e presubmit. On main there are ~40 e2e presubmits, and each ran ~180 times in a recent 48h window. Without per-step numbers, it is hard to decide or justify setup optimizations (e.g. installing operators in parallel, applying manifests first and waiting once, trimming image loads).

**Proposal**:

1. Add two small helpers to `e2e-common.sh`:
   - `e2e_timed <label> <command> [args...]` runs the command unchanged and, when it succeeds, prints one line:
     `e2e-timing: step=<label> status=0 duration=<n>s`
   - `e2e_timed_log_unfinished <rc>`, called first in the `cleanup` EXIT trap of `e2e-test.sh`, prints the same line with `status=<rc>` for the step that was still running when the script exited, so a step that fails or times out still shows how long it ran.
2. Wrap the top-level steps in `e2e-test.sh`: `build_kind_node_image`, cluster creation (backgrounded), `prepare_docker_images`, the wait for the cluster, `kueue_deploy`, and the ginkgo run.
3. Wrap the inner steps in the shared functions, so every script that uses them benefits:
   - in `kind_load`: `cluster_kind_load` and each `install_*`, labelled `<cluster>/<step>` so the parallel MultiKueue clusters can be told apart;
   - in `cluster_kueue_deploy`: `wait_for_kueue_controller_operator`.
4. Add cases to `hack/testing/e2e-common_test.sh`.

Behaviour notes:
- Logging only; no change to what the scripts do or to their exit status.
- The helper must be called as a plain command, not inside `if` / `&&` / `||`, because bash disables `errexit` for the whole function in those contexts and a failing multi-command step would keep running.
- With `errexit` on, a failing step exits before its own timing line, and the EXIT trap logs it instead. The trap only sees steps in the main shell of `e2e-test.sh`: a failed cluster creation (background job) is logged as the wait for the cluster, a failed `kueue_wait_ready` (subshell) as `kueue_deploy`, and the MultiKueue and KueueViz scripts log successful steps only.
- The tests cover the success line and the failure line from the trap.

**Out of scope**:

Any actual setup optimization; that would be a follow-up once the numbers are available.

I have a draft implementation and am happy to open the PR.
