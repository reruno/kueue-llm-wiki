**What would you like to be added**:

One of the major selling points of Run.AI / KAI scheduler is the use of fractions for GPU scheduling.

This is different from MIG and Run.AI provides support for a larger range of GPUs than MIG can provide.

With the OSS offering of Run.AI, it could be possible to offer fractional gpu scheduling with OSS software.

https://github.com/kai-scheduler/gpu-fractioning#gpu-fractioning-operator

**Why is this needed**:

Provide fractional gpu scheduling where MIG is not a great fit.

### Comment by [@sohankunkerkar](https://github.com/sohankunkerkar) — 2026-10-27T04:52:41Z

Thanks for raising this, @kannon92. I think Kueue can cover fractional GPUs in a generic way, by charging quota from ResourceClaims rather than from vendor annotations.

The path I'd push is DRA consumable capacity, where a claim asks for part of a shared GPU. In envtest, five 20Gi claims on one 80Gi GPU with an 80Gi quota admitted four. With TAS, the device check (tested in #17642) also skips a node whose shared GPU doesn't have enough capacity left. HAMi's extended resources already work today with a resource transformation.

It's not end to end yet, though. NVIDIA's ConsumableShares is Alpha, and there's an open report that two memory-only claims can't share one GPU (kubernetes-sigs/dra-driver-nvidia-gpu#1572). Capacity there is accounting only. kubernetes-sigs/dra-driver-nvidia-gpu#1283 tracks isolation.

KAI's fractions are annotations only, so Kueue doesn't see them. It would be great if gpu-fractioning could take the share from a DRA allocation instead. On our side, consumable capacity is going to Beta (#17636, #17642). Counting how many slices fit per node is part of the device feasibility Beta. WDYT?
