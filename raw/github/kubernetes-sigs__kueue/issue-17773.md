# Successfully completed Indexed Job pod on a `NoSchedule`-tainted node triggers TAS failed-node replacement and suspends remaining workers

**What happened**:

We observed an Indexed Kubernetes Job in which a worker completed successfully on a node that had previously received an untolerated maintenance `NoSchedule` taint. The node remained healthy and the taint was added by our internal maintenance automation so that the node could be refreshed after it became idle.

When the worker completed, Kueue treated its node as unhealthy through `TASReplaceNodeOnNodeTaints`. Kueue moved the Workload from admitted to pending and suspended the entire Job. The Kubernetes Job controller consequently deleted 13 other workers that were still running successfully on other nodes.

There was no unfinished worker left on the tainted node. The taint itself did not evict any pod.

Kueue patched the Job with `kueue.x-k8s.io/stopping: "true"` and `spec.suspend: true`. Kubernetes audit logs attribute the subsequent deletion of the remaining active pods to `system:serviceaccount:kube-system:job-controller` with reason `SuccessfulDelete`.

During attempted readmission, Kueue calculated a remaining PodSet count of 13 while retaining the original slice size of 16. Kueue v0.17.8 produced an empty topology assignment and admission was rejected with:

```text
status.admission.podSetAssignments[0].topologyAssignment.slices: Required value
```

The readmission error appears related to `TASPartialSlices`, but the primary issue reported here is why the successful completion triggered failed-node replacement and workload-wide suspension in the first place.

**What you expected to happen**:

Once the worker on the tainted node completed successfully, no replacement should have been required for that completed index. We expected Kueue to:

1. Account for the worker index as successfully completed.
2. Remove its resource and topology usage from the outstanding workload.
3. Ignore the node for failed-node replacement because no unfinished pod remained assigned to it.
4. Leave the other 13 active workers running on their existing nodes.
5. Allow the independent maintenance controller to refresh the now-idle node.

Conceptually, we expected failed-node replacement to require an unfinished pod:

```text
untolerated scheduling taint
AND pod assigned to the node has stopped running
AND that pod/index has not completed successfully
```

**How to reproduce it (as minimally and precisely as possible)**:

We have not yet reduced this to a standalone reproduction, but the observed setup and sequence were:

1. Enable Topology-Aware Scheduling and `TASReplaceNodeOnNodeTaints`.
2. Create an Indexed Job with:

   ```yaml
   spec:
     parallelism: 32
     completions: 32
     completionMode: Indexed
     backoffLimit: 0
     template:
       metadata:
         annotations:
           kueue.x-k8s.io/podset-required-topology: topology.k8s.aws/zone-id
           kueue.x-k8s.io/podset-slice-required-topology: nvidia.com/gpu.clique
           kueue.x-k8s.io/podset-slice-size: "16"
   ```

3. Allow all 32 workers to start. Let worker `W17` run on node `N17`.
4. While `W17` is running and `N17` remains healthy, apply an untolerated maintenance taint:

   ```text
   internal.example.com/mid-term-maintenance=true:NoSchedule
   ```

5. Allow `W17` to exit successfully with `exitCode: 0` and reason `Completed`.
6. Observe whether Kueue adds `N17` to `status.unhealthyNodes`, suspends the Job, and causes the Job controller to delete workers running on other nodes.

Observed timeline, in UTC:

- **T1 — 2026-10-16 16:09:35:** `W17` starts successfully on `N17`. All 32 workers are active.
- **T2 — 2026-10-18 18:21:46.072:** Maintenance automation adds the untolerated `NoSchedule` taint to `N17`. The node remains healthy and `W17` continues running.
- **T3 — 2026-10-19 14:12:42:** Approximately 19h 50m 55.9s later, `W17` exits successfully with `exitCode: 0` and reason `Completed`.
- **T4 — 2026-10-19 14:12:49.215:** Kueue records `N17` in `unhealthyNodes`. By this point, 19 of 32 indexed workers have completed and 13 remain active on other nodes.
- **T5 — 2026-10-19 14:12:49.489:** Kueue patches the Job with `spec.suspend: true` and `kueue.x-k8s.io/stopping: "true"`.
- **T6 — 2026-10-19 14:12:49.541:** The Workload is observed transitioning from admitted to pending.
- **T7:** The Job controller deletes the 13 still-running workers, whose nodes had not failed.
- **T8:** Kueue attempts to readmit the 13 unfinished indices, but the non-divisible count and slice size result in an empty topology assignment on v0.17.8.

**Anything else we need to know?**:

At T2, Kueue did not treat the node as unhealthy while its assigned pod was running. It reacted only when that pod terminated successfully nearly 20 hours later.

Our node-maintenance controller is independent of Kueue. It uses the taint to prevent new work from reaching the node, waits for the node to become idle, and then refreshes it. `TASReplaceNodeOnNodeTaints` does not perform that refresh.

Questions:

1. Is this expected for `TASReplaceNodeOnNodeTaints` with successfully completed Indexed Job workers?
2. Should Kueue exclude completed indices when deciding whether a tainted node requires replacement?
3. Is there an existing issue or fix?
4. Is there a safe configuration that preserves replacement for genuinely failed active workers while ignoring nodes whose workers completed successfully?
5. Would v0.19.x or v0.20.x change T3–T7 independently of the `TASPartialSlices` fix for T8?

The Job used Dynamic Resource Allocation resource claims. We do not currently know whether DRA is relevant.

### Comment by [@yuluo-yx](https://github.com/yuluo-yx) — 2026-10-27T02:02:26Z

This looks like a real bug in the interaction between `TASReplaceNodeOnNodeTaints` and Indexed Jobs.

With `TASReplaceNodeOnPodTermination` enabled, Kueue waits until no running Pod remains on the tainted node. A successfully completed Indexed Pod satisfies that condition, but the existing topology assignment still contains the node. Kueue therefore marks the node unhealthy and suspends the whole Workload, even though no unfinished index remains there.

The `TASPartialSlices` error is a separate follow-up issue. v0.17.8 cannot handle the remaining count being smaller than the configured slice size; newer v0.20 releases add partial-slice support. The newer replacement fixes may address the re-admission failure, but they do not appear to prevent the initial false node replacement.

For now, the only reliable workaround is to disable `TASReplaceNodeOnNodeTaints` or avoid applying an untolerated `NoSchedule` taint while a partially completed Indexed TAS Job is running. The intended fix should exclude successfully completed indexes from failed-node detection while retaining replacement for failed or unfinished indexes.
