## Description


**What happened**:

When Kueue replaces a failed node of a TAS Workload, the replacement fails if another node of the topology assignment is cordoned, even though free nodes exist and the Pods on the cordoned node are still running.

Cordoned nodes are removed from the TAS snapshot. Before replacing a node, `findReplacementAssignment` checks that every other node of the assignment is in the snapshot (`isTopologyAssignmentStaleIgnoringNodes`), so the cordoned node makes the assignment look stale.

**What you expected to happen**:

The drained node is replaced on a free node, and the Pods on the other nodes keep running.

**How to reproduce it (as minimally and precisely as possible)**:

```shell
# 1. Create a Job with 3 Pods
$ cat <<EOF | kubectl create -f -
apiVersion: batch/v1
kind: Job
metadata:
  name: roll
  labels:
    kueue.x-k8s.io/queue-name: lq
spec:
  parallelism: 3
  completions: 3
  suspend: true
  template:
    spec:
      restartPolicy: Never
      containers:
      - name: c
        image: busybox:1.36
        command: ["sleep", "3600"]
        resources:
          requests:
            cpu: 10m
            example.com/slot: "1"
          limits:
            example.com/slot: "1"
EOF

# 2. Cordon worker2. Its Pod keeps running and the node is not reported unhealthy.
$ kubectl cordon kueue-h1-repro-worker2

# 3. Drain worker (wait ~40s). worker4 is free.
$ kubectl drain kueue-h1-repro-worker --ignore-daemonsets

# 4. Check the Workload
# OUTPUT: the Workload was evicted and cannot be admitted again while worker and worker2 are cordoned
$ kubectl get events --field-selector involvedObject.name=job-roll-6edf6 -o custom-columns=REASON:.reason,MSG:.message

EvictedDueToNodeFailures   Workload was evicted as there was no replacement for unhealthy node(s): kueue-h1-repro-worker
TopologyPlacementFailed    couldn't assign flavors to pod set main: topology "host" allows to fit only 2 out of 3 pod(s)

```

### Comment by [@nsega](https://github.com/nsega) — 2026-10-29T07:14:48Z

I looked into this error. I found the root cause is broader than the gate-off stale check, and enabling `TASReplaceMultipleFailedNodes` doesn't fix it. I'd like to agree on a fix direction before opening a PR.

**Root cause.** With `SchedulerLibraryIntegration` off (the default), a cordoned or NotReady node is dropped from the TAS snapshot, but the node controller still treats it as healthy while its pods run, so it never enters `unhealthyNodes`. Replacing another failed node then trips over the missing one.

**Where it breaks** (I could repro unit-level on main at  ce0f8786f):

| Case | `TASReplaceMultipleFailedNodes` off | on |
|---|---|---|
| This issue: another assigned node is cordoned | fails | works |
| Required topology, all surviving nodes cordoned | fails | fails |
| `TASPartialSlices` (on by default), one cordoned node anywhere | fails | fails |
| Elastic TAS scale-up | fresh placement | fresh placement |

A NotReady node with running pods behaves like a cordoned one until the not-ready toleration expires. With `TASFailedNodeReplacementFailFast` (on by default), these failures evict the whole workload. With `SchedulerLibraryIntegration` on, every case works for hostname-level topologies.

**Possible Options to Address This Issue**
1. **Minimal:** stop gating the "ignore nodes missing from the snapshot" step in `replacementIgnoreNodes`. Fixes only this issue, is easy to cherry-pick, and changes gate-off behavior that an existing test pins on purpose.
2. **Root cause:** keep nodes that still exist in the API in the snapshot tree with their topology labels, and exclude them only from new placements, as the `SchedulerLibraryIntegration` path already does. Fixes every case above, but is larger and probably main-only.
3. **Rely on `SchedulerLibraryIntegration`** and leave the default path as is. (Related: #15457 makes the tests pass with it enabled.)

Option 1 and option 2 could also be combined.  Option 1 on main with a cherry-pick to release-0.20, then option 2 on main. release-0.19 has an older stale check without `replacementIgnoreNodes`, so it would need a separate look.

Which would you prefer? I can split the gate-on cases into a separate issue, and I have unit-level reproductions ready to turn into tests. cc @mimowo


For your reference, this is code paths for each case
- This issue (gate off): `isTopologyAssignmentStaleIgnoringNodes` marks the assignment stale. Option 1 flips the test "multi-node replacement: missing tail still fails the stale check when gate is disabled".
- Required topology: `requiredReplacementDomain` returns `""`, then "required topology domain of the remaining assignment cannot be determined". An existing test expects this when all assigned nodes are *unhealthy*; here they are healthy, just cordoned.
- Slices: `sliceLevelUsages` skips the missing node, so `assignmentSliceAligned` fails with "cannot replace the node ... without splitting a PodSet slice" although no slice is split. `findIncompleteSliceDomain` can also pick an intact slice.
- Elastic: `handleElasticWorkload` treats the previous assignment as stale and falls back to a fresh placement.

(AI disclosure: The analysis and reproductions were AI-assisted; I reviewed them.)
