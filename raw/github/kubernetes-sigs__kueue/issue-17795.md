**What happened**:

When a workload $W_1$ is processed earlier in the scheduling cycle and triggers preemption of victim workload(s) $V$:
1. [`Scheduler.processEntry`](file:///usr/local/google/home/dpastuszka/gitrepos/kueue/pkg/scheduler/scheduler.go#L578-L579) records $V$ in `preemptedWorkloads` and calls [`bookUsage`](file:///usr/local/google/home/dpastuszka/gitrepos/kueue/pkg/scheduler/scheduler.go#L772-L784), which **adds $W_1$'s quota and TAS domain usage** to `snapshot` **without removing $V$** from `snapshot`.
2. When a subsequent workload $W_2$ runs [`entry.checkFits`](file:///usr/local/google/home/dpastuszka/gitrepos/kueue/pkg/scheduler/scheduler.go#L763-L766), [`fits`](file:///usr/local/google/home/dpastuszka/gitrepos/kueue/pkg/scheduler/scheduler.go#L947-L953) temporarily strips `preemptedWorkloads` usage via [`Snapshot.SimulateWorkloadUsageRemoval`](file:///usr/local/google/home/dpastuszka/gitrepos/kueue/pkg/cache/scheduler/snapshot.go#L181-L201).
3. However, if $W_2$ fails the TAS check (`FitsCheckNoTAS`) and enters `needsTASRecompute` in [`Scheduler.updateAssignmentIfNeeded`](file:///usr/local/google/home/dpastuszka/gitrepos/kueue/pkg/scheduler/scheduler.go#L869-L945) **without** calling [`simulateOtherPreemptions`](file:///usr/local/google/home/dpastuszka/gitrepos/kueue/pkg/scheduler/scheduler.go#L1010-L1018), [`Scheduler.getAssignments`](file:///usr/local/google/home/dpastuszka/gitrepos/kueue/pkg/scheduler/scheduler.go#L1560-L1634) runs against a corrupt snapshot state that simultaneously holds **both the incoming preemptor $W_1$'s booked usage and the evicted victim $V$'s usage, pods, and workload entry**.

**What you expected to happen**:

Before running `Scheduler.getAssignments` during `needsTASRecompute` (and throughout native TAS assignment and preemption target selection), workloads already in `preemptedWorkloads` for the current scheduling cycle should have their quota usage, TAS usage, `cq.Workloads` entries, and simulator pods excluded from the snapshot (via `simulateOtherPreemptions`), and workloads that fit only because of those in-flight preemptions should be handled as `DeferredFit` rather than re-preempting the same victims or over-preempting additional workloads.

This however introduces the issue, where another workload may now fit because of the Preemptions, where it should be considered a DeferredFit as it will fit only once the Preemptions happen. We need a fix that will ensure native planner accounts for this issue.

**How to reproduce it (as minimally and precisely as possible)**:

1. Enable `TopologyAwareScheduling` and `TASRecomputeAssignmentWithinSchedulingCycle` (with native planner, i.e., `SchedulerLibraryDeepIntegration=false`).
2. Set up a cohort (or ClusterQueue) with two nodes (`node-1` and `node-2`, 4 CPU each):
   - Victim workload `v1` (priority 1) is admitted on `node-2` using 4 CPU.
   - `node-1` has 4 CPU free.
3. Submit two pending workloads scheduled in the same cycle:
   - `w1` (priority 10, requires 4 CPU, needs quota preemption of `v1`): nominated on `node-1` with preemption target `v1`.
   - `w2` (priority 5, requires 4 CPU, has sufficient quota in its CQ): nominated on `node-1` with `Fit` mode.
4. During `processEntry`:
   - `w1` is processed first, adds `v1` to `preemptedWorkloads`, and books 4 CPU on `node-1`.
   - `w2` is processed next: `checkFits` returns `FitsCheckNoTAS` (since `node-1` is now taken by `w1`), triggering `needsTASRecompute`.
   - During `w2`'s recomputation, `v1` is still present on `node-2` in the snapshot, so `w2` cannot place on `node-2` without also targeting `v1` (which then fails with overlapping preemption targets) or failing placement altogether.

**Anything else we need to know?**:
