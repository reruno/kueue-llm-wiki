## Description

**What happened**:

A Deployment, StatefulSet or LeaderWorkerSet without the `kueue.x-k8s.io/queue-name` label is running (`readyReplicas > 0`). Someone then creates a LocalQueue named `default` in that namespace. After that, every update to the object is rejected, even an annotation change or an image bump:

```
admission webhook "vstatefulset.kb.io" denied the request: metadata.labels[kueue.x-k8s.io/queue-name]: Invalid value: "default": field is immutable
```

The defaulting webhook adds `queue-name: default` on UPDATE, and the validating webhook then rejects adding the queue name to a running object. The user didn't touch the label.

This is the same pattern as #16333 (default WorkloadPriorityClass), which #16474 fixed. That fix didn't cover the default LocalQueue.

**What you expected to happen**:

Updates that don't touch the queue-name label keep working. The default LocalQueue should only be applied when the label can still be set, the way #16474 handles the default WorkloadPriorityClass.

**How to reproduce it (as minimally and precisely as possible)**:

1. Enable the `statefulset` (or `deployment`, `leaderworkerset`) integration. The namespace must match `managedJobsNamespaceSelector`.
2. Create a StatefulSet without `kueue.x-k8s.io/queue-name` and wait until `readyReplicas > 0`.
3. Create a LocalQueue named `default` in the same namespace.
4. `kubectl annotate statefulset <name> example.com/foo=bar` is rejected with the error above.

`kubectl scale` and HPA still work, because the webhooks don't intercept the scale subresource.

I reproduced this on main (3c68ccf53) with an envtest integration test in `test/integration/singlecluster/controller/jobs/statefulset`: the annotation update succeeds before the `default` LocalQueue exists and is rejected after it's created. The Deployment and LeaderWorkerSet webhooks follow the same code path.

**Anything else we need to know?**:

- `ApplyDefaultLocalQueue` runs on both create and update ([deployment_webhook.go](https://github.com/kubernetes-sigs/kueue/blob/3c68ccf53/pkg/controller/jobs/deployment/deployment_webhook.go), and the same in the statefulset and leaderworkerset webhooks), and `defaultLocalQueueApplies` in `pkg/controller/jobframework/defaults.go` has no create/not-running check.
- The default WorkloadPriorityClass call right below it is already guarded by `CanSetWorkloadPriorityClassName(oldObj.Status.ReadyReplicas == 0, oldObj)`. A similar guard for the default LocalQueue would fix it.
- Present since the default LocalQueue was added in v0.10.0 (#3610).

I'm happy to send a fix.

**Environment**:
- Kubernetes version: envtest 1.36.2
- Kueue version: main (3c68ccf53)
