**What happened**:

With `SchedulerLibraryDeepIntegration` enabled, a Job with `podset-required-topology: cloud.provider.com/topology-rack` is admitted with a TopologyAssignment that spans two racks.

**What you expected to happen**:

All 3 Pods assigned within one rack (either rack has room), as happens with the gate off.

**How to reproduce it (as minimally and precisely as possible)**:

kind v1.37.0, Kueue main @10df1bbeb, Kueue gates `SchedulerLibraryIntegration=true,SchedulerLibraryDeepIntegration=true,GenericWorkload=true`.
4 workers × 4 CPU, all labeled `cloud.provider.com/topology-block=b1`; `cloud.provider.com/topology-rack`: r1 = worker, worker2; r2 = worker3, worker4.

| Configuration | `topologyAssignment` (hostname) |
|---|---|
| deep off | worker2 ×3 |
| deep on | worker (r1), worker3 (r2), worker4 (r2) |
| deep on + k8s `TopologyAwareWorkloadScheduling=true` | worker (r1), worker2 (r1), worker3 (r2) |

**Anything else we need to know?**:

`BuildVirtualPodGroups` carries the required topology into the virtual PodGroup's `schedulingConstraints.topology`, but the resulting TopologyAssignment violates it. The `tasapi/deepintegration` e2e suite doesn't cover required topology yet.

The general context is that SchedulerLibraryDeepIntegration is a complex feature in "early Alpha", still under development.
Hence, you'll still see various aspects of it not working, until they become supported.

For example, preemptions aren't yet supported at all, which is being worked on in #17679 and follow-ups.

### Comment by [@apullo777](https://github.com/apullo777) — 2026-10-28T08:58:25Z

Thanks @olekzabl for the broader context and pointers to the ongoing work!

I tested #17678's `PlacementGenerate` change against my original repro (10df1bbeb, which already includes #17605). It fixes required placement when either `TopologyAwareWorkloadScheduling` or `CompositePodGroup` is enabled. With both off, the Workload is still admitted with a cross-rack TopologyAssignment.

Would it make sense to document or validate this gate dependency, or is this an acceptable limitation for early Alpha?

### Comment by [@olekzabl](https://github.com/olekzabl) — 2026-10-28T09:18:56Z

Thanks for checking.

Yes, I think it makes sense to enforce such dependencies.

Because the pre-reqs (`TopologyAwareWorkloadScheduling`, `CompositePodGroup`, possibly more to come) are non-Kueue FGs, I'd rather use the "imperative validation" path (e.g. in `LoadAndValidateFeatureGates`) rather than the declarative system of FG dependencies.
