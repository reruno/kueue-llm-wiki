## Description

**What happened**:

When running `"Should not admit a Job if Rack required"` ([`test/e2e/singlecluster/tasapi/baseline/job_test.go`](https://github.com/kubernetes-sigs/kueue/blob/966f00d214583a20cd45577fa69ac8ce1fb29d9b/test/e2e/singlecluster/tasapi/baseline/job_test.go#L89)) with `SchedulerLibraryDeepIntegration` enabled, the Job gets admitted when it shouldn't.

In the test cluster (`hack/testing/kind-cluster-tas.yaml`), each rack only has 2 nodes, and the Job asks for 3 pods on the same rack. However, both block `b1` and block `b2` have a rack named `r1`. WAS only checks the rack label (`r1`) without checking the block, so it thinks `r1` has 4 nodes total and admits the Job across both blocks.

**What you expected to happen**:

`r1` in `b1` and `r1` in `b2` are in different blocks and should be treated as two separate racks (2 nodes each), so the 3-pod Job should stay pending.

## Discussion

### Comment by [@olekzabl](https://github.com/olekzabl) — 2026-10-28T10:41:25Z

I see 3 potential ways to tackle this issue (which I'll enumerate in a subjective order of conceptual complexity):

1. [medium term] Translate Kueue requirements like "same rack [and implicitly same block]" to multiple explicit WAS requirements "same rack, same block".
   * Problem with this: WAS right now allows only a single-level requirement per single level of [Composite]PodGroup hierarchy, and the number of [C]PG hierarchy levels is bounded quite strictly (to at most 4). \
      Hence, this solution would be problematic as of now.
   * OTOH I heard the WAS team is considering to support multiple-level topology specs (e.g. "same rack, same block") on a single [C]PG object. When this arrives, the considered Kueue-side fix will work in general.

2. [long term] Wait until WAS supports a concept of Topology (like Kueue currently does), with an explicitly declared hierarchy of levels, and until it adds implicitly "and same block" just like Kueue does today. \
   I heard the WAS team is considering such a feature, though AFAIK there are no hard commitments.

3. [short term] I think we can also fix this without any WAS-side support, though in a bit hacky way: \
   In the scheduler-library's `ClusterSnapshot`, for every Topology `T`, and its level `L`, add artificial "full ancestry labels" to all involved nodes, for example:
   ```
   kueue.x-k8s.io/full-ancestry-T-up-to-L: b1/r1
   ```
   and then, "same rack [and implicitly same block]" in Kueue would translate to "same `kueue.x-k8s.io/full-ancestry-T-up-to-rack`" in WAS.
   * Note: this ad-hoc translation would need to happen only once we know `T`, i.e. once we know the Flavor assignment for the workload currently considered for admission. \
     But that doesn't seem problematic; we're virtualizing candidate Pods after flavor assignment anyway.

---

Bottom line: I'd rather not jump into # 3 right away - as it's hacky, while future WAS developments are likely to unlock simpler solutions.

That's why I'd propose to leave this unfixed for now. 
However, if any user actually hits the name clash and needs this fixed, I think # 3 is a potential feasible solution.
