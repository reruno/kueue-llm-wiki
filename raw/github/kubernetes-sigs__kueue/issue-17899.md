## Description

**What happened**:

The validating webhook accepts a check state with two `podSetUpdates` entries for the same PodSet:

```yaml
  admissionChecks:
  - name: check
    state: Ready
    podSetUpdates:
    - name: main
      labels:
        example.com/checked: "true"
    - name: main
      tolerations:
      - key: dedicated
        operator: Exists
        effect: NoSchedule
```

Kueue does not read such a list the same way everywhere.
Job start takes the first entry for each PodSet in each check and skips the rest ([reconciler.go#L2218-L2227](https://github.com/kubernetes-sigs/kueue/blob/966f00d214583a20cd45577fa69ac8ce1fb29d9b/pkg/controller/jobframework/reconciler.go#L2218-L2227)), so the Job gets the label but not the toleration.
TAS placement uses every entry of the Ready checks ([tas_flavorassigner.go#L116-L125](https://github.com/kubernetes-sigs/kueue/blob/966f00d214583a20cd45577fa69ac8ce1fb29d9b/pkg/scheduler/flavorassigner/tas_flavorassigner.go#L116-L125)).
With a ProvisioningRequest check, TAS assigns topology in a second pass that runs once all checks are Ready.
It can then pick a node tainted `dedicated:NoSchedule` that the Job's Pods do not tolerate.

**What you expected to happen**:

The webhook rejects the second entry.
Before #2265 it required a non-empty list to have as many entries as there are PodSets, and the comment that replaced that check assumes the names stay unique ([workload_webhook.go#L256-L264](https://github.com/kubernetes-sigs/kueue/blob/966f00d214583a20cd45577fa69ac8ce1fb29d9b/pkg/webhooks/workload_webhook.go#L256-L264)):

```go
// no need to check the number of podSetUpdates,
// because it cannot exceed the one of the podSets without having an unknown podSet name
```

[`validatePodSetUpdates`](https://github.com/kubernetes-sigs/kueue/blob/966f00d214583a20cd45577fa69ac8ce1fb29d9b/pkg/webhooks/workload_webhook.go#L266-L285) checks that each name is a known PodSet, not that the names are unique.

**How to reproduce it (as minimally and precisely as possible)**:

Add this entry to the "Should have valid values when setting AdmissionCheckState" table in `test/integration/singlecluster/webhook/core/workload_test.go`:

```go
ginkgo.Entry("two podSetUpdates for the same PodSet",
	func() *kueue.Workload {
		return utiltestingapi.MakeWorkload(workloadName, ns.Name).
			Obj()
	},
	kueue.AdmissionCheckState{
		Name:          "check",
		State:         kueue.CheckStateReady,
		PodSetUpdates: []kueue.PodSetUpdate{{Name: kueue.DefaultPodSetName}, {Name: kueue.DefaultPodSetName}}},
),
```

```sh
make test-integration INTEGRATION_TARGET=./test/integration/singlecluster/webhook/core GINKGO_ARGS="--focus='two podSetUpdates for the same PodSet'"
```

**Anything else we need to know?**:

- The ProvisioningRequest check writes one entry per PodSet ([controller.go#L832-L858](https://github.com/kubernetes-sigs/kueue/blob/966f00d214583a20cd45577fa69ac8ce1fb29d9b/pkg/controller/admissionchecks/provisioning/controller.go#L832-L858)), so the repeats come from admission check controllers outside Kueue.
- `ValidateWorkloadUpdate` runs this validation on every write ([workload_webhook.go#L403-L407](https://github.com/kubernetes-sigs/kueue/blob/966f00d214583a20cd45577fa69ac8ce1fb29d9b/pkg/webhooks/workload_webhook.go#L403-L407)).
  A new rule must keep accepting writes to a Workload that already stores repeats, for example by checking only a list that changed.
- If repeats should stay allowed instead, job start and the TAS node controller ([node_controller.go#L463-L472](https://github.com/kubernetes-sigs/kueue/blob/966f00d214583a20cd45577fa69ac8ce1fb29d9b/pkg/controller/tas/node_controller.go#L463-L472)), which also takes the first entry, need to apply all of them.
  #16170 (open) changes the merge in both loops and keeps the `break`.
- release-0.20 and release-0.19 have the same code. I ran the test only on main.
