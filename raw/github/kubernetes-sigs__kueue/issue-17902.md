## Description

**What would you like to be added**:

Support an opt-in container-level scope for resource transformations, allowing expressions such as `GPU count × per-GPU memory` to be evaluated within each container before aggregating the Pod’s quota requests.

Existing Pod-level transformation behavior should remain the default for backward compatibility.

**Why is this needed**:

My deployment uses Kueue **v0.19.0** with **volcano-vgpu-device-plugin**. Multiple containers in the same Pod request vGPUs, potentially with different per-vGPU resource requirements.

For each container, Volcano interprets:

- `volcano.sh/vgpu-number`: number of requested vGPUs.
- `volcano.sh/vgpu-memory`: memory requested per vGPU.
- `volcano.sh/vgpu-cores`: compute percentage requested per vGPU.

The accounting results below are derived from the Kueue implementation, rather than captured cluster output.

**Example transformation configuration**:

```yaml
resources:
  transformations:
    - input: volcano.sh/vgpu-memory
      strategy: Replace
      multiplyBy: volcano.sh/vgpu-number
      outputs:
        quota.example.com/gpu-memory: "1"

    - input: volcano.sh/vgpu-cores
      strategy: Replace
      multiplyBy: volcano.sh/vgpu-number
      outputs:
        quota.example.com/gpu-cores: "1"
```

**Example PodSpec fragment**:

The Ubuntu containers only run `sleep`; this example concerns quota accounting and does not require a CUDA application.

```yaml
schedulerName: volcano
containers:
  - name: container-a
    image: ubuntu:22.04
    command: ["sleep", "infinity"]
    resources:
      requests:
        volcano.sh/vgpu-number: "2"
        volcano.sh/vgpu-memory: "8192"
        volcano.sh/vgpu-cores: "50"
      limits:
        volcano.sh/vgpu-number: "2"
        volcano.sh/vgpu-memory: "8192"
        volcano.sh/vgpu-cores: "50"

  - name: container-b
    image: ubuntu:22.04
    command: ["sleep", "infinity"]
    resources:
      requests:
        volcano.sh/vgpu-number: "3"
        volcano.sh/vgpu-memory: "4096"
        volcano.sh/vgpu-cores: "25"
      limits:
        volcano.sh/vgpu-number: "3"
        volcano.sh/vgpu-memory: "4096"
        volcano.sh/vgpu-cores: "25"
```

Assume a single-Pod PodSet and a ClusterQueue covering the following resources with sufficient quota:

- `volcano.sh/vgpu-number`
- `quota.example.com/gpu-memory`
- `quota.example.com/gpu-cores`

No transformation inputs are excluded from accounting. This example does not involve init containers, Pod overhead, DRA, or TAS.

The generated `quota.example.com/*` resources are used only for Kueue quota accounting and are not requested by the actual containers.

**Expected quota accounting**:

Each container’s vGPU count should multiply that container’s per-vGPU resource requests:

```text
vgpu-number = 2 + 3                   = 5
gpu-memory  = 2 × 8192 + 3 × 4096     = 28672
gpu-cores   = 2 × 50   + 3 × 25       = 175
```

Memory quantities above use the same resource units as the original `volcano.sh/vgpu-memory` requests.

**Current behavior inferred from the implementation**:

In v0.19.0, `totalRequestsFromPodSets` in `pkg/workload/workload.go` calls `PodRequests` before `applyResourceTransformations`.

Consequently, the per-container values are aggregated before `multiplyBy` is evaluated:

```text
vgpu-number = 2 + 3                   = 5
gpu-memory  = (8192 + 4096) × (2 + 3) = 61440
gpu-cores   = (50 + 25) × (2 + 3)     = 375
```

The required calculation is:

```text
Σ(vgpu_count_i × per_vgpu_resource_i)
```

The current aggregation order produces:

```text
Σ(vgpu_count_i) × Σ(per_vgpu_resource_i)
```

This introduces cross-container terms and overstates quota usage.

Mapping vGPU count to constant resource quantities can work for a fixed resource profile, but it cannot support independently configurable per-vGPU requirements across containers.

**Suggested behavior**:

Allow selected transformations to operate on each container’s effective requests before Pod-level aggregation.

The implementation should:

- Preserve existing Pod-level transformation behavior by default.
- Preserve Kubernetes aggregation semantics for init containers and restartable sidecars.
- Apply the PodSet count after calculating each Pod’s effective quota requests.
- Affect quota accounting without rewriting the actual Volcano resource requests.

Could maintainers confirm whether container-level transformations are the appropriate extension, or whether an existing supported mechanism can express this calculation?
