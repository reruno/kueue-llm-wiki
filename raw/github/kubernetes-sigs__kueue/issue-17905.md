### Comment by [@ivnovakov](https://github.com/ivnovakov) — 2026-10-28T16:59:03Z

The refused webhook is `mleaderworkerset.kb.io` from the LWS operator, not a Kueue webhook. Kueue had no restarts in either build, and its own webhook probe passed at install time.

LWS v1.0.0 sets readyz to `healthz.Ping` and registers its webhooks only after its certs are ready. So both `lws-controller-manager` replicas turn Ready, and `WaitForLeaderWorkerSetAvailability` returns, before each of them serves the webhook. The apiserver picks a random webhook endpoint per call, so the first LeaderWorkerSet `Create` can land on the replica that is not serving yet.

The LWS manager logs in both linked builds match that.
- In the first build, the non-leader pod (the refused `10.244.2.4`) logged "Serving webhook server" at 12:31:42.5, 4.7s after the failure at 12:31:37.8. The leader was serving since 12:31:31.9.
- In the second build, the non-leader pod (the refused `10.244.1.4`) started serving at 15:19:27.0, 2.5s after all 6 LWS specs failed at 15:19:24.5.

It most likely started with #17822. Since the e2e suite is now compiled during cluster setup, the first LWS spec runs about 10s after the LWS manifest is applied, and the non-leader replica needed 12 to 14s to start serving. I didn't compare pass rates before and after, so this part is based on timing only.

### Comment by [@ivnovakov](https://github.com/ivnovakov) — 2026-10-28T18:16:17Z

Agree, we should wait for LWS to be operational. A dry-run create alone is not enough on 1.35 and 1.36 though. Before 1.37 the apiserver picks the webhook endpoint when it opens a connection, not per call, and then reuses that connection. So the dry-run can pass on the replica that is already serving while the specs still hit the other one. Both failures were on 1.36.4. This also corrects my comment above, where I said the apiserver picks the endpoint per call.

In #17935, `WaitForLeaderWorkerSetAvailability` first waits for the Deployment to be Available, as before. Then it calls the LWS webhook on each pod through the apiserver pod proxy and waits until every pod returns success. This works no matter which replica the apiserver picks. I also opened kubernetes-sigs/lws#1253 to gate readyz on the webhook server, so we can drop this later.
