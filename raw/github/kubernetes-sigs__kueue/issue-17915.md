## Description

**What happened**:

With `ConcurrentAdmission` enabled, `concurrentAdmissionPolicy.migration.mode: RetainFirstAdmission`, and a ProvisioningRequest AdmissionCheck on every flavor, the parent Workload is evicted with reason `VariantEvicted` ("Admitted variant was evicted") shortly after one variant is admitted, although the admitted variant was never evicted.

Sequence (v0.19.0, `pkg/controller/concurrentadmission/controller.go`):

1. Both variants reserve quota and wait on their ProvisioningRequest checks.
2. One variant's check becomes Ready and it is Admitted. `deactivateVariants` sets `spec.active=false` on the losing variant, and `syncAdmissionStatus` copies the winner's admission to the parent.
3. `deactivateVariant` re-reads the loser immediately. `Evicted` is not set yet, so its quota is not cleared.
4. The workload controller then sets `Evicted=True` (reason `Deactivated`) on the loser, which still has `QuotaReserved=True`.
5. On the next reconcile, `syncVariantEvictionStatus` (L396-426) finds a variant with `Evicted=True` and quota reserved, sees the parent has quota, and evicts the parent. It does not check whether that variant is active or is the one backing the parent's admission.

Result: the running job is suspended and restarted. Under MultiKueue (ConcurrentAdmission on the worker), the manager sees the worker workload evicted while its MultiKueue check is Ready, sets the check to Retry and re-dispatches, so the job loops and the capacity provisioned for it is orphaned.

**What you expected to happen**:

Deactivating a losing variant releases that variant's quota only. The parent stays admitted on the winning variant.

**How to reproduce it (as minimally and precisely as possible)**:

1. Enable feature gate `ConcurrentAdmission`.
2. ClusterQueue with one resourceGroup, two flavors (`a`, `b`), `concurrentAdmissionPolicy.migration.mode: RetainFirstAdmission`, and `admissionChecksStrategy` applying a ProvisioningRequest check to both flavors (any check that keeps both variants QuotaReserved but not Admitted works).
3. Submit a batch/v1 Job.
4. Make the check for flavor `a` Ready while `b` stays Pending.
5. The parent Workload gets `Evicted=True, reason=VariantEvicted` within a reconcile or two.

Unit test sketch for `TestReconcile`: parent admitted on `a`; variant `a` Admitted; variant `b` `Active(false)`, quota reserved, `Evicted=True reason=Deactivated`. Expected: parent not evicted and `b`'s quota cleared. Actual: parent evicted.

**Anything else we need to know?**:

Proposed fix: in `syncVariantEvictionStatus`, only propagate eviction to the parent from the variant backing the parent's admission. Treat inactive variants as losers and release their quota:

    if !workload.IsActive(v) {
        if evicted && workload.HasQuotaReservation(v) {
            if err := r.clearWorkloadAdmission(ctx, v, evCond); err != nil { ... }
        }
        continue
    }

Existing tests only cover an active admitted variant evicted by preemption; the inactive-loser case has no coverage.

Related: #12470 (MultiKueue + ConcurrentAdmission), #15838 (different parent-eviction path on flavor removal), #16734 (ProvisioningRequest podSetUpdates with ConcurrentAdmission).

**Environment**:
- Kubernetes version: GKE 1.36.4
- Kueue version: v0.19.0 (function unchanged on main as of 2026-10-28, v0.19.10, v0.20.3)
- AdmissionCheck: ProvisioningRequest (GKE queued provisioning / flex-start)
- Feature gates: ConcurrentAdmission
- MultiKueue: manager + 2 workers, ConcurrentAdmission on workers only
