**What happened**:

When one Workload doesn't fit, Kueue skips the identical Workloads behind it. A skipped Workload that's brand new gets no QuotaReserved condition while it waits. With 20 identical waiting Jobs, only 1 had a condition.

**What you expected to happen**:

Every waiting Workload gets QuotaReserved=False, as it does with SchedulingEquivalenceHashing off.

**How to reproduce it (as minimally and precisely as possible)**:

1. A BestEffortFIFO ClusterQueue with 4 GPUs. One Job holds all 4.
2. Create 20 identical Jobs, each asking for 4 GPUs.
3. `kubectl get workloads`: 19 of the 20 waiting Workloads have no QuotaReserved condition.

**Anything else we need to know?**:

#12821 writes the bypass message for these only when UnadmittedWorkloadsExplicitStatus is on. Applying it to new Workloads whenever hashing is on fixed it in my runs.  cc @j-skiba @mimowo @tenzen-y

**Environment**:
- Kubernetes version: v1.36.1 (kind)
- Kueue version: v0.20.3

### Comment by [@j-skiba](https://github.com/j-skiba) — 2026-10-29T07:33:33Z

There was discussion about this in the mentioned PR - https://github.com/kubernetes-sigs/kueue/pull/12821#discussion_r3530323167

The problem is that SchedulingEquivalenceHashing and UnadmittedWorkloadsExplicitStatus don't really go together very well. I think SchedulingEquivalenceHashing (already enabled by default) was introduced with large scale clusters in mind while enabling UnadmittedWorkloadsExplicitStatus (disabled by default) causes 1 API call for each workload which in large scale clusters could be devastating.

In the mentioned thread there was idea to document this functionality better to avoid confusion.

It's mentioned briefly in KEP - https://github.com/kubernetes-sigs/kueue/tree/main/keps/10852-inadmissible-workloads-observability#resolution-algorithm - but it's missing the UnadmittedWorkloadsExplicitStatus part too, it could be improved.

If we want bypassed workloads to get QuotaReserved=False by default (or when promoting UnadmittedWorkloadsExplicitStatus in the near future), we should consider whether large-scale clusters need a feature gate to opt out of per-workload status writes on EquivalenceHashing-bypassed workloads so API call churn doesn't become an issue at scale.

### Comment by [@mimowo](https://github.com/mimowo) — 2026-10-29T07:44:27Z

Yes, performance is the main concern, at the same time 1 extra API call shouldn't be "devastating". I think we need more benchmarking to see the impact, and also collect user feedback on large deployments (20k+ workloads) from users who enable that.

cc @kshalot who is collecting such feedback from one of our users. 

So, I would consider graduating UnadmittedWorkloadsExplicitStatus to Beta when we collect the feedback, it is positive, and also we conduct experiments.

### Comment by [@kshalot](https://github.com/kshalot) — 2026-10-29T11:56:26Z

> Yes, performance is the main concern, at the same time 1 extra API call shouldn't be "devastating".

In some cases we are talking about **thousands** of workloads being bulk moved into inadmissible (observed in prod), which would mean that we have to do thousands of requests to change the status. This could be expensive and DOS-y for the apiserver.

The gap within observability was raised as a concern though, so it is a valid problem to try and solve. For observability, we can consider exposing the hash in the workload status so you can query the "representative" workload to get the reason why it is unschedulable. This is not a perfect solution though.
