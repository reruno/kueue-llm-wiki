### Comment by [@henry3260](https://github.com/henry3260) — 2026-10-28T20:23:27Z

I compared both shards on the same commit (PR #17392):

| | shard-0 | shard-1 |
|---|---|---|
| CPU request/limit | 7 | 3.4 |
| GOMAXPROCS | 7 | 4 |
| packages with tests | 59 | 56 |
| sum of per-package test time (gotestsum) | 301s | 358s |
| `make test` step | 420s | 779s |

The work is roughly equal (~1.2x); shard-1 is slow mainly because it has half the CPU, and `GOMAXPROCS=4 `is above its `3.4 CPU `limit, which kubernetes/test-infra@c84b3f7b85 noted causes throttling.

This is the reverse of #16794: on Oct 7 shard-0 was the slow one, so only shard-0 got 7 CPU. Since packages are assigned round-robin in `go list` order, adding a package shifts the rest between shards, and the heavy ones (e.g. jobs/job, concurrentadmission) are now on shard-1.
So, I don't think splitting large packages helps much: the slowest package takes ~55s (with `-count 3`), far below the shard's runtime, which is dominated by building ~56 race + coverage test binaries on 3.4 CPUs.
So I think the quick way might be set shared1 to 7 CPU. Longer term, balancing by measured runtime (#17190) would stop the shards from flipping again. wdyt?
