## Description


**What happened**:

A node running a Pod of an elastic Job became unreachable. After the taint-based eviction, the old Pod stays `Terminating` because its kubelet is gone, and the Job creates a replacement Pod. The replacement Pod stays behind the `kueue.x-k8s.io/elastic-job` scheduling gate until the node comes back, even though a free node exists.

`podsToUngate` in the elastic Job ungater skips only Pods in phase `Failed` or `Succeeded` (`utilpod.IsTerminated`), so the Terminating Pod still uses one of the admitted slots.

| Job | Replacement Pod after eviction |
|---|---|
| elastic | `SchedulingGated` until the node returns |
| non-elastic (same spec, no annotation) | Created 1s after the eviction and Running on the free node |

**What you expected to happen**:

The replacement Pod is ungated and scheduled on the free node, as for a non-elastic Job.

**How to reproduce it (as minimally and precisely as possible)**:

```shell

# 1. Create an elastic Job with 3 Pods
$ cat <<EOF | kubectl create -f -
apiVersion: batch/v1
kind: Job
metadata:
  name: elastic
  labels:
    kueue.x-k8s.io/queue-name: lq-plain
  annotations:
    kueue.x-k8s.io/elastic-job: "true"
spec:
  parallelism: 3
  completions: 10
  suspend: true
  template:
    spec:
      restartPolicy: Never
      containers:
      - name: c
        image: busybox:1.36
        command: ["sleep", "3600"]
        resources:
          requests:
            cpu: 10m
            example.com/slot: "1"
          limits:
            example.com/slot: "1"
EOF


# 2. Make worker2 unreachable (worker4 stays free)
$ docker stop kueue-h1-repro-worker2

# 3. Wait for NotReady (~40s) and the taint-based eviction (300s)
$ kubectl get events -o custom-columns=OBJ:.involvedObject.name,REASON:.reason,MSG:.message
OBJ                      REASON                 MSG
kueue-h1-repro-worker2   NodeNotReady           Node kueue-h1-repro-worker2 status is now: NodeNotReady
elastic-8pm2k            TaintManagerEviction   Marking for deletion Pod default/elastic-8pm2k
elastic                  SuccessfulCreate       Created pod: elastic-56brk

# 4. Check the Pods
# OUTPUT: the replacement Pod elastic-56brk stays gated while worker4 is free
$ kubectl get pods -l job-name=elastic -o custom-columns=NAME:.metadata.name,STATUS:.status.phase,NODE:.spec.nodeName,DELETED:.metadata.deletionTimestamp,GATES:.spec.schedulingGates[*].name
NAME            STATUS    NODE                     DELETED                GATES
elastic-56brk   Pending   <none>                   <none>                 kueue.x-k8s.io/elastic-job
elastic-8pm2k   Running   kueue-h1-repro-worker2   2026-10-27T18:15:57Z   <none>
elastic-nzlwg   Running   kueue-h1-repro-worker    <none>                 <none>
elastic-szjzc   Running   kueue-h1-repro-worker3   <none>                 <none>
$ kubectl get job elastic -o jsonpath='active={.status.active} ready={.status.ready} terminating={.status.terminating}'
active=3 ready=2 terminating=1

# 5. Bring the node back
# OUTPUT: the Terminating Pod goes away and the replacement Pod runs within 15s
$ docker start kueue-h1-repro-worker2
$ kubectl get pods -l job-name=elastic -o custom-columns=NAME:.metadata.name,STATUS:.status.phase,NODE:.spec.nodeName
NAME            STATUS    NODE
elastic-56brk   Running   kueue-h1-repro-worker2
elastic-nzlwg   Running   kueue-h1-repro-worker
elastic-szjzc   Running   kueue-h1-repro-worker3
```
