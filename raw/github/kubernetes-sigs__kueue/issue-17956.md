## Description

/kind bug

**What happened**:

Three handlers in `pkg/controller/core` chain into a loop:

1. Every ClusterQueue event, status writes included, reaches the Cohort controller (`ClusterQueueReconciler.Update` → `notifyWatchers` → `CohortReconciler.NotifyClusterQueueUpdate`), whose `cohortCqHandler` enqueues every ancestor Cohort of that ClusterQueue except the root.
2. Every Cohort reconcile calls `notifyWatchers` unconditionally; `ClusterQueueReconciler.NotifyCohortUpdate` enqueues every ClusterQueue under that Cohort (`cache.ClusterQueuesUsingCohort`, the whole subtree).
3. Each ClusterQueue reconcile recomputes its status and writes it when usage or counts changed, which is a ClusterQueue event, back to 1.

With a steady stream of admissions and completions some ClusterQueue's status changes on every pass, so the sweep over the tree never ends. The cost of one status write is one reconcile per ClusterQueue in the tree, so the controller's work grows with (status writes per second) × (ClusterQueues in the tree).

Measured on a cluster with ~900 ClusterQueues under ~900 Cohorts (one ClusterQueue and one Cohort per tenant, four levels deep, a tenant created or deleted about once a second), Kueue v0.20.3:

- In 53 s of the leader's log at v=2: 260 ClusterQueue update events, 14,466 `Reconcile ClusterQueue` lines, 836 `Reconcile Cohort` lines. The two Cohorts nearest the root reconciled 158 and 163 times, about three times a second each, and every one of those requeued the whole subtree.
- The single ClusterQueue worker ran at one full core, about 3.7 ms per reconcile, so one sweep takes ~3.4 s and the next one is already queued.
- A new tenant's Workload, evaluated before its Cohort entered the cache, was marked `ExceedsMaxQuota` and waited behind the sweep for up to 35 s; 122 such events in one hour.
- `controller.groupKindConcurrency` of 2 for ClusterQueue and Cohort shortens each sweep (about 4,800 ClusterQueue reconciles per minute, leader at 2.3 cores) but the loop stays.

The handlers are unchanged on main (ce0f8786).

**What you expected to happen**:

A ClusterQueue status write refreshes its ancestors' status and metrics (fair-sharing weighted share, cohort gauges) and stops. ClusterQueues are reconciled again only when a Cohort, or a ClusterQueue under it, is created, deleted or changes its spec or quotas, since that is the only Cohort-side change their status depends on.

**How to reproduce it (as minimally and precisely as possible)**:

1. Create a root Cohort, a child Cohort with a parent, and N ClusterQueues (N ≥ 500) in the child Cohort, each with a LocalQueue.
2. Submit short Jobs continuously to one LocalQueue, so one ClusterQueue's status changes every second or so.
3. Run the manager at `--zap-log-level=2` and count `Reconcile ClusterQueue` lines per minute: each status write produces N reconciles, and the count per minute stops depending on the Job rate once the worker is saturated.
4. Create a new ClusterQueue and Cohort with a Workload at the same time: the Workload is marked `ExceedsMaxQuota` and admitted only when the sweep lets the Cohort reconcile through.

**Anything else we need to know?**:

The ClusterQueue → ancestor requeue came with the Cohort fair-sharing status in #4561 so Cohort status and metrics follow usage; it is still needed for that. The fan-out from a Cohort reconcile to every ClusterQueue under it predates it (#2971) and is what closes the loop. A fix follows in a PR: the Cohort reconciler notifies its ClusterQueues only when the Cohort was created or changed spec or quotas, or, with fair sharing, a ClusterQueue under it was created, deleted or changed spec or quotas. Without fair sharing nothing in a ClusterQueue's status depends on another ClusterQueue (`updateCqStatusIfChanged` writes its own usage, counts, pending count and Active condition), so a ClusterQueue event then refreshes its ancestors and nothing else.

Two related gaps in the same code, closed by the same PR: a ClusterQueue that moves to another Cohort only requeues the new Cohort's ancestors, so the old tree's status is never refreshed; and with fair sharing a quota change refreshes only the changed Cohort's subtree, while the weighted share divides borrowing by the whole tree's lendable quota (`computeLendable` walks to the root), so ClusterQueues in other branches keep a stale `status.fairSharing.weightedShare`. Left as is: `qManager.AddOrUpdateCohort` on every Cohort reconcile still requeues the tree's inadmissible Workloads to the scheduler, and `cache.ClusterQueuesUsingCohort` walks every ClusterQueue's path to the root per call.

**Environment**:
- Kubernetes version: v1.36
- Kueue version: v0.20.3 (66ff21115867ef4a80ced2a662d3665d86cb0d78); same handlers on main ce0f8786
- Cloud provider or hardware configuration: Nebius managed Kubernetes, 2 manager replicas, leader election on
- Install tools: Helm chart
- Others: `MetricsForCohorts=false`, fair sharing off; the loop does not depend on either
