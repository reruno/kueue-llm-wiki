## Description

## What happened

A failure while listing existing objects during queue registration can leave the Kueue queue manager in a partially initialized state.

Both `Manager.AddLocalQueue` and `Manager.AddClusterQueue` publish their internal queue state before completing the corresponding backfill operation.

If the `client.List` call fails, the method returns an error without undoing the registration. A later registration attempt encounters an already-existing queue, even though its initial workloads or child queues were never imported.

This is a code-path finding based on `main` at commit `e0900cd1d2c2f9e5e008870083766a469fd3ffcc`. I have not reproduced it in a running Kubernetes cluster; a deterministic fake-client regression test is proposed below.

### Case 1: LocalQueue initialization

Relevant file:

[`[pkg/cache/queue/manager.go](https://github.com/kubernetes-sigs/kueue/blob/main/pkg/cache/queue/manager.go)`](https://github.com/kubernetes-sigs/kueue/blob/main/pkg/cache/queue/manager.go)

In `addLocalQueueLocked`, initialization proceeds as follows:

```go
key := queue.Key(q)
if _, ok := m.localQueues[key]; ok {
    return nil, fmt.Errorf("queue %q already exists", q.Name)
}

qImpl := newLocalQueue(q)
m.localQueues[key] = qImpl

cq := m.hm.ClusterQueue(qImpl.ClusterQueue)
if cq != nil {
    cq.addLocalQueue(key, afs.LQWeightAsFloat64(q))
}

var workloads kueue.WorkloadList
if err := m.client.List(
    ctx,
    &workloads,
    client.MatchingFields{
        utilindexer.WorkloadQueueKey: q.Name,
    },
    client.InNamespace(q.Namespace),
); err != nil {
    return nil, fmt.Errorf(
        "listing workloads that match the queue: %w",
        err,
    )
}
```

The important ordering is:

1. Create an internal LocalQueue.
2. Insert it into `m.localQueues`.
3. Optionally register it with the ClusterQueue.
4. Query existing Workloads.
5. Return immediately if the query fails.

The error path leaves the earlier state changes intact.

Consequently, a subsequent `AddLocalQueue` call returns `queue "..." already exists`, while any pre-existing Workloads that were supposed to be recovered by the backfill may remain absent.

`UpdateLocalQueue` does not repeat this initial Workload listing.

### Case 2: ClusterQueue initialization

The same failure pattern exists in `Manager.AddClusterQueue`.

```go
cqImpl, err := newClusterQueue(
    ctx,
    cq,
    m.customLabels,
    m.workloadOrdering,
    m.admissionFairSharingConfig,
    afsUsageLedger,
)
if err != nil {
    return err
}

m.hm.AddClusterQueue(cqImpl)
m.hm.UpdateClusterQueueEdge(
    kueue.ClusterQueueReference(cq.Name),
    cq.Spec.CohortName,
)

var queues kueue.LocalQueueList
if err := m.client.List(
    ctx,
    &queues,
    client.MatchingFields{
        utilindexer.QueueClusterQueueKey: cq.Name,
    },
); err != nil {
    return fmt.Errorf(
        "listing queues pointing to the cluster queue: %w",
        err,
    )
}
```

Here, a failed List leaves:

- The ClusterQueue inserted into the hierarchy manager.
- Its Cohort relationship established.
- Previously existing LocalQueues not imported into the new ClusterQueue.

A retry immediately encounters `errClusterQueueAlreadyExists`.

`UpdateClusterQueue` updates the existing ClusterQueue configuration but does not rerun the failed LocalQueue backfill.

### Why normal controller handling may not repair this

The relevant controller event handlers log the errors rather than making initialization transactional.

- [`[localqueue_controller.go](https://github.com/kubernetes-sigs/kueue/blob/main/pkg/controller/core/localqueue_controller.go)`](https://github.com/kubernetes-sigs/kueue/blob/main/pkg/controller/core/localqueue_controller.go)
- [`[clusterqueue_controller.go](https://github.com/kubernetes-sigs/kueue/blob/main/pkg/controller/core/clusterqueue_controller.go)`](https://github.com/kubernetes-sigs/kueue/blob/main/pkg/controller/core/clusterqueue_controller.go)

Their Create handlers log failures from the queue manager and return `true`.

There is no retry of the failed backfill directly from these handlers.

Subsequent workload or queue events may repair some missing state incidentally, but successful recovery should not depend on unrelated future updates.

## What you expected to happen

Queue initialization should be atomic with respect to failures in its initial backfill.

If an initial List fails:

1. No incompletely initialized LocalQueue or ClusterQueue should be published.
2. No orphaned Cohort relationship should remain.
3. A subsequent attempt after the underlying read recovers should succeed.
4. Existing child objects should be imported correctly.
5. Scheduler notifications and pending-workload metrics should reflect successfully initialized state.

A transient read failure should not require a controller restart or object recreation to restore missing queue entries.

## How to reproduce it (as minimally and precisely as possible)

The problem can be reproduced deterministically in `pkg/cache/queue/manager_test.go` by injecting a one-time List error using the existing fake-client interceptor infrastructure.

### Reproduction A: LocalQueue

Prepare:

- A LocalQueue `ns/lq`, targeting ClusterQueue `cq`.
- An admissible pending Workload `ns/wl`, targeting `lq`.
- A fake client that fails the first WorkloadList operation, then behaves normally.

The following is a suggested regression-test implementation. It has not been compiled or executed as part of this report.

```go
func TestAddLocalQueueRetryAfterListFailure(t *testing.T) {
    ctx, _ := utiltesting.ContextWithLog(t)

    lq := utiltestingapi.MakeLocalQueue("lq", "ns").
        ClusterQueue("cq").
        Obj()

    wl := utiltestingapi.MakeWorkload("wl", "ns").
        Queue("lq").
        Obj()

    failOnce := true

    cl := utiltesting.NewClientBuilder().
        WithObjects(lq, wl).
        WithInterceptorFuncs(interceptor.Funcs{
            List: func(
                ctx context.Context,
                delegate client.WithWatch,
                list client.ObjectList,
                opts ...client.ListOption,
            ) error {
                if _, ok := list.(*kueue.WorkloadList); ok &&
                    failOnce {
                    failOnce = false
                    return errors.New("injected List failure")
                }

                return delegate.List(ctx, list, opts...)
            },
        }).
        Build()

    manager := NewManagerForUnitTests(
        cl,
        nil,
        WithPreemptionExpectations(
            preemptexpectations.New(),
        ),
    )

    // First registration should report the read failure.
    if err := manager.AddLocalQueue(ctx, lq); err == nil {
        t.Fatal("expected injected List failure")
    }

    // This should succeed after the client recovers.
    // It currently fails with "queue already exists".
    if err := manager.AddLocalQueue(ctx, lq); err != nil {
        t.Fatalf("registration retry failed: %v", err)
    }

    // The pre-existing Workload must be recovered.
    pending, err := manager.PendingWorkloads(lq)
    if err != nil {
        t.Fatalf("reading pending workloads: %v", err)
    }

    if pending != 1 {
        t.Fatalf(
            "pending workloads = %d, want 1",
            pending,
        )
    }
}
```

**Expected behavior after the fix:** The first attempt fails without publishing partial state. The second attempt succeeds and recovers `ns/wl`.

**Current code-path behavior:** The second attempt is rejected by the existing-entry check.

### Reproduction B: ClusterQueue

Use a similar fail-once interceptor for `*kueue.LocalQueueList`.

Test setup:

1. Create a LocalQueue and an associated pending Workload in the fake client.
2. Register the LocalQueue with the queue manager before registering its ClusterQueue.
3. Inject one List failure during `AddClusterQueue`.
4. Verify that the failed operation does not leave the ClusterQueue registered.
5. Retry after restoring successful List behavior.
6. Confirm that the ClusterQueue now contains the existing LocalQueue's pending Workload.

Suggested assertions:

```go
// The initial registration reports the injected error.
err := manager.AddClusterQueue(ctx, cq)
if err == nil {
    t.Fatal("expected injected List failure")
}

// Retry must not encounter a partially registered CQ.
if err := manager.AddClusterQueue(ctx, cq); err != nil {
    t.Fatalf("ClusterQueue retry failed: %v", err)
}

// The pending Workload must become visible to the CQ.
pending, err := manager.Pending(cq)
if err != nil {
    t.Fatalf("reading ClusterQueue pending state: %v", err)
}
if pending != 1 {
    t.Fatalf("pending = %d, want 1", pending)
}
```

This second excerpt illustrates the assertions; it requires the corresponding fake-client setup and is not a standalone test.

## Impact

The backfill operations are important for event-order independence.

Kueue must handle cases where Workloads already exist before their LocalQueue is registered, or LocalQueues are present before their ClusterQueue becomes available in the queue manager.

Losing initial backfill after a read failure can lead to:

- Pending Workloads missing from the scheduler's in-memory queue.
- Previously registered LocalQueues not being represented in a ClusterQueue's scheduling heap.
- Pending-workload counters not reflecting all eligible pending work.
- Recovery depending on unrelated object events or controller restarts.
- Incomplete Cohort relationships or metrics associated with unsuccessful registration.

The exact duration and user-visible impact depend on subsequent informer events and controller reconciliation behavior.

The primary concern is that an error-returning initialization method still makes its object appear successfully registered to the queue manager.

## Root cause

The implementation violates the intended failure atomicity of the initial registration path.

The sequence is effectively:

```text
Create internal queue
        |
        v
Publish queue in manager
        |
        v
Register hierarchy relationship
        |
        v
List existing child objects
        |
        +---- Success ---> Backfill and notify
        |
        +---- Error -----> Return without rollback
                              |
                              v
                       Partial state remains
                              |
                              v
                       Retry rejected
```

The initial List is a prerequisite for complete queue registration, but it executes after registration state has already been published.

## Suggested fix

Move the fallible child-object List operation before publishing the new queue into the manager's internal maps or hierarchy.

Keep the existing manager mutex held across the preparation and registration phases to preserve event ordering.

For LocalQueue initialization, the intended ordering would be:

```text
Acquire manager lock
        |
        v
Check for existing queue
        |
        v
List existing Workloads
        |
        +---- Error ---> Return without state mutation
        |
        v
Construct and register LocalQueue
        |
        v
Import Workloads
        |
        v
Update ClusterQueue and metrics
        |
        v
Release lock
```

For ClusterQueue initialization:

```text
Acquire manager lock
        |
        v
Check for existing ClusterQueue
        |
        v
Construct ClusterQueue object
        |
        v
List existing LocalQueues
        |
        +---- Error ---> Return without registration
        |
        v
Register ClusterQueue and Cohort edge
        |
        v
Import existing LocalQueues and Workloads
        |
        v
Notify scheduler and update metrics
```

This avoids publishing partially initialized queue state on the demonstrated List-error path.

An alternative is rollback or explicitly retryable incomplete initialization, although preparing the List before registration appears to offer a smaller change.

The fix should preserve current success-path ordering and behavior for fair-sharing weights, Cohort membership, DRA-backed Workloads, metrics, and scheduler notifications.

## Acceptance criteria

- [ ] A failed initial WorkloadList does not leave a new LocalQueue registered.
- [ ] A failed initial LocalQueueList does not leave a new ClusterQueue registered.
- [ ] Failed ClusterQueue registration does not retain an orphaned Cohort edge.
- [ ] Registration succeeds after a transient List failure is removed.
- [ ] Pre-existing Workloads and LocalQueues are imported exactly once after successful registration.
- [ ] Existing duplicate-registration behavior remains unchanged for fully initialized queues.
- [ ] Fair-sharing weights, pending-workload metrics and scheduler notifications remain correct.
- [ ] Regression tests cover both error paths and a successful retry.

The initial-sync barrier does not itself undo partially published state or retry a failed backfill.
