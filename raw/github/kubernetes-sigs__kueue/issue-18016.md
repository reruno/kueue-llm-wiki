## Description

**Which test is flaking?**:
`test/integration/singlecluster/controller/concurrentadmission` →
`Concurrent Admission / when A workload carries the parent label under a ClusterQueue without ConcurrentAdmissionPolicy / evicts the parent, delete the variant, releases quota, and removes the parent label`

**Link to failed CI job or steps to reproduce locally**:
CI (first run, failed):
https://prow.k8s.io/view/gs/kubernetes-ci-logs/pr-logs/pull/kubernetes-sigs_kueue/18008/pull-kueue-test-integration-shard-1-main/2116017922001342464
Same commit, retest (passed):
https://prow.k8s.io/view/gs/kubernetes-ci-logs/pr-logs/pull/kubernetes-sigs_kueue/18008/pull-kueue-test-integration-shard-1-main/2116027226368512000

Local reproduction: in that spec, add `time.Sleep(2 * time.Second)` right after
`behavioral.FinishEvictionForWorkloads(...)`, then run this package against envtest
assets (for example `make test-integration` with
`-ginkgo.focus='evicts the parent, delete the variant'` on
`TestSchedulerWithConcurrentAdmission`):

    go test ./test/integration/singlecluster/controller/concurrentadmission \
      -run TestSchedulerWithConcurrentAdmission \
      -ginkgo.focus='evicts the parent, delete the variant'

It fails every time with the message below.

**Failure message or logs**:
```
[FAILED] Timed out after 10.000s.
The function passed to Eventually failed at test/integration/singlecluster/controller/concurrentadmission/concurrent_admission_test.go:1060 with:
Expected
    <bool>: true
to be false
```

**Anything else we need to know?**:
The check runs right after `behavioral.FinishEvictionForWorkloads`, which already
asserts that the quota reservation is unset. The parent loses the ConcurrentAdmission
parent label as part of the eviction (`cleanupParentAndVariants` removes it in the
same reconcile), so it can be re-admitted as soon as the eviction completes. The
released quota is therefore only observable for a short window; on the failed CI run
the re-admission won the race and `HasQuotaReservation` stayed true for the whole
10s timeout.

Another spec in the same file waits for a parent to be re-admitted after its eviction
("Verifying the parent re-admits on the surviving spot flavor"), so re-admission is
expected behavior and not the bug — asserting on the transient released state is.

The spec was added in #14954 (merged 2026-10-29).

I have a fix ready (hold admissions on the ClusterQueue while the check runs, which
keeps the released state observable) and will open a PR referencing this issue.

### Comment by [@ivnovakov](https://github.com/ivnovakov) — 2026-10-30T13:22:28Z

I looked into it, and the mechanism is right.
`FinishEvictionForWorkloads` unsets the quota reservation itself ([`test/util/behavioral/workload.go:424-433`](https://github.com/kubernetes-sigs/kueue/blob/19613c1ae8de397893ca246796e9b15edb16a740/test/util/behavioral/workload.go#L424-L433)), so the check at [line 1060](https://github.com/kubernetes-sigs/kueue/blob/19613c1ae8de397893ca246796e9b15edb16a740/test/integration/singlecluster/controller/concurrentadmission/concurrent_admission_test.go#L1060) reads back the test's own update.
It can only pass if it runs before the scheduler admits the parent again.

I have a 2-line fix that asserts the parent is admitted again, which is how the other `FinishEvictionForWorkloads` steps in this file check the end state.
With the 2s sleep from the description, the spec fails in 2 of 2 runs on main and passes with the fix.
Without the sleep, it passed 20 of 20 runs.
The spec is also on release-0.20 at the same lines, so the fix applies there without changes and needs a cherry-pick.
