**What happened**:

When `hack/cherry_pick_pull.sh` cherry-picks several PRs into one PR, it copies each PR's `release-note` block as is ([L346-347](https://github.com/kubernetes-sigs/kueue/blob/216c17e0bdcdd11c1ef93aa85becb04c772cf944/hack/cherry_pick_pull.sh#L346-L347)) and prints them all in a single block ([L179-180](https://github.com/kubernetes-sigs/kueue/blob/216c17e0bdcdd11c1ef93aa85becb04c772cf944/hack/cherry_pick_pull.sh#L179-L180)).
If one PR has a real note and another has `NONE`, the `NONE` ends up as the last line of the real note.

This happened in #18061, which cherry-picks #14954 and #18058 to release-0.19.
We pin the `release-notes` tool at v0.22.0, and it skips a PR only when the whole block is `none`, `n/a` or `na` ([notes.go#L798](https://github.com/kubernetes/release/blob/v0.22.0/pkg/notes/notes.go#L798)).
It publishes any other block as is, so the changelog would get the `NONE` line.
I removed it from #18061 by hand.

**What you expected to happen**:

The script drops `NONE` notes when it combines PRs, and writes a single `NONE` only when every PR's note is `NONE`.

**How to reproduce it (as minimally and precisely as possible)**:

Run the script's own extraction on the two PRs from #18061:

```
for pr in 14954 18058; do
  gh pr view $pr -R kubernetes-sigs/kueue --json body --jq .body | awk '/```release-note/{f=1;next} /```/{f=0} f'
done
```

It prints the #14954 note followed by a `NONE` line, which is what the script puts in the PR body.

**Anything else we need to know?**:

The fix is a few lines where the script collects the notes.
It skips a note that is only `NONE`, and writes `NONE` if nothing is left.
I can open a PR for it.

**Environment**:
- Kueue version (use `git describe --tags --dirty --always`): main at 216c17e0b
- Others: `hack/cherry_pick_pull.sh`, not a runtime component
