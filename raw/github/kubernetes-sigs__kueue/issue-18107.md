## Description

**What would you like to be added**:

MultiKueue support for SparkApplication: a MultiKueue adapter for the SparkApplication integration, so a SparkApplication submitted to a ClusterQueue with a MultiKueue admission check is dispatched to a worker cluster.

spark-operator added `spec.managedBy` to SparkApplication in kubeflow/spark-operator#3221 (merged 2026-10-07). When it is set to `kueue.x-k8s.io/multikueue`, the operator skips reconciliation. The field is immutable and only accepts `sparkoperator.k8s.io/spark-operator` or `kueue.x-k8s.io/multikueue`. This is the same mechanism the other MultiKueue integrations use (for example RayJob).

The latest spark-operator release (v2.5.2) does not include this field yet. Proposed plan:

1. Bump `github.com/kubeflow/spark-operator/v2` to a pseudo-version that includes #3221, the same way `github.com/kubeflow/trainer/v2` is pinned today. Dependency check: <RESULT OF go get + go mod tidy, e.g. "only spark-operator changes, k8s.io/* and controller-runtime unchanged">.
2. Implement `JobWithManagedBy` and a MultiKueue adapter for SparkApplication, with unit and integration tests.
3. Add a MultiKueue e2e test once a spark-operator release with `managedBy` is available, since e2e installs the released chart.
4. Update the MultiKueue docs.

Elastic SparkApplication (#17127, #18068) on MultiKueue would be out of scope for the first version.

Questions:
- Is a pseudo-version acceptable here, or should we wait for the next spark-operator release?
- @reruno, does this overlap with your elastic SparkApplication work?

cc @everpeace @olekzabl

**Why is this needed**:

SparkApplication does not have a MultiKueue adapter yet, so users who run Spark across clusters cannot use MultiKueue with it. MultiKueue support would also help adoption toward the SparkApplicationIntegration Beta graduation (#10260).

### Comment by [@yindia](https://github.com/yindia) — 2026-10-31T18:14:12Z

I looked into step 1 and the pseudo-version doesn't work yet.

Pinning `github.com/kubeflow/spark-operator/v2` (kubeflow/spark-operator#3221) gives `v2.0.0-20261007153619-641c40eb2917`. `go mod tidy` only touches spark-operator; k8s.io/* and controller-runtime stay the same. But Kueue no longer builds:

```
spark-operator/v2/api/v1beta2/zz_generated.openapi.go:298: undefined: v1.WorkloadReference
spark-operator/v2/api/v1beta2/zz_generated.openapi.go:221: undefined: v1.PodStatusResult
```

spark-operator regenerated `zz_generated.openapi.go` against k8s.io/api v0.35.4, and those core/v1 types are gone in v0.37, which Kueue uses. spark-operator master is still on v0.35.4.

Two smaller issues:
- That commit isn't built on top of the v2.5.2 tag, so Go reports the pin as a downgrade from v2.5.2.
- `SPARKOPERATOR_VERSION` comes from go.mod and builds the controller image tag for the Spark e2e. There is no image for a pseudo-version, so the existing Spark e2e would break unless that version is set separately.

Proposal:
1. I open a PR in spark-operator to bump k8s.io to v0.37 (or at least regenerate the OpenAPI file so it builds against v0.37).
2. After that merges, pin the pseudo-version here, the same way trainer is pinned. Keep the Spark e2e on v2.5.2 until a release with `managedBy` ships.
3. Then implement `JobWithManagedBy`, the MultiKueue adapter, unit and integration tests, and docs. Add the MultiKueue e2e once there is a release.

Alternatively, we can wait for the next spark-operator release built on k8s 0.37 and skip the pseudo-version. Which do you prefer?
