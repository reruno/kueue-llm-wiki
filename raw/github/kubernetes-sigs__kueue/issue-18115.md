## Description

**What happened**:

The MultiKueue remote client opens one watch per kind on each worker: `Workload`, plus one for every adapter that implements `MultiKueueWatcher`. That includes the built-in integrations and each `multiKueue.externalFrameworks` entry. Our manager has 11 per worker.

When any one of those watches ends while its context is still live, `establishWatcher` marks the whole remote client disconnected:

https://github.com/kubernetes-sigs/kueue/blob/e691e542aa8737bbe1b9c1b0a31238ea4523c2ce/pkg/controller/admissionchecks/multikueue/multikueuecluster.go#L519-L540

The `multikueue_cluster` reconciler then stops every other watch and rebuilds the client. The client is marked connected again only after every watch is re-established. If one adapter's watch can't be established, the whole connection fails, even though the comment there says "we can function with only the wl watcher":

https://github.com/kubernetes-sigs/kueue/blob/e691e542aa8737bbe1b9c1b0a31238ea4523c2ce/pkg/controller/admissionchecks/multikueue/multikueuecluster.go#L401-L425

`markDisconnected` records `disconnectedSince`. That timestamp starts the `workerLostTimeout` grace for every workload admitted to that worker:

https://github.com/kubernetes-sigs/kueue/blob/e691e542aa8737bbe1b9c1b0a31238ea4523c2ce/pkg/controller/admissionchecks/multikueue/workload.go#L712-L720

So a problem scoped to one job kind is treated as losing the worker. Examples: that kind's watch ends and can't be re-opened, its CRD is reinstalled, or listing that resource is slow. After `workerLostTimeout`, every admitted workload on the worker is set to `Retry` with `Admitting remote lost`. Each one is evicted and its remote copy deleted, including workloads of unrelated kinds.

Watches also end routinely, on the API server's request timeout or on a load balancer's idle timeout (see #16887). So every worker goes through this full teardown each time the first of its watches expires. On v0.19.5 it looks like this (cluster name and CRD group replaced):

```
{"ts":"2026-10-30T23:52:01.047034565Z","caller":"multikueue/multikueuecluster.go:509","msg":"Watch ended","clusterName":"worker-b","watchKind":"example.com/v1alpha1, Kind=Benchmark"}
{"ts":"2026-10-30T23:52:01.047102885Z","caller":"multikueue/multikueuecluster.go:512","msg":"Queue reconcile for reconnect","clusterName":"worker-b","watchKind":"example.com/v1alpha1, Kind=Benchmark","cluster":"worker-b"}
{"ts":"2026-10-30T23:52:01.047937571Z","caller":"multikueue/multikueuecluster.go:509","msg":"Watch ended","clusterName":"worker-b","watchKind":"/v1, Kind=Pod","ctxErr":"context canceled"}
... 8 more "Watch ended" lines with ctxErr "context canceled", Workload included ...
{"ts":"2026-10-30T23:52:01.290711642Z","caller":"multikueue/multikueuecluster.go:507","msg":"Starting watch","clusterName":"worker-b","watchKind":"Workload.kueue.x-k8s.io"}
{"ts":"2026-10-30T23:52:01.290757175Z","caller":"multikueue/multikueuecluster.go:507","msg":"Starting watch","clusterName":"worker-b","watchKind":"batch/v1, Kind=Job"}
... 9 more "Starting watch" lines ...
```

The `Benchmark` watch ended on its own, with no `ctxErr`. The other 10 watches were cancelled, and all 11 were re-opened 240 ms later. A reconnect that fast evicts nothing. A slow one doesn't help either, because the lost-worker clock is already running for every workload on the worker. Each reconnect attempt opens the watches one after another. The per-watch establish timeout is 1m, 2m, 4m, 8m, then capped at 10m, with 5s to 5m20s of backoff between attempts. Four failed attempts already run past the default 15m `workerLostTimeout`.

What this cost us: one worker was disconnected for about 38 minutes. 15 minutes in, about 200 workloads admitted to it were evicted with `Admitting remote lost` within 36 seconds, including long-running multi-node GPU training jobs. The manager logs from that window had rotated, so we can't tell whether the worker was unreachable or a single kind kept the reconnect failing. As written, the code can't tell those two cases apart either. As a mitigation we've raised `workerLostTimeout`.

**What you expected to happen**:

If a watch ends while the worker is reachable, only that watch is re-opened and the worker stays connected. The lost-worker clock starts only when the worker itself can't be reached, not when one job kind's watch ends or fails.

Proposed fix. I'm happy to send a PR if this direction works for you:

1. In `establishWatcher`, when a watch ends with a live context, re-open that kind's watch in place, with backoff. Don't call `markDisconnected` or rebuild the client. A watch opened without a `resourceVersion` begins with synthetic `ADDED` events for every existing object. So the restarted kind resyncs every workload key it maps to, and nothing from the gap is missed.
2. Call `markDisconnected` only when the worker is unreachable: the `Workload` watch can't be re-opened, or a re-open fails with a transport error. A failure scoped to one kind (NotFound or Forbidden for that resource, or an establish timeout on that kind alone) should be retried for that kind and reported through a log line, event, or condition. It should not start `workerLostTimeout`.
3. Apply the same rule when connecting. Don't fail the whole connection when one adapter's watch can't be established, as the existing comment suggests.

**How to reproduce it (as minimally and precisely as possible)**:

I haven't run this end to end. It follows from the code paths above.

1. Set up a manager with one `MultiKueueCluster`, the `batch/job` integration, one `multiKueue.externalFrameworks` entry for a CRD installed on the worker, and `multiKueue.workerLostTimeout: 2m`.
2. Admit a batch Job on the worker and wait for it to run.
3. On the worker, delete the external framework's CRD. Its watch ends, and re-establishing it fails.
4. The `MultiKueueCluster` goes `Active=False`, even though the worker's API server and the remote `Workload` are fine. After 2m, the batch Job's manager `Workload` is set to `Retry` with `Admitting remote lost` and evicted, and the remote Job is deleted.

### Comment by [@apullo777](https://github.com/apullo777) — 2026-11-03T05:33:23Z

> If we flip it immediately then we could have an integration test which verifies it never flipped

There are actually two separate states here. On main, a watch ending immediately marks the client disconnected internally, starting the `workerLostTimeout` clock. But `Active=False` is only written when a reconnect attempt fails, without waiting for the timeout. A successful reconnect leaves `Active=True` throughout.

So that test would also pass on main for a fast reconnect. For #18117, we'd need to observe whether a full reconnect is triggered instead, perhaps through the `multikueue_cluster` reconcile count. The tricky part seems to be making a single watch end in envtest. Happy to help explore that.
