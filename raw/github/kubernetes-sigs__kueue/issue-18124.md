**What happened**:
CodeRabbit refuses to open an issue when the requester has no write access to the repository. It does not run any command. It replies with a draft that it says only "a repository member with write access" can open.

On https://github.com/kubernetes-sigs/kueue/pull/16995, I asked it three times:

1. [Request](…#issuecomment-6540540591) → [refusal](…#issuecomment-6540543188): "GitHub writes require repository write access, which your account does not have in the current permission context."                                                                                                              
  2. Retry without `--label` and with `/kind cleanup` in the body → [refusal](…#issuecomment-6542001751): "Omitting `--label` does not remove that restriction."                                                                                                                                             
  3. [Question](…#issuecomment-6542025368) about what changed → [reply](…#issuecomment-6542029393): the session now requires "verified repository write access for the requester", separate from the GitHub App permissions. CodeRabbit cannot tell what changed.

**What you expected to happen**:
CodeRabbit opens the issue, as it did before for the same account. For example, it opened #17952, #17980 and #17982 on October 29, 2026.

If the restriction is intended, contributors without write access should know it in advance and know what to do instead.

**How to reproduce it (as minimally and precisely as possible)**:
1. As a contributor without write access to `kubernetes-sigs/kueue`, comment on a PR: `@coderabbitai please open an issue to track this and leave it unassigned.`
2. CodeRabbit replies with a draft and does not open the issue.

**Anything else we need to know?**:
  - The last request that CodeRabbit fulfilled for me was #17982 on October 29, 2026. The first refused request was on October 31, 2026.                    
  - `.coderabbit.yaml` has not changed since October 9, 2026, so the change is probably in the CodeRabbit organization settings or on the CodeRabbit side.  
  - Since October 29, CodeRabbit has opened issues only for maintainers with write access, for example #17996, #18074 and #18101.

@HarshithaMS005 thanks for picking this up. Some findings and a fix idea.

**The refusal is inconsistent, not a hard cut-off.** After October 31, CodeRabbit still opened issues for requesters who are not maintainers, for example #18513 (for me, November 9), #18577, #18410, #18234, #18187 and #18186. It refused on #18554 (November 12) and #17515.
On #18554, its analysis chain ran `gh api repos/kubernetes-sigs/kueue/collaborators/<user>/permission`, got `read`, and refused. So CodeRabbit appears to decide on its own, per run, whether to check permissions and what counts as enough. The repository gives it no rule. The "since October 29" statement in the description is therefore not accurate.

**Proposal:** give CodeRabbit an explicit rule in `cmd/experimental/skills/kueue-pr-issue-workflow/SKILL.md`, under "Opening issues". CodeRabbit already reads this skill through `AGENTS.md`. `tone_instructions` in `.coderabbit.yaml` is limited to 250 characters, so it is not a good place.

```markdown
- CodeRabbit AI (@coderabbitai) opens an issue when the requester is a member
  of the `kubernetes-sigs` GitHub organization, even without repository write
  permission. Check membership with `gh api orgs/kubernetes-sigs/members/<user>`
  (204 means member).
```

Organization membership matches the Prow trust model, where members do not need `/ok-to-test`, and a PR cannot spoof it.

**Validation:** after the change merges, a `kubernetes-sigs` member without write access asks CodeRabbit to open an issue. If it still refuses, the restriction is enforced by CodeRabbit itself, and the next step is the CodeRabbit organization settings or CodeRabbit support.
