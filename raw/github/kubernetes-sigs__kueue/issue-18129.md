## Description

**What happened**:

A Job with `nodeSelector: {node-group: tas}` is admitted with implicit TAS to a ClusterQueue whose only flavor is a TAS flavor with `nodeLabels: {node-group: tas}`. After the flavor's label is changed to `node-group: other`, the next reconcile of the Job suspends it. A status-only update, such as `status.ready` going from 0 to 1, is enough to trigger it.

With `status.active` above 0, restoring the template is then rejected (`restore info: Job.batch "job" is invalid: spec.template: Invalid value: ...`), so the Workload stays admitted and the reconcile retries on that error, as in #18004.
With `status.active` at 0, as in envtest, the same pass deletes the admitted Workload, and Kueue then creates a new one, which no longer fits the flavor. Events from an earlier run of the same steps, with other object names:

```
Normal   Stopped           Job/probe-job                No matching Workload; restoring pod templates according to existent Workload
Normal   DeletedWorkload   Job/probe-job                Deleted not matching Workload: rf-tas-probe-hhzqx/job-probe-job-ad007
Normal   CreatedWorkload   Job/probe-job                Created Workload: rf-tas-probe-hhzqx/job-probe-job-ad007
Warning  NoMatchingFlavor  Workload/job-probe-job-ad007  couldn't assign flavors to pod set main: flavor probe-flavor doesn't match node affinity
```

The new label conflicts with the Job's own nodeSelector, so `podset.Merge` fails and `expectedRunningPodSets` returns nil before it marks the topology request as unconstrained ([reconciler.go#L1718-L1729](https://github.com/kubernetes-sigs/kueue/blob/4a2bb59f9b3ce4474dc79280bcf3ab381951d57c/pkg/controller/jobframework/reconciler.go#L1718-L1729)).
`EquivalentToWorkload` then compares the Job with `wl.Spec.PodSets` ([reconciler.go#L1774-L1785](https://github.com/kubernetes-sigs/kueue/blob/4a2bb59f9b3ce4474dc79280bcf3ab381951d57c/pkg/controller/jobframework/reconciler.go#L1774-L1785)).
The running Job carries the `kueue.x-k8s.io/podset-unconstrained-topology: "true"` annotation that Kueue added at start, while the Workload's topology request has only `podIndexLabel`.
The two don't match, so `ensureOneWorkload` stops the Job, and deletes the Workload once the stop succeeds ([reconciler.go#L1246-L1282](https://github.com/kubernetes-sigs/kueue/blob/4a2bb59f9b3ce4474dc79280bcf3ab381951d57c/pkg/controller/jobframework/reconciler.go#L1246-L1282)).

**What you expected to happen**:

The Job keeps running and its Workload stays admitted, as it does when the Job sets the annotation itself.
The TAS KEP handles a PodSet without the annotation "as if it had the `podset-unconstrained-topology: true` annotation" ([README.md#L1683-L1695](https://github.com/kubernetes-sigs/kueue/blob/4a2bb59f9b3ce4474dc79280bcf3ab381951d57c/keps/2724-topology-aware-scheduling/README.md?plain=1#L1683-L1695)), and #13738, which made the nodeLabels of TAS flavors mutable, says "Admitted workloads keep their quota reservation and topology assignment".

**How to reproduce it (as minimally and precisely as possible)**:

Add this spec to the `Job controller with TopologyAwareScheduling` Describe in `test/integration/singlecluster/controller/jobs/job/job_controller_test.go`:

<details>
<summary>Spec</summary>

```go
ginkgo.It("should keep a running implicit TAS Job when its flavor's nodeLabels change", func() {
	job := testingjob.MakeJob("job", ns.Name).
		Queue(kueue.LocalQueueName(localQueue.Name)).
		NodeSelector(nodeGroupLabel, "tas").
		Request(corev1.ResourceCPU, "100m").
		Obj()
	behavioral.MustCreate(ctx, k8sClient, job)
	wl := behavioral.ExpectWorkloadsInNamespace(ctx, k8sClient, ns.Name, 1)[0]
	behavioral.ExpectWorkloadsToBeAdmitted(ctx, k8sClient, &wl)
	behavioral.ExpectJobUnsuspended(ctx, k8sClient, client.ObjectKeyFromObject(job))

	gomega.Eventually(func(g gomega.Gomega) {
		g.Expect(k8sClient.Get(ctx, client.ObjectKeyFromObject(tasFlavor), tasFlavor)).To(gomega.Succeed())
		tasFlavor.Spec.NodeLabels[nodeGroupLabel] = "other"
		g.Expect(k8sClient.Update(ctx, tasFlavor)).To(gomega.Succeed())
	}, behavioral.Timeout, behavioral.Interval).Should(gomega.Succeed())
	gomega.Eventually(func(g gomega.Gomega) {
		rf := &kueue.ResourceFlavor{}
		g.Expect(indexedClient.Get(ctx, client.ObjectKeyFromObject(tasFlavor), rf)).To(gomega.Succeed())
		g.Expect(rf.Spec.NodeLabels[nodeGroupLabel]).To(gomega.Equal("other"))
	}, behavioral.Timeout, behavioral.Interval).Should(gomega.Succeed())

	// Any Job event runs the reconciler; an annotation change is the simplest one.
	gomega.Eventually(func(g gomega.Gomega) {
		g.Expect(k8sClient.Get(ctx, client.ObjectKeyFromObject(job), job)).To(gomega.Succeed())
		metav1.SetMetaDataAnnotation(&job.ObjectMeta, "example.com/trigger", "1")
		g.Expect(k8sClient.Update(ctx, job)).To(gomega.Succeed())
	}, behavioral.Timeout, behavioral.Interval).Should(gomega.Succeed())

	gomega.Consistently(func(g gomega.Gomega) {
		g.Expect(k8sClient.Get(ctx, client.ObjectKeyFromObject(job), job)).To(gomega.Succeed())
		g.Expect(job.Spec.Suspend).To(gomega.Equal(new(false)))
	}, behavioral.LongConsistentDuration, behavioral.Interval).Should(gomega.Succeed())
})
```

**Anything else we need to know?**:

- Adding a toleration to the flavor, or a nodeLabel with a new key, keeps the Job running. Of these flavor changes, only a nodeLabel value that conflicts with the Job's own nodeSelector makes `podset.Merge` fail.
- The unconstrained marking in `expectedRunningPodSets` and the topology request comparison came with #14585.
- I reproduced it on main and on v0.20.4. release-0.19 rejects changes to the nodeLabels of a TAS flavor.
