## Description

**What happened**:

With `ConcurrentAdmission` and TAS, when a node in the topology assignment fails, the node controller marks both the admitted Variant and its parent Workload as unhealthy (the parent holds a copy of the Variant's assignment). The Variant is moved to a healthy node, but the parent also goes through the second pass, although parents are never queued or held in the scheduler cache.
- **Enough capacity**: the admission write is skipped because the cache does not hold the parent (#15761), and the second pass retries forever. The parent keeps the failed node, so the TopologyUngater never ungates the replacement Pods. **The Job is stuck.**
- **Capacity taken by the Variant**: no replacement is found and the parent is evicted with `EvictedDueToNodeFailures`. **The Job restarts.**

**What you expected to happen**:

Only the Variant is replaced, and the parent gets the Variant's new topology assignment. The Job keeps running.

**How to reproduce it (as minimally and precisely as possible)**:

1. Start the TAS kind cluster (`E2E_MODE=dev make kind-image-build test-tas-e2e-baseline`). The e2e config already enables `ConcurrentAdmission`.
2. Create a ClusterQueue with `concurrentAdmissionPolicy.migration.mode: TryPreferredFlavors` and two TAS flavors (rack `r1` and rack `r2`).
3. Submit a Job with 2 Pods and `kueue.x-k8s.io/podset-required-topology: cloud.provider.com/topology-rack`.
4. After the Pods run, taint their node: `kubectl taint node kind-worker zz-test=1:NoExecute`.
5. The Variant moves to another node, but the parent keeps `unhealthyNodes: [kind-worker]` and the replacement Pods stay gated by `kueue.x-k8s.io/topology`.
