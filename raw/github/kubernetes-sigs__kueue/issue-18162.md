## Description

**What would you like to be added**:

When `kueuectl list pods --for pod/NAME` resolves a Pod group whose name is stored only in `kueue.x-k8s.io/pod-group-name` annotation, print a warning to stderr before listing Pods. The warning should state that Kubernetes cannot select Pods by annotation, identify the scan scope, and explain how to narrow it with the command namespace or an existing selector.

The command must preserve its current result: it should still list the complete annotation-based Pod group by filtering the returned Pods client-side. Label-based Pod groups and standalone Pods must remain silent and unchanged.

**Why is this needed**:

Kubernetes supports label selectors but not annotation selectors. The existing annotation-group support, added for #15709, correctly lists and filters Pods client-side, but can require listing every Pod in the selected namespace (or every namespace with `--all-namespaces`) to return a small group. The command currently gives no indication of this potentially expensive scan, so it can appear unexpectedly slow and increase API-server, network, and client memory usage in large clusters.

**Completion requirements**:

- [ ] Annotation-based `kueuectl list pods --for pod/NAME` writes one actionable warning to stderr before it issues the broad Pod list.
- [ ] The warning explains why server-side filtering is unavailable and names the effective scan scope.
- [ ] The warning gives a concrete way to narrow the request when applicable.
- [ ] Label-based groups and standalone Pods retain their current output and do not emit the warning.
- [ ] Unit tests cover the warning and unchanged output for the other group forms.

This enhancement requires the following artifacts:

- [ ] Design doc
- [ ] API change
- [ ] Docs update

No design document, API change, or standalone documentation update is expected; command help and tests should make the behavior discoverable.
