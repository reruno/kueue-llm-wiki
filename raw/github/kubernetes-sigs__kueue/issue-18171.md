## Description

/kind bug
/area dra

### What happened:

After upgrading Kueue from `v0.17.1` to `v0.19.6` (where `KueueDRAIntegration` and `KueueDRARejectWorkloadsWhenDRADisabled` are Beta and enabled by default), workloads (`JobSet` / `Job`) that use standard Kubernetes extended resources for accelerator quota (`nvidia.com/gpu` or `google.com/tpu`) **alongside** a pass-through DRA `ResourceClaimTemplate` with `allocationMode: All` for node-local networking or multi-node NVLink fail admission and remain permanently `Suspended`.

`kueue-controller-manager` logs the following reconciler error and emits a `DRAFailure` event on the `Workload`:

```text
ERROR controller/controller.go:474 "Reconciler error" controller="workload_controller" controllerGroup="kueue.x-k8s.io" controllerKind="Workload" err="spec.podSets[0].template.spec.resourceClaims[0].devices.requests[0].exactly.allocationMode: Invalid value: \"All\": ResourceClaimTemplate default-rdma: AllocationMode 'All' is not supported"
```

This impacts standard cloud/hardware DRA drivers where DRA is used purely to attach node-local companion devices (with `allocationMode: All`) while Kueue only manages quota for the primary accelerators via standard `resources.requests`:
1. **GKE DRANET (`mrdma.google.com` / `netdev.google.com`):** Uses a `ResourceClaimTemplate` (`default-rdma` / `default-netdev`) with `allocationMode: All` to attach all RDMA or secondary NICs on the node to the pod, while GPU/TPU quota is tracked via `nvidia.com/gpu` or `google.com/tpu` in `ClusterQueue`.
2. **NVIDIA DRA Driver `ComputeDomain` (`resource.nvidia.com/v1beta1`):** Automatically generates a channel `ResourceClaimTemplate` with `allocationMode: All` for multi-node NVLink (GB200 / A4X), while GPU quota is tracked via `nvidia.com/gpu`.

### What you expected to happen:

When a `ResourceClaimTemplate` references a `deviceClassName` (such as `mrdma.google.com`, `netdev.google.com`, or an NVIDIA `ComputeDomain` channel class) that is **not** configured in Kueue's `resources.deviceClassMappings` (or is configured as unmanaged/pass-through), Kueue should not block admission of the workload due to `allocationMode: All` (or unmapped `DeviceClass`), and should allow `kube-scheduler` to allocate those DRA claims natively while Kueue enforces quota on the resources covered by the `ClusterQueue` (`nvidia.com/gpu`, `google.com/tpu`, `cpu`, `memory`).

Currently, the only workaround is to disable DRA integration globally across the entire cluster (`KueueDRAIntegration=false` and `KueueDRARejectWorkloadsWhenDRADisabled=false`), which prevents using Kueue DRA quota management for any device class on clusters that also use DRANET or NVIDIA `ComputeDomain`.

### How to reproduce it (as minimally and precisely as possible):

1. Deploy Kueue `v0.19.6` with default feature gates (`KueueDRAIntegration=true`, `KueueDRARejectWorkloadsWhenDRADisabled=true`) and a `ClusterQueue` / `LocalQueue` covering `nvidia.com/gpu` (with no `deviceClassMappings` in Kueue's `Configuration`).
2. Create a DRANET `ResourceClaimTemplate` using `allocationMode: All`:
   ```yaml
   apiVersion: resource.k8s.io/v1
   kind: ResourceClaimTemplate
   metadata:
     name: default-rdma
   spec:
     spec:
       devices:
         requests:
         - name: req-0
           exactly:
             deviceClassName: mrdma.google.com
             allocationMode: All
   ```
3. Submit a Kueue-managed `Job` or `JobSet` that requests `nvidia.com/gpu: 8` and references `default-rdma`:
   ```yaml
   apiVersion: batch/v1
   kind: Job
   metadata:
     name: sample-rdma-job
     labels:
       kueue.x-k8s.io/queue-name: local-queue
   spec:
     template:
       spec:
         restartPolicy: Never
         resourceClaims:
         - name: rdma
           resourceClaimTemplateName: default-rdma
         containers:
         - name: worker
           image: busybox
           command: ["sh", "-c", "sleep 10"]
           resources:
             requests:
               nvidia.com/gpu: 8
             limits:
               nvidia.com/gpu: 8
             claims:
             - name: rdma
   ```
4. Observe that the `Workload` fails reconciliation with:
   `Failed to process DRA resources for workload: spec.podSets[0].template.spec.resourceClaims[0].devices.requests[0].exactly.allocationMode: Invalid value: "All": ResourceClaimTemplate default-rdma: AllocationMode 'All' is not supported`.

### Root Cause & Proposed Fix in Kueue (`pkg/dra/claims.go`):

In `pkg/dra/claims.go` (`GetResourceRequestsForResourceClaimTemplates` -> `countDevicesPerClass`):
1. `countDevicesPerClass` unconditionally validates every request in every `ResourceClaimTemplate` referenced by the pod and rejects `resourcev1.DeviceAllocationModeAll` before checking whether the request's `DeviceClassName` is even managed by Kueue (`deviceClassMappings`).
2. Furthermore, if `DeviceClassName` is not present in `deviceClassMappings`, `GetResourceRequestsForResourceClaimTemplates` returns an unmapped `DeviceClass` error rather than skipping unmanaged DRA device classes.

**Suggested approaches:**
- **Option A (Skip unmapped `DeviceClass`es in `pkg/dra/claims.go`):** Before enforcing `AllocationMode == ExactCount` (or selector/config restrictions) on a DRA request in `countDevicesPerClass` / `GetResourceRequestsForResourceClaimTemplates`, check whether `DeviceClassName` is present in Kueue's `resources.deviceClassMappings`. If a `DeviceClass` is not mapped in `deviceClassMappings`, treat it as pass-through (unmanaged by Kueue quota) and skip DRA quota accounting/validation for that request.
- **Option B (Explicit pass-through / ignored `DeviceClass`es list):** If rejecting unmapped `DeviceClass`es by default is intentional to catch typos, allow cluster admins to configure `unmanagedDeviceClasses` / `ignoredDeviceClasses` (or allow mapping `deviceClassName` to an empty/pass-through target in `deviceClassMappings`) so pass-through DRA drivers using `allocationMode: All` (`mrdma.google.com`, `netdev.google.com`, `compute-domain.nvidia.com`) are skipped during Kueue's DRA preprocessing.

### Environment:
- Kubernetes version: `v1.35.x` (GKE)
- Kueue version: `v0.19.6` (Helm chart `oci://registry.k8s.io/kueue/charts/kueue`)

### Comment by [@sohankunkerkar](https://github.com/sohankunkerkar) — 2026-11-02T16:10:39Z

Thanks for the detailed report! I ran both templates through a unit test on main and got the same errors, but the two stacks actually break for different reasons.

ComputeDomain isn't hitting the `All` check. The claim template the NVIDIA driver creates is a plain `ExactCount` request for one `compute-domain-default-channel.nvidia.com` device. The `allocationMode` you saw sits inside the driver's opaque parameters. So it only fails as "not mapped", and you can unblock it today on 0.19 and 0.20: map that class in `deviceClassMappings` to its own resource and give that resource a large `nominalQuota` in the ClusterQueue.

DRANET is different. GKE's `all-mrdma` and `all-netdev` templates use `allocationMode: All`, and Kueue rejects `All` even for mapped classes, since it can't know the device count before a node is picked. If you know how many NICs a node has, an `ExactCount` template like GKE's `two-mrdma` plus a mapping works the same way as ComputeDomain. With `All`, the only option today is turning off both `KueueDRAIntegration` and `KueueDRARejectWorkloadsWhenDRADisabled`. Your `nvidia.com/gpu` requests still get charged that way.

I don't think we can skip unmapped classes in general (option A). We kept rejecting them in #10504 so that an unmapped GPU class can't skip quota. Option B makes sense to me though, something like:

```yaml
resources:
  excludeDeviceClassNames:   # name TBD
  - mrdma.google.com
  - netdev.google.com
```

Kueue wouldn't charge requests for those classes, whatever the allocation mode, and would skip its ResourceSlice check for them. TAS would still simulate the claims when `KueueDRADeviceFeasibility` is on, so pods only land on nodes with free NICs. Validation would reject a class that's both listed and mapped. With MultiKueue, the manager and workers need the same list, because the manager charges too. Since it's a new config field, I'd put it behind a new alpha gate, update KEP-2941, and target 0.21 rather than backporting it.

**Two known gaps stay when the feasibility gate is on:** TAS can put more `All` pods on a node than will run, and preemption doesn't free a victim's devices. Both are already beta items in the KEP. With 8-GPU pods that fill a node, you won't hit the first one.

### Comment by [@shubpal07](https://github.com/shubpal07) — 2026-11-05T14:11:54Z

Thanks @sohankunkerkar ! Option B (`resources.excludeDeviceClassNames`) works well for our use case in Cluster Toolkit.

1. **Short-term (`v0.19` / `v0.20`):** We are disabling the DRA feature gates so `nvidia.com/gpu` and `google.com/tpu` remain quota-managed by Kueue while Kubernetes handles the DRA claims directly (see GoogleCloudPlatform/cluster-toolkit#6620). Note for anyone else applying this on `v0.19`: because `KueueDRAIntegrationExtendedResource` and `KueueDRAIntegrationPartitionableDevices` also default to `true` in `v0.19`, all four gates must be set to `false` (`KueueDRAIntegration=false`, `KueueDRARejectWorkloadsWhenDRADisabled=false`, `KueueDRAIntegrationExtendedResource=false`, and `KueueDRAIntegrationPartitionableDevices=false`) so `kueue-controller-manager` passes startup validation.
2. **Long-term (`v0.21` `excludeDeviceClassNames`):** Skipping both the `allocationMode: All` check and the unmapped `DeviceClass` check for excluded classes will let us exclude all three companion device classes without needing extra quota mappings in `ClusterQueue`:
   ```yaml
   resources:
     excludeDeviceClassNames:
     - mrdma.google.com
     - netdev.google.com
     - compute-domain-default-channel.nvidia.com
   ```
