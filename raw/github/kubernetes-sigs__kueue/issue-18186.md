## Description

**What happened**:

Kueue-managed, non-elastic SparkApplications can bypass the dynamic-allocation restriction through `spec.sparkConf["spark.dynamicAllocation.enabled"]: "true"` while `spec.dynamicAllocation` is absent or disabled. This risks executor resource use beyond reserved quota.

In #17127, the new SparkConf-only validation protects elastic applications. The non-elastic validation still checks only `spec.dynamicAllocation.enabled`. This report is based on code inspection; a real-cluster quota overrun has not been reproduced here.

**What you expected to happen**:

Reject SparkConf-based dynamic allocation for Kueue-managed SparkApplications. Require the supported structured `spec.dynamicAllocation` configuration and elastic-job opt-in.

Acceptance criteria:
- Validate create and update requests, including non-elastic applications and disabled elastic feature gates.
- Return a clear field error for unsupported SparkConf dynamic allocation.
- Add webhook unit and integration regression tests.
- Preserve supported structured dynamic allocation and unmanaged-application behavior; document the restriction.

**How to reproduce it (as minimally and precisely as possible)**:

1. Enable SparkApplication integration.
2. Submit a queue-associated, non-elastic SparkApplication with `spec.sparkConf["spark.dynamicAllocation.enabled"]: "true"` and `spec.dynamicAllocation` absent or disabled.
3. Check whether admission accepts it, then compare executor resource use with the Workload's reserved quota.

**Anything else we need to know?**:

Affected areas: `pkg/controller/jobs/sparkapplication/sparkapplication_webhook.go`, its unit tests, SparkApplication webhook integration tests, and SparkApplication documentation.
