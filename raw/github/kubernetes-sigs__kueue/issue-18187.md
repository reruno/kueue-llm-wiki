## Description

**What happened**:

Kueue-managed, non-elastic SparkApplications can bypass the dynamic-allocation restriction through `spec.sparkConf["spark.dynamicAllocation.enabled"]: "true"` when `spec.dynamicAllocation` is absent or disabled. This risks executor resource use beyond reserved quota.

The guard in #17127 covers elastic applications. Non-elastic validation checks only `spec.dynamicAllocation.enabled`. This is based on code inspection; a real-cluster quota overrun has not been reproduced here.

**What you expected to happen**:

Reject SparkConf-based dynamic allocation for Kueue-managed SparkApplications. Require supported structured `spec.dynamicAllocation` configuration and elastic-job opt-in.

Acceptance criteria:
- Validate create and update requests, including non-elastic applications and disabled elastic feature gates.
- Return a clear field error for unsupported SparkConf dynamic allocation.
- Add webhook unit and integration regression tests.
- Preserve supported structured dynamic allocation and unmanaged-application behavior; document the restriction.

**How to reproduce it (as minimally and precisely as possible)**:

1. Enable SparkApplication integration.
2. Submit a queue-associated, non-elastic SparkApplication with `spec.sparkConf["spark.dynamicAllocation.enabled"]: "true"` and `spec.dynamicAllocation` absent or disabled.
3. Check admission, then compare executor resource use with the Workload's reserved quota.

**Anything else we need to know?**:

Affected areas: `pkg/controller/jobs/sparkapplication/sparkapplication_webhook.go`, its unit tests, SparkApplication webhook integration tests, and SparkApplication documentation.
