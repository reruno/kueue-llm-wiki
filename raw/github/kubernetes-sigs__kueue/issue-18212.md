## Description

**What happened**:

ElasticJobUngater and TopologyUngater can remove their gates from different replacement pods. Both controllers then consider admission consumed, but neither replacement can run.

**What you expected to happen**:

Coordinate pod selection and quota accounting between both ungaters so that an eligible replacement can pass both gates without exceeding admission or topology capacity.

**How to reproduce it (as minimally and precisely as possible)**:

Reported scenario for an elastic Job or RayCluster using TAS:
1. Admit two workers: rank 0 in domain r1 and rank 1 in r2.
2. Scale to three workers while admission stays at two.
3. Rank 0 fails. Rank 2 passes both gates and uses the lent slot in r1.
4. Create rank 0's replacement, then fail and replace rank 1. Both replacements have both gates.
5. ElasticJobUngater selects rank 0 for the remaining admission slot.
6. TopologyUngater selects rank 1 because r1 is occupied and r2 is free.

Rank 0 retains its topology gate. Rank 1 retains its elastic gate. Rank 2 remains running.

**Anything else we need to know?**:

Affected areas: `pkg/controller/elasticjobs/elastic_job_ungater.go` and TAS TopologyUngater selection/accounting.

Add a regression test for this sequence. Verify progress with either controller reconciliation order while preserving admission and per-domain limits. The reporter suspects this also predates completion-index ordering; name ordering can produce the same mismatch.
