## Description

**What happened**:

The webhook validation for the `kueue.x-k8s.io/max-exec-time-seconds` label and the code that reads it parse the value with different integer widths.

- `validateCreateForMaxExecTime` (pkg/controller/jobframework/validation.go) uses `strconv.Atoi`, which is 64-bit on amd64/arm64, and accepts any value greater than 0 that fits in an int.
- `MaximumExecutionTimeSecondsForObject` (pkg/controller/jobframework/utils.go) uses `strconv.ParseInt(strVal, 10, 32)`, so a value above 2147483647 returns an error and the function returns `nil`.

As a result, a job created with a value such as `2147483648` or `3000000000` is admitted by the webhook, but the Workload gets no `maximumExecutionTimeSeconds`. The job then runs with no execution time limit, and nothing tells the user.

**What you expected to happen**:

A value that cannot be honored (above the int32 maximum, which is the type of `Workload.spec.maximumExecutionTimeSeconds`) should be rejected at creation with a validation error, instead of being accepted and silently dropped.

**How to reproduce it (as minimally and precisely as possible)**:

Verified at unit level only, on upstream main (731f02e6d):

1. Add a case to the `TestValidateCreate` table in pkg/controller/jobs/job/job_webhook_test.go with the label `kueue.x-k8s.io/max-exec-time-seconds: "2147483648"` (or `"3000000000"`) and no expected validation errors. The case fails because validation currently returns no error.
2. Call `MaximumExecutionTimeSecondsForObject` on an object carrying the same label. It returns `nil` for `2147483648` and `3000000000`, and `2147483647` for `2147483647`.

I did not reproduce this through a real admission webhook or on a cluster. The end-to-end effect (a job running without a limit) follows from reading the code paths above and from the two unit-level results; it has not been observed in a running cluster.

**Anything else we need to know?**:

Proposed fix: parse the label with `strconv.ParseInt(strVal, 10, 32)` in the webhook so it matches the reader. The update path (`validateUpdateForMaxExecTime`) only checks immutability and is not changed.
