## Description

**What happened**:

Changing a ClusterQueue's custom metric label values without changing its Cohort can leave stale series in `kueue_cohort_subtree_admitted_active_workloads`. Relabel handling and incremental per-label counts were deferred from PR #18078.

**What you expected to happen**:

Update each affected Cohort's per-label counts immediately after a relabel. Remove obsolete series when no ClusterQueue contributes to them. Preserve the correct total across all series.

**How to reproduce it (as minimally and precisely as possible)**:

1. Enable custom metric labels sourced from ClusterQueues.
2. Admit a Workload in a ClusterQueue belonging to a Cohort.
3. Change the ClusterQueue's configured label value without changing its Cohort.
4. Inspect the Cohort gauge before any further Workload event.

The old label series can retain its count instead of transferring the contribution to the new label value.

**Anything else we need to know?**:

Required changes:
- Handle relabels even when the old and new parent Cohorts are identical.
- Maintain incremental per-label counts for Workload admission and deletion to avoid repeated subtree scans.
- Cover relabels, shared label values, nested Cohorts, moves, and deletion with regression tests. Verify that summed series equal actual admitted counts and that behavior without custom labels remains unchanged.

Affected areas: `pkg/cache/scheduler/{cache.go,clusterqueue.go,cohort.go,cohort_metrics.go,cohort_metrics_test.go}` and custom-label tracking in `pkg/metrics/custom_labels.go`.
