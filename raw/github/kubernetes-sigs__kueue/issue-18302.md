### Comment by [@yuluo-yx](https://github.com/yuluo-yx) — 2026-11-04T12:26:32Z

I broke down the five successful runs listed above. The bottleneck looks like repeated Go compilation. Approximate average wall-clock times were:

| Stage | Average |
|---|---:|
| Main image, four architectures | 5m33s |
| Importer | 1m51s |
| KueueViz backend | 1m00s |
| KueueViz frontend | 15s |
| Populator | 57s |
| Priority booster | 54s |
| Startup, cleanup, and remaining overhead | 1m10s |

The stages run sequentially, while the main image's four architecture builds overlap. Counting those overlapping builds once, compilation accounts for about 80% of the job's wall time; `go mod download` accounts for about 3%. All five samples completed their download/build retry wrappers on the first attempt. For example, [this run](https://storage.googleapis.com/kubernetes-ci-logs/pr-logs/pull/kubernetes-sigs_kueue/17962/pull-kueue-build-image-main/2117607772936736768/build-log.txt) shows the individual BuildKit steps and Make timings.

I would start with an experiment that preserves the existing image and architecture coverage:

1. **Keep one builder for the whole job and share the Go build cache.** `image-local-build` currently creates a `docker-container` builder and removes it immediately after the main image; the remaining builds use the `default` Docker builder. Keep a job-scoped builder until all images finish, and add cache mounts for `GOCACHE` in the Go build stages. This should allow subsequent images to reuse compatible standard-library and dependency compilation results. Builder reuse alone would not share caches created inside separate `RUN` layers. Start with reuse within one job, without depending on a persistent cache across Prow jobs.
2. **Check redundant module downloads separately.** The root module has vendored dependencies, so some download steps may be unnecessary. The KueueViz backend is a separate module and needs its own treatment. This is a smaller opportunity than compilation reuse.
3. **Tune concurrency after measuring the cache change.** The job has 4.7 CPUs and 6 GiB of memory, and already compiles four architectures concurrently. I would measure the build containers' effective Go parallelism and peak memory before adding outer `make -j` parallelism, particularly given the recent image-build OOMs addressed in #18073.

For validation, I would compare several cold-job baseline/candidate runs at the same source revision, recording whole-job and per-stage times, cache reuse, and peak memory. All six images and the existing architecture coverage should still pass. These are profiling results and a proposed experiment; I have not measured a speedup for the proposed changes yet.

Yes, I confirmed that **6Gi is both the memory request and the hard limit**, not just the request:

- [Current Prow configuration, pinned to the inspected revision](https://github.com/kubernetes/test-infra/blob/1f5d18b7d4e46e6212adff61d6a271288ab723e3/config/jobs/kubernetes-sigs/kueue/kueue-presubmits-main.yaml#L1862-L1903): `pull-kueue-build-image-main` has `requests.memory: 6Gi` and `limits.memory: 6Gi`, with CPU request/limit both `4700m`.
- [The recorded ProwJob for one of the five profiled runs](https://storage.googleapis.com/kubernetes-ci-logs/pr-logs/pull/kubernetes-sigs_kueue/17962/pull-kueue-build-image-main/2117607772936736768/prowjob.json): `spec.pod_spec.containers[0].resources` confirms those same values in the executed job.

Doubling the memory budget would mean setting both the request and limit to **12Gi**, while leaving the CPU allocation unchanged.

One clarification to my earlier comment: #18073 fixed OOMs in the separate Cloud Build postsubmit image-pushing job. It is useful context for peak compilation memory, but it does not establish that this Prow presubmit has itself been OOM-killed.
