## Description

# Summary

When multiple ClusterQueue heads are processed within a single scheduling cycle, a workload that was nominated with `Fit` (no preemption targets) can be erroneously admitted right away (`Fit`) even when its assigned TAS node capacity is still occupied by a workload whose preemption was triggered earlier in the same scheduling cycle.

# Background

A Kueue scheduling cycle (`s.schedule`) essentially consists of 3 phases:

1. **Nomination** (`s.nominate`): Each ClusterQueue head is evaluated **in isolation** against the initial snapshot (taken at the start of the cycle).
2. **Ordering** (`s.makeIterator`): Order the heads according to some "quality" of the assignments (details not relevant here).
3. **Processing** (`s.processEntry`): The entries are processed **incrementally**, in order to detect potential **overlaps**:
   - Basically, whenever an entry `e` fits, possibly with preemptions:
     - its usage is booked into `snapshot` (`bookUsage`)
     - its preemption targets (if any) are added to `preemptedWorkloads`, and eviction is initiated asynchronously while the entry itself waits (`WaitingForPreemptedWorkloads`).
   - Before that, however, we check (`updateAssignmentIfNeeded`) if `e` overlaps with the already-considered entries:
     - `e.checkFits()` calls `fits()`, which unconditionally removes all `preemptedWorkloads` from the snapshot (`snapshot.SimulateWorkloadUsageRemoval(merged.Workloads())`) before calling `cq.Fits(*usage)`.

Because `preemptedWorkloads` are subtracted during `e.checkFits()`, `cq.Fits()` evaluates `e` against the **post-preemption** state (i.e. after all previous admissions from this cycle get in, and after their preemption victims get out).

This means that `e` will get a `Fit` (and be admitted immediately) if it:

- **fits** against the **initial** state (snapshot taken at the start of scheduling cycle)
- **fits** against the **post-preemption** state (as described above).

However, these conditions are not sufficient. To allow an immediate `Fit`, we **should also check** if `e` fits against the "immediate future" state, i.e. the initial state (including the preemption victims that haven't yet been preempted as of now) **plus** the entries preceding `e` which have already got a `Fit` and booked their usage.

Otherwise, we may overlook an overlaps.

Whenever `e`'s placement does not fit against "immediate future", it should be recomputed, or `e` should be demoted at least to `DeferredFit`.

# Example

_An e2e test reproducing this scenario is available at [this branch](https://github.com/kubernetes-sigs/kueue/compare/main...olekzabl:kueue:br59)._
_(For clarity: this test **expects** the bug to happen, and passes)._

1. A single TAS node has free capacity of 10 CPU, and currently runs a low-priority workload `wl0` using 6 CPU.
2. Three ClusterQueues (`cq1`, `cq2`, `cq3`) in a shared Cohort have head workloads ordered by priority (`wl1` > `wl2` > `wl3` > `wl0`):
   - `wl1`: 2 CPU
   - `wl2`: 3 CPU
   - `wl3`: 4 CPU
3. In a single scheduling cycle:
   - **Nomination (in isolation against `wl0` = 6 CPU)**:
     - `wl1` fits (`6 + 2 <= 10`) -> nominated as `Fit` (`preemptionTargets = []`).
     - `wl2` fits (`6 + 3 <= 10`) -> nominated as `Fit` (`preemptionTargets = []`).
     - `wl3` fits (`6 + 4 <= 10`) -> nominated as `Fit` (`preemptionTargets = []`).
   - **Sequential processing (`wl1` -> `wl2` -> `wl3`)**:
     - `wl1` (2 CPU) is processed: `6 + 2 <= 10` -> admitted immediately as `Fit`.
     - `wl2` (3 CPU) is processed: `6 + 2 + 3 > 10` -> fails `checkFits()` with `FitsCheckNoTAS`, recomputes assignment, and preempts `wl0` (`mode = Preempt`, `preemptionTargets = [wl0]`). `wl0` is added to `preemptedWorkloads`, `wl2`'s 3 CPU is booked, and `wl2` waits (`WaitingForPreemptedWorkloads`).
     - `wl3` (4 CPU) is processed: `e.checkFits()` removes `preemptedWorkloads` (`wl0`, 6 CPU) and checks `2 (wl1) + 3 (wl2) + 4 (wl3) <= 10`, returning `FitsCheckOk`. Neither `needsTASRecompute` nor `needsOverlapRecompute` triggers, so `wl3` is **erroneously admitted** right away as `Fit` - while `wl0` (6 CPU, terminating) and `wl1` (2 CPU, running) occupy 8 CPU on the node.
