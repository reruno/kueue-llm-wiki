## Description

**What happened**:

After an elastic TAS Job shrinks, a PodSet with a slice-size constraint larger than 1 retains its full topology reservation. PR #17374 skips trimming grouped reservations. Waiting Workloads cannot use the freed domains until the Job finishes or is evicted.

**What you expected to happen**:

Release unused topology capacity after shrink while preserving slice-size and grouped placement constraints.

**How to reproduce it (as minimally and precisely as possible)**:

1. Admit an elastic TAS Job with a PodSet slice-size constraint larger than 1 and reservations across multiple domains.
2. Shrink the Job so surviving Pods no longer occupy some reserved domains.
3. After removed Pods terminate, observe that the full reservation remains and prevents a waiting Workload from using those domains.

**Anything else we need to know?**:

Non-blocking follow-up to https://github.com/kubernetes-sigs/kueue/pull/17374, requested by @sohankunkerkar:
https://github.com/kubernetes-sigs/kueue/pull/17374#issuecomment-6661094433

Affected area: `pkg/controller/tas/topology_ungater.go` and elastic TAS shrink tests.

Required change: support safe reservation trimming for grouped reservations instead of skipping all PodSets with slice-size constraints larger than 1. Preserve reservations while Pod observations are incomplete or unhealthy nodes remain.

Acceptance criteria:
- Add regression coverage for shrink with a slice-size constraint larger than 1.
- Verify that unused domains become available to a waiting Workload after removed Pods terminate.
- Preserve valid slice-size and grouped topology constraints.

### Comment by [@nsega](https://github.com/nsega) — 2026-11-11T08:58:17Z

I looked into this issue and would like to take it. I plan to start once #17374 merges.

To address this issue, I would propose that after a shrink, each slice domain keeps its remaining Pods rounded up to whole slices and releases the rest. Only the topology ungater changes, and there is no API change. For example, with slice size 4 and a shrink from 12 to 6, the full slice stays, the slice with 2 Pods stays fully reserved, and the empty slice is released. Then, 8 stay reserved.

There are two constraints. When Pods carry ranks, only slices at the end of the assignment can be released, because the ungater maps ranks to domains by position. When there are several topology layers, only empty outer domains are released.

Here are three open questions.: 
1. Is this ungater-only rule fine, or would you rather change elastic placement so the trim can be exact, as the comment in #17374 suggests? 
2. Is it OK that a partial slice stays fully reserved, as in the 8 reserved for 6 Pods above? 
3. Pods without ranks, such as those of a non-Indexed Job, can stay spread across slices. Hence, a shrink may release nothing. Is that acceptable?

cc @sohankunkerkar

### Comment by [@sohankunkerkar](https://github.com/sohankunkerkar) — 2026-11-15T05:27:44Z

 Thanks @nsega, this looks right. Rounding up keeps the count a multiple of the slice size, so the next resize can reuse the assignment.
1. Ungater-only is fine.
2. Yes. Kueue already does this for reclaimable Pods.
3. Yes, that's a safe fallback.

With ranks, keep the first `ceil(count/sliceSize)*sliceSize` slots and release the tail. With several layers, round to the outermost size. Also, only patch when the assignment changes. Otherwise the ungater returns early on every reconcile and never ungates replacement Pods.
