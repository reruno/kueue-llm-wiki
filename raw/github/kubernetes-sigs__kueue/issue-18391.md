## Description

**What happened**

After upgrading from v0.19 to v0.20.4 (Helm chart), every kube-apiserver logs this error about once a second, roughly 3,500 errors an hour per apiserver:

```
E1105 ... cacher.go:482] cacher (clusterqueues.kueue.x-k8s.io): unexpected ListAndWatch error: failed to list kueue.x-k8s.io/v1beta1, Kind=ClusterQueue: conversion webhook for kueue.x-k8s.io/v1beta2, Kind=ClusterQueue failed: the server could not find the requested resource; reinitializing...
```

In v0.20 the chart's CRDs (`charts/kueue/templates/crd/`) still declare `v1beta1`, now `served: false`, and still configure `spec.conversion.strategy: Webhook` with `service: kueue-webhook-service`, `path: /convert`. The v0.20 manager returns 404 on `/convert` for every kind. I sent a ConversionReview for ClusterQueue, LocalQueue, Workload and Cohort directly to the webhook port and got HTTP 404 each time.

The apiserver still keeps a watch cache for the declared `v1beta1` version. Filling it converts the stored v1beta2 objects through the webhook, which returns 404, so the cache reinitializes forever. This happened with no v1beta1 objects stored: every object had been rewritten as v1beta2, and `status.storedVersions` was then set to `[v1beta2]`.

Restarting the apiservers doesn't help. Each restarted apiserver starts looping again within a few minutes.

The five CRDs with webhook conversion are clusterqueues, cohorts, localqueues, multikueueclusters and workloads. In my cluster only clusterqueues produced the error, presumably because it was the only one of the five with any objects.

**What you expected to happen**

After the upgrade, the apiservers make no conversion calls that the manager can't answer. Either the v0.20 CRDs use `strategy: None` (v1beta1 is not served, and after the migration script nothing is stored as v1beta1), or the manager keeps serving `/convert` until v1beta1 is removed from the CRDs.

**How to reproduce it (as minimally and precisely as possible)**

1. Install Kueue v0.19.x with the Helm chart and create a ClusterQueue.
2. Upgrade to v0.20.4. The v0.20.5 chart CRDs have the same conversion config.
3. Watch the kube-apiserver logs for `cacher (clusterqueues.kueue.x-k8s.io): unexpected ListAndWatch error`.
4. Check the webhook directly: `kubectl -n kueue-system port-forward <manager pod> 9443:9443`, then POST any `apiextensions.k8s.io/v1` ConversionReview to `https://localhost:9443/convert`. It returns 404.

**Anything else we need to know?**

Workaround: confirm all objects are stored as v1beta2 and that `status.storedVersions` is `[v1beta2]`, then set `spec.conversion` to `{strategy: None}` on the five CRDs. We do this with a Flux HelmRelease post-renderer. After that change, the apiserver errors stopped and stayed at zero over 30 minutes.

#16485 (drop v1beta1 entirely, milestone v0.21) looks like it fixes this for v0.21. Could the conversion change be backported to release-0.20, or the issue documented in the v0.20 upgrade notes? Anyone on v0.20.x is affected, including v0.20.5.

- Kueue version (use `git describe --tags --dirty --always`): v0.20.4 (Helm chart `oci://registry.k8s.io/kueue/charts/kueue`); the v0.20.5 chart CRDs have the same conversion config

### Comment by [@alanhuangch](https://github.com/alanhuangch) — 2026-11-06T03:51:36Z

Thanks for the detailed reproduction.

I confirmed on `release-0.20` that #14558 stopped registering `kueuev1beta1` with the manager scheme, while the five CRDs still use webhook conversion and the certificate rotator still manages those conversion endpoints. controller-runtime registers `/convert` only when the scheme reports the types as convertible, which explains the 404 responses.

For `release-0.20`, I think the minimal fix is to register the `v1beta1` types in the manager scheme for conversion while keeping the `v1beta1` API unserved. This preserves the existing v0.20 migration contract and avoids backporting the larger `v1beta1` removal from #16485.

I have a local patch with a regression test covering ClusterQueue, Cohort, LocalQueue, MultiKueueCluster and Workload. If this direction is acceptable, I can open a PR against `release-0.20`.
