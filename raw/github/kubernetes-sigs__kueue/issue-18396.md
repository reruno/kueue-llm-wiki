## Description

/kind bug

**What happened**:

During an elastic scale-up, the scheduler cache charges the ClusterQueue for both the replacement Workload slice and the slice it replaces, from the moment the replacement is assumed until the replaced slice's `Finished` update arrives. For that window the cached usage, which the scheduler admits and preempts against, is the sum of the two slices and can exceed the ClusterQueue's quota. `ClusterQueue.status` shows it when a status write lands in the window.

With one elastic `batch/v1` Job in a 400m-CPU ClusterQueue, scaled 1 → 2 → 3 → 4 Pods of 100m each, the 2 → 3 replacement is charged 200m + 300m = 500m and the 3 → 4 replacement 300m + 400m = 700m, against 400m.

Window per replacement, from the new slice showing `Admitted` to the old one showing `Finished`, both seen by one watch on one clock:

| Trial | 1→2 (300m) | 2→3 (500m) | 3→4 (700m) |
|---|---|---|---|
| 1 | 0.085s | 0.727s | 0.141s |
| 2 | 0.168s | 0.205s | 0.150s |
| 3 | 0.133s | 0.121s | 0.208s |

- The cache's window starts earlier, when the scheduler assumes the new slice (0.12–0.41s before `Admitted` in trial 1), so it is roughly 0.2–1.0s.
- The 0.727s outlier is a conflict: the scheduler's finish of the old slice failed (`Failed to finish old workload slice after admitting replacement`) and the job reconciler finished it.
- `ClusterQueue.status` showed it in 1 of 3 trials (`reservedCPU=500m/400m reservingWorkloads=2`), since its status writes are batched.
- Running Pods never exceeded the quota: the ungater holds the new Pods until the old slice is finished (`pending elastic ungate operations`), and the new slice alone fits. Only the accounting is inflated.

Trial 1, watch (local time; `held` = CPU of the slices with `QuotaReserved` and not `Finished`):

**What you expected to happen**:

While a replacement slice is admitted and the slice it replaces has not finished, the ClusterQueue charges the job once, so its usage stays within what the job runs and within the quota.

**How to reproduce it (as minimally and precisely as possible)**:

Needs `ElasticJobsViaWorkloadSlices` (on by default) and the `batch/job` integration.

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: dc-repro
---
apiVersion: kueue.x-k8s.io/v1beta2
kind: ResourceFlavor
metadata:
  name: default-flavor
---
apiVersion: kueue.x-k8s.io/v1beta2
kind: ClusterQueue
metadata:
  name: dc-repro
spec:
  namespaceSelector:
    matchLabels:
      kubernetes.io/metadata.name: dc-repro
  resourceGroups:
  - coveredResources: ["cpu", "memory"]
    flavors:
    - name: default-flavor
      resources:
      - name: cpu
        nominalQuota: 400m
      - name: memory
        nominalQuota: 1Gi
---
apiVersion: kueue.x-k8s.io/v1beta2
kind: LocalQueue
metadata:
  name: dc-repro
  namespace: dc-repro
spec:
  clusterQueue: dc-repro
---
apiVersion: batch/v1
kind: Job
metadata:
  name: elastic
  namespace: dc-repro
  labels:
    kueue.x-k8s.io/queue-name: dc-repro
  annotations:
    kueue.x-k8s.io/elastic-job: "true"
spec:
  parallelism: 1
  suspend: true
  template:
    spec:
      restartPolicy: Never
      terminationGracePeriodSeconds: 0
      containers:
      - name: sleep
        image: busybox:1.36
        command: ["sleep", "3600"]
        resources:
          requests:
            cpu: 100m
            memory: 64Mi
```

1. Watch the queue, `kubectl get clusterqueue dc-repro -w -o custom-columns=CPU:.status.flavorsReservation[0].resources[0].total,RESERVING:.status.reservingWorkloads`, and the slices, `kubectl -n dc-repro get workloads -w`.
2. Apply the YAML, then scale up 10s apart: `kubectl -n dc-repro patch job elastic --type=merge -p '{"spec":{"parallelism":N}}'` for N = 2, 3, 4.
3. On each scale-up the new slice is `ADMITTED True` before the old one is `FINISHED True`. The ClusterQueue status goes above 400m only when a status write falls in that window; a watch that timestamps each Workload event shows the overlap on every replacement.

**Anything else we need to know?**:

This comes from the "admit first, finish the old slice after" order chosen in #9015 and implemented in #11195, where the double count was expected to be rare and a follow-up on excluding the unfinished old slice from the cache was requested in review. KEP-77's GA checklist also has an unchecked item: "Re-evaluate cache-level quota accounting during slice replacement to avoid temporary double-counting". In practice it happens on every replacement.

The scheduler works against the inflated usage during the window, so an admission refused or a preemption issued then is not undone when the charge settles.

I have a fix ready and will open a PR for it.
