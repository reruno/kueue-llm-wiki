**What happened**:

SparkApplications that got the `kueue.x-k8s.io/elastic-job` annotation on an earlier Kueue release do not have the `ElasticJobSchedulingGate` in the executor template: `isAnElasticJob` then checked only the annotation, and the defaulter did not add the gate. Now `isAnElasticJob` does not check the `ElasticJobsViaWorkloadSlicesForSparkApplication` gate, so an update of such a job goes `ValidateUpdate` → `validateCreate` → `validateElasticJob` and is rejected with `an elastic job must have the ElasticJobSchedulingGate`. This happens after an upgrade even with the Spark gate at its default (off), and it also blocks Kueue's own unsuspend of the job.

**What you expected to happen**:

Existing elastic SparkApplications can still be updated and unsuspended after an upgrade, so they can finish. On update, the webhook rejects only the removal of the gate (the old object had it and the new one does not), so the existing "must not drop" cases are kept.

**How to reproduce it (as minimally and precisely as possible)**:

Add a `TestValidateUpdate` case with the elastic annotation, no `ElasticJobSchedulingGate` in the executor template, and `Suspend` changed from true to false, with `ElasticJobsViaWorkloadSlices` on and `ElasticJobsViaWorkloadSlicesForSparkApplication` off. It fails with `an elastic job must have the ElasticJobSchedulingGate`. At 8c4181a73 the gate check was skipped with the Spark gate off.

**Anything else we need to know?**:

Code: `isAnElasticJob`, `validateCreate` and `validateElasticJob` in `pkg/controller/jobs/sparkapplication/sparkapplication_webhook.go`.
