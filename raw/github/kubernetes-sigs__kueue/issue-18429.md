**What would you like to be added**:

Integration test coverage, published as its own profile by the same coverage job that #18135 adds for the unit shards. This follows https://github.com/kubernetes-sigs/kueue/pull/18135#issuecomment-6684776991.

1. **Collect.** `test-integration-run` and `test-multikueue-integration` in `hack/make/test.mk` run Ginkgo with `--race` and no coverage today. Add `--cover --coverpkg=sigs.k8s.io/kueue/... --coverprofile=...`. Ginkgo combines the suites' profiles in `--output-dir`. `--race` makes the mode `atomic`, the same as the unit shards. Then filter with the same exclusion list as the unit profile. That list is `UNIT_COVERAGE_EXCLUDE` today, and could be renamed to `COVERAGE_EXCLUDE`. Each shard then writes `filtered.cov` for its own coverage lens, as the unit shards do.
2. **Merge.** `pull-kueue-test-integration-shard-{0..3}-main` and `pull-kueue-test-integration-multikueue-main` run these make targets, so they publish the profile with no job change. The coverage job then merges their builds the same way it merges the unit shards: the presubmit waits for builds on the same refs, and the postsubmit matches trees. The result goes in a separate artifact, so the unit number stays as it is. The coverage job could also write a combined unit + integration profile.
3. **Publish.** In TestGrid and, after #18136, in Codecov, report integration as its own number. In Codecov that means a separate upload flag.

**Open questions:**

- **Coverage lens.** The Spyglass coverage lens reads one `filtered.cov` per job. Which profile does the coverage job show there: unit, integration, or combined?
- **Naming.** Should the jobs be renamed from `*-test-unit-coverage-main` to `*-test-coverage-main` once they cover more than unit tests?
- **Presubmit wait.** The presubmit would also wait for the integration shards. They have the same `skip_if_only_changed` as the unit shards, so they start together, but the coverage result would arrive only when the slowest shard of either kind finishes.
- **Overhead.** How much slower do integration runs get with coverage on? This needs measuring on the shard jobs before it is turned on everywhere.

**Why is this needed**:

#11173 lists integration as one of the three coverage layers. Some code is only reached through envtest reconciliation, so the unit number alone says it is untested. A separate integration profile shows where coverage really is missing. A combined profile shows what no test reaches.
