**What would you like to be added**:

E2E test coverage of the Kueue manager, published as its own profile by the same coverage job that #18135 adds for the unit shards. This follows https://github.com/kubernetes-sigs/kueue/pull/18135#issuecomment-6684776991.

1. **Instrument.** The e2e jobs need a coverage build of the manager image: `go build -cover -covermode=atomic -coverpkg=sigs.k8s.io/kueue/...`. Today the image is built by `make build` in the `Dockerfile`.
2. **Collect.**
   - Give the manager Deployment `GOCOVERDIR`, pointing at a directory that the kind node exposes to the job pod.
   - Stop the manager cleanly at suite teardown. The Go runtime writes the counters only when the process exits normally.
   - Convert the counters with `go tool covdata textfmt`.
   - Filter with the same exclusion list as the unit profile, and write `filtered.cov`.
3. **Merge.** The coverage job merges the e2e builds into a separate artifact, as it merges the unit shards. It could also add them to a combined profile.
4. **Publish.** In TestGrid and, after #18136, in Codecov, report e2e as its own number. In Codecov that means a separate upload flag.

**Open questions:**

- **Which jobs.** main has about 40 e2e presubmits, many of them one per Kubernetes version. Should coverage run on a subset, such as one Kubernetes version of each baseline, extended and multikueue suite? Or in periodic jobs only, as #11173 suggests, to keep presubmits fast?
- **MultiKueue.** In those suites both the manager and worker clusters run the manager. Should their counters be merged?
- **kueueviz.** Should the kueueviz backend be instrumented in the same way?
- **Overhead.** What does a coverage image cost in image build time and in test run time?

**Why is this needed**:

#11173 lists e2e as one of the three coverage layers. Manager startup, webhooks, leader election and the in-cluster RBAC paths are only reached in e2e tests, so the unit and integration numbers report them as untested.
