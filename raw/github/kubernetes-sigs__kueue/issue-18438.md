## Description

With `KueueDRADeviceFeasibility` and `TASRespectNodeAffinityPreferred` enabled, a node rejected by DRA can still increase its rack’s affinity score. TAS can consequently choose a less preferred usable node.

This happens during the **first placement evaluation** and requires only **one PodSet**, without leader/worker grouping.

Consider a Workload containing one Pod that requests a DRA device, with TAS placement at rack level. All other scheduling requirements are satisfied:

| Node | Rack | Affinity score | Device available |
|---|---|---:|---|
| a1 | A | 100 | No |
| a2 | A | 0 | Yes |
| b1 | B | 75 | Yes |

The simulator scores the nodes before DRA checks their devices. DRA rejects a1, but [does not clear its score](https://github.com/kubernetes-sigs/kueue/blob/798a6823424a2a6712d658951798ad4997ca0ed4/pkg/cache/scheduler/dra/checker.go#L131-L146). Rack A therefore scores 100 and wins over rack B’s 75. The Pod is placed on a2, although **b1 is the preferred feasible node**.

If the same PodSet is evaluated again against the same snapshot, the node-matching cache restores scores only for a2 and b1. Rack A then scores 0 and b1 wins. This repeated evaluation exposes the inconsistency,

Proposed fix and coverage:

- Clear scores when DRA rejects a node, covering both unavailable devices and allocation errors.
- Add a test using the real DRA checker and nonzero affinity scores.

@mimowo I'll send a PR for the DRA case that clears the score of every node the device check drops. A related case without DRA: a node with no room left still adds its score to its rack, so with a1 at 0 CPU and score 100, a2 at 0 and b1 at 75, the Pod still lands on a2. KEP-2724 only says child scores are summed, so should a domain count only nodes that can hold at least one Pod?
