## Description

Following [this discussion](https://github.com/kubernetes-sigs/kueue/pull/16516#issuecomment-6685984095), I propose a bugfix with two goals:

1. **Delayed cleanup:** removing a worker from `MultiKueueConfig` stops new dispatches, while existing jobs keep running and remain tracked. If their manager Workload is later evicted, clean up the previous execution on that worker too.

2. **No in-memory cleanup history:** #16516 uses `previousClusterNames`, which is lost on restart and can leave the old execution running. Recover cleanup from persisted API state, potentially by retaining `status.clusterName` until cleanup completes.

The goal is to avoid duplicate running jobs and unnecessary eviction, and have a solution which works well for restarts.

### Comment by [@mimowo](https://github.com/mimowo) — 2026-11-17T18:21:33Z

I think there is one more problematic scenario requiring fixing:
1. Workload W is admitted on worker A.
2. A is removed from `MultiKueueConfig`, but its `MultiKueueCluster` remains.
3. A’s kubeconfig Secret becomes missing or invalid, and the manager restarts.
4. Loading credentials fails before a remote-client record is created. Consequently, `disconnectCluster(A)` has no record to update.
5. The workload reconciler considers A temporarily unavailable, but `admittingWorkerLostSince(A)` returns `Now()` on every reconcile because the client record is absent.

As a result, `workerLostTimeout` never expires: W stays `Ready`, holds quota, and cannot fail over.

This small fix appears to be sufficient:

```go
// Track disconnection even if credentials cannot be loaded.
c.findOrCreateRemoteClient(cluster.Name, c.origin)

clientConfig, reason, err := c.loadClientConfig(ctx, cluster)
```

Possibly the bug also affects workers still listed in `MultiKueueConfig`; removing A is not required.
