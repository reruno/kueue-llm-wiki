## Description

## Goal

Reduce how much a MultiKueue worker reconnect delays the dispatch of new Workloads.

Since #16175, each time a worker watch reconnects, the manager requeues every Workload assigned to or nominated for that worker. Watches end routinely on the API server's request timeout (`--min-request-timeout`, 30–60 min), so every worker goes through this resync about every 30–60 minutes. The `multikueue_workload` controller reconciles them one at a time, and each reconcile reads the remote Workload from every worker. New Workloads wait behind the burst.

Observed on production managers:
- ~2,900 Workloads (2,468 replaced elastic slices): a resync of ~2,200 Workloads delayed a new Workload's dispatch by about 10 min 30 s.
- ~196 active Workloads, farthest worker about 0.5 s RTT away: about 0.58 s per reconcile, so a new Workload waited about 114 s behind the resync.

This umbrella can be closed when a reconnect no longer delays new Workloads by more than a few seconds on managers of this size, or when the remaining directions below are rejected.
