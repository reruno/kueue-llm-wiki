## Description

**What happened:**

A running RayJob that loses a worker is never evicted by `waitForPodsReady.recoveryTimeout`: its Workload stays `PodsReady=True`, so the recovery timer never starts.

The RayJob integration reads the RayCluster's legacy `state` field ([rayjob_controller.go#L237-L239](https://github.com/kubernetes-sigs/kueue/blob/v0.20.5/pkg/controller/jobs/rayjob/rayjob_controller.go#L237-L239), same on `main`):

```go
func (j *RayJob) PodsReady(ctx context.Context, _ client.Client, _ ...jobframework.PodsReadyOption) bool {
	return j.Status.RayClusterStatus.State == rayv1.Ready
}
```

KubeRay sets `state` to `ready` once all pods are first running and never clears it when a pod is lost ([raycluster_controller.go#L2017-L2021](https://github.com/ray-project/kuberay/blob/v1.7.1/ray-operator/controllers/ray/raycluster_controller.go#L2017-L2021)); the field is deprecated in favor of Conditions. #17591 moved the RayCluster integration off `state` for the same reason ("can keep a stale `ready` value"), but RayJob wasn't changed.

**What you expected to happen:**

Once a worker is lost and not replaced, `PodsReady` becomes `False`, and after `recoveryTimeout` the Workload is evicted and requeued, as with batch Jobs, whose integration counts ready pods.

**How to reproduce it (as minimally and precisely as possible):**

1. Enable `waitForPodsReady` with a `recoveryTimeout` and the `ray.io/rayjob` integration.
2. Submit a RayJob with one worker and a long-running entrypoint to a LocalQueue, and wait for `PodsReady=True`.
3. Make a replacement worker unschedulable (e.g. cordon its node when no other node fits), then delete the worker pod.
4. Wait longer than `recoveryTimeout`.

With `recoveryTimeout: 5m`, >5 minutes after deleting the worker the Workload was still `PodsReady=True` and admitted, with no `Evicted` condition. The RayCluster showed `state: ready` with 0 of 1 workers ready, and the replacement worker was `Pending`.

**Anything else we need to know?:**

- The startup path works: an unschedulable RayJob is evicted after `unscheduledTimeout` and requeued.
- Possible fix: base RayJob readiness on `HeadPodReady` plus `readyWorkerReplicas >= desiredWorkerReplicas`. Unlike RayCluster devboxes, RayJob workers are needed to make progress. Autoscaling RayJobs would need care, since `desiredWorkerReplicas` changes.

**Environment:**
- Kubernetes version: v1.37
- Kueue version: v0.20.3 (though RayJob `PodsReady` is unchanged through v0.20.5)
- KubeRay version: v1.7.1
