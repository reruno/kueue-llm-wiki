## Description

**What would you like to be added**:

Support LeaderWorkerSets with `spec.groupIdentity: Hash` (LWS v1.0.0, [KEP 898](https://github.com/kubernetes-sigs/lws/tree/main/keps/898-group-identity)) in the LeaderWorkerSet integration, so that each group is admitted and counted against quota as in `Ordinal` mode.

A possible approach, as discussed in #18250:
- Create each group's Workload when its leader Pod appears, named from the leader's group key (`leaderworkerset.sigs.k8s.io/group-index`), instead of from ordinals `0..replicas-1`.
- Keep the leader Pod gated until its Workload is admitted.
- Delete the Workload when its group goes away. A recreated group gets a new key, so it gets a new Workload and queues again.

**Why is this needed**:

The integration assumes `Ordinal`: it creates Workloads for ordinals `0..replicas-1` and ungates any Pod that is not owned by a StatefulSet. With `Hash`, leaders are owned by a ReplicaSet and each group gets a random 40-character key when its leader Pod is created. As a result:
- leader Pods run without admission,
- worker Pods stay gated, waiting for a Workload named from the group key that is never created,
- the ordinal Workloads can be admitted and reserve quota that no Pod uses.

#18250 rejects `Hash` when a LeaderWorkerSet is created under Kueue management. A LeaderWorkerSet already managed with `Hash`, created before that change or in a namespace that became managed later, keeps this behavior. Its worker Pods already reference Workloads named from the group key, so this would also fix it. The DisaggregatedSet integration (#17675) also rejects `Hash` for its roles.

Open questions:
- LWS gates `Hash` leaders with its own `leaderworkerset.sigs.k8s.io/group-replacement` scheduling gate and creates no worker StatefulSet while that gate is set. How should it interact with Kueue's gate on the leader?
- Rolling updates and group restarts replace groups under new keys, so each replacement group queues again.
