## Description

**What happened**:

The SparkApplication integration added by #17127 decides `PodsReady` from `status.executorState` ([`sparkapplication_controller.go` L370-L397 at 887e6f8](https://github.com/kubernetes-sigs/kueue/blob/887e6f8daa34b9fad84119d86ab953415ef17ac1/pkg/controller/jobs/sparkapplication/sparkapplication_controller.go#L370-L397)): the driver is running and the number of `RUNNING` + `COMPLETED` entries is at least `minExecutors` (Dynamic Allocation) or `spec.executor.instances`. That map is a poor source for readiness in three ways:

1. **It stops at the tracking limit.** The Kubeflow Spark Operator skips executors whose ID is above `--max-tracked-executor-per-app` (default 1000), and Spark never reuses executor IDs. A long-running Dynamic Allocation application, or one that replaces failed executors, stops having its new executors counted. Once the tracked ones leave, it drops below the floor and is evicted by `waitForPodsReady` while running fine.
2. **`COMPLETED` entries pile up.** Entries are never removed from the map, so an application that has lost its executors can still count enough `COMPLETED` entries to look ready, hiding exactly the loss that `waitForPodsReady` with `recoveryTimeout` should catch. For executors, a completed Pod is lost capacity, not finished work; Kueue's "Ready or Succeeded" rule comes from batch Jobs.
3. **The Dynamic Allocation fallback is wrong.** With Dynamic Allocation on and `minExecutors` unset, the expected count falls back to `spec.executor.instances` (L385), although Spark's own minimum is 0, so an application that scales down correctly looks not ready. ( deferred to #18715 )



Executors removed by Dynamic Allocation while the driver runs become `UNKNOWN` in the map, which isn't counted, so the map can't tell a removed executor from one that never started either.

Sizing and slice names are not affected: they already count executor Pods (`countExecutorPods`).

**What you expected to happen**:

`PodsReady` counts the executors that are ready now: driver running, and the number of executor Pods of the current submission that are `Running`, `Ready` and not being deleted is at least the floor (`minExecutors` with Dynamic Allocation, `0` if unset; `spec.executor.instances` otherwise). Completed, pending and terminating executors don't count. This matches how the Apache Spark Kubernetes Operator decides readiness (ready executor Pods against its threshold).

**How to reproduce it (as minimally and precisely as possible)**:

Reproduced on a cluster with a lowered tracking limit, so the IDs pass it in minutes instead of at 1000.

1. Lower the Spark Operator's limit to 5:
   ```sh
   helm upgrade spark-operator spark-operator/spark-operator -n spark-operator --reuse-values \
     --set controller.maxTrackedExecutorPerApp=5
   ```
2. Turn on `waitForPodsReady` in Kueue's configuration (it's off in the default config) and restart Kueue:
   ```yaml
   waitForPodsReady:
     timeout: 10m
     recoveryTimeout: 1m
     blockAdmission: false
   ```
3. Run a Kueue-managed SparkApplication with 3 executors that runs a few minutes. `spark.executor.maxNumFailures` keeps the deletions below from failing it:
   ```yaml
   apiVersion: sparkoperator.k8s.io/v1beta2
   kind: SparkApplication
   metadata:
     name: podsready-limit
     namespace: <namespace>
     labels:
       kueue.x-k8s.io/queue-name: <local-queue>
   spec:
     type: Scala
     mode: cluster
     image: docker.io/library/spark:4.0.1
     mainClass: org.apache.spark.examples.SparkALS
     mainApplicationFile: local:///opt/spark/examples/jars/spark-examples.jar
     arguments: ["1500", "1500", "12", "200", "60"]
     sparkVersion: 4.0.1
     sparkConf:
       spark.kubernetes.executor.podNamePrefix: podsready-limit
       spark.executor.maxNumFailures: "50"
     driver:
       cores: 1
       memory: 512m
       serviceAccount: spark-operator-spark
     executor:
       cores: 1
       memory: 512m
       instances: 3
   ```
4. Once its Workload has `PodsReady=True`, delete the executors with IDs 1 to 5 one at a time, waiting for Spark to replace each one (`kubectl delete pod podsready-limit-exec-1`, then `-exec-2`, and so on). Each replacement gets the next ID, so after five, every running executor (IDs 6, 7, 8) is above the limit.
5. Watch the Workload's conditions and the executor Pods.

What happened (times from the run):

```
01:11:57 ready executor Pods [1, 2, 3]  executorState RUNNING=3  Workload PodsReady=True/Started
01:12:13 ready executor Pods [4, 5, 6]  executorState RUNNING=2  Workload PodsReady=False/WaitForRecovery
01:12:24 ready executor Pods [6, 7, 8]  executorState RUNNING=0  Workload PodsReady=False/WaitForRecovery
01:13:04 ready executor Pods [6, 7, 8]  executorState RUNNING=0  Workload PodsReady=False/WaitForRecovery
01:13:10 SparkApplication SUSPENDED      Workload Evicted=True/PodsReadyTimeout
```

- `PodsReady` turned `False` as soon as executor 6, the first one past the limit, replaced a tracked one: the map had 2 `RUNNING` entries for 3 expected, while all 3 executors were running and ready.
- After `recoveryTimeout` (1m), Kueue evicted the application with `PodsReadyTimeout`, with its 3 executors still running and ready.
- With an operator that also declares `status.readyExecutors` (kubeflow/spark-operator#3290), that field reported 3 throughout.

The `COMPLETED` pile-up case follows from the same code but wasn't run: with `recoveryTimeout` set, let an application's executors complete (e.g. decommissioned or scaled down) and stay below the floor; `PodsReady` stays `True` from the `COMPLETED` entries.

**Anything else we need to know?**:

- Proposed fix in `pkg/controller/jobs/sparkapplication/sparkapplication_controller.go`: count live ready executor Pods with the existing `listExecutorPods`, and read `status.readyExecutors` when the operator publishes it. kubeflow/spark-operator#3290 (fixes kubeflow/spark-operator#3282) adds `status.activeExecutors`, `status.readyExecutors` and `status.maxExecutorId`, counted from the Pods, so they are exact at any scale; Pod listing stays as the fallback for older operators.
- Tests: executors above the tracking limit, completed and terminating executors, a running executor that isn't `Ready`, and Dynamic Allocation without `minExecutors`.
- Behaviour change: an application that was only "ready" because of stale `COMPLETED` entries becomes not ready; worth a release note.
- Follow-up to #17127, proposed in [this comment](https://github.com/kubernetes-sigs/kueue/pull/17127#issuecomment-6714652908). Happy to send the PR.
- Reproduced on a cluster with `--max-tracked-executor-per-app=5`, steps above.
