**What would you like to be added**:

Support KubeRay `spec.deletionStrategy.deletionRules` for Kueue-managed RayJobs that create their own RayCluster (`rayClusterSpec` set, no `clusterSelector`).

Today these RayJobs cannot use `deletionRules` at all:

| Setting | Rejected by | Reason | Code |
| --- | --- | --- | --- |
| `shutdownAfterJobFinishes: false` | Kueue RayJob webhook | `a kueue managed job should delete the cluster after finishing` | [rayjob_webhook.go#L145-L147](https://github.com/kubernetes-sigs/kueue/blob/6b79acb1d56f2eaf7650f9e0730c25fdb7831250/pkg/controller/jobs/rayjob/rayjob_webhook.go#L145-L147) |
| `shutdownAfterJobFinishes: false` | KubeRay validation | A RayJob with `suspend: true` must set `shutdownAfterJobFinishes: true`, and Kueue always creates RayJobs suspended. | [validation.go#L547-L549 (v1.7.1)](https://github.com/kuberay-project/kuberay/blob/v1.7.1/ray-operator/controllers/ray/utils/validation.go#L547-L549) |
| `shutdownAfterJobFinishes: true` | KubeRay validation | `shutdownAfterJobFinishes` and `deletionStrategy.deletionRules` are mutually exclusive. | [validation.go#L771-L773 (v1.7.1)](https://github.com/kuberay-project/kuberay/blob/v1.7.1/ray-operator/controllers/ray/utils/validation.go#L771-L773) |

The only option left is the deprecated `onSuccess`/`onFailure` strategy. It uses the single top-level `ttlSecondsAfterFinished` for every action, so users cannot delete the RayCluster soon after completion while keeping the RayJob CR longer for debugging.

Kueue checks `shutdownAfterJobFinishes` to make sure the RayCluster is deleted after the job ends. A `deletionRules` configuration that also deletes the cluster could meet the same requirement. Possible approaches:

- Kueue accepts `deletionRules` that delete the RayCluster, together with the KubeRay change that allows `suspend: true` with `deletionRules`.
- KubeRay allows `shutdownAfterJobFinishes: true` together with `DeleteSelf`-only rules (proposed in kuberay-project/kuberay#5469). In that case Kueue needs no webhook change, but it should document the combination and cover it with tests.

Whichever approach is chosen, it should take quota accounting into account. Kueue releases the Workload's quota when the RayJob reaches `Complete` or `Failed`, so any rule that keeps Ray Pods running after that point holds resources Kueue no longer counts.

**Why is this needed**:

`deletionRules` is the deletion API KubeRay recommends, and the `onSuccess`/`onFailure` fields are deprecated. Users who move RayJobs under Kueue lose independent retention periods. For example, they cannot delete the RayCluster 300 seconds after completion while keeping the RayJob CR for 30 days and deleting it afterwards to keep API server load bounded. See kuberay-project/kuberay#5469 for a real use case that blocks a Kueue rollout.
