## Description

**What happened:**

A network partition between the MultiKueue manager and one worker, longer than `workerLostTimeout`, leaves the job in a state it never recovers from:

1. The partition starts. Workloads keep running on the worker (W1).
2. After `workerLostTimeout`, the manager evicts them and re-dispatches them to another worker (W2), so `status.clusterName` becomes W2.
3. The partition heals. The copy on W2 is removed. The original on W1 keeps running.
4. The original on W1 finishes, but the manager never sees it complete. The manager Job stays `active: 1` indefinitely, holding quota, so the submitter waits forever. If anything kills the W1 copy, the job is lost and the manager still shows it as active.

Reproduced 4 out of 4 times.

The W1 copy is also never garbage-collected. `runGC` (v0.20.5, `pkg/controller/admissionchecks/multikueue/multikueuecluster.go:801`) keeps a remote workload whenever a manager workload with the same namespace/name exists and isn't being deleted:

```go
if err == nil && localWl.DeletionTimestamp.IsZero() {
    // The local workload exists and isn't being deleted, so the remote workload is still relevant.
    continue
}
```

It doesn't check whether the manager workload's `status.clusterName` is this worker. The same check is on `main`.

Deleting the W1 copy doesn't recover the job, because by then it is the only live execution. In our tests, deleting the W1 Workload happened to make the manager requeue it. Deleting only its pods left the job lost, with the manager still showing it as active.

**What you expected to happen:**

When the worker reconnects, the manager should reconcile where the workload actually runs. Either it adopts the W1 copy (and drops W2's), or it removes the W1 copy and keeps the re-dispatched one. Either way, the manager must keep tracking exactly one copy until it finishes. As a minimum, GC should treat a remote workload as stale when the manager's `clusterName` points to a different cluster.

**How to reproduce it (as minimally and precisely as possible):**

1. Use kind: 1 manager and 2 workers, with Kueue v0.20.5 on all of them. Set the manager's `multiKueue.workerLostTimeout: 1m` and `gcInterval: 30s`. Create one ClusterQueue with a MultiKueue admission check listing both workers.
2. Submit a `batch/v1` Job that sleeps for about 5 minutes. Note the worker it lands on (W1).
3. Cut the manager off from W1 by running this inside the manager node: `docker exec <manager>-control-plane iptables -I OUTPUT -d <W1 node IP> -j DROP` (and the same rule on `FORWARD`).
4. Wait more than 1 minute. The manager re-dispatches the Job to W2.
5. Remove the rules (`iptables -D …`).
6. Watch the result: the W2 copy is removed, the W1 copy runs to completion, and the manager Job stays `active: 1` and is never marked Complete.

**Anything else we need to know?**

Related, but not the same issue: #13238 (unify handling of unavailable workers) and #18115 / #18117 / #18125 (one ended watch marks a whole worker as disconnected, which makes spurious re-dispatch, and so this path, more likely).

Our workaround: a long `workerLostTimeout`, a detection-only sweeper that alerts when a remote workload's manager `clusterName` differs from the worker it is on, and idempotent jobs.

**Environment:**
- Kubernetes version: v1.32.2 (kind v0.27.0)
- Kueue version: v0.20.5 (also checked: GC logic unchanged on `main`)
- JobSet v0.13.0; integrations enabled: batch/job, jobset, deployment
