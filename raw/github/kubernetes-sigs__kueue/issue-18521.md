## Description

**What happened**:

A StrictFIFO ClusterQueue repeatedly reevaluates its head Workload after ordinary quota NoFit, even when the Workload and available quota have not changed. The Workload returns directly to the active heap, and the scheduler's global backoff caps at 10ms. Each unsuccessful reevaluation can also call the Event recorder with the same Pending diagnosis.

On upstream main commit `6b79acb1d56f2eaf7650f9e0730c25fdb7831250`, an isolated 500ms test using the real scheduler, queue manager and backoff loop recorded 45 completed attempts and 45 Event recorder calls for a single Workload requesting 2 CPU from a 1-CPU StrictFIFO ClusterQueue. The BestEffortFIFO control recorded one attempt and one Event call. Counts vary with the host; repeated reevaluation without an input change is the relevant result.

The same new regression was independently run against an archive of official v0.20.5 (`7e71578095b353cedbfa63607b60c9739af9d501`), with no product-code changes: StrictFIFO recorded 42 attempts and 42 Event calls; BestEffortFIFO recorded one of each. These are fresh local measurements, separate from any earlier incident report.

This test uses a fake Kubernetes client and recorder. It does not measure HTTP request counts, API-server load, or Lease renewals.

**What you expected to happen**:

StrictFIFO should preserve its head-of-line ordering while avoiding repeated millisecond-scale fit calculations for unchanged NoFit input. Relevant quota, resource-usage or Workload changes should make the head eligible again. A bounded safety retry should prevent a missed notification from leaving it stuck indefinitely. Other ClusterQueues and higher-priority Workloads should continue to make progress.

**How to reproduce it (as minimally and precisely as possible)**:

Create a StrictFIFO ClusterQueue with one flavor covering CPU and a nominal quota of `1`; connect a LocalQueue to it, then create a Workload requesting `2` CPU. Keep the quota and Workload unchanged. Observe the same Workload repeatedly evaluated as NoFit in scheduler logs. BestEffortFIFO provides a useful control, because the failed Workload normally enters its inadmissible stage.

The local regression is `TestStrictFIFOStableNoFitSchedulingLoop`. It creates these objects with a fake client, calls the scheduler through `UntilWithBackoff`, and counts completed attempts and recorded Events over 500ms. There is no injected external retry notification. A second integration regression uses a real envtest API server and normal controllers: a temporarily occupied StrictFIFO queue retains its blocked head and tail, an independent CQ is admitted, and releasing the occupier's quota permits the original queue to progress.

The relevant queue policy is:

```go
if c.queueingStrategy == kueue.StrictFIFO {
    immediate = reason != RequeueReasonNamespaceMismatch
}
```

Ordinary quota NoFit satisfies this condition.

**Anything else we need to know?**:

The proposed local fix retains the blocked Workload in the active heap, gates both normal and mid-cycle pops until an existing retry notification or a one-second fallback, and suppresses an identical Pending Event when its condition does not change. It preserves the existing global 10ms backoff and immediate paths for pending preemption, migration and remaining flavor exploration. The one-second fallback is a proposal for maintainer review, not an existing upstream policy guarantee.

Related work was checked in open and closed PRs:

- [PR #9697](https://github.com/kubernetes-sigs/kueue/pull/9697) deliberately reduced global backoff for BestEffortFIFO throughput and acknowledged possible StrictFIFO logging pressure. This proposal leaves that global backoff unchanged.
- [Issue #7139](https://github.com/kubernetes-sigs/kueue/issues/7139) and [PR #13483](https://github.com/kubernetes-sigs/kueue/pull/13483) concern safety retries for Workloads already in the inadmissible stage. The StrictFIFO head here remains active; this is a different retry path, although the safety-retry design should be coordinated.
- Closed, unmerged [PR #18328](https://github.com/kubernetes-sigs/kueue/pull/18328) changes generic retry classification for skipped BestEffortFIFO Workloads. It does not control ordinary StrictFIFO NoFit retries.

Leader-election limiter isolation from [PR #15538](https://github.com/kubernetes-sigs/kueue/pull/15538) is a separate fix. This report does not claim that current Kueue loses its leader Lease because of this retry behavior.
