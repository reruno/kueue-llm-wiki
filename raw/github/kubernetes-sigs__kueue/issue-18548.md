## Description

**What happened**:

With `DynamicQuotaOrchestration=true`, a failed quota redistribution can leave the scheduler using a mixture of the previous and next allocations. Quota increases are published even when the corresponding decreases fail.

A minimal case keeps the provider's capacity fixed at **100 CPU** and changes one ClusterQueue's proportional weight:

| State | `cq-a` effective CPU | `cq-b` effective CPU | Total effective CPU |
|---|---:|---:|---:|
| Initial successful distribution, weights 1:1 | 50 | 50 | 100 |
| Intended redistribution, weights 3:1 | 75 | 25 | 100 |
| `cq-a` update succeeds; `cq-b` status update returns Conflict | 75 | 50 | **125** |
| Retry after the conflict is removed | 75 | 25 | 100 |

The excess is visible to admission, rather than only to reporting: in the reproduction below, the production scheduler cache reports **125000 milliCPU available**, and `FlavorAssigner.AssignFlavors` returns **`Fit` for 125 Pods requesting 1 CPU each**. The provider continues to report 100 CPU throughout.

The same result occurs when the donor is listed first: its failed decrease is collected as an error, and the controller proceeds to publish the receiver's increase. The DQO also retains its previous `Distributed=True` condition after the failed redistribution.

This was found by source analysis and verified with deterministic fault injection against current `main` at `4d6d8679f489302def49939620cd3368ade28cdb`. The reproduction uses controller-runtime's fake API client and the production reconciler, scheduler cache and flavor assigner. It does not run a live Kubernetes cluster or observe real Pod scheduling.

**What you expected to happen**:

For redistribution of a fixed discovered capacity, a failed participant update should not make additional quota available that depends on a decrease which has not taken effect. The scheduler should retain a safe allocation or otherwise withhold the unsupported increase until the transfer can be completed safely.

Distribution status should also expose an incomplete redistribution instead of leaving the prior success condition as the only signal.

**How to reproduce it (as minimally and precisely as possible)**:

1. Check out `4d6d8679f489302def49939620cd3368ade28cdb`.
2. Save the following file as `pkg/controller/core/dqo/redistribution_repro_test.go`. It first runs a successful 50/50 distribution, changes the receiver's weight to 3, then injects a Kubernetes Conflict only for the donor's status update. All other writes still use the underlying client. Both participant orders are covered.

// TestRedistributionRepro asserts capacity conservation after a failed
// redistribution. It is expected to fail on the unmodified main branch.
func TestRedistributionRepro(t *testing.T) {
	features.SetFeatureGateDuringTest(t, features.DynamicQuotaOrchestration, true)
	cases := map[string]string{"receiver listed first": "cq-a", "donor listed first": "cq-b"}
	for name, receiverName := range cases {
		t.Run(name, func(t *testing.T) {
			ctx, log := utiltesting.ContextWithLog(t)
			cp := utiltestingalpha.MakeCapacityProvider("cp").
				ControllerName("example.com/test-provider").
				OrchestratedFlavors("default").
				Generation(1).
				Condition(metav1.Condition{
					Type:   kueuealpha.CapacityProviderCapacitySynchronized,
					Status: metav1.ConditionTrue, Reason: "Synchronized", ObservedGeneration: 1,
				}).
				Capacity(utiltestingalpha.MakeNormalizedCapacity().Flavors(
					utiltestingalpha.MakeNormalizedCapacityFlavor("default").
						Resource(corev1.ResourceCPU, "100").Obj(),
				).Obj()).Obj()
			dqo := utiltestingalpha.MakeDynamicQuotaOrchestrator("dqo").
				DiscoveryProvider(cp.Name, nil).
				SubtreeRoot(kueuealpha.CohortSubtreeRootRefKind, "root").Obj()
			root := utiltestingapi.MakeCohort("root").Obj()
			a := utiltestingapi.MakeClusterQueue("cq-a").Cohort("root").ResourceGroup(
				*utiltestingapi.MakeFlavorQuotas("default").Resource(corev1.ResourceCPU, "1").Obj(),
			).Obj()
			b := utiltestingapi.MakeClusterQueue("cq-b").Cohort("root").ResourceGroup(
				*utiltestingapi.MakeFlavorQuotas("default").Resource(corev1.ResourceCPU, "1").Obj(),
			).Obj()
			objects := []client.Object{cp, dqo, root, a, b}
			donorName := "cq-b"
			if receiverName == "cq-b" {
				donorName = "cq-a"
			}
			conflict := apierrors.NewConflict(kueue.Resource("clusterqueues"), donorName, errors.New("injected concurrent status write"))
			blockDecrease := false
			cl := utiltesting.NewClientBuilder().WithObjects(objects...).WithStatusSubresource(objects...).
				WithInterceptorFuncs(interceptor.Funcs{
					SubResourceUpdate: func(ctx context.Context, c client.Client, sub string, obj client.Object, opts ...client.SubResourceUpdateOption) error {
						if _, ok := obj.(*kueue.ClusterQueue); ok && sub == "status" && blockDecrease && obj.GetName() == donorName {
							return conflict
						}
						return c.SubResource(sub).Update(ctx, obj, opts...)
					},
				}).Build()
			r := NewReconciler(cl)
			req := reconcile.Request{Name: dqo.Name}
			if _, err := r.Reconcile(ctx, req); err != nil {
				t.Fatal(err)
			}
			var receiver kueue.ClusterQueue
			if err := cl.Get(ctx, client.ObjectKey{Name: receiverName}, &receiver); err != nil {
				t.Fatal(err)
			}
			if got := receiver.Status.EffectiveQuotas.ResourceGroups[0].Flavors[0].Resources[0].NominalQuota; got.Cmp(resource.MustParse("50")) != 0 {
				t.Fatalf("initial quota = %s, want 50", got.String())
			}
			receiver.Spec.ResourceGroups[0].Flavors[0].Resources[0].NominalQuota = resource.MustParse("3")
			if err := cl.Update(ctx, &receiver); err != nil {
				t.Fatal(err)
			}
			blockDecrease = true
			if _, err := r.Reconcile(ctx, req); !errors.Is(err, conflict) {
				t.Fatalf("Reconcile error = %v, want injected conflict", err)
			}

			// Use the production scheduler cache to inspect the capacity that an
			// admission cycle would see once these persisted statuses are observed.
			cache := schdcache.New(cl)
			cache.AddOrUpdateResourceFlavor(log, utiltestingapi.MakeResourceFlavor("default").Obj())
			if err := cl.Get(ctx, client.ObjectKeyFromObject(root), root); err != nil {
				t.Fatal(err)
			}
			if err := cache.AddOrUpdateCohort(root); err != nil {
				t.Fatal(err)
			}
			for _, name := range []string{"cq-a", "cq-b"} {
				var cq kueue.ClusterQueue
				if err := cl.Get(ctx, client.ObjectKey{Name: name}, &cq); err != nil {
					t.Fatal(err)
				}
				q := cq.Status.EffectiveQuotas.ResourceGroups[0].Flavors[0].Resources[0].NominalQuota
				t.Logf("persisted %s quota: %s CPU", name, q.String())
				if err := cache.AddClusterQueue(ctx, &cq); err != nil {
					t.Fatal(err)
				}
			}
			snapshot, err := cache.Snapshot(ctx)
			if err != nil {
				t.Fatal(err)
			}
			fr := resources.FlavorResource{Flavor: "default", Resource: corev1.ResourceCPU}
			available := snapshot.ClusterQueue(kueue.ClusterQueueReference(receiverName)).Available(fr)
			var latest kueuealpha.DynamicQuotaOrchestrator
			if err := cl.Get(ctx, client.ObjectKeyFromObject(dqo), &latest); err != nil {
				t.Fatal(err)
			}
			t.Logf("Distributed condition after error: %v", apimeta.IsStatusConditionTrue(latest.Status.Conditions, kueuealpha.DynamicQuotaOrchestratorDistributed))
			if available.Cmp(resources.NewAmount(100000)) > 0 {
				t.Errorf("scheduler sees %v milliCPU available; provider reports 100000", available)
			}
			wl := utiltestingapi.MakeWorkload("over-capacity", "default").PodSets(
				*utiltestingapi.MakePodSet("main", 125).Request(corev1.ResourceCPU, "1").Obj(),
			).Obj()
			wi := workload.NewInfo(log, wl)
			cqSnapshot := snapshot.ClusterQueue(kueue.ClusterQueueReference(receiverName))
			assignment := flavorassigner.New(wi, cqSnapshot, snapshot.ResourceFlavors, false, nil, nil,
				configapi.QuotaCheckBlockUndeclared, resources.NewResourceFormatter(), 0).AssignFlavors(ctx, log, nil)
			t.Logf("quota assignment for 125 x 1 CPU Pods: %v", assignment.RepresentativeMode())
			if assignment.RepresentativeMode() == flavorassigner.Fit {
				t.Error("125-CPU workload fits quota from a 100-CPU provider")
			}

			// The same objects converge after the conflict is removed. The excess
			// capacity above is the intermediate persisted state, not bad math.
			blockDecrease = false
			if _, err := r.Reconcile(ctx, req); err != nil {
				t.Fatal(err)
			}
			for _, name := range []string{"cq-a", "cq-b"} {
				var cq kueue.ClusterQueue
				if err := cl.Get(ctx, client.ObjectKey{Name: name}, &cq); err != nil {
					t.Fatal(err)
				}
				if err := cache.UpdateClusterQueue(log, &cq); err != nil {
					t.Fatal(err)
				}
			}
			recovered, err := cache.Snapshot(ctx)
			if err != nil {
				t.Fatal(err)
			}
			recoveredAvailable := recovered.ClusterQueue(kueue.ClusterQueueReference(receiverName)).Available(fr)
			t.Logf("after successful retry: %v milliCPU available", recoveredAvailable)
			if recoveredAvailable.Cmp(resources.NewAmount(100000)) != 0 {
				t.Errorf("recovered capacity = %v, want 100000 milliCPU", recoveredAvailable)
			}
		})
	}
}

**Anything else we need to know?**:

The relevant code path is:

1. [`reconcileDistribution`](https://github.com/kubernetes-sigs/kueue/blob/4d6d8679f489302def49939620cd3368ade28cdb/pkg/controller/core/dqo/distribution.go#L78-L83) calculates a complete allocation, then applies it across participant objects.
2. [`applyEffectiveQuotas`](https://github.com/kubernetes-sigs/kueue/blob/4d6d8679f489302def49939620cd3368ade28cdb/pkg/controller/core/dqo/distribution.go#L244-L290) updates ClusterQueues followed by Cohorts, collecting errors and continuing. Successful writes remain published when a later or earlier write fails.
3. [`EffectiveResourceGroups`](https://github.com/kubernetes-sigs/kueue/blob/4d6d8679f489302def49939620cd3368ade28cdb/pkg/util/resourcegroups/effective.go#L24-L44) exposes each object's effective quota immediately. [`clusterQueue.updateClusterQueue`](https://github.com/kubernetes-sigs/kueue/blob/4d6d8679f489302def49939620cd3368ade28cdb/pkg/cache/scheduler/clusterqueue.go#L180-L192) rebuilds the quota tree from those individual updates, and [`accumulateFromChild`](https://github.com/kubernetes-sigs/kueue/blob/4d6d8679f489302def49939620cd3368ade28cdb/pkg/cache/scheduler/resource_node.go#L254-L264) sums their capacities.
4. [`fitsResourceQuota`](https://github.com/kubernetes-sigs/kueue/blob/4d6d8679f489302def49939620cd3368ade28cdb/pkg/scheduler/flavorassigner/flavorassigner.go#L1138-L1144) returns Fit against the resulting available quota. It has no distribution-wide capacity check at this point.
5. On the update-error path, [`Reconcile`](https://github.com/kubernetes-sigs/kueue/blob/4d6d8679f489302def49939620cd3368ade28cdb/pkg/controller/core/dqo/reconciler.go#L234-L245) returns the distribution error without replacing the previous `Distributed=True` condition.

A concurrent write to another field of ClusterQueue status can produce a resourceVersion conflict. Returning an error schedules a retry, but does not withdraw the already-published increase. Consequently, a later successful retry does not prevent a quota reservation during the intervening state. The reproduction demonstrates the quota feasibility decision; an integration test should cover actual Workload admission during a paused or failed redistribution.

This differs from the intentional stale-quota retention described in [KEP-12382](https://github.com/kubernetes-sigs/kueue/blob/4d6d8679f489302def49939620cd3368ade28cdb/keps/12382-dynamic-quota-orchestration/README.md#stale-effective-quota): the provider remains synchronized and the same active DQO is transferring an unchanged capacity budget between participants.

Related work checked before filing:

| Work | Relationship |
|---|---|
| [#15283](https://github.com/kubernetes-sigs/kueue/pull/15283), merged | Introduced distribution; its apply loop publishes per-object updates and collects errors. |
| [#15407](https://github.com/kubernetes-sigs/kueue/pull/15407), merged | Covers successful redistribution and eventual final quotas; does not assert conservation after an individual write fails. |
| [#18314](https://github.com/kubernetes-sigs/kueue/pull/18314), open at investigation time | Adds optional quota expiration; its current diff retains per-object distribution writes and does not coordinate this transfer. |

I searched open and closed issues/PRs using `DQO`, `effectiveQuotas`, `applyEffectiveQuotas`, redistribution, partial distribution and overcommit terms; I did not find an existing report of this failure mode. Related feature tracking: [#12382](https://github.com/kubernetes-sigs/kueue/issues/12382).

A fix needs agreement on how allocation transfers become safe for admission. Merely changing iteration order or returning on the first error is insufficient: an increase may already have succeeded, and one participant can increase one resource while decreasing another. Cross-kind updates to ClusterQueues and Cohorts also need to account for separate informer observation.

Suggested acceptance criteria for the fix:

- The fixed-capacity redistribution above cannot produce an admission-feasible budget above the provider's capacity when any participant update fails, in either participant order.
- Cover transfers between ClusterQueues and Cohorts, and participants with simultaneous increases/decreases across resources or flavors.
- Exercise the event/watch path with an integration test that holds a decrease pending while a Workload requests the capacity being transferred.
- Check repeated retries and restart recovery from any persisted intermediate state used by the chosen design.
- Report incomplete distribution through an appropriate condition, and recover it after success.
- Preserve discovery-only behavior, feature-gate-off behavior, configured lending/borrowing limits, rounding and documented stale-quota semantics.
