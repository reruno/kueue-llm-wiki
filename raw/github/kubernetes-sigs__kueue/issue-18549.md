## Description

**What happened**:

An elastic MultiKueue RayJob can finish on the worker while its manager copy remains nonterminal.

During scale-up, the manager reserves quota for a replacement Workload slice and marks the old slice `Finished=True`, reason `WorkloadSliceReplaced`. If the replacement cannot obtain quota on the worker, the worker RayJob continues referencing the old slice.

When that RayJob finishes, completion does not propagate to the manager. The replacement remains unfinished and normal remote cleanup does not happen.

The relevant state is:

| Object | State |
|---|---|
| Old manager Workload | Finished: `WorkloadSliceReplaced` |
| Replacement manager Workload | Quota reserved; MultiKueue admission pending |
| Replacement worker Workload | No quota reservation |
| Worker RayJob | `SUCCEEDED` / `Complete`; prebuilt-workload reference still points to the old slice |
| Manager RayJob | Nonterminal |

We reproduced this with Kueue v0.20.0 and v0.20.5, and with an integration regression test against upstream commit `4d6d8679f489302def49939620cd3368ade28cdb`.

**What you expected to happen**:

A worker RayJob’s terminal status should reach the manager even when its replacement slice cannot be admitted. The manager should finish the current Workload and perform normal cleanup without requiring additional worker quota.

**How to reproduce it (as minimally and precisely as possible)**:

1. Configure MultiKueue with the RayJob integration and enable `ElasticJobsViaWorkloadSlices` and `MultiKueueRayInTreeAutoscaling`.
2. Submit an elastic RayJob with in-tree autoscaling, initially using one worker.
3. Admit its initial slice on the manager and worker.
4. Scale the worker-side child RayCluster from one worker to two.
5. Allow the replacement slice to reserve manager quota, but withhold worker quota. Wait until the old manager slice is marked `WorkloadSliceReplaced`. Confirm that the worker RayJob still references the old slice.
6. Complete the worker RayJob with `jobStatus: SUCCEEDED` and `jobDeploymentStatus: Complete`.
7. Observe that the manager does not receive completion and the replacement remains unfinished.

The integration reproduction uses real API servers and Kueue controllers, with simulated KubeRay child creation and status updates. It does not run the KubeRay operator or Ray pods.

**Anything else we need to know?**:

The worker completion event reaches the old slice, but MultiKueue skips replaced slices before synchronizing job status. The pending replacement also does not synchronize that status while worker admission is blocked.

Restoring worker quota recovered completion in our local reproduction.

A local prototype that copies only terminal job status through the replaced slice passes the regression test. The same integration test fails against unmodified upstream code. With the prototype, the replacement finishes and remote cleanup occurs without granting worker quota. Success and failure are covered by unit tests; the integration case currently covers success.

Related reports are #9015, #15380, and #18512. This case occurs while connectivity is healthy and the worker RayJob still exists.

AI assistance disclosure: OpenAI Codex assisted with the investigation, local prototype, tests, and this draft.

**Environment**:

- Kubernetes version: v1.37.0 API-server binaries for the integration reproduction.
- Kueue version: upstream `4d6d8679f489302def49939620cd3368ade28cdb`; also reproduced locally with v0.20.0 and v0.20.5.
- Cloud provider or hardware configuration: local CPU-only integration environment; no GPUs required.
- OS: macOS 26.5.2.
- Kernel: Darwin 25.5.0.
