## Description

**What happened**:

With Kueue v0.16.9, we observed repeated admission, PodsReadyTimeout eviction, and re-admission of Jobs with permanently unsatisfiable placement constraints. Each Job had two Pods restricted to one hostname, while required Pod anti-affinity prevented those Pods from sharing a hostname. TAS admitted the Workload and assigned both Pods to that hostname. One Pod ran; the other remained Pending. After 300 seconds, Kueue evicted the Workload and subsequently admitted it again without any change to the constraints or eligible nodes.

In our 100:1 load test, ordinary Jobs arrived at 30/s and topology-constrained Jobs at 0.3/s. We successfully created 708 constrained Jobs and observed 1,326 cumulative requeues across 448 of them. Ordinary Jobs accumulated 997 requeues. The Kueue manager's maximum valid sampled working set before stopping arrivals was 511.86 MiB against a 512Mi limit. We recorded 266 additional manager restarts with reason Error and exit code 137, together with liveness-probe failure events. These were not confirmed OOMKilled events.

**What you expected to happen**:

TAS should account for hard placement constraints that make an assignment infeasible, or provide a clear diagnostic when it cannot evaluate them. We understand that our configuration permits unlimited retries. Our concern is repeatedly admitting and recreating Pods for an unchanged, structurally infeasible Workload. We would appreciate guidance on avoiding these futile cycles and their controller overhead.

**How to reproduce it (as minimally and precisely as possible)**:

1. Enable the batch/job and pod integrations and TAS. Ensure the test namespace is managed by Kueue. Configure waitForPodsReady with timeout: 5m, recoveryTimeout: 5m, blockAdmission: false, and requeuingStrategy with backoffLimitCount: null, backoffBaseSeconds: 5, backoffMaxSeconds: 5.
2. Create a Topology with kubernetes.io/hostname as its level, a ResourceFlavor referencing that Topology, and a ClusterQueue/LocalQueue using the flavor. Provide sufficient quota and node resources; our flavor quota was 600 CPU and 1Ti memory.
3. Create a suspended batch/v1 Job with parallelism: 2, completions: 2, and backoffLimit: 0. Both Pods select the same single hostname and run an indefinite sleeping loop. Each requests 5m CPU/8Mi memory, with limits of 50m/32Mi. Set the Pod-template annotation kueue.x-k8s.io/podset-unconstrained-topology: "true". Add requiredDuringSchedulingIgnoredDuringExecution Pod anti-affinity using kubernetes.io/hostname and a label selector matching only the two Pods of this Job.
4. Observe the Workload's topologyAssignment and admission conditions. Verify that one Pod remains Pending because of anti-affinity. After approximately 300 seconds, inspect PodsReadyTimeout eviction, quota release, increased requeueState.count, subsequent Admitted=True, and replacement Pods. The first measured Job was re-admitted at T+305s.
5. For the measured load, use 100 uniformly staggered submitters at 0.003 constrained Jobs/s each, alongside 30 ordinary Jobs/s. Ordinary Jobs run sleep 1, request 5m CPU/8Mi memory, and use ttlSecondsAfterFinished: 10. Use separate worker pools/flavors for the two streams, backed by one ClusterQueue. Use one Kueue manager with requests and limits of 3 CPU/512Mi. Keep each constrained Job's anti-affinity selector unique.

**Anything else we need to know?**:

This is an intentionally infeasible workload, not evidence that TAS makes an otherwise feasible Job infeasible. The topology annotation requests unconstrained TAS; the contradiction comes from the hostname selector and required Pod anti-affinity. Job backoffLimit is separate from Kueue's requeue limit. This was one manually terminated run; continued arrivals, retained objects, and ordinary Jobs also contributed to controller load. We have not established a memory leak or isolated requeueing as the sole cause of failures. The reduced reproducer has not been independently rerun, and newer Kueue versions have not been tested.

**Environment**:

- Kubernetes version (use `kubectl version`): client/server v1.35.6, linux/amd64.
- Kueue version (use `git describe --tags --dirty --always`): v0.16.9; deployed image registry.k8s.io/kueue/kueue:v0.16.9.
- Cloud provider or hardware configuration: on-premises KVM/bare-metal cluster, 24 nodes; 18 ordinary workers and 3 constrained workers. Constrained workers had 48/104/20 allocatable CPU cores. One Kueue replica, requests/limits 3 CPU and 512Mi.
- OS (e.g: `cat /etc/os-release`): controller Ubuntu 22.04.5 LTS; constrained workers Ubuntu 22.04.3 LTS and Ubuntu 20.04.6 LTS.
- Kernel (e.g. `uname -a`): controller 6.8.0-40-generic; constrained workers 6.8.0-136-generic and 5.15.0-139-generic.
- Install tools: kubeadm; Kueue manifests managed with kubectl.
- Others: containerd 2.2.3 on VM/controller nodes and 1.7.27 on bare-metal workers; Calico; standard kube-scheduler. Kueue client QPS/burst 448/509; Job/Workload concurrency 31/5. JobSet v0.10.1 was installed but these workloads were ordinary Jobs.
