## Description

**What happened**:

With Kueue v0.16.9, we observed repeated admission, scheduling failure, PodsReadyTimeout eviction, and re-admission under unchanged CPU fragmentation. Three eligible workers each had 3 CPU cores available, totaling 9 CPU. Each Job requested one 4-CPU Pod. Kueue admitted the Workload, but kube-scheduler reported Insufficient cpu on every eligible worker. After 300 seconds, Kueue released the quota and re-admitted the Workload after backoff; the replacement Pod remained Pending.

An equal-total-capacity placement check succeeded with 5/2/2 CPU available, whereas 3/3/3 prevented placement of the same 4-CPU request. In the subsequent 100:1 load test, ordinary Jobs arrived at 30/s and fragmentation-blocked Jobs at 0.3/s. We successfully created 420 blocked Jobs and observed 424 cumulative requeues across 233 of them; ordinary-Job requeues remained zero. The observer recorded 36,969 ordinary completions before freezing. Three confirmed OOMKilled/exit-137 terminations caused automatic stopping approximately 24 minutes 16 seconds after startup. The maximum valid sampled manager working set before stopping arrivals was 504.56 MiB against a 512Mi limit. A fourth OOM occurred after arrivals stopped, before cleanup completed.

**What you expected to happen**:

We understand that non-TAS quota admission does not guarantee physical placement, and that a single Pod cannot combine CPU fragments across nodes. The concern is repeatedly recreating unschedulable Pods while the resource shape remains unchanged, together with the controller resource pressure observed under sustained arrivals. We would appreciate guidance on feasibility-aware retry conditions, clearer scheduling feedback, or an appropriate bounded retry policy.

**How to reproduce it (as minimally and precisely as possible)**:

1. Enable batch/job integration and ensure the test namespace is managed. Configure waitForPodsReady with timeout: 5m, recoveryTimeout: 5m, blockAdmission: false, and requeuingStrategy with backoffLimitCount: null, backoffBaseSeconds: 5, backoffMaxSeconds: 5.
2. Select three Ready workers without untolerated taints. Use unmanaged sleeping reservation Pods to leave exactly 3 CPU cores of request-based headroom on each worker. Calculate headroom from allocatable CPU minus scheduler-effective requests, not measured CPU utilization. Our allocatable/existing/reservation values were 48/0/45, 104/0.735/100.265, and 20/0.2/16.8 CPU. Keep reservations outside Kueue.
3. Create a ResourceFlavor selecting exactly these workers, without topologyName, and a ClusterQueue/LocalQueue with sufficient quota; ours was 600 CPU/1Ti. Submit a suspended batch/v1 Job with one Pod, parallelism: 1, completions: 1, backoffLimit: 0, CPU request/limit 4, memory request 16Mi, memory limit 64Mi, and an indefinite sleeping command. All three workers must be eligible. Do not add TAS annotations or Pod affinity/anti-affinity.
4. Observe Admitted=True while the Pod reports Insufficient cpu. After approximately 300 seconds, verify PodsReadyTimeout eviction, quota release, requeueState.count increasing, BackoffFinished, another Admitted=True, and a replacement Pending Pod. Our first Job was admitted at 02:44:46 UTC, evicted at 02:49:46, and re-admitted at 02:49:51 on November 7, 2026.
5. For the 100:1 load, use 100 uniformly staggered submitters at 0.003 blocked Jobs/s each, alongside 30 ordinary Jobs/s. Ordinary Jobs run sleep 1, request 5m CPU/8Mi memory, and use ttlSecondsAfterFinished: 10. Use separate worker pools/flavors backed by one ClusterQueue. Use one Kueue manager with requests/limits of 3 CPU/512Mi. The 600-CPU fragmentation quota permits at most 150 simultaneous 4-CPU reservations.

**Anything else we need to know?**:

This is static CPU-request fragmentation, not CPU utilization saturation or GPU fragmentation. The placement control used true instead of the sleeping command, so it was not a matched-runtime performance comparison. During sustained arrivals, total demand also exceeded the 9 CPU available; later effects cannot all be attributed exclusively to fragmentation. Unlimited retries and the 5-second backoff cap were explicit configuration choices. This was one automatically terminated run with unfinished work right-censored. We have not isolated a memory leak or the precise allocation causing OOM. The reduced reproducer has not been independently rerun, and newer Kueue versions have not been tested.

**Environment**:

- Kubernetes version (use `kubectl version`): client/server v1.35.6, linux/amd64.
- Kueue version (use `git describe --tags --dirty --always`): v0.16.9; deployed image registry.k8s.io/kueue/kueue:v0.16.9.
- Cloud provider or hardware configuration: on-premises KVM/bare-metal cluster, 24 nodes; 18 ordinary workers and 3 fragmentation workers. Fragmentation workers had 48/104/20 allocatable CPU cores. One Kueue replica, requests/limits 3 CPU and 512Mi.
- OS (e.g: `cat /etc/os-release`): controller Ubuntu 22.04.5 LTS; fragmentation workers Ubuntu 22.04.3 LTS and Ubuntu 20.04.6 LTS.
- Kernel (e.g. `uname -a`): controller 6.8.0-40-generic; fragmentation workers 6.8.0-136-generic and 5.15.0-139-generic.
- Install tools: kubeadm; Kueue manifests managed with kubectl.
- Others: containerd 2.2.3 on VM/controller nodes and 1.7.27 on bare-metal workers; Calico; standard kube-scheduler. Kueue client QPS/burst 448/509; Job/Workload concurrency 31/5. JobSet v0.10.1 was installed but these workloads were ordinary Jobs.
