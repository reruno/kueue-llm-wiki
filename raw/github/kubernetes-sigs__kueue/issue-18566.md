## Description

**What happened**:

With `ElasticJobsViaWorkloadSlicesWithTAS` enabled, only unconstrained topology is supported for elastic jobs. The Job webhook rejects an elastic Job with `kueue.x-k8s.io/podset-required-topology` or `kueue.x-k8s.io/podset-preferred-topology` (`pkg/controller/jobs/job/job_webhook.go`, `validateTopologyRequest`), but the RayCluster, RayJob, RayService and SparkApplication webhooks accept it.

The Workload is then created and stays pending, because the scheduler marks the PodSet with `required topology is not supported with ElasticJobsViaWorkloadSlices` (or `preferred topology ...`) in `pkg/scheduler/flavorassigner/tas_flavorassigner.go`.

**What you expected to happen**:

The RayCluster, RayJob, RayService and SparkApplication webhooks reject an elastic job with required or preferred topology at creation when `ElasticJobsViaWorkloadSlicesWithTAS` is enabled, as agreed for KEP-77 in https://github.com/kubernetes-sigs/kueue/pull/18447#discussion_r4494656483.

With the gate disabled, these jobs stay accepted: TAS places each Workload slice independently, so required and preferred topology are valid there. The existing Job check, which depends on `ElasticJobsViaWorkloadSlices` only, stays as is.

To keep existing elastic jobs updatable after an upgrade (for example, autoscaler updates to a RayCluster), the check should run on create only, like the RayService upgrade-strategy check.

**How to reproduce it (as minimally and precisely as possible)**:

1. Enable `ElasticJobsViaWorkloadSlices`, `TopologyAwareScheduling` and `ElasticJobsViaWorkloadSlicesWithTAS` (and `ElasticJobsViaWorkloadSlicesForSparkApplication` for Spark).
2. Create a RayCluster with a queue name, `kueue.x-k8s.io/elastic-job: "true"`, and `kueue.x-k8s.io/podset-required-topology: cloud.com/block` on a worker group template.
3. The RayCluster is accepted, and its Workload stays pending with `required topology is not supported with ElasticJobsViaWorkloadSlices`.

The same happens for RayJob, RayService, and SparkApplication (annotation on the driver or executor).

**Anything else we need to know?**:

KEP-77 tracks this as an open Alpha item in the `ElasticJobsViaWorkloadSlicesWithTAS` graduation criteria (#18447).

KubeRay copies the parent's labels, annotations and spec to the child RayCluster, so the RayCluster webhook also validates the children of RayJobs and RayServices, as it already does for the elastic scheduling gate check.
