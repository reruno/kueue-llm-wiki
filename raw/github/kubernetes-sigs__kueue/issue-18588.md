## Description


**What happened**:

While reviewing the asynchronous inadmissible-Workload requeue path, I found a potential lost-retry scenario: a transient failure to read a Workload's Namespace is treated exactly like an ineligible namespace/backoff check. The Workload remains in the inadmissible map, but the one-shot requeue request is consumed without preserving the failed lookup or scheduling another retry.

**Verification status:** This is a **source-level finding** on upstream `main` at `a3e22d85246d69e22bb747340ffebe96607cc830`. I have **not yet run a controlled fault-injection reproduction or a large-scale benchmark**. The execution path and proposed regression test are detailed below for maintainers to verify independently.

## Exact code path

1. [`requeueWorkloadsCQ` (L90–104)](https://github.com/kubernetes-sigs/kueue/blob/a3e22d85246d69e22bb747340ffebe96607cc830/pkg/cache/queue/inadmissible_workloads.go#L90-L104) takes the **exclusive queue-manager lock** with `m.Lock()`. [`requeueWorkloadsCohort` (L112–131)](https://github.com/kubernetes-sigs/kueue/blob/a3e22d85246d69e22bb747340ffebe96607cc830/pkg/cache/queue/inadmissible_workloads.go#L112-L131) does the same for a whole cohort subtree.
2. [`queueInadmissibleWorkloads` (L152–175)](https://github.com/kubernetes-sigs/kueue/blob/a3e22d85246d69e22bb747340ffebe96607cc830/pkg/cache/queue/inadmissible_workloads.go#L152-L175) holds `c.rwm.Lock()` while iterating over **every** inadmissible Workload. The loop executes one `client.Get(Namespace)` **per Workload**, even when many Workloads share the same Namespace.
3. Any Namespace lookup error is silently swallowed by `if err != nil || ... { continue }`. It is not reported or classified as transient/permanent.
4. [`workqueueRequeuer.reconcile` (L273–280)](https://github.com/kubernetes-sigs/kueue/blob/a3e22d85246d69e22bb747340ffebe96607cc830/pkg/cache/queue/inadmissible_workloads.go#L273-L280) returns no error. Its caller [`Start` (L256–270)](https://github.com/kubernetes-sigs/kueue/blob/a3e22d85246d69e22bb747340ffebe96607cc830/pkg/cache/queue/inadmissible_workloads.go#L256-L270) calls `queue.Done(item)` with no retry for the error skipped in step 3.
5. If that notification was the only signal that newly freed quota/capacity made the Workload schedulable, the Workload is not reconsidered until **another event** triggers a requeue.

Relevant excerpt (existing logic, simplified to emphasize the failure branch):

```go
// requeueWorkloadsCQ holds m.Lock(); queueInadmissibleWorkloads holds c.rwm.Lock().
for key, wInfo := range c.workloads.inadmissible {
    ns := corev1.Namespace{}
    err := client.Get(ctx, types.NamespacedName{Name: wInfo.Obj.Namespace}, &ns)
    if err != nil || !c.namespaceSelector.Matches(labels.Set(ns.Labels)) ||
        !c.backoffWaitingTimeExpired(wInfo) {
        continue // A transient API/cache error is lost here.
    }
    if c.workloads.MoveToActive(key, wInfo) {
        moved++
    }
}
```

## Why this matters

- **Correctness / liveness:** A transient Namespace lookup failure during the sole requeue notification can leave an otherwise schedulable Workload in `inadmissible`, particularly in a quiet ClusterQueue/cohort with few subsequent events. This is a potential lost scheduling opportunity, not merely a delayed log/event.
- **Throughput:** The same path performs O(number of inadmissible Workloads) Namespace client reads while holding the queue-manager's exclusive lock, then the per-CQ lock. Even with an informer-backed client, repeated reads and any stalled read lengthen the critical section. The cohort path scans its child CQs under the same manager lock.
- **Observability:** A skipped read error currently looks identical to a selector mismatch or valid backoff; there is no explicit error/retry signal.

**What you expected to happen**:

1. A transient Namespace lookup failure should **not consume the last scheduling opportunity**. When reads succeed again, an otherwise eligible and backoff-expired Workload should eventually be retried without requiring an unrelated workload/cluster mutation.
2. A genuinely deleted Namespace should still be handled safely (no tight retry loop for `IsNotFound`), and Namespace selectors and per-Workload backoff must continue to be honored.
3. Processing should avoid redundant Namespace reads and minimize client I/O under the queue-manager's exclusive lock.
4. Workloads that can be moved in a partially failing batch should still advance and be broadcast; one problematic Namespace should not stall other Workloads.

**How to reproduce it (as minimally and precisely as possible)**:

Proposed deterministic regression test (fault injection; **not yet run**):

1. Construct a queue-manager fixture with a `ClusterQueue`, matching `Namespace`, `LocalQueue`, and an inadmissible Workload whose backoff has expired. Make its previous scheduling restriction disappear (or inject the normal `NotifyRetryInadmissible` signal).
2. Wrap the test client so the **first** `Get` for that Namespace returns a transient non-`NotFound` error, while all subsequent reads succeed. Use a fake/interceptor client; no flaky apiserver is needed.
3. Process **exactly one** requeue request. On current `main`, `queueInadmissibleWorkloads` skips the Workload; `moved == 0`; the request is marked done without a retry.
4. Restore the client and leave the cluster idle. Assert that a bounded retry eventually moves the Workload to the active heap. There is no such retry mechanism in the current requeue path.
5. Repeat with a cohort containing two CQs: one Namespace lookup fails, the other succeeds. The successful Workload must still advance.

Illustrative fault injection (pseudocode; **not a ready-to-run patch**):

```go

// Assert eventual move to the active heap without another external trigger.
```

## Suggested implementation direction (open to maintainer feedback)

1. **Recover transient lookup failures.** Separate Namespace lookup errors from selector mismatch/backoff. Propagate a `retryNeeded` indication (or error) through CQ/cohort helpers and arrange bounded delayed retries without a hot loop. Preserve partially moved Workloads and distinguish `NotFound` from retryable failures.
2. **Deduplicate Namespace reads.** Resolve each distinct Namespace once per batch, ideally from a cached snapshot outside the queue-manager's exclusive lock. If prefetch happens outside the lock, revalidate Workload identity, current queue membership, selector and backoff under the lock before moving anything.
3. **Preserve concurrency invariants.** Keep correct behavior for `SchedulingEquivalenceHashing`, fair sharing, cohort traversal, deletion/recreation races, metrics, broadcasts, and shutdown/cancellation. Avoid waiting on client reads while holding the exclusive manager lock.
4. **Tests and benchmarks.** Isolated CQ and cohort retries; one failing Namespace mixed with successful ones; `NotFound` vs transient errors; selector changes; backoff not elapsed; delete/recreate during prefetch; repeated signals; cancellation; large-batch performance.

## Acceptance criteria

- [ ] A transient Namespace lookup error is surfaced and eventually retried instead of silently dropped.
- [ ] When the injected error clears, an otherwise eligible Workload is reconsidered without another independent triggering event.
- [ ] No unbounded retries on nonexistent Namespaces or intentionally ineligible/backing-off Workloads.
- [ ] Partially successful CQ/cohort batches still advance eligible Workloads and preserve scheduler notifications.
- [ ] Duplicate Namespace reads and lock-held duration are measured before/after; regular scheduler tests remain passing.
- [ ] Regression tests exercise errors, concurrency, backoff, and cohort behavior.
