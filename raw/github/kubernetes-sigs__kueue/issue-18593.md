## Description

/kind bug

**What happened**:

In a controller-runtime fake-client reproduction with `DynamicQuotaOrchestration` enabled, two active DynamicQuotaOrchestrators manage sibling Cohorts: `dqo-a` on `team-a` and `dqo-b` on `team-b`. Updating ClusterQueue `cq-moved` from `team-a` to `team-b` changes `spec.cohortName` and switches `spec.resourceGroups` from `pool-a` to `pool-b`.

`dqo-b` should take over `cq-moved`. Instead it stops distributing for its whole subtree:

```yaml
- type: Distributed
  status: "False"
  reason: EffectiveQuotasConflict
  message: ClusterQueue "cq-moved" already managed by DynamicQuotaOrchestrator/dqo-a
```

`dqo-a` is still `Distributed=True`. It no longer lists `cq-moved` among its targets, so it never writes `cq-moved` again. Nothing clears the old `orchestratorRef`, so nothing gets better on its own. The following table summarizes the reported local reproduction and source-level consequences (each provider initially reports 100 CPU). The supplied minimal regression test below directly checks the post-move condition, owner, and flavor; the later capacity-shrink scenario needs an additional test:

| | before the move | after the move | after `cp-b` drops to 40 CPU |
|---|---|---|---|
| `dqo-b` | `Distributed=True` | `False / EffectiveQuotasConflict` | `False / EffectiveQuotasConflict` |
| `cq-a1` (team-a) | dqo-a, `pool-a` cpu=50 | dqo-a, `pool-a` cpu=**100** | dqo-a, `pool-a` cpu=100 |
| `cq-moved` | dqo-a, `pool-a` cpu=50 | **dqo-a, `pool-a` cpu=50** (spec says `pool-b`) | dqo-a, `pool-a` cpu=50 |
| `cq-b1` (team-b) | dqo-b, `pool-b` cpu=100 | dqo-b, `pool-b` cpu=100 | **dqo-b, `pool-b` cpu=100** |

The move causes three problems:

1. **`pool-a` is over-committed.** `dqo-a` gives all 100 CPU of `pool-a` to the queues still in its subtree. `cq-moved` keeps its old 50, so the effective nominal quota for `pool-a` adds up to 150 against 100 discovered. `cq-moved` is now in `team-b` under `org`, so that stale 50 is also lent into a Cohort tree that `dqo-a` does not manage.
2. **The whole `dqo-b` subtree stops getting updates.** `findOwnershipConflict` runs before `applyEffectiveQuotas`, so no target in `team-b` is written. When `pool-b` falls from 100 to 40 CPU, `cq-b1` still has 100. Kueue can keep admitting workloads against quotas that no longer reflect the latest capacity report. Pod scheduling impact still needs an end-to-end reproduction.
3. **The admin's spec change is ignored.** The scheduler cache uses `status.effectiveQuotas` whenever it is set ([`EffectiveResourceGroups`](https://github.com/kubernetes-sigs/kueue/blob/3529813c8c8ab8b1c2d42b24a07ced7b9c1a008f/pkg/util/resourcegroups/effective.go#L30)). So `cq-moved` keeps admitting against `pool-a` and has no `pool-b` quota, even though its spec now declares `pool-b` only.

Moving a whole Cohort has the same effect. Changing `spec.parentName` of a Cohort `squad` from `team-a` to `team-b` deactivates `dqo-b` with `ClusterQueue "cq-squad" already managed by DynamicQuotaOrchestrator/dqo-a`.

**What you expected to happen**:

An `orchestratorRef` should block takeover only while the referenced orchestrator can still write the object. Once the object has left that orchestrator's subtree, its current orchestrator should take it over:

- `dqo-b` stays `Distributed=True`.
- `cq-moved` gets `orchestratorRef: dqo-b` and its proportional share of `pool-b` (50/50 with `cq-b1` here).
- Later capacity changes in `pool-b` keep flowing to `team-b`.

**Anything else we need to know?**:

### Existing documented behavior and scope

The [DQO concepts documentation](https://kueue.sigs.k8s.io/docs/concepts/dynamic_quota_orchestration/#caveats) already notes that effective quotas remain after moving a ClusterQueue or Cohort out of a managed subtree; the [setup troubleshooting guide](https://kueue.sigs.k8s.io/docs/tasks/manage/setup_dynamic_quota_orchestration/#troubleshooting) explicitly identifies leftover ownership as a possible cause of `EffectiveQuotasConflict` and advises manual status cleanup.

Therefore this report is **not claiming the retained quota behavior is undocumented**. The concern is that a moved object can prevent *every target in an otherwise healthy destination subtree* from receiving subsequent capacity updates, until an operator manually repairs ownership. I'd like maintainer input on whether safe cross-subtree ownership handoff should be supported automatically, or whether this should instead be tracked as an enhancement to the current alpha behavior.

### Root cause

[`checkManagedConflict`](https://github.com/kubernetes-sigs/kueue/blob/3529813c8c8ab8b1c2d42b24a07ced7b9c1a008f/pkg/controller/core/dqo/distribution.go#L164-L212) treats `status.effectiveQuotas.orchestratorRef` as an ownership claim whenever the referenced DQO exists, is distributing and is not `Distributed=False`. It allows takeover only in these cases:

- the other DQO is being deleted or has no `capacityDistribution`;
- the other DQO is `Distributed=False` (added in #15505);
- the current DQO's root is a strict ancestor of the other DQO's root;
- both roots are the same and the current DQO has precedence.

None of these checks whether the other DQO's **current** subtree still contains the object. When a ClusterQueue or Cohort moves to another Cohort, it keeps the `orchestratorRef` of a DQO that will never write it again. [`resolveSubtree`](https://github.com/kubernetes-sigs/kueue/blob/3529813c8c8ab8b1c2d42b24a07ced7b9c1a008f/pkg/controller/core/dqo/distribution.go#L482) no longer returns it for that DQO. The check then returns `already managed by …` at [L211](https://github.com/kubernetes-sigs/kueue/blob/3529813c8c8ab8b1c2d42b24a07ced7b9c1a008f/pkg/controller/core/dqo/distribution.go#L211), and [`reconcileDistribution`](https://github.com/kubernetes-sigs/kueue/blob/3529813c8c8ab8b1c2d42b24a07ced7b9c1a008f/pkg/controller/core/dqo/distribution.go#L73-L76) stops before writing any target.

### Why it never recovers

- `dqo-a` stays `Distributed=True`. It never writes `cq-moved` again, so it never clears or rewrites the mark.
- Nothing sets `dqo-a` to `Distributed=False`, so the #15505 takeover path does not apply.
- The opt-in TTL in #18314 / #18111 would eventually stop the scheduler from using the stale `pool-a` quota (problem 1). It does not change `checkManagedConflict`, and an expired effective quota keeps its `orchestratorRef`. So `dqo-b` would still be blocked (problem 2).
- The documented operator workaround is to clear the moved object's `status.effectiveQuotas` manually (for example with a status-subresource JSON patch). Removing or deactivating the original orchestrator also affects the original subtree.

### Why existing tests do not catch it

The two tests that cover this branch, [`effective quotas conflict when managed by another DynamicQuotaOrchestrator`](https://github.com/kubernetes-sigs/kueue/blob/3529813c8c8ab8b1c2d42b24a07ced7b9c1a008f/pkg/controller/core/dqo/distribution_test.go#L844) and [`managed conflict where other DQO root is non-existent returns conflict error`](https://github.com/kubernetes-sigs/kueue/blob/3529813c8c8ab8b1c2d42b24a07ced7b9c1a008f/pkg/controller/core/dqo/distribution_test.go#L1457), point the other DQO at a root object that does not exist. No test has an owner DQO whose root exists but no longer contains the object.

### Relation to the KEP

KEP-12382's [Stale Effective Quota](https://github.com/kubernetes-sigs/kueue/blob/3529813c8c8ab8b1c2d42b24a07ced7b9c1a008f/keps/12382-dynamic-quota-orchestration/README.md#stale-effective-quota) section keeps a stale effective quota in effect when the **owner** stops managing it: the DQO is deleted, deactivated or unpinned, or distribution is disabled. Here the owner is healthy, and another active DQO now covers the object and is ready to write it. Treating the stale mark as a claim does not protect an owner. It just leaves the object with no writer and blocks a whole subtree.

### Possible fix (proposal, not yet accepted)

Keep existing protection against two simultaneously covering DQOs, but consider an `orchestratorRef` stale if the referenced active DQO's **current** subtree no longer contains the target. Do not treat API lookup failures or an unresolvable root as proof that takeover is safe. A concrete candidate diff is below; it still needs integration coverage for concurrent reconciles, reparenting, missing references, and non-DQO ownership.


In `checkManagedConflict`, after the `Distributed=False` check, allow takeover when the other DQO's subtree no longer contains the object. To keep today's conservative behavior when the other DQO's root cannot be found (that DQO soon reports `Distributed=False / Misconfigured`, and #15505 takes over from there), the helper treats a missing root as still covering the object:

```diff
@@ func (r *Reconciler) checkManagedConflict(
 	if isDistributedFalse(other) {
 		// The other orchestrator is deactivated; its effective quota can be taken over.
 		return nil
 	}
+	covered, err := r.subtreeCovers(ctx, other.Spec.CapacityDistribution.SubtreeRootQuotaRef, kind, name)
+	if err != nil {
+		return err
+	}
+	if !covered {
+		// The object left the other orchestrator's subtree, for example after a
+		// spec.cohortName or spec.parentName change. That orchestrator no longer
+		// writes it, so its orchestratorRef is a stale mark, not an ownership claim.
+		return nil
+	}
 	isAncestor, err := r.isStrictAncestor(ctx, currentRoot, other.Spec.CapacityDistribution.SubtreeRootQuotaRef)

+// subtreeCovers reports whether the subtree rooted at root currently contains the
+// ClusterQueue or Cohort identified by kind and name. When root itself cannot be
+// found it answers true, so an unresolvable owner keeps blocking takeover until it
+// reports Distributed=False.
+func (r *Reconciler) subtreeCovers(
+	ctx context.Context,
+	root kueuealpha.CapacityDistributionSubtreeRootRef,
+	kind kueuealpha.SubtreeRootRefKind,
+	name string,
+) (bool, error) {
+	target := kueuealpha.CapacityDistributionSubtreeRootRef{Kind: kind, Name: name}
+	if root == target {
+		return true, nil
+	}
+	var rootObj client.Object
+	switch root.Kind {
+	case kueuealpha.CohortSubtreeRootRefKind:
+		rootObj = &kueue.Cohort{}
+	case kueuealpha.ClusterQueueSubtreeRootRefKind:
+		rootObj = &kueue.ClusterQueue{}
+	default:
+		return true, nil
+	}
+	if err := r.client.Get(ctx, types.NamespacedName{Name: root.Name}, rootObj); err != nil {
+		if apierrors.IsNotFound(err) {
+			return true, nil
+		}
+		return false, err
+	}
+	return r.isStrictAncestor(ctx, root, target)
+}
```

Results reported by the earlier local reproduction work (not independently re-run for this issue):

- The test above passes. `dqo-b` takes over `cq-moved`, splits `pool-b` 50/50, and follows the drop to 40 CPU (20/20).
- The Cohort-move variant (`squad` moved from `team-a` to `team-b`) passes.
- All existing tests pass: `go test ./pkg/controller/core/dqo/...` is `ok`, including the two conflict tests above.

The proposed membership check should also be tested against informer-cache skew and concurrent reconciliation: do not assume a single shared snapshot or promise that ownership cannot ping-pong without an integration test.

### Open questions for maintainers

1. When the object moves to a Cohort that **no** DQO covers, it keeps `dqo-a`'s share, and `pool-a` stays over-committed (problem 1) until an admin clears it, or until the TTL from #18314 expires it if one is set. Is that acceptable as the KEP's "stale effective quota" behavior? Or should a DQO release `status.effectiveQuotas` on objects that still reference it but have left its subtree, for example through an index on `orchestratorRef`?
2. Should the DQO watch on ClusterQueues/Cohorts also enqueue the **previous** owner from `status.effectiveQuotas.orchestratorRef`? Today the predicate is `GenerationChangedPredicate` and the map function enqueues every distributing DQO, so this works, but only by fanning out to all of them.

Suggested acceptance criteria for a follow-up PR:
1. Cross-subtree ClusterQueue and Cohort moves can hand ownership to the destination DQO without disabling unrelated destination targets.
2. Legitimate overlapping-subtree conflicts and non-DQO owners remain protected.
3. A missing root or transient API read error never triggers unsafe takeover.
4. Capacity shrink after the move updates all eligible destination queues; test with real reconciler watches and the feature gate enabled.
5. Define what should happen if an object moves outside *every* DQO's coverage, including compatibility with the stale-effective-quota policy.

I can prepare a PR with the focused fix and regression/integration coverage if maintainers agree with the desired handoff semantics.
