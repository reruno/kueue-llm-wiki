## Description

**What happened**:

A workload in its second pass (TAS node replacement, or the delayed topology assignment after a ProvisioningRequest) already holds its quota reservation, and the ClusterQueue snapshot already includes that usage. But when the second pass needs to preempt, `buildContext` still sets the preemptor's quota to its full request:

https://github.com/kubernetes-sigs/kueue/blob/4d6d8679f489302def49939620cd3368ade28cdb/pkg/scheduler/preemption/preemption.go#L303-L308

and `workloadQuotaFits` compares that against `Available()`, which has already subtracted the workload's own usage:

https://github.com/kubernetes-sigs/kueue/blob/4d6d8679f489302def49939620cd3368ade28cdb/pkg/scheduler/preemption/preemption.go#L667-L677

So the workload's quota is counted twice. Preemption only succeeds if the free quota plus the quota the victims give back covers the whole workload a second time.

For example, `foo` is in its second pass and already holds 3 CPUs of quota. It needs the node that the lower-priority `blocker` is on:

| CPU quota | `foo` holds | `blocker` holds | Free after evicting `blocker` | `foo` is checked for | Result on main |
|---|---|---|---|---|---|
| 10 | 3 | 2 | 7 | 3 | `blocker` preempted |
| 6 | 3 | 3 | 3 | 3 | `blocker` preempted |
| 5 | 3 | 2 | 2 | 3 | no victims found |

`foo` should need 0 extra quota in every row, because its 3 CPUs are already reserved. In the last row the scheduler logs:

```
Workload requires preemption, but there are no candidate workloads allowed for preemption
```

The workload is requeued with `PreemptionNoCandidates` and keeps retrying until the lower-priority workloads finish on their own.

I hit this while testing node replacement (related to my other issue https://github.com/kubernetes-sigs/kueue/issues/16900), now with `TASFailedNodeReplacementFailFast` disabled, and reproduced it on main with the unit tests below.

**What you expected to happen**:

The reservation already covers the workload's quota, so the second pass should only need its topology to fit once the victims are gone. That's also how the scheduler's own fit check treats a workload with a reservation (`netUsage`).

**How to reproduce it (as minimally and precisely as possible)**:

Two `TestScheduleForTAS` cases (I'll include them in the PR). Both fail on main at `4d6d8679f` and pass with the fix:

1. ProvisioningRequest second pass: the existing "preempts under a pods quota" case, but with the CPU quota lowered from 10 to 5 so the queue is full (`foo` holds 3, `blocker` holds 2). `blocker` is never preempted.
2. Node replacement with `TASFailedNodeReplacementFailFast=false`: one rack of three 1-CPU nodes and 3 CPUs of quota. A 2-pod job loses one of its nodes, and a priority -1 `blocker` is on the third node. `blocker` is never preempted.

**Anything else we need to know?**:

- #16167 fixed a similar double count in the same function (`pods` added to the request twice). Its test doesn't catch this one because the queue there has twice the quota it needs.
- The ProvisioningRequest path hits this with no feature gates. The node replacement path needs `TASFailedNodeReplacementFailFast` off; with it on (the default), the workload is evicted instead of trying to preempt.
- Proposed fix: in `buildContext`, set the quota the preemptor adds to zero while `workload.NeedsSecondPass(wl.Obj)` is true, but keep its flavor-resources in the map. The fit check then passes on quota, and the borrowing checks (`borrowWithinCohort`, hierarchical reclaim, Fair Sharing) still run against the usage the ClusterQueue already has. I check `NeedsSecondPass` rather than `HasQuotaReservation` because `TestFairPreemptions` has an incoming workload with a reservation in a different ClusterQueue, and that one still needs its request charged.
- Related: #15337 and #15561 are deciding whether a node replacement should preempt at all. If it stays allowed, it needs this fix. The ProvisioningRequest path needs it either way.
