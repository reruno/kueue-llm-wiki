#18616 did not cause it. [A run on #18591](https://prow.k8s.io/view/gs/kubernetes-ci-logs/pr-logs/pull/kubernetes-sigs_kueue/18591/pull-kueue-test-integration-multikueue-main/2120493354281078784) failed the same way. Green runs take about 10 minutes.

### Comment by [@ekam-walia](https://github.com/ekam-walia) — 2026-11-11T16:36:27Z

Hi all, I think this happened 

The 3 parallel Ginkgo worker processes were OOM-killed (SIGKILL) only 6.5 minutes into the run (13:33:54). Because they died abruptly without reporting back, the parent Ginkgo CLI hung waiting for results until the overall 55-minute job timeout expired.

Why the OOM occurred (The Resource Leak):
In envtest, namespaces do not automatically garbage-collect child objects on deletion.
DeleteNamespace in` test/util/behavioral/namespace.go` cleans up workloads and calls `c.Delete(ctx, ns)`, marking the namespace as Terminating.
However, `DeleteNamespace `never called several existing cleanup helpers from jobs.go (e.g., `DeleteAllRayServicesInNamespace`, `DeleteAllTrainJobsInNamespace`, `DeleteAllLeaderWorkerSetsInNamespace`).
Because of this, custom resources like RayService remained alive in terminating namespaces after their tests ended.
As subsequent tests ran, controllers saw these leftover jobs without workloads, continuously failed to recreate workloads in terminating namespaces, and entered tight reconcile/requeue loops. Across 3 parallel workers and multiple control planes, this churn exhausted container memory and triggered the OOM kill.

The Fix could be 
In test/util/behavioral/namespace.go, update DeleteNamespace to call all missing DeleteAll*InNamespace helpers (for RayService, RayCluster, TrainJob, LeaderWorkerSet, and Kubeflow jobs) before deleting workloads and the namespace itself.
