**Remaining time and follow-up candidates**

Across the same 22 successful logs, stage medians are:

| Stage | Median | Range |
| --- | ---: | ---: |
| Manager image build | 171s | 166–182s |
| Backend module download + race tests | 97s | 93–113s |
| Cluster creation | 44s | 38–50s |
| Image preparation / loading | 5s / 8s | 4–6s / 8–11s |
| Kueue deployment, including readiness | 10s | 8–17s |
| Backend rebuild | 3s | 2–4s |
| Frontend container, including setup/unit tests/Cypress | 91.5s | 90–102s |
| RBAC stage | 3s | 2–3s |
| Time outside the first-to-last Make timing span | 54s | 53–96s |

Medians are computed independently and should not be summed. The [583s outlier](https://prow.k8s.io/view/gs/kubernetes-ci-logs/pr-logs/pull/kubernetes-sigs_kueue/18544/pull-kueue-test-e2e-kueueviz-main/2120852072302645248) has both a slower Make span (487s versus a 443s median) and 96s outside that span; it is not evidence that backend compilation-cache reuse stopped working.

I would prioritize these follow-ups:

1. **Remove unnecessary KueueViz preparation.** The shared image helpers still pull and load two agnhost versions. Current KueueViz example Jobs use busybox and the RBAC fixture uses pause; neither the browser scenarios nor the RBAC script references agnhost. A KueueViz-specific image selection is a small candidate to validate while preserving the manager image and all tests. The entire image preparation/loading budget is only about 13s, so its potential saving is bounded.
2. **Reduce frontend installation work.** The [latest log](https://storage.googleapis.com/kubernetes-ci-logs/pr-logs/pull/kubernetes-sigs_kueue/18662/pull-kueue-test-e2e-kueueviz-main/2120864902225596416/build-log.txt) shows `apt-get install -y curl make xdg-utils` installing **69 new packages**, followed by two npm installations (6s and 11s in that run). First time these substeps separately, then test the minimal required system-package set / `--no-install-recommends`; a maintained prepared runner image is a larger alternative. Cypress itself is already only 45–48s for all 17 tests, and the frontend stage also includes the 132 unit tests. Do not treat all 91.5s as removable setup.
3. **Benchmark manager compilation for this job specifically.** Its current `kind-image-build` path still passes empty `IMAGE_BUILD_GOMAXPROCS` and `IMAGE_BUILD_GO_PARALLELISM`. The 2/2 tuning in #18624 applies to `image-presubmit`, not this single-platform path. Compare automatic versus explicit budgets under this job's actual **3.7 CPU / 10Gi** limits; do not assume the multi-platform result transfers unchanged.
4. **Consider overlapping independent setup only after measuring resource contention.** Frontend dependency preparation or cluster preparation may overlap with other stages, but blindly parallelizing the two expensive Go compilation paths on 3.7 CPU can make the job slower. Preserve explicit readiness, failure propagation, artifact collection, and cleanup.

I would keep the race detector, all tests, Cypress video/screenshots, and the real-cluster RBAC assertions. Backend rebuild/RBAC micro-optimizations now have very little upside. Shrinking the cluster is a larger semantic change: the existing two workers have different flavor labels, and the image loader currently requires worker nodes, so simply switching to a control-plane-only cluster is not a drop-in optimization.

The next useful experiment is a narrow preparation change with repeated alternating baseline/candidate runs, recording both whole-job time and stage time. No additional speedup is claimed until that comparison passes the full existing suite.
