## Description

**What happened**:

While a ClusterQueue is being deleted and still holds the `kueue.x-k8s.io/resource-in-use` finalizer because admitted workloads reserve quota, its resource metrics stop updating. When those workloads finish, these gauges keep the value they had when the deletion started:

- `kueue_cluster_queue_resource_reservation` and `kueue_cluster_queue_resource_usage` (with `metrics.enableClusterQueueResources`)
- `kueue_cohort_subtree_resource_reservations` for the ClusterQueue's cohort and its ancestors

They are cleared only once the last workload finishes and the ClusterQueue is gone.

The ClusterQueue `Update` event handler returns early for an object with a `deletionTimestamp`, so it never refreshes the ClusterQueue resource metrics. `Reconcile` still runs for the terminating ClusterQueue and updates its status, but it calls `RecordCohortMetrics` only for ClusterQueues that are not being deleted.

**What you expected to happen**:

The gauges follow the reservations of the terminating ClusterQueue while it drains, the same way its status (`flavorsReservation`) already does.

**How to reproduce it (as minimally and precisely as possible)**:

1. Enable `metrics.enableClusterQueueResources`.
2. Create a ClusterQueue in a cohort and admit two workloads that request 1 CPU each. Both gauges show 2.
3. Delete the ClusterQueue. It stays Terminating because of the finalizer.
4. Finish one workload.
5. `kueue_cluster_queue_resource_reservation` and `kueue_cohort_subtree_resource_reservations` still show 2 instead of 1.

An integration spec for this scenario fails on main with `Expected <float64>: 2 to equal <float64>: 1`.

**Anything else we need to know?**:

This came up in the review of #14180 ([comment](https://github.com/kubernetes-sigs/kueue/pull/14180#discussion_r4537715249)), whose fix commit includes the change. It is split out so that it can be cherry-picked. The same code is in release-0.20 and release-0.19.
