## Description

**What would you like to be added**:

A way to cap the total number of Workload objects, both per-ClusterQueue and cluster-wide. The limit should count every non-deleted Workload — pending, reserving (quota reserved, including admitted and those awaiting AdmissionChecks), and finished-but-not-yet-garbage-collected — and reject creation of new Workloads once the limit is reached.

Concretely this would be an optional, opt-in guardrail:
- a per-ClusterQueue limit (unset = no limit);
- a cluster-wide limit (unset = no limit).

This issue is intentionally scoped to the *problem and the semantics*; the exact API surface (field names, where the cluster-wide limit lives, validation vs. status reporting) is left for a follow-up KEP if there is interest.

**Why is this needed**:

We hit a concrete production failure caused by unbounded Workload growth:

1. A large number of Workloads finished and accumulated as objects. Because finished Workloads are only deleted by `objectRetentionPolicies` (and that retention was not aggressive enough / not configured), they kept piling up in etcd.
2. The growing volume of Workload objects degraded etcd — the object count and the size of LIST responses for the Workload resource grew until etcd became slow and unhealthy.
3. When the kueue-controller-manager restarted, its startup `LIST` of all Workloads (to warm the informer cache) timed out against the degraded etcd, so the controller could not finish initializing and failed to start. The scheduler stayed down until Workload objects were manually cleaned up.

This is a self-reinforcing failure: the more Workloads accumulate, the slower the LIST, and the harder it is for Kueue to recover by restarting — exactly when an operator most needs it back. A guardrail that bounds the number of Workload objects at admission time prevents the pile-up from ever reaching the point where etcd and controller startup are affected.

This failure mode is already acknowledged upstream in a narrower form: #13029 bounded the visibility pending-workloads list specifically "to prevent OOM and panic". That was a local patch at one consumer. The root cause — an unbounded number of Workload objects — also pressures etcd and the controller's own startup LIST as described above. Addressing it at admission time tackles the cause at the source rather than hardening each consumer after the fact.

**Why existing mechanisms do not cover this**:

The reserved `pods` resource quota on a ClusterQueue can cap the number of pods admitted at a time. That is a *concurrency / resource-occupancy* control and differs from what this requests:

| Aspect | `pods` resource quota (existing) | This request |
|---|---|---|
| Counts | pod count at admission | Workload **object** count |
| Pending backlog | not bounded | bounded |
| Finished (not yet GC'd) | not counted | counted |
| Protects | concurrent resource usage | etcd / controller object-count pressure |

In short, the existing mechanism guards *concurrent resources*; the missing dimension is *object count*, which is what pressures etcd and the controller's startup LIST.

**Known design tensions (for discussion)**:

Flagging these up front so the direction can be agreed before any API work:

1. **Enforcement strictness.** Counting at a validating webhook via the informer cache is cheap but approximate — concurrent creates can briefly overshoot the limit. Is a best-effort guardrail acceptable, or is strict (no-overshoot) enforcement required? The former is far simpler; the latter needs an admission-time counter.
2. **Finished Workloads and retention coupling.** If finished Workloads count toward the limit, capacity is only freed by deletion. Clusters that do not configure `objectRetentionPolicies.workloads.afterFinished` could have a queue permanently wedged by historical finished Workloads. Mitigation (require retention when the limit is set, or surface a prominent warning) needs to be decided.
