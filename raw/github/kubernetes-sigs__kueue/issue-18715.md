## Description

**What happened**:

#17127 Dynamic Allocation support defect: with `waitForPodsReady`, a SparkApplication with Dynamic Allocation gets the wrong PodsReady floor.

- **Before it starts**, PodsReady expects `minExecutors` ready executors, while the driver starts with the largest of the executor instances, `minExecutors` and `initialExecutors`. With `initialExecutors: 4` and `minExecutors: 2`, PodsReady turns True once 2 executors are ready, so `waitForPodsReady` cannot catch an application whose initial executors never all start.
- **When `minExecutors` is unset**, the floor falls back to the executor instances, while Spark's minimum is 0. Once the application has scaled down below its instances, PodsReady turns False although the application runs as configured.

**What you expected to happen**:

PodsReady waits for the executors the driver starts with (`max(instances, minExecutors, initialExecutors)`, capped at the executors Kueue grants) until the application has been ready, and then tolerates scaling down to `minExecutors` (0 when unset), how far the application is configured to scale down. A replacement workload slice expects `minExecutors`: Kueue creates one only once the driver stops ramping up to its initial executors.

**How to reproduce it (as minimally and precisely as possible)**:

1. Enable `waitForPodsReady` and `ElasticJobsViaWorkloadSlicesForSparkApplication`.
2. Run an elastic SparkApplication with `spec.dynamicAllocation` `minExecutors: 2`, `initialExecutors: 4`, `maxExecutors: 4`, with executor readiness staggered (for example an init container that sleeps 10–40s by executor ID).
3. Watch the Workload's `PodsReady` condition against the ready executor Pods: it turns True at the 2nd ready executor instead of the 4th.

For the second case, drop `minExecutors`, let the application scale down below its executor instances, and PodsReady turns False.

**Anything else we need to know?**:

Split out of #18547 at review, which now only changes how ready executors are counted.
