## Description

**What happened**:

A Workload whose Pods break a `type: Pod` LimitRange `max` through their limits (not their requests) passes Kueue's LimitRange check, reserves quota and gets admitted. The job controller then cannot create any Pod, because the LimitRanger admission plugin rejects it:

```
pods "sample-job-xxxxx" is forbidden: maximum cpu usage per Pod is 2, but limit is 3
```

The Workload keeps holding its quota while no Pod runs (until `waitForPodsReady` evicts it, if enabled).

`limitrange.Summary.ValidatePodSpec` compares the pod `max` only with the summed pod requests:

```go
if podRange, found := s[corev1.LimitTypePod]; found {
	total := resources.NewRequestsFromPodSpec(ps)
	if resNames := total.GreaterKeysRL(podRange.Max); len(resNames) > 0 {
```

LimitRanger's `maxConstraint` checks the pod limits as well as the pod requests against `max` ([admission.go](https://github.com/kubernetes/kubernetes/blob/master/plugin/pkg/admission/limitranger/admission.go)). The container branch in Kueue already uses the max of requests and limits, so only the pod branch is affected.

**What you expected to happen**:

The Workload is marked inadmissible with the LimitRange message, same as when the requests are above `max`, and it does not take quota.

**How to reproduce it (as minimally and precisely as possible)**:

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: pod-max
spec:
  limits:
  - type: Pod
    max:
      cpu: "2"
```

Then submit a Kueue Job in that namespace with two containers, each `requests.cpu: 500m` and `limits.cpu: 1500m` (pod requests 1, pod limits 3). The Workload is admitted and every Pod creation fails as above.

At the unit level, `ValidatePodSpec` returns no error for this pod spec and a pod `max` of `cpu: 2`.

**Anything else we need to know?**:

Overhead is left out of the limits sum, matching LimitRanger. I have a fix with tests ready and will open a PR.

**Environment**:
- Kueue version: main (70fe032)
