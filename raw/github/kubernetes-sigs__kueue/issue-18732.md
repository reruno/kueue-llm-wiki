## Description

**What happened?**

`Scheduler.requeueAndUpdate` logs an error-level line `Could not update Workload status` with `workloads.kueue.x-k8s.io "<name>" not found` when a pending Workload is deleted while a scheduling cycle holds it. The deletion is an ordinary lifecycle event (the owning Pod was deleted before it was admitted), so the line is noise at error level, and it is inconsistent with the admission path in the same file, which treats the same NotFound as "workload was deleted" and logs it at info.

**Where**

v0.19.12, `pkg/scheduler/scheduler.go` `requeueAndUpdate` (line 1347):

```go
if err := workloadpatching.PatchAdmissionStatus(ctx, s.client, wl, s.clock, func(wl *kueue.Workload) (bool, error) {
	...
}, workloadpatching.WithLooseOnApply(), workloadpatching.WithRetryOnConflict()); err != nil {
	log.Error(err, "Could not update Workload status")
}
```

The same code is present at `v0.19.13`, `v0.20.6` and `main`. In the admission path of the same file, NotFound is handled explicitly (`apierrors.IsNotFound(err)` -> `"Workload not admitted because it was deleted"`, v0.19.12 lines 1158-1173; `main` lines 1148-1165).

**Mechanism**

1. `Manager.Heads` pops the pending Workload from the ClusterQueue (`pkg/cache/queue/manager.go`).
2. The cycle runs nominate/process; the Workload does not fit, so `requeueAndUpdate` is called for it.
3. In the meantime the Workload is deleted (the Pod it was created for was deleted while still scheduling-gated). `WorkloadReconciler.handleDelete` removes it from the queues, but only after the delete event reaches the informer.
4. `RequeueWorkload` reads the informer cache and returns `false` on NotFound, which is handled. The following `PatchAdmissionStatus` writes to the API server (`Status().Patch` with `client.Apply`, or the cached `Get` inside `RetryOnConflict`) and gets NotFound, which is logged with `log.Error`.

**Impact observed**

No stuck quota, no leaked admission, no requeue loop: ClusterQueue usage equals the requests of the live admitted Pods and pending counts drain to 0; each deleted Workload logs the line once (45 lines for 44 Workloads over 7 days, one name repeated once 28 ms apart). It is only an error-level log for an expected condition.

**What did you expect to happen?**

`requeueAndUpdate` treats NotFound from the status update like the admission path does: no error log (a V(3) info line such as "Workload not found while updating status; it was deleted"), and no `Eventf` against a Workload that no longer exists.

**How can we reproduce it (as minimally and precisely as possible)?**

- Plain-Pod integration, a StrictFIFO ClusterQueue whose quota is exhausted, a few hundred scheduling-gated Pods queued behind it.
- Delete queued Pods (for example `kubectl delete pod` of many pending Pods at once, or a workflow engine that deletes the Pods of a terminated run).
- Count `Could not update Workload status ... not found` lines from the leader. It is timing dependent: it occurs when a Workload is deleted while it is the head being processed.

**Anything else we need to know?**

Related but different: #10874 (NotFound in the preemption path, open) and #10495 (follower stale cache, closed). Neither touches `requeueAndUpdate`.

**Environment**

- Kueue version: v0.19.12 (also checked v0.19.13, v0.20.6, main by source)
- Pod integration only, `manageJobsWithoutQueueName: false`, 2 replicas with leader election
