## Description



/kind bug
/area concurrent-admission

**What happened**:

When a queued Job is updated, jobframework updates the Parent Workload's spec in place ([`updateWorkloadToMatchJob`](https://github.com/kubernetes-sigs/kueue/blob/2082b97e4c0c1a77ee0333cac04a492681c22970/pkg/controller/jobframework/reconciler.go#L1947-L1965)), keeping its UID. The Variants are not updated: [`generateVariant`](https://github.com/kubernetes-sigs/kueue/blob/2082b97e4c0c1a77ee0333cac04a492681c22970/pkg/controller/concurrentadmission/controller.go#L411-L426) copies `parent.Spec` only when a Variant is created, and [`deleteStaleVariants`](https://github.com/kubernetes-sigs/kueue/blob/2082b97e4c0c1a77ee0333cac04a492681c22970/pkg/controller/concurrentadmission/controller.go#L391-L409) only checks flavors.

As a result, quota is reserved for the old spec:

- After raising `parallelism` from 1 to 3 on a queued Job, the Job runs 3 Pods while the ClusterQueue counts 1.
- Variants created at different times can have different specs, so a migration can change correct quota usage into wrong usage.
- If the PodSet list changes, the Parent can never be admitted: copying the Variant's admission fails with `podSetAssignments must have the same number of podSets as the spec`.

**What you expected to happen**:

An admitted Variant matches the Parent's current spec, so quota accounting matches the Job, as it does without ConcurrentAdmission.

**How to reproduce it (as minimally and precisely as possible)**:

With the `ConcurrentAdmission` gate enabled, create a ClusterQueue with `concurrentAdmissionPolicy` and two flavors with zero quota. Submit a Job with `parallelism: 1` and a 100m CPU request. While it is queued, set `parallelism: 3`: the Parent has `count: 3`, the Variants still have `count: 1`. Then give one flavor 1 CPU of quota. The Job starts 3 Pods (300m), and the ClusterQueue reports 100m used.

I agree that deriving the desired Variants from the Parent during reconciliation would address this more generally than syncing individual fields. I'd be happy to work on this and look into MultiKueue's synchronization approach as a reference, including how to handle existing quota reservations safely.
