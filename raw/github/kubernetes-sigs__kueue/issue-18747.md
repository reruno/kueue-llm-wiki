## Description


/kind bug
/area concurrent-admission

**What happened**:

With ConcurrentAdmission, the Parent is not queued ([`AddOrUpdateWorkload`](https://github.com/kubernetes-sigs/kueue/blob/2082b97e4c0c1a77ee0333cac04a492681c22970/pkg/cache/queue/manager.go#L710-L718)), and every Variant is queued. The pending counts count the queued Workloads, so one Job is counted once per flavor:

- ClusterQueue and LocalQueue `status.pendingWorkloads`
- `kueue_pending_workloads` and `kueue_local_queue_pending_workloads`
- the Visibility On-Demand pending list, which shows each Variant with its own position

For one Job in a ClusterQueue with three flavors, all of the above report 3. With a second Job, the ClusterQueue reports 6, and the second Job's Variants are at positions 3 to 5.

**What you expected to happen**:

Each Job is counted once. KEP-8691 says: "The existing metrics will be only used to track Parent Workloads, and skip Variants." The unadmitted Workload metrics already skip Variants ([`unadmitted_workloads.go`](https://github.com/kubernetes-sigs/kueue/blob/2082b97e4c0c1a77ee0333cac04a492681c22970/pkg/cache/queue/unadmitted_workloads.go#L273-L276)), but the pending counts do not.

**How to reproduce it (as minimally and precisely as possible)**:

With the `ConcurrentAdmission` gate enabled, create a ClusterQueue with `concurrentAdmissionPolicy` and three flavors with zero quota, and a LocalQueue for it. Submit one Job. The Parent and three Variants are created, and the ClusterQueue and LocalQueue report `pendingWorkloads: 3`. The same ClusterQueue without `concurrentAdmissionPolicy` reports 1.

Two questions for the follow-ups:

With `TryPreferredFlavors`, a Parent admitted on a less-preferred flavor can still have pending Variants for migration. In my three-flavor test, main reports 2 pending Workloads and #18748 reports 1. ### Comment by [@Narwhal-fish](https://github.com/Narwhal-fish) — 2026-11-15T13:40:41Z

@apullo777 
Thanks for testing this.

On the first question: I lean toward not counting an admitted Parent as pending. KEP-8691 states that the existing metrics "track Parent Workloads, and skip Variants." #18748 counts the Parent once only because the Parent itself is not queued; once it is admitted, there is nothing left to stand in for. Otherwise, the same Job would be reported as both admitted and pending.

While migration Variants still represent real demand for the preferred flavor—which could matter for autoscaling based on these metrics—the KEP defers Variant-specific metrics to Beta based on user feedback. That demand fits better there rather than in the existing pending counts. The Visibility On-Demand list should follow the same rule for consistency.

On the second question: I think this should also be counted per Parent. Since Variants copy the Parent's spec, counting them once accurately reflects the Parent's resource requests. Consistent with the first point, an admitted Parent's requests should not be counted as pending either.
