## Description

**What happened**:

With the `CustomMetricLabels` feature gate on, a custom label change on a ClusterQueue that is being deleted leaves the gauge series with the old label value in place. Kueue then writes new series under the new value, so the ClusterQueue has two series for each gauge that Kueue writes again, until it is gone.

The ClusterQueue reconciler stores the new label value. The ClusterQueue update event handler returns early for a ClusterQueue with a deletion timestamp, so it skips the step that clears and re-records the gauges after a label change on an active ClusterQueue. While the ClusterQueue drains, Kueue keeps writing gauges with the new value:

- `kueue_reserving_active_workloads` gets a second series. The old series keeps its last count.
- `kueue_admitted_active_workloads` is changed by +1 and -1, not set. A Workload admitted before the label change was added to the old series, and its removal subtracts 1 from the new series. The new series goes negative and the old series never decreases.
- With fair sharing and `enableClusterQueueResources` on, `kueue_cluster_queue_weighted_share` gets a second series.
- `kueue_pending_workloads` and `kueue_finished_workloads` can get a second series when a Workload of the ClusterQueue is deleted or finishes. The old series keeps its last count.

Kueue does not write the other ClusterQueue gauges again after the label change. `kueue_cluster_queue_status`, `kueue_cluster_queue_info`, `kueue_cluster_queue_nominal_quota`, `kueue_cluster_queue_borrowing_limit`, `kueue_cluster_queue_lending_limit`, `kueue_cluster_queue_resource_reservation`, and `kueue_cluster_queue_resource_usage` keep only the series with the old label value.

This is on main today. #18631 (open) makes Kueue record resource metrics for terminating ClusterQueues. With #18631, `kueue_cluster_queue_nominal_quota`, `kueue_cluster_queue_borrowing_limit`, `kueue_cluster_queue_lending_limit`, `kueue_cluster_queue_resource_reservation`, and `kueue_cluster_queue_resource_usage` also get a second series. A query that sums by `cluster_queue` then counts quota, reservations, and usage twice.

When the last Workload leaves, Kueue removes the finalizer, and the ClusterQueue delete event removes every series of that ClusterQueue, old and new.

**What you expected to happen**:

After a custom label change on a terminating ClusterQueue, each gauge has one series for that ClusterQueue. The series carries the new label value and the current count, and no series goes negative.

**How to reproduce it (as minimally and precisely as possible)**:

An envtest integration spec reproduces it on main. It follows steps 2-7 and fails with `kueue_admitted_active_workloads` at -1 under the new value. I did not run these steps on a real cluster.

1. Start Kueue with this configuration. `enableClusterQueueResources` matters only for the resource gauges and `kueue_cluster_queue_weighted_share`.

   ```yaml
   apiVersion: config.kueue.x-k8s.io/v1beta2
   kind: Configuration
   featureGates:
     CustomMetricLabels: true
   metrics:
     enableClusterQueueResources: true
     customLabels:
       - name: team
   ```

2. Create a ResourceFlavor, a ClusterQueue `cq-a` with the label `team=a` and enough `cpu` quota for two Jobs, and a LocalQueue that points to `cq-a`.
3. Submit two long-running Jobs, for example `sleep 3600`, to the LocalQueue. Wait until both Workloads are admitted. Two Workloads keep the ClusterQueue terminating after the first one finishes.
4. Scrape `/metrics`. Expect `kueue_reserving_active_workloads{cluster_queue="cq-a",custom_team="a"} 2` and `kueue_admitted_active_workloads{cluster_queue="cq-a",custom_team="a"} 2`.
5. Delete the ClusterQueue with `kubectl delete clusterqueue cq-a --wait=false`. The finalizer keeps it while the Workloads run, and its `Active` condition has the reason `Terminating`.
6. Change the label with `kubectl label clusterqueue cq-a team=b --overwrite`.
7. Delete one of the two Jobs.
8. Scrape `/metrics` again. The spec observed only the `custom_team="b"` admitted count of -1, because it stops at the first failed assertion. The other values are inferred from the code. The output has these series:

   ```text
   kueue_reserving_active_workloads{cluster_queue="cq-a",custom_team="a"} 2
   kueue_reserving_active_workloads{cluster_queue="cq-a",custom_team="b"} 1
   kueue_admitted_active_workloads{cluster_queue="cq-a",custom_team="a"} 2
   kueue_admitted_active_workloads{cluster_queue="cq-a",custom_team="b"} -1
   ```

   The label sets are shortened. The real series also carry `replica_role`.

   With #18631, `kueue_cluster_queue_resource_reservation` and the other resource gauges also have a series for `custom_team="a"` and one for `custom_team="b"`.

**Anything else we need to know?**:

CodeRabbit found this in the review of #18631, in [this thread](https://github.com/kubernetes-sigs/kueue/pull/18631#discussion_r4541247862). I kept it out of #18631 because main already has the behavior for the Workload count gauges.

The code is in `pkg/controller/core/clusterqueue_controller.go`, in the early return for a deleting ClusterQueue in the update event handler.

This is done when a custom label change on a terminating ClusterQueue leaves only the series with the new values in the ClusterQueue gauges, covered by a test. Label changes on active ClusterQueues are out of scope for the ClusterQueue gauges, since the update event handler already resyncs them.

The Cohort gauge `kueue_cohort_subtree_admitted_active_workloads` keeps the old series after a relabel on an active ClusterQueue too. That is #18234, and it is out of scope here. Its fix in #18486 detects the relabel in the scheduler cache update, which the update event handler skips for a terminating ClusterQueue.
