## Description

**What happened**:

`RecordCohortMetrics` can write older Cohort values after newer ones, so a Cohort gauge such as `kueue_cohort_subtree_resource_reservations` or `kueue_cohort_subtree_quota` keeps a stale value.

`RecordCohortMetrics` takes the scheduler cache read lock to collect the values for the Cohort and its ancestors, releases the lock, and then writes the gauges. A cache write can land between those two steps. Consider two calls for the same Cohort. Call A collects its values and releases the lock. The scheduler then admits a Workload, which changes the reservations. Call B collects the new values and writes them. Call A writes last, so the gauge shows the values from before the admission.

The gauge stays wrong until the next call for that Cohort or for a Cohort below it. On a quiet Cohort, that call can be a long time away.

Several callers run at the same time. The ClusterQueue reconciler calls `RecordCohortMetrics` for the parent Cohort. The controller configuration that ships with Kueue sets 5 ClusterQueue workers, so two ClusterQueues in one Cohort can be reconciled in parallel. The Cohort reconciler and the ClusterQueue update and delete event handlers also call it. `ClearCohortMetrics` publishes the same way and has the same gap.

This is on main for every caller of `RecordCohortMetrics`. #18631 only moves one call so that it also runs for terminating ClusterQueues.

**What you expected to happen**:

Calls that overlap do not write older Cohort values over newer ones.

**How to reproduce it (as minimally and precisely as possible)**:

I did not run these steps on a real cluster. The window between collection and publication is short, so this does not reproduce on demand. A local unit stress test shows it, though. With 5 goroutines calling `RecordCohortMetrics` while the cache is updated, the gauge sometimes ended with an outdated value.

1. Use the controller configuration that ships with Kueue, which sets 5 ClusterQueue reconciler workers.
2. Create a Cohort `co` and two ClusterQueues, `cq-1` and `cq-2`, in it, with a LocalQueue for each.
3. Submit many short Jobs to both LocalQueues at the same time, so that the scheduler admits Workloads while both ClusterQueues are being reconciled.
4. When the queues are idle, compare `kueue_cohort_subtree_resource_reservations{cohort="co"}` with the sum of `status.flavorsReservation` of `cq-1` and `cq-2`. Per the code, they can differ until the next reconcile in `co`.

**Anything else we need to know?**:

CodeRabbit found this in the review of #18631, in [this thread](https://github.com/kubernetes-sigs/kueue/pull/18631#discussion_r4541247872). I kept it out of #18631 because the race is already on main.

I'll send a small PR that holds the cache read lock from collection through the gauge writes in both `RecordCohortMetrics` and `ClearCohortMetrics`. A cache write needs the write lock, so it cannot land between the two steps. Calls that overlap then read the same state and write the same values. #14180 (open) carries the same change and will rebase onto that PR, which keeps the fix small enough to cherry-pick.

The code is in `pkg/cache/scheduler/cohort_metrics.go`.

This is done when Cohort gauges are written under the same cache lock as the collection of their values. `-race` does not flag the bug, because each gauge write is thread-safe on its own.

A Cohort delete has a separate gap that this fix does not close. `removeCohortInMemory` in `pkg/controller/core/cohort_controller.go` clears the Cohort metrics and deletes the Cohort from the cache in two lock sections. A `RecordCohortMetrics` call for another Cohort in the same tree between the two can leave the root gauge counting the deleted Cohort. That is #18769.
