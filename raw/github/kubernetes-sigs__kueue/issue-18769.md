## Description

**What happened**:

Deleting a Cohort can leave the `kueue_cohort_subtree_quota` and `kueue_cohort_subtree_resource_reservations` gauges of its ancestors counting the deleted Cohort.

`CohortReconciler.removeCohortInMemory` first calls `ClearCohortMetrics`, which writes the ancestor values without the deleted Cohort, and then calls `DeleteCohort`, which removes the Cohort from the scheduler cache. These are two separate lock sections. A `RecordCohortMetrics` call for another ClusterQueue or Cohort in the same tree can run between them. It still sees the deleted Cohort in the cache and writes the old values. `DeleteCohort` writes no quota or reservation gauges afterwards, so the old values stay.

The gauges stay wrong until the next metrics update that reaches the root. With fair sharing on, the ClusterQueues of the old tree are reconciled about 1s after the delete, which fixes them. With fair sharing off and a quiet tree, nothing tied to the delete updates them, so they can stay wrong until the next informer resync.

There is a second, deterministic case. When the deleted Cohort still has child Cohorts, it stays in the cache as an implicit Cohort. Its own subtree gauges are cleared although it still holds its children's quota. If it has no ClusterQueues of its own, they stay missing until the next activity below it.

**What you expected to happen**:

After a Cohort is deleted, the subtree gauges of its former ancestors match the scheduler cache, and an implicit Cohort that stays keeps its subtree gauges.

**How to reproduce it (as minimally and precisely as possible)**:

I did not run these steps on a real cluster. A local unit probe showed the race in a few of 2000 trials, on main and with the fix for #18760.

1. Disable fair sharing.
2. Create a root Cohort `root` with two child Cohorts, `co-a` and `co-b`, each with a ClusterQueue that has nominal quota.
3. Keep `co-b` busy, for example by submitting short Jobs to its LocalQueue, so its ClusterQueue is reconciled often.
4. Delete `co-a`.
5. When the queues are idle, compare `kueue_cohort_subtree_quota{cohort="root"}` with the quota of `co-b`'s subtree plus the quota of `root`. Per the code, it can still include `co-a`.

For the second case, delete a Cohort that has only child Cohorts and check its own `kueue_cohort_subtree_quota`.

**Anything else we need to know?**:

I found this while working on #18760. That fix holds the cache read lock while the gauges are written, which does not help here. The old values are a correct read of the cache at that moment, written before the delete.

The ClusterQueue delete path already handles the same case. #16762 added a `RecordCohortMetrics` call after `DeleteClusterQueue`. The smallest fix is the same for Cohorts: after `DeleteCohort`, record the metrics of the former parent, and of the deleted Cohort when it stays as an implicit Cohort. The post-delete write is only guaranteed to be the last one once #18760 is fixed, so this depends on it.

The code is in `pkg/controller/core/cohort_controller.go` and `pkg/cache/scheduler/cohort_metrics.go`.

#14180 (open) adds a `kueue_cohort_lendable_resources` gauge on the same write path, so it would be affected the same way.
