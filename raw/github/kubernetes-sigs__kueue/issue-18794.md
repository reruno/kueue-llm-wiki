## Description

/kind bug

**What happened**:

With `ConcurrentAdmission` enabled, a Variant can reserve quota for an old Parent spec, wait for an AdmissionCheck, and later admit the updated Parent using that old reservation.

I reproduced this on PR #18782 head `d4962af1a7b772dc4c50f3f9e6d64d2daddb8a2e`, which includes synchronization for unreserved Variants. The already-reserved case remains:

1. Create a Parent with one Pod requesting 100m CPU.
2. Its Variant reserves 100m, but remains unadmitted because an AdmissionCheck is Pending. The Parent is still unreserved and unadmitted.
3. Update the Parent's PodSet count from 1 to 3 through the real API server. This succeeds, so the Parent now requests 300m CPU.
4. Mark the Variant's AdmissionCheck Ready.
5. The Variant is admitted and its old admission is copied to the Parent.

Observed final state (asserted together in the envtest integration reproduction):

| Object / field | Observed value |
|---|---|
| Parent `spec.podSets[0].count` | 3 (300m requested) |
| Parent `Admitted` condition | True |
| Parent `status.admission.podSetAssignments[0].count` | 1 |
| Parent admission CPU resourceUsage | 100m |
| Variant PodSet count | 1 |
| ClusterQueue admitted CPU usage on the selected flavor | 100m |

The Parent is therefore marked admitted with a reservation that does not match its current resource requirements. This is a Workload admission/accounting reproduction; I have not verified actual Job/Pod execution or cluster-level oversubscription.

**What you expected to happen**:

An admitted Parent should have an admission valid for its current PodSets and resource requirements. A reservation for the old spec should not be promoted as if it satisfied the updated Parent.

The stale Variant reservation needs a defined lifecycle (for example, safely invalidating/releasing the stale reservation and retrying the current request). Merely refusing to copy the admission without a release/retry path could leave quota held indefinitely. This report does not prescribe a particular eviction/recreation implementation.

**How to reproduce it (as minimally and precisely as possible)**:

The script below adds one temporary Ginkgo spec to the existing ConcurrentAdmission envtest suite, runs only that spec, and restores the original test file on exit. It uses a real local etcd/API server, Webhooks, the ConcurrentAdmission and core controllers, and Kueue's scheduler. It changes no product code and does not require a GPU or a running Kubernetes cluster.

The existing suite supplies two flavors: `reservation` with zero CPU quota, and `provreq-flavor` with 5 CPU quota and a manual AdmissionCheck. The script waits for the latter Variant's real quota reservation before changing the Parent, so no timing race is required. No autoscaler/ProvisioningRequest controller is needed; the test marks the generic AdmissionCheck Ready through the status API.

Prerequisites: a Kueue checkout with Go as declared in `go.mod`, Python 3, compiled CRD manifests, and envtest assets. Tested against the exact PR head above. For example:

```bash

# Save the script below as reproduce-stale-reservation.sh, then:
```

**Anything else we need to know?**:

Follow-up to #18745 and the explicitly deferred reserved-Variant case discussed in #18782:
https://github.com/kubernetes-sigs/kueue/pull/18782#discussion_r4573332568

On the tested head, `syncVariantSpecs` skips Variants with quota reservations, while `syncAdmissionStatus` can propagate their old admission onto an unadmitted Parent without establishing that it matches the current Parent spec. This reproduction confirms the cross-controller result through a real API server, rather than inferring it only from the code.

I'd like to work on this follow-up and discuss the expected reservation invalidation/requeue lifecycle.
