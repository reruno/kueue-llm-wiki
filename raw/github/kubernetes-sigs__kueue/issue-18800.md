## Description

/kind bug

**What happened**:

Kueue validates a Workload's PodSets against the namespace LimitRanges before it reserves quota (`workload.ValidateLimitRange` -> `limitrange.Summary.ValidatePodSpec`). `limitrange.Summarize` merges `maxLimitRequestRatio` into the summary, but `ValidatePodSpec` and `validatePodSpecContainers` only check `max` and `min`. The ratio is never read.

So a Workload whose containers (type `Container`) or whose Pod (type `Pod`) have a limit to request ratio above `maxLimitRequestRatio` passes Kueue's check, reserves quota, and is admitted. The LimitRanger admission plugin then forbids every Pod the job creates, with an error like:

```
cpu max limit to request ratio per Container is 2, but provided ratio is 4.000000
```

This is the same "admitted, then every Pod forbidden" failure as #18722 (fixed in #18723), but for the ratio instead of the pod `max`.

Kueue already treats the ratio as an admission constraint elsewhere. `limitRangeSchedulingFieldsChanged` in `pkg/controller/core/workload_controller.go` requeues LimitRange-rejected Workloads when `MaxLimitRequestRatio` changes (see #14967). Its doc comment lists the fields "used to compute effective resources or validate admission". Since nothing ever rejects on the ratio, that path has nothing to react to.

**What you expected to happen**:

The Workload should be marked inadmissible with the usual `resources didn't satisfy LimitRange constraints: ...` message, the same as for `max`/`min` violations, and it should not reserve quota.

The docs say the adjusted values "will be validated against the ranges" (`site/content/en/docs/concepts/workload.md`). LimitRanger (`plugin/pkg/admission/limitranger/admission.go`, `limitRequestRatioConstraint`) checks every `maxLimitRequestRatio` entry per container and init container for type `Container`, and against the summed pod requests and limits (overhead excluded) for type `Pod`.

**How to reproduce it (as minimally and precisely as possible)**:

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: ratio
spec:
  limits:
  - type: Container
    maxLimitRequestRatio:
      cpu: "2"
```

Then submit a job to a LocalQueue in that namespace with one container that has `requests.cpu: 1` and `limits.cpu: 4`. Kueue admits the Workload, and the Pods are rejected at creation by LimitRanger.

Unit-level reproduction on `main`: this `TestValidatePodSpec` case in `pkg/util/limitrange/limitrange_test.go` gets `nil` instead of an error (`want` holds an error message constant that a fix would add):

```go
"container limit to request ratio over": {
	summary: Summarize(*testingutil.MakeLimitRange("", "").
		WithType(corev1.LimitTypeContainer).
		WithValue("MaxLimitRequestRatio", corev1.ResourceCPU, "2").
		Obj()),
	podSpec: &corev1.PodSpec{
		Containers: []corev1.Container{
			*testingutil.MakeContainer().
				WithResourceReq(corev1.ResourceCPU, "1").
				WithResourceLimit(corev1.ResourceCPU, "4").
				Obj(),
		},
	},
	want: field.ErrorList{field.Invalid(podSpecPath.Child("containers").Index(0), []corev1.ResourceName{corev1.ResourceCPU}, "...")},
},
```

The same holds for a type `Pod` item. With a `maxLimitRequestRatio` entry added to the LimitRange `DescribeTable` in `test/integration/singlecluster/scheduler/scheduler_test.go` (request 1 CPU, limit 3 CPU, ratio 2), the Workload gets quota and the spec times out waiting for the LimitRange message, for both the `Container` and the `Pod` type.

This was reproduced with the unit test and with envtest, not on a live cluster; the LimitRanger message above is taken from its source.

**Anything else we need to know?**:

Suggested fix: in `validatePodSpecContainers`, check `containerRange.MaxLimitRequestRatio` against each container's requests and limits. In `ValidatePodSpec`, check `podRange.MaxLimitRequestRatio` against the pod requests and the pod limits that the pod `max` check already computes, with overhead excluded from both, as LimitRanger does. Compare exactly (`limit > request * maxLimitRequestRatio` on the decimal quantities), as LimitRanger does on Kubernetes master (`exceedsAllowed`), and add a new message constant. LimitRanger in v1.37 and earlier uses milli values and a float ratio instead; that form can reject a ratio that is exactly equal to some fractional maximums (for example request `1`, limit `2007m`, maximum `2.007`), so I would not copy it.

One choice to confirm: LimitRanger also rejects a ratio when the request or the limit is missing or zero. I'd only enforce the ratio when both are set and non-zero, to stay consistent with how the existing `max`/`min` checks treat missing keys. Happy to match LimitRanger exactly instead if you prefer.

I will open a PR for this. A fix with unit and integration tests is ready locally.
