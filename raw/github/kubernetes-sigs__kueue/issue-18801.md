## Description


**What happened**:

With `flavorFungibility.preference: PreemptionOverBorrowing`, a Workload that has to borrow cpu and preempt for memory in the same flavor is never admitted. The lower-priority Workload it should preempt keeps running, and the pending one gets `Workload no longer fits after processing another workload` on every cycle. With `BorrowingOverPreemption`, the same setup preempts in the first cycle.

The flavor assigner works out a mode for each resource and keeps the worst one as the mode of the flavor. But "worst" is decided by `isPreferred`, which is the ranking used to compare flavors with each other:

https://github.com/kubernetes-sigs/kueue/blob/f48f3140e8578632fb7e58c93a24596bded4ba2b/pkg/scheduler/flavorassigner/flavorassigner.go#L919-L922

Under `PreemptionOverBorrowing` that ranking looks at borrowing first. In the example below:

| Resource | What it needs | Mode |
|---|---|---|
| cpu | borrow from `cq-b` | `{fit, borrowingLevel: 1}` |
| memory | preempt `low` | `{preempt, borrowingLevel: 0}` |

cpu counts as the worse of the two, so the flavor ends up as `{fit, 1}`, and the need to preempt is lost. Since the mode is `fit`, `findFlavorForPodSets` returns a nil status:

https://github.com/kubernetes-sigs/kueue/blob/f48f3140e8578632fb7e58c93a24596bded4ba2b/pkg/scheduler/flavorassigner/flavorassigner.go#L975-L977

and `RepresentativeMode()` returns `Fit` for a nil status:

https://github.com/kubernetes-sigs/kueue/blob/f48f3140e8578632fb7e58c93a24596bded4ba2b/pkg/scheduler/flavorassigner/assignment.go#L528-L531

So the scheduler never looks for victims, and the quota check then fails on memory. The memory `FlavorAssignment` itself still says `Preempt`; only the summary for the flavor is wrong.

**What you expected to happen**:

The flavor needs both things, so its mode should be `{preempt, 1}`: `low` is preempted and `high` is admitted while borrowing cpu, as with `BorrowingOverPreemption`.

**How to reproduce it (as minimally and precisely as possible)**:

One flavor. `cq-a` can borrow cpu from `cq-b`, but `cq-b` has no memory to lend:

```yaml
apiVersion: kueue.x-k8s.io/v1beta2
kind: ClusterQueue
metadata:
  name: cq-a
spec:
  cohortName: cohort
  preemption:
    withinClusterQueue: LowerPriority
  flavorFungibility:
    whenCanBorrow: TryNextFlavor
    whenCanPreempt: TryNextFlavor
    preference: PreemptionOverBorrowing
  resourceGroups:
  - coveredResources: ["cpu", "memory"]
    flavors:
    - name: default
      resources:
      - name: cpu
        nominalQuota: 4
      - name: memory
        nominalQuota: 4Gi
---
apiVersion: kueue.x-k8s.io/v1beta2
kind: ClusterQueue
metadata:
  name: cq-b
spec:
  cohortName: cohort
  resourceGroups:
  - coveredResources: ["cpu", "memory"]
    flavors:
    - name: default
      resources:
      - name: cpu
        nominalQuota: 4
      - name: memory
        nominalQuota: 0
```

1. Admit `low` (priority 0) in `cq-a`: cpu 1, memory 4Gi.
2. Submit `high` (priority 100) to `cq-a`: cpu 6, memory 2Gi. cpu fits only by borrowing from `cq-b`, memory only by preempting `low`.
3. `high` stays pending and `low` keeps running. Switch the preference to `BorrowingOverPreemption` and `low` is preempted right away.

I haven't run this on a real cluster. I reproduced it with two unit tests, which I'll include in the PR. Both fail on main at `f48f3140e`:

- a `TestAssignFlavors` case for this setup:
  ```
  e.assignFlavors(_).RepresentativeMode()=Fit, want Preempt
  ```
- a scheduler test that runs three scheduling cycles with each preference: `low` is evicted in the first cycle with `BorrowingOverPreemption` and never with `PreemptionOverBorrowing`.

**Anything else we need to know?**:

- The default `BorrowingOverPreemption` loses information through the same merge, just the other way round: cpu `{preempt, 0}` and memory `{fit, 1}` become `{preempt, 0}`, so the borrowing is forgotten. With `whenCanBorrow: TryNextFlavor` and `whenCanPreempt: MayStopSearch`, the search then stops at this flavor instead of trying the next one, even when the next one fits without borrowing or preemption.
- Proposed fix: combine the two parts of the mode separately, taking the worst preemption mode and the deepest borrowing level among the resources of the flavor:
  ```go
  representativeMode = granularMode{
      preemptionMode: min(representativeMode.preemptionMode, preemptionMode),
      borrowingLevel: max(representativeMode.borrowingLevel, borrowingLevel(borrow)),
  }
  ```
  With this, all existing `pkg/scheduler/...` tests pass, and so do the new ones.
- #9462 and #13607 also involved the `PreemptionOverBorrowing` ranking, but they were about comparing flavors. This one is about combining the resources inside one flavor.

I'd like to work on the fix.
