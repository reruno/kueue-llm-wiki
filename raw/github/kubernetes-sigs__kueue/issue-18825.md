## Description

<!-- Please only use this template for submitting enhancement requests -->

**What would you like to be added**:

Let Kueue prefer preempting TrainJobs that would lose the least GPU hours.

The Kueue's TrainJob controller reads `status.trainerStatus.lastUpdatedTime` and writes a label on the TrainJob to identify how many seconds will be wasted if TrainJob is preempted.
PreemptionConfig rules can then use this label with numericLabels to prefer victims that lose the least work.

Example of label (open to alternative names): `kueue.x-k8s.io/trainjob-unsaved-gpu-seconds: "<int>"` 

**Why is this needed**:

Victim selection uses priority and admission recency, so it ignores how much compute is lost on eviction. A TrainJob that reported status 30 seconds ago and one that reported 3 hours ago look identical. Kubeflow Trainer's trainerStatus already exposes lastUpdatedTime, progressPercentage and estimatedRemainingSeconds information.

Ref:
- https://trainer.kubeflow.org/en/latest/user-guides/trainjob-progress.html
- https://kueue.sigs.k8s.io/docs/concepts/preemption/configurable_preemption/

 ### Proposal (Phase 1)

  - Value: `(now − trainerStatus.lastUpdatedTime) × GPUs requested`, in seconds. The GPU count comes from the Workload's PodSets. As we discussed with @tenzen-y and @mimowo, in the Phase 1, we can say that `lastUpdatedTime` indicates time of the latest TrainJob checkpoint that was updated after each epoch ends.
A later phase, we would need an explicit `lastCheckpointTime` in the TrainJob API.
  - Writer: the TrainJob reconciler recomputes the value for admitted TrainJobs on a throttled interval and patches the label. It writes nothing when trainerStatus or lastUpdatedTime is absent.
  - Format: a non-negative int32 that is a decimal string. This fits the numericLabels constraint types and the label-value rules.
  - Gate: behind a feature gate: `TrainJobCheckpointAwarePreemption`

###  Gaps and open questions:

1. Label sync to the Workload. I found no re-sync path for admitted Workloads. A periodically updated label on the TrainJob would be stale on the Workload, which is what preemption reads. Should Kueue sync the configured keys on change? That would also help other integrations.
2. Filter, not rank. numericLabels filters candidates. Configurable preemption has no documented ordering control, so "least waste first" is only approximated by escalating tiers. Is an ordering extension acceptable?
3. Label ownership. A Kueue controller mutating user-owned TrainJob metadata. Users or GitOps tools could overwrite it. Which side owns this key, and should Kueue's webhook reject user-set values, as it does for other reserved keys?
4. GPU-count scaling. The value grows with job size, so one threshold means different things for 4-GPU and 64-GPU jobs. Is a normalized value preferable?

 ### Alternatives considered

- Set `kueue.x-k8s.io/priority-boost` on the Workload from the TrainJob controller. It is dynamic and already feeds effective priority, but it conflates priority with waste and has no clamp.
- An external controller writes the label. This works today but every user has to build it

### Comment by [@vic-comm](https://github.com/vic-comm) — 2026-11-17T12:19:36Z

Great to see @7xuanlu jumping in to help drive Phase 1

Writing the metric label directly to the `Workload` is a clean way to bypass GitOps drift on the user-owned `TrainJob` metadata. The primary tradeoff to keep in mind there is **scheduler informer churn**: if many admitted TrainJobs are running, periodically patching `Workload.Labels` will continuously fire Workload update events into the scheduler cache. A strict throttling interval (or recording it under status rather than metadata) will be essential.

Since @andreyvelich is waiting on confirmation from @mimowo and @tenzen-y regarding whether the preemption configuration approach works as intended, here are a few deeper architectural findings from `scheduler/preemption` and `jobframework` to keep in mind for the design doc:

### 1. Candidate Filtering vs. Candidate Ordering (`PreemptionConfig`)
In `pkg/scheduler/preemption/config/filters/numeric_label_filters.go`, `numericLabels` implements `WorkloadFilter`, which is strictly a boolean check (`Matches(...) bool`).

Once candidates pass through the filters, actual victim selection is governed by `CandidatesOrdering` (`pkg/scheduler/preemption/policy/ordering.go`), which sorts by:
1. Eviction status
2. ClusterQueue
3. LocalQueue Fair Sharing usage
4. Effective Priority
5. Quota Reservation Time (admission recency)
6. UID

Using stepped tiers (e.g., `maxValue: 600` followed by `maxValue: 7200`) gives rough bucketing, but **within any single tier, Kueue cannot order candidates by least compute wasted**. If two TrainJobs both match `maxValue: 600` (e.g., Job A wasted 30s and Job B wasted 580s), victim selection falls back to Priority and Admission Recency—Job B could be evicted before Job A.

To achieve true "least waste first", are we open to introducing an ordering/ranking clause for numeric labels in `PreemptionConfig`, or is tiered filtering acceptable for Phase 1?

### 2. Workload Reconciliation Path (`jobframework`)
If the label is written directly to the `Workload`, note that Kueue's existing `jobframework` reconciler (`UpdateWorkloadPriority`) currently only updates priority and eviction/suspension conditions. We will need an explicit path in the TrainJob reconciler to patch admitted Workload labels without conflicting with generic job reconciliation loops.

### 3. Looking Ahead: Phase 2 with Elastic TrainJobs (kubeflow/trainer#3654 & Kueue KEP-77)
Once the in-flight work on Elastic TrainJobs (PR #3654 / KEP-2903) lands, linking this preemption mechanism to elastic execution offers a huge opportunity:
- **Scale-Down Still Discards Compute**: In PyTorch Elastic (`torchrun`), any membership resize (including scale-down to `minNodes`) destroys the rendezvous and forces all surviving workers to restart and reload from the latest checkpoint. Downscaling an 8-node job to 4 nodes burns `(now - T_checkpoint) * 8 nodes` of compute.
- **Checkpoint Recency as a Scale-Down Gate**: `trainerStatus.lastUpdatedTime` shouldn't only drive full eviction—it is the exact gating variable to decide whether an elastic job should be **preemptively downscaled** vs fully evicted. Jobs immediately post-checkpoint are near-zero-cost victims for shedding nodes.
- **Transparent Checkpointing Synergy (kubeflow/trainer#2777)**: If Kueue signals an eviction or scale-down intention with a grace period, Trainer could trigger a transparent checkpoint before Kueue revokes quota, bringing wasted compute to zero.
