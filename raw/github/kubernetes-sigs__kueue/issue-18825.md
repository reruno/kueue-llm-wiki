## Description

<!-- Please only use this template for submitting enhancement requests -->

**What would you like to be added**:

Let Kueue prefer preempting TrainJobs that would lose the least GPU hours.

The Kueue's TrainJob controller reads `status.trainerStatus.lastUpdatedTime` and writes a label on the TrainJob to identify how many seconds will be wasted if TrainJob is preempted.
PreemptionConfig rules can then use this label with numericLabels to prefer victims that lose the least work.

Example of label (open to alternative names): `kueue.x-k8s.io/trainjob-unsaved-gpu-seconds: "<int>"` 

**Why is this needed**:

Victim selection uses priority and admission recency, so it ignores how much compute is lost on eviction. A TrainJob that reported status 30 seconds ago and one that reported 3 hours ago look identical. Kubeflow Trainer's trainerStatus already exposes lastUpdatedTime, progressPercentage and estimatedRemainingSeconds information.

Ref:
- https://trainer.kubeflow.org/en/latest/user-guides/trainjob-progress.html
- https://kueue.sigs.k8s.io/docs/concepts/preemption/configurable_preemption/

 ### Proposal (Phase 1)

  - Value: `(now − trainerStatus.lastUpdatedTime) × GPUs requested`, in seconds. The GPU count comes from the Workload's PodSets. As we discussed with @tenzen-y and @mimowo, in the Phase 1, we can say that `lastUpdatedTime` indicates time of the latest TrainJob checkpoint that was updated after each epoch ends.
A later phase, we would need an explicit `lastCheckpointTime` in the TrainJob API.
  - Writer: the TrainJob reconciler recomputes the value for admitted TrainJobs on a throttled interval and patches the label. It writes nothing when trainerStatus or lastUpdatedTime is absent.
  - Format: a non-negative int32 that is a decimal string. This fits the numericLabels constraint types and the label-value rules.
  - Gate: behind a feature gate: `TrainJobCheckpointAwarePreemption`

    - name: cheap-victims
      activationPolicy:
        trigger: Always
      candidateSelectors:
        - scope: WithinClusterQueue
          priority:
            mode: Base
            comparison: LessThan
          numericLabels:
            - key: kueue.x-k8s.io/trainjob-unsaved-gpu-seconds
              maxValue: 600
    - name: moderate-victims
      activationPolicy:
        trigger: InsufficientQuota
      candidateSelectors:
        - scope: WithinClusterQueue
          priority:
            mode: Base
            comparison: LessThan
          numericLabels:
            - key: kueue.x-k8s.io/trainjob-unsaved-gpu-seconds
              maxValue: 7200

apiVersion: kueue.x-k8s.io/v1beta2
kind: ClusterQueue
metadata:
  name: training-cq
  annotations:
    kueue.x-k8s.io/preemption-config-name: lowest-unsaved-gpu-first

  preemption:
    reclaimWithinCohort: Never
    withinClusterQueue: Never

kind: TrainJob
metadata:
  name: llama-finetune

    kueue.x-k8s.io/queue-name: training-lq

###  Gaps and open questions:

1. Label sync to the Workload. I found no re-sync path for admitted Workloads. A periodically updated label on the TrainJob would be stale on the Workload, which is what preemption reads. Should Kueue sync the configured keys on change? That would also help other integrations.
2. Filter, not rank. numericLabels filters candidates. Configurable preemption has no documented ordering control, so "least waste first" is only approximated by escalating tiers. Is an ordering extension acceptable?
3. Label ownership. A Kueue controller mutating user-owned TrainJob metadata. Users or GitOps tools could overwrite it. Which side owns this key, and should Kueue's webhook reject user-set values, as it does for other reserved keys?
4. GPU-count scaling. The value grows with job size, so one threshold means different things for 4-GPU and 64-GPU jobs. Is a normalized value preferable?

 ### Alternatives considered

- Set `kueue.x-k8s.io/priority-boost` on the Workload from the TrainJob controller. It is dynamic and already feeds effective priority, but it conflates priority with waste and has no clamp.
- An external controller writes the label. This works today but every user has to build it
