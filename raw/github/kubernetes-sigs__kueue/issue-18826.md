## Description

**What happened**:

With Fair Sharing, a ClusterQueue can't reclaim its own nominal quota from a cohort peer whose Workloads run on a flavor that was removed from the peer's quota. The incoming Workload gets no preemption candidates and stays pending until the other Workloads finish.

Removing a flavor from a ClusterQueue doesn't evict the Workloads already admitted on it (#17287), so their usage stays in the ClusterQueue's `Usage`. But the flavor no longer has a `SubtreeQuota` entry, and `dominantResourceShare` only looks at `SubtreeQuota` keys:

https://github.com/kubernetes-sigs/kueue/blob/7da1cd878fb80d78096f91ff949db8fbc6d1afa4/pkg/cache/scheduler/fair_sharing.go#L170-L176

So the ClusterQueue reports DRS 0 and "not borrowing", and `TargetClusterQueueOrdering` prunes it before the within-nominal reclaim is considered:

https://github.com/kubernetes-sigs/kueue/blob/7da1cd878fb80d78096f91ff949db8fbc6d1afa4/pkg/scheduler/preemption/fairsharing/ordering.go#L219

The rest of the code counts the same usage as borrowing, because a missing quota reads as 0. For example, `ClusterQueueSnapshot.BorrowingWith`, used by `findCandidates`, picks the Workload as a candidate in the same preemption attempt:

https://github.com/kubernetes-sigs/kueue/blob/7da1cd878fb80d78096f91ff949db8fbc6d1afa4/pkg/cache/scheduler/clusterqueue_snapshot.go#L182-L184

Classical preemption decides borrowing only with checks like this one, so it isn't affected.

**What you expected to happen**:

Usage on a flavor that has no quota in the ClusterQueue counts as borrowed, as it does elsewhere, so the peer can reclaim its nominal quota.

**How to reproduce it (as minimally and precisely as possible)**:

Fair Sharing enabled, one cohort, two flavors `x` and `y`:

1. ClusterQueue `a` has 10 cpu on flavor `y`. Admit `a1` (10 cpu) on `y`.
2. Move the quota: remove `y` from `a` (it keeps cpu on `x`), and give `b` 10 cpu on `y` with `reclaimWithinCohort: Any`. `a1` keeps running.
3. Submit 8 cpu to `b`. It needs preemption on `y`, but `a1` is never preempted, although `b` is within its nominal quota.

I reproduced this with a `TestFairPreemptions` case that sets up the state after step 2 directly (`a` has only `x`, `a1` holds 10 cpu on `y`). On main at `7da1cd878` it fails:

```
preemption_fair_test.go:1826: Issued preemptions (-want,+got):
    - 	{"/a1:InCohortReclamation": {}},
    + 	{},
```

**Anything else we need to know?**:

- Proposed fix: in `dominantResourceShare`, also count usage on flavor-resources that have no `SubtreeQuota` entry, with a quota of 0. With that, the test above passes, and so do all existing tests in `pkg/cache/scheduler`, `pkg/scheduler/preemption/...` and `pkg/scheduler`.
- Visible side effects of the fix: such a ClusterQueue's `weightedShare` in status and metrics becomes non-zero, and it no longer wins admission ordering as if it weren't borrowing.
- Workaround: set the flavor's `nominalQuota` to 0 instead of removing it, or evict the Workloads by hand.
- Related, not duplicates: #16529 and its PR #17194 cover a quota key that exists with nothing lendable; here the key is missing and the cohort has lendable quota. #17194 edits the same function, so whichever lands second needs a small rebase. #17612 (workload-scoped DRS) would need to keep counting this usage.

I'd like to work on the fix.
