## Description

**What happened**:

When a ClusterQueue moves out of a flat cohort (its `spec.cohortName` changes), the inadmissible Workloads left in that cohort aren't requeued, even though the quota the moved ClusterQueue was borrowing there is now free. They stay pending until some unrelated event happens in that cohort, such as another Workload finishing. In a quiet cohort that can take a long time.

`Manager.UpdateClusterQueue` moves the ClusterQueue to its new cohort first, and only then requeues inadmissible Workloads by the ClusterQueue's root, which is by then the new root:

https://github.com/kubernetes-sigs/kueue/blob/7da1cd878fb80d78096f91ff949db8fbc6d1afa4/pkg/cache/queue/manager.go#L429-L436
https://github.com/kubernetes-sigs/kueue/blob/7da1cd878fb80d78096f91ff949db8fbc6d1afa4/pkg/cache/queue/inadmissible_workloads.go#L198-L199

The cohort controller doesn't cover it either: for the old ClusterQueue it enqueues `ClusterQueueAncestors`, which leaves out the root, and the Fair Sharing tree notification only refreshes ClusterQueue status.

https://github.com/kubernetes-sigs/kueue/blob/7da1cd878fb80d78096f91ff949db8fbc6d1afa4/pkg/cache/scheduler/cache.go#L1147-L1150

This affects a ClusterQueue whose parent cohort is the root of its tree: a flat cohort, explicit or implicit. If the parent is a non-root Cohort object, that Cohort is reconciled, and `qManager.AddOrUpdateCohort` requeues the whole tree, so the hierarchical case already works.

**What you expected to happen**:

When a ClusterQueue leaves a cohort tree, the inadmissible Workloads in that tree are requeued, as they are when the ClusterQueue's quota changes.

**How to reproduce it (as minimally and precisely as possible)**:

1. Cohort `alpha`: `cq1` and `cq2`, each with 5 cpu nominal and the default `reclaimWithinCohort: Never`.
2. Admit an 8 cpu Workload in `cq2` (it borrows 3 from `cq1`).
3. Submit a 5 cpu Workload to `cq1`. It doesn't fit and becomes inadmissible.
4. Change `cq2`'s `cohortName` to `beta`. `cq1` now has 5 cpu free, but its Workload stays pending until something else happens in `alpha`.

I reproduced the missing requeue with a `TestQueueInadmissibleWorkloads` case that moves `cq2` from `alpha` to `beta` with `UpdateClusterQueue`. On main at `7da1cd878` it fails:

```
manager_test.go:1001: Expected 1 moved workloads, got 0
manager_test.go:1004: Unexpected inadmissible workloads (-want +got):
    - 	nil,
    + 	{"cq1": {"default/a"}},
```

**Anything else we need to know?**:

- Proposed fix: in `UpdateClusterQueue` and `AddOrUpdateCohort`, read the old root before the edge moves, and requeue it too when it differs from the new one. With that, the test above, an integration test along the steps above, and all of `pkg/cache/queue` pass.
- `AddOrUpdateCohort` has the same order (edge first, then the new root), so a Cohort whose `parentName` changes leaves its old tree without a requeue too. A unit test in the same table reproduces it, and the same fix covers it.
- Related: #17957 refreshed the old tree's status after a move, but not the requeue. #7139 / #13483 (periodic retry of inadmissible Workloads) would hide this, but isn't merged. Open #18522 edits the same lines in `UpdateClusterQueue` for StrictFIFO retries.

I'd like to work on the fix.
