## Description

**What happened**:

With Admission Fair Sharing and Fair Sharing preemption, the victim chosen inside an AFS ClusterQueue depends on map iteration order. Sometimes it's a Workload from the LocalQueue with the highest usage, as KEP-4136 describes, and sometimes one from a lightly used LocalQueue, so the same state can lead to different preemptions from one scheduling cycle to the next.

`fairPreemptionStrategy` sorts the candidates from all ClusterQueues of the cohort with `CandidatesOrdering`:

https://github.com/kubernetes-sigs/kueue/blob/31a8411e3c701b140baebf82ba3dbcdd1ee98cc6/pkg/scheduler/preemption/fair_strategy.go#L71

`CandidatesOrdering` compares LocalQueue usage only for two Workloads of the same ClusterQueue, and falls through to priority otherwise:

https://github.com/kubernetes-sigs/kueue/blob/31a8411e3c701b140baebf82ba3dbcdd1ee98cc6/pkg/scheduler/preemption/policy/ordering.go#L57-L67
https://github.com/kubernetes-sigs/kueue/blob/31a8411e3c701b140baebf82ba3dbcdd1ee98cc6/pkg/scheduler/preemption/policy/ordering.go#L87-L93

So it isn't a strict weak ordering once candidates from several ClusterQueues are mixed. Take `a` and `b` in AFS ClusterQueue `q1` and `c` in `q2`:

| Workload | ClusterQueue | LocalQueue usage | Priority |
|---|---|---|---|
| `a` | `q1` | 10 (`lq1`) | 5 |
| `b` | `q1` | 1 (`lq2`) | 0 |
| `c` | `q2` | – | 3 |

`a` < `b` by usage, `b` < `c` by priority, and `c` < `a` by priority, which is a cycle. The input order comes from iterating `ClusterQueueSnapshot.Workloads` and the cohort's ClusterQueues in `findCandidates`, and the sort keeps `[a, b, c]` as is but also leaves `[b, c, a]` unchanged. `MakeClusterQueueOrdering` then splits the result by ClusterQueue in that order and takes the first Workload of each as the victim:

https://github.com/kubernetes-sigs/kueue/blob/31a8411e3c701b140baebf82ba3dbcdd1ee98cc6/pkg/scheduler/preemption/fairsharing/ordering.go#L93-L95

so `q1`'s victim is `a` in one cycle and `b` in another. The chosen Workload is still allowed by priority; it's the LocalQueue usage order from KEP-4136 that isn't kept:

> Kueue orders workloads based on the LocalQueue resource usage when considering workloads within the same ClusterQueue. Workloads from different ClusterQueues are not compared against each other using the resource usage dimension.

**What you expected to happen**:

Within an AFS ClusterQueue, the victim is always the Workload from the LocalQueue with the highest usage (`a` above), whatever Workloads the other ClusterQueues hold.

**How to reproduce it (as minimally and precisely as possible)**:

Admission Fair Sharing configured, Fair Sharing preemption on, one cohort:
- `p`: 3 cpu nominal, `reclaimWithinCohort: Any`;
- `q1`: 0 cpu, `admissionScope.admissionMode: UsageBasedAdmissionFairSharing`, LocalQueues `lq1` (usage 10 cpu) and `lq2` (usage 1 cpu);
- `q2`: 0 cpu.

Admitted, each with 1 cpu: `a` (`lq1`, priority 5) and `b` (`lq2`, priority 0) in `q1`, `c` (priority 3) in `q2`. A 1 cpu Workload in `p` reclaims from `q1`, which borrows the most.

I reproduced it with a `TestFairPreemptions` case that repeats the preemption 300 times on one snapshot. On main at `31a8411e3`, it failed in each of 20 `go test` runs, for example:

```
Issued preemptions in run 37 (-want,+got):
    - 	{"default/a:InCohortReclamation": {}},
    + 	{"default/b:InCohortReclamation": {}},
```

**Anything else we need to know?**:

- Proposed fix: in `fairPreemptionStrategy`, sort by ClusterQueue first and then with `CandidatesOrdering`, which is a consistent ordering within one ClusterQueue. Only the order within each ClusterQueue is used afterwards (`MakeClusterQueueOrdering`, and the retry candidates of the second strategy), so cross-ClusterQueue decisions don't change. With that, the case above passes every time, and so do the existing preemption, scheduler and fair sharing tests.
- Classical preemption sorts mixed-ClusterQueue slices with the same comparator, where the global order matters, so grouping by ClusterQueue isn't a fix there:

  https://github.com/kubernetes-sigs/kueue/blob/31a8411e3c701b140baebf82ba3dbcdd1ee98cc6/pkg/scheduler/preemption/classical/candidate_generator.go#L124-L129

  I haven't checked whether it leads to a wrong choice there. Would you rather fix it at the comparator instead of the call site?
- Similar earlier fixes: #6764 (pseudo-random fair sharing preemption targets) and #14547 (AFS victim order for LocalQueues with the same name).

I'd like to work on the fix.
