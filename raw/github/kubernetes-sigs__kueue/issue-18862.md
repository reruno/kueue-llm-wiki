## Description

**What happened**:

The Pod webhook accepts a `kueue.x-k8s.io/pod-group-total-count` annotation value above the int32 maximum (2147483647), for example `2147483648` or `4294967297`.

`validatePodGroupMetadata` only checks that the value parses with `strconv.Atoi` and is at least 1. With the fast-admission annotation, `constructGroupPodSetsFast` then converts the value to the int32 PodSet count (`int32(groupTotalCount)`), so it wraps around: `4294967297` becomes `1` and `2147483648` becomes a negative count. The group Workload would then be built with the wrong count.

**What you expected to happen**:

The webhook should reject a `kueue.x-k8s.io/pod-group-total-count` value that does not fit in the int32 PodSet count, as it already rejects `0` and non-numeric values.

**How to reproduce it (as minimally and precisely as possible)**:

Unit level, in `pkg/controller/jobs/pod`: add these cases to the `TestValidateCreate` table in `pod_webhook_test.go` on current main:

```go
"pod with group total count above the int32 maximum": {
	featureGates: map[featuregate.Feature]bool{features.WorkloadIdentifierAnnotations: false},
	pod: testingpod.MakePod("test-pod", "test-ns").
		ManagedByKueueLabel().
		GroupNameLabel("test-group").
		GroupTotalCount("2147483648").
		Obj(),
	wantErr: field.ErrorList{
		&field.Error{
			Type:  field.ErrorTypeInvalid,
			Field: "metadata.annotations[kueue.x-k8s.io/pod-group-total-count]",
		},
	}.ToAggregate(),
},
```

and the same case with `GroupTotalCount("4294967297")`. Then run:

```
go test ./pkg/controller/jobs/pod/ -run 'TestValidateCreate/pod_with_group_total_count' -count=1 -v
```

Both cases fail because `ValidateCreate` returns no error:

```
--- FAIL: TestValidateCreate/pod_with_group_total_count_above_the_int32_maximum
    pod_webhook_test.go:1359: Unexpected error (-want,+got):

```

**Anything else we need to know?**:

This was reproduced only at the unit level (the webhook's `ValidateCreate` accepting the value). The wrap-around in `constructGroupPodSetsFast` follows from the `int32(...)` conversion in the code; it was not reproduced on a cluster or against a running webhook server.
