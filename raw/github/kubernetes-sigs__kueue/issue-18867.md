## Description

/kind bug
/area integrations
/area tas

**What happened**:

With TopologyAwareScheduling enabled, a Kueue-managed StatefulSet can resume from zero replicas with an outdated Workload topology request.

After the retained Workload enters `QuotaReserved=False` with reason `OnHold`, update the StatefulSet from zero to a positive replica count and change the Pod template's `kueue.x-k8s.io/podset-required-topology` annotation in the same API update. The StatefulSet update is accepted and the Workload leaves OnHold, while `spec.podSets[0].topologyRequest.required` retains its previous value.

For example, changing the requirement from `cloud.example/block` to `kubernetes.io/hostname` leaves the Workload requesting a shared block. Two Pods can consequently be admitted across two hosts even though the updated template requires one host.

**What you expected to happen**:

Before releasing OnHold, synchronize the retained Workload's topology request with the current StatefulSet Pod template so its next admission uses the accepted topology requirements. Removing a constraint or switching between required, preferred, and unconstrained requests should also be reflected.

**How to reproduce it (as minimally and precisely as possible)**:

Prerequisites are a Kueue-managed StatefulSet, a LocalQueue backed by a TAS ResourceFlavor, and a Topology containing `cloud.example/block` and `kubernetes.io/hostname`. To observe the admission impact, use two Ready nodes in the same block, each with one CPU available, and request one CPU per Pod.

1. Create a two-replica StatefulSet with `spec.template.metadata.annotations["kueue.x-k8s.io/podset-required-topology"]` set to `cloud.example/block`. Wait for its Workload to be admitted across the two nodes.
2. Scale the StatefulSet to zero. Wait for its Pods to exit and its retained Workload to enter OnHold with no admission.
3. In one update, restore two replicas and change the required topology to `kubernetes.io/hostname`.
4. Inspect the StatefulSet template and the retained Workload's `spec.podSets[0].topologyRequest.required`.

The StatefulSet template requests `kubernetes.io/hostname`, while the Workload retains `cloud.example/block`. The expected result is that admission waits until one hostname can fit both Pods.

For an existing StatefulSet named `tas-sts` in namespace `test`, use the following resume update.

```sh
kubectl -n test patch statefulset tas-sts --type=merge -p \
  '{"spec":{"replicas":2,"template":{"metadata":{"annotations":{"kueue.x-k8s.io/podset-required-topology":"kubernetes.io/hostname"}}}}}'
```

**Anything else we need to know?**:

The retained-Workload lifecycle was introduced in #12233. The related fix in #15279 updates `podSets[].count` before releasing OnHold, and #16039 validates TAS annotations during StatefulSet updates. The topology request is still only constructed during initial Workload creation. [#12233](https://github.com/kubernetes-sigs/kueue/pull/12233), [#15279](https://github.com/kubernetes-sigs/kueue/pull/15279), [#16039](https://github.com/kubernetes-sigs/kueue/pull/16039)

The local regression checks exercise the normal StatefulSet Reconcile entry point and real API updates with the controller and TAS scheduler. The integration environment uses synthetic Node capacity and validates admission and topology assignments. It does not run kubelets or validate physical Pod execution.
