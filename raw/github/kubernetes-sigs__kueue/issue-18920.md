## Description

**What happened**:

During rolling restarts of Kueue (3 replicas, leader election, TAS, `TASFailedNodeReplacementFailFast` at its default), a pod from the old ReplicaSet won the lease and, in its first scheduling cycle, evicted running Workloads for node failures that the previous leader had already handled. 

An example job (`L` was the Kueue controller leader, `F` a follower):

| Time (UTC) | Replica | Log |
|---|---|---|
| 11-09 03:36:08.95 | `L`, `F` | `Workload queued for second pass of scheduling` (node-1 failed) |
| 11-09 03:36:09.13 | `L` | replacement on node-2 admitted; `F` receives that update at 03:36:09.130 |
| 11-10 17:25:41.33 | `F` | `Successfully acquired lease` |
| 11-10 17:25:42.84 | `F`, cycle 1 | `Evicting workload after failed try to find a node replacement`, `unhealthyNodes: [node-1]` |

In other cases the node had recovered hours earlier. In the same cycle, the admission-write fence from #15761 rejected the stale copies whose replacement did fit; only the eviction got through.

**What you expected to happen**:

A new leader doesn't act on a second-pass copy that is older than the stored Workload.

**How to reproduce it (as minimally and precisely as possible)**:

- Unit test on main: queue a second pass for an admitted TAS Workload with `unhealthyNodes: [x1]` and let the queue re-read it. Store and cache a repaired version (moved to `x2`, or `x1` recovered) and call `QueueSecondPassIfNeeded(repaired, 0)` as the update handler does. With no free node for a replacement, one `schedule()` cycle evicts the repaired Workload, with both write modes.
- On a cluster: run 2+ replicas, admit a TAS Workload, make one of its nodes NotReady, and let the leader replace it (or the node recover). Then fill the remaining capacity and delete the leader pod. The new leader evicts the Workload in its first cycle.

**Anything else we need to know?**:

Code at v0.20.5, unchanged on main at 600cb2f:

- Every replica queues second passes (#14386). [`queueSecondPass`](https://github.com/kubernetes-sigs/kueue/blob/7e71578095b353cedbfa63607b60c9739af9d501/pkg/cache/queue/manager.go#L1158-L1192) keeps a re-read copy, and only the leader's scheduler takes it.
- On the repaired update, [`handleUpdate`](https://github.com/kubernetes-sigs/kueue/blob/7e71578095b353cedbfa63607b60c9739af9d501/pkg/controller/core/workload_controller.go#L1515-L1521) calls [`QueueSecondPassIfNeeded(ctx, wl, 0)`](https://github.com/kubernetes-sigs/kueue/blob/7e71578095b353cedbfa63607b60c9739af9d501/pkg/cache/queue/manager.go#L1131-L1155). It removes entries only when `iteration > 0` (#8431), a branch that never runs in production, so followers keep the old copy.
- After the takeover, [`evictWorkloadAfterFailedTASReplacement`](https://github.com/kubernetes-sigs/kueue/blob/7e71578095b353cedbfa63607b60c9739af9d501/pkg/scheduler/scheduler.go#L987-L1000) evicts with `WithLooseOnApply(), WithRetryOnConflict()`, so the write lands on the repaired Workload.
- #7933 made this eviction loose to stop #8258's conflict loop. Since #15571 the requeue re-reads the Workload, so a strict write no longer loops.

Proposed fix (I can send a PR):

1. Drop the ready second-pass copy when an update shows the Workload no longer needs the pass (finishes #8357).
2. Make the fail-fast eviction strict, like the admission write. On Conflict, skip it, record `OutdatedScheduleCycle`, and let the requeue re-read the Workload.

Workarounds: restart the followers or scale to one replica before a roll, or disable `TASFailedNodeReplacementFailFast`.
