## Description

**What happened**:

After the MultiKueue manager restarts (for example on a rollout or a leader change), new Workloads wait for several minutes before they are dispatched to a worker.

When the `multikueue_workload` controller starts, the AdmissionCheck informer delivers a Create event for every existing AdmissionCheck in its initial list. `admissionCheckHandler.Create` in `pkg/controller/admissionchecks/multikueue/workload.go` then lists every Workload that uses the MultiKueue AdmissionCheck and enqueues each of them with `q.AddAfter(...)`, at the default priority. It does not check `e.IsInInitialList`, unlike the controller-runtime handlers, which enqueue initial-list events at `handler.LowPriority`.

The controller processes one Workload at a time by default. New Workloads have the same default priority, so they are queued behind all of these Workloads.

On a production manager with about 250 unfinished Workloads, the `workqueue_depth{name="multikueue_workload", priority="0"}` metric after a restart was:

| time after restart | depth at priority 0 |
|---|---|
| +10s | 247 |
| +40s | 202 |
| +1m30s | 103 |
| +2m30s | 6 |
| +3m30s | 0 |

New Workloads submitted during these 3.5 minutes waited behind this backlog.

**What you expected to happen**:

Workloads that are only queued because of the initial list are queued at low priority, so new Workloads are dispatched first. A real AdmissionCheck creation or a change of its MultiKueueConfig still queues the Workloads at the default priority.

**How to reproduce it (as minimally and precisely as possible)**:

1. Run a MultiKueue manager with many unfinished Workloads that use the MultiKueue AdmissionCheck.
2. Restart the manager.
3. Watch `workqueue_depth{name="multikueue_workload"}` by `priority`: the unfinished Workloads appear at priority `0`, not `-100`.
4. Create a new Workload right after the restart: its first MultiKueue reconcile happens only after the backlog drains.

**Anything else we need to know?**:

A possible fix: in `admissionCheckHandler.Create`, when `e.IsInInitialList` is true and the queue is a `priorityqueue.PriorityQueue`, enqueue with `AddWithOpts(priorityqueue.AddOpts{After: eventsBatchPeriod, Priority: ptr.To(handler.LowPriority)}, ...)`.

Related: #18407 handles the same problem for the requeue after a worker reconnect.
