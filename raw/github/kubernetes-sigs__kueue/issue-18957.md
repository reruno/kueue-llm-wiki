## Description

/kind bug
/area testing

**What happened**:

`pull-kueue-test-unit-coverage-main` keeps waiting for the unit shards long after they finished.

In [this build](https://prow.k8s.io/view/gs/kubernetes-ci-logs/pr-logs/pull/kubernetes-sigs_kueue/18955/pull-kueue-test-unit-coverage-main/2122600014533365760) the log stops at:

```
07:59:25 Waiting for the unit shards on {"base":"d1bed6a93eb4742bd69e759101b0a479c9898b97","pulls":[{"number":18955,"sha":"9180650d38a092763368a74de042399f495718ce"}],"type":"presubmit"}
```

Both shards on the same refs succeeded at 08:05 and 08:08, but at 08:26 the job still had not picked them.

`hack/testing/merge-unit-coverage.sh` reads each shard's state from `prowjob.json` via `storage.googleapis.com`. Prow writes that file with `pending` when the job starts and overwrites it when the job ends. Public objects in the bucket are served with `cache-control: public, max-age=3600`, so once the script has read the `pending` version, it can keep getting that cached copy for up to an hour.

The build listing comes from the JSON API, which is not cached, so new builds show up; only the state is stale.

This makes the job take about an hour longer than it should. With `WAIT_SECONDS=5100` and the 1h30m job timeout, there is little margin left before the job fails.

**What you expected to happen**:

The job merges the coverage within one poll interval after the last shard finishes.

**How to reproduce it (as minimally and precisely as possible)**:

1. Trigger the unit shards and `pull-kueue-test-unit-coverage-main` together on a PR.
2. Wait until both shards succeed.
3. The coverage job keeps polling and logs nothing new until the cached `prowjob.json` expires.

```
curl -sI https://storage.googleapis.com/kubernetes-ci-logs/pr-logs/pull/kubernetes-sigs_kueue/18955/pull-kueue-test-unit-shard-0-main/2122600014353010688/prowjob.json | grep -i cache-control
cache-control: public, max-age=3600
```

**Anything else we need to know?**:

A possible fix is to read `prowjob.json` through the JSON API (`${GCS_API}/<url-encoded path>?alt=media`), which is not cached. `list_builds` already uses that API.

The `curl` calls in `scan` also have no `--max-time`, so a stalled connection can block the job until it times out.
