## Description

**What happened**:

With `SchedulerLibraryDeepIntegration=true`, Kueue does not consider a Workload with a quota reservation but no Pods as a preemption victim.

For example, a low-priority Workload can reserve all available CPU quota while waiting for an AdmissionCheck. If a higher-priority Workload then needs that quota, it remains pending even when its Pods can fit on existing nodes.

**What you expected to happen**:

If the higher-priority Workload can fit on the current nodes and the lower-priority Workload is eligible for preemption, Kueue should preempt the lower-priority Workload and release its quota reservation.

**How to reproduce it (as minimally and precisely as possible)**:

1. Enable `SchedulerLibraryIntegration=true` and `SchedulerLibraryDeepIntegration=true`.
2. Configure `withinClusterQueue: LowerPriority` and an AdmissionCheck.
3. Submit a low-priority Workload that reserves all available CPU quota but waits for the AdmissionCheck before creating Pods.
4. Submit a higher-priority Workload requiring the same CPU quota.
5. Ensure the higher-priority Workload's Pods can fit on the current nodes.

The higher-priority Workload remains pending because the podless low-priority Workload is skipped as a preemption candidate.

**Anything else we need to know?**:

This only affects the alpha `SchedulerLibraryDeepIntegration` feature gate, which is disabled by default.

The issue is that WAS currently represents preemption victims through Pods. A Workload waiting for an AdmissionCheck can hold quota without having Pods, so it cannot be selected even though preempting it would release quota.
