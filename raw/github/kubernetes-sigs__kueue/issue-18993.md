**What would you like to be cleaned**:

Remove `features.SetFeatureGateDuringTest(..., features.X, true)` calls from unit and integration tests where `X` is already enabled by default and the call does not change the result.

Many feature gates were promoted to Beta, so they are on by default. Their tests still turn them on explicitly. On `main` there are 277 such calls for 45 gates in `pkg/` and `test/integration`. The biggest ones:

| Gate | Calls | Beta since | Default in 0.20 | Default in 0.19 |
|---|---|---|---|---|
| `ElasticJobsViaWorkloadSlices` | 61 | 0.18 | true | true |
| `LocalQueueMetrics` | 36 | 0.17 | true | true |
| `TASNodeFeasibilityForAllLevels` | 22 | 0.20 | true | not present |
| `UnadmittedWorkloadsObservability` | 19 | 0.20 | true | false |
| `KueueDRAIntegration` | 17 | 0.18 | true | true |
| `KueueDRAIntegrationExtendedResource` | 13 | 0.19 | true | true |
| `SchedulingEquivalenceHashing` | 11 | 0.18 | true | true |
| `AdmissionFairSharing` | 11 | 0.15 | true | true |

By release:

- 200 calls are for gates that are on by default in both 0.19 and 0.20.
- 63 calls are for gates that are on by default in 0.20 only.
- 14 calls are for gates that are on by default on `main` only (Beta in 0.21).

The same applies to `features.X: true` entries in table-driven `featureGates` maps, when `X` is enabled by default (about 830 entries).

Keep a call when it changes the result, for example:

- the test turned the gate off earlier and turns it back on, such as a spec that stops the manager, disables the gate, and enables it again;
- the gate depends on another gate that the test disables.

#18804 did this for `TopologyAwareScheduling` in `pkg/` unit tests. This issue covers the remaining gates and `test/integration`.

Open question: how should we handle gates that are not on by default in every supported release?
Cherry-picks usually go to both 0.19 and 0.20. If a cleanup PR removes a call for a gate that is off in 0.19 (for example `UnadmittedWorkloadsObservability`), its cherry-pick to 0.19 breaks the test there.
A possible rule:

- gates on by default in 0.19 and 0.20: remove the call and cherry-pick to both;
- gates on by default since 0.20: remove the call in a separate PR and cherry-pick only to 0.20;
- gates on by default only on `main`: remove the call, no cherry-pick.

Is that acceptable, or should we skip the gates that are not on by default in every supported release?

**Why is this needed**:

A call that turns on an enabled gate is noise. Readers cannot tell which tests depend on the gate, and the call gets copied into new tests.

It also adds a cleanup. When a call comes after `StartManagerForSpec` (or after any `ginkgo.DeferCleanup` that stops the manager), the gate is reset before the manager stops. Removing the calls that are not needed removes those cases too.
