**What would you like to be added**:

A worker reconnect scenario for the MultiKueue performance benchmark in `test/performance/multikueue`. The current baseline measures dispatch and admission of a steady stream of Workloads. It does not cover what happens when the manager loses and re-establishes its connection to a worker that already runs many Workloads.

The scenario would:

1. Admit a large number of Workloads on one or more workers, for example 1,000 per worker, and keep them running.
2. Force a reconnect to a worker, for example by closing one of its remote watches, which marks the whole worker disconnected and re-establishes every watch.
3. While the reconnect resync and the replayed `ADDED` events are processed, create new Workloads at a fixed rate.
4. Optionally, restart the manager controllers with the same Workloads in place, to cover the initial-list burst.

And report:

- The dispatch latency of the new Workloads (creation → admitted on the manager): p50, p90, and max, before, during, and after the reconnect.
- The `multikueue_workload` queue depth by `priority` over time, and the time until the backlog drains.
- The number of reconciles caused by the reconnect.

The checker would fail when the dispatch latency of the new Workloads during the reconnect exceeds a calibrated threshold.

**Why is this needed**:

A worker reconnect is a routine event, not a failure. The API server closes each watch after a random timeout between `--min-request-timeout` and twice that value (30 to 60 minutes by default). MultiKueue reconnects the whole worker when any one of its watches ends. With about five watches per worker (Workload plus one per job framework), a production manager reconnects to each worker about every 35 minutes.

Each reconnect requeues every Workload of the worker, and the new watches replay an `ADDED` event for every remote object. On a production manager, new Workloads used to wait behind this burst:

| version | time to dispatch a new Workload after a reconnect |
|---|---|
| main before #18232 | ~10 m 30 s |
| + #18232 | ~3 m 35 s |
| + #18232 + #18277 | ~2 m 00 s |
| + #18232 + #18277 + #18407 | ~2 s |

These numbers come from manual measurements on a live cluster. No test protects them, so a change that, for example, enqueues a reconnect event at the default priority again would bring the delay back without any CI signal. #18938 is the same kind of regression after a manager restart.
