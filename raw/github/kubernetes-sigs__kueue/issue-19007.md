## Description

/kind feature

**What would you like to be added**:

A feature gate that adds a second attempt to fair sharing preemption. When the fair sharing search finds a target set that fits, but `FairSharingVerifyFinalTargets` rejects it after fill-back, Kueue tries again with only the preemptor's own ClusterQueue candidates that `withinClusterQueue` already allows: lowest priority first, then most recently admitted, with the usual fill-back.

- It runs only after that rejection. If the fair sharing search runs out of candidates without fitting, the own candidates were already all removed in that simulation, so the fallback is skipped.
- It takes no targets from other ClusterQueues. Its targets have reason `InClusterQueue`, which the final check already exempts.
- It accepts the plan only if the DominantResourceShare of the preemptor's ClusterQueue and of each of its ancestor Cohorts does not go up. While the queue is borrowing, that means the victims free at least what the incoming workload takes.
- Off by default (Alpha).

**Why is this needed**:

The final check from #16343 fixes the loop in #14543, and we want to keep it. But when it rejects a plan, the whole set is dropped and the workload is requeued with "no candidate workloads allowed for preemption". Nothing else is tried, so the next cycle builds and rejects the same plan. The analysis linked from #16343 measured this. The merged option "refuses all 186 own-only cases", where the only fair answer evicts only the preemptor's own workloads. Its nested-cohort section describes the mechanism we hit.

What we saw this:

- A project queue with weight 5 had high-priority single-node workloads that needed an empty node. Quota fit by borrowing.
- On each attempt the search removed workloads from other orgs and from sibling queues in the same org. The sibling ones lowered the org's share at the root. A workload in another org then passed `LessThanInitialShare` by a tiny margin, and removing it emptied a node. Fill-back put the earlier victims back, the final check saw the org's share at higher score, and rejected the set.
- In one 68-minute window, the head of that queue spent 47 minutes in 417 attempts that ended this way. One workload was rejected on 97 of its 104 attempts. Each rejected attempt cost about 280 ms of scheduler time.
- The same queue had about 150 lower-priority single-node workloads running. Evicting one of them would have admitted the head. The search never got there, because the preemptor's own queue had the lowest share among its siblings.
- A high-priority 1-GPU workload behind those heads waited 68 minutes, although it fit on its first evaluation.

The same reject-and-stop behaviour is on main (checked 2026-11-05). Classical preemption got a similar fix in #16060: a borrowing workload can now preempt lower-priority workloads in its own ClusterQueue.

On fairness: the fallback swaps lower-priority work for higher-priority work inside one ClusterQueue. With the guard, that queue's usage does not grow, so no other queue's share changes. If the victims free more than needed, the queue's share drops, and the evicted workloads compete again under the normal rules. The #14543 loop needs a cross-queue target that is justified by a temporarily lowered share, and the fallback takes none.

On cost: one extra attempt, only after a rejection, and it starts with a single fit check with all own candidates removed. Today the same rejected plan is rebuilt every cycle.
