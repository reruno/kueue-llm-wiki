**What happened**:

With AdmissionFairSharing configured and ClassicalPreemptionCandidateOrderCache disabled, classical preemption can select different victims across repeated reclaims.

This is the classical-preemption counterpart of #18837. The uncached newCandidateIterator sorts candidates from multiple ClusterQueues with CandidatesOrdering, which does not provide a consistent global order when LocalQueue usage and priority comparisons are mixed.

**What you expected to happen**:

The victim should not depend on candidate iteration order for the same state. Within an AFS ClusterQueue, the LocalQueue usage ordering described in KEP-4136 should be respected.

**How to reproduce it (as minimally and precisely as possible)**:

I reproduced this in the quotacheckstrategy envtest integration suite, with AdmissionFairSharing configured but without Fair Sharing. The setup uses one cohort:

- p: 4 CPU nominal, reclaimWithinCohort: Any.
- q1: 0 CPU nominal, UsageBasedAdmissionFairSharing, with a (lq1, 2 CPU, priority 5) and b (lq2, 1 CPU, priority 0).
- q2: 0 CPU nominal, with c (1 CPU, priority 3).

After AFS usage has accumulated, a 1 CPU Workload in p triggers reclamation. Each run finishes the victim's eviction, removes the incoming Workload, and waits for a, b, and c to be admitted again before the next run.

On main at fdb509307:

| Candidate order cache | Victims (60 runs) |
|-----------------------|-------------------|
| Disabled              | a 52, c 8         |
| Enabled               | c 60              |

A unit-level probe with identical snapshot state and fixed LocalQueue usage (lq1=10, lq2=1) also selected different victims, including b despite its LocalQueue having lower usage. This occurred on base 31a8411e3 (7/300) and release-0.20 at c6b6477f4 (7/300).

**Anything else we need to know?**:

ClassicalPreemptionCandidateOrderCache is disabled by default in release-0.19 and release-0.20, so the uncached classical path is the default in those releases.

Unlike #18838, which only needs ordering within each ClusterQueue, the uncached classical path relies on ordering candidates across ClusterQueues.
