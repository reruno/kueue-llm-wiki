**What happened**:

While Kueue manages a StatefulSet or a LeaderWorkerSet, the webhook rejects Pod template changes that affect admission by comparing `SpecShape` of the old and new Pod specs in [`ValidateImmutablePodGroupPodSpec`](https://github.com/kubernetes-sigs/kueue/blob/cc90711a5f5cc0960cd4c72b22b6b522b2697337/pkg/controller/jobframework/validation.go#L345). For the containers, [`ContainersShape`](https://github.com/kubernetes-sigs/kueue/blob/cc90711a5f5cc0960cd4c72b22b6b522b2697337/pkg/util/pod/pod.go#L185-L195) keeps only `resources.requests` and `ports`, so the webhook accepts these changes although they increase the requests of the new Pods:

- Adding, raising or removing a limit of a resource that the container does not request. The API server defaults the missing request of the Pod to the limit, and Kueue computes the quota the same way (`UseLimitsAsMissingRequestsInPod`). For example, adding `limits: memory: 1Gi` to a container without a memory request, or raising `limits: cpu` of an init container without a CPU request above the largest container request.
- Changing an init container to a sidecar container (`restartPolicy: Always`) with the same requests. The requests of a sidecar container add up with the containers instead of being covered by the maximum of the init containers.

The Workload keeps its admission and quota, so the new Pods request more than the Workload reserves. In v0.20, these Pods run outside the reserved quota. On main, `PodIntegrationVerifyRoleRequests` (Beta, enabled by default) should keep these Pods gated with a `PodExceedsRoleRequests` event instead, so the update is accepted but the new Pods do not start (not verified end-to-end).

**What you expected to happen**:

The webhook rejects Pod template changes that change the effective requests of the Pods, computed as for the quota of the Workload: limits are used as missing requests, and sidecar containers add up with the containers. Changes of limits that do not change the effective requests, such as a limit of a resource that the container requests, are still accepted.

**How to reproduce it (as minimally and precisely as possible)**:

1. Create a ClusterQueue and a LocalQueue `user-queue` in the namespace.
2. Create a StatefulSet managed by Kueue:

   ```yaml
   apiVersion: apps/v1
   kind: StatefulSet
   metadata:
     name: sts
     labels:
       kueue.x-k8s.io/queue-name: user-queue
   spec:
     replicas: 1
     selector:
       matchLabels:
         app: sts
     template:
       metadata:
         labels:
           app: sts
       spec:
         containers:
         - name: app
           image: registry.k8s.io/pause:3.10
           resources:
             requests:
               cpu: "1"
   ```

3. After the Workload is admitted, add a memory limit to the container:

   ```shell
   kubectl patch statefulset sts --type=json -p='[{"op":"add","path":"/spec/template/spec/containers/0/resources/limits","value":{"memory":"1Gi"}}]'
   ```

4. The webhook accepts the change. The Workload still reserves only `cpu: 1`, while the new Pod requests `memory: 1Gi` too.

The same happens for a LeaderWorkerSet.

**Anything else we need to know?**:

- The fix must not change `SpecShape` itself: it is also used for the role hash of the Pods ([`GenerateRoleHash`](https://github.com/kubernetes-sigs/kueue/blob/cc90711a5f5cc0960cd4c72b22b6b522b2697337/pkg/util/pod/pod.go#L150)) and the hash of the Workloads, so changing it would change the hashes of the existing Pods after an upgrade. The comparison in `ValidateImmutablePodGroupPodSpec` could apply `UseLimitsAsMissingRequestsInPod` to both Pod specs and take `restartPolicy` of the init containers into account.
- The fix rejects updates that earlier versions accepted, so it needs an `ACTION REQUIRED:` release note, and possibly a feature gate enabled by default to restore the previous validation.
- #17903 adds the `LWSAllowMutatingContainersWhenEffectiveRequestsDontChange` feature gate for LeaderWorkerSet. With that gate enabled, the LeaderWorkerSet webhook compares the effective requests, but keeps accepting every change that `ContainersShape` accepts, so that enabling the gate does not reject updates that were accepted before. The fix for this issue should cover that path too. See the discussion in https://github.com/kubernetes-sigs/kueue/pull/17903#discussion_r4611251076.
