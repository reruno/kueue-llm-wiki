## Description

**What happened**:

With partial scale-up for elastic jobs (`ElasticJobsViaWorkloadSlicesWithPartialReplicaScaleUp`), a partially admitted Workload slice gets a pending scale-up probe for its full count. If that slice is evicted while the probe is pending (deactivated or preempted), the job ends up suspended while the probe holds quota:

1. The evicted slice A suspends the job and releases its quota.
2. The probe P still says it replaces A (`kueue.x-k8s.io/workload-slice-replacement-for`), and it isn't evicted, so the scheduler admits it into the freed quota as A's replacement. A gets `Finished=True(WorkloadSliceReplaced)`.
3. P is admitted partially too, so Kueue creates a new probe P2 for it, which stays pending.
4. `normalizeActiveSlices` picks the pending replacement before the admitted slice ([pkg/workloadslicing/workloadslicing.go#L408-L415](https://github.com/kubernetes-sigs/kueue/blob/6efb16dc2/pkg/workloadslicing/workloadslicing.go#L408-L415)), so the job reconciler gets P2, not P.
5. The job is suspended, and `reconcileSuspendedJob` ([pkg/controller/jobframework/reconciler.go#L772](https://github.com/kubernetes-sigs/kueue/blob/6efb16dc2/pkg/controller/jobframework/reconciler.go#L772)) starts it only if that workload is admitted. P2 isn't, so it logs "Job is suspended and workload not yet admitted by a clusterQueue, nothing to do".

The job stays suspended while P holds its quota, until P2 fits in full, which may never happen. With deactivation, the job's quota is taken even though the user deactivated it, and reactivating A does nothing because A is already finished.

State after deactivating A (batch Job, quota 7 CPUs, 1 CPU per Pod, scaled from 5 to 10):

```text
A   replacementFor=initial  count=10  Evicted=True(Deactivated)  Finished=True(WorkloadSliceReplaced)
P   replacementFor=A        count=10  QuotaReserved=True  Admitted=True   (holds 7 CPUs)
P2  replacementFor=P        count=10  QuotaReserved=False(WaitingForQuota)
Job .spec.suspend=true
```

**What you expected to happen**:

Evicting or deactivating a slice doesn't leave quota held by another slice of the same job while the job is suspended. Either the pending probe is evicted (or deleted) along with the slice it was meant to grow, or the job starts again on the admitted slice.

**How to reproduce it (as minimally and precisely as possible)**:

Reproduced on upstream `main` at 6efb16dc2 with an integration test, by adding this spec to `test/integration/singlecluster/controller/jobs/job/job_controller_partial_scaleup_test.go`. It reuses that suite's setup: quota 7 CPUs and the `scaleJob` helper. The spec passes, which means the bug is present:

```go
ginkgo.It("REPRO deactivating a partially admitted slice with a pending probe", func() {
	testJob := testingjob.MakeJob("repro", ns.Name).
		SetAnnotation(workloadslicing.EnabledAnnotationKey, workloadslicing.EnabledAnnotationValue).
		SetAnnotation(constants.ElasticJobScaleUpStrategyAnnotationKey, constants.ElasticJobScaleUpStrategyPartial).
		Indexed(true).
		Queue(kueue.LocalQueueName(localQueue.Name)).
		Request(corev1.ResourceCPU, "1").
		Parallelism(5).
		Completions(5).
		Obj()
	behavioral.MustCreate(ctx, k8sClient, testJob)
	initialSlice := &behavioral.ExpectWorkloadsInNamespace(ctx, k8sClient, ns.Name, 1)[0]
	behavioral.ExpectPodSetAdmittedCount(ctx, k8sClient, initialSlice, kueue.DefaultPodSetName, 5)
	behavioral.ExpectJobUnsuspended(ctx, k8sClient, client.ObjectKeyFromObject(testJob))

	ginkgo.By("scale to 10: slice A admitted with 7, probe P pending")
	scaleJob(testJob, 10)
	sliceA := behavioral.ExpectNewWorkloadSlice(ctx, k8sClient, initialSlice)
	behavioral.ExpectPodSetAdmittedCount(ctx, k8sClient, sliceA, kueue.DefaultPodSetName, 7)
	probe := behavioral.ExpectNewWorkloadSlice(ctx, k8sClient, sliceA)
	behavioral.ExpectWorkloadsToBePending(ctx, k8sClient, probe)

	ginkgo.By("deactivate slice A")
	behavioral.DeactivateWorkload(ctx, k8sClient, client.ObjectKeyFromObject(sliceA))

	ginkgo.By("BUG: the probe is admitted into the freed quota")
	behavioral.ExpectPodSetAdmittedCount(ctx, k8sClient, probe, kueue.DefaultPodSetName, 7)
	behavioral.ExpectWorkloadToFinish(ctx, k8sClient, client.ObjectKeyFromObject(sliceA))

	ginkgo.By("BUG: the Job stays suspended while the probe holds 7 CPUs")
	gomega.Consistently(func(g gomega.Gomega) {
		g.Expect(k8sClient.Get(ctx, client.ObjectKeyFromObject(testJob), testJob)).Should(gomega.Succeed())
		g.Expect(testJob.Spec.Suspend).Should(gomega.Equal(new(true)))
		g.Expect(k8sClient.Get(ctx, client.ObjectKeyFromObject(probe), probe)).Should(gomega.Succeed())
		g.Expect(probe.Status.Admission).ShouldNot(gomega.BeNil())
	}, 5*behavioral.LongConsistentDuration, behavioral.Interval).Should(gomega.Succeed())
})
```

```sh
INTEGRATION_TARGET=./test/integration/singlecluster/controller/jobs/job/... GINKGO_ARGS="--focus=REPRO" make test-integration
```

Preemption gives the same end state. After step "scale to 10" above, create a Job with a higher WorkloadPriorityClass that requests 3 CPUs. It preempts A, and the probe stays pending, because the 4 free CPUs are below its `minCount` of 5. Delete the high-priority Job. The probe is then admitted, a new probe is created, and the elastic Job stays suspended.

**Anything else we need to know?**:

- This isn't specific to batch Job. It was first found with an elastic SparkApplication, using the partial scale-up from #18064, and the code path is shared by every integration that supports partial scale-up. With #18064, a SparkApplication's first admission can also be partial, so a first slice can hit this too.
- Possible directions:
  - When a slice is evicted, also evict or delete its pending scale-up probe, so a probe never outlives the slice it was meant to grow. This also respects deactivation.
  - Or, for a suspended job, have `normalizeActiveSlices` prefer the admitted slice over the pending probe, so the job starts on it.
