## Description

/kind bug

**What happened**:

When a ClusterQueue is not active (`stopPolicy: Hold`, or deleted and still held by its finalizer), the quota its admitted Workloads borrowed from the cohort cannot be reclaimed. A sibling ClusterQueue with `reclaimWithinCohort: Any` stays pending with `insufficient unused quota`, and the borrowing Workloads are not preempted.

`Cache.Snapshot` leaves inactive ClusterQueues out of the snapshot tree (`pkg/cache/scheduler/snapshot.go:333`, `:397`), but the Cohort's `ResourceNode` is cloned from the cache (`snapshot.go:324`) and still counts their usage. Preemption only looks for victims among ClusterQueues in the tree (`hierarchical_preemption.go:191`, `preemption.go:654`, `config/evaluator.go:309`), so these Workloads count against the cohort but can never be victims.

**What you expected to happen**:

The lender reclaims its nominal quota by preemption, as it does when the borrower's ClusterQueue is active. Hold and deletion stop new admissions; they should not keep borrowed quota away from the rest of the cohort.

**How to reproduce it (as minimally and precisely as possible)**:

kind (Kubernetes v1.37.0) with Kueue built from main at 563774b46, default configuration. Two workers each report `nvidia.com/gpu: 2` through a node status patch. One cohort:

- gpu-tenant-a: 2 GPU nominal, reclaimWithinCohort: Any.
- gpu-tenant-b: 2 GPU nominal, same spec. Its Job runs 2 Pods of 2 GPUs, so it borrows 2 from gpu-tenant-a.

Then change gpu-tenant-b as below, and submit a Job of 1 Pod with 2 GPUs to gpu-tenant-a, within its nominal quota. Each case was watched for 90 s:

| gpu-tenant-b | gpu-tenant-a Job | gpu-tenant-b Job |
|---|---|---|
| unchanged | admitted after 2 s | preempted |
| `stopPolicy: Hold` | pending: `insufficient unused quota for nvidia.com/gpu in flavor gpu, 2 more needed` | keeps running |
| deleted (`Terminating`) | pending, same message | keeps running |

An integration test in `test/integration/singlecluster/scheduler/preemption_test.go` reproduces both cases with plain Workloads: on main the borrowing Workload is never preempted (3/3 runs each).

**Anything else we need to know?**:

The `stopPolicy` comment says "Admitted workloads will run to completion" for Hold. I read that as "stopping does not evict them", not as protection from preemption: KEP-83 puts borrowed quota under the lender's control. The Terminating case looks like a bug either way.

A possible fix is to keep `NotActive` ClusterQueues in the snapshot tree while still listing them in `InactiveClusterQueueSets`, which the scheduler already checks before nominating (`scheduler.go:941`). ClusterQueues in a cohort cycle or with unsynced TAS usage would stay out as today. This also makes their Workloads candidates for fair-sharing and `ConfigurablePreemptions` rules. I have a branch with this change and the integration test and can open a PR if this direction looks right.
