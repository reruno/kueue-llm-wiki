## Description

**What happened**:

A MultiKueue worker Workload that is evicted after it reserved quota but before it is admitted (`QuotaReserved=True`, `Admitted=False`) stays at `Evicted=True`, `QuotaReserved=True` forever. The worker keeps counting its quota, never requeues it and never retries its admission checks. Triggers are a worker admission check going to `Retry` and a preemption on the worker.

The defect is general: it hits any Workload without an owning job. A Workload with an owning job is not affected, because its job reconciler completes the eviction. A MultiKueue worker Workload has no owning job until it is admitted, because in this scenario the manager creates the remote job only after the remote Workload reports `Admitted=True`.

Observed on v0.20.6 with one manager and two workers, each worker ClusterQueue having a ProvisioningRequest AdmissionCheck and a Topology-Aware Scheduling flavor:

1. The manager dispatches the job and a worker reserves quota.
2. The ProvisioningRequest reports `Provisioned=True`, so the check is `Ready`, but the provisioned node never becomes Ready. The delayed topology assignment stays pending and the Workload stays `Admitted=False`.
3. About 10 minutes later the autoscaler sets `BookingExpired=True`. Kueue sets the check to `Retry` and evicts the worker Workload.

The worker Workload then stays like this indefinitely, and no second ProvisioningRequest is created:

```yaml
status:
  admissionChecks:
  - name: <provisioning-check>
    state: Pending
    message: 'Reset to Pending after eviction. Previously: Retry'
    requeueAfterSeconds: 30
    retryCount: 1
  conditions:
  - type: QuotaReserved
    status: "True"
  - type: Evicted
    status: "True"
    reason: AdmissionCheck
  - type: Admitted
    status: "False"
```

Both workers were short of capacity, so with the all-at-once dispatcher both worker Workloads ended in this state. The job made no progress while holding quota on the manager and on both workers.

**What you expected to happen**:

- A Workload evicted before admission releases its quota, with or without an owning job. On the worker above: `QuotaReserved=False`, a requeue after the retry delay, a new reservation, and the next ProvisioningRequest attempt.
- A worker Workload that is deactivated because its admission check was `Rejected` is not deleted and recreated endlessly with a fresh retry history (a separate problem, described at the end of "Anything else we need to know?").

**How to reproduce it (as minimally and precisely as possible)**:

What was observed where:

- Live, on v0.20.6: the MultiKueue scenario above (the `BookingExpired` case).
- In an integration test (envtest) on `main` at `8c0e862dd`, single cluster, no MultiKueue: a Workload without owner references gets stuck the same way after an admission check `Retry` (with and without `requeueAfterSeconds`) and after a preemption. Only the plain `Retry` spec is shown below; the other two are not shown and would become the regression tests of the PR.
- That the MultiKueue path is unchanged on `main` is from reading the code, not from a run.

On MultiKueue:

1. Set up MultiKueue with a worker ClusterQueue that has an AdmissionCheck, for example a ProvisioningRequest check or a custom check.
2. Submit a Job on the manager and wait until the worker Workload has `QuotaReserved=True` and `Admitted=False`.
3. Get the worker check to `Retry`. For a ProvisioningRequest check, while retry attempts remain: `Failed=True` while the check is `Pending`, or `BookingExpired=True` after `Provisioned=True` while the Workload is still not admitted because a second check or a delayed topology assignment is pending, as in the scenario above. For a custom check: set the state to `Retry` in the Workload status.
4. Wait past the retry delay, if any (`status.requeueState.requeueAt`). The worker Workload stays at `QuotaReserved=True`, `Evicted=True` (reason `AdmissionCheck`), `Admitted=False`, with the check back at `Pending`. It holds the worker ClusterQueue quota and is never retried.

On a single cluster, the integration test below does the same without MultiKueue: an AdmissionCheck that no controller serves (set `Active=True` through its status), a ClusterQueue with 4 CPU, a Workload of 3 CPU created directly with no owner reference, a second Workload of 3 CPU that has to wait, and then the check of the first Workload set to `Retry` through the status subresource. It asserts for 45 seconds that the first Workload keeps `Evicted=True`, `QuotaReserved=True` and `status.admission`, that the ClusterQueue status keeps `reservingWorkloads: 1`, and that the second Workload gets no quota. It passes on `main` at `8c0e862dd`.

**Anything else we need to know?**:

Root cause, at `8c0e862dd`:

1. A check in `Retry` makes the Workload controller call `Evict` ([`pkg/controller/core/workload_controller.go:1107-1113`](https://github.com/kubernetes-sigs/kueue/blob/8c0e862ddf9f05cfa7079f95320bc3e76ca92c70/pkg/controller/core/workload_controller.go#L1107-L1113)). `Evict` sets `Evicted=True` and resets the checks to `Pending`, and leaves the reservation in place ([`pkg/workload/evict/evict.go:218-225`](https://github.com/kubernetes-sigs/kueue/blob/8c0e862ddf9f05cfa7079f95320bc3e76ca92c70/pkg/workload/evict/evict.go#L218-L225), [`:234-254`](https://github.com/kubernetes-sigs/kueue/blob/8c0e862ddf9f05cfa7079f95320bc3e76ca92c70/pkg/workload/evict/evict.go#L234-L254)).
2. Releasing the reservation is the second phase of the eviction, and only the job reconciler does it: `reconcileEvicted` stops the job, then `clearAdmissionAfterEviction` sets `Requeued` and `QuotaReserved=False` ([`pkg/controller/jobframework/reconciler.go:753-770`](https://github.com/kubernetes-sigs/kueue/blob/8c0e862ddf9f05cfa7079f95320bc3e76ca92c70/pkg/controller/jobframework/reconciler.go#L753-L770), [`:906-945`](https://github.com/kubernetes-sigs/kueue/blob/8c0e862ddf9f05cfa7079f95320bc3e76ca92c70/pkg/controller/jobframework/reconciler.go#L906-L945)). The job reconciler reaches a Workload only through its owner reference ([`:2707`](https://github.com/kubernetes-sigs/kueue/blob/8c0e862ddf9f05cfa7079f95320bc3e76ca92c70/pkg/controller/jobframework/reconciler.go#L2707)).
3. A MultiKueue worker Workload has no owner before admission. The manager creates it without owner references ([`pkg/controller/admissionchecks/multikueue/workload.go:1781-1799`](https://github.com/kubernetes-sigs/kueue/blob/8c0e862ddf9f05cfa7079f95320bc3e76ca92c70/pkg/controller/admissionchecks/multikueue/workload.go#L1781-L1799)). It creates the remote job once a remote is admitted ([`:814-815`](https://github.com/kubernetes-sigs/kueue/blob/8c0e862ddf9f05cfa7079f95320bc3e76ca92c70/pkg/controller/admissionchecks/multikueue/workload.go#L814-L815), [`:847-885`](https://github.com/kubernetes-sigs/kueue/blob/8c0e862ddf9f05cfa7079f95320bc3e76ca92c70/pkg/controller/admissionchecks/multikueue/workload.go#L847-L885)), or finished, or evicted while the manager Workload is itself evicted ([`:686`](https://github.com/kubernetes-sigs/kueue/blob/8c0e862ddf9f05cfa7079f95320bc3e76ca92c70/pkg/controller/admissionchecks/multikueue/workload.go#L686), [`:700-715`](https://github.com/kubernetes-sigs/kueue/blob/8c0e862ddf9f05cfa7079f95320bc3e76ca92c70/pkg/controller/admissionchecks/multikueue/workload.go#L700-L715)); none of these applies here.
4. Nothing else acts on it. The Workload controller skips its backoff path while quota is reserved and returns without a requeue ([`workload_controller.go:786-788`](https://github.com/kubernetes-sigs/kueue/blob/8c0e862ddf9f05cfa7079f95320bc3e76ca92c70/pkg/controller/core/workload_controller.go#L786-L788), [`:954-989`](https://github.com/kubernetes-sigs/kueue/blob/8c0e862ddf9f05cfa7079f95320bc3e76ca92c70/pkg/controller/core/workload_controller.go#L954-L989)). The ProvisioningRequest controller returns early for an evicted Workload ([`pkg/controller/admissionchecks/provisioning/controller.go:162-164`](https://github.com/kubernetes-sigs/kueue/blob/8c0e862ddf9f05cfa7079f95320bc3e76ca92c70/pkg/controller/admissionchecks/provisioning/controller.go#L162-L164)). The scheduler does not queue a Workload that holds quota ([`pkg/workload/workload.go:1406-1409`](https://github.com/kubernetes-sigs/kueue/blob/8c0e862ddf9f05cfa7079f95320bc3e76ca92c70/pkg/workload/workload.go#L1406-L1409)). The MultiKueue manager redoes admission after a worker eviction (#8477) only when its own check is `Ready`, that is after admission ([`multikueue/workload.go:730`](https://github.com/kubernetes-sigs/kueue/blob/8c0e862ddf9f05cfa7079f95320bc3e76ca92c70/pkg/controller/admissionchecks/multikueue/workload.go#L730)), so that path does not cover an eviction before admission.

Impact:

- Quota is held forever by a Workload that will never run. On MultiKueue this is worker quota plus the manager's quota for the same job.
- When every nominated worker ends in this state, the job is stuck across the fleet. The bug is masked whenever another worker admits first, because the manager then deletes the other remote Workloads.
- A Workload without an owner that is preempted before admission gets stuck the same way. Its preemptor waits forever, and the scheduler does not idle: the integration test log has more than 4000 `Preemption ongoing` lines for one such preemptor in 45 seconds.

Proposed fix: let the core Workload controller complete the eviction when a Workload has `Evicted=True`, `QuotaReserved=True`, is not `Admitted` and has no owner references, using the same write the job reconciler uses today (moved to a shared helper). A Workload without an owner has no job that Kueue could have started, so there is nothing to stop first. Workloads with an owner stay with their job reconciler, and the MultiKueue manager does not change. The ConcurrentAdmission controller already completes evictions itself in this way for its Variants, which are owned by their Parent Workload and not by a job ([`pkg/controller/concurrentadmission/controller.go:488-507`](https://github.com/kubernetes-sigs/kueue/blob/8c0e862ddf9f05cfa7079f95320bc3e76ca92c70/pkg/controller/concurrentadmission/controller.go#L488-L507)). I can send the PR.

Backport: please consider backporting the fix to the supported release branches. #18116, a smaller quota retention bug on the same path (quota held for the retry backoff), was backported to release-0.19 and release-0.20; this one never recovers.

Related: the same worker status appears in a test report on #8089 (comment of 2026-01-21). #18116 changed when the eviction happens (before the retry backoff instead of after it), but not who completes it.

A separate problem, which the proposed fix does not solve: when a worker admission check goes to `Rejected`, the worker deactivates the remote Workload (`spec.active: false`). The manager then sees a spec mismatch and deletes the remote Workload ([`multikueue/workload.go:755-810`](https://github.com/kubernetes-sigs/kueue/blob/8c0e862ddf9f05cfa7079f95320bc3e76ca92c70/pkg/controller/admissionchecks/multikueue/workload.go#L755-L810)), and, as long as its own check is `Pending` and the worker is still nominated, creates a new one ([`:1283-1293`](https://github.com/kubernetes-sigs/kueue/blob/8c0e862ddf9f05cfa7079f95320bc3e76ca92c70/pkg/controller/admissionchecks/multikueue/workload.go#L1283-L1293)). The new object has an empty status, so the check's `retryCount` starts again, and so does the ProvisioningRequest attempt number once the requests of the previous incarnation are gone. The `retryStrategy.backoffLimitCount` of the ProvisioningRequestConfig, which is what turns `Retry` into `Rejected`, therefore ends each incarnation but never ends the cycle. No quota is leaked here: an inactive Workload is not counted, and it is then deleted. This is from reading the code and was not reproduced. It can be split into its own issue.
