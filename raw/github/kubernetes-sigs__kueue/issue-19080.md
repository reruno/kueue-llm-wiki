## Description

**What would you like to investigate**:

When someone asks CodeRabbit to open an issue in a reply to an inline review thread, CodeRabbit first answers with:

> 📌 Tracking this review finding. CodeRabbit will verify future changes against the original feedback and will only mark it fixed when the code satisfies it.

Nobody asked it to track anything. Examples:

| Request | Tracking reply |
|---|---|
| https://github.com/kubernetes-sigs/kueue/pull/18783#discussion_r4578765990 | https://github.com/kubernetes-sigs/kueue/pull/18783#discussion_r4578771006 |
| https://github.com/kubernetes-sigs/kueue/pull/18934#discussion_r4611127660 | https://github.com/kubernetes-sigs/kueue/pull/18934#discussion_r4611143343 |
| https://github.com/kubernetes-sigs/kueue/pull/18934#discussion_r4614323377 | https://github.com/kubernetes-sigs/kueue/pull/18934#discussion_r4614353553 |

In the first two cases a full reply followed a few minutes later. In the third, no other reply followed and no issue was opened. On #18783 CodeRabbit itself replied: "Sorry for the earlier PR-tracking reply."

What we checked:

- The [CodeRabbit docs](https://docs.coderabbit.ai/reference/review-commands) say `track` runs only on an explicit `@coderabbitai track` reply in a review thread on code.
- The [config schema](https://coderabbit.ai/integrations/schema.v2.json) has no option to turn finding tracking off, and `.coderabbit.yaml` does not mention it.

Open questions:

- Can anything in `.coderabbit.yaml` or the skills prevent this?
- Does asking in a top-level PR comment, instead of an inline review thread, avoid it?
- Should this be reported to CodeRabbit as a bug?

**Why is this needed**:

The tracking reply is noise in review threads. It can also make CodeRabbit drop the actual request, as in the third example.
