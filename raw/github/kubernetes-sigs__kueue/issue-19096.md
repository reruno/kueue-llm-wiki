**What would you like to be added**:

A manager restart scenario for the MultiKueue performance benchmark in `test/performance/multikueue`, next to the worker reconnect scenario of #19003.

The scenario would:

1. Admit a large number of Workloads on one or more workers, for example 1,000 per worker, and wait until the `multikueue_workload` queue stays empty.
2. Restart the manager controllers with the same Workloads, AdmissionChecks and MultiKueueConfigs in place, so that every informer lists every existing object again.
3. While the initial-list burst is processed, create new Workloads at a fixed rate.

And report:

- The dispatch latency of the new Workloads (creation → admitted on the manager): p50, p90, and max, during and after the restart.
- The `multikueue_workload` queue depth by `priority` over time, and the time until the backlog drains.

The checker would fail when the dispatch latency of the new Workloads during the restart exceeds a calibrated threshold.

**Why is this needed**:

When the manager restarts, the informers report every existing object as created, and the event handlers queue every unfinished Workload. Before #18949, the AdmissionCheck event handler queued these Workloads at the default priority, so new Workloads waited behind them (#18938). On a production manager:

| | `multikueue_workload` queue depth at priority 0 | time to dispatch a new Workload after a restart |
|---|---|---|
| without #18949 | peak 247, drained after about 3.5 min | up to about 3.5 min |
| with #18949 | peak 3 in the first 5 min | 0–3 s |

These numbers come from manual measurements on a live cluster. No test protects them, so a change that queues an initial-list event at the default priority again would bring the delay back without any CI signal.

Related: #18466, #18938, #18949, #19003
