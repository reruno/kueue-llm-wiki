## Description

**What happened**:

With MultiKueue, elastic RayJobs, and partial replica scale-up enabled, the manager and worker can admit different worker counts for the same Workload slice. The effective worker-side grant does not reliably drive the next scale-up probe.

I reproduced two directions in a local two-cluster Kind setup using real Ray actors, without GPUs:

| Available capacity, excluding the head | Manager grant | Worker grant | Observed behavior |
| --- | --- | --- | --- |
| Manager: 6 workers; worker cluster: 2 | 6 | 2 | Two workers run and four pods remain scheduling-gated. Raising worker quota to fit all six does not produce another probe or ungate the remaining pods. |
| Manager: 2 workers; worker cluster: 6 | 2 | 6 | All six workers run, exceeding the manager-side worker reservation. |

Both directions reproduced with Kueue v0.20.5 on both clusters, and again with **both manager and worker running unmodified current main** at `1fa7c3eabf6ebfa9c32f0514ec617f204bf85818`. I checked upstream main before the repeat and verified that both healthy controllers ran the same image ID before submitting fresh jobs. These failures do not require a manager/worker version mismatch.

In the first case, both sides report the admitted slice as `Admitted=True`, and the MultiKueue admission check is `Ready`. The manager's worker PodSet has requested count 6 and assignment count 6; the worker's corresponding PodSet has requested count 6 and assignment count 2. Increasing worker quota alone leaves that state unchanged. This is not a shortage of schedulable node resources: the extra pods retain `kueue.x-k8s.io/elastic-job`, and real actor calls complete on only two workers.

**What you expected to happen**:

A worker cluster should not execute more replicas than the manager has reserved. When it admits fewer replicas than the manager requested, the effective grant should remain visible to the elastic scale-up logic so the job can request more capacity as it becomes available, without restarting its head or existing workers.

**How to reproduce it (as minimally and precisely as possible)**:

1. Use two local Kubernetes clusters with Kueue built from the main commit above (or v0.20.5) and KubeRay v1.7.0. Configure MultiKueue with one worker cluster. Use one CPU ResourceFlavor and a LocalQueue on each cluster; the manager ClusterQueue uses the MultiKueue admission check. No topology, borrowing, preemption, or GPUs are needed.
2. Enable these feature gates on both Kueue controllers, with the `batch/job`, `ray.io/rayjob`, and `ray.io/raycluster` integrations:

   ```yaml
   featureGates:
     ElasticJobsViaWorkloadSlices: true
     ElasticJobsViaWorkloadSlicesWithPartialReplicaScaleUp: true
     MultiKueueRayInTreeAutoscaling: true
     SkipChildJobSuspension: true
   ```

3. Give the manager queue `2750m` CPU quota and the worker queue `1750m`, with sufficient memory quota (12Gi in this test). Submit a RayJob through the manager with:

   ```yaml
   metadata:
     labels:
       kueue.x-k8s.io/queue-name: local
     annotations:
       kueue.x-k8s.io/elastic-job: "true"
       kueue.x-k8s.io/elastic-job-scale-up-strategy: partial
   ```

   Use Ray 2.53.0, `submissionMode: HTTPMode`, and in-tree autoscaling. The head container requests `750m` CPU and advertises `num-cpus: "0"`; the autoscaler sidecar adds its default `500m` request. The single worker group starts at zero replicas, has `minReplicas: 0` and `maxReplicas: 6`, requests `250m` CPU per worker, and advertises one CPU and one custom `worker-unit` resource per worker. Set the autoscaler idle timeout to 10 seconds and update interval to 2 seconds. The total queue requirement is therefore `1250m + 250m * worker_count`.

4. Run a driver that first creates one actor requiring `worker-unit: 1`, then raises demand to six while retaining the first actor. This is the driver used in the test; write `6` to `/tmp/partial-lab-demand` in the head's Ray container once the first actor is running:

   ```python
   import json
   import pathlib
   import time
   import ray

   ray.init(address="auto")

   @ray.remote(num_cpus=0, resources={"worker-unit": 1})
   class Counter:
       def tick(self):
           return ray.get_runtime_context().get_node_id()

   actors = []
   while True:
       path = pathlib.Path("/tmp/partial-lab-demand")
       target = int(path.read_text()) if path.exists() else 1
       if target < 0:
           break
       while len(actors) < target:
           actors.append(Counter.remote())
       while len(actors) > target:
           ray.kill(actors.pop())
       refs = [actor.tick.remote() for actor in actors]
       ready, _ = ray.wait(refs, num_returns=len(refs), timeout=2) if refs else ([], [])
       print(json.dumps({"target": target, "completed": len(ready), "nodes": ray.get(ready)}), flush=True)
       time.sleep(5)
   ```

5. Observe manager assignment 6 / worker assignment 2 and two actors completing. Raise the worker queue CPU quota to `2750m` without changing Ray demand. In the baseline, the job remains at two running workers with four gated pods; no further expansion probe appears. I observed this for more than two minutes after quota release with both clusters on main, as well as in the released-version run.
6. For the reverse case, start a fresh job with manager quota `1750m` and worker quota `2750m`. Repeat the one-to-six demand change. On both tested versions, the manager grants two workers while the worker grants six, and actor calls complete on six distinct worker nodes.

**Anything else we need to know?**:

This appears related to the interaction between partial scale-up and MultiKueue, rather than the original all-or-nothing expansion behavior tracked in https://github.com/kubernetes-sigs/kueue/issues/12100. Partial scale-up was implemented in https://github.com/kubernetes-sigs/kueue/pull/14937; MultiKueue WorkloadSlices support was tracked in https://github.com/kubernetes-sigs/kueue/issues/6335. I did not find an existing report covering this manager/worker grant mismatch.

Source investigation points to two places: `cloneForCreate` copies the manager's requested PodSet counts into the remote Workload rather than bounding partial counts by the manager grant; and the manager's elastic reconciliation continues to see its own larger assignment when the worker admits fewer replicas. A local prototype bounds the remote request by the manager grant and reconciles the smaller worker grant back into the manager's effective slice count. It also preserves a distinct next-probe name when that correction happens without a new Ray desired-count revision.

The prototype resumed a stalled two-worker job to six without replacing its Ray head or existing workers. The same job then shrank from six to one and expanded through two, three, and six as worker quota was increased in steps. Real actor calls completed at those sizes. In the reverse case, the prototype limited execution to two workers despite six-worker capacity on the worker cluster. The pending probe survived a manager-controller restart, then expanded to six after manager quota increased, preserving the same head and two existing workers. Focused MultiKueue, jobframework, and workload-slicing unit suites pass, including feature-gate-off, reclaim-accounting, and oversized-admission eviction-propagation cases.

The prototype checks were also repeated with the worker on unmodified current main. Changing only the manager to the prototype recovered the stalled forward case from two to six executing actors, retaining the head and both existing workers. A fresh reverse-case job stayed at two actors until manager quota increased, then reached six while preserving its head and existing workers.

This is diagnostic evidence, not a claim that the prototype is ready to merge. Existing oversized admissions need careful handling so quota is not released while pods are still running. Broader upgrade, eviction/retry, worker-disconnect, and multiple-worker-group behavior still need validation.

AI assistance was used for this investigation, local prototype, and report. The observations above are from executed local tests.
