## Description

**What happened**:

In MultiKueue, a worker-rejected elastic Workload count reduction aborts `reconcileGroup` before independent updates can complete. With `ElasticJobsViaWorkloadSlices` enabled on the manager and disabled on the worker, the worker rejects a reduction of an admitted Workload's PodSet count as immutable. The failed update also blocks a priority change included in that update and the later additive-toleration update.

The return is inside the remote loop, so any remaining remotes for the same Workload are skipped as well. That last effect follows from the control flow; the local reproduction used one remote. This is not a claim that unrelated Workloads stop reconciling.

I reproduced the rejection against the unmodified upstream MultiKueue controller at `1fa7c3eabf6ebfa9c32f0514ec617f204bf85818`, using its existing scale-down path. The partial-grant projection in #19106 adds another way to encounter the same limitation. The finding came from [CodeRabbit's review](https://github.com/kubernetes-sigs/kueue/pull/19106#pullrequestreview-5969125610).

**What you expected to happen**:

An unsupported resize should have an explicit compatibility/error-handling policy that preserves the existing reservation and allows independent supported updates to proceed. It should not continually block those updates on the same rejected resize.

This does not require accepting a resize that the worker's feature gates prohibit. Possible approaches include isolating the rejected update or detecting the unsupported configuration before attempting it. The choice needs discussion and regression coverage.

**How to reproduce it (as minimally and precisely as possible)**:

The reproduction is a local controller test using a fake Kubernetes client and the real `webhooks.ValidateWorkloadUpdate` function. It does not run two API servers, schedulers, or actual jobs.

1. Enable `ElasticJobsViaWorkloadSlices`, `ElasticJobsViaWorkloadSlicesWithPartialReplicaScaleUp`, and `AllowAddingPodTemplateTolerations` for the manager reconciliation.
2. Create manager and worker copies of an elastic Workload with a single `workers` PodSet, `minCount: 1`, an existing toleration, and an admitted assignment of 2. Set the manager admission check to `Ready` and its `status.clusterName` to the worker.
3. For the existing upstream scale-down path, use manager `spec.podSets[0].count: 2` and worker count 6. Give the manager a changed priority and one additional toleration.
4. Intercept the worker client's `Update`. Fetch the stored old Workload and validate the candidate with `webhooks.ValidateWorkloadUpdate`, with both elastic gates disabled for this worker validation and `AllowAddingPodTemplateTolerations` enabled. Return the validation error without storing the candidate. Restore the manager's gates before reconciliation continues.
5. Invoke `reconcileGroup`. It returns `failed to update remote workload` with `spec.podSets.0 ... field is immutable`. The stored worker count remains 6, its admission assignment remains 2, and neither the changed priority nor the added toleration is stored.

I also tested the #19106 path with both spec counts initially 6 and the manager and worker each assigned 2. The manager projects the remote count to its grant of 2:

| Controller / configuration | Observed result |
| --- | --- |
| #19106, matching elastic and partial-scale-up gates | Count converges to 2; priority and added toleration propagate |
| #19106, worker elastic gates disabled | Count update rejected; priority and toleration updates blocked |
| Unmodified upstream controller, existing scale-down path, worker elastic gates disabled | Same rejection and blocked updates |

The negative tests assert that reconciliation and independent updates succeed, and fail as expected in the mixed-gate cases. The matching-gate control passes. Repeated rejection is expected from the unchanged stored state and the same update path; retry/backoff behavior was not measured.

**Anything else we need to know?**:

Relevant source at the tested upstream revision:

- [Remote spec updates and early return](https://github.com/kubernetes-sigs/kueue/blob/1fa7c3eabf6ebfa9c32f0514ec617f204bf85818/pkg/controller/admissionchecks/multikueue/workload.go#L747-L815).
- [PodSet immutability validation](https://github.com/kubernetes-sigs/kueue/blob/1fa7c3eabf6ebfa9c32f0514ec617f204bf85818/pkg/webhooks/workload_webhook.go#L555-L568).

Related: #17952 and #19028 extract the remote-update logic. The current #19028 diff preserves the early return on a failed spec update, so that cleanup does not resolve this report. #15249 concerned partial-scale-up Workload-shape validation, rather than isolation of a rejected remote resize.

I am tracking this separately from #19106 to keep that PR focused on asymmetric partial grants. Simply ignoring the error would leave the rejected spec in memory; restoring it alone would still retry an unsupported update. The compatibility policy deserves a separate change. This remains unfixed.
