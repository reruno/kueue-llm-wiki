## Description

/kind bug
/area concurrent-admission

**What happened**:

With ConcurrentAdmission and a Workload custom metric label configured, `kueue_pending_workloads`
counts one Job once per Variant. One Job with three Variants shows as 3 in the metric, while the
ClusterQueue status shows 1 pending Workload. Without the custom label, the metric shows 1, matching
the status.

**What you expected to happen**:

Each Job is counted once, with or without custom labels, so the per-label values add up to the status.
KEP-8691 says the existing metrics track Parent Workloads and skip Variants, and #18747 fixed this for
the counts without labels (#18748, and #18806 for LocalQueues).

**How to reproduce it (as minimally and precisely as possible)**:

1. Enable the `ConcurrentAdmission` and `CustomMetricLabels` feature gates, and configure a Workload
   custom metric label:
   ```yaml
   metrics:
     customLabels:
     - name: team
       sourceKind: Workload
       sourceLabelKey: team
       trackedValues: [a]
   ```
2. Create a ClusterQueue with three flavors with zero quota, and a LocalQueue for it:
   ```yaml
   spec:
     namespaceSelector: {}
     concurrentAdmissionPolicy:
       migration:
         mode: TryPreferredFlavors
     resourceGroups:
     - coveredResources: [cpu]
       flavors:
       - name: reservation
         resources: [{name: cpu, nominalQuota: "0"}]
       - name: on-demand
         resources: [{name: cpu, nominalQuota: "0"}]
       - name: spot
         resources: [{name: cpu, nominalQuota: "0"}]
   ```
3. Submit one Job with the labels `kueue.x-k8s.io/queue-name: <local queue>` and `team: a`, requesting
   `cpu: 1`. Kueue creates the Parent and three Variants.
4. The ClusterQueue status reports `pendingWorkloads: 1`, but the metric reports 3:
   ```
   kueue_pending_workloads{cluster_queue="labelled-pending-cq",custom_team="a",replica_role="leader",status="inadmissible"} 3
   ```
   Without the custom label configured, the same setup reports
   `kueue_pending_workloads{cluster_queue="labelled-pending-cq",replica_role="leader",status="inadmissible"} 1`.

**Anything else we need to know?**:

I ran into this while looking at #8249, adding `priority_class` to these gauges. That needs the same
kind of per-label split, so it would hit the same problem.

The LocalQueue metric with custom labels still has the same gap after #18806, from reading the code on
main. With CustomMetricLabels going to beta in v0.21 (#18706), more setups will have custom labels on.

The fixes for the totals take out the extra Variants when the total is read, but the per-label numbers
skip that step. A fix would need to cover both ClusterQueues and LocalQueues and keep the totals cheap to
read, ideally in a way #8249 can build on. Two questions that affect it:

1. Variants of one Job can end up with different label values, since labels can change after the
   Variants are created. Counting the Job under the Parent's labels seems simplest. Does that sound right?
2. When a Parent is admitted and its migration Variants are still pending (`TryPreferredFlavors`), the
   totals count it as pending today. This came up in #18747. Matching the totals here and leaving that
   question separate seems simplest, unless you'd rather settle it in this fix.

Opening this as suggested in #18747.
