## Description

**What happened**:

Follow-up from the [#19158 review](https://github.com/kubernetes-sigs/kueue/pull/19158#pullrequestreview-5993930246).

The DRA CEL device check evaluates the selectors of a claim on the devices of every node, in listing order: it filters ResourceSlices by pool, not by node ([pools.go](https://github.com/kubernetes-sigs/kueue/blob/c364da8e0129321e4c094fbc0f4ff7099826c83d/pkg/dra/pools.go#L47-L75)).
When a selector reads an attribute that a device on another node lacks, the evaluation fails and the check returns Invalid ([claims.go](https://github.com/kubernetes-sigs/kueue/blob/c364da8e0129321e4c094fbc0f4ff7099826c83d/pkg/dra/claims.go#L732-L740)), even when the only node the Pod can use has a matching device.
kube-scheduler's allocator reads only the ResourceSlices of the node it filters ([pools_stable.go](https://github.com/kubernetes/dynamic-resource-allocation/blob/v0.37.2/structured/internal/stable/pools_stable.go#L58-L95)), so it allocates the device there.

For an `exactly` request, the result depends on listing order, because the check stops at the first device that gives enough matches ([claims.go](https://github.com/kubernetes-sigs/kueue/blob/c364da8e0129321e4c094fbc0f4ff7099826c83d/pkg/dra/claims.go#L580-L611)).
#19158 added the same check for a `firstAvailable` request with a CEL selector on every alternative ([claims.go](https://github.com/kubernetes-sigs/kueue/blob/c364da8e0129321e4c094fbc0f4ff7099826c83d/pkg/dra/claims.go#L698-L753)).
When the preferred alternative matches no device on the Pod's node, the check reads every device for it, so it fails in both listing orders before it tries the fallback.

The workload controller retries the check with backoff only when the result has an internal error ([workload_controller.go](https://github.com/kubernetes-sigs/kueue/blob/c364da8e0129321e4c094fbc0f4ff7099826c83d/pkg/controller/core/workload_controller.go#L301-L303)), so a result with only this Invalid error does not trigger that backoff.

**What you expected to happen**:

An evaluation error on a device of a node the Pod cannot use does not keep Kueue from admitting a Workload that kube-scheduler can place.

**How to reproduce it (as minimally and precisely as possible)**:

Found with a unit test that calls `GetResourceRequestsForResourceClaimTemplates` and the `k8s.io/dynamic-resource-allocation` v0.37.2 allocators, then reproduced on a kind cluster.

<details><summary>Setup and results</summary>

- DeviceClass `cls`, mapped in `deviceClassMappings`.
- A ResourceSlice on `node-a` with `dev-a`, which has the attribute `test-driver/tier: slow`.
- A ResourceSlice on `node-b` with `dev-b`, which has no `tier` attribute.
- The Pod can only run on `node-a`.

An `exactly` request, on main at c364da8e0:

```yaml
requests:
- name: gpu
  exactly:
    deviceClassName: cls
    selectors:
    - cel:
        expression: device.attributes["test-driver"].tier == "slow"
```

- With node-a's slice listed first, the check passes.
- With node-b's slice listed first, it returns `exactly.selectors: Invalid value: null: ResourceClaimTemplate claim: CEL evaluation failed for DeviceClass cls: no such key: tier`.

A `firstAvailable` request, on main at c364da8e0:

```yaml
requests:
- name: gpu
  firstAvailable:
  - name: preferred
    deviceClassName: cls
    selectors:
    - cel:
        expression: device.attributes["test-driver"].tier == "fast"
  - name: fallback
    deviceClassName: cls
    selectors:
    - cel:
        expression: device.driver == "test-driver"
```

- In both listing orders, the check returns `firstAvailable[0].selectors: Invalid value: null: ResourceClaimTemplate claim: CEL evaluation failed for DeviceClass cls: no such key: tier`.
- Before #19158 (c7d530509), with the Alpha gate on, Kueue admitted it, because it did not check `firstAvailable` requests.

The stable, incubating and experimental allocators, given both slices:

- On node-a, they allocate `dev-a`, as `gpu` or as `gpu/fallback`.
- On node-b, they return `CEL runtime error: no such key: tier. consider using CEL optional chaining (.? followed by orValue()) or guarding the check with has() for optional fields`.

With `has(device.attributes["test-driver"].tier) &&` in front of the `tier` comparison, the check passes in both orders and for both requests.

</details>

<details><summary>On a kind cluster</summary>

Kubernetes v1.37.0 with two workers, Kueue main at f1314eb02, and `deviceClassMappings` mapping `cls` to `example.com/gpu`. The two ResourceSlices above are created by hand for the driver `test-driver`. No driver runs, so Pods stay Pending after kube-scheduler allocates their claims.

- A Job with the `firstAvailable` claim, pinned to node-a: the Workload has `QuotaReserved=False` with reason `DRAResourcesUnresolved` and the CEL error above, and the Job stays suspended. Seven minutes later it is unchanged.
- The same claim in a Pod that Kueue does not manage: on node-a, kube-scheduler allocates `gpu/fallback` to `dev-a`. On node-b, it reports `FailedScheduling` with `CEL runtime error: no such key: tier`.
- With the `has()` guard, Kueue admits the `firstAvailable` and the `exactly` Jobs, and kube-scheduler allocates `dev-a` to both.
- 20 identical Jobs with the `exactly` claim, pinned to node-a: all 20 are admitted when the slice of node-a is created first. After recreating the slices with node-b's created first and named to sort first, and restarting Kueue, 15 of 20 stay rejected with the CEL error.

</details>

**Anything else we need to know?**:

- kube-scheduler aborts the scheduling attempt and retries when a node it filters has such a device ([dynamicresources.go](https://github.com/kubernetes/kubernetes/blob/v1.37.2/pkg/scheduler/framework/plugins/dynamicresources/dynamicresources.go#L1080-L1092)), so a Pod that can land on node-b fails there too. It never reads the devices of nodes that its earlier filters rejected.
- The check runs before Kueue knows which nodes the Pod can use, since device matching is computed globally ([KEP-2941](https://github.com/kubernetes-sigs/kueue/blob/c364da8e0129321e4c094fbc0f4ff7099826c83d/keps/2941-DRA/README.md#L493-L494)).
- #19172 searches other device choices when a request falls short. It does not change this, because an evaluation error also stops the search.

### Comment by [@thc1006](https://github.com/thc1006) — 2026-11-20T17:07:10Z

A related trigger ([CodeRabbit on #19172](https://github.com/kubernetes-sigs/kueue/pull/19172#discussion_r4634774352)). When any CEL request in a claim has no counter or capacity source, the check lists the ResourceSlices of every driver. A counter- or capacity-backed `exactly` request is then matched against other drivers' devices too. If its DeviceClass has no driver selector, its selector can fail on one of them, depending on listing order. Source-less `exactly` requests already did this before #19158; `firstAvailable` requests now do too. On one node, the stable allocator fails the same way, while incubating and experimental sort pools by driver and allocate.

### Comment by [@thc1006](https://github.com/thc1006) — 2026-11-20T22:01:29Z

On the same kind cluster, Workloads that were already admitted can get stuck too. Five admitted `exactly` Jobs were evicted by `WaitForPodsReady`, which is on by default with a 30-minute timeout, because their Pods never became ready in this setup. On requeue the check ran again and returned the CEL error, so they stayed at `DRAResourcesUnresolved`. It runs from scratch for every pending Workload and its device order is not stable, so passing once does not carry over.

### Comment by [@thc1006](https://github.com/thc1006) — 2026-11-21T22:03:34Z

Compile and DeviceClass errors don't depend on the devices, so they should stay as they are. An error on one node's device is different: kube-scheduler never evaluates it when another filter, such as node affinity, rules that node out first. But when it does filter that node, the [DRA filter returns an error](https://github.com/kubernetes/kubernetes/blob/v1.37.0/pkg/scheduler/framework/plugins/dynamicresources/dynamicresources.go#L1077-L1088) and the [whole scheduling attempt fails](https://github.com/kubernetes/kubernetes/blob/v1.37.0/pkg/scheduler/schedule_one.go#L818-L823); a non-match would then admit some Workloads whose Pods stay Pending. @sohankunkerkar, which side would you rather err on?
