## Description


What happened:

Follow-up to #18800 / [#18931](https://github.com/kubernetes-sigs/kueue/pull/18931), as asked in https://github.com/kubernetes-sigs/kueue/pull/18931#discussion_r4644805140.

A LimitRange sets maxLimitRequestRatio for a resource and has no default for it. A Workload's container sets a request for that resource and no limit. Kueue skips the ratio check for that resource (keysOverLimitRequestRatio in pkg/util/limitrange/limitrange.go skips a resource without both a non-zero request and a non-zero limit), so the Workload is admitted and reserves quota. The LimitRanger admission plugin then forbids every Pod:

cpu max limit to request ratio per Container is 2, but no limit is specified or limit is 0
The same happens when the request is missing or zero (... but no request is specified or request is 0).

What you expected to happen:

The Workload should be marked inadmissible with the resources didn't satisfy LimitRange constraints: ... message and should not reserve quota, as for a ratio above the maximum.

How to reproduce it (as minimally and precisely as possible):

apiVersion: v1
kind: LimitRange
metadata:
  name: ratio
spec:
  limits:
  - type: Container
    maxLimitRequestRatio:
      cpu: "2"
Submit a job to a LocalQueue in that namespace with one container that has requests.cpu: 1 and no limits.cpu. Kueue admits the Workload, and LimitRanger rejects the Pods at creation.

Unit level: Summary.ValidatePodSpec returns no error for a container with a cpu request of 1 and no cpu limit under that LimitRange. The TestValidatePodSpec case container limit to request ratio without limit added in [#18931](https://github.com/kubernetes-sigs/kueue/pull/18931) records this.

Anything else we need to know?:

LimitRanger (plugin/pkg/admission/limitranger/admission.go, limitRequestRatioConstraint) rejects when the request or the limit is missing or zero, after it has applied the LimitRange default and defaultRequest. Kueue also applies those defaults before it validates (pkg/workload/effective_resources.go), so only a LimitRange without a matching default is affected.
The max and min checks have the same gap. LimitRanger's maxConstraint rejects a container with no limit (No limit is specified) and minConstraint rejects one with no request (No request is specified). ValidatePodSpec returns no error for a container with a cpu request and no cpu limit under a Container max, or with no cpu request and no cpu limit under a Container min. A fix could cover the three checks together.
