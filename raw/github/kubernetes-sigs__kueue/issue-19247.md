## Description

**What happened**:

With the partial scale-up strategy (`kueue.x-k8s.io/elastic-job-scale-up-strategy: partial`), an elastic job that scales down below its `minCount` while a scale-up slice is pending gets stuck. The job reconciler fails on every retry, and the admitted slice keeps holding quota for the pods the job no longer has.

The pending slice is the scale-up probe after a partial admission, or a scale-up slice that is not admitted yet. It carries the `minCount` copied forward from the admitted slice, which is the job's initial count. `normalizeActiveSlices` (`pkg/workloadslicing/workloadslicing.go`) selects the pending replacement, so `EnsureWorkloadSlices` (`pkg/workloadslicing/manager.go`) applies the job's new counts to it with `workload.ApplyPodSetCounts`. #16742 lowers `minCount` in `ApplyPodSetCounts` only for admitted Workloads, so the pending slice gets `count < minCount`. The API server rejects the update:

```
failed to update workload pod set counts: Workload.kueue.x-k8s.io "..." is invalid: spec.podSets[0]: Invalid value: minCount should be less or equal to count
```

The error is returned from `ensureOneWorkload`, so the whole job reconcile stops there and is retried with backoff. The rest of the reconcile never runs while the count stays below the floor. For example, when the job finishes, its admitted slice is never finished and keeps its quota.

I reproduced it with batch/Job and RayCluster in integration tests. For RayCluster, the KubeRay autoscaler lowers `replicas` by itself when the cluster is idle, so a partially admitted scale-up followed by an idle period is enough.

**What you expected to happen**:

The pending slice follows the job's counts, as it does when the count stays above `minCount`. The quota held by the job drops to what it still runs, the same way it does when no scale-up slice is pending.

**How to reproduce it (as minimally and precisely as possible)**:

1. Enable `ElasticJobsViaWorkloadSlices` and `ElasticJobsViaWorkloadSlicesWithPartialReplicaScaleUp`.
2. A ClusterQueue with 7 CPU.
3. Create an elastic Indexed Job with the partial strategy, `parallelism: 5`, `completions: 5`, and 1 CPU per pod. It is admitted with 5 pods, so `minCount` is 5.
4. Scale it to 10 (`parallelism` and `completions`). A scale-up slice is admitted with 7 of the 10 pods, and a probe for 10 with `minCount: 5` stays pending.
5. Scale it to 2. The probe update is rejected with `minCount should be less or equal to count`, the job reconciler keeps failing, and the admitted slice keeps holding 7 CPU.

**Anything else we need to know?**:

Proposed fix: in `ApplyPodSetCounts`, also cap `minCount` at the new count for a pending scale-up slice (a Workload without quota reservation that has the `kueue.x-k8s.io/workload-slice-replacement-for` annotation). This matches what #16742 does for admitted slices: KEP-12100 already says that a later scale-up does not restore a minimum lowered on scale-down. While the replaced slice is admitted, the scheduler still requires the replacement to grow past its grant, so a lower `minCount` does not allow a smaller admission.

The initial Workload is left as it is. Lowering its `minCount` before the first admission would let a 4 → 1 → 5 sequence admit it partially, which KEP-12100 lists as a non-goal (discussed in https://github.com/kubernetes-sigs/kueue/pull/16742#issuecomment-6137159184).

This also blocks #19226: the fix there raises the SparkApplication executor `minCount` from `minExecutors` to the initial executor count, so SparkApplications with dynamic allocation hit this as soon as idle executors are removed while a probe is pending.

### Comment by [@mimowo](https://github.com/mimowo) — 2026-11-23T13:07:34Z

First a bit of context: minCount was originally designed for partial admission. This feature isn't used much (if at all).

I'm not sure we need it for elastic jobs, I think it might have been a mistake we instrocuced it for partial scale up. Do you see any reason to keep using minCount actually for elastic jobs? it seems to introduce more confusion than needed. I would rather call it  `spec.podSets[].partialAdmission.minCount`. 

I think for ElasticJobs it seems we need to have `spec.podSets[].elasticJobs.initialMinCount` which determines the size of the initial admission, but later it can be use any value. 

I guess we can consolidate them both into `spec.podSets[].minCount`, but then the proper name is probably  `spec.podSets[].initialMinCount`.

> This is an intentional limitation, I still think minRetainedCount shoud be equal to minCount.

Currently `spec.podSets[].minCount` (interpreted as `spec.podSets[].initialMinCount`) stands for the initial min count, whereas `minRetainedCount` is a fixed value indicating the `minCount` during livetime. So,  they seem a bit different, no?
