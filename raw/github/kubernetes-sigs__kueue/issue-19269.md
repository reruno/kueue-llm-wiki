## Description

**What happened**:

A Job with a `kueue.x-k8s.io/queue-name` label, created in a namespace that `managedJobsNamespaceSelector` doesn't match, is suspended by the webhook and then never unsuspended. Nothing in Kueue picks it up, and nothing tells the user why it stays suspended.

The webhook suspends any Job with a queue name without looking at the namespace:

https://github.com/kubernetes-sigs/kueue/blob/f85dd791882468af1680b32881285194bce955ef/pkg/controller/jobframework/utils.go#L162-L165

The reconciler skips Jobs in namespaces outside the selector, whether they have a queue name or not:

https://github.com/kubernetes-sigs/kueue/blob/f85dd791882468af1680b32881285194bce955ef/pkg/controller/jobframework/reconciler.go#L431-L433
https://github.com/kubernetes-sigs/kueue/blob/f85dd791882468af1680b32881285194bce955ef/pkg/controller/jobframework/reconciler.go#L574-L576

The reconciler matches the current semantics: since `ManagedJobsNamespaceSelectorAlwaysRespected` went GA in v0.19, the selector restricts reconciliation of all jobs regardless of the queue-name label (KEP-3589). The webhook still follows the pre-v0.13 rule.

The same defaulting is used by the webhooks of the other job kinds that the job reconciler handles (JobSet, MPIJob, the Ray kinds, SparkApplication, and the BaseWebhook integrations), so they have the same gap.

**What you expected to happen**:

A job in a namespace outside `managedJobsNamespaceSelector` is left alone by the webhook too, so it runs as if Kueue weren't installed, like a job without a queue name there.

**How to reproduce it (as minimally and precisely as possible)**:

1. Configure `managedJobsNamespaceSelector` to exclude a namespace, for example the default `kubernetes.io/metadata.name NotIn [kube-system, kueue-system]`.
2. Create a Job with `kueue.x-k8s.io/queue-name: any` in `kube-system`.
3. The Job is created with `suspend: true` and stays suspended; no Workload is created.

A `TestDefault` case for the Job webhook and a spec in the Job webhook integration suite both fail on main at `f85dd7918`: the Job comes back suspended.

**Anything else we need to know?**:

- Proposed fix: in `ApplyDefaultForSuspend`, don't suspend a job in a namespace that the selector doesn't match. That covers only the job kinds the job reconciler handles; StatefulSet and the other Pod-based integrations decide management in their own reconcilers, and their tests expect a queued StatefulSet outside the selected namespaces to be managed, so they're left unchanged.
- The doc comment of `managedJobsNamespaceSelector` in the Configuration API still describes the pre-GA "weaker exemption" for non-Pod integrations, where a job with a queue name is always managed. It could be updated separately.

I'd like to work on the fix.
