## Description

**What would you like to be added**:

Allow `.spec.topologyName` to be removed from a ResourceFlavor, so that TAS can be turned off for one flavor without a new flavor or the feature gate. Changing it to a different Topology would stay forbidden.

Today the CEL rule on `ResourceFlavorSpec` forbids both:

```
!has(oldSelf.topologyName) || (has(self.topologyName) && self.topologyName == oldSelf.topologyName)
```

The proposal is to relax it to "may be removed, may not be changed":

```
!has(oldSelf.topologyName) || !has(self.topologyName) || self.topologyName == oldSelf.topologyName
```

Setting `topologyName` on a flavor that has none is already allowed, so after this change TAS could be turned on and off per flavor, in place.

**Why is this needed**:

Once `TopologyAwareScheduling` graduates (#16368), the feature gate can no longer be disabled, and the only rollback left is swapping in a new non-TAS ResourceFlavor. Writing that route up in the migration guide (#17999) showed how heavy it is:

- Quota is tracked per flavor name, so the swap splits one node pool across two quota buckets until the workloads admitted on the TAS flavor finish, which can take days for long-running jobs.
- Every ClusterQueue in the cohort has to be switched together, and to avoid over-admitting the pool the administrator either drains the ClusterQueues or lowers the new flavor's `nominalQuota` and raises it by hand as workloads finish. Fair Sharing and preemption see two flavors during the overlap.

Keeping the flavor name keeps running and new workloads under one quota bucket, with no ClusterQueue changes.

`tolerations` (#13622), `nodeLabels` (#13738) and Topology levels (since v0.20) have already been made mutable. `topologyName` is the last field on the flavor that blocks an in-place rollback.

Much of the runtime already copes with a TAS-admitted workload whose flavor is not in the TAS cache:

- The topology ungater selects on the Workload (`workload.IsAdmittedByTAS`, `pkg/controller/tas/topology_ungater.go`), not on the flavor, so Pods of workloads already admitted through TAS would still be ungated onto their assigned nodes.
- `updateWorkloadTASUsage` (`pkg/cache/scheduler/clusterqueue.go`) logs and skips TAS usage for a flavor that is not in the TAS cache, the path used today when a flavor is deleted.
- Setting `topologyName` again later does not repeat the issues of re-enabling the feature gate (#18503). Workloads admitted while it was unset either have no TAS annotations, so their Pods count as non-TAS usage, or have explicit annotations and were refused by the flavor.

Open questions for the design:

1. `Cache.AddOrUpdateResourceFlavor` only adds TAS flavors to the TAS cache. Removing `topologyName` would also need to remove the flavor from it, as `DeleteResourceFlavor` does.
2. After `topologyName` is set again, should the TAS usage of workloads that are still running from the earlier TAS period be restored, or should they be left to `TASResidualPodAccounting`?
3. ClusterQueues listing the flavor become non-TAS (or mixed). Pending workloads with explicit TAS annotations will be refused with `does not support TopologyAwareScheduling`. Is a warning or event on the update enough?
4. A recreated Pod of a TAS-admitted workload can still lose its assigned node to a newly admitted non-TAS Pod, as with the flavor swap. Document only, or handle?
5. Should the `kueue.x-k8s.io/resource-in-use` finalizer on the Topology be released when the last flavor referencing it drops `topologyName`?
