## Description

/kind bug
/area tas

**What happened**

The scheduler can reserve quota using an assignment computed from an older copy of a pending Workload, even after the API server has persisted a newer Workload spec. For example, two Pods may be assigned to different nodes in one block after the Workload has switched to requiring both Pods on the same hostname.

I reproduced this ordering against an envtest API server on `0f504548314f727dcecadbc35cb6bb738b70a450`, with `WorkloadRequestUseMergePatch` both disabled (SSA) and enabled (Merge Patch). In both modes, the newer request was present in `spec.podSets[0].topologyRequest`, while `status.admission` still contained the old assignment and `QuotaReserved=True`. Adding or removing a topology request during the same window also reproduced the problem.

**What you expected to happen**

When a pending Workload spec changes before its first admission write, the write based on the old spec should be rejected. The scheduler should release its assumed reservation and re-evaluate the updated Workload. Status-only updates should not force a new scheduling cycle if the inputs to the pending admission are still valid.

**How to reproduce it (as minimally and precisely as possible)**

1. Start envtest with the Kueue Workload CRD. Create an unreserved Workload with a two-Pod PodSet requiring `cloud.example/block`.
2. Hold the scheduler's first admission write after it chooses one node per Pod in the same block. Keep the Workload snapshot and assignment from that cycle.
3. Update the Workload spec through the API server to require `kubernetes.io/hostname`. Verify the write succeeds and advances the Workload generation.
4. Resume the first admission write using the earlier snapshot and assignment. Read the Workload from the API server. The new hostname requirement is stored alongside the old two-node assignment and a quota reservation.
5. Repeat with `WorkloadRequestUseMergePatch` toggled.

**Anything else we need to know?**

First-pass SSA does not send a resourceVersion precondition. With Merge Patch, the conflict retry can read the new object and then apply the previously calculated assignment. The race is at the scheduler admission boundary and can also occur for Workloads updated by jobframework while their Jobs are suspended. The StatefulSet synchronization in #18868 stays scoped to its controller.

Using generation as the freshness check may avoid extra scheduling cycles for status-only changes. The check still needs to be tied to the write so another spec update cannot land between the check and the write. Related work includes #15761 for second-pass TAS writes and #18794 for the separate ConcurrentAdmission Parent/Variant path.

**Environment**

- Kubernetes version: v1.37.0 via envtest
- Kueue revision: `0f504548314f727dcecadbc35cb6bb738b70a450`
- Install tools: controller-runtime envtest, Workload CRD, Linux amd64
