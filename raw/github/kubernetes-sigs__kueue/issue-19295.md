### Comment by [@iluv7](https://github.com/iluv7) — 2026-11-22T13:49:07Z

Hi, @mbobrovskyi, I ran the test locally and traced the failing CI run. I couldn't reproduce the flake locally, but the CI logs show a controller-side race. One reconcile resolved the template and queued the Workload without setting `Requeued=True`. The next reconcile tried to persist `Requeued=True`, but the scheduler had already written the admission status, so the controller's patch hit a resource version conflict. This is consistent with the first reconcile seeing the new template while still holding an older Workload without `Requeued=False`.

For a follow-up, I'd like to validate the Workload's `resourceVersion` against an uncached API read after DRA resolution and before making the enqueue decision. If the Workload has changed, the controller would retry reconciliation. If it sees a DRA-related `Requeued=False`, it would persist `Requeued=True` with the version check and enqueue the returned Workload only after the patch succeeds. I'd also add a regression test that simulates the stale cache read.

Does that direction sound reasonable? If so, I'd be happy to pick up the controller fix in a follow-up PR.

### Comment by [@ekam-walia](https://github.com/ekam-walia) — 2026-11-22T14:04:37Z

Good catch tracing the stale cache read! I opened #19301 to deflake the test by polling `Requeued=False` with `managerClient` instead of `k8sClient`, so the test waits for the manager's informer cache to observe `Requeued=False` before creating the ResourceClaimTemplate.

Regarding a controller side fix: since an uncached API read on every DRA reconcile would add extra API server load on the hot path and in a real cluster the workload still gets admitted normally if this race occurs, I'll leave it to @mbobrovskyi to decide whether a controller side change is needed beyond deflaking the test.
