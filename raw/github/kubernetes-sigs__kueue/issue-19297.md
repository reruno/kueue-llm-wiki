## Description

/kind bug
/area integrations
/area tas

**What happened**:

A Kueue-managed StatefulSet can change its Pod template's TAS request while its Workload has a quota reservation and is waiting for an AdmissionCheck. The StatefulSet update accepts the new annotation, but the Workload keeps the topology request and assignment calculated from the old template. When the check becomes Ready, the Workload is admitted using the old assignment across two hosts, despite the updated requirement to place both Pods on one host.

**What you expected to happen**:

Before the StatefulSet is admitted, Kueue should invalidate the reservation based on the old request and evaluate the Workload using the updated topology. For example, changing a two-replica StatefulSet from requiring a shared block to requiring a single hostname should make it wait if no one host can fit both Pods.

**How to reproduce it (as minimally and precisely as possible)**:

1. Configure a LocalQueue backed by a TAS ResourceFlavor, a topology with block and hostname levels, and an AdmissionCheck that can remain Pending. Use two Ready nodes in the same block with one CPU available apiece.
2. Create a Kueue-managed StatefulSet with two replicas requesting one CPU each and set the Pod template annotation `kueue.x-k8s.io/podset-required-topology` to the block level.
3. Wait for the Workload to report `QuotaReserved=True` while the AdmissionCheck is Pending and `Admitted` is not True. Confirm the Workload's topology assignment spans the two nodes.
4. Change the same StatefulSet template annotation to `kubernetes.io/hostname`. Keep the replica count and AdmissionCheck unchanged. Check that the StatefulSet template has the new value and compare it with `spec.podSets[0].topologyRequest.required` on the Workload.
5. Mark the AdmissionCheck Ready. The Workload becomes admitted and retains the original topology request and assignment across both hosts.

I reproduced this sequence with the StatefulSet and TAS controllers, scheduler, and a real API server in envtest. The test asserts the Workload's admission and topology assignment. It does not run kubelets.

**Anything else we need to know?**:

The Workload webhook makes its PodSets immutable while quota is reserved. The StatefulSet reconciler proposed in #18868 therefore updates the topology request only before quota reservation. The generic Job reconciler takes a different path when a suspended Job no longer matches its reserved Workload. It deletes the mismatched Workload so it can create a new one with the current template.

This follows up on [the discussion in #18868](https://github.com/kubernetes-sigs/kueue/pull/18868#issuecomment-7077056612). The related reports cover different time windows: #18867 covers topology changes while resuming from OnHold without a reservation, and #19285 (fix #19291) covers a spec update that races the scheduler before the first quota reservation is written. This issue is strictly about updates that arrive after `QuotaReserved=True`, while the Workload is still waiting for an AdmissionCheck: the existing reservation is never re-evaluated, and the stale assignment is used for admission.

**Environment**:

- Kueue revision examined: `8d4be2938743f325b0d9d6bdae5d9312567e3d6f` (PR #18868).
- Kubernetes version: envtest v1.37.0.
- Hardware: two synthetic Ready nodes in one block, with one CPU available on each.
- Features: TopologyAwareScheduling enabled.
