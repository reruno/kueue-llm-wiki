## Description

**What happened**:

When a job's LocalQueue points to a ClusterQueue with a MultiKueue AdmissionCheck, the job webhooks set `spec.managedBy: kueue.x-k8s.io/multikueue`, even when the job's namespace doesn't match `managedJobsNamespaceSelector`. Kueue doesn't reconcile jobs in such a namespace, so the MultiKueue controller never dispatches the job, and its own controller ignores it because of `managedBy` (the Job controller honors it). The job never runs.

https://github.com/kubernetes-sigs/kueue/blob/707ab47c7c00d12ba0fab7dcf264bf5edce253da/pkg/controller/jobframework/defaults.go#L140-L160

This is the same gap as #19269, in the `managedBy` default instead of the suspend default.

**What you expected to happen**:

A job in a namespace outside `managedJobsNamespaceSelector` keeps its `managedBy`, as Kueue leaves the job alone.

**How to reproduce it (as minimally and precisely as possible)**:

1. MultiKueue enabled, with `managedJobsNamespaceSelector` excluding namespace `ns`.
2. In `ns`, a LocalQueue bound to a ClusterQueue with a MultiKueue AdmissionCheck.
3. Create a Job with `kueue.x-k8s.io/queue-name` set to that LocalQueue in `ns`. It gets `spec.managedBy: kueue.x-k8s.io/multikueue` and never runs.

A Job webhook `TestDefault` case for this fails on main at `707ab47c7`.

**Anything else we need to know?**:

Proposed fix: in `ApplyDefaultForManagedBy`, check the namespace selector before setting `managedBy`. It's shared by all the job webhooks, so they all get the fix. CodeRabbit pointed this out on #19270.

I'd like to work on the fix.
