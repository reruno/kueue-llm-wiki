**What happened**:

When a SparkApplication is admitted via the Kueue integration of apache/spark-kubernetes-operator, the Workload PodSets are built from `spec.sparkConf` and the pod templates in the spec at submission time. However, Spark allows the application jar to override any config at runtime (`SparkConf#set` / `SparkSession.Builder#config`), and the driver builds executor pods from the *merged* config where programmatically set values take precedence over what spark-submit / the operator passed.

As a result, an application that hard-codes executor resources gets admitted with a Workload that reserves far less than it actually consumes:

- The spec declares `spark.executor.instances: "2"`, `spark.executor.memory: "1g"`, `spark.executor.cores: "1"`.
- The Workload executor PodSet reserves 2 × (1 core, 1408Mi) ≈ 2 cores / ~2.8Gi.
- The jar's main class calls `new SparkConf().set("spark.executor.memory", "8g").set("spark.executor.cores", "4")`.
- The actual executor pods run at 4 cores / 8g+overhead each ≈ 8 cores / ~17.6Gi total.

Kueue's quota accounting silently diverges from actual usage, the ClusterQueue over-commits, and later Workloads may be admitted against headroom that does not exist — the resources their admission promised are not there. There is no Event, Workload condition, or metric that flags the mismatch. The driver pod is unaffected (it is created before user code runs), but executor pod requests and executor count are not.

The same gap exists for PodSet *count*: `spark.executor.instances` or `spark.dynamicAllocation.*` set in the jar changes how many executor pods start, while the PodSet count was fixed at admission.


**What you expected to happen**:

Admission and quota accounting should not silently diverge from actual usage. At minimum I would expect some signal (Event / Workload condition / metric) when pods belonging to a Workload consume more than the admitted PodSets reserved, and ideally a documented integration contract that PodSets must match actual pod resources, plus guidance on what Kueue does (or should do) when they don't.


**How to reproduce it (as minimally and precisely as possible)**:

1. Install apache/spark-kubernetes-operator 1.1.0 (also reproduces on `main`) with `spark.kubernetes.operator.kueue.enabled`, and Kueue v0.20.0+ with a LocalQueue/ClusterQueue having finite `cpu`/`memory` quota.
2. Submit the SparkApplication below. Its jar's main class calls `new SparkConf().set("spark.executor.memory", "8g").set("spark.executor.cores", "4")`, while the spec declares 1 core / 1g per executor.
3. `kubectl describe workload` shows the executor PodSet reserving 2 × (1 core, 1408Mi), while the executor pods actually report 4 cores / 8g+overhead per pod.

```yaml
apiVersion: spark.apache.org/v1
kind: SparkApplication
metadata:
  name: code-overrides-resources
  labels:
    kueue.x-k8s.io/queue-name: spark-queue
spec:
  mainClass: "org.example.Main"
  jars: "local:///opt/spark/examples/jars/example.jar"
  sparkConf:
    spark.executor.instances: "2"
    spark.executor.memory: "1g"
    spark.executor.cores: "1"
  runtimeVersions:
    sparkVersion: "4.3.0"
```


**Anything else we need to know?**:

- This is cross-posted from apache/spark-kubernetes-operator#1000, which tracks the integration-side root cause: `KueueWorkloadFactory` builds PodSets from `spec.sparkConf` (mirroring Spark's resource formulas — memory + overhead factors + off-heap + PySpark memory, `request.cores` / `cores`, `spark.<role>.resource.*`) but only from the submitted config, so `SparkConf#set` in the jar is never accounted for. The class of problem is general: any workload type whose runtime can request more than the submission manifest declares can silently under-reserve quota.

- Config-source summary from the upstream issue:

  | Config source | Accounted in PodSet? | Applied to executors? |
  |---|---|---|
  | `spec.sparkConf` | yes | only if code doesn't override it |
  | Pod template in `spec.driverSpec`/`spec.executorSpec` | yes | merged, but Spark overwrites container resources with conf values |
  | `SparkConf#set` in the jar | no | wins over both |
  | `spark.executor.instances` / `spark.dynamicAllocation.*` in the jar | no | changes pod count |

- Other unaccountable cases are already handled explicitly by the operator: pod template files fail with `SchedulingFailure`, and dynamic allocation reserves `spark.dynamicAllocation.maxExecutors` via the `spark.operator/kueue-reserve-max-executors` annotation (SPARK-60225). Code-overridden resource configs are neither detected nor documented.

- Open questions for discussion:
  1. Should the integration contract require PodSets to equal actual pod usage (and be documented as such)?
  2. Can Kueue detect Workload-tracked pods whose requests exceed the admitted PodSets and surface an Event / condition / metric?
  3. Should such mismatches be enforced (re-quota, eviction, preemption) or advisory-only?
