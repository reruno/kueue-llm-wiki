## Description

**What happened**:

With the partial scale-up strategy, changing an elastic job's replica count before its initial Workload is admitted leaves the Workload's `minCount` out of sync with `count`.

- Scale-down below `minCount` fails Workload validation with "minCount should be less or equal to count". Reconciliation retries and the job remains suspended.
- Scale-up retains the old `minCount`, so the initial Workload can be admitted partially.

This affects batch/Job and RayCluster, RayJob and RayService. PR #19250 applies the same initial floor to SparkApplication.

**What you expected to happen**:

Keep the initial Workload's `minCount` equal to the updated target in both directions. The update must pass API validation, and initial admission must remain all-or-nothing. Preserve partial scale-up for later slices.

**How to reproduce it (as minimally and precisely as possible)**:

1. Use the partial scale-up strategy and block initial admission of an elastic batch/Job requesting 8 replicas.
2. Reduce the requested count to 2. The Workload update is rejected; the stored count and minimum remain 8.
3. Separately, increase a blocked initial target from 3 to 5 while quota fits only 3. The old minimum can allow partial admission.

**Anything else we need to know?**:

Update the shared count-update path in `pkg/workloadslicing/manager.go` and `pkg/workload/podsetscounts.go` as needed. Add regression coverage for both directions, including API validation and all-or-nothing admission, across the affected integrations.

Context for the wider scope: the same root cause also shows up after an **eviction**, not only before the first admission.

**Repro** (SparkApplication, partial scale-up, dynamic allocation min=1 / initial=3 / max=3; 2 CPU queue, 500m per pod):
1. The first slice is admitted all-or-nothing: driver + 3 executors, `count=3`, `minCount=3`.
2. Spark releases idle executors down to 1. Kueue shrinks the slice to `count=1` and lowers `minCount` to 1 (#19249, as intended).
3. A higher-priority Job preempts the whole app. With no driver, the count goes back to the initial target ([sparkapplication_controller.go#L514](https://github.com/kubernetes-sigs/kueue/blob/8e50a8c365495a12a897c12f1624b5a8b8885e69/pkg/controller/jobs/sparkapplication/sparkapplication_controller.go#L514)), so the requeued slice becomes `count=3` while `minCount` stays 1.
4. When 1 CPU frees up, the slice is admitted with driver + 1 executor.
5. Kueue creates a scale-up probe for the missing 2 executors and picks the pending probe as the current slice, so the app stays `suspend=true`. It holds 1 CPU until the probe fits in full, which may never happen.

Same end state as #19046, but nothing has to be pending at eviction time: an idle scale-down followed by preemption is enough.

**Other integrations:** RayJob/RayService with autoscaling should behave the same way (not reproduced yet), because their count falls back to the spec once the child RayCluster is deleted on suspend. Batch Job and RayCluster keep their scaled-down count across eviction, but hit the same thing if the count is raised while the slice is pending.

**Intended approach:** key the fix on the slice's state, not on "initial slice". When the job's only active slice holds no quota reservation, it takes the job's `MinCount`. That covers a never-admitted slice and an evicted, requeued one. A pending probe always has its admitted predecessor active next to it, so it keeps the lowered floor from #19249. The check needs to come before the `EqualTo` early return in [manager.go#L98](https://github.com/kubernetes-sigs/kueue/blob/8e50a8c365495a12a897c12f1624b5a8b8885e69/pkg/workloadslicing/manager.go#L98): a slice whose count didn't change can still carry a stale `minCount`.

Whether re-admission after eviction should be all-or-nothing at all is still open in #18995 (https://github.com/kubernetes-sigs/kueue/issues/18995#issuecomment-6971674645). This follows the current rule that a slice without quota is admitted whole.
