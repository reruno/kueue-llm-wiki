## Description

<!-- Please only use this template for submitting enhancement requests -->

**What would you like to be added**:

A metric that breaks down the time a Workload waits in the queue (from creation or requeue until admission) by reason. Operators could then answer: "Why did this workload wait, and was it waiting on the user's quota or on the system?"

Kueue already exposes `quota_reserved_wait_time_seconds` and `admission_wait_time_seconds`. These show *how long* a Workload waited in the queue but not *why*.

Proposal (names are tentative):

`kueue_workload_wait_time_seconds{cluster_queue, priority_class, reason}` (histogram)

For each completed queueing episode (creation or latest `Requeued=True` → `Admitted=True`), the scheduler attributes elapsed time to one reason per scheduling attempt. A few reasons I had in mind:
  - `UserOverQuota`: the request exceeds the available logical quota of the queue/cohort. This wait is expected and caused by the user.
  - `SystemPreemption`: Kueue has issued preemptions and is waiting for the targets to release quota.
  - `SystemTASContention`: logical quota fits, but TAS fits only after existing TAS reservations are removed (fragmentation).
  - `SystemTASBlocked`: logical quota fits, but TAS can't place the Workload even after removing TAS reservations (unhealthy nodes, etc.).
  - `SystemProcessing`: the Workload is at the queue head and Kueue is processing it - mainly the time of executing scheduling loop.
  - `Unaccounted`: elapsed time with no more specific safe attribution. This keeps the sum of all reasons equal to the total wait and provides expandability. It supports more conservative approach where we have low confidence on the reason of waiting. 

**Why is this needed**:

- On busy clusters (especially with TAS and large multi-node Workloads), "why is my job still pending?" is very common question. Existing histograms can't tell whether the wait was caused by the user's quota, Kueue preemption latency, topology fragmentation or contention, or Kueue's own processing time. Today this has to be reconstructed from logs and condition timestamps for each Workload.
- Separating user-caused wait (`UserOverQuota`) from system-caused wait (`System*`) enables SLOs on what the platform controls. Without it, quota-limited tenants skew the latency numbers.
- Related: #12997 and #18238 (OpenTelemetry tracing of where a Workload spends time), #10124 (pending age and preemption latency). Tracing is useful for debugging individual Workloads. This metric complements it with a cheap, always-on aggregate suitable for dashboards and alerts.
