## Description

**What happened**:

`make -k verify` failed on my machine in `verify-image-build-test`:

```text
FAIL: test_failed_build_stops_remaining_images_and_removes_builder (__main__.ImageBuildTest.test_failed_build_stops_remaining_images_and_removes_builder)
  File "hack/testing/image-build_test.py", line 155, in test_failed_build_stops_remaining_images_and_removes_builder
    self.assertEqual(len(commands), 4)
AssertionError: 8 != 4
Ran 7 tests in 18.637s
FAILED (failures=1)
```

The test fails when the make that runs it has `-k`. `build_images()` in `hack/testing/image-build_test.py` passes `os.environ` unchanged to the nested `make`:

```python
env = {**os.environ, "IMAGE_TEST_LOG": str(log), "IMAGE_TEST_FAIL": fail,
       "IMAGE_TEST_LOCK": str(directory / "build.lock")}
```

The parent make puts `k` in the `MAKEFLAGS` that it exports to the recipe. The nested `make image-presubmit` reads it, and so does the `$(MAKE) -j1 ... image-build importer-image kueueviz-image ...` sub-make in the `image-presubmit` recipe. After the injected importer build failure, that sub-make keeps going and builds the remaining images. The stub `docker` then records 8 commands (1 `buildx create`, 6 `buildx build`, and 1 `buildx rm`) instead of 4.

**What you expected to happen**:

`verify-image-build-test` gives the same result whatever flags and variables the calling make has. `make -k verify` and `make verify` agree on this check.

**How to reproduce it (as minimally and precisely as possible)**:

On main at `8654453a8`, with no Docker daemon:

```sh
make verify-image-build-test       # Ran 7 tests, OK
make -k verify-image-build-test    # AssertionError: 8 != 4
```

The same failure without a parent make:

```sh
MAKEFLAGS=k python3 -I hack/testing/image-build_test.py
```
