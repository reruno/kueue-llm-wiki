## Description

<!-- Please only use this template for submitting enhancement requests -->

**What would you like to be added**:

Allow AdmissionChecks other than the built-in ProvisioningRequest check to delay Topology Aware Scheduling (TAS) assignment until after admission checks are Ready.

Today the first scheduling pass skips the TAS placement only when the ClusterQueue has a ProvisioningRequest check (or MultiKueue) for the flavor. This is hardcoded by controller name:

- [`pkg/cache/scheduler/clusterqueue.go`](https://github.com/kubernetes-sigs/kueue/blob/8654453a8c0c574229d307db7bd6db034bb9c113/pkg/cache/scheduler/clusterqueue.go#L511): `if ac.Controller == kueue.ProvisioningRequestControllerName`
- [`pkg/scheduler/flavorassigner/tas_flavorassigner.go`](https://github.com/kubernetes-sigs/kueue/blob/8654453a8c0c574229d307db7bd6db034bb9c113/pkg/scheduler/flavorassigner/tas_flavorassigner.go#L105): `cq.HasProvRequestAdmissionCheck(*tasFlvr)`

The second pass ([`NeedsSecondPass`](https://github.com/kubernetes-sigs/kueue/blob/8654453a8c0c574229d307db7bd6db034bb9c113/pkg/workload/workload.go)) already works for any check: it runs when all checks are Ready and a PodSet has `DelayedTopologyRequest=Pending`. Only the first-pass decision needs to be generalized.

**Why is this needed**:

Admission checks that provision capacity cannot work with topology aware scheduling flavors when no suitable nodes exist yet, for example on scale-from-zero:

1. The scheduler does not delay the placement, so it tries to place the PodSets on existing Ready nodes during quota reservation (flavorassigner.go).
2. With no suitable nodes, even after simulating preemption of all workloads, the result is NoFit with reason TopologyPlacementFailed, and the scheduler skips the workload without reserving quota.
3. The check controller does nothing, because it needs a quota reservation (status.admission) to know the flavor and the count.
4. The Job stays suspended, so there are no pending Pods for the autoscaler either.

Nothing requests capacity, and the workload stays pending until unrelated nodes appear. When suitable nodes exist but are in use, Kueue can preempt workloads instead of provisioning capacity.

This stops us from creating a custom AdmissionCheck that performs a similar function to how the ProvisioningRequest one works today.

**Completion requirements**:

- Generalize the first-pass TAS delay from the hardcoded controller name to an opt-in, keeping the current default for ProvisioningRequest.
- Integration test: an external admission check provisions Ready nodes for a topology aware scheduling flavor that starts with zero nodes, becomes Ready, and the workload is admitted with a topology assignment.
- Documentation for TAS and for writing admission check controllers.

This enhancement requires the following artifacts:

### Comment by [@OliverMKing](https://github.com/OliverMKing) — 2026-11-23T21:34:38Z

I found two potential options for this.

1. Adding a field to the AdmissionCheck custom resource where the topology assignment would be defined
```yaml
apiVersion: kueue.x-k8s.io/v1beta2
kind: AdmissionCheck
metadata: {name: nap-capacity}
spec:
  controllerName: example.com/my-provisioner
  topologyAssignment: AfterAdmissionChecks 
```

2. Adding a field to the Kueue configuration for controllers that delay the assignment
```yaml
apiVersion: config.kueue.x-k8s.io/v1beta2
kind: Configuration
topologyAwareScheduling:
  delayAssignmentForAdmissionCheckControllers:
  - kueue.x-k8s.io/provisioning-request   # default
  - kueue.x-k8s.io/capacity-buffer        # default
  - example.com/my-provisioner
```

### Comment by [@mimowo](https://github.com/mimowo) — 2026-11-23T21:47:05Z

I think for CapacityBuffer I would probably hardcode it as we did for ProvisioningRequests - it doesn't make sense to run TAS before ProvReq completes, same for CapacityBuffers. 

For external controllers I think the `AdmissionCheck` option is more interesting (1), because conceptually speaking this is property of an admission check. I'm wondering if we need to defer TAS after all admission checks, or rather just after the last one which requires deferring. So the field would rather be `topologyAssignmentMode: Delayed`. There `Delayed` means delay after this AC. If multiple ACs delay, then we would delay after the last one. Then, we can assume implicitly that if `topologyAssignmentMode` is unspecified for ProvReq and CapBuffers, then it is "Delayed".

### Comment by [@blanquicet](https://github.com/blanquicet) — 2026-11-24T00:31:08Z

> I'm wondering if we need to defer TAS after all admission checks, or rather just after the last one which requires deferring.

I can only imagine cases where one wants to delay the TAS. So, I'd say we should defer TAS after all ACs. But, do you know of any users with ACs that need TAS to run before their checks are Ready?

BTW, requiring custom ACs to set `topologyAssignmentMode: Delayed`, but making it the default for ProvReq and CapacityBuffers, feels confusing to me. In fact, when I read about custom AC documentation, I was expecting them to work as ProvReq does, meaning delaying TAS. Only after trying it we discovered that this behavior was hardcoded for ProvReq.
