## Description

## What happened?

Changing `ProvisioningRequestConfig.spec.podSetMergePolicy` does not cause a **pending** ProvisioningRequest to be reconciled to the newly requested PodSet layout.

The controller honors this policy when constructing a *new* ProvisioningRequest, but two independent paths ignore it during updates:

1. `prcHandler.Update` only enqueues the config's dependent Workloads when `provisioningClassName`, `parameters`, or `managedResources` change. Updating **only** `podSetMergePolicy` does not enqueue them.
2. Even when a dependent Workload happens to be reconciled for another reason, `activeOrLastPRForChecks` reuses the previous request because `provReqSyncedWithConfig` compares its provisioning class and parameters, **not the PodSet grouping that the current policy would generate**.

Consequently, if an operator adds a merge policy to make a pending request compatible with an autoscaler requiring a single PodSet, that policy change has no effect on the already-created ProvisioningRequest. The AdmissionCheck can remain Pending with an obsolete request shape.

**Scope:** The code-path inconsistency is verified against upstream `main` at [988b8464d5aa](https://github.com/kubernetes-sigs/kueue/commit/988b8464d5aa87717b566be61e21399c89908340) (24 November 2026 UTC). This is a **source-level finding**; a new regression test and live-cluster reproduction have **not yet been run**.

## How to reproduce it

Reproduction can be added in the existing provisioning-controller envtest integration suite; a real autoscaler response is not needed to observe the stale pending request.

1. Configure the ProvisioningRequest admission-check controller and an `AdmissionCheck` pointing at a `ProvisioningRequestConfig` called `example-config`. Start with `spec.podSetMergePolicy` **unset** and a valid `provisioningClassName`.
2. Create a Workload with quota reserved and two PodSets, `head` and `worker`, each with `count: 1`. Make their **effective PodTemplates identical**: same container resources and scheduling fields, and assignments to the same ResourceFlavor. Keep the AdmissionCheck Pending (do not mark the ProvisioningRequest Provisioned).
3. Wait until the provisioning controller creates the first ProvisioningRequest. Its `spec.podSets` contains two entries, one for each Workload PodSet.
4. Change **only** the merge policy:

   ```bash
   kubectl patch provisioningrequestconfigs.kueue.x-k8s.io example-config \
     --type=merge \
     -p '{"spec":{"podSetMergePolicy":"IdenticalPodTemplates"}}'
   ```

5. Read the existing ProvisioningRequest again. It retains two entries. No replacement request with one merged PodSet is created by this policy-only update.
6. Force an unrelated Workload reconcile without changing its admission-check name, provisioning class, or config parameters. The old request continues to be treated as synchronized.

A simplified comparison (using the **underlying Workload PodSet names**, not literal `ProvisioningRequest.spec.podSets[].name` fields):

```text
Initial policy (nil):  head: 1 pod, worker: 1 pod  -> PR with 2 PodSet entries
Updated policy:       IdenticalPodTemplates
Expected:             head: 2 pods             -> PR with 1 merged PodSet entry
Actual:               head: 1, worker: 1       -> original PR with 2 entries remains
```

This can also be reproduced in reverse: begin with `IdenticalPodTemplates` and then remove it. The pending request remains merged instead of reverting to two entries.

## What did you expect to happen?

When `podSetMergePolicy` changes while a Workload's provisioning check is still Pending, Kueue should re-evaluate that Workload's desired ProvisioningRequest layout. If the layout differs, the controller should converge to the correct request using its established safe deletion/recreation lifecycle. Unrelated spec changes should not be required.

A request already Ready/admitted, or associated with an active/live booking, requires deliberate safety handling; **this issue does not propose deleting active bookings indiscriminately**. If the intended contract is that this policy affects only requests created *after* a config update, it should be stated explicitly in the API/docs, because other config updates already invalidate pending requests.

## Root cause / code walk-through

### 1. The `ProvisioningRequestConfig` watch misses policy-only updates

[`pkg/controller/admissionchecks/provisioning/controller.go:983–1001`](https://github.com/kubernetes-sigs/kueue/blob/988b8464d5aa87717b566be61e21399c89908340/pkg/controller/admissionchecks/provisioning/controller.go#L983-L1001):

```go
func (p *prcHandler) Update(ctx context.Context, event event.UpdateEvent, q workqueue.TypedRateLimitingInterface[reconcile.Request]) {
    // ... oldPRC and newPRC type checks ...
    if oldPRC.Spec.ProvisioningClassName != newPRC.Spec.ProvisioningClassName ||
        !maps.Equal(oldPRC.Spec.Parameters, newPRC.Spec.Parameters) ||
        !slices.CmpNoOrder(oldPRC.Spec.ManagedResources, newPRC.Spec.ManagedResources) {
        // enqueue dependent AdmissionChecks / Workloads
    }
}
```

`PodSetMergePolicy` is not included. The [watch wiring](https://github.com/kubernetes-sigs/kueue/blob/988b8464d5aa87717b566be61e21399c89908340/pkg/controller/admissionchecks/provisioning/controller.go#L1035-L1070) uses this handler for both the provisioning Workload controller and the provisioning AdmissionCheck controller, so a policy-only change is not propagated to either controller by the PRC event.

### 2. An unrelated reconciliation still reuses the stale request

[`activeOrLastPRForChecks` at `controller.go:213–244`](https://github.com/kubernetes-sigs/kueue/blob/988b8464d5aa87717b566be61e21399c89908340/pkg/controller/admissionchecks/provisioning/controller.go#L213-L244):

```go
if matchesWorkloadAndCheck(req, wl.Name, checkName) {
    if reqNeeded && provReqSyncedWithConfig(req, prc) {
        // Keep the existing ProvisioningRequest.
    }
}
```

[`provReqSyncedWithConfig` at `provisioning.go:119–131`](https://github.com/kubernetes-sigs/kueue/blob/988b8464d5aa87717b566be61e21399c89908340/pkg/controller/admissionchecks/provisioning/provisioning.go#L119-L131) compares provisioning class and config parameters. It does not compare the existing request's `spec.podSets` to the output of the *current* merge policy.

Therefore adding an event notification alone is insufficient: the next reconcile still selects the old request as current.

### 3. Creation uses the policy, proving the config is behaviorally relevant

[`mergePodSets` at `controller.go:1119–1153`](https://github.com/kubernetes-sigs/kueue/blob/988b8464d5aa87717b566be61e21399c89908340/pkg/controller/admissionchecks/provisioning/controller.go#L1119-L1153) checks `prcSpec.PodSetMergePolicy` and returns the original list if nil. Otherwise it compares effective PodTemplates and combines compatible PodSets. [`syncOwnedProvisionRequest`](https://github.com/kubernetes-sigs/kueue/blob/988b8464d5aa87717b566be61e21399c89908340/pkg/controller/admissionchecks/provisioning/controller.go#L306-L405) calls that logic while creating a ProvisioningRequest, but not when deciding whether an existing request can be reused.

The [v1beta2 API field](https://github.com/kubernetes-sigs/kueue/blob/988b8464d5aa87717b566be61e21399c89908340/apis/kueue/v1beta2/provisioningrequestconfig_types.go#L87-L95) is exposed as optional and declares both merging strategies; there is no field-level immutability validation in this definition.

## Why is this a bug?

- **Configuration convergence:** A pending resource no longer reflects the current desired configuration, even though the changed field directly determines the resource's structural layout.
- **Operational recovery:** An administrator cannot correct a pending request's PodSet shape by updating the documented configuration field alone. This matters for provisioning integrations with PodSet-count constraints.
- **Silent failure:** The AdmissionCheck may remain Pending while its referenced config appears correct. Nothing explicitly reports that the request was built using a previous policy.
- **Nontrivial root cause:** Fixing either update notification or request synchronization by itself does not restore convergence; both must be addressed.

## Suggested fix (subject to maintainer guidance)

### A. Treat policy changes as relevant config updates

In `prcHandler.Update`, extend the change check using semantic equality (the file already imports `k8s.io/apimachinery/pkg/api/equality`):

```go
!equality.Semantic.DeepEqual(
    oldPRC.Spec.PodSetMergePolicy,
    newPRC.Spec.PodSetMergePolicy,
)
```

This covers nil ↔ non-nil and changes between the two supported strategies. It should not enqueue on metadata-only edits.

### B. Compare the expected merged layout before retaining a pending request

The existing `activeOrLastPRForChecks` returns an error, so it can propagate failures from `c.mergePodSets(ctx, wl, &prc.Spec)` instead of treating a transient ResourceFlavor lookup failure as evidence that the old request is stale.

For an eligible **pending** check, compute the desired merged PodSet projection once per check (not for each candidate attempt) and compare it to the current request. At minimum compare:

- Number of `ProvisioningRequest.spec.podSets` entries.
- Each entry's `count`.
- Each `podTemplateRef.name`, derived using the existing deterministic `getProvisioningRequestPodTemplateName(req.Name, mergedPodSet.Name)` helper.

Conceptual comparison of the *already computed* desired projection:

```go
func desiredPodSetsMatch(
    req *autoscaling.ProvisioningRequest,
    desired []MergedPodSet,
) bool {
    if len(req.Spec.PodSets) != len(desired) {
        return false
    }
    for i := range desired {
        got := req.Spec.PodSets[i]
        want := desired[i]
        if got.Count != want.Count ||
            got.PodTemplateRef.Name != getProvisioningRequestPodTemplateName(req.Name, want.Name) {
            return false
        }
    }
    return true
}
```

This is a **proposed helper, not a tested patch**. Its call site must restrict stale-request replacement to safe pending states and preserve the existing behavior of Ready/admitted requests, ProvisioningRequest retries, and elastic WorkloadSlice bookings. If grouping is unchanged, avoid recreating an equivalent request.

The current lifecycle already deletes unselected requests and builds a new one. Reuse that path rather than mutating immutable `ProvisioningRequest.spec` fields in place. Account for deterministic request-name reuse and informer/cache propagation between deletion and recreation.

### C. Add targeted regression coverage

| Test | Assertion |
| --- | --- |
| Policy nil → `IdenticalPodTemplates`, two identical effective PodSets, request Pending | Dependent Workload is enqueued; old two-entry request converges to one merged entry with total count 2 |
| Policy `IdenticalPodTemplates` → nil, request Pending | Existing merged request converges to two unmerged entries |
| Policy changes but effective grouping is unchanged | No unnecessary request replacement |
| Config metadata-only change | No dependent Workload enqueue |
| Existing provisioning class/parameter update | Previous behavior remains unchanged |
| ResourceFlavor read fails while computing the desired grouping | Reconciliation retries; no destructive cleanup based on an incomplete comparison |
| Request Ready or Workload admitted | No regression in live-booking retention |
| Elastic WorkloadSlice with admitted predecessor | No unexpected deletion or duplicate capacity booking |

## Related work / duplicate check

I searched upstream issues/PRs using `podSetMergePolicy`, `ProvisioningRequestConfig`, stale PodSets, and config updates. I did not find a report of **policy-only updates being ignored, with the obsolete request surviving later reconciliation**.

Related but distinct work:
- [PR #18627](https://github.com/kubernetes-sigs/kueue/pull/18627) — correct container requests/limits comparison *during* PodSet merging.
- [PR #16834](https://github.com/kubernetes-sigs/kueue/pull/16834) — prevent merging PodSets assigned to different flavors.
- [PR #14408](https://github.com/kubernetes-sigs/kueue/pull/14408) — propagate PodSet updates to all members of a merged group.
- [PR #14416](https://github.com/kubernetes-sigs/kueue/pull/14416) — compare provisioning class/parameters to prevent stale parameters and recreation loops. This issue concerns the separate PodSet **shape** computed under the current merge policy; a fix should compose with that PR.

**Question for maintainers:** Is `podSetMergePolicy` intended to affect pending existing requests, like other relevant config changes, or explicitly *only* new requests? If the latter, can we document that contract? Otherwise the two reconciliation gaps above appear to be a concrete convergence bug.
