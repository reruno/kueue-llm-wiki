## Description

## What happened?

A pending Workload that was evaluated as **NoFit** can remain in its ClusterQueue's `inadmissible` set after its referenced `RuntimeClass` changes in a way that makes the Workload schedulable. Kueue refreshes the effective resource requests on the RuntimeClass event, but the queue's decision to retry an inadmissible Workload considers changes to the Workload API object (and DRA-specific requests), **not changes to effective scheduling inputs derived from another Kubernetes object**.

This creates a liveness gap for non-DRA Workloads: an operator can **reduce RuntimeClass Pod overhead below the available quota**, yet the Workload does not re-enter the active scheduling heap. An unrelated ClusterQueue/cohort event may eventually wake it, but the RuntimeClass event that actually made admission possible does not.

There is a related accounting symptom: the same in-place inadmissible update can replace `TotalRequests` without updating the aggregate pending-resource counters.

## What did you expect to happen?

When a relevant `RuntimeClass` creation, update, or deletion changes a pending Workload's *effective* scheduling shape:

- A previously NoFit Workload should be retried when its new effective requirements may fit, even if `Workload.spec`, `metadata.generation`, and status conditions are identical.
- Backoff and explicit `Requeued=False` must still be respected.
- Workloads with unchanged effective requirements should not be unnecessarily rescheduled on metadata-only events or informer resyncs.
- Pending-resource aggregates should agree with the requests of their active and inadmissible entries.

## Minimal reproduction

Assume one available RuntimeClass handler, an active ClusterQueue, no other quota consumers or capacity blockers, and no AdmissionChecks that independently hold the Workload.

1. Create a `RuntimeClass` named `test-runtime` with `overhead.podFixed.cpu: 1500m` and a valid handler.
2. Create a ClusterQueue with **2 CPU** nominal quota and a LocalQueue pointing at it.
3. Submit a Kueue-managed Job referencing `test-runtime`, with one Pod whose container requests **1 CPU**. Its effective request is **2.5 CPU**; after a scheduling attempt the Workload becomes NoFit and enters `inadmissible`.
4. Update *only* the RuntimeClass's `overhead.podFixed.cpu` to `100m`. The effective request becomes **1.1 CPU**, which fits the original quota. Do not modify the Workload or the queue.
5. Observe `status.admission`, the queue's active/inadmissible state, and any subsequent admission attempt.

**Expected:** the RuntimeClass event causes the Workload to be retried; quota reservation is now possible.

**Code-predicted current behavior:** Kueue builds a fresh `Info` with the lower effective requests, but `ClusterQueue.PushOrUpdate` replaces the existing *inadmissible* entry instead of moving it to the active heap. It remains pending until another retry trigger occurs.

## Root cause (upstream `main`, commit `4703250c7bb8b72172365aa1bcaf91481ac81468`)

### 1. RuntimeClass events refresh pending Workload Infos but do not explicitly retry inadmissible ClusterQueues

[`resourceUpdatesHandler.Create/Update/Delete`](https://github.com/kubernetes-sigs/kueue/blob/4703250c7bb8b72172365aa1bcaf91481ac81468/pkg/controller/core/workload_controller.go#L2039-L2070) dispatch both `LimitRange` and `RuntimeClass` events through `handle`. The extra `notifyForLimitRangeSchedulingChange` invocation exists only for LimitRanges.

[`resourceUpdatesHandler.handle` and `queueReconcileForPending`](https://github.com/kubernetes-sigs/kueue/blob/4703250c7bb8b72172365aa1bcaf91481ac81468/pkg/controller/core/workload_controller.go#L2151-L2200) select pending Workloads using `WorkloadRuntimeClassKey`. For a non-DRA Workload the handler calls `queues.AddOrUpdateWorkload`.

By contrast, [`retryInadmissibleForNamespace`](https://github.com/kubernetes-sigs/kueue/blob/4703250c7bb8b72172365aa1bcaf91481ac81468/pkg/controller/core/workload_controller.go#L2127-L2149) invokes `qcache.NotifyRetryInadmissible` for affected ClusterQueues when a scheduling-relevant LimitRange changes. There is no analogous RuntimeClass notification path.

### 2. Effective requests change, but the API Workload does not

[`Manager.AddOrUpdateWorkloadWithoutLock`](https://github.com/kubernetes-sigs/kueue/blob/4703250c7bb8b72172365aa1bcaf91481ac81468/pkg/cache/queue/manager.go#L722-L775) constructs a fresh Info through `workload.NewInfoFromClient` and then calls `cq.PushOrUpdate`.

[`ResolveAdjustmentInputs`](https://github.com/kubernetes-sigs/kueue/blob/4703250c7bb8b72172365aa1bcaf91481ac81468/pkg/workload/effective_resources.go#L35-L114) reads `RuntimeClass.overhead.podFixed`, and [`UpdateFromClient`](https://github.com/kubernetes-sigs/kueue/blob/4703250c7bb8b72172365aa1bcaf91481ac81468/pkg/workload/effective_resources.go#L175-L194) recomputes effective PodSpecs, total requests and scheduling hash even when the Workload resource version has not changed. This is intentional and necessary.

### 3. `ClusterQueue.PushOrUpdate` treats the recomputed Info as unchanged

In [`pkg/cache/queue/cluster_queue.go`](https://github.com/kubernetes-sigs/kueue/blob/4703250c7bb8b72172365aa1bcaf91481ac81468/pkg/cache/queue/cluster_queue.go#L386-L445), the branch for an existing inadmissible Workload:

```go
specChangedSinceEval := oldInfo.LastEvaluatedGeneration != 0 &&
    wInfo.Obj.Generation != oldInfo.LastEvaluatedGeneration

if !specChangedSinceEval &&
    equality.Semantic.DeepEqual(oldInfo.Obj.Spec, wInfo.Obj.Spec) &&
    // ... unchanged Workload status fields ...
    !draRequestsChanged(oldInfo, wInfo) {
    c.workloads.UpdateInadmissible(key, oldInfo, wInfo)
    return
}
```

The condition does not compare `oldInfo.TotalRequests`, `oldInfo.EffectivePodSpecs`, or the non-DRA effective scheduling shape. The `draRequestsChanged` helper is explicitly DRA-gated and returns false for a normal RuntimeClass/LimitRange-only resource adjustment.

Consequently, the new Info stays in `inadmissible` instead of reaching the existing active/backoff/shape-hash path. The `RuntimeClass` event does not by itself change the Workload spec or generation, so those checks cannot catch it.

### 4. In-place replacement can also leave pending-resource totals stale

[`PendingWorkloads.UpdateInadmissible`](https://github.com/kubernetes-sigs/kueue/blob/4703250c7bb8b72172365aa1bcaf91481ac81468/pkg/cache/queue/pending_workloads.go#L249-L271) swaps the entry and updates trackers but does not subtract its old `TotalRequests` and add its new ones. The insertion and removal methods *do* update pending-resource totals. [`updateInadmissible`](https://github.com/kubernetes-sigs/kueue/blob/4703250c7bb8b72172365aa1bcaf91481ac81468/pkg/cache/queue/pending_workloads.go#L510-L525) also only changes maps/trackers. Thus an in-place update after external default changes can leave aggregate pending resources describing the *old* effective request.

## Proposed focused regression test

The following test isolates the queue transition without requiring a live Kubernetes cluster. It models two effective PodSpecs for the same unchanged Workload. Add it to `pkg/cache/queue/cluster_queue_test.go`, which already imports the helpers below. **Source-derived proposed test, not executed.**

```go
func TestPushOrUpdateRetriesInadmissibleAfterEffectiveOverheadChange(t *testing.T) {
    ctx, log := utiltesting.ContextWithLog(t)
    cq := newClusterQueueImpl(ctx, nil, defaultOrdering,
        testingclock.NewFakeClock(time.Now()))

    wl := utiltestingapi.MakeWorkload("runtime-wl", defaultNamespace).
        PodSets(*utiltestingapi.MakePodSet(kueue.DefaultPodSetName, 1).
            Request(corev1.ResourceCPU, "1").Obj()).
        Obj()

    withOverhead := func(overhead string) *workload.Info {
        spec := *wl.Spec.PodSets[0].Template.Spec.DeepCopy()
        spec.Overhead = corev1.ResourceList{
            corev1.ResourceCPU: resource.MustParse(overhead),
        }
        return workload.NewInfo(log, wl.DeepCopy(),
            workload.WithEffectivePodSpecs([]corev1.PodSpec{spec}))
    }

    before := withOverhead("1500m")
    key := workload.Key(before.Obj)
    // Model a previously evaluated NoFit Workload.
    cq.workloads.InsertInadmissible(key, before)

    after := withOverhead("100m")
    // Same Workload API spec and generation; only external inputs changed.
    cq.PushOrUpdate(after)

    active, _ := cq.Dump()
    if len(active) != 1 {
        t.Fatalf("expected retry after effective overhead change; active=%v", active)
    }
    inadmissible, _ := cq.DumpInadmissible()
    if len(inadmissible) != 0 {
        t.Fatalf("expected no inadmissible Workload; got=%v", inadmissible)
    }
}
```

On current `PushOrUpdate`, this is expected to fail because the API Workload specs are identical, neither status nor generation changed, and `draRequestsChanged` returns false. An integration test should additionally mutate a real RuntimeClass and confirm the previously-NoFit Workload is rescheduled.

## Suggested implementation approach

There are two complementary approaches; the smaller/safest change should be chosen with maintainers:

1. **Make `ClusterQueue.PushOrUpdate` aware of relevant effective-input changes.** In addition to Workload API object comparisons, use the effective PodSpecs and normalized total request / assignment-relevant shape to decide when an inadmissible Workload deserves another scheduling attempt. Follow the existing removal, backoff, active-heap and scheduling-hash code paths instead of bypassing them. Do not rely only on `SchedulingHash` when equivalence hashing can be disabled.
2. **Alternatively/additionally, send a targeted inadmissible retry on scheduling-relevant RuntimeClass changes.** Use the existing `WorkloadRuntimeClassKey` index and queue lookup to limit affected ClusterQueues. Preserve behavior for in-flight work, backoff and metadata-only updates; avoid a global retry of every ClusterQueue at each informer event.
3. **Keep aggregate pending resource usage consistent** whenever `UpdateInadmissible` replaces an Info with different `TotalRequests`. Subtract the old and add the new effective requests under the existing lock, while retaining current metric/tracker semantics.

## Regression tests / acceptance criteria

- [ ] Reducing RuntimeClass overhead so a previously NoFit **non-DRA** Workload fits quota causes a new scheduling attempt without changing the Workload API object.
- [ ] Reproduction covers identical `Workload.spec`, generation and status before and after the external input change.
- [ ] Increasing overhead refreshes admission accounting and does not permit under-reservation.
- [ ] RuntimeClass scheduling changes that affect placement but not CPU/memory totals are handled if the fix covers the full effective scheduling shape.
- [ ] `Requeued=False`, backoff, in-flight checkout and `StrictFIFO` semantics stay intact.
- [ ] Metadata-only RuntimeClass changes with unchanged effective shapes do not churn inadmissible queues.
- [ ] Aggregate pending resources match current effective requests after an in-place inadmissible update.
- [ ] Existing DRA, LimitRange and scheduling-equivalence tests pass.
