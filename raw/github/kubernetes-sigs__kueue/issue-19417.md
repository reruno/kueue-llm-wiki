## Description

/kind bug
/area integrations
/area tas

**What happened**:

A Kueue-managed LeaderWorkerSet (LWS) can update its Pod template's Topology Aware Scheduling (TAS) request after a group's Workload has reserved quota and while an AdmissionCheck is still Pending. The API accepts the template update, but the Workload keeps the topology request and assignment from the previous template. In the reproduction, the new template requires both Pods on one host, while the old reservation still spans two hosts in the same block.

**What you expected to happen**:

Once a group is eligible to use the new template, Kueue should reevaluate its reservation before admission. If neither host fits both Pods, the replacement Workload should wait for capacity on a single host.

**How to reproduce it (as minimally and precisely as possible)**:

1. Configure a TAS ResourceFlavor with block and hostname levels, a LocalQueue, and a ClusterQueue with at least two CPUs and an AdmissionCheck that can stay Pending. Make two Ready nodes in the same block available to the flavor, with one allocatable CPU on each.
2. Create a managed LWS with one replica, group size two, and one CPU requested per Pod. Set `kueue.x-k8s.io/podset-required-topology` on the worker template to the block level. Use the worker template for both Pods.
3. Wait for the group's Workload to get `QuotaReserved=True` while its AdmissionCheck is Pending. Record the Workload UID and the assigned hosts.
4. Update that annotation on the same LWS to `kubernetes.io/hostname`, leaving the AdmissionCheck Pending. Compare the updated LWS template with `spec.podSets[0].topologyRequest.required` and `status.admission.podSetAssignments[0].topologyAssignment` on the Workload. The Workload retains its UID and the old block-level request and assignment.

**Anything else we need to know?**:

The reproduction reaches the stale reservation while the check is still Pending. This is the LWS follow-up to the StatefulSet report in #19297 and the discussion on #19300. The LWS fix also needs to respect groups that still use the previous template during a partitioned rollout. [Original review](https://github.com/kubernetes-sigs/kueue/pull/19300#pullrequestreview-6029738534)

Proposed fix in https://github.com/kubernetes-sigs/kueue/pull/19418.

**Environment**:

- Kubernetes version: envtest v1.37.0.
- Kueue revision: upstream `4703250c7bb8b72172365aa1bcaf91481ac81468`, with the regression test applied.
- Cloud provider or hardware configuration: two synthetic Ready nodes in one block.
- Others: `TopologyAwareScheduling` enabled. Envtest starts the API server and Kueue components. The test drives the LWS rollout status and partition changes.
