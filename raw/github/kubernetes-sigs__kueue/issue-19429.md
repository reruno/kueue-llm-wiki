**What would you like to be cleaned**:

Convert the remaining slice-based table-driven unit tests to `map[string]struct` tables keyed by test case name, following the same scheme as #19407 (PR #19428):

- Replace `testCases := []struct{ name string; ... }{ {name: "x", ...}, ... }` with `testCases := map[string]struct{ ... }{ "x": {...}, ... }`.
- Replace `for _, tc := range testCases { t.Run(tc.name, ...) }` with `for name, tc := range testCases { t.Run(name, ...) }`.
- Preserve the existing cases and assertions.

Before converting a table, check that its cases do not depend on execution order (for example, shared state mutated across iterations). Map iteration order is random, so such tables must stay slices. For this reason, `pkg/controller/admissionchecks/multikueue/fswatch_test.go` is excluded: its steps share one watcher.

Some tables need extra care:

- `pkg/util/tas/tas_assignment_test.go` ranges over `slices.Concat(bothWaysTestCases, oneWayTestCases)`; merge the maps instead (for example, with `maps.Copy`).
- `pkg/cache/queue/cluster_queue_test.go` and `pkg/scheduler/scheduler_test.go` contain inline tables (`for _, tc := range []struct{...}{...}`).

After all tables are converted, add a lint check that reports slice-based tables (a `[]struct` with a `name` field whose runner calls `t.Run(tc.name, ...)`) in unit tests and asks for a `map[string]struct` table keyed by test case name, so new tests do not reintroduce the pattern. One option is a gocritic `ruleguard` rule in `.golangci.yaml`. Order-dependent tables, such as the steps in `fswatch_test.go`, need an explicit exception.

**Why is this needed**:

This follows the repository's map-based table-driven unit test guidelines ([Writing tests](https://github.com/kubernetes-sigs/kueue/blob/main/site/content/en/community/contribution_guidelines/writing_tests.md)) and makes the remaining tests consistent with the rest of the codebase, where most unit test tables are already maps.

### Comment by [@tenzen-y](https://github.com/tenzen-y) — 2026-11-24T11:42:23Z

Let me describe why we should use a map instead of a slice in a table-driven test for new contributors.
Slice is consistently executed in the same order, which potentially introduces co-dependencies between test cases.

OTOH, a map is not consistently executed, which is in random order. So, map tables allow us to randomize test execution, which helps us make our tests healthy and production code healthy.
