## Description

**What would you like to be added**:

A way to choose how classical preemption orders the candidates of the preemptor's own ClusterQueue that have the same effective priority. Today the order is fixed: most recently admitted first. I would like an opt-in alternative, and I would like to discuss where such an option belongs.

The first use case I have is "smaller workloads first": within a group of equal-priority candidates, evict the one with the smaller dominant share of the ClusterQueue's nominal quota first (the notion fair sharing already uses). Ties keep today's order. It never crosses priority, and candidates from other ClusterQueues (reclaim) and workloads already being evicted keep the default order.

I have a working implementation on v0.20.4 behind an alpha feature gate, so I can show real numbers. I do not think a cluster-wide gate is the right shape for upstream, so this issue is about the shape.

**Why is this needed**:

Within a priority, candidates are ordered newest first with no regard for size, and Kueue stops as soon as the preemptor fits. A small higher-priority workload can therefore evict a large multi-node workload that happens to be the newest, even when smaller candidates of the same priority would free enough room. A priority class per size does not help: workloads of one class range from 1 to 128 GPUs and come from many users, and a class per size inverts priorities.

Setup: a production training cluster with several dozen 8-GPU nodes, TAS with a hostname topology, and a ClusterQueue with `withinClusterQueue: LowerPriority`. A higher-priority workload evicted a large multi-node workload (tens of GPUs) of lower priority while lower-priority workloads of 1 to 2 GPUs were running.

Evidence (production, shadow comparison): with the ordering enabled, I log for every preemption what the default order would have chosen next to what was applied. The default result is computed on the same snapshot and never applied. In a window of about half a day, roughly one in seven preemption events differed. In every one of those, the default order would have evicted a multi-node workload of 32 to 40 GPUs, and the applied order evicted one smaller workload instead. In none of the events did the applied order evict more workloads than the default. Before I enabled it, the same comparison showed the default evicting an 8 to 32 GPU workload where a single 2 GPU workload was enough, several times within a few hours.

Trade-off, stated plainly: evicting smaller workloads first can evict more of them. In an offline replay on a snapshot of the cluster, a request for several 8-GPU pods made the default evict one large workload and the size-first order evict about a dozen workloads of at most 2 GPUs each, for a similar or smaller total number of GPUs. Whether that is better depends on the cost of interrupting a workload, which Kueue does not model.

**Where I think this does and does not fit**:

- **`PreemptionConfig` (KEP-13396) cannot express it today.** Its candidates are appended after the classical and fair sharing candidates ("a configurable candidate is never preferred over a classical/fair sharing candidate"), and the `ordering` field is future work (`FUTURE_WORK.md`), applying to the configurable candidates only. The candidates in question here come from `withinClusterQueue: LowerPriority`, which is the classical path. A list of predefined sorting keys would also need a size key.
- **KEP-83 deferred the neighbouring idea.** Its non-goals include not penalizing long-running workloads of the same priority, and "inform how costly it is to interrupt a workload" was discarded for a later KEP. Size is only a proxy for that cost. The current newest-first rule protects long-running workloads, so a size-first order trades that protection for protecting large ones. I would keep the default unchanged and make this opt-in.
- **Shape options I can see**, and I would like your guidance on which is acceptable:
  1. a new field next to `ClusterQueue.spec.preemption` that selects the order of same-priority candidates (the KEP notes that changing `spec.preemption` is delicate because of its defaulting, so this needs care);
  2. a global option in the Kueue configuration;
  3. extending `PreemptionConfig` so that it can also order or select the classical candidates, together with the `ordering` field from the future work section.

**Questions**:

1. Is configurable ordering of classical candidates in scope at all, or should this wait for `PreemptionConfig` to cover the classical path?
2. If it is in scope, which of the three shapes above do you prefer?
3. Is the dominant share of nominal quota a reasonable "size", or should the user name the resource?

Not proposed here: ordering to free whole topology domains. I have an experimental variant, but I could not show a benefit over the size order, and KEP-13396 lists full defragmentation as a non-goal.

Limits of the evidence: one cluster, a shadow comparison rather than an A/B test, and an implementation on v0.20.4 that has not been rebased on main.
