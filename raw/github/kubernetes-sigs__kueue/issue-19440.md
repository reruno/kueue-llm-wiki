**What happened**:

With PartialPreemption enabled, the scheduler requests a shrink in both of these cases:
- A Workload that has never become ready, which KEP-975 excludes when waitForPodsReady is enabled.
- A worker Workload with the kueue.x-k8s.io/multikueue-origin label.

**What you expected to happen**:

The merged KEP (#14589: Eligibility, and the MultiKueue row under Interactions) says both cases are evicted whole in Alpha.

The readiness exclusion applies only with `waitForPodsReady` enabled and before the Workload first becomes ready. It does not cover a previously ready Workload in `WaitForRecovery`.

**How to reproduce it (as minimally and precisely as possible)**:

Use variants of the scheduler unit test "a victim shrinks only as far as the workload needs" in `TestScheduleForPartialPreemption`:

| Victim | Observed |
|---|---|
| Ready (control) | Shrinks to 2 Pods |
| Never ready: `PodsReady=False`, reason `WaitForStart` | Shrinks to 2 Pods |
| Has the `multikueue-origin` label | Shrinks to 2 Pods |

The result is the same with the cache's PodsReady tracking on and off. Set the readiness condition after the quota reservation, because the test helper replaces existing conditions.

**Anything else we need to know?**:

A MultiKueue worker can receive this combination: `cloneForCreate` keeps the opt-in annotation and `minRetainedCount`, and adds the origin label.
