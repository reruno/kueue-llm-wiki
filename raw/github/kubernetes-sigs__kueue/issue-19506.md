## Description

**What happened**:

- **Background**: to support partial preemption with both fair sharing and classical, #14590 moved candidate selection out of each strategy's iterator and into `getTargets`. Both strategies now reuse their existing candidate filtering, and the preemption plan drives the walk itself. A strategy still decides whether to offer a candidate with its original criteria, which assume the candidate is removed from the snapshot as a whole, while the plan may only shrink it to its `minRetainedCount`.
- **Fair sharing**: `ComputeTargetShareAfterRemoval` computes the target's share assuming a whole removal, so the strategy compares the preemptor's share against a share that a shrink would never produce. When the shrink would be enough, the strategy can still reject the candidate and the search returns no targets.
- **Classical**: `candidateIsValid` looks at the current snapshot and offers a candidate only while its ClusterQueue is still above its nominal quota on the resources to preempt. During the shrink pass the victim keeps its floor, so the usage drops less and the following candidates still appear. During the plain walk a candidate is removed whole, the usage drops more, and the following candidates are filtered out. Since `evictionPass` only evicts victims found by the plain walk ("The plan evicts no other victim"), a victim that only appears under the shrink is never evicted.
- **Examples**: both problems are illustrated below.

**Example 1, fair sharing**

Cohort `all`, total CPU 6, only `LessThanOrEqualToFinalShare` configured.

| Item | Value | Notes |
| --- | --- | --- |
| Cohort `all` | total CPU 6 | contains a, b and c |
| ClusterQueue `a` | nominal 2, usage 0 | the incoming Workload arrives here |
| ClusterQueue `b` | nominal 2, usage 6 | borrows 4 from the cohort |
| ClusterQueue `c` | nominal 2, usage 0 | empty |
| Workload `v` in `b` | usage 6, floor 3 | priority 0 |
| Incoming Workload in `a` | needs 3 CPU | priority 10 |

| Aspect | Current action | Expected action |
| --- | --- | --- |
| Target share after the action | 0, computed after removing `v` whole | 0.167, computed after shrinking `v` to 3 |
| `LessThanOrEqualToFinalShare` | 0.167 <= 0 does not hold, candidate rejected | 0.167 <= 0.167 holds, candidate offered |
| Search result | no targets | shrink `v` to 3 |

**Example 2, classical**

Cohort `all`, total CPU 20.

| Item | Value | Notes |
| --- | --- | --- |
| Cohort `all` | total CPU 20 | contains p, q and s |
| ClusterQueue `p` | nominal 2, usage 0 | the incoming Workload arrives here |
| ClusterQueue `q` | nominal 8, usage 14 | borrows 6 from the cohort |
| ClusterQueue `s` | nominal 10, usage 0 | lends only |
| Workload `a` in `q` | usage 8, floor 4 | priority 0 |
| Workload `b` in `q` | usage 6, floor 6 | priority 0, cannot shrink |
| Incoming Workload in `p` | needs 15 CPU | priority 10 |

| Step | Current action | Expected action |
| --- | --- | --- |
| Shrink pass | offers `a` and `b`, does not fit | records the victims `a` and `b` |
| Plain walk | removes `a` whole, `q` drops to 6, `candidateIsValid` hides `b`, does not fit | keeps walking the recorded victims |
| Eviction | only `a` can be evicted, does not fit | evicts `a` and `b`, fits |
| Fill back | not reached | `b` is not restored, `a` is restored to 4 |
| Result | no targets for 15 to 20 CPU | `a` shrunk to 4 plus `b` evicted |

**What you expected to happen**:

- Fair sharing should judge the candidate by the share the plan will actually produce, that is after the shrink.
- The eviction step should consider the victims the shrink pass already found, not only the ones the plain walk removed.

**How to reproduce it (as minimally and precisely as possible)**:

- Enable `PartialPreemption`.
- Use `reclaimWithinCohort: Any`, `withinClusterQueue: LowerPriority` and `borrowWithinCohort.policy: LowerPriority`.
- For Example 1, also configure only `LessThanOrEqualToFinalShare`.
- Create the cohorts and Workloads described above.
- For Example 2, vary the incoming request from 15 to 20 CPU: all of them return no targets.
- Both reproduce in scheduler unit tests without a cluster; I can share the test cases with the fix.

### Comment by [@zhengchenyu](https://github.com/zhengchenyu) — 2026-11-24T11:50:43Z

The main reason is that the results returned by strategy.candidates do not account for the partial case, which leads to some problems. In our internal version, it is implemented in CandidateIterator, which does not have this issue, but it is indeed hard to maintain.
