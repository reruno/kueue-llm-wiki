## Description

## What happened

In a cluster running Kueue alongside LeaderWorkerSet (LWS), configuring `spec.placementPolicy` on a LeaderWorkerSet (an upcoming LWS field for exclusive topology placement) results in the field being **silently removed** by Kueue's `mleaderworkerset` mutating webhook. The field is dropped without any error or warning, so LWS placement (both `Required` and `Preferred` enforcement) silently stops working.

## What you expected to happen

Kueue's mutating webhook should preserve fields it does not model, or at minimum the `placementPolicy` should survive a round-trip through the webhook so the LWS controller can act on it.

## How to reproduce it

Apply a LeaderWorkerSet with a `placementPolicy`:

```yaml
apiVersion: leaderworkerset.x-k8s.io/v1
kind: LeaderWorkerSet
metadata:
  name: bug-repro
  namespace: default
spec:
  replicas: 2
  placementPolicy:
    type: ExclusiveTopology
    topology: kubernetes.io/hostname
    scope: Own
    enforcement: Preferred
  leaderWorkerTemplate:
    size: 2
    leaderTemplate:
      spec:
        containers:
        - name: leader
          image: busybox:1.36
          command: ["sleep", "infinity"]
    workerTemplate:
      spec:
        containers:
        - name: worker
          image: busybox:1.36
          command: ["sleep", "infinity"]
```

Then observe the field is gone after passing through the webhook:

```bash
# bypasses server-side webhooks -> field preserved
kubectl apply -f repro.yaml --dry-run=client -o json | jq '.spec.placementPolicy'
# -> {"enforcement":"Preferred","scope":"Own","topology":"kubernetes.io/hostname","type":"ExclusiveTopology"}

# goes through the Kueue mutating webhook -> field dropped
kubectl apply -f repro.yaml --dry-run=server -o json | jq '.spec.placementPolicy'
# -> null

# on the persisted object the field is gone
kubectl get lws bug-repro -o jsonpath='{.spec.placementPolicy}'
# -> (empty)
```

## Root cause

Kueue's `mleaderworkerset` mutating webhook is built with `ctrl.NewWebhookManagedBy(mgr, &leaderworkersetv1.LeaderWorkerSet{})`, so the admission request is deserialized into Kueue's vendored `sigs.k8s.io/lws` API struct. `placementPolicy` does not exist in that struct — **even in the latest LWS release v1.0.0** — because the field was only added on LWS `main` (kubernetes-sigs/lws#1165, merged) and has not shipped in any release yet. Kueue defines its own type alias in `pkg/controller/jobs/leaderworkerset/leaderworkerset_controller.go`:

```go
type LeaderWorkerSet leaderworkersetv1.LeaderWorkerSet
```

Because the vendored struct has no `PlacementPolicy` field, Go's `encoding/json` silently discards the unknown `placementPolicy` field during deserialization. When the webhook serializes the object back, the field is permanently gone.

This is the same class of problem as the already-open issue #14849 ("Preserve unmodeled spec fields when MultiKueue SyncJob creates remote jobs"): Kueue loses spec fields it does not explicitly model.

## Anything else we need to know?

- Verified against the current upstream `main` (which vendors `sigs.k8s.io/lws v1.0.0`): the bug is **still reproducible**, because `placementPolicy` exists on LWS `main` (kubernetes-sigs/lws#1165, merged) but not yet in any LWS release, including v1.0.0.
- The failure is silent: no error, no warning, no admission rejection. The user configures placement and it simply never takes effect.
- Impact: in any cluster where Kueue and LWS coexist, LWS exclusive-topology placement (Required and Preferred) is fully disabled.

Proposed directions (for discussion):
1. Bump the vendored `sigs.k8s.io/lws` dependency once a release containing `placementPolicy` ships upstream.
2. More generally, avoid silently dropping unmodeled fields in the LWS webhook path (align with the spirit of #14849).

### Comment by [@zhouyou9505](https://github.com/zhouyou9505) — 2026-11-24T12:04:08Z

Closing this issue — the root cause turned out to be different from the initial report, and it is already resolved on current `main`.

**Actual root cause**: Kueue v0.11.3 (the version I reproduced on) carries this in `go.mod`:

```go
// TODO: Once #4470 is resolved, we should upgrade this.
replace sigs.k8s.io/controller-runtime => sigs.k8s.io/controller-runtime v0.19.4
```

controller-runtime v0.19.4 predates the `dropSchemeRemovals` mechanism (introduced in v0.20.0), which is what preserves fields present in the raw admission JSON but absent from the vendored Go type. So the mutating webhook silently dropped `spec.placementPolicy`.

Current `main` uses controller-runtime v0.25.3 (no replace), so the field is preserved — I verified this locally by running the full `Handle → Decode → Default → patch` path against a raw LWS JSON containing `placementPolicy`: the resulting patch contains only `add` ops and no `remove /spec/placementPolicy`.

So there is nothing to fix here on `main`. Apologies for the noise.
