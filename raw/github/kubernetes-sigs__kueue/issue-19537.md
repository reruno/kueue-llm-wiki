## Description

**What happened**:

With the Pod integration on a MultiKueue manager, the manager Pod (which stays gated and only mirrors the worker Pod's status) never reports a failure when its worker Pod disappears after it started, for example when the worker's node is removed (a spot or preemptible VM eviction, a node deletion, or a force-deleted Pod). Instead, one of two things happens:

1. **Silent re-run.** The worker Workload is garbage collected together with its Pod, or finished as `OwnerNotFound`. The manager resets the admission check to `Retry` ("Admitting remote no longer exists", or the `OwnerNotFound` reset from #14997) and re-dispatches it. Alternatively, `SyncJob` finds no worker Pod and creates it again. Either way, a new worker Pod with the same name runs the job from scratch. The manager Pod's copied status goes from `Running` back to gated `Pending` (since #17420) and then to `Running` again. The Pod's owner never sees a failure.
2. **Left Running.** If the worker Workload is already finished (for example as `Failed`) when the manager reconciles, `SyncJob` finds no worker Pod and creates an orphan one instead of copying a final status. The manager Workload is then finished while the manager Pod keeps its copied `Running` status. The Pod only runs again once the finished Workload is deleted by `objectRetentionPolicies.workloads.afterFinished`.

**What you expected to happen**:

When a worker Pod that already started is lost without a final status, the manager Pod should end up `Failed`, the same way a Pod on a single cluster does when its node goes away (the Pod GC marks it `Failed` with a `DisruptionTarget` condition). The owner can then retry it as a new attempt. The manager Workload should be finished as `Failed`.

Pods that never started on a worker, and Kueue's own evictions on a worker (preemption, deactivation), should keep the current behaviour: the Workload is requeued and re-dispatched, with the manager Pod reset to gated `Pending` (#17420).

**How to reproduce it (as minimally and precisely as possible)**:

1. Set up MultiKueue with the Pod integration enabled on the manager and one worker.
2. On the manager, create a plain Pod (not a Pod group) in a namespace managed by Kueue, with the `kueue.x-k8s.io/queue-name` label.
3. Wait until the worker Pod is `Running` and the manager Pod shows the copied `Running` status.
4. On the worker, run `kubectl delete pod <name> --force --grace-period=0`, or delete the worker Pod's node.
5. Observe that the manager Pod never becomes `Failed`. Within seconds, the admission check goes to `Retry` and the Pod is re-dispatched, or the worker Pod is recreated with the same name.

**Anything else we need to know?**:

The relevant code paths are unchanged on `main` (checked at 9f223b614):

- `syncLocalPodWithRemote` in `pkg/controller/jobs/pod/pod_multikueue_adapter.go` creates the remote Pod whenever it is not found, without considering whether the local Pod already started.
- In `pkg/controller/admissionchecks/multikueue/workload.go`, a missing admitting remote Workload (step 6a) and a remote `OwnerNotFound` finish (step 3, #14997) both reset to `Retry` for re-dispatch.

We fixed this in our fork and have run it on our clusters. The approach:

- Add an optional MultiKueue adapter interface that finishes the local object when it started on a worker and its remote object no longer exists. For single Pods, the manager Pod becomes `Failed` with reason `MultiKueueRemotePodLost` and a `TerminationTarget` condition, the condition Kueue already sets on Pods it stops.
- Only the workload reconciler decides that a remote object was lost. It checks before re-dispatching after a remote `OwnerNotFound`/`OutOfSync` finish, before copying the status of a remote finish, when the admitting remote Workload no longer exists, and during the regular sync while the admission check is `Ready`. `SyncJob` just stops recreating the worker Pod for a manager Pod that already started.
- A manager Pod counts as started when its copied status has a start time, the `Running` phase, or container statuses.

Questions for maintainers:

1. **Default or opt-in?** This changes the re-dispatch behaviour from #14997 for Pods that already started. Should it sit behind a feature gate?
2. **Telling a worker eviction apart from a lost Pod.** A Kueue eviction on the worker also deletes the worker Pod, and the orphaned remote Workload is then finished as `OwnerNotFound` or garbage collected, often before the manager reconciles. Our fork remembers, from the remote Workload watch, which remote Workloads were last seen evicted. That record is in memory, so a manager restart in that window fails a preempted Pod instead of requeuing it. Is there a more durable signal you'd prefer, or is an in-memory record acceptable as a first step?
3. **A worker Pod that succeeded but was removed before its final status was copied.** We mark the manager Pod `Succeeded` when the remote Workload finished as `Succeeded`, so a completed task isn't retried. Is that acceptable, or should it be left to the owner?
4. **Scope.** Our change covers single Pods only. Pod groups and other integrations keep the current behaviour (a worker `batch/v1` Job, for example, replaces its own lost Pods).

Possibly related: #14997 (re-dispatch after a remote `OwnerNotFound` finish), #17420 (reset of the manager Pod status after a requeue).
