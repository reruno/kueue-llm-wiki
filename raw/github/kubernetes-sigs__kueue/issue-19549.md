## Description

**What happened**:

The Kubeflow SparkApplication integration grants the Kueue manager ClusterRole CRUD permissions on `sparkapplications`, but does **not** grant permissions on the `sparkapplications/finalizers` subresource.

On clusters that enable the `OwnerReferencesPermissionEnforcement` admission plugin (for example OpenShift), creating a Workload owned by a SparkApplication with `blockOwnerDeletion: true` fails:

```text
Handling job with no workload
gvk: sparkoperator.k8s.io/v1beta2, Kind=SparkApplication
error: workloads.kueue.x-k8s.io "..." is forbidden: cannot set blockOwnerDeletion if an ownerReference refers to a resource you can't set finalizers on: , <nil>
```

The SparkApplication remains suspended and no Workload is created.

In [`config/components/rbac/role.yaml`](https://github.com/kubernetes-sigs/kueue/blob/main/config/components/rbac/role.yaml) (and the Helm chart RBAC), Spark currently has:

```yaml
- apiGroups:
  - sparkoperator.k8s.io
  resources:
  - sparkapplications
  verbs:
  - delete
  - get
  - list
  - patch
  - update
  - watch
```

There is no corresponding `sparkapplications/finalizers` rule.

Other job integrations already include finalizer subresource RBAC, for example:

- `batch` → `jobs/finalizers`
- `jobset.x-k8s.io` → `jobsets/finalizers`
- `kubeflow.org` → `jaxjobs/finalizers`, `mpijobs/finalizers`, …
- `ray.io` → `rayclusters/finalizers`, `rayjobs/finalizers`, …
- `trainer.kubeflow.org` → `trainjobs/finalizers`
- `workload.codeflare.dev` → `appwrappers/finalizers`

This looks like the same class of omission previously fixed for other integrations in #1485 / #1486.

Note: the `, <nil>` text in the API server error is a misleading formatting of a failed finalizer authorization check. When the missing RBAC is added, the Workload is created with a fully populated ownerReference (`apiVersion: sparkoperator.k8s.io/v1beta2`, `kind: SparkApplication`, `blockOwnerDeletion: true`).

**What you expected to happen**:

The manager role should include finalizer permissions for SparkApplication, matching other integrations:

```yaml
- apiGroups:
  - sparkoperator.k8s.io
  resources:
  - sparkapplications/finalizers
  verbs:
  - get
  - update
```

With that RBAC present, Workload creation should succeed on clusters with `OwnerReferencesPermissionEnforcement` without requiring operators to apply an extra ClusterRole manually.

**How to reproduce it (as minimally and precisely as possible)**:

1. Deploy Kueue with the SparkApplication framework enabled.
2. Create a ResourceFlavor, ClusterQueue, and LocalQueue.
3. Ensure the manager ServiceAccount does **not** have an extra ClusterRole granting `sparkapplications/finalizers`.
4. On a cluster with `OwnerReferencesPermissionEnforcement` enabled, create a SparkApplication labeled with `kueue.x-k8s.io/queue-name`.
5. Observe the SparkApplication stays suspended, no Workload is created, and controller logs show the `blockOwnerDeletion` / finalizers error above.
6. Grant `update` on `sparkapplications/finalizers` to the Kueue manager SA and recreate the SparkApplication → Workload is created and admission proceeds.

**Anything else we need to know?**:

- SparkApplication integration was added in #7268; manager RBAC appears to have landed with CRUD only.
- Proposed fix: add `sparkapplications/finalizers` (`get`, `update`) to the manager ClusterRole and regenerate Helm RBAC / related manifests as needed.
- Related prior art: #1485, #1486.

**Environment**:
- Kubernetes version (use `kubectl version`): observed on OpenShift (OwnerReferencesPermissionEnforcement enabled)
