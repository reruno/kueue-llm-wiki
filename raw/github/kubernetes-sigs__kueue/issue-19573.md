**What would you like to be added**:

A way for an operator to cordon a MultiKueue worker cluster: the manager stops dispatching new workloads to that worker, while it keeps managing the workloads already dispatched there (admission, status synchronization, and cleanup). Uncordoning resumes dispatch.

A draft implementation is in https://github.com/kubernetes-sigs/kueue/pull/16777 (closed, needs a rebase). It adds `MultiKueueCluster.spec.unschedulable`, mirroring the Node API, behind a default-off alpha feature gate `MultiKueueClusterCordon`:

- Both built-in dispatchers (AllAtOnce and Incremental) skip a cordoned worker when they pick candidates.
- Remote workload creation also enforces the cordon, for external nominations and for component or elastic workloads pinned to the worker. New pinned workloads wait for uncordon.
- Cordon does not change the `Active` condition and does not evict workloads already running on the worker.

**Why is this needed**:

During worker cluster maintenance (for example, an upgrade or node pool changes), operators want to stop sending new work to one worker without disconnecting it. Today the closest option is to remove the worker from every `MultiKueueConfig` that lists it, and add it back afterwards. That edits configuration shared by all ClusterQueues using those configs, and it does not show on the `MultiKueueCluster` that the worker is under maintenance.
