## Description

/kind bug

**What happened**:

`kueuectl list workload --for TYPE/NAME -A` and `kueuectl list pods --for TYPE/NAME -A` resolve the owner across all namespaces by name, then always take `infos[0]` with no check for multiple matches.

If two Jobs (or other owners) share the same name in different namespaces, the command silently picks an arbitrary one (API order) and lists Workloads/Pods for that owner. Exit code is 0.

**What you expected to happen**:

When more than one owner matches `TYPE/NAME` under `-A`, fail with a clear error asking for `-n` / removing `-A` (or otherwise disambiguating). Do not pick an arbitrary match.

**How to reproduce it (as minimally and precisely as possible)**:

1. Create Jobs named `train` in namespaces `team-a` and `team-b` (both managed by Kueue).
2. Run:

```bash
kueuectl list workload --for job/train -A
# or
kueuectl list pods --for job/train -A
```

Observed: results for whichever Job the API returned first.
Expected: error that the owner is ambiguous.

**Anything else we need to know?**:

- `list workload`: `cmd/kueuectl/app/list/list_workload.go` (`Complete` builds the query with `AllNamespaces(o.AllNamespaces)` then uses `infos[0]`)
- `list pods`: `cmd/kueuectl/app/list/list_pods.go` (`getForObjectInfos` / `getForObject` — same `infos[0]` pattern)
- Without `-A`, names are unique per namespace, so this failure mode is specific to cross-namespace `--for`.
- Suggested fix: if `o.AllNamespaces && len(infos) > 1`, return an error naming the count and suggesting `-n`.
