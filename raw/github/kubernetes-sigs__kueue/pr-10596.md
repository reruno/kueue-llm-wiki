## Description

#### What type of PR is this?

/kind kep

#### What this PR does / why we need it:

Adds KEP-7029 proposing the ability to configure a default maximum execution time on a ClusterQueue. When a job is submitted to a LocalQueue backed by a ClusterQueue with a default maximum execution time configured, the resulting workload will automatically have its `maximumExecutionTimeSeconds` field set, unless the job already specifies a value via the `kueue.x-k8s.io/max-exec-time-seconds` label.

This builds on KEP-3125 (maximum execution time) and addresses community requests in:
- https://github.com/kubernetes-sigs/kueue/discussions/6684
- https://github.com/kubernetes-sigs/kueue/issues/6587#issuecomment-3342233971

#### Which issue(s) this PR fixes:

Fixes #7029

#### Special notes for your reviewer:

This is the KEP only. Implementation will follow in a separate PR.

The original proposal placed the default at the LocalQueue level. Based on review feedback (most configuration lives at the ClusterQueue level, and LocalQueue acts primarily as a pointer), the design was moved to the ClusterQueue level. LocalQueue-level defaults are documented as a future extension.

Looking at Slurm, it does turn out that they enforce that users can't go over the CQ timelimit.

> Note: The precedence order specified above is respected except for the following limits: Max[Time|Wall], [Min|Max]Nodes. For these limits, even if the job is enforced with QOS and/or Association limits, it can't go over the limit imposed at Partition level, even if it listed at the bottom. So the default for these 3 types of limits is that they are upper bound by the Partition one.

ref: https://slurm.schedmd.com/resource_limits.html#:~:text=Note%3A%20The%20precedence%20order%20specified,it%20listed%20at%20the%20bottom.&text=This%20Partition%20level%20bound%20can,level%20respecting%20the%20order%20above.

I think this makes sense to me. The change would be that a user can specify a time limit on their workload but it cannot be less than ClusterQueue timelimit. If it is, then the workload will not be admitted. We can't really enforce this at creation time so I think keeping the workload in pending makes sense.
