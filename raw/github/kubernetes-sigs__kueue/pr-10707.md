### Comment by [@sohankunkerkar](https://github.com/sohankunkerkar) — 2026-04-24T19:46:40Z

>do you know already why the submitter job is failing in new Ray - what is the root cause so that we can help to guide the community there, or even fix by ourselves?

The submitter Job is failing because KubeRay's RayJob controller gates submission using the cached DashboardURL and the deprecated `RayCluster.Status.State`, instead of rechecking whether the head is actually ready to serve requests. Once the dashboard URL is cached, the controller can proceed without verifying `HeadPodReady=True`. With Ray 2.53.0, head startup is slower in our CI environment, so the submitter starts retrying against a dashboard endpoint that is not serving yet, eventually hitting BackoffLimitExceeded.

>does it fail deterministically or occasionally

In CI, this failure mode is reproducible deterministically with Ray 2.53.0. The older Ray 2.41.0 issue is different and appears only occasionally. That older flake is the `opencensus DeltaProducer::RunHarvesterLoop()` crash.

>the looks bad, and I'm wondering if/how new KubeRay works on real / not e2e clusters

I do not think this means new KubeRay is broadly broken on real clusters. On clusters with enough CPU, the head usually comes up quickly enough that the race is masked.

> can we maybe attempt the upgrade in the meanwhile to a Ray version which solves the stability issues, but does not run into the newly discovered issue, wdyt?

Unfortunately I do not see a good intermediate Ray version. The crashing opencensus stats path remains present through the 2.42.x-2.52.x line and is only fully removed in 2.53.0.
