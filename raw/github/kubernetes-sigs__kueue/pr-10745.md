+## Summary
+
+This KEP proposes extending the ClusterQueue API to support automatic quota
+detection based on node selectors. Instead of requiring administrators to
+manually set and maintain `nominalQuota` values, Kueue can dynamically compute
+quotas by watching Kubernetes Nodes that match a given selector and aggregating
+their Allocatable resources. This removes the operational burden of keeping
+ClusterQueue quotas in sync with the underlying infrastructure, especially in
+autoscaled clusters where node pools frequently change size.
+
+## Motivation
+
+Currently, `nominalQuota` in a ClusterQueue ResourceQuota is a static value that
+administrators must manually configure and update. When the underlying node pool
+scales up or down (e.g., via cluster-autoscaler or manually), the administrator
+must manually adjust the ClusterQueue quota to reflect the new cluster capacity.
+This creates several problems:
+
+1. **Operational overhead**: In dynamic environments, node pools scale
+   frequently. Manually updating ClusterQueue quotas for each scaling event is
+   error-prone and labor intensive.
+2. **Quota drift**: If quotas are not updated promptly after a scaling event,
+   Kueue may over-admit workloads (quota > actual capacity) or under-utilize the
+   cluster (quota < actual capacity).
+3. **Redundant configuration**: Capacity management is already handled at the
+   node pool level (e.g. via max node count settings in cloud providers).
+   Requiring administrators to duplicate this information in ClusterQueue
+   configuration is redundant.
+4. **ResourceFlavor already knows the nodes**: A ResourceFlavor specifies
+   `nodeLabels` that associate it with a set of Nodes. However, Kueue does not use
+   this information to compute how many resources those nodes actually provide.
+   The administrator must separately and manually state the total quota.
+
+### Goals
+
+- Allow ClusterQueue quotas to be automatically computed from the Allocatable
+  resources of Nodes matching a selector.
+- Support configurable headroom to reserve resources for system and non-Kueue
+  workloads.
+- Ensure automatic quotas update dynamically as Nodes are added, removed, or
+  change status.
+- Be backward compatible — existing static `nominalQuota` configurations
+  continue to work unchanged.
+- Support coexistence of auto-detected and manually specified quotas within the
+  same ClusterQueue.
+
+### Non-Goals
+
+- Replace or deprecate static `nominalQuota`. Both modes will coexist.
+- Automatically create or manage ResourceFlavors.
+- Account for resources consumed by non-Kueue workloads (DaemonSets, system pods)
+  beyond a configurable headroom percentage or fixed amount.
+- Integrate with cluster-autoscaler to predict future capacity. This feature
+  reflects current capacity only. Future capacity planning is covered by
+  ProvisioningRequest (KEP-1136).
+- ProvisioningRequest (KEP-1136).
+- Introduce auto-detection for DRA Device resources. DRA quota is managed through
+  DeviceClassMappings (KEP-2941).
+
+## Proposal
+
+Add an optional `autoDetect` field to ResourceQuota within the ClusterQueue spec.
+When `autoDetect` is set, Kueue watches Nodes matching the specified selector,
+aggregates their Allocatable values for the resource, subtracts the configured
+headroom, and uses the result as the effective `nominalQuota`. The static
+`nominalQuota` field becomes optional when `autoDetect` is specified.
+
+### User Stories
+
+#### Story 1
+
+As a cluster administrator, I manage a GPU node pool that autos-scales between 2
+and 20 nodes. Each node has 8 GPUs. I want Kueue to automatically know that the
+cluster has between 16 and 160 GPUs available, without me updating the ClusterQueue
+every time a node is added or removed.
+
+```yaml
+apiVersion: kueue.x-k8s.io/v1beta2
+kind: ClusterQueue
+metadata:
+  name: gpu-team-cq
+spec:
+  resourceGroups:
+  - coveredResources: ["nvidia.com/gpu"]
+    flavors:
+    - name: gpu-nodes
+      resources:
+      - name: nvidia.com/gpu
+        autoDetect:
+          nodeSelector:
```

  I would simplify the API to just be node selectors:
  ```
  apiVersion: kueue.x-k8s.io/v1beta2
  kind: ClusterQueue
  metadata:
    name: gpu-team-cq
  spec:
    resourceGroups:
    - coveredResources: ["nvidia.com/gpu"]
      flavors:
      - name: gpu-nodes
        resources:
        - name: nvidia.com/gpu
          nodeSelector:
            matchLabels:
              gpu-type: a100
  ```
  
  But there needs to be validation such that it's mutually exclusive with inline quotas

+## Summary
+
+This KEP proposes extending the ClusterQueue API to support automatic quota
+detection based on node selectors. Instead of requiring administrators to
+manually set and maintain `nominalQuota` values, Kueue can dynamically compute
+quotas by watching Kubernetes Nodes that match a given selector and aggregating
+their Allocatable resources. This removes the operational burden of keeping
+ClusterQueue quotas in sync with the underlying infrastructure, especially in
+autoscaled clusters where node pools frequently change size.
+
+## Motivation
+
+Currently, `nominalQuota` in a ClusterQueue ResourceQuota is a static value that
+administrators must manually configure and update. When the underlying node pool
+scales up or down (e.g., via cluster-autoscaler or manually), the administrator
+must manually adjust the ClusterQueue quota to reflect the new cluster capacity.
+This creates several problems:
+
+1. **Operational overhead**: In dynamic environments, node pools scale
+   frequently. Manually updating ClusterQueue quotas for each scaling event is
+   error-prone and labor intensive.
+2. **Quota drift**: If quotas are not updated promptly after a scaling event,
+   Kueue may over-admit workloads (quota > actual capacity) or under-utilize the
+   cluster (quota < actual capacity).
+3. **Redundant configuration**: Capacity management is already handled at the
+   node pool level (e.g. via max node count settings in cloud providers).
+   Requiring administrators to duplicate this information in ClusterQueue
+   configuration is redundant.
+4. **ResourceFlavor already knows the nodes**: A ResourceFlavor specifies
+   `nodeLabels` that associate it with a set of Nodes. However, Kueue does not use
+   this information to compute how many resources those nodes actually provide.
+   The administrator must separately and manually state the total quota.
+
+### Goals
+
+- Allow ClusterQueue quotas to be automatically computed from the Allocatable
+  resources of Nodes matching a selector.
+- Support configurable headroom to reserve resources for system and non-Kueue
+  workloads.
+- Ensure automatic quotas update dynamically as Nodes are added, removed, or
+  change status.
+- Be backward compatible — existing static `nominalQuota` configurations
+  continue to work unchanged.
+- Support coexistence of auto-detected and manually specified quotas within the
+  same ClusterQueue.
+
+### Non-Goals
+
+- Replace or deprecate static `nominalQuota`. Both modes will coexist.
+- Automatically create or manage ResourceFlavors.
+- Account for resources consumed by non-Kueue workloads (DaemonSets, system pods)
+  beyond a configurable headroom percentage or fixed amount.
+- Integrate with cluster-autoscaler to predict future capacity. This feature
+  reflects current capacity only. Future capacity planning is covered by
+  ProvisioningRequest (KEP-1136).
+- ProvisioningRequest (KEP-1136).
+- Introduce auto-detection for DRA Device resources. DRA quota is managed through
+  DeviceClassMappings (KEP-2941).

+## Summary
+
+This KEP proposes extending the ClusterQueue API to support automatic quota
+detection based on node selectors. Instead of requiring administrators to
+manually set and maintain `nominalQuota` values, Kueue can dynamically compute
+quotas by watching Kubernetes Nodes that match a given selector and aggregating
+their Allocatable resources. This removes the operational burden of keeping
+ClusterQueue quotas in sync with the underlying infrastructure, especially in
+autoscaled clusters where node pools frequently change size.
+
+## Motivation
+
+Currently, `nominalQuota` in a ClusterQueue ResourceQuota is a static value that
+administrators must manually configure and update. When the underlying node pool
+scales up or down (e.g., via cluster-autoscaler or manually), the administrator
+must manually adjust the ClusterQueue quota to reflect the new cluster capacity.
+This creates several problems:
+
+1. **Operational overhead**: In dynamic environments, node pools scale
+   frequently. Manually updating ClusterQueue quotas for each scaling event is
+   error-prone and labor intensive.
+2. **Quota drift**: If quotas are not updated promptly after a scaling event,
+   Kueue may over-admit workloads (quota > actual capacity) or under-utilize the
+   cluster (quota < actual capacity).
+3. **Redundant configuration**: Capacity management is already handled at the
+   node pool level (e.g. via max node count settings in cloud providers).
+   Requiring administrators to duplicate this information in ClusterQueue
+   configuration is redundant.
+4. **ResourceFlavor already knows the nodes**: A ResourceFlavor specifies
+   `nodeLabels` that associate it with a set of Nodes. However, Kueue does not use
+   this information to compute how many resources those nodes actually provide.
+   The administrator must separately and manually state the total quota.
+
+### Goals
+
+- Allow ClusterQueue quotas to be automatically computed from the Allocatable
+  resources of Nodes matching a selector.
+- Support configurable headroom to reserve resources for system and non-Kueue
+  workloads.
+- Ensure automatic quotas update dynamically as Nodes are added, removed, or
+  change status.
+- Be backward compatible — existing static `nominalQuota` configurations
+  continue to work unchanged.
+- Support coexistence of auto-detected and manually specified quotas within the
+  same ClusterQueue.
+
+### Non-Goals
+
+- Replace or deprecate static `nominalQuota`. Both modes will coexist.
+- Automatically create or manage ResourceFlavors.
+- Account for resources consumed by non-Kueue workloads (DaemonSets, system pods)
+  beyond a configurable headroom percentage or fixed amount.
+- Integrate with cluster-autoscaler to predict future capacity. This feature
+  reflects current capacity only. Future capacity planning is covered by
+  ProvisioningRequest (KEP-1136).
+- ProvisioningRequest (KEP-1136).
+- Introduce auto-detection for DRA Device resources. DRA quota is managed through
+  DeviceClassMappings (KEP-2941).
+
+## Proposal
+
+Add an optional `autoDetect` field to ResourceQuota within the ClusterQueue spec.
+When `autoDetect` is set, Kueue watches Nodes matching the specified selector,
+aggregates their Allocatable values for the resource, subtracts the configured
+headroom, and uses the result as the effective `nominalQuota`. The static
+`nominalQuota` field becomes optional when `autoDetect` is specified.
+

+      resources:
+      - name: cpu

+          nodeSelector:
+            matchLabels:
+              team: alpha

+            percentage: 5
```

+detection based on node selectors. Instead of requiring administrators to
+manually set and maintain `nominalQuota` values, Kueue can dynamically compute

+administrators must manually configure and update. When the underlying node pool
+scales up or down (e.g., via cluster-autoscaler or manually), the administrator
+must manually adjust the ClusterQueue quota to reflect the new cluster capacity.

+

+   error-prone and labor intensive.

+## Summary
+
+This KEP proposes extending the ClusterQueue API to support automatic quota
+detection based on node selectors. Instead of requiring administrators to
+manually set and maintain `nominalQuota` values, Kueue can dynamically compute
+quotas by watching Kubernetes Nodes that match a given selector and aggregating
+their Allocatable resources. This removes the operational burden of keeping
+ClusterQueue quotas in sync with the underlying infrastructure, especially in
+autoscaled clusters where node pools frequently change size.
+
+## Motivation
+
+Currently, `nominalQuota` in a ClusterQueue ResourceQuota is a static value that
+administrators must manually configure and update. When the underlying node pool
+scales up or down (e.g., via cluster-autoscaler or manually), the administrator
+must manually adjust the ClusterQueue quota to reflect the new cluster capacity.
+This creates several problems:
+
+1. **Operational overhead**: In dynamic environments, node pools scale
+   frequently. Manually updating ClusterQueue quotas for each scaling event is
+   error-prone and labor intensive.
+2. **Quota drift**: If quotas are not updated promptly after a scaling event,
+   Kueue may over-admit workloads (quota > actual capacity) or under-utilize the
+   cluster (quota < actual capacity).
+3. **Redundant configuration**: Capacity management is already handled at the
+   node pool level (e.g. via max node count settings in cloud providers).
+   Requiring administrators to duplicate this information in ClusterQueue
+   configuration is redundant.
+4. **ResourceFlavor already knows the nodes**: A ResourceFlavor specifies
+   `nodeLabels` that associate it with a set of Nodes. However, Kueue does not use
+   this information to compute how many resources those nodes actually provide.
+   The administrator must separately and manually state the total quota.
+
+### Goals
+
+- Allow ClusterQueue quotas to be automatically computed from the Allocatable
+  resources of Nodes matching a selector.
+- Support configurable headroom to reserve resources for system and non-Kueue
+  workloads.
+- Ensure automatic quotas update dynamically as Nodes are added, removed, or
+  change status.
+- Be backward compatible — existing static `nominalQuota` configurations
+  continue to work unchanged.
+- Support coexistence of auto-detected and manually specified quotas within the
+  same ClusterQueue.
+
+### Non-Goals
+
+- Replace or deprecate static `nominalQuota`. Both modes will coexist.
+- Automatically create or manage ResourceFlavors.
+- Account for resources consumed by non-Kueue workloads (DaemonSets, system pods)
+  beyond a configurable headroom percentage or fixed amount.
+- Integrate with cluster-autoscaler to predict future capacity. This feature
+  reflects current capacity only. Future capacity planning is covered by
+  ProvisioningRequest (KEP-1136).
+- ProvisioningRequest (KEP-1136).
+- Introduce auto-detection for DRA Device resources. DRA quota is managed through
+  DeviceClassMappings (KEP-2941).

+## Proposal
+
+Add an optional `autoDetect` field to ResourceQuota within the ClusterQueue spec.
+When `autoDetect` is set, Kueue watches Nodes matching the specified selector,
+aggregates their Allocatable values for the resource, subtracts the configured
+headroom, and uses the result as the effective `nominalQuota`. The static
+`nominalQuota` field becomes optional when `autoDetect` is specified.

  @mwielgus @tenzen-y That's a strong separation-of-concerns argument, and it aligns with how Kubernetes handles similar problems (e.g., HPA adjusting replicas on a Deployment rather than embedding scaling logic in the Deployment itself).
  
  The current design puts autoDetect: true in the FlavorQuotas spec, which does conflate "what the quota is" with "how it's derived." Your suggestion would mean keeping CQ/Cohort spec clean, just nominalQuota,  and introducing a separate object (e.g., QuotaDetector or NodePoolQuota) that references a CQ/Cohort, defines the node selection logic, and has its own controller that patches nominalQuota.
  
  The tradeoff I see:
  - Separate CRD: cleaner CQ/Cohort API, composable with other quota sources (budget tools, inventory systems), but users must manage an additional object type and the controller needs a reliable way to patch CQ/Cohort without conflicting with manual edits
  - Inline autoDetect: simpler UX for the common case (one object, one place), tighter integration with Kueue's internal scheduler cache/snapshot
  
  A close Kubernetes precedent is Node.Status.Allocatable, kubelet automatically computes available capacity inline on the Node object itself, rather than via a separate CRD. Our proposal follows the same principle: a
  ClusterQueue or Cohort representing a node pool should naturally reflect the actual capacity of that pool, just as a Node reflects its own Allocatable resources.
  
  The HPA/VPA pattern (separate CRD patching the target object) is appropriate when the adjustment logic is external business logic (e.g., "scale based on RPS"). But quota derived from physical node capacity is intrinsic to the capacity object, I think it's closer to Allocatable than to HPA, thougts?
