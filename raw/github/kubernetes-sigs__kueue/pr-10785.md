  My original assumption that "the workload reconciler will eventually observe  the object via watches" is wrong in this scenario. These are pre-existing  workloads that were already reconciled before the LocalQueue was created, the channel send in AddLocalQueue is the *only* trigger that re-fires their  reconciliation. Dropping it would leave them stuck.
  
  I'll implement the fix you proposed: collect the DRA workloads inside the  lock, release it, then do a blocking send to draReconcileChannel to guarantee  delivery without holding the lock.
  
  This is actually a performance issue here, we should never have a blocking send in a critical section while holding the manager lock, as it can stall all other manager operations (scheduling, workload admission, etc.) if the channel buffer (size=10) fills up. Like when LoacalQueue recovered or created, `AddLocalQueue` may detect bunch of workloads which will block this function.
