#### Special notes for your reviewer:

### TAS Workload Domain lookup logic
When a workload is admitted, TAS writes a TopologyAssignment into wl.Status.Admission.PodSetAssignments[*].TopologyAssignment. This contains the topology Levels (the label keys, e.g. ["block", "rack", "hostname"]) and per-domain Values — but as a storage optimization, when hostname is the lowest level only the hostname value is stored in Values, omitting ancestor values.

At metrics time, the code takes that hostname value, looks it up in the in-memory node informer cache, and reads the full set of ancestor label values off the node object — reconstructing the complete Values slice to match all Levels. 

With the full path, it fans out one Prometheus gauge increment per topology level, so a single node assignment contributes a series at each of hostname, rack, and block.

### Track Non-TAS Usage Changes
(I need both TAS and non-TAS workloads aggregated into this metric so that we have a full view of what Kueue thinks is being used by the domain.)

- Pre-compute topology coordinates at pod add time (tas_non_tas_pod_cache.go, tas_cache.go): When a non-TAS pod is first added to the cache, the matching flavor/topology coordinates (flavor name, topology levels, node label values) are computed and stored alongside the pod entry. This decouples metric subtraction from the current state of nodesCache — if a node is marked unschedulable and evicted from the cache between pod add and pod delete (e.g. by a cluster autoscaler), the subtract still fires correctly.

- Fix Delete predicate for terminal-phase pods (non_tas_usage_controller.go): The previous predicate called belongsToNonTASCache, which returns false for Succeeded/Failed pods. If the informer skipped the Running→Succeeded Update event and delivered only the Delete event with the pod already in a terminal phase, the predicate would drop it and the pod's usage would never be subtracted. The new predicate filters only on NodeName and TAS annotation, so terminal-phase deletes are always reconciled. DeletePodByKey is idempotent, so double-removal is safe. (case caught during e2e)
