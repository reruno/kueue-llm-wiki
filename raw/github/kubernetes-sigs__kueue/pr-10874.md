## Description

#### What type of PR is this?

/kind bug

#### What this PR does / why we need it:

When the controller restarts, the cache is rebuilt by listing all Workloads from the API server. Some entries returned by that List may be deleted shortly after by external controllers (job controllers, deactivation, etc.), so the cache can transiently contain Workloads that no longer exist on the API server. 

When IssuePreemptions selected such a Workload as a preemption target, the eviction patch returned 404 NotFound. The deleted Workload remained in Cache.workloadAssignedQueues, so on the next scheduling cycle it was re-selected as a target and re-failed in the same way — an infinite loop that pinned quota and starved real work.

This change treats NotFound as a terminal, successful preemption inside IssuePreemptions:

> I'm wondering if maybe you hit also another issue where the Delete event was skipped due to replica failover: #10495,. This issue was fixed here:

Thanks for sharing that bug fix — it may very well be the cause here since this loop only happened during leader failover during kueue-controller restarts and it was a bit unclear why it never received the delete event to clear the workload.

> It does not indicate the PR is not useful, but maybe the severity of the issue would be smaller on the version fixing wdyt?

Yup agreed, with delete event propagation fixed, this PR would just expedite the unblocking of the scheduling loop since it would eventually unblock once the delete event is reconciled. The other thing this catches is that NotFound on one preemption target currently cancels the parallel evictions for the other targets in the same IssuePreemptions call which would have succeeded otherwise
