## Description

#### What type of PR is this?

/kind bug
/area tas

#### What this PR does / why we need it:

Adds regression test coverage for a TAS scheduling bug where `TopologyDomainAssignment.Count` could be emitted with a negative value, causing the apiserver to reject the Workload admission update with a CRD validation error (`podCounts.individual[*]` requires `>= 1`).

The bug occurs in over-subscribed leaf domains: when `tasUsage` (or `tasUsage + assumedUsage`) exceeds `freeCapacity`, `CountInWithLimitingResource` returns a negative `int32`. That value was previously stored verbatim on `leaf.state` and propagated through `fillInCountsHelper` (`childrenCapacity += child.state`) into the emitted `TopologyAssignment`.

This PR adds two regression tests in `pkg/cache/scheduler/tas_flavor_snapshot_test.go`:

1. `TestBuildTopologyAssignmentForLevels_DropsNonPositiveStateDomains` — asserts the output-side filter in `buildTopologyAssignmentForLevels` skips any domain whose `state <= 0`, so a non-positive `Count` is never emitted.
2. `TestFillInCounts_ClampsNegativeRemainingCapacity` — asserts the source-side fix: `fillInCounts` must clamp `leaf.state` to `0` when remaining capacity goes negative, covering both the `tasUsage` over-subscription case and the `assumedUsage` (preempt-mode) case.

Both tests currently fail on `main`, demonstrating the bug. The fix will land in a follow-up PR.

### Comment by [@mimowo](https://github.com/mimowo) — 2026-05-06T12:25:02Z

I see, ok I'm not sure what is the root cause, but:
1. I think the change in [here](https://github.com/kubernetes-sigs/kueue/pull/10949/changes#diff-015ac0ccc6a319e922161cdd677487236e5d4e7edc11d0376fd59aebf14ae148R1478-R1480) would not be necessary if the leaf.state is non-negative, so we correct the other place
2. I think instead of correcting outside of CountInWithLimitingResource, this function should never produce negative results - the responsibilty of this function is to give "count" of pods which can schedule. Negative count does not make sense.
3. I think it is technically possible (not sure if this is what happened in your env) that the CountInWithLimitingResource produce negative results in some cases when the Node resources "allocatable" minus pods is negative - that could happen for example:
a) if a Node driver reduced the Node allocatable - then for a short while the node could be running over-booked. 
b) if we have a non-TAS Pod scheduled by kube-scheduler and accounted before the TAS workload is fully evicted and releases the quota. For example, a TAS workload spans 1000 Nodes, it will release quota and domains only ones all Pods terminate, but this creates a time windows when a non-TAS Pod may schedule on the Node1, and so the Node1 will be running overbooked - and so CountInWithLimitingResource will produce currently negative results.

Again, I'm not sure if this is what happened for you, but this is possible in such scenarios, so I would propose:
1. make the correction inside CountInWithLimitingResource
2. add logging at V(2) around here if you observe the remainingCapacity is negative: https://github.com/kubernetes-sigs/kueue/pull/10949/changes#diff-015ac0ccc6a319e922161cdd677487236e5d4e7edc11d0376fd59aebf14ae148R1628-R1629 for any resource
3. drop the corrective actions outside of calling CountInWithLimitingResource
