```diff
@@ -476,7 +476,7 @@ var _ = ginkgo.Describe("WaitForPodsReady with default Timeout and a long Recove
 			gomega.Eventually(func(g gomega.Gomega) {
 				g.Expect(k8sClient.Get(ctx, wlKey, &wl)).Should(gomega.Succeed())
 				g.Expect(wl.Status.Conditions).To(utiltesting.HaveConditionStatusTrueAndReason(kueue.WorkloadPodsReady, kueue.WorkloadRecovered))
-			}, util.MediumTimeout, util.Interval).Should(gomega.Succeed())
+			}, util.LongTimeout, util.Interval).Should(gomega.Succeed())
```

  In this test Job controller only creates the replacement Pod when the failing Pod is marked as Failed. 
  
  And only when the replacement Pod is created the "recovery" is done.
  
  However, on a busy system transitioning a Pod from Running to Failed may take > 60s. 
  
  We already knew about the transition sometimes taking long, and so we introduced the LongTimeout to account for this phenomenon.
  
  FYI: Pod tranisitioning started to take long probably after we started to run e2e tests in parallel, but that is a good change, because it speeds up the tests runtime overall, but puts more load on the CI machines.
  
  See also the more detailed analysis: https://github.com/kubernetes-sigs/kueue/issues/11029#issuecomment-4405702131
