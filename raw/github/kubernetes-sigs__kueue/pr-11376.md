#### What this PR does / why we need it:

Adds `keps/11375-multikueue-cross-cluster-preemption/` for a new
MultiKueue dispatcher mode (alpha, default-off feature gate
`MultiKueueCrossClusterPreemption`) that, when an incoming workload at
the manager finds sibling clusters full of *borrowed* work, evicts a
borrower on a sibling worker so the incoming workload can be admitted
there. Mirrors single-cluster Kueue's `ReclaimWithinCohort` cross-cluster
via the External-dispatcher extension point.

The load-bearing semantic is **quota-based reclaim** (`cqIsBorrowing`):
a sibling ClusterQueue is only an eligible victim source when it is
currently borrowing cohort capacity (`Status.FlavorsUsage > NominalQuota`).
Priority is one configurable value of the `ReclaimWithinCohort` policy
gate, not the primary driver. With `ReclaimWithinCohort=Any`, an owner
reclaims at *equal* priority — the ownership-of-nominal-quota use case
that motivates the KEP.

The KEP covers:

- `cqIsBorrowing` filter + `ReclaimWithinCohort` policy gate +
  `BorrowWithinCohort` borrow-while-preempting gate (with
  `MaxPriorityThreshold` as a victim-side cap, matching the upstream
  API godoc and single-cluster `isAboveBorrowingThreshold`).
- Priority + creation-time + name victim ordering across the cohort.
- Flat cohorts via the shared `ClusterQueue.spec.cohortName` string;
  the dispatcher does not read `Cohort` CRs.
- Joint operation with [KEP-8303](https://github.com/kubernetes-sigs/kueue/tree/main/keps/8303-multikueue-orchestrated-preemption)
  OrchestratedPreemption — both gates may be enabled simultaneously
  without coordination.

No new CRDs. No changes to existing CRDs other than a new dispatcher
mode constant.

Fixes #11375

#### Special notes for your reviewer:

This PR contains the **KEP only**. A working alpha prototype with
25 unit tests + 5 integration scenarios lives at
[`up/multikueue-cross-cluster-preemption`](https://github.com/ningziwen/kueue/tree/up/multikueue-cross-cluster-preemption);
the implementation PR will follow once the KEP is `implementable`.

Relationship to existing work (audited before opening):

- Builds on the umbrella in [#10766](https://github.com/kubernetes-sigs/kueue/issues/10766)
  / [KEP-8692](https://github.com/kubernetes-sigs/kueue/pull/10784)
  (composable MultiKueue dispatcher), which explicitly lists
  *Cross-cluster preemption scheduling* under **Non-Goals**. This KEP
  fills that gap as a separate dispatcher mode.
- Originating bug report: [#6790](https://github.com/kubernetes-sigs/kueue/pull/6790)
  ("Fix preemption in MultiKueue worker cluster"). That PR addresses
  the worker-to-manager eviction propagation half; this KEP is the
  manager-to-worker initiation half. Both can coexist.
- Independent of [KEP-8303](https://github.com/kubernetes-sigs/kueue/tree/main/keps/8303-multikueue-orchestrated-preemption)
  (separate feature gate; joint mode validated by integration test in
  the prototype).
- Reuses single-cluster [KEP-1337](https://github.com/kubernetes-sigs/kueue/tree/main/keps/1337-preempt-within-cohort-while-borrowing)
  (BorrowWithinCohort + MaxPriorityThreshold) API and semantics
  unchanged.

Out of scope for this KEP (potential follow-ons if a need surfaces):
[KEP-1714](https://github.com/kubernetes-sigs/kueue/tree/main/keps/1714-fair-sharing)
(FairSharing weights / DRS) cross-cluster, [KEP-79](https://github.com/kubernetes-sigs/kueue/tree/main/keps/79-hierarchical-cohorts)
(hierarchical cohorts) cross-cluster, and cross-cluster aggregation of
`LendingLimit` / `BorrowingLimit`. Worker-local schedulers continue to
honor each of these at admission time as today.

Open questions I'd specifically appreciate maintainer input on:

1. Forward-compat with [KEP-8692](https://github.com/kubernetes-sigs/kueue/pull/10784):
   if the composable dispatcher framework lands first, would
   maintainers prefer the cross-cluster preemption logic restructured
   as plugins within KEP-8692's pipeline at beta, or kept as a sibling
   dispatcher mode?
2. Joint operation with [KEP-8303](https://github.com/kubernetes-sigs/kueue/tree/main/keps/8303-multikueue-orchestrated-preemption):
   alpha keeps the two paths independent (the prototype has an
   integration test asserting no `MultiKueuePreemptionGate` activates
   on workloads our dispatcher touches). Is independent operation OK
   long-term, or should beta unify them?

Happy to discuss in `#sig-scheduling` / `#wg-batch` or at a Kueue
community meeting in parallel with PR review.

### Key topic

I claim that MultiKueue **already has** functionality **like you need**. 
(Though, admittedly, I'm not sure if it's *exactly* what you need. We'll need to discuss).

### Evidence

To kick off the discussion, please look at [this branch](https://github.com/olekzabl/kueue/blob/br44/test/integration/multikueue/scheduler/cross_cluster_preemption_test.go). 
It's my experimenting on top of your implementation. (Specifically, my changes as of now are [these](https://github.com/olekzabl/kueue/commit/c5cee81f405907ae7a37296269ae4911b246df8c)).
_(disclaimer: AI helped me in this)_
I *essentially* made your integration tests pass **without cross-cluster preemption**, by changing the following bits:

1. Use `AllAtOnce` instead of your new dispatcher.
2. Use `OrchestratedPreemption` to make sure reclaiming in cohorts won't cause more evictions than necessary.
3. **Flip** `ReclaimWithinCohort` settings between the 2 tenants A & B.
    The meaning of this field is "how you can reclaim"; **not** "how you can be reclaimed from".
    Cf. [Kueue docs](https://kueue.sigs.k8s.io/docs/concepts/cluster_queue/#preemption):

    > `reclaimWithinCohort` determines whether a pending Workload *[in this ClusterQueue]* can preempt Workloads from **other** ClusterQueues in the cohort that are using more than their nominal quota.

4. Finally, some technical glue to keep the tests meaningful:

   * change the way of verifying that a workload was evicted
      (in the current behavior, the manager-side workload does not become `Evicted` but rather blocked-again on the MultiKueue AdmissionCheck transitioned to `Retry` and then back to `Pending`)
      * OTOH, to make things more convincing, I added checks for `Evicted` condition on the workers
   * remove Scenario 4 (which now became a duplicate of Scenario 1)
   * remove Scenario 3 (which was very specific to the cross-cluster preemption mechanics)

### Conclusions

At this point, I'm **not sure** how much of your work (KEP, impl) remains relevant for your needs.

Let me share my early thoughts on this:

1. `AllAtOnce` + `OrchestratedPreemption` is admittedly not perfect.
   It's quite "noisy". Will dispatch the candidate to _every worker_, and then just make sure not to _evict_ in many places.
   I'm assuming your new dispatcher can do better, in making a smart worker selection and leaving the other workers undisturbed.
   That feels valuable in general.
   How valuable is it from your perspective? Maybe that gain alone is a good reason to introduce a new dispatcher?

2. If we choose to continue this KEP, I'm blindly hoping that my findings above will allow **simplifying** it.
   For example, I imagine the dispatcher could just nominate the best worker - however, it should not need to deal with evicting workloads.
   Here, the existing logic behind `ReclaimWithinCohort` should do.
   (Of course, unless there are some bugs which I haven't yet realized).

3. Given my experiments above, I'm feeling that your background ("Summary" and "Motivation" in this KEP, also the phrasing of #11375) are a bit misleading.
   It's not that MultiKueue does not support quota reclaiming on workers at all. It can :) Possibly a bit imperfectly.
   Once we align here, let's comment-or-update on #11375 to make sure it's not misleading for future readers.
   Same will apply to this KEP if we choose to continue it.
