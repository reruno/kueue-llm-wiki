#### What this PR does / why we need it:

Several Kueue CRDs were missing `shortNames`, making them verbose to use with `kubectl`. This PR adds short names to the remaining resources so operators can use concise aliases like `kubectl get ac` or `kubectl get topo`.

  | Resource | Short Name(s) added |
  |---|---|
  | `AdmissionCheck` | `ac` |
  | `Cohort` | `co` |
  | `MultiKueueCluster` | `mkc` |
  | `MultiKueueConfig` | `mkconf` |
  | `ProvisioningRequestConfig` | `prc` |
  | `Topology` | `topo` |
  | `WorkloadPriorityClass` | `wpc` |

  Resources that already had short names (`ClusterQueue`→`cq`, `LocalQueue`→`lq`, `ResourceFlavor`→`rf`, `Workload`→`kwl`) are unchanged.

  Changes are applied to both `v1beta1` and `v1beta2` API type files, the generated CRD YAML under `config/components/crd/bases/`, and the Helm chart CRD templates under `charts/kueue/templates/crd/`.

Good point, thanks @mimowo for the due diligence! Following the same pattern as wl -> kwl, I prefer rename all short names by adding `k` as prefix, like topo -> ktopo, wpc -> kwpc to avoid potential conflicts if upstream Kubernetes introduces Topology or WorkloadPriorityClass CRDs in the future.

### Comment by [@mimowo](https://github.com/mimowo) — 2026-05-22T19:01:09Z

> I prefer rename all short names by adding k as prefix, like topo -> ktopo, wpc -> kwpc to avoid potential conflicts if upstream Kubernetes introduces Topology or WorkloadPriorityClass CRDs in the future.

I'm not sure about that, we still like to use "cq" and "lq" for ClusterQueue and LocalQueue. It is very unlikely they would be introduced in the core k8s any time soon, so I like the preferrable names for them. 

On top of that, there is no guarantee really k8s core will no have some CRD which resolves to "kcq" so adding "k" proactively may not even benefit us in all cases. I would use the prefix only when needed.
