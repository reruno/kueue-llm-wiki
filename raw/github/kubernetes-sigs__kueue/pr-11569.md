```diff
+			util.ExpectPendingWorkloadsMetric(cq2, 0, 2)
```

  **Why isn't the same change needed at line 2848?**
  
  Both assertions look identical, so it's natural to suspect both are flaky.But, because foundation-queue's heap is in a different state at each call site, and that changes the scheduler path best-effort workloads take.
  
  **Line 2848  foundation has a stuck head, so cycles are multi-entry**
  
  At this point, `workload-7f9t2` (the second foundation workload, 2 CPU) is queued and cannot admit (cohort has only 1 CPU free). foundation-queue is `StrictFIFO`, and the StrictFIFO requeue rule in [`pkg/cache/queue/cluster_queue.go`](pkg/cache/queue/cluster_queue.go#L870-L871) is:
  
  ```go
  if c.queueingStrategy == kueue.StrictFIFO {
      immediate = reason != RequeueReasonNamespaceMismatch
  }
  ```
  
  Any other reason (including the Generic reason from NoFit) is `immediate=true`, so `workload-7f9t2` goes straight back into foundation's heap every cycle.
  
  Because foundation has a head every cycle, `heads()` returns `count=2` and the scheduler runs a **multi-entry** cycle. When best-effort is processed *after* foundation, it goes through the "skipped" path (`"Workload no longer fits after processing another workload"`, status=`skipped`). In `requeueAndUpdate` ([`pkg/scheduler/scheduler.go`](pkg/scheduler/scheduler.go#L947-L949)):
  
  ```go
  if e.status != notNominated && e.requeueReason == qcache.RequeueReasonGeneric {
      e.requeueReason = qcache.RequeueReasonFailedAfterNomination
  }
  ```
  
  `skipped != notNominated`, so the reason is upgraded to `FailedAfterNomination`, which **is** in BestEffortFIFO's immediate set ([`pkg/cache/queue/cluster_queue.go`](pkg/cache/queue/cluster_queue.go#L873-L876)) → workload stays in the heap → `(active=2, inadmissible=0)` is stable.
  
  **Line 2855 foundation has admitted, so cycles are single-entry**
  
  By this point, `finish first foundation workload` has run and the second foundation admits. foundation-queue's heap is empty. `heads()` returns `count=1` (best-effort only). The single-entry path goes through `FlavorAssigner assigned NoFit mode` at [`pkg/scheduler/scheduler.go:302`](pkg/scheduler/scheduler.go#L302), which sets `status=""` (notNominated). The `requeueReason` stays at `Generic` — and Generic is **not** in BestEffortFIFO's immediate set → workload goes to `inadmissibleWorkloads` → metric reports `(active=0, inadmissible=2)`.
  
  **Side-by-side**
  
  | | Line 2848 (foundation queued) | Line 2855 (foundation admitted) |
  |---|---|---|
  | foundation in heap? | yes (StrictFIFO + Generic → immediate) | no |
  | cycle entries | 2 | 1 |
  | best-effort scheduler path | "skipped" (after another workload) | "notNominated" (FlavorAssigner NoFit) |
  | requeueReason | `FailedAfterNomination` | `Generic` |
  | BestEffortFIFO treatment | immediate → heap | not immediate → `inadmissibleWorkloads` |
  | stable state | `(2, 0)` (this) | `(0, 2)` |
  
  **Empirical confirmation from the failing run** ([Prow #2042478052260188160](https://gcsweb.k8s.io/gcs/kubernetes-ci-logs/pr-logs/pull/kubernetes-sigs_kueue/10348/pull-kueue-test-integration-baseline-release-0-17/2042478052260188160/build-log.txt)): line 2848 *passed* — the test successfully reached `STEP: finish first foundation workload @ 06:03:15.372` and `STEP: best-effort workloads not admitted @ 06:03:15.447`. Cycles 201–206 in that window were all `entries=2` with best-effort taking the skipped → FailedAfterNomination → heap path. The failure is only at line 2855, where cycle 207 was the first `entries=1` cycle and immediately put workload-7wbbt into `inadmissibleWorkloads`.
  
  So line 2848 is correct as-is; the bug really is one literal at line 2855.
