#### What this PR does / why we need it:

Fixes a race in TAS node replacement when `TASReplaceNodeOnNodeTaints` is enabled.

When a node is tainted and a pod is replaced, the node controller may call `markPodsFailed` on the pending replacement pod (old node selector, unschedulable) on a later reconcile, after the node is already listed in `status.unhealthyNodes`. That consumes the Job's `BackoffLimit` before second-pass scheduling can evict
the workload and reschedule it (e.g. to another rack).

This change skips `markPodsFailed` only when the unhealthy node was recorded in a prior reconcile **and** the workload still has progressing pods on other nodes. All other cases (including all pods still pending on a failed node) are unchanged.

Repro: e2e `Should evict the workload if replacement is not possible due to taint` (flaky in #11617).

  Thanks for the detailed scenario, this helped me tighten the condition.
  
  A few clarifications on what the controller actually does:
  
  - On the first reconcile after the node becomes unhealthy, `unhealthyNodes` does not yet contain this node, so we still call `markPodsFailed` for pending pods on that node (same as before). That is the reconcile that fails the first replacement/stray pod and records the node in unhealthyNodes.
  
  - We only skip `markPodsFailed` on a later reconcile when both are true:
    - the node is already in `status.unhealthyNodes`, and
    - the workload still has progressing pods on other nodes (`hasProgressingPodsOnOtherNodes`).
  
  That matches the flake in #11617: one pod is still running elsewhere while a replacement pod is pending on the tainted node with the old node selector. Skipping `markPodsFailed` there avoids consuming BackoffLimit before second-pass scheduling / eviction can run.
  
  - For the second stray pod in your sequence: while siblings are still running, we intentionally do not fail it immediately. It should not stay forever, because cleanup happens when either:
    - Second pass / eviction completes, topology is updated or the workload is evicted; pods with a node selector for a node that is no longer in the topology assignment are handled as strays (`!hasTASAssignment` path in `checkPodsOnNode`) and are still eligible for `markPodsFailed` (they are not in `pendingSecondPassWorkloads`, which only applies to `workloadUnhealthy`), or
    - No progressing pods remain on other nodes, `hasProgressingPodsOnOtherNodes` becomes false, so we stop skipping and `markPodsFailed` runs again.
  
  I ran `make test-tas-e2e-baseline` locally (14/14 passed, including the hotswap tests). Happy to add an integration test for this sequence if you think it would help. Do you think we need to add this integration test?

  Thanks @j-skiba @mimowo for the discussion here.
  
  The connection goes through BackoffLimit exhaustion:
  1. The bug: markPodsFailed was called on each replacement/stray pod on the tainted node even after the node was already recorded in unhealthyNodes. Each call consumes one unit of BackoffLimit.
  2. Once BackoffLimit is exhausted, Kubernetes moves the Job to Failed state.
  3. Kueue then tries to evict the workload: StopJob → RestorePodSetsInfo → Patch(spec.template) to strip the TAS node selectors.
  4. Kubernetes rejects that patch on a Failed Job with "field is immutable" — the patch loop retries forever.
  5. The test times out waiting for eviction to complete.
  
  This PR prevents step 1 by skipping markPodsFailed when the node was already recorded in unhealthyNodes and sibling pods are still progressing. The Job never exhausts BackoffLimit, so it never enters Failed state, so the eviction patch succeeds.
  
  I will add a new test case based on @mimowo 's comment.
