## Description

#### What type of PR is this?

/kind bug
/area multikueue

#### What this PR does / why we need it:

Follow-up for @mimowo's #11615.
It adjusts MultiKueue lifecycle of a Job to be compatible with K8s 1.36+ validation changes. (See https://github.com/kubernetes/kubernetes/issues/139281).

#### Which issue(s) this PR fixes:

Fixes #11614

#### Special notes for your reviewer:

The old code skipped `syncElasticJob` (i.e. adjusting worker spec to manager spec) in cases when chose to skip syncing statuses. 
There seems to be no good reason behind this, so this PR removes this skipping.

#### Does this PR introduce a user-facing change?

```release-note
MultiKueue: Fixed admission for Kubernetes Jobs on Kubernetes 1.36 clusters by ensuring all Job status updates comply with the updated Kubernetes Job validation rules. See kubernetes/kubernetes#139281 for more details.
```

  Actually, I don't think we need these updates: `newLocalStatus.Active = 0` and `newLocalStatus.StartTime = nil`.
  
   I suggested them thinking about the k8s validation, but I think this is "defensive programming" which can have a negative impact on code simplicity, and correctness in some cases.
  
  The relevant validation in the k8s for starting a job (which requires injection of scheduling directives like nodeSelectors):
  - 1.36 requires `status.Active=0`: https://github.com/kubernetes/kubernetes/blob/release-1.36/pkg/registry/batch/job/strategy.go#L198
  - 1.35 requires `status.startTime=nil`: https://github.com/kubernetes/kubernetes/blob/release-1.35/pkg/registry/batch/job/strategy.go#L192-L193
  
  Now, while with this updates we will make the validation pass we can see these are defensive programming when we consider how can we step into the code.
  
  The stepping into the code happens when:
  - Job on manager is supended, spec.suspend=True
  - Job on worker is running, spec.suspend=false
  - the job is not finished
  
  Now, to get into this state I can see the following scenarios:
  1. start of a newly created Job (worker starts and manager remains stopped)
  2. start of a Job after stop (worker starts and manager is still stopped)
  3. stop is called on manager (worker remains running)
  
  **Let's first think about the need to set `status.active=0`.**
  1. not needed because we have it already for new job
  2. not needed because we awaited on active=0 when stopping the previously running Job
  3. not needed, because once worker is also stopped, then we will start syncing the status between stopped Jobs using the code above
  
  Actually, (3.) is the slightly problematic case, because we may set status.active=0 which will be updated to >0 just a moment later. It may also result in premature quota freeing.
  
  **Let's first think about the need to set `status.startTime=nil`.**
  
  1. not needed because we have status.startTime=nil for new jobs
  2. not needed because it was cleaned already by our job_controller code [here](https://github.com/kubernetes-sigs/kueue/blob/a393561c2072b1b1366a0bd5ec915be897219373/pkg/controller/jobs/job/job_controller.go#L187)
  3. not needed because again it will be cleaned by the Job controller integration
  
  At the same time here I'm less sure it is a problem, because k8s core is clearing the field when the Job is suspended in 1.36+. Since we take the ownership of adding the JobSuspended=True it is more subtle here, ptal: https://github.com/kubernetes/kubernetes/blob/master/pkg/controller/job/job_controller.go#L1168-L1170
