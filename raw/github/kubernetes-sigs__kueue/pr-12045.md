#### What type of PR is this?

#### What this PR does / why we need it:

With `ElasticJobsViaWorkloadSlices` enabled, the `ElasticJobUngater` ungated
**every** gated pod returned by `listGatedPods`, and `listGatedPods` was
uncapped. Because every pod of an elastic job (including scale-up workers
belonging to a still-`Pending` replacement slice) carries the chain-root
workload name in its `kueue.x-k8s.io/workload` annotation, reconciling the
already-admitted root slice ungated the entire chain — including surplus
workers whose replacement slice was over quota. The result: an elastic job
could exceed its ClusterQueue's nominal quota during scale-up, with the
surplus replicas running outside quota accounting.

This PR caps ungating, per PodSet, to the replicas actually **granted quota**
across the slice chain (the max `Count` among quota-reserved slices sharing
the chain root), counting already-ungated pods against the cap. Surplus pods
stay `SchedulingGated` until their replacement slice is admitted.

- `listGatedPods` now buckets candidate pods by their PodSet label and ungates
  at most `granted[podSet] - alreadyUngated[podSet]` gated pods (lowest pod
  name first for determinism).
- A new `grantedPodSetCounts` walks the slice chain via the existing
  `OwnerReferenceUID` workload index (siblings sharing the parent job's owner
  UID and the same slice name) and takes the per-PodSet max `Count` among
  slices that hold a quota reservation.

#### Which issue(s) this PR fixes:

Fixes #11977

#### Special notes for your reviewer:

- Unit tests added: surplus pods over quota stay gated during scale-up, and
  are ungated once the replacement slice is admitted (the chain walk raises
  the cap). Existing cases were updated to carry the PodSet label that real
  elastic pods always have.
- AI disclosure: this change was developed with the assistance of an AI coding
  tool, in line with the Kubernetes AI tool usage policy.

### Comment by [@mcochner](https://github.com/mcochner) — 2026-06-10T10:37:54Z

**Why the e2e test change in fb91733** (analysis of the `pull-kueue-test-e2e-extended-shard-0` failures on the first push):

All four shard-0 jobs (k8s 1.33–1.36) failed deterministically on the same spec, `Kuberay: Should run a rayjob with multi scale-up steps`, timing out waiting for 5 running worker pods.

The expectation of 5 running workers is not reachable within the suite's quota: head (1 CPU) + submitter (400m) + 5 workers (5×400m) = **3.4 CPU**, but the shared ClusterQueue had **3 CPU**. A 5-worker workload slice can never be admitted under that quota.

Comparing the kueue-controller-manager logs of the failed run against a passing run of the same job from another PR (built on unmodified `main`) shows both runs behaved identically on the scheduler side:

- the 5-worker replacement slice was rejected in both runs with `insufficient unused quota for cpu ... 400m more needed` and requeued with `PreemptionNoCandidates`;
- in both runs that slice was only admitted after Ray's autoscaler downsized it back to 3 workers once the demand window passed — **the ClusterQueue never granted 5 workers in either run**.

The only difference: on `main`, the ungater ungated the 2 surplus worker pods while their slice was still `Pending` (3 admitted + 2 running outside quota — exactly the bug from #11977), which is what satisfied the test's "5 running workers" assertion. With the fix, those pods correctly stay gated, so the assertion can no longer be met under a 3-CPU quota.

Raising the quota to 4 CPU makes the 5-worker slice (3.4 CPU) admissible via the normal slice-replacement path — the same path that admitted the 1→3 scale-up within a second in both runs — so the test now verifies legitimate, quota-respecting elastic scale-up. The sibling tests sharing this ClusterQueue are demand-driven (Ray task parallelism caps their worker counts, not quota), so they are unaffected.
