#### What this PR does / why we need it:

Reworks KEP-11980 after the earlier review: round robin becomes an option of the `kueue-priority-booster` time sharing, instead of a `ClusterQueue.spec.ordering` field.

- Today a Workload preempted by the booster's time sharing returns to the queue ahead of the Workloads created after it, so only the oldest Workloads take turns (`a b a b …` instead of `a b c d e a b …`).
- Kueue: an optional Workload field `spec.yieldTime`, behind the new `YieldTime` feature gate (Alpha, off by default).
  Kueue orders a pending Workload by this time, unless it already orders it by an eviction or preemption time.
- Booster: `timeSharing.ordering: RoundRobin`. The default, `DefaultOrder`, is the current behavior.
  When a Workload with the boost returns to the queue with the `Evicted` reason `Preempted`, the booster writes the requeue time to `spec.yieldTime` in the same patch that removes the boost.
  A Workload preempted before its interval ends keeps its place.
- The KEP changes only the order among Workloads of the same priority.

+By policy, the team accepts that an urgent job with a higher priority preempts regular jobs. About halfway through l1's interval, an urgent job h arrives and preempts l1.
+
+`yieldTime` is the time when a Workload yielded its turn. l1 was only pushed out by h before it used up its turn; it did not hand its turn to another regular job.
+If `yieldTime` were written on every eviction, l1 would move to the end of the queue, and the queue would be `l2 l3 l4 l5 l6 l1`. Although l1 ran for only half of its interval, it would have to wait after h finishes until all five jobs finish their turns.
+
+So the booster writes `yieldTime` only for a Workload that used up its interval and has a negative boost. l1 has no negative boost, so its value does not change.
+
+```yaml
+apiVersion: kueue.x-k8s.io/v1beta2
+kind: Workload
+metadata:
+  name: l1
+spec:
+  yieldTime: "2026-11-20T06:30:05Z" # written by the booster when the previous turn ended; unchanged after h preempts l1
+```
+
+The queue is `l1 l2 l3 l4 l5 l6`, and l1 runs again as soon as h finishes.
+
+### Notes/Constraints/Caveats
+
+#### Round robin can increase the mean completion time
+
+For finite Workloads of similar size, round robin increases the mean completion time.
+

+#### Workloads of different sizes
+
+Round robin only sets the queue order. It does not change how Kueue admits Workloads.
+With BestEffortFIFO, if the head Workload does not fit in the resources freed by one Workload whose interval passed, a smaller Workload behind it is admitted first, as today.
+So when Workloads of different sizes are mixed, a large Workload can keep missing its turn.
+
+#### Supported preemption policy
+
+Like the booster, round robin works only when the ClusterQueue uses `withinClusterQueue: LowerPriority`.
+
+#### Interaction with waitForPodsReady
+
+`waitForPodsReady` is enabled by default (timeout 30 minutes) and evicts a Workload with `PodsReadyTimeout` when not all Pods of the admitted Workload become ready in time.
+This eviction is not a time-sharing preemption, so the booster does not write `yieldTime`. `waitForPodsReady.requeuingStrategy.timestamp` decides where the Workload waits again.
+
+- `Eviction` (default): the Workload is ordered by its eviction time and goes to the back. Even if a `yieldTime` from an earlier turn remains, the eviction time applies first, so Kueue's default behavior of moving a Workload that may fail to the back stays the same.
+- `Creation`: the Workload waits by its `yieldTime` if set, or by its creation time otherwise. This setting keeps the Workload's original place after a failure, and with round robin the original place is the time when it last yielded its turn.
+
+#### When the booster writes spec.yieldTime
+
+The value of `spec.yieldTime` is the time when the Workload returned to the queue, that is, when its `QuotaReserved` condition became `False`, and the booster writes it to the Workload when it removes the negative boost.
+Round robin is not involved if another Workload is admitted in between.
+
+### Risks and Mitigations
+
+#### The switches are split between Kueue and the booster
+
+The round-robin order applies only when all of the following are in place.
+- Kueue: a version with `spec.yieldTime` (including the CRD), with the `YieldTime` gate enabled.
+- Booster: a version with `timeSharing.ordering`, set to `RoundRobin`.
+
+So when an administrator enables or disables round robin, the actual order can differ from what they expect.
+- Enabling: if any of these is missing, the order stays as today and no error occurs. The booster cannot see the Kueue version or feature gates.
+- Disabling: if only the booster is set back to `DefaultOrder`, the `spec.yieldTime` values already written remain, and those Workloads are still ordered by those times.
+
+Mitigation: the booster README states that enabling or disabling round robin requires changing both the booster's `ordering` and Kueue's `YieldTime` feature gate.
+
+#### A user who can write Workloads can change the order
+
+`spec.yieldTime` is meant to be written by an external controller such as the booster, but when the `YieldTime` gate is enabled, a user with write access to Workloads can also use this field to change the order within the same priority.
+- Writing a later value moves the Workload back. The user can also move other users' Workloads back.
+- Clearing the value of their own Workload undoes the move by the booster, and the Workload goes back ahead of the Workloads that were already waiting.
+- Writing a value earlier than the creation time can move the Workload forward.
+
+Mitigation: this KEP adds no new permissions. kueue-controller-manager and the booster work with the permissions they have today, and the users who can write this field are the users who can write Workloads today.
+A Job cannot set this field, so users who submit Jobs cannot change it.
