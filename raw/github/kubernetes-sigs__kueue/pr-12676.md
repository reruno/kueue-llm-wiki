## Description

#### What type of PR is this?

#### What this PR does / why we need it:

Adds guidance on structured errors to the contribution guidelines. It replaces the earlier `structured-errors` review skill proposal, following the discussion on this PR.

- `coding_guidelines.md`, Error Handling: expose errors that callers or tests need to distinguish as sentinels or typed errors with an `Is` method, not as message text. Includes examples based on `ErrCqNotFound` and `FilterBuildError`. Do not match on `err.Error()`.
- `coding_guidelines.md`, Unit Test Assertions: avoid/prefer example comparing `strings.Contains(err.Error(), ...)` with `cmpopts.EquateErrors()`. Do not write custom comparers that fall back to message comparison.
- `writing_tests.md`: one bullet pointing to the new section.

Per the review discussion, the main gap is a good copy-pasteable example rather than a skill, so the guide now provides one. A skill can be added later if the pattern is still not followed.

```diff
+# Skill: Structured Errors
+
+**Structured errors over string comparison** — error checking (especially in tests)
+done via substring/equality checks on `err.Error()` instead of a sentinel or typed
+error checked with `errors.Is` / `errors.As`. String-matching turns tests into
+"change detector" tests, where a purely cosmetic wording tweak forces updates across
+every test that asserted on it.
+
+- A test asserting `err.Error() == "..."` or `strings.Contains(err.Error(), "...")`
+  against a bare `errors.New(...)` / `fmt.Errorf(...)`. Prefer a sentinel
+  (`var ErrFoo = errors.New(...)`) or a typed error with an `Is` method, checked with
+  `errors.Is`.
+- An error whose data (offending names, counts, a resource reference) only exists in
+  the formatted message (`fmt.Errorf("...: %s", x)`) when a caller already needs that
+  data. Prefer a typed error struct with the data as a field.
+- A `cmp.Comparer` or similar helper that falls back to `strings.HasPrefix` to work
+  around errors not being directly comparable — make the errors comparable instead
+  (sentinel values or an `Is` method), and prefer `cmpopts.EquateErrors()` in tests.
```

  I think these descriptions aren't very clear without example snippets for "how-to-do-well" .
  
  Alternatively, maybe instead of the SKILL we could introduce our Error comparator in Kueue and reuse it across all tests giving the good example how to do it? 
  
  From my experience most people and AI agents just copy-paste code in that situations, so the more good examples we have the more of a chance the next example is as we want.
  
  From my experience with errors in golang and k8s in general some kind of better comparator is really needed as an option to cmp.Diff, and currently people tend to workaround that problem
