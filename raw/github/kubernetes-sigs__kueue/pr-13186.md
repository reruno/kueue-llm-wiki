## Description

#### What type of PR is this?

/kind bug
/area tas

#### What this PR does / why we need it:

A Topology pending deletion keeps its `kueue.x-k8s.io/resource-in-use` finalizer until no ResourceFlavor references it. That check reads the TAS cache, and the reconcile is triggered by the referencing flavor's **delete** event (delayed by `UpdatesBatchPeriod`). If the reconcile runs before the cache has observed the flavor deletion, it logs "topology is still in use" and returns **without requeue**.

Because `spec.topologyName` is immutable on ResourceFlavors (CEL validation on both v1beta1 and v1beta2), the flavor's delete event is the *last* event that can ever enqueue that Topology — losing the race leaves the Topology stuck in `Terminating` until a controller restart resyncs it, matching the symptom reported in #12572.

This PR requeues the Topology with a 1-minute interval while it is pending deletion and still referenced, so finalizer removal re-verifies periodically instead of depending on event/cache ordering. A table-driven reconciler test covers both the requeue-while-referenced and finalizer-removal paths.

#### Which issue(s) this PR fixes:

Fixes #12572

#### Special notes for your reviewer:

- The issue proposed handling ResourceFlavor `Update` events. During implementation I found that `topologyName` is immutable once set (CEL rule in both served API versions), so a flavor can never be *updated* to stop referencing a Topology — only deleted, which the handler already covers. The remaining reachable stuck-in-Terminating path is the event/cache race above, which this PR fixes; an `Update` handler would have no effect today. Detailed analysis is in the linked issue comment.
- Verified with the new `TestTopologyReconcilerFinalizerRemovalOnDeletion` and `go test ./pkg/controller/tas/ -count=1`.

Thanks for tracking this down. The race is real. The core ResourceFlavor controller drops the flavor from the TAS cache in its delete predicate (`pkg/controller/core/resourceflavor_controller.go:161`). This Topology is enqueued by a different listener on the same shared informer (`resourceFlavorHandler.Delete`). client-go runs each listener on its own goroutine, so the 1s `UpdatesBatchPeriod` makes the window smaller but doesn't close it. Once the TAS cache reflects the flavor deletion, the requeue fixes the race you describe.

I left one non-blocking design alternative and two small test suggestions inline.

  Non-blocking alternative: check references through the cached client instead of `CloneTASCache()`.
  
  client-go removes an object from the informer indexer before it dispatches `OnDelete` to any listener (`tools/cache/controller.go`, `processDeltas`). The cached client reads that same indexer. So by the time this reconcile runs, the deleted flavor is already gone from a `List`, whatever order the listeners run in. There is also an existing, currently unused field index on `spec.topologyName` (`indexer.ResourceFlavorTopologyNameKey`, `pkg/controller/tas/indexer/indexer.go:117`), so this can be an indexed lookup:
  
  ```go
  var rfs kueue.ResourceFlavorList
  if err := r.client.List(ctx, &rfs, client.MatchingFields{indexer.ResourceFlavorTopologyNameKey: topology.Name}); err != nil {
  	return ctrl.Result{}, err
  }
  if len(rfs.Items) != 0 {
  	flavors := make([]string, 0, len(rfs.Items))
  	for _, rf := range rfs.Items {
  		flavors = append(flavors, rf.Name)
  	}
  	log.V(3).Info("topology is still in use", "ResourceFlavors", flavors)
  	return ctrl.Result{}, nil
  }
  ```
  
  Benefits:
  - **No periodic polling.** A Topology deleted while a live flavor still references it no longer reconciles (and logs) every minute. That flavor's later delete already enqueues the Topology.
  - **No dependency on TAS-cache convergence.** The cache has a second, pre-existing writer: the TAS `rfReconciler` predicates call `AddOrUpdateResourceFlavor` on Create (`pkg/controller/tas/resource_flavor.go:172`) and on scheduling-field Updates (`:191`). Its Delete predicate (`:178-180`) doesn't remove the entry. If a Create or Update for a short-lived flavor is still queued on that listener after core `Delete`, the deleted flavor is put back in the cache. Any reconcile that sees it then keeps requeueing until restart.
  - **It also counts flavors the informer has seen but the TAS cache hasn't processed yet.** Terminating flavors still count, as they do today.
  
  RBAC for `resourceflavors` list/watch is already granted in this package (`resource_flavor.go:64`). Unit tests would need `indexer.SetupIndexes(ctx, utiltesting.AsIndexer(clientBuilder))`, as `node_controller_test.go` does. I checked this locally with stale-cache-only, live-flavor, live-flavor-not-in-cache and no-flavor cases.
  
  Keeping the requeue is also a reasonable trade-off if you prefer it.
