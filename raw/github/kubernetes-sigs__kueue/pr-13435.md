#### What this PR does / why we need it:

Lets the Ray in-tree autoscaler actually resize a MultiKueue-dispatched elastic RayCluster or RayJob (`ElasticJobsViaWorkloadSlices`), by adding the worker→manager direction that no MultiKueue integration has today. Today the manager-driven forward sync (#12885) propagates manager resizes to the worker, but an autoscaler running on the worker cluster has no way to feed its resizes back — the manager's quota accounting goes stale and spec divergence can tear the running job down.

- **Reverse elastic sync** in the shared Ray adapter: an autoscaler-driven resize on the worker cluster is reflected onto the manager as **annotations**, leaving the manager spec untouched. A single `Runtime` hook drives it — `Fetch` reads the live per-worker-group counts plus a revision from the worker cluster, and `Apply` records them on the manager copy as the `multikueue-runtime-podset-replica-sizes` and `raycluster-generation` annotations. The manager's PodSets derivation reads them (gated on `spec.managedBy`) and the workload-slicing machinery re-reserves quota; workload-slice naming folds in the revision so each reflected resize mints a freshly named replacement slice (`GetWorkloadNameExtraPart` on both the RayJob and RayCluster jobs). The revision is derived from the worker RayCluster's UID and generation — a worker-side resize reflects onto the manager as an annotation, which never bumps the manager object's `metadata.generation`, so keying the slice name on that generation alone would recompute an already-existing name and fail to mint the replacement. `Fetch` reads whichever object holds the live worker replicas on the worker cluster:
  - **RayCluster**: the remote copy itself.
  - **RayJob**: the child RayCluster KubeRay creates on the worker (the child never exists on the manager).

  Count-neutral updates (revision-only bumps) do not mint replacement slices; a suspended remote is skipped, since its counts were restored by the worker's Kueue while stopping the job, not set by the autoscaler.
- **Worker-side resize tolerance** in the jobframework, scoped to MultiKueue-dispatched copies (origin label): a transient job/slice count mismatch during the handover no longer finishes the workload `OutOfSync`. Scale-up pods stay behind scheduling gates (never past quota); scale-down briefly over-reserves (never under).
- **ElasticJobUngater: resolve the slice chain when its root is deleted.** On a MultiKueue worker the manager deletes the remote copy of a replaced slice, so the chain's root can be gone while newer slices and gated pods naming the chain key live on; the ungater previously dead-ended there, leaving pods `SchedulingGated` forever. It now falls back to resolving the chain through any surviving member.
- The remote copy keeps `enableInTreeAutoscaling` (the worker runs the autoscaler sidecar, which is accounted in the head PodSet); in autoscaling mode the forward sync never pushes replicas — its only duty is repointing the remote's prebuilt-workload marker at the current slice (idempotent).

Verification beyond the unit and integration tests in this PR: real-autoscaler e2e (part of the extended MultiKueue suite, KubeRay v1.6.2) on kind, with detached Ray actors that each require a per-worker custom resource, driving the actual Ray Autoscaler. Both a standalone RayCluster and a RayJob's child worker group are driven **up (2 workers) → down (0) → up again (1)** by creating and terminating actors, and each resize is reflected onto the manager. Each step asserts the manager runtime annotation, the worker RayCluster's `DesiredWorkerReplicas` and Running worker-pod count, the ClusterQueue's admitted-workload count, and — on **both** the manager and the worker cluster — exactly one live workload slice, admitted and reserving the reflected count. The slice lifecycle is checked by slice **name**: scale-down updates the live slice in place (name unchanged), and each scale-up mints a **fresh replacement** slice (new name; the previous slice kept finished as `WorkloadSliceReplaced`, prebuilt marker repointed, admitted by the real scheduler). Tracking the live slice by name rather than an exact total-slice count keeps the assertions robust to the Ray Autoscaler transiently overshooting the requested worker count. The worker RayCluster is verified not torn down mid-handover; MultiKueue GC clean.

My current implementation introduces a new annotation to achieve the same result. I didn’t modify `RayClusterPodsetReplicaSizesAnnotation` because it is currently dead code, and I don’t have the historical context behind it.

> They are specifically designed to propagate the information from the RayCluster to RayJob and RayService without overriding the user settings in the spec.

This would be great. Currently, this PR divides jobs into two categories. In the first category, the PodSets can be inferred from the job CR (e.g., a RayCluster). In the second category, the PodSets can only be inferred from the runtime state (e.g., a RayJob needs to infer its PodSets from its underlying RayCluster). Because the community prefers not to override user-defined settings in the spec, we can always retrieve the runtime state and remove the mechanism that syncs the CR spec back from the worker cluster.
