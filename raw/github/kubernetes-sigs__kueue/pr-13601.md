## Description

#### What type of PR is this?

/kind feature
/area dra

#### What this PR does / why we need it:

Defines quota accounting for DRA `firstAvailable` requests in KEP-2941, behind a new Alpha, default-off `KueueDRAIntegrationPrioritizedList` gate.

For each top-level `firstAvailable` request, Kueue maps every alternative's DeviceClass to its logical quota resource and charges the largest of them. Multiple top-level requests stay additive. kube-scheduler selects exactly one alternative from each request, so that charge is an upper bound on whichever it selects.

For the initial Alpha, every alternative of one request has to map to the same logical resource. The envelope then covers one resource, which takes one flavor, and nothing downstream has to know the request was a prioritized list.

##### Alpha scope

Supported: `ResourceClaimTemplate` references, `ExactCount` subrequests, count-based `deviceClassMappings`, request-selector CEL compiled against the DRA feature environment the supported Kubernetes API uses.

Rejected: direct `ResourceClaim` references; `All` and unknown allocation modes; unmapped DeviceClasses; `DeviceSubRequest.capacity`; counter- and capacity-backed alternatives; and a request whose alternatives map to more than one logical resource.

##### What the bound rests on

It holds for a fixed `ResourceClaimSpec`, over the resources the target ClusterQueue manages, while every operand merged into the charge is non-negative and exactly representable, and while each contribution reaches the merge exactly once and as the value its own source defines. That last one is not the same as arriving at whatever was computed for it: #13992 computes a retained input of 512 where 1024 was requested and delivers 512 faithfully.

The accounting path has to keep the charge through resource transformation, preprocessing, queue-entry construction, requeue, and PodSet aggregation. The KEP records #13930, #13985, #13988, #13990, #13991, #13992, #13998, #14004 and #14007 as prerequisites: each of them can lose or alter a correct envelope after it is computed, and the Alpha implementation does not ship until each failure mode is answered by a merged fix or an equivalent guard. The non-negative premise also rests on `WorkloadValidateResourcesAreNonNegative`, which is Beta and on by default but can be turned off, and the bound cannot rest on something an administrator can switch off, so Alpha checks the operand at the merge instead of requiring the gate. Reading the sign of the result is weaker: a request of -3 merged with an envelope of 8 gives 5, positive and three short.

Two further boundaries came out of reading current `main`. Fitting in an `int64` is not the finite range, because `resources.Amount` keeps `math.MaxInt64` as its `Unlimited` sentinel: `MaxInt64 - 10` on one PodSet plus `10` on another is exact and still folds to unlimited. That fold, `Info.ResourceUsage`, is also where the cross-PodSet sum actually happens rather than in the builder, and neither half of it is checked; the unassigned side is a plain `+=` that wraps. And `excludeResourcePrefixes` is applied before the DRA merge, so a mapping name an excluded prefix covers is charged anyway: with `example.com/` excluded, an ordinary `example.com/other` request drops to zero while a logical `example.com/gpu` stays at 8. That last one is a policy question rather than an undercharge. Answering it for everyone would change what the `Exactly` path does today, so Alpha restricts only what it adds and refuses a `firstAvailable` request whose logical resource an excluded prefix covers. The cost is that the refusal lands on a workload whose author cannot remove the overlap, and a view on that would help.

Preprocessing also has to say which logical resources a `firstAvailable` request reached. A merged `ResourceList` per PodSet cannot, so the checked accounting would either take in every DRA dimension or miss the shared boundaries; the scope is the union of those names across the workload.

#### Which issue(s) this PR fixes:

Related to #13987, which #13993 closes. Part of #13599. Related to #10548 and #12422. #13842 is a known limitation the bound is stated around rather than made conditional on.

#### Special notes for your reviewer:

Documentation only: the gate, the implementation, its tests and the user-facing release note ship with the implementation PR, so the release note here is `NONE`.

The scope question I would most like a view on is whether rejecting `DeviceSubRequest.capacity` is the right boundary for the initial Alpha. It is a deliberate scope restriction rather than a counting limit: under a count mapping it leaves the declared device count alone, so the envelope still bounds it, but what it consumes is not something this path accounts for.
