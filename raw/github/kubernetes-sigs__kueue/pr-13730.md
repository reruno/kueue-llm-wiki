#### What this PR does / why we need it:

Experimental validation companion to #13729

This branch enables `FairSharingRefill` by default so the full unit, integration, and e2e test suites exercise the refill path, including tests not written specifically for the feature.

It contains the main PR's commits, the drain-to-empty benchmark used for its performance analysis, and an experiment-only gate flip. The gate is temporarily marked Beta because the feature-lifecycle validation does not permit a default-on Alpha gate; this does not propose promoting the feature or changing its default.

### Comment by [@apullo777](https://github.com/apullo777) — 2026-09-21T07:21:58Z

> It would be great to have a summary for the following runs:
> 
> scheduler perf test vanilla (classical preemption) - before and after Refill enabled
> scheduler perf test with FairSharing - before and after Refill enabled

@mimowo I ran both (with full results and methodology in https://github.com/kubernetes-sigs/kueue/pull/13729#issuecomment-5756816541):

* **Fair Sharing:** refill cuts the number of scheduling cycles (−16.6% on `baseline`, −24.1% on `tas`) while scheduler time per admitted workload is unchanged (+0.5% / −0.1%), and wall clock, CPU and peak RSS stay within what this setup resolves.
* **Classical preemption:** flat as expected, and I also used the pair as the measurement control.

The reduction is concentrated in short cycles; cycles over 10 s occur at about the same rate in both arms. I don't see evidence of a worse long-cycle tail, though the histogram can't resolve durations beyond 10 s.

One result I'd keep watching: `baseline` shows a ~1.2% increase in `smallMsToAdm` that clears its internal null and is matched by per-CQ mean wait; `tas` doesn't corroborate it.

Main caveat: neither fixture is shaped to exercise a persistent sharing imbalance, and `tas` never became topology-constrained, so I'd read this as cost/regression evidence rather than fairness evidence. "Flat" means within what this setup resolves, not zero.

### Comment by [@apullo777](https://github.com/apullo777) — 2026-09-21T09:20:50Z

CI surfaced one Refill × TAS topology-spreading interaction: once refill admits multiple workloads from the same ClusterQueue in one cycle, spreading counts need to see admissions made earlier in that cycle.

I pushed a narrow fix that records those in-cycle admissions for the spreading count only, without adding them to the normal `Workloads` snapshot, plus regression coverage.

Once refill lands, i would like to follow up separately on the more general same-cycle snapshot invariant so this doesn't stay implicit.
