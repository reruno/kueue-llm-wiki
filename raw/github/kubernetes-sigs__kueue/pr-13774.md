### Review by [@tomsen02](https://github.com/tomsen02) (commented) — 2026-08-05T10:45:56Z

I did a deep pass with everything run locally (prow hasn't run the suites yet, so these were likely this PR's first real executions): reverting the non-test changes to the merge-base turns all the new assertions red (the focused integration spec 6/6 across repeats), and green with the fix. Two things genuinely worth calling out first:

- the changed snapshot assertion in `cohort joining cohort with cycle...` doesn't just cover the fix — it exposes and fixes a second, unreported bug: on `main` a *rejected* move still recomputes the old parent's tree, silently dropping its `SubtreeQuota`;
- repointing the now-unreachable cycle-guard tests at manually corrupted caches instead of deleting them keeps the downstream defense-in-depth covered. Nice.

One design note that doesn't belong to any single line: **"last valid state" is instance-local and not reconstructible from the API.** With the same two conflicting Cohort objects persisted, which edge survives a cache rebuild depends on delivery order — a long-running instance can hold `{a->b}` while a restarted/failed-over one ends with `{b->a}` (the edge that arrives before the cycle closes wins). To be clear, this PR is strictly better than `main` on restart too — today the rebuilt cache contains the cycle and the unguarded traversal can hang the controller at startup, which this fixes — so I'd only suggest documenting the order-dependence as a known trade-off (code comment / PR description), not changing the design here.

On the earlier comment about synchronizing the integration test: the timing concern is real in principle (nothing orders the cyclic-parent update before the root-capacity update), though empirically it's deterministic today — 6/6 red on merge-base with the default single-threaded cohort reconciler; it would need `groupKindConcurrency > 1` to bite. The catch is that the suggested fix isn't currently implementable: there is no rejection signal to wait on — no event (the cohort controller has no recorder), no condition (`CohortStatus` only has `fairSharing`), the rejection surfaces only as a generic reconcile error, and `RecordCohortMetrics` is skipped on rejection, so even `cohort_info` can't distinguish "not yet processed" from "rejected". Minimal in-scope step: include the rejected new parent and the retained old parent in the returned error and/or a dedicated log line; an Event or status condition could be a follow-up issue — and would give the test something sound to wait on.
