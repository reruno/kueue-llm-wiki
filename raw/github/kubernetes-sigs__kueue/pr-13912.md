## Description

Fixes #13911

### Summary

Follow-up to #13681. This PR caches `RuntimeClass` objects in the queue manager using event-driven handlers and passes the cached data to `workload.AdjustResources`, avoiding `client.Get` API calls when resolving pod overhead.

### Changes

- Added a thread-safe `RuntimeClasses` cache store in `pkg/cache/queue/runtime_classes.go`, with unit tests.
- Integrated the RuntimeClass cache into `Manager` and exposed it through `RuntimeClassCache()`.
- Updated `handlePodOverhead` and `AdjustResources` to accept cached RuntimeClasses instead of a `client.Client`.
- Added `RuntimeClass` event handling in `resourceUpdatesHandler` to keep the cache synchronized.
- Updated all `AdjustResources` call sites to use the RuntimeClass cache.

TLDR: main already watches RuntimeClass and LimitRange, so the `Get` and `List` being replaced are served from the manager's cache rather than the API server. That makes these stores a second copy of something the manager already keeps, and the copy behaves differently from the cached read in two ways I could measure. If I have missed a setting that takes RuntimeClass out of the manager cache, tell me and I will withdraw all of it.

Thanks for the tests that came with the stores. `runtime_classes_test.go` and the new `AdjustResources` cases made this quick to follow, and dropping the `error` return from `handlePodLimitRange` reads better than what was there.

### Where the premise sits

`SetupWithManager` on main already has both watches:

```go
Watches(&corev1.LimitRange{}, ruh).
Watches(&nodev1.RuntimeClass{}, ruh).
```

Nothing in the tree sets `client.CacheOptions.DisableFor` or `UnsafeDisableDeepCopy`, and `addCacheByObjectTo` in `pkg/config/config.go` special-cases only Secrets. So `r.client.Get(ctx, ..., &runtimeClass)` reads from that same informer and controller-runtime hands back a deep copy. Those calls were not reaching the API server.

### What the deep copy was doing

`Add` keeps the object the handler was given, and both readers return it unchanged, because `maps.Copy` copies keys while the values stay the same pointers:

```go
func (r *RuntimeClasses) Add(rc *nodev1.RuntimeClass) { r.store[rc.Name] = rc }
```

`handlePodOverhead` then assigns `podSpec.Overhead = rc.Overhead.PodFixed`. That line was fine while `rc` was a fresh copy out of `cl.Get`. Writing to the Workload now reaches the store:

```
wrote 99 to the Workload; the cached RuntimeClass now reads 99
```

No non-test code writes `Template.Spec.Overhead` today, so this is a sharp edge rather than something breaking right now. The object in the store is the one the informer delivered and every other consumer shares, which is why I would rather a Workload not hold a piece of it.

### Where the mirror can disagree with the cache

The store is written inside `resourceUpdatesHandler`, and handlers run once the shared cache has already taken the new object. A Workload event handled in between builds its footprint from the older overhead:

```
charged with the mirror one update behind: cpu=2000
charged with what the shared cache holds:   cpu=9000
```

`queueReconcileForPending` is the repair path, and it lists with `client.MatchingFields{indexer.WorkloadQuotaReservedKey: string(metav1.ConditionFalse)}`. A Workload that took a reservation inside that window falls outside the selector, so the older charge stays with it until it finishes. The cached `Get` had nothing between the informer store and the caller, so it had no second place to fall behind.

### One smaller thing

`RuntimeClasses.Get(name)` is there but unused. All five call sites take `GetAll()`, so every Workload event copies the whole map under the read lock in order to look up one entry. Threading the name down would keep it O(1) and would give the not-found error somewhere natural to be built.

### What I would suggest

Leaving `AdjustResources` on a `client.Reader` gets the same reads with no second store to keep in step:

```go
func handlePodOverhead(ctx context.Context, reader client.Reader, wl *kueue.Workload) []error {
	// unchanged body, cl.Get becomes reader.Get
}
```

and call sites pass `r.client`, which is already the cached one. `handlePodLimitRange` can keep the `[]corev1.LimitRange` parameter you gave it, since that part is a clean separation whichever way the data arrives.

If you would rather keep the stores, the two things that would close the gap for me are a `DeepCopy` on the way in or out so nothing hands out the informer's object, and something that lets accounting tell that the snapshot it read is at least as new as the shared cache, so it can wait instead of charging on the older value.

Worth saying that coderabbitai's open thread about retaining workloads after `AdjustResources` fails sits on the same seam. Both come from accounting now depending on a store that can be behind, where before it depended on a read that could not be.

I think one admitted-Workload reconstruction path is still bypassing the resource adjustment this PR is changing.

Supplying the adjusted Workload makes TAS usage 2 CPU and `Fits` returns false.

This appears pre-existing rather than introduced by this PR, but since this PR changes the `AdjustResources` inputs and call sites, should the `AddClusterQueue` reconstruction path be covered here, or tracked as a follow-up? A restart/reconstruction regression test would make the intended ownership clear.
