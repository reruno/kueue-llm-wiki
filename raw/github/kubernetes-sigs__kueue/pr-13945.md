#### What this PR does / why we need it:

Reverts commit `4ad84193cab895ee37cda6662f4a14394f72511b` from https://github.com/kubernetes-sigs/kueue/pull/13014 ("fix(pod): refuse adopting non-pod-group Workloads by group name").

The merged fix is incomplete. It guards only the adoption path — `FindMatchingWorkloads` in `pkg/controller/jobs/pod/pod_controller.go` — behind the `PodIntegrationValidateGroupOwner` feature gate, so a pod group no longer *adopts* a foreign Workload that merely happens to share its pod-group name.

The finalization path remains exposed. `(*Pod).ListChildWorkloads` (`pkg/controller/jobs/pod/pod_controller.go`) resolves the Workload purely by pod-group name, with no check that the Workload actually belongs to a pod group. That means the chain

```
JobReconciler.getWorkloads -> finalizeWorkloads -> workload.FinalizeOrphanedWorkload
```

(`pkg/controller/jobframework/reconciler.go`) can still strip the Kueue finalizer from, and then delete, an unrelated victim Workload. The core bug the original PR set out to fix is therefore still reachable, just via a different entry point.

Rather than leave a partial guard (and its feature gate) on `main`, we revert now and re-land a complete fix.

#### Which issue(s) this PR fixes:

None — this is a revert.

3. Re-land as a new PR that covers **both** the adoption path and the finalization path, with integration tests that reproduce the victim-Workload deletion scenario end to end.
