## Description

#### What type of PR is this?

/kind bug

#### What this PR does / why we need it:

A PodSet can carry a negative request. The Workload webhook refuses one only while `WorkloadValidateResourcesAreNonNegative` is enabled, and a Workload written before that check keeps what it has. Nothing after that told such a request apart from a resource nobody asked for: it was summed with whatever else was charged under the same name and paid for part of it, and because the total stayed positive, `FloorToZero` at the end saw nothing to correct. On main, a container requesting `example.com/gpu: -3` beside `example.com/credit: 8` with a transformation generating one gpu per credit comes out as:

```
before   example.com/gpu = 5
after    example.com/gpu = 8
```

The PodSet is charged 5 gpu where its transformation alone generates 8.

`PodRequests` now reads a negative request as zero before it aggregates. A zero pod-level entry is raised back to the container aggregate by the merge #16047 added for a too-small pod-level request, and a name nothing else asks for stays at zero, so a `multiplyBy` reading it scales by zero rather than by one. The spec the caller lent is copied first, and only when a negative is present, so a valid PodSpec takes the path it always took, and nothing here writes to the spec it was given.

The same reader serves quota, the TAS single-pod requests and the pod-level LimitRange check, so the three cannot disagree; the tests cover each of them.

#### Which issue(s) this PR fixes:

Fixes #14015

#### Special notes for your reviewer:

This is the negative-request half of the earlier version of this PR. The shared PodSpec reader it also carried is now the `PodRequests` that #16047 added, so the negative-request handling sits inside it. The one addition is `ContainerRequests`, the same reader without the overhead, which `subtractReplacedRequestsFrom` now uses so the DRA subtraction reads the same normalized container total. `negativeContainerRequestDoesNotInflateTheDRAReplacement` pins it: two containers asking 5 and -3 under a DRA charge of 8 come out at 8, where the raw total gives 11. That case guards the reader `subtractReplacedRequestsFrom` uses rather than the negative read itself, so it stays green under the mutant below and red if the raw container total is put back.

The cases that reproduce the undercharge fail without the change; making `hasNegativeRequest` always answer false turns exactly these red. In `TestPodRequests` they are the negative sidecar, the sidecar before an ordinary init container, the negative pod-level request no container asked for, and the negative overhead. In `TestNewInfo` they are `admitted with TAS and a negative sidecar`, `transformNegativeRequestDoesNotSpendAGeneratedOutput`, `transformNegativeInputDoesNotSpendWhatAnotherInputGenerated`, `transformNegativeMultiplierDoesNotSpendAGeneratedOutput`, `negativePodLevelMultiplierWithoutContainerFallbackStaysZero`, `negativePodLevelMultiplierWithNegativeFactorDoesNotOvercharge`, `negativeOverheadReadAsAMultiplierIsZeroRatherThanAbsent` and `negativeOrdinaryRequestDoesNotSpendPreprocessedDRACharge`, plus the `ComputeTASNetUsage` and `ValidatePodSpec` sidecar cases.

The rest already pass on main and pin what the copy must keep: the ordinary init container and the pod-level fallback in `TestPodRequests`, and in `TestNewInfo` `negativePodLevelCPUFallsBackToTheContainerAggregate`, `unsupportedPodLevelNameStaysOutOfTheCharge`, `normalizationKeepsAPodLevelRequestTheApiserverWouldAccept`, `explicitPodLevelZeroSurvivesTheNormalization` and `transformNegativeRequestOnItsOwnIsZero`. The `TestNewInfo` loop also checks that `NewInfo` leaves the Workload it was given unchanged, which is what guards the copy.

In the scheduler integration suite, a Workload whose container asks for 3 CPU beside a sidecar asking for -1, created with `WorkloadValidateResourcesAreNonNegative` off, is admitted at 3.

_Disclosure: I used an AI coding assistant while preparing this PR. I reviewed and tested every change myself._

#### Does this PR introduce a user-facing change?

```release-note
Scheduling: Fixed a bug where a negative resource request in a PodSet, accepted while `WorkloadValidateResourcesAreNonNegative` is disabled, could reduce the quota charged for another container, the pod overhead, or a resource transformation output under the same name. A negative request is now charged as zero, and the same total is used for the pod-level LimitRange check and TAS placement.
```

### Comment by [@thc1006](https://github.com/thc1006) — 2026-08-13T17:34:39Z

I force-pushed to drop the last commit, `bcfb51d2e`, so the head is now `1663c1aeb`. Nothing about negative accounting changed.

That commit was fixing a different bug that turned up while testing this one. `component-helpers` puts a pod-level request into the total by assignment rather than by copy, and the pod overhead is then added to that total in place, so a quantity holding a decimal is added to through the caller's own pointer. Measured with a pod-level `memory: 1.5Gi` beside an overhead of `100Mi`, the spec read 1636Mi after the first call, 1736Mi after the second and 1836Mi after the third, while a whole-unit `1Gi` never moves. It is the same thing as kubernetes/kubernetes#141241, and #141242 there is still open, so the version we build against still has it.

It does not belong here: it is on the positive path, it is on main without this PR, and the guard I had put in this file covered only one of the readers that hit it. It is now #14407, which detaches in the shared `pkg/resources` reader instead, so the admitted TAS reconstruction, TAS placement and net usage, the flavor overlap check, LimitRange validation and the TAS pod controller are covered by the same change, and it carries its own release note.

The immutability assertion added in `1663c1aeb` still passes without it, since none of its cases carries a positive pod-level request.
