#### What this PR does / why we need it:

Draft companion to #13601, so the count-based `firstAvailable` contract can be read as code rather than only as prose. Part of #13599.

For each top-level `firstAvailable` request it requires every alternative to use `ExactCount`, resolves each DeviceClass through `deviceClassMappings`, refuses unmapped and source-backed alternatives, requires them all to map to one logical resource, and charges the largest count among them. Independent requests stay additive, added exactly rather than saturated.

Classification happens once per request, so a request setting both `exactly` and `firstAvailable`, or neither, fails closed instead of reaching one walker and not the other. Every alternative's selectors go through the same compiler the `Exactly` path uses. The cluster cardinality check deliberately stays off, since only one alternative has to be satisfiable.

An unset `allocationMode` means `ExactCount` and an unset `count` means one, which is what the apiserver defaults them to. Objects that never went through it, in tests and fake clients, arrive here unset, so a subrequest naming only a DeviceClass is read the same way. That is an asymmetry with the `Exactly` path, which refuses an empty mode outright, and it is worth a decision rather than my quietly picking one.

`math.MaxInt64` is the `Unlimited` sentinel in `resources.Amount`, so a sum reaching it is refused rather than clamped: clamping there reports no limit, not a conservative one.

3. the unset mode and count reading above.

Deliberately not here, so this stays readable: envelope provenance through `WithPreprocessedDRAResources`, the checked merge, PodSet multiplication and cross-PodSet boundaries, MultiKueue fail-closed, and integration tests. Those are the following commits.

#### Does this PR introduce a user-facing change?

```release-note
DRA: Added the `KueueDRAIntegrationPrioritizedList` feature gate, alpha and disabled by default. With it enabled, a DRA `firstAvailable` request is charged the largest device count among its alternatives. Every alternative of one request must map to the same logical resource, and an alternative on a counter-backed or capacity-backed mapping is refused rather than charged. Kueue does not check that any alternative is satisfiable by the cluster, and MultiKueue does not support prioritized lists.

A ResourceClaimTemplate whose device count cannot be represented as a bounded quota amount is now refused when the Workload is admitted, rather than being charged a wrapped or saturated value. This check reads the charge the claim templates produce, so it applies to `exactly` requests as well and does not wait on the prioritized-list feature gate.

Both take effect for Workloads still waiting for quota. A Workload that already holds a quota reservation keeps the usage recorded in `status.admission` until that reservation is released and rebuilt.
```
