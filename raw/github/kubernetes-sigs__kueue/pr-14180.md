## Description

#### What type of PR is this?

/kind feature

#### What this PR does / why we need it:

Adds two gauge metrics that show how much quota can be lent out right now, based on current reservations:

- `kueue_cluster_queue_lendable_resources`: what a ClusterQueue can still lend to its peers, per flavor and resource. Quota covered by the ClusterQueue's own `localQuota` is not lendable, so only the part of its usage that spills past `localQuota` reduces the value. Inactive ClusterQueues report 0.
- `kueue_cohort_lendable_resources`: the same value summed over the Cohort's subtree. Series with a value of 0 are not exported.

To keep these metrics fresh, workload add, update and delete now report ClusterQueue and cohort metrics through one path. 
On ClusterQueue restore, metrics are reported once after all workloads are loaded. 
Workload events refresh only the cohort lendable metric. Full cohort metric refresh and cleanup are unchanged.

#### Which issue(s) this PR fixes:

Fixes #12282

#### Special notes for your reviewer:

- The ClusterQueue metric needs `metrics.enableClusterQueueResources`. The cohort metric needs the `MetricsForCohorts` feature gate.
- AI assistance (GitHub Copilot) was used. I reviewed and validated all changes.

#### Does this PR introduce a user-facing change?

```release-note
Observability: Add `kueue_cluster_queue_lendable_resources` (requires `metrics.enableClusterQueueResources`) and `kueue_cohort_lendable_resources` (requires the `MetricsForCohorts` feature gate). They report how much quota a ClusterQueue or Cohort can currently lend, per flavor and resource.

  I think this under-reports whenever a lendingLimit is set. Walking through it, since the
  mechanism is easy to miss.
  
  `localQuota` (resource_node.go:67) is the part of a ClusterQueue's nominal quota that is
  never lent out, `max(0, SubtreeQuota - LendingLimit)`. With nominal 10 and lendingLimit 6,
  localQuota is 4, and the remaining 6 is what the Cohort can see and hand to a peer.
  
  `addUsage` (resource_node.go:144-152) charges usage against that local 4 first, and only
  bubbles the excess up to the Cohort:
  
      localAvailable := LocalAvailable(node, fr)   // max(0, localQuota - Usage)
      r.Usage[fr] = r.Usage[fr].Add(val)
      if node.HasParent() && val.Cmp(localAvailable) > 0 {
          addUsage(node.parentHRN(), fr, val.Sub(localAvailable))
      }
  
  So with 4 CPU reserved, `val (4) > localAvailable (4)` is false, nothing reaches the
  Cohort, `cohort.resourceNode.Usage` stays 0, and a peer can still borrow the full 6.
  
  These two lines subtract the ClusterQueue's whole `Usage` from that slice:
  
      lendableSlice := SubtreeQuota - localQuota      // 10 - 4 = 6
      lendableAmt   := max(0, lendableSlice - Usage)  // max(0, 6 - 4) = 2
  
  The same 4 CPU is charged twice, once against localQuota inside `addUsage` and again here.
  The metric says 2 where the scheduler will lend 6.
  
  `available()` (resource_node.go:116-117) already keeps the right pair:
  
      storedInParent := r.SubtreeQuota[fr].Sub(lq)
      usedInParent   := max(0, r.Usage[fr].Sub(lq))
  
  `storedInParent - usedInParent` gives `6 - max(0, 4-4)` = 6. I checked it by adding an
  empty ClusterQueue to the same Cohort and reading `available()` on it, which is the
  function the scheduler uses for borrowing decisions: 6, not 2.

  localQuota is 0 and the two formulas are identical, and at usage 0 and at usage == nominal

  lendingLimit, and there the gauge reaches 0 while the ClusterQueue still has lending
  capacity left.
