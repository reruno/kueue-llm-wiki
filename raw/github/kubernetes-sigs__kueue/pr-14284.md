## Description

#### What type of PR is this?

/kind bug

#### What this PR does / why we need it:

Compatible workload slices are matched by PodSet shape and count. Changing a Job's `maximumExecutionTimeSeconds` therefore takes the compatible early-return path and leaves the live Workload slice with its previous timeout.

This change synchronizes an explicitly configured timeout to compatible live slices that are not admitted. A retained `Admitted=True` slice keeps its existing timeout, and a missing Job label does not clear an existing or defaulted value. Slice compatibility remains limited to PodSet shape and count, so timeout changes do not recreate Workloads.

#### Which issue(s) this PR fixes:

Part of #13836

#### Special notes for your reviewer:

The Workload API rejects timeout changes while a Workload remains Admitted=True, so a retained admitted slice keeps its existing timeout and the new value applies to non-admitted or replacement slices.

Tests cover pending, quota-reserved but not admitted, admitted, replacement, scale-up, and stale-status cases. An integration test verifies the update through the API server after quota reservation and before admission.

AI tools were used to assist with implementation and review. The final diff was manually reviewed and validated.

#### Does this PR introduce a user-facing change?

```release-note
ElasticJobsViaWorkloadSlices: Fixed a bug where changes to `maximumExecutionTimeSeconds` were not applied to compatible non-admitted Workload slices.
```
