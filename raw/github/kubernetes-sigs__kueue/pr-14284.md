## Description

#### What type of PR is this?

/kind bug

#### What this PR does / why we need it:

Compatible workload slices are matched by PodSet shape and count. Changing a Job's `maximumExecutionTimeSeconds` therefore takes the compatible early-return path and leaves the live Workload slice with its previous timeout.

This change synchronizes the Job's timeout to compatible live slices that are not admitted, including clearing the timeout when the Job label is removed. Admitted and finished slices keep their existing timeout. Slice compatibility remains limited to PodSet shape and count, so timeout changes do not recreate Workloads.

#### Which issue(s) this PR fixes:

Part of #13836

#### Special notes for your reviewer:

The Workload API rejects timeout changes while a Workload remains Admitted=True. Timeout synchronization skips admitted and finished slices, and applies changes to live non-admitted slices.

Tests cover adding, updating, and clearing timeouts across pending, quota-reserved but not admitted, admitted, finished, replacement, scale-up, and stale-status cases. An integration test verifies both updating and clearing the timeout through the API server after quota reservation and before admission, while preserving the Workload UID and quota reservation.

AI tools were used to assist with implementation and review. The final diff was manually reviewed and validated.

#### Does this PR introduce a user-facing change?

```release-note
ElasticJobsViaWorkloadSlices: Fixed a bug where changes to or removal of the Job's maximum execution time label were not applied to compatible non-admitted Workload slices.
```

**Security architecture risk:** **🔵 Low** · up to `6934f`

Execution limits remain protected after admission. A bounded lifecycle risk remains: a newly created Job with a reused name can change a surviving, non-admitted slice from the previous Job identity. This exposure is confined to matching slices in the same namespace.

**Retained concerns**
- **Low · security · inferred:** A recreated Job can overwrite or clear a previous Job identity's execution limit if a compatible, non-finished Workload survives with the same owner name and GVK. Slice selection does not compare owner UID, and the new writer checks admission and completion but not ownership. The selector already existed; this PR newly exposes the timeout field through it. Namespace isolation, admission immutability, and cleanup bound the concern.

**Security Blast Radius**
- _observed_ — Each production synchronization call targets at most the returned slice and one distinct retained quota-reserved slice in the Job's namespace. The timeout writer skips admitted and finished objects. Entry into this production path requires workload slicing to be enabled for the Job.

**Security Findings and Attack Paths**
- _inferred_ — An actor authorized to create a managed elastic Job under a reused name can supply a timeout, or omit it, that is copied onto a surviving previous-UID Workload. This requires matching namespace and owner GVK/name, compatible slice selection, and a target that is neither admitted nor finished. The controller performs the write without requiring the actor to update that Workload directly. The additional timeout mutation is new; name-based selection and other slice mutations predate this PR. No operational exploit was demonstrated.

**Trust Boundaries and Controls**
- _observed_ — Admission protection has two layers: the writer checks refreshed state, and the API rejects timeout changes while admission remains true. Strict patches include resource version, and conflict retries refresh before re-running the checks. These controls protect state transitions but do not establish ownership identity.

**Resilience and Maintainability Implications**
- _observed_ — Deletion finalization can finish orphaned workloads and release their finalizers, but it is not a prerequisite to the compatible-path timeout write. The ordinary matching path has a feature-gated UID check that the compatible slice path bypasses. The Workload controller's orphan predicate requires missing owner references, so it does not itself reject a surviving stale reference before synchronization.
