## Description

#### What type of PR is this?

/kind bug

#### What this PR does / why we need it:

`handlePodOverhead` only read the RuntimeClass when the PodSet template carried no overhead of its own:

```go
if podSpec.RuntimeClassName != nil && len(podSpec.Overhead) == 0 {
```

On a Pod that is safe, because the apiserver will not let the two disagree. Measured against v1.36.3 with a server-side dry run, against a RuntimeClass defining `cpu: 250m`:

```
overhead, no runtimeClassName        rejected: Pod Overhead set without corresponding RuntimeClass defined Overhead
overhead, runtimeClass not found     rejected: RuntimeClass "nosuchclass" not found
overhead 250m, class 250m            accepted
overhead 1m,   class 250m            rejected: Pod's Overhead doesn't match RuntimeClass's defined Overhead
```

Only the matching shape survives, so at create time the two always agree. A Workload is not a Pod, and nothing runs that check on `podSets[].template.spec`. One written directly, or a prebuilt Workload for a Job, can name a class defining `250m` while carrying `1m`. Kueue charged the `1m`; the Pods the Job creates go through the admission controller and get `250m`.

The class cannot simply win, though. A PodSet copied off a Pod that already exists carries what the apiserver actually gave that Pod, and the class is free to be edited afterwards, since only `handler` is immutable and the admission that writes the overhead runs on create. Rewriting such a PodSet from the class as it stands now can lower the charge below what the Pod it will ungate carries.

So take the larger of the two, per resource. A template carrying less than its class, or none at all, is charged the class. A PodSet carrying more keeps what it has.

That holds where the maximum is taken and no further. What a Workload finally reserves is this figure after exclusions, resource transformations and DRA processing, and those can move it either way. A transformation may write a negative output factor as a per-unit allowance, so raising an overhead can lower the total it generates. That is the configured policy doing what it was asked, and it is why the claim stops at the adjustment rather than at the quota.

Raising to the class the Workload names is only the right charge if that is also the class the Job names, and `comparePodTemplate` did not read `runtimeClassName` at all, so a prebuilt Workload could point at a cheaper class, or at none, and still be accepted as equivalent. A Workload naming no class has nothing to raise it to, so without this the same undercharge comes back through a prebuilt Workload. The comparison now includes the class, and such a Workload is finished for reason `OutOfSync`.

#### Which issue(s) this PR fixes:

Fixes #14274

#### Special notes for your reviewer:

An earlier revision decided per Workload whether its PodSets had been copied off Pods, by looking for a `core/v1` Pod among the owner references, and left those alone. That was wrong twice over. A StatefulSet builds its Workload from `sts.Spec.Template.Spec`, which never passes the admission that writes overhead, and the pod controller then adds the created Pods as owner references; on that update the rule read the Workload as Pod-built and stopped resolving the class, a regression against `main`. And owner references are user-settable, so one extra line of metadata turned the lookup off. Taking the maximum needs neither question answered, so the helper and the notion of provenance are gone.

One behaviour change worth flagging: the class is now resolved for every PodSet that names one, where before it was resolved only for those carrying no overhead. `AdjustResources` logs what `handlePodOverhead` returns without acting on it, so nothing that used to be admitted stops being admitted. What does change is that a Workload naming a class Kueue cannot read, while carrying overhead of its own, now logs an error on each adjustment where it used to be silent. The errors still go nowhere else, which is #9030.

`Overhead` deliberately stays out of the template comparison. A Job template never passes through the RuntimeClass admission that writes it, so the class name is the field carrying the provenance and the overhead is derived from it.

#13995 changes the same loop, adding a `ChargeableOverhead` call that drops a negative or `pods` entry from every PodSet before anything reads it. The two compose in that order: an entry that will not be charged is dropped, and what is left is raised to the class.

A failed lookup still leaves the template alone rather than zeroing it. Zero is not the conservative reading of a class nobody could resolve, and making that fail closed is #9030, not this.

Tests. `TestEffectivePodSpecs` has the PodSet carrying less than its class, more than it, a key the class does not define, and two resources each taking their own larger value. `TestComparePodSetSlices` has the same class, different classes, and a class on one side only. In the scheduler integration suite a Workload carrying `1m` against a class defining `250m` is charged the `250m`, and in the Job suite a Job naming a class whose prebuilt Workload names none is adopted and then finished for reason `OutOfSync`, beside the existing case that asserts the same adoption without the Finished condition. Each half was reverted separately. Putting the `len(overhead) == 0` condition back fails `own overhead below the class`, `own overhead key the class does not define` and `each resource takes its own larger value`. Taking the minimum instead of the maximum fails `own overhead below the class`, `own overhead above the class`, `each resource takes its own larger value` and the existing `Handle runtimeClass with podOverHead` case. Dropping the `runtimeClassName` line from the comparison fails the two `TestComparePodSetSlices` cases that differ on the class and the Job spec, which times out waiting for the Finished condition.

The upgrade shape in the release note is why I opened #14395 rather than widening this PR. Reaching the state it describes needs an admitted Workload and a running Job that stop matching, and neither side can move once quota is reserved: `validateImmutablePodSets` freezes the whole PodSet, template included, and a Job's `spec.template` is immutable to the apiserver. Changing the comparison is the one thing that can reach it, and `git log -S comparePodTemplate` finds no field added since `c03612ea9` moved it into the framework, so this is the first PR that would. The ordering itself is untouched here, and I would rather #14395 landed first; the release note is what operators need if it does not.

#13912 is the other change to this function. Its branch still carries `if podSpec.RuntimeClassName != nil && len(podSpec.Overhead) == 0` as an unchanged line and still assigns `podSpec.Overhead = rc.Overhead.PodFixed`, so taking its side of a conflict reopens #14274. Whichever lands second has to keep the shape rather than the lines: resolve the class whenever one is named, then take the per-resource maximum.

Rebased on 30 September and squashed to one commit.

#### Does this PR introduce a user-facing change?

```release-note
RuntimeClass: Fixed a bug where a Workload naming a RuntimeClass was charged only the pod overhead its PodSet carried, even when the class defines more. Kueue now charges the larger of the two per resource, and a prebuilt Workload must name the same RuntimeClass as its Job to be accepted for it.

ACTION REQUIRED: If a prebuilt Workload names a different RuntimeClass from its Job, or none while its Job names one, bring the two into agreement before upgrading, or drain those Jobs first; the first reconcile after the upgrade otherwise finishes that Workload for reason `OutOfSync` and releases its quota while its Pods keep running (#14395). Workloads that name a RuntimeClass and have not yet reserved quota may need more quota than before, since they are now charged the overhead their class defines. A Workload that already holds a quota reservation keeps the usage recorded in its `status.admission` until that reservation is released.
```
