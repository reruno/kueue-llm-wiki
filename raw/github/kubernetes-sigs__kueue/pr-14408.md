#### What this PR does / why we need it?

With `podSetMergePolicy` set, `mergePodSets` folds the PodSets that the policy treats as equivalent into one, under the name of the first. The ProvisioningRequest then carries one PodSet per group. When the request was provisioned, `podSetUpdates` emitted one `PodSetUpdate` per PodSet of the request, under that first name, and the other members of the group got none.

The job framework looks updates up by exact PodSet name and moves on when there is none. The Pods of those PodSets started without the ProvisioningRequest annotations and without the nodeSelector from the config's `podSetUpdates`, so nothing ties them to the capacity provisioned for them, and they can land on nodes outside it.

The grouping is now recorded on the ProvisioningRequest when it is created, in the `kueue.x-k8s.io/provisioning-podset-groups` annotation, and `podSetUpdates` gives each member of a group the group's update.

There is no issue for this. I found it while reading the merge path.

#### Useful notes for your reviewer

The grouping is recorded because a request's spec can't change while the configuration it came from can. `managedResources` and `podSetMergePolicy` may change while a request is in flight, and `provReqSyncedWithConfig` checks neither, so the request stays in use. For an elastic slice, the previous slice's counts are also subtracted before merging (#14316), so a PodSet with nothing new drops out and the group can end up under another name. Merging again once the request is provisioned could give the updates to a different set of PodSets than the capacity was requested for.

A request created before this change has no annotation and keeps the old reading, one PodSet per pod template, so its updates stay the same after an upgrade. Workloads whose admission check already passed are not revisited.

`podSetUpdates` can now return an error. It does when the recorded grouping maps a pod template of the request to no PodSet or gives one PodSet to two templates, and when the annotation can't be parsed. Like a `reqIsNeeded` error, it aborts the status patch and ends the reconcile before any request is created or deleted, so an update that another check staged in the same patch is dropped too. #14414 deals with that same problem, one check dropping the others' updates, for a check whose request is missing.

`TestPodSetUpdates` covers the mapping, and a new integration spec takes a merged request to `Provisioned` and checks the full update, nodeSelector included, on both PodSets. The existing merge spec stops before the request is provisioned, which is how this went unnoticed. The spec and two of the unit cases fail when only the first PodSet of a group gets the update.

This pull request was written in part with the assistance of generative AI.
