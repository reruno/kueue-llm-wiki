#### What this PR does / why we need it?

With `podSetMergePolicy` set, `mergePodSets` folds the PodSets that the policy treats as equivalent into one, under the name of the first. The ProvisioningRequest then carries one PodSet per group. When the request was provisioned, `podSetUpdates` emitted one `PodSetUpdate` per PodSet of the request, under that first name, and the other members of the group got none.

The job framework looks updates up by exact PodSet name and moves on when there is none. The Pods of those PodSets started without the ProvisioningRequest annotations and without the nodeSelector from the config's `podSetUpdates`, so nothing ties them to the capacity provisioned for them, and they can land on nodes outside it.

When the request is provisioned, the PodSets are merged again, and every PodSet merged into one of its PodTemplates gets the update.

This needs #18627 first, which keeps a PodSet with a GPU only in its limits from merging with one that has none; otherwise that PodSet would get the update of a request provisioned without GPUs.

There is no issue for this. I found it while reading the merge path.

#### Useful notes for your reviewer

Merging again can give other groups if `podSetMergePolicy` or an assigned flavor changed in between. A group whose count differs from the count in the request is then not trusted, and only the PodSet its PodTemplate is named after gets the update, as on main. For an elastic slice, the request covers the increment over the slice it replaces, named in `kueue.x-k8s.io/workload-slice-replacement-for`. If that slice is deleted before the request is provisioned, for example by `objectRetentionPolicies`, the PodSets are not merged again.
