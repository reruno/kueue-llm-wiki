## Description

#### What type of PR is this?

/kind bug

#### What this PR does / why we need it:

`quotaResourcesToReserve` has two branches for a preempting entry, and only one of them clamps:

```go
if e.assignment.Borrowing > 0 {
	if cqQuota.BorrowingLimit == nil {
		reservedUsage[fr] = usage
	} else {
		reservedUsage[fr] = resources.MinAmount(usage, cqQuota.Nominal.Add(*cqQuota.BorrowingLimit).Sub(cq.ResourceNode.Usage[fr]))
	}
} else {
	reservedUsage[fr] = resources.MaxAmount(resources.NewAmount(0), resources.MinAmount(usage, cqQuota.Nominal.Sub(cq.ResourceNode.Usage[fr])))
}
```

`Nominal + BorrowingLimit - Usage` is negative once usage sits above the cap, and nothing brings it back to zero. `reserveCapacityForUnreclaimablePreempt` then hands the result to `snapshot.AddUsage`, which puts the ClusterQueue's usage in the snapshot below what its admitted workloads hold. A later preemptor that removes those workloads in its fit check then frees less capacity than they hold, so it can fail to fit and skip preempting in that cycle.

A ClusterQueue with nominal 10 and borrowing limit 5, already using 20, against an entry that wants 4:

```
Borrowing>0 branch  (as written) -> -5
Borrowing==0 branch (clamped)    ->  0
```

Same shape of input, opposite sign, purely because one branch kept the guard and the other did not.

#### Which issue(s) this PR fixes:

None filed; I found this reading the two branches side by side.

#### Special notes for your reviewer:

Reaching it needs an assignment in Preempt mode that borrows, a ClusterQueue already over `nominal + borrowingLimit`, no preemption candidates, and either `reclaimWithinCohort` not `Any` or, with `PrioritizePreemptorWorkloads`, an entry that is already a preemptor. I'd expect that only after a quota or borrowing limit shrank under admitted workloads. The effect lasts one scheduling cycle. The `TestSchedule` case below reaches it end to end with `PrioritySortingWithinCohort` disabled, so that the entry without candidates runs before the preemptor; I did not find a case with the default ordering.

`TestResourcesToReserve` already drives this function. The diff adds two cases to it, "Reserved gpu is what is left under the borrowing limit, assignment preempts while borrowing" (usage 12, wants 4, reserves 3) and "Reserved gpu is zero when usage is already past the borrowing limit, assignment preempts while borrowing" (usage 20, wants 4, reserves 0), so the clamp is pinned without hiding the normal answer. With the production line reverted the first still passes and the second fails with a reserved amount of -5.

The new `TestSchedule` case, "capacity reserved for a preemptor past the borrowing limit does not block preemption of its ClusterQueue", has ClusterQueueA at 20 against nominal 5 plus borrowing limit 5, and a preemptor in another ClusterQueue that fits only by preempting both of its workloads. With the production line reverted, the preemptor gets `WaitingForQuota` and nothing is preempted.

#### Does this PR introduce a user-facing change?

```release-note
Preemption: Fixed a bug where the capacity reservation made when a preempting Workload finds no candidates could go negative for a ClusterQueue already using more than its nominal quota plus borrowing limit, which could keep another Workload from preempting that ClusterQueue's workloads in the same scheduling cycle.
```
