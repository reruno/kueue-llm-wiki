#### What this PR does / why we need it:

`syncCheckStates` handles every provisioning admission check on a workload inside one status patch. A check that needs a ProvisioningRequest and does not have one yet returned from the callback:

```go
pr := activeOrLastPRForChecks[check]
if pr == nil {
	return false, nil
}
```

That is not a skip. `PatchStatus` treats a `false` answer as "nothing to write" and never issues the patch, so anything the loop had already staged for the other checks is dropped, including a check that had just gone `Provisioned` and staged `Ready`. The map is iterated in random order, so which checks had already been staged before the return varies from one reconcile to the next.

The events go out anyway. `updated` and `recorderMessages` are declared outside the callback, and the caller reads the closure variable rather than the callback's answer:

```go
updated := false
err := workloadpatching.PatchStatus(..., func(wlPatch *kueue.Workload) (bool, error) { ... })
...
if updated {
	for i := range recorderMessages {
		c.record.Eventf(wl, ..., "UpdatedAdmissionCheck", ...)
	}
}
```

So the workload gets an `UpdatedAdmissionCheck` event for a transition that was not saved, and can get it again on later reconciles, whenever the iteration happens to reach that check before the one without a request. Once the other check gets its request, the next reconcile writes the patch. It never does if the check without a request is one that already went `Ready` and lost it, since the controller only creates a request for a `Pending` check, and the checks still waiting stay `Pending` behind it.

Skipping just that check fixes both halves: the callback ends up answering with the same variable the events are gated on, so a patch that does not happen no longer announces itself.

With two checks, one already `Ready` and holding no request and one whose request has just gone `Provisioned`, the reconcile test asserts the second is persisted as `Ready` with its PodSet updates. Reverting the `continue` leaves it `Pending`.

#### Which issue(s) this PR fixes:

None filed; I found this reading the callback's early return against the closure variables above it.

#### Special notes for your reviewer:

The unit case sits in `TestReconcile` beside the other provisioned-request cases: `check1` is `Ready` and has no request, `check2`'s request is `Provisioned`, and the workload must come out with `check2` `Ready` and one `UpdatedAdmissionCheck` event for it. The integration test reaches the same state through the API: a check that is already `Ready` gets no replacement request, since the controller only creates one for a `Pending` check, so deleting its request leaves it without one while the second check is still waiting for its own. The second check has to turn `Ready` once that request is provisioned, and without the fix it never does.

Reverting the `continue` turns both red on the surviving check's state rather than on an event count, which is the part that matters: the events were only ever a symptom of the patch not going out.

While writing it I noticed that the same function dereferences `retryStrategy` without a guard a few lines below. The CRD defaults that field, so a config cannot reach the controller without it; I first sent a guard for it as #14415 and closed that once I saw the default.
