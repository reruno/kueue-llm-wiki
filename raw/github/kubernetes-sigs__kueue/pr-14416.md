#### What this PR does / why we need it?

Kueue decides whether an existing ProvisioningRequest still matches its ProvisioningRequestConfig in `provReqSyncedWithConfig`. That check only looked one way: every parameter in the config had to be on the request with the same value.

When a parameter was removed from the config, the request kept it and still counted as in sync, so it was never replaced.

When a Workload's `provreq.kueue.x-k8s.io/` annotation set a parameter that the config also sets, the request got the annotation's value, as the docs describe, and then failed the check right after Kueue created it. Kueue deleted and recreated it on every reconcile, and the admission check never left Pending.

Now one function, `provReqParameters`, builds the parameters for a new request, and a request is in sync only when its parameters are exactly those. Both problems go back to #1869, so every supported release has them.

#### Useful notes for your reviewer

Editing a provreq annotation on an existing Workload now also makes its request stale, the same as a config change would. Kueue itself only copies these annotations when it creates the Workload.

On upgrade, a request whose config has since dropped one of its parameters, or whose Workload's provreq annotations changed after it was created, is replaced if its check is Pending. A check that is already Ready stays Ready, and its old request is deleted without a new one, as happens today when the config changes. On a Workload with two provisioning checks, the missing request then stops `syncCheckStates` from updating the other check; #14414 fixes that.

With the old one-way comparison put back, three rows of the new unit table fail: a dropped parameter, an overriding annotation and a changed annotation. The config sync spec then fails at the dropped parameter, and the new spec times out with the check still Pending.

#### Release note

```release-note
ProvisioningRequest: Fixed a bug where a `provreq.kueue.x-k8s.io/` Job annotation that overrides a ProvisioningRequestConfig parameter made Kueue delete and recreate the ProvisioningRequest on every reconcile, so the admission check stayed Pending. Kueue now also replaces the ProvisioningRequest of a pending admission check when the request still carries a parameter that was removed from the ProvisioningRequestConfig.
```

The change preserves existing parameter precedence and does not add permissions or public endpoints. However, newly detected stale requests can expose an existing multi-check synchronization defect, potentially preventing later readiness, failure, or capacity-revocation updates for the affected workload.

**Retained concerns**
- **Medium · reliability · inferred:** Newly recognized parameter mismatches can delete a Ready check's request without replacing it. The defective branch predates this PR, but parameter removal and annotation mutation expand its triggers.
