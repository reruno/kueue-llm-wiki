#### What this PR does / why we need it?

Kueue decides whether an existing ProvisioningRequest still matches its ProvisioningRequestConfig in `provReqSyncedWithConfig`. That check only looked one way: every parameter in the config had to be on the request with the same value.

When a parameter was removed from the config, the request kept it and still counted as in sync, so it was never replaced.

When a Workload's `provreq.kueue.x-k8s.io/` annotation set a parameter that the config also sets, the request got the annotation's value, as the docs describe, and then failed the check right after Kueue created it. Kueue deleted and recreated it on every reconcile, and the admission check never left Pending.

Now one function, `provReqParameters`, builds the parameters for a new request, and a request is in sync only when its parameters are exactly those. Both problems go back to #1869, so every supported release has them.

#### Useful notes for your reviewer

Editing a provreq annotation on an existing Workload now also makes its request stale, the same as a config change would. Kueue itself only copies these annotations when it creates the Workload.

On upgrade, a request whose config has since dropped one of its parameters, or whose Workload's provreq annotations changed after it was created, is replaced if its check is Pending. A check that is already Ready stays Ready, and its old request is deleted without a new one, as happens today when the config changes. On a Workload with two provisioning checks, the missing request then stops `syncCheckStates` from updating the other check; #14414 fixes that.

With the old one-way comparison put back, three rows of the new unit table fail: a dropped parameter, an overriding annotation and a changed annotation. The config sync spec then fails at the dropped parameter, and the new spec times out with the check still Pending.

ProvisioningRequest: Fixed a bug where a `provreq.kueue.x-k8s.io/` Job annotation that overrides a ProvisioningRequestConfig parameter made Kueue delete and recreate the ProvisioningRequest on every reconcile, so the admission check stayed Pending. Kueue now also replaces the ProvisioningRequest of a pending admission check when the request still carries a parameter that was removed from the ProvisioningRequestConfig.

### Security Architecture Review

**Security architecture risk:** _🟡 Moderate_ · up to `91ac3`

Exact matching fixes stale parameters and supports the documented annotation precedence. However, newly stale requests for Ready checks can be deleted without replacement, preventing other provisioning checks from publishing failure or capacity-revocation updates. This expands an existing lifecycle weakness; it does not introduce new parameter-override privileges.

**Retained concerns**
- **Medium · reliability · inferred:** Changing a Workload provisioning annotation or removing a config parameter can now exclude a Ready check's request from the active map. Cleanup deletes that request, but creation skips Ready checks. The missing request then aborts the entire admission-check synchronization batch; in the inspected server-side-apply path, sibling checks cannot publish updates, including CapacityRevoked rejection. The lifecycle defect predates this PR, but the new compatibility predicate expands its triggers and can leave provisioning enforcement out of sync until the missing-request condition is repaired.

<details>
<summary>Security review details</summary>

**Security Blast Radius**
- _inferred_ — A principal permitted to edit a Workload's metadata can trigger the stale-request behavior for that Workload and its provisioning checks. An authorized editor of a shared config can affect multiple dependent Workloads by removing parameters. The inspected controller operates on owned requests within each Workload namespace; broader tenant exposure depends on permission bindings and config usage.

**Security Findings and Attack Paths**
- _inferred_ — A conditional control-drift path is supported: edit provisioning metadata after a check becomes Ready, invalidate its request, and cause cleanup without replacement. The missing request can then suppress publication of sibling provisioning failures or revocation in the inspected server-side-apply path. This is an expanded recovery and enforcement weakness, not a demonstrated cross-tenant exploit or new privilege grant.

**Trust Boundaries and Controls**
- _observed_ — Parameter annotations are intentionally user-controlled pass-through inputs, not trusted enforcement values. Config selection still determines the provisioning class, and provider status remains the normal admission authority. Prefix filtering selects inputs but does not validate their operational meaning; external provider validation was not available for assessment.

**Resilience and Maintainability Implications**
- _observed_ — Continuation of an already admitted Workload after request deletion is intentional and covered by an existing test. The added tests establish Pending parameter removal and creation-time override success, but do not establish isolation of sibling checks after post-Ready mutation. The concern is loss of independent status enforcement, not continuation by itself.
