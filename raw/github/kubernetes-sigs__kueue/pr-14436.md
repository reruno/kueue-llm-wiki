#### What this PR does / why we need it:

`equality.comparePodTemplate` (`pkg/util/equality/podset.go`) backs `EquivalentToWorkload`, which decides whether a Job's generated PodSets are equivalent to an existing (e.g. prebuilt) Workload's PodSets and can be adopted as-is. It compared `Tolerations`, `InitContainers` and `Containers`, but not `PodSpec.Resources` (pod-level resources) or `PodSpec.ResourceClaims` (DRA claims). Both are read when Kueue accounts for a PodSet's requests, so a prebuilt Workload could omit either field while still comparing equal to a Job whose Pods actually carry them, letting the Workload under-charge for what its Pods request.

This PR adds the same `equality.Semantic.DeepEqual` check already used for `Containers`/`InitContainers`/`Tolerations` for `PodSpec.Resources` and `PodSpec.ResourceClaims`.

```

  `PodSpec.ResourceClaims` is declared as a map list (`+listType=map`, `+listMapKey=name`), so its ordering is not semantically significant. However, `Semantic.DeepEqual` compares slice elements by position; for example, claims `[a, b]` and `[b, a]` are reported as different. For a prebuilt Workload produced independently from the Job, this could incorrectly mark an otherwise equivalent Workload as `OutOfSync`. Could we compare the claims order-independently (keyed by name) and add a reversed-order test?
