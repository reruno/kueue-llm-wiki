## Description

#### What type of PR is this?
/kind bug

#### What this PR does / why we need it:
The Workload CEL rule that makes `spec.maximumExecutionTimeSeconds` immutable keys on the `Admitted` condition:

```
... oldSelf.status.conditions.exists(c, c.type == 'Admitted' && c.status == 'True') ...
message="maximumExecutionTimeSeconds is immutable while workload quota reserved"
```

but its message says "while workload quota reserved". A `QuotaReserved` workload that is not yet `Admitted` can still change the field, so the message names the wrong condition. The `Admitted` keying is what KEP-3125 specifies ("immutable, while the workload is admitted"), and `reconcileMaxExecutionTime` only enforces the limit once the workload is admitted, so the rule is right and the message is what's off.

This corrects the message to "while the workload is admitted" for both the v1beta1 and v1beta2 Workload CRDs, and regenerates the manifests and Helm chart CRDs. The rule itself is unchanged.

#### Which issue(s) this PR fixes:
None filed separately; details above.

#### Special notes for your reviewer:
Message-only change; the CEL condition is unchanged, so there is no behavioural test change. CRDs regenerated with `make manifests` and `make update-helm`.

Prepared with AI assistance (Claude Code); disclosed per the project's AI contribution policy, and the commit carries no AI trailers.

_Disclosure: I used an AI coding assistant while preparing this PR. I reviewed and tested the change myself._

#### Does this PR introduce a user-facing change?
```release-note
Workload: Fixed the validation message shown when changing `spec.maximumExecutionTimeSeconds` on an admitted Workload to say "immutable while the workload is admitted" instead of "while workload quota reserved".
```
