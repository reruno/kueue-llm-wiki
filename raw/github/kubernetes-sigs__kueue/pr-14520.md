#### What this PR does / why we need it?

`Requests` sums the per-Pod request of a PodSet into an int64 that saturates at `math.MaxInt64`. `PodSetResources.ScaledTo` then rebuilt the request for a different Pod count by dividing that total by the old count and multiplying by the new one. Once the total had saturated, the division produced a number that no longer meant anything, and partial admission compared that number with the quota.

Three Pods asking for 4e18 each total 12e18, which saturates to `MaxInt64`. With a quota of 7e18, partial admission tried two Pods, divided `MaxInt64` by 3 and multiplied by 2, got 6148914691236517204, found that it fit, and admitted two Pods that really need 8e18. One Pod, which fits at 4e18, was the right answer.

The pending PodSet already keeps its processed per-Pod request in `PerPodRequests`, so `ScaledTo` now multiplies that by the new count instead of dividing the total. The admitted path is unchanged: `totalRequestsFromAdmission` has no per-Pod value and keeps dividing the admitted total, which is exact unless that total had already saturated when it was admitted. An earlier version of this PR kept `MaxInt64` fixed under division; that treated an exact total of `MaxInt64` (seven Pods asking `MaxInt64/7` each) as if it had overflowed, so reclaiming six of them released nothing.

Because partial admission now depends on `PerPodRequests`, `computeSchedulingHash` and `sameHashedRequests` read it as well. Container requests reach the hash per Pod through `SpecShape`, but DRA charges only through the total, so two pending Workloads that differ only in their per-Pod DRA charges could share an equivalence hash once their totals saturate. In a `BestEffortFIFO` ClusterQueue, one that does not fit could then move the other to inadmissible with it. The zero-count probe in `probeRequestsFor` already read `PerPodRequests`, which the hash missed in the same way: with a count of 0, the total hides the per-Pod DRA charge.

Two scheduler integration specs cover the two outcomes: partial admission picks one Pod charged 4e18 rather than two Pods charged 6148914691236517204, and reclaiming six of seven Pods whose total is exactly `MaxInt64` lets a waiting one-unit Workload in. `TestAssignFlavors` checks the reduced counts directly, `TestPodSetResourcesScaledTo` the arithmetic, and `TestSchedulingHash` and `TestSameHashedRequests` the hash.

A total that saturates before any scaling still fits a quota of `MaxInt64`, for example seven Pods asking 1.4e18 each, because the saturated sum equals the quota. A reduced count whose total still overflows saturates the same way: with five Pods asking 4e18 each against a `MaxInt64` quota and a CPU quota that allows four, the scheduler now charges four Pods `MaxInt64`, where main charged them 7378697629483820644 and admitted them. The webhook rejects that admission because `MaxInt64` is not a multiple of 4, and the scheduler keeps retrying it without setting a condition, as main already does when a full count's total saturates and the count does not divide `MaxInt64`. Both come from `Requests` saturating at `MaxInt64`. #16405 tracks keeping `Requests` exact, and #16479 is the open PR for it.

Part of #14371.

#### Useful notes for your reviewer

The reclaim spec needs more than one Pod and an exact total of `MaxInt64`, and 7 is the smallest count above one that divides `MaxInt64`, which is `7 * 1317624576693539401`. An exact total always passes the webhook's divisibility check.

Both specs were run against the previous code as well. With the division on `main`, the partial-admission spec fails because two Pods are admitted (`Expected <int32>: 2 to equal <int32>: 1`) and the reclaim spec passes. With the earlier version of this PR, which kept `MaxInt64` fixed under division, the partial-admission Workload is never admitted and the reclaim spec's waiting Workload stays pending, so both fail.
