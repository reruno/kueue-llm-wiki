## Description

Cherry pick of #14138 on release-0.18.

#14138: Backfill queue-name onto LeaderWorkerSet pods

The automated cherry-pick (#14492) did not merge, so this is the manual pick per @tenzen-y's request. Two branch-specific adjustments were needed on top of the original commit, so the diff is not identical to #14138:

1. **Added the `utilpod` import.** This branch's import block does not have `sigs.k8s.io/kueue/pkg/util/pod`, so the two `utilpod.HasGate(...)` calls from the picked commit did not compile. `HasGate` and `SchedulingGateName` both already exist on this branch, so nothing else had to be backported.
2. **Added `Queue("queue")` to `wantPods`** of `should set default values even if queue-name changed and workload has quota reservation`. The patch applied that label to the test's input pod but not to its expectation, which is the same reason the unit tests failed on the release-0.19 automated pick (#14491).

Verified locally on release-0.18: `gofmt`/`go vet` clean, and `./pkg/controller/jobs/...` plus `./pkg/controller/jobframework/...` pass. Reverting the reconciler to the branch version leaves the 31 pre-existing `TestReconciler` cases passing and only the two new ones failing.

Note: #14492 also failed `pull-kueue-test-scheduling-perf-release-0-18` and `pull-kueue-test-tas-scheduling-perf-release-0-18`. Those do not reproduce locally and look unrelated to this change, but flagging them in case they are known issues on this branch.

/kind bug
/area integrations

```release-note
LeaderWorkerSet: Fixed a bug where Pods of a LeaderWorkerSet admitted before the queue-name write moved into the LWS webhook could stay permanently SchedulingGated after an upgrade, eventually deactivating the Workload. Kueue now sets `kueue.x-k8s.io/queue-name` on LeaderWorkerSet Pods when adopting them and reconciles it on already-adopted gated Pods.
```
