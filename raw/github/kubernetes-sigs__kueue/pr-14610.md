## Description

#### What type of PR is this?

/kind cleanup

#### What this PR does / why we need it:

Optimizes the classical preemption candidate pool collection. Previously
`NewCandidateIterator` always collected and sorted all three candidate pools
(same-queue, hierarchy, priority) before the caller decided — via a
short-circuit — that some of them could not help the incoming workload.

This PR classifies the preemptor cluster queue's post-admission quota position
and skips the O(N) cohort scan for hierarchy/priority candidates when they
provably cannot free usable space (the queue would exceed its borrowing limit,
or it is already borrowing with cohort borrowing forbidden and no hierarchical
candidate). The result is behavior-preserving — the skipped pools are exactly
the ones the caller's existing short-circuit would have discarded — while
avoiding wasted collection and sorting on the hot preemption path.

#### Which issue(s) this PR fixes:

Related to #14608

#### Special notes for your reviewer:

The change is intended to be behavior-preserving. Added
`TestHierarchicalPreemptions` cases cover the exceeds-borrowing-limit reclaim
path, the WithinClusterQueue=Never no-candidate case, and a regression guard
for a nil `BorrowWithinCohort` configuration.

### Comment by [@hahahaheihei](https://github.com/hahahaheihei) — 2026-09-14T08:33:24Z

Pushed a follow-up (76d35888) that strengthens the earlier over-pruning fix — PTAL @pajakd.

The previous fix computed the cohort's required supply as `request - usage`, which assumes same-queue preemption can reclaim *all* of the queue's usage. That is still wrong when part of the usage is held by workloads with higher priority than the incoming one (non-preemptible): `request - usage` gets understated (even negative once `usage > request`), and the required cross-queue candidate is dropped again.

This commit bases the check on the usage that the *eligible* `sameQueueCandidates` can actually release: `needed = max(0, request - R)`, where `R = releasableSameQueueUsage`. Since `R` excludes non-preemptible usage and `R <= usage`, this is strictly more conservative than before and can only retain more cross-queue candidates.

It also adds `cannotFitUnderBorrowingLimit` as a separate early-return (the "second proof" from the discussion): when the queue would still exceed its borrowing cap after reclaiming every eligible same-queue candidate, no preemption can make the workload fit — the borrowing cap is a hard ceiling cross-queue preemption cannot raise — so all candidate collection and the cohort scan are skipped.

New regression tests cover mixed preemptible/non-preemptible same-queue usage in a full cohort, plus the single- and multi-resource early-return paths. `usageAtOrAboveNominal` and `borrowingCap` were extracted as helpers along the way.

  1. Still over cap after full same-queue eviction → `cannotFitUnderBorrowingLimit`, drop all. Cross-queue preemption cannot raise the cap, so the workload genuinely does not fit — old heuristic also returns nil.
  2. Fits under cap, and cohort free quota already covers the shortfall → cross-queue dropped. Old heuristic would stop at `workloadFits` (preemption.go:329) before touching a sibling anyway.
  3. Fits under cap, but cohort free quota is insufficient → cross-queue pools collected. **The only case where sibling reclamation is required, and it is never truncated.**
