## Description

Cherry pick of #13960 on release-0.19.

#13960: fix(pod): refuse adopting and finalizing foreign Workloads by pod group name

For details on the cherry pick process, see the [cherry pick requests](https://git.k8s.io/community/contributors/devel/sig-release/cherry-picks.md) page.

> [!NOTE]
> This PR is self-contained: it reverts the previous pick and re-applies it in one branch, so it can merge on its own.

#### Why this re-pick

The previous pick, #14599, declared the `PodIntegrationValidateGroupOwner` feature gate at version `0.20`. Versioned feature gate entries only apply when their version is `<=` the binary's emulation version, which is `0.19` on this branch — so the gate could never be enabled and the fix was dead code.

This branch therefore reverts that pick (first commit) and re-lands the two upstream commits with the gate **versioned at `0.19`** to match the release branch.

The gate version is changed in all three places, in a separate final commit:

- `pkg/features/kube_features.go` (`defaultVersionedFeatureGates`)
- `site/data/featuregates/versioned_feature_list.yaml`
- `test/compatibility_lifecycle/reference/versioned_feature_list.yaml`

The revert and the re-applied upstream commits cancel out byte-for-byte (`git diff` between the re-applied tip and `release-0.19` was empty before the version commit), so the **net diff of this branch against `release-0.19` is exactly the three `0.20` -> `0.19` lines** — the behavior fix itself is unchanged from what is already on the branch.

#### Does this PR introduce a user-facing change?

```release-note
PodGroup integration: Fixed a bug where a Pod could bypass ClusterQueue quota by setting `kueue.x-k8s.io/pod-group-name` to another Workload's name. Kueue now only adopts Workloads created by the pod-group framework (stamped with `kueue.x-k8s.io/is-group-workload`), and no longer finalizes a foreign Workload that merely shares the pod group name, which previously marked it Finished and released its quota while its pods were still running.
```
