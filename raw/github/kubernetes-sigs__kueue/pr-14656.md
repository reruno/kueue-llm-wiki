#### What this PR does / why we need it:

When a RayCluster worker group cannot be admitted because the ClusterQueue
lacks sufficient quota (FlavorAssigner returns `NoFit`), the scheduler now
appends a quota-exceeded scaling gate
(`kueue.k8s.io/quota-exceeded`) to that group's
`spec.workerGroupSpecs[i].scaleStrategy.scaleGate`. The Ray Autoscaler
observes the gate and falls back to a lower-priority worker group
immediately, instead of waiting on a group that cannot get quota. The gate
is cleared on admission so the preferred group can scale again once quota is
available.

The reconcile is best-effort: it only acts on RayCluster-owned Workloads,
never blocks scheduling, and only logs on failure. Only worker-group PodSets
are gated; the head group is excluded. Patches are skipped when nothing
changes to avoid unnecessary API writes.

#### Special notes for your reviewer:

- Depends on a KubeRay release exposing `ScaleStrategy.ScaleGate`. The branch
  currently carries a local `replace github.com/ray-project/kuberay/ray-operator
  => ../kuberay/ray-operator` directive in `go.mod` so it can build against the
  in-progress KubeRay change; this must be removed and replaced with a published
  KubeRay version before merge. Marking as draft until then.
- Version skew note: on clusters with an older RayCluster CRD that lacks the
  `scaleGate` field, the API server prunes it on patch, so the feature is a
  safe no-op there.
- AI assistance was used to help author this change.
- Tests run locally:
  - `go build ./pkg/...`
  - `go test ./pkg/scheduler/` (new tests: `TestNotFitWorkerGroups`,
    `TestApplyScaleGate`, `TestReconcileRayClusterScaleGate`,
    `TestReconcileRayClusterScaleGate_NonRayClusterOwnerIgnored`)

### Comment by [@kvnloo](https://github.com/kvnloo) — 2026-09-20T18:18:23Z

AI-assisted: I used an AI assistant to trace the KubeRay ScaleGate contract and Kueue's patch helper; I reviewed the relevant code paths myself.

I think there's a cross-repo ownership invariant worth fixing before this moves forward.

KubeRay's merged `ScaleGate` API explicitly documents that each writer should add/remove only its own gate using **Server-Side Apply with a distinct field manager**. The list is `+listType=map` / `+listMapKey=type` specifically so multiple controllers can independently own entries.

This PR currently calls `clientutil.Patch()`. Tracing that helper, it builds the update with `client.MergeFrom`, i.e. a JSON merge patch.

`applyScaleGate` does preserve unrelated gates from the object it fetched, which handles the non-concurrent case, but it doesn't establish ownership of only Kueue's map entry or give Kueue the SSA concurrency semantics that the KubeRay API contract calls for.

Could this write live in the RayCluster integration and use SSA with a Kueue-specific field manager, owning only something like:

`scaleGate[type=kueue.../quota-exceeded]`

rather than patching the containing list?

A useful regression test might have a second fake controller own another gate through a different field manager, then add/remove the Kueue gate and verify neither controller disturbs the other's entry.

That also seems to align with the existing review direction that Ray-specific behavior should move out of the scheduler package and into `pkg/controller/jobs/raycluster`.
