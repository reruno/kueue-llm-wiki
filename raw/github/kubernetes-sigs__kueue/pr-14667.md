## Description

Fixes #14609

`reclaimablePods` belongs to a workload's active quota reservation. When the quota reservation is removed, the field could remain populated and become stale across subsequent admission attempts.

This change clears `Status.ReclaimablePods` when `UnsetQuotaReservationWithCondition` removes the quota reservation.

The regression coverage verifies that reclaimable pods are cleared after eviction/re-admission while preserving the existing behavior during an active quota reservation.

Tests:
- `go test -v ./pkg/workload/...` — PASS
- JobSet integration test — not run locally because envtest etcd/kube-apiserver binaries were unavailable.

  This clear is dropped by the default SSA patch path.
  
  `UnsetQuotaReservationWithCondition` is normally called from inside `PatchAdmissionStatus`. When `WorkloadRequestUseMergePatch` is disabled (the default), the callback first clears `Status.ReclaimablePods`, but `PatchAdmissionStatus` then rebuilds the applied object through `prepareWorkloadPatch` / `admissionStatusPatch`. That payload does not include `ReclaimablePods`, so the deletion never reaches the API server.
  
  I reproduced this with a focused test:
  
  - `WorkloadRequestUseMergePatch=false`: the stored Workload still has `reclaimablePods: [{name: main, count: 1}]`
  - `WorkloadRequestUseMergePatch=true`: the field is cleared
  
  Could this clear be persisted through the existing reclaimable-pods field manager, or otherwise be explicitly included in the SSA path? A regression test covering both patch modes would also catch this.
