## Description

Fixes #14609

`reclaimablePods` belongs to a workload's active quota reservation. When the quota reservation is removed, the field could remain populated and become stale across subsequent admission attempts.

This change clears `Status.ReclaimablePods` when `UnsetQuotaReservationWithCondition` removes the quota reservation.

The regression coverage verifies that reclaimable pods are cleared after eviction/re-admission while preserving the existing behavior during an active quota reservation.

Tests:
- `go test -v ./pkg/workload/...` — PASS
- JobSet integration test — not run locally because envtest etcd/kube-apiserver binaries were unavailable.

### Review by [@HARSHRAJ2789](https://github.com/HARSHRAJ2789) (commented) — 2026-09-03T17:14:18Z

`UnsetQuotaReservationWithCondition` is not reached on the path #14609 reports. Step 4 of that repro keeps `QuotaReserved` at `True` through the JobSet restart, and every caller of that function removes the reservation. The stale count in steps 5 and 6 is therefore still there with this change applied.

What happens on that path instead: when the JobSet restarts, `ReplicatedJobsStatus[].Succeeded` returns to 0, `JobSet.ReclaimablePods` stops returning the entry, and `jobframework/reconciler.go:547` calls `UpdateReclaimablePods` with an empty list. Running the repro under envtest with a `job-a` of 2 replicas, one succeeded then restarted:

```
after success: reclaimablePods=[{job-a 1}] quotaReserved=true
jobframework/reconciler.go:552  updated reclaimable pods
after restart:  reclaimablePods=[] quotaReserved=true
```

That removal does not survive validation in a cluster. Passing the same workload to `ValidateWorkloadUpdate` directly, with podSet `job-a` of 2, a matching admission and one reclaimed pod, returns:

```
status.reclaimablePods[job-a]: Required value: cannot be removed
```

`ValidateWorkloadUpdate` runs `validateReclaimablePodsUpdate` when both the old and the new object hold a quota reservation, which is the state throughout this repro. The one exemption in that check applies only when workload slicing is enabled. `config/components/webhook/manifests.yaml` registers the validating webhook on both `workloads` and the `workloads/status` subresource, so the status patch goes through it.

`reconciler.go:550` returns that error, so the reconcile ends there and step 5 onward, including the `waitForPodsReady` handling, does not run for that JobSet.

The integration test cannot reach any of this. `test/integration/singlecluster/controller/jobs/jobset/suite_test.go` builds its framework with `DepCRDPaths` and leaves `WebhookPath` unset, so the validating webhook is never installed for that suite and the removal is accepted. Eleven job suites are in that state, among them the ones for job, raycluster and rayjob, while the pod, statefulset, mpijob and trainjob suites do install it. Adding `WebhookPath` to the JobSet suite on its own is not enough either. With the configuration installed, JobSet creation in that suite fails with a nil pointer dereference inside `mjobset.kb.io` before the scenario is reached.

The clear on reservation removal does cover the residue in the reporter's follow-up comment, where the workload was requeued and the count stayed at 2.
