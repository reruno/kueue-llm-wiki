#### What this PR does / why we need it:

Restarting the kueue controller or leader election will reconcile all the workloadpriorityclass' priority. Say we have modified the .spec.priority earlier, the reconciliation of workloadpriorityclass in the workloadpriorityclass_controller.go when the kueue controller restarts would override the .spec.priority back to workloadpriorityclass' priority.

  Could we clarify the intended behavior when a `WorkloadPriorityClass` is updated or re-created while Kueue is down? Skipping initial-list events preserves direct Workload priority edits, but it also drops the only signal for changes made during that downtime, so the affected Workloads will not be reconciled after restart. This seems to conflict with the current reconciler behavior introduced by #8442, which intentionally propagates value changes and re-creations, while the `WorkloadPriorityClass.value` API documentation says existing Workloads are unaffected. Since those contracts point in opposite directions, could we document which behavior is intended and cover the downtime case in a test (or explain why retaining the old Workload value is expected)?

  If I understand the code correctly, when the controller is down and a new workloadpriorityclass got created, the jobframework controller would have picked up the new workloadpriorityclass in https://github.com/kubernetes-sigs/kueue/blob/dca2e06376decfc9f42914c9ce1e88fdbb65b0bd/pkg/controller/jobframework/reconciler.go#L1729, so it will be business as usual.
  
  However, if the value field of workloadpriorityclass is modified when the controller isn't running, the changes won't get propagated. I expect my priority override on the workload stays when I change the workloadpriorityclass.value, it should only get overwritten if I have never override the workload priority. The KEP that introduces the workload priority says
  https://github.com/kubernetes-sigs/kueue/blob/db6c86b7058d4e4f1ad76d18e815431e6f6a62ed/keps/973-workload-priority/README.md#L456-L460 So I think the current reconciler behaviour introduced by https://github.com/kubernetes-sigs/kueue/pull/8442 is conflicting the existing design. 
  
  That being said, I think the override case could be on top of the behavior introduced in https://github.com/kubernetes-sigs/kueue/pull/8442. We can still have WorkloadPriorityClass.value being propagated everywhere *if they haven't been manually overwritten*. The PR unfortunately doesn't address this bug, but it does prevent restarting kueue from overriding the .spec.priority field, so this is one step towards that direction. 
  
  I am not sure if I should still document this since it is already a documented feature in the original KEP. What do you think?
