#### What this PR does / why we need it:

`computeSchedulingHash` includes each PodSet's `Name` in the scheduling equivalence hash. The name does not affect flavor assignment or placement, so a client that gives each Workload a unique PodSet name puts every Workload in its own equivalence class and the inadmissible bulk-move never matches anything. The Pod group integration is one such client: `getRoleHash` returns the `kueue.x-k8s.io/role-hash` annotation as-is when it is already set, and `constructGroupPodSets` uses that value as the PodSet name.

This adds the scheduling unit tests requested in #14534 to pin down the current behaviour before the hash changes. Three cases in `TestSchedule`, all with multiple PodSets and `FlavorFungibilityPreserveScanProgress` enabled:

- Workloads sharing PodSet names: the head fails with `NoFit` and the siblings in its equivalence class are bulk-moved to inadmissible without being evaluated.
- Workloads with unique PodSet names: the bulk-move matches nothing, so the siblings stay in the active heap and are re-evaluated on later cycles even though they are identical to the head for scheduling.
- The same unique-name case with `ConcurrentAdmission` enabled, since that gate adds the allowed-flavors annotation to the shape.

The second and third cases fail if `ps.Name` is dropped from the hash, so they will show the behaviour change when the follow-up lands behind its own feature gate.

#### Which issue(s) this PR fixes:

Part of #14534

#### Special notes for your reviewer:

`cmpDump` needed one addition. Its `SortSlices` comparator is typed for `string`, so it never applied to the `[]workload.Reference` values that `Dump` and `DumpInadmissible` return, and those have no defined order: `DumpInadmissible` iterates a map and `DumpActive` walks the heap. No existing case holds more than one workload per ClusterQueue, so this was never visible. The new cases do, and were flaky across the scenario matrix until a `workload.Reference` comparator was added. It only sorts, so it cannot hide a real difference. Happy to split it into its own PR if you would prefer that.

The new ClusterQueue is declared per case rather than added to the shared fixtures because the existing ones are `StrictFIFO`, where `handleInadmissibleHash` returns early and the bulk-move is a no-op.
