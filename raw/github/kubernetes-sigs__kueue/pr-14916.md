#### What this PR does / why we need it:

`ProvisioningRequestName` hashed the full name including the attempt number. `getAttemptRegex` hashed only the workload+check prefix, so a long name produced two different hashes. `matchesWorkloadAndCheck` then missed the object, `deleteUnusedProvisioningRequests` deleted it, and `syncOwnedProvisionRequest` recreated it in a loop.

This change truncates the stable prefix first (reserving space for an int32 attempt), then appends the attempt so matching and naming stay consistent and the final name stays within 253 characters.

This is sound change, all looks really good.
I don't know how to pass this but we should probably mention that in the release notes, that...
upgrading to this fix will silently delete and recreate any in-flight `ProvisioningRequest` whose combined workload+check name is long enough to hit the truncation path.
Since its old hash-based name no longer matches the new prefix regex. 
This resets the attempt count and discards any provisioning progress the autoscaler had already made (e.g. an Accepted request), purely as a side effect of the controller upgrade rather than any change to the workload itself.

However the impact doesn't appear to be dramatic, AI suggests that:
the workload's admission via that check takes longer right around the moment of the Kueue controller upgrade - a one-time extra provisioning cycle — rather than any lasting inconsistency or stuck state.

Other than that
