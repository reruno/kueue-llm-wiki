#### What this PR does / why we need it:

`variantReconciler.Reconcile` had an unimplemented TODO: if `ConcurrentAdmissionPolicy`
is removed from a `ClusterQueue` that still has parent/variant Workloads left over
from when the feature was enabled, the reconciler kept treating them as active —
running `createVariants`/`deleteStaleVariants`/`syncVariantEvictionStatus` against a
policy that no longer exists.

This adds the missing check at the point the TODO marked. When `cq.Spec.ConcurrentAdmissionPolicy`
is `nil`:
- Each variant is deactivated via the existing `deactivateVariant` helper (same
  primitive already used elsewhere in this reconciler to retire variants that are
  no longer needed).
- If the parent is currently admitted, its admission is cleared via the same
  `PatchAdmissionStatus` + `SetEvictedCondition` pattern already used in
  `syncAdmissionStatus` for the analogous "no variant is running" case — this
  returns the parent to `Pending` so it re-enters normal, single-workload
  scheduling rather than being deleted or permanently deactivated.
- The `ConcurrentAdmissionParentLabelKey` label is removed from the parent (mirroring
  how `createVariants` already strips this same label when copying the parent into
  a variant), so `IsParent()` returns `false` afterward and this reconciler stops
  reconciling it going forward.

No new logic was needed beyond the `nil` check itself and the label removal — every
other operation reuses an existing, already-tested code path in this file.

### Comment by [@NasitSony](https://github.com/NasitSony) — 2026-09-10T15:46:33Z

Separate from the reuse point above — deactivateVariant leaves the Variant objects behind. `deactivateWl` sets `wl.Spec.Active = false` and does a plain `client.Update`, so the object survives. Once the parent label is stripped, `getFamilyAndClusterQueue` bails on `!IsParent(wl)` and the family is never reconciled again.

Nothing else collects them:

- `isOrphanedWorkload` returns false immediately for anything with owner references, before checking anything else — Variants have one.
- `afterFinished` retention is gated on the `WorkloadFinished` condition, which deactivated Variants don't have. (Variants that go through `syncFinished` do get Finished, so those are covered.)
- `afterDeactivatedByKueue` doesn't apply to Workloads deactivated via `.spec.active=false` — the retention docs call that out explicitly, and that's the path `deactivateWl` takes.

So I'd use `workload.Delete` here instead — it removes the finalizer and no-ops if deletion is already in flight. Related: gating the `DeletedVariant` event on its return value avoids emitting one per Variant per reconcile.

### Comment by [@NasitSony](https://github.com/NasitSony) — 2026-09-10T15:51:27Z

One case I don't think this PR can fix as scoped, and I'd like your call on it.

ConcurrentAdmissionPolicy is immutable, so the realistic way to reach the cleanup path is a `spec.queueName` change onto an LQ backed by a policy-less CQ. But `concurrentAdmissionEnabledForWithoutLock` resolves `wl.Status.Admission.ClusterQueue` — the old CQ, which still has a policy — so `AddOrUpdateWorkload` returns early and the parent is never added to the scheduler cache, while the Variants' charge disappears when they're deleted. Running pods, accounted nowhere, and it doesn't self-correct: `Status.Admission.ClusterQueue` won't change while the Workload stays admitted.

Two ways out. Evict the parent when `Status.Admission.ClusterQueue` still has a policy, treating a cross-CQ move as a restart. Or key the accounting guard on `IsVariant` alone, making "not a Variant ⇒ charged" unconditional — but that changes accounting for every concurrent-admission Workload, not just this path.

The first is scoped to this PR; the second isn't. Happy to do the first here and file the second separately, unless you'd rather this PR handle only the same-CQ case and the cross-CQ path gets its own issue.

### Comment by [@NasitSony](https://github.com/NasitSony) — 2026-09-10T16:57:46Z

Following up on the leak above — it's worse than object retention. The quota reservation leaks too, and permanently.

`deactivateWl` sets `wl.Spec.Active = false` and does a plain `client.Update`, which doesn't touch quota. The core `WorkloadReconciler` then picks up the inactive Workload on its own reconcile — the `else` branch of `if workload.IsActive(&wl)` in `workload_controller.go` — computes `reason := kueue.WorkloadDeactivated` and calls `workloadevict.Evict`. But `Evict` doesn't release quota either: `prepareForEviction` (`pkg/workload/evict/evict.go:205`) sets the Evicted condition, resets cluster nomination, resets admission checks, resets unhealthy nodes and closes preemption gates, with no `UnsetQuotaReservation` on that path.

Eviction and quota release are deliberately separate in Kueue, which is why `deactivateVariant` calls `clearWorkloadAdmission` itself once it sees the Evicted condition. Two problems with that here:

1. The condition is written by a different controller on a different reconcile, so the `r.client.Get` inside `deactivateVariant` won't see it in the same pass and `clearWorkloadAdmission` is skipped.
2. In the cleanup path there is no later pass — once the parent label is stripped, `getFamilyAndClusterQueue` bails on `!IsParent(wl)` and the family is never reconciled again.

I checked the other release paths. Every `UnsetQuotaReservationWithCondition` call site in `workload_controller.go` is gated on something else (DRA claims, misconfiguration, LocalQueue terminating/stopped, ClusterQueue terminating/stopped, admission-gate clearing); the two in `scheduler.go` are PodsReady and inadmissibility; the `jobframework` ones need a job owner, which a Variant doesn't have. Nothing covers plain deactivation. In practice this is one reservation per cleanup rather than one per Variant, since `HasQuotaReservation` is just the `QuotaReserved` condition and only the admitted Variant has it — but it's leaked indefinitely.

That makes `workload.Delete` a correctness fix rather than cleanup: it sidesteps the two-pass eviction dance instead of depending on a pass that won't come.

On ordering, the argument is the queue cache rather than quota — `PushOrUpdate` and `AddFromLocalQueue` in `pkg/cache/queue/cluster_queue.go` refuse to push a labelled Parent onto the heap, while scheduler-cache accounting keys on `concurrentAdmissionEnabledForWithoutLock` resolving `Status.Admission.ClusterQueue`, and `IsParent` doesn't appear in the scheduler cache at all.
