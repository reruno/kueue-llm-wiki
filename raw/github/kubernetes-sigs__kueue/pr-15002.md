## Description

#### What type of PR is this?

#### What this PR does / why we need it:

Implements the alpha of KEP-13416, adding an optional `sizes` field to a slice
topology constraint layer. It lets a PodSet ask for co-location groups of
different sizes at a topology level:

```yaml
kueue.x-k8s.io/podset-slice-required-topology-constraints: |
  [{"topology": "topology.example.com/rack", "sizes": [4, 3, 1]}]
```

Today `size` cuts a PodSet into equal chunks, so the only way to keep a group of
four together is `size: 4`, which forces every other group to four as well.
Users end up picking a chunk size that is wrong for most of their groups, or
splitting the work into separate PodSets and losing the single pod index space
their application depends on.

`sizes` is the smallest change that covers this. It keeps exactly the contract
`size` already provides: no chunk is split across domains, and chunks may share
a domain.

Everything is behind the new alpha `TASExactTopologyDistribution` feature gate,
which depends on `TopologyAwareScheduling` and `TASMultiLayerTopology`. With the
gate off, behavior is unchanged and `sizes` requests are rejected on both the
job integration and the direct Workload path.
Workloads that already use `sizes` when the gate is turned off stay pending with
a reason naming the gate, rather than being placed as if the list were absent
and having their groups split.

#### Which issue(s) this PR fixes:

Part of https://github.com/kubernetes-sigs/kueue/issues/13416

The KEP itself is under review separately in
https://github.com/kubernetes-sigs/kueue/pull/14821 and is included here so this
branch builds against the design it implements.

#### Special notes for your reviewer:

**This PR was rescoped** after review feedback on the KEP. The earlier version
gave each entry its own distinct domain and used list order to pin contiguous
pod-rank blocks. That is a bigger promise than `size` makes, and the ordering
guarantee rode entirely on the stored domain order in `TopologyAssignment`,
which three separate code paths are free to re-sort. `sizes` is now a plain
generalization of `size`, and distinctness plus rank ordering are left to a
follow-up that should apply to `size` too.

What that removed: the distinct-domain matcher, the ordering branch in
`buildAssignment`, and the topology ungater change that withheld ungating when
ranks were unavailable. `pkg/controller/tas/topology_ungater.go` is now identical
to `main`.

How placement works: at the `sizes` layer, chunks are walked largest-first and
each goes into the first candidate domain with room, reducing that domain's
remaining capacity as it goes. Candidate order is whatever the active TAS
placement mode produces, so `BestFit` and `LeastFreeCapacity` both keep working.
Largest-first matters — placing a chunk of one before a chunk of four can leave
the four with nowhere to go. It does not make placement optimal; this is bin
packing and a greedy pass can miss a valid arrangement. That limitation is
covered by a test (`slice sizes: greedy placement can miss a valid packing`) and
is the same behavior `size` has today.

Composition: a `sizes` layer can sit below a scalar layer, so an outer layer
shapes a region and the chunk list subdivides it. The list is repeated as many
times as the enclosing domain holds chunks of the layer above — without that,
only the first chunk's worth of pods gets placed. A scalar layer below a `sizes`
layer must divide every chunk, so `[8, 4]` works with `size: 4` below it but
`[8, 3]` does not. Those scalar layers are honored all the way down to the
hosts: a chunk of four with `size: 2` on hostname lands as two pairs, never as
three pods on one host and one on another.

Two alpha limitations worth knowing. Both are rejected rather than leading to
pods being placed incorrectly:
- A topology level in between an inner `sizes` layer and the layer above is
  rejected at scheduling time, since a chunk could otherwise straddle two
  domains.
- At most one layer in a constraints list may use `sizes`. This is rejected at
  creation time. On the direct Workload path the error message is currently
  misleading ("must sum to the parent layer size 0"). That will be tidied up
  with the multi-layer follow-up the KEP describes under Non-Goals.

Preemption needs no change. When the preemptor picks targets, it runs the full
TAS placement (chunk placement included) for each candidate set and only accepts
a set whose placement succeeds. So a set that frees capacity too thinly for the
largest chunk is never chosen.

**Not implemented in this PR**, deliberately, and called out so review does not
assume otherwise:
- The `kueue_tas_slice_placement_failures_total` metric the KEP commits to for
  alpha.
- Failed-node replacement still decides whether a chunk is incomplete using
  modulo arithmetic against the slice size, which has no meaning when chunk
  sizes differ.
- Update-time validation for partial admission (`MinCount`) and elastic
  workload slicing.
- Integration and e2e tests. Coverage here is unit-level: chunk placement and
  its helpers, eleven `TestFindTopologyAssignments` cases covering the real
  snapshot path, plus validation cases on the annotation and Workload paths.

#### Does this PR introduce a user-facing change?

```release-note
TAS: Added an alpha `sizes` field to `podset-slice-required-topology-constraints`, allowing a PodSet to request co-location groups of different sizes at a topology level. Each group is kept within a single topology domain, and groups may share a domain. Requires the `TASExactTopologyDistribution` feature gate.
```
