## Description

#### What type of PR is this?

/kind bug

#### What this PR does / why we need it:

`updateClusterQueue` returns as soon as `updateCohortTreeResources` reports a cycle. Nine spec-derived assignments sit after that return:

- `isStopped`
- `AdmissionChecks`
- `Preemption`
- `UpdateWithFlavors`
- `updateWithAdmissionChecks`
- `FlavorFungibility`
- `FairWeight`
- `AdmissionScope`
- `ConcurrentAdmissionPolicy`

They keep their previous values while the ClusterQueue stays registered in the hierarchy manager, so the cached ClusterQueue no longer matches its own spec.

This holds the error in a local until those assignments have run and returns it at the end. Every existing call keeps its current order, which matters because `updateQuotasAndResourceGroups` still has to run before the Cohort-tree update.

#### Which issue(s) this PR fixes:

None.

#### Special notes for your reviewer:

This continues the fix in PR 13571, which moved the namespace selector above the same early return and left the rest of the function after it. A Cohort cycle is a supported runtime state, since no webhook rejects one, and `cache.UpdateClusterQueue` is called only from the ClusterQueue controller's update predicate, which logs the error without retrying.

The added test drives the real path: a ClusterQueue in a Cohort, a cycle introduced through the Cohort tree, then an update that changes both the quota and one of the affected fields. The quota change matters, since the Cohort-tree branch is entered only when the quota or the parent changes.

Reverting the production change and leaving the test in place fails all three subtests:

```
--- FAIL: TestUpdateClusterQueueAfterCohortCycle/StopPolicy_is_applied
    Expected the ClusterQueue to be stopped
--- FAIL: TestUpdateClusterQueueAfterCohortCycle/AdmissionChecks_are_applied
    Unexpected AdmissionChecks (-want,+got)
--- FAIL: TestUpdateClusterQueueAfterCohortCycle/FairWeight_is_applied
    Unexpected FairWeight: got 1, want 3
```

I have not found a path where this is externally observable. A ClusterQueue update event that arrives after the cycle is repaired re-runs the function and assigns the fields correctly, and the controller's own status write usually produces one within milliseconds. The change is worth making for the correctness of the cached state itself. I can point at no symptom beyond that.

  The unit test in this PR discriminates cleanly: revert the production change and it fails on all three fields, apply it and it passes. At the integration level it is harder to expose, because after the Cohort cycle is repaired a later ClusterQueue update event re-runs `updateClusterQueue` and reassigns the fields, and the controller's own status write tends to produce such an event within milliseconds.
