## Description

#### What type of PR is this?

/kind bug

#### What this PR does / why we need it:

#12838 added the non-negative check for container resource limits together with the one for requests. The same change made a `pods` key in limits or pod-level resources invalid. A Workload that already stored such a value cannot be updated afterwards, so evicting, deactivating or removing its finalizer fails validation and the Workload stays in Terminating. For example, from #14373:

```
...requests[example.com/gpu]: Invalid value: "-3": must be greater than or equal to 0
```

`ValidateWorkloadUpdate` now lets an unchanged request or limit through, matching containers by name, including an unchanged `pods` entry in limits or pod-level resources. A new or changed invalid value is still rejected.

#### Which issue(s) this PR fixes:

Fixes #14373

#### Special notes for your reviewer:

Author: roshpr. Kubernetes CLA applies.
Unchanged resource-list entries, including a reserved `pods` key already on the object, are grandfathered on update so lifecycle operations are not blocked by the same Terminating-stuck problem.

**Security Blast Radius**
- _inferred_ — The direct relaxation concerns updates to existing Workloads carrying invalid resource entries. An actor able to update such an unreserved Workload can preserve those entries while changing otherwise mutable fields, including activation or PodSet count. This broadens accepted updates relative to the base, but a resulting cross-tenant quota or execution impact was not established.

**Trust Boundaries and Controls**
- _observed_ — The update handler passes the previous Workload into validation rather than trusting an exemption flag in the new object. Matching is local to the resource owner and list. The generated CRD declares both regular and init-container lists as name-keyed maps, providing counterevidence to duplicating a container name to multiply one legacy exemption.
- _observed_ — Existing unadmitted-Workload accounting derives requests from the current PodSets and floors aggregate per-Pod requests at zero before multiplying by count. This limits direct negative quota credit in that path; it does not establish safety for every consumer or every combination of legacy resources and mutable fields.

**Resilience and Maintainability Implications**
- _inferred_ — The new grandfathering checks only read prior state and introduce no persistent reservation or exemption state to strand after failure. Repeating validation against the same object pair yields the same exemption decision. After an entry is successfully removed, a later re-addition lacks an old match and is validated as new; concurrency correctness still depends on the surrounding API update mechanism.
