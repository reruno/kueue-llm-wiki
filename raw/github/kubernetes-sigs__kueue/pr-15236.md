## Description

Fixes #15221

/kind bug

```release-note
Deduplicate AdmissionFairSharing entry-penalty settlement so admit → evict → re-admit no longer double-charges the same Workload/LocalQueue path.
```

#### What this PR does / why we need it:

Entry-penalty settlement was not deduplicated per Workload + LocalQueue, so admit → evict → re-admit could double-charge AdmissionFairSharing accounting.

This keeps settlement identity so the same Workload/LocalQueue path is not charged twice, with unit coverage for the admit/evict/re-admit path.

Draft until human review. Author: roshpr. Kubernetes CLA applies.

### Review by [@tomsen02](https://github.com/tomsen02) (commented) — 2026-09-08T07:38:58Z

A same-name replacement can incorrectly inherit the previous Workload's settled penalty. This is independent of the lifetime-scope question already raised above.

After UID A settles its penalty, an informer can report deletion of A and creation of UID B with the same namespace/name as a single Update(A, B); this is explicitly documented in [client-go's SharedInformer contract](https://github.com/kubernetes-sigs/kueue/blob/337bf2bb534e21723f666b7b20253ddb79086c9e/vendor/k8s.io/client-go/tools/cache/shared_informer.go#L125-L133). When B is pending on the same LocalQueue, this Update retains A's settled marker. The scheduler's subsequent [`PushPenalty` for B returns early](https://github.com/kubernetes-sigs/kueue/blob/337bf2bb534e21723f666b7b20253ddb79086c9e/pkg/cache/queue/afs/entry_penalties.go#L35-L37), so B's first admission contributes no entry penalty. The Delete cleanup added here is not invoked for that notification sequence.

I reproduced this on 337bf2bb5 using envtest with a real API server, etcd, manager/informer, controllers, and scheduler. The test interrupts the Workload watch, gates reconnection while real API deletion and same-name creation complete, then allows relisting (with one injected Expired response). The informer itself delivers Update(old UID, new UID); the test never calls Update or seeds the ledger. With a 4-CPU request and AFS half-life/sampling interval both set to one hour, each entry penalty is 2 CPU. The new object is admitted by the scheduler, but consumed CPU remains about 2.002 instead of about 4 for the two first-entry penalties. Clearing the old settled marker on UID change before queue insertion makes the same test pass at about 4; the test also checks an upper bound to reject extra charges. This is a controlled watch-failure integration reproduction, not an observation of a production cluster. Separate callback controls also pass for same-UID readmission and ordinary Delete/Create.

Please distinguish replacement object identity before applying the settled-marker suppression, and add the different-UID Update regression alongside the existing readmission coverage.

AI assistance (Codex) was used for this review and local validation.
