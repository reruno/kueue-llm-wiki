#### What type of PR is this?

#### What this PR does / why we need it:

A Pod group adopts an existing Workload from its PodSet names and counts alone, in `(*Pod).equivalentToWorkload`, never reading the requests. A prebuilt Workload can therefore state fewer resources than its Pods request, and quota is charged from the Workload. The generic single-Job path already guards this through `comparePodTemplate`; the group path never reaches it.

This compares, for each matched PodSet, the computed per-Pod requests (`resources.NewRequestsFromPodSpec`), which is the resource shape the charge is taken from. The count stays free to differ, so the group can widen its PodSet count past the seed Pod.

The comparison deliberately reads the requests and sets the rest of the template aside. The group builds its PodSets from the live Pods through `constructGroupPodSets`, and the live Pod is API-defaulted, so its template carries `imagePullPolicy: IfNotPresent`, `terminationMessagePath`, `terminationGracePeriodSeconds`, and a `dnsPolicy` that the stored Workload template does not. A whole-template `DeepEqual` there rejects the group's own Workload over those defaults and stalls unsuspension (I confirmed this against the existing pod-group integration specs). The requests are stable across defaulting, so they discriminate an understated Workload without that false rejection.

#### Which issue(s) this PR fixes:

Fixes #14374

#### Special notes for your reviewer:

Scope: this covers the Pod group path from #14374. The two workload-slice paths in the issue are left for a follow-up, since they run through the slice state machine (`EnsureWorkloadSlices`), a separate path that wants its own tests. The comparison covers resource requests, the charged shape; resource claims (which the generic path also compares) are not covered here and can extend the same check.

Unit coverage is `TestGroupEquivalentToWorkloadComparesRequests`: an understated request is rejected, while an equal request with a higher Workload count still matches. Neutralizing the new check makes the understated case pass, so the test discriminates. The `feature:jobset`-adjacent pod-group integration specs, including "Should ungate pods with prebuilt workload", pass with the change.

#### Does this PR introduce a user-facing change?

```release-note
Pod: Fixed a bug where a Pod group could adopt a prebuilt Workload that understated its Pods' resource requests, so quota was charged from the Workload, not from what the Pods actually request. The group now also compares the per-Pod requests when adopting a Workload.
```
