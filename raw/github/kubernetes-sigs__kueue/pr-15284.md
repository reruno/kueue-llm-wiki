#### What this PR does / why we need it?

Resource accounting depends on each producer remembering to copy a Workload and call `AdjustResources`. Missing an entry point can give the same workload different resource requests on creation, requeue, or restart. Validation and DRA can also consume different resource views depending on the path.

This change stores the effective resource view in `workload.Info` and migrates its consumers together, following [the discussion about reviewing the representation and consumer migration together](https://github.com/kubernetes-sigs/kueue/issues/14964#issuecomment-5505524733).

- Keep the API resource representation in `Info.Obj`; resolve LimitRange defaults and RuntimeClass overhead into effective PodSpecs when constructing queue/cache Info.
- Use the effective view for validation, DRA request detection/conversion, scheduling hashes, TAS accounting, and the WAS simulation template.
- Refresh defaults on normal updates, while preserving the same snapshot across DRA preprocessing and enqueueing (including requeue after backoff), scheduler assume, and TAS cache resync.
- Remove production `AdjustResources` calls. Retain the previous implementation only as an independent test oracle and exercise the existing defaulting test matrix through the new Info path.

Reserved quota still comes from `status.admission.resourceUsage`. `resourceTransformations` remain at their existing total-request calculation stage. There are no CRD changes.

Part of #14964.

#### Useful notes for your reviewer

Start with `pkg/workload/effective_resources.go` and Info construction, then the queue/cache producers and the controller/scheduler consumers. The representation stores full effective PodSpecs only when they differ from the original specs. Allocation/performance benchmarks have not been run; no performance improvement is claimed.

The elastic-slice `ClusterName` assignment uses copy-on-write to preserve the API object, and WAS receives an effective template. Tests cover both, along with resource defaults changing between DRA preprocessing and queue insertion or between scheduling and assume. The backoff path retains the DRA options introduced by #13967; the accounting regression test from #15096 is included through the updated base.

Local validation on the updated branch:

- `go test -p 2 ./pkg/controller/core -race -count=1`
- `make ci-lint CI_LINT_NPROCS=2` across all Go modules, plus core-package lint after the final test update.
- Kubernetes 1.37 envtest: five core scenarios covering raw-object preservation through LimitRange/RuntimeClass events, accounting after a manager restart, scheduling-hash freshness, and accounting after requeue backoff.
- Kubernetes 1.37 DRA envtest: eight DeviceClass event scenarios and ResourceClaimTemplate re-admission after PodsReady backoff.
- A targeted red/green check verifies the DRA backoff snapshot handoff: dropping the options only at the second queue insertion makes the regression test fail; the proposed code passes.

The full project E2E suite has not been run locally. AI assistance was used for implementation, test development, review, and drafting this PR.

`@mimowo` I verified both unresolved findings. Both findings remain valid.

1. `UseLimitsAsMissingRequestsInPod` copies a missing pod-level request directly from the pod-level limit. Kubernetes pod-level defaulting uses aggregate container requests first for supported resources. A PodSet with a container CPU request of `1` and a pod-level CPU limit of `4` can therefore get an effective request of `4` in Kueue while the created Pod gets `1`. This affects quota accounting and the scheduling hash.

2. `UpdateFromClient` logs RuntimeClass and LimitRange resolution errors, then creates `Info` from incomplete `AdjustmentInputs`. The queue, scheduler cache, DRA detection, and admissibility paths cannot receive or propagate that failure because `NewInfoFromClient` returns only `*Info`. These paths can publish incomplete effective-resource state.

The current source confirms the behavior. The installed Kubernetes module source was unavailable in the sandbox, but the dependency version is Kubernetes v1.37.0 and the Kubernetes defaulting rule cited in the first review thread matches the required behavior.

`@tomsen02` Please address both findings in this PR, or document and link a separate prerequisite fix before merge.

  **Use aggregate container requests for missing pod-level requests.**
  
  Kubernetes v1.37 first applies container defaults, then uses aggregate container requests for supported resources. It uses the pod-level limit only when the aggregate request is absent. `UseLimitsAsMissingRequestsInPod` currently copies the pod-level CPU limit directly, so a container request of `1` and pod-level limit of `4` produces an effective pod request of `4`. `resourcehelpers.PodRequests` then charges `4` in `totalRequestsFromPodSets`, while the API server creates the Pod with a pod-level request of `1`. This can over-reserve quota and make LimitRange validation and scheduling-equivalence hashes use the wrong effective request.
  
  Apply the Kubernetes pod-level defaulting rules after container-level defaulting. Use aggregate container requests first, and use pod-level limits only as the fallback. Add a regression test for a smaller container request with a pod-level limit.

  When a RuntimeClass or LimitRange lookup fails, `UpdateFromClient` logs the error and still calls `Info.Update` with partial `AdjustmentInputs`. `rebuildTotalRequests` then derives effective specs, `TotalRequests`, and the scheduling hash from those incomplete inputs.   Return the resolution failure from `NewInfoFromClient`/`UpdateFromClient`, and propagate it through the queue and controller paths so transient RuntimeClass or LimitRange errors retry instead of publishing partial resource state.
