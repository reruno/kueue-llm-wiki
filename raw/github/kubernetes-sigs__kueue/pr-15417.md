#### What this PR does / why we need it?

A partially-admitted RayCluster elastic scale-up slice could get
evicted (ClusterQueue drain, preemption, ...) while its scale-up probe sibling was still
pending, and the probe looked "stranded" since its `MinCount` floor was set relative to a
predecessor that no longer existed.

Turns out no production code change is needed. #15776 already fixed the underlying
problem: `PodSetReducer.Reduce`'s `mustGrow` parameter means that once the probe's
predecessor is gone, the scheduler is free to admit the probe directly at its own
`MinCount` floor (the baseline the job actually held) instead of requiring growth beyond
it. `normalizeActiveSlices` already finishes only the evicted slice and leaves the
probe alone as an ordinary pending replacement, so the probe simply gets rescheduled and
re-admits itself once enough quota is available again - no recreation, no history lookup,
nothing new to write.

This PR only adds regression coverage for that recovery path, plus a test documenting the
one related gap that does still exist:

- `pkg/workloadslicing/workloadslicing_test.go`: a `normalizeActiveSlices` unit case
  confirming a pending scale-up probe survives its evicted predecessor and is kept as the
  replacement, both with and without the partial-scale-up feature gate enabled.
- `raycluster_controller_partial_scaleup_test.go`: three new/expanded integration specs:
  - re-admission after a ClusterQueue drain
  - re-admission after preemption
  - a known-gap spec: if the ClusterQueue's quota shrinks below what the job held before
    eviction, the probe stays pending (its floor can only be met exactly, not degraded to
    a smaller value) until the quota is restored to at least that floor.

No behavior changes. `pkg/workloadslicing/workloadslicing.go` is untouched.

AI-assisted: investigation, test authoring, and this description were done with Claude
Code; all findings were verified by running the unit/integration tests and `make ci-lint`
before writing this up.

#### Useful notes for your reviewer

- The gap covered by the last spec (quota shrinking below the pre-eviction baseline) is
   out of scope here - follow-up issue for that gap might be useful.
