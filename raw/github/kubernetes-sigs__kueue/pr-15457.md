#### What this PR does / why we need it?

<!--

-->
Part of #14969 (item 2). Makes the unit and integration tests that fail with the `SchedulerLibraryIntegration` feature gate enabled pass, without changing product behavior. The failures were scoped from the Prow runs of #14966 and #14968.

**Job reconciler (`pkg/controller/jobs/job`)**: six `TestReconciler` cases pin `TopologyAwareScheduling` off so the `kueue.x-k8s.io/workload` pod annotation stays out of the expected template while they assert on queue labels, PodSetUpdates, and partial admission. The reconciler also adds that annotation when `SchedulerLibraryIntegration` is on, so the cases now pin that gate too.

**TAS node health (`pkg/cache/scheduler`, integration `tas` and `pod` suites)**: with the gate on, the node cache keeps NotReady and unschedulable nodes at hostname level and relies on the scheduler library to reject them (#14203). The library has no readiness logic of its own: in a real cluster the node lifecycle controller adds the `node.kubernetes.io/not-ready` taint and the `TaintToleration` plugin rejects the node. The failing tests flipped only the Ready condition, and both the unit harness and the integration suites built the cache with the default simulator, a pairing production never runs. The replacement therefore landed back on the failed node.

- The TAS cache test harness now picks the WAS simulator when the gate is on, mirroring `cmd/kueue/main.go`.
- NotReady nodes in the TAS cache cases carry the not-ready taint, as they would in a real cluster. The not-ready and unschedulable cases gained gate-on twins.
- Cases that assert on the default simulator's per-reason exclusion stats (which the scheduler library does not report yet, see the `TODO(#13283)` in `simulator.NodeExclusionStats`) are pinned to the gate-off path.
- The nodes cache tests are gate-explicit and gained gate-on coverage for find and generation bumps (sync already had gate-on cases).
- The `tas` and `pod` integration suites wire the WAS simulator when the gate is on, and the three node replacement specs add the not-ready taint next to the Ready flip via a new `util.TaintNodeNotReady` helper.

Rebased on top of #15456 (merged), which addressed #15455. With the WAS simulator wired into the `tas` suite, the `Updating TAS ResourceFlavor tolerations` and ProvisioningRequest dedicated-nodes specs, and `TestScheduleForTAS/scheduling workload on a tainted node when the toleration is on ResourceFlavor`, only pass under a gate-on run with that fix in place, because ResourceFlavor tolerations and admission-check PodSetUpdates did not reach the simulated pod before it.

#### Useful notes for your reviewer

Verified locally on top of current main with the gate default temporarily flipped to `true`:
- `go test ./pkg/... ./cmd/...`: all packages pass, except the `kueue-populator` e2e and the `kueue-populator` and `kueue-priority-booster` integration packages, which need a live cluster.
- The `tas` and `pod` integration suites: 147 of 147 and 59 of 59 specs pass with the gate on, and again with the gate off.

Two observations for maintainers, not addressed here:
1. With the gate on, node replacement relies on the not-ready taint being present. Kueue already lists the node in `status.unhealthyNodes`, so a defensive exclusion of those nodes from replacement candidates in `findReplacementAssignment` would remove the dependency on the lifecycle controller's timing.
2. The other integration suites still build the cache with the default simulator. A gate-on CI run would pair gate-on cache logic with a simulator production never uses. This PR only wires the WAS simulator into the two suites with node-health specs.
