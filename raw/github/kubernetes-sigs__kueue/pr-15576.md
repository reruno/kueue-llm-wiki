## Description

#### What type of PR is this?

/kind bug

#### What this PR does / why we need it?

LocalQueue lifecycle events can leave pending-workload metrics stale. If a Workload is observed before its LocalQueue, creating the queue loads the Workload without refreshing the gauges. Deleting or stopping a LocalQueue removes its queued Workloads but leaves the ClusterQueue gauge counting them until another event refreshes it.

Refresh pending gauges when a LocalQueue is added, removed, or moved internally between ClusterQueues, using existing reporting helpers under the manager lock. Register LocalQueue custom labels before adding the queue so the first report uses the configured values. When moving a queue, refresh both ClusterQueues and report the LocalQueue after updating its reference.

The creation issue was exposed by the metrics-filtering integration failure in [PR #15284](https://prow.k8s.io/view/gs/kubernetes-ci-logs/pr-logs/pull/kubernetes-sigs_kueue/15284/pull-kueue-test-integration-shard-2-main/2099685531133677568). It also reproduced on that PR's base commit and is independent of the effective-resource migration.

#### Useful notes for your reviewer

`spec.clusterQueue` is immutable through the Kubernetes API. The move-path changes keep the existing internal manager operation consistent; they do not enable API-level migration.

Tests cover creation ordering and custom labels; deletion and internal moves with active/inadmissible Workloads, disabled LocalQueue metrics, and missing source/destination ClusterQueues; and real-API deletion, Hold, and HoldAndDrain. The latter keep another LocalQueue populated and verify the ClusterQueue gauge changes from 2 to 1 to 0 without losing the remaining queue's metrics.

Local validation passed:

- `go test -race -p 2 ./pkg/cache/queue ./pkg/controller/core -count=1`.

- Red/green checks: all eight new manager cases and all three lifecycle integration cases failed before the fix and passed afterward.
