## Description

#### What type of PR is this?

/kind bug
/area integrations

#### What this PR does / why we need it?

`buildDriverPodTemplateSpec` and `buildExecutorPodTemplateSpec` only copied `spec.driver.nodeSelector` and `spec.executor.nodeSelector` into the Workload PodSet templates, ignoring the SparkApplication-level `spec.nodeSelector`. Since the two levels are mutually exclusive, `RunWithPodSetsInfo` flattens `spec.nodeSelector` into the per-role selectors and then clears it, which makes the Workload the only place `RestorePodSetsInfo` can read the original selector back from. A SparkApplication that only set `spec.nodeSelector` therefore lost it for good on the first eviction, and the selector was also invisible to ResourceFlavor matching.

This records the SparkApplication-level node selector in the PodSet templates, with the per-role selector taking precedence on conflict.

None

```release-note
SparkApplication: Fixed a bug where a SparkApplication that only set the SparkApplication-level `spec.nodeSelector` permanently lost it after the first eviction, letting the driver and executor pods be scheduled onto any node once re-admitted. The selector is now recorded in the Workload PodSets, so it also participates in ResourceFlavor matching.
```
