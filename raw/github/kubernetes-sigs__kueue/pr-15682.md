#### What this PR does / why we need it?

Any MultiKueue-managed job's manager-side copy has no local operator driving it - its status only ever changes because MultiKueue mirrors it from the remote copy. If the remote is deleted before it ever mirrors a status the generic eviction-completion path treats as inactive, that wait never resolves, and the Workload holds its quota reservation forever. Reported for RayJob specifically, but not Ray-specific: it's the same architecture for any job type MultiKueue manages.

`RemoveRemoteObjects`, in the generic MultiKueue reconciler, already knows for any job type when a remote copy is gone. It now clears the local Workload's quota reservation itself right after, if the Workload is still evicted and still reserving quota at that point - deletion is proof nothing related to the job is running anywhere, so there's nothing left to wait for. Guarded to that exact shape (evicted, quota still reserved, not finished) so it never touches a Workload outside this scenario, and in particular never overwrites what `workloadfinish.Finish` already did for a finished one.

An earlier version of this fix lived in the Ray MultiKueue adapter instead (a per-type callback invoked after deleting the remote). Moved to the generic reconciler after review - the original approach worked but meant every job type would need its own copy of essentially the same fix.

I attempted an integration test for this; it surfaced an unrelated pre-existing issue (workloads with no `OwnerReference` racing with `FinishOrphanedWorkloads`) that made it unsuitable here. Not pursuing that separately - out of scope for this fix.

#### Useful notes for your reviewer

New test: `TestRemoveRemoteObjects_ClearsStuckQuotaReservation` in `pkg/controller/admissionchecks/multikueue/workload_test.go`, covering the stuck scenario plus the three guard conditions (not evicted, already finished, no reservation to begin with).
