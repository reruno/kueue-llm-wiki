## Description

#### What type of PR is this?
/kind bug

/area multikueue

#### What this PR does / why we need it?

When the manager evicts a MultiKueue workload, the worker sets `spec.active=false` on its copy before it reports `Evicted`. If MultiKueue reconciled in that window, step 5 saw the remote as out of sync and deleted it. The remote's final job status (for example a RayJob going `Suspended`) was never mirrored back, so the job reconciler kept waiting for `IsActive()` to turn false and the Workload held its quota.

Step 5 now skips the out-of-sync deletion while the local Workload is evicted. Quota is released by the job reconciler as usual, and step 2 removes the remote once the reservation is gone. No new writer touches the Workload status.

An earlier version cleared the quota reservation from MultiKueue after deleting the remote. Dropped after review, since it added another writer to the Workload.

#### Useful notes for your reviewer

New `TestWlReconcile` case sets up the in-between state (local evicted and holding quota, remote deactivated but not yet evicted). It fails on main, where the remote is deleted and recreated empty, and passes here.

New integration test in `test/integration/multikueue/kuberay_test.go` follows the issue: a RayJob admitted on worker2 is evicted when another admission check goes to `Retry`. A ValidatingAdmissionPolicy on worker2 holds back the `Evicted` condition so worker2 Kueue stops after setting `spec.active=false`, which keeps the window open. The test checks the remote is kept, then lets eviction finish and checks quota is released and the remote removed. It fails on main and passes here. The full MultiKueue integration suite passes.

Fixes #15380

The fix protects reservations during pending deletion, but cleanup of one worker copy can release capacity while another admitted copy remains active. That can weaken shared-resource accounting until subsequent cleanup completes.

**Retained concerns**
- **Medium · reliability · inferred:** Absence of one removed worker copy is treated as sufficient evidence to release the manager reservation. For an unfinished, evicted, quota-reserved workload with a selected admitted copy, a non-selected copy returning NotFound can clear quota while the selected copy remains active. The patch updates the in-memory local workload, so the following quota-dependent deactivation branch can also be skipped. Subsequent cleanup offers recovery, but the intervening unaccounted execution weakens shared-capacity failure containment.

**Security Blast Radius**
- _inferred_ — The affected accounting boundary is the manager reservation for a MultiKueue workload and its configured worker copies. Because the change is generic, exposure is not Ray-specific. Effects on other tenants depend on shared queue capacity and deployment configuration, which were not established.

**Security Findings and Attack Paths**
- _inferred_ — A source-permitted availability failure requires an unfinished local workload that is evicted but still reserved, an admitted worker copy without a visible remote eviction condition, and a non-selected copy disappearing between read and deletion. Its NotFound result can release the local reservation while the admitted copy continues execution. Attacker control of this timing and an end-to-end exploit were not demonstrated.

**Trust Boundaries and Controls**
- _observed_ — The existing reconciliation path selects a MultiKueue admission check and adapter, verifies management of a live local owner, and uses configured worker clients. The new mutation remains guarded by local lifecycle conditions. Status patching defaults to strict operation, with resource-version protection in the apply path; these local controls do not synchronize shutdown across clusters.

**Resilience and Maintainability Implications**
- _observed_ — Successful delete requests and non-NotFound errors do not release quota. Fresh remote reads distinguish absence from read failure, and subsequent reconciliation removes remote objects when local quota is absent. This provides recovery behavior, but not an atomic guarantee that execution ends before capacity is released.

**Hardening Proposals**
- _proposed_ — Make quota release a group-level decision requiring confirmed absence or completed shutdown of every execution-bearing copy, rather than a side effect of deleting one copy. Preserve the reservation when the selected copy's shutdown cannot be confirmed.

The e2e run here (pull-kueue-test-e2e-multikueue-extended-shard-1-main) caught a real bug in the first version: a RayJob that finished normally got its correct `Complete` status overwritten to `Suspended`.
