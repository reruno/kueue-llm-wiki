**pkg/cache/scheduler/tas_flavor_snapshot.go:1938**
* This guard leaves leader feasibility disabled for topologies whose lowest level is not a hostname: `buildPodRequirements` treats the aggregate leaf as having no node filter, and this function returns before checking the leader. A leader selector or affinity that matches no node in a rack can therefore still be admitted, and the leader/worker-different-nodes-in-one-rack scenario from the companion cherry-pick is not implemented. Add the all-level node/virtual-hostname feasibility path before relying on this gate for those topologies.
```
	if requirements.leader == nil || requirements.leader.podRequirements == nil || !s.isLowestLevelNode {
```
**pkg/cache/scheduler/tas_flavor_snapshot.go:1018**
* Under `SchedulerLibraryIntegration`, the feasibility checker builds its dummy Pod only from `leaderPodRequirements.PodTemplate`; it does not read `PodRequirements.Tolerations`. However, `buildPodRequirements` adds the ResourceFlavor tolerations only to that separate field, so this new leader check treats tainted nodes as infeasible even when the flavor tolerates the taint and rejects otherwise valid grouped workloads. Include the flavor tolerations in the `PodSetInfo` merged into the leader template (while retaining the explicit field for the default checker).
```
		if err := podset.Merge(s.log, &leaderPodRequirements.PodTemplate.ObjectMeta,
			&leaderPodRequirements.PodTemplate.Spec, leaderInfo); err != nil {
```
