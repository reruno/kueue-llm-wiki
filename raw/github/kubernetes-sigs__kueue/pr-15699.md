#### What this PR does / why we need it?

Revises KEP-12100's design for how an elastic job (RayJob/RayCluster) scales up partially when quota is short, and opportunistically finishes scaling up once more quota frees up.

**The core change:** the old design set `minCount = admitted + 1` independently on *every* growing PodSet, effectively requiring every worker group to grow by at least one replica in the same admission. That's wrong for multi-PodSet jobs — it can block a PodSet that has room to grow just because a sibling PodSet doesn't, send capacity to the wrong (lower-priority) PodSet, or leave a job stuck unable to recover to a size it was previously running at.

This revision replaces that with a **baseline/target model**: each PodSet has a `baseline` (`minCount`, the last granted count) and a `target` (`count`, what's currently desired). A scale-up assignment must stay within `[baseline, target]` per PodSet, but only needs to make progress in **at least one** PodSet, not all of them — evaluated globally across the Workload, not per PodSet. The existing order-based reducer (shrink from the last-defined PodSet first, then give back capacity once a fit is found) is unchanged in mechanics; it's now just parameterized by baseline/target and additionally excludes the "no PodSet grew" outcome as a successful scale-up admission.

As background, this pass also:
- adds a normative "Probe lifecycle" section describing how a scale-up replacement Workload progresses from creation to full admission;
- documents eviction/readmission behavior, aligned with the fix in kubernetes-sigs/kueue#15417 (a stranded probe's baseline can't be resolved once its predecessor is evicted, so the probe is finished together with the predecessor and the next attempt reseeds its baseline from the job's last known admitted count);
- updates the worked examples and test plan accordingly.

No implementation code changes — KEP document only.
