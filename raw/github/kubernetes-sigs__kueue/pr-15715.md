#### What this PR does / why we need it?

`workload.UseLimitsAsMissingRequestsInPod` defaults a missing pod-level
resource request (KEP-2837, `pod.Spec.Resources`) by copying the pod-level
*limit* straight into it. The Kubernetes v1.37 API server does not do this:
it defaults the missing pod-level request to the aggregate of the (already
limit-defaulted) container-level requests, and only falls back to the
pod-level limit for a resource no container contributes to at all. When a
Pod set a small container request together with a much larger pod-level
limit, Kueue overestimated the effective request, which flows into
`Info.TotalRequests` and therefore into admission and scheduling decisions.

This PR changes the pod-level branch of `UseLimitsAsMissingRequestsInPod` to
compute the effective aggregate container requests via
`resourcehelpers.AggregateContainerRequests` (from the vendored
`k8s.io/component-helpers/resource`, already used elsewhere in this package
for the same aggregation, e.g. `pkg/workload/workload.go`), merge that into
any still-missing pod-level request key first, and only then fall back to
the pod-level limit for whatever is still missing. An explicit pod-level
request is never touched.

This only affects Pods that set pod-level resources
(`PodLevelResources`/KEP-2837); it does not change container-level
request/limit defaulting, which is unchanged.

### Comment by [@KR-Ravindra](https://github.com/KR-Ravindra) — 2026-09-17T11:18:51Z

One gap against `defaultPodRequests` in the API server (pkg/apis/core/v1/defaults.go on release-1.37): it only copies an aggregate container request into the pod level when `IsSupportedPodLevelResource(key)` (cpu, memory, hugepages-*) and `IsOvercommitAllowed(key)` hold, and it returns early when pod-level limits are empty. `AggregateContainerRequests` returns every resource the containers request, so on 57ea72e a container with `nvidia.com/gpu: 1` and `ephemeral-storage: 1Gi` next to a pod-level cpu limit ends up with `spec.resources.requests = {cpu: 1, ephemeral-storage: 1Gi, nvidia.com/gpu: 1}`.

For `NewInfo`/`TotalRequests` that is harmless because `PodRequests` filters through `applyPodLevelResources`. But `createPodTemplate` in the provisioning admission-check controller calls `UseLimitsAsMissingRequestsInPod` on the spec it then persists (pkg/controller/admissionchecks/provisioning/controller.go:428), and `validatePodResourceName` rejects that PodTemplate with `NotSupported` for `spec.resources.requests[nvidia.com/gpu]`, so a GPU PodSet with pod-level limits and a ProvisioningRequest check would stop admitting.

Filtering the aggregate with `resourcehelpers.IsSupportedPodLevelResource` and keeping the `len(Limits) == 0` early return would match the API server; a test row with an extended resource in the container would pin it.
