Fixes #15463

`ListChildWorkloads` was doing two responsibilities: listing related Workloads and deciding which Workloads should not be finalized.

For PodGroups, a same-named Workload owned by another controller was previously filtered out when `PodIntegrationValidateGroupOwner` was enabled. This made the Workload invisible to the reconciler, which could allow the PodGroup to be finalized incorrectly.

This change separates the two responsibilities:

- `ListChildWorkloads` returns the same-named Workload without filtering it based on ownership.
- Adds the optional `JobWithCustomWorkloadFinalization` interface.
- Adds `CanFinalizeWorkload` for determining whether a Workload can be finalized.
- Prevents foreign controller-owned Workloads from being finalized for PodGroups when `PodIntegrationValidateGroupOwner` is enabled.
- Keeps standalone Pod finalization behavior unchanged.
- Keeps the existing behavior when the feature gate is disabled.
- Logs when a Workload is skipped because it cannot be finalized.

This ensures that a remaining foreign Workload correctly prevents finalization of an all-terminating PodGroup.

#### Useful notes for your reviewer

The finalization check is intentionally separate from `ListChildWorkloads`.

`ListChildWorkloads` is responsible for discovering related Workloads, while `CanFinalizeWorkload` determines whether the reconciler is allowed to finalize each Workload.

The `CanFinalizeWorkload` check applies the ownership validation only to PodGroups, so controller-owned Workloads for standalone Pods retain their existing behavior.
