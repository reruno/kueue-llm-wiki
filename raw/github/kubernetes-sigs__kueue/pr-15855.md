#### What this PR does / why we need it?

When an elastic job’s target replica count increases, Kueue creates a replacement Workload and reevaluates its quota and admission.

The previous logic determined whether actual growth was required solely by checking whether a replaced Workload existed:
`mustGrow := replaceableWorkloadSlice != nil`

However, the replaced Workload can be in either of two states:
1. Fully admitted, with its granted replicas able to run.
2. Holding reserved quota but still waiting for an AdmissionCheck, with none of its replicas running yet.

Previous logic did not distinguish between these states. In second case, even when available quota was sufficient for replacement Workload to recover previous replica count—represented by `.spec.podSets[].minCount` — scheduling was rejected because assigned replica count did not exceed that value. If cluster had no additional capacity for scale-up, replacement Workload remained pending and job could not start.

After fix, replacement Workload is required to exceed `.spec.podSets[].minCount` only when old Workload has been fully admitted. If old Workload has not been admitted, replacement Workload can first be admitted at `.spec.podSets[].minCount`, while increased target remains in `.spec.podSets[].count` for subsequent scale-up.
