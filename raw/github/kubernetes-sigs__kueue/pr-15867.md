## Description

#### What type of PR is this?

#### What this PR does / why we need it?

A Pod group whose `kueue.x-k8s.io/pod-group-pod-index-label` annotation names a label that does not hold the Pod's index is never admitted: the webhook copies the unusable value into the index label, and Workload construction then fails on it for every Pod in the group, on every reconcile.

`validatePodGroupMetadata` ignores `ErrLabelNotFound`, since KEP-976 makes the index optional, but not `ErrInvalidUInt` or `ErrValidation`. An absent label is therefore the one case that behaves; an empty value, a non-numeric one, and an index past the group's total count each wedge the group with its Pods scheduling-gated, no event, and only a controller log. Nothing validates the annotation, so a typo is enough to reach it.

This PR:

* Copies the index only when it survives the same read Workload construction performs later, so the annotation can no longer wedge a group.
* Refuses such a Pod at creation under the new `TASRejectInvalidPodIndexLabel` gate, so the misconfiguration is reported when it is submitted rather than found later in the placement.

The gate is off by default: a controller creating Pods may miss the index label on one of them, a replacement in particular, and a cluster that hits that would rather keep the greedy fallback than have Pod creation refused.

#### Useful notes for your reviewer

* `Default` and the new validation share one `readPodIndex`, so the copy and the refusal cannot drift apart. Outside a group there is no total count to bound the index against, so the value only has to parse.
* The refusal is wired into `ValidateCreate` alone: the mutating webhook is create-only, so the annotation cannot appear later, and validating updates would strand Pods created before the gate was turned on.
* The nil-map guard is gone because a read from a nil map cannot yield a valid index.
* Reverting the webhook change fails both integration specs and every added unit case that asserts the new behaviour; the rest are regression guards that pass either way.
* Drafted with AI assistance (Claude Code, Opus 5), per the Kubernetes AI tool usage policy.

### Security Architecture Review

**Security architecture risk:** _🔵 Low_ · up to `c2d90`

Default behavior avoids copying unusable Pod indexes. Stricter creation checks are off by default, but enabling them before Pod creators consistently supply indexes—including on replacements—could prevent a group from progressing. No new privilege path was established.

**Retained concerns**
- **Medium · reliability · inferred:** If the opt-in rejection gate is enabled while a Pod-creating controller omits the referenced index label on replacements, replacement creation is rejected rather than allowed to use the existing placement fallback. An incomplete Pod group may then remain unable to progress until its producer or gate configuration is corrected.

<details>

**Security Blast Radius**
- _inferred_ — The independently affected unit is a Pod creation and potentially its Pod group's progress. The opt-in gate applies at Pod admission; no broader cross-tenant access or privilege gain was established.

**Trust Boundaries and Controls**
- _observed_ — Create admission checks an annotation-selected, Pod-supplied label through the shared bounded parser when rejection is enabled. Update admission does not invoke this new check; the implementation makes a create-time promise, not an update-time one.

**Resilience and Maintainability Implications**
- _inferred_ — A later change to referenced metadata is not shown to refresh the persisted canonical label. This limits the new gate's enforcement claim to creation; invalid canonical labels could already impede construction independently of this PR.

**Hardening Proposals**
- _proposed_ — Before enabling rejection in a cluster, verify that each relevant Pod producer supplies a valid referenced index on initial and replacement creations, and define how incomplete groups recover if that assumption fails.
