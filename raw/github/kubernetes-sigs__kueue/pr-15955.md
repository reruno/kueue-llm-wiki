## Description

#### What type of PR is this?

/kind cleanup

#### What this PR does / why we need it:

`calculateLendable` was recomputed once per preemption candidate during fair sharing, and the result cannot change between those calls. #15957 has the analysis.

`Lendable` now lives on `resourceNode`, next to the `SubtreeQuota` it derives from. `updateCohortLendable` rebuilds it in the same pass that rebuilds `SubtreeQuota`, `Clone()` carries it into the snapshot, and `dominantResourceShare` reads it instead of computing.

It has to be a second, top-down pass. `SubtreeQuota` is accumulated bottom-up, so the root's is not final until the recursion unwinds, and `Lendable` reads the root both for the FlavorResource key set and as `potentialAvailable`'s base case. Computing it inside the accumulation would be silently wrong by whatever the unvisited branches contribute. The pass is gated on the node being parentless, which is true only of the outermost call.

`BenchmarkRunFirstFsStrategy`, median of 3, before at `d756f749`:

| | ns/op | B/op | allocs/op |
| --- | --- | --- | --- |
| 10 candidates, v2 | 14569 to **11726 (-20%)** | 13168 to **8128 (-38%)** | 105 to **75** |
| 10 candidates, v4 | 19320 to **16288 (-16%)** | 15474 to **10406 (-33%)** | 144 to **114** |
| 100 candidates, v2 | 118278 to **100239 (-15%)** | 104848 to **69568 (-34%)** | 741 to **531** |
| 100 candidates, v4 | 146058 to **126857 (-13%)** | 121352 to **85452 (-30%)** | 964 to **754** |

The relative gain does not grow with the candidate count, so do not read it that way. Most of what this benchmark shows is the removed per-call map allocation, which is why B/op moves about twice as far as ns/op. Its cohort tree is depth 1 with a single FlavorResource, so `computeLendable` there is close to free. The arithmetic the change actually removes scales with tree depth and FlavorResource count, neither of which this fixture exercises.

A 60s CPU profile from a cluster with roughly 4,000 candidates per cycle, before this change, re-rooted at `fairPreemptions`:

![Fair-sharing CPU flamegraph](https://raw.githubusercontent.com/venuchitta/kueue/pprof-assets/flame-lendable.png)

Pink is `calculateLendable`, 11.5% of sampled CPU there and 11.7% on a second cluster, in two towers because the tournament reaches it through both `(*CohortSnapshot).DominantResourceShare` and `(*ClusterQueueSnapshot).DominantResourceShare`.

#### Which issue(s) this PR fixes:

Fixes #15957

#### Special notes for your reviewer:

Why the carried value cannot go stale: `resourceNode.Clone()` shares `SubtreeQuota`, `Quotas` and now `Lendable` with the cache rather than copying them, so a snapshot is not isolated by value. It is isolated because every writer replaces the map through `make(...)` instead of writing into it, so a snapshot holding the previous pointer never observes a change. `TestSnapshotCarriesLendable` and `assertLendableInSync` in `TestDeleteCohortUpdatesAncestorSubtreeQuota` are what should fail if that stops being true.

One thing I would like an opinion on. `TestCohortCycles` compares whole `resourceNode` literals in 10 places, so the new field needs `cmpopts.IgnoreFields` there. Those subtests assert how `SubtreeQuota` propagates, and `Lendable` is asserted directly in three other tests, so ignoring it seemed better than spelling a derived value into 10 literals. Happy to switch if you disagree.

#### Does this PR introduce a user-facing change?

```release-note
FairSharing: improved preemption performance by maintaining each Cohort's lendable capacity when quotas or the cohort hierarchy change, instead of recomputing it once per preemption candidate.
```
