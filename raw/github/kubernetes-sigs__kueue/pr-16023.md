## Description

Design change for https://github.com/kubernetes-sigs/kueue/issues/15255, split out of
https://github.com/kubernetes-sigs/kueue/pull/15278 at the maintainers' request. No code here.

## Problem

`waitForPodsReady.requeuingStrategy` can only bound re-queuing by a *count*. With the exponential backoff described
in this KEP, a count is hard to translate into wall-clock time: ten retries is anywhere from a few minutes to several
hours depending on `backoffBaseSeconds` and `backoffMaxSeconds`. An operator who wants "stop retrying this workload
after an hour" cannot express that today.

This was already anticipated in the KEP. `backoffLimitTimeout` sits in the Alternatives section under "Make knob to
be possible to set timeout until the workload is deactivated", deferred on the grounds that `backoffLimitCount` was
enough for the original stories.

## Fix

Move that knob out of Alternatives and into the accepted design, as @bolubo and @pajakd asked for on
https://github.com/kubernetes-sigs/kueue/pull/15278 — design first, implementation after.

- `RequeuingStrategy` gains `backoffLimitTimeout *metav1.Duration`, and `RequeueState` gains `firstEvictedAt`.
- New "Deactivation on a time limit" section: the window starts at the first `PodsReadyTimeout` eviction since the
  workload last reached `PodsReady=true` and resets when it reaches `PodsReady=true` again, so it bounds time spent
  cycling through evictions rather than total time in the queue. `backoffLimitCount` and `backoffLimitTimeout` are
  independent and whichever is reached first deactivates the workload.
- It records one deliberate narrowing against the original sketch, which is the open question worth reviewing: the
  limit is evaluated **at eviction time**, in the same place `backoffLimitCount` is evaluated, rather than also
  having the queueManager deactivate workloads while they sit in the queue. A single deactivation point keeps
  `.status.requeueState` unambiguous; the queueManager side can be added later if the eviction-time bound proves
  too loose. Happy to go the other way if you would rather have both from the start.
- The Alternatives entry now points at the accepted design instead of being silently contradicted by it.

## How tested

Documentation only — no code in this PR. The described semantics are the ones implemented and tested in
https://github.com/kubernetes-sigs/kueue/pull/15278, where the unit and `scheduler/podsready` integration suites
cover the timeout, the independence from `backoffLimitCount`, and the reset of `firstEvictedAt` on `PodsReady=true`.

### Comment by [@bolubo](https://github.com/bolubo) — 2026-09-23T00:14:52Z

I raised the queueManager sketch on #15278, so let me close that loop: having tried it, I would settle on the eviction-time evaluation, without the queueManager side.

I tried the queue-side evaluation locally (the deadline checked while the workload waits, in-flight attempts protected). It is not just a stricter version of this one: the `scheduler/podsready` spec added in #15278 fails under it, because the workload is deactivated before it is re-admitted, so it never runs the attempt it was queued for. That reads to me as a behaviour change of its own, so I would rather settle it here than add it later.

As I read the current design, the overshoot is loose in one direction, and the struct comment already names it: after the limit, at most one more attempt runs, and its failure deactivates the workload in place of the next eviction, so the retry budget is still enforced. What is not bounded is time spent waiting with nothing to retry.

If a hard wall-clock cap is ever wanted, I would suggest a separate knob rather than a stricter reading of this one: `firstEvictedAt` is already in the status, and the workload controller is the only writer of `requeueState` today, so it would not need a second deactivation path. The part I am least sure about is the motivation: is it meant as a retry budget, or as a wall-clock promise?

### Comment by [@KR-Ravindra](https://github.com/KR-Ravindra) — 2026-09-23T17:40:42Z

@bolubo thank you for actually running it — that is a much better answer than the one I could have argued for. The `scheduler/podsready` failure is the convincing part: deactivating before re-admission means the workload never gets the attempt it was queued for, which is a different behaviour rather than a stricter one.

On your question: it is meant as a **retry budget expressed in time**, not a wall-clock promise. The intent is "stop retrying this workload after roughly an hour of failing to become ready", which is the thing `backoffLimitCount` cannot express once the backoff is exponential. It deliberately does not promise deactivation within T of anything: the measurement resets on PodsReady=true, time spent queued with nothing to retry is not counted, and at most one attempt can start after the limit and deactivate on its failure.

I have written that into the KEP (86e8da5) rather than leaving it implied, along with your finding about the queue-side variant and the note that a hard wall-clock cap would want its own knob built on `firstEvictedAt`. If you would rather the motivation read as a wall-clock promise, that changes the shape and is worth settling before the implementation lands.
