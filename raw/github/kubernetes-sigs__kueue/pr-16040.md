## Description

#### What type of PR is this?

/kind bug

#### What this PR does / why we need it?

`kueuectl list workload --for` lists again without the job-uid label when that query is empty, then keeps workloads owned by the target object. The retry condition was a substring check, so a `-l` selector that already contained the job-uid requirement matched on every pass and the command never returned.

Fixes #16038

#### Useful notes for your reviewer

The fallback now runs only while the list is still using the selector this command built, and only once. A selector that already includes the job-uid label finishes with no resources when nothing matches it.

  This condition only looks at the current page. If page 1 already returned Workloads and the last page comes back empty with no continue token , the owner-reference fallback still runs. Since `opts.Continue` is reset, it lists from the start and prints the page-1 Workloads again.
  
  I reproduced it with envtest and `KUEUECTL_LIST_REQUEST_LIMIT=1`: one Workload with the job-uid label and owner reference, plus one unrelated Workload. This PR prints the Workload twice; main prints it once.
  
  Checking `opts.Continue == ""` limits the fallback to an empty first page, and `!enableOwnerReferenceFilter` still prevents the loop:
  
  ```suggestion

  			len(list.Items) == 0 && list.Continue == "" && opts.Continue == "" {
  			opts.LabelSelector = o.LabelSelector
  			enableOwnerReferenceFilter = true

  		}
  ```
  
  `initialLabelSelector` and its comment are then no longer needed.
