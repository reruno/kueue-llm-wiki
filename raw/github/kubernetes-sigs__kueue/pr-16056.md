#### What this PR does / why we need it?

Investigated #15399: a partially-admitted RayCluster elastic scale-up slice could get
evicted (ClusterQueue drain, preemption, ...) while its scale-up probe sibling was still
pending. #15776 already fixed the main case: once the predecessor is gone,
`PodSetReducer.Reduce`'s `mustGrow` parameter lets the probe fall back and admit itself
directly at its own frozen `MinCount` baseline, once quota returns to at least that level.

That left one gap: the probe's baseline is a snapshot of whatever its predecessor held at
probe-creation time, and nothing ever revisits it. If quota comes back to *less* than
that baseline - even to a level the same job already ran at successfully earlier in its own
history - the probe stays `Pending` forever, with no way for the scheduler to try
anything below `MinCount`.

**Fix**: `normalizeActiveSlices` now lowers the pending probe's `MinCount` (per PodSet,
matched by name) to its evicted predecessor's own `MinCount`, wherever that's lower -
never raises it. The predecessor's own baseline is one step further back in the job's
admission history and still a proven, achievable count. The read happens on the
predecessor before it's finished later in the same call, so it's unaffected by workload
retention GC (which only starts counting from the `Finished` condition), and needs no new
query - the predecessor is already in the in-memory `workloads` slice.

This recovers exactly one additional step of history. If quota drops below the
predecessor's own baseline too, the probe still can't recover - closing that fully would mean
walking the job's entire admission history, which is unbounded over a job's scaling
lifetime and left as a documented, separate gap (see below).

- `pkg/workloadslicing/workloadslicing.go`: added `lowerProbeMinCount`, wired into the
  existing "predecessor evicted" detection in `normalizeActiveSlices`.
- `pkg/workloadslicing/workloadslicing_test.go`: `TestLowerProbeMinCount` (lowers when
  lower, never raises, skips when the predecessor has no baseline, skips a PodSet name the
  predecessor doesn't have), plus an updated `TestNormalizeActiveSlices` case.
- `raycluster_controller_partial_scaleup_test.go`: four specs covering re-admission after
  a ClusterQueue drain, after preemption, recovery at a worker count from one step back in
  history, and a known-gap spec for a shrink below even that one-hop baseline.

AI-assisted: investigation, implementation, and this description were done with Claude
Code; all findings were verified by running the unit/integration tests before writing
this up.

#### Useful notes for your reviewer

- **Why not just finish both the predecessor and the probe, and let the job start over?**
  A workload built with no live predecessor to compare against is indistinguishable from
  a brand-new job's very first admission: `MinCount` never gets set, and an unset
  `MinCount` means "admit exactly `Count` or not at all" (Kueue's general
  `PartialAdmission` convention), not "no restriction." So restarting from scratch would
  make the fresh workload demand the *entire* new request (e.g. 10 workers) to admit
  anything - strictly worse than today's bug, which only requires the old, smaller baseline.
  Fixing that would still need to source a baseline from somewhere, and by the time a fresh
  workload is created the predecessor has already been finished and filtered out of every
  normal lookup - recovering it would mean a new, GC-exposed query, plus solving a
  workload-naming problem that broke in an earlier attempt at this same fix. Patching the
  existing probe's `MinCount` in place avoids all of that: same object, no new query, no
  naming to get right, and no exposure to workload-retention GC.

- **What about the residual gap - quota shrinking below even the predecessor's own baseline?**
  Known limitation, not fixed here. Closing it fully means recovering more than one hop of the job's
  admission history, which we considered two ways of doing and rejected both for now:

  - Walking every finished workload for the job to find the lowest count it's ever been
    granted. This is an unbounded query over the job's entire scaling lifetime, with no
    existing precedent for "search finished history" anywhere in Kueue.

  - Tracking a baseline in an annotation on the job object itself, updated on every
    admission. This avoids the unbounded query, but has its own problems: 
    - keeping it as an all-time minimum risks falling back to a value from a job's
      ancient history that no longer reflects what it realistically needs;
    - keeping it instead as just the most-recently-admitted count (overwritten each time,
      not accumulated) doesn't reach any further back than reading the evicted predecessor
      already does today - it would only make the *same* one-hop recovery more robust
      (surviving even if the in-memory read in `normalizeActiveSlices` were somehow missed),
      not deeper.
    
  Either way, it's a new write path onto a user-managed resource for a benefit we haven't
  confirmed is needed.
  Deferring both as follow-up ideas to revisit if Alpha feedback shows the one-hop
  recovery here isn't enough, rather than building either speculatively.

- `MinCount` is only ever mutated on the probe, which has never held a quota reservation -
  no webhook change was needed (the immutability check on `PodSets` only applies once a
  workload has held a reservation).
