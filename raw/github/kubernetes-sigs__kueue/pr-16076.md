#### What this PR does / why we need it?

The Pod integration currently adds `deletionGracePeriodSeconds` to `metadata.deletionTimestamp` when checking whether a terminating Running Pod still keeps a PodGroup active. For graceful deletion, the API server has already added that grace period when it writes `deletionTimestamp`. A Pod stuck Running beyond the intended deletion deadline can therefore retain quota for an extra grace period.

This PR compares the clock directly with `deletionTimestamp` for Pods with an explicit deletion grace period. It preserves the existing strict deadline boundary, the behavior when no grace period is recorded, and the immediate-release behavior when `FastQuotaReleaseInPodIntegration` is enabled. Tests now use realistic future deletion deadlines for Pods still within grace and cover an expired deadline that previously remained active because of the second addition. An integration test also verifies that a PodGroup releases quota when a subsequent Pod update causes reconciliation after the deletion deadline. The changed activity decision takes effect on the next reconciliation after the deadline; this PR does not add a deadline-triggered reconcile.

Fixes #16075

#### Useful notes for your reviewer

Kubernetes API Server's [`BeforeDelete`](https://github.com/kubernetes/apiserver/blob/master/pkg/registry/rest/delete.go#L894-L898) sets the graceful-deletion timestamp to `now + gracePeriodSeconds`; the [`ObjectMeta` contract](https://github.com/kubernetes/apimachinery/blob/master/pkg/apis/meta/v1/types.go#L2541-L2559) describes it as the expected deletion time. The original Kueue behavior came from #6872.

This PR is based on upstream `main` and changes only PodGroup activity semantics. The separate StatefulSet PR #16044 shares the Pod activity helper but deliberately preserves the current upstream deletion-grace semantics. For active terminating Pods with computable activity deadlines, it uses Pod events and a one-shot recheck after the latest computed activity deadline; it does not poll every second. This PR independently fixes the double-counted deletion grace period. The branches overlap in the helper and its unit tests; whichever PR merges second will be rebased to preserve both changes and their regression tests.

As before, a Pod that remains API-visible and Running beyond its expected deletion time may be treated as inactive for quota accounting even when a partitioned node prevents confirmation that its process has stopped. This change removes the unintended extra grace period, in line with the original stuck-Pod policy from #6872.
