#### What this PR does / why we need it?

Proof of concept for KEP #16088: a built-in `kueue.x-k8s.io/local-capacity` CapacityProvider controller.

- For each flavor in `spec.orchestratedFlavors`, sums `status.allocatable` of Nodes matching the ResourceFlavor's `nodeLabels`. Nodes that are NotReady, cordoned, deleting, or have an untolerated NoSchedule/NoExecute taint are skipped.
- Reports `Misconfigured` (and keeps the last capacity) when a flavor is missing, a flavor is claimed by two local-capacity providers, or a Node matches more than one orchestrated flavor.
- New alpha feature gate `LocalCapacityProvider` (requires `DynamicQuotaOrchestration`), plus RBAC for `capacityproviders/status`.
- No new API types.

Part of #10270

#### Useful notes 

- Relies on the DQO fix in #16168 (merged): a provider orchestrates all resources of its flavors. A flavor without eligible nodes is published with empty `resources`, which DQO distributes as 0.
- Tests: unit tests in `pkg/controller/core/localcapacity`, and an integration test showing Cohort quota following Nodes being added, cordoned and removed (down to 0).
- AI disclosure: prepared with the help of an AI coding assistant and reviewed by me.

### Security Architecture Review

**Security architecture risk:** _🔵 Low_ · up to `b83a1`

The controller is opt-in and preserves the existing administrative access boundaries. The main design concern is rollback: disabling capacity publication alone can leave old capacity marked synchronized and eligible for quota distribution.

**Retained concerns**
- **Medium · reliability · inferred:** After successful publication, restarting with LocalCapacityProvider disabled and DynamicQuotaOrchestration enabled leaves the provider's last capacity and CapacitySynchronized=True unchanged. DQO can continue treating that value as synchronized and distributing it despite subsequent Node changes. Intentional last-good quota retention during reported failures limits disruption, but producer shutdown supplies no equivalent not-ready signal or quota handoff. This is an administrative rollback and control-drift issue, not a demonstrated tenant privilege escalation.

<details>
<summary>Security review details</summary>

**Security Blast Radius**
- _inferred_ — Authority to change matching Node observations, ResourceFlavor mappings, or provider configuration can influence capacity consumed by explicitly referencing DQOs and their configured quota subtrees. The maximum affected scope can span multiple Cohorts and ClusterQueues sharing those inputs. Actual tenant exposure depends on deployment-specific permissions and configuration.

**Trust Boundaries and Controls**
- _observed_ — The controller queues providers identified by the local controllerName and reads Nodes without mutation authority. Status publication is protected by Kubernetes RBAC; DQO consumes explicitly referenced providers and filters published flavors against their declared scope. The inspected RBAC change grants status authority to the manager, not a tenant identity.

**Resilience and Maintainability Implications**
- _observed_ — Input and status-write errors return through reconciliation for retry, while configuration changes enqueue all local providers to recheck ownership conflicts. This supports recovery without deleting the last published capacity. The gate-disabled path differs because it stops the producer without reporting that its observations are no longer current.

**Hardening Proposals**
- _proposed_ — Define a coordinated provider-retirement and quota-handoff procedure before disabling the producer. Specify how freshness is invalidated and how existing effective quotas are retained, replaced, or removed; stopping publication or marking a provider not ready does not itself retract already distributed quotas.

+// flavor orchestrated by the provider.
+//
+// A node counts toward a flavor when it matches all of the flavor's nodeLabels,
+// is Ready, schedulable and not being deleted, and has no scheduling taint that
+// the flavor neither tolerates nor declares in nodeTaints.
+//
+// Every orchestrated flavor is published, with empty resources when it has no

+// good quota instead of distributing double-counted capacity.
+func computeCapacity(provider *kueuealpha.CapacityProvider, in *inputs) result {

+		}

  **Add a watch on CapacityProvider deletion so the remaining overlapping providers recover.**
  
  The `For` watch uses `GenerationChangedPredicate`. This predicate lets create and delete events pass. A delete event enqueues only the deleted provider, and `Reconcile` returns NotFound for it. Suppose `nodes` and `nodes-dup` both claim `h100`, so both are Misconfigured. If an operator deletes `nodes-dup`, nothing enqueues `nodes`. A spec change to one provider has the same effect: the other provider that overlaps with it is not re-reconciled. That provider stays Misconfigured, and DQO keeps the stale quota until an unrelated Node or ResourceFlavor event arrives. Add a second watch on `CapacityProvider` that maps to all local-capacity providers through `mapToAllProviders`.
