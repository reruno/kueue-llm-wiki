## Description

#### What type of PR is this?

#### What this PR does / why we need it?

Kueue derives the effective resources of a Workload for quota accounting, and that view now defaults the pod-level requests (`pod.spec.resources`, KEP-2837) the way the API server does.

Before this change a missing pod-level request was filled from the pod-level limit. The API server instead aggregates the container requests and falls back to the pod-level limits only when no container specifies the resource. Two containers requesting 1 CPU each under a pod-level limit of 4 run with a pod-level request of 2, while Kueue counted 4, so the capacity reserved for the Workload was wrong in both directions.

The defaulting also depends on when the API server runs it. Starting with 1.37, the pod-level requests are defaulted after admission, so the aggregate includes the container defaults that LimitRanges inject. Older servers run it before admission and only see what the user wrote. Kueue mirrors the matching order and picks it from the server version, which now comes from the existing `ServerVersionFetcher`. The effective resources are also what the pod role-request validation checks against, so that path follows the server version too.

The one configuration Kueue cannot detect is a 1.37+ server running with `PodLevelResourcesFixDefaulting` disabled, so the gate covers it: `PodLevelResourceFixDefaultingForNewServer` (0.21, beta, enabled by default). When it is enabled the order follows the server version; when it is disabled Kueue always mirrors the pre-1.37 order. It only changes behavior on 1.37+ and will be removed together with the version detection.

This is the accounting part of the fix. The provisioning pod template change that consumes the same defaulting follows in a separate PR, to keep this one reviewable.

#### Tests

- `pkg/workload`: table tests cover both orderings, the pod-level hugepage limits, pod-level requests without limits, and the same cases with the Kueue gate disabled. `TestUpdateFromClientServerVersionDefaulting` adds the gate-off 1.37 case.
- `pkg/controller/jobs/pod`: a pod-level limit without container requests reserves the pod-level limit on a 1.36 server and the LimitRange default on 1.37, so the same pod is ungated on the first and kept gated on the second.
- `pkg/features`: `make generate-featuregates` regenerates both YAML files and is idempotent.
- `test/integration/singlecluster/scheduler`: the existing pod-level resources case now expects 3 CPU of queue consumption, the container LimitRange default, instead of 4 from the pod-level limit.
- `go build ./...`, `go test ./pkg/workload/ ./pkg/features/ ./pkg/cache/... ./pkg/controller/core/ ./pkg/controller/jobs/pod/ ./pkg/controller/jobframework/`, `gofmt`, `go vet` and `golangci-lint --config .golangci.yaml` pass locally.

#### Release note

```release-note
Fix the pod-level request defaulting used for quota accounting: it now aggregates the container requests like the API server, including the container LimitRange defaults on Kubernetes 1.37+, instead of reading the pod-level limits. The order follows the server version and can be forced to the pre-1.37 behavior with the PodLevelResourceFixDefaultingForNewServer feature gate (0.21, beta).
```

Normal resource accounting becomes more accurate, but an API-server version transition can leave an existing quota reservation inconsistent with newly derived provisioning requests. The concern is bounded to resource isolation and capacity allocation; no credential or privilege escalation was established.

**Retained concerns**
- **Medium · security · inferred:** A quota reservation can outlive the defaulting mode used to calculate it, while provisioning independently selects the latest mode. The partial-container test case changes its pod-level CPU request from 1 to 2 across 1.37, but existing reservations continue to use stored admission.ResourceUsage. Without coordinated re-reservation, this creates a potential quota-isolation mismatch during a version transition.
