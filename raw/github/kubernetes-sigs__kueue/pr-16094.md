#### What this PR does / why we need it:

Requires Kueue-managed RayServices that use zero-downtime upgrades to enable workload slicing. An unset upgrade strategy or type follows KubeRay's default zero-downtime behavior, so only an explicit `None` strategy can run without the `ElasticJobsViaWorkloadSlices` feature gate and elastic-job annotation.

This prevents RayServices from starting a second RayCluster without a workload-slice replacement that accounts for both clusters. It also updates the sample and non-upgrade test fixtures to explicitly select `None`.

Note: zero-downtime upgrade still has some issues before https://github.com/kubernetes-sigs/kueue/pull/11264/ is merged.

AI disclosure: This pull request was developed with assistance from OpenAI Codex.

NONE

#### Special notes for your reviewer:

### Security Architecture Review

**Security architecture risk:** _🟡 Moderate_ · up to `d2035`

Requiring workload slicing addresses an upgrade-accounting problem, but the new validation can also reject RayServices in namespaces excluded from Kueue management. That could block otherwise valid service creation or updates. No privilege escalation or independently exploitable attack path was established.

**Retained concerns**
- **Medium · architecture · inferred:** The upgrade-strategy gate uses the manage-without-queue setting without checking whether a queue-less RayService's namespace is selected for Kueue management. In an excluded namespace, this can reject default-strategy creates and updates that the management defaulting path leaves unmanaged.
