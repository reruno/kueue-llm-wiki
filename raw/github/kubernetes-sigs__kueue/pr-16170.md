## Description

#### What type of PR is this?

/kind bug

#### What this PR does / why we need it?

`podset.FromAssignment` builds a PodSet's node selector from the assigned flavors. When two flavors set the same node label key to different values, the result depended on map iteration order.

This makes the merge deterministic: flavors are processed in sorted resource order, the first value wins, and later conflicts are logged. `AssignFlavors` also rejects the conflict before quota is reserved, behind the `FailAdmissionOnConflictingFlavorLabels` feature gate. The gate is beta and enabled by default for 0.21; the backport will set it to disabled.

Admission check `podSetUpdates` are merged with the same rule: values already present on the flavor or pod template win, and among admission checks the first update wins. Later conflicting values are logged and ignored. This keeps already admitted workloads, the provisioning admission check, and job start from getting stuck on a conflict that was previously only detected at runtime.

Fixes #14409

#### Tests

- Unit tests cover deterministic flavor merging, admission-check-first-wins, and the gate on/off behavior.
- Integration tests cover a pending workload that never reserves quota when the gate is on, and admission-check conflicts that now start with the existing value.
- The full job integration suite passes 137/137. `go test ./pkg/...` passes except for the pre-existing `pkg/config.TestClusterProfileCRDPresent` environment test.

#### Release note

```release-note
Make node label merging across assigned flavors deterministic when the same key has conflicting values. Pending workloads can be rejected before quota reservation with the FailAdmissionOnConflictingFlavorLabels feature gate (beta, enabled by default). Admission check podSetUpdates are merged deterministically so existing workloads are not disrupted.
```

The change prevents contradictory placement requirements from silently selecting a node-label value. New conflicting assignments are rejected before reserving quota. A bounded recovery concern remains for already-reserved workloads awaiting provisioning: the new error can leave them pending while capacity remains reserved.

**Retained concerns**
- **Medium · reliability · inferred:** An already quota-reserved workload with conflicting flavor labels can remain Pending when provisioning still needs to build its PodTemplate. FromAssignment now returns a permanent error, but provisioning records the error without changing the admission check to a terminal or retry state. The job framework's FailedToStart handling requires the workload to be admitted, so it does not resolve this pending-check path. Reserved capacity can consequently remain unavailable until configuration correction or separate eviction/deactivation. Scheduler validation prevents fresh conflicting selections; the exposure is existing reservations or flavor changes after reservation, not an unrestricted new allocation path.

```golang
func (s *flavorNodeSelector) Add(flv *kueue.ResourceFlavor) error {
```
