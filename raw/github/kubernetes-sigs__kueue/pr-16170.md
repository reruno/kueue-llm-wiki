## Description

#### What type of PR is this?

/kind bug

#### What this PR does / why we need it?

`podset.FromAssignment` builds the Pod's node selector from `assignment.Flavors`, a map, by copying each flavor's node labels onto it. When two assigned flavors set the same label key to different values, the winner was whichever flavor the loop visited last, and the selector could differ from one reconcile to the next.

This walks the flavors in a stable resource order, and refuses the conflict the same way `PodSetInfo.Merge` already does, so a contradictory assignment fails visibly instead of silently picking a side.

Fixes #14409

#### Useful notes for your reviewer

The conflict is refused rather than resolved. Today a workload that spans two flavors which disagree on a label key, say `topology.kubernetes.io/zone`, gets pinned to one of the values depending on map order. Returning an error matches the contract `PodSetInfo.Merge` already has and surfaces the misconfiguration. If you would rather keep it silent with a stable winner, that part is easy to drop.

`FromAssignment` feeds pod preparation in the job framework, the provisioning admission check and the TAS node controller, so all three now see the error instead of a silently chosen value.

The stable walk also fixes the tolerations slice, which was appended in map order before.

Two of the new tests fail against the current code: one asserts that a conflict is refused on every run, the other runs the assignment 100 times and checks that the tolerations order is stable. The third pins that flavors which share a key with the same value still merge.

### Review by [@j-skiba](https://github.com/j-skiba) (commented) — 2026-10-21T07:53:15Z

I'd like to come back to @tomsen02's first question.

The `FailedToStart` path only kicks in from the job reconciler. If the `ClusterQueue` has a `ProvisioningRequest` admission check, the provisioning controller calls `FromAssignment` first (it runs at `QuotaReserved`, before the workload is `Admitted`), gets the error, and just requeues forever while holding the quota. So for those users we trade "running but mispinned" for "stuck".

I think we should refuse the combination in the flavor assigner, so it is never admitted in the first place. In `AssignFlavors`, after the per resource loop fills `groupFlavors`, we can run `HaveConflict` over the assigned flavors' nodeLabels and set groupFlavors = nil + a status naming both flavors and the key, same as the existing no-fit path. Then the workload stays pending with a readable reason and we don't have to add special case handling for all of the cases.
