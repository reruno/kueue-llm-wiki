#### What this PR does / why we need it?

Adds end-to-end coverage for re-admitting a worker-side autoscaled RayCluster after preemption.

The test verifies that:

- the RayCluster starts with one worker from the manager specification;
- the worker-side autoscaler scales it to two workers;
- a higher-priority Job preempts it on the same worker cluster; and
- the RayCluster is re-admitted with one worker from the manager specification and a newly created worker copy.

This draft depends on PR 15871. Until that PR merges, this branch intentionally includes its prerequisite commits.

AI assistance was used to prepare and validate the test and this PR description.

### Security Architecture Review

**Security architecture risk:** _🟡 Moderate_ · up to `e225d`

The test checks successful preemption and readmission, but the accompanying worker-count changes need review for annotation ownership and recovery after interrupted updates. No security vulnerability was verified.

**Retained concerns**
- **Medium · security · inferred:** Manager-side workload counts can derive from mutable runtime annotations. The available evidence does not establish who may write those annotations or whether count and generation state is reliably cleared across interrupted preemption and readmission. This is an unresolved control-boundary and recovery question, not a verified bypass.

<details>
<summary>Security review details</summary>

**Security Blast Radius**
- _inferred_ — If runtime annotations are accepted from an unauthorized or stale writer, the directly affected decision is manager-side PodSet sizing for the associated Ray workload. The available evidence does not establish a path to broader privileges or cross-tenant exposure.

**Trust Boundaries and Controls**
- _observed_ — The runtime-count reader is feature-gated and ignores malformed annotations and negative counts. These checks do not, by themselves, establish writer authorization.

**Hardening Proposals**
- _proposed_ — Confirm the annotation writer's authority and the ordering of count and generation clearing during preemption, including retry and partial-failure paths.
