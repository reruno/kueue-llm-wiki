#### What this PR does / why we need it?

When a MultiKueue worker watch reconnects after being disconnected, the manager now immediately resynchronizes remote workloads owned by that worker. This detects state changes such as `Finished` or `Evicted` that occurred while the watch was disconnected.

Previously, the manager relied on the next periodic workload reconciliation to detect those changes. This could delay status propagation and cleanup by up to the configured `workerLostTimeout` interval, even after the worker connection had recovered.

This PR adds `requeueWorkloadsForCluster`, which lists remote workloads matching the manager's MultiKueue origin label and queues the corresponding manager workloads for reconciliation. The existing reconciliation logic then re-reads the remote state and updates the manager workload as usual.

Fixes #16172 

#### Useful notes for your reviewer

- Resynchronization runs only after a previously disconnected client reconnects, guarded by `!connected` in `updateConfigAndRefreshWatchers`.
- Existing watch event handling is unchanged; this adds an immediate recovery pass for matching workloads.
- If the remote workload list fails, the error is logged and the normal watch remains active.
- Individual manager workload lookup failures do not stop processing other listed workloads.
- No new dependencies are introduced.
- Tests:
  - `TestRemoteClientResyncWorkloads` verifies origin filtering and manager-workload enqueueing.
  - `TestDisconnectedClientReconnectsWithSameConfig` exercises reconnect behavior.

#### Release note

```release-note
MultiKueue: Immediately resynchronize workloads when a worker watch reconnects instead of waiting for the next polling interval.
```
