#### What this PR does / why we need it?

Moves the latest admitted slice -> reclaim-adjusted PodSet counts logic out of the provisioning admission-check controller into `pkg/workloadslicing` as `PreviousAdmittedPodSetCounts(ctx, client, wl)`, so partial atomic scale-up
can reuse it instead of duplicating. 

The`ElasticJobsViaWorkloadSlicesForProvisioningRequests` feature-gate check stays in the provisioning controller; `previousSlicePodSetCounts` is now just the gate plus a call to the shared helper.

The helper returns the effective PodSet counts of the latest admitted, non-evicted slice in the workload's chain other than the workload itself (finished/replaced slices included, since their pods are the running capacity baseline while a successor waits), taken from `workload.Info.TotalRequests` so reclaimed pods and in-place scale-downs are accounted for the same way quota is.

No behavior change.

Follow-up to #14316, specifically addressing https://github.com/kubernetes-sigs/kueue/pull/14316#discussion_r4104082203 

Related: #14316

#### Useful notes for your reviewer

- `TestPreviousAdmittedPodSetCounts` (new, in `pkg/workloadslicing`) covers:
  latest finished slice as baseline with a pending intermediate ignored,
  reclaimed pods reducing the baseline, in-place scale-down using the current
  spec rather than the stale assignment, the workload not being its own
  baseline, and no admitted predecessor.
- `TestPreviousSlicePodSetCounts` in the provisioning controller is reduced to
  the gating cases (feature gate on/off, non-elastic workload).
- Validated end to end on GKE with both `queued-provisioning.gke.io` and
  `best-effort-atomic-scale-up.autoscaling.x-k8s.io`: rapid 1->2->3->4
  overlap (PRQ of 3), in-place 4->1 shrink (no PRQ), 1->3 re-grow (PRQ of 2
  from the shrunk slice), pod-loss recovery, leader failover during a resize
  (single PRQ, no duplicates), Job-deletion GC, and a non-elastic control Job
  (full-size PRQ, legacy template handling).

+// nil when there is none. Finished (replaced) slices are included because

+// Counts come from workload.Info.TotalRequests, so reclaimed pods are
+// subtracted the same way quota accounting does: a predecessor admitted for 3
+// with 1 pod reclaimed is a baseline of 2.
+//
+// This is the baseline an incremental scale-up (e.g. a ProvisioningRequest or
+// a partial atomic scale-up) should subtract from wl's own counts.
+func PreviousAdmittedPodSetCounts(ctx context.Context, c client.Client, wl *kueue.Workload) (map[kueue.PodSetReference]int32, error) {
