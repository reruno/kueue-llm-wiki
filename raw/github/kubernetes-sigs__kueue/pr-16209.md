#### What this PR does / why we need it?

When a new workload slice was created for an elastic scale-up, its PodSet's MinCount
was recomputed from the predecessor's live granted count. Each successive scale-up
step therefore ratcheted the floor up to whatever was most recently admitted, instead
of preserving the count the job was originally admitted at. If quota later shrank
below that most-recent live grant - even to a level the job had already run
successfully at earlier in its own chain - the workload could get stuck pending
instead of recovering.

MinCount is now copied forward verbatim from the predecessor's own recorded MinCount
at creation (prepareWorkloadSliceForScaleUp), so it keeps tracing back to the chain's
origin rather than drifting upward with every scale-up. The scheduler still enforces
that a re-admission must be genuine growth over what's currently running: while a
live predecessor exists, effectiveReducerPodSets swaps its live granted count in as
the reducer's baseline for that one check (getInitialAssignments), without ever
mutating the persisted MinCount itself.

RayCluster's BuildPodSets also now unconditionally bootstraps a worker group's
MinCount to its own requested count (Replicas) when the partial-scale-up annotation
is set, instead of only doing so when MinReplicas was set - MinReplicas is no longer
consulted for this at all.

Fixes #16052

#### Useful notes for your reviewer

- `pkg/scheduler/scheduler.go`: `effectiveReducerPodSets` is the only place a live
  grant is consulted, and only to compute the in-memory reducer baseline for the
  mustGrow check - the workload's own `MinCount` field is never mutated.
- `pkg/controller/jobs/raycluster/common.go`: dropped the `MinReplicas != nil` gate,
  since keeping it made the bootstrap value depend on an upstream KubeRay field this
  mechanism doesn't otherwise need.
- New/updated integration coverage in the RayCluster and RayJob partial-scaleup
  suites pins both the fixed behavior (recovery at a previously-run-at count below
  the immediate predecessor's grant) and the known remaining gap (quota shrinking
  below the chain's origin entirely - out of scope here, likely follow-up material
  once scale-down/preemption for elastic jobs is designed).

### Security Architecture Review

**Security architecture risk:** _🔵 Low_ · up to `0c8e3`

The change is limited to partial scale-up workloads, and the scheduler keeps its live-grant adjustment temporary. One ordering case could nevertheless assign a worker group the wrong persisted floor and impair recovery.

**Retained concerns**
- **Medium · architecture · inferred:** A scale-up following a worker-group reorder can persist another group's minimum-count floor. Slice compatibility accepts the same PodSet names regardless of order, but replacement construction copies floors by index. This can compromise the intended floor and quota-shrink recovery for the affected workload.

<details>
<summary>Security review details</summary>

**Security Blast Radius**
- _inferred_ — Triggering the identified ordering case requires a partial-scale-up job whose worker-group order changes before a replacement slice is created. The inspected path does not establish privileges to edit such a job or exposure beyond its workload.

**Trust Boundaries and Controls**
- _observed_ — The scheduler consults predecessor grants only when growth over an admitted predecessor is required. It matches grants by PodSet name, caps them to predecessor spec counts, and substitutes them in a cloned reducer input.

**Resilience and Maintainability Implications**
- _inferred_ — Name-based compatibility followed by position-based floor copying leaves a persistent-state identity gap: after a reordered scale-up, a later quota recovery can be evaluated against the wrong worker-group floors.

**Hardening Proposals**
- _proposed_ — Copy predecessor floors by PodSet name, or reject replacement construction when predecessor and candidate identities cannot be matched; cover reordered groups alongside the existing drain-and-recovery scenario.
