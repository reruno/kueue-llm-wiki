#### What this PR does / why we need it?

MultiKueue currently removes completed remote objects immediately, preventing users from inspecting completed runs on worker clusters. Extend KEP-693 with an optional global retention duration, behind the default-off Alpha `MultiKueueRemoteObjectRetention` gate targeting v0.21.

The proposal defines configuration defaults, completion and early-cleanup behavior, safe cleanup across same-name runs, restart and disable behavior, and the test plan. Retaining objects does not delay scheduler quota release. Manager-side Workload retention remains independent, and the proposal documents the cleanup limitation when worker configuration is removed or reassigned.

Part of #13847

#### Useful notes for your reviewer

Documentation only, following the request for a small KEP update: https://github.com/kubernetes-sigs/kueue/issues/13847#issuecomment-5810329424. ### Review by [@kshalot](https://github.com/kshalot) (commented) — 2026-10-20T12:40:26Z

@YQ-Wang Thanks for taking the time to work on this 🎉 , but I wanted to highlight a few concerns/questions.

I'm wondering whether this is truly preferable over letting workers do the cleanup. This per-worker autonomy also makes sense for the multi-tenant setup in the original issue. It does not require relying on a global timer, isn't prone to leaks after changing the list of clusters, respects TTLs defined in the job objects etc. I think this is missing in the alternatives.

This is also a little bit at odds with `objectRetentionPolicies.workloads.afterFinished`, because as soon as the manager-side workloads are deleted, the deletion cascades to worker job and workload as well. You stated that:
> The manager-side `objectRetentionPolicies.workloads` policy from
[KEP-1618](../1618-optional-gc-of-workloads/README.md) stays a separate field: there
`nil` means never delete, while for remote objects `nil` must keep today's immediate
cleanup.

But I'm wondering whether we really have to preserve this "immediate deletion" approach. I think it was just the simplest way to avoid name collisions during resubmits, but I'm not 100% sure. It's most likely an implementation detail

Given this, even if we want to proceed with manager-initiated cleanups, maybe for alpha we could use a simple feature gate instead of committing to an API. This way we could verify that this is the right approach without going too deep.

This is also closely related to a race condition we have open: https://github.com/kubernetes-sigs/kueue/issues/14779.
It might be worth it to make sure there is no overlap.

LMK what you think
