#### What type of PR is this?

#### What this PR does / why we need it?

MultiKueue currently removes completed remote objects immediately, preventing users from inspecting completed runs on worker clusters. Extend KEP-693 with an optional global retention duration, behind the default-off Alpha `MultiKueueRemoteObjectRetention` gate targeting v0.21.

The proposal defines configuration defaults, completion and early-cleanup behavior, safe cleanup across same-name runs, restart and disable behavior, and the test plan. Retaining objects does not delay scheduler quota release. Manager-side Workload retention remains independent, and the proposal documents the cleanup limitation when worker configuration is removed or reassigned.

Part of #13847

Following up on the field vs gate-only question: I'd suggest gate-only for Alpha. That means `MultiKueueRemoteObjectRetention` skips the finished-path remote delete in `reconcileGroup`, and the README picks it and rejects the `remoteObjects.afterFinished` field in Alternatives, not the other way round.

- **Keep from the current design:** the same-name guard. The Job adapter syncs status from any existing same-name remote Job (`job_multikueue_adapter.go:60-87`), so a retained copy would leak the old run's status into a re-run. Keep immediate cleanup for eviction, deactivation, quota loss and non-selected workers.
- **Scope Alpha to `batch/Job` and JobSet.** Pod groups, LWS and multi-Workload adapters keep immediate cleanup.
- **Risks:** add the disconnected-worker leak. `runGC` lists only remote Workloads, so a mirrored Job whose Workload is already gone is never found, and retention widens that window.
- **Beta criterion:** decide whether a dedicated duration is still needed once Alpha users report on the coupling to the manager Workload lifetime. A field can be added later; it can't be removed.
- **#15247:** I see it as separate and not on this path. It deletes manager owners, and it doesn't keep worker copies.

### Review by [@kshalot](https://github.com/kshalot) (commented) — 2026-10-20T12:40:26Z

@YQ-Wang Thanks for taking the time to work on this 🎉 , but I wanted to highlight a few concerns/questions.

I'm wondering whether this is truly preferable over letting workers do the cleanup. This per-worker autonomy also makes sense for the multi-tenant setup in the original issue. It does not require relying on a global timer, isn't prone to leaks after changing the list of clusters, respects TTLs defined in the job objects etc. I think this is missing in the alternatives.

This is also a little bit at odds with `objectRetentionPolicies.workloads.afterFinished`, because as soon as the manager-side workloads are deleted, the deletion cascades to worker job and workload as well. You stated that:
> The manager-side `objectRetentionPolicies.workloads` policy from
[KEP-1618](../1618-optional-gc-of-workloads/README.md) stays a separate field: there
`nil` means never delete, while for remote objects `nil` must keep today's immediate
cleanup.

+##### Lifecycle
+
+When the manager Workload finishes with reason `Succeeded` or `Failed`, the
+MultiKueue Workload Controller keeps the remote Workload and mirrored job on the
+worker where the Workload ran until `Finished.LastTransitionTime + afterFinished`,
+and requeues the Workload for the remaining time. Completion reporting and quota
+release are not delayed. Because the deadline comes from the persisted condition, a
+manager restart neither extends retention nor recreates objects that are already
+gone. If that worker is unreachable, the controller retries every
+`workerLostTimeout` without resetting the deadline.
+
+Cleanup stays immediate when:
+
+* the Workload finishes for any other reason, such as `OutOfSync` or `OwnerNotFound`;
+* the manager Workload is evicted, deactivated, or loses its quota reservation, even
+  if it has also finished;
+* the manager Job or Workload is deleted;
+* the objects are on a worker other than the one the Workload ran on;
+* the retained remote Workload is out of sync with the manager Workload, is evicted
+  on the worker, or is confirmed missing. An unreachable worker does not count as
+  missing.
+
+Elastic Workload handling is unchanged: replaced slices keep their existing
+shared-object lifecycle and never start retention.
+
+The orphan garbage collector finds remote objects only through remote Workloads
+that carry this manager's origin label. A mirrored job whose remote Workload is gone
+could therefore never be collected if a later manager-side cleanup were missed, so
+the controller deletes the job once it confirms that the remote Workload is missing.
+As a consequence, deleting the remote Workload on the worker, for example through
+the worker's own `objectRetentionPolicies.workloads`, also ends retention of its job.
+
+The manager-side `objectRetentionPolicies.workloads` policy from
+[KEP-1618](../1618-optional-gc-of-workloads/README.md) stays a separate field: there
+`nil` means never delete, while for remote objects `nil` must keep today's immediate
+cleanup. Deleting the manager Workload, including by that policy, ends remote
+retention, so that policy caps how long remote objects can be kept. Deleting the
+manager Job has the same effect, including deletion by the job retention policy
+proposed in [KEP-14672](https://github.com/kubernetes-sigs/kueue/pull/15247). The
+orphan garbage collector (`gcInterval`) is unchanged and still deletes remote
+objects only when their manager Workload no longer exists.
+
+Expiry cleanup uses the current `MultiKueueConfig` worker list, so the worker, its
+`MultiKueueCluster`, and its credentials must stay configured until cleanup
+finishes. Otherwise, retained objects need manual cleanup; this feature does not
+discover objects on workers outside the current configuration.
+

  This rule only helps while the worker is reachable. If a worker's own workloads.afterFinished deletes the worker-side Workload while the worker is disconnected, and the manager Job is deleted before reconnect (or the manager restarts), the delete path skips the unreachable worker and drops deletedWlCache, and runGC lists only worker-side Workloads, so the worker-side Job is never found and leaks. Retention widens this window from seconds to afterFinished (or, with gate-only, the lifetime of the manager Job).
  
  Two ideas:
  
  1. Make manager-side cleanup durable, e.g. keep the manager Workload (finalizer or persisted pending-cleanup state) until the mirrored job has been deleted on every worker it was dispatched to. The job is deleted by its known name, so the worker-side Workload isn't needed. Tradeoff: the manager Workload stays Terminating while a worker is down.
  2. Let GC discover mirrored objects directly, listing each adapter GVK by kueue.x-k8s.io/multikueue-origin and checking the prebuilt Workload name against the manager. Tradeoff: an extra uncached List per GVK per worker every gcInterval, plus per-adapter ownership checks (LWS/STS have no prebuilt name).
  
  If neither fits Alpha, could Risks and Mitigations at least call out this leak?
