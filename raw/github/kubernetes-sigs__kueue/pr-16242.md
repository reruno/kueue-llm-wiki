#### What this PR does / why we need it?

Assume the RayCluster uses elastic workload slicing with partial scale-up, and its existing WorkloadSlice has been admitted. 

Initially, its worker groups are ordered as follows:

```
apiVersion: ray.io/v1
kind: RayCluster
...
spec:
  workerGroupSpecs:
  - groupName: analytics
    replicas: 2
    ...
  - groupName: serving
    replicas: 5
    ...
```

The user then scales `groupName: analytics` from 2 to 5 replicas and swaps its position with `groupName: serving` in the same update. The updated order is saved by the API server:

```
apiVersion: ray.io/v1
kind: RayCluster
...
spec:
  workerGroupSpecs:
  - groupName: serving
    replicas: 5
    ...
  # The worker groups have been reordered.
  - groupName: analytics
    replicas: 5
    ...
```

Kueue creates a new WorkloadSlice for the scale-up. Before the fix, it inherited each PodSet’s `MinCount` from the previous WorkloadSlice by array position rather than by name. Consequently, the new WorkloadSlice could record a minimum of 2 for `serving` and 5 for `analytics` , the opposite of their original minimums.

The fix looks up each PodSet in the previous WorkloadSlice by name and copies its corresponding `MinCount`.
