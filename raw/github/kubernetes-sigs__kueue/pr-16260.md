#### What this PR does / why we need it?

Validates RayJob and RayService creation when MultiKueue in-tree autoscaling is requested.

MultiKueue-managed elastic Ray workloads that enable in-tree autoscaling are rejected unless the `MultiKueueRayInTreeAutoscaling` feature gate is enabled. This prevents users from creating workloads whose autoscaling behavior is not supported by the active feature-gate configuration.

This change includes webhook unit coverage for both the disabled and enabled feature-gate cases for RayJob and RayService.

AI usage disclosure: This PR was developed with assistance from an AI coding tool. The contributor reviewed and tested the resulting changes.

#### Useful notes for your reviewer

This PR intentionally contains only the webhook validation and its unit tests. The runtime MultiKueue RayService autoscaling changes are handled separately.

### Security Architecture Review

**Security architecture risk:** _🔵 Low_ · up to `f5637`

The change tightens admission without demonstrating new access or authority. However, the restriction also applies to updates, so previously accepted RayServices can lose ordinary update and suspension paths after an upgrade, even with the autoscaling feature enabled.

**Retained concerns**
- **Medium · reliability · inferred:** Previously admissible queued, workload-sliced MultiKueue RayServices with in-tree autoscaling now fail update validation even when the autoscaling gate is enabled. Updates that retain this configuration, including suspension changes, encounter the new prohibition without an existing-object exception. This creates an upgrade-related failure-containment and recovery risk; production stranding or deletion failure has not been demonstrated.

- _inferred_ — The identified exposure is bounded to Ray objects selected by the existing admission-routing conditions and the MultiKueue ownership check. - _inferred_ — Because suspension modifies the RayService spec, applying the new prohibition to updates can obstruct suspension of an existing incompatible object. This matters to operational containment, although an end-to-end eviction or recovery failure was not demonstrated.
