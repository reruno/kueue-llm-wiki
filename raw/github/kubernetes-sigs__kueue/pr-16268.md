#### What this PR does / why we need it?

Adds `workload.ExtractGrantedPodSetCountsAfterReclaim(wl)`: `ExtractGrantedPodSetCounts` with each count capped at the PodSet count after reclaimable pods (nil when there is no admission). `workloadslicing.PreviousAdmittedPodSetCounts` now uses it instead of constructing a `workload.Info` to read `TotalRequests`. 

Predecessor selection and error behavior are unchanged, the baseline stays reclaim adjusted.

Fixes #16227
Follow-up to #16206 requested in https://github.com/kubernetes-sigs/kueue/pull/16206#discussion_r4104771743.

#### Useful notes for your reviewer

- `TestExtractGrantedPodSetCountsAfterReclaim` covers no admission, partial grants, reclaimed pods, in-place scale-down (with and without reclaim), reclaim exceeding the count, multiple PodSets, and the `ReclaimablePods` gate off.
- `TestPreviousAdmittedPodSetCounts` is unchanged and still passes, including the reclaim case, so the swap is behavior-preserving.
- Validated on GKE `queued-provisioning.gke.io` and `best-effort-atomic-scale-up`

Run tests added:
```bash
go test ./pkg/workload/ -run 'TestExtractGrantedPodSetCountsAfterReclaim' -v -count=1
```

### Security Architecture Review

**Security architecture risk:** _🔵 Low_ · up to `4b36e`

For normally admitted workloads, the new calculation preserves the reclaim-adjusted provisioning baseline. It handles a contradictory admission status differently, but whether that state can occur in practice remains unconfirmed.

**Retained concerns**
- **Low · reliability · inferred:** If a selected predecessor has Admitted=true but no Admission, the new baseline is nil rather than the former spec-derived counts. Incremental provisioning would then omit the predecessor subtraction. Reachability of this contradictory status is unproven.
