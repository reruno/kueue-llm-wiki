#### What this PR does / why we need it?

`fetchWorkloadDetails` builds a `workloadResult` with `clusterQueueName` and `preemption`, but returned the bare Workload. Since #7663 the workload detail page has shown no ClusterQueue and linked to `/cluster-queue/undefined`. This returns the `workloadResult`.

Also adds unit tests for `fetchWorkloads`, `fetchWorkloadDetails` and `fetchWorkloadEvents`. The details tests fail on main and pass with the fix.

Fixes #16275

- Ran `go test ./...` and `go vet ./...` in `cmd/kueueviz/backend`.

### Security Architecture Review

**Security architecture risk:** _🔵 Low_ · up to `bf3cc`

The detail response now includes the ClusterQueue name associated with a workload’s LocalQueue. A user permitted to view the workload may learn that association without permission to view the LocalQueue. The exposure is limited to a name, and the workload-detail route still requires authorization.

**Retained concerns**
- **Low · security · inferred:** Returning the LocalQueue’s ClusterQueue name can reveal a queue association to a Workload reader who lacks LocalQueue read permission, particularly before the Workload has admission information.

<details>

**Security Blast Radius**
- _inferred_ — The additional exposure is a LocalQueue-to-ClusterQueue name association for callers authorized to view the Workload; it does not return the LocalQueue object or grant access to the ClusterQueue detail route.

**Security Findings and Attack Paths**
- _inferred_ — A caller with Workload get/watch but without LocalQueue read permission can request an unadmitted workload’s detail response and learn the LocalQueue’s ClusterQueue name through the new field.
