#### What this PR does / why we need it?

`classifyWorkloadsForPriorityUpdate` compares each workload's class name against the owner's `kueue.x-k8s.io/priority-class` label. When the owner has no label, that name is `""`, and a workload with no `priorityClassRef` reads as naming the same empty class, so it lands in `sameClassName`. If a sibling in the same batch still holds a `WorkloadPriorityClass` reference, it lands in `needsClassChange`, the helper resolves the fallback, and `UpdateWorkloadPriority` writes the resolved ref and value to both groups. The unreferenced workload's value came from a Pod `PriorityClass` or the cluster default, not from the label, so this reconciliation should not touch it (the same intent as #13781 / #8480).

This PR skips workloads without a `priorityClassRef` when the owner names no class, next to the existing quota-reserved skip. It is the guard proposed in the issue.

Fixes #14484

#### Useful notes for your reviewer

- Single-workload calls are unaffected: a lone unreferenced workload under an unlabelled owner already produced an empty `needsClassChange`, so nothing was written. The guard only changes the mixed-batch case described in the issue.
- A new case in `TestUpdateWorkloadPriority`, "leaves the unreferenced workloads of an unlabelled owner alone while a sibling transitions", asserts that the unreferenced workload keeps its ref and value, that the sibling moves to the Pod PriorityClass fallback, and that exactly one workload write happens.
- Verification: `go vet ./pkg/controller/jobframework/` and `gofmt` are clean. I could not execute the unit tests locally because Windows Application Control on my machine blocks the compiled test binary, so I'm relying on CI for the test run.
- The issue notes it is not yet established that a real workload-slice pair can hold both shapes at once. This change is a defensive fix to the shared helper either way.
