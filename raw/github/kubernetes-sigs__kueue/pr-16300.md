### Security Architecture Review

**Security architecture risk:** _🟡 Moderate_ · up to `0b060`

The new status validation can reject an empty capacity result, potentially leaving quota-related status stale. The review found no new access path or privilege escalation, but the behavior of status writers during empty-capacity transitions remains uncertain.

**Retained concerns**
- **Medium · reliability · inferred:** A present capacity-status object with no flavors is no longer publishable. DQO discovery can produce that state, so a status update may fail and retry without persisting its new condition; analogous empty CapacityProvider publications may be rejected. This is a failure-containment concern, not an established privilege bypass.

<details>
<summary>Security review details</summary>

**Security Blast Radius**
- _inferred_ — Exposure is bounded by permissions to create these cluster-scoped resources or publish their status, and by the applicable feature gates. A failed capacity publication could affect the quotas derived from the last persisted status; its effective scope in a deployment was not established.

**Trust Boundaries and Controls**
- _observed_ — Kubernetes CRD validation remains the input and status-write boundary. The existing PreemptionConfig editor role permits mutation, while the controller role reads the resource; configurable preemption also checks its feature gate before loading a referenced object. Role bindings were not inspected.

**Resilience and Maintainability Implications**
- _inferred_ — The new nested status constraint can turn an empty-capacity transition into a rejected write rather than a persisted condition. That matters to quota-state failure containment, although no privilege gain or attacker-triggered exploit was established.

**Hardening Proposals**
- _proposed_ — Define a compatible empty-capacity transition for both status writers and CRD schemas, and verify status publication, retry, and CRD-upgrade behavior against both packaged schema copies.
