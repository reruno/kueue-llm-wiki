#### What this PR does / why we need it?

Removes the two `filterOutBannedDomains` calls in the topology descent loops of `findTopologyAssignment`, keeping the single filter in `findLevelWithFitDomains`, and documents there why it is the only place spreading bans apply.

Both calls always returned their input:

- Spreading rules are only set in Required topology mode, where `findLevelWithFitDomains` never climbs above the requested level, so the fit level is `requestedLevelIdx`. Balanced placement (which also uses the second loop) requires `!state.required`, so it never carries rules.
- `validateSpreadingLevels` rejects rules below `requestedLevelIdx`, so the domains visited during descent have no rule at their own level.
- Their ancestors were already checked by `findLevelWithFitDomains` (`bannedBySpreading` walks up the tree), and the spread counts are populated once in `fillInCounts` and not mutated afterwards.

Fixes #16305

#### Useful notes for your reviewer

Placement behavior is unchanged. Verification:

- Unit tests for `pkg/cache/scheduler/...`, `pkg/scheduler/...` and `pkg/util/tas/...` pass. With a temporary probe that panicked if the first filter ever dropped a domain, the existing `pkg/cache/scheduler` tests went through the descent loop with active spreading rules 50 times and the filter never removed anything.
- The TAS integration suite (`test/integration/singlecluster/tas/`, including `tas_topology_spreading_test.go`) passes: 156/156.
- On a kind cluster I compared an image built from `main` against this branch on zone → rack → hostname topologies: zone-level and rack-level requests with Required rules that descend below the rule levels, and saturated child racks. Placements and rule outcomes were the same, and a rule below the requested level is still rejected with `topology spreading level ... is below the podset topology ...`.
