```diff
+## Topology-Aware Scheduling with DRA
+
+{{< feature-state state="alpha" for_version="v0.20" >}}
+{{% alert title="Note" color="info" %}}
+`KueueDRADeviceFeasibility` is currently an alpha feature and is disabled by default.
+
+You can enable it by editing the `KueueDRADeviceFeasibility` feature gate. Refer to the
+[Installation guide](/docs/installation/#change-the-feature-gates-configuration)
+for instructions on configuring feature gates. It requires `KueueDRAIntegration`,
+`TopologyAwareScheduling` and `TASNodeFeasibilityForAllLevels` to be enabled as well.
+{{% /alert %}}
+
+When you use DRA with [Topology-Aware Scheduling](/docs/concepts/topology_aware_scheduling/)
+(TAS), quota limits how many devices a `ClusterQueue` admits, not where they are. TAS
+counts CPU, memory and other node resources, but DRA devices are not part of a node's
+allocatable, so TAS does not count them. For example, a `ClusterQueue` with a quota
+of 8 GPUs on two nodes with 4 GPUs each admits a Pod whose `ResourceClaimTemplate`
+requests 6 GPUs: the quota allows it, but no node has 6. The Pod stays `Pending` while
+the workload holds the quota. The device check prevents this: before admission, Kueue
+checks that a node has the devices each Pod requests.
+
+### How the device check works
+
+1. A workload is assigned a flavor with a `topologyName` (a TAS flavor).
+2. For each node that the flavor and the Pod's other scheduling constraints allow,
+   Kueue tries to allocate the PodSet's claims, including the one the kube-scheduler
+   creates for an extended resource, using the same allocator as the kube-scheduler.
```

  At admission there is no kube-scheduler-created claim for an extended-resource request yet; Kueue synthesizes a claim from the `DeviceClass` to run this check. As written, this suggests the check allocates an object that does not exist until after admission. Describe it as a synthetic claim so the admission-time behavior is accurate.
