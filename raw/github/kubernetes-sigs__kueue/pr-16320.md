#### What this PR does / why we need it?


An administrator creates a StatefulSet with `replicas: 2` and `kueue.x-k8s.io/queue-name: lq-a`. Its Workload reserves quota, but the Pods are still pulling images, so `readyReplicas` is `0`.

The existing StatefulSet webhook rejects queue changes when `readyReplicas > 0`. The gap is the `readyReplicas == 0` branch: it allows a change to another non-empty LocalQueue even when the Workload already holds quota. 

If a user changes the label to `lq-b`, the controller then tries to update the Workload’s `spec.queueName`, but the Workload CRD rejects it with `queueName` is immutable while workload quota reserved. Reconciliation repeatedly fails and retries with backoff.

The fix preserves queue changes before quota is reserved, but rejects them when the Workload holds quota, even if no Pod is Ready yet.

  > I'm wondering if this is consistent with the way we handle regular batch/Jobs, can you double check that, I cannot remember now
  
  Thanks for flagging this. For the window covered by this PR—fully admitted, but Pods not yet Ready, yes. Kueue has unsuspended a regular Job, so its webhook rejects queue changes regardless of Pod readiness. This fix makes StatefulSet behave the same way in that window.
