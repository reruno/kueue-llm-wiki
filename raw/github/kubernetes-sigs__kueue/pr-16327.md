#### What this PR does / why we need it?

A user creates a  LeaderWorkerSet  with  `replicas: 2`  and  `kueue.x-k8s.io/queue-name: lq-a`. Kueue creates a Workload for each replica group. A Workload may reserve quota before any replica becomes Ready. For example, while its Pods are still pulling images, so  readyReplicas  can remain  0 .

The existing  LeaderWorkerSet  webhook rejects queue changes when  `readyReplicas > 0` . When it is  0 , however, the webhook allows a change to another non-empty LocalQueue even if an existing Workload still holds quota.
If the queue changes to  lq-b , the reconciler attempts to update the existing Workloads’  `spec.queueName` . The Workload CRD rejects updates to Workloads that still reserve quota because  queueName  is immutable while quota is reserved. Reconciliation then fails and retries with backoff.

The fix rejects the  LeaderWorkerSet  queue change whenever one of its existing Workloads holds a quota reservation, including when  readyReplicas  is  0 .

### Security Architecture Review

**Security architecture risk:** _🟡 Moderate_ · up to `b2792`

The new validation blocks queue changes for workloads that are already quota-reserved, but validation and the later workload update are separate operations. A reservation that appears between them can still leave the LeaderWorkerSet configured for a new queue while its workload remains on the old queue until quota is released.

**Retained concerns**
- **Medium · reliability · inferred:** The quota-reservation gate is not atomic with persistence and later reconciliation. A reservation can be established after validation observes no reservation, allowing the LeaderWorkerSet queue change to persist while the subsequent owned Workload queue update is rejected until the reservation is removed.

<details>
<summary>Security review details</summary>

**Security Blast Radius**
- _observed_ — The gate affects queue transitions only for Workloads owned by the updating LeaderWorkerSet in its namespace, containing its direct scope to that owner-dependent set.

**Security Findings and Attack Paths**
- _inferred_ — An actor already authorized to update a LeaderWorkerSet can encounter the remaining timing window if quota is reserved after admission validation; this can defer enforcement of the intended queue and quota association until reservation release, rather than crossing tenant or owner boundaries.

**Trust Boundaries and Controls**
- _observed_ — The owner UID index is derived from Kubernetes owner references, and the controller establishes that owner reference when creating LeaderWorkerSet Workloads, preserving a stable identity boundary for the validation query.

**Resilience and Maintainability Implications**
- _observed_ — Reservation state is represented by the quota-reserved condition and admission state together: setting a reservation sets admission and the condition, while unsetting it clears admission and sets the condition false.

**Hardening Proposals**
- _proposed_ — Use a coordination mechanism that closes the interval between queue-change authorization and Workload propagation, or explicitly revalidates reservation state at the persistence boundary, so a newly reserved Workload cannot strand the parent and dependent on different queues.

</details>
