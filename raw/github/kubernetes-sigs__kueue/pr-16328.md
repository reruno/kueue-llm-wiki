#### What this PR does / why we need it?

A RayCluster uses the ray-queue LocalQueue, which points to a ClusterQueue with normal quotas. The ClusterQueue offers two ResourceFlavors, `pool-a` and `pool-b`, for nodes labeled `workload-pool: a` and `workload-pool: b`, respectively.

```
apiVersion: ray.io/v1
kind: RayCluster
metadata:
  name: example
  namespace: team-a
  labels:
    kueue.x-k8s.io/queue-name: ray-queue
spec:
  # headGroupSpec and unchanged fields omitted
  workerGroupSpecs:
  - groupName: analytics
    replicas: 2
    template:
      spec:
        nodeSelector: {workload-pool: a}
        # Same containers and resource requests as serving
  - groupName: serving
    replicas: 2
    template:
      spec:
        nodeSelector: {workload-pool: b}
        # Same containers and resource requests as analytics
```

While the RayCluster is waiting for quota, the user updates it by only swapping the positions of the two complete worker groups. Neither group’s configuration changes:

```
spec:
  workerGroupSpecs:
  - groupName: serving
    replicas: 2
    template:
      spec:
        nodeSelector: {workload-pool: b}
  - groupName: analytics
    replicas: 2
    template:
      spec:
        nodeSelector: {workload-pool: a}
```

Kueue retains the existing Workload, whose worker groups are still ordered [analytics, serving]. Later, other workloads finish and release quota. Kueue admits the waiting Workload, assigning pool-a to analytics and pool-b to serving.

Before the fix, Kueue applied those admission results to the RayCluster’s worker groups by position rather than by name. 

It therefore tried to apply analytics’s result—including `workload-pool: a` to `serving`, which already requires `workload-pool: b`. The conflicting node selectors caused RayCluster startup to fail. 

The correct behavior is to match each admission result to its worker group by name, regardless of list order.
