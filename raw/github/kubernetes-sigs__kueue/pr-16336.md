#### What this PR does / why we need it?

It bumps the [`maxParallelism`](https://github.com/kubernetes-sigs/kueue/blob/992a68d1c89f9dc7eaa5d0a8c3686b14cf02a7ea/pkg/util/parallelize/parallelize.go#L25) setting (controlling how many concurrent API updates at most can be simultaneously issued by a single reconciler thread) from 8 to 32.

The current limit of 8 has been conservatively set back in [#1632](https://github.com/kubernetes-sigs/kueue/pull/1632), and even that PR already mentioned a possible outlook of increasing it, or making it configurable.
Currently, this became a bottleneck for some users (e.g. in a Workload with several thousands of Pods, where ungating a single Pod takes ~100 ms, ungating the whole Workload can exceed 1 minute).

The main risk about having this too high seems to be potentially hitting the QPS / burst limits of API updates across the whole Kueue binary. However, those limits - at least their default values - have been significantly raised in the meantime (from [20 / 30 one year ago](https://github.com/kubernetes-sigs/kueue/blob/3674c93deb9e6a8224ea7cb1dc60bb80d4052ef1/apis/config/v1beta2/defaults.go#L44-L45) to [1000 / 1000 now](https://github.com/kubernetes-sigs/kueue/blob/1c8d827c2f790a78d84e40d7aea232468cb0e889/apis/config/v1beta2/defaults.go#L44-L45)).
Therefore, a 4x bump here feels well affordable.

A feature gate is introduced for safety; yet, the above reasoning justifies starting with Beta.

#### Useful notes for your reviewer

This is not necessarily the end of the story.
We're considering making `maxParallelism` configurable.
However, this simple fix should improve things already for 0.20.

### Security Architecture Review

**Security architecture risk:** _🟡 Moderate_ · up to `2d4b9`

The change can quadruple concurrent work within each affected batch. Existing API throttling and a gate that restores the old limit reduce the risk, but large workloads could increase contention with other reconciliation work. No new privilege or access path was identified.

**Retained concerns**
- **Medium · reliability · inferred:** The default fourfold increase in workers per batch can multiply across concurrent reconciles. Under large workloads, contention for the shared API client limiter could delay unrelated reconciliation and cleanup; actual saturation has not been established.
