#### What this PR does / why we need it?

Fix `kueue_cohort_subtree_admitted_active_workloads` drifting after Cohort hierarchy changes.

A Cohort's `admittedWorkloadsCount` was maintained incrementally on Workload events but not rebuilt when the Cohort tree changed, so the gauge could become stale, zero or negative. The flake in #16205 is one case: reconciling `ch1` with an unchanged parent recreates its implicit root with a zero count. Reparenting or deleting a Cohort that still has children can cause the same drift.

This PR:
- rebuilds `admittedWorkloadsCount` from the children together with the rest of the Cohort tree
- re-reports the gauge for the affected trees after a hierarchy change, dropping series left by ClusterQueues that moved away
- leaves `kueue_cohort_subtree_admitted_workloads_total` unchanged, as it counts admissions

#### Useful notes for your reviewer

- As in https://github.com/kubernetes-sigs/kueue/issues/16205#issuecomment-5907469484, the gauge follows the current subtree: moving `ch1` with 3 admitted Workloads under `root2` with 2 makes `root2`'s gauge 5, while its total counter stays 2.
- Deleting an explicit Cohort that still has children leaves it as an implicit Cohort, so its gauge is kept: in the existing integration test `ch1` now stays at 5 instead of 0, and its counter is still cleared. The old 0 was the zeroed count, which went negative as the Workloads finished.
- The gauge is re-reported together with the cache's tree rebuild rather than on the next reconcile, since the old tree and implicit Cohorts may not be reconciled again.
