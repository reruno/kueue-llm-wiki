## Description

What type of PR is this?
/kind feature
/area dra

What this PR does / why we need it?
Documents the ClusterQueue accounting policy for DRA devices that supply node-allocatable resources through Kubernetes KEP-5517.

Kueue continues charging the existing DRA logical resource through device count, counter value, consumable capacity, or the extended-resource mapping. It does not add the translated CPU, memory, or other native resource to ClusterQueue usage. Native resources requested directly in the Pod template remain charged normally.

The concept and administrator guides also explain that Kubernetes namespace ResourceQuota handling for the translated resource is separate and depends on Kubernetes support for quota evaluation during the scheduler's Pod status update.

Part of #16536
Related: #14401

Useful notes for your reviewer
The KEP update and any required API or implementation changes are tracked separately in #16536. This PR is intentionally limited to user documentation.

```release-note
DRA: Clarified that Kueue charges DRA devices through their configured logical resources, not the native node resources they supply.
```

### Security Architecture Review

**Security architecture risk:** _🔵 Low_ · up to `69988`

The logical-resource accounting policy preserves existing admission charges. The main risk is that the new guidance promises namespace quota protection without qualifying which Kubernetes versions implement it. Existing logical quotas limit exposure, and no new runtime bypass was demonstrated.

**Retained concerns**
- **Medium · security · inferred:** The new guidance treats namespace native-resource quota enforcement during PreBind as generally available, including when enabling the feature on earlier Kubernetes versions. The inspected prerelease implementation does not apply the core Pod quota evaluator to the scheduler's status update, while the upstream design explicitly requires a Beta enforcement change. Administrators relying on the unconditional guarantee could mistake logical DRA admission limits for complete namespace native-resource isolation. This is an introduced guidance and control-assurance risk, not a demonstrated new runtime vulnerability; final-release behavior remains unverified.

**Security Blast Radius**
- _inferred_ — The relevant exposure is native-resource consumption by permitted DRA workloads in namespaces and ClusterQueues using these DeviceClasses. Deployment-specific permissions, tenant reach, and shared capacity are not established by the available evidence.

**Security Findings and Attack Paths**

This is a conditional control gap, not a verified deployed exploit. The inspected runtime behavior predates this PR; the new risk is presenting that protection as unconditional.

**Trust Boundaries and Controls**
- _observed_ — Kueue logical quota admission and Kubernetes namespace native-resource quota are separate control owners. The documentation acknowledges that ClusterQueue native-resource usage is not the complete post-allocation footprint and directs administrators to size distinct logical resource quotas to represented capacity.

**Hardening Proposals**
- _proposed_ — Qualify the namespace quota guarantee by verified Kubernetes release, component compatibility, and feature-gate configuration. Before relying on it for isolation, validate over-quota rejection and quota release after failed binding or retry; distinguish intended Beta behavior from earlier implementations.

+### Node-allocatable resources
+
+Kubernetes KEP-5517 allows a DRA device to supply native node resources such as CPU,
+memory, ephemeral storage, or hugepages. The scheduler derives the exact resource amount
+from the selected device and persists it to Pod status during PreBind. The feature is beta
+and enabled by default in Kubernetes 1.38.
+
+#### ClusterQueue accounting
+
+Kueue does not merge the translated native-resource amount into a Workload's CPU, memory,
+or other native-resource `ClusterQueue` charge. Kueue reserves quota before kube-scheduler
+selects a concrete device, so the exact translated amount is not available at admission
+time and can vary between candidate devices.
+
+Instead, the existing DRA path remains the quota source. ResourceClaimTemplates use the
+logical resource and accounting source configured by `deviceClassMappings`: device count,
+counter value, or consumable capacity. The extended-resource path uses the DeviceClass
+extended resource name or its configured logical mapping. Native resources requested
+directly in the Pod template remain part of the normal `ClusterQueue` charge.
+No Kueue API change is required because `deviceClassMappings` already defines the
+logical resource and accounting source.
+
+This produces a deterministic charge and avoids charging both the device abstraction and
+the native resources that the same allocation supplies. Administrators should give
+device-count mappings a distinct logical resource name rather than naming a count-based
+unit `cpu` or `memory`.
