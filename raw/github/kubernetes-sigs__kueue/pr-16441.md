What this PR does / why we need it?
Documents the ClusterQueue accounting policy for DRA devices that supply node-allocatable resources through Kubernetes KEP-5517.

Kueue continues charging the existing DRA logical resource through device count, counter value, consumable capacity, or the extended-resource mapping. It does not add the translated CPU, memory, or other native resource to ClusterQueue usage. Native resources requested directly in the Pod template remain charged normally.

The concept and administrator guides also explain that Kubernetes namespace ResourceQuota handling for the translated resource is separate and depends on Kubernetes support for quota evaluation during the scheduler's Pod status update.

Part of #16536
Related: #14401

Useful notes for your reviewer
The KEP update and any required API or implementation changes are tracked separately in #16536. This PR is intentionally limited to user documentation.

```release-note
DRA: Clarified that Kueue charges DRA devices through their configured logical resources, not the native node resources they supply.
```

The logical-resource accounting policy preserves existing admission charges. The main risk is that the new guidance promises namespace quota protection without qualifying which Kubernetes versions implement it. Existing logical quotas limit exposure, and no new runtime bypass was demonstrated.

**Retained concerns**
- **Medium · security · inferred:** The new guidance treats namespace native-resource quota enforcement during PreBind as generally available, including when enabling the feature on earlier Kubernetes versions. The inspected prerelease implementation does not apply the core Pod quota evaluator to the scheduler's status update, while the upstream design explicitly requires a Beta enforcement change. Administrators relying on the unconditional guarantee could mistake logical DRA admission limits for complete namespace native-resource isolation. This is an introduced guidance and control-assurance risk, not a demonstrated new runtime vulnerability; final-release behavior remains unverified.

**Security Blast Radius**
- _inferred_ — The relevant exposure is native-resource consumption by permitted DRA workloads in namespaces and ClusterQueues using these DeviceClasses. Existing logical DRA quotas and direct Pod resource charges remain limiting controls. Deployment-specific permissions, tenant reach, and shared capacity are not established by the available evidence.

**Security Findings and Attack Paths**
- _inferred_ — On a gate-enabled implementation lacking the described status-update quota check, a workload author already permitted to request DRA devices could consume translated native resources without the promised namespace quota rejection. This is a conditional control gap, not a verified deployed exploit. The inspected runtime behavior predates this PR; the new risk is presenting that protection as unconditional.

**Trust Boundaries and Controls**
- _observed_ — Kueue logical quota admission and Kubernetes namespace native-resource quota are separate control owners. The documentation acknowledges that ClusterQueue native-resource usage is not the complete post-allocation footprint and directs administrators to size distinct logical resource quotas to represented capacity.

**Hardening Proposals**
- _proposed_ — Qualify the namespace quota guarantee by verified Kubernetes release, component compatibility, and feature-gate configuration. Before relying on it for isolation, validate over-quota rejection and quota release after failed binding or retry; distinguish intended Beta behavior from earlier implementations.

+#### ClusterQueue accounting

+or other native-resource `ClusterQueue` charge. Kueue reserves quota before kube-scheduler

+## Node-allocatable resources supplied by DRA
+
+Kubernetes KEP-5517 targets the `DRANodeAllocatableResources` feature for beta
+in Kubernetes 1.38. With the v1.38 default `MinCompatibilityVersion` of 1.37,
+the gate remains disabled by default. Operators can enable it on all
+participating components or set `MinCompatibilityVersion` to 1.38. The KEP
+targets default enablement for Kubernetes 1.39. The feature lets DRA devices
+supply node resources such as CPU, memory, ephemeral storage, or hugepages. The
+scheduler resolves the exact amount for the selected device and records it
+in the Pod status field defined by Kubernetes KEP-5517 during PreBind.
+
+Kueue does not add that translated amount to the Workload's CPU, memory, or
+other native-resource `ClusterQueue` quota. For ResourceClaimTemplates, it
+charges the claim through the `deviceClassMappings` entry and its selected
+accounting source: device count, counter value, or consumable capacity. The
+extended-resource path continues to charge the extended resource name or its
+configured logical mapping. Ordinary resource requests in the Pod template are
+charged normally.
+
+This policy keeps quota admission deterministic because Kueue admits the
+Workload before the scheduler selects and allocates a specific device. It also
+avoids charging both the device and the node-allocatable resource supplied by
+the same allocation. Consequently, native-resource quota does not represent
+the complete post-allocation footprint of Pods that use this Kubernetes
+feature.
+
+KEP-5517's beta design calls for Kubernetes namespace `ResourceQuota` to account
+for the translated native resource during PreBind when the Kubernetes version
+supports quota evaluation for the scheduler's Pod status update. Where
+supported, Kueue can admit a Workload whose Pod later remains Pending or enters
+scheduler backoff because its namespace lacks native-resource quota for the
+selected device. Where it is not supported, namespace `ResourceQuota` does not
+cover the translated amount; administrators must rely on the DRA logical quota
+or other controls.
+
+Administrators should use a distinct logical quota resource, such as
+`example.com/cpu-device`, for these DeviceClasses and size that quota to reflect
+the capacity represented by each unit. Naming the logical resource `cpu` or
