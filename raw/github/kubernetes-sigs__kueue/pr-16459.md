#### What this PR does / why we need it?

`WorkloadPriorityClassReconciler` lists the Workloads on a class from the cache and skips the ones whose `spec.priority` already equals the class value:

```go
if wl.Spec.Priority != nil && *wl.Spec.Priority == wpc.Value {
	wlLog.V(3).Info("Workload priority already up to date")
	return nil
}
```

Right after the sweep itself wrote them, the cache can still show the values from before those writes. A class `high` at 100 with a Workload at 100: `high` is edited to 200 and the sweep writes 200. `high` is edited back to 100 before the Workload informer has seen that write. The sweep runs again, lists the Workload at 100 from the cache, and skips it. The API server holds 200, and nothing brings it back: the class predicate fires only on a value change, and the class controller doesn't watch Workloads.

The reconciler now remembers, per class name, the object and generation of the class, recorded when it first sees the class and after each run that ends without error. When the class has changed since, a Workload the cache shows as current is written anyway instead of skipped. If the cache is behind, the update fails on the old resourceVersion and the reconcile retries, and by then the cache has the earlier write, so the Workload goes back to the class value. If the cache is current, the update doesn't change anything. The first run over a class, and a class that didn't change, still skip as today, so startup and failover write nothing extra.

Fixes #14006

#### Useful notes for your reviewer

The first version read the Workload from the API server through `mgr.GetAPIReader()` before skipping it. After the review it stays on the cache and relies on the resourceVersion check instead. That check also covers a Workload that was replaced, for example by a MultiKueue remote one, or moved to another class while the cache lagged: the write conflicts and nothing is overwritten.

The object identity is remembered next to the generation because a class deleted and re-created under the same name starts again at generation one.

The integration test changes the class value and then changes it back. envtest gives no way to hold the Workload informer back, so it passes with or without this change, but it covers the flow. The unit table sets up the lag directly, with a cache and an API server that disagree.
