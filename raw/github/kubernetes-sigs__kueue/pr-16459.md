#### What this PR does / why we need it?

When a WorkloadPriorityClass changes, `WorkloadPriorityClassReconciler` writes the class value into the Workloads that reference it, and skips those whose cached `spec.priority` already matches. If the value is changed and changed back before the Workload informer has seen the first write, the second reconcile finds the old value in the cache and skips those Workloads, which keep the intermediate priority. Nothing requeues the class after that, because the controller does not watch Workloads.

The controller now also watches Workloads and requeues the class of a Workload whose priority differs from the class value. A Workload whose `spec.priority` is edited by hand gets the class value back, and so does a Workload that starts to reference the class with an earlier value, the case of #13866.

Fixes #14006
Fixes #13866

The webhook spec "workload's priority should be mutable when referencing WorkloadPriorityClass" no longer waits for the edited value to stay, since the controller now sets the class value back. It still checks that the webhook accepts the update.

#17100 fixes #13866 with a separate Workload-keyed controller and keeps a priority edited by hand. Its spec for that fails with this change, so only one of the two can merge.

A webhook or controller that keeps writing another priority to such a Workload now writes back and forth with Kueue about once a second; Kueue's own webhooks don't set it.

**Resilience and Maintainability Implications**

**Hardening Proposals**

### Comment by [@thc1006](https://github.com/thc1006) — 2026-10-03T01:56:13Z

Thanks @mimowo, that's a fair concern. The observable consequence is narrow: if a WorkloadPriorityClass value is changed and then changed back before the Workload informer has seen the first sweep's writes, the second sweep finds the Workloads at the class value in the cache and skips them, so they keep the intermediate priority until the class changes again or Kueue restarts. No write is attempted, so there is no conflict to retry on, and nothing requeues the class.

I think this can stay on the cache: after a class change, write the Workloads the cache shows as current instead of skipping them. If the cache is behind, the update fails on the old resourceVersion and the reconcile retries; if not, the update doesn't change anything. That drops the API reader and the extra ownership and reference checks. wdyt?

For the integration test, I couldn't make the informer lag deterministically in envtest, so a spec that changes the class and back passes with or without the fix. I can still add it as a regression test for that flow.
