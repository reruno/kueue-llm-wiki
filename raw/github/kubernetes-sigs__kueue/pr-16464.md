### Comment by [@mimowo](https://github.com/mimowo) — 2026-10-01T20:40:28Z

/hold
I have analyzed the issue, and I think this is rather test issue actually 

The test is racy because occasionally the Pod remains gated, and so it is not deleted on eviction - if that happens the Pod will also not receive TerminationTarget, nor deletionTimestamp, and so the proposed changes will not help.

The intention of the test is to verify `WaitingForReplacementPods=True`, not the racy behavior of handling very short PodsReady timeouts.

So, I propose to fix the test should wait for the Pod to be ungated, and only then trigger eviction, to achieve that I can see two easy ways:
1. increase the WaitForPodsReady timeout to make ungating more likely
2. use CQ HoldAndDrain to force eviction instead of 1s PodsReady timeout

My preference is to re-work the  `WaitingForReplacementPods=True` tests using controlled eviction by CQ HoldAndDrain. This will (a) prevent flakes by better control, (b) shorten the test avoiding waiting 1s (or more) for the timeout.

cc @mbobrovskyi
