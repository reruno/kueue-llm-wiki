## Description

#### What type of PR is this?

/kind bug

#### What this PR does / why we need it?

A zero-count PodSet can find a suitable flavor, but another PodSet prevents the Workload from being admitted. On retry, the existing flavor search skips that earlier choice and can assign a flavor with no capacity. This can block later elastic scale-up even when the suitable flavor has free quota.

Start zero-count capacity probes from the first configured flavor on every attempt. Also clear their retry progress so the probe does not keep triggering immediate retries while another PodSet is blocked. The probe still runs again whenever the Workload is retried.

Fixes #16443

#### Useful notes for your reviewer

- Groups containing a non-zero PodSet keep their existing flavor-search behavior. Zero-count PodSets still consume no quota.
- Unit tests cover flavor preference, fallback, affinity, and avoiding unnecessary retries. A generic Workload integration test covers admission retry followed by zero-to-one scale-up through a replacement slice.
- Validation passed: scheduler, flavor-assigner and workload unit suites; the generic retry regression and two existing Workload-slicing integration tests with race detection; `ci-lint`.

AI disclosure: Codex helped implement, test, and draft this PR.
