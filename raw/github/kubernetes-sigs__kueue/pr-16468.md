#### What this PR does / why we need it?

`queueSecondPass` re-reads the Workload before deciding whether to queue it. A new second-pass request arriving between that read and the decision can see the old pass as pending, while the old pass can then drop the Workload based on its earlier read. The new request is lost until another Workload update.

Hold the `secondPassQueue` lock across the re-read and queue decision. Since informer updates are stored before handlers run, a concurrent request is now either seen by the re-read or arrives afterward and arms a new pass.

This is step 2 of the split agreed in https://github.com/kubernetes-sigs/kueue/pull/14078#issuecomment-5905201360; the scenario was described in https://github.com/kubernetes-sigs/kueue/pull/14078#discussion_r3991209914.

**Security Blast Radius**
- _inferred_ — The relevant exposure is shared scheduling-state availability within one queue manager: requests for different workload keys use the same second-pass queue lock. A slow read can therefore delay other second-pass requests and cleanup, rather than affecting only the workload being re-read.

**Trust Boundaries and Controls**
- _inferred_ — The inspected path preserves the existing workload-controller-to-queue-manager relationship and uses the existing manager client. The change serializes decisions behind that interface; it does not introduce a new caller, credential source or authority transition in the reviewed production ranges.

**Resilience and Maintainability Implications**
- _inferred_ — The wider queue lock adds waiting for queue-only operations, but scheduler head selection already required the manager lock held during these reads. This limits the demonstrated incremental failure-containment impact.
