## Description

#### What type of PR is this?

#### What this PR does / why we need it?
`resources.Requests` stored each resource as an `int64` and clamped addition, subtraction, and multiplication at `math.MaxInt64`. ClusterQueue, LocalQueue, and Cohort usage is already an exact `resources.Amount`, so a workload whose total request overflowed `int64` was recorded as `math.MaxInt64` and that clamped value was what quota accounting saw.
Both `MapRequests` and `SliceRequests` now store `Amount`. Add, subtract, multiply, and divide stay exact, including past `int64`. Values that still fit `int64` marshal as JSON numbers, so scheduling hashes for in-range requests stay the same. API-facing `Quantity` output still stops at what a `Quantity` can hold.

Fixes #16405 

#### Useful notes for your reviewer
- This change was prepared with AI assistance.
- `SaturatingAdd`, `SaturatingSub`, and `SaturatingMul` remain. DRA capacity and counter code still uses them.
- A single non-CPU `Quantity` is still capped at the `Quantity` magnitude. The overflow this fixes is a sum or product of in-range requests, such as pod count times per-pod CPU.
- The scheduler benchmarks mentioned in the issue were not compared against `main`.

```go
func AmountFromQuantity(name corev1.ResourceName, q resource.Quantity) Amount {
	limit := int64(math.MaxInt64)
	if name == corev1.ResourceCPU {
		limit = math.MaxInt64 / 1000
	}
	// Up to the limit, Value and MilliValue cannot overflow, and for a
	// non-negative quantity they round up as scaledBig does.
	if q.Sign() >= 0 && q.CmpInt64(limit) <= 0 {
		if name == corev1.ResourceCPU {
			return NewAmount(q.MilliValue())
		}
		return NewAmount(q.Value())
	}
	return fromBig(scaledBig(name, q))
}
```
