#### What this PR does / why we need it?

`ZeroWeightBorrows` inferred borrowing from a non-zero ratio, but `dominantResourceShare` only takes the ratio on resources the Cohort can lend, and already records whether the node borrows at all in `borrowing`. A ClusterQueue or Cohort with weight 0 that borrows only resources with nothing lendable, which a running workload can reach when the quota it was admitted under is withdrawn, therefore had a share of 0 instead of `+Inf`: its status reported 0 and `CompareDRS` ranked it as if it were within its quota.

`ZeroWeightBorrows` now reads `IsBorrowing`, and `PreciseWeightedShare` checks it before returning 0 for a zero ratio. A positive weight is unchanged: such a node still has a share of 0, which `TestDominantResourceShare` keeps as a control case. This is the change from #14412. That PR was closed when the change moved into #15026, and #16477 asks for it as a separate PR.

Part of #16477.

#### Useful notes for your reviewer

`fsStrategyUnsatisfiable` assumes that removing a workload cannot turn its target into a zero-weight borrower. Removing usage can only clear `borrowing`, never set it, so that still holds.

For a zero-weight ClusterQueue that borrows only resources with nothing lendable, `kueue_cluster_queue_weighted_share` now reports NaN instead of 0, which its help text already describes for a zero-weight ClusterQueue that borrows. A Cohort in the same state now reports +Inf in `kueue_cohort_weighted_share`, which is what it already reported for a zero-weight Cohort that borrows lendable resources, although its help text says NaN.

The integration test admits a workload within the nominal quota of a weight-0 ClusterQueue, withdraws that quota while the workload stays admitted, and reads the status: `0` on main, `9223372036854775807` with this change. `TestDominantResourceShare` covers the ClusterQueue and Cohort cases, and `TestCompareDRS` the ordering against a finite share, an idle node and other zero-weight borrowers, in both argument orders.

### Comment by [@thc1006](https://github.com/thc1006) — 2026-10-01T22:55:29Z

> What happens when there are multiple 0-weight CQs? How they are handled?

Zero-weight ClusterQueues that borrow all get the maximum share, which the status reports as MaxInt64. `CompareDRS` orders them among themselves by their unweighted ratio, the same as on main. When those ratios are equal, the same tie-breakers as for any other equal shares decide, both in the admission order and in the choice of a preemption target. The existing integration test "should not cause an infinite preemption cycle" covers two zero-weight ClusterQueues. The one borrowing more loses one Workload to the other, and then both keep running with no further preemption. This PR only adds zero-weight nodes whose ratio is 0 to that group, where `CompareDRS` gives them a lower share than zero-weight nodes with a positive ratio. `TestCompareDRS` covers that ordering, and the existing integration test still passes.
