## Description

#### What type of PR is this?

/kind bug

#### What this PR does / why we need it?

`AmountFromQuantity` built a `big.Int` for every quantity, including values that already fit in an int64. Those conversions allocate on the quota path today, and workload requests will use the same function once resource requests stay exact past int64.

A non-negative quantity inside the int64 range now uses `Quantity.Value` or `MilliValue`, which round a positive remainder away from zero the same way as the decimal path. Anything past that range, and every negative quantity, still uses the decimal path, so an exact amount past int64 and the Quantity cap are unchanged.

On this machine, `BenchmarkAmountFromQuantity` for `100m`, `1`, `1Gi`, and one device dropped from about 140–190 ns/op and 8–10 allocs/op to about 9–12 ns/op and 0 allocs/op.

Related: #16405
Related: #16479

#### Useful notes for your reviewer

This pull request was prepared with AI assistance.

Negative quantities stay on the decimal path. `Quantity.Value` and `MilliValue` round a negative remainder toward +inf on that path, and `MilliValue` overflows to zero at the most negative int64 milli. The decimal path already rounds away from zero and keeps that milli exact.

This is meant to land before #16479. That pull request starts calling `AmountFromQuantity` for every workload request, which is where `BenchmarkSchedulerTAS` picked up the extra allocations.
