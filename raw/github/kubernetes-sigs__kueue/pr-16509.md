#### What type of PR is this?

#### What this PR does / why we need it?

When a worker cluster is removed from a MultiKueueConfig, the workload reconciler only reads the clusters left in the config. It no longer sees the remote Workload on the admitting cluster, so it retries the admission check right away and dispatches the job to another cluster, while the original remote Workload and Job keep running on the removed cluster.

This PR keeps reading the admitting cluster while its MultiKueueCluster exists, so the Workload keeps running there until it finishes and its remote objects are then cleaned up. Removing a cluster from the config now only stops new dispatches to it. A disconnected admitting cluster gets the usual `workerLostTimeout` grace, and a Workload whose admitting cluster has no MultiKueueCluster is still retried right away.

None

```release-note
MultiKueue: Fixed a bug where removing a worker cluster from a MultiKueueConfig re-dispatched the Workloads admitted on that cluster to another cluster without deleting their remote objects, so the same job could run twice. Workloads already admitted on the removed cluster now keep running there until they finish.
```

**Security Blast Radius**
- _observed_ — For each reconciliation, the added remote target is the workload's recorded admitting cluster, not an arbitrary supplied endpoint. Remote Workload reads use the local workload's namespace and name, and associated job cleanup uses the owning controller's name in that namespace. Effective credential privileges were not established by this inspection.

**Trust Boundaries and Controls**
- _observed_ — Admission synchronization refuses to change an already-recorded ClusterName to a different admitting worker. The lookup also requires a registered cluster controller and separates connected clients from unavailable workers.
- _observed_ — The existing remote-job deletion helper rejects an empty origin, invokes remote-object ownership validation, and skips objects reported as belonging to another origin. Retained-worker cleanup continues to use this helper rather than an unconditional job deletion.

**Resilience and Maintainability Implications**
- _observed_ — Ordinary workloads skip nomination unless their admission check is Pending and ClusterName is unset. Eviction clears both ClusterName and nominated workers before resetting checks to Pending within the admission-status update. This counters the concern that ordinary retry recovery would intentionally nominate the removed worker using stale admission identity.
- _observed_ — Deletion cleanup defers unavailable workers to per-cluster garbage collection after reconnect. That collector skips disconnected clients and selects remote Workloads by manager-origin label before checking whether the corresponding local Workload is missing or being deleted. This recovery mechanism predates the new client-selection behavior.
