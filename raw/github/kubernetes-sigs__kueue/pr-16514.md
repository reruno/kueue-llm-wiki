#### What this PR does / why we need it?

For elastic Jobs with ProvisioningRequest admission checks (`ElasticJobsViaWorkloadSlicesForProvisioningRequests`), the ungater stamps `autoscaling.x-k8s.io/consume-provisioning-request` on each gated Pod before removing the elastic scheduling gate, and relied on `autoscaling.x-k8s.io/provisioning-class-name` reaching the Pod through the job template. That holds for Pods created after the template was stamped, but not for Pods created before it. The first ProvisioningRequest-backed slice in a chain. Those Pods are ungated carrying the consume annotation but no class annotation.

On GKE, the ProvisioningRequest mutator treats a consume annotation without a class as `queued-provisioning.gke.io`and injects the `autoscaling.gke.io/provisioning-request=<id>` node selector and the `cloud.google.com/gke-queued` toleration. For `best-effort-atomic-scale-up.autoscaling.x-k8s.io` requests no node ever carries that label, the node selector is immutable once set, and the Pod stays `Unschedulable` for good while the cluster autoscaler ignores it for regular scale-up (`IgnoredInScaleUp ... consuming ProvisioningRequest ... in Provisioned state`).

Fix: `admissionUpdateForPodSet` now stamps `provisioning-class-name` together with `consume-provisioning-request`, so a Pod never carries one without the other.

#### Which issue(s) this PR fixes

Related: #14316

#### Useful notes for your reviewer

- The only behavioural change is in `admissionUpdateForPodSet()`: the loop over the admission check's `PodSetUpdates` now copies `provisioning-class-name` as well as `consume-provisioning-request`, with the same conflict check between updates. `podAdmissionCompatible()` is unchanged, so only the consume annotation is treated as immutable request identity; a stale class annotation inherited from the template is overwritten with the active slice's value.

#### Release note

```release-note

Kueue now applies both annotations, preventing such Pods from being pinned by the cluster autoscaler to nodes that are never created.

Edit:

I agree that with `best-effort-atomic-scale-up` the annotations should be transparent. In practice on GKE they are not, and I've tried to isolate exactly which layer breaks. Here's what happens, reproduced today:

Kueue stamps autoscaling.x-k8s.io/consume-provisioning-request=prq123 on the admitted pods (podSetUpdates).

GKE's admission layer treats that annotation as "this pod must run on nodes created for that request" and injects a node selector, independent of the provisioning class:

pod.spec.nodeSelector:
  autoscaling.gke.io/provisioning-request: gke-ray-clusters-raycluster-prod-nbre-0c796ba4bd50bc42
For queued-provisioning.gke.io that is correct: nodes are created for the request, labelled with that key, and tainted, so the 1:1 pin is the whole point.

With `best-effort-atomic-scale-up`, when the capacity already exists (free reservation, warm nodes) the request completes with Provisioned=True, reason=CapacityIsFound and the autoscaler creates and labels nothing. No node ever carries that label, so the pinned pods are Unschedulable forever.

It's unrecoverable because the autoscaler also excludes pods with the consume annotation from ordinary scale-up: IgnoredInScaleUp: ... consuming ProvisioningRequest ... that is in Provisioned state (and later BookingExpired). So Kueue thinks the workload is admitted and running, while the pods never schedule.

Even in the scale-up case (CapacityIsProvisioned) the pin hurts: the atomic request's created nodes don't necessarily match the pod's own node selector (e.g. zone), and the pods can't fall back to other capacity.

So I agree it is a layering mismatch: the consume annotation carries two meanings 1) "account these pods against this request" (what CA needs) and 2) "restrict these pods to the request's nodes" (what GKE adds), and the second meaning is wrong for a class whose answer can be "the capacity is already there". Maybe we can raise the node-selector injection with GKE as well. But I think a Kueue side switch is still needed:

1) Kueue is the component that decides to stamp the annotation, and the ProvisioningRequestConfig is the only place that knows which class the request uses; GKE can't infer from the pod whether the user wants the pin.

2) Even if GKE changes behaviour, we'd want to use atomic requests as a pure capacity gate while pods schedule as ordinary pods honouring their own selectors. That's a legitimate mode of using the class!

That's where idea to have opt in per config and off by default: queued-provisioning configs in the same cluster keep the current behaviour. 

If you'd prefer, I'm happy to a) key it off a spec field rather than an annotation, or b) scope it more narrowly, e.g. only skip consume-provisioning-request and keep provisioning-class-name. I didn't want to hard-code provider class names into Kueue, which is why it's not automatic for `best-effort-atomic-scale`

Let me know what you think! Thanks
