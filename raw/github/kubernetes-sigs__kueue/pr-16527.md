## Description

#### What type of PR is this?

#### What this PR does / why we need it?

`AmountFromQuantity` checks whether a quantity fits the int64 range with `Quantity.CmpInt64`, which, for a large exponent n, brings both sides to one scale by building 10^n. A ClusterQueue quota of `1e10000000` passes the webhooks and is stored as `10e9999999` (a server-side dry run on v0.20.0), and converting it on main took about 1.6 s and up to 46 MB, where the decimal path it used before #16492 takes about 3 µs. `10e999999` took about 42 ms. A scale that far below zero, which only a `Quantity` built in code can have, cost as much.

`AsApproximateFloat64` computes its estimate in float64, so for such a scale it is 0 or past the limit, and the quantity now goes to the decimal path, which bounds it by its digit count as before. Zero is returned first, so it still does not allocate.

Related: #16492. It also went to release-0.20 and release-0.19 in #16496 and #16495, and no release contains it yet, so this needs the same cherry-picks.
Related: #16479, which moves workload requests onto this function.

#### Useful notes for your reviewer

I suggested the `CmpInt64` check on #16479, so this is my mistake to fix.

On main the new test fails: each case allocates roughly three to five times as often as the decimal path, for example 42 against 8 for `10e999999` of CPU. It compares with `scaledBig` instead of a fixed count, so it does not depend on how `big.Int` allocates. `TestAmountFromQuantityBelowOneAtALargeScale` says its case is decided "without building the divisor"; on main it builds 10^100000 to compare and again to divide, about 460 KB in all, and still passes, while with this change it allocates 128 B.

The new function matches `scaledBig` on 5.4M generated conversions, including scales of ±2e9 and ±1e6 and the float64 boundaries. `BenchmarkAmountFromQuantity` goes from 12.5 to 24.8 ns per op on main to 14.5 to 28.7 ns with this change (8 alternating runs, Go 1.27, 4 CPUs), still with no allocations.
