#### What this PR does / why we need it?

QA of the alpha `TASTopologySpreading` feature on v0.20.0-rc.2 found that KEP-13746 no longer describes the released behavior in several places. One sentence in the user docs is also wrong. This PR updates the text to match the code; it doesn't change any behavior.

KEP-13746:
- **Spreading group:** Workloads count against each other only when their labels match the selector **and** they share the PodSet group key (`podset-group-name`, otherwise the PodSet name). Story 3 gave each PodGroup its own `podset-group-name`, so its PodGroups were never spread. The story now omits it and explains why.
- **Admission constraint formula and banned domains:** `N` is the count in the domain's parent domain, and the total only for the top topology level, as in `populateSpreadCounts`. The `maxShareAllowingPlacement` descriptions now point to the formula.
- **Story 1:** with `DeploymentJobUIDLabel` (Beta, on by default in v0.20), the default `job-uid` selector groups a Deployment's replicas. The story uses the default and explains when an explicit selector plus `labelKeysToCopy` is needed.
- **Stories 1 and 4:** add the mandatory `podset-required-topology` annotation. Without it, the manifests are rejected.
- **Validation and error handling:** documents that `podset-required-topology` is required. A `Required` rule with an unknown `topologyKey` rejects the flavor (`NoMatchingFlavor`), and a `Preferred` one is skipped. A rule below the requested level leaves the Workload pending with `TopologyPlacementFailed`.
- **Visibility:** describes the condition messages and the `V(3)` log for Workloads blocked by spreading. Removes the planned `TopologySpreadKeyNotFound` and `TopologySpreadingNotApplied` conditions, which were never implemented; whether to add a dedicated condition is left for beta.
- **Test plan, unit test 18:** matches the behavior above.
- **Graduation Criteria, Alpha:** other integrations don't reject the annotation, but they are untested and unsupported.
- **Non-Goals and Drawbacks:** rolling updates can leave replicas spread across fewer domains than a fresh scale-up, because old replicas still count while new ones are placed.

User docs (`site/content/en/docs/concepts/topology_aware_scheduling.md`):
- Fixes the sentence saying the default selector doesn't group a Deployment's Pods. With `DeploymentJobUIDLabel` enabled (the default) it does.
