#### What this PR does / why we need it?
This PR deflakes the following freshness integration tests:
- `Pending scheduling hashes under differing LimitRange defaults`
- `Scheduling hash freshness across LimitRange changes`

In both tests there was a race between the manager's `LimitRange` informer cache and the first scheduling cycle.
Diagnosis is as follows based on the [prow build logs](https://storage.googleapis.com/kubernetes-ci-logs/pr-logs/pull/kubernetes-sigs_kueue/16601/pull-kueue-test-integration-shard-2-release-0-20/2106015016556695552/build-log.txt):
| Time | Event |
|---|---|
| 40.806 | Workload one is created in `hash-defaults-small-*`. Its effective resources are computed from the manager cache, which has no LimitRange yet, so the request is 0 CPU. |
| 40.809 | Scheduling cycle 1: “Workload assumed in the cache.” Zero quota still fits a 0-CPU request. |
| 40.812 | The informer delivers both LimitRange create events (“LimitRange scheduling fields changed,” `oldLimits: null`). |
| 40.835 | Workload two is created after the cache has seen the LimitRange, so it gets 3 CPU, `NoFit`, and becomes inadmissible. |
| 40.871 | Workload one is “successfully admitted.” |

Solved the race by reordering the lines, so when the manager starts, each cache does an initial full listing of existing objects, and Kueue waits for that listing to finish before it processes anything.
