## Description

#### What type of PR is this?

/kind bug
/area multikueue

#### What this PR does / why we need it?

MultiKueue workload counter series were not removed when a ClusterQueue or MultiKueueCluster was deleted. This left stale metric series behind and caused recreated objects with the same names to continue from the old counter values.

This PR:

- clears dispatched, admitted, and evicted MultiKueue workload counters when a MultiKueueCluster is removed;
- clears the same counters when a ClusterQueue is deleted through the always-on core ClusterQueue delete handler;
- keeps `ClearMultiKueueClusterQueueMetrics` limited to status-gauge cleanup, since it is also used during normal reconciliation and must not reset counters;
- adds tests covering cleanup by worker cluster and ClusterQueue while preserving unrelated metric series.

Fixes #16615

#### Useful notes for your reviewer

The ClusterQueue counter cleanup is intentionally wired into the core ClusterQueue Delete handler rather than the feature-gated MultiKueue ClusterQueue reconciler, so it also works when `MultiKueueManagerQuotaAutomation` is disabled.

> 🤖 **Claude Opus 5.5 responding on behalf of vladikkuzn**

The cleanup placement and label matching look correct. I have two small test nits inline and one non-blocking FYI. I reviewed the diff against `a2625887` by reading the code; I didn't run tests locally.

- `DeletePartialMatch` on `cluster_queue` / `cluster` drops every series of the three counters, including every `replica_role` and, for the evicted counter, every `reason`.
- `ClearMultiKueueClusterMetrics` is only reached from `stopAndRemoveCluster` (MultiKueueCluster NotFound or being deleted). Connection loss and config failures only mark the client disconnected (`disconnectCluster`, or `markDisconnected` when a watch ends), so they keep the counters.
- Putting the ClusterQueue cleanup in the core `Delete` handler rather than `ClearClusterQueueMetrics` is right. `ClearClusterQueueMetrics` also runs from `resyncClusterQueueGaugeMetrics` for live CQs when custom labels change, and these counters carry no custom labels, so clearing them there would only lose data.
- `ClearMultiKueueClusterQueueMetrics` stays gauge-only, which its live-CQ callers (`multikueue/clusterqueue.go:91`, `multikueue/metrics.go:54,82`) require. Its NotFound caller is behind `MultiKueueManagerQuotaAutomation`, which is why the counter cleanup can't live there.

FYI, no change expected in this PR: the workload reconciler works from the `*remoteClient` snapshot taken in `readGroup`. `StopWatchers` cancels and joins only the watcher goroutines and leaves the client usable, so a reconcile already in flight can still report after `stopAndRemoveCluster` cleared the series. For example, a remote `Create` at `workload.go:830` followed by `ReportMultiKueueWorkloadDispatched` at `:834` recreates the series starting from 1. The ClusterQueue path is much less exposed, because the `ResourceInUse` finalizer waits until no quota-reserving workloads remain in the cache.
