#### What this PR does / why we need it?

With `KueueDRADeviceFeasibility`, the TAS assignment counts a DRA-backed extended resource against a node that publishes it through a device plugin (`forLeaf`). The usage it records between the PodSets of one Workload, though, comes from `SinglePodRequests`, where that resource is zeroed for the device check, so a later PodSet sees the device as still free on that node. Two PodSets that each need one device can both land on a node that publishes only one, and one of the Pods stays Pending.

An elastic scale up runs into the same miscount. Placement can keep choosing the node the retained Pod already uses, the final fit check rejects that every time, and the scale up stays pending.

The usage recorded between PodSets now goes through the rule the flavor assigner already applies to an assignment's TAS usage. That rule moves to `TASFlavorSnapshot.RequestsForDomain`, and `forLeaf` makes the same choice through a shared helper, so what placement counts on a node and what it records there come from one place. Every place that records usage between PodSets uses it: the regular path, node replacement and elastic scale up or down.

Related: #14443

#### Useful notes for your reviewer

This came up while reviewing #14443, which makes the final `Fits` check deduct what each PodSet takes. With that change alone, `Fits` rejects the placement above, and the recompute, which uses the same accounting, picks the same node again, so the Workload is skipped in every cycle. This one should merge first.

Nothing changes with the gate off, or for a PodSet without a DRA-backed extended resource. The new `TestFindTopologyAssignments` cases fail without this change, and so do the three new specs in the WAS integration suite: a plain placement, a node replacement and an elastic scale up. One of the unit cases uses a rack as the lowest level, where the node a Pod lands on is known only within the cycle.

When the lowest level is above the node, say a rack, the usage of an admitted Workload, or of the Pods an elastic scale up keeps, is recorded against the rack rather than a node. The rack's bound uses the delegated request, the device check drops the claim it derives for the resource on nodes that publish it, and a node only sees what the current cycle put on it, so placement doesn't see the devices those Pods hold. A Pod can still be placed in a rack whose device plugins have nothing left. With the gate off, the rack's bound counts them. This PR doesn't change that.

`RequestsForDomain` also keeps the rule that `forLeaf` and the device check already use: a node counts the delegated resources only when it publishes every one of them. kube-scheduler decides per resource instead, so a Pod that takes one resource from a device plugin and another through DRA on the same node can be judged differently. Changing that touches all three, and is left out here.
