## Description

#### What type of PR is this?

/kind bug

#### What this PR does / why we need it?

`requeueAndUpdate` overwrote the `updated` flag with the result of `SetBlockedOnPreemptionGatesCondition`, so once a workload had the `BlockedOnPreemptionGates` condition, the `QuotaReserved` and resource request changes in the same patch were dropped. Fixing that exposed a status loop: the scheduler used the `AdmissionGated` reason, which the workload controller treats as the `AdmissionGatedBy` reason and rewrites to `PendingEvaluation`. This PR only sets the flag when the gate condition changes, and switches preemption-gated workloads to the `PreemptionGated` reason, which the workload controller preserves.

None

### Comment by [@apullo777](https://github.com/apullo777) — 2026-10-03T12:13:37Z

Thanks for the fix! One interaction I noticed with the 0.20 defaults and StrictFIFO is that this can expose a status loop around the existing `AdmissionGated` reason collision. The scheduler writes `AdmissionGated` here, the workload controller rewrites it to `PendingEvaluation`, and the preemption-gated head can then be retried and write `AdmissionGated` again.

I reproduced this in an integration test using the "Queue head is preemption gated" setup with a StrictFIFO ClusterQueue: on the PR head the Workload kept flipping between the two reasons (~660 resourceVersion changes in 5s), while on main it stayed put.

Would it make sense to handle that interaction as part of this fix, or avoid using `AdmissionGated` for the preemption-gated status?
