#### What this PR does / why we need it?

@mimowo @anguszzzz

After a cold leader start, `Scheduler.Start` begins scheduling as soon as the lease is held. controller-runtime has already synced the informer stores, but ClusterQueue create handlers can still be walking that list. A victim ClusterQueue whose flavor is already loaded becomes active while occupant ClusterQueues are missing. `AddClusterQueue` backfills only the queue being added, and `isTASSynced` only checks that queue. Topology Aware Scheduling then treats nodes held by the missing occupants as free. The same window applies to cohort usage.

This does not change `isTASSynced`, TAS placement, or `handleCreate`.

How it works now (reworked after review, no polling and no list comparison):

- The scheduler cache wraps the controller-runtime sources whose event handlers fill it (`Cache.TrackInitialSync`): ClusterQueue, Cohort, ResourceFlavor, Workload, LocalQueue, and Topology plus the TAS ResourceFlavor source when TAS runs. These controllers run on every replica, so a follower is synced before it can lead.
- A Kind source reports synced only after its handler has returned for every object in the informer's initial list. `Scheduler.Start` calls `Cache.WaitForInitialSync` and starts the loop once every tracked source is done. There are no lists, no copies, and no timeout; a source that never syncs already stops the manager through `CacheSyncTimeout`.
- The Cohort create, update, and delete handlers now update the cache and queue manager on every replica, the same way the ClusterQueue, ResourceFlavor, and Topology handlers do. Before this, Cohorts only reached the cache from `Reconcile`, which `leaderAwareReconciler` requeues by `LeaseDuration` on followers, so a warm follower took the lease without its explicit Cohorts for up to one lease duration (borrowing ClusterQueues could not admit and subtrees were detached from their parent). That gap exists on main too. `Reconcile` is otherwise unchanged (status, cycle notifications, metrics, still leader only) and repeats the same idempotent update.

Fixes #16624

#### Useful notes for your reviewer

- The TAS cold-start regression test no longer depends on the informer replay order (with WatchListClient the initial list is replayed from a map, so it is not name order). It uses two hostnames and two ClusterQueues, each with a running workload on its own hostname and a pending workload that needs a whole hostname, and pauses after whichever ClusterQueue is cached first. Without the gate it fails 8/8; with it, it passes 8/8.
- New `test/integration/singlecluster/controller/failover` suite runs two managers with real leader election (lease 30s, retry 1s). An explicit Cohort holds 4 CPU and a 0 quota ClusterQueue borrows from it. After the leader stops, a 1 CPU workload is admitted within 0.8 to 0.9s (about 2ms after the election). main and the previous head of this PR take 29.1s and 29.5s.
- The scheduling perf job failed on the previous head because the first cycle started a few seconds late (cached lists on lazily started Cohort and Topology informers plus 100ms polls) while the generator was already creating workloads.

@anguszzzz thanks for the detailed review and the numbers. pushed d3efa67, which reworks the gate.

**1. polling cost.** no, i hadn't load tested it at 50k, and your numbers make sense. every 100ms it listed 4 to 5 kinds from the informer cache, which deep copies every object, so cost grew with cluster size for as long as the gate was closed.

i dropped polling entirely. the new version waits on the event handlers instead:
- the cache wraps the controller-runtime sources whose handlers fill it (clusterqueue, cohort, resourceflavor, workload, localqueue, and topology plus the tas resourceflavor when tas runs).
- a kind source only reports synced after its handler has returned for every object in the informer's initial list, so the scheduler waits on a counter and a channel.
- no lists, no copies, and the cost doesn't depend on the number of workloads. the 2 minute cap is gone too, since a source that never syncs already stops the manager via CacheSyncTimeout.

this is basically the WaitForHandlersSync idea from #5221.

**2. warm failover.** good catch, and main has the same gap. cohort is the only kind that reaches the cache only from Reconcile. on a follower, leaderAwareReconciler does a get and requeues after the lease duration, and winning the election doesn't wake those items (#14386). so a warm follower leads without its explicit cohorts until that requeue fires: borrowing cqs can't admit, and the subtree is detached from its parent. my gate turned that into a full scheduler stall.

fix: the cohort create/update/delete handlers now update the cache and the queue manager on every replica, same as the cq, rf and topology handlers. Reconcile is otherwise unchanged (status, cycle notifications, metrics, still leader only) and repeats the same idempotent update.

i added an integration test with two managers and real leader election (lease 30s, retry 1s). an explicit cohort holds the quota, and a 0 quota cq borrows from it. i stop the leader, create a workload, and time it:
- main: admitted after 29.1s
- previous pr head: admitted after 29.5s
- now: admitted after 0.8 to 0.9s, which is just the election (2ms after the new leader is elected)

the test asserts admission within 10s, so it fails on main and on the old head.

### Comment by [@dundysm](https://github.com/dundysm) — 2026-10-15T22:34:13Z

@mimowo thanks for digging in, and for the pointer to #5311. answering the exploratory questions in one place; happy to follow whichever shape you prefer.

### why wrappers (vs waiting on controller-runtime alone / #5311)

controller-runtime's informer sync only means the store has the objects. the bug is one step later: `Scheduler.Start` can take the lease and schedule while the *handlers that fill kueue's cache* are still walking that list. `AddClusterQueue` backfills only the CQ being added, and `isTASSynced` only checks that CQ, so a victim CQ whose flavor is already loaded goes active while occupant CQs (and their admitted workloads / cohort usage) are still missing. the TAS cold-start test in this PR is exactly that window: pause after whichever CQ lands first, and without the gate it double-books 8/8.

`source.Kind`'s `WaitForSync` is the primitive that closes only after the handler has returned for every object in the initial list. the wrappers just expose that signal to the scheduler (a separate leader-elected Runnable), so it waits on the same barrier the cache-filling controllers already use. #5311 waited synchronously before scheduling for TAS RF/Topology; that direction was right, but waiting on informer sync alone does not cover CQ / Cohort / Workload handler lag, which is what produces both the TAS double-book and the cohort under-accounting @tenzen-y hit (3k CQs in cache vs 6k real).

so the wrappers are not a substitute for controller-runtime's start wait; they are how the scheduler learns that the *kueue cache* is filled, not just the informer stores.

### Start shape / dedicated goroutine

agreed we can drop the nested goroutine and do what you sketched:

```go
func (s *Scheduler) Start(ctx context.Context) error {
    if err := s.cache.WaitForInitialSync(ctx); err != nil {
        return err
    }
    go wait.UntilWithBackoff(ctx, s.schedule)
    return nil
}
```

i wrapped the wait inside the existing `go` only so `Start` returned immediately the way main does today. blocking in `Start` until sync (and surfacing a sync failure as a Start error) is cleaner; happy to switch to that in a follow-up commit.

your channel-per-source sketch for `TrackInitialSync` is also fine; functionally it matches the pending counter. i can switch to that form if you prefer the readability.

### partitioning

yes. two clean cuts if you want them smaller:

1. **Cohort event handlers** (and the follower-cache / failover suite): preparatory, useful on its own for warm failover and the class of "took the lease without Cohorts / CQ quota" issues (#10346-shaped, and what @tenzen-y saw). detectable with the follower metrics / failover test already in this PR.
2. **`TrackInitialSync` + scheduler wait**: the cold-start scheduling gate, with the TAS cold-start regression that fails without it.

i can open (1) as a first PR and leave (2) on this branch, or keep them together since CI is already green on the combined tip. your call.

### discriminating test vs #5311

the TAS cold-start integration test is meant to discriminate: it fails when you only have informer sync / no handler barrier, and passes with the gate. if useful i can add an explicit comment (or a tiny unit assertion) that `WaitForCacheSync`-style readiness alone is insufficient, keyed off the same "pause after first CQ" hook. the failover suite separately covers the cohort-on-follower piece so (1) and (2) stay independently testable if we split.

### #10346 / preemption storms

agree premature scheduling with a partial CQ/Cohort set is a plausible root for under-accounting of quota and then picking too many victims. this PR's gate stops the first cycle until CQs, Cohorts, flavors, topologies, and admitted workloads are in the cache; the cohort handlers keep that state warm on followers so the next leader does not need a lease-duration reconcile wave. i have not claimed #10346 fixed (no direct repro from that issue yet), but the mechanism matches what you and @tenzen-y described.

+// initialSync counts the event sources whose handlers fill the cache and
+// have not yet processed their informer's initial list.
+type initialSync struct {
+	mu      sync.Mutex
+	pending int
+	// synced is closed when pending drops to zero. It is nil while nothing
+	// is pending.
+	synced chan struct{}
+}
+
+func (s *initialSync) add() {
+	s.mu.Lock()
+	defer s.mu.Unlock()
+	if s.pending == 0 {
+		s.synced = make(chan struct{})
+	}
+	s.pending++
+}
+
+func (s *initialSync) done() {
+	s.mu.Lock()
+	defer s.mu.Unlock()
+	s.pending--
+	if s.pending == 0 {
+		close(s.synced)
+		s.synced = nil
+	}
+}
+
+// wait returns a channel that is closed once no source is pending.
+func (s *initialSync) wait() <-chan struct{} {
+	s.mu.Lock()
+	defer s.mu.Unlock()
+	if s.synced == nil {
+		closed := make(chan struct{})
+		close(closed)
+		return closed
+	}
+	return s.synced
+}
+
+// TrackInitialSync returns src wrapped so that WaitForInitialSync does not
+// return before src has synced. Call it while setting up a controller whose
+// event handlers add objects to this cache, before the manager starts.
+//
+// A source built with source.Kind syncs once its event handler has returned
+// for every object in the informer's initial list, so after that the cache
+// holds every object of that kind that existed when the informer synced. The
+// controller waits for its sources before it starts workers, which is the
+// only time it calls WaitForSync. The controllers that use it run on every
+// replica (NeedLeaderElection is false), so a follower is synced before it
+// takes the lease.
+func (c *Cache) TrackInitialSync(src source.SyncingSource) source.SyncingSource {
+	c.initialSync.add()
+	return &initialSyncSource{SyncingSource: src, done: sync.OnceFunc(c.initialSync.done)}
+}
+
+// WaitForInitialSync blocks until every source passed to TrackInitialSync has
+// synced, or ctx is done. It returns at once if no source is tracked.
+func (c *Cache) WaitForInitialSync(ctx context.Context) error {
+	select {
+	case <-c.initialSync.wait():
+		return nil
+	case <-ctx.Done():
+		return ctx.Err()
+	}
+}
+
+type initialSyncSource struct {
+	source.SyncingSource
+	done func()
+}
+
+// WaitForSync marks the source as synced once the wrapped source has synced.
+// A source that fails to sync stays pending. The controller then fails to
+// start and the manager stops, which cancels the scheduler's wait.
+func (s *initialSyncSource) WaitForSync(ctx context.Context) error {
+	if err := s.SyncingSource.WaitForSync(ctx); err != nil {
+		return err
+	}
+	s.done()
+	return nil
+}

+func (s *initialSyncSource) String() string {
+	return fmt.Sprintf("%v", s.SyncingSource)
