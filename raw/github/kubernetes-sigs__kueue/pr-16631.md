What this PR does / why we need it?
Updates KEP-2941 to define how Kueue accounts for DRA devices that supply native node-allocatable resources through Kubernetes KEP-5517 (DRANodeAllocatableResources).

Workloads continue to be charged against the existing DRA logical resource configured in `deviceClassMappings` (via count, counter, or capacity) or extended resource mappings. Kueue does not merge translated CPU or memory amounts into ClusterQueue usage at admission time. Kubernetes namespace ResourceQuota interaction during scheduler PreBind is also documented.

## AI summary

This PR updates KEP-2941 (DRA support) to define how Kueue accounts for DRA devices that supply native node-allocatable resources through Kubernetes KEP-5517 (`DRANodeAllocatableResources`). The change is documentation only. It touches two files and adds 66 lines.

- `keps/2941-DRA/README.md` (+65): adds a "Node-allocatable resources" section with three subsections: ClusterQueue accounting, Kubernetes ResourceQuota interaction, and rejected ClusterQueue accounting. It also adds a goal, a non-goal, a proposal item, a test plan entry, and a graduation note.
- `keps/2941-DRA/kep.yaml` (+1): adds the KEP-5517 link to `see-also`.

The policy is:

- Kueue does not merge translated CPU, memory, ephemeral storage, or hugepage amounts into the native-resource `ClusterQueue` charge.
- The existing DRA logical resource, set by `deviceClassMappings`, stays the admission-time quota unit. This applies to device count, counter, or capacity mappings and to extended-resource mappings.
- Native resources requested directly in the Pod template remain charged.
- Where Kubernetes supports `ResourceQuota` evaluation for `Pod/status`, namespace `ResourceQuota` accounts for translated resources separately during scheduler PreBind. Kueue can therefore admit a Workload whose Pod stays Pending or enters scheduler backoff.

The planned E2E test is documented but not implemented in this PR.
