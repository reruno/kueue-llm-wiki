## Description

#### What type of PR is this?
/kind bug

#### What this PR does / why we need it?
When `ElasticJobsViaWorkloadSlices` is enabled and an elastic `Workload` replacement slice shrinks one PodSet (e.g., `workers-a: 4 -> 1`) and grows another (e.g., `workers-b: 2 -> 5`), `FlavorAssigner.AssignFlavors` evaluates PodSet groups sequentially in `spec.podSets` order and previously only recorded a shrinking PodSet's negative quota delta (`requestAmount.Sub(oldRequest)`) in `Assignment.append` after visiting that PodSet.

As a result, when a growing PodSet preceded a shrinking PodSet in `spec.podSets`, `findFlavorForPodSets` evaluated the growing PodSet's positive delta before the shrinking PodSet's released quota was credited, causing the replacement slice to stay pending with `insufficient unused quota` even though the net quota delta fit within the ClusterQueue.

This PR pre-credits the negative quota deltas from shrinking PodSet groups in the quota usage passed to `findFlavorForPodSets` (and removes each group's pre-credited delta as that group is visited, since `findFlavorForPodSets` and `Assignment.append` account for the group's own delta directly). This ensures quota freed by shrinking PodSets is visible to growing PodSets regardless of `spec.podSets` order while preserving `groupedRequests.InOrder`, `Assignment.PodSets`, and `FlavorScanState.LastTriedFlavorIndexes` ordering.

Fixes #16657

#### Useful notes for your reviewer
- `groupedRequests.InOrder` and `Assignment.PodSets` order are preserved so downstream callers indexing by PodSet order remain unaffected.
