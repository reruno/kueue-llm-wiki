#### What this PR does / why we need it?

With `CustomMetricLabels` enabled and a `Workload`-sourced custom label configured, `kueue_pending_workloads` kept stale series for a ClusterQueue after it was stopped or resumed:

- On stop, active workloads are merged into the inadmissible tracker and the active tracker is replaced with an empty one, so the previously reported `status="active"` series were never deleted.
- On resume, `status="inadmissible"` series that only existed because of that merge were never deleted either, because the ClusterQueue's own inadmissible tracker never contained those label values.

As a result, `sum(kueue_pending_workloads)` double-counted pending workloads after a stop/resume.

The previous code only deleted series whose label set was present in the trackers with a zero count. On stop, the active tracker is replaced with an empty one, and on resume, the merged-only label sets are absent from the inadmissible tracker, so those series were never considered for deletion.

The trackers keep label sets whose count dropped to zero, so the union of the active and inadmissible label sets (computed before merging for a stopped ClusterQueue, which reuses the merge that was already done) covers every series reported for the ClusterQueue. For each of these label sets and both statuses, this PR sets the series when the count is positive and deletes it with `DeleteLabelValues` otherwise. This only touches the ClusterQueue's own series, does not scan the whole metric, and never deletes a series that is still valid, so scrapes do not see it briefly disappear.

`LabelValsTracker.PopZeroCounts` is no longer used and is removed; `LabelValsTracker.Count` is added for the per-label-set lookup.

Related: #16372
