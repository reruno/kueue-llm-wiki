## Description

The Incremental dispatcher used to skip every Workload that has a cluster name. Since it switched to the shared ShouldSkipClusterNomination helper, it no longer skips elastic Workloads, which the helper exempts because the MultiKueue workload reconciler must still sync a new slice to the cluster of the slice it replaces.

#### What this PR does / why we need it?

Since #11598 (v0.18.0), the Incremental dispatcher uses `workload.ShouldSkipClusterNomination` to decide whether to skip a Workload. That helper does not skip elastic Workloads that already have `status.clusterName`, because the MultiKueue workload reconciler still has to sync a new slice to the cluster of the slice it replaces. Before #11598, the dispatcher skipped every Workload with a cluster name.
As a result, every scale-up of an elastic job makes the Incremental dispatcher try to nominate worker clusters for the new slice. The API server rejects each attempt, because `clusterName` and `nominatedClusterNames` are mutually exclusive, and the request is retried with backoff until the slice's MultiKueue admission check is Ready. This PR makes the dispatcher skip any Workload that already has a cluster name again.

#### Useful notes for your reviewer
- `TestIncrementalDispatcherReconciler_Reconcile` now also checks the nominated clusters after Reconcile, because the fake client does not enforce the CRD rule. The new elastic case fails without the fix. A second new case shows that an elastic Workload without a cluster is still nominated.
- End to end, I ran the MultiKueue ElasticJob integration specs with the Incremental dispatcher (`MultiKueueDispatcherModeIncremental` passed to `managerAndMultiKueueSetup`). On main they pass but log 36 rejection lines (3 new slices, each rejected 6 times, each rejection logged twice). With this fix they log none. I did not keep that as a permanent spec, because the specs pass with or without the fix.
- The default AllAtOnce dispatcher is not affected, because it nominates inside the MultiKueue workload reconciler, which handles this case.
- v0.18, v0.19 and v0.20 are affected (ElasticJobsViaWorkloadSlices is Beta and enabled by default since v0.18), so this may be worth cherry-picking to release-0.20 and release-0.19.
- #10937 moves this check into the code shared by the AllAtOnce and Incremental dispatchers.
