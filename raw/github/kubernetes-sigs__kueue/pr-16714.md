#### What this PR does / why we need it?
Makes the milestone creation step in `hack/releasing/milestone_pull.sh` opt-in.

The script tried to create the next minor's milestone in kubernetes-sigs/kueue before opening the test-infra `milestone_applier` PR. Release managers run it from a personal fork without write access to upstream, so that call fails with a 404. Since #16502 the `/create-milestone` ChatOps command creates the milestone, and the release checklist already runs it one step before this script.

Following the suggestion on the issue, the step is kept but disabled by default:
- `ensure_milestone` returns early unless `CREATE_MILESTONE` is set, so a default run makes no milestones API call. The summary reports `skipped (use /create-milestone, or set CREATE_MILESTONE)`.
- `SKIP_MILESTONE` is removed, since skipping is now the default. `SKIP_PR`, `DRY_RUN` and the test-infra PR flow are unchanged.
- The usage text points to `/create-milestone` and notes that `CREATE_MILESTONE` needs write access to the Kueue repository.

I wonder if a cleaner split would serve release managers better long-term.

The CREATE_MILESTONE env var is a reasonable short-term fix, but it still leaves one script that does two things, with the milestone phase being a silent no-op by default.

```                                                                                                                                                            
./hack/releasing/milestone_pull.sh --create-milestone v0.21.0                                                                                             
./hack/releasing/milestone_pull.sh --create-pr v0.21.0                                                                                                    
./hack/releasing/milestone_pull.sh v0.21.0   # runs only the PR phase (current default)                                                                   
```
                                                                                                                                                       
This would make `NEW_RELEASE.md` self-documenting – the checklist step that previously pointed to the `/create-milestone` ChatOps command could also use `./milestone_pull.sh --create-milestone $VERSION` as an alternative. We could also reuse this logic in `release-utils.yml` to avoid duplicating it.                                              
                                                                                                                                                            
Not blocking this PR on that – the current change is safe and correct. Just flagging it as a potential follow-up if the release tooling continues to evolve.
