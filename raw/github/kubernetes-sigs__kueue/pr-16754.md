#### What this PR does / why we need it?
For elastic `batch/v1 Job`s, `PodsReady` must be evaluated against the granted replica count in the latest admitted Workload slice. During scale-up, a pending replacement slice can otherwise make an already-admitted Job appear unready to `WaitForPodsReady`.

<!--

Use `Related:` or `Part of:` to reference an issue without closing it.

Relates to #16478

#### Useful notes for your reviewer
`PodsReady` now receives the Workload selected by jobframework reconciliation, so the Job integration can use its granted count without fetching Workloads itself. Unit and integration coverage exercise scale-up while the replacement Workload is pending, without enabling partial replica scale-up.

PR was prepared with AI assistance.

**Security architecture risk:** **🔵 Low** · up to `1dfa9`

The change remains behind existing feature controls and admission checks. The main concern is that a failed capacity lookup can be interpreted as pod loss and, if that state persists, cause an otherwise healthy workload to be evicted. No introduced security boundary bypass was established, but workload identity and deployment-policy coverage remain incomplete.

**Retained concerns**
- **Low · reliability · inferred:** During pending partial scale-up, readiness now updates the retained admitted slice. A subsequent grant lookup failure falls back to the full Job target instead of reporting an unknown readiness result. When healthy pods satisfy the granted count but not the full target, this can persist WaitForRecovery; if it remains unresolved until the configured recovery timeout, the workload controller can evict the healthy reserved slice. The base pending-probe path did not apply that readiness transition to the retained slice, so this introduces a dependency-failure path into its capacity lifecycle.


<details>
<summary><h4><strong>Security review details</strong></h4></summary>
<dl>
<dd>

**Security Blast Radius**
- _observed_ — The selected status target is confined to the Job’s namespace and owner-reference API version, kind, and name. The shared reconciler’s new branch additionally requires readiness handling, slicing enabled on the object, a scaled-up workload, and non-admission; sharing the reconciler does not alone activate it for other integrations.

**Trust Boundaries and Controls**
- _observed_ — The active-workload selector does not validate owner UID or require the matching reference to be the controller reference. This identity limitation predates the PR: the base already used the same selector to update retained-slice priority. The new readiness write extends its uses, but attacker reachability through forged references and stale same-name Job lifetimes remains unverified, rather than an established new boundary bypass.

**Resilience and Maintainability Implications**
- _inferred_ — The retained-slice grant lookup failure is a bounded failure-containment concern: it can alter recovery and eviction state for the selected admitted workload, but the inspected path does not use that failure to grant additional capacity or bypass admission.

**Hardening Proposals**
- _proposed_ — Consider deriving readiness from the already-selected, UID-validated admitted workload snapshot, or propagating grant-lookup uncertainty separately from pod readiness. This would strengthen workload identity binding and avoid converting dependency failures into pod-loss recovery transitions.
