#### What this PR does / why we need it?
When the CapacityProviders referenced by a DQO together orchestrate more than 128 distinct flavors, discovery built a status.effectiveCapacity.flavors list above the MaxItems=128 limit, so the status update was rejected by the API server.

Discovery now sets EffectiveCapacityComputed=False with reason AggregationFailed, clears status.effectiveCapacity, and returns without attempting the invalid update. The API comment and generated CRDs are updated to describe the limit.

Fixes #16356

#### Useful notes for your reviewer
Follows the discussion in #16349. I chose soft validation over raising MaxItems. Tests cover exactly 128 flavors (accepted) and 129 (rejected).

#### Release note

```release-note
DQO: when the referenced CapacityProviders orchestrate more than 128 distinct flavors in total, the DQO now sets EffectiveCapacityComputed=False with reason AggregationFailed instead of failing to update its status.
```

The limit now fails cleanly without weakening access controls. The remaining risk is that overflow stops quota refresh while previously distributed quotas stay active, potentially leaving shared capacity allocations stale.

**Retained concerns**
- **Medium · reliability · inferred:** For an already-distributing DQO, overflow now stops quota refresh without clearing target effectiveQuotas, which remain scheduler-authoritative. If provider capacity subsequently decreases while the aggregate stays above 128 flavors, earlier allocations can remain active until recovery or permitted takeover. Retention predates this PR for other discovery failures, but synchronized overflow newly enters that policy; the base could still distribute before its oversized DQO status update failed. This affects shared-quota failure containment, although no unauthorized exploitation was established.


<details>
<summary><strong>Security review details</strong></summary>
<dl>
<dd>

**Security Blast Radius**
- _inferred_ — A shared provider configuration change can affect every referencing DQO and, for distributing DQOs, their configured quota subtrees. The retained-state concern therefore reaches shared ClusterQueue and Cohort allocations rather than only one workload; it does not confer authority over unrelated subtrees.

**Security Findings and Attack Paths**
- _observed_ — The overflow count comes from declared orchestrated flavor names, including declared flavors with no reported resources. Extra status-only flavor names are ignored. Consequently, changing provider capacity quantities alone cannot create additional counted flavors; an overflow trigger requires the referenced flavor configuration to exceed the aggregate bound.

**Trust Boundaries and Controls**
- _observed_ — Overflow does not write new target quotas or change their owner references. Normal distribution checks subtree conflicts and target ownership before writing. A failed distributor's retained quotas may be taken over under existing ownership rules, including the Distributed=False condition; overflow does not bypass those checks.

**Resilience and Maintainability Implications**
- _observed_ — Clearing DQO effective capacity is not equivalent to revoking target effective quotas. While the feature gate is enabled, quota consumers select target status.effectiveQuotas whenever present, without consulting the DQO's failure conditions. This existing separation explains why the new failure outcome can leave earlier allocations active.

**Hardening Proposals**
- _proposed_ — Make the retain-on-overflow policy explicit and verify the transition using already-distributed targets: supported aggregate, overflow, failed status persistence, repeated reconciliation, permitted takeover, and recovery. Validate retained scheduler-visible quotas rather than only DQO discovery status.
