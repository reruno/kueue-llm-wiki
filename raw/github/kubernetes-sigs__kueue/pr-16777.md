#### What this PR does / why we need it?
Adds `MultiKueueCluster.spec.unschedulable` so operators can cordon a worker cluster during maintenance. After the manager observes `unschedulable: true`, it stops creating new remote workloads there while continuing to manage previously dispatched workloads, including queued workloads that may still be admitted. Setting the field to `false` resumes dispatch.

The change adds the default-off alpha feature gate `MultiKueueClusterCordon`, filters AllAtOnce and Incremental candidates, and enforces the policy at remote workload creation for external nominations and pinned component/elastic workloads. Cordon leaves connection health (`Active`) unchanged and does not evict existing work.

#### Useful notes for your reviewer
- Cordon changes enqueue workloads associated with the cluster's MultiKueue configurations for both built-in dispatchers.
- New component workloads and elastic slices pinned to a cordoned worker wait for uncordon. Already-dispatched workloads retain admission, status synchronization, and cleanup behavior.
- This is a controller-observed policy: dispatch already in progress can complete. It affects dispatch from this manager, not worker-local jobs or other managers.
- The binary `unschedulable` field intentionally mirrors the Node API; a narrowly scoped API-lint exception documents that choice.
- Regenerated the API deepcopy/apply configuration, CRDs, Helm CRDs, API reference, and feature-gate documentation.
- AI usage: implementation, tests, documentation, and review were assisted by OpenAI Codex.
