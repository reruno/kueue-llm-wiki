## Description

#### What type of PR is this?

/kind bug

/area multikueue

#### What this PR does / why we need it?

With the AllAtOnce dispatcher, a Workload reconciled while none of its worker clusters is connected gets no nomination, creates no remote Workload, and returns neither an error nor a requeue. Nothing enqueues it again when a worker reconnects, so it stays Pending until some unrelated update touches it.

`nominateAndSynchronizeWorkers` now requeues the Workload after `retryIncrement` (5s) in that case: AllAtOnce, nothing nominated, and at least one cluster unavailable. `reconcileGroup` no longer replaces a requested requeue with a zero `requeueAfterSynchronize`.

Fixes #16887

#### Useful notes for your reviewer

- Only AllAtOnce is affected: Incremental and External nominate whether or not a cluster is connected, and an unreachable nominated cluster already returns an error that is retried.
- `retryIncrement` is the base step of the cluster reconnect backoff; the requeue stops as soon as a cluster is connected and a nomination happens.
- #16175, still open, would resync workloads on reconnect, but only those already nominated or assigned to the reconnecting cluster. The Workload here has neither.
- Tests:
  - New `TestWlReconcile` case "pending workload requeues when all clusters unavailable" fails without the change (`RequeueAfter` 0s instead of 5s) under both `WorkloadRequestUseMergePatch` settings, and passes with it.
  - New case "pending workload is dispatched to connected clusters without requeue while another cluster is unavailable" checks the requeue does not fire when a connected cluster takes the Workload.
  - The `multikueue` package passes with `-race`; `make test-multikueue-integration` passes; golangci-lint reports 0 issues.
- Reproduced on kind (one manager, one worker, AllAtOnce): paused the worker's control plane, submitted a Job, then unpaused it. Without the change the Workload was still Pending with no nomination three minutes after the reconnect. With it, the requeue ran every 5s while the worker was down, dispatch was attempted about a second after the reconnect, and the Workload was admitted on the worker once the worker's own webhook was ready. With the worker connected throughout, a Job was admitted within a second and the requeue never ran.
- This PR was made with AI assistance, but every change has been reviewed line by line.
