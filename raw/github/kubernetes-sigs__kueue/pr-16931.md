#### What this PR does / why we need it?

During TAS scheduling, Kueue incorrectly counts old Pods from failed nodes against the slots allocated to new Pods after recovery. This prevents some new Pods from being scheduled.

For example, Kueue is configured with `waitForPodsReady` enabled and `recoveryTimeout` set. A Job initially has 4 Pods. One node fails, and its Pod gets stuck terminating. The other 3 Pods remain healthy. If the Workload does not regain readiness before `recoveryTimeout` expires, Kueue evicts the entire Workload, not just the affected Pod.

The task is requeued and admitted again. The Job resumes with 4 new Pods, but the old Pod on the failed node is still stuck terminating. There are now “4 new Pods + 1 old Pod”. If TAS assigns the task to the same rack again, the old Pod is incorrectly counted as occupying a slot. 

```
	for _, pod := range pods {
		if utilpod.IsTerminated(pod) {
			// ignore failed or succeeded pods as they need to be replaced, and
			// so we don't want to count them as already ungated Pods.
			continue
		}
	 ...	

func IsTerminated(p *corev1.Pod) bool {
    return p.Status.Phase == corev1.PodFailed ||
        p.Status.Phase == corev1.PodSucceeded
}
```

As a result, Kueue only ungates 3 new Pods. The remaining new Pod has already been created, but its scheduling gate prevents it from being scheduled.
