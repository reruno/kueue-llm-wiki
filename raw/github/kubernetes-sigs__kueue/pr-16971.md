## Description

#### What type of PR is this?

/kind bug

#### What this PR does / why we need it?

`ParseAnnotation` multiplied `timeoutSeconds` and `recoveryTimeoutSeconds`
from the `kueue.x-k8s.io/wait-for-pods-ready` annotation by `time.Second`
with no overflow check. A value such as `36028797018963969` (2^55+1) wraps
to exactly `1s`, which passes the `maxTimeoutOnWorkload` validation, so the
workload ends up with a much smaller timeout than the user wrote. Other huge
values wrap to a negative duration and are rejected with the misleading
"must be greater than 0" message.

This PR converts seconds to a `time.Duration` with `utilmath.SaturatingMul`,
clamping to the max/min `Duration` on overflow. The existing validation then
rejects oversized values as exceeding `maxTimeoutOnWorkload`.

Fixes #16970

#### Useful notes for your reviewer

- I clamp instead of returning an error from `ParseAnnotation`, because it is
  deliberately non-validating (see the existing "negative timeoutSeconds
  parses without error" test case). The webhook stays the single place that
  rejects values.
- If `maxTimeoutOnWorkload` is unset, a clamped value is accepted as the
  maximum duration, which matches what the user wrote.
- Tests: 4 new cases in `TestParseAnnotation` and 3 in
  `TestValidateJobOnCreateWaitForPodsReadyAnnotation`. All 7 fail without the
  fix.
- The same bare `time.Duration(x) * time.Second` pattern exists in
  `pkg/controller/core/core.go` (`BackoffMaxSeconds`) and
  `pkg/workload/admissionchecks.go` (`RequeueAfterSeconds`). I left them out to
  keep this change scoped to the user-controlled annotation.
- Verified with `go test ./pkg/util/waitforpodsready/... ./pkg/controller/jobframework/...`.

accordance with the Kubernetes AI tool usage policy. I reviewed and tested
the change myself.

New submissions receive stronger overflow protection. However, a previously accepted annotation can change from a short timeout to roughly 292 years after upgrade, delaying automatic eviction. Where admission blocking is enabled, this can affect unrelated queues. Exposure requires existing overflow values and an explicitly enabled workload-level feature.

**Retained concerns**
- **Medium · security · inferred:** Previously accepted overflow annotations acquire centuries-long runtime deadlines after upgrade. For example, 36028797018963969 seconds previously wrapped to one second and could pass admission; the same persisted value now saturates to roughly 292 years. Runtime timeout selection trusts the annotation without enforcing the configured workload maximum, while unchanged annotations bypass update validation. A queued legacy job or existing workload can therefore delay readiness-timeout eviction and retain quota far beyond its previously effective deadline. With BlockAdmission enabled, a non-ready workload can also block fresh admissions across ClusterQueues. Recovery timeout overrides have the same reinterpretation risk.

**Security Blast Radius**
- _inferred_ — The identified regression requires a persisted overflow override and enabled workload-level parsing. It can prolong the affected workload's quota retention; with global admission blocking enabled, the availability impact can extend to fresh admissions across the controller's ClusterQueues. This is not an identity or privilege-escalation change.

**Security Findings and Attack Paths**
- _inferred_ — A user able to submit a managed job before upgrade could persist an overflow value that formerly validated as a short timeout. If that job remains queued or its workload later enters a non-ready state after upgrade, runtime parsing converts the stored value into a centuries-long deadline. The attack depends on legacy state; ordinary new creates and valid-to-overflow updates are rejected at head.

**Trust Boundaries and Controls**
- _observed_ — The existing Deployment create webhook calls the shared validator and declares failurePolicy=fail. The strengthened validator rejects saturated values and retains configured-cap checks. Update validation skips raw-equal or parsed-equivalent annotations, so it does not provide retrospective enforcement for legacy overflow values.

**Resilience and Maintainability Implications**
- _observed_ — Readiness, deactivation, and eviction remain escape paths from timeout waiting. The optional scheduling deadline can impose an earlier limit while scheduling is pending, but does not generally bound start or recovery waits. Scheduler second-pass workloads are exempt from the shared readiness wait.

**Hardening Proposals**
- _proposed_ — Define a bounded runtime policy for saturated legacy overrides, such as rejecting them during timeout selection and using a configured fallback, with an explicit normalization path for persisted annotations. This would make upgrade safety independent of whether admission revalidates an existing object.
