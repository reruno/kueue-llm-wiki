## Description

#### What type of PR is this?

/kind bug

#### What this PR does / why we need it?

`ParseAnnotation` multiplied `timeoutSeconds` and `recoveryTimeoutSeconds`
from the `kueue.x-k8s.io/wait-for-pods-ready` annotation by `time.Second`
with no overflow check. A value such as `36028797018963969` (2^55+1) wraps
to exactly `1s`, which passes the `maxTimeoutOnWorkload` validation, so the
workload ends up with a much smaller timeout than the user wrote. Other huge
values wrap to a negative duration and are rejected with the misleading
"must be greater than 0" message.

This PR converts seconds to a `time.Duration` with `utilmath.SaturatingMul`,
clamping to the max/min `Duration` on overflow. The existing validation then
rejects oversized values as exceeding `maxTimeoutOnWorkload`.

Fixes #16970

#### Useful notes for your reviewer

- I clamp instead of returning an error from `ParseAnnotation`, because it is
  deliberately non-validating (see the existing "negative timeoutSeconds
  parses without error" test case). The webhook stays the single place that
  rejects values.
- If `maxTimeoutOnWorkload` is unset, a clamped value is accepted as the
  maximum duration, which matches what the user wrote.
- Tests: 4 new cases in `TestParseAnnotation` and 3 in
  `TestValidateJobOnCreateWaitForPodsReadyAnnotation`. All 7 fail without the
  fix.
- The same bare `time.Duration(x) * time.Second` pattern exists in
  `pkg/controller/core/core.go` (`BackoffMaxSeconds`) and
  `pkg/workload/admissionchecks.go` (`RequeueAfterSeconds`). I left them out to
  keep this change scoped to the user-controlled annotation.
- Verified with `go test ./pkg/util/waitforpodsready/... ./pkg/controller/jobframework/...`.

AI disclosure: this PR was developed with AI assistance (Claude), in
accordance with the Kubernetes AI tool usage policy. I reviewed and tested
the change myself.

#### Release note

```release-note
WaitForPodsReady: Fixed a bug where a very large `timeoutSeconds` or `recoveryTimeoutSeconds` in the `kueue.x-k8s.io/wait-for-pods-ready` annotation could overflow into a small timeout and pass validation. Such values are now rejected for exceeding `waitForPodsReady.maxTimeoutOnWorkload`.
```
