## Description

#### What type of PR is this?

/kind bug

#### What this PR does / why we need it?

Fixes #16736.

A Job referencing a prebuilt workload that was left in a finished state by a deleted predecessor adopted it and was finalized immediately: the workload finalizer was removed and the Job kept running unmanaged, without a quota reservation.

This refuses to adopt a prebuilt workload that is already finished and is not controlled by the Job being reconciled, so the Job is stopped and the leftover workload is left untouched, consistent with how the reconciler already treats a prebuilt workload that is missing or controlled by another object.

#### Useful notes for your reviewer

The new check sits in the shared prebuilt branch of `ensureOneWorkload`, right after the guard for workloads controlled by another object, so it covers every integration that supports prebuilt workloads.

A finished workload that is controlled by the Job itself is still returned, so the regular path is unchanged: the Job is finalized and the workload finalizer is removed as usual. The two added tests pin both cases: one for a finished workload with no controller, which is no longer adopted (the Job is stopped with a "missing workload" message and `ErrPrebuiltWorkloadNotFound`), and one for a finished workload controlled by the Job, which is still finalized.

#### Release note

```release-note
A Job no longer adopts an already finished prebuilt workload. Previously the Job could be treated as finished and keep running without a quota reservation; it is now stopped, consistent with other unusable prebuilt workloads.
```

<summary><h3>Security Architecture Review</h3></summary>

**Security architecture risk:** **🔵 Low** · up to `4804d`

The change strengthens quota protection for jobs referencing finished workloads. However, some grouped workloads may stop without completing finalizer cleanup. This potential recovery problem is conditional on the affected group’s finalizer and retention configuration.

**Retained concerns**
- **Medium · reliability · inferred:** The controller-only eligibility guard also rejects finished prebuilt workloads legitimately owned through Pod-group member references. For managed serving groups that retain Kueue Pod finalizers, reconciliation then deletes Pods using StopReasonNoMatchingWorkload, which does not authorize finalizer removal. Serving groups never report themselves finished, and an existing Workload prevents the terminating-group finalization fallback. Without configured finished-workload retention or external cleanup, the group can remain stuck terminating. Previously, an equivalent finished workload could reach normal group finalization. This affects cleanup ownership and recovery after quota-safe shutdown; it is not a claim that every StatefulSet or LeaderWorkerSet configuration is affected.
