`433-444`: **📐 Maintainability & Code Quality** | **🔵 Trivial** | **⚖️ Poor tradeoff**

**`PodsReady` lists Workloads from the API on every reconcile of a partial-strategy Job.**

`partialScaleUpGrantedCount` calls `FindLatestActiveWorkload` each time `PodsReady` runs. In `reconciler.go`, `generatePodsReadyCondition` already has the admitted target Workload, so this second lookup is redundant. Each reconcile reads from the informer cache, so the cost is low. The real risk is drift: the two lookups can choose different Workloads, and then readiness is computed against one slice's grant while the condition is written to another slice. Use the grant from the Workload passed to `generatePodsReadyCondition` instead. One option is an optional interface such as `PodsReadyForWorkload(ctx, c, wl)`.
