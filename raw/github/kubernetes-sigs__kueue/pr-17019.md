#### What this PR does / why we need it?

Graduates the `PreemptionConfigPriorityClassSelector` (`matchNames` and `notMatchNames`) design from `keps/13396-configurable-preemptions/FUTURE_WORK.md` into `keps/13396-configurable-preemptions/README.md`:

- **Preemptor filtering (`preemptorPriorityClassSelector`)**: Allows preemption rules to filter which incoming workloads can trigger the rule based on `Workload.spec.priorityClassRef.name`.
- **Candidate filtering (`priority.matchNames` / `priority.notMatchNames`)**: Embeds `PreemptionConfigPriorityClassSelector` into `PreemptionConfigPriorityConstraint` and makes `mode` and `comparison` optional (validated via CEL `has(self.mode) == has(self.comparison)`), allowing candidate selection by priority class name alone or combined with relative priority comparison.
- **Unified priority class support**: Evaluates `Workload.spec.priorityClassRef.name` directly, supporting both `WorkloadPriorityClass` (`kueue.x-k8s.io`) and Pod `PriorityClass` (`scheduling.k8s.io`) without requiring `labelKeysToCopy`.
- **Alternatives considered**: Moves the `Priority Class Selectors` alternatives section and updates Story 2 in `README.md`.

  If we are going with nameExpressions & sourceType as in example:
  ```
  priorityClassSelector:
    sourceType:
      group: kueue.x-k8s.io
      kind: WorkloadPriorityClass
    nameExpressions:
    - operator: In
      values: [batch-low, batch-mid]
    - operator: NotIn
      values: [batch-high]
  ```
  
  Then IMO we should once again rethink the operator pattern - it made sense if we have many options of properties/labels or we see extensions possibilities in the future.
  
  But if we make this "name" specific. Then from my point of view:
  1) There are no plausible extensions inside.
  2) Always at most 2 entries make sense - One with `In` and one with `NotIn` (and one may still argue that even only 1 entry is reasonable as combination of In and NotIn can be replaced with simpler In).
  
  So we are losing all of the benefits and paying all of the cognitive complexity.
  
  Then I would once again suggest making it simple and just use simple arrays like `nameIn`/ `nameNotIn`, the above API will then simply look as follows:
  ```
  priorityClassSelector:
    sourceType:
      group: kueue.x-k8s.io
      kind: WorkloadPriorityClass
    nameIn: [batch-low, batch-mid]
    nameNotIn: [batch-high]
  ```
  From my point of view it will have the same expressibility, at a fraction of "types/boilerplate".
  
  But this is just my opinion - leaving the decision to you as the Kueue maintainers @mimowo @tenzen-y
