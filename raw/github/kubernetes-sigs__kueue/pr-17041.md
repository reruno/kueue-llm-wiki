## Description

#### What type of PR is this?
/kind bug

#### What this PR does / why we need it?
`Scheduler.admit` assumes a Workload into the scheduler cache synchronously, then patches its admission status in a goroutine. On a patch error it rolls back the cache assumption (`cache.DeleteWorkload`), implicitly assuming the write did not persist. But an overloaded apiserver can commit the write while the client only observes a timeout/reset, leaving a cache↔API divergence: the Workload is QuotaReserved/Admitted in the API while the scheduler cache has forgotten it, so the ClusterQueue under-counts usage. Scheduler-cache membership is otherwise populated only by edge-triggered update
handlers, so the divergence persists until the Workload's next update event.

This PR adds level-triggered convergence in the workload reconciler: when a Workload holds a quota reservation in the API but is missing from the scheduler cache, `Reconcile` re-adds it (retrying if its ClusterQueue is not cached yet). The scheduler's optimistic rollback on error is left unchanged; the reconciler converges any resulting divergence,
so the repair also covers divergences from other sources, without depending on the freshness of any single read. The membership check uses a minimal `workload.Info` so the hot path does not build the full effective-resource view every reconcile.

Fixes #17040 

#### Useful notes for your reviewer
- This supersedes the earlier scheduler error-path re-`Get` approach, which was considered and rejected:  it reads the informer-cached client, which lags the just-committed write under the overload premise (and even an uncached read can time out), so it could not be made reliably accurate from one point in the error path. The fix now lives in the reconciler.
- Covered by `TestReconcileConvergesSchedulerCacheFromAPIState`, which seeds the divergence (forgetting an admitted Workload from the cache, modeling the rollback) and asserts `Reconcile` re-adds it; a pending Workload is not added. No integration test is included on purpose: the branch only fires on a divergence, which cannot be forced in a clean integration run without fault injection, so such a test would pass with or without the change.
- Severity is latent/hardening: the divergence is largely self-correcting and the over-admission window is narrow, but a quiet Workload with no imminent update can stay diverged until this convergence runs.
- AI assistance: analysis, fix, and test were prepared with AI assistance, per the Kubernetes AI tool usage policy.

#### Release note
```release-note
Scheduling: Fixed a latent issue where the scheduler cache could forget a Workload that was actually admitted in the API (for example when an admission status write committed but the client observed a timeout), leaving the ClusterQueue's usage under-counted. The workload reconciler now reconciles scheduler-cache membership from API state, repairing the divergence on the next reconcile.
```
