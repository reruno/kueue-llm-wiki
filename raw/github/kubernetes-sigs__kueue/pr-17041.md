## Description

#### What type of PR is this?

#### What this PR does / why we need it?
`Scheduler.admit` assumes a Workload into the scheduler cache, then writes its admission status. On a write error it removed the assumed entry unconditionally. But the apiserver can commit a write while the client observes an error, such as a timeout or reset. If the Workload's update event arrives before the rollback, the event replaces the assumed entry with the admitted Workload, and the rollback then removes it. Nothing re-adds it, so the ClusterQueue under-counts its usage until the Workload's next update.

The rollback now calls `Cache.DeleteWorkloadIfUnchanged`, which removes the entry only if the cache still holds the version the scheduler assumed. This matches the second-pass branch of the same rollback, which already uses `UpdateWorkloadIfUnchanged`. If the event arrives after the rollback, the Update handler re-adds the Workload, as before.

Fixes #17040 

#### Useful notes for your reviewer
- An earlier revision repaired the cache from the workload reconciler. As @pajakd pointed out, that Reconcile can run before the rollback, so it missed the failing order. Following their suggestion, the fix now lives in the rollback itself.
- Covered by `TestSchedulerKeepsAdmittedWorkloadWhenCommittedAdmissionWriteReportsError`, which commits the write, applies its update event, and then has the client report a timeout. It fails without the change. `TestDeleteWorkloadIfUnchanged` covers the cache method.
