#### What this PR does / why we need it?

With `SkipReassignmentForPodOwnedWorkloads` enabled (Beta, on by default since v0.19), a Workload owned by a single Pod is parked with `Requeued=False` after an eviction by preemption or node failure, on the assumption that the Workload finishes together with its Pod and that the owning controller's replacement Pod arrives as a new Workload.

That assumption does not hold while the Pod still carries the Kueue scheduling gate: `Stop()` skips gated Pods, then the Pod is never deleted, nothing flips `Requeued` back to `True`, and the Workload and its Pod are stuck forever. This happens when a pod-owned Workload is preempted after it got `QuotaReserved` but before it was `Admitted`, typically because an AdmissionCheck (for example a ProvisioningRequest) was still pending.

This PR makes `clearAdmissionAfterEviction` park a pod-owned Workload only when the job is not suspended (`!job.IsSuspended()`). For the Pod integration that is exactly "the Pod no longer carries the `kueue.x-k8s.io/admission` scheduling gate", the same check `Stop()` applies: a terminated single Pod is handled as finished before the eviction step. After that, on every path that reaches this branch `IsSuspended()` means gated. A Workload whose Pod was never released is requeued as before this gate existed, while an evicted Workload whose Pod was already running keeps the current parking behavior.

Workloads that an earlier version already parked in this state (`Evicted=True`, `Requeued=False` with the same reason, quota released, Pod still gated) are repaired on reconcile by setting `Requeued=True`. Upgrading recovers them without deleting Pods by hand. That repair is marked with a TODO for removal once the affected releases are out of support.

Tests: unit cases in `pod_controller_test.go` (gated Pod requeued after preemption and after node failures, ungated Pod parked, parked gated Pod repaired, parked ungated Pod left alone) and three integration specs in the Pod controller suite. The first evicts the Workload directly while the Pod is gated. The second reproduces the reported scenario with the scheduler: a borrowing ClusterQueue with a pending AdmissionCheck and an owner ClusterQueue with `reclaimWithinCohort: Any`, checking that the preempted Workload is requeued, its gated Pod is left in place, and the Workload is admitted again once the preemptor finishes. The third reproduces the status an earlier version leaves behind and checks it is requeued. The TAS concept page and KEP-2724 are updated accordingly.

Fixes #16901

#### Useful notes for your reviewer

The gate has been on by default since v0.19, so a cherry-pick to `release-0.19` and `release-0.20` would be appreciated, as requested in the issue.

The branch is guarded by `workload.OwnedBySinglePod`, which only the Pod integration satisfies. Thus, other integrations are not affected.

`IsSuspended()` reads the Pod from the informer cache, like `Stop()` does. If the eviction reconcile runs before the cache has seen the ungate written by `Run()`, the Workload is requeued and, if re-admitted before the next Pod event, the released Pod keeps running while the Workload holds a new assignment. That read-after-write window is pre-existing for pod groups and for single Pods with the gate off; this change exposes gate-on single Pods to it as well, in exchange for not leaving them parked forever. A fix for the window itself (re-reading the Pod before `Stop()` decides) is a separate change.

Not in scope here: `shouldKeepExistingAssignment` in the TAS snapshot keeps the existing topology assignment of a pod-owned Workload on node failure even while the Pod is still gated. That is the same assumption in the node-replacement path and is worth a follow-up.
