#### What this PR does / why we need it?

With `SkipReassignmentForPodOwnedWorkloads` enabled (Beta, on by default since v0.19), a Workload owned by a single Pod is parked with `Requeued=False` after an eviction by preemption or node failure, on the assumption that the Workload finishes together with its Pod and that the owning controller's replacement Pod arrives as a new Workload.

That assumption does not hold while the Pod still carries the Kueue scheduling gate: `Stop()` skips gated Pods, so the Pod is never deleted, nothing flips `Requeued` back to `True`, and the Workload and its Pod are stuck forever. This happens when a pod-owned Workload is preempted after it got `QuotaReserved` but before it was `Admitted`, typically because an AdmissionCheck (for example a ProvisioningRequest) was still pending.

This PR adds the optional `JobWithStarted` interface to the job framework. The Pod integration implements it as "at least one Pod has had the `kueue.x-k8s.io/admission` scheduling gate removed", which is the same check `Stop()` applies, and `clearAdmissionAfterEviction` parks a pod-owned Workload only when the job has started. A Workload whose Pod was never released is requeued as before this gate existed, while an evicted Workload whose Pod was already running keeps the current parking behavior.

Workloads that an earlier version already parked in this state (`Evicted=True`, `Requeued=False` with the same reason, quota released, Pod still gated) are repaired on reconcile by setting `Requeued=True`, so upgrading recovers them without deleting Pods by hand. That repair is marked with a TODO for removal once the affected releases are out of support.

Tests: unit cases in `pod_controller_test.go` (gated Pod requeued after preemption and after node failures, ungated Pod parked, parked gated Pod repaired, parked ungated Pod left alone, plus a table test for `IsStarted`) and three integration specs in the Pod controller suite. The first evicts the Workload directly while the Pod is gated. The second reproduces the reported scenario with the scheduler: a borrowing ClusterQueue with a pending AdmissionCheck and an owner ClusterQueue with `reclaimWithinCohort: Any`, checking that the preempted Workload is requeued, its gated Pod is left in place, and the Workload is admitted again once the preemptor finishes. The third reproduces the status an earlier version leaves behind and checks it is requeued. The TAS concept page and KEP-2724 are updated accordingly.

Fixes #16901

#### Useful notes for your reviewer

The gate has been on by default since v0.19, so a cherry-pick to `release-0.19` and `release-0.20` would be appreciated, as requested in the issue.

Jobs that do not implement `JobWithStarted` are treated as started, so integrations other than Pod are not affected. The helper is only consulted for Workloads owned by a single Pod, which only the Pod integration creates, and that integration's compliance is checked at compile time.

`IsStarted` reads the Pod from the informer cache. A stale read can only show a gate that is already gone, which errs toward requeueing and heals when `Stop()` deletes the Pod on the next reconcile; basing the decision on the Workload's `Admitted` condition instead would park a Pod that is still gated whenever the eviction lands between `Admitted` and `Run`, which never heals.

Not in scope here: `shouldKeepExistingAssignment` in the TAS snapshot keeps the existing topology assignment of a pod-owned Workload on node failure even while the Pod is still gated. That is the same assumption in the node-replacement path and is worth a follow-up.

#### Release note

```release-note
Pod: Fixed a bug where, with `SkipReassignmentForPodOwnedWorkloads` enabled, a Workload owned by a single Pod that was preempted or evicted due to node failures while its Pod was still scheduling-gated (for example while an AdmissionCheck was pending) stayed parked with `Requeued=False` forever and its Pod was never deleted. Such Workloads are now requeued, and Workloads already left in that state by an earlier version are requeued on upgrade.
```
