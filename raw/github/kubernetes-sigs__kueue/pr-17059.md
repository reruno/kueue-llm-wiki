## Description

#### What type of PR is this?
/kind bug
/area multikueue

#### What this PR does / why we need it?

When a MultiKueue batch/Job is re-dispatched after eviction (e.g. following `EvictedDueToNodeFailures`), the new worker Job starts with `status.failed=0` and `status.succeeded=0`. Previously, the MultiKueue adapter copied the remote status wholesale onto the manager Job.

Starting with Kubernetes 1.35+ (`RejectDecreasingFailedCounter`), the API server rejects any status patch that attempts to decrease `status.failed` or `status.succeeded` on a `managedBy` Job:
status.failed: Invalid value: 0: cannot decrease the failed counter


Because the patch failed, the manager Job status was never updated with active/ready pods from the new worker Job, causing the workload to exceed `PodsReady` timeout and enter an eviction loop.

This fix introduces `mergeJobStatus`, which copies the remote Job status while clamping `failed` and `succeeded` to `max(local, remote)`. This guarantees monotonically non-decreasing counters on the manager Job while accurately syncing active pods, ready pods, conditions, and start time from the worker Job.

Fixes #17047 

#### Useful notes for reviewer

- In MultiKueue, `status.failed` on the manager Job is informational; backoff limit evaluation and pod restart policies are handled by the worker cluster.
- Clamping prevents API server rejection without hiding failures that occurred across dispatches.
- Added 3 regression tests in `job_multikueue_adapter_test.go` verifying non-decreasing failed and succeeded counters during re-dispatch.

**Security architecture risk:** **🟡 Moderate** · up to `34124`

Preserving counters addresses rejected status updates, but successes from an earlier dispatch can now combine with current worker readiness and prematurely disable readiness timeouts. Existing ownership checks and independent worker admission limit the exposure; no new credential or privilege boundary was identified.

**Retained concerns**
- **Medium · reliability · inferred:** Historical successes can satisfy readiness for a fresh worker dispatch. For a nonterminal Job with parallelism and completions of four, manager Succeeded=3 and Ready=0, and a replacement worker with Succeeded=0 and Ready=1, the merged status makes PodsReady true although three replacement pods are not ready. The base either accepted the worker status and counted only one ready pod, or rejected the decrease and retained the prior not-ready status. The head instead combines progress from different dispatches, causing the manager readiness-timeout controller to stop timing out this workload. This weakens recovery and shared-resource failure containment without requiring direct access to the manager status subresource.

**Resilience and Maintainability Implications**

**Hardening Proposals**

+//
+// Kubernetes 1.35+ rejects any status patch that would decrease status.failed
+// or status.succeeded on a managedBy Job (RejectDecreasingFailedCounter).

  **Separate the monotonic API counter from current-dispatch accounting.**
  
  `mergeJobStatus` preserves the manager Job’s higher `Succeeded` value, but the same value is used as current-dispatch progress. For non-indexed Jobs, `Job.ReclaimablePods` uses `Status.Succeeded` to calculate reclaimable pods. `Job.PodsReady` also includes `Status.Succeeded` when it determines readiness. After redispatch, prior-worker completions can therefore reclaim quota or mark the workload ready before the new worker completes its pods.
  
  Keep the Kubernetes-required monotonic counter in the manager status, but provide `ReclaimablePods` and `PodsReady` with a current-dispatch completion count instead of using that retained counter.
