#### What this PR does / why we need it?

Manual cherry-pick of #16076 to `release-0.19`, following the automatic backport conflict and @mimowo's request.

The API server's deletion timestamp already represents the end of graceful deletion. This backport stops adding the deletion grace period again when checking whether a Running Pod keeps its PodGroup active. It preserves the strict timestamp boundary, behavior when no deletion grace period is recorded, and the existing `FastQuotaReleaseInPodIntegration` behavior.

Related: #16075.
The `release-0.20` backport is already merged as #17077.

#### Useful notes for your reviewer

- Original merged commit: `d739c442ff86a12c9b3b75dbe62b887763655332`.
- The automatic backport conflicted in `pkg/controller/jobs/pod/pod_controller_test.go`. The manual resolution preserves release-0.19's Pod fixture structure while retaining the future, expired, and equal deletion-timestamp regression cases.
- The Pod integration regression is retained and uses the helpers available in this release branch. It verifies quota release following a Pod update after the deletion deadline while the Pod remains Running and terminating.
- This does not introduce a timer-based PodGroup reconcile, change StatefulSet behavior, or import unrelated main-branch refactoring.
- Local validation passed with Go 1.26.3 and envtest Kubernetes 1.36.0: the full Pod unit package, the Pod activity race tests (three repetitions), the complete Pod integration suite including the slow deletion-deadline regression, and `make ci-lint` (zero issues).
- A negative-control overlay restoring the original double-counted grace period fails the new expired-deadline unit regression; the same regression passes with this backport. The overlay was not committed.
- CI for this backport will run on the published head; the original PR's CI is not used as validation of the release-0.19 adaptation.
- AI assistance: Codex assisted with conflict resolution, compatibility adaptation, and validation.
