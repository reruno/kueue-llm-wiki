#### What this PR does / why we need it?

KueueViz derives the `/ws/namespaces` websocket payload from LocalQueues. Before this change, the endpoint always registered a LocalQueue informer for live updates, even when the authenticated caller did not have cluster-wide `watch` access to LocalQueues.

This updates the endpoint so callers without cluster-wide `watch localqueues` still receive the initial namespace snapshot, filtered by the existing per-namespace `list localqueues` authorization checks, but do not receive informer-driven live updates.

Fixes #17073

#### Useful notes for your reviewer

The endpoint keeps supporting namespace-scoped users. The change only gates the live LocalQueue informer registration on cluster-wide `watch` access.

Added a regression test for the no-watch path to verify that the websocket sends the initial payload without registering a LocalQueue informer handler.

**Security Blast Radius**
- _inferred_ — The changed capability is informer-driven namespace publication from the backend's LocalQueue view. Admission requires cluster-wide watch access, while visible namespace names remain bounded by per-namespace list permissions. The change restricts this capability rather than granting Kubernetes write access or expanding the backend's resource authority.

**Trust Boundaries and Controls**
- _observed_ — Caller-supplied bearer tokens are authenticated through TokenReview before identity is recorded in request context. The watch decision uses that identity with fixed LocalQueue resource attributes and empty namespace and name. SubjectAccessReview carries the caller's user, groups, UID, and extra attributes; authorization errors prevent snapshot and callback delivery.

**Resilience and Maintainability Implications**
- _observed_ — Active connections periodically revalidate tokens when a validator is configured, but do not repeat watch authorization. Revoking watch permission alone therefore does not remove an already-admitted callback. Snapshot list filtering still runs on updates. This lifecycle limitation predates the PR and is not an introduced or worsened concern.

**Hardening Proposals**
- _proposed_ — If live-update authorization is intended to remain valid throughout a connection, define its revocation timing and consider rechecking watch permission for active sessions. This is a follow-on hardening proposal, not a defect established as introduced by this PR.
