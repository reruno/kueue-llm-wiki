#### What this PR does / why we need it?

KueueViz derives the `/ws/namespaces` websocket payload from LocalQueues. Before this change, the endpoint always registered a LocalQueue informer for live updates, even when the authenticated caller did not have cluster-wide `watch` access to LocalQueues.

This updates the endpoint so callers without cluster-wide `watch localqueues` still receive the initial namespace snapshot, filtered by the existing per-namespace `list localqueues` authorization checks, but do not receive informer-driven live updates.

Fixes #17073

#### Useful notes for your reviewer

The endpoint keeps supporting namespace-scoped users. The change only gates the live LocalQueue informer registration on cluster-wide `watch` access.

Added a regression test for the no-watch path to verify that the websocket sends the initial payload without registering a LocalQueue informer handler.

### Comment by [@danylott](https://github.com/danylott) — 2026-10-14T08:41:32Z

@coderabbitai Please create two follow-up issues for the KueueViz authorization implementation:

### Issue 1: [KueueViz] Gate secondary GVK informer registrations on user `watch` permissions across multi-resource WebSocket endpoints

**Description:**
PR #17088 resolved the informer registration leak for `/ws/namespaces` by checking `watch` permission on `localqueues` before registering `LocalQueuesGVK` in `GenericWebSocketHandler`. However, several other multi-resource WebSocket handlers still register secondary GVK informers unconditionally:
- `/ws/workloads/dashboard` unconditionally watches `ClusterQueuesGVK`, `FlavorsGVK`, and `PodsGVK`.
- `/ws/cohorts` and `/ws/cohort/:cohort_name` unconditionally watch `ClusterQueuesGVK`.
- `/ws/cluster-queue/:cluster_queue_name` unconditionally watches `LocalQueuesGVK`.
- `/ws/resource-flavor/:flavor_name` unconditionally watches `ClusterQueuesGVK` and `NodesGVK`.

When a client has restricted permissions (e.g. a tenant who cannot watch cluster-wide resources like ClusterQueues or Nodes), these informers still trigger on cluster changes and stream live WebSocket updates.

**Proposed Fix:**
Adopt the PR #17088 pattern across all multi-resource WebSocket endpoints: dynamically authorize `watch` access for secondary GVRs via `authorizer.Authorize(ctx, identity, ResourceAccess("watch", gvr, "", ""))` and only register informers for GVKs the client is authorized to watch.

---

### Issue 2: [KueueViz] Enforce `list clusterqueues` SubjectAccessReview in `/ws/cohorts` handler

**Description:**
In `cmd/kueueviz/backend/handlers/cohorts.go`, `fetchCohorts` lists all `ClusterQueue` objects using the backend client and populates the `clusterQueues` field for each cohort without checking if the requesting user has permission to list `ClusterQueues`.

In contrast, `/ws/cohort/:cohort_name` checks `list` access on `ClusterQueuesGVR()` and populates `omittedPanels` when unauthorized. Because `/ws/cohorts` lacks this check, users with permission only to view cohorts receive cluster-wide ClusterQueue names.

**Proposed Fix:**
In `fetchCohorts`, perform a SubjectAccessReview check for `list` access on `ClusterQueuesGVR()`. If the user lacks access, omit the `clusterQueues` list from the response payload.
