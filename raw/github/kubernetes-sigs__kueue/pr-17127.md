#### What this PR does / why we need it?

Adds SparkApplication support to `ElasticJobsViaWorkloadSlices`, so a Kueue-managed SparkApplication can use Spark dynamic allocation.
Until now the webhook rejected `spec.dynamicAllocation.enabled=true`.

It reuses the existing WorkloadSlices mechanism, the same way RayCluster does; there is no new API or feature gate:

- Opt-in: `kueue.x-k8s.io/elastic-job: "true"` is now allowed on SparkApplication.
- Executor count: once the driver runs, the executor PodSet count is the number of `PENDING` and `RUNNING` executors in `status.executorState`, capped at `maxExecutors`. Before that, and for non-elastic apps, it stays `spec.executor.instances`.
  Spark changes executors without touching the spec, so the count comes from the status. For Ray it comes from the spec.
- Scale-up creates a new Workload slice, and scale-down shrinks the admitted one in place. This is the existing slice logic, unchanged.
- The webhook adds `ElasticJobSchedulingGate` to the executor template, so executors the driver creates wait until their slice is admitted. Removing the gate is rejected, as for RayCluster.
- `GetWorkloadNameExtraPart` keeps slice names unique, because executor scaling doesn't change `metadata.generation`. It has the same shape as the Ray helper.

Kueue does not start any scaling. Spark's dynamic allocation decides; Kueue only accounts for it and enforces quota.

Fixes #16806

#### Useful notes for your reviewer

**Design notes**
- The live count is trusted only from `RUNNING` onwards, terminal states included (`driverStarted`):
  - Before the driver runs, `executorState` is empty, or stale after a suspend or rerun.
  - Without the terminal states, an app that scaled to 0 executors and then completed fell back to `instances`. That looks like a scale-up, so the active slice was never finished and the driver's quota leaked. An integration test covers this, and it fails without the fix.
- No API change is needed. The existing annotation, scheduling gate and WorkloadSlices cover the feature.

**Known limitations (documented)**
- Scale-up is atomic. The `partial` strategy (KEP-12100) is not wired for SparkApplication yet; that could be a follow-up.
- The first admission uses `spec.executor.instances`, even when `initialExecutors` or `minExecutors` is higher. This is the existing behaviour, left unchanged.
- The Spark Operator tracks at most `--max-tracked-executor-per-app` executors (default 1000). Executors beyond that are not counted and stay gated.
- Only `spec.dynamicAllocation` is read. Dynamic allocation enabled only through `spec.sparkConf` isn't detected; that gap already exists upstream, so a separate PR.

**Testing**
- Unit: `TestNumExecutors`, `TestGetWorkloadNameExtraPart`, webhook defaulting and validation cases.
- Integration, `controller/jobs/sparkapplication` (16/16). The suite simulates the Spark Operator by writing the status:
  - scale-up, with the old slice finished as `WorkloadSliceReplaced`;
  - in-place scale-down;
  - scale to 0 then `COMPLETED` releases all quota;
  - a scale-up stays pending until there is quota;
  - a pending app is admitted after another one scales down;
  - non-elastic apps are unchanged.
- Integration, `webhook/jobs` (78/78): the gate is added on create, and removing it is rejected.
- `make ci-lint` is clean.
- Also checked by hand on a kind cluster with Spark Operator v2.5.2: real dynamic allocation scaled up and down, gated executors stayed gated beyond the quota, and quota was released on completion.

**AI disclosure:** I used an AI assistant (Claude) for parts of the implementation, tests and docs. I reviewed all changes manually.

#### Release note

```release-note
ElasticJobsViaWorkloadSlices: SparkApplication supports Spark dynamic allocation when annotated with `kueue.x-k8s.io/elastic-job: "true"`. Kueue follows the executors the driver adds or removes and holds new executors until their quota is admitted.
```
