#### What this PR does / why we need it?

Adds SparkApplication support to `ElasticJobsViaWorkloadSlices`, so a Kueue-managed SparkApplication can use Spark dynamic allocation.
Executors are gated until a Workload slice admits them, and the executor count follows the executor Pods while the driver keeps running.

Fixes #16806

#### Useful notes for your reviewer

- Same approach as RayCluster, behind the new Alpha gate `ElasticJobsViaWorkloadSlicesForSparkApplication`.
- Also restores template scheduling gates when a SparkApplication is stopped.
- Partial scale-up comes in a follow-up PR: #17350.
- Tests: unit, integration, and one e2e test with the real Spark Operator.

### Comment by [@Pradeep39](https://github.com/Pradeep39) — 2026-10-23T06:56:35Z

@reruno, have you seen kubeflow/spark-operator#2977? I think it affects this PR for long-running Dynamic Allocation apps.

Since kubeflow/spark-operator#2181, the operator stops adding executors to status.executorState once their executor ID exceeds MaxTrackedExecutorPerApp (default 1000). Existing entries are never pruned. Spark never reuses executor IDs, so a long-running DA app eventually creates only executors that are never recorded. For this PR, that means:

- The derived count collapses. numActiveExecutors() sees only the old entries, which are completed by then, so numExecutors() falls to minExecutors. The Workload shrinks in place while the untracked executors keep running, and the ClusterQueue is under-charged for them.
- Scale-ups stay gated forever. New executor Pods still carry ElasticJobSchedulingGate, but they never raise the count, so no new slice is created. The ungater only releases Pods within the current, now smaller, grant, so the rest never schedule.
- Slice names stop changing. GetWorkloadNameExtraPart uses len(status.executorState), which stops growing at the cap, so a later scale-up would compute a slice name that already exists.

@reruno - I noodled a bit more on this. I think what we need from the Kubeflow Community to make our reliance on `status.ExecutorState` foolproof is the fix in [kubeflow/spark-operator#2977](https://github.com/kubeflow/spark-operator/pull/2977). The fix in this Kubeflow PR instead of ceasing to track executorState after the executor Id goes past 1000 (MaxTrackedExecutorPerApp), only keeps 1000  active executor states and evicts the oldest finished entries instead. I think the sole purpose of this bookkeeping is to keep the SparkApplication object below the etcd acceptable bound of 1.5 mb. I initially thought job growing to the 1000th executor is very unlikely, but it turns out that a crash-looping executor can add a new executor every few seconds, since each retry gets a new ID and the SparkApplication executor id within no time can surpass id#1000.

IMO counting executor pods from Kueue's cache feels brittle to me. The SparkApplication integration doesn't watch pods, so a new executor pod alone doesn't trigger a reconcile. Today, the trigger is the operator updating status.executorState. Once executor IDs pass the tracking limit, those updates stop, and Kueue won't recount the pods. if I missed to infer the fix correctly, please keep me honest.
