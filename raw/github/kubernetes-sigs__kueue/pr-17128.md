#### What this PR does / why we need it?                                                                                                                                                
                                                                                                                                                                                            
Updates KEP-13396 (Configurable Preemptions) so that it describes how Alpha actually combines classical/fair sharing preemption candidates with `PreemptionConfig` candidates.          
                                                                                                                                                                                            
The KEP said candidates from both strategies are "gathered into two separate sets, merged, deduplicated, and ordered" in one list. The implementation does not do this (see `classical_strategy.go`, `fair_strategy.go` and `config/evaluator.go` in `pkg/scheduler/preemption`). It works as follows:                                                                
                                                                                                                                                                                            
1. The classical or fair sharing algorithm yields its candidates first, unchanged.                                                                                                      
2. Only if the preemptor still does not fit, the `PreemptionConfig` rules are evaluated tier by tier (`Always` → `InsufficientQuota` → `QuotaFeasibleAndInsufficientTopology`). Within each tier, candidates are deduplicated and ordered with the default ordering. 
3. Workloads already selected by classical/fair sharing preemption are never selected again, because each yielded candidate is removed from the snapshot.
4. Classical preemption can run separate attempts with and without borrowing; configurable candidates are appended at the end of each attempt. With fair sharing, they are appended after all fair sharing strategies.
5. Reverse-order backfilling runs over the combined sequence.                                                                                                                           
                                                                                                                                                                                            
The Integration section is rewritten accordingly. All other places that described the "merged" behavior are aligned: Summary, Proposal, Alpha integration phase, success criteria, Constraints, trigger tiers, test plan, graduation criteria, Implementation History, Alternatives, and one paragraph in `FUTURE_WORK.md`.                                                  
                                                                                                                                                                                            
This matters for Beta: feature parity with classical/fair sharing preemption, and the meaning of "no regression" for Alpha users, must be defined against the actual Alpha behavior.
