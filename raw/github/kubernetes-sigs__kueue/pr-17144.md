  Yes, but it's not new in this PR.
  Since #12501, removing a flavor from the ClusterQueue deletes the matching variant in
  `deleteStaleVariants`.
  If that variant was the admitted one, the controller evicts the parent with "No variant is running".
  The integration test "Should evict the parent when the admitted variant's flavor is removed" covers
  it.
  
  This PR fixes the case when another variant is already admitted at that moment.
  That is what happened in #16872.
  The scheduler admitted the `spot` variant before the variant reconciler saw the ClusterQueue update.
  So, the controller went to the "Parent and Variant admitted" branch, which only syncs PodsReady.
  The parent stayed admitted on the removed `reservation` flavor.
  
  Regular workloads do keep running when their flavor is removed.
  KEP-8691 doesn't cover this case either.
  If we want the same semantics for concurrent admission, I think it should be a separate change together with a KEP update.
