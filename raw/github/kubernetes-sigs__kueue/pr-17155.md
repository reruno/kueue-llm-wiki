## Description

#### What type of PR is this?

/kind bug
/area tas

#### What this PR does / why we need it?

When a PodSet has no effective resource requests and Kueue cannot select a
topology-aware flavor, the Workload currently remains inadmissible with the
generic message `no TAS flavor assigned`.

This PR distinguishes that case and reports actionable guidance:

> no effective resource requests; specify requests, limits, or namespace LimitRange defaults

The check runs on Kueue's effective resource requests, after limits and
namespace `LimitRange` defaults have been applied. It therefore preserves
workloads that obtain requests from either source.

The change is implemented in the common PodSet flavor-assignment path, so the
message applies consistently to all workload integrations. Existing behavior
is preserved for explicit zero requests, grouped PodSets that inherit a TAS
flavor, missing TAS flavors with nonempty requests, and multiple assigned TAS
flavors.

#### Useful notes for your reviewer

This PR was written in part with the assistance of generative AI. The change
was reviewed and tested by the contributor, including an adversarial review of
empty versus zero requests, explicit versus implied TAS, topology-group flavor
inference, and effective requests derived from limits and `LimitRange`
defaults.

Validation performed with Go 1.27.0:

- `go test ./pkg/scheduler/flavorassigner -count=1`
- `go test ./pkg/scheduler/... -count=1`
- `go vet ./pkg/scheduler/...`
- Focused topology-request, topology-assignment, and grouped-PodSet tests
- `gofmt`
- `git diff --check`

`make fmt-verify` was not run because GNU `sed` is not installed on the macOS
host. Direct formatting and the relevant Go tests and vet checks passed.

#### Release note

```release-note
TAS: Improved the message for workloads that cannot select a topology-aware flavor because a PodSet has no effective resource requests. The message now directs users to specify requests, limits, or namespace LimitRange defaults.
```
