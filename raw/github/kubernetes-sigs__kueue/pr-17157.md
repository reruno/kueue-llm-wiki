#### What this PR does / why we need it?

Since `MultiKueueOrchestratedPreemption` graduated to beta in #16235, every Workload that MultiKueue replicates to a worker cluster carries the `kueue.x-k8s.io/multikueue` preemption gate in its spec. The worker's Workload controller then wrote a `Closed` state for that gate into `status.preemptionGates`. The scheduler's admission apply is built from its queued copy, which does not have that state yet, and uses the same `kueue-admission` field manager, so the apply removed the state and the Workload controller wrote it again. Each replicated Workload paid two extra status writes, plus the watch events and reconciles they trigger on the worker and the manager.

A gate in the spec without a state is already closed (KEP 8303 and `HasClosedPreemptionGate`), so the `Closed` state carries no information. The Workload controller now only removes states of gates that are no longer in the spec. States are still written when a gate is opened, and eviction still resets existing states to `Closed`.

Related: #15891

#### Useful notes for your reviewer

User-visible change: `status.preemptionGates` no longer lists `Closed` states for gates that have never been opened. Every reader already treats a missing state as closed: the scheduler (`HasClosedPreemptionGate`), MultiKueue gate orchestration (`workloadToOpenPreemptionGate`), and concurrent admission (`HasOpenPreemptionGate`, `latestOpenGateTime`). Eviction only resets states that exist. The KEP sentence describing the worker-side status update is updated to match.

In CI, `periodic-kueue-test-multikueue-perf-main` throughput dropped from about 46 to about 33 workloads/s at the first run that included #16235, and has stayed there. Local MultiKueue benchmark runs (1,000 workloads, 3 workers, macOS arm64, 3 runs each):

| Build | Throughput | Generation time |
|---|---|---|
| `main`, gate enabled | 85.8–93.7/s | 6.1–11.1 s |
| This PR, gate enabled | 99.1–100.3/s | 3.1–3.7 s |
| `main`, gate disabled | 96.9–99.0/s | 3.5–4.5 s |

An instrumented run of the same change showed Workload status applies on each worker drop from about 3,000 to 1,000, and core Workload reconciles from about 19.5k to 13.2k, matching the gate-disabled run.

This PR alone does not make the periodic job pass: #15982 reverted the calibrated expectations from #15952 back to the 75 workloads/s floor, which will be restored separately.

#16235 is included in v0.20.0, so this is a cherry-pick candidate for `release-0.20`.

Validation:

- Unit tests in `pkg/controller/core`, `pkg/controller/admissionchecks/multikueue`, `pkg/controller/concurrentadmission`, `pkg/scheduler/...`, and `pkg/workload/...` pass. The updated and new `TestReconcile` cases fail without the fix.
- Integration tests pass: `test/integration/multikueue` (73 specs), `test/integration/multikueue/scheduler` (5), `test/integration/singlecluster/controller/concurrentadmission` (11), and the preemption-gated specs in `test/integration/singlecluster/scheduler` (2).
- `golangci-lint` on `pkg/controller/core`: 0 issues.

AI tools were used to assist with the investigation, implementation, and this description.
