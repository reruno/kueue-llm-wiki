## Description

#### What type of PR is this?

/kind bug

#### What this PR does / why we need it?

jobframework.UpdateWorkloadPriority resolves the target WorkloadPriorityClass once via ExtractPriority and updates target Workloads sequentially: first same-class workloads whose priority value drifted, then workloads transitioning from another class name.

If the WorkloadPriorityClass value changes after ExtractPriority and WorkloadPriorityClassReconciler.Reconcile runs before a workload update lands, the class reconciler skips a same-class workload that still holds the new value in the store (and misses transitioning workloads that still reference the old class name), and UpdateWorkloadPriority then overwrites the workload with the value resolved before the class change. Because every workload now carries the target PriorityClassRef.Name, subsequent job reconciles return at len(needsClassChange) == 0 without re-resolving the class.

This re-reads the WorkloadPriorityClass after the initial batch of updates in UpdateWorkloadPriority and merge-patches spec.priority on the written workloads when the class value changed while the updates were in flight.

Fixes #17122

#### Useful notes for your reviewer

- The follow-up write in syncWorkloadPriorityClassValue uses c.Patch(ctx, wl, client.MergeFrom(wl.DeepCopy())) on spec.priority rather than c.Update: once the initial batch has cleared the class-name mismatch, a 409 Conflict from a concurrent status or metadata update on a full Update would otherwise leave no needsClassChange marker for the next job reconcile unless restored.
- Added unit tests in pkg/controller/jobframework/workload_priority_test.go covering a WorkloadPriorityClass value change during the first workload Update combined with a concurrent ResourceVersion bump before the follow-up repair, as well as a mutating webhook storing a different priority while the WorkloadPriorityClass is unchanged.

#### Release note

```release-note
WorkloadPriorityClass: Fixed a race where a WorkloadPriorityClass value change during UpdateWorkloadPriority could leave updated Workloads on the outdated priority value.
```

I was thinking maybe we should restructure the UpdateWorkloadPriority a bit so there are explicit steps and relevant parts of the code moved to helpers.
I can identify 5 steps here:
1. Classify the workloads by whether their class name has to change.
2. Re-resolve only if a class name must change or same-class workloads disagree on priority - fast exit
3. Resolve the class once for the whole set.
4. Write the resolved ref and value to every workload whose state differs.
Something like:
`written, marker, err := applyWorkloadPriority(ctx, c, r, obj, sameClassName, needsClassChange, priorityClassRef, priority)`
5. Pick up a class value edited while the writes were in flight.

I actually think explicitly calling the steps with relevant comment will improve readability.

  A non-NotFound patch failure is not recoverable on the controller retry. All initial updates have already changed the workloads to the target class name, so the next `UpdateWorkloadPriority` call exits at `len(needsClassChange) == 0` without re-reading the class. The failed workload—and any later workload not yet visited—can therefore remain on the stale value indefinitely. Please preserve a durable retry marker or otherwise make a retry re-enter this repair path before returning the error.

  The restore works when the Workload moves between two classes. A Workload that moves from no class to `high` can reserve quota before the restore runs, though. The API server then rejects removing `priorityClassRef` (`priorityClassRef is immutable while workload quota reserved`). Every write in the restore fails, the errors are dropped, and the next call returns at the fast exit.
  
  I reproduced it in envtest with the pair from #17122, except that `w1` starts with no class. I changed `high` from 200 to 100 during the Update of `w0`, reserved quota for `w1` right after its Update, and made the follow-up patch fail once. The next two calls returned nil, and both Workloads stayed at 200.
  
  Could the same-class Workloads be written and checked against the class before the others move to it? If a write or patch fails in that part, the other Workloads still have their old class name, so the next reconcile resolves the class again. With that order, neither this restore nor `hasSplitPriority` is needed. A failure after the moves would only leave Workloads that started to reference the class in this call, which is #13866. I tried that order locally: in the same envtest steps both Workloads end at 100, and the table passes except one case that now reads the class three times instead of two.
