## Description

#### What type of PR is this?

/kind bug

#### What this PR does / why we need it?

`ParseAnnotation` in `pkg/util/waitforpodsready/waitforpodsready.go` multiplied
`timeoutSeconds` and `recoveryTimeoutSeconds` from the
`kueue.x-k8s.io/wait-for-pods-ready` annotation by `time.Second` with no
overflow check.

A value such as `36028797018963969` (2^55+1) wraps to exactly `1s`, which
passes the `maxTimeoutOnWorkload` validation, so the workload ends up with
a much smaller timeout than the user wrote. Other huge values wrap to a
negative duration and are rejected with the misleading
"must be greater than 0" message.

This PR converts seconds to a `time.Duration` with `utilmath.SaturatingMul`
(clamping to max/min `Duration` on overflow). The existing webhook
validation then correctly rejects oversized values as exceeding
`maxTimeoutOnWorkload`.

Refs #16970

#### Useful notes for your reviewer

- I clamp instead of returning an error from `ParseAnnotation`, because it
  is deliberately non-validating (the existing "negative timeoutSeconds
  parses without error" test case documents this). The webhook stays the
  single place that rejects values.
- Verified with `go build ./pkg/util/waitforpodsready/...` — builds cleanly.

#### Release note

```release-note
WaitForPodsReady: Fixed a bug where a very large `timeoutSeconds` or
`recoveryTimeoutSeconds` in the `kueue.x-k8s.io/wait-for-pods-ready`
annotation could overflow into a small timeout and pass validation.
Such values are now rejected for exceeding `waitForPodsReady.maxTimeoutOnWorkload`.
```

The fix rejects newly submitted oversized timeouts, but existing annotations can become roughly 292-year timeouts after upgrade. In deployments with admission blocking enabled, one affected non-ready workload can stall new admissions across queues. This requires an explicitly enabled workload-level timeout feature and a legacy annotation.

**Retained concerns**
- **Medium · security · inferred:** An annotation accepted before upgrade can change from a subsecond timeout into a roughly 292-year timeout without revalidation. Reconciliation trusts the newly parsed value, delaying timeout eviction far beyond the configured maximum. With BlockAdmission enabled, an authorized submitter's affected non-ready workload can block ordinary new admissions across all ClusterQueues. Fresh submissions are protected; the concern is the newly worsened interpretation of legacy state.

**Security Blast Radius**
- _inferred_ — The maximum supported availability exposure crosses queue boundaries: with BlockAdmission enabled, one affected admitted non-ready workload can hold the global readiness gate for ordinary new admissions across all ClusterQueues. Second-pass workloads are exempt. Without that mode, the demonstrated impact is delayed timeout eviction of affected workloads.

**Security Findings and Attack Paths**
- _inferred_ — An authorized job submitter can supply an overflowing annotation under the base implementation whose wrapped duration passes admission. If the raw annotation survives into a Workload processed after upgrade, saturation turns that input into a practically unbounded timeout. This worsens the earlier overflow condition rather than adding a new submission privilege; it requires legacy state and an admitted workload that remains non-ready.

**Trust Boundaries and Controls**
- _observed_ — Job admission checks positivity and the configured maximum when validation runs. Update validation skips unchanged raw annotations and semantically equal parsed configurations. Distinct positive-overflow inputs now share the same saturated configuration. The Workload create/update validators do not enforce this annotation's timeout maximum.

**Resilience and Maintainability Implications**
- _observed_ — The strongest alternative bounds are conditional. UnscheduledTimeout applies to the active scheduling phase with a current PodsScheduled=False observation, not every normal or recovery state. MaximumExecutionTimeSeconds is checked only when present. PodsReady, deactivation, or eviction can end the affected state, but timeout-driven eviction itself follows the saturated duration.

**Hardening Proposals**
- _proposed_ — Define an explicit legacy-value policy before controller timer computation, such as validating overrides against the effective configured maximum and falling back to a bounded cluster timeout. Ensure equivalent saturated updates cannot preserve an invalid legacy override without that policy being applied.
