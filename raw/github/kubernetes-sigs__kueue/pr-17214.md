#### What this PR does / why we need it?

#17158 restored the 35 workloads/s throughput floor from #15952, but that floor was calibrated before #16235 enabled `MultiKueueOrchestratedPreemption` by default. No run since then reaches it. The [first run after #17158](https://prow.k8s.io/view/gs/kubernetes-ci-logs/logs/periodic-kueue-test-multikueue-perf-main/2110434165617856512) failed at 33.15 and 33.18 workloads/s.

As requested in https://github.com/kubernetes-sigs/kueue/pull/17157#issuecomment-6163317990, this PR calibrates the floor from the CI runs on the current `main`, so the periodic passes whether or not #17157 lands. The floor is 23 workloads/s, about 21% below the slowest CI attempt; #15952 set its floor about 22% below the slowest attempt of its calibration runs. The latency ceilings, watch-gap tolerance, and scenario are unchanged.

Fixes #15891

#### Useful notes for your reviewer

Calibration data from all saved summaries of `periodic-kueue-test-multikueue-perf-main`. Every attempt admitted all 1,000 workloads with zero watch gaps and an identical scenario.

| Measurement | Since #16235 (32 runs, 64 attempts) | Before #16235 (21 runs, 42 attempts) | Bound |
|---|---|---|---|
| Throughput | 29.29–34.43 workloads/s | 44.25–46.86 workloads/s | ≥ 23 workloads/s |
| Admission P95 | 3.13–5.04 s | 0.52–1.38 s | ≤ 15 s |
| Quota-reservation P95 | 0.078–0.093 s | 0.063–0.074 s | ≤ 1 s |

Replaying the checker with the new expectations against all 106 saved attempts: all pass. No `kubernetes/test-infra` change has touched this job's resources since it was added, so the drop at #16235 is not a CI capacity change.

The README's CI calibration section now describes the runs since #16235 and keeps the earlier ranges for context.

`periodic-kueue-test-multikueue-perf-release-0-20` measures the same range (28 runs, 56 attempts, 30.58–34.11 workloads/s) and still uses the 75 workloads/s floor, so it also fails on every run. With this floor and the `release-0.20` configuration, all 56 attempts pass. Cherry-picking #17158 alone would leave that job failing, so this PR should be cherry-picked along with it.

Noise and sensitivity: on current `main`, attempts average 33.44 workloads/s with a standard deviation of 0.79. The slowest attempt is 29.29 workloads/s, and the slowest run outcome after the retry is 32.26. The two attempts in a run are correlated (r = 0.78), so the retry guards against one slow attempt more than against a slow node. A spurious failure would need both attempts to be over 6 workloads/s slower than the slowest of the 120 attempts observed on current code across both jobs. The cost is sensitivity: the floor fails only on a drop of about 31% from current throughput, or about 50% if #17157 lands and throughput returns to about 46 workloads/s. In that case, the floor should be tightened after a few runs. Neither periodic has email or Slack alerts configured.

`go test ./test/performance/multikueue/...` passes.
