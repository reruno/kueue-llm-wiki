## Description

#### What type of PR is this?

/kind bug
/area integrations

#### What this PR does / why we need it?

##### Why

When a `LeaderWorkerSet` is updated, the webhook checks if its `queue-name` label can change.
It allows the change while `status.readyReplicas` is 0, because then it treats the `LeaderWorkerSet` as not started. But a group's Workload can already hold a quota reservation while no replica is Ready, for example while the Pods pull images.

The Workload's `spec.queueName` can't change while its quota is reserved. So the webhook accepts the new label, and then the reconciler fails to update the Workload on every retry. The Workload stays in the old queue. In an integration test on main, the reconciler logged `queueName is immutable while workload quota reserved` 6 times in 300ms.

##### What

The webhook now rejects the change if any Workload of the `LeaderWorkerSet` holds a quota reservation. `LeaderWorkerSet` has one Workload per group, so the webhook checks all of them. It finds them with the `OwnerReferenceUID` index, like `reconcileWorkloads` does. The lookup only runs when the queue name changes.

#16320 added the same check for StatefulSet. This PR moves the check into `jobframework.ValidateQueueNameUpdate` and uses it in both webhooks. The helper and its tests come from #17257 by weizhoublue.

Fixes #17251

#### Useful notes for your reviewer

StatefulSet behavior does not change. It now uses the shared helper.

The webhook reads the Workloads from the cache, so a reservation made right before the update can still get through. #16320 has the same gap.

I used Claude Code to help investigate, write the change, and draft this description.

#### Release note

```release-note
LeaderWorkerSet: Fixed a bug where changing the `kueue.x-k8s.io/queue-name` label while no replica was Ready, but a Workload already held a quota reservation, made the LeaderWorkerSet reconciler fail on every retry and left the Workload in the old queue. Kueue now rejects the change in that case.
```
