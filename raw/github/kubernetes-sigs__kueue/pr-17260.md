#### What type of PR is this?

#### What this PR does / why we need it?

**Why**

When a custom metric label value changes on a ClusterQueue, LocalQueue or Cohort, Kueue clears the object's old series and records the gauges again under the new value. ClusterQueue and LocalQueue also delete their counters and histograms, and Cohort always keeps its counter. KEP-7066 now says these series keep their old values only when every custom label on them has `trackedValues` (#17413), because then the number of series is bounded.

**What**

On a label change, keep the old counter and histogram series only when every custom label of that object's kind has `trackedValues`, and remove them otherwise. This applies to ClusterQueue, LocalQueue and Cohort. Workload labels always have `trackedValues`, so only the object's own kind needs checking.

This takes over #15010.

Fixes #14478

#### Useful notes for your reviewer

- The integration tests use asymmetric configs (ClusterQueue bounded with LocalQueue mixed, the reverse, and both unbounded), so they also show that each queue kind decides on its own.
- #17423 also changes `TestClusterQueueCustomLabelUpdateMetricRefresh` and the code around `ClearClusterQueueMetrics`, so whichever PR merges second needs a rebase.

Preserving metric history fixes counter resets, but unrestricted custom-label values can now accumulate historical series within a single queue. Where non-admin users can edit those values, repeated changes and workload activity could exhaust shared controller or monitoring resources. The feature is opt-in, and value allowlists and full cleanup constrain the exposure.

**Retained concerns**
- **Medium · security · inferred:** For an exposed LocalQueue with an unrestricted custom-label source, a user permitted to edit that metadata can repeatedly choose fresh values while workload events create counters and histograms. Gauge-only refresh now retains every previously recorded identity instead of deleting it at the next label change. This permits growth without a configured historical-series bound within one queue and could degrade the shared controller and its monitoring. trackedValues prevents unrestricted value growth when configured, but remains optional; the new documentation recommendation is not enforcement.
