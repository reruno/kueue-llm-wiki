#### What this PR does / why we need it?

What #15062 asks for is that the LocalQueue accounting path run on Kueue's own resource types and convert only at the API boundary. The AFS ledger is the one part that cannot: its values are fractional, and the internal type we have, `Amount`, is integral — so there is no internal type to move the ledger onto, and it keeps carrying `corev1.ResourceList` through a path that is not an API boundary.

This PR adds the missing type. `resources.Decimal` is an exact fractional resource amount counted in 10^-9 of the unit the API reports a resource in, with `resources.Resources` as its map form. Nothing calls it yet: the ledger moves onto it in a follow-up, which I'd like to coordinate with #15236 since it touches the same files.

Part of: #15062

#### Useful notes for your reviewer

This PR changes no behaviour, since nothing calls the type yet. `NearestFloat64` can differ from today's `AsApproximateFloat64` in the last place, so ordering can change where two LocalQueues' scores land within one ulp of each other — that arrives with the ledger switch, not here.

Four things worth a look:

1. **`MulFloatRoundDown` reproduces `MulByFloat` digit for digit** — the semantics from #13621: the factor goes through the same shortest decimal string, each term is rounded before the sum, and rounding is towards zero. Pinned by a differential test (205 values x 20009 factors, including the real alpha and its complement) and by a 500-tick decay test against the `ResourceList` path. Of the two #13621 tests at the `MulByFloat` level, one ports over: rounding towards zero has to actually reach zero, or an idle queue settles on a non-zero fixed point. The other guards the decimal scale against growing, which does not apply here — a `Decimal` has no scale to grow — so that reason is recorded on the type. The three that cover `CalculateDecayedConsumed` belong in the ledger PR.

2. **`NearestFloat64` rounds once**, rather than replicating `AsApproximateFloat64`, which rounds twice and whose result also depends on how the `Quantity` happens to be stored. The correctness argument sits above the function because it is not recoverable from the code, and because the `big.Int` branch needs a different argument from the `int64` one: a value there can sit exactly on a rounding boundary. One test constructs boundary values and requires both branches to see one.

3. **`scale` is not a free parameter.** It is fixed by `MulByFloat` on one side and by what a `Quantity` can carry on the other, since `ParseQuantity` rounds to nano on the way in. The `int64` split in `NearestFloat64` depends on it as well: the margin is about 8.6x at scale 9 and below 1 at scale 10, where the argument no longer holds. `TestNearestFloat64SplitIsSafeAtThisScale` recomputes that margin from the constant.

4. **`AsQuantity` is exact and deliberately not capped** the way the `Amount` conversion is. `Amount` caps because its values are summed across a cohort tree and `ResourceQuantity` takes an `int64`; neither applies here. The one magnitude that does not survive a round trip is a whole multiple of 10^21 of the reported unit, where `Quantity.String` runs out of suffixes — pre-existing, and the test checks that the `ResourceList` path prints the same string.

Left out on purpose: the shared `int64`/`big.Int` core is not factored out of `Amount`. That would touch the scheduling hot path, which seems worth its own change rather than riding along here. The duplicate helpers are gone, though — `Decimal` reuses `maxExactFloat64Int`, `addInt64` and `subInt64`.

*Disclosure: I used Claude (AI) to generate parts of the code and comments in these two files, and the programs behind the numbers above. I reviewed the result line by line, made the design decisions myself, and ran the tests locally.*

On the duplication, let me explain what I understood, and please correct me if
I've got it wrong. `Amount`'s unit is whatever the resource is accounted in,
milli for CPU and whole units otherwise, while AFS decay multiplies by 1−α once
per sampling interval — at the documented defaults (168h half-life, 5m sampling)
α ≈ 3.4e-4, so one half-life is 2016 samples. For a queue holding 8 GPUs of
history, one sample should remove 0.0028 GPU; rounded away from zero, as
`AmountFromQuantity` does, it removes nothing and the history never decays, and
rounded towards zero it removes a whole GPU. That looked like the same design
point #15062 was left open on, where the options were a decimal variant of
`Amount` or keeping AFS in `float64`/`ResourceList`, so I tried the first — as a
sibling type, since rewriting `Amount` felt like more than I should decide on my
own. The repeated shape comes from that: same int64/big.Int invariant, so I
followed `amount.go` rather than invent a different convention beside it.

If the shape shouldn't appear twice, where would you want the shared core to
live? Pulling it into something both types embed would touch `Amount`'s
internals, so I'd rather ask before doing it.

+// Decimal is an exact fractional resource amount, counted in 10^-9 of the unit
+// the API reports the resource in. It is what AdmissionFairSharing keeps its
+// decayed history and pending penalties in; quota accounting stays on Amount,
+// which is integral. The count is an integer at a fixed scale, so unlike a
+// decimal there is no scale here to grow. Equal amounts are held the same way
+// however they were reached.
+type Decimal struct {
+	// Makes Decimal uncomparable: == would compare the pointer in large.
+	_ [0]func()
+	// small holds the value while it fits an int64.
+	small int64
+	// large holds it otherwise. It is never mutated, since a ledger entry is
+	// copied shallowly and a snapshot shares it with readers.
+	large *big.Int
+}
+
+// NewDecimalFromNano returns the Decimal for v base units, v * 10^-9 of the
+// unit the API reports the resource in. The name says which unit v is in.
+func NewDecimalFromNano(v int64) Decimal { return Decimal{small: v} }
+
+// decimalFromBig returns the Decimal for v, in an int64 when it fits one. It
+// takes ownership of v: a value past int64 is kept by pointer and never copied.
+func decimalFromBig(v *big.Int) Decimal {
+	if v.IsInt64() {
+		return Decimal{small: v.Int64()}
+	}
+	return Decimal{large: v}
+}
+
+// big returns d as a *big.Int the caller may not modify.
+func (d Decimal) big() *big.Int {
+	if d.large != nil {
+		return d.large
+	}
+	return big.NewInt(d.small)
+}
+
+func (d Decimal) Add(o Decimal) Decimal {
+	if d.large == nil && o.large == nil {
+		if sum, ok := addInt64(d.small, o.small); ok {
+			return Decimal{small: sum}
+		}
+	}
+	return decimalFromBig(new(big.Int).Add(d.big(), o.big()))
+}
+
+func (d Decimal) Sub(o Decimal) Decimal {
+	if d.large == nil && o.large == nil {
+		if diff, ok := subInt64(d.small, o.small); ok {
+			return Decimal{small: diff}
+		}
+	}
+	return decimalFromBig(new(big.Int).Sub(d.big(), o.big()))
+}
+
+func (d Decimal) Neg() Decimal {
+	// MinInt64 is the one value whose negation leaves the int64 range, since
+	// the range is not symmetric.
+	if d.large == nil && d.small > math.MinInt64 {
+		return Decimal{small: -d.small}
+	}
+	return decimalFromBig(new(big.Int).Neg(d.big()))
+}
+
+func (d Decimal) Sign() int {
+	if d.large != nil {
+		return d.large.Sign()
+	}
+	switch {
+	case d.small > 0:
+		return 1
+	case d.small < 0:
+		return -1
+	}
+	return 0
+}
+
+func (d Decimal) IsZero() bool { return d.Sign() == 0 }
+
+// Cmp returns -1 / 0 / +1 like bytes.Compare. It leans on the invariant that
+// decimalFromBig keeps: a value that fits an int64 is always held in small, so
+// a value held in large is outside that range and its sign alone decides the
+// comparison against one held in small.
+func (d Decimal) Cmp(o Decimal) int {
+	if d.large == nil && o.large == nil {
+		return cmp.Compare(d.small, o.small)
+	}
+	switch {
+	case o.large == nil:
+		return d.large.Sign()
+	case d.large == nil:
+		return -o.large.Sign()
+	default:
+		return d.large.Cmp(o.large)
+	}
+}
+
+func (d Decimal) Equal(o Decimal) bool { return d.Cmp(o) == 0 }
+
+// MulFloatRoundDown returns d * f, rounded towards zero at the scale, which
+// reproduces resource.MulByFloat digit for digit: f is taken as the shortest
+// decimal reading back as the same float64, the product is formed exactly, and
+// only then are the digits past the scale dropped. Rounding towards zero is
+// what keeps a decayed value from settling above the usage it decays towards
+// (#13621). It panics on a non-finite factor, as MulByFloat does.
+func (d Decimal) MulFloatRoundDown(f float64) Decimal {
+	mantissa, exp := decimalParts(f)
+	product := new(big.Int).Mul(d.big(), mantissa)
+	if exp == 0 {
+		return decimalFromBig(product)
+	}
+	return decimalFromBig(product.Quo(product, pow10(-exp)))
+}
+
+// pow10 returns 10^n as a *big.Int the caller may not modify. The exponents
+// repeat, so the small ones are built once rather than on every multiplication.
+func pow10(n int) *big.Int {
+	if n < len(pow10Table) {
+		return pow10Table[n]
+	}
+	return new(big.Int).Exp(bigTen, big.NewInt(int64(n)), nil)
+}
+
+// The exponent MulFloatRoundDown needs is the number of decimal places in the
+// factor's shortest form, at most 23 across the configurations AFS allows. The
+// table holds those with room rather than being a bound; pow10 computes the rest.
+var (
+	bigTen     = big.NewInt(10)
+	pow10Table = buildPow10Table(41)
+)
+
+func buildPow10Table(n int) []*big.Int {
+	t := make([]*big.Int, n)
+	t[0] = big.NewInt(1)
+	for i := 1; i < n; i++ {
+		t[i] = new(big.Int).Mul(t[i-1], bigTen)
+	}
+	return t
+}
+
+// decimalParts returns m and e with f == m * 10^e exactly, taking f through the
+// same shortest decimal string MulByFloat parses.
+func decimalParts(f float64) (*big.Int, int) {
+	s := strconv.FormatFloat(f, 'f', -1, 64)
+	exp := 0
+	if dot := strings.IndexByte(s, '.'); dot >= 0 {
+		exp = -(len(s) - dot - 1)
+		s = s[:dot] + s[dot+1:]
+	}
+	m, ok := new(big.Int).SetString(s, 10)
+	if !ok {
+		panic(fmt.Sprintf("MulFloatRoundDown called with a non-finite factor: %v", f))
+	}
+	return m, exp
+}

+// The name is deliberate: Quantity.AsApproximateFloat64 rounds twice and its
+// result depends on how the Quantity happens to be stored, while this depends
+// only on the value. Most values have no exact float64, so which neighbour is
+// chosen is decided here rather than left to a two-step conversion.
+//
+// Each branch rounds the exact value once:
+//
+//   - |d| <= 2^53: both operands are exact float64s, so the division rounds once.
+//   - a larger int64: q and rem are each exact as float64s, so only the addition
+//     rounds. The error in rem/10^9 is at most 2^-54, while an exact value here
+//     is at least 2^9/(10^9 * 2^30) from any rounding boundary, so it cannot
+//     cross one: boundaries lie on a grid no finer than 2^-30 because the result
+//     exceeds 2^23, and the distance has a numerator divisible by 2^9 because
+//     10^9 = 2^9 * 5^9, and is never zero because that would need |d| past
+//     MaxInt64. The margin is only 8.6x and it comes from the scale, so this
+//     branch holds at scale 9 and not finer; a test pins it.
+//   - past int64: the same split holds while the integer part is exact, and a
+//     value sitting on a boundary is then dyadic, so rem/10^9 is exact and the
+//     addition breaks the tie. Beyond that the quotient is taken in arbitrary
+//     precision and rounded once to 53 bits instead.
+func (d Decimal) NearestFloat64() float64 {
+	if d.large == nil {
+		if d.small >= -maxExactFloat64Int && d.small <= maxExactFloat64Int {
+			return float64(d.small) / nano
+		}
+		q, rem := d.small/nano, d.small%nano
+		return float64(q) + float64(rem)/nano
+	}
+	q, rem := new(big.Int).QuoRem(d.large, nanoInt, new(big.Int))
+	if q.IsInt64() && q.Int64() > -maxExactFloat64Int && q.Int64() < maxExactFloat64Int {
+		return float64(q.Int64()) + float64(rem.Int64())/nano
+	}
+	exact := new(big.Float).SetPrec(uint(d.large.BitLen()) + 1).SetInt(d.large)
+	f, _ := new(big.Float).SetPrec(53).Quo(exact, nanoFloat).Float64()
+	return f
+}

+// copied rather than stored.
+func FromQuantity(q resource.Quantity) Decimal {

+	case s < scale:
