#### What this PR does / why we need it?

Thanks to @mimowo for suggesting this rule on [#17260](https://github.com/kubernetes-sigs/kueue/pull/17260#issuecomment-6264416364).

The KEP says a custom label value change deletes counters and histograms. Kueue does this for ClusterQueue and LocalQueue values, but has kept the Cohort counter `kueue_cohort_subtree_admitted_workloads_total` since #10088.

The KEP now says Kueue keeps them only when the labels have `trackedValues`, because the lists bound how many series an object can have. A `SourceKind` can mix labels with and without `trackedValues`, so every label of the kind must have it. Otherwise they are deleted. Series shared by objects of the same `SourceKind` stay either way, as before.

Part of: #14478

#### Useful notes for your reviewer

This partly reverses #10088: unless every Cohort label has `trackedValues`, a value change deletes `kueue_cohort_subtree_admitted_workloads_total` again. The spec `shouldn't clear cohort counter metrics on label changed` uses a Cohort label without `trackedValues`, so the fix will need to change what it expects.

Deciding by the labels that changed would also be bounded, because a change to a label without `trackedValues` would still delete all of the object's series. It keeps more history when a kind mixes both, but whether an object keeps its history would then depend on which label changed, so I went with the simpler rule.

I replaced the sentence about `rate()` and `increase()`. They cannot recover what a deleted series recorded after the last scrape, as the example in Alternatives shows.

The rule does not reach `kueue_workload_creation_latency_seconds`. It carries LocalQueue labels but no LocalQueue key, so nothing deletes its series, and with LocalQueue labels without `trackedValues` it gains a series for each new value. I noted it under Stale metrics and left a fix out of this PR.
