#### What type of PR is this?

#### What this PR does / why we need it?

`multikueue_workloads_dispatched_total`, `multikueue_workloads_admitted_total` and `multikueue_workloads_evicted_total` were not cleared when a ClusterQueue was deleted, so their series stayed after the deletion.

This PR adds `ClearDeletedClusterQueueMetrics`, which the ClusterQueue deletion path now calls to clear these counters after `ClearClusterQueueMetrics`. They are not cleared in `ClearClusterQueueMetrics` itself, because it also runs when the custom label value of a live ClusterQueue changes, and these counters carry no custom labels.

A new unit test covers several worker clusters and replica roles and checks that another ClusterQueue's series are kept. `TestClusterQueueCustomLabelUpdateMetricRefresh` now checks that a custom label update keeps the counters.

Part of #17415

> **Stale MultiKueue reports can recreate a deleted ClusterQueue's counter series.**
> 
> This is a pre-existing follow-up. This PR does not introduce it. The reconcile reads a workload snapshot once, then sends a remote Create and reports Dispatched with the snapshot's ClusterQueue. The ClusterQueue can be deleted and its series cleared while that Create is still running. The report at `pkg/controller/admissionchecks/multikueue/workload.go:834` then increments the `cluster_queue` series again. This follow-up covers only the Dispatched report at that line.
> 
> The reconcile reads `group.local` once at the start (`readGroup`, `workload.go:335`). Step 2 checks quota only against that snapshot (`workload.go:387`). If quota is reserved, the reconcile calls the remote Create and then reports Dispatched with `admittedClusterQueue(group.local)` (`workload.go:834`). No lock or cancellation links this call to the ClusterQueue's workload count. The workload controller can remove the workload from the scheduler cache while the call runs. This happens when the workload becomes finished or inactive (`pkg/controller/core/workload_controller.go:1450`) or returns to pending (`workload_controller.go:1486`). If `cq.Workloads` becomes empty, the ClusterQueue finalizer is removed (`clusterqueue_controller.go:194-198`). The delete cleanup then clears the counter series. If the Create returns after that, the Dispatched increment can recreate the series for the deleted ClusterQueue.
> 
> The stale series also exists at the merge base. The base never clears these counters on deletion, so the series persists after deletion there too. This change narrows the case but does not add it.
> 
> Note: this behaviour predates this PR (already present at merge base `3ab60ecf53eb`); the change keeps it reachable.
