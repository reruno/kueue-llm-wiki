#### What this PR does / why we need it?

With `SchedulerLibraryIntegration` and `SchedulerLibraryDeepIntegration` enabled, a workload carrying `kueue.x-k8s.io/podset-preferred-topology` is admitted, but the scheduler library has no placement support for a preferred topology request. The object is left suspended and only the controller logs say why.

Reject a new or changed preferred topology request during admission when the deep integration gate is enabled, naming the gate in the message. Required and unconstrained requests are unaffected, and so is any request made with the gate disabled.

Following review feedback, this is not a Job-only check. The rejection lives in a shared `jobframework.ValidateTASPreferredTopologyRequest` next to the existing `ValidateTASPodSetRequest`, and every integration that validates topology requests calls it: Job, JobSet, LeaderWorkerSet, MPIJob, Pod, StatefulSet, TrainJob, SparkApplication, RayCluster, RayJob, RayService and the Kubeflow jobs.

On update, an unchanged annotation is still accepted. Objects that already carry it can therefore be suspended, resumed and cleaned up after the gate is turned on, matching the treatment of the wait-for-pods-ready annotation in `validateUpdate`.

Fixes #17427

#### Useful notes for your reviewer

- `ValidateTASPodSetRequest` keeps its signature, since out-of-tree integrations import it. The new helper is `ValidateTASPreferredTopologyRequest(replicaPath, replicaMetadata, oldReplicaMetadata)`; `oldReplicaMetadata` is nil on create.
- Every integration passes the previous pod template from its update validation, so an unchanged request stays accepted on update and an unrelated update of an object created before the gate was enabled is not blocked. Only new or changed requests are rejected.
- `SchedulerLibraryDeepIntegration` depends on `SchedulerLibraryIntegration`, which depends on `TopologyAwareScheduling`, so the helper checks only the deep integration gate. The gate machinery already rejects enabling the deep integration without TAS.
- The equivalent Workload-level guard is being added separately in #17419. This change is independent: it rejects earlier, at admission, so the user gets an error instead of an accepted object whose Workload creation keeps failing.
- Covered by `TestValidateTASPreferredTopologyRequest`, plus new cases in the Job, JobSet, StatefulSet and RayCluster webhook tests (rejected with the gate on, accepted with the gate off, unchanged accepted on update, added and changed rejected). The cases fail when the guard is removed.
- Ran `go test -count=1 ./pkg/controller/jobframework/... ./pkg/controller/jobs/...` and `go build ./pkg/controller/...`. `make verify` with the full lint toolset was not run locally.
- AI usage: this change was prepared with AI assistance (opencode) and reviewed by me before submission.

#### Release note

```release-note
Workloads with a preferred topology request are now rejected at admission when the SchedulerLibraryDeepIntegration feature gate is enabled, instead of being admitted and then staying suspended without an explanation.
```
