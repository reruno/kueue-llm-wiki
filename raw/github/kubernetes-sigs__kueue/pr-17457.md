**What this PR does / why we need it**:
When a LocalQueue update changes a custom metric label and also updates `spec.stopPolicy` to a non-None value (e.g. `Hold`), `stoppingQueue` is true.
Previously:
1. The `default:` branch of the `switch` omitted updating the cache when `customLabelsChanged || clusterQueueChanged`.
2. Downstream, `clearLocalQueueMetrics(e.ObjectOld)` cleared the old metric series.
3. However, `resyncLocalQueueGaugeMetrics` was skipped due to `!stoppingQueue`.
4. Because admitted workloads in this LocalQueue continue running actively despite the queue being stopped from accepting new admissions, skipping the resync prevented `kueue_local_queue_admitted_active_workloads` from being reported under the new label values. Later, when these workloads finish and decrement the metric, the gauge drops to -1.

This PR:
- Calls `cache.UpdateLocalQueue` in the `default:` case when `customLabelsChanged || clusterQueueChanged`.
- Removes `!stoppingQueue` from the gauge resync condition so `resyncLocalQueueGaugeMetrics` is called to rebuild gauge metrics for running admitted workloads under the new label values.
- Adds an integration test in `custom_labels_test.go` verifying that admitted active workloads gauge metric resyncs under new custom labels when the queue is stopped in the same update, and returns to 0 upon completion without going negative.

**Which issue(s) this PR fixes**:
Fixes #17356

**Does this PR introduce a user-facing change?**:
```release-note
Fix a bug where kueue_local_queue_admitted_active_workloads could go negative when a LocalQueue custom metric label was updated alongside stopPolicy.
```

Thanks! I checked that the new test fails without the fix and passes with it.

One gap: the new test still passes if I remove the `cache.UpdateLocalQueue` call you added in `default:`, because it only runs when `customLabelsChanged || clusterQueueChanged`.
