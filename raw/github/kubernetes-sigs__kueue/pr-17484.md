#### Useful notes for your reviewer
High level overview of the approach

Partial preemption consists from 2 steps: Picking victims, Scale down mechanism. Only Ray and Spark are supported in this POC

##### Picking victims
high wl - high priority workload 
wl - workload 
wls - array of wl sorted by priority (ascending) (all have minCount and part of partial preemption)
wl.minCount - minimum count of pods that we can have 
```
high wl comes -> 
evaluate lower prio wl from wls -> 

highWlRequest = high wl quota request
targets = [] # targets ie victims whom to evict to free space for high prio wl
for i in len(wls)
     # workload that could be partially evicted, 
     # we should be able to add to targets arr only a slice of this workload to not evict whole workload
    reclaimableSlice = wls[i].currCount - wls[i].minCount  
    1. if reclaimableSlice >= highWlRequest then we add to targets highWlRequest, 
    otherwise add to targets reclaimableSlice, highWlRequest -= reclaimableSlice
    if wls[i] is already reduced then we add whole wls[i] to targets ->
    after steps 1. quota is 
    enough -> break, we found quota for high wl
    not enough -> continue loop

if targets quota is not enough then high wl is pending
```
##### Scale down 
Kueue forcefully removes executor pods + lowers the workload's pod count (this reclaims quota) -> 
job runtime (spark driver) creates new pod -> 
kueue automatically gate it (here the state of workload is similar to pre state for partial scale up feature) -> 
partial scale up feature scales up the workload when quota is available

  Although the initial version of the KEP was designed this way, I think it shouldn't scale down directly to `minCount`. Preempting resources based on equal priority—distributed evenly—minimizes the impact on existing tasks; therefore, I suggest introducing a `max-reclaim-count` parameter to control this. When H1 re-enters the queue, it will trigger a full-scale preemption of L1/L2. In this case, H1 undergoes both a scale-down and a subsequent scale-up; such "jitter" is something that should be avoided.

If any loss costs about the same, e.g. a gang that restarts as a whole (a JobSet or an MPIJob), touching fewer jobs is better. For Spark, the cost grows faster than the number of executors lost, so spreading is cheaper overall:
  
  - Shuffle and cached blocks on lost executors have to be migrated or recomputed. Taking many executors from one job loses more of its data at once and leaves fewer peers to migrate to, so recomputation cascades.
  - A stage finishes with its slowest tasks: halving one job's executors roughly doubles its remaining stage time, while one executor from each of N jobs adds about 1/N to each.
  - Unless they're decommissioned gracefully, lost executors count toward `spark.executor.maxNumFailures`, so concentrating can fail a job outright.
  - The first candidates in preemption order are the same jobs every time, so concentrating keeps hitting one job among equals.
  
  So perhaps the strategy should follow the workload: spread by default for jobs that keep running with fewer Pods, like Spark, and concentrate, or preempt whole, for jobs that restart when they lose any Pod, like a JobSet or an MPIJob.
