## Description

#### What type of PR is this?

/kind feature

#### What this PR does / why we need it?

`requeueState.count` only accumulates and is only cleared when the Workload is deactivated, so with a finite `waitForPodsReady.requeuingStrategy.backoffLimitCount`, any long-lived Workload (LeaderWorkerSet, StatefulSet, serving pod groups) is eventually deactivated by PodsReadyTimeout evictions from unrelated, fully recovered incidents.

Observed in production: a serving LWS group Workload that was continuously PodsReady for 36.5 days was deactivated because ~69 timeouts from a single five-day incident weeks earlier stayed on the clock; the count is only ever compared against the lifetime limit, never reset by a recovered period. For batch Workloads the two are equivalent (Ready → Finished → deleted), which is why the semantics went unnoticed.

This PR adds the Alpha feature gate `ResetRequeueStateOnPodsReady` (default off). When enabled, once an admitted Workload holds `PodsReady=True` for at least the resolved WaitForPodsReady timeout (including the per-workload `kueue.x-k8s.io/wait-for-pods-ready` override), the whole `requeueState` (count and `requeueAt`) is cleared via the same merge-patch approach the deactivation path uses, a `RequeueStateReset` event is emitted, and a recheck is scheduled until the threshold elapses. Readiness flipping before the threshold restarts the measurement, so a flapping Workload still accumulates every timeout; deactivation of genuinely hopeless Workloads is unchanged.
