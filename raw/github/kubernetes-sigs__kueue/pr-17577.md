#### What this PR does / why we need it?

Follow-up to #17200.

- `gh pr view` didn't name the repository, so gh chose one. With `gh repo set-default` or `GH_REPO` pointing at a fork, it chose the fork, and the script stopped with `Could not resolve to a PullRequest`. A fork named `origin` with no `upstream` or `github` remote did the same. The script now passes `--repo`, like `gh pr create`.
- `--repo` uses `MAIN_REPO_ORG` and `MAIN_REPO_NAME`, which were wrong for `ssh://`, `user@`, `http://` and SSH host alias remotes, for example `/github` for `ssh://git@github.com/kubernetes-sigs/kueue.git`. They now come from the last two parts of the URL.
- `CLICOLOR_FORCE` or `GH_FORCE_TTY` made gh color its JSON, and `jq` failed with `parse error: Invalid numeric literal`. `GH_FORCE_TTY` also sent the JSON through the configured pager, so `GH_PAGER='cat -n'` broke it too. The call now sets `CLICOLOR_FORCE=0` and clears `GH_FORCE_TTY`.
- With `log.showSignature=true`, the `git log` output the script reads had signature checks in it, and they ended up in the commit message. When no commit matched the PR author's GitHub login, as in dependabot PRs, the author was read from that output too. It could then be a signature line, and `git commit` failed. These calls now pass `--no-show-signature`.
- With rerere enabled, `cherry-pick --quit` dropped rerere's state before the commit, so no resolution was ever recorded. The script now runs `git rerere` first. It also passes `--no-rerere-autoupdate`. With `rerere.autoupdate=true`, a reused resolution was staged while the pick still failed, and when that covered every conflict, the script aborted with `no conflicts to resolve`.
- `git commit -m` fails once the message reaches 128 KiB (Linux with 4 KiB pages). It is the last step, so any conflict resolution was lost with it. The message now goes through stdin.

#### Useful notes for your reviewer

I ran each case against local repositories with a stubbed gh, with `DRY_RUN` or a full run that pushes to a local fork. Each one fails on main and passes here. The cases from the #17200 reviews give the same results as before.

With real gh and `DRY_RUN`, I picked #17289 to release-0.20 and #16647, #16771 and #17118 to release-0.19, on the commits the bot used. The trees match the bot's #17512, #17225, #17341 and #17358, also with `GH_REPO` set to a fork, `CLICOLOR_FORCE=1`, and `GH_FORCE_TTY=1` with a rewriting pager.

The script is the same on release-0.19 and release-0.20, so this can be picked to both.
