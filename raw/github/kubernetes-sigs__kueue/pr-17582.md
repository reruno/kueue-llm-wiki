## Description

This is a manual cherry-pick of #16630. The bot hit conflicts on release-0.19 for this commit, and the release-0.20 pick went in as #17455.

Adjustments for this branch:

- `pkg/controller/tas/resource_flavor.go`: main also watches ResourceSlice, DeviceClass, ResourceClaim and DeviceTaintRule behind `KueueDRADeviceFeasibility`, which does not exist on release-0.19, so only the `cache.TrackInitialSync(...)` wrapper is applied.
- `test/integration/singlecluster/controller/jobs/leaderworkerset`, `.../jobs/rayclusterwebhook` and `.../scheduler/configurablepreemptions` are gone on release-0.19, so their one-line `sched.Start(ctx)` -> `mgr.Add(sched)` change goes with them. `test/integration/singlecluster/conversion/suite_test.go` exists only on this branch and needed the same conversion, because `Scheduler.Start` now blocks until the tracked sources have synced and those only start when the manager starts.

Verified locally on the release-0.19 tree: `go build ./...`, unit tests with `-race` for `./pkg/cache/scheduler/... ./pkg/scheduler/... ./pkg/controller/core/... ./pkg/controller/tas/...`, and the integration suites `singlecluster/tas` (136/136), `singlecluster/controller/core` (88/88), `singlecluster/scheduler` (136/136), `singlecluster/controller/jobs/job` (101/101), `singlecluster/controller/failover` (2/2) and `singlecluster/conversion` (2/2), all passing.

I used AI tools to help prepare this cherry-pick; I reviewed and tested the result.

/assign mimowo
/cc @dundysm

```release-note
TAS: Fixed a bug where a cold-started scheduler could admit workloads onto occupied nodes before existing ClusterQueues and their admitted Workloads were loaded into its cache. Kueue now waits for cache-filling handlers to process their initial data before scheduling.
```
