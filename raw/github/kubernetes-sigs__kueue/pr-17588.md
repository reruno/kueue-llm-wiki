#### What this PR does / why we need it?

Workloads could undercount Pod overhead when a PodSet already carried an `overhead` value and also named a RuntimeClass. Kueue skipped reading the RuntimeClass in that case, although the Pods created from the job could carry the class-defined overhead instead.

This always resolves the referenced RuntimeClass and merges its overhead with the PodSet's overhead per resource, keeping the larger value. It also includes `runtimeClassName` in the PodSet template equivalence check before a Job starts, so a prebuilt Workload cannot stand in for a suspended Job that uses a different RuntimeClass. Already admitted Jobs that may still have running Pods retain the previous equivalence behavior during an upgrade.

Fixes #14274

#### Useful notes for your reviewer

- The per-resource maximum is a conservative quota estimate: it preserves overhead from Pods admitted under an older, larger class configuration and accounts for a higher current class value. If existing Pods retain a lower overhead after a class increase, a requeued Workload can reserve more than those Pods consume. This deliberately prioritizes avoiding under-reservation over exact accounting of mixed Pod generations.
- Pod-group role verification preserves any overhead already recorded in the PodSet template over the current RuntimeClass overhead so a later class increase cannot allow an oversized replacement through. When the template did not record the overhead used at admission, a RuntimeClass update may keep a valid Pod gated; this limitation is documented in `validatePodsBeforeUngating`.
- The role check intentionally uses raw Pod resources; admission ResourceUsage can contain resource transformations and cannot be compared directly with those requests.
- An upgrade can expose a RuntimeClass mismatch in an existing admitted Job/Workload pair. While the Job is unsuspended or still has active Pods, equivalence ignores only the newly compared RuntimeClass name; other PodSet differences remain checked. This avoids finishing its Workload and releasing quota while Pods may still run. Suspended Jobs with no active Pods are checked strictly.
- Regression tests cover lower, higher, and mixed overhead values, RuntimeClass template equivalence, rejecting oversized replacements after class increases, and allowing Pods within the original role after increases or decreases.
- An earlier implementation in #14289 was closed while this code area was being reworked; this version is based on the current effective-resource implementation.

### Comment by [@sheldon-lang](https://github.com/sheldon-lang) — 2026-10-22T11:31:16Z

@henry3260 Yes, that scenario can over-reserve: existing Pods retain their admission-time overhead, while a requeued Workload uses the per-resource maximum of its PodSet overhead and the current RuntimeClass overhead. This is a conservative estimate intended to avoid under-reservation; it is not exact accounting across old and new Pod generations. I've made that tradeoff explicit in the PR description.

While tracing this, I also found and fixed a related ungating regression in 9ace0fb314272e1c69ddd4724fd161f2914dc529: increasing the live class overhead could raise the validation bound for a replacement Pod even though the group's existing reservation had not increased. Pod-group validation now preserves any nonempty overhead already recorded in the PodSet as the role bound. This keeps the pre-existing validation behavior; quota estimation still uses the maximum. We cannot substitute admission ResourceUsage directly for raw Pod requests because it can contain resource transformations.

Added regression cases for rejecting oversized replacements after an increase, allowing Pods within the original role, and preserving the original overhead after a decrease. The rejection case fails before the fix and passes afterward. The five relevant package test suites and golangci-lint v2.14.0 pass locally.
