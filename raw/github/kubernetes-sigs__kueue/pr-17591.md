#### What this PR does / why we need it?

RayCluster's legacy `status.state` can stay unready while workers are starting or waiting for scale-up quota, even when the head is ready. It can also retain an earlier `ready` value after the head becomes unready.

For example, an elastic RayCluster can encounter this sequence:

1. Create a RayCluster with one head Pod and one worker Pod. The initial Workload slice is admitted.
2. The head becomes ready, but the initial worker is not ready yet. The user can already be using the head as a devbox.
3. The user submits a Ray job that triggers autoscaling to 16 workers before the initial worker becomes ready.
4. The initial worker then becomes ready, but the 15 additional workers remain scheduling-gated while the scale-up Workload waits for quota.
5. `status.state` still has not reached `ready`: the cluster never had all desired Pods ready together before scaling, and the gated workers now prevent that first transition.
6. The initial admitted Workload slice remains `PodsReady=False` and eventually receives a `PodsReadyTimeout` eviction, which can suspend the RayCluster and delete the head the user is working on.

Add the Beta `RayClusterHeadPodReady` feature gate, enabled by default. When enabled, `RayCluster.PodsReady()` uses `HeadPodReady=True` for all RayClusters, regardless of elastic-job annotations. Missing, False, and Unknown head conditions are treated as unready even if the legacy cluster state is `ready`. When disabled, readiness continues to use `status.state == ready`.

#### Useful notes for your reviewer

- Known limitation: when a pending replacement becomes the reconciliation target, the retained admitted Workload can still miss readiness updates and hit `PodsReadyTimeout`. This PR alone does not fix that scenario; the status-update path needs a separate follow-up.
- Related: #17589 contains the retained-Workload status update.

AI assistance: OpenAI Codex assisted with the implementation, tests, and this PR description.

```release-note
RayCluster: Added the Beta RayClusterHeadPodReady feature gate, enabled by default. PodsReady checks now use head readiness so unready workers do not block readiness of a usable head. Disable the gate to restore readiness checks based on the cluster state.
```

## AI summary

With the `RayClusterHeadPodReady` feature gate enabled, Kueue determines `RayCluster` readiness from the `HeadPodReady` condition for all RayClusters. A ready head pod counts as ready even when workers are unready; a missing, false, or unknown condition counts as unready. With the gate disabled, Kueue continues to use `status.state`. The gate requires KubeRay v1.3.0 or later.

### Suggested release note

RayCluster: Fixed a bug where cluster state could misreport readiness while a RayCluster head pod was ready or unready. Kueue now uses the `HeadPodReady` condition to determine readiness. This behavior is gated by `RayClusterHeadPodReady`.
