#### What this PR does / why we need it?

When an elastic job scales up, Kueue creates a replacement Workload slice. While that slice waits for quota, the job reconciler writes the `PodsReady` condition on the slice it selects, which is the pending replacement slice. The admitted slice keeps a stale `PodsReady=False`, and the workload controller evicts it with `PodsReadyTimeout`, even after its Pods become ready.

For example, an elastic RayCluster can encounter this sequence:

1. Create a RayCluster with one head Pod and 0 worker Pods. The initial Workload slice is admitted.
2. The autoscaler scales up to 1 worker before the head Pod becomes ready.
3. The additional worker stays scheduling-gated while the scale-up Workload slice waits for quota.
4. The head becomes ready, but `PodsReady` is written only on the pending scale-up slice. The initial admitted slice keeps `PodsReady=False` and is evicted with `PodsReadyTimeout`. The RayCluster is suspended and the head the user is working on is deleted.

This PR keeps `PodsReady` on the latest admitted slice while a replacement slice is pending, as suggested in https://github.com/kubernetes-sigs/kueue/pull/17643#discussion_r4360334141. The PodsReady timeout still applies during a scale-up: if the Pods never become ready, the admitted slice is evicted as before.

Related: #17591, #16754

#### Useful notes for your reviewer

- The first version of this PR skipped the PodsReady timeout eviction while a replacement slice was pending. Based on the review, it is reverted in favor of updating the admitted slice.
- #16754 contains a similar change for its batch.Job partial scale-up fix. This PR only covers the generic part, which fixes RayCluster together with #17591 (`PodsReady()` checks only the head).
- Integration tests cover both outcomes while a scale-up slice waits for quota: the head becomes ready and the admitted slice is not evicted, and the head never becomes ready and the admitted slice is evicted.

| Integration test | With this PR | Without this PR |
|---|---|---|
| Head becomes ready | Passes | Fails: the admitted slice never reports `PodsReady=True` |
| Head never becomes ready | Passes (evicted) | Passes (evicted) |

  > I think we should rather based the check on the last admitted slice
  
  This is close to the “Update the admitted slice’s status” approach in the PR description, where I explained why I prefer the current solution.
  
  While a replacement slice is pending, the definition of “ready” may drift, and the readiness signals may conflict depending on how the integration controller is implemented. For example, before #17591, RayCluster’s PodsReady() checked whether `Status.State == rayv1.Ready`, which means that all Pods in the RayCluster became running and ready for the first time.
  
  In addition, most K8s controllers are stateless. They infer the desired state only from the current CR spec, so they don’t guarantee that the admitted slice’s readiness definition is met before the replacement slice’s. For example:
  
  * Step 1: The admitted slice’s PodSets are head: 1, cpu_worker: 2, gpu_worker: 4.
  * Step 2: Before RayCluster.Status.State is set to rayv1.Ready, the autoscaler updates the RayCluster spec.
  * Step 3: The replacement slice is created with PodSets head: 1, cpu_worker: 1, gpu_worker: 8.
  
  KubeRay doesn’t guarantee the transition current state → (1, 2, 4) → (1, 1, 8). It only works toward current state → (1, 1, 8). Because cpu_worker decreases from 2 to 1, KubeRay deletes one CPU worker right away while the new GPU workers stay gated, so the admitted slice’s (1, 2, 4) may never be reached again.
  
  With #17591, RayCluster’s PodsReady() only checks the head, so [kubernetes-sigs/kueue#16754](https://github.com/kubernetes-sigs/kueue/pull/16754)’s change to update the admitted slice would also fix the RayCluster case. However, [kubernetes-sigs/kueue#16754](https://github.com/kubernetes-sigs/kueue/pull/16754) may have issues for integrations whose readiness definitions can still drift.
  
  My suggestion would be:
  * Sol-1: Adopt this PR and delegate some of the PodsReady responsibilities to the integration controllers. For example, KubeRay implements timeout mechanisms similar to the PodsReady timeout.
  * Sol-2: Adopt #16754 and make sure that no integration’s PodsReady definition drifts. (ex: #17591)
