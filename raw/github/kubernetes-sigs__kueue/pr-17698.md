## Description

#### What type of PR is this?

/kind bug

#### What this PR does / why we need it?

Discovery checks the 128 flavor limit (#16767) but not the 64 resources per flavor limit on `status.effectiveCapacity`. Two providers can push one flavor over 64. Then the status update is rejected and the DQO keeps showing stale capacity as Computed.

This adds the same check per flavor and reports `AggregationFailed`.

Fixes #17697

#### Useful notes for your reviewer

Same approach as #16767. Tests:
- unit: 64 resources accepted, 65 fails
- integration: provider update takes a flavor from 64 to 65 resources. This is the case where the status went stale. It fails without the fix.

#### Release note

```release-note
DQO: Fixed a bug where CapacityProviders that together reported more than 64 distinct resources for a flavor could leave stale effective capacity marked as computed. Kueue now sets `EffectiveCapacityComputed=False` with reason `AggregationFailed` and clears `status.effectiveCapacity`.
```
