#### What this PR does / why we need it?

Add the `kueue-doc-writing` experimental agent skill for creating and reviewing Kueue documentation from KEPs, the current implementation, and Kubernetes and Google technical-writing guidance.

The skill covers audience and page-type selection, KEP-to-documentation mapping, Kueue/Hugo conventions, API and feature-state accuracy, safe examples, review criteria, and validation commands. The experimental skills index and website contribution guide link to the skill.

Fixes #10991

#### Useful notes for your reviewer

The skill uses current code and generated references as the source of truth when they differ from a KEP. It incorporates the review feedback:

- Use "system administrator" for the reader while preserving the existing "Batch administrator" task-navigation label.
- Distinguish generated files from hand-written reference explanations, including feature-gate tables.
- Cross-link related concepts, tasks, API/CLI references, and KEPs with descriptive text and one canonical explanation.
- Update the parent `tasks/_index.md` persona lists for pages under `manage/`, `run/`, and `dev/`.
- Show the angle-bracket `feature-state` and percent-delimited `alert` syntax.
- Document development and production Hugo checks, including the production Node dependencies.

### Comment by [@MichalZylinski](https://github.com/MichalZylinski) — 2026-10-28T10:57:42Z

Thanks @yuluo-yx for putting this together!

I ran a controlled A/B evaluation of `kueue-doc-writing` across 4 MultiKueue documentation tasks using Claude Opus 5.5 and Gemini Argon models as a reference.

The skill noticeably improved:
- Consistent `{{< feature-state >}}` shortcode usage when adding new feature gate subsections to existing task pages.
- Adherence to Kubernetes sentence-case heading conventions.
- Surfacing code-vs-KEP discrepancies as explicit open questions for maintainers (e.g., KEP-8303's unimplemented timeout configuration field and missing `patch` RBAC verbs in `create-multikueue-kubeconfig.sh`).

From the failure modes observed during those test runs, three small additions to `cmd/experimental/skills/kueue-doc-writing/SKILL.md` would make agent execution much smoother:

1. **Local Hugo validation without PostCSS (`## Validate the change`)**
   When an agent runs `hugo --source site --renderToMemory --noBuildLock` in a clean environment without `site/node_modules` installed, Hugo fails in `site/layouts/partials/head-css.html` (`postcss: file not found`) because the default environment is `production`. Passing `--environment development` skips the PostCSS pipeline and validates all Markdown/shortcodes in a few seconds. Could we add the exact command to `## Validate the change`?
   ```markdown
   - Run `hugo --environment development --source site --renderToMemory --noBuildLock`
     for a fast local shortcode and template check without requiring Node/PostCSS, or
     run `npm --prefix site ci && PATH="$PWD/site/node_modules/.bin:$PATH" hugo --source site --renderToMemory --noBuildLock`
     for a full production build check.
   ```

2. **Explicit index list in `site/content/en/docs/tasks/_index.md` (`### Front matter and navigation`)**
   Currently `SKILL.md` says:
   > Put new pages under the appropriate `site/content/en/docs` subsection and update the nearest `_index.md` when the section uses an explicit list.

   In our site layout, `site/content/en/docs/tasks/manage/`, `tasks/run/`, and `tasks/dev/` do not have their own `_index.md` files—new task pages under those subdirectories need to be added to the explicit persona lists in the parent `site/content/en/docs/tasks/_index.md` (in addition to setting `weight` in front matter). Calling out `tasks/_index.md` explicitly here will prevent agents from stopping after checking `tasks/manage/` for an `_index.md`.

3. **Delimiter syntax for `alert` vs. `feature-state` shortcodes (`### Front matter and navigation` / `### Examples and operational safety`)**
   It would help to show one-line syntax examples distinguishing `<` vs. `%` delimiters so agents do not use `{{< alert >}}` around Markdown links or code blocks:
   - `{{< feature-state state="beta" for_version="v0.20" >}}`
   - `{{% alert title="Note" color="primary" %}}...{{% /alert %}}` (use `%` delimiters so inner Markdown and links render properly)
