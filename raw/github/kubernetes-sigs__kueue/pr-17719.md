#### What this PR does / why we need it?

With `MultiKueueRayInTreeAutoscaling`, the worker-side Ray autoscaler resizes the remote RayCluster. Kueue then creates a replacement slice N for the old slice O, and the manager repoints the remote RayCluster's prebuilt-workload marker from O to N.

If the manager evicts N (for example, through preemption) after the worker admits N, which finishes O, but before the manager repoints the remote, the cluster ends up in a permanent deadlock:

- The manager eviction branch sets `DeactivationTarget` on the remote N and returns before `SyncJob`, so the remote is not repointed.
- On the next reconcile, the remote N is evicted, and the manager calls `SyncJob`. The manager RayCluster is already suspended, so the Ray adapter returns before `repointPrebuiltWorkload`. This happens on every reconcile, so the remote is never repointed.
- The worker keeps reconciling the finished slice O. It takes the Finished branch, which does not stop the job, so the worker never suspends the RayCluster. The worker pods keep running, while N is inactive and no longer counted in the worker ClusterQueue usage.
- The worker status (`state=ready`) is copied back to the manager. The manager job therefore stays active, so its quota reservation is never cleared and the remote objects are never deleted. The preemptor stays in `WaitingForPreemptedWorkloads`.

This PR keeps skipping the runtime-state write-back while the manager copy is suspended, but still repoints the remote to the current slice. The worker then reconciles the evicted N, stops the RayCluster through the normal eviction path, and the existing quota and remote cleanup paths complete. Only the current slice reaches `SyncJob`, because replaced slices and scale-ups in progress return early in `reconcileGroup`. A separate bug can repoint the remote backwards onto the replaced slice. That is fixed independently in https://github.com/kubernetes-sigs/kueue/pull/17774.

Related: no upstream issue yet; found while investigating a production incident. See also https://github.com/kubernetes-sigs/kueue/pull/17774.

#### Useful notes for your reviewer

Reproduced on kind with a manager and a worker cluster. The setup used real MultiKueue dispatch, a real Ray autoscaler scale-up from 1 to 2 workers, and real priority preemption on the manager. An API proxy held the 201 response for the replacement Workload create to pin the window between worker admission and manager repoint. No Workload status was patched by hand.

| Image | Result |
|---|---|
| upstream main `a110c02cf` | 2/2 runs leak. The remote RayCluster stays on O with `suspend=false`; 3 pods keep running; worker CQ usage is 0; manager CQ usage is 1250m. |
| main + this PR | 5/5 runs recover. The remote is repointed to N and suspended, the pods are removed, the remote RayCluster is deleted, and the preemptor is admitted. |

On a cluster that had already leaked, switching only the manager image to this PR recovered it within a few seconds. So upgrading the manager should also heal existing stuck workloads.
