#### What this PR does / why we need it?

With `MultiKueueRayInTreeAutoscaling`, a worker-side scale-up creates a replacement slice N for the old slice O. The manager repoints the remote RayCluster's prebuilt-workload marker onto the slice it reconciles. Nothing stops it from repointing backwards.

The scheduler admits N and finishes O in two separate writes. If the second write fails, or the MultiKueue reconciler has not observed it yet, O is still "not finished, holds quota" on the manager. Meanwhile the worker has already finished its copy of O. O's MultiKueue reconcile then calls `SyncJob(O)` (remote finished) and repoints the remote back to O, while N's reconcile repoints it to N:

- The remote pointer flaps between O and N for as long as O is not finished on the manager. Each time the pointer lands on O, the worker emits a `FinishedWorkload` event on the RayCluster.
- If the job is evicted on the manager during that window, the pointer freezes wherever it is. Remote RayCluster events are mapped to the workload named by the pointer, so they keep enqueueing O, which returns early once it is finished. When the pointer froze on O, the worker kept reconciling the finished O and never stopped the job. Its pods kept running, unaccounted in the worker ClusterQueue, while the manager held quota and the preemptor stayed pending.

This PR makes `repointPrebuiltWorkload` skip the repoint when the remote already points at a manager slice whose `workload-slice-replacement-for` is the reconciled slice. The repoint can still move forward, but never backwards. The check is one Get against the manager cache; it does not read from the worker cluster.

This is independent of, and complementary to, the PR related below. That PR fixes the missing forward repoint when the job is evicted before the remote was repointed. This PR fixes the backward repoint.

Related: https://github.com/kubernetes-sigs/kueue/pull/17719

#### Useful notes for your reviewer

Reproduced on kind with a manager and a worker cluster, using real MultiKueue dispatch, a real Ray autoscaler scale-up from 1 to 2 workers, and real priority preemption on the manager. To model the failed or delayed finish of O on the manager, a ValidatingAdmissionPolicy on the manager rejected Workload status writes that set `Finished=True` in the test namespace. No Workload status was patched by hand.

| Scenario | upstream main `c3313660f` | main + this PR |
|---|---|---|
| Finish of O blocked for ~40s, then unblocked | 4/4 runs: pointer flaps O↔N 56–66 times. It ends on N once O finishes. | 1/1 run: a single forward repoint O→N, no flapping. |
| Job preempted on the manager while the finish of O is blocked | 2/2 runs leak: pointer frozen on O, worker RayCluster `suspend=false`, 3 pods running, preemptor not admitted. The leak persists after the block is lifted. | 2/2 runs recover: worker pods stopped, remote RayCluster deleted, preemptor admitted. |
