#### What this PR does / why we need it?

Some controllers add volumes only to the Pods they create, so the pod template that Kueue copies into the Workload has a volumeMount without a matching volume:
- JobSet `spec.volumeClaimPolicies`
- StatefulSet and LeaderWorkerSet `volumeClaimTemplates`

When the ClusterQueue has a ProvisioningRequest admission check, the provisioning controller builds a PodTemplate from that PodSet. The API server rejects it (`template.spec.containers[0].volumeMounts[0].name: Not found`), no ProvisioningRequest is created, and the workload stays pending.

The provisioning controller now adds an emptyDir placeholder, when building the PodTemplate, for each container and init container volumeMount that has no matching volume. This is done on a deep copy, so the Workload is unchanged. Templates that are valid today come out unchanged, so the change is not feature gated.

Fixes #17601

#### Useful notes for your reviewer

Reproduction: a batch/v1 Job or a Pod can't reproduce this. The API server validates their pod templates on create, and Pod volumes are immutable. StatefulSet validation adds the volumeClaimTemplate volumes only to a copy of the template, so the persisted template keeps a mount without a volume. Kueue's StatefulSet integration copies that template into the Workload without needing the StatefulSet controller. The integration test therefore uses a StatefulSet whose container mounts a volumeClaimTemplate, and needs no extra CRDs. Without the fix it fails with the exact error from the issue. With the fix the ProvisioningRequest is created, the PodTemplate has the emptyDir placeholder, and the Workload has no volume.

Why the placeholder and not the real volumes:
- The JobSet controller creates the claim PVCs even while the JobSet is suspended. Referencing them would still tie Kueue to JobSet's `<claim>-<jobset>` naming.
- It would also bring unbound (WaitForFirstConsumer) PVC binding and zone constraints into the cluster-autoscaler simulation.
- It would leave StatefulSet and LeaderWorkerSet volumeClaimTemplates broken.
- A placeholder in the ProvisioningRequest PodTemplate fixes all integrations in one place.

Limitations:
- The emptyDir placeholder is optimistic. It adds no resource requests, and the capacity check does not model PV zone, binding or attach limits.
- The MultiKueue variant is not separately tested.

Known gaps, left for follow-ups:
- `volumeDevices` without a volume (block-mode StatefulSet or LeaderWorkerSet volumeClaimTemplates) are still rejected. An emptyDir can't back a device.
- Ephemeral containers copied into a pod-group PodSet, or into a single Pod on a Workload rebuild, are rejected in PodTemplates.

+//
+// Some controllers add such volumes only to the Pods they create, so the
+// template that Kueue copies into the Workload has the mount but not the volume:
+// JobSet spec.volumeClaimPolicies, and StatefulSet or LeaderWorkerSet
+// volumeClaimTemplates. The API server rejects a PodTemplate with such a mount.
+//
+// It is not feature gated because it only changes templates that the API server
+// would otherwise reject; valid templates are left unchanged.
+//
+// The emptyDir placeholder is optimistic: it adds no resource requests, and it
+// does not model the real volume's storage or topology constraints (PV zone,
+// binding, attach limits), so the capacity check may succeed for Pods that
+// later cannot be scheduled because of their volumes.
+func addPlaceholderVolumes(spec *corev1.PodSpec) {
+	volumes := sets.New[string]()
+	for _, v := range spec.Volumes {
+		volumes.Insert(v.Name)
+	}
+	for _, containers := range [][]corev1.Container{spec.InitContainers, spec.Containers} {
+		for _, c := range containers {
+			for _, m := range c.VolumeMounts {
+				if volumes.Has(m.Name) {
+					continue
+				}
+				volumes.Insert(m.Name)
+				spec.Volumes = append(spec.Volumes, corev1.Volume{Name: m.Name, EmptyDir: &corev1.EmptyDirVolumeSource{}})
