#### What this PR does / why we need it?

Grouped PyTorchJobs and JobSets submitted through AppWrapper can fall back to greedy TAS placement instead of index-based placement when no Pod index offset is set.

Their worker indexes start from 0 within each PodSet, but the default PodSet group offset assumes indexes continue across the group. This can produce a negative rank for the first worker and trigger greedy placement for the entire worker PodSet.

A PyTorchJob submitted through `AppWrapper` has one Master and four Workers. Both replica types belong to the same PodSet group and specify topology requirements. The PyTorchJob controller assigns these Pod indexes:

```
Master: 0
Workers: 0, 1, 2, 3
```

Kueue uses these indexes to map individual Pods to their assigned topology domains. 

However, its default PodSet group handling assumes LeaderWorkerSet indexing, where the leader has index 0 and workers start at 1. It therefore subtracts 1 from each Worker index to obtain a zero-based position within the Worker placement assignment.

With `TopologyAwareScheduling` enabled, Kueue needs an explicit zero offset to interpret these Worker indexes correctly. Before this fix, the AppWrapper integration did not supply that default. The child PyTorchJob also bypasses Kueue's direct Kubeflow job-start path, where the offset is normally defaulted. As a result, Worker 0 gets an invalid position of -1, and Kueue falls back to greedy placement for the entire Worker PodSet. The topology assignment still applies, but placement no longer follows Pod index order.

The fix defaults the Pod index offset to 0 when AppWrapper starts these grouped PyTorchJobs. It preserves explicit settings and does not change the Pods' original indexes.
