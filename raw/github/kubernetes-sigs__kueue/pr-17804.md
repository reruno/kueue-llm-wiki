#### What this PR does / why we need it?

Updates KEP-2941 (`keps/2941-DRA`) to specify that a MultiKueue manager (`ClusterQueue` configured with a MultiKueue admission check) skips Stage 2 of DRA CEL selector validation (evaluating CEL selectors against local `ResourceSlices` for device availability/cardinality) on source-less (`deviceClassMappings`) requests, matching the existing MultiKueue manager behavior for `KueueDRADeviceFeasibility` and TAS device checks.

On a MultiKueue manager without local DRA devices or `ResourceSlices`, evaluating CEL selectors against local `ResourceSlices` leaves the Workload stuck at `QuotaReserved=False` (`DRAResourcesUnresolved: 0 device(s) match in the cluster...`), preventing MultiKueue from ever dispatching the Workload to worker clusters. With this update:
- **Stage 1 (CEL syntax/type compilation)** still runs on the manager so invalid CEL expressions are rejected immediately.
- **Stage 2 (`ResourceSlice` availability check)** is skipped on the manager for source-less mappings and runs on the selected worker cluster.
- **Counter-based (`consumesCounters`) and capacity-based (`capacity.requests`) mappings** continue to read `ResourceSlices` on the manager to compute quota charges.

Part of #17769

Updated the DRA KEP to describe MultiKueue handling for CEL selectors in source-less `deviceClassMappings`. The manager compiles selectors but skips local `ResourceSlices` availability checks. Selected workers perform those checks. If no worker has matching devices, the manager may retain quota while worker copies remain `QuotaReserved=False` with reason `DRAResourcesUnresolved`.

Counter- and capacity-based mappings still use manager `ResourceSlices` to calculate quota charges. The KEP also updates its integration-test plan and implementation history. This change documents proposed behavior; it does not confirm that the behavior has shipped.
