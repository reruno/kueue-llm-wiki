## Description

#### What type of PR is this?

/kind bug

#### What this PR does / why we need it?

Block-mode volumeClaimTemplates can leave container `volumeDevices` without a matching volume in a Workload PodSet. The API server then rejects the ProvisioningRequest PodTemplate. This removes devices not backed by a PersistentVolumeClaim or Ephemeral volume from the PodTemplate copy, including init containers, while leaving the Workload unchanged. Backed devices are retained.

#17786 merged and addressed missing volumes for mounts. #17855 merged and removes ephemeral containers from these PodTemplates; #17859 merged and fills missing container images.

Fixes #18240
Related: #17601

#### Useful notes for your reviewer

- The StatefulSet integration case covers an unbacked claim-template device alongside a PVC-backed device, checking the resulting PodTemplate and original Workload. The builder unit cases cover PVC and ephemeral backing, init containers, missing volumes and emptyDir placeholders, and verify the input PodSet remains unchanged.
- The capacity check remains optimistic: it does not account for storage or topology constraints of dropped devices.
- Unit: `go test -race -count=3 ./pkg/controller/admissionchecks/provisioning` passed in the pinned environment. Integration: `INTEGRATION_TARGET=test/integration/singlecluster/controller/admissionchecks/provisioning make -j1 test-integration` passed 41 specs.
- Local `make -j1 ci-lint`, `make -j1 verify-checks`, and `make -j1 verify` passed in the pinned environment. The commit hooks passed.
- AI disclosure: the original change and this update were prepared with AI assistance.
