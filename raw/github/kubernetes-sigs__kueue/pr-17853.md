#### What this PR does / why we need it?

Follow-up to #17601 / #17786.

**Depends on #17786; review only the last commit (193d4759f).** This branch is stacked on #17786, so its first commit is #17786's. I will rebase once #17786 merges.

#17786 fixes ProvisioningRequest PodTemplates whose containers have a `volumeMount` with no volume. Block-mode volumeClaimTemplates (StatefulSet, LeaderWorkerSet) are used through `volumeDevices` instead, and those still make the PodTemplate invalid, so no ProvisioningRequest is created:

```
Error creating PodTemplate "ppt-statefulset-sts-...-ac-prov1-1-main": PodTemplate "..." is invalid: template.spec.containers[0].volumeDevices[0].name: Not found: "state"
```

An emptyDir placeholder cannot fix this. The API server accepts a device only when its volume is a PersistentVolumeClaim or Ephemeral volume (`ValidateVolumeDevices` / `isMatchedDevice`). A PVC or Ephemeral placeholder would point at a claim that doesn't exist, so the cluster-autoscaler VolumeBinding check would fail.

So this PR removes devices that are not backed by a PersistentVolumeClaim or Ephemeral volume from the PodTemplate copy only, in init and regular containers. The Workload is not changed. The rule is the API server's own rule, so templates that are valid today come through unchanged. It also covers two cases that a "drop devices whose volume is missing" rule would miss:
- one container mounts a claim and another uses it as a device, so #17786 has already added an emptyDir placeholder under that name;
- a StatefulSet template volume is overridden by a volumeClaimTemplate with the same name.

Related: #17601

#### Which issue(s) this PR fixes:
Fixes #18240

#### Useful notes for your reviewer

- Reproduction: the new integration spec "A StatefulSet uses a block volumeClaimTemplate as a volume device" uses the StatefulSet wiring from #17786. Without the fix it fails on every run with the error above. With the fix it passes 3/3. The full provisioning integration suite passes 29/29.
- Like the emptyDir placeholder in #17786, this is optimistic: the capacity check ignores the dropped device's storage and topology constraints.
- Left to the sibling follow-ups: devices in ephemeral containers, and LeaderWorkerSet envtest coverage. LWS would need the CRD and controller wiring that was taken out for JobSet in #17786; its `newPodSet` deep-copies the template the same way, and the fix sits in the shared `buildPodTemplate` path.

Proof: reproduced the failure in envtest, applied the fix, and watched the same spec pass. Unit tests, the provisioning integration suite, golangci-lint and the pre-commit checks pass.
