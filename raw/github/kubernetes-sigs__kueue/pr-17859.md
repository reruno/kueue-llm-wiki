#### What this PR does / why we need it?

KubeRay injects an autoscaler sidecar (in-tree autoscaling) and, for RayJob `submissionMode: SidecarMode`, a submitter container into the head Pod. Kueue mirrors these on the head PodSet for quota accounting, but without an image. The provisioning controller then fails to create the ProvisioningRequest PodTemplate with `template.spec.containers[N].image: Required value`, so the Workload is stuck.

This PR sets the images the way KubeRay does. The autoscaler uses `spec.autoscalerOptions.image` if set, otherwise the head Ray container image. The SidecarMode submitter uses the head Ray container image. This covers RayJob, RayCluster and RayService.

Upgrade compatibility: `raycluster.LegacySidecarImageOptions` (built on #17858's option) tolerates the legacy empty sidecar image in workload equivalence only when the Workload is admitted, its job is running, or it is prebuilt (MultiKueue worker). Other legacy Workloads mismatch and go through the normal path. Suspended Workloads without a reservation are updated in place. Suspended Workloads that hold quota but are not admitted (e.g. stuck on a Pending ProvisioningRequest check) are deleted and recreated once. Marked `TODO(#17601): remove in v0.23`.

Follow-up to #17601 / #17786.

for RayJob, RayCluster and RayService Workloads with an autoscaler or SidecarMode submitter container. Kueue now sets

ACTION REQUIRED: upgrade notes, for such Workloads created by an earlier version:
- The legacy empty sidecar image is tolerated while a Workload is admitted, while its job is running, or when it is a

  this includes every Workload with an autoscaler container. Delete a stuck one with

- MultiKueue: upgrade the worker clusters before the manager. An older worker treats Workloads from an upgraded
  manager as out of sync and does not run them.
- Downgrade: an earlier version treats non-elastic Workloads created or updated by this version as not matching their
  job. It stops their running jobs and recreates the Workloads.
