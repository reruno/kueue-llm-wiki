#### What this PR does / why we need it?

When a Workload PodSet has a container without an image, the provisioning controller can't create the ProvisioningRequest PodTemplate: the API server rejects it with `template.spec.containers[N].image: Required value`. The admission check stays `Pending` and the Workload is stuck. The Ray integration produces such PodSets. It mirrors the sidecars KubeRay injects into the head Pod, the in-tree autoscaler and the RayJob `SidecarMode` submitter, with their resources but no image.

`buildPodTemplate` now sets the fixed placeholder image `kueue.x-k8s.io/placeholder-image:placeholder` on every container and init container without an image in the PodTemplate copy, as mimowo suggested in review. This follows `addPlaceholderVolumes` from #17786. The Workload is not changed, and there is no feature gate.

#### Which issue(s) this PR fixes:
Fixes #18243

#### Useful notes for your reviewer

- Design: discussed with dkaluza in this PR's comments. This replaces the earlier approach, which set KubeRay's images on the Ray head PodSet and needed #17858, a legacy-image equivalence tolerance, and MultiKueue upgrade-order and downgrade notes. That approach is dropped; #17858 and #17860 will be closed. Quota is unaffected either way: the sidecar resources were already counted.
- An earlier revision copied another container's image from the same PodSet. Review preferred an explicit placeholder: it can be traced, and it doesn't make a sidecar look like the head container. Every empty image is now filled, including in a PodSet where no container has an image.
- Stuck Workloads recover in place. The rejected PodTemplate was never stored and no ProvisioningRequest exists, so the next reconcile builds the template again. That includes elastic slices; no Workload is recreated. Templates that were already valid don't change.
- The placeholder is never pulled. Cluster Autoscaler's `check-capacity` and `best-effort-atomic-scale-up` classes build the Pods in memory and run only scheduler PreFilter and Filter. GKE's docs say queued provisioning creates nodes without starting these Pods. KubeRay, not this template, creates the real Pod. The tag keeps the API server from defaulting `imagePullPolicy` to `Always`. One residual risk: an admission policy that matches PodTemplates and allowlists registries could reject the name. Policies that match only Pods don't see this object.
- Validation on `7b18c57a6`, rebased on `main` at `9f223b614` with no conflicts: provisioning unit tests pass; provisioning integration suite passes, including the new spec; `make verify-checks` passes. Not run locally: `make verify`, e2e.
- AI disclosure: written with AI assistance (Claude Code with a multi-model review council). All validation listed above was run locally.
