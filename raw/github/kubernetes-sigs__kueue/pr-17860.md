#### What this PR does / why we need it?

Adds provisioning admission-check integration specs for the Ray head PodSet sidecar image fix in #17859:

- `Should create the ProvisioningRequest for a RayCluster with in-tree autoscaling`
- `Should create the ProvisioningRequest for a RayJob in SidecarMode`
- `Should replace a legacy reserved Workload with an empty submitter image for a suspended RayJob`: checks that a legacy Workload which holds quota but is not admitted is deleted and recreated with the image set.

`suite_test.go` installs the Ray operator CRDs. It also adds an opt-in `runRayControllers` manager option, which sets up the RayCluster and RayJob reconcilers, webhooks and indexes.

Follow-up to #17601 / #17786.

#### Useful notes for your reviewer

- **Depends on #17859. Review only this PR's own two commits (`a3b840e9e`, `be888a7db`).**
- Without #17859, the specs fail. The ProvisioningRequest specs get `containers[1].image: Required value`, and the legacy-replacement spec times out waiting for the legacy Workload to be deleted. With #17859 they pass 3/3, three times in a row. The provisioning suite passes 30/30.
- Known non-blocking nit: the legacy Workload fixture is named `legacy`, not the generated Workload name. Because of that, the spec does not exercise the same-name delete/create path.
- Validation: golangci-lint 0 issues; prek pass; `make verify`: passed on the PR3 tip (be888a7db, covers all three PRs).
- AI disclosure: written with AI assistance (Claude Code). All validation listed above was run locally. An AI review council reviewed the stack; the round 3 feedback asked for the behavioral upgrade spec. Details are in #17859.

The new spec names the legacy Workload `legacy`, so it does not build a Workload with the name that Kueue generates for the RayJob. A Workload from an older Kueue version may carry that generated name, and this spec does not cover that case. Add a separate spec whose legacy Workload uses the generated name. The helper is `jobframework.GetWorkloadNameForOwnerWithGVK(rj.Name, rj.UID, rayv1.GroupVersion.WithKind("RayJob"))`. `provisioning_test.go` does not import `jobframework` today, so the spec file needs that import.

Do not change only the name in the existing spec. Its deletion step waits for NotFound on the legacy key. With a shared name, the replacement can be created after the old object is removed, and that poll can miss the NotFound window. In the new spec, wait until the legacy UID is gone from the namespace listing. Then check that the remaining Workload has a different UID. Keep the existing fixed-name spec unchanged.
