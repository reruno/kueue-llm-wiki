## Description

#### What type of PR is this?
/kind bug

#### What this PR does / why we need it?

When a `default` LocalQueue is created in a namespace, every update to a running (`readyReplicas > 0`) Deployment, StatefulSet or LeaderWorkerSet without the `kueue.x-k8s.io/queue-name` label is rejected. The defaulting webhook adds `queue-name: default`, and ValidateUpdate rejects adding the queue name to a running object.

This applies the default LocalQueue only when the label can still be set: on create, when the object isn't running, or when the old object already had a queue name. It's the same guard #16474 added for the default WorkloadPriorityClass.

Fixes #17863

#### Useful notes for your reviewer

- Added `jobframework.CanSetQueueName`, next to `CanSetWorkloadPriorityClassName`.
- If a running object had `queue-name: default` and an update drops it, the default is still applied, so the label is restored, as in #16474.
- The integration test is in `controller/jobs/statefulset`, not `webhook/jobs`, because the webhook only sees the default LocalQueue through the queue manager, and the webhook suite doesn't run the LocalQueue controller.
- The new unit tests and the integration test fail without the change. `controller/jobs/statefulset`, `controller/jobs/leaderworkerset` and `webhook/jobs` integration suites pass.
