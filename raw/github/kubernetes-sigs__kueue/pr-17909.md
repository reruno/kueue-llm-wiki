#### What this PR does / why we need it?

With the default configuration, the Kueue controller's `WorkloadIdentifierAnnotations` feature gate is disabled in v0.17.8 and enabled in v0.18.0. This changes where Kueue writes the group name for new Pods, from a label to an annotation.

For example, before the upgrade, a Kueue-managed `StatefulSet` named `train` in the `batch` namespace has two Pods: 
- Pod `train-0`  
- Pod `train-1`. 

Both store their group name in a label.

After upgrading Kueue, existing Pods retain their labels. If `train-1` is recreated, the replacement stores its group name in an annotation, while `train-0` still uses a label. Both Pods belong to the same Pod group.

Users then run:

```
kueuectl list pods -n batch --for pod/train-0
kueuectl list pods -n batch --for pod/train-1
```

The first command lists only `train-0` and omits `train-1`. The second lists only `train-1` and omits `train-0`. 

Both commands should list both Pods. The incomplete results can mislead users into thinking that only one Pod belongs to the Workload.

The root cause is inconsistent group membership matching between the controller and CLI. The controller reads the annotation first and falls back to the label. The CLI only matches members that use the same identifier format as the specified Pod, so it misses members that use the other format.

Good point on the tradeoff. Keeping the labelSelector for a label-only anchor pod would break mixed groups, because a label-only pod can share a group with annotation-only pods and the CLI cannot tell from the anchor pod alone.

A couple of small notes on scope: standalone pods (without a group name) still use fieldSelector instead of scanning, and group scans are scoped to the anchor pod's namespace. With WorkloadIdentifierAnnotations now Beta and enabled by default, annotation-based groups are also the default path going forward, and users with pure label-based groups can still pass `--selector` (including `kueue.x-k8s.io/pod-group-name=<group>`) to filter server-side.

`completePodSelectors` already has a short comment on why we drop the group label selector, though I'm happy to make the label-only anchor case explicit there if you'd like.
