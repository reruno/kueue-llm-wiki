#### What this PR does / why we need it?

On the manager cluster, MultiKueue emitted the `Normal` `MultiKueue` event `The workload was admitted on "<worker>"` and re-patched the admission check on every reconcile of a Workload whose remote is admitted. This happened not only when the check became `Ready` but also on periodic requeue every `workerLostTimeout` and on every Workload change.

The repeated patch was used to refresh the admission check's `LastTransitionTime`, which was "used to detect the lost worker state" (according to the comment above it). That is no longer needed as the lost worker is detected from the connection state (`admittingWorkerLostSince`).

With this PR, `syncAdmittingRemoteState` updates the admission check only when:
- The check is `Pending`, or
- The check is `Ready` but `status.ClusterName` does not match the admitting remote: if it's unset, then it gets filled. Otherwise the existing immutability error is returned.

The event now only happens when the check was not `Ready` before the patch, so filling in a missing `status.clusterName` on a `Ready` check does not emit the event again.
