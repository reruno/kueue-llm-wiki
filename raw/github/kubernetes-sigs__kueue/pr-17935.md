#### What this PR does / why we need it?

`WaitForLeaderWorkerSetAvailability` only waits for the `lws-controller-manager` Deployment to be Available. LWS v1.0.0 sets readyz to `healthz.Ping` and starts its webhook server only after the certs are ready, so both replicas can be Ready while one of them still refuses `mleaderworkerset.kb.io` calls. In both builds linked in the issue, the first LWS specs got `connection refused` from the non-leader replica, which started serving 2.5 to 4.7 seconds after the failure.

Now `WaitForLeaderWorkerSetAvailability` also calls the LWS mutating webhook path on each pod through the apiserver pod proxy, `pods/https:<pod>:9443/proxy/mutate-leaderworkerset-x-k8s-io-v1-leaderworkerset`, and waits until every pod returns success. Once the handler is registered, an empty request gets HTTP 200 with an admission error. A refused connection or a 404 fails the call.

A dry-run create through the webhook Service is not enough on 1.35 and 1.36. There `WebhookRoundTripLoadBalancing` is off by default, so the apiserver picks an endpoint when it opens a connection and then reuses that connection. Every dry-run create can then land on the replica that is already serving.

The function now takes a `*rest.Config`, so the 7 call sites pass the config of their cluster.
