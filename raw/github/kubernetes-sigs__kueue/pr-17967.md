### Comment by [@kshalot](https://github.com/kshalot) — 2026-10-30T23:17:11Z

> Why is it needed? Why WAS cannot track the victims on its own?

WAS **currently** does not guarantee a deterministic choice of victims, i.e. in cycle 1 workload A can get a different set of preemption candidates than in cycle 2 (this is an implementation detail of WAS). So we agreed to pass the **known evicted** victims so we don't needlessly extend the victim set in subsequent cycles (`scheduler-library` will prioritize those for preemptions).

How this solves the problem, in short:
1. In cycle 1 workload A chooses workload B as preemption target.
2. In cycle 2 for workload A (preemptions span multiple cycles) workload B will be part of "committed victims" which `scheduler-library` will prioritize, so it **won't non-deterministically choose workload C** as the victim.

PTAL at the "Non-deterministic node placement across scheduling cycles" section in "Risks and Mitigations" in the draft KEP (#17402).

LMK if that's clear.

  I don't love the fact that we are using pod tracker for this. Even quoting the docstring from this file:
  
  > Package podtracker maintains **event-driven Pod state for the scheduler cache**. It does not decide which Pods consume capacity or are covered by reservations.
  
  So we had a "logicless" tracking logic which now gets some imperative operations of moving stuff around between two trackers. Not only that, but IIUC tracking those preemptees is only done in the leader replica, i.e. the replica which is doing the scheduling. During failover the state will be skewed.
  
  I think the idea that we discussed this week of using `deletionTimestamp` is more robust because it can be rebuilt by informers and avoids potential edge cases like evicting a workload whose pods were not created yet. After the pods are created, they would be placed in active pods and not preempted pods. **We also get handling of evictions for free this way.**
  
  This, combined with some fallbacks to `IsEvicted` and potentially `preemptionExpectations`, should cover most of the edge cases as well.

  As for the gap mentioned by @Singularity23x0:
  
  > There is one more case, one where the workload has been preempted and is already ready to be re-admitted (evicted = false), but its old, stale pods do not have even the DeletionTimestamp yet.
  
  Yes, it exists, but it's narrower than it may sound. `Evicted` stays `True` until the Workload gets `QuotaReserved` again (because AFAICS the only place in Kueue code removing `Evicted` is [here](https://github.com/kubernetes-sigs/kueue/blob/d25654fed7f70f380f5e975ce95e5009a27041e5/pkg/workload/workload.go#L1064)). Therefore, for the gap to hit a Workload X, we'd need to observe the following timeline:
  
  1. X gets `Evicted`.
  2. Kueue calls `stopJob` [here](https://github.com/kubernetes-sigs/kueue/blob/13796bfe13a7af14bed74413026c509e9a64c938/pkg/controller/jobframework/reconciler.go#L617).
  3. The external controller for X (strictly, for its GenericJob) reacts to API updates made in step 2.
  4. Following step 3, the external controller for X makes changes leading to `.IsActive() == false` [here](https://github.com/kubernetes-sigs/kueue/blob/d25654fed7f70f380f5e975ce95e5009a27041e5/pkg/controller/jobframework/reconciler.go#L620).
  5. X's Admission is cleared.
  6. X gets `QuotaReserved` again.
  7. Following step 3, the old Pods for X get a non-zero `.DeletionTimestamp`.
  
  So we have the "Kueue chain of events" 4 -> 5 -> 6, and the "non-Kueue chain of events" 3 -> {4, 7}. The gap exists only if 5, 6 both manage to happen before 7, and only for as long as the gap between 6 and 7 lasts. This is relatively minor.
  
  While handling this gap feels desirable in the long term, I propose to postpone it because:
  
  - it's small (as argued above)
  - handling it requires increased conceptual complexity (e.g. switching from stateless to stateful approach; other ways may exist but they'd also require careful thought)
  - this will often fall into a subcase of a "fidelity gap" which we've already consciously allowed at this milestone (i.e. ignoring real Pods for a Workload X for which we've succeeded in building any virtual ones)
