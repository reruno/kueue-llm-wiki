#### What type of PR is this?

#### What this PR does / why we need it?

Fixes #17987

The queue manager currently publishes LocalQueues and ClusterQueues into its internal state before completing the initial backfill of existing child objects.

If a `client.List` call fails, the registration returns an error but leaves the queue partially initialized. A later registration attempt is rejected because the queue already exists, even though its existing Workloads or LocalQueues were not imported.

This change makes the initial registration failure-atomic for both paths.

**Changes:**

- Move the initial Workload List before publishing a LocalQueue.
- Move the initial LocalQueue List before registering a ClusterQueue and its Cohort relationship.
- Preserve existing successful backfill behavior, scheduler notifications, fair-sharing weights, metrics, and DRA handling.
- Add regression tests for injected List failures and recovery.

No API or configuration changes are introduced.

#### Useful notes for your reviewer

**Regression coverage**

Added `pkg/cache/queue/manager_backfill_retry_test.go` covering:

1. **LocalQueue registration:** Inject a one-time `WorkloadList` failure. Verify that the unsuccessful operation leaves no registered LocalQueue or ClusterQueue weight. On retry, the pre-existing pending Workload must be recovered and visible in both queue levels.

2. **ClusterQueue registration:** Register a LocalQueue containing a pending Workload, then inject a one-time `LocalQueueList` failure. Verify that no incomplete ClusterQueue or implicit Cohort remains. On retry, the existing Workload and Cohort relationship must be restored.

Both scenarios also verify that duplicate registration remains rejected after successful initialization.

**Implementation scope**

This change covers queue-manager initialization and recovery in the LocalQueue and ClusterQueue reconcilers. It does not change the separate scheduler-cache partial-registration path. No public API or configuration changes are introduced.

The tests inject List errors. These Lists use cache-backed indexes in production, and a recoverable transient failure has not yet been established. Maintainer input on that premise is welcome.

## AI summary

This PR changes LocalQueue and ClusterQueue registration in the queue manager. Before, registration published the queue first and then ran the initial backfill `List` calls. A failed `List` therefore left a partially registered queue. A retry then hit duplicate-registration rejection and did not import existing Workloads or LocalQueues.

The change does the following:

- `Manager.AddClusterQueue` lists matching LocalQueues before it registers the ClusterQueue in the hierarchy. A list error returns without registration.
- `addLocalQueueLocked` lists matching Workloads before it publishes the LocalQueue or adds it to a ClusterQueue. A list error returns without registration.
- A new method, `Manager.ClusterQueueExists(cqRef kueue.ClusterQueueReference) bool`, reports whether the hierarchy contains a ClusterQueue.
- `ClusterQueueReconciler` and `LocalQueueReconciler` use a mutex shared with their create, update, and delete event handlers. When a queue is missing from the queue manager, reconciliation rereads the object under the lock. It registers the queue only if the object is still live and still absent.
- New tests in `pkg/cache/queue/manager_backfill_retry_test.go` and `pkg/controller/core/queue_registration_retry_test.go` cover:
  - an injected one-time `List` failure;
  - a successful retry that counts existing Workloads;
  - duplicate-registration rejection after success;
  - stop, delete, and cohort-update races during paused reconciliation.

The PR does not change public APIs or configuration. It does not address the scheduler-cache registration path in `pkg/cache/scheduler/cache.go`, which a reviewer reported separately.
