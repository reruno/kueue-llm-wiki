#### What this PR does / why we need it?

Currently, a change to the `priority-boost` annotation on an admitted Workload without a `WorkloadPriorityClass` does not trigger scheduler reevaluation.
This PR updates priority-change detection to recognize changes to the `priority-boost` annotation when the PriorityBoost feature gate is enabled, while preserving the existing behavior for:                                                                                                                                                                      
   - Pod PriorityClass changes.                                                                                                                                                                                     
   - Direct `spec.priority` changes without a WorkloadPriorityClass.                                                                                                                                                
   - WorkloadPriorityClass-based priority changes.       

MultiKueue now updates a class-less remote Workload's priority in place.

**Keep the in-place priority update limited to remote specs that otherwise match.**

When `workload.PriorityChanged` returns true, this branch copies only `PriorityClassRef` and `Priority` to the remote Workload and calls `Update`. It never compares the other spec fields. With `PriorityBoost` enabled, a class-less Workload reaches this branch. If the same write also reduces a PodSet `Count` on a Workload that is not marked elastic, the webhook accepts the write and the elastic scale-down branch is skipped. The remote keeps the old `Count`. The remote boost annotation is not synchronized, so `PriorityChanged` stays true on later reconciles. The same priority-only update repeats and the remote `Count` does not converge.

Update in place only when the remaining spec already matches. Otherwise, let the existing removal path recreate the remote.
