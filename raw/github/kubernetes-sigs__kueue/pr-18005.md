## Description

#### What type of PR is this?

/kind bug

#### What this PR does / why we need it:

On Kubernetes 1.36, `MutableSchedulingDirectivesForSuspendedJobs` is beta and on by default. The API server then accepts scheduling directive changes on a suspended Job only once `status.active == 0`. `Job.Stop()` restores the PodSets info right after suspending the Job, before the job controller has deleted the Pods and updated status. So every eviction fails with `restore info: ... field is immutable` and is retried with backoff, and each retry logs the whole pod template.

This PR:
- Makes `Stop()` keep the `kueue.x-k8s.io/stopping` annotation and return without an error while `status.active > 0`. The job controller's status update (active → 0) triggers the next reconcile, which restores the PodSets info and clears the annotation.
- Reports `stoppedNow` only for the call that actually suspends the Job, so the follow-up reconcile doesn't emit a second `Stopped` event.

#### Which issue(s) this PR fixes:

Fixes #18004

#### Special notes for your reviewer:

- The three existing `TestReconciler` cases that evict a Job with `Active(10)` now expect the deferral: suspended, `startTime` reset, nodeSelector kept, stopping annotation set.
- A new case covers the follow-up reconcile: stopping annotation present, no active Pods → restore and annotation cleared.
- On clusters without the gate, the restore is delayed by one job-controller status update.
- Tested with `go test ./pkg/controller/jobs/job/ ./pkg/controller/jobframework/...`, `go vet` and `gofmt` (Go 1.27.3). Integration and e2e tests were not run locally.

#### Does this PR introduce a user-facing change?

```release-note

Kueue now waits for the Job's active Pods to terminate before restoring the PodSets info.

### Comment by [@robfischer1](https://github.com/robfischer1) — 2026-10-30T02:29:34Z

Addressed both review findings in 35ea372:

- **Deleted Workload while Pods are active:** confirmed. Path 1.1 removed the finalizer once `stopJob` returned nil, so the Workload could be gone before the restore. A new optional `JobWithPendingStop` interface lets the batch/v1 Job report a pending stop while it carries the stopping annotation, and the deleted-Workload path keeps the finalizer until the stop completes. Eviction, not-admitted and no-match callers are unchanged.
- **Stopping annotation not compared:** the reconcile test now checks the annotation explicitly, since `jobCmpOpts` ignores annotations. That exposed a second gap: when `Stop` deferred on a Job that was already suspended without the annotation, nothing marked the restore as pending. `Stop` now sets the annotation whenever it defers.

New cases cover a deleted Workload with active Pods (the finalizer is kept) and after the Pods are gone (the info is restored and the Workload released). `go test ./pkg/controller/jobframework/... ./pkg/controller/jobs/...` and `go vet` pass.

This approach introduces a bug related to job original state restoration.

Let's consider the following scenario:

1. Reconcile N (active > 0)
- `ensureOneWorkload` finds no matching Workload because the counts differ, and calls [stopJob(w)](https://github.com/kubernetes-sigs/kueue/blob/f564e2d734e6493783ee02453f79ce6a085ddd68/pkg/controller/jobframework/reconciler.go#L1270)
- `Job.Stop` suspends the Job and sets the stopping annotation. Because active > 0, it [returns nil without restoring](https://github.com/kubernetes-sigs/kueue/blob/f564e2d734e6493783ee02453f79ce6a085ddd68/pkg/controller/jobs/job/job_controller.go#L222-L236)
- [workload.Delete(w)](https://github.com/kubernetes-sigs/kueue/blob/f564e2d734e6493783ee02453f79ce6a085ddd68/pkg/controller/jobframework/reconciler.go#L1280)
 removes the finalizer and deletes the Workload. That Workload held the only copy of the original pod template

2. Reconcile N+1…N+k (active > 0)
- With no Workload left, `stopJob(nil)` is still deferred, and [handleJobWithNoWorkload waits](https://github.com/kubernetes-sigs/kueue/blob/f564e2d734e6493783ee02453f79ce6a085ddd68/pkg/controller/jobframework/reconciler.go#L2287-L2290)
 while the Job is active

3. Reconcile N+k+1 (active == 0)
- stopJob(nil) → [RestorePodSetsInfo(nil)](https://github.com/kubernetes-sigs/kueue/blob/f564e2d734e6493783ee02453f79ce6a085ddd68/pkg/controller/jobs/job/job_controller.go#L438-L441)
 restores nothing. Only the annotation is cleared.
- [constructWorkload](https://github.com/kubernetes-sigs/kueue/blob/f564e2d734e6493783ee02453f79ce6a085ddd68/pkg/controller/jobframework/reconciler.go#L2297)
 builds the new Workload from the polluted template, so `nodeSelector: {instance: on-demand}` is recorded as if the user had written it.

4. Reconcile N+M (later eviction or preemption)
- The restore reads the new Workload's polluted copy, so the injected values are never removed. The Job stays pinned to on-demand

On main, step 1 either restores successfully before the delete (gate off) or returns an error before reaching the delete (1.36+), so the original template is never lost.
