## Description

#### What type of PR is this?

/kind bug

#### What this PR does / why we need it:

On Kubernetes 1.36, `MutableSchedulingDirectivesForSuspendedJobs` is beta and on by default. The API server then accepts scheduling directive changes on a suspended Job only once `status.active == 0`. `Job.Stop()` restores the PodSets info right after suspending the Job, before the job controller has deleted the Pods and updated status. So every eviction fails with `restore info: ... field is immutable` and is retried with backoff, and each retry logs the whole pod template.

This PR:
- Makes `Stop()` keep the `kueue.x-k8s.io/stopping` annotation and return without an error while `status.active > 0`. The job controller's status update (active → 0) triggers the next reconcile, which restores the PodSets info and clears the annotation.
- Reports `stoppedNow` only for the call that actually suspends the Job, so the follow-up reconcile doesn't emit a second `Stopped` event.

#### Which issue(s) this PR fixes:

Fixes #18004

#### Special notes for your reviewer:

- The three existing `TestReconciler` cases that evict a Job with `Active(10)` now expect the deferral: suspended, `startTime` reset, nodeSelector kept, stopping annotation set.
- A new case covers the follow-up reconcile: stopping annotation present, no active Pods → restore and annotation cleared.
- On clusters without the gate, the restore is delayed by one job-controller status update.
- Tested with `go test ./pkg/controller/jobs/job/ ./pkg/controller/jobframework/...`, `go vet` and `gofmt` (Go 1.27.3). Integration and e2e tests were not run locally.

#### Does this PR introduce a user-facing change?

```release-note

Kueue now waits for the Job's active Pods to terminate before restoring the PodSets info.
```

### Comment by [@sunilmehta-si](https://github.com/sunilmehta-si) — 2026-11-02T08:25:48Z

Thanks for the fix, the diagnosis in #18004 matches what I see on 1.36 and the deferral is the right shape. Two things from reading the branch (f564e2d):

**1. A Job whose Workload gets admitted while the stop is pending stays suspended.**

While the stopping annotation is set, `IsSuspended()` returns false. In step 8 (`!IsAdmitted` → `stopJob`) the Workload is still in the queue, so the scheduler can admit it before the Pods finish terminating. On the next reconcile step 7 is skipped (the Job does not count as suspended) and step 8 sees an admitted Workload and returns "Job running with admitted workload, nothing to do". The Job keeps `spec.suspend: true` and the annotation, and the node selector is never restored.

Before this PR the suspend and the restore were two patches in one `Stop` call, so this window only opened on a failed patch. Now it spans the whole Pod termination.

Reproduced with a `TestReconciler` case on this branch: Job `Suspend(true)` + stopping annotation + `NodeSelector("provisioning","spot")`, `Active(0)`, Workload `AdmittedAt(true, now)`. After reconcile the Job still has `Suspend: &true`, the annotation and the node selector (test in the fold below).

A possible fix: finish a pending stop before the admitted check, e.g. at the top of step 7/8

```go
if jps, ok := job.(JobWithPendingStop); ok && jps.IsStopPending() {
    if err := r.stopJob(ctx, job, wl, StopReasonWorkloadEvicted /* or a dedicated reason */, "Completing a pending stop"); err != nil {
        return ctrl.Result{}, err
    }
    if jps.IsStopPending() {
        return ctrl.Result{}, nil // Pods still active, wait for the status update
    }
    // fall through: the Job is now suspended and step 7 can start it
}
```

**2. Question on the no-matching-Workload path.** `ensureOneWorkload` calls `stopJob(w)` and then deletes `w` in the same reconcile (`workload.Delete` a few lines below). The deleted-Workload guard added in this PR only covers path 1.1. What keeps `w`'s PodSetsInfo around until the deferred restore runs once `status.active` reaches 0?

  **Admitted Workload can leave a pending stop unfinished.**
  
  A Job with a pending stop reports `IsSuspended()` as false. `Stop` keeps the `kueue.x-k8s.io/stopping` annotation while `status.active` is greater than zero.
