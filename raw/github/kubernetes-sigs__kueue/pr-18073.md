#### What this PR does / why we need it?
#15712 lowered `image-pushing-postsubmit` from `-j5` to `-j3`. That stopped most of the OOMs, but not all of them. On 2026-10-30, a `release-0.20` run failed. The kueue manager and kueueviz builds were both killed at almost the same moment, each while compiling `k8s.io/client-go/informers/core/v1` for s390x (`/usr/local/go/pkg/tool/linux_amd64/compile: signal: killed`). That pattern points to the OOM killer at peak memory.

With `-j3`, up to three buildx targets overlap. Each fans out over the four `PLATFORMS`, so up to twelve `go build` processes run at once. Each one sees all 32 vCPUs of the `E2_HIGHCPU_32` machine (32 GB RAM). This PR lowers the recipe to `-j2`. `helm-chart-push` is not an image build and finishes early, so in practice at most two image targets (eight `go build` processes) overlap.

There is plenty of room for the extra wall-clock time. Over the last 700 runs of `post-kueue-push-images` (2026-10-09 to 2026-10-30), builds took p50 9 min, p95 11 min and p99 12 min. The Cloud Build timeout is 50 min. In the same window, 3 of 700 runs failed. Only this one was an OOM. The other two were a metadata-service 500 during source upload and a registry 503 during push. Because the job alerts on the first failure, even a rare OOM is worth removing.

`image-pushing-periodic` is unchanged. It builds fewer targets, and `ray-project-mini` builds for only two platforms.
