#### What type of PR is this?

/kind bug

#### What this PR does / why we need it?

With `CustomMetricLabels` enabled, every series of `kueue_cohort_subtree_admitted_active_workloads` for a Cohort carried the whole subtree count, so summing a Cohort's series over-counted. The gauge now counts only the ClusterQueues whose custom label values match each series. Without custom labels the single series is unchanged.

Fixes #18060

#### Useful notes for your reviewer

Added `TestCohortAdmittedWorkloadsCustomLabelsCountMatchingClusterQueues` in `pkg/cache/scheduler/cohort_metrics_test.go`, covering two labelled ClusterQueues in one Cohort, no custom labels, a nested Cohort (ancestor counts only matching ClusterQueues), and deleting a ClusterQueue. It fails on main (each series reports the full Cohort count) and passes with the fix.

Tested locally:
- `go test ./pkg/cache/...`

### Comment by [@henry3260](https://github.com/henry3260) — 2026-11-02T06:14:15Z

> On CodeRabbit's subtree-walk note: the walk only runs when `CustomMetricLabels` is enabled, and it's bounded by the ClusterQueues under each ancestor. Keeping per-label counts on each cohort would avoid it, but they'd need updating on every admit, delete, relabel and cohort move, which is a bigger change. I'd prefer to keep this PR to the counting fix and do incremental counts in a follow-up together with the relabel handling. @henry3260 does that work for you, or would you rather have it here?

Thanks for raising this! The incremental counts can wait for a follow-up, but I think the rebuild should be handled in this PR. With nested Cohorts, every ClusterQueue update reconciles the parent Cohort, and `reportTreeAdmittedActiveWorkloads` then runs one walk per `ClusterQueue` under the cache write lock. With 500 labelled `ClusterQueues`, admitting 1000 Workloads took about 20s in my local run, versus 2.6s without the walk. Maybe we could compute per-label totals in one pass per rebuild? That brought it down to about 5.7s and needs no state kept in sync. wdyt?

### Comment by [@vshalpnjabi](https://github.com/vshalpnjabi) — 2026-11-02T14:38:34Z

**Keep a per-label admitted count on each cohort. Stop rescanning the subtree on every labelled report.**

With `CustomMetricLabels` enabled, each labelled ClusterQueue report walks the full subtree of every ancestor. The base read one cached `admittedWorkloadsCount` per ancestor. The change makes each report cost the sum of ancestor subtree sizes instead of one read per ancestor.

Two callers multiply this cost:

- `reportActiveWorkloads` runs on every workload add and delete for a labelled ClusterQueue. Each call walks every ancestor's subtree.
- `reportTreeAdmittedActiveWorkloads` calls the per-CQ report once for each ClusterQueue in the tree. In a flat Cohort with N labelled ClusterQueues, a rebuild therefore performs about N walks of about N nodes each, which is quadratic in N.

The workload add and delete paths hold the cache write lock (`pkg/cache/scheduler/cache.go:873`, `pkg/cache/scheduler/cache.go:980`), so these scans run while readers are blocked.

A per-label aggregate can be kept current with work proportional to the cohort depth. It can be updated at the same points where `admittedWorkloadsCount` changes. Each labelled report would then read the aggregate once per ancestor, as the base does for the unlabelled count. The update paths must also handle a ClusterQueue whose custom label values change.
