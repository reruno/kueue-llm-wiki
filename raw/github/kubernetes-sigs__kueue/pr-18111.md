#### What type of PR is this?

#### What this PR does / why we need it?

Right now when a DQO stops managing a ClusterQueue or Cohort, the last `effectiveQuotas` just stay there. Kueue keeps admitting against them until someone clears them by hand. That happens when the DQO is deleted, when `capacityDistribution` is removed, or when a CapacityProvider stops reporting and `Distributed` goes False. I checked the delete and provider cases on a local cluster from main.

The KEP update moves "automatic expiration of effective quota" from Alternatives into the design, as opt-in for Alpha (v0.21):
- `status.effectiveQuotas.validUntil`. When the TTL is set, the DQO sets it on each successful distribution, and renews it when at most half the TTL is left.
- `spec.capacityDistribution.effectiveQuotaTTLSeconds` on the DQO, between 60 and 604800 (7 days), with no default. Expiration is opt-in for now, and a Beta item re-evaluates a default. It is a number of seconds because `make lint-api` does not allow Duration fields.
- The ClusterQueue and Cohort controllers set `EffectiveQuotaActive`. It is `True` while the effective quota is in effect. Once `validUntil` passes it is `False`, and Kueue goes back to `spec.resourceGroups`.
- No `validUntil` means no expiry, so external controllers that don't set it keep working like today.

Part of #12382

Implementation: #18314

#### Useful notes for your reviewer

Follow-up to https://github.com/kubernetes-sigs/kueue/issues/12382#issuecomment-6374494540. Three things I'm not sure about:
- I added `conditions` to `CohortStatus`, since Cohort has none today. The other option is a marker inside `EffectiveQuotaStatus`. Any preference?
- TTL as a DQO field vs a fixed value or a Kueue config field. I went with the DQO field.
- After a provider outage, falling back to spec can give more quota than the last reported capacity. Leaving the TTL unset, or a longer TTL, is the way around it for now. Should we keep the last value and just mark it stale instead?

Code behind the "why a condition" part, since it doesn't belong in the KEP:
- The DQO reconciler returns early once the DQO is gone or being deleted, so nothing touches the quotas after that ([reconciler.go](https://github.com/kubernetes-sigs/kueue/blob/e691e542aa8737bbe1b9c1b0a31238ea4523c2ce/pkg/controller/core/dqo/reconciler.go#L204-L211)).
- The DQO watches ClusterQueues and Cohorts only for generation changes ([reconciler.go](https://github.com/kubernetes-sigs/kueue/blob/e691e542aa8737bbe1b9c1b0a31238ea4523c2ce/pkg/controller/core/dqo/reconciler.go#L93-L102)), and the Cohort update handler skips events unless spec or effective resource groups change ([cohort_controller.go](https://github.com/kubernetes-sigs/kueue/blob/e691e542aa8737bbe1b9c1b0a31238ea4523c2ce/pkg/controller/core/cohort_controller.go#L178-L184)). So a time check in the cache wouldn't fire when `validUntil` passes. Setting a condition does.
