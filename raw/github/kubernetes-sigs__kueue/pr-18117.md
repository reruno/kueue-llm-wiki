#### What this PR does / why we need it?

When any one of the manager's watches on a worker ends, `establishWatcher` marks the whole remote client disconnected. The `multikueue_cluster` reconciler then stops every other watch and rebuilds the client, and `disconnectedSince` starts the `workerLostTimeout` grace for every workload admitted to that worker. Watches end routinely, on the API server's request timeout or a proxy's idle timeout, so each worker goes through this full teardown every time the first of its watches expires. A fast reconnect hides this. A slow one evicts every admitted workload on the worker with `Admitting remote lost`, whichever kind's watch actually ended.

This PR re-opens an ended watch in place instead:

- The client stays connected and the grace period doesn't start.
- Only a watch that can't be re-opened marks the client disconnected and requests a full reconnect, which is the existing path. The loss is recorded from when the watch ended, not from when the re-open gave up, so a worker that is really gone gets exactly the grace it gets today.
- A watch opened without a `resourceVersion` replays every existing object, but not deletions made while it was down. So a re-opened `Workload` watch requeues the manager Workloads on that worker, the same resync a full reconnect does via `requeueWorkloadsForCluster`. Job-kind watches don't need this: deleting a remote job also deletes its remote Workload, and the `Workload` watch sees that.

Part of #18115

#### Useful notes for your reviewer

- **Re-opens run concurrently.** Each watch loop has its own establishing flag, so when several kinds end at once (for example on an API server restart), they re-open in parallel instead of colliding on the client-wide `watchEstablishing` flag that guards a full connect. That flag and the full-connect path are unchanged.
- **Re-open timeout and its trade-off.** A re-open uses `initialEstablishTimeout` (1m). During that window the client still reports connected while one kind's events are paused. Workload reconciles read the remote directly, so the cost is reconcile errors and backoff, not a wrong decision.
- **Ended watches are stopped.** The loop now calls `Stop()` on every ended watch. That releases the establishment context, which would otherwise pile up as children of the watch context with each in-place re-open.
- **Shutdown is unchanged.** On `StopWatchers` the watch context is cancelled and the loop returns without re-opening, so the existing join behavior is preserved, and `TestStopWatchersJoinsParkedWatcher` still passes. The reconnect integration tests break the connection by swapping the kubeconfig, which goes through the config-change path and is unaffected.
- **Intentionally not in this PR** (follow-up, see #18115): a failure scoped to one kind still disconnects the worker, whether it's a NotFound or Forbidden on re-open or an adapter watch that can't be established at connect. The comment at the connect site says that is a deliberate choice ("let's not accept this for now"), so I'd like agreement on that direction before changing it.
- **New unit tests**, which fail on `main`:
  - `TestWatchThatEndsIsReopenedWithoutDisconnecting` checks that an ended watch is re-opened, the client stays connected, and the re-opened watch is the one consumed.
  - `TestReopenedWorkloadWatchResyncsAssignedWorkloads` checks that only the manager Workloads on this worker are requeued.
  - `TestWatchThatCannotBeReopenedDisconnectsFromWhenItEnded` guards the fallback, including that the loss time is the watch's end and not the failed re-open's.
- **Testing.** `go test ./pkg/controller/admissionchecks/multikueue/` passes and `go vet` is clean. The new tests pass 30 out of 30 with `-count=30`. I couldn't run `-race` or the integration suites locally, so I'm relying on CI for those.
- This PR was developed with AI assistance. I reviewed the change and the tests.

#### Release note

```release-note
MultiKueue: a manager watch on a worker cluster that ends on its own, for example at the API server's request timeout, is now re-opened in place. Previously it marked the whole worker disconnected, restarted every watch, and started workerLostTimeout for every workload admitted to that worker.
```

  I noticed that if an exec credential plugin hangs during token refresh, this `openWatch` can stay blocked past `initialEstablishTimeout`: client-go doesn't cancel the plugin, and with an exec provider `establishWatch` waits for `Watch` to return (#14020). Since this now runs in the watcher goroutine, that has two consequences:
  
  - `StopWatchers` waits for it, and `disconnectCluster`/`stopAndRemoveCluster` call it while holding `clustersReconciler.lock`, so `controllerFor` blocks for every cluster.
  - The client stays connected with no `lostSince`, so `workerLostTimeout` doesn't start while it's blocked.
  
  A probe with a `Watch` that ignores cancellation left `StopWatchers` blocked after 5s and the client connected after 70s. 
  
  Could we make sure a stuck re-open doesn't block watcher shutdown or delay worker-loss detection?
