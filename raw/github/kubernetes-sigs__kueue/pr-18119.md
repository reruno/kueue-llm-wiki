#### What this PR does / why we need it?

Pages under `site/content/en/docs/tasks/manage/` shared several navigation weights:

| weight | siblings |
| --- | --- |
| 1 | `productization`, `enforce_job_management`, `rbac` |
| 3 | `share_quotas_across_flavors`, `monitor_pending_workloads` |
| 5 | `observability`, `setup_wait_for_pods_ready` |
| 7 | `setup_configurable_preemption`, `setup_dra` |

The children of `en/docs/tasks/manage/enforce_job_management/` also shared weight 10. The Chinese pages under `site/content/zh-CN/docs/tasks/manage/` repeat the same collisions: three top-level siblings had weight 1, two had weight 5, and the three `enforce_job_management` children all had weight 10.

Hugo breaks a weight tie by date, newest first, so the rendered order of each tied group depends on the front-matter dates. Editing a date for an unrelated reason then silently moves the page in the sidebar.

This renumbers every affected sibling to a unique multiple of 10, in the order the published sidebar renders today.

#### Useful notes for your reviewer

**Weight convention for this section:** multiples of 10, in sidebar order. A new page takes the first free slot in the range where it should appear, so adding a page does not renumber the rest.

**Order verification:** I compared the sequence above with the rendered sidebars for `main` (`https://kueue.sigs.k8s.io/docs/tasks/manage/`, `.../enforce_job_management/`, `https://kueue.sigs.k8s.io/zh-CN/docs/tasks/manage/`, and `.../zh-CN/.../enforce_job_management/`). Each new sequence is strictly increasing in the order those sidebars render today, so the rendered order is unchanged. The only intended difference is the free 110 slot after the Topology-Aware Scheduling setup page.
