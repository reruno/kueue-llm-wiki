#### What this PR does / why we need it?


When `PriorityBoost` is enabled, external controllers can update a `Workload`'s `kueue.x-k8s.io/priority-boost` annotation to apply an offset to its base priority without changing Pod priority.
This adjustment applies to both `WorkloadPriorityClass` and Kubernetes `PriorityClass`, but before this fix, boost changes on admitted `Workload` objects were handled differently:

• With `WorkloadPriorityClass`, changing the boost triggered reevaluation of pending `Workload` objects.
• With Kubernetes `PriorityClass`, the annotation update succeeded and the effective priority changed, but pending `Workload` objects were not reevaluated.

Consequently, in the Kubernetes `PriorityClass` case, pending `Workload` objects still had to wait for another scheduling event, even if a decreased or removed boost made the admitted `Workload` eligible for preemption.

This fix detects `priority-boost` annotation changes for `Workload` objects backed by Kubernetes `PriorityClass` and triggers reevaluation of pending `Workload` objects. It preserves the existing behavior of ignoring changes to Pod priority itself.

## AI summary

This change makes Kueue reevaluate pending Workloads when the priority boost of an admitted Workload changes its effective priority. The change applies when the `PriorityBoost` feature gate is enabled and the Workload uses a Pod `PriorityClass`. Before this change, changes to the boost did not trigger reevaluation for Pod `PriorityClass`-backed Workloads, which delayed preemption. Changes to the Pod priority itself do not trigger reevaluation.

Changes (3 files, +138/-1):
- `pkg/controller/core/workload_controller.go`: `WorkloadReconciler.handleUpdate` adds a trigger. When `PriorityBoost` is enabled and `podPriorityBoostChanged` returns true, the reconciler calls `QueueAssociatedInadmissibleWorkloadsAfter`, the same path used for existing priority changes. The new `podPriorityBoostChanged` helper returns true only when the old or new Workload uses a Pod `PriorityClass` and the boost (effective priority minus base priority) differs. The change also imports `pkg/util/priority`.
- `pkg/controller/core/workload_controller_test.go`: Adds `TestUpdateRequeuesForPodPriorityBoost`. The test checks that a numeric boost decrease requeues an inadmissible pending Workload. It also checks that equivalent numeric boost strings, a disabled feature gate, and a base-priority-only change do not requeue it.
- `test/integration/singlecluster/scheduler/scheduler_test.go`: Adds an integration test table for a Pod `PriorityClass` with `PriorityBoost` enabled. The admitted Workload's boost is decreased to `-100` or removed. In both cases, the test expects the admitted Workload to be preempted and the pending Workload to reserve quota after eviction finishes.

Test results for the current head are not available.

  **Sync the priority boost annotation on the in-place remote update.**
  
  When a Pod PriorityClass Workload changes both `spec.priority` and its boost annotation while quota is reserved, `workload.PriorityChanged` returns true. The remote loop then takes the in-place update branch. That branch copies only `PriorityClassRef` and `Priority`, not the boost annotation. After the update, the remote spec matches the local spec, so later reconciles do not enter this branch. The remote keeps the old boost annotation for as long as it exists. Before this change, the remote was removed and recreated, and the recreated remote received the current annotation. A worker with `PriorityBoost` enabled can then order and preempt the admitted remote using the old boost.
  
  If another non-priority spec field also differs, the in-place update repeats on each reconcile, and the remote is not recreated. The fix below resolves that case too. After the annotation is synced, the boost difference is zero, so a later reconcile follows the existing removal path for the remaining drift.
