## Description

#### What type of PR is this?

#### What this PR does / why we need it?

Updates the MultiKueue KEP so the `MultiKueueClusterProfile` feature gate has its own graduation criteria before it moves to beta. Maintainers agreed in the issue to put this in KEP-693 rather than a new KEP.

- Adds `MultiKueueClusterProfile` to `feature-gates` in `kep.yaml` and sets `latest-milestone` to `v0.21`.
- Describes how kueue-controller-manager handles each combination of gate state and ClusterProfile CRD presence, and what status a `MultiKueueCluster` using `clusterProfile` reports in each case.
- Adds two risks:
  - the upstream ClusterProfile API (KEP-4322) is still alpha
  - a CRD installed after Kueue starts is not picked up until kueue-controller-manager restarts
- Lists the existing integration and e2e coverage for the gate in the Test Plan.
- Adds alpha, beta and GA criteria for the gate.

Part of #17133

#### Useful notes for your reviewer

One beta criterion needs a decision: it proposes graduating this gate without waiting for the upstream ClusterProfile API to reach beta. In return, Kueue keeps supporting `v1alpha2` while upstream serves it, and adds a newer upstream version in a minor release before `v1alpha2` goes away. I asked this on the issue. If you'd rather wait for upstream beta, I'll change that criterion.

The state table describes current behavior on `main`. One row has only been traced through the code, not tested: gate on, CRD not installed, and a `MultiKueueCluster` that uses `clusterProfile` gets `Active=False` with reason `BadClusterProfile`. The beta criterion for a dedicated reason will come with a test for that case.

The setup guide doesn't mention the restart yet. That's listed as a beta item and will land with the default-on PR.
