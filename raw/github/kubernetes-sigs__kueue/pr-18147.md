#### What this PR does / why we need it?

The `ProvisioningRequest` concept page says Cluster Autoscaler sets `Provisioned=true` when the
nodes are ready, and that the job then starts with all its GPUs available. For
`best-effort-atomic-scale-up`, Cluster Autoscaler sets `Provisioned=true` when the node group
resize call returns, which can be before the new nodes are registered and Ready. Kueue admits on
`Provisioned=true`, so Pods can stay Pending after admission.

This corrects the concept page (the condition list and the worked example) and adds a risk to
KEP-1136, next to the existing `BookingExpired` risk: Pending Pods after admission, booking expiry
while nodes boot, and capacity that never arrives, with `WaitForPodsReady` as a mitigation.

Fixes #17156

The discussion in #17156 concluded that waiting for Ready nodes belongs in Cluster Autoscaler rather
than in Kueue. This PR covers the Kueue side by documenting the current behavior; the autoscaler change
is tracked in kubernetes/autoscaler#10430.

#### Useful notes for your reviewer

The behavior comes from Cluster Autoscaler: the `best-effort-atomic-scale-up` class sets `Provisioned=true`
right after a successful scale-up call (`pkg/provisioningrequest/besteffortatomic/provisioning_class.go`
in kubernetes-sigs/cluster-autoscaler), and Pods that consume a `ProvisioningRequest` are excluded
from regular scale-up (`pkg/processors/provreq/pods_filter.go`), so nothing retries for them if
the nodes never arrive.

An opt-in Cluster Autoscaler parameter to keep `Provisioned=false` until the nodes are Ready is
proposed in kubernetes/autoscaler#10430. The KEP mentions it as a mitigation; no Kueue change is
needed to use it, since `ProvisioningRequestConfig` parameters are passed through.

Only the latest docs are changed; the versioned `v0.19` and `v0.20` copies are left as they are.
