## Description

#### What type of PR is this?

/kind bug

#### What this PR does / why we need it?

With `TASRespectNodeAffinityPreferred` enabled, a leaf's preferred affinity score lives in domain state, which every `fillInCounts` pass clears. With `TASCacheNodeMatchResults`, a cache hit skips the simulator, so the score stayed at zero and the preference was ignored. The same Workload could then land on a different domain than on an uncached evaluation.

The cache entry now stores the scores and a hit restores them.

`fillInCounts` also added the score to the same field the simulator had just written it to, so it was counted twice. That does not reorder domains on its own, but the score is now counted once.

Fixes #14438

#### Useful notes for your reviewer

- Split out of #17051, as discussed there, so that it can be picked to release-0.20 and release-0.19.
- `TestMatchingLeavesCacheIsInvisible` gets a case where only the workers' preference separates two nodes. It fails without this fix: with the cache enabled, the Pods land on `n3` instead of the preferred `n4`.
- `TestLeaderPodSetFeasibilityKeepsWorkerAffinityScores` asserted the doubled score (14). It now expects 7.
- A `git merge-tree` check shows this applies cleanly to release-0.20. It conflicts on release-0.19, so that pick needs manual resolution.
