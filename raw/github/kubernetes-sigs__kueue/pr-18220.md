#### What this PR does / why we need it?

Adds tests for TAS behaviour documented in #17838 that had no test behind it:

- Disabling `TopologyAwareScheduling` together with every default-enabled dependent gate passes feature-gate validation.
- Implicit TAS applies only when every flavor across all `resourceGroups` sets `topologyName`; one non-TAS flavor in another group disables it.
- A PodSet whose requests span a non-TAS and a TAS `resourceGroup` is not admitted, with or without a TAS annotation.
- `podset-preferred-topology` naming a level missing from a flavor's Topology rejects that flavor and falls through to one that has it (the `preferred` counterpart of the existing `required` cases).
- A TAS annotation on the Job's top-level metadata is ignored.
- A ClusterQueue whose TAS flavor references a missing Topology stays Ready when TAS is disabled.
- CEL rejects unsetting `topologyName` and removing every `nodeLabel` on a TAS ResourceFlavor.

Also renames unconstrained-placement cases labelled `BestFit` that run under the default `TASProfileMixed` (so `LeastFreeCapacity`), and pins the `BestFit` cases to `TASProfileMixed=false` so the fallback stays covered.

Follow-up to #17838.
