## Description

#### What type of PR is this?

/kind bug

#### What this PR does / why we need it?

Part of #16840 (third case: deleting and recreating a ClusterQueue leaves a stale unadmitted series).

When a LocalQueue still points at a ClusterQueue that has been deleted, ClusterQueueNameForWorkloadWithoutLock returns the queue name together with ok set to false, and both callers in the queue manager dropped that flag. A Workload that turned Misconfigured in that window was therefore reported under the missing ClusterQueue with empty custom-label values, because CQDelete had already removed the labels. After the ClusterQueue was recreated, cleanup resolved the restored label value and missed that series, so one Workload reported both an old Misconfigured series and a current PendingEvaluation series, each at 1.

This change passes the existence flag through to the unadmitted workload metrics and reports or clears ClusterQueue-level series only when the ClusterQueue exists, which matches DeleteClusterQueue already clearing every series for that queue. The in-memory counts, the stored statuses and the LocalQueue metrics are unchanged.

The new unit test follows the controller's event order (delete the ClusterQueue, drop its custom labels, mark the Workload Misconfigured, recreate the ClusterQueue, mark it PendingEvaluation) and fails on main with the extra empty-label Misconfigured series.

#### Useful notes for your reviewer

Two things I would like your view on. First, when the old status belonged to a different ClusterQueue than the current one, the decrement assumes that old queue exists, because update cannot consult the manager for the old queue without its lock (one caller holds it, the other does not). That keeps a retargeted Workload clearing its old series, and the one case it does not cover is a Workload moved away from a deleted queue while other Workloads still sit under it. Second, AddClusterQueue does not re-report unadmitted series on recreation if no Workload status changes afterwards; that is existing behaviour and may belong with the second case in the issue, so I left it out.

Verified with go test -race on pkg/cache/queue and pkg/controller/core and golangci-lint at the pinned version. The integration suite was not run.
