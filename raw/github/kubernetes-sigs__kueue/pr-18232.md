## Description

#### What type of PR is this?

/kind bug

#### What this PR does / why we need it?

An elastic workload slice that finished with reason `WorkloadSliceReplaced` stays on the manager until it is deleted. Every reconcile of such a slice runs `readGroup`, which GETs its remote Workload from every worker, then does nothing with it, because `reconcileGroup` returns early for a replaced slice. With `ElasticJobsViaWorkloadSlices`, replaced slices can be most of the Workloads on the manager. For example, one manager had ~2,900 Workloads, 2,468 of them replaced slices.

This delays dispatching new Workloads:
1. Since #16175, every time a worker watch reconnects, the manager requeues every Workload assigned to that worker. Watches end routinely on the API server's request timeout, so on that manager each worker reconnected about every 30 minutes.
2. Each requeued Workload, including every replaced slice, runs `readGroup`. The remote GETs took about 0.23 seconds per Workload.
3. A resync of ~2,200 Workloads therefore took 8–10 minutes with one concurrent reconcile. A Workload that reserved quota during that time waited behind it, so it was dispatched to a worker up to ~10 minutes later, even with free quota.

This PR returns from `Reconcile` before `readGroup` for a replaced slice that is not being deleted.

Related: #16175

#### Useful notes for your reviewer

- Tested on a production manager with three workers. The manager had ~2,900 Workloads, 2,468 of them replaced slices. The test image was this change on top of the commit for kubernetes-sigs/kueue#18211, which is a separate change. I submitted a small CPU-only RayCluster (head and 1 worker, 1 CPU / 2Gi each) to the manager. I submitted runs 2–4 within a few seconds of a worker watch reconnect, and run 1 when no resync was running. I measured the time from `QuotaReserved` on the manager until the pods were scheduled on the worker. Quota was free in every run.

  | Run | Manager image | Activity in the reconcile queue at submit | QuotaReserved → pods scheduled |
  |---|---|---|---|
  | 1 | without this PR | idle | 8 s |
  | 2 | without this PR | resync of a worker with ~465 Workloads | 1 min 55 s |
  | 3 | without this PR | resync of a worker with ~2,200 Workloads | **10 min 30 s** |
  | 4 | with this PR | resyncs of two workers 47 s apart (~2,200 and ~160 Workloads) | **3 min 35 s** |

  In run 3, the manager first reconciled the Workload 10 min 6 s after `QuotaReserved`. The worker admitted it immediately. In run 4, replaced slices took almost no time: up to ~375 reconciles every 30 seconds, compared with ~250 per minute without this PR. The remaining delay comes from Workloads that still read remote state, and the reconciler runs one at a time. Run 4 is slower than it would normally be, because restarting the manager to deploy reset all worker watches, so two resyncs overlapped.

```release-note
MultiKueue: The manager no longer reads remote Workloads from worker clusters when it reconciles an elastic workload slice that was replaced by a newer slice. Many such slices could delay dispatching new Workloads after a manager restart or a worker reconnect.
```
