#### What this PR does / why we need it?

Since #16175, every time a worker watch reconnects, the manager requeues every Workload assigned to or nominated for that worker. Watches are opened without a timeout or resourceVersion, so the API server's routine watch expiry (`--min-request-timeout`, every 30–60 min) also counts as a reconnect. A full resync therefore runs on every worker about every 30–60 minutes.

With elastic jobs, most of these Workloads are elastic workload slices that finished because a newer slice replaced them (reason `WorkloadSliceReplaced`). The reconcile of such a slice does nothing, but requeueing it still costs a slot in the queue: `queueWorkloadEvent` resolves the slice chain and queues both the active slice and the replaced slice.

Measured on a manager with ~2,900 Workloads, of which only ~257 were unfinished and 2,468 were replaced slices:
- Before any fix, a resync of ~2,200 Workloads delayed the dispatch of a new Workload by 10 min 30 s.
- With #18232 alone (Reconcile no longer reads remote Workloads for replaced slices), the delay was 3 min 35 s, across two overlapping resyncs after a manager restart. The remaining delay is queueing and requeueing time, which this PR removes.

This PR skips replaced slices that are not being deleted in the reconnect resync. All other Workloads, including other finished Workloads, are still requeued.

Related: #16175, #18232

### Comment by [@kevin85421](https://github.com/kevin85421) — 2026-11-03T09:04:16Z

Benchmark result: this PR does not measurably improve dispatch latency in our environment.

Setup: a production manager with three workers and ~2,860 Workloads (2,469 replaced slices, ~240 unfinished), running #18232 + this PR. After a worker watch reconnected, we submitted a small RayCluster and measured `QuotaReserved` → pods scheduled on the worker.

| Build | Reserve → pods scheduled | Non-replaced reconciles ahead of it | Replaced-slice reconciles ahead of it |
|---|---|---|---|
| #18232 only (two resyncs overlapped) | 3m35s | 353 | 928 |
| #18232 + this PR (one resync) | 2m54s | 346 | 1,311 |

The ~40s difference came from the second reconcile of the test Workload: it waited 73s behind another resync in the first run and 6s in the second. It did not come from this PR. Time to the first reconcile was 2m19s vs 2m46s.

Why this PR barely helps:
- `establishWatch` opens the watch without a `ResourceVersion`, so on reconnect the API server replays a synthetic ADDED event for every remote object with the origin label, and `handleWatchEvent` queues the owning Workload. The worker still had remote Workloads for 1,311 replaced slices, so they were queued anyway through the watch. The workqueue dedupes them with the resync keys, so skipping them in the resync changes nothing.
- With #18232, reconciling a replaced slice is nearly free: the 1,272 queued ones took ~10s in total.
- The remaining delay is the ~350 non-replaced Workloads at ~0.5s each, because each reconcile reads the remote Workload from every worker with one reconcile worker. Of those, ~200 were unfinished and ~140 were finished or gone.

What might help more:
- The resync from #16175 is only needed for what the replay cannot show: remote objects deleted while disconnected. A finished Workload whose remote objects still exist is queued by the replay, and one whose remote objects are gone has nothing to sync. So the resync could skip every finished Workload that is not being deleted, which would have removed ~140 of the ~350 slow reconciles here. This relies on the watch being re-established without a `ResourceVersion`; resuming from a bookmark would change that.
- Replaced slices' remote Workloads seem to stay on the worker. Removing them would drop the replay burst.
- `groupKindConcurrency` for Workloads on the manager.

I'll keep this PR as a draft until we decide whether to repurpose it as the "skip finished Workloads" variant or close it.
