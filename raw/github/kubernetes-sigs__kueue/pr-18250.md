#### What this PR does / why we need it?

With `spec.groupIdentity: Hash` (LWS v1.0.0), LWS manages the leader Pods through a Deployment and names groups by hash. Kueue's LWS reconciler creates Workloads per ordinal group index and ungates any Pod that has no StatefulSet, so the leader Pods of a managed Hash LeaderWorkerSet ran without admission while the worker Pods stayed gated waiting for a Workload that is never created.

This PR rejects `spec.groupIdentity: Hash` in the LeaderWorkerSet webhook when a LeaderWorkerSet is created under Kueue management or an update brings it under management, following the DisaggregatedSet integration (#17675). A LeaderWorkerSet already managed with `Hash` stays updatable, since `groupIdentity` is immutable and rejecting it would block scaling and finalizer removal; its updates return a warning because its ordinal Workloads can reserve quota that no Pod uses. On update, the default LocalQueue is not applied to a Hash LeaderWorkerSet without a queue name, so an unmanaged one stays updatable after a default LocalQueue appears in its namespace; a dropped `default` label is still restored.

Related: #18479

#### Release note

```release-note
LeaderWorkerSet: Kueue now rejects `spec.groupIdentity: Hash` when a LeaderWorkerSet is created under Kueue management or an update brings it under management, for example by adding the `kueue.x-k8s.io/queue-name` label. Kueue does not support this mode: the leader Pods ran without admission while the worker Pods stayed gated.

ACTION REQUIRED: If you create LeaderWorkerSets with `spec.groupIdentity: Hash` that Kueue manages, including through a default LocalQueue or `manageJobsWithoutQueueName`, use `spec.groupIdentity: Ordinal` instead, or disable the `LeaderWorkerSetRejectGroupIdentityHash` feature gate to keep accepting them. If Kueue already manages such a LeaderWorkerSet, delete it and create it again with `spec.groupIdentity: Ordinal`; until then, its leader Pods keep running without admission.
```
