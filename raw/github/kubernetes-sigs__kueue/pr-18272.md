#### What this PR does / why we need it?

POC, opened as a draft for discussion.

Every reconcile of a MultiKueue Workload reads the remote Workload from every worker in `readGroup`, even when the Workload is already admitted on one worker and nothing changed. With many workers and many admitted Workloads, these reads dominate the cost of each reconcile. After a worker watch reconnect, the manager reconciles every Workload on that worker, and new Workloads wait behind that burst.

This PR makes the remote reads lazy:

- `readGroup` no longer reads any worker.
- `reconcileGroup` first reads only the remote Workload on the admitting worker (`status.clusterName`). When the local Workload is admitted there (the AdmissionCheck is `Ready`, it holds quota and is not finished) and the remote Workload is admitted, not finished or evicted, and its spec is in sync, the other workers are skipped.
- In every other case, and on deletion, all workers are read as before.

#### Useful notes for your reviewer

- The fast path assumes the remote Workloads on the other workers were removed when the Workload was admitted. If a remote Workload was left behind on another worker (for example, because its deletion failed), the fast path does not see it, so it is not cleaned up until the Workload leaves the fast path. Feedback is welcome on whether that is acceptable or whether the fast path needs another guard.
- Builds on the replaced-slice early return from #18232.
- Unit tests cover the fast path and the fallback to reading all workers. No integration or e2e test yet.
- Local validation: `go test ./pkg/controller/admissionchecks/multikueue/...` passes. `make verify` reports 0 golangci-lint issues; `helm-unittest-plugin` and `verify-release-utils-test` failed only because of the local environment (the helm plugin install hook failed, and the local Python is 3.9).
- This PR was written with AI assistance (Claude Code) and reviewed by me.

#### Release note

```release-note
MultiKueue: Reduced reads from worker clusters when reconciling a Workload that is already admitted on a worker, which shortens the delay for new Workloads after a worker reconnects.
```
