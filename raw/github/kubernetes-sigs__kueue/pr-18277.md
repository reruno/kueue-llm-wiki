#### What this PR does / why we need it?

After a worker watch reconnects, the manager requeues every Workload assigned to or nominated for that worker (#16175), and each reconcile reads the remote Workload from every worker in `readGroup`. Most of those Workloads are finished and their remote objects are already gone, so every read returns NotFound.

This PR skips finished Workloads that are not being deleted in that resync.

Why this helps:

- On a reconnect, the re-established watch requeues every manager Workload that still has remote objects on the worker, and the resync requeues every manager Workload assigned to or nominated for the worker.
- With this PR, a finished Workload is requeued only through the watch, that is, only while it still has remote objects to remove. Finished Workloads whose remote objects were already removed by [step 2 of `reconcileGroup`](https://github.com/kubernetes-sigs/kueue/blob/aa832b341a075112d9527d4b77a5ae31e95f589f/pkg/controller/admissionchecks/multikueue/workload.go#L536-L556) are no longer requeued, so they skip `readGroup`.

This is safe because the resync is only needed for what the re-established watch cannot show:

- `establishWatch` opens the watch without a `ResourceVersion`, so the API server replays an ADDED event for every remote object with the origin label, and `handleWatchEvent` queues the owning Workload. A finished Workload whose remote objects still exist is therefore queued anyway, and step 2 of `reconcileGroup` removes them.
- A finished Workload whose remote objects are gone has nothing left to sync.
- An unfinished Workload whose remote objects were deleted while the watch was down gets no event at all, which is what the resync is for. It still requeues those.
- Workloads being deleted are still requeued, so their finalizer is removed.

This relies on the watch being re-established without a `ResourceVersion`; resuming the watch from a bookmark would change that.

It does not help after a restart of the manager's Kueue controller: the initial list still queues every finished Workload, and each still runs `readGroup`. Reconnects happen much more often than restarts, so this PR targets them.

Related: #18232, #18233, #18236, #18272

#### Useful notes for your reviewer

An [earlier version](https://github.com/kubernetes-sigs/kueue/pull/18277/commits/8d0489371d9d0820c668fc45615c0054afc644a0) of this PR added a `RemoteObjectsRemoved` Workload condition and skipped `readGroup` for Workloads that had it. Following review, it now filters the resync instead, which avoids the API change and the extra status write.

Benchmark on a manager with three workers. After a reconnect of the farthest worker, I submitted a small RayCluster pinned to that worker and measured QuotaReserved → pods scheduled. The runs were on two days with live traffic, so the Workload mix differs between them:

| Build | Workers resyncing | Workloads reconciled (replaced slices / other) | Time |
|---|---|---|---|
| main before #18232 | 1 | ~2,250 (~1,770 / ~490) | 10 m 30 s |
| + #18232 | 2 | ~2,490 (~1,940 / ~560) | 3 m 35 s |
| + #18232 + [earlier version](https://github.com/kubernetes-sigs/kueue/pull/18277/commits/8d0489371d9d0820c668fc45615c0054afc644a0) | 2 | ~2,280 (~1,980 / ~300: ~120 finished, ~180 running) | 1 m 37 s |
| + #18232 + this PR | 1 | ~1,530 (~1,320 / ~200: 0 finished, ~200 running) | 2 m 00 s |

Counts are unique Workloads reconciled between the reconnect and the test Workload being scheduled. Replaced slices are cheap from #18232 on.

Where the time went, from the manager's reconcile logs (the MultiKueue Workload controller runs a single worker):

| | 3 m 35 s run | 1 m 37 s run | 2 m 00 s run (this PR) |
|---|---|---|---|
| Finished Workloads | ~140 s (~420 × 0.3–0.5 s) | ~0 s (~120, skipped) | 0 s (none requeued) |
| Running Workloads | ~60 s (~110 × 0.56 s) | ~85 s (~145 × 0.58 s) | ~114 s (~196 × 0.58 s) |
| Replaced slices | ~6 s | ~2 s | ~2 s |

- **Finished Workloads** read every worker and got NotFound. With the [earlier version](https://github.com/kubernetes-sigs/kueue/pull/18277/commits/8d0489371d9d0820c668fc45615c0054afc644a0) they returned before `readGroup`; with this PR they are not requeued at all. This accounts for the whole gain over the 3 m 35 s run.
- **Running Workloads** cost the same in every run: each one reads every worker plus the remote job. The worker had more running Workloads during the last run (~196 vs ~145), which is why it is slower than the 1 m 37 s run. In that run, the test Workload was nominated within 2 s, and then waited about 114 s behind the running Workloads for the reconcile that marks it Admitted.
