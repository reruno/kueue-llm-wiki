## AI summary

Kueue now rejects SparkApplications that enable dynamic allocation through `spec.sparkConf["spark.dynamicAllocation.enabled"]` when they are managed and non-elastic. The check applies on create and on update. Creating such an application fails when structured `spec.dynamicAllocation` is absent or disabled. An update fails when it newly enables the SparkConf setting. Existing managed applications may keep the setting on update. Adding a queue to an unmanaged application that already has the setting is rejected. Unmanaged applications that keep the setting are unaffected. The validation recognizes the value case-insensitively and ignores surrounding whitespace. The rejection returns a field error that names the SparkConf field. The change also adds webhook unit and integration tests and updates the SparkApplication documentation.

### Suggested release note

SparkApplication: Fixed a bug that allowed non-elastic managed SparkApplications to enable dynamic allocation through `spec.sparkConf["spark.dynamicAllocation.enabled"]`, which could bypass quota accounting. Now Kueue rejects creating or updating such applications to enable dynamic allocation through SparkConf.

### Comment by [@Pradeep39](https://github.com/Pradeep39) — 2026-11-08T13:56:02Z

@anuragdalvi - Thanks for closing this gap. Rejecting dynamic allocation for non-elastic jobs is right, since Kueue can't follow it on a static Workload, and +1 to @reruno's ratchet on update.

A concern about where this leaves users migrating existing applications to Kueue. The Spark Operator treats `sparkConf` as a first-class source: it emits `sparkConf` first and the typed fields after, so a typed field wins only when it's set, and anything it leaves unset comes from `sparkConf`. Its defaulting also honours `spark.executor.instances` and `spark.dynamicAllocation.enabled` in `sparkConf`. Kueue reads only the typed fields for these, so the same spec behaves differently once Kueue manages it:

- `sparkConf` `spark.executor.instances` without `spec.executor.instances`: Kueue sizes 0 executors, while the driver starts the configured number. That's not rejected, so it's a quota leak this PR doesn't cover.
- `spec.dynamicAllocation.enabled: true` with `minExecutors`/`maxExecutors` only in `sparkConf`: Kueue misses the bounds Spark uses.
- Dynamic allocation only in `sparkConf` is rejected for both elastic (#17127) and non-elastic jobs, though the operator runs it as is.

Would it make sense, as a follow-up, to resolve the few quota-relevant keys (`spark.executor.instances`, `spark.dynamicAllocation.{enabled,initialExecutors,minExecutors,maxExecutors}`) with the operator's precedence, as Kueue already does for cores and memory (`typedOrSparkConf`)? Specs that run under the operator would then run under Kueue without rewriting, and the two silent cases above would be sized correctly. Rejection would stay for what Kueue can't support: dynamic allocation, from either source, on a non-elastic job. Longer term, the operator could declare the effective settings in the SparkApplication status (as kubeflow/spark-operator#3290 does for executor counts), so Kueue wouldn't need to replicate the precedence.

@mimowo / @reruno  - Thoughts?
