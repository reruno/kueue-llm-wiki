#### What this PR does / why we need it?

Cherry-pick of #18277 onto release-0.19.

After a worker reconnects, the MultiKueue manager's resync no longer requeues finished Workloads that are not being deleted. The re-established watch still queues finished Workloads that have remote objects left on the worker, so those are still cleaned up. This shortens the reconcile burst that delays dispatching new Workloads after a worker reconnect.

#### Useful notes for your reviewer

Cherry-pick of commit `2f37224d50d99688c785b32f1e82627f36039600`. The production code change is identical to #18277. Conflicts and adaptations:
- `multikueuecluster.go`: import-only conflict. release-0.19 doesn't import `workloadslicing` in this file, so only the `workloadfinish` import is added.
- `multikueuecluster_test.go`: the new `TestReconnectResyncSkipsFinishedWorkloads` was adapted to release-0.19's test helpers. It gets adapters from `jobframework.GetMultiKueueAdapters` and calls `newClustersReconciler` with positional arguments, because main's `jobs.NewIntegrationManager` and functional options aren't on this branch. It also uses `reconcile.Request{NamespacedName: ...}`. The test assertions are unchanged.

Validation:
- `go build ./...`, `go vet` and `go test ./pkg/controller/admissionchecks/multikueue/...` pass.
- `TestReconnectResyncSkipsFinishedWorkloads` fails when the resync filter is disabled, and passes with it.
