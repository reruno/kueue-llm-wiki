#### What this PR does / why we need it?

Prototype. Behind a new alpha feature gate, `MultiKueueRemoteWorkloadCache` (disabled by default), MultiKueue reads remote Workloads from a per-worker informer cache instead of doing a live GET on every worker in every reconcile.

**Motivation.** `Reconcile` → `readGroup` GETs the remote Workload on every available worker, every time. The MultiKueue workload controller runs a single worker. After a worker watch reconnects (every ~30–60 min per worker), the resync requeues every active Workload. In our production setup (one hub, 3 workers, the farthest about 0.5 s RTT away), each active-Workload reconcile costs about 0.58 s, mostly these cross-cluster GETs plus the adapter's remote job reads. With about 196 active Workloads, a newly submitted Workload waits about 114 s behind the resync. We measured QuotaReserved → pods scheduled at 2m00s. Serving the Workload reads locally removes N cross-cluster round trips per reconcile, one for each worker in the MultiKueueConfig.

**Design**
- When a worker connects, `updateConfigAndRefreshWatchers` starts a controller-runtime cache for `Workload` on that worker. The cache uses `ByObject` with the manager's origin label selector, so only this manager's remote copies are kept, and strips managedFields. It runs on the watch context, so `StopWatchers` stops it. `StopWatchers` runs on disconnect, on kubeconfig or ClusterProfile change, and when the MultiKueueCluster is removed. The next connection builds a fresh informer. `StopWatchers` also drops `remoteClient.wlCache`, so a stopped store is never read.
- `readGroup` reads through `remoteClient.getRemoteWorkload`. It serves from the cache only when the informer `HasSynced`, and falls back to a live GET in every other case: not synced (startup, reconnect), a cache read error, or a pending write (next bullet).
- **Read-after-write.** The remote client is wrapped by `workloadWriteRecordingClient`. It records every Workload write this manager makes (Create, Update, Patch, Apply, Delete, and status Update/Patch/Apply) together with the resourceVersion returned. Until the cache shows that resourceVersion or a newer one (or, for a delete, shows the object gone or terminating), reads of that key go live. A failed write is recorded as "unknown outcome", which forces live reads; this also covers a Conflict caused by a stale cached base. Entries expire after 30 s.
- **Liveness.** A reconcile triggered by the existing raw remote-Workload watch can run before the informer has applied the same event. To make sure that change is not lost, the informer's own add (after the initial list), update and delete events also requeue the workload. A reconcile triggered that way is guaranteed to see the change in the cache. Initial-list adds are skipped because the raw watch replay and the reconnect resync already cover them.
- **Confirm before acting.** These decisions are confirmed with a live GET when the cached read is what triggered them, so a lagging cache can delay them but never cause them:
  - step 3: finishing the local workload from a remote `Finished`
  - step 4: Retry on a remote `Evicted`
  - step 5: updating or deleting an out-of-sync remote
  - step 6a: resetting a Ready admission check because no admitted remote is visible

  These paths are rare. The steady state (an admitted, running workload) stays on the cache.
- I kept the existing raw Workload watch rather than replacing it with informer handlers. Its end-of-stream drives disconnect detection, `workerLostTimeout` and the reconnect resync. A reflector hides disconnects by relisting internally, so changing that is a separate design discussion. The cost is one extra LIST+WATCH of origin-labeled Workloads per worker connection.

**Not covered / follow-ups**
- Remote job reads in the adapters (`ValidateRemoteObjectOwnership`, `SyncJob`, `DeleteRemoteObjectIfOwned`) and `removeObjectsOnPreviousCluster`'s GET stay live. Moving the jobs to the cache would need a per-adapter staleness analysis (create on NotFound, status copy, objects without the origin label), so I left them out. An admitted workload therefore still pays the job reads on its admitting worker, but no longer pays the Workload GET on every worker.
- Two MultiKueueClusters that point at the same worker get two independent caches and pending-write trackers. A write through one is not tracked by the other. This configuration already makes `readGroup` see the same remote object twice; with the cache, the cost is memory and a possibly stale read on the second entry, bounded by the confirm-before-acting reads.
- After a stale `NotFound`, a create can hit `AlreadyExists`. It is returned as an error (backoff retry), and the failed write forces the next read live. There is no duplicate object because remote names are fixed.
- Resource versions are compared as decimal integers, which matches etcd-backed API servers. A non-numeric resourceVersion means the read stays live until the 30 s TTL.
- No latency benchmark is included yet. Measuring it in production is the next step.
