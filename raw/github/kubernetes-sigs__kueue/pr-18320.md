#### What this PR does / why we need it?

With the AllAtOnce dispatcher, a Workload can stay pending forever if no worker cluster is connected when its first MultiKueue nomination runs. This happens, for example, when the only worker is reconnecting during the normal API-server watch expiry.

- `nominateAndSynchronizeWorkers` nominates only the connected clusters (`group.remotes`). With no connected cluster, the nomination is empty. The not-connected check loops over the nominated clusters only, so the reconcile returns without error and is not requeued.
- On reconnect, `requeueWorkloadsForCluster` only queues Workloads whose `status.clusterName` or `status.nominatedClusterNames` contain the worker. This Workload has neither, so it is never reconciled again. Its MultiKueue admission check stays `Pending` while its quota stays reserved.

Seen in production: the watches on a worker ended at 07:02:58.787 and were re-established at 07:03:00.420. A Workload first reconciled at 07:02:59.884 hung for 10+ minutes until it was deleted.

Fix: when no cluster is connected, `nominateAndSynchronizeWorkers` returns an error, so controller-runtime retries the reconcile with backoff until a cluster is connected. The next reconcile after a cluster reconnects nominates it as usual. `nominatedClusterNames` still holds only connected clusters, and the nomination is unchanged when at least one cluster is connected.

How likely this is: with several workers, AllAtOnce only hits this when every worker is disconnected at the same time, which is rare. With a single worker it happens whenever that worker reconnects. It becomes much more likely with cluster targeting by annotation (POC #14539), where a Workload is restricted to one requested cluster: it hits the same empty nomination whenever that one cluster reconnects, even if the other workers are healthy. This PR fixes the shared path, so that change can build on it.

#### Useful notes for your reviewer

**kind repro.** 1 manager and 1 worker `cn-worker`, MultiKueueConfig `[cn-worker]`, default AllAtOnce dispatcher, `batch/v1` Job without annotations. To reserve quota before the worker disconnects, as in production, the ClusterQueue also has an AdmissionCheck `hold-ac` with no controller (its `Active` condition set by hand). MultiKueue waits for it before it nominates.

Steps:
1. Submit the Job. The Workload reserves quota; `hold-ac` and the MultiKueue check are `Pending`.
2. Overwrite the worker kubeconfig Secret so it points at a wrong port. MultiKueueCluster `cn-worker` becomes `Active=False`.
3. Set `hold-ac` to `Ready` on the Workload, so MultiKueue nominates while the worker is down.
4. Restore the Secret, so `cn-worker` becomes `Active=True` again. Watch the Workload for 3 minutes.

Before (main `e691e542a`):
```
06:32:54 workload: quotaReserved=True checks=hold-ac:Pending,mk-ac:Pending nominated=
06:32:59 cn-worker Active=False mk-ac Active=False cq Active=False

06:33:10 restore worker kubeconfig -> cn-worker Active=True
06:33:20 +10s  mk-ac:Pending nominated= clusterName= admitted=False
...
06:36:13 +180s mk-ac:Pending nominated= clusterName= admitted=False
worker: No resources found
```

After (this PR):
```

16:16:01 after hold-ac Ready: nominated=, 11 reconciles in 10s (retried with backoff)
16:16:01 restore worker kubeconfig -> cn-worker Active=True

worker: workload admitted, job.batch/job-fix4 Running
```
