#### What this PR does / why we need it?

Fixes the greedy topology ungater counting the same already-ungated Pods against every occurrence of a topology domain. This can leave another Pod gated even though the admitted assignment reserves capacity for it.

**Supported upstream scenario:** `TopologyAssignment` represents the assignment through slices, and its schema permits the same domain to occur more than once, including across slices. The assignment iterator retains those occurrences. The Workload update webhook also permits topology-assignment changes on an admitted Workload when TAS is enabled. A caller authorized to update Workload status can therefore submit an equivalent reservation split across repeated-domain slices. The new API integration test exercises that accepted status encoding through the real API server and webhooks, rather than relying only on a constructed helper input.

This is distinct from normal native elastic scale-up: its `mergeTopologyAssignments` path currently coalesces equal domain IDs. This PR does **not** claim that native scale-up produces repeated domains, and it does not change validation or introduce a new producer.

The minimal reproduction is:

1. Admit two Pods on one hostname, then express the same reservation as two slices, each containing that hostname with count 1.
2. Have one already-ungated, running Pod on that hostname and one Pod still carrying the topology scheduling gate, without rank labels so that greedy placement applies.
3. Previously, both entries independently subtracted the same running-Pod count: each calculated `max(1 - 1, 0)`, so the second Pod remained gated.

The fix consumes the already-ungated count as entries are visited. The first entry accounts for the running Pod; the second then has one available slot and selects the gated Pod. This fixes progress without coalescing or reordering the assignment.

Placement remains bounded by the admitted reservation: each entry consumes at most its own count, and the existing cap on the number of remaining gated Pods is unchanged. The rank-based paths, assignment counts, slice encoding, and domain order are untouched.

#### Useful notes for your reviewer

The production change is confined to greedy ungating. Ordinary reconciliation coverage includes the two count-1 hostname entries, plus mixed compact/multiple-slice encodings with repeated entries, running counts spanning entries, a second hostname, and an excess gated Pod that must remain gated. The integration regression starts with native admission, updates the equivalent assignment through the status API, and checks that the remaining Pod is ungated while the running Pod and admitted reservation are preserved.

Both new unit cases fail without the accounting fix. The integration regression also fails without it: the status update succeeds, but the second Pod retains `kueue.x-k8s.io/topology` until the assertion times out. Restoring the fix makes the integration test pass.
