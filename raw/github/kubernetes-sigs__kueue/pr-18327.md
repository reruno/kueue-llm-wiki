#### What this PR does / why we need it?

Whole-workload eviction after a node failure tears down healthy placements as well as failed ones. For a large, long-running distributed job, re-admission may require finding capacity for the entire job again and can discard application progress since its last checkpoint. Where the job controller can create replacement Pods within the same Workload, retaining the existing admission and quota reservation while incrementally replacing failed nodes can avoid that disruption. It does not imply that surviving Pods or the application continue making progress while workers are missing.

Upstream already provides the necessary controls. This PR documents and regression-tests their composition rather than introducing a competing no-eviction feature gate, a new configuration field, or any runtime behavior change:

- Enable `TASReplaceMultipleFailedNodes` for incremental recovery of up to eight concurrently unhealthy nodes per Workload. The ninth distinct failure while all eight remain unhealthy still triggers eviction; this is not unlimited failure recovery.
- Disable `TASFailedNodeReplacementFailFast` to keep retrying when no compatible replacement fits. Multiple-node replacement does not implicitly override fail-fast. The existing useful-in-flight-eviction deferral is described separately and is not a general indefinite-retention policy.
- Set cluster-level `waitForPodsReady.recoveryTimeout: 0s` to disable recovery-timeout eviction while keeping the initial `timeout` enforced. This is explicitly global, not TAS-specific: non-TAS workloads using the cluster-level setting are affected too, and positive per-workload recovery overrides can still impose a deadline.

The documentation explains head-of-queue replacement, preserved pending unhealthy-node entries, topology constraints, PodSet-group recovery, and the possibility that an unreplaceable head blocks later nodes. It also makes the operational tradeoff explicit: unrecoverable admitted jobs may retain scarce quota and healthy-node reservations indefinitely. Preemption, queue draining, and workload deactivation remain available; operators can deactivate an affected workload or restore a positive recovery timeout and restart Kueue. Neither this recipe nor disabling a gate is presented as an immediate drain command.

Focused tests cover configuration conversion, TAS and non-TAS recovery with a zero global timeout, positive recovery deadlines, preserved initial startup deadlines, positive per-workload overrides, and unchanged admission/resource reservation/unhealthy-node bookkeeping after Workload reconciliation. Existing upstream replacement and generic Job integration tests remain responsible for actual multi-node replacement and fail-fast behavior.
