#### What this PR does / why we need it?

Keep skipped BestEffortFIFO workloads subject to the normal inadmissible-queue policy, rather than treating a scheduling skip as an admission failure.

The trigger is contention between ClusterQueue heads during one scheduling cycle. Both heads can receive an assignment against the initial snapshot, but processing one workload can consume capacity or claim preemption targets needed by another. The latter workload is marked `skipped`: it has not reached admission and no admission write failed.

Previously, `requeueAndUpdate` converted every generic result other than `notNominated` to `FailedAfterNomination`, including `skipped`. BestEffortFIFO deliberately returns `FailedAfterNomination` workloads directly to its active heap. Consequently, the skipped workload could immediately become the same queue's head again, ahead of later workloads that BestEffortFIFO is intended to let advance. Repeated contention can repeatedly select that head instead of examining the backlog.

Only generic results in the `nominated` or `assumed` state now become `FailedAfterNomination`. A skipped workload with no remaining flavor search and no intervening retry event instead enters the inadmissible stage, allowing the next workload to become the head. This restores BestEffortFIFO's ability to move past a temporarily ineligible workload; it does not change workload priority or ordering within the active heap.

Immediate retries remain important for genuine admission failures: an unsuccessful cache assumption or API admission write does not establish that the workload cannot fit, and waiting for an unrelated capacity event could leave it stranded. Both nominated failures and asynchronous assumed-workload write failures retain their immediate retry path.

#### Useful notes for your reviewer

Scope is limited to generic retry classification and regression coverage. There are no API, configuration, feature-gate, preemption-policy, or ordering changes.

The following existing behaviors are intentionally preserved:

- Explicit retry reasons, including pending preemption and Fair Sharing refill deferral, are not rewritten.
- StrictFIFO still keeps its head active according to its own queue policy.
- Remaining flavor-search progress and retry events can still make a generic requeue immediately eligible.
- Second-pass recovery still takes precedence over ordinary queue requeueing.
- Workload, quota, flavor, and related wake-up events still reactivate inadmissible workloads. The queue's existing pop/requeue cycle bookkeeping also preserves retry events that arrive while a workload is checked out.

The regression uses the real queue manager: a skipped head must enter the inadmissible stage, a lower-priority workload must become the next head, and a retry notification must make the skipped workload eligible again. The existing requeue table also covers nominated/assumed failures, StrictFIFO, pending preemption, explicit refill-style retries, and pending flavors, with unadmitted-workload observability both enabled and disabled.

Related work was checked for overlap. The merged TAS reassignment (#12419), preemption-target recomputation (#13863), and Fair Sharing refill (#13729) changes address different scheduling stages.
