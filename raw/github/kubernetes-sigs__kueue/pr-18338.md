## Description

#### What type of PR is this?

#### What this PR does / why we need it?

With `WorkloadRequestUseMergePatch` enabled, `Evict` can dereference a nil `status.admission` and panic the scheduler.

`Evict` decides whether to report the eviction from `hadAdmission`, read before the status patch. The scheduler evicts preemption targets, migration victims and Workloads that lost their TAS nodes with a retry on conflict. On a conflict the retry reads the Workload again and copies it back into `wl`. If the Workload released its quota in between, `wl.Status.Admission` is nil when `Evict` reads `wl.Status.Admission.ClusterQueue`.

`Evict` now checks the Workload that each retry reads. Without a quota reservation, it skips the patch and reports nothing, since there is nothing left to evict. `IssuePreemptions` treats such a target like one that is already evicted: it counts the preemption, releases the expectation, and records no `Preempted` event.

Related: #7035

#### Useful notes for your reviewer

The retry comes from #7933, which lets the scheduler's evictions survive a conflict with another writer. This PR keeps that and only stops a retry that reads the Workload without a quota reservation. Checking the whole eviction decision again on every retry is a larger change; the discussion in #7035 is about the same question.

The default Server-Side Apply path does not retry, so it does not reach this code.

The retry reads from the informer cache, so it can also get an older copy of a target that the scheduler admitted just before. The preemption is then skipped once and issued again in the next cycle.
