#### What this PR does / why we need it?  
  
"Should update status when ClusterQueue are forcefully deleted" admits 3 workloads to `cluster-queue.queue-controller`, then removes the ClusterQueue finalizer by hand. The `AfterEach` deletes only the LocalQueue, so the workloads stay in the API server with `status.admission.clusterQueue` still pointing at that ClusterQueue name.

When the next spec on the same process creates a ClusterQueue with the same name, `Cache.AddClusterQueue` lists workloads by the `WorkloadClusterQueueKey` index and picks up the 3 leftover admitted workloads. The ClusterQueue is then never empty, so the `resource-in-use` finalizer stays and the deletion hangs. "Should update conditions when clusterQueues that its localQueue references are updated" fails at its final step because the ClusterQueue is still there, and the `AfterEach` `ExpectObjectToBeDeleted(clusterQueue)` times out.

CI does not hit this today. It runs without `--randomize-all`, so specs inside the container keep declaration order and the forced-deletion spec always runs last. Any reordering, a new spec reusing the ClusterQueue name, or a randomized run makes it fail every time.

This PR replaces `DeleteObject(queue)` with `DeleteNamespace(ns)` in the `AfterEach`, as other suites in this package already do. `DeleteNamespace` removes the LocalQueue, the workloads and the namespace before the ClusterQueue deletion check runs.
