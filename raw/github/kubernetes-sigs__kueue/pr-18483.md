#### What this PR does / why we need it:

Updates **KEP-10076: Configurable Quota Release Strategy** for the **v0.21** release cycle based on maintainer review consensus on PR kubernetes-sigs/kueue#13308:

1. **Shift Milestone**: Moves target milestone from v0.20 to v0.21.
2. **Decouple 3 Release Strategies**: Formally defines the three distinct strategies under `.integrations.frameworkConfigs[].quotaReleaseStrategy`:
   - `OnQuotaReleased`: Releases quota immediately upon deletion initiation or status deactivation.
   - `OnTerminatingPodsBeyondGracePeriod`: Holds quota during pod termination, but releases quota once `now > deletionTimestamp + deletionGracePeriodSeconds` (preserving historical PodGroup default behavior and avoiding stuck-pod deadlocks).
   - `OnTerminal`: Strictly holds quota until all underlying pods reach a terminal phase (`Succeeded` or `Failed`), without releasing early on grace-period expiration (required for Topology-Aware Scheduling / hardware isolation).
3. **Alpha Scope**: Targets both `Pod` and `batch/v1.Job` integrations for Alpha in v0.21.
4. **Validation & Architecture**: Reflects the per-framework configuration design, defense-in-depth feature gating, and validation short-circuiting agreed upon during implementation review.

Thanks for the revision. Two points on the integration scope, with some measurements in case they help.

**TrainJob is in the Integration Release Behavior Summary but not in the Beta expansion list.** The table lists `trainer.kubeflow (trainjob)` as `OnQuotaReleased`, keyed on "Every `JobsStatus[].Active == 0`". The Beta list names JobSet, the Kubeflow jobs, Ray, AppWrapper and SparkApplication. A TrainJob runs as a JobSet, so it has the same window while evicted Pods terminate.

**JobSet's Beta criterion as written relies on a field that neither JobSet nor TrainJob reports today.** The KEP notes that the approaches for these integrations aren't finalized and will be revisited before Beta, so this is input for that. It says JobSet is fully terminated when, for all replicated jobs, `Active == 0` AND `Terminating == 0`. But `ReplicatedJobStatus` has no `terminating` field (JobSet v0.12.0, v0.13.0 and main: `ready`, `succeeded`, `failed`, `active`, `suspended`, plus the restart lists). TrainJob's `status.jobsStatus[]` mirrors it (Trainer v2.3.0, v2.4.0 and master). So `OnTerminal` for JobSet and TrainJob would need either a `terminating` count added upstream or a look at the child Jobs' own `status.terminating`. It might be worth saying in the KEP which one Beta assumes.

Measured windows under today's default, for reference (Kueue v0.20.3, v0.20.0 for the first row; Trainer v2.3.0; JobSet v0.12.0):

| Evicted workload | Cluster | Quota released | Evicted Pod kept its resources |
|---|---|---|---|
| TrainJob, preempted by a higher-priority Job | kind, Kubernetes 1.36.4 | at once: the preemptor was admitted in the same second | 31 s, until the kill at the end of the 30 s grace period |
| TrainJob gang, evicted by `waitForPodsReady` | kind, Kubernetes 1.36.4, fake GPUs | within about 5 s | 25 s more, until the kill at the end of the 30 s grace period |
