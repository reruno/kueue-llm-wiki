## Description

#### What type of PR is this?

#### What this PR does / why we need it?

The RayJob integration based `PodsReady` on the deprecated RayCluster `state` field. KubeRay sets `state` to `ready` once and never clears it after a worker is lost, so a RayJob whose worker disappeared stayed `PodsReady=True`. The `waitForPodsReady.recoveryTimeout` therefore never started and the Workload was never evicted.

This PR derives RayJob readiness from `HeadPodReady` together with `readyWorkerReplicas >= desiredWorkerReplicas`. Unlike a RayCluster devbox, a RayJob needs its workers to make progress, so a ready head alone is not enough.

The change is guarded by the new `RayJobPodsReadyFromConditions` feature gate (Beta, enabled by default), matching the gate that #17591 added for RayCluster.

Fixes #18469

#### Useful notes for your reviewer

- The gate is registered as `{Version: "0.21", Default: true, PreRelease: Beta}` in `pkg/features/kube_features.go`, and both `versioned_feature_list.yaml` files were regenerated with the feature gate generator.
- With the gate disabled, the old `state == ready` behavior is preserved exactly.
- Autoscaling RayJobs: while scaling up, the autoscaler raises `desiredWorkerReplicas` above the number of workers that are already running, so comparing against it would treat a healthy scale-up as a lost worker. When `enableInTreeAutoscaling` is set, readiness compares `readyWorkerReplicas` against `minWorkerReplicas`, the floor the cluster must keep, instead. A RayJob that drops below its floor is still reported as not ready.
- KubeRay before v1.3.0 does not publish the `HeadPodReady` condition. When the condition is absent the gate keeps the legacy `state == ready` signal, so healthy RayJobs on older operators are not reported as unready.
- Tests: unit tests cover the legacy path, the ready path, a missing worker, an unready head, the zero-worker case, a missing `HeadPodReady` condition on older KubeRay, and an autoscaling scale-up at and below the floor. Integration entries cover the legacy path and the lost-worker transition to `WorkloadWaitForRecovery`.
- Validation in this environment: `go build ./...`, `go vet ./pkg/controller/jobs/rayjob/ ./pkg/features/`, `go test ./pkg/controller/jobs/rayjob/`, and compilation of the integration package pass. `make verify` could not run here because no container runtime is available for the skillsaw lint image, and `make test-integration` did not finish because the Kubernetes 1.37 envtest binaries did not download. I ran the feature gate generator directly and it produced only the expected gate entry.

#### Release note

```release-note
RayJob: PodsReady now uses the HeadPodReady condition and the worker replica counts instead of the deprecated RayCluster state, so a RayJob that loses a worker is evicted after the recovery timeout. The behavior is gated by the new RayJobPodsReadyFromConditions feature gate, enabled by default.
```

## AI summary

RayJob readiness can use the `HeadPodReady` condition and worker replica counts instead of KubeRay’s deprecated `state` field. This lets `waitForPodsReady` detect when workers are lost and start the recovery timeout. If the feature gate is disabled or the condition is absent, RayJob uses the legacy readiness check.

The `RayJobPodsReadyFromConditions` feature gate controls this behavior. Unit and integration tests cover the legacy and condition-based paths, including worker loss.

### Suggested release note

RayJob: Fixed a bug where losing a worker could leave a RayJob Workload marked ready and prevent its recovery timeout from starting. Kueue now checks the head condition and worker replica counts. This behavior is controlled by the `RayJobPodsReadyFromConditions` feature gate.
