#### What this PR does / why we need it?

A restartable, long-running job can occupy a shared ClusterQueue's quota indefinitely, leaving other jobs of the same priority with no opportunity to run. A cumulative execution-time limit eventually deactivates the Workload, while priority boosting changes the ordering policy. Neither provides repeated, bounded admissions while retaining the original priority.

This PR adds opt-in per-admission run-duration limits behind the disabled-by-default Alpha `WorkloadRunDuration` gate:

- `ClusterQueue.spec.maximumRunDurationSeconds` supplies a positive default, captured atomically with quota reservation in `Workload.status.admission.runDurationPolicy`.
- `Workload.spec.maximumRunDurationSeconds` overrides that captured default with a shorter or longer duration. Ordinary field edits immediately recalculate the deadline from the same admission start; removing the override restores this reservation's captured default, including unlimited. ClusterQueue edits affect subsequent reservations only.
- `Workload.status.runDuration` persists the admission start and deadline for restart-safe reconciliation. Expiration requests eviction; a late extension cannot cancel an eviction or deactivation already requested.
- The job integration suspends and confirms drain before quota is released. Kueue then requeues the same active, unfinished Workload with a fresh FIFO turn and starts a new timer on readmission.

**Priority precedence is preserved.** The fresh turn gives waiting, otherwise eligible Workloads of the same priority an opportunity under ordinary priority/FIFO ordering; it does not guarantee fairness across different priorities or override resource-fit, Fair Sharing, priority boosting, or preemption policies. Suspension is not application checkpointing.

The first in-tree implementation supports batch Jobs. Registered restartable integrations can implement the optional `JobWithRunDuration` capability without a kind allowlist. Its drain contract must account for terminating and old-revision resources and preserve the same job and Workload for restart. For batch Jobs, an internal suspension-acknowledgement fence and uncached Pod checks prevent early quota release; this is not a user-facing edit protocol.

Timed admissions are initially unsupported for integrations without that capability, ConcurrentAdmission variants, ElasticJobsViaWorkloadSlices, and MultiKueue manager admissions. Unsupported timed Workloads receive an observable explanation without blocking otherwise eligible untimed queue entries; live overrides cannot bypass the unsupported-admission guard. Ordinary local admission on worker clusters is unaffected.

Both configuration fields are typed CR fields with generated schema/client surfaces. There is no additional UI, policy ConfigMap, priority mutation, or role machinery. Kubernetes RBAC governs access: any principal with Workload write permission can change its override. Existing cumulative `maximumExecutionTimeSeconds` behavior remains independent and takes precedence when both limits expire together.
