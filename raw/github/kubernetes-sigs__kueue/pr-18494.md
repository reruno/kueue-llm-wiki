## Description

#### What type of PR is this?

/kind bug

#### What this PR does / why we need it?

Flavors assigned to one PodSet are picked independently per resource group, so two of them can set the same node label key to different values. No node matches such a selector, so the workload was admitted and the conflict surfaced later: either in `podset.FromAssignment`, or as Pods that never schedule while the workload holds quota.

This rejects the combination during flavor assignment, before quota is reserved. The PodSet gets `NoMatchingFlavor` with a message naming both flavors, the key and both values, so the pending workload explains itself:

```
flavors label-x-a and label-xy-b have conflicting node labels: conflict for key=x, value1=a, value2=b
```

The check applies to admissions only. A Workload that already holds quota keeps the assignment it was admitted with: it is re-evaluated on the TAS node replacement path, and rejecting it there would evict it even when a healthy replacement node is available. A scale-up slice of an elastic Job keeps the flavors it inherits from the slice it replaces for PodSets that still have pods; a PodSet the replaced slice had no pods for can pick a new flavor with `ElasticJobsViaWorkloadSlicesFlavorChangeFromZero`, so it is still checked.

The check is behind `FailAdmissionOnConflictingFlavorLabels` (0.21, beta, enabled by default). With the gate disabled the assignment is kept and the deterministic merge from #16170 applies, so clusters that rely on the current behavior can opt out. The backports to 0.20 and 0.19 (#18369, #18370) contain only #16170 and not this gate, which keeps the released branches on the deterministic merge.

This implements item 2 of the split proposed in #16170. Issue #14409 lists an explicit refusal as an acceptable alternative to deterministic merging.

#### Tests

- `pkg/scheduler/flavorassigner`: a table case asserts that a PodSet spanning two resource groups with conflicting zone labels ends in `NoFit` with the message above and `NoMatchingFlavor`; the same case with the gate disabled succeeds and keeps both flavors. Removing the new check makes the first case fail.
- `pkg/scheduler/flavorassigner`: `TestAssignFlavorsKeepsReservedAssignmentWithConflictingFlavors` asserts that a reserved Workload with two conflicting flavors on a TAS ClusterQueue stays `Fit`. Without the admission boundary it reports `NoFit`.
- `pkg/scheduler/flavorassigner`: `TestAssignFlavorsConflictingNodeLabelsInheritedBySlice` covers a scale-up slice inheriting the conflicting pair, and a PodSet scaled to zero with and without `ElasticJobsViaWorkloadSlicesFlavorChangeFromZero`. `TestConflictingFlavorsReportsFirstKeyInSortedOrder` pins the reported key when several node label keys conflict.
- `test/integration/singlecluster/controller/jobs/job`: a Job spanning the two groups stays pending and suspended, reports the conflict in the `QuotaReserved` condition, and a second Job then gets the CPU quota, which shows the first workload never reserved any.
- `go test ./pkg/features/ ./pkg/scheduler/flavorassigner/ ./pkg/scheduler/` and the focused integration suite pass. `gofmt`, `go vet`, `make generate-featuregates` (idempotent) and `./bin/golangci-lint run --config .golangci.yaml` report no issues.

Reject PodSets whose assigned ResourceFlavors set the same node label key to different values, before quota is reserved, behind the FailAdmissionOnConflictingFlavorLabels feature gate (beta, enabled by default). Disable the gate to keep the deterministic merge introduced earlier.

## AI summary

Adds the `FailAdmissionOnConflictingFlavorLabels` feature gate. The gate is Beta and defaults to `true` from 0.21.

When the gate is enabled, flavor assignment rejects a PodSet for a new admission. The rejection occurs when the selected ResourceFlavors set different values for the same node-label key. The result is `NoMatchingFlavor`. The message names both flavors, the conflicting key, and both values. The check runs before quota is reserved.

The check does not apply in two cases:
- Workloads that already hold quota (`status.admission` is set). TAS node replacement uses this path and proceeds.
- PodSet groups that inherit flavors from a replaced workload slice.

Eligible scale-up slices with zero-count PodSets can select a new flavor. The check applies to that new selection. A conflicting choice is rejected.

With the gate disabled, the deterministic merge behavior from `#16170` remains. When several conflicts exist, the reported key is the first one in sorted order.

Changes span:
- The feature-gate registry and both feature-gate lists.
- The flavor assigner (`AssignFlavors` and `sliceFlavorsInherited`).
- Unit tests in `flavorassigner_test.go`.
- A new job integration test for a pending Job that does not reserve quota.

### Suggested release note

Scheduling: Now Kueue rejects a new admission when the selected ResourceFlavors of a PodSet set different values for the same node-label key. The workload stays pending with `NoMatchingFlavor`. The message names both flavors, the key, and both values. Kueue does not reserve quota for the rejected workload. This behavior is gated by the `FailAdmissionOnConflictingFlavorLabels` feature gate.
