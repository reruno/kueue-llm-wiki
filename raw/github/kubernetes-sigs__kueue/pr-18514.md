#### What this PR does / why we need it?
In DeepWAS, we rebuild virtual pods from scratch every cycle even when workloads haven't changed, which adds noticeable snapshot latency. Now we'll add a cache in `wasSimulatorFactory` keyed by `(UID, ResourceVersion)` so we can reuse existing pods across cycles

Here are the results I collected across preemption tests:
### [Preemption Cycle Benchmark](https://github.com/alien1403/kueue/blob/d1534fe7e1ba15331a1f52a359d18b5fab688053/pkg/scheduler/scheduler_tas_was_preemption_test.go#L805) (682 workloads, 60 victims)
| Mode | Latency | Memory | Allocations |
|---|---|---|---|
| **Classic TAS** | `18.6 ms/op` | `5.9 MB/op` | `73.0k allocs/op` |
| **DeepWAS (before)** | `117.0 ms/op` | `47.6 MB/op` | `225.5k allocs/op` |
| **DeepWAS (with cache)** | **`93.6 ms/op`** (-20%) | **`42.7 MB/op`** (-4.9 MB) | **`194.2k allocs/op`** (-31.4k allocs) |

### [Preemption Run](https://github.com/alien1403/kueue/blob/d1534fe7e1ba15331a1f52a359d18b5fab688053/pkg/scheduler/scheduler_tas_was_preemption_test.go#L630) (800 workloads, ExactQuota)
| Mode | Snapshot | Nomination | Total Decision |
|---|---|---|---|
| **Classic TAS** | `0.23 ms` | `30.29 ms` | `30.52 ms` |
| **DeepWAS (baseline)** | `41.23 ms` | `76.71 ms` | `117.94 ms` |
| **DeepWAS (with cache)** | **`20.41 ms`** (-50%) | `49.62 ms` | **`70.03 ms`** (-41%) |

### Comment by [@olekzabl](https://github.com/olekzabl) — 2026-11-13T00:52:11Z

IIUC you started caching `nil` virtual Pods following a CodeRabbit suggestion; yet, this can be problematic.

`Cache.UpdateWorkloadIfUnchanged` may change the state of a Workload in Kueue Cache without bumping the ResourceVersion.
* Some of these stories are not supported yet in WAS deep-integration (e.g. node hotswap).
* OTOH, 2-pass admission (e.g. with a ProvisioningRequest) may hit this already, as the Workload will get an Assignment twice.
  However, the first of these Assignments would then have `.TopologyAssignment == nil`, and consequently our virtual Pods being nil.
  Hence, by skipping caching of nil virtual Pods, we can easily win correctness for the current scope of integration.

Proposal for now:
1. Stop caching `nil` virtual Pods.
   (Caveat: don't just ignore them; actively invalidate old cached VPs whenever seeing `nil`. This may matter in [this case](https://github.com/kubernetes-sigs/kueue/blob/70fe0324827a95774682e14c72d0ad7ff91e6777/pkg/scheduler/scheduler.go#L1156-L1157) - when an error [in `patchWorkloadAdmission`](https://github.com/kubernetes-sigs/kueue/blob/70fe0324827a95774682e14c72d0ad7ff91e6777/pkg/scheduler/scheduler.go#L1126) leads to a rollback in cache, from a non-empty `.TopologyAssignment` back to a `nil` one)
2. Leave a TODO that more fixes (e.g. explicit invalidation) will be needed once we come to node hotswap.
