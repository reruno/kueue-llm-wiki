#### What this PR does / why we need it?


Suppose `MultiKueueConfig` lists two worker clusters, and the task is running on `worker-a`:

```
apiVersion: kueue.x-k8s.io/v1beta2
kind: MultiKueueConfig
metadata:
  name: multikueue-config
spec:
  clusters:
  - worker-a
  - worker-b
```

When a network interruption disconnects `worker-a` from the manager, the original task continues running there. After the timeout, the manager evicts the corresponding local `Workload`. Because `worker-a` is still in the configuration, Kueue assumes normal reconciliation will handle cleanup and prematurely drops the pending cleanup record. However, the cluster is still unreachable, so cleanup has not actually happened.

The administrator then removes `worker-a` from `MultiKueueConfig.spec.clusters` to stop dispatching tasks to it, but retains its `MultiKueueCluster` and valid access credentials. The task is subsequently dispatched to `worker-b`.
After `worker-a` reconnects, Kueue can still access it but no longer cleans up the original task. If neither copy has finished, the same task runs on both clusters.

The fix retains pending cleanup records across disconnections and deletion failures. If the workload is re-admitted on the same worker cluster, it clears only the earlier record and preserves any record from a newer eviction.
