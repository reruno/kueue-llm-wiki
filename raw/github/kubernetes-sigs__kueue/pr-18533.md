#### What this PR does / why we need it?

A Workload whose ResourceClaimTemplate uses a CEL selector was marked inadmissible when the cluster had fewer matching devices in ResourceSlices than the claim requested. With a ProvisioningRequest admission check and a node pool at zero nodes, there are no ResourceSlices yet, so the Workload never reserved quota, no ProvisioningRequest was created, and the pool never scaled up.

The workload controller now skips the present-device count when the ClusterQueue has a ProvisioningRequest admission check, the same way #17916 skips it for MultiKueue. CEL compilation still runs first, so an invalid selector is still rejected. If no node pool can supply the devices, the ProvisioningRequest check moves to Retry or Rejected as it does for other resources.

Fixes #18524

#### Useful notes for your reviewer

`hasMultiKueueAdmissionCheck` is renamed to `skipDRADeviceAvailabilityCheck`, since it now covers both controllers.

New `TestReconcileDRA` cases in `pkg/controller/core/workload_controller_dra_test.go`:
- valid CEL, zero slices, ProvisioningRequest check: queued (fails on main with "insufficient matching devices", passes with the fix)
- valid CEL, zero slices, no admission check: still inadmissible
- invalid CEL with a ProvisioningRequest check: still inadmissible
- MultiKueue: unchanged
- 2 requested, 1 matching device, ProvisioningRequest check: queued
- ProvisioningRequest check scoped to a non-DRA flavor, or to one of two GPU flavors: still inadmissible
- DRA feature gate off: unchanged

`TestReconcileDRA` needed a small helper so the scheduler cache sees the ClusterQueue's AdmissionChecks.

Integration: a new `It` in `test/integration/singlecluster/controller/dra` mirrors the existing MultiKueue CEL case and checks that quota is reserved. The DRA suite doesn't run the provisioning controller, so it doesn't assert that a ProvisioningRequest object is created.

Tested locally:
- `go test -race ./pkg/controller/core ./pkg/dra`
- `INTEGRATION_TARGET=./test/integration/singlecluster/controller/dra make test-integration` (75/75)
- `make ci-lint`, `gofmt`

`make verify` didn't finish locally because `verify-skills-lint` needs docker.

The skip only applies when a ProvisioningRequest check covers every ClusterQueue flavor that can supply a DRA logical resource (all flavors if none map), so a check scoped to an unrelated flavor keeps the device count. `ProvisioningRequestConfig.managedResources` isn't consulted here, because the workload controller has no access to that object.

I used an AI assistant to help write the fix and the tests; I reviewed and verified the change myself.

#### Release note

```release-note
DRA: Fixed Workloads with CEL device selectors being marked inadmissible on ClusterQueues with a ProvisioningRequest admission check when the node pool had scaled to zero. The device availability check is now skipped for those ClusterQueues, so the ProvisioningRequest can scale the pool up.
```
