#### What this PR does / why we need it?  
  
 When a spec starts a manager with `StartManager` and doesn't stop it, the next `StartManager` call overwrites the stored cancel function. The old manager keeps running and can reconcile objects from later specs. Most per-spec callers avoid this by pairing `StartManager` with `ginkgo.DeferCleanup(fwk.StopManager, ctx)`, but that relies on each spec doing it, and some specs registered the stop late or not at all.

This PR adds `StartManagerForSpec` to the integration framework. It registers `StopManager` with `DeferCleanup` before it starts the manager, so the manager is stopped even when setup fails. The stop runs after `AfterEach`, so the manager is still running while the spec deletes its resources. `StartManager` is unchanged for suite-level callers.

Singlecluster integration tests now use the helper where they paired `StartManager` with a `DeferCleanup` stop.

Specs that stop and restart the manager inside a spec keep using `StartManager` for the restart. The stop registered by the helper still stops the restarted manager, because `StopManager` reads the current cancel function.
