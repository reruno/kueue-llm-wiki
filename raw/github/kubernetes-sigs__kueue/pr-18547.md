#### What this PR does / why we need it?

With `waitForPodsReady`, the SparkApplication integration decided `PodsReady` from the RUNNING and COMPLETED entries of `status.executorState`:

- **Healthy applications are evicted.** The Spark Operator stops adding executors to `executorState` once their ID passes `--max-tracked-executor-per-app` (1000 by default), and Spark never reuses executor IDs. Once a long-running or dynamic allocation application's tracked executors are replaced, Kueue counts none ready and evicts it with `PodsReadyTimeout` while its executors run.
- **Applications look ready without executors.** COMPLETED entries are never removed, and they counted as ready.

`PodsReady` now counts the executor Pods of the current submission that are running and ready, and not being deleted. The integration watches the executor Pods of every SparkApplication, not only elastic ones, and reacts to phase, readiness and deletion changes. The expected count is unchanged.

Part of #18490: fixes points 1 and 2. Point 3, the dynamic allocation floor, is tracked in #18715.

#### Useful notes for reviewers

Tests:

- **Ready executors counted from Pods** (unit, `TestPodsReadyCountsReadyExecutorPods`): ready Pods count although `executorState` lists none; COMPLETED entries don't count; one case each for unready, succeeded, terminating and other submissions' Pods. The first two cases fail with the previous `executorState` counting.
- **Watch** (unit, `TestExecutorPodChanged`).
- **Reconciler** (unit): the `TestReconciler` PodsReady cases now create the ready executor Pods.
- **Integration**: the PodsReady integration helper creates the executor Pods, running and ready, under the application's submission ID.
- **End to end** (e2e): on a cluster with the operator at `--max-tracked-executor-per-app=5`, an application whose executors were all replaced past the limit kept `PodsReady=True` with `executorState` showing none running; without the fix it was evicted with `PodsReadyTimeout`.

Other notes:

- Scope: following review, other changes are split out: the dynamic allocation PodsReady floor, `sparkConf` precedence for the executor count, and reading operator-declared counts once kubeflow/spark-operator#3290 lands.
- This PR was prepared with AI assistance (Claude).

## AI summary

This change makes the SparkApplication integration determine `PodsReady` from executor Pods. It no longer reads `status.executorState`.

- `PodsReady` requires the driver to be in the Running state.
- The expected count is `DynamicAllocation.MinExecutors` when dynamic allocation is enabled. Otherwise it is `Executor.Instances`. A zero expected count returns true.
- The controller lists executor Pods and counts those that are Running, Ready, and not being deleted. The listing uses `listExecutorPods`. This review did not inspect that helper, so the current-submission filter is not confirmed from the code read here.
- If listing Pods fails, the error is logged at V(2) and `PodsReady` returns false.
- `PodsReady` now takes a `client.Client` parameter.
- The executor Pod watch is registered without the `ElasticJobsViaWorkloadSlices` feature gate. The update predicate `executorPodChanged` enqueues reconciliation when the object is not a Pod, or when the Pod's phase, readiness, or deletion status changes. Other Pod updates are ignored.
- Unit tests cover `PodsReady` counting in `TestPodsReadyCountsReadyExecutorPods` and the predicate in `TestExecutorPodChanged`. `TestReconciler` PodsReady cases were updated.
- Integration test helpers simulate executor Pod readiness and executor states from the application state.

The supplied materials do not show use of declared `status.executors` counts or the dynamic-allocation initial-count rule. This summary does not claim either.

Validation results were not available from the supplied materials. No completed CI or test run on the current head was provided.

`SparkApplication:` Fixed a bug where `WaitForPodsReady` could evict running SparkApplications whose executors were no longer tracked in `status.executorState`, or count completed executors as ready. Now Kueue counts running, ready executor Pods of the current submission to determine `PodsReady`.
