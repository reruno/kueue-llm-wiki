#### What this PR does / why we need it?

Adds `kueue-pr-evidence-perf-delta`, a guidance-only skill (one `SKILL.md`, no scripts). The PR author's coding agent picks one scheduler harness config from the diff and writes a short median table. It prefers the PR's scheduling-perf CI artifacts, compared with recent main periodics, and otherwise runs the minimalkueue harness on a merge-base worktree and the head. AFS changes additionally select the local AFS harness, reported as its own table inside this skill's block. When the merge base lacks that harness, report head-only results without a baseline or comparative verdict. The applicable existing harness comparison remains separate. Publishing follows `kueue-pr-evidence-common` (own PR, dry run first, `gh pr edit` only after approval).

Adds the `kueue-pr-evidence-perf-delta` skill. The skill guides a PR author's coding agent to compare scheduler performance between the PR head and its merge base. The change adds guidance only. It adds no scripts and changes no harness, config, or threshold.

- The skill applies only when the diff touches hot-path code: `pkg/scheduler/`, `pkg/cache/`, `pkg/resources/`, `pkg/workload/`, `pkg/controller/core/`, or `test/performance/scheduler/`. TAS, DRA, and AFS logic in those paths qualifies. Otherwise, the verdict is `not applicable`.
- It selects one config from the diff. Both sides must run the same workload.
- It prefers Prow scheduling-performance artifacts for the head SHA. The base then uses recent main periodic runs, not the merge base, and the block states this.
- If no presubmit has finished for the head, the user is asked to comment `/test <presubmit>`. Otherwise, the skill runs the harness locally in a merge-base worktree and on the head, with three interleaved runs per side by default.
- It reports medians with min–max ranges. A delta under 5% shows as `~`. A weak delta is marked with `?`. Failed runs are listed and excluded from medians.
- Publishing follows `kueue-pr-evidence-common`. `gh pr edit` runs only after explicit user approval.

+`pkg/workload/`, `pkg/controller/core/`, TAS and DRA code

+## Metrics
+
+The visible table carries minimalkueue wall, user CPU, sys CPU, and max
+RSS, plus the metrics the PR claims to change and the metrics the diff
+can move. Put every other row in `<details>`.

+| File | Rows |
+|---|---|
+| `minimalkueue.stats.yaml` | `wallMs`, `userMs`, `sysMs`, `maxrss` (bytes on darwin, KiB on linux; report MiB) |

+| `metricsDump.tgz` | newest `*.prometheus` scrape: sum of `kueue_admission_attempts_total`, mean `kueue_admission_attempt_duration_seconds` (sum/count), sum of `kueue_preempted_workloads_total` |
+
+Wall, CPU, and time to admission are seconds. Mean attempt duration is milliseconds.

+## Statistics
+
+Median per side, written `median (min–max)` when that side has more than
+one run. Delta is the head median against the base median, as a percent.
+
+- `~` when the absolute percent is under 5, or when a count (evictions,
+  admission attempts, preempted workloads) moves by fewer than 10.
+- When the base median is 0 and the change is not `~`, write the absolute
+  change instead of a percent, for example `+12 (base 0) worse`.
+- A trailing `?` marks a weak delta: the min–max ranges overlap, or a
+  side has one run. Ranges that do not overlap are a clear delta.
+- CQ usage higher is better. Every other metric here lower is better.
+  Write the signed percent, then `better` or `worse` from that direction:
+  `−6.2% better` for wall, `+3.0% better` for CQ usage, `+5.4% worse`
+  for user CPU.

+The verdict names only clear changes, largest first. With none, write
+`no clear change` and name the largest weak deltas. On a local run, when
+minimalkueue wall `(max-min)/median` exceeds 15% within one side, add
+`Noisy machine`. Evictions and time to admission are timing-sensitive.
+Quote `rangespec.yaml` only in `<details>`: it is the CI check, and a
+laptop result uses a different scale.
