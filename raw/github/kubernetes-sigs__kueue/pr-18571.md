#### What this PR does / why we need it?

Adds `kueue-pr-evidence-perf-delta`, a guidance-only skill (one `SKILL.md`, no scripts). The PR author's coding agent picks one scheduler harness config from the diff and writes a short median table. It prefers the PR's scheduling-perf CI artifacts, compared with recent main periodics, and otherwise runs the minimalkueue harness on a merge-base worktree and the head. Publishing follows `kueue-pr-evidence-common` (own PR, dry run first, `gh pr edit` only after approval).

## AI summary

Adds the `kueue-pr-evidence-perf-delta` skill. The skill guides a PR author's coding agent to compare scheduler performance between the PR head and its merge base. The change adds guidance only. It adds no scripts and no harness, config, or threshold changes.

- The skill applies only when the diff touches hot-path code, such as `pkg/scheduler/`, `pkg/cache/`, `pkg/resources/`, `pkg/workload/`, `pkg/controller/core/`, `test/performance/scheduler/`, and TAS or DRA code. Otherwise, the verdict is `not applicable`.
- It selects one config from the diff. Both sides must run the same workload.
- It prefers Prow scheduling-performance CI artifacts for the head SHA. The base then uses recent main periodic runs, not the merge base, and the block states this.
- If no presubmit has finished for the head, the skill asks the user to comment `/test <presubmit>`. Otherwise, it runs the minimalkueue harness locally on a merge-base worktree and on the head. The default is three interleaved runs per side.
- It reports medians with min–max ranges. A delta under 5% shows as `~`. A weak delta is marked with `?` when ranges overlap. It lists every failed run and keeps failed runs out of the medians.
- Publishing follows `kueue-pr-evidence-common`. It uses a separate PR and a dry run first. It runs `gh pr edit` only after explicit user approval.

The README adds the skill to the skills table and to the agent-readable references. It also changes the "Agent-readable references" heading from third-level to second-level.

The linked issue asks for end-to-end runs on `#16340` and `#17461`. This change adds guidance only and includes no such runs.

+
+The PR author's coding agent compares scheduler performance on two sides

+thresholds stay unchanged.

+
+## When to use
+
+Use this when the diff touches the scheduler hot path, or when the PR
+claims a performance effect (`perf(...)` in the title, or a claim that the
+change is faster or allocates less).
+
+Hot path: `pkg/scheduler/`, `pkg/cache/`, `pkg/resources/`,
+`pkg/workload/`, `pkg/controller/core/`, TAS and DRA code
+(`pkg/controller/tas/`, `pkg/util/tas/`, `pkg/dra/`, and the same logic
+inside generic files such as preemption and flavor assignment), and
+`test/performance/scheduler/`.
+
+For a docs-only, API-only, webhook, integration, or test-only PR, stop.
+The verdict is `not applicable`. Any change under
+`test/performance/scheduler/` is hot path, not test-only.

+| TAS, including TAS lines in a generic file | `run-tas-performance-scheduler` | `pull-kueue-test-tas-scheduling-perf-main` |
+| Other hot-path code | `run-performance-scheduler` | `pull-kueue-test-scheduling-perf-main` |
+
+Only `run-tas-dra-performance-scheduler` enables DRA; it also enables TAS.
+
+A large-scale harness change uses `run-large-scale-performance-scheduler`
+and `pull-kueue-test-large-scale-scheduling-perf-main`.
+
+Both sides must run the same workload: the same contents of the
+generator file named by the target's `SCALABILITY_*GENERATOR_CONFIG`
+variable, and the same recipe flags (`--enableTAS`, `--enableDRA`,
+`--timeout`) in each tree's `hack/make/test.mk`, except as below. A
+matching job or target name is not enough, because main periodics use
+main's files. Check both before comparing.
+
+- The PR changes only the harness or its configs: the workload change is
+  what to measure. Compare each side's own config, CI or local, and write

+  sides at the head's generator file through the target's
+  `SCALABILITY_*GENERATOR_CONFIG` variable, and name that file in the
+  provenance line. Publish no CI delta.

+  them. Publish no delta, and say why.
+

+One table, one source. When both exist and Which config allows a CI

+The test target retries a failed attempt and moves its artifacts to
+`artifacts/<test-target>-fail-<n>/` (`hack/testing/performance-test.sh`),

+`artifacts/<test-target>/<run-target>/`.
+The measured files are `summary.yaml`, `minimalkueue.stats.yaml`, and
+`metricsDump.tgz` under `artifacts/<test-target>/<run-target>/`.

+source when the user wants numbers before CI finishes.

+### Local

+Resolve the merge base and the base worktree as in
+[kueue-pr-evidence-common](../kueue-pr-evidence-common/SKILL.md). Run the

+time stays out of the numbers.

+Default 3 runs per side, interleaved `B H H B B H`, on one machine. Each
+run is `make -C <tree> <target>` with its own `ARTIFACTS=` directory under
+`${XDG_CACHE_HOME:-$HOME/.cache}/kueue-pr-evidence/pr-<n>/`. Use envtest
+and minimalkueue. Label a kind or in-cluster run, requested by a reviewer,
+as that runner in its own table. One run takes 6 to 8 minutes: start the
+series in the background and leave the machine idle.
+
+## Metrics
+
+The visible table carries minimalkueue wall, user CPU, sys CPU, and max
+RSS, plus the metrics the PR claims to change and the metrics the diff
+can move. Put every other row in `<details>`.
+
+| File | Rows |
+|---|---|
+| `minimalkueue.stats.yaml` | `wallMs`, `userMs`, `sysMs`, `maxrss` (bytes on darwin, KiB on linux; report MiB) |
+| `summary.yaml` | CQ usage `cpuAverageUsage / nominalQuota`, `averageTimeToAdmissionMs` per class, sum of `totalEvictions` |
+| `metricsDump.tgz` | newest `*.prometheus` scrape: sum of `kueue_admission_attempts_total`, mean `kueue_admission_attempt_duration_seconds` (sum/count), sum of `kueue_preempted_workloads_total` |
+
+Wall, CPU, and time to admission are seconds. Mean attempt duration is milliseconds.
+
+## Statistics
+
+Median per side, written `median (min–max)` when that side has more than
+one run. Delta is the head median against the base median, as a percent.
+
+- `~` when the absolute percent is under 5, or when a count (evictions,
+  admission attempts, preempted workloads) moves by fewer than 10.
+- When the base median is 0 and the change is not `~`, write the absolute
+  change instead of a percent, for example `+12 (base 0) worse`.
+- A trailing `?` marks a weak delta: the min–max ranges overlap, or a
+  side has one run. Ranges that do not overlap are a clear delta.
+- CQ usage higher is better. Every other metric here lower is better.
+  Write the signed percent, then `better` or `worse` from that direction:
+  `−6.2% better` for wall, `+3.0% better` for CQ usage, `+5.4% worse`
+  for user CPU.
+
+The verdict names only clear changes, largest first. With none, write
+`no clear change` and name the largest weak deltas. On a local run, when
+minimalkueue wall `(max-min)/median` exceeds 15% within one side, add
+`Noisy machine`. Evictions and time to admission are timing-sensitive.
+Quote `rangespec.yaml` only in `<details>`: it is the CI check, and a
+laptop result uses a different scale.
+
