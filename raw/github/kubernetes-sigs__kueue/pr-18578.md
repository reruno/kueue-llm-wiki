#### What type of PR is this?

/kind bug

#### What this PR does / why we need it?

`setDistributionCondition` in the DynamicQuotaOrchestrator controller wrote the condition message as-is, so a long distribution error could exceed the 32KiB `metav1.Condition` message limit. It now passes the message through `api.TruncateConditionMessage`, the same helper other Kueue controllers use. Type, status, reason and observed generation are unchanged.

Fixes #18570

This is the independent follow-up mentioned in #18552. It doesn't touch the incomplete-distribution reporting there; once #18552 lands, messages it sends through `setDistributionCondition` get truncated too.

#### Useful notes for your reviewer

New `TestSetDistributionConditionTruncatesMessage` in `pkg/controller/core/dqo/distribution_condition_test.go` covers a short message, a message at exactly 32KiB, one over the limit, and multibyte messages under and over the byte limit. The two over-limit cases fail on main (the message is stored untruncated) and pass with the fix. The test follows the helper's existing byte-based behavior and doesn't change the helper.

Tested locally:
- `go test -race ./pkg/controller/core/dqo`
- `INTEGRATION_TARGET=./test/integration/singlecluster/controller/dynamicquotaorchestrator make test-integration` (22/22)
- `make ci-lint`, `make fmt-verify`, `make e2e-common-test`

`make verify` didn't finish locally because `verify-skills-lint` needs docker.

Not changed here: `setDiscoveryCondition` also writes its message untruncated. I can send that separately if you'd like it covered.

I used an AI assistant to help write the fix and the test; I reviewed and verified the change myself.

#### Release note

```release-note
DQO: Fixed a bug where a long Distributed condition message (over 32 KiB) caused the API server to reject the DynamicQuotaOrchestrator status update. Kueue now truncates the message.
```
