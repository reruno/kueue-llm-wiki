## Description

#### What type of PR is this?

/kind bug

#### What this PR does / why we need it?

A workload in its second pass (the delayed topology assignment after a ProvisioningRequest, or a TAS node replacement) already holds its quota reservation, and the ClusterQueue snapshot counts it. `buildContext` still sized the preemptor at its full request, so its quota was counted twice. In a full queue it found no preemption targets and was requeued with `PreemptionNoCandidates`. #18597 has the details and a worked example.

A second-pass preemptor now adds zero quota, so only the topology fit decides.

Fixes #18597

#### Useful notes for your reviewer

- The flavor-resources stay in `workloadUsage` with a zero amount instead of an empty map. The borrowing checks (`workloadQuotaFits`, `QuantitiesFitInQuota`) loop over that map, so with no entries they would be skipped, and a second-pass preemptor whose ClusterQueue borrows could reclaim from other ClusterQueues in the cohort.
- Fair Sharing reads the requested flavor-resources from the positive amounts (`requestedFlavorResources`). The context now keeps the assignment's request in `requestedQuota` for that.
- The guard is `NeedsSecondPass` rather than `HasQuotaReservation`: `TestFairPreemptions` has an incoming workload with a reservation in a different ClusterQueue, which the snapshot does not count.
- New `TestScheduleForTAS` cases:
  - Full queue, same ClusterQueue: the ProvisioningRequest second pass, and a node replacement with `TASFailedNodeReplacementFailFast=false`. Both fail on main.
  - Cohort, classical and Fair Sharing: a preemptor whose ClusterQueue borrows does not reclaim (passes on main, guards the first two notes), and one within its nominal quota does (fails on main).
- #15337 / #15561 are deciding whether a node replacement should preempt at all. This PR only fixes the quota accounting when it does. Happy to drop the node replacement case if that path goes away.
- AI disclosure: I used an AI coding assistant (Claude Code) to help investigate the bug, write the fix and tests, and draft this description. I reviewed and tested the result.

## AI summary

A second-pass preemptor no longer adds its full quota request during preemption. Its quota reservation already counts in the ClusterQueue snapshot. The preemptor now adds zero quota for each requested flavor-resource. Those flavor-resource entries stay in the map so the borrowing checks still run. The preemption context stores the requested quota separately, and the flavor-resources that need preemption derive from that stored value.

The change applies to workloads that `workload.NeedsSecondPass` reports as second-pass. Workloads that are not second-pass add their full request, as before. `SimulatePreemption` in `preemption_oracle.go` sets the same stored requested quota.

Test coverage in `scheduler_tas_test.go` adds `TestScheduleForTAS` cases for:
- ProvisioningRequest second pass with tight CPU quota.
- Node replacement with a lower-priority blocker on a spare node.
- Cohort borrowing with classical preemption.
- Cohort borrowing with Fair Sharing preemption.

`tas_helper_test.go` accepts optional Fair Sharing configuration. `preemption_fair_log_test.go` computes the requested quota once.

### Suggested release note

```release-note
TAS: Fixed a bug that caused a workload in its second scheduling pass to find no preemption candidates when its existing quota reservation already used the available quota. Now Kueue counts the reservation once when it checks quota for preemption.
```
