#### What this PR does / why we need it?

When an AppWrapper without explicit TAS annotations is admitted to a TAS-only ClusterQueue (implicit TAS), Kueue suspends it right after it starts, admits it again, and suspends it again, so the AppWrapper does not keep running. With a prebuilt Workload, the Workload is finished as `OutOfSync` instead.

For implicit TAS, `FromAssignment` adds `kueue.x-k8s.io/podset-unconstrained-topology: "true"` to the PodSetInfo, and since #14585 `expectedRunningPodSets` mirrors it as `TopologyRequest.Unconstrained`. Most integrations merge PodSetInfos into the Pod template, so `PodSets` sees the annotation. AppWrapper keeps them in `spec.components[].podSetInfos`, so `PodSets` does not, and `EquivalentToWorkload` reports a mismatch.

`AppWrapper.PodSets` now sets `Unconstrained` when the matching PodSetInfo has the annotation, under the same condition as `FromAssignment`. Both now use `IsUnconstrainedByDefault` from `pkg/util/tas`.

Related: #14395. The prebuilt case is one where the Workload is finished as `OutOfSync` before the job is stopped.

- I did not merge PodSetInfos into the template in `PodSets`. `expectedRunningPodSets` does not rebuild `TopologyRequest` from merged annotations either, and the merge can fail on conflicting values.
- MultiKueue: without this fix, #14736 can also stop the manager from re-dispatching.
- #18503 does not cover this. It makes `EquivalentToWorkload` ignore the topology request only for Workloads admitted without TAS, and these Workloads are admitted with TAS. The 2 new integration specs still fail without this fix on a main that includes #18503.
