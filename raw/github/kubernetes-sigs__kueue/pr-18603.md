#### What this PR does / why we need it?

Updates KEP-1714 with the ReclaimOnly fair sharing use case and API.

`fairSharing.preemptionStrategies: [ReclaimOnly]` keeps share-based admission ordering and limits cross-ClusterQueue preemption to nominal-quota reclaim (scenario S1), including Cohort-level reclaim. Share rebalancing (scenario S2) does not run. The list cannot be combined with `LessThanOrEqualToFinalShare` or `LessThanInitialShare`.

Related: #17857

#### Useful notes for your reviewer

The text matches the implementation in #17857:

- `[ReclaimOnly]` is valid only as that single-entry list. An empty list and every mixed list fail configuration validation.
- A workload in another ClusterQueue is preempted only when AlmostLCA(preemptor, target), with the preemptor admitted, stays within nominal quota and every Cohort and ClusterQueue from AlmostLCA(target, preemptor) down to the target is borrowing.
- Candidates are taken farthest-first. After each target the search starts again at the root, so a closer reclaim can make a farther ClusterQueue reclaimable. If one target is enough, the farther one is chosen.
- `withinClusterQueue` still applies to the preemptor's own ClusterQueue. Reasons are `InCohortReclamation` and `InClusterQueue`.
- `FairSharingPreemptWithinNominal` and `FairSharingVerifyFinalTargets` do not change ReclaimOnly. Fill-back keeps a target when dropping it would make another target fail the nominal-quota checks.
