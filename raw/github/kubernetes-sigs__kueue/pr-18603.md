## Description

#### What type of PR is this?

#### What this PR does / why we need it?

Updates KEP-1714 with the ReclaimOnly fair sharing use case and API.

`fairSharing.preemptionStrategies: [ReclaimOnly]` keeps share-based admission ordering and limits cross-ClusterQueue preemption to nominal-quota reclaim (scenario S1), including Cohort-level reclaim. Share rebalancing (scenario S2) does not run. The list cannot be combined with `LessThanOrEqualToFinalShare` or `LessThanInitialShare`.

Related: #17857

#### Useful notes for your reviewer

The text matches the implementation in #17857:

- `[ReclaimOnly]` is valid only as that single-entry list. An empty list and every mixed list fail configuration validation.
- A workload in another ClusterQueue is preempted only when AlmostLCA(preemptor, target), with the preemptor admitted, stays within nominal quota and every Cohort and ClusterQueue from AlmostLCA(target, preemptor) down to the target is borrowing.
- Candidates are taken farthest-first. After each target the search starts again at the root, so a closer reclaim can make a farther ClusterQueue reclaimable. If one target is enough, the farther one is chosen.
- `withinClusterQueue` still applies to the preemptor's own ClusterQueue. Reasons are `InCohortReclamation` and `InClusterQueue`.
- `FairSharingPreemptWithinNominal` and `FairSharingVerifyFinalTargets` do not change ReclaimOnly. Fill-back keeps a target when dropping it would make another target fail the nominal-quota checks.

+### ReclaimOnly preemption strategy
+
+`[ReclaimOnly]` keeps the admission ordering from this KEP and applies only scenario S1 when choosing workloads in other ClusterQueues.
+
+#### API
+
+`ReclaimOnly` is a value of the existing `fairSharing.preemptionStrategies` list in `config.kueue.x-k8s.io/v1beta2`.
+It is not a new field and it has no feature gate.
+
+```go
+type PreemptionStrategy string
+
+const (
+	LessThanOrEqualToFinalShare PreemptionStrategy = "LessThanOrEqualToFinalShare"
+	LessThanInitialShare        PreemptionStrategy = "LessThanInitialShare"
+
+	// ReclaimOnly preempts a Workload in another ClusterQueue only to reclaim
+	// nominal quota (scenario S1).
+	// AlmostLCA(preemptor, preemptee), with the preemptor Workload admitted,
+	// must stay within its nominal quota, and every Cohort and ClusterQueue
+	// on the path from AlmostLCA(preemptee, preemptor) down to the preemptee's
+	// ClusterQueue must be borrowing.
+	// Workloads in the preemptor's own ClusterQueue can still be preempted
+	// according to withinClusterQueue.
+	// Fair Sharing still orders admission.
+	// It never triggers a preemption on its own to rebalance shares.
+	// Candidates are considered starting from the ClusterQueues farthest from
+	// the preemptor in the cohort hierarchy.
+	// A level that cannot be reclaimed yet is revisited once reclaiming
+	// elsewhere makes it possible.
+	//
+	// Not the default.
+	// Used only when preemptionStrategies is exactly ["ReclaimOnly"].
+	// An empty preemptionStrategies list is invalid and does not select
+	// ReclaimOnly.
+	ReclaimOnly PreemptionStrategy = "ReclaimOnly"
+)
+
+type FairSharing struct {
+	// preemptionStrategies indicates which constraints a preemption must
+	// satisfy.
+	// The next entry is used only when the incoming Workload still does not
+	// fit after the previous entries.
+	// AlmostLCA(x, y) is defined under "Choosing ClusterQueues to preempt from".
+	//
+	// Only the following lists are supported:
+	// - ["LessThanOrEqualToFinalShare"]
+	// - ["LessThanInitialShare"]
+	// - ["LessThanOrEqualToFinalShare", "LessThanInitialShare"]
+	// - ["ReclaimOnly"]
+	//
+	// Any other combination or ordering fails validation and
+	// kueue-controller-manager does not start.
+	//
+	// Required when fairSharing is set.
+	// There is no default that means ReclaimOnly.
+	PreemptionStrategies []PreemptionStrategy `json:"preemptionStrategies"`
+}
+```
+
+#### Validation
+
+`fairSharing` itself is optional.
+When it is omitted, Fair Sharing is off and classical preemption is unchanged.
+
+When `fairSharing` is set, `preemptionStrategies` must be one of these lists:
+
+* `["LessThanOrEqualToFinalShare"]`
+* `["LessThanInitialShare"]`
+* `["LessThanOrEqualToFinalShare", "LessThanInitialShare"]`
+* `["ReclaimOnly"]`
+
+An empty list is rejected.
+`ReclaimOnly` together with either share strategy is rejected, in either order.
+Any other value, duplicate, or order is rejected.
+Kueue reports the field as unsupported and does not start.
+
+Removing `fairSharing` from the configuration turns Fair Sharing off, including `ReclaimOnly`.
+Kueue reads the configuration at startup, so a change applies when kueue-controller-manager restarts.
+
+#### Handling
+
+Admission is unchanged.
+Pending workloads are still ordered by dominant resource share and weight.
```

  good point; with reclaimonly the share ordering at admission is what does the work, so it does sit close to admission fair sharing. i added a "admission fair sharing across clusterqueues" entry to alternatives in f47433bd0. short version:
  
  - admissionScope only exists on clusterqueue today, so workloads from different clusterqueues are never compared by usage; the cohort scope sketched in kep-4136 needs usage status on cohorts, a cohort-wide candidate list and rules for nested cohorts, which feels like its own kep update and api.
  - the signal is different: afs orders by decayed usage history, while the story 4 admin wants the current share ordering (weights, borrowing and lending limits) they already get from fair sharing, with only s2 turned off. moving them to a history signal changes admission order and needs a half life and sampling interval tuned per cluster.
  - nominal quota still has to be reclaimed with either ordering, and reclaimonly keeps the fair sharing s1 rules for that.
  
  if afs gains a cohort scope i'm happy to revisit reclaimonly the same way the kep already says for configurable preemptions. would you rather see the cohort-scope afs route explored first?
