## Description

#### What type of PR is this?

/kind bug

#### What this PR does / why we need it?

With Fair Sharing, a ClusterQueue can contribute several candidates to one
scheduling cycle: the workloads waiting for a second pass (delayed topology
assignment, node replacement) plus its own pending head. `fairSharingIterator`
kept one entry per ClusterQueue, so the head replaced the second-pass entries.
They were never evaluated, got `SecondPassFailed`, and were requeued with growing
backoff while still holding their quota reservation. As long as the ClusterQueue
kept a pending head, they could starve indefinitely.

The iterator now keeps a per-ClusterQueue list ordered like the classical
iterator (quota-reserved entries first), and only the first entry of each
ClusterQueue takes part in the tournament. `push`, used by the fair sharing
refill, inserts into that list instead of replacing it.

This takes over #13179 by @aburan28, as @mimowo suggested there. Their commit is
kept, rebased on current main and adapted to the refill's `push`; the commit
message says what changed.

Fixes #14090

#### Useful notes for your reviewer

- On the `compareEntries` extraction in `scheduler.go` (raised on #13179): it is
  a move without behavior change for the classical iterator, and the fix depends
  on it. Each ClusterQueue's entries need a deterministic order: second-pass
  workloads before the head, and among themselves by priority and FIFO, since
  they can compete for the same topology domains. The queue manager returns
  second-pass workloads in map iteration order, so a local "quota-reserved first"
  sort would leave that order random, and a complete local comparator would
  duplicate the classical rules. Reusing the function keeps the two iterators
  consistent: second-pass workloads go first in both.
- Second-pass entries add no quota to the DRS computation (`netUsage` skips
  workloads that already hold a reservation), so a ClusterQueue represented by
  one in the tournament is not penalized.
- The refill pushes a successor only after a fresh admission of the
  ClusterQueue's head, which comes after its second-pass entries, so in practice
  the list is empty at that point; `push` no longer depends on that.
