#### What this PR does / why we need it?

`/set-release-note` fails with `The pull request body contains multiple release-note blocks.` whenever CodeRabbit has added its "Suggested release note" to the PR body, because that suggestion is a second `release-note` fence.

This PR implements the first approach from the issue: release-note blocks inside a bot generated section, delimited by `<!-- This is an auto-generated comment: LABEL -->` and the matching `<!-- end of auto-generated comment: LABEL -->`, are ignored when looking for the block to update. The generated section and the rest of the body are kept unchanged.

- One author block before CodeRabbit's suggestion: the author block is replaced.
- An author block after a generated release-note block: rejected with an error, since Prow reads the first `release-note` block in the body and would still use the suggestion.
- Only CodeRabbit's suggestion: the new block is inserted right before the first generated section rather than appended at the end, so it stays the first `release-note` block in the body (the one the release-note plugin reads).
- Two or more author blocks: still rejected with the same error.
- An unterminated or mismatched marker pair is not treated as a generated section, so the old behavior applies.
- Markers only count on their own line and outside fenced code, so a quoted or inline marker does not start or end a section.

`.coderabbit.yaml` now asks CodeRabbit to put its suggested release note in a `text` block instead of a `release-note` block, so in most cases there is no second block at all.

Fixes #18634

#### Useful notes for your reviewer

The end marker must carry the same label as the start marker, so a stray end comment cannot hide an author block. I kept the "replace every block" option out since rewriting CodeRabbit's section would conflict with "keep all other content of the body unchanged".

Tests: `cd hack/releasing && python3 -m unittest discover -p '*_test.py'` (all pass) and `python3 -m doctest set_release_note.py`. New cases in `set_release_note_test.py` cover the author block before a generated section (replaced) and after one (rejected), quoted and inline markers, a body whose only block is the suggestion, several generated sections, and unterminated or mismatched markers.

## AI summary

`hack/releasing/set_release_note.py` now ignores `release-note` blocks inside bot-generated sections of a PR body. A generated section starts with `<!-- This is an auto-generated comment: <label> -->` on its own line. It ends with a matching `<!-- end of auto-generated comment: <label> -->` on its own line. Marker lines inside fenced code blocks do not start or end a section. An unterminated or mismatched marker keeps the previous behavior.

The command handles release-note blocks as follows:

- If an author block appears before a generated section, `/set-release-note` replaces that block.
- If an author block appears after a generated release-note block, the command rejects the request with a new error. Prow reads the first release-note block, so the generated suggestion must stay first.
- If the only release-note block is in a generated section, the command inserts a new block before the first generated section.
- Two or more author blocks raise the existing multiple-block error.

Other body content does not change.

`hack/releasing/set_release_note_test.py` adds tests for block ordering, marker placement, multiple generated sections, and malformed markers. It also adds a test for the rejection of an author block after a generated section. The former multiple-block test is replaced by a broader ambiguity test suite.

`.coderabbit.yaml` now asks CodeRabbit to format its suggested release note in a `text` block instead of a `release-note` block. The PR reports that commit `cd118b9` added this instruction. The script change still handles existing PRs and cases where CodeRabbit does not follow the instruction.

The linked issue `#18634` requests this behavior. The PR chooses the approach of ignoring blocks in the generated section. The PR does not report the design doc, API change, or docs update that the issue lists.
