#### What this PR does / why we need it?

KEP-12100 covers partial scale-up for a `batch/v1` Job since #16574, but the website doesn't say so. The ElasticJob section in `jobs.md` shows only atomic scale-up, and `elastic_workload.md` describes the `kueue.x-k8s.io/elastic-job-scale-up-strategy` annotation only in general terms.

This adds a "Partial scale-up" subsection to the ElasticJob section of `jobs.md`. It lists the `ElasticJobsViaWorkloadSlicesWithPartialReplicaScaleUp` feature gate and the annotation, and describes what happens when the whole scale-up doesn't fit in the quota.

## AI summary

This PR adds a "Partial scale-up" subsection to the ElasticJob section of `site/content/en/docs/tasks/run/jobs.md`. The subsection is marked alpha for v0.21. The diff adds 22 lines and removes none.

The section documents the following:

- By default, Kueue admits a scale-up only when all added Pods fit in the quota. With partial scale-up, Kueue admits as many added Pods as the quota allows.
- To enable partial scale-up, set the `ElasticJobsViaWorkloadSlicesWithPartialReplicaScaleUp` feature gate to `true`. Annotate the Job with `kueue.x-k8s.io/elastic-job-scale-up-strategy: "partial"`.
- If only some added Pods fit, Kueue admits a new Workload for those Pods. The Job's `parallelism` does not change.
- Kueue removes the `kueue.x-k8s.io/elastic-job` scheduling gate only from the admitted Pods. The other Pods stay `SchedulingGated`.
- Kueue keeps a separate Workload for the full `parallelism` pending. It admits more Pods as quota is freed.
- For `Indexed` Jobs, Kueue removes gates in ascending completion index order when `TopologyAwareScheduling` is enabled, which is the default. Otherwise, it removes gates in Pod name order.

The PR description says this PR should merge after `#16742`. That dependency is not in the diff, so this summary does not describe it as a code change.
