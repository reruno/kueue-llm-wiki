#### What this PR does / why we need it?

When the scheduler assumes a Workload, its quota reservation exists only in the scheduler cache, not on the Workload in the API. If that Workload is deleted after its LocalQueue, `handleDelete` removes it from the cache and notifies the watchers with the informer object, which has no reservation. `ClusterQueueReconciler.requestCQForWL` then needs the LocalQueue to find the ClusterQueue, and the LocalQueue is gone. So nothing requests the ClusterQueue, and it keeps its `resource-in-use` finalizer until an unrelated event, such as the periodic resync, a ClusterQueue update, or a restart.

`Cache.ForgetWorkload` now returns the cached Workload it removed, and `handleDelete` notifies the watchers with that copy when the cache held one. The cached copy carries the reservation, so `requestCQForWL` finds the ClusterQueue without the LocalQueue. As asked in #17629, the nine `AfterEach` blocks in the concurrent admission integration tests now delete the ClusterQueue before the LocalQueue.

## AI summary

This change fixes a ClusterQueue deletion that stalls on its `resource-in-use` finalizer. The scheduler cache is empty, but the ClusterQueue is not notified. This happens when a LocalQueue is deleted before an assumed Workload is removed. The API Workload has no admission in that case. The deletion notification therefore cannot identify the ClusterQueue.

- `pkg/cache/scheduler/cache.go`:
  - `ForgetWorkload` now returns the removed cached `*kueue.Workload` and an error. It returns `nil` for the Workload when the cache does not hold one.
  - The shared `deleteWorkloadWithoutLock` helper returns the cached Workload before removing it.
  - `DeleteWorkload` discards the cached Workload and returns only the error. Its signature does not change.
- `pkg/controller/core/workload_controller.go`:
  - `handleDelete` no longer defers `notifyWatchers`. It calls `notifyWatchers` after cache and queue cleanup.
  - It uses the cached Workload from `ForgetWorkload` as the old object when one is returned. Otherwise, it uses the deleted object.
  - If `ForgetWorkload` returns an error, the deleted object is used.
- `pkg/controller/core/workload_controller_test.go`: Adds `TestDeleteAssumedWorkloadRequestsClusterQueue`. It runs three cases:
  - The LocalQueue exists.
  - The LocalQueue was deleted.
  - The Workload moved to another LocalQueue before deletion.

  Each case checks that the assumed Workload leaves the cache. It also checks the ClusterQueue and LocalQueue requests. In the move case, it expects requests for both the original and the destination queues.
- `test/integration/singlecluster/controller/concurrentadmission/concurrent_admission_test.go`: In nine `AfterEach` blocks, teardown deletes the ClusterQueue before the LocalQueue. This reduces a test flake. It does not fix the production race, which the `handleDelete` change addresses.

Public API change: `ForgetWorkload` changes from `(log, wl) error` to `(log, wl) (*kueue.Workload, error)`.

### Suggested release note

```release-note
Workloads: Fixed a bug that caused ClusterQueue deletion to stall when a LocalQueue was deleted before an assumed Workload was removed from the scheduler cache. Now Kueue notifies the ClusterQueue of the removed Workload, and the ClusterQueue deletion completes.
```
