#### What this PR does / why we need it?

When the scheduler assumes a Workload, its quota reservation exists only in the scheduler cache, not on the Workload in the API. If that Workload is deleted after its LocalQueue, `handleDelete` removes it from the cache and notifies the watchers with the informer object, which has no reservation. `ClusterQueueReconciler.requestCQForWL` then needs the LocalQueue to find the ClusterQueue, and the LocalQueue is gone. So nothing requests the ClusterQueue, and it keeps its `resource-in-use` finalizer until an unrelated event, such as the periodic resync, a ClusterQueue update, or a restart.

`Cache.ForgetWorkload` now returns the cached Workload it removed, and `handleDelete` notifies the watchers with that copy when the cache held one. The cached copy carries the reservation, so `requestCQForWL` finds the ClusterQueue without the LocalQueue. As asked in #17629, the nine `AfterEach` blocks in the concurrent admission integration tests now delete the ClusterQueue before the LocalQueue.

## AI summary

This change fixes a race where a ClusterQueue keeps its `resource-in-use` finalizer after its scheduler cache is empty. The race occurs when a LocalQueue is deleted before an assumed Workload is removed. The API Workload has no admission in that case, so the deletion notification cannot identify the ClusterQueue.

- `pkg/cache/scheduler/cache.go`: `ForgetWorkload` now returns the removed cached `*kueue.Workload` along with an error. The shared `deleteWorkloadWithoutLock` helper returns the cached Workload, if present, after removing it. `DeleteWorkload` discards that value and returns only the error.
- `pkg/controller/core/workload_controller.go`: `handleDelete` uses the cached Workload returned by `ForgetWorkload` when it is available. It passes that copy to `notifyWatchers`, so the ClusterQueue reconciler can find the ClusterQueue without the LocalQueue. If forgetting fails or returns no cached Workload, watchers receive the deleted object. The watcher notification now runs after cache and queue cleanup, not in a deferred call.
- `pkg/controller/core/workload_controller_test.go`: Adds `TestDeleteAssumedWorkloadRequestsClusterQueue`. The test covers an assumed Workload whose LocalQueue exists and one whose LocalQueue was deleted. In both cases, it checks that the Workload is removed from the cache and that its ClusterQueue is queued for reconciliation.
- `test/integration/singlecluster/controller/concurrentadmission/concurrent_admission_test.go`: In nine cleanup blocks, deletion order changes from LocalQueue then ClusterQueue to ClusterQueue then LocalQueue. This mitigates the test flake. It does not fix the production race, which the handler change addresses.

Public API change: `ForgetWorkload` signature changes from `(log, wl) error` to `(log, wl) (*kueue.Workload, error)`.
