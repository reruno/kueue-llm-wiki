#### What this PR does / why we need it?

Sets `serviceAccount: projects/k8s-staging-images/serviceAccounts/kueue-sa@k8s-staging-images.iam.gserviceaccount.com` in `cloudbuild.yaml`, so the staging postsubmit build runs as the dedicated `kueue-sa` service account.

This is step 1 of the "Build identity rollout" in KEP-1466 (#17754). KEP-1466 signs SLSA provenance with Sigstore keyless signing, which uses the build's service account as the signing identity, so the build needs a Kueue-specific identity before the attestation step can land.

Why the staging build keeps working:
- `post-kueue-push-images` still runs as `gcb-builder`, which holds `roles/iam.serviceAccountUser` on `kueue-sa` through the `gcb-builder` migration shim (`kueue` is not in `skip_gcb_builder_shim` in kubernetes/k8s.io `infra/gcp/terraform/k8s-staging-images/registries.tf`).
- `kueue-sa` has `roles/artifactregistry.writer` on the `kueue` repository (images and `charts/`), and the image-builder already writes build logs to `gs://k8s-staging-images-gcb`. That matches the Security Profiles Operator staging build, which sets only `serviceAccount:`.

These permissions come from the terraform in kubernetes/k8s.io; the applied IAM state was not checked.

What stays the same:
- The pushed images and charts are the same, and no attestations are produced yet.
- `cloudbuild-periodic.yaml` is unchanged; the periodic build keeps its current identity.

Follow-ups, in order:
1. Cherry-pick this change to the supported release branches.
2. kubernetes/test-infra: switch the job to `serviceAccountName: kueue`.
3. kubernetes/k8s.io: add `kueue` to `skip_gcb_builder_shim`.
