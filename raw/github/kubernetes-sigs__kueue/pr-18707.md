#### What this PR does / why we need it?

#18545 added `StartManagerForSpec` and used it where specs paired `StartManager` with a `DeferCleanup` stop. Many singlecluster and MultiKueue specs still start the manager in `BeforeEach`, `JustBeforeEach` or `BeforeAll` and stop it with `fwk.StopManager(ctx)` in `AfterEach` or `AfterAll`. Each of those specs has to remember the stop. If one drops it, the next `StartManager` replaces the stored cancel function and the old manager keeps reconciling objects from later specs.

This PR converts those pairs to `StartManagerForSpec` and removes the `StopManager` calls. `AfterEach` and `AfterAll` blocks that only stopped the manager are removed.

Some `AfterEach` blocks ran cleanup after `StopManager` that needs the manager to be stopped: `metrics.InitMetricVectors(nil)` replaces the global metric vectors that controllers read, and `fwk.Teardown()` stops envtest. Since the helper stops the manager after `AfterEach`, that cleanup now goes into a `ginkgo.DeferCleanup` registered before `StartManagerForSpec`. Ginkgo runs cleanups in reverse order, so it still runs right after the manager stops.

In MultiKueue `Ordered` containers, the manager is started in `BeforeAll`. The stop registered by `StartManagerForSpec` runs after `AfterAll`, which is where it ran before.

Manager pairs in `BeforeSuite`/`AfterSuite` (including the MultiKueue `suite_test.go` files) and stop/restart inside a spec keep using `StartManager`. In MultiKueue these are the restart helpers in `capacity_provider_test.go`, the restart spec in `jobs_test.go`, the CapacityProvider feature-gate specs and the `lateCRDCluster` manager in `setup_test.go`.

## AI summary

This PR changes integration tests only. It adds a per-spec manager start path, `StartManagerForSpec`, and uses it in applicable single-cluster and MultiKueue tests. Each converted test no longer calls `StopManager` in its `AfterEach` or `AfterAll` hook.

- The helper registers manager cleanup with `ginkgo.DeferCleanup` before it starts the manager. Cleanup that must run after the manager stops is also registered before the start, so it runs after the manager cleanup.
- In MultiKueue `Ordered` containers, the manager starts in `BeforeAll`. Its cleanup runs after `AfterAll`.
- `StartManager` is unchanged. Suite-level manager pairs and explicit stop and restart within a spec still use `StartManager`.
