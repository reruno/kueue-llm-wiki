## Description

#### What type of PR is this?

/kind bug

#### What this PR does / why we need it?

`ValidatePodSpec` checked a `type: Pod` LimitRange `max` against the summed pod requests only. LimitRanger also checks the summed pod limits against `max`, so a Workload whose Pods have limits above the max was admitted, took quota, and then every Pod creation was forbidden.

The pod `max` check now uses the max of the pod requests and the pod limits, like the container check already does. Pod limits come from `resourcehelpers.PodLimits` with overhead excluded (LimitRanger does not add overhead to limits); sidecar init containers are counted the same way LimitRanger counts them.

Fixes #18722

#### Useful notes for your reviewer

The error message stays `requests must not be above the limitRange max`, which the container branch already uses for limits too.

Tests: new `TestValidatePodSpec` cases for pod limits above `max` (with and without a sidecar) and pod limits within `max`. `go test ./pkg/util/limitrange/ ./pkg/workload/` and `go test ./pkg/controller/core/ -run LimitRange` pass.

```release-note
Workloads: Fixed a bug that caused Kueue to admit a Workload when the summed limits of its Pods exceeded a `type: Pod` LimitRange `max`. Now Kueue marks the Workload inadmissible with the LimitRange message, and the Workload does not reserve quota.
```

- Before this change, `ValidatePodSpec` compared the pod `max` only with summed pod requests.

  - A case with a pod maximum of 3 CPU is accepted.
  - Pod overhead is excluded from the limits comparison.
- `test/integration/singlecluster/scheduler/scheduler_test.go` adds a LimitRange case with a pod request of 1 CPU, a pod limit of 3 CPU, and a pod maximum of 2 CPU. The case expects the quota-reservation condition to report a LimitRange constraint failure.
