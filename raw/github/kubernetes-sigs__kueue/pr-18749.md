#### What this PR does / why we need it?
The DeviceClass tracking integration spec creates a LimitRange and then a Workload whose device request comes only from that LimitRange. Workload and LimitRange watches are not ordered, so the scheduler can admit the Workload from empty requests before the LimitRange reaches the manager cache. The spec then times out waiting for `pending_workloads{status="inadmissible"}` to equal 1.
Wait until the manager cache can read the LimitRange before creating those Workloads. The same wait covers the defaulted DeviceClass-deletion specs, which create a LimitRange and a Workload back to back.

Prepared with AI assistance.
Fixes #18744

## AI summary

This change updates integration tests only. It does not change controller behavior.

- `test/integration/singlecluster/controller/dra/suite_test.go` (+18/-0): Adds a client that reads from the manager cache. Adds `expectLimitRangesInManagerCache`, which waits until the supplied LimitRanges can be read from that cache. `managerSetup` assigns this client before it sets up indexes and controllers.
- `test/integration/singlecluster/controller/dra/dra_test.go` (+2/-0): `verifyRequeueOnDeviceClassDelete` waits for the created LimitRange to appear in the manager cache when it tests defaulted requests.

The change fixes a flake in the DRA DeviceClass tracking specs. A Workload that depends on a LimitRange could be processed before the LimitRange reached the manager cache. The Workload could then be admitted with empty requests, and the spec timed out while it waited for `pending_workloads{status="inadmissible"}` to equal 1.
