#### What this PR does / why we need it?

The scheduler integration spec "Should admit workloads after updating lending limit" creates `wl-1` and `wl-2` back to back and then expects `wl-1` to get the quota and `wl-2` to stay pending. Both ask for 5 CPU against a 5 CPU `prod-cq`, so only one fits.

Nothing in the spec guarantees that `wl-1` is admitted first. The ClusterQueue orders Workloads by priority, then `CreationTimestamp`, then UID. `CreationTimestamp` has one-second precision, so the two Workloads almost always tie, and the UID tie-break is random. When the ClusterQueue, LocalQueue and both Workloads are created faster than the reconcilers react (a cold start, or a loaded machine), both Workloads are in the queue before the first scheduling cycle. Then `wl-2` wins half the time and `ExpectWorkloadsToBePending(wl2)` fails.

This PR creates `wl-1` and waits for its quota reservation before creating `wl-2`. By then `wl-1` already holds the quota, so `wl-2` can never be ahead of it in the queue, and the order no longer depends on the UID.

The assertions after that point are unchanged. The separate `ExpectWorkloadsToHaveQuotaReservation(wl1)` after the pending check is dropped, since the new wait covers it.

#### Useful notes for your reviewer

How I reproduced it: I ran only this spec with `INTEGRATION_NPROCS=1`. It failed on the first, cold run, and it failed once in 10 runs with 30 `yes` processes saturating the CPU. It passed 8 of 8 runs on an idle machine. Both failures were `Unexpected workloads are pending` at the `wl-2` check, with `wl-2` admitted.

In the failing run with debug logs, the workload reconciler observed `wl-1` (UID `b15d54d4...`) and `wl-2` (UID `410f5891...`) 4ms apart, before the LocalQueue was reconciled. Scheduling cycle 1 then picked `wl-2`, because `410f...` sorts before `b15d...`.

## AI summary

This PR changes one integration test file: `test/integration/singlecluster/scheduler/scheduler_test.go` (+4/−2).

The test "Should admit workloads after updating lending limit" now creates `wl-1` and waits for its quota reservation before it creates `wl-2`. The test then checks that `wl-2` stays pending. The separate quota-reservation check for `wl-1` moved before the `wl-2` creation. The remaining metric assertions are unchanged.

This removes a race in the test. Both workloads request 5 CPU, and their creation timestamps can tie at one-second precision. In that case, the UID tie-break decides which workload is admitted first. The test now enforces the order, so it no longer depends on UID order.

The change affects test code only. It does not change controller, API, or runtime behavior.

The author reports 20 of 20 passing runs of the focused spec under CPU load after the change. I did not run the tests.
