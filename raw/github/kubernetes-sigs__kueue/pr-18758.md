## Description

#### What type of PR is this?

#### What this PR does / why we need it?

Since #16459, the WorkloadPriorityClass controller watches Workloads: a Workload whose priority differs from its class value gets the class value back, also after its `priority` was changed directly.
As requested in [this review](https://github.com/kubernetes-sigs/kueue/pull/16459#discussion_r4564454144), this adds the `WorkloadPriorityClassWatchesWorkloads` feature gate, Beta and enabled by default.
With the gate disabled, the controller does not watch Workloads, and a changed priority stays until the class is reconciled again.

Related: #16459

#### Useful notes for your reviewer

The gate decides whether the Workload watch is registered, the way `KueueDRAIntegrationExtendedResource` decides it for the DeviceClass watch of the Workload controller.

| Behavior | Level | Command and result | Not run |
|---|---|---|---|
| Gate disabled: a Workload keeps a priority changed directly | integration | `ginkgo --race --focus 'Should keep a priority changed' ./test/integration/singlecluster/controller/core/`: 3 of 3 runs pass. With the watch always registered, the priority is back at 200 after about a second and the spec fails. | none |
| Gate enabled (default): the specs from #16459 still pass | integration | `ginkgo --race -procs=4 ./test/integration/singlecluster/controller/core/`: 119 of 119 specs pass. | none |

## AI summary

This PR adds the `WorkloadPriorityClassWatchesWorkloads` feature gate. The gate is Beta and enabled by default starting in version 0.21.

- The WorkloadPriorityClass controller watches Workloads only when the gate is enabled.
- With the gate enabled, the controller reconciles the class of a Workload whose priority differs from the class value. This restores the class value after a direct priority change on the Workload.
- With the gate disabled, the Workload watch is not registered. A changed Workload priority stays until its WorkloadPriorityClass is reconciled again.
- The WorkloadPriorityClass watch is unchanged.
- The PR updates the feature gate lists (`site/data/featuregates/versioned_feature_list.yaml` and the compatibility lifecycle reference).
- The PR updates the priority class docs to describe the disabled-gate behavior.
- The PR adds an integration test that runs with the gate disabled. It checks that a changed priority stays at 100 after the class is created with value 200.

The author reports that the new integration test passed in 3 runs with the gate disabled. The author also reports that the core controller integration suite passed 119 specs with the gate enabled. These results were not verified in this review.

## Suggested release note

```release-note
Workloads: Kueue restores the priority of a Workload from its WorkloadPriorityClass when the Workload priority is changed directly. Without this behavior, a changed priority remains until the WorkloadPriorityClass is reconciled again. This behavior is gated by the `WorkloadPriorityClassWatchesWorkloads` feature gate.
```

  **Wait for the Workload in the manager cache before creating the class.**
  
  With `WorkloadPriorityClassWatchesWorkloads` disabled, the class create event is the only trigger for this reconcile. `Reconcile` reads Workloads through the manager client, which can serve them from the informer cache. The class event and the Workload event arrive on separate watches. The class reconcile can therefore run before the cache contains `wl`. The list then returns no items, and `Reconcile` returns without requeue. With the Workload watch disabled, no later event retries the class, so the priority-200 assertion can time out.
