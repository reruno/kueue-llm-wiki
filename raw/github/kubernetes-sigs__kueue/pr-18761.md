## Description

#### What this PR does / why we need it?

In the gate-off spec from #18758, only the create event of the WorkloadPriorityClass reconciles the class.
The reconcile lists Workloads from the manager cache, so a Workload that is not in that cache yet is skipped, and with the gate disabled nothing requeues the class. The spec then times out waiting for priority 200.
CodeRabbit [pointed this out](https://github.com/kubernetes-sigs/kueue/pull/18758#discussion_r4565541844) on #18758.

The spec now waits for the Workload in the manager cache before it creates the class, as `expectLimitRangesInManagerCache` does for LimitRanges.
It also deletes the class with `DeferCleanup`, so an early failure does not delete a nil object, and it ends by changing the class value, to check that class events still update the Workload with the gate disabled.

Related: #18758

The race depends on timing and did not show up locally; the wait removes it by construction.

## AI summary

This change updates one integration test in `test/integration/singlecluster/controller/core/workload_controller_test.go`. It does not change controller code. The change is in the spec that runs with `WorkloadPriorityClassWatchesWorkloads` disabled.

- The spec waits until the Workload is in the manager cache before it creates the `WorkloadPriorityClass`. This prevents a timing race. With the gate disabled, the class reconcile can run before the Workload is cached, and nothing requeues the class.
- The class is created with `DeferCleanup`. The `AfterEach` no longer deletes it.
- The spec adds a step that changes the class value from 200 to 300. It then checks that the Workload priority becomes 300.
- The spec name changes to "Should keep a priority changed on a workload until the class value changes".
- The shared `workloadPriorityClass` variable is removed.
