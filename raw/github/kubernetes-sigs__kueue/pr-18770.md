#### What this PR does / why we need it?

With the `CustomMetricLabels` feature gate on, `ClusterQueueReconciler.Update` returns early for a terminating ClusterQueue, before its custom label check. So a label change on a terminating ClusterQueue skips the gauge resync that an active ClusterQueue gets. Kueue keeps the old series and writes new ones under the new label value. `kueue_admitted_active_workloads` is updated by +1 and -1, so when an admitted Workload is removed, the new series goes to -1 while the old one keeps its count.

`Update` now stores the label values and, on a relabel, calls `resyncClusterQueueGaugeMetrics` before it returns for a terminating ClusterQueue. The cache and the queue manager keep a terminating ClusterQueue until its delete event. So the resync rebuilds `kueue_reserving_active_workloads`, `kueue_admitted_active_workloads`, `kueue_cluster_queue_status` and the resource gauges under the new value. `Update` still skips everything else for a terminating ClusterQueue.

## AI summary

This PR fixes gauge metrics for terminating ClusterQueues when custom metric labels change. Before the change, `ClusterQueueReconciler.Update` returned early for a terminating ClusterQueue. It did this before it checked for custom-label changes. Kueue therefore did not resync the ClusterQueue gauges after a label change. Old series stayed, and new series were written under the new label value.

The change in `pkg/controller/core/clusterqueue_controller.go`:

- Moves the custom-label store update ahead of the deletion check.
- For a terminating ClusterQueue whose labels changed, calls `resyncClusterQueueGaugeMetrics` before it returns.
- Keeps the early return for the rest of the terminating-ClusterQueue update flow. The cache, queue manager, cohort metrics, resource metrics, and watcher notification remain skipped for these queues.
- Leaves the update flow for non-terminating ClusterQueues unchanged.

The PR adds an integration spec in `test/integration/singlecluster/controller/core/custom_labels_test.go`. The spec deletes a ClusterQueue that still has admitted Workloads, changes its `team` label, and checks that the gauges use only the new value.

The Cohort gauge `kueue_cohort_subtree_admitted_active_workloads` is out of scope. The linked issue tracks it separately.

```text
Observability: Fixed a bug where relabeling a terminating ClusterQueue with `CustomMetricLabels` enabled left ClusterQueue gauges with the old custom label value. This could create duplicate series and make `kueue_admitted_active_workloads` negative under the new value. Kueue now resyncs the ClusterQueue gauges with the new label value.
```

  > [!NOTE]
  > 🤖 **GPT-6.1 Sol responding on behalf of @vladikkuzn**
  
  **P2: synchronize gauge clearing with workload accounting.** This new call reaches a helper that clears the admitted gauge before acquiring the scheduler-cache lock. A workload removal can run between that clear and the rebuild: with two admitted workloads, removal creates the new-label series at -1, then rebuilding the survivor adds 1 and leaves 0 instead of 1. Removing the survivor then leaves -1. I reproduced this ordering with the public cache operations. The shared helper already has this race for active relabels; this call also exposes it while terminating queues drain. Clear and rebuild the admitted series under the same cache synchronization. The new test's CQGet wait precedes completion of resync; add a completion barrier before deleting its workload so the test does not intermittently hit this window.
