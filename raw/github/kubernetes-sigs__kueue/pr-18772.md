#### What this PR does / why we need it?

#17127 Dynamic Allocation support defect: with Dynamic Allocation, PodsReady expected `minExecutors` from the start, or the executor instances when `minExecutors` was unset, while the driver starts with the largest of instances, `minExecutors` and `initialExecutors`.

PodsReady now expects:

- **until the Workload has been ready**, the initial executors, `max(instances, minExecutors, initialExecutors)`, capped at the executors Kueue grants, since the driver can lower its target before it creates them all and the slices then follow it;
- **once it has been ready** (`PodsReady` True or `WaitForRecovery`), **or for a replacement slice**, `minExecutors`, Spark's default of 0 when unset, how far the application tolerates scaling down. Kueue creates a replacement slice only once the driver stops ramping up (see `numExecutors`).

The expected count without Dynamic Allocation, and how ready executors are counted, are unchanged.

Fixes #18715

Part of #18490: point 3, the dynamic allocation floor.

#### Useful notes for reviewers

Tests:

- **Floor before and after readiness** (unit, `TestPodsReadyDynamicAllocationFloor`): fewer than, and exactly, the initial executors; instances as the initial executors; the grant cap; started, waiting for recovery, a replacement slice; no `minExecutors`. With the previous floor, the "not ready yet" cases fail.
- **Reconciler** (unit, `TestReconciler`): instances 10, `minExecutors` 5, 5 executors running now stays `WaitForStart`, and stays `Started` once the Workload has been ready.
- **Helper** (unit, `TestHasBeenReady`): the new `workload.HasBeenReady`.
- **End to end** (e2e): on a cluster with `initialExecutors` 4, `minExecutors` 2 and executor readiness staggered, PodsReady turned True only at the 4th ready executor, stayed True with 2, and turned False with 1.

Other notes:

- Independent of #18547: it changes the expected count, #18547 how ready executors are counted. They touch adjacent lines of `PodsReady`, so whichever merges second may need a small rebase.
- `numExecutors` now shares `initialExecutors()` with PodsReady, with no change in behavior.
- This PR was prepared with AI assistance (Claude).


## AI summary

This PR changes how the SparkApplication integration computes the executor count that `PodsReady` requires when dynamic allocation is enabled.

- **Without dynamic allocation:** The required count is `spec.executor.instances` (default 0). This is unchanged.
- **With dynamic allocation, before the executors have started:** The required count is `max(instances, minExecutors, initialExecutors)`, capped at the executor count granted to the Workload.
- **With dynamic allocation, after the executors have started:** The required count is `minExecutors` (default 0).

The executors have started when the Workload has been ready (`PodsReady` is True, or False with reason `WaitForRecovery`) or when the Workload replaces another Workload slice.

Changes by file:
- `sparkapplication_controller.go`: `PodsReady` accepts `PodsReadyOption` values and reads the Workload from them. New helpers compute the required count. `numExecutors` reuses the initial-executor calculation.
- `workload.go`: Adds `HasBeenReady`.
- Tests: Adds `TestPodsReadyDynamicAllocationFloor` and `TestHasBeenReady`, and updates `TestReconciler` expectations.

### Suggested release note

```release-note
SparkApplication: Fixed a bug that caused `WaitForPodsReady` to report PodsReady before the initial executors started when dynamic allocation was enabled and `minExecutors` was lower than `initialExecutors`. Now Kueue waits for the initial executors, capped at the granted executor count, until the Workload has been ready. After readiness, Kueue requires only `minExecutors` (0 when unset), so PodsReady stays True when the application scales down.
```

This behavior applies when `ElasticJobsViaWorkloadSlicesForSparkApplication` and `waitForPodsReady` are enabled. The release note does not state whether that feature gate is enabled by default.
