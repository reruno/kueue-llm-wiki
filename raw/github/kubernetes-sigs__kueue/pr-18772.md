#### What this PR does / why we need it?

#17127 Dynamic Allocation support defect: with Dynamic Allocation, PodsReady expected `minExecutors` from the start, or the executor instances when `minExecutors` was unset, while the driver starts with the largest of instances, `minExecutors` and `initialExecutors`.

For an elastic SparkApplication with Dynamic Allocation, PodsReady now expects:

- **until the executors of the current submission have started**, its starting executors: `max(instances, minExecutors, initialExecutors)`, capped at `maxExecutors` and at the executors Kueue grants, since the driver can lower its target before it creates them all and the slices then follow it;
- **once they have started**, `minExecutors`, Spark's default of 0 when unset, how far the application tolerates scaling down.

Kueue records that the executors of a submission have started in the `kueue.x-k8s.io/spark-executors-started-submission` annotation on the SparkApplication, as `kueue.x-k8s.io/spark-max-executor-id` records the highest executor ID per submission. It records it once as many executors are ready as the smaller of the starting executors and the executors it requests quota for (`numExecutors`), leaving out terminating executors, which hold quota but are never ready again, so the record follows a lowered target the way the grant does. It also records it once every executor the driver has created is ready: the driver can lower its target during the ramp-up without stopping an executor, and it creates the next executors without waiting for the previous ones to be ready. A resubmission (for example after a driver failure with `restartPolicy: OnFailure`) gets a new submission ID, so its driver waits for its starting executors again, whether it keeps the workload slice or gets a new one. PodsReady does not read the Workload's PodsReady condition for this: a `WaitForRecovery` transition says when readiness was lost, not in which submission it was reached.

The driver can lower its target during the ramp-up only where creating executors falls behind registering them, since Spark submits the first stage once 80% of the initial executors have registered on Kubernetes: with `spark.kubernetes.allocation.maxPendingPods` below the starting executors, or a lower `spark.scheduler.minRegisteredResourcesRatio`. With `maxPendingPods`, every created executor is briefly ready after each wave, so the start is usually recorded at the first wave, and PodsReady then expects `minExecutors` for that submission, as on main.

A SparkApplication that is not elastic keeps expecting `minExecutors`, which defaults to the executor instances. The expected count without Dynamic Allocation, and how ready executors are counted, are unchanged.

**Upgrade.** An elastic SparkApplication with Dynamic Allocation that is already running at the upgrade has no record yet. Kueue records it at the first reconcile where its current executors, apart from terminating ones, are all ready, also when it has scaled below its starting executors, since `numExecutors` then follows the executors it keeps. From then on it expects `minExecutors`, as before this PR. Until then it expects the smaller of its starting executors and its grant: if admitted scale-up executors are Pending at the upgrade, its slice is `False/WaitForRecovery` until they are ready, and then recovers.

Fixes #18715

Part of #18490: point 3, the dynamic allocation floor.

#### Useful notes for reviewers

Tests:

- **Floor** (unit, `TestPodsReadyDynamicAllocationFloor`): before the executors started, fewer than, and exactly, the starting executors; instances as the starting executors; the `maxExecutors` cap; the grant cap. Once they started, `minExecutors` and below it, and no `minExecutors`. Started in a previous submission expects the starting executors. A SparkApplication that is not elastic expects `minExecutors`, or the instances.
- **Record** (unit, `TestGetCustomAnnotations`): recorded once the starting executors are ready, not with fewer, kept, and recorded again for a new submission. Recorded when the driver lowered its target before creating all its starting executors (initial 4, `minExecutors` 1, executor 2 stopped, 1 ready), not during a ramp-up. Recorded once every created executor is ready after the driver lowered its target without stopping one (initial 10, `minExecutors` 2, 6 created), not with one of them Pending, nor with an executor stuck terminating on a lost node while the others are Pending.
- **Resubmission keeping the slice** (unit, `TestPodsReadyResubmissionKeepingTheSlice`): two `Reconcile` calls on an elastic SparkApplication resubmitted while Kueue kept its slice, still `PodsReady` from the previous submission. With 1 of 3 starting executors ready, or none and no `minExecutors`, the slice stays `WaitForRecovery`; with the previous floor it became `True/Recovered`.
- **Running without the record** (unit, `TestPodsReadyRunningWithoutTheRecord`): two `Reconcile` calls on an application running at the upgrade, scaled from 3 starting executors to 2. With both ready, with one terminating, and once it's gone, it is recorded and stays `True`.
- **End to end** (e2e), on an earlier version of this PR, to run again: on a cluster with `initialExecutors` 4, `minExecutors` 2 and executor readiness staggered, PodsReady turned True only at the 4th ready executor, stayed True with 2, and turned False with 1. With `restartPolicy: OnFailure`, the resubmission's replacement slice stayed `WaitForStart` until its 4th executor was ready.

Other notes:

- Rebased on #18547, which counts the ready executor Pods: this PR changes only the expected count, and its tests build ready executor Pods accordingly.
- `numExecutors` now shares `initialExecutorTarget()` and `startingExecutors()` with PodsReady, with no change in behavior.
- This PR was prepared with AI assistance (Claude).

  Yes. Current behavior with dynamic allocation: PodsReady is True once the driver is running and `minExecutors` executors are ready. When `minExecutors` is unset, it expects `spec.executor.instances` ready executors instead.
  
  Two problems with this approach:
  
  - **At start:** Spark starts the driver with `max(instances, minExecutors, initialExecutors)` executors. With initial 4 and min 2, PodsReady turns True at 2 ready executors, so `waitForPodsReady` can't catch the other 2 never starting.
  - **After start:** the initial executors are only where the driver starts. Once executors go idle, Spark can scale below that, down to `minExecutors`, which is 0 if unset ([Spark's defaults](https://github.com/apache/spark/blob/v4.0.0/core/src/main/scala/org/apache/spark/internal/config/package.scala#L696-L705)). So expecting the instances turns PodsReady False on a normal scale-down.
  
  With this PR, PodsReady waits for the initial executors (capped at the grant) until the Workload has been ready. After that it expects `minExecutors` ready executors. When `minExecutors` is unset, Spark's minimum is 0, so a running driver is enough. It no longer falls back to the instances.

  It's a problem because Kueue acts on PodsReady being False: with `waitForPodsReady`, a workload that isn't ready within `timeout` is evicted. With dynamic allocation, every scale-up would then put a running application at risk of eviction, for executors it doesn't need.
  
  A scale-up is a new Workload slice, so its readiness is timed like a start. The slice starts in `WaitForStart`, and `timeout` counts from its own admission. If PodsReady expects the grant, the slice is ready only once every executor the driver just asked for is ready. Those executors can be Pending for reasons outside the application, since Kueue's quota isn't node capacity: a node with room, the cluster autoscaler, an image pull. If they're late, the slice is evicted with `PodsReadyTimeout`. That suspends the SparkApplication, stops the driver and the executors that were doing the work, and the application starts over. On its next scale-up the same can happen again.

  @Pradeep39 one more case I'd like your opinion on, as a proposal: the driver lowers its target during the ramp-up **without stopping an executor**.
  
  Spark's `initializing` ends at the first stage submission ([ExecutorAllocationManager.scala#L679](https://github.com/apache/spark/blob/v3.5.8/core/src/main/scala/org/apache/spark/ExecutorAllocationManager.scala#L679)), not when the starting executors are created. After that it can lower the target, and lowering it doesn't kill anything ([L380-L385](https://github.com/apache/spark/blob/v3.5.8/core/src/main/scala/org/apache/spark/ExecutorAllocationManager.scala#L380-L385): "We lower the target number of executors but don't actively kill any yet").
  
  Example: `initialExecutors` 10, `minExecutors` 2.
  
  1. The driver creates executors 1-5 (first batch).
  2. The first stage, with 6 tasks, is submitted. Spark lowers the target to 6, and the driver creates executor 6.
  3. All 6 are ready and busy for longer than `waitForPodsReady.timeout`, so none idles out.
  
  There is no ID gap and `created` (6) is below the starting executors (10), so `numExecutors` stays at 10 and the record is never written. PodsReady expects `min(10, 10)` with 6 ready, and the application is evicted after the timeout. On main it expects 2. This is different from the lowered-target case we discussed, where an executor stops and leaves an ID gap.
  
  As far as I can see, nothing Kueue can read says the driver lowered its target: `initializing` and the target live only in the driver. A proposal: also record the start once every executor the driver has created is ready:
  
  ```go
  created := max(j.recordedMaxExecutorID(), maxID)
  if ready >= int(min(j.startingExecutors(), target)) || (created > 0 && ready >= created) {
  	annotations[executorsStartedSubmissionAnnotation] = j.Status.SubmissionID
  }
  ```
  
  While its target is above the executors it has, the driver creates the next batch about every `spark.kubernetes.allocation.batch.delay` (1s), once the previous batch's pods exist, without waiting for them to be ready ([ExecutorPodsAllocator.scala#L378](https://github.com/apache/spark/blob/v3.5.8/resource-managers/kubernetes/core/src/main/scala/org/apache/spark/scheduler/cluster/k8s/ExecutorPodsAllocator.scala#L378)). So "every created executor ready" means the driver wants no more. Pending executors keep `ready < created`, so unschedulable executors still hit the timeout, and an executor lost during the ramp-up leaves a gap.
  
  **Trade-off:** if a whole batch is ready before the driver creates the next one (within about a second, for example with cached images), or the next batch's creation fails, the start is recorded early. PodsReady then expects `minExecutors` for that submission, as on main. So the fix can fail only toward main's behaviour, while today this case evicts a healthy application. A time condition (the newest executor pod older than a few batch delays) would close that race, but it needs a requeue, so I'm not sure it's worth it.
  
  Test cases: 6 of 6 created executors ready, recorded; the same with executor 6 Pending, not recorded.
  
  wdyt? Do you see a better signal, or a case where this records too early that I've missed?
