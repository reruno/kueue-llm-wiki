#### What this PR does / why we need it?

Resolves `spark.executor.instances` and `spark.dynamicAllocation.{enabled,minExecutors,initialExecutors,maxExecutors}` with the Spark Operator's precedence, as the Pod resources already are: a typed field wins when the operator passes it, and `spec.sparkConf` applies otherwise.

- **Resolver:** new `sparkapplication_dynamicallocation.go` with `dynamicAllocation()` and `executorInstances()`. As in Spark, values ignore case and surrounding whitespace, and keys are case-sensitive.
- **Callers:** `numInitialExecutors`, `numExecutors` (initial count, ramp-up and min/max clamp) and the PodsReady expected count read through it.
- **Quota leak closed:** an executor count set only in `spark.executor.instances` was sized as 0 executors.
- **Webhook:** elastic SparkApplications may enable dynamic allocation in `sparkConf`; the rejection existed only because Kueue could not follow it. Rejecting dynamic allocation on non-elastic jobs is #18289's.
- **Suspension:** `RestorePodSetsInfo` writes `spec.executor.instances` only when that changes the resolved count, so that a count set in `spec.sparkConf` is not copied to the typed field, where it would override later `sparkConf` changes.

Fixes #18716

#### Useful notes for reviewers

All unit tests:

- **Resolver,** `TestDynamicAllocation`: typed only, `sparkConf` only, typed fields winning with `sparkConf` fallback, typed `enabled: false` not overriding `sparkConf`, value case, wrong-case keys, malformed counts.
- **Sizing,** `TestPodSetsExecutorCount`: count from `sparkConf`, typed count winning, dynamic allocation from `sparkConf`, a `sparkConf` `maxExecutors` cap under `spec.dynamicAllocation`.
- **PodsReady,** `TestPodsReadyExpectsTheExecutorsSetInSparkConf`.
- **Suspension,** `TestRestorePodSetsInfoKeepsTheExecutorCountInSparkConf`.
- **Webhook:** the two `sparkConf`-only elastic cases are now accepted.

11 of these cases fail when the resolver ignores `sparkConf`. `cmd/kueue` builds.

- Independent of #18547 and #18772. It changes where the counts are read from, not how ready executors are counted or the PodsReady floor; it touches neighboring lines of `PodsReady` and `numExecutors`, so whichever merges later may need a small rebase.
- This PR was prepared with AI assistance (Claude).

## AI summary

This PR makes the SparkApplication integration resolve executor count and dynamic-allocation settings the same way the Kubeflow Spark Operator does. Typed fields win when set. Otherwise, Kueue reads `spec.sparkConf`.

The resolved values now drive:
- Workload sizing for the `executor` PodSet.
- Dynamic-allocation bounds (`minExecutors`, `initialExecutors`, `maxExecutors`) used for slice sizing and clamping.
- The PodsReady expected count. Readiness uses the minimum executor count, falling back to the initial count.

Other changes:
- Elastic SparkApplications with dynamic allocation enabled only in `sparkConf` are now accepted by the webhook.
- Executor-count restoration on suspension writes `spec.executor.instances` only for non-elastic jobs when the effective count changes. A count that is unchanged stays unset in the spec.
- Rejection of dynamic allocation on non-elastic jobs is not changed here. The PR leaves that to `#18289`.

Tests cover resolver precedence, `sparkConf`-based PodSet counts, restoration behavior, PodsReady, and webhook acceptance. The PR description reports that 11 test cases fail when the resolver ignores `sparkConf`. Current CI results are not available in the supplied context.

SparkApplication: Fixed a bug where executor counts and dynamic-allocation bounds set only in `spec.sparkConf` were ignored, so Kueue sized the Workload with zero executors and rejected elastic applications that enabled dynamic allocation only in `sparkConf`. Kueue now resolves `spark.executor.instances` and `spark.dynamicAllocation.*` with the Spark Operator precedence, where typed fields take precedence over `spec.sparkConf`.
