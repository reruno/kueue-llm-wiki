#### What this PR does / why we need it?

Resolves `spark.executor.instances` and `spark.dynamicAllocation.{enabled,minExecutors,initialExecutors,maxExecutors}` with the Spark Operator's precedence, as the Pod resources already are: a typed field wins when the operator passes it, and `spec.sparkConf` applies otherwise.

- **Resolver:** `dynamicAllocation()` returns the effective `sparkv1beta2.DynamicAllocation`, in `sparkapplication_podset.go` next to `numInitialExecutors()`. As in Spark, values ignore case and surrounding whitespace, and keys are case-sensitive.
- **Callers:** `numInitialExecutors`, `numExecutors` (initial count, ramp-up and min/max clamp), the partial scale-up `minCount` and the PodsReady expected count read through it.
- **Quota leak closed:** an executor count set only in `spark.executor.instances` was sized as 0 executors.
- **Webhook:** elastic SparkApplications may enable dynamic allocation in `sparkConf`; the rejection existed only because Kueue could not follow it. Rejecting dynamic allocation on non-elastic jobs is #18289's.
- **Suspension:** `RestorePodSetsInfo` restores the executor count only when `spec.executor.instances` is set. Kueue never changes that field when it starts the job, so restoring only undoes an edit: a count set in `spec.sparkConf` stays there, and an edit of it takes effect instead of being overwritten in the typed field. It now also reports a restored count as a change.
- **Docs:** the dynamic allocation section no longer lists reading the settings from `spec.dynamicAllocation` only as a limitation, and says they can be set in `spec.sparkConf`, with the same precedence as the Pod resources.

Fixes #18716

#### Useful notes for reviewers

All unit tests:

- **Sizing,** `TestPodSetsExecutorCount`: count from `sparkConf`, typed count winning, dynamic allocation from `sparkConf`, typed fields winning with `sparkConf` fallback, typed `enabled: false` not overriding `sparkConf`, value case, wrong-case keys, malformed counts, a `sparkConf` `maxExecutors` cap under `spec.dynamicAllocation`, and the partial scale-up `minCount` from `sparkConf`.
- **PodsReady,** `TestPodsReadyCountsReadyExecutorPods`: counts from `sparkConf`, and `minExecutors` from `sparkConf` for an elastic job and for one that is not elastic.
- **Editing the count in `sparkConf`** (integration): an admitted application is suspended with the edit kept, a new Workload requests the edited count, and it is readmitted with `spec.executor.instances` unset.
- **Suspension,** `TestRestorePodSetsInfo`: an unchanged or edited count in `sparkConf` stays there, and a typed count is restored as unset when the executor PodSet count is 0.
- **Webhook:** the two `sparkConf`-only elastic cases are now accepted.

12 of these cases fail when the resolver ignores `sparkConf`. `cmd/kueue` builds.

Other notes:

- Builds on #18547, which counts the ready executor Pods: this PR changes only where the counts are read from.
- **Will be rebased once #18772 merges.** Both PRs change how `PodsReady` computes the expected count: that PR the floor, this PR where the bounds come from. After the rebase, the floor reads its bounds through `dynamicAllocation()`, and the sparkConf PodsReady test expects the initial executors until the Workload has been ready. Reviewers may want to wait for that rebase.
- This PR was prepared with AI assistance (Claude).

Elastic SparkApplications may now enable dynamic allocation in spec.sparkConf. On upgrade, a running application without the kueue.x-k8s.io/elastic-job annotation and with spark.executor.instances only in spec.sparkConf is restarted once, because its Workload now includes those executors.

## AI summary

This change makes the SparkApplication integration resolve executor counts and dynamic-allocation settings with the Spark Operator precedence. Typed fields in the spec take precedence when set. Otherwise, Kueue reads the values from `spec.sparkConf`.

Changes by area:

- **Executor sizing:** `numInitialExecutors` uses `spec.executor.instances` when set. Otherwise, it uses a valid, non-negative `spark.executor.instances` from `spec.sparkConf`. If neither is set, the count is zero. A malformed value is treated as unset, not as an error. `sparkConfInt32` parses base-10 signed 32-bit values.
- **Dynamic allocation:** A new `dynamicAllocation()` resolver reads the enabled state and the min, initial, and max executor bounds from `spark.dynamicAllocation.*` in `spec.sparkConf`. A typed `spec.dynamicAllocation` value overrides the matching Spark value when that typed value is set.
- **Sizing and clamping:** `numExecutors` uses the resolved values for the enabled check, the initial count, and min/max clamping.
- **PodsReady:** For elastic jobs, the expected executor count uses the resolved minimum when dynamic allocation is enabled. For other jobs, it uses the initial executor count from `numInitialExecutors`.
- **Suspension restore:** For non-elastic jobs, `RestorePodSetsInfo` writes the admitted count to `spec.executor.instances` only when that field is set and the count differs. Unset fields stay unset, so counts supplied through `sparkConf` are not copied into typed fields.
- **Webhook:** Elastic SparkApplications no longer fail validation when dynamic allocation is enabled only in `spec.sparkConf`. The `sparkConf` path check and its related `strings` import were removed.
- **Documentation:** The dynamic-allocation guide describes `spec.sparkConf` as a source for executor and dynamic-allocation settings, and it states the precedence rule. It removes the former limitations that said Kueue reads only typed fields and rejects `sparkConf`-only elastic applications.
- **Tests:** Unit tests cover resolver precedence, malformed and negative values, PodSet sizing, PodsReady thresholds, suspension restore, and webhook acceptance. An integration test covers editing `spark.executor.instances` in `sparkConf` across suspension and readmission.

Non-elastic jobs that set dynamic allocation are not changed. Rejection of those jobs is separate work (`#18289`).

Unit test and build results are not available in this summary.

### Comment by [@reruno](https://github.com/reruno) — 2026-11-17T13:02:17Z

@Pradeep39 the precedence logic looks right to me: it matches the operator's submission order, and the call sites are the right ones. I'd like to propose a smaller shape that fits the existing code more closely:

1. **Reuse `sparkv1beta2.DynamicAllocation` instead of a new struct.** The new `dynamicAllocation` struct has the same fields with the same types as the operator's `DynamicAllocation` (`Enabled`, `InitialExecutors`, `MinExecutors`, `MaxExecutors`). Returning the effective `sparkv1beta2.DynamicAllocation` avoids a new type, and the controller changes become a plain swap from `j.Spec.DynamicAllocation.X` to `da.X`.
2. **No new file.** With fewer helpers it is about 25 lines, and `sparkapplication_podset.go` already owns the executor count (`numInitialExecutors()`), so it can live right next to it.
3. **Drop the single-caller helpers.** `executorInstances()` is only used by `numInitialExecutors()`, and `sparkConfBool()` only by `dynamicAllocation()`, so both can be inlined. `sparkConfInt32()` has 4 callers and stays.
4. **Point to the existing precedence comment** in `sparkapplication_resources.go` instead of explaining the operator ordering again.

Roughly:

```go
// The executor count and dynamic allocation follow the same precedence as the
// Pod resources (see sparkapplication_resources.go): a typed field wins when
// spark-operator passes it, and spec.sparkConf applies otherwise.
// spark-operator passes spec.dynamicAllocation only when it is enabled.

func (j *SparkApplication) numInitialExecutors() int32 {
	return ptr.Deref(cmp.Or(j.Spec.Executor.Instances, j.sparkConfInt32(sparkcommon.SparkExecutorInstances)), 0)
}

// dynamicAllocation returns the dynamic allocation Spark runs the application with.
func (j *SparkApplication) dynamicAllocation() sparkv1beta2.DynamicAllocation {
	da := sparkv1beta2.DynamicAllocation{
```
