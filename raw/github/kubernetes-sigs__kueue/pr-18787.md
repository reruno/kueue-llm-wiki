## Description

#### What type of PR is this?

/kind bug
/area integrations

#### What this PR does / why we need it?

A Job can have Pods while `status.active` is still zero. If Kueue evicts and readmits it before the native Job controller processes suspension, the old Pods can survive with placement constraints from the previous admission.

Keep the reservation until the native controller acknowledges the current suspension request. Clear stale acknowledgements and suspend the Job again if it is manually resumed while stopping. This acknowledgement requirement applies only to native batch Jobs.

Related: #16027, #16867.

#### Useful notes for your reviewer

Unit/race tests, all 146 Job integration specs, focused provisioning and MultiKueue tests, and `make verify` passed.

A separate Kind reproduction on Kubernetes 1.35.5 passed same-flavor readmission, cross-flavor readmission, and manual resume during stopping. It seeded an old gated Pod; the real native controller handled suspension and replacement Jobs completed. Both negative controls failed at the expected assertions.

The Kind run verified acknowledgement and Pod deletion initiation before quota release. It did not test complete termination of running containers.

AI assistance was used to draft this PR.

#### Release note

```release-note
Job: Fixed premature readmission during eviction that could leave old Pods with incompatible placement constraints.
```

## AI summary

This PR makes Kueue wait for the native Kubernetes Job controller to acknowledge suspension before it releases workload admission. The change applies only to native batch Jobs, where `ManagedBy` is unset or names the native controller. Jobs managed by another controller do not wait.

- `Job.IsActive` returns true when the Job has active Pods or its stopping annotation is `"true"`.
- For workload eviction, `Job.Stop` clears any prior `JobSuspended` condition, requests suspension, and keeps the stopping annotation until `JobSuspended=True`. A failure to clear the condition returns a wrapped error. Other stop reasons do not wait.
- If a stopping Job is manually resumed, Kueue suspends it again and keeps admission.
- The goal is to prevent old Pods from surviving readmission with placement constraints from a previous admission.

Tests added or updated:

- Unit tests (`TestStopWaitsForSuspension`) cover resumed Jobs, stale acknowledgements, and resume-versus-acknowledgement races.
- Integration tests cover readmission while an old Pod remains, and acknowledge suspension in preemption, priority-change, deactivation, and PodsReady-timeout scenarios.
- A test helper, `AcknowledgeJobSuspension`, emulates the native Job controller.

The author reports passing unit, race, and Job integration tests, focused provisioning and MultiKueue tests, `make verify`, and a Kind reproduction on Kubernetes 1.35.5. The Kind run did not test complete termination of running containers. These results were not independently verified in this summary.

## Suggested release note

```release-note
Job: Fixed a bug that caused premature readmission during eviction when a Job still had Pods with incompatible placement constraints. Now Kueue waits for the native Job controller to acknowledge suspension before it releases admission. This applies to native batch Jobs only.
```
