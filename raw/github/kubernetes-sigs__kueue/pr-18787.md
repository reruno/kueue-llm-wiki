## Description

#### What type of PR is this?

/kind bug

#### What this PR does / why we need it?

A Job can have Pods while `status.active` is still zero. If Kueue evicts and readmits it before the native Job controller processes suspension, the old Pods can survive with placement constraints from the previous admission.

Keep the reservation until the native controller acknowledges the current suspension request. Clear stale acknowledgements and suspend the Job again if it is manually resumed while stopping. This acknowledgement requirement applies only to native batch Jobs.

Related: #16027, #16867.

## AI summary

This PR makes Kueue wait for the native Kubernetes Job controller to acknowledge suspension before it releases workload admission. The wait applies only to native batch Jobs, where `spec.managedBy` is unset or set to `batchv1.JobControllerName`. Jobs managed by another controller do not wait.

- `Job.IsActive` returns true when the Job has active Pods or when the stopping annotation (`StoppingAnnotation`) is `"true"`.
- For a `WorkloadEvicted` stop on a native Job, `Job.Stop` clears existing `JobSuspended` conditions from status before it requests suspension. This occurs when the Job is not stopping and `JobSuspended` is not `True`. If clearing fails, `Stop` returns `reset suspension acknowledgement: ...`.
- `Job.Stop` then requests suspension and sets the stopping annotation. If the Job was already suspended, `stoppedNow` is false.
- While the stopping annotation is `"true"` and `JobSuspended` is not `True`, `Stop` returns early. It does not reset the start time or restore PodSet info. Admission stays in place until the native controller reports `JobSuspended=True`.
- Other stop reasons do not wait for acknowledgement.
- If a stopping Job is manually resumed, `Stop` sees that the Job is not suspended and suspends it again.
- The goal is to prevent old Pods from surviving readmission with placement constraints from a previous admission.

Tests added or updated:

- `TestStopWaitsForSuspension` covers missing, stale, and current acknowledgements, resumed Jobs, native and external controllers, and Jobs already suspended.
- Job reconciler unit tests model the native controller. A patch with the stopping annotation writes `JobSuspended=True`.
- Integration tests cover readmission while an old Pod remains. They also acknowledge suspension after deactivation, preemption, eviction, and priority change.
- The new helper `integration.AcknowledgeJobSuspension` emulates the native Job controller.

The diff I inspected covers `job_controller.go` up to the early return in `Stop`. The rest of `Stop` was not in the inspected hunk. The author reports that the Job unit tests, race-enabled Job and MultiKueue suites, three focused provisioning tests, and `make verify` passed. The author also reports a Kind reproduction on Kubernetes 1.35.5. These results come from the PR description and were not verified here.

Job: Fixed a bug that caused premature readmission of native batch Jobs during eviction when old Pods still existed with incompatible placement constraints. Now Kueue waits for the native Job controller to acknowledge suspension before it releases admission.
