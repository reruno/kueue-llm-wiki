#### What this PR does / why we need it?

Follow-up to #18750, as requested in https://github.com/kubernetes-sigs/kueue/pull/18750 ("Let's handle the blockAdmission configuration for a follow up").

With `waitForPodsReady.blockAdmission` enabled, the scheduler sets the `WaitingForPodsReady` condition on the head Workload and then blocks until all admitted Workloads are PodsReady. When that status write fails with NotFound, the Workload was deleted, yet the scheduler still waited for PodsReady on its behalf and then attempted an admission that could only fail and be rolled back.

The scheduler now skips both the wait and the admission when the Workload was deleted, and requeues the entry without a status update. The requeue drops the deleted Workload.

Related: #18732

## AI summary

This PR changes how the scheduler handles a head Workload that is deleted while `waitForPodsReady.blockAdmission` is enabled.

- `waitForPodsReadyIfNeeded` now returns whether the Workload was deleted.
- When the quota reservation update returns NotFound, the function logs the deletion and returns `true` without waiting for PodsReady.
- Other update errors are logged, and the scheduler still waits for PodsReady.
- `processEntry` sets the entry's `inadmissibleMsg` to "Workload was deleted" and `skipStatusUpdate` to true. It then returns before admission.
- The V(3) log message changes from "Workload status not updated because it was deleted" to "Workload not admitted because it was deleted".
- `TestSchedulerSkipsPodsReadyWaitForDeletedWorkload` adds coverage. It runs with `WorkloadRequestUseMergePatch` off and on. It checks that scheduling finishes before the timeout, that the deleted Workload gets no admission attempt, and that no error log or event is recorded.
- `TestStatusUpdateWhenWorkloadDeleted` has an updated comment about the cancellation behavior.
