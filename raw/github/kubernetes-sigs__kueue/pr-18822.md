## Description

#### What type of PR is this?

/kind bug

#### What this PR does / why we need it?

The flavor assigner currently uses `isPreferred` to aggregate resource modes within a single flavor. However, this comparison is intended for ranking different flavors.

When one resource requires borrowing and another requires preemption, the aggregated mode can lose one of these requirements. Under `PreemptionOverBorrowing`, this can incorrectly report `Fit`, preventing victim selection and leaving the workload pending.

This PR fixes the aggregation by independently preserving:

- The worst preemption mode across resources.
- The deepest borrowing level across resources.

Flavor-to-flavor preference ordering remains unchanged.

#### Regression coverage

Added three regression cases covering:

1. CPU borrowing with memory preemption under `PreemptionOverBorrowing`.
2. The same combination under `BorrowingOverPreemption`.
3. CPU preemption with memory borrowing, ensuring the scheduler's flavor assigner can continue to a fully fitting alternative flavor.

The tests exercise flavor assignment using scheduler-cache snapshots.

#### Which issue(s) this PR fixes

Fixes #18801

#### Special notes for reviewers

Thanks to @YevheniiOrlovEngineering for identifying the root cause and providing the reproduction. Happy to coordinate on the additional scheduler-cycle regression test mentioned in the issue.

The change is intentionally limited to resource-mode aggregation. DCO sign-off is included. Full Go test execution and CI validation are still pending.

## AI summary

This PR changes how the flavor assigner combines resource modes within one flavor. Before this change, `findFlavorForPodSets` kept the single worst mode across resources, ranked with `isPreferred` and the flavor-fungibility preference. Under `PreemptionOverBorrowing`, a resource that borrowed could hide another resource's need to preempt. The flavor then appeared to fit, and the scheduler did not look for victims.

Now the flavor keeps two values independently:
- `preemptionMode`: the minimum (worst) preemption mode across the flavor's resources.
- `borrowingLevel`: the maximum borrowing level across the flavor's resources.

Flavor-to-flavor preference ordering is unchanged. The change applies only to combining resources inside one flavor.

Changed files:
- `pkg/scheduler/flavorassigner/flavorassigner.go` (+4/−4): replaces the `isPreferred` selection with the independent min/max combination.
- `pkg/scheduler/flavorassigner/flavorassigner_mixed_resource_modes_test.go` (+209): adds `TestAssignFlavorsMixedBorrowingAndPreemption`. The table-driven test covers CPU borrowing with memory preemption, and CPU preemption with memory borrowing with fallback to another flavor when configured to try the next flavor.

Test results are not available in the supplied evidence. This summary does not state that the tests pass.

Linked issue `#18801` is addressed by this aggregation change.

### Suggested release note

```text
Scheduling: Fixed a bug where a Workload that needed to borrow one resource and preempt for another resource in the same flavor could never be admitted when `preference` was `PreemptionOverBorrowing`. The scheduler dropped the preemption requirement, so it did not preempt lower-priority Workloads. Kueue now keeps both the preemption and borrowing requirements for the flavor, so the scheduler preempts the required Workloads and admits the pending Workload while borrowing.
```
