## Description

#### What type of PR is this?

/kind bug

#### What this PR does / why we need it?

With `flavorFungibility.preference: PreemptionOverBorrowing`, a Workload that has to borrow one resource and preempt for another in the same flavor is never admitted. `findFlavorForPodSets` summarized the flavor by keeping the "worst" mode of its resources, but decided which one is worst with `isPreferred`, the ranking used to compare flavors with each other. Under `PreemptionOverBorrowing` that ranking looks at borrowing first, so cpu `{fit, borrowingLevel: 1}` won over memory `{preempt, 0}`, the flavor came out as `Fit`, and the scheduler never looked for victims.

The flavor now keeps both parts separately: the worst preemption mode and the deepest borrowing level among its resources. `isPreferred` still ranks flavors against each other.

The default `BorrowingOverPreemption` lost information through the same merge the other way round (cpu `{preempt, 0}` and memory `{fit, 1}` became `{preempt, 0}`), so with `whenCanBorrow: TryNextFlavor` and `whenCanPreempt: MayStopSearch` the search stopped at that flavor instead of moving on to one that fits. This is fixed by the same change.

Fixes #18801

#### Useful notes for your reviewer

Tests, all added to the existing tables:
- `TestSchedule`: one scheduling cycle with cpu borrowed from a cohort member and memory freed by preempting a lower-priority Workload. Without the fix nothing is preempted.
- `TestAssignFlavors`: the same setup under both preferences, checking `RepresentativeMode() == Preempt`, and a two-flavor case for the `MayStopSearch` effect, where the first flavor needs preemption for cpu and borrowing for memory and the second one fits.

Without the fix, the `TestSchedule` case, the `PreemptionOverBorrowing` case and the two-flavor case fail; the `BorrowingOverPreemption` single-flavor case passes on main too and is there to show both preferences now agree.

I used an AI assistant while preparing this PR.

## AI summary

This PR changes how the flavor assigner combines resource modes within one flavor. Previously, it used `isPreferred`, which ranks flavors against each other, to pick the worse mode for each resource. Under `PreemptionOverBorrowing`, a borrow-only resource could hide a preempt need from another resource. Under `BorrowingOverPreemption`, a preempt-only resource could hide a borrow need.

The fix combines the two parts separately. The flavor keeps the worst preemption mode and the deepest borrowing level across its resources. The `isPreferred` ranking still applies when comparing flavors.

Changed files:
- `pkg/scheduler/flavorassigner/flavorassigner.go` (+5/-3): Combines per-resource modes into the flavor's representative mode.
- `pkg/scheduler/flavorassigner/flavorassigner_test.go` (+206): Adds three `TestAssignFlavors` cases. Two compare `PreemptionOverBorrowing` and `BorrowingOverPreemption` when CPU can borrow and memory needs preemption. One checks that `WhenCanBorrow: TryNextFlavor` moves to a second flavor that fits.
- `pkg/scheduler/scheduler_test.go` (+131): Adds a `TestSchedule` scenario with `PreemptionOverBorrowing`. A higher-priority workload needs borrowed CPU and preemption for memory. The test checks that the scheduler preempts the lower-priority workload.

No exported or public declarations change.

Test results: not available from the supplied materials. The PR objectives report that the new cases fail without the change, but no completed CI run on the current head was supplied.

Scheduling: Fixed a bug that caused a Workload to never be admitted when `flavorFungibility.preference` is `PreemptionOverBorrowing` and the Workload must borrow one resource and preempt for another resource in the same flavor.
