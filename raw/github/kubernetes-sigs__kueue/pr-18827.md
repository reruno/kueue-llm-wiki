## Description

#### What type of PR is this?

/kind bug

/area fair-sharing

#### What this PR does / why we need it?

When a flavor is removed from a ClusterQueue, the Workloads already admitted on it keep running, so their usage stays in the ClusterQueue's (and its Cohorts') `Usage`, but the flavor no longer has a `SubtreeQuota` entry. `dominantResourceShare` only iterated `SubtreeQuota`, so such a ClusterQueue reported a DRS of 0 and no borrowing. `TargetClusterQueueOrdering` then pruned it before the within-nominal reclaim, and a peer ClusterQueue that got the flavor's quota couldn't take its nominal quota back until those Workloads finished. Classical preemption isn't affected, since `ClusterQueueSnapshot.BorrowingWith` already treats a missing quota as 0.

`dominantResourceShare` now also counts usage on flavor-resources with no `SubtreeQuota` entry, with a quota of 0. The same applies to Cohorts, whose `Usage` carries that usage up the tree.

Fixes #18826

#### Useful notes for your reviewer

Tests, all of which fail on main and pass with the fix:
- `TestDominantResourceShare`: a ClusterQueue with usage on a flavor it has no quota for, and the same one level down for a Cohort subtree.
- `TestFairPreemptions`: a peer ClusterQueue reclaims its nominal quota from such a Workload (`InCohortReclamation`).
- Integration, `fairsharing` suite: admit on `flavor1`, remove `flavor1` from the ClusterQueue, give its quota to another ClusterQueue, and check that the Workload is preempted and the new one admitted.

Visible side effect: such a ClusterQueue's `weightedShare` in status and metrics is no longer 0, and it no longer gets admission ordering as if it weren't borrowing.

#17194 edits the same function (the lendable loop below this one), so whichever lands second needs a small rebase.

I used an AI assistant while preparing this PR.


## AI summary

This PR changes `dominantResourceShare` in `pkg/cache/scheduler/fair_sharing.go`. Usage on a flavor-resource that has no `SubtreeQuota` entry now counts as borrowed, with a quota of 0. Before this change, the function checked only `SubtreeQuota` keys. A ClusterQueue whose Workloads kept running on a removed flavor therefore reported a dominant resource share (DRS) of 0 and appeared not to borrow.

The change:
- Caches the node's resource node in `rn`.
- Adds an `addBorrowed` helper. It runs for each `SubtreeQuota` key and for each `Usage` key that lacks a quota entry.
- Adds doc comments that describe the DRS calculation.

The diff adds 189 lines and removes 3 across 4 files. The test files add cases for:
- `TestDominantResourceShare`, including a child-cohort case where the flavor is absent from every node in the subtree.
- `TestFairPreemptions`, where a ClusterQueue has lost a flavor but still runs a Workload on it, and a peer reclaims nominal quota.
- The fair-sharing integration suite, which checks that the running Workload is preempted.

Expected side effects, per the linked issue and PR objectives:
- The affected ClusterQueue's `weightedShare` in status and metrics becomes non-zero.
- The ClusterQueue no longer receives admission ordering as if it were not borrowing.

I did not run the tests. Test results are not available.
