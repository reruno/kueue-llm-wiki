## Description

#### What type of PR is this?

/kind bug

/area fair-sharing

#### What this PR does / why we need it?

With Admission Fair Sharing and Fair Sharing preemption, `fairPreemptionStrategy` sorted the candidates of all ClusterQueues with `CandidatesOrdering`. That comparator compares LocalQueue usage only between Workloads of the same ClusterQueue and priority otherwise, so it isn't a strict weak ordering across ClusterQueues: with `a` and `b` in an AFS ClusterQueue and `c` in another one, `a` < `b` by usage while `b` < `c` < `a` by priority. The order inside the AFS ClusterQueue then depended on the map iteration order in `findCandidates`, and the victim was sometimes the Workload from a lightly used LocalQueue instead of the most used one, as KEP-4136 describes.

The candidates are now sorted by ClusterQueue first, then with `CandidatesOrdering`. Only the order within each ClusterQueue is used afterwards (`MakeClusterQueueOrdering` and the retry candidates), so decisions across ClusterQueues don't change. The V(5) "Simulating fair preemption" log now lists candidates grouped by ClusterQueue.

Fixes #18837

#### Useful notes for your reviewer

- Test: a `TestFairPreemptions` case with the three Workloads above. The runner gets AdmissionFairSharing options (LocalQueues, usage, AFS-enabled preemptor) and a `runs` field that repeats the preemption on the same snapshot, since the bug depends on map iteration. With 300 runs, the case failed on main in each of 20 `go test` runs and passes every time with the fix.
- Classical preemption sorts mixed-ClusterQueue slices with the same comparator (`classical/candidate_generator.go`), where the global order matters, so it isn't changed here; see the issue.

I used an AI assistant while preparing this PR.


## AI summary

This PR changes how Fair Sharing preemption orders candidates when Admission Fair Sharing (AFS) is used.

- `fairPreemptionStrategy` in `pkg/scheduler/preemption/fair_strategy.go` sorts candidates by ClusterQueue name first. It then applies the existing candidate ordering within each ClusterQueue.
- The existing ordering compares LocalQueue usage only for Workloads in the same ClusterQueue. For Workloads in different ClusterQueues, it falls back to priority. Sorting mixed-ClusterQueue candidates with this comparator can form a cycle, so the result depended on input order.
- Only the order within each ClusterQueue is used afterward. Cross-ClusterQueue decisions do not change.
- The V(5) "Simulating fair preemption" log groups candidates by ClusterQueue.
- `TestFairPreemptions` in `pkg/scheduler/preemption/preemption_fair_test.go` adds AFS test cases. One case checks that the victim comes from the LocalQueue with the highest usage within its ClusterQueue. The test setup can now supply LocalQueues and an AFS usage state. The test repeats preemption on one snapshot to detect results that vary with map iteration order.
- Classical preemption is not changed.

```text
FairSharing: Fixed a bug that caused the preemption victim inside an AFS ClusterQueue to change between scheduling cycles when the cluster state did not change. Now Kueue selects the Workload from the LocalQueue with the highest usage within that ClusterQueue when Fair Sharing preemption runs.
```
