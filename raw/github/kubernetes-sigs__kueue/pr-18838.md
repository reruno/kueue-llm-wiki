## Description

#### What type of PR is this?

/kind bug

/area fair-sharing

#### What this PR does / why we need it?

With Admission Fair Sharing and Fair Sharing preemption, `fairPreemptionStrategy` sorted the candidates of all ClusterQueues with `CandidatesOrdering`. That comparator compares LocalQueue usage only between Workloads of the same ClusterQueue and priority otherwise, so it isn't a strict weak ordering across ClusterQueues: with `a` and `b` in an AFS ClusterQueue and `c` in another one, `a` < `b` by usage while `b` < `c` < `a` by priority. The order inside the AFS ClusterQueue then depended on the map iteration order in `findCandidates`, and the victim was sometimes the Workload from a lightly used LocalQueue instead of the most used one, as KEP-4136 describes.

The candidates are now sorted by ClusterQueue first, then with `CandidatesOrdering`. Only the order within each ClusterQueue is used afterwards (`MakeClusterQueueOrdering` and the retry candidates), so decisions across ClusterQueues don't change. The V(5) "Simulating fair preemption" log now lists candidates grouped by ClusterQueue.

Fixes #18837

#### Useful notes for your reviewer

- Test: a `TestFairPreemptions` case with the three Workloads above. The runner gets AdmissionFairSharing options (LocalQueues, usage, AFS-enabled preemptor) and a `runs` field that repeats the preemption on the same snapshot, since the bug depends on map iteration. With 300 runs, the case failed on main in each of 20 `go test` runs and passes every time with the fix.
- Classical preemption sorts mixed-ClusterQueue slices with the same comparator (`classical/candidate_generator.go`), where the global order matters, so it isn't changed here; see the issue.

## AI summary

This PR changes candidate ordering in Fair Sharing preemption when Admission Fair Sharing (AFS) is used.

- `fairPreemptionStrategy` in `pkg/scheduler/preemption/fair_strategy.go` now sorts candidates by ClusterQueue name first. It then applies the existing candidate ordering.
- The existing ordering compares LocalQueue usage only between Workloads in the same ClusterQueue. For Workloads in different ClusterQueues, it falls through to priority. Mixed-ClusterQueue sorting therefore produced an order that depended on input order.
- Only the order within each ClusterQueue is used afterward, so cross-ClusterQueue decisions do not change.
- The V(5) "Simulating fair preemption" log now lists candidates grouped by ClusterQueue.
- `TestFairPreemptions` in `pkg/scheduler/preemption/preemption_fair_test.go` adds AFS test cases. They check that the victim comes from the LocalQueue with the highest usage within a ClusterQueue. The test setup can now supply LocalQueues and an AFS usage ledger. The test also supports repeated runs to check results across map iteration orders.
- Classical preemption is not changed.

## Suggested release note

FairSharing: Fixed a bug where the Workload chosen for preemption inside an AFS ClusterQueue could change between scheduling cycles, even when the state did not change. Kueue now always selects the Workload from the LocalQueue with the highest usage within that ClusterQueue, regardless of Workloads in other ClusterQueues of the cohort. The V(5) fair preemption simulation log now groups candidates by ClusterQueue.
