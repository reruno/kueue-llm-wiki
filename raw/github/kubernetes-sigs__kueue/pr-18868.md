#### What this PR does / why we need it?

A StatefulSet Workload can retain a stale TAS request when its Pod template topology annotation changes while the Workload is pending or as the StatefulSet resumes from zero. For example, changing a required topology from block to hostname can leave the Workload requesting a shared block.

When TAS is enabled, synchronize the Workload's topology request from the current StatefulSet template if replicas are positive and the Workload has no quota reservation. Reuse the builder for initial creation and subsequent sync, including the Pod index label. On resume from zero, persist the updated Workload spec before clearing OnHold.

This builds on the retained-Workload lifecycle in #12233, replica-count synchronization in #15279, and StatefulSet topology update validation in #16039.

Fixes #18867

#### Useful notes for your reviewer

The unit cases cover refreshing a pending Workload, preserving the request after quota reservation while admission is pending, and retaining the existing scale-from-zero and TAS-disabled behavior. The API regressions cover scale-from-zero and annotation-only updates at a fixed replica count. Both verify that the original Workload UID is retained.

Race-enabled tests for StatefulSet and jobframework/tas passed, all 27 StatefulSet integration scenarios passed, and complete `make verify` exited 0.

## AI summary

This PR keeps a StatefulSet Workload's TAS topology request in sync with the StatefulSet Pod template while the Workload waits for quota. Before this change, the request kept its creation-time value. A StatefulSet that scaled up from zero could therefore be admitted with a stale topology requirement.

Changes in `pkg/controller/jobs/statefulset/statefulset_reconciler.go`:
- `reconcileWorkload` refreshes `wl.Spec.PodSets[0].TopologyRequest` when all of these hold:
  - `replicas > 0`
  - the Workload has no quota reservation
  - TopologyAwareScheduling is enabled
- The refresh builds the request from the StatefulSet template and compares it with the stored request using `apiequality.Semantic.DeepEqual`. If they differ, it replaces the request and marks the Workload for update. A build error stops reconciliation.
- The refresh runs on every reconcile that meets these conditions. It does not depend on clearing OnHold.
- The request builder moved into the helper `podSetTopologyRequest`. `constructWorkload` and the reconcile path both use it.

Tests:
- `statefulset_reconciler_test.go` adds unit cases for topology changes and removals, replica-count updates, preserved Pod index labels, reserved Workloads, the disabled gate, and error paths.
- `statefulset_controller_test.go` adds two TAS integration tests. One scales to zero and back while changing the required topology. The other changes the topology of a pending Workload. Both check that the Workload keeps its UID.

Not covered: physical Pod placement. Integration tests use synthetic Node capacity. CI results are not available in the supplied evidence.

### Suggested release note

```text
StatefulSet: Fixed a bug where a StatefulSet could be admitted with a stale TAS topology request after its Pod template changed the `kueue.x-k8s.io/podset-required-topology` annotation. Now Kueue updates the Workload's topology request from the StatefulSet template while the Workload waits for quota, so admission uses the current topology requirements.
```

This behavior is gated by the TopologyAwareScheduling feature gate.
