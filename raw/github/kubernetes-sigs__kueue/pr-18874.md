#### What this PR does / why we need it?

The ResourceFlavor webhook did not check the value of a toleration with the `Equal` operator (or an empty operator, which means `Equal`). kube-apiserver requires that value to be a valid label value for Pods. Kueue adds the ResourceFlavor tolerations to the Pod templates of the Jobs it admits with that flavor, so an invalid value was accepted on the ResourceFlavor and only rejected later, on the Job's Pod template.

This adds that check to the ResourceFlavor webhook, reported on `spec.tolerations[i].value`.

**Behavior change**
- Now: creating a ResourceFlavor with such a toleration is rejected. Updating a ResourceFlavor is rejected only when its tolerations change and a value is invalid.
- Unchanged: tolerations with a valid value, and tolerations with the `Exists` operator, are accepted as before. The other ResourceFlavor checks and the Workload `podSetUpdates` validation are not changed.
- Existing objects: a ResourceFlavor that already has such a toleration can still be updated without changing its tolerations, for example to remove its finalizer on deletion.

Fixes #18873

## AI summary

This change adds a value check to the ResourceFlavor webhook for tolerations. A toleration with operator `Equal` or an empty operator must have a valid label value. Otherwise, the webhook rejects it at `spec.tolerations[i].value`.

The check runs on creation. On update, it runs only when the tolerations change. Unchanged tolerations are not rechecked, so an existing ResourceFlavor can still be updated, for example to remove a finalizer. Tolerations with operator `Exists` are not checked. Other ResourceFlavor checks and Workload `podSetUpdates` validation are unchanged.
