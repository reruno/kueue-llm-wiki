## Description

#### What type of PR is this?

#### What this PR does / why we need it?

Same cleanup as #18890.

`TopologyAwareScheduling` is enabled by default, so setting it to `true` changes nothing. The first commit removes that override from the 53 MPIJob and Kubeflow job cases that have it.

After that, `TestValidateCreate` of the MPIJob webhook and `TestValidate` of the five Kubeflow jobs have no case that sets a feature gate, and none of them has a case with TAS disabled. The second commit adds one such case to each. It also adds to JAXJob the TAS-disabled `TestPodSets` case that the other four Kubeflow jobs already have.

The cases that set it to `false` stay, because they cover TAS disabled.

Part of #18804

@coderabbitai please open a cleanup issue for a follow-up:

The MPIJob webhook's pod-index-offset check has no test with TAS disabled, in both `ValidateCreate` and `ValidateUpdate` (`pkg/controller/jobs/mpijob/mpijob_webhook.go`, the `features.Enabled(features.TopologyAwareScheduling)` checks around `validateWorkerPodIndexOffset`). If these checks are replaced with `true`, all unit tests still pass.

The existing case `"pod-index-offset removed on update, TAS disabled"` in `TestValidateUpdate` does not cover it. It has no `RunLauncherAsWorker(true)`, so it passes with TAS enabled too.

Suggested fix: add `RunLauncherAsWorker(true)` and a wrong offset (e.g. `"5"`) to that case, and add a similar TAS-disabled case to `TestValidateCreate`. Both should fail if the check ignores the gate.
