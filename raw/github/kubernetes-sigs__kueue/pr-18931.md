## Description

#### What type of PR is this?

/kind bug

#### What this PR does / why we need it?

`limitrange.Summarize` merged `maxLimitRequestRatio` into the summary, but `ValidatePodSpec` only checked `max` and `min`. The LimitRanger admission plugin rejects a Pod whose limit to request ratio is above `maxLimitRequestRatio`. So a Workload with such Pods was admitted and took quota, and then every Pod creation was forbidden (`cpu max limit to request ratio per Container is 2, but provided ratio is 4.000000`).

`ValidatePodSpec` now checks the ratio the way LimitRanger does:
- Type `Container`: each container and init container, from its own requests and limits.
- Type `Pod`: the summed pod requests and the summed pod limits. Overhead is left out of both, as in LimitRanger. The limits are the ones the pod `max` check already computes.

The comparison follows LimitRanger in Kubernetes 1.35–1.37: the request, the limit and the maximum are first rounded up to milli units (to whole units when a value would overflow), as its `requestLimitEnforcedValues` does. The rounded values are then compared exactly (`limit > request * maxLimitRequestRatio` on the decimal quantities) instead of with float64 division. A violation adds a `field.Invalid` with the new message `limit to request ratio must not be above the limitRange maxLimitRequestRatio`. The Workload then shows the usual `resources didn't satisfy LimitRange constraints: ...` condition.

Fixes #18800

#### Useful notes for your reviewer

- Resources without both a non-zero request and a non-zero limit are skipped. LimitRanger rejects those too; they are skipped here for consistency with how the `max`/`min` checks treat missing keys. See the question in the issue.
- LimitRanger in Kubernetes 1.35–1.37 rounds the values up to milli units before it compares them, so it accepts maximum `2.0001`, request `1`, limit `2001m`. An exact compare without rounding would reject that Workload while its Pods are accepted, so the values are rounded the same way here. The float64 division is not copied: it rejects a ratio exactly equal to some fractional maximums (maximum `2.007`, request `1`, limit `2007m`), which the exact compare accepts.
- Kubernetes v1.38 (kubernetes/kubernetes#141348) compares the exact values without rounding. There, the rounding here can accept values that LimitRanger rejects (maximum `2.0001`, request `1`, limit `2001m`); such a Workload is admitted and its Pods are forbidden, as before this PR. It can be stricter than LimitRanger only when the limit has sub-milli precision (maximum `1.001`, request `1.5`, limit `1.5012`).
- No `ACTION REQUIRED:`, following #18723. The change only makes inadmissible those Workloads whose Pods LimitRanger already forbids, so they could not run before either. Admitted Workloads are not re-validated.
