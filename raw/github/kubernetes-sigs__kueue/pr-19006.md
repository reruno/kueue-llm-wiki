#### What this PR does / why we need it?

Adds a worker reconnect scenario to the MultiKueue performance benchmark, so CI can catch a regression in how long new Workloads wait behind a reconnect resync.

On a production manager, each worker reconnects about every 35 minutes, because the API server ends each watch after `--min-request-timeout` to twice that value. Each reconnect requeues every Workload of the worker, and the new watches replay an `ADDED` event for every remote object. PRs 18232, 18277 and 18407 cut the dispatch delay of new Workloads after a reconnect from about 10m30s to about 2s. Before this PR, only manual measurements covered that.

The scenario (`configs/reconnect/`):

1. Admits 3,000 preloaded Workloads across 3 workers with `workloadConcurrency: 1`, the production default, and waits until the MultiKueue workload queue stays empty.
2. Sets `--min-request-timeout` to 60s on the worker API servers only, so the manager's remote watches end and it reconnects through the production code path. The manager API server keeps its default, so the runner's own Workload watch is not affected. The baseline does not set the flag and its configuration and calibration are unchanged.
3. Creates a probe Workload every 250 ms until 3 reconnects have drained, and reports probe admission latency before, during and after reconnects (P50/P90/max).
4. Samples `workqueue_depth{name="multikueue_workload"}` by `priority` and `controller_runtime_reconcile_total` from the in-process registry every 100 ms. It reports each reconnect window (drain time, peak depth, reconciles), the peak depth by priority, and writes `queue-depth.csv`.

The checker fails when fewer than 3 reconnects are observed, when fewer than 20 probes are pending during reconnects, or when their P90 exceeds 1,500 ms. New Make targets: `run-performance-multikueue-reconnect` and `test-performance-multikueue-reconnect`. The scenario is not wired into a periodic job yet. A manager-restart scenario (issue 18938) is follow-up work. Once PR 18236 merges, the scenario can request the watch timeout from the manager instead of the worker API server flag.
