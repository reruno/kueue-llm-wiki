## Description

#### What type of PR is this?

/kind bug

#### What this PR does / why we need it?

The LimitRanger admission plugin checks pod requests against a `Pod` LimitRange Min/Max without the pod overhead. Kueue added the overhead to the requests before comparing, so a Workload whose Pods fit the LimitRange could be rejected for going over Max, and one whose Pods are below Min could be admitted. Kueue now drops the overhead from the requests the same way #18723 did for limits.

No issue filed.

#### Useful notes for your reviewer

Rebased onto #18931. The maxLimitRequestRatio check now reuses the same overhead-free requests as Min and Max, so I removed the second `podRequests` it added.

One case changes direction: a Workload whose requests reach a Pod Min only because of the RuntimeClass overhead used to pass and is now rejected, which is what LimitRanger does with its Pods. A Pod with no request at all for a Min resource is still admitted, as on main. Making that a violation would change admission for every Pod Min user, so I left it out.

| behavior | level | command and result | not run |
|---|---|---|---|
| Pod requests are checked against Pod Max/Min without the overhead | unit | `go test ./pkg/util/limitrange/... -count=1`: new cases `pod requests within max exclude overhead` and `pod requests below min exclude overhead` fail on main and pass with the fix. `go test ./pkg/workload/... ./pkg/scheduler/... ./pkg/controller/core/...` and `make ci-lint` pass. | |
| A Workload with a RuntimeClass overhead that fits Pod Max only without it gets admitted | integration | New `request within pod max without runtime class overhead` entry in the scheduler LimitRange table (1800m request, 500m overhead, Pod max 2). On main's `limitrange.go` it is rejected with `requests must not be above the limitRange max`; with the fix it is admitted. | e2e |

## AI summary

This PR excludes pod overhead from the LimitRange Pod Min/Max checks in `pkg/util/limitrange/limitrange.go`. This aligns Kueue with the LimitRanger admission plugin.

- `Summary.ValidatePodSpec` copies the pod spec and clears `Overhead`. It uses the copy for requests and limits.
- The Max check compares the larger of requests and limits against `podRange.Max`.
- The Min check compares `podRange.Min` against requests without overhead.
- Workloads can now pass Max checks that failed because of overhead. Workloads whose requests reach Min only through RuntimeClass overhead now fail Min checks.
- Pods with no request for a Min resource remain admitted.
- `limitrange_test.go` lowers the pod CPU maximum from `4` to `3` in the "pod over" and "multiple" cases. It adds "pod requests within max exclude overhead" and "pod requests below min exclude overhead."
- The integration test in `test/integration/singlecluster/scheduler/scheduler_test.go` adds a RuntimeClass overhead case. A Workload with 1800m requests and limits, plus 500m overhead, is admitted under a pod CPU maximum of 2.

The author reports that the LimitRange tests and `make ci-lint` pass. Integration and e2e tests were not run by the author.

### Suggested release note

```text
Workloads: Fixed a bug where LimitRange Pod Min/Max checks counted RuntimeClass overhead, which could cause Workloads to be wrongly rejected or admitted. Now Kueue excludes Pod overhead from these checks, matching the LimitRanger admission plugin.
```
