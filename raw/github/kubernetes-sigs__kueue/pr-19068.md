## Description

#### What type of PR is this?

/kind bug

#### What this PR does / why we need it?

A ClusterQueue that is not active (`stopPolicy: Hold`, or deleted and held by its finalizer) was left out of the scheduler snapshot tree, while its Workloads still counted in the Cohort's usage. Preemption only searches the tree, so a sibling with `reclaimWithinCohort: Any` could not reclaim the quota those Workloads borrowed.

The snapshot now keeps `NotActive` ClusterQueues in the tree and still lists them in `InactiveClusterQueueSets`, which the scheduler checks before nominating a Workload, so they still cannot admit. ClusterQueues in a cohort cycle or with unsynced TAS usage stay out of the tree as before; `skipInactiveCQReason` now checks those two first, because a ClusterQueue in a cycle is also not active.

Fixes #19064

| behavior | level | command and result | not run |

| No regression | unit | `go test ./pkg/cache/... ./pkg/scheduler/...`: pass | other integration suites (CI) |

The new specs have no `slow` or `redundant` label, so `test-integration-baseline` selects them.

Because an inactive ClusterQueue now stays in the scheduler snapshot, its admitted Workloads are also visible to the other readers of `snapshot.ClusterQueues()`:

- Configurable preemption (`pkg/scheduler/preemption/config/evaluator.go`): they can be selected as candidates when a rule's scope, label and priority filters match, as classical reclaim can now pick them. The preemptor still comes only from an active ClusterQueue, because `nominateWorkload` rejects heads of inactive ClusterQueues first.
- `inFlightEvictionVictims` (`pkg/scheduler/scheduler.go`): an evicted Workload of an inactive ClusterQueue now counts as an in-flight eviction for the deferred TAS replacement check. Its eviction frees its quota and TAS usage whether or not the ClusterQueue is active, the inactive ClusterQueue does not readmit it, and the simulated removal is reverted after the check.

One open question, also in #19064: this also makes these Workloads candidates for fair sharing. I think that is intended, since they hold cohort quota, but please say if Hold should instead protect its Workloads from preemption.

This PR was written in part with the assistance of generative AI.

```release-note
Scheduling: Fixed a bug where a ClusterQueue with `stopPolicy: Hold`, or one being deleted, kept the quota its Workloads borrowed from the cohort, so other ClusterQueues could not reclaim it by preemption.
```
