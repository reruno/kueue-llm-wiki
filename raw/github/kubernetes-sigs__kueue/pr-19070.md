#### What this PR does / why we need it?

When a pending Workload changes `spec.queueName` from a LocalQueue without ConcurrentAdmission to a LocalQueue whose ClusterQueue has `concurrentAdmissionPolicy`, it becomes a Parent. `AddOrUpdateWorkloadWithoutLock` returned early for a Parent before the code that removes a Workload from its previously assigned queue, so the Workload stayed queued in the old LocalQueue and ClusterQueue. The old ClusterQueue could then admit it and start the Job, and the ConcurrentAdmission controller evicted it again with `ConcurrentAdmissionDisabled`. The old LocalQueue kept reporting it as pending.

This PR fixes both paths that put a moved Parent in the wrong queue:

1. `AddOrUpdateWorkloadWithoutLock`: when the Workload is a Parent and its queue changed, it is removed from the old LocalQueue and ClusterQueue before the early return, as a regular Workload is.
2. `requeueWorkloadLocked`: when the Workload changed queue while the scheduler had it checked out, the requeue removed it from the old queue and then added it to the new LocalQueue, even though it is now a Parent. It is now not queued again. The inflight entry is already cleared at the start of the function, so returning early leaves nothing behind.

Fixes #18939

## AI summary

This PR fixes a queue cleanup bug. It applies to Workloads that change LocalQueue while the ConcurrentAdmission feature gate is enabled.

Before this change, `Manager.AddOrUpdateWorkload` returned early for a concurrent-admission parent. That return skipped cleanup of the Workload's previous queue assignment. The Workload stayed pending in the old LocalQueue and ClusterQueue. The old ClusterQueue could admit it and start its Job.

The change:

- `AddOrUpdateWorkloadWithoutLock` in `pkg/cache/queue/manager.go` reads the Workload key, LocalQueue key, and prior queue assignment before the parent check. If a parent's LocalQueue assignment changed, the manager deletes the Workload from the old queue and clears the assignment before it returns.
- `requeueWorkloadLocked` checks whether the refreshed Workload became a parent while the scheduler had it checked out. If so, it returns without requeuing the Workload in the new LocalQueue.
- Unit tests in `pkg/cache/queue/manager_test.go` (`TestWorkloadMovedToConcurrentAdmissionQueue`) cover the direct update path and the requeue-after-checkout path. They run with the gate enabled and disabled.
- An integration test in `test/integration/singlecluster/controller/concurrentadmission/concurrent_admission_test.go` covers a Workload that moves to a ConcurrentAdmission LocalQueue. It checks that:
  - the Workload becomes a labeled parent with a flavor variant;
  - the old queue pending counts and metric no longer include it;
  - the Workload is counted once in the new queue;
  - the Workload stays unadmitted after the old ClusterQueue gets quota.

The change does not cover a Workload that becomes a parent without a queue change.

Test results: the author reports that the targeted unit tests, the `pkg/cache/queue`, `pkg/controller/core`, and `pkg/controller/concurrentadmission` test packages, and the integration test package (16/16) passed. These results were not verified against the current head.
