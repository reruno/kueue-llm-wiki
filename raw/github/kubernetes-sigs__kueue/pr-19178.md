#### What this PR does / why we need it?
An unmanaged RayJob, RayCluster, RayService, or SparkApplication skips admission checks, so it can keep a `kueue.x-k8s.io/wait-for-pods-ready` annotation above `waitForPodsReady.maxTimeoutOnWorkload`. Adding `kueue.x-k8s.io/queue-name` makes the object managed, but the annotation was checked only when its value changed.
`ValidateWaitForPodsReadyAnnotationOnUpdate` now applies the create-time checks, including the maximum, when the object gains a queue-name label. An unchanged annotation on an object that already has a queue-name label is still accepted, so lowering the maximum does not block later updates such as suspension. The same queue-name transition is covered for every integration that uses this helper.
This change was prepared with AI assistance.

Fixes #19148

#### Release note
```release-note
WaitForPodsReady: Fixed a bug where adding `kueue.x-k8s.io/queue-name` did not check an unchanged `kueue.x-k8s.io/wait-for-pods-ready` annotation against `waitForPodsReady.maxTimeoutOnWorkload`, so an unmanaged RayJob, RayCluster, RayService, or SparkApplication could become managed with `timeoutSeconds` or `recoveryTimeoutSeconds` above the maximum.
ACTION REQUIRED: Before adding `kueue.x-k8s.io/queue-name` to an existing object whose annotation exceeds `waitForPodsReady.maxTimeoutOnWorkload`, lower `timeoutSeconds` and `recoveryTimeoutSeconds` to that maximum, or raise the configuration. This applies when `WorkloadLevelWaitForPodsReady` is enabled. An unchanged annotation on an object that already has a queue-name label is still accepted.
```

## AI summary

`ValidateWaitForPodsReadyAnnotationOnUpdate` now also validates an unchanged WaitForPodsReady annotation when an object gains a queue-name label. This check applies when `WorkloadLevelWaitForPodsReady` is enabled. Objects that already have a queue-name label are not rechecked when the annotation is unchanged. A RayJob with a non-empty `spec.clusterSelector` is excluded. The Job webhook comment is updated to match.

## Suggested release note

```text
WaitForPodsReady: Fixed a bug that allowed a RayJob, RayCluster, RayService, or SparkApplication to become managed with a wait-for-pods-ready timeout above `maxTimeoutOnWorkload` when the queue-name label was added without changing the annotation. Now Kueue rejects the update. This behavior is gated by the WorkloadLevelWaitForPodsReady feature gate. Before adding the queue-name label, lower `timeoutSeconds` and `recoveryTimeoutSeconds` to the maximum, or raise the configured maximum.
```
