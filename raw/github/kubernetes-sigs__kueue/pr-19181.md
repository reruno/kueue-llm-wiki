#### What this PR does / why we need it?
Follow-up to #17903, split out as requested in https://github.com/kubernetes-sigs/kueue/pull/17903#discussion_r4598126128.

When the spec of a manager job that implements `MultiKueueLocalJobWatcher` changes, the MultiKueue workload controller queues every Workload owned by the job. Since #17903, LeaderWorkerSet is such a job, and it has one Workload per group. `SyncJob` syncs the whole job to the worker, so only the first reconcile patches the remote LeaderWorkerSet. The other N-1 reconciles only read it again from the worker.

With this PR, the controller queues one Workload per worker. It skips Workloads that are not on a worker yet or are finished, because they have no remote job to sync.

`localJobHandler.queue` now enqueues at most one Workload per worker cluster when a manager job spec changes. It skips Workloads that have no assigned cluster, Workloads whose cluster is already queued, finished or evicted Workloads, and Workloads with a deletion timestamp. The change is in `workload.go`, with new `TestLocalJobHandlerUpdate` cases in `workload_test.go`.

## Suggested release note

```text
MultiKueue: Fixed a bug that caused the manager to read the same remote job once for each Workload of a job with many Workloads, such as a LeaderWorkerSet, after a spec change. Now Kueue reads the remote job once per worker cluster.
```
