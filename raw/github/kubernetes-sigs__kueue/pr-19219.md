#### What this PR does / why we need it?
Thanks @reruno for the detailed report and the code pointers, they made this straightforward to reproduce.

With partial scale-up, evicting a partially admitted slice that has a pending scale-up probe left the job suspended while the probe held quota.

- Preemption or drain: per KEP-12100, the probe stays in the queue and is readmitted. If the readmission is partial, a new probe is created, and the job reconciler got that pending probe and never started the job. Now, when the job is suspended and its workload is a pending probe, the job starts on the admitted slice that the probe replaces, unless that slice is being deleted.
- Deactivation: the slice's quota leaves the scheduler cache as soon as it is deactivated, so the probe was admitted on its own into the freed quota and replaced the deactivated slice. The job stayed suspended while the probe held quota, and reactivating the slice had no effect. Now the scheduler does not admit a probe whose predecessor slice is deactivated, the job reconciler deletes such a probe, and no new probe is created from a deactivated slice. A new probe is created after the slice is reactivated and admitted.

Fixes #19046

Changes since the last push:
- Rebased on main (including #19154 and #19249; the guard still runs before planner selection, and #19249's minCount reduction does not create probes or touch the replacement annotation).
- The scheduler check now ignores a predecessor that has finished. A finished predecessor was already replaced and holds no quota, so deactivating it releases nothing. Before, deactivating it blocked the slice that replaced it from being admitted again, for example after that slice was deactivated and reactivated. The new integration spec and unit case above reproduce it.
- The log line for deleting a probe moved to `V(4)`, because it is written before the API call.
- The test fixtures in `TestAdmittedSliceReplacedByProbe` are built from a cloned wrapper instead of a closure.

Known limitation, not introduced by this PR: the scheduler checks the predecessor's `spec.active` when it nominates the scale-up probe (`ReplacedSliceDeactivated`, called from `nominateWorkload` in `pkg/scheduler/scheduler.go`), but the admission patch is applied asynchronously. A deactivation that lands between nomination and that patch still lets the probe reserve quota, after which `replaceWorkloadSlice` finishes the deactivated predecessor and the job keeps running on the probe. On the base branch the same happens without any window restriction, so this PR narrows the race rather than widening it; closing it fully would require handling already-reserved successors during deactivation, which is left for a follow-up.

One more race comes from the deletion path this PR adds, so it is not covered by the paragraph above: if the deactivation lands while the scheduler's admission patch for a probe it already nominated is in flight, `deleteProbesOfDeactivatedSlices` can delete that probe right after it is admitted. It decides on the copy it read (`HasQuotaReservation`), and `workload.Delete` removes the finalizer and deletes without a resourceVersion precondition. `normalizeActiveSlices` already deletes a withdrawn scale-up replacement with the same unconditioned call (`pkg/workloadslicing/workloadslicing.go`), so I followed that pattern here. A precondition alone is not enough, because the finalizer is removed before the delete and nothing adds it back. If you'd prefer, I can add a precondition-safe delete for pending slices in this PR or in a follow-up.

A probe that the scheduler refuses because its slice is deactivated is left inadmissible, and it is not retried when the slice is reactivated. This shows only in a scheduler-only setup without the job reconciler. With the job reconciler, the pending probe is deleted when its slice is deactivated, and a new probe is created after the slice is reactivated and admitted ("Should not admit the pending scale-up probe of a deactivated slice" in `job_controller_partial_scaleup_test.go`). If you would like the scheduler to retry such a probe on its own, I can add a wake-up on reactivation.

## AI summary

This PR fixes elastic jobs that stay suspended while a pending scale-up probe holds quota.

- The job reconciler starts a suspended job on its admitted predecessor slice when a pending probe replaces that slice. It does this unless the slice is being deleted.
- The scheduler does not admit an unreserved probe whose predecessor is deactivated. It retries after a delay if the predecessor lookup fails.
- `EnsureWorkloadSlices` deletes unreserved probes that replace deactivated slices.

The behavior is gated by the `ElasticJobsViaWorkloadSlices` feature gate.
