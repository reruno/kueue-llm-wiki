**AI summary**

This change raises two validation limits from 20 to 50:

- `MultiKueueConfig.spec.clusters`, in the Go API and CRD manifests.
- `Workload.status.nominatedClusterNames`, in the Go API and CRD manifests. The AllAtOnce dispatcher nominates every cluster in the MultiKueueConfig, so this limit must match.

The change also adds webhook integration tests. They check that 50 entries are accepted and 51 are rejected.

**Suggested release note**

```text
MultiKueue: Increased the maximum number of clusters in a MultiKueueConfig from 20 to 50, allowing a workload to use up to 50 clusters.

### Comment by [@mimowo](https://github.com/mimowo) — 2026-11-20T18:28:30Z

Yeah, we will share some benchmarks. I think it is ok to ask.

At the same time I share the sentiment that performance should non-blocking for validation limits. If we block users then it is hard to collect data - many users walk away annoyed that the project cannot support their scale, or fork, and don't report any feedback. From my experience only a small portion of users actually report "please bump validations" (most forks), or they would tell me while Oncalling. So we need to know that "No oss issue" doesn't mean "users happy with validation".

So, I think it is healthy to allow for a bit more than we are comfortable with, collect feedback, and improve performance.

Also, performance is a very multi-dimensional problem while the validation is usually one dimension.  So it may turn out that MultiKueue at 50 clusters cannot process at the same rate (per cluster) as when using 2 clusters, sure.

Still, validation plays sometimes a role of guiding users. Registering 10k clusters would probably mean someone is doing something wrong. Registering 100 clusters I don't think would be wrong, and I'm sure some users will quickly (a year) reach the scale of 100 clusters.

> **Remove nominations for clusters that left the configuration before appending new ones.**
> 
> The incremental dispatcher appends new nominations to `wl.Status.NominatedClusterNames` without filtering out names that are no longer in `remoteClusters`. A workload that already holds 50 nominations can therefore receive a 51st entry after one configured cluster is replaced. `NominatedClusterNames` is limited to 50 items, so the status patch fails. `nominateWorkers` then returns an error and does not update the round start time, so each reconcile repeats the same failing append. The workload stops making nomination progress until its nominations are reset elsewhere.
> 
> Stale nominations for removed clusters must not count against the limit. The resulting list must stay at or below 50 entries and must reflect the current configuration. The exact pruning rule is a design choice for the maintainers. The change must make sure that a permitted configuration update cannot push the nominated list past the status limit.
