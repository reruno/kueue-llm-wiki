#### What this PR does / why we need it?

Fixes #19226, part of partial scale-up for elastic jobs tracked in #12100.

The SparkApplication integration set the executor PodSet's `minCount` to `minExecutors` on every slice, so with the partial scale-up strategy the first slice could be admitted partially. Kueue then created a scale-up probe and selected it as the active slice, so the SparkApplication was never unsuspended, while the admitted slice held its quota.

- `PodSets` sets the executor `minCount` to the executor count, as batch/Job (`podsCount()`) and Ray (`effectiveWorkerCount`) do. The first slice is admitted all-or-nothing, as KEP-12100 requires, and later scale-up slices copy this floor forward.
- Docs: the first admission of an elastic SparkApplication is all-or-nothing.

#### Useful notes for your reviewer

- Why this needed #19249 (merged): this PR raises the floor from `minExecutors` to the initial executor count. With dynamic allocation, the driver removes idle executors down to `minExecutors`, below the new floor. If that happens while a scale-up probe is pending, the probe update fails validation and the reconcile fails on every retry, so the admitted slice keeps its quota, even after the app completes. With the old floor Spark could not reach that path. The integration test "Should update a pending scale-up probe when the executors drop below its minCount" covers it.
- Integration test for #19226: "Should admit the first workload all-or-nothing" replaces "Should partially admit the first workload and create a scale-up probe", which asserted the partial first admission but never checked that the app starts. With another app holding part of the quota, the Workload stays pending with no quota and no probe, and the app stays suspended. Once the quota frees up, all executors are admitted and the app starts. It fails on the old code.
- Scale-down below the initial count of an admitted slice is covered by #16742 and the existing test "Should scale down the admitted workload below its initial executor count".

#### Release note

```release-note
SparkApplication: Fix a bug where an elastic SparkApplication with the partial scale-up strategy, whose initial executors did not fit, was admitted partially but never started, while holding quota. Its first admission is now all-or-nothing.
```

## AI summary

- SparkApplication: For elastic partial scale-up, the executor PodSet `minCount` now equals the executor count instead of `minExecutors`. The first slice is admitted all-or-nothing. The app stays suspended and holds no quota until all initial executors fit.
- Workloads: `CanReduceMinCountOnScaleDown` also applies to pending scale-up replacement slices. When executors scale down below such a slice's `minCount`, Kueue lowers that slice's stored `minCount`. The initial Workload keeps its `minCount` until admission.
- Tests and docs: Integration tests cover all-or-nothing first admission, app start after quota frees, and pending probe updates. The SparkApplication docs state that partial scale-up applies only after initial admission.

SparkApplication: Fixed a bug that caused an elastic SparkApplication with partial scale-up to be partially admitted on its first slice and never start when the initial executors did not fit. Now Kueue admits the first slice all-or-nothing, and the application starts after all initial executors fit.
