## Description

#### What type of PR is this?

/kind bug

#### What this PR does / why we need it?

With `PartialPreemption` and the `partial` scale-up strategy, a Workload that partial preemption shrank does not grow back as quota frees. Its Pods stay gated until the whole job fits again. KEP-975 says it should grow back as quota frees.

Cause: partial preemption lowers a PodSet's admitted count below its minimum. The scale-up slice copies that minimum, which equals its count, so the scheduler skipped partial admission. This PR drops that precheck. The reducer already returns early when no PodSet can shrink, and its baseline is the admitted count of the slice being replaced.

Found while testing RayCluster partial preemption (#19224).

Part of #975

1. Apply `00-setup.yaml` and `01-shrinkable.yaml`, and wait until `shrinkable` runs 3 Pods. They use all 3 Pods of quota.
2. Apply `02-preemptors.yaml`. Each preemptor needs 1 Pod, so `shrinkable` shrinks to 1 Pod.
3. Run `kubectl delete job preemptor-2 -n pp-repro`.
4. Run `kubectl get pods,workloads -n pp-repro`. Without the fix, `shrinkable` stays at 1 running Pod and its scale-up Workload waits with `insufficient unused quota for pods in flavor pp-repro-rf, 1 more needed`. With it, `shrinkable` runs 2 Pods, and 3 once `preemptor-1` is deleted.

### Comment by [@zhengchenyu](https://github.com/zhengchenyu) — 2026-11-21T01:01:27Z

I also encountered this issue during testing, but I marked it as not a bug. Because minCount is set to the initial Count for ElasticJobsViaWorkloadSlicesWithPartialReplicaScaleUp, partially preempted jobs can only be scheduled when resources satisfying minCount are available. This is a design limitation of ElasticJobsViaWorkloadSlicesWithPartialReplicaScaleUp. Its initial scheduling behaves somewhat like gang scheduling and cannot coexist with minCount.
In my cases https://github.com/zhengchenyu/cases/tree/main/kueue/partial-preempt, if we configure a low parallelism (i.e., a low minCount) upfront and then perform scaling up, partial preempted jobs can be scaled up again after being partially preempted.

  `Reduce` already does this check: it returns early when no PodSet can shrink (`totalDelta == 0`). It also uses the right floor: for a scale-up slice with an admitted predecessor, `effectiveReducerPodSets` uses what the predecessor still holds as each PodSet's minimum.
  
  `CanBePartiallyAdmitted()` read the spec minimum instead. After partial preemption, the scale-up slice has count 5 and minimum 5 while the predecessor holds 1, so this check skipped a scale-up the reducer would have admitted.
