#### What this PR does / why we need it?

`ListChildWorkloads` for a pod group did two things: it listed the Workload named
after the group, and with `PodIntegrationValidateGroupOwner` it silently returned
nothing when that Workload was controller-owned by another job, so the reconciler
would not finalize it. As agreed in the issue, this splits the two:

- `ListChildWorkloads` returns the same-named Workload without filtering it.
- A new optional interface, `JobWithCustomWorkloadFinalization`, lets a job veto
  finalization of a listed Workload. `finalizeWorkloads` skips a vetoed Workload
  and logs it at V(2), as the removed branch did.
- `Pod.CanFinalizeWorkload` holds the ownership rule: with the gate on, a pod
  group may not finalize a Workload that has a controller reference. A single pod
  and the gate-off path keep their behavior.

One behavior change, following CodeRabbit's review: the `is-group-workload`
annotation no longer exempts a controller-owned Workload. The annotation can be
set by whoever creates the Workload and does not prove ownership, and a pod group
only adds non-controller owner references, so a controller reference means the
Workload belongs to another job. Before, a Workload with both the annotation and a
foreign controller reference lost its `resource-in-use` finalizer and quota when a
pod group with its name emptied.

This takes over #15717 by @chandan009s, as @mbobrovskyi suggested there. Their two commits are kept and rebased on current main (the merge commit is dropped), with the conflicts resolved: the finalization veto now runs before the newer check for a live managed owner, so a foreign Workload is not touched at all. The follow-up commit is on top.

Fixes #15463

#### Useful notes for your reviewer

- The last commit carries the behavior change above. If you prefer the pure
  refactor, it can be dropped without touching the rest.
- `FindMatchingWorkloads` still adopts any Workload that carries the annotation,
  controller reference or not. That path is unchanged here.
- The all-terminating gate (`FinalizeTerminatingPodGroups`) reads the Workload by
  name in `Load` and never depended on `ListChildWorkloads` hiding it; only its
  test comment changed.

Tests (each fails on main, or is a mutation check):
- `TestReconciler`: a new case where an emptied pod group leaves a same-named Workload with the group annotation and a foreign controller owner untouched. It fails on main. The existing cases still pass: a foreign Workload kept with the gate on, finalized with the gate off, and own and prebuilt group Workloads finalized.
- `TestPod_CanFinalizeWorkload`: the group Workload owned by its pods, a Workload without a controller, a foreign controller owner, a controller owner with the group annotation, gate off, and a single Pod.
- Integration: the existing spec "Should not finalize a foreign Workload sharing the group name when the pod group has no pods" still passes with the whole Pod suite.

Restoring the annotation bypass in `CanFinalizeWorkload` makes the new `TestReconciler` case and the annotation case of `TestPod_CanFinalizeWorkload` fail.

### Review by [@abhinavkdeval08-design](https://github.com/abhinavkdeval08-design) (commented) — 2026-11-21T11:45:28Z

Thanks for working on this! Decoupling workload discovery in `ListChildWorkloads` from the finalization veto via `JobWithCustomWorkloadFinalization` makes the controller logic much cleaner and addresses the foreign workload visibility issue nicely.

A couple of minor observations and questions:

1. **Defensive nil check in `CanFinalizeWorkload`:**
   In `pkg/controller/jobs/pod/pod_controller.go`:
   ```go
   func (p *Pod) CanFinalizeWorkload(wl *kueue.Workload) bool {
   	if !features.Enabled(features.PodIntegrationValidateGroupOwner) || !p.isGroup {
   		return true
   	}
   	return metav1.GetControllerOfNoCopy(wl) == nil
   }
   ```
   Since `CanFinalizeWorkload` is an exported interface method, should we add a defensive guard `if wl == nil { return false }` before `metav1.GetControllerOfNoCopy(wl)` to avoid potential nil dereference panics if called outside `finalizeWorkloads`?

2. **Dropping the `is-group-workload` annotation check:**
   Dropping `workload.Annotations[podconstants.IsGroupWorkloadAnnotationKey] != podconstants.IsGroupWorkloadAnnotationValue` makes total sense. Pod groups only add non-controller owner references (`EnsureWorkloadOwnedByAllMembers`), so if a controller reference is present, the pod group should not finalize it regardless of annotations.

3. **Follow-up on `FindMatchingWorkloads`:**
   As you noted in the PR description, `FindMatchingWorkloads` still matches on the annotation even if a controller reference is present. Do you see that as something worth addressing in a follow-up PR, or is there a case where a pod group intentionally adopts a controller-owned workload?

Overall the test coverage and separation of concerns look very solid.

  @mimowo, before we go further with the new interface, a question about #15463. Do we need a separate `CanFinalizeWorkload` check at all, or can we keep the filter in `Pod.ListChildWorkloads` and only fix the comments?
  
  I think the filter is about ownership, not finalization:
  
  - A Workload controlled by another job is not a child of the pod group. Kueue only adds non-controller owner references to group Workloads, including prebuilt ones (`EnsureWorkloadOwnedByAllMembers`). So leaving such a Workload out is what `ListChildWorkloads` should do anyway. `ensureOneWorkload` already does the same for prebuilt Workloads controlled by another object.
  - Only `finalizeWorkloads` uses the result. `FinalizeTerminatingPodGroups` reads the Workload by name in `Load`, so no caller needs the foreign Workload.
  - I think the confusion came from the comment and the log ("not finalizing") and from the fact that an empty result can be read as "no Workload with this name exists". A clear contract on `ComposableJob.ListChildWorkloads` fixes both.
  - External integrations implement the `jobframework` interfaces, so a new method there is hard to change or remove later. And only Pod would implement it.
  
  So the change would be:
  1. Remove the `is-group-workload` exemption in `Pod.ListChildWorkloads`. This is the bug fix from the last commit.
  2. Rewrite the comment and log there in terms of ownership.
  3. Document on `ComposableJob.ListChildWorkloads` that it returns only Workloads the job owns, and that an empty result does not mean no Workload with that name exists.
  
  WDYT? cc @YevheniiOrlovEngineering @vladikkuzn
