## Description

#### What type of PR is this?

/kind bug

#### What this PR does / why we need it?

When a preemption target is deleted after the scheduling snapshot, for example when a user deletes a Deployment and many Workloads go away at once, its eviction returns NotFound. `IssuePreemptions` treated that as a failed preemption:
- it cancelled the parallel evictions of the other targets of the same preemptor;
- the scheduler logged `Failed to preempt workloads` at error level;
- the preemptor was requeued as "Preempting N workload(s) failed, will retry" instead of waiting for its other targets.

A deleted target needs no eviction. It now counts as preempted: its preemption expectation is released, the other evictions continue, and the deletion is logged at V(3). No `Preempted` event or metric is recorded for it, since Kueue did not evict it.

The scheduler cache keeps the target until its Delete event, as for any other deleted Workload. The workload controller then releases its quota and requeues the inadmissible workloads.

This takes over #10874 by @jzhaojieh, who didn't reply for a week. Their commit is kept and rebased onto main, and a second commit reworks it:
- The original change also removed the target from the scheduler cache on NotFound. As discussed on #10874, the stuck cache entries came from the lost Delete events fixed for #10495. Removing the entry from the preemption path would duplicate the Delete handler's work and skip the requeue of inadmissible workloads that the handler does, so this PR leaves cache cleanup to the Delete event.
- Their standalone test is replaced by a case in the existing `TestPreemption` table.

Related: #10874, #10495

#### Useful notes for your reviewer

- @mimowo's review comment on #10874 pointed at the status update error in `requeueAndUpdate`. #18750 has since handled NotFound there and in `waitForPodsReadyIfNeeded`, so this PR changes only the preemption path. With this change, `issuePreemptions` in `scheduler.go` no longer receives a NotFound error, so it no longer logs it.
- #18338, merged since, added a similar branch next to this one, for a target that lost its quota reservation during a merge-patch retry.
- Not changed: the flavor-migration eviction in `scheduler.go` still logs NotFound as an error. Migration is not preemption, so I left it for a separate change.

Test: a `TestPreemption` case where one of two targets is deleted from the API server after the snapshot. It counts as preempted, and the other target is still evicted, with `WorkloadRequestUseMergePatch` off and on. On main it fails with `Failed doing preemption: workloads.kueue.x-k8s.io "mid" not found`. `pkg/scheduler/...` passes, and golangci-lint reports no issues.

An integration test isn't added: the deletion has to land between the snapshot and the eviction inside one scheduling cycle, which can't be made deterministic at that level.
