#### What this PR does / why we need it?

Follow-up to #18931. The LimitRanger admission plugin rejects a Pod when a LimitRange constraint needs a request or a limit and the Pod does not have it. `limitrange.Summary.ValidatePodSpec` skipped those resources, so the Workload was admitted and took quota, and then every Pod creation was forbidden.

`ValidatePodSpec` now rejects these cases:

- `maxLimitRequestRatio`, type `Container` and type `Pod`: the request or the limit is missing or zero (`cpu max limit to request ratio per Container is 2, but no limit is specified or limit is 0`).
- `max`, type `Pod`: the pod has no limit for the resource (`maximum cpu usage per Pod is 2.  No limit is specified`).
- `min`, type `Pod`: the pod has no request for the resource (`minimum cpu usage per Pod is 1.  No request is specified`).

Each case adds a `field.Invalid` with a new message, and the Workload shows the usual `resources didn't satisfy LimitRange constraints: ...` condition. The pod requests and limits leave overhead out, as in LimitRanger.

Fixes #19235

#### Useful notes for your reviewer

- `max` and `min` of type `Container` are not changed. The issue says they have the same gap, but that only holds for a LimitRange built in a unit test. The API server defaults a `Container` item (`SetDefaults_LimitRangeItem`): `default` from `max`, and `defaultRequest` from `default` or `min`. Kueue applies those defaults before it validates, so the container always has the value. On a 1.37 API server, a Pod with a cpu request and no cpu limit is accepted under a `Container` `max`, and a Pod with no cpu request is accepted under a `Container` `min`. The new integration entry `no limit with container max` records this.
- A `Pod` item gets no defaults, and `maxLimitRequestRatio` has no default in either type, so these three cases reach LimitRanger.
- When the limit is missing under a `Pod` `max`, LimitRanger reports only the missing limit. Here the request is still compared with `max` too, so a Workload can show both messages.
- The shared pod spec of `TestValidatePodSpec` and two `TestValidateLimitRange` cases set cpu requests without limits under a `Pod` `max`. LimitRanger forbids such Pods, so cpu limits equal to the requests were added to keep what these cases test.
- No `ACTION REQUIRED:`, as in #18931. The change only makes inadmissible those Workloads whose Pods LimitRanger already forbids.
