#### What this PR does / why we need it?

Fixes #19297

When a StatefulSet changes its TAS annotations while its Workload has reserved quota and is waiting for admission, the Workload can keep the topology request and placement computed from the old template. For example, a two-replica workload reserved across two hosts can still be admitted after the template changes to require a single host.

The StatefulSet reconciler requests deletion of a reserved, unadmitted Workload whose topology request no longer matches the template. It uses the Workload UID and resource version as delete preconditions so admission or another update that wins the race is respected. The PodGroup controller handles finalization, including cleanup of any still-gated member Pods. The StatefulSet then creates a Workload from the current template. The replacement must reserve quota and complete its own admission checks.

This follows the discussion in [#18868](https://github.com/kubernetes-sigs/kueue/pull/18868#issuecomment-7077056612). #18868 synchronizes changes before quota reservation, and #19291 guards the scheduler's first reservation write.

#### Useful notes for your reviewer

The replacement path uses the existing Pod activity check. A Workload that reaches Admitted before the delete is committed is kept. The StatefulSet and Workload are separate API objects, so a StatefulSet template update and a Workload admission are not one transaction.

The StatefulSet reconciler now replaces an unadmitted Workload that holds quota for an outdated TAS topology request. When TAS is enabled, the reconciler compares the reserved topology request with the current Pod template. If they differ, it waits while owned Pods remain active. Otherwise, it deletes the stale Workload with UID and resource-version preconditions. A concurrent admission keeps the Workload. Kueue then creates a Workload from the current template.

> I just wondering, For a Workload that is already Admitted, the template change is accepted but the Pods are re-placed by the old assignment. Is that intentionally out of scope here? Should the webhook reject the change, or should we emit a warning event?

Thanks, Henry. Yes, that's intentional. For StatefulSet, #18868 updates the existing Workload while it is waiting for quota. This PR handles the next stage by replacing an eligible stale reservation while admission is still pending. #19418 follows the same boundary for LWS and accounts for the template revision each group uses during a rollout.

Once a Workload is admitted, both integrations keep its existing TAS assignment. A template update can therefore leave replacement Pods using the previous placement. I'd handle this as a shared follow-up for both integrations. My preference would be to start with a Warning event when the topology request in the applied template differs from the one in the admitted Workload. For LWS, that means checking the revision each group actually uses. We can discuss whether the webhook should reject those updates in the same follow-up.
