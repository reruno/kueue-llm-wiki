## Description

#### What type of PR is this?

/kind bug

#### What this PR does / why we need it?

When a Pod label update conflicts, the importer reloads the Pod and retries the write. If another actor assigned the Pod to a different LocalQueue, the retry could overwrite that assignment. If the Pod was replaced under the same name, the importer could label the replacement and admit a Workload owned by the original Pod UID.

Check the reloaded Pod's UID and queue label before retrying. If either conflicts with the original import, stop before writing labels or creating a Workload.

#### Useful notes for your reviewer

- Added tests for a concurrent queue assignment, a same-name Pod replacement, and a successful retry that preserves an unrelated label change.
- Both race tests failed on upstream `main` and passed with the fix. All four importer packages passed their Go tests.
- Generative AI assisted with investigation, implementation, and validation.

#### Release note

```release-note
Pod importer: Preserve concurrent LocalQueue assignments and leave same-name replacement Pods untouched when retrying a label update.
```

## AI summary

The importer now reloads a Pod after a label-update conflict. It stops if the Pod UID changed or if the Pod has a different LocalQueue label. In those cases, it does not retry the label write and does not create a Workload.

- `cmd/importer/pod/check.go`: Adds `validatePodQueueLabel` and uses it in `checkPodWorkload`.
- `cmd/importer/pod/import.go`: `addLabels` checks the reloaded Pod UID and queue label before it applies labels.
- `cmd/importer/pod/import_test.go`: Adds cases for a conflicting queue label, an unrelated label change, and a same-name replacement Pod.

### Suggested release note

```text
Importer: Fixed a bug that caused the importer to overwrite a Pod's queue label or import a Workload for a replaced Pod when a Pod update conflicted. Now Kueue checks the Pod UID and queue label after the conflict and stops the import if either changed.
```
