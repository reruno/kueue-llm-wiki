## Description

#### What type of PR is this?

/kind bug

/area multikueue

#### What this PR does / why we need it?

The job webhooks default `spec.managedBy` to `kueue.x-k8s.io/multikueue` when the job's LocalQueue points to a ClusterQueue with a MultiKueue AdmissionCheck. They did that also for a job in a namespace that `managedJobsNamespaceSelector` doesn't match. Kueue doesn't reconcile such a job, so nothing dispatched it, and its own controller ignored it because of `managedBy`.

`ApplyDefaultForManagedBy` now checks the namespace selector before setting `managedBy`, and only when it would set it, so other jobs cost no extra Namespace read. It takes the context, client and selector, and returns the error of that read; all job webhooks that call it are updated.

Fixes #19305

#### Useful notes for your reviewer

- Follow-up from CodeRabbit's comment on #19270, which fixes the same gap in the suspend default. The two PRs touch the same `TestDefault` runner, so whichever lands second needs a small rebase. Once both are in, a job in an unmanaged namespace is neither suspended nor handed to MultiKueue.
- Test: two `TestDefault` cases for the Job webhook, a MultiKueue ClusterQueue with the job in a managed and an unmanaged namespace. The unmanaged case fails on main. The webhook and MultiKueue integration suites pass.

I used an AI assistant while preparing this PR.

```release-note
MultiKueue: Fixed a bug where a job in a namespace that doesn't match `managedJobsNamespaceSelector` got `spec.managedBy` set to MultiKueue when its LocalQueue used a MultiKueue ClusterQueue, so the job never ran.
```
