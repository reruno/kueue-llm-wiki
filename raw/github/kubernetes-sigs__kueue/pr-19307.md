## Description

#### What type of PR is this?

/kind bug

#### What this PR does / why we need it?

With Admission Fair Sharing, a LocalQueue whose ClusterQueue is inactive (for example on `Hold`) returned from `Reconcile` before sampling its consumed usage, and scheduled no further sample. Its admitted Workloads keep running, finish or get evicted, so their usage during that time was not sampled. The first sample after the ClusterQueue became active applied the usage left at that moment to the whole gap, so a Workload that finished during the hold was undercounted.

The inactive-ClusterQueue branch now returns only on a status update error, like the active branch, and then reaches the existing AFS sampling block unchanged. With AFS disabled the behavior is the same as before.

A new ClusterQueue has no `Active` condition yet, so it now reaches the sample too, possibly before `ClusterQueueReconciler` caches it. That case, and an Active ClusterQueue that isn't cached yet right after a restart, skips the sample instead of returning `ErrCqNotFound` and retries after the sampling interval.

Fixes #19286

#### Useful notes for your reviewer

- This is the ClusterQueue-side counterpart of #19267, which keeps sampling for a stopped LocalQueue and lists this case as out of scope. The two fix different branches of `Reconcile` but both edit `localqueue_controller.go`, so whichever merges second needs a rebase.
- It covers every inactive reason, not only `Hold`, since admitted Workloads use resources whatever the reason.
- Holding a ClusterQueue does not clear the LocalQueue AFS usage gauge, so the stopped-LocalQueue metric guard from #19267 is not needed here.
