#### What this PR does / why we need it?

Fixes a race in the Dynamic Quota Orchestration scheduler test "should fallback to spec when EffectiveQuotas status is cleared".

The test cleared `status.effectiveQuotas` on the ClusterQueue and created `wl2` as soon as the status update returned. The scheduler cache picks up the cleared status only when the ClusterQueue update event is handled. If `wl2` came first, the scheduler admitted it against the old effective quota of 5 CPU, and the test timed out waiting for it to stay pending. That is what the CI run shows: `wl2` has `status.admission` set.

After clearing, the test now waits for the ClusterQueue info metric to report `dynamic_quota_orchestrator=""`. The cache records this metric in `UpdateClusterQueue`, under its lock, right after it applies the new quotas, so once the metric changes the cache has the spec quota. The file already uses this metric the same way in other tests. The test also waits for the metric to report the orchestrator after setting the effective quota.

"should fallback to spec when Cohort EffectiveQuotas status is cleared" has the same race for the Cohort, and gets the same wait on the Cohort info metric.

Fixes #19324

#### Useful notes for your reviewer

To reproduce locally, add a 3s sleep in the ClusterQueue and Cohort update event handlers when `status.effectiveQuotas` goes from set to nil:

- on main, both tests fail at the `ExpectWorkloadsToBePending` step, and the ClusterQueue test fails at the same line as in CI;
- with this change, both pass with the sleep in place.

The `EffectiveQuotaActive` condition can't be used for this wait. A ClusterQueue reconcile started by another event can remove it before the update handler refreshes the cache, and the sleep reproduces that.
