#### What this PR does / why we need it?

Adds the internal `PreemptionLimit` types to `pkg/scheduler/preemption/policy` for KEP-16925 so follow-up PRs implementing the preemption limit matcher, tracker, snapshot, budget, limiter, controller, and scheduler integration can build on them:

- Add `PreemptionLimitReference`, `PreemptionLimitAggregationKey`, `GlobalAggregationKey`, and `PreemptionLimitAggregationCounts`.
- Add `ConsumedLimit` (with `NewConsumedLimit` and `IsStaleFor`), `ConsumedLimits`, and the `ConsumedLimits` field on `ConfigurablePreemptionReasonData`.
- Add `BlockingPreemptionLimit` with `Message()` and `Earlier()` helpers.
- Add unit tests in `pkg/scheduler/preemption/policy/types_test.go`.

This change introduces internal types only and does not change runtime scheduling or preemption behavior yet.

### Comment by [@dkaluza](https://github.com/dkaluza) — 2026-11-23T17:18:11Z

/lgtm

However since maintainers didn't see the implementation yet, maybe it is worth a little bit to describe why we need non obvious methods.

`Earlier` is needed to identify the limit that will be used both in the condition message and requeue - "earlier blocking limit" will be preferred from multiple limits blocking different candidates.

`IsStaleFor` is needed to identify if preemptions were computed against "previous" version of the limits from the snapshot, therefore they should not increment the currently consumed limits in the system.
 Each scheduling iteration will be using snapshot of the limits frozen in time.  Thereby, limits representation tracked in state may get updated in the meantime, because of the CRD spec updates. 
As in this case the state references already "newer" version of the resource than those that we are trying to consume based on the snapshot, in such situation incrementing appropriate counts will lead to inconsistencies and we shouldn't do it.
