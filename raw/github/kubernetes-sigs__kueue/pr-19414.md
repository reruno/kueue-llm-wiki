## Description

#### What type of PR is this?

/kind bug

#### What this PR does / why we need it?

Fixes #19411

A pending Workload can remain indefinitely in a ClusterQueue's inadmissible set after a `RuntimeClass` overhead change makes it eligible for admission.

The RuntimeClass event correctly triggers recomputation of the Workload's effective resource requests. However, `ClusterQueue.PushOrUpdate` determines whether an inadmissible Workload should be retried primarily from changes to its API spec, generation, and selected status fields.

Since RuntimeClass overhead and LimitRange defaults can change independently of the Workload object, the updated requests are retained in the inadmissible entry without triggering a new scheduling attempt.

Additionally, replacing an inadmissible `Workload.Info` can leave aggregate pending-resource accounting stale when its effective requests have changed.

**Changes introduced**

1. **Retry Workloads when effective scheduling inputs change**
   - Compare `EffectivePodSpecs` and `TotalRequests` when updating an inadmissible Workload.
   - Detect changes caused by external resource defaults, even when the Workload spec and generation remain unchanged.
   - Reuse the existing queue transition and backoff handling rather than introducing a separate scheduling path.

2. **Maintain accurate pending-resource accounting**
   - Subtract the previous effective requests before replacing an inadmissible entry.
   - Add the updated effective requests after replacement.
   - Preserve the existing workload tracking and metrics updates.

3. **Add regression coverage**
   - Verify that reduced effective overhead moves an inadmissible Workload back to the active scheduling queue.
   - Verify that unchanged effective resources do not trigger unnecessary retries.
   - Verify that effective-resource changes respect existing backoff restrictions.
   - Verify that replacing and deleting inadmissible entries maintains correct pending-resource totals.

#### Useful notes for your reviewer

**Implementation scope**

The fix is limited to the queue update and pending-resource accounting paths:

- `pkg/cache/queue/cluster_queue.go`
- `pkg/cache/queue/pending_workloads.go`
- `pkg/cache/queue/cluster_queue_test.go`

No API changes, configuration changes, or new controller watches are introduced.

**Why compare effective resources?**

A Workload's API generation does not capture changes to external dependencies such as RuntimeClass overhead. Comparing the recomputed effective PodSpecs and total requests allows the queue to identify these changes without requiring modifications to the Workload object.

The comparison also avoids relying exclusively on scheduling equivalence hashes, which may be disabled.

**Safety and compatibility**

- Existing in-flight Workload protection remains unchanged.
- Existing backoff and `Requeued=False` checks remain in place.
- Workloads with unchanged effective inputs remain inadmissible, avoiding unnecessary scheduling attempts.
- Existing queue transition logic continues to determine whether a Workload can enter the active heap.
- The fix does not introduce a global inadmissible-queue retry for RuntimeClass events.

**Testing**

Four focused unit tests have been added to cover the retry decision, unchanged-resource behavior, backoff protection, and pending-resource accounting.

Suggested verification:

```bash
go test ./pkg/cache/queue -count=1
```

The tests have not yet been executed in the development environment. CI results and any additional integration-test requirements should be reviewed before merging.

An end-to-end RuntimeClass mutation test is not included in this patch; the current tests isolate the queue behavior responsible for the reported issue.

**Related work**

- #14317 — RuntimeClass overhead changes affecting already quota-reserved Workloads.
- #17385 — Excessive pending-Workload reconciliation on RuntimeClass events.
- #14965 — Retry behavior after LimitRange changes.

This PR addresses the separate transition of a previously inadmissible Workload back to active scheduling after its effective requirements change.

#### Release note

```release-note
Queueing: Retry previously inadmissible Workloads when changes to effective resource requirements make them eligible for scheduling, and keep pending-resource accounting consistent with the updated requests.
```

AI assistance was used in investigating and preparing this change. The resulting implementation and tests are submitted for maintainer review.

### AI summary
`ClusterQueue.PushOrUpdate` now keeps a Workload in the inadmissible state only when both `EffectivePodSpecs` and `TotalRequests` are unchanged. A change to either value removes the Workload from inadmissible and reprocesses it. This replaces the `draRequestsChanged` check. `PendingWorkloads.UpdateInadmissible` subtracts the old requests and adds the new ones, so pending-resource totals stay accurate. Backoff, `Requeued`, and in-flight checks are not modified. Four unit tests were added. They have not been run.

Scheduling: Fixed a bug where a previously inadmissible Workload could stay pending after a RuntimeClass overhead or LimitRange default changed its effective requests, until an unrelated ClusterQueue or cohort event occurred. Kueue now retries such Workloads when their effective requests change.
