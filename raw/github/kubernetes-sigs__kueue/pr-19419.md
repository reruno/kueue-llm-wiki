#### What this PR does / why we need it?

The CapacityBuffer check measured `timeoutSeconds` from the creation of the CapacityBuffers, and only evaluated it after the buffers were created. If a buffer could not be created, for example because an object with its name exists that the Workload does not own, or because the create call keeps failing, the timeout never fired and the workload held its quota indefinitely.

The timeout is now measured from the quota reservation and checked before the buffers are created, so such a workload is set to `Retry`, evicted and requeued after the backoff like any other timeout. In the normal case the buffers are created right after the reservation, so the effective timeout barely changes. The `timeoutSeconds` API comment, the generated references and the KEP are updated to say where the timeout is measured from, as suggested in https://github.com/kubernetes-sigs/kueue/pull/14700#discussion_r4644535059.

Part of #19231 (a timeout that covers failed CapacityBuffer creation).

## AI summary

The CapacityBuffer `timeoutSeconds` now counts from quota reservation, not from buffer creation. The controller checks the timeout before it creates or checks buffers. When the timeout expires and a required PodSet has no ready buffer, the admission check is set to `Retry`. The Workload is then evicted and requeued after backoff. This also applies when buffer creation fails, such as a name conflict with a foreign CapacityBuffer. The foreign buffer is kept. The PR updates the API comment, CRD and reference docs, the KEP, and unit and integration tests.
