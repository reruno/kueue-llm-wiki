## Description

#### What type of PR is this?

/kind bug

#### What this PR does / why we need it?

Kueue adds a new admission check to every workload of the ClusterQueue as `Pending`, including admitted ones, and the docs say that adding an AdmissionCheck does not evict an admitted workload. The CapacityBuffer controller handled that `Pending` check like the check of a workload that waits for admission: it created buffers and measured `timeoutSeconds` from the quota reservation. For a workload admitted earlier than the timeout, the check went to `Retry` right away, so Kueue evicted a running workload because an admin added the check to its ClusterQueue.

A `Pending` check of an admitted workload is now `Ready` without buffers, so the workload keeps running. The KEP Handling table gets a row for this case.

The behavior was reported in https://github.com/kubernetes-sigs/kueue/pull/19419#discussion_r4681840209.

Part of #19545

Without the fix the new spec fails: the workload is evicted and its check is `Pending` with "Reset to Pending after eviction. Previously: Retry" | - |
| Same, at the reconciler level | unit | `go test -count=1 ./pkg/controller/admissionchecks/capacitybuffer/...`: pass; the new case fails without the fix | - |

The CapacityBuffer admission check is in v0.21.0-rc.2, so this PR should land before v0.21.0.

A ProvisioningRequest check added to an admitted workload behaves differently: it creates a ProvisioningRequest for the running workload, and a `Failed` request deactivates it. I checked this with a temporary integration spec, and left it out of this PR.
