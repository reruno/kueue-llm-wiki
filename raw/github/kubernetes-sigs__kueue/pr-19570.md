## Description

#### What type of PR is this?

/kind feature
/area tas

#### What this PR does / why we need it?

TAS delays the topology assignment only for ProvisioningRequest and MultiKueue
admission checks. With a CapacityBuffer admission check, TAS tries to place the
pods on the existing Ready nodes when it reserves quota. The CapacityBuffer has
not provisioned the nodes yet, so on a flavor with no nodes the workload fails
with "no topology domains", never reserves quota, and the check never runs.

This PR:

- Delays the TAS assignment on flavors that use a CapacityBuffer check, like a
  ProvisioningRequest check. Kueue reserves quota with
  `DelayedTopologyRequest=Pending` and assigns the topology in the second pass,
  after the check is Ready. CapacityBuffer checks are not added to the rule that
  rejects MultiKueue together with ProvisioningRequest.
- Applies `timeoutSeconds` of the CapacityBufferConfig to the wait for the
  topology assignment, measured from the time the check became Ready. Without
  this, a workload whose topology never fits (for example, a required rack
  topology when the autoscaler spread the nodes over racks) keeps its quota and
  its CapacityBuffers forever: the buffer fits, the check is Ready, and the
  second pass retries without a limit. ProvisioningRequest leaves this state
  when the booking expires; CapacityBuffer has no booking. The wait is measured
  from the Ready transition, so buffers that fit late still get the full timeout.
- Updates KEP-5133 and the `timeoutSeconds` API doc.

Part of #19398

#### Useful notes for your reviewer

**Open questions**

1. The topology wait reuses `timeoutSeconds`, which is opt-in. The two waits
   differ (provisioning can take long, while a topology that does not fit
   rarely recovers), and ProvisioningRequest always has an exit through the
   booking. Should the topology wait instead have (a) its own
   CapacityBufferConfig field with a default, or (b) a scheduler-level timeout
   for the second pass that applies to every check that delays TAS, including
   external checks once #19398 generalizes the delay? I lean towards (b) and
   kept `timeoutSeconds` as an interim limit.
2. Should a ClusterQueue with both MultiKueue and CapacityBuffer checks be
   inactive, like MultiKueue with ProvisioningRequest (#8347)? This needs a new
   reason constant, and the KEP lists MultiKueue as not supported in alpha, so
   I left it for a follow-up.
3. The timeout change can move to a separate PR if you prefer a smaller diff.

**Limits (documented in the KEP)**

- The CapacityBuffer has no topology request, so a required topology fits only
  if the autoscaler provisions the capacity in one domain.
- TAS does not know which nodes the buffer provisioned and can place the pods
  on other free capacity.
- The topology timeout looks at all PodSets of the workload, as the
  ProvisioningRequest booking expiry does.

**Real cluster**

I ran this branch (image built from 5705768c6) on an AKS 1.36 cluster with
node auto-provisioning (Karpenter), with `CapacityBufferACC` enabled. The TAS
flavor selected 4-CPU nodes, and there were no matching nodes at the start.

| Scenario | Result |
|---|---|
| 2 pods, preferred `kubernetes.io/hostname` | Quota reserved with `DelayedTopologyRequest=Pending`, the CapacityBuffer was created, and Karpenter created a node. The check became Ready after the buffer fit, before the node was Ready. The second pass failed with "no topology domains" until the node was Ready, then assigned the topology to the new node. The workload was admitted and both pods ran on that node, about 100s after submission. |
| 2 pods of 3 CPU, required `kubernetes.io/hostname`, `timeoutSeconds: 240` | Karpenter created one node for each pod, so the buffer fit and the check became Ready (22:27:01). The second pass failed because the pods do not fit on one node. At 22:31:01, 240s after the Ready transition, the check became Retry with "the topology was not assigned within 240s after the check became Ready", the workload was evicted, and the CapacityBuffer was deleted. |

The second scenario is the limit described above: the autoscaler satisfies the
buffer with capacity that TAS cannot use for a required topology.

### Comment by [@OliverMKing](https://github.com/OliverMKing) — 2026-11-25T02:19:54Z

> The CapacityBuffer has no topology request, so a required topology fits only if the autoscaler provisions the capacity in one domain.

This limit isn't ideal but it's not actually really a result of the changes of this pr so it should be a followup instead. I made a poc for something that helps fix this that I could do as a followup that requires no api changes. When we build the buffer's pod template, we can give each buffer a unique label. It can then add a required pod affinity on that label, using the PodSet's required topology level as the topologyKey (preferred affinity for a preferred topology).

```yaml
template:
  metadata:
    labels:
      kueue.x-k8s.io/capacity-buffer: <buffer-name>   # unique per buffer
  spec:
    affinity:
      podAffinity:
        requiredDuringSchedulingIgnoredDuringExecution:
        - topologyKey: kubernetes.io/hostname           # the PodSet's required level
          labelSelector:
            matchLabels:
              kueue.x-k8s.io/capacity-buffer: <buffer-name>
```
