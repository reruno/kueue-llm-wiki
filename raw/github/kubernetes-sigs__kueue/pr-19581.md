#### What this PR does / why we need it?

A Workload that is evicted after it reserved quota but before it is admitted stays at `Evicted=True`, `QuotaReserved=True` forever when it has no owner references. It keeps its quota, is never requeued and never retries its admission checks.

Releasing the quota is the second phase of an eviction, and only a job reconciler does it, after stopping the job. A job reconciler reaches a Workload only through its owner reference. A MultiKueue worker Workload has no owner until it is admitted, so an admission check `Retry` (for example ProvisioningRequest `BookingExpired`) or a preemption on the worker leaves it stuck. When every nominated worker ends in this state, the job is stuck across the fleet while holding quota on the manager and on the workers.

With this PR, the Workload controller completes the eviction of a Workload that has no owner references, is evicted, still reserves quota and is not admitted. It uses the same write as the job reconciler: `Requeued` is set (`True` only for preemption and node failures) and the quota reservation is released. The write is moved to a shared helper in `pkg/workload`. A Workload without an owner has no job that Kueue could have started, so there is nothing to stop first. Workloads with an owner stay with their job reconciler, admitted Workloads are not changed, and the MultiKueue manager is not changed.

Fixes #19072

#### Useful notes for your reviewer

Why the scope is narrow:

- Only Workloads with no owner references at all. Pod-group Workloads have non-controller owner references to their Pods, so "no controller owner" would take them away from the Pod reconciler.
- Only Workloads that are not admitted. Evicting an admitted Workload keeps `Admitted=True` until its quota is released, and the MultiKueue manager may already be creating the remote job for it.
- The ConcurrentAdmission controller already completes evictions this way for its Variants (`clearWorkloadAdmission`); it is left unchanged to keep the backport small.

`test/integration/singlecluster/scheduler/delayedadmission`: the spec "should requeue workloads after a delayed retry" used a Workload without an owner and called `FinishEvictionForWorkloads` to stand in for the missing job reconciler. The Workload controller now does that step, and without a retry delay the Workload reserves quota again before the helper observes `Evicted=True`, so the step is removed. The rest of the spec (retry count, check back to `Pending`, new reservation) is unchanged and passes.

Not covered: there is no MultiKueue-level test. The fix is in the single-cluster Workload controller and the MultiKueue manager code is unchanged; the core integration specs reproduce the worker state from the issue (a Workload without an owner with a `Pending` admission check).

The separate problem at the end of the issue (a `Rejected` worker check makes the manager delete and recreate the remote Workload with a fresh retry history) is not addressed here.

Backport: please consider release-0.19 and release-0.20, as for #18116 on the same path.
