#### What this PR does / why we need it?

`kube-apiserver` does not enable the OwnerReferencesPermissionEnforcement admission plugin by default. However, on OpenShift (where it is enabled by default) or on clusters with this plugin enabled manually, the following issue occurs:

A user submits a job to a ClusterQueue configured with a ProvisioningRequest AdmissionCheck. After the Workload gets a quota reservation, the provisioning controller creates a ProvisioningRequest and a companion PodTemplate. It then moves the controller ownerReference on the PodTemplate from the Workload to the ProvisioningRequest so old PodTemplate objects are garbage-collected when the ProvisioningRequest is retried or deleted.

This step calls `controllerutil.SetControllerReference`, which sets `blockOwnerDeletion: true`. When `OwnerReferencesPermissionEnforcement` is enabled, `kube-apiserver` checks whether the caller has update permission on `<resource>/finalizers` for the target owner resource. Kueue's manager-role declares permissions for provisioningrequests and provisioningrequests/status but omits `provisioningrequests/finalizers`. As a result, kube-apiserver rejects the PodTemplate update with 403 Forbidden.
