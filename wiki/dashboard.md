# Dashboard (KueueViz)

**Summary**: KueueViz is a web UI for Kueue: it reads the Kueue API (and, partially, the [[visibility-api]]) to show per-[[cluster-queue]] usage, pending workloads, cohort utilization, and per-namespace quotas. It's a separate component (backend + frontend) deployed alongside Kueue, not part of the controller-manager.

**Sources**: `raw/github/kubernetes-sigs__kueue/`.

**Last updated**: 2026-09-29

---

## Components

- **Backend** — service account with read access to Kueue CRDs and Workloads; exposes a JSON API consumed by the frontend.
- **Frontend** — a web UI for cluster admins and tenants.

## Scope

KueueViz is oriented at operational visibility, not management actions — edits happen through [[kueuectl]] or plain `kubectl`. The UI covers:

- Cluster-queue list with usage vs. nominal quota.
- Cohort-level views.
- Per-namespace / per-LocalQueue pending workloads.
- Resource utilization plots ([[issue-10072]] — UI improvements).

## Known issues / evolution

- "Kueueviz backend fails to list cohorts due to missing permissions" ([[issue-10091]]) — the backend ServiceAccount needed an RBAC update when cohorts became a first-class CRD.
- "KueueViz: add e2e tests for the resource utilization feature" ([[issue-10132]]) — test coverage catching up to features.

## LocalQueue details: filter by `spec.queueName`

The LocalQueue details page used to list **every** Workload in the namespace regardless of which LocalQueue was selected: the backend `fetchLocalQueueWorkloads` (`cmd/kueueviz/backend/handlers/local_queue_workloads.go`) accepted a `queueName` parameter but never applied it ([[pr-11199]], fixes [[issue-6613]]; cherry-picked to 0.16/0.17 in [[pr-11212]]/[[pr-11213]]). The fix filters `wql.Items` client-side on `item.Spec.QueueName == queueName`. A server-side field selector was rejected because `spec.queueName` is not registered as a selectable field on the Workload CRD — so client-side filtering is used, consistent with `kueuectl list workload localqueue`.

## Namespace selector: WebSocket closed with a status

Selecting a namespace on the dashboard produced a WebSocket `1005` error (no status code) because the backend closed the connection without one. [[pr-14788]] (cherry-picks [[pr-14789]], [[pr-14790]]) closes the socket with an explicit normal-closure status on error and on component cleanup.

## KueueViz cluster RBAC no longer carries a namespace

The Helm chart emitted `metadata.namespace` on KueueViz's `ClusterRole` and `ClusterRoleBinding`, which are cluster-scoped. The API server clears namespace metadata for cluster-scoped resources before validation, so this was a manifest-hygiene problem rather than a rejection; [[pr-14816]] (cherry-picks [[pr-14824]], [[pr-14825]]) removes it while keeping the namespace where it is valid — the ServiceAccount subject and the namespaced `Role`/`RoleBinding`. Regression coverage renders the chart with a non-default release namespace.

## Frontend backend-URL resolution

The frontend reads the backend WebSocket URL from `REACT_APP_WEBSOCKET_URL` / `VITE_WEBSOCKET_URL`. Two bugs produced a blank page or a silent failure: `getBackendWebSocketUrl` threw before render when unset, and the Helm template `frontend-configmap.yaml` built `"<scheme>://<host>"` from `kueueViz.backend.ingress.host`, so an empty host yielded the truthy bare `wss://` and connections to `wss:///ws/workloads` (`new URL()` throws). Fixes: the frontend falls back to the page's same origin when no URL (or a bare-scheme URL) is set, using `wss` on HTTPS pages (source: pr-15293.md; backports pr-15646.md, pr-15647.md); the chart applies `| default "backend.kueueviz.local"` to the host like the other consumers, and generates `ws` or `wss` from the TLS configuration (source: pr-15242.md, pr-15591.md; backports pr-15644.md, pr-15645.md). The frontend ConfigMap kustomize patch must carry `namespace: system` to match the resource, otherwise `kustomize build config/kueueviz` fails (source: pr-15696.md; backports pr-15707.md, pr-15708.md). The `Code generated by yaml-processor` marker was removed from the ConfigMap template since the processing plan never generated it.

## Single-host, path-routed Ingress

By default the browser opens the WebSocket straight at the backend Service, which needs two DNS names, an `env.js` ConfigMap carrying the backend's external address, and `KUEUEVIZ_ALLOWED_ORIGINS` matching the frontend origin. The opt-in Helm value `kueueViz.ingress` (disabled by default) renders one Ingress on one host: `/ws`, `/api` and `/auth` go to the `kueueviz-backend` Service, `/` to the frontend (source: pr-15574.md; backports pr-15673.md, pr-15676.md). The Ingress is generated from the shared config directory, so non-Helm installs get an equivalent single-host manifest (docs cover host, TLS and migration) (source: pr-15863.md, issue-15669.md).

## Open backend bugs

After the move to the typed client (pr-7663) the handlers return bare objects: the workload detail handler `fetchWorkloadDetails` drops `clusterQueueName` and `preemption` (the page shows no ClusterQueue and links to `/cluster-queue/undefined`, [[issue-16275]]), and the `/ws/workloads` list returns the raw `WorkloadList`, so the "Preempted" column always shows "No" ([[issue-16276]]); both open at writing. Backend tests now run in CI (source: pr-16257.md).
