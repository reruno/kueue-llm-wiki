# Security — Supply Chain

**Summary**: Patterns from the 6 Supply Chain CVEs in `raw/cve/`. Smallest category in the corpus, but the one whose impact scales to every Kueue deployment because a compromised release artifact affects all downstream clusters at once.

**Sources**: `raw/cve/` — representative entries `CVE-2020-8564.md` and other supply-chain category CVEs; CWE-295 (improper cert validation) and CWE-494 (download of code without integrity check) entries broadly.

**Last updated**: 2026-05-18

---

## Why this matters for Kueue

Two pipelines define Kueue's supply chain:

1. **Build & release** — `kubernetes-sigs/kueue` → container image at `registry.k8s.io/kueue/kueue:vX.Y.Z`. The release process is described in [[release-process]]; [[reviewer-tenzen-y|tenzen-y]] is the de-facto release manager.
2. **Dependencies** — `go.mod` / `go.sum` — every Kubernetes client-go, controller-runtime, and integration SDK update flows through here. [[reviewer-mbobrovskyi|mbobrovskyi]] is the project's dependency-bump approver.

A compromise in either pipeline runs Kueue's controller pod with attacker-chosen code, inheriting the manager-role ClusterRole on every cluster running Kueue.

## Patterns to flag in review

From the shared `Security Code Patterns` block in supply-chain CVE files:

- **Image references without digest pinning** (`image: foo:latest`).
- **Missing image signature verification before admission.**

For the broader supply-chain surface, the additional patterns are:

- **`go.mod` updates without justification.** Every replace directive, every direct dependency added, every major version bump deserves an explicit reason in the PR body.
- **`go.sum` mutations divorced from `go.mod` changes** — sign of tampering.
- **Build-time scripts pulled from the internet** in `Dockerfile`, `Makefile`, or CI YAML (`curl ... | sh`). None should exist; verify on review.
- **Unpinned actions in GitHub workflows** (`uses: org/repo@main` rather than a SHA). Prow + the SIG infrastructure pin to SHAs by convention.

## Specific anti-patterns by CWE

### CWE-295 — Improper certificate validation

In Kueue, the canonical instances are:

- `tls.Config{InsecureSkipVerify: true}` anywhere in `pkg/`. Must never appear outside `_test.go` files. `git grep -n 'InsecureSkipVerify' pkg/` should return nothing.
- [[multikueue]] kubeconfigs with `insecure-skip-tls-verify: true`. The controller should reject worker kubeconfigs flagged insecure, or at least log a prominent warning.
- HTTP clients constructed without a custom `TLSClientConfig` — relying on Go defaults is fine for HTTPS, but any custom transport that omits cert pinning when talking to a non-API-server endpoint is suspect.

### CWE-494 — Download of code without integrity check

- Tooling installs in `hack/` scripts that `curl | sh` are the canonical case. Audit `hack/tools.go` and `hack/*.sh`.
- Helm chart dependencies — if Kueue's chart ever pulls a sub-chart, pin to digest, not version range.

## Release & artifact hygiene

Items that the project already does and reviewers should preserve:

- **Multi-arch images published to `registry.k8s.io/kueue/`** — the SIG infrastructure handles signing via the GCP KMS chain.
- **Reproducible builds** — `go build` with pinned compiler version via `.go-version`.
- **Release notes** — every release lists CVE-fix references when present (none yet for Kueue itself).

Items that aren't yet routine but should be flagged for new code:

- **Cosign signature verification example** in install docs for users who run Kueue under a strict policy controller.
- **SBOM publication** — generated by SIG-release tooling; verify it ships with each release.

## Mitigation pattern in CVE corpus

> Pin all container images to their digest (`:tag@sha256:...`). Enable image signature verification via Cosign/Sigstore. Use admission webhooks to reject unsigned or unpinned images.

Applied to Kueue itself:

- The bundled `config/default/manager.yaml` should reference `registry.k8s.io/kueue/kueue:vX.Y.Z@sha256:...` in release builds (the dev manifest uses `:devel` — that's fine for development).
- Downstream installers (Helm chart, kustomize) should preserve the digest when pinning.
